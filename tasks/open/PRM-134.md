Also from his runs:
- NVIDIA A2000: all 256 rows match in every check.
- On Intel, every run has 256 departing rows.
- With 400b86ce93 (full subgroups) on top, the plain test still fails 6 of 6, with the same forms.

**My reading. Check it; don't take it as given.**
- In the dynamic-header path of `LookupTableWord` (`SpirvImageEmitter.cpp` ~2093-2101), the child header's eight fields are eight `OpLoad`s from `table_map` at `header + 0..7`, where `header` (the root code) differs per lane.
- On Intel the words that come back wrong are all in the upper four: `TableBaseLow` (+4) and `TableFault` (+7). `mapStart` (+0), `keys` (+1) and `mapped` read correctly.
- In the poison row, `child.baseLow` = 0x104 = 0x41 × 4, the byte address of that lane's header, not a value from the map. `child.fault` = 0xeddfd600, the other root record's low word (map[189]).
- The departing lanes come in 16-lane blocks.
- That pattern fits the eight adjacent loads being combined into wider loads and split per 16 lanes, with the upper part's results landing wrong. It doesn't fit a wrong index: the lower words are right.

## What to do

1. **Check the reading against the module.** Recompile the arm program's two-lane module for a 32-lane host, as in PRM-130, and disassemble the child-header loads of the pc 0xfc lookup.
   - Confirm they are eight adjacent `OpLoad`s of `header + k` through `OpAccessChain` on the `table_map` SSBO.
   - Say whether anything between them could stop a compiler combining them: barriers, control flow, or a `Volatile`/`Coherent` decoration.
   - Note the memory model and the decorations of the `table_map` variable.
   - Say whether the `0x290000000a4` fault address can be formed from any value in these rows. For example, its low word `0xa4` = `offset + 4`. If it can't be, say so.
2. **One variant branch, `prm/9969-intel-split`, on top of `prm/9969-intel-trace` (992d97fae8)**, so the trace still records. One change only: the child header's field loads in the dynamic-header path can no longer be combined. Pick the smallest form that spirv-val accepts for the module's memory model, for example:
   - the `Volatile` memory operand on those eight loads;
   - or, if `Volatile` isn't valid there, another per-load operand or structure with the same effect.
   Say which you chose and why. Leave every other load as it is, and the static-header path untouched. Prefer the change always-on in this branch over an environment switch, since the trace argument already bypasses the shader cache.
3. **Lavapipe proof:**
   - spirv-val passes on the two-lane module and on the dispatched modules;
   - `--pointer-vsharp-child-key-arm-trace` 3 of 3, decoding with 256/256 per check as before;

   - the 51-test set.
