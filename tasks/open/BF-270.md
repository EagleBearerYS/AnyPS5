# BF-270: rework B266-1 (libSceFreeTypeOt ft_mem_*) to reuse main's FreeType::GuestMemoryRec

from: Bug Finder
for: any
priority: high

## Why

BF-266 built fork `feat/libSceFreeTypeOt-sourced-b266-1` **9069d95ba6**, with the 8 `ft_mem_*` rows. It adds `struct GuestMemory` to `core/libs/prx/libSceFreeType/include/GuestFreeType.hpp`. But main already has the same record as `FreeType::GuestMemoryRec`, in `core/libs/prx/libSceFreeType/include/GuestList.hpp:22` (alloc, free and realloc callbacks, used by `FT_List_Finalize`). Two types for one guest layout is something a reviewer will flag.

The family next to it is santhoshkumar-dev's open allocator series:
- **#12004:** `feat(libSceFreeType): implement the legacy memory allocators`;
- **#12373:** `FT_Realloc`/`FT_QRealloc`, in `libSceFreeType/src/MemoryAllocation.cpp` with `MemoryAllocation.hpp` in both libSceFreeType and libSceFreeTypeOt, citing FreeType 2.4.12 ftutil.c.

## Do

1. **Drop `GuestMemory`,** and use `FreeType::GuestMemoryRec` from `GuestList.hpp` in `Memory.hpp`, `Memory.cpp` and the test. Keep the layout `static_assert`, moved next to `GuestMemoryRec` if main doesn't have one. Add it as a new commit on the branch. Don't rewrite 9069d95ba6.
2. **Read #12004 and #12373** (upstream `refs/pull/12004/head` and `refs/pull/12373/head`):
   - Do they add their own memory record type, or helpers our `ft_mem_*` could share (a qalloc/qrealloc core)?
   - Is FreeType 2.4.12's `ft_mem_*` the same as 2.13.3's for our 8 functions? If it differs, list each difference.
   - Run `git merge-tree` of our branch with each, and give the files and lines.
   - Don't take their code. Report only what would make the two compose (for example, whether a shared helper could live in a header that one of the two adds).
3. **Rerun** `guest_freetype_ot_memory` with `--repeat until-fail:10`, plus the FreeType suite, `check_conventions`, MinGW `-fsyntax-only` and the comment-line count.
