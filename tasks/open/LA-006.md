## Why

BF-046 (`results/cloud-2/BF-046.md` on `cloud-results`) measured driver CPU per draw on a Resident Evil Village-shaped frame on lavapipe (850 draws per frame, a 2,000-entry T# table, object V#s that move every frame). The harness is `tests/execution/VillageDrawCost.cpp` on fork branch `exp/bf046-main` b7d6d98610:
- today's path: 471 µs per draw;
- fable-void's run-time path: 173 µs;
- the floor: 57.5 µs.

His 173 µs splits into a fresh `ShaderResources` build on every draw (80 µs), recording (55.5), his pre-pass (44) and the target refresh (10.9).

**The AnyPS5 Project Manager's checkpoint (S4):** lane A keeps run-time resolution and takes BF-046's binding changes in order:
- **change 1:** key builds by program pair, pipeline layout and target formats, keep them per program, and put per-draw data in push constants or a ring;
- **change 2:** bind the heap and the device table once, not per draw.

**The bar:** with both in, our port must reach about **80 µs of driver CPU per draw** on BF-046's harness. This run is the checkpoint, reported to the PM whether it passes or not. If it can't get there, the GPU-prologue design comes back.

**Where lane A stands.** Its first piece reads image tables at run time through a device key table on PR 6947's heap, on fork `exp/lane-a-join`. Read `results/cloud-*/LA-002.md`, `LA-003.md` and `LA-004.md` first. Three facts about it:
- device-table images work only in non-GPU-mode stages, with the heap at set 2 and our table at set 3, bound per draw;
- main's per-draw `ShaderResources` build stays for everything else;
- PR 6947's GPU mode, which already does changes 1 and 2 for its stages (heap stage templates keyed per program in `MaterializeHeapStage` and `heapTemplates`, a per-draw data ring in `BindlessHeap::Allocate`, the heap set bound per batch), skips **indirect draws**, on one condition: `heapCandidate = ... && !drawParameters.indirect && HeapFragmentsEnabled()` (`Execution/src/Driver/Draw/DrawCapture.cpp` ~41).

Village's menu draws are nearly all indirect: CPU-path `DRAW_INDIRECT` and mesh draws, and GPU-side indirect draws. Raghav314 wrote on PR 6947 that "image tables and indirect draws in GPU mode are not on my list", so they are ours to do, as a follow-up with "Depends on: #6947".

Handle the real reason: per-record user data, base vertex or instance, draw id or draw count.
   - **The stale-read risk (Bug Finder, BF-051).** If you read indirect arguments or counts on the CPU to fill per-record data, a store through the BDA table isn't a pending write until `markWrittenPages` at `CheckFault`, and `FlushForAccess` syncs only on `PendingWriteOverlaps`. So `ReadDrawArguments` and `ReadDrawCount` can read old values. Either keep the arguments GPU-read, or finish pending table stores before the CPU read (upstream PR 6786's `FinishLeaseWork` shows how). Add BF-051's red test, `agc_driver_bda_store_cpu_indirect_read` (fork `test/bda-store-cpu-read` 9a87fa97ca, 20/20 red on main), and say what it shows on your branch.

It conflicts with this base in `Draw.cpp` and `DrawCapture.cpp`. Keep your change compatible with it: before pushing, test-merge 6a5ae80c63 onto your head, and report the conflicts and whether both still pass their tests together.
2. **Device tables inside GPU mode.** Let a GPU-mode stage have device-table images too: the heap arrays are already its set 1, and the device table needs a set or bindings of its own.
   - Today GPU mode uses set 1 (heap), set 2 (data, `GpuDataSet`) and set 3 for compute workgroup memory (`GpuWorkgroupMemoryDescriptorSet`). Choose a layout that keeps to 4 bound sets where it can, and fall back to the CPU path per device where it can't.
   - Lift LA-002's "GPU-mode stages keep the CPU table path" rule for the stages you cover.
3. **Bound once.** Bind the heap set and the device table set once per command buffer, or once per batch, not per draw.
   - Vulkan keeps a set bound across pipeline changes only while the layouts agree for every lower set. Order the sets, or make their lower layouts compatible, so it holds for consecutive draws.
   - Never bind the heap set in the same `vkCmdBindDescriptorSets` call as a set with dynamic offsets, because lavapipe would copy the 28 MiB heap set on every such call (LA-007). That applies to our set 2/3 bind and to PR 6947's `BindHeap` (heap plus its dynamic data set) wherever your GPU-mode draws use it.
   - Report the binds per draw before and after, and how many of them carry dynamic offsets.
