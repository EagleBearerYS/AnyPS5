# LA-009: lane A, stop false ring-overflow fallbacks. Count an overflow only for a batch recorded after its keys' inserts, and record each missing key once per batch, not once per lane
from: AnyPS5 lane A (PC session)
for: any
priority: high

## Why

LA-007's interim result (`results/cloud-4/LA-007.md` on `cloud-results`) found that the device image table's ring-overflow fallback depends on timing.

**The mechanism.** `DeviceImageTable::drain` (`Graphics/src/DeviceImageTable.cpp` ~670 on fork `exp/lane-a-bind`) counts a batch toward `overflowStreaks` when it dropped records while `pending` is empty. Batches recorded before the first drain's misses were inserted still overflow, and they drain after those misses are resolved. When the CPU runs a few batches ahead, three of them count in a row, although none was recorded with the warm table. The program then takes the CPU table path ("its misses overflowed the ring of 4096 records in 3 batches in a row").

**What LA-007 saw:**
- **After 421d8d343** made the bench fast, the fallback happens in every unprofiled run of LA-004's `--village-bench`, imports and copies alike.
- **Before it,** it already happened with copies.
- **On lavapipe** the CPU path then OOMs at about 13 GB.

**A second cause makes it worse on real frames.** Every missing lane appends a record: 128 per draw on the bench's 64×4 target (LA-004's open problem 3).
- A full-screen draw at 1080p has about 2 million lanes, so one new texture overflows a 4,096-record chunk at once.
- With the counting fixed, three batches in a row that each bring a new texture would still fall back, as happens when textures stream in.

**Why it's urgent.** Resident Evil Village's A2 run on the PC is at **16:40 PT** today. If its cold frames send programs to the CPU path through this, A2 measures a false "few draws on the path". Lane A's kill rule reads exactly that number. Push by about **14:30 PT** if you can, so the fork's Windows Build and the PC build still fit. If you can't, push whatever is done and say so.

## What to do

1. **Count only batches that had the inserts.**
   - Tag each ring chunk, when it is taken for a batch, with the table's insert generation: a counter that moves whenever a resolve inserts keys.
   - In `drain`, an overflowing batch adds to a program's streak only if its chunk was taken after the inserts that resolved the misses it overflowed on. One way: the chunk's generation is at or after the generation at which the program's last missed keys were inserted.
   - Batches recorded earlier don't count, and don't reset the streak either.
   - Keep `OverflowBatches` and the fallback message as they are.
2. **One record per missing key per batch.**
   - Make the miss append in the recompiler's device lookup record each distinct missing key at most once per batch, plus any hash collisions, whatever the draw's size.
   - **Suggested mechanism:** a small open-addressed table of seen key hashes in each ring chunk. Use the lookup's own Murmur3 hash, and `OpAtomicCompareExchange` on `hash | 1`. The lane that sets the slot appends; a lane that finds its own hash skips; a lane that finds another hash appends anyway.
   - **A per-wave election first** (`OpGroupNonUniformBallot` with a broadcast of the first lane's key) cuts the atomics for wave-uniform keys. Use it if the recompiler's subgroup emulation makes it cheap.
   - **Clear the seen table** when the driver takes the chunk, where it already clears the header.
   - Bump the ring's ABI version and `FormatVersion` if the layout changes.
   - Faults (`FaultFlag` records) keep their rule. Say whether you dedup them too.
3. **Keep it honest.** The fallback must still happen when a program really misses more distinct keys than the ring holds, batch after batch, with the table warm.
