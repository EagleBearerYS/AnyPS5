# BF-110: run the sample-order tests under Vulkan validation, to find what in `SampleOrders::Depth`'s draw loses the device on AMD
from: Bug Finder
for: any
priority: high

## Why

DavidSamir reports on #6683 (ours, merged; https://github.com/boykopovar/AnyPS5/pull/6683#issuecomment-6315373710): on a Radeon 680M (Windows, AMD 32.0.21030.2001, main 27fabb6b7), `agc_driver_sample_order_grid_reference` loses the device in the exact path's `SampleOrders::Depth` (`core/libs/prx/libSceAgcDriver/Graphics/src/SampleOrder.cpp`).
- **Their bisection with early returns:** skipping only `draw(pass.depth, 0u, 0xffu, 0u)` stops the fault. The image copy, the barrier and the descriptor writes before it don't cause it.
- **Their suspect, an out-of-range `texelFetch` sample index from `DepthPush.map`, is ruled out on main:**
  - `Graphics/shaders/SampleOrder.frag` reads `(map >> (gl_SampleID * 4)) & 7` only for `gl_SampleID < samples`;
  - `SameSetSampleOrder` (`Graphics/src/State.cpp`) writes only guest indices below `samples` into those nibbles;
  - `InvertSampleOrder` permutes them;
  - the test's own 2x orders are `KeptSampleOrder` and `0x76543201`.
- **The path:** the test reaches it by forcing the exact path (`emulated.sampleLocationGridSampleCounts = 0u` in `GridReference`, `tests/execution/SampleOrder.cpp`). The draw renders into the test's located 2x D32_SFLOAT target with sample locations, from a 2x copy sampled as `texture2DMS`, writing `gl_FragDepth`.

lavapipe and NVIDIA don't fault, so it's most likely a spec violation that AMD's driver punishes. The validation layers name violations like that.

## What to do

On upstream `main` (give the commit). This is a diagnostic; a fix only if it's clear.

1. **Validation:** run the sample-order tests on lavapipe with `VK_LAYER_KHRONOS_validation`:
   - `agc_driver_sample_order_grid_reference`, `agc_driver_sample_order_recipe_depth_locations` and the other `agc_driver_sample_order_*` tests.
   - Turn on synchronization validation and GPU-assisted validation, through `VK_LAYER_ENABLES` or `vk_layer_settings.txt`. Say which settings you used.
   - Install `vulkan-validationlayers` if the machine lacks it, and give the version.
   - Report every message raised inside `SampleOrders::Depth`, `SampleOrders::Storage` and the copy, transitions and render pass around them, with VUID, text and the call. Messages elsewhere are noted, but only those matter.
2. **Read the draw's setup against the spec** and say whether each of these is valid:
   - **the copy image** (`CopyImage`): it is created without `VK_IMAGE_CREATE_SAMPLE_LOCATIONS_COMPATIBLE_DEPTH_BIT_EXT`, while the target has it. It is copied from a target that was transitioned with sample-locations info, then sampled as `texture2DMS` in `GENERAL`;
   - **the descriptors:** for `SampleOrderMethod::Depth`, only binding 0 is written (`stencil ? 2u : 1u`), but the layout has two bindings. Is binding 1 statically used by the `SAMPLE_ORDER_DEPTH` SPIR-V? Check with `spirv-dis`;
   - **the dynamic stencil state:** dynamic stencil write mask and reference are set on a pipeline whose depth-only format has no stencil;
   - **the render pass and pipeline sample locations:** the render pass begins with `VkRenderPassSampleLocationsBeginInfoEXT`, and the pipeline has `sampleLocationsEnable` with a {1,1} grid;
   - **sample shading:** `sampleShadingEnable` with `minSampleShading = 1.0` and `gl_FragDepth` at 2x;
   - **the extents:** the copy extent against the framebuffer region and `gl_FragCoord`.
3. **A CPU check** in the test (or `RecordSampleOrder` under a debug flag): every nibble a map word gives for `sample < samples` must be below `samples`. Run it over the test's orders and `SameSetSampleOrder`'s output for random location sets at 2, 4 and 8 samples, so the index question is closed by a test.
4. **If validation names a violation:** fix it on a branch `fix/agc-sample-order-depth-<what>`, with a test that fails without it.
   - Make that test fail on lavapipe through the validation layer: a run under `VK_LAYER_KHRONOS_validation` that fails on any message in that pass. Or check the condition directly.
   - Give the red (the fix reverted) and green.
   - If nothing is named, say so, and list the two or three settings most likely to differ on AMD, so the PC can ask the reporter to try them.
