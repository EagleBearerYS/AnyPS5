## The design both halves share (lane A, first piece)

**What changes.** Today, for a T# that a shader loads from a table at a key it computes, the CPU snapshots every record the key can select and resolves each one at every capture. On upstream main, Resident Evil Village's menu snapshots tables of 32,768 records (48-byte records, the T# at byte 16) at about 8 ms each.

With `APS5_GPU_PATH=1`, a qualifying table column (rules below) is read at run time instead:
- the shader loads the T# itself, through the table's V#, with its own scalar loads;
- it hashes the T# with the image interface id and the sampler class;
- it probes a device-side key table (fable-void's DeviceImageKeys, already on the base branch);
- it samples through Raghav314's global image heap (upstream PR 6947's `BindlessHeap`, on the base branch) at the slot and view mode the bucket names.

A miss or a null T# returns zeros, and a miss appends a record to the batch's miss ring. After the batch completes, the driver resolves each distinct missed key with the CPU table path's checks, takes a heap slot, and inserts the entry before the next batch.

With the switch off, nothing changes: the SPIR-V, the disk cache output and the driver's work are identical to the base.

**Qualifying columns (this piece):**
- The T# comes from a V#-addressed table: the descriptor dwords are `ReadConstBuffer` (s_buffer_load) at key·stride + addend. Pointer tables (`LoadAddressU32`) and indirect columns (a record holding a pointer to the T#) stay on the CPU path.
- Every access of the column is `ImageSampleRaw`, `ImageGatherRaw`, `ImageRead` (a texel fetch from a sampled image), `ImageQueryDimensions` or `ImageQueryLod`, without packed or byte-element addressing (`MemoryInfo::imagePacked`, `imageByElements`).
- No sampler, or a direct sampler. Sampler tables stay on the CPU path.
- A sampled-class image: not storage, written or atomic, no depth compare (color-compare emulation), no unnormalized sampler. fable-void's 0d921f9838, bf9b077db5, debc03fce5 and 84d7ee7af4 are the later ports for these.
- Any stage: compute (his d35b01a5b8) and the draw stages (his 1ffc203905). Resident Evil Village's queue-0 draws are all indirect, so indirect draws must qualify too.
- Not a stage compiled in PR 6947's GPU mode (`gpuResolvedImages`). GPU mode with device tables is a later piece.

**Descriptor sets** of a non-GPU-mode stage with at least one device-table image (the names and values are fixed, so both halves add identical lines and merge cleanly):

```cpp
// core/shader/recompiler/RuntimeAbi.hpp, right after "inline constexpr std::uint32_t GpuDataSet = 2u;"
inline constexpr std::uint32_t DeviceHeapSet = 2u;
inline constexpr std::uint32_t DeviceTableSet = 3u;
inline constexpr std::uint32_t DeviceTableBucketsBinding = 0u;
inline constexpr std::uint32_t DeviceTableRingBinding = 1u;
// core/shader/recompiler/PipelineSpecialization.hpp, right after "UnnormalizedBaseLevelBase = 57408u;"
inline constexpr std::uint32_t DeviceSamplerClassBase = 58368u;
// core/shader/recompiler/Recompiler.hpp, struct SpirvTarget, right after "    bool gpuConstantsVerify = false;"
    bool deviceImageTables = false;
// core/shader/recompiler/Recompiler.hpp, struct CompiledShaderArtifact, right after "    std::uint32_t samplerSlotDword = 0;"
    bool deviceImageTables = false;
```

`SpirvTarget::deviceImageTables` is the recompile option: the driver sets it when `APS5_GPU_PATH=1`, and it is part of the cache key. `CompiledShaderArtifact::deviceImageTables` (and so `RecompileResult`'s) tells the driver that a stage samples device-table images and needs sets 2 and 3.

- **Set 2 (`DeviceHeapSet`)** is PR 6947's heap set unchanged: `BindlessHeap::HeapLayout()` and `HeapSet()`. It holds a sampled-image array per kind at `RuntimeAbi::BindingNumber(Stage::Fragment, kind)` for kind in [FirstImageBinding, FirstStorageImageBinding), each `GpuImageHeapSlots` long, and the samplers. The shader declares only the kinds its modes use.
- **Set 3 (`DeviceTableSet`)** is new and owned by the driver's device image table:
  - binding 0 (`DeviceTableBucketsBinding`): a read-only storage buffer holding the 16-word header (`DeviceImageTableAbi::HeaderWords`; the shader uses `HeaderMask` and `HeaderRingCapacity`, and the address words stay zero), then the buckets, `BucketWords` each. It is sized once for the largest table (2^17 buckets).
  - binding 1 (`DeviceTableRingBinding`): a dynamic storage buffer at the batch's miss-ring chunk. It holds the count at `RingCountWord`, then `RecordWords`-word records from `RingRecordsWord`: the 15 key words, and the pc at `RecordPcWord`. A fault record sets `DeviceImageTableAbi::FaultFlag` in its pc word.
  - Both are plain storage buffers, not device addresses, so no Int64 or BDA is needed for the table.
- **Graphics pipeline libraries:** both library layouts carry identical set 2 and set 3 layouts, as PR 6947 does for its heap set (VUID-VkGraphicsPipelineCreateInfo-flags-06729, -06756).

**The key** (`DeviceImageTableAbi::Key`, 15 words), as fable-void's head has it:
- words 0–7: the T# as the shader loaded it;
- words 8–9: the 64-bit image interface id;
- word 10: the sampler class;
- words 11–14: S# words, zero in this piece (the `RuntimeSampler` bit clear).
- The hash is `DeviceImageTableAbi::Hash` (Murmur3), with linear probing over at most `ProbeSteps` buckets from home = hash & mask.

**The image interface id** is fable-void's `ResourceMaterializer::DeviceImageInterfaceId(image, modes)` from d35b01a5b8: a 64-bit FNV-1a over the normalized `ImageResource` and its runtime modes, a compile-time constant in the shader. `RegisterDeviceImageInterfaces` records each id with its image and modes when a result is materialized, and `FindDeviceImageInterface(id)` returns them. The driver needs that to resolve a missed key.

**The sampler class** of a direct sampler is computed on the CPU from its S#, with fable-void's class bits (`DeviceImageTableAbi::Sampler*`: minmax, opaque-black border, non-seamless cube, float/integer border, aniso override, reduction, exact-at-base), the way his d35b01a5b8 and 81119eea49 fill `HeaderSamplerClasses`. It reaches the shader as specialization constant `DeviceSamplerClassBase + sampler`. No sampler means class 0.

**The bucket value** (`DeviceImageValue`):
- `slot`: the heap slot in the kind array of the chosen mode, from `BindlessHeap::TextureSlot(kind, texture, view, layout)`;
- `mode`: the index into the interface's mode list;
- `fault`: 0, or 1 + `ImageTableAbi::PoisonReason` for a descriptor the CPU path would poison or the driver rejects;
- `samplerSlot`: 0 in this piece.

**Shader behaviour:**
- A null T# (`word0 == 0 && (word1 & 0xff) == 0`) does no lookup and returns zeros.
- Lanes with EXEC clear record nothing.
- A hit with fault 0 samples through the mode's heap array at the slot. Main's table path already emits the mode switch (`EmitTableImageCall`, `tableAccess.element`); here the heap arrays are the table image variables.
- A hit with a fault returns zeros and appends a fault record. The driver reports it after the batch the way the CPU path does when a lane selects a poisoned entry: the same error text and reason.
- A miss returns zeros and appends the key and pc while the ring count is below capacity.
- The lookup may stay a DontInline function, as fable-void wrote it. Report module words.

**Driver behaviour:**
- **Ownership.** One device image table per device, created only when `APS5_GPU_PATH=1`. It holds the host `DeviceImageKeys` (4096 buckets at first, at most 2^17), the device bucket buffer and the ring.
- **Uploads.** Before the first draw or dispatch of a batch that uses the table, record the changed buckets (`TakeChanged()`, or everything after `Rebuilt()`) and the header into the command buffer, with a transfer-to-shader barrier.
- **The ring.** Each in-flight batch gets its own chunk, bound through the dynamic offset, with its count reset before the batch. When the batch's fence or timeline completes, decode the chunk (first record per key, overflow counted), resolve, insert, and report faults.
- **Resolution.** `FindDeviceImageInterface(id)` gives the image and its modes. Pick the mode with the same check the CPU table path applies per record (`ResourceMaterializer::TryRuntimeImageMode` and the poison rules of `ResolveImageTables`). Get the texture through the texture cache as a direct binding of that mode would, a converted format through its decoded copy. Take a heap slot and insert.
- **References.** An entry holds its `Texture`, so the heap's sweep keeps the slot. A dropped entry's reference is released only after every batch that could have sampled it has completed.
- **Freshness.** Before a batch that uses the table, entries whose texture memory the CPU wrote since their last refresh are made current through the texture cache's own path. GPU-written memory under an entry (render targets, storage results) reaches it the way it reaches a direct binding (fable-void's 54ef9042a7 and cfaef76b7f are the reference).
- **Eviction.** `Retain` under a budget (live entries or texture bytes), least recently used first (his 0a90d704ec).
- **Snapshots.** The table snapshot is skipped for device-table images, so the CPU reads no table records for them.
- **Copied ranges.** The device path must work where guest memory can't be host-imported: Linux without `/dev/udmabuf`, as on the workers. The table's V# range and the textures reach the GPU through main's copy paths there; never require an import. (This is checkpoint S's rule for every lane: fable-void's 68cc97aed0 requires imports and fails 239 tests on Linux.)
- **Profiling.** With `APS5_PROFILE_DRAW=1`, a `[device-images]` line every 10 s gives: records drained, distinct misses, dropped records, inserts, faults, refreshes, evictions, live entries, buckets and bytes uploaded.

## What to do (the driver half)

1. **The switch.** Add `APS5_GPU_PATH=1` (read once, as PR 6947 reads `APS5_GPU_HEAP`). When it's set, the driver sets `SpirvTarget::deviceImageTables` on the recompile requests it builds (`Execution/src/ShaderDeviceProfile.cpp` and wherever `SpirvTarget` is filled), and creates the device image table. When it's unset, nothing else changes.
   - Add only the shared lines the design fixes (the two `deviceImageTables` fields, the RuntimeAbi and PipelineSpecialization constants), exactly as written there.
   - Leave the recompiler's use of them to LA-002 (`CacheKey.hpp`, the tracker, the emitter).
2. **The device image table** (`Graphics/include/DeviceImageTable.hpp`, `Graphics/src/DeviceImageTable.cpp`). Port fable-void's DeviceImageTable from d35b01a5b8 and his later fixes to it (81119eea49's insert path, a0080950fe, 0a90d704ec, 54ef9042a7, cfaef76b7f), changed to this design:
   - **Set 3.** Its set layout, pool and set: binding 0 is the bucket buffer (device-local, sized for 2^17 buckets plus the header); binding 1 is the ring, a dynamic storage buffer, host-visible, one chunk per in-flight batch, about 4096 records each.
   - **Uploads.** Changed buckets and the header are recorded into the batch's command buffer, with barriers, before the first draw or dispatch that uses the table.
   - **The ring.** Each batch resets its chunk's count and binds the chunk through the dynamic offset. When the Recorder reports the batch complete, decode the chunk with DeviceImageKeys' ring decoder, then resolve, insert and report faults.
   - **Resolution.** Take a missed key's interface (image and modes) through an injected lookup, `std::function<std::shared_ptr<const Interface>(std::uint64_t id)>`. Production wiring to LA-002's `ResourceMaterializer::FindDeviceImageInterface` is LA-004's job; your tests inject their own interfaces.
     - Choose the mode with the CPU table path's per-record checks: `ResourceMaterializer::TryRuntimeImageMode` and the poison rules of `ResolveImageTables` in `ResourceMaterializer.cpp`, the way main decides a table record. If the symbols you need aren't exported from the recompiler library yet, add them to its export list.
     - Get the texture through the texture cache as a direct binding of that mode would (find the call the ImageTable role's binding makes per element in `Graphics/src/ShaderResources.cpp`), a converted format through its decoded copy.
     - Take `BindlessHeap::For(context).TextureSlot(kind, texture, view, layout)` for the mode's kind, and insert `{slot, mode, fault 0, samplerSlot 0}`.
     - A descriptor the checks reject is inserted with `fault = 1 + reason`. A fault record drained from the ring then raises the same error the CPU path raises when a lane selects a poisoned table entry, naming the T# words and the reason.
   - **Lifetime.** An entry holds its `std::shared_ptr<Texture>`. An entry dropped by eviction, or replaced, releases its texture only after every batch that could have sampled it has completed (the Recorder's serials), so the heap's sweep can't reuse a slot under a pending batch.
   - **Freshness.** Before a batch that uses the table, make current the entries whose texture's guest memory the CPU wrote since their last refresh, using main's write tracking and the texture cache's own refresh path. It costs nothing when nothing was written: no walk over all entries per batch. Keep an index from tracked memory to entries, or use the texture cache's change notification if one exists. GPU-written memory under an entry has to reach the entry the way it reaches a direct binding of the same T#: read how the texture cache handles pending GPU results, and port the intent of fable-void's 54ef9042a7 and cfaef76b7f.
   - **Eviction.** Through `DeviceImageKeys::Retain`, least recently used first, under a budget: live entries (16384 by default) and texture bytes (follow 0a90d704ec's policy).
   - **Profiling.** With `APS5_PROFILE_DRAW=1`, a `[device-images]` line every 10 s: records drained, distinct misses, dropped records, inserts, faults, refreshes, evictions, live entries, buckets, upload bytes.
3. **Pipeline layouts and binding:**
   - **Layouts.** A stage set where some stage's result has `deviceImageTables` gets set 2 = `BindlessHeap::HeapLayout()` and set 3 = the table's layout in its pipeline layout, for graphics and compute, non-GPU mode only.
   - **Pipeline libraries.** Both library parts carry the same set 2 and set 3 layouts, as PR 6947 does for its heap set.
   - **The journal.** The pipeline journal records and replays these layouts.
   - **Binding.** At draw or dispatch, bind set 2 = `BindlessHeap::HeapSet()` and set 3 = the table's set with the batch's ring offset, once per batch where the layout allows it.
   - Find where PR 6947 builds its GPU-mode layouts and binds its heap set (`Graphics/src/Pipeline.cpp`, `PipelineLibrary.cpp`, `ShaderResources.cpp`, `Draw.cpp`, `Execution/src/VulkanDevice.cpp`), and follow it.
4. **Fallback per program, never a stop.** The CPU table path stays the fallback for every program the device path can't serve. Keep a per-device set of programs (by code hash or the registry's source key) whose recompile requests get `deviceImageTables = false`. A program enters it, and is reported once in the log with the reason, when:
   - **(a) The heap is full.** `BindlessHeap::TextureSlot` returns no slot for a kind. PR 6947 `Require`s a slot in its own path (`ShaderResources.cpp` ~4876 "the global image heap is full") and `AbsentSlot` throws (`BindlessHeap.cpp` ~341); the device path must not.
   - **(b) The key table is full.** `Insertion::Full` even after `Retain`.
   - **(c) Repeated ring overflow.** The program's misses keep overflowing the ring (pick a bound, for example three batches in a row).

   Its draws and dispatches then take today's CPU path from their next recompile on. Until then they keep sampling zeros for unresolved keys, so make the switch-over fast: the next draw of the program. Resident Evil Village's tables hold 32,768 records, and its scene touches far more textures than the menu, while PR 6947's heap has 4096 slots per kind. Count, per kind, the peak distinct textures the device table holds, and print it in the `[device-images]` line.
5. **Device limits.** Turn the device path off for a device whose `limits.maxBoundDescriptorSets < 4`, since sets 2 and 3 need four. Do the same for one that lacks what PR 6947's heap set needs, with the reason printed once. Main still runs on devices that bind fewer sets (`ShaderResources.cpp` ~1561 requires only `>= 1`, and `tests/Graphics.cpp` ~3939 runs with 1); for those, `APS5_GPU_PATH=1` must give main's behaviour.
6. **The CPU table path is skipped for device-table images.** That falls out of LA-002's plan change, but check the driver side too: no table snapshot, no `ImageTable` elements, no texture lookups per record for them. The table's V# is now an ordinary scalar-buffer binding.
