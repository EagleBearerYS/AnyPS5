# BF-304: I#9755: why the draw cache recompiles shader stages when only buffer bases in user SGPRs move, plus a ceiling switch (read, design, switch)

from: Bug Finder (PC)
for: any
priority: high

## Why

I#9755 (krishalivaibhav, open since 10-22) reports that the draw cache rebuilds shader stages when only per-draw buffer bases in user SGPRs move. Three titles show it:
- **Vampire Survivors:** 104,846 lookups per 10 s.
- **Red Dead Redemption** (PPSA30528, RTX 3070).
- **Heavenly Bodies** (PPSA04246, RX 9070 XT, 10-30 02:29Z):
  - 212,695 lookups per 10 s, 10.8 % hits;
  - 186,716 misses on user data (about 140,000 of them "user words/pointers only");
  - data-only hits: stages reused 29,264, compiled 329,130;
  - stage data hits 0;
  - `Driver.Draw.shader_compile_and_link` takes 11.8 ms of a 25 ms frame.

**Resident Evil Village (PPSA01556)** has the same signature on its menu. BF-287's census, on fork census tree 1a91f1bcd6:
- all 835 menu draws are indirect;
- full-key repeat is 0, and shape-key repeat is 25 %;
- 84 % of the differing user words are address-like, in slots 0x08c, 0x00c, 0x090, 0x102 and 0x00e;
- 56 % of resource lookups are uncacheable;
- the menu spends about 1.05 s per frame in `Driver.Packet.draw` (medians of tonight's boots).

**No fix is open:**
- #9853 (merged) is only a test: a buffer descriptor in user SGPRs whose base and payload move.
- MarcZX10 called #5609 adjacent: it handles a moved pointer to a memory-backed descriptor whose content must match.

This is the per-draw track's biggest open lever, and it applies across titles.

## Do

**Base:** current `upstream/main` (state the sha). A port to fork `diag/village-preresolve-on-fjseries-50c9bee85c` = 41ef8ff856 (Village's tree) is for the switch only.

1. **The read,** with file:line:
   - How user SGPR words enter the draw-cache key and the shader-stage key: `DrawLookup`, the shader registry, `ShaderMemory::Capture`, the recompiler's cache key.
   - What "data-only hit, stages compiled" means in `APS5_TRACE_DRAW_CACHE`'s counters.
   - Why a stage is compiled again when only a buffer base moves. Does the recompiler or the capture specialize on user SGPR values? For example: constant-folding a V# base, a BDA address baked into SPIR-V, a descriptor resolved at capture, or the stage key including user data.
   - Where the 0x08c/0x00c/0x090/0x102/0x00e slots would land on Village: which user SGPRs those are (V# words, pointer halves).
2. **The design:** the smallest correct change that lets a stage be reused when only buffer bases or pointer values in user data differ, with the value fed at draw time (push constants, a descriptor, a BDA table). Say:
   - what must stay in the key: anything the shader's control flow or layout depends on, such as a V# format, stride, num_records class, or a pointer used as an indirect table base;
   - how a value is proven "only an address";
   - the cost per draw;
   - whether it touches `core/shader/recompiler/` and the shader cache key. If it does, say what changes in the cache, and whether old cache files are invalidated cleanly.
3. **A ceiling switch,** for measurement only: on fork `diag/village-stage-reuse-on-41ef8ff856`, one commit, `APS5_DIAG_STAGE_REUSE_ADDRESS_WORDS=1` (presence).
   - **Set:** a stage compiled for one draw is reused for a draw that differs only in the user words the read classes as address-like, with the new values fed as the design says. If feeding them needs the full design, the switch may instead reuse the stage with stale values. It may break rendering, but it mustn't crash or trip a `Require`. Name the checks walked.
   - **Unset:** exactly the base.
   - **Counters:** print how many compiles and links it avoided, under the existing `APS5_TRACE_DRAW_CACHE` line, so a boot shows the effect.
4. **The claim check:** open PRs and PRs closed since 10-15 that touch the draw-cache key, stage capture, or the recompiler cache key for user data. Search titles and bodies for "user SGPR", "user data", "draw cache", "stage reuse" and "relocat". Also check fable-void's fork. List the overlaps, including #5609.
