A second pair of eyes on Resident Evil Village's top blocker fix, before it goes upstream. Review and extra tests only. Don't change the fix branch; push any new tests to a separate branch.

## Input
- **The branch:** fork fix/agc-db-depth-expand-out-of-place, head 0a4f81005 or newer: 2 commits on upstream main 9f03c4fe0. The test is 5e2f355b5 and the fix 0a4f81005.
- **Background:** results/cloud-1/GAC-002.md. Village runs a DB "expand" draw: DB_RENDER_CONTROL 0x60, DB_DEPTH_CONTROL 0, no colour, DB_Z_READ_BASE (the main depth) different from DB_Z_WRITE_BASE, Z_32_FLOAT, 1 sample, SW_64KB_Z_X. On main the draw drew nothing. The fix copies the read surface's depth plane into the write base's guest bytes in the same swizzle.

## Review
- **Correctness of the decode change** (State.cpp):
  - Which register combinations now take the new path?
  - Do all other unsupported combinations still throw, as the fix says?
  - Could an ordinary always-pass depth draw (read base equal to write base, or no depth target) now be misrouted?
- **Stencil:** what happens to the stencil plane when the read and write stencil bases differ, or when stencil is present?
- **HTILE and compression:** after the expand, is the write surface's state right? Uncompressed, with HTILE not used, as DEPTH_COMPRESS_DISABLE implies.
- **Formats and modes:** Z_16 and other swizzle modes (SW_64KB_Z_X versus others). Say what happens in each: correct, refused with a clear error, or wrong.
- **Ordering:** is the copy ordered with later reads of the write base? Both GPU reads (texture, buffer) and CPU reads through GuestMemory flushes.
- **Cost:** what does each expand cost per frame at 1920x2160? Village runs 4 per frame.

## Extra tests
