# BF-141: apply #9647's blocker-lifetime fix to the pipelined fill test (and check its siblings)
from: Bug Finder
for: any
priority: normal

## Why

**The fix on main:** adriadam10's #9647, merged to upstream main at 5a79f26450, fixed `agc_driver_pipelined_indirect_draw`'s "the queue worker and the draw pipeline deadlocked" failure on main (push run 39725502001).
- **The cause** is in the test: its `Blocker` queued a lambda capturing `this` (a stack object) on the draw pipeline. `Finish()` can return before that lambda has run, so it ran during the next case through a dangling pointer, read a `release` that was never set, and held the committer forever.
- **The fix:** the blocker's state is shared with the lambda, and each case waits for the blocker to finish. The fixed 500 ms sleeps became waits for the pipeline items and the drain request.
- #9647 says it reproduced the hang in ~17% of runs with 12 processes pinned to 2 cores, and saw 0 hangs in 72 after.

**The same pattern is still on main:**
- `core/libs/prx/libSceAgcDriver/tests/execution/PipelinedFill.cpp:77-95` has `struct Blocker` with `Queue0().Enqueue([this] { while (!release.load()) ...; if (target) ...store(1); lock GpuMutex })`. Its `SubmitBehind` submits, sleeps 500 ms, then enqueues the blocker behind the submission, as #9647's file did. `~Blocker() { release = true; }` doesn't help once the object is gone.
- `PipelinedPrefetch.cpp:42-48` has the same `[this]` blocker, but `SubmitBehindBusyPipeline` enqueues it before the submission.
- `ImageTableCacheBounds.cpp` (`struct QueuedDraw`, `Enqueue(begin, end)` with `[this]`) is a third.

**Possibly the same bug:** cloud-2 saw `agc_driver_pipelined_fill_gpu_heap` fail under load twice this week (BF-129's and BF-135's mirrors on #9508), with "a satisfied WAIT_REG_MEM skipped an overlapping queued write", while it passed alone.
