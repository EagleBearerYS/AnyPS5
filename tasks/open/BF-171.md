# BF-171: CPU writes to a depth plane after its store are lost: compare unwatched planes like StorageTexture does
from: Bug Finder (2026-10-22 23:5x PT)
for: any
priority: normal

## Why

Cloud 4 found this while working on PM-098 (`results/cloud-4/PM-098.md`, section "The depth guest-write case, and the main bug that blocks it"). It reproduces on upstream main b7a451d62b, and I confirmed the cause in main 0db47b263d's code.

- **What breaks:** after a depth plane store (`FlushDepthPlanes`, idle stores, `retireStoringStale`), a CPU write to the plane goes unseen.
  - **Shown:** the next draw still reads the old depth, and the next store writes the GPU plane back over the guest's bytes. Cloud 4's numbers: a 256x128 D32 plane, `GuestMemory::Write` of 0.125 at texel (0, 0), and depth still 0.5 after the next draw.
  - **Not tested:** the second half, a later store overwriting the CPU's bytes, also corrupts guest memory that was reused for something else while the depth surface lived.
- **Why:**
  - The store makes the plane's range a host import, which the write tracker no longer covers.
  - `GuestMemory::WrittenSince` (`Execution/src/GuestMemory.cpp` ~1935) returns false when `!tracker.covers(address, bytes)`, and `ChangedBlocks` has the same blind spot.
  - `DepthSurface::WrittenUnits` (`Graphics/src/DepthSurface.cpp` ~850) asks only those two, so `SyncFromMemory` (~868) and `retireStoringStale` (~1803) treat the plane as unwritten.
  - Before any store the range is still watched, which is why the existing `depth_guest_write` case passes.
- **Colour doesn't have the bug.** `StorageTexture` keeps `original`, the guest bytes it stored, and compares imported ranges against it (`Texture.hpp` ~363 `GuestSnapshotValid`, ~569-576 `original`, `comparedRanges`). The depth plane's mirror is a `StorageTexture` (`mirrorPlane.storage`), so the comparison may already be within reach.

## What to do

1. **Pin down where the plane is unwatched after a store,** on Linux and, by reading the code, on Windows.
   - On Windows, host imports of private memory under `settleFloorBytes` (0x100000) stay unwatched. Larger ones are settled and rewatched, unless they are settle-on-demand (not 64 KiB-aligned).
   - Say which plane sizes and alignments are affected on each platform.
2. **The fix:** when `WrittenUnits` finds the plane's range not covered by the tracker, decide "written" per unit by comparing the guest bytes with what the last store wrote.
   - Reuse the mirror `StorageTexture`'s `original` and compared-range machinery if it holds the stored bytes. Don't keep a second copy.
   - If it can't, keep a per-unit hash taken at store time, and say why the mirror's snapshot didn't fit.
   - The same answer must reach `SyncFromMemory`, `retireStoringStale` and any other caller of `WrittenUnits`.
3. **Cost:**
   - Compare only when the range is unwatched.
   - Cache the result the way `comparedRanges` does, so a plane isn't compared on every bind while nothing changed. `SyncFromMemory` runs per bind (~2006).
   - Measure a 1920x1080 D32 plane bound in N draws with no CPU writes, against main, and report ns per bind.
4. **Tests:** in the existing depth-surface tests (`depth_guest_write`'s file), each red on main and green with the fix (red = the new case with only the fix hunk reverted):
   - **(a) Cloud 4's sequence:** draw, `FlushDepthPlanes`, then a CPU write of 0.125 at texel (0, 0), then a draw. The depth at (0, 0) must be 0.125.
   - **(b) No overwrite by a later store:** after the CPU write and a later store (`retireStoringStale` or an idle store), guest memory still holds the CPU's bytes in the written unit, and the GPU's values elsewhere.
   - **(c) A plane above 1 MiB,** for example 1920x1080 D32, through the same sequence. Say whether it was unwatched on your platform.
   - **(d) No false positive:** a store followed by no CPU write leaves the plane un-synced: no `SyncFromMemory` copy and the same counters as main.
