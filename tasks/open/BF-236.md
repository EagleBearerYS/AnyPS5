## What
New fork branch **`fix/agc-msaa-depth-alias-same-value-fill`** on `fix/agc-msaa-depth-alias-htile-stencil` a2911ffb72. One commit with its test: `fix(agc): keep a native multisample depth alias proven after a fill that rewrites its clear value`.
- **The rule:** in `sameDepthAlias` (or where it compares `newest`), accept a recorded Clear followed by a Fill only when all of these hold:
  1. the fill covers the whole alias range (every sample, every byte the alias spans), not a part of it;
  2. the fill's byte pattern, read in the alias's format, equals the recorded clear's value bit for bit (0x0 for R32F against a clear of 0.0f; say how `-0.0` and NaN payloads are treated);
  3. nothing else was recorded on the alias between them, such as a draw or a partial fill;
  4. the depth side's own proof still holds at the sample: the HTILE words still prove the clear. Re-check it there, or show from the code that nothing between import and the sample can change them.
  - Anything else still refuses, exactly as now.
- **Reasons and a source:**
  - The depth sample reads `DB_DEPTH_CLEAR` through HTILE, and the colour samples are host-only. So a fill that rewrites the same clear value leaves what the depth sample reads unchanged.
  - If main's code already compares a fill against a clear elsewhere (CMASK or DCC clear codes, `FillClear`), reuse that comparison and cite it.
  - **If any of 1–4 can't be shown from main's code, stop and report.** Don't widen the accept path on a guess.

  - Controls that must still refuse:
    - a full Fill with a different value;
