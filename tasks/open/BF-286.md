## What the Bug Finder already read (check it, don't trust it)

- **The unwatch hook takes the GPU mutex.** It's `StorageTexture::SaveBeforeUnwatch`, `Graphics/src/Texture.cpp`, set at `:1412` on 730c721773. It takes `Pending().mutex`, then `Live().mutex`, then `std::lock_guard gpu(GuestMemory::GpuMutex())`. Under the GPU mutex, `hashBeforeUnwatch` and `saveBeforeUnwatch` call `ReadCommittedUnsynced` and `CollectWritesUncached`, i.e. the tracker lock again.
- **Where the hook is called** (`Execution/src/GuestMemory.cpp` on 730c721773):
  - `ImportWatched`'s `leave`, under `TrackerLock::Suspension`, after each walk (`:1935`);
  - `markWritten`'s failed collect path, under `Suspension` (`:2113`);
  - `beforeUnwatch`. On `_WIN32` it takes `lockTracker` to read `coverage.ExcludedSpan`, then calls the hook outside it.
- **The flush hook takes the GPU mutex.** `GuestMemory::FlushGpuWrites` → `flushHook` is `FlushForAccess` (`Recorder.cpp:1300`) or `FlushHook` (`Texture.cpp:4043`). It's reached from `GuestMemory::Read` and from GuestArena's host read hook (`PrepareHostRead`, `GuestMemory.cpp:~2672`), i.e. a host file read into guest memory.
- **The draw path's order is GPU mutex → tracker lock:** worker 0x0 holds the GPU mutex in the commit and calls `collectWrites`.

**Suspected cycle,** for you to prove or refute: a thread enters the GPU mutex (through the unwatch hook, or the flush hook of a host read inside an import) while it still holds the tracker lock. The draw worker holds the GPU mutex and waits for the tracker lock. Ways the tracker lock could still be held:
- `Suspension` releases only one level of a lock held twice;
- `runImport()` runs under the tracker lock, and the file read reaches `PrepareHostRead` → flush hook → GPU mutex;
- a caller of `ImportWatched` or `markWritten` holds another `TrackerLock`.

The `catnames_*.txt` freeze (file reads, i.e. host imports) and the own-base stacks both fit the `runImport` → host-read-hook variant. That's a guess.
