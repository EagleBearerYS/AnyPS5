## Why

LA-004 (`results/cloud-5/LA-004.md` on `cloud-results`) measured lavapipe's GPU time on its Village-shaped bench: **4.3 ms per device-path draw, against 0.17 ms per CPU-path draw.** It also caught lavapipe's queue thread in `memset`.

Mesa's lavapipe source (25.0 and 25.2) explains it:
- **Every set in the call is copied.** `handle_descriptor_sets` (`src/gallium/frontends/lavapipe/lvp_execute.c`) calls `apply_dynamic_offsets` for every set in a `vkCmdBindDescriptorSets` call, with the call's *remaining* dynamic-offset count. With any offset left, `apply_dynamic_offsets` makes a new set with `lvp_descriptor_set_create` (`lvp_descriptor_set.c`, which does `memset(set->map, 0, bo_size)`) and `memcpy`s the whole old set into it. It does this even for a set that has no dynamic binding.
- **Our bind carries an offset.** `DeviceImageTable::Bind` (`Graphics/src/DeviceImageTable.cpp` ~291) binds set 2 (PR 6947's heap set) and set 3 (our table) in one call with one dynamic offset, on every draw. Set 3's ring binding is `STORAGE_BUFFER_DYNAMIC`.
- **The heap set is 28 MiB.** It holds 28 sampled-image arrays of 4,096 plus 256 samplers, which is 114,944 descriptors. A lavapipe descriptor (`struct lp_descriptor`) is 256 bytes. So every device-path draw zeroes 28 MiB and copies 28 MiB.
- **PR 6947 does the same.** Its `ShaderResources::BindHeap` binds its heap (set 1) and its data set (set 2, four dynamic offsets) in one call, so its GPU mode pays the same copy on lavapipe.

GPU drivers don't copy sets for dynamic offsets, so this should be a lavapipe-only cost. It still bounds every lavapipe measurement of lane A, and of PR 6947's GPU mode. LA-006's arm D on BF-046's harness needs this fix first.
