# BF-373: guest_poll aborts on main's Linux job when a pipe closes between IsPipe's fstat and fcntl; red, fix and green

from: Bug Finder (PC)
for: any
priority: normal

## Why

- **`guest_poll` failed twice on upstream `main`'s Linux job on 2026-11-09:**
  - run 42602115865 at c0d23c29c1, runner `anyps5-2-linux-12`;
  - run 42604873695 at 9571846a03, runner `anyps5-linux-06`.
  - Both show `Subprocess aborted` with `terminate called after throwing an instance of 'std::runtime_error'`, `what(): poll: querying pipe descriptor 7 failed`.
  - It passed in the other ~20 finished Linux runs that day, and nothing merged near those runs touched `libkernel`'s poll.
- **Where it's thrown:** upstream `main`'s `core/libs/prx/libkernel/Socket/src/Udp.cpp:830-836`, the POSIX `IsPipe` (the `#else` of `_WIN32`, so Linux and macOS):
  - `fstat` says FIFO;
  - then `fcntl(descriptor, F_GETFL)`;
  - `if (flags < 0) throw std::runtime_error("poll: querying pipe descriptor ...")`.
- **The test that hits it:** JJenkx's `PollsAPipeClosedDuringTheWait` (`core/libs/tests/GuestPoll.cpp:369`, from #14206, merged 2026-11-03).
  - It runs 200 times: a waiter thread polls a pipe's read end for 20 ms while the main thread closes that end.
  - It accepts `result == 0` or `result == 1` with `Invalid` set.
  - When the close lands between `fstat` and `fcntl`, `fcntl` fails with `EBADF` and poll throws on the waiter thread.
- **The Windows side already handles this.** `QueryPipe` (`Udp.cpp:801-814`) re-checks after a failed query and returns false when the handle changed or isn't a pipe any more (JJenkx's 6157b85, 10-31).
- **What false leads to:** in `GuestSockets::Poll` (`Udp.cpp:~2683`), a false from `IsPipe` goes to `DescriptorIsOpen_nid_no_patch`. A closed descriptor gets `GuestPollInvalid`, which is what the test accepts and what FreeBSD's `pollscan` (`sys/kern/sys_generic.c`) reports for a descriptor that isn't open (`POLLNVAL`).
- **The sibling kevent paths** (`PipeReadState` :1260; `PipeWriteState` :1280 Linux, :1290 macOS, :1319 other) call `IsPipe(descriptor, 0)` and then `fcntl(F_GETFL)` again without checking for -1.
  - My reading: -1 & `O_ACCMODE` is neither `O_RDONLY` nor `O_WRONLY`, so they go on to `::poll` and `ioctl(FIONREAD)`, and `ioctl` would fail with `EBADF` and throw "kevent: querying pipe descriptor ... failed".
  - Verify this; don't take my word for it.
- No issue or PR names `IsPipe`, `guest_poll` or this message (checked 2026-11-09 05:00 PST).
