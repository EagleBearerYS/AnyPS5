# BF-061: live counters for the shader-side holders of the process heap, so the PC can name what fills it at Resident Evil Village's menu (lane B, memory budget)
from: Bug Finder
for: any
priority: normal

## Why

Memory is now a goal of the redesign (the user, 2026-10-17 06:36 PT). The budget for Resident Evil Village (PPSA01556) on the PC:
- ≤ ~16 GB private at the menu (milestone 1), then ≤ ~12 GB (milestone 2);
- today it is 26.2 GB, of which ~19.7 GB is the emulator's own.

**The process heap is the largest holder we control:** 6.2 GB of small blocks at menu +2 min, and still growing.

**What BF-054 found** (`results/cloud-3/BF-054.md` §5, heaptrack on the harness):
- per registered program: decoded resource plans 231 KiB, heap SPIR-V copies 200 KiB, variant metadata 57 KiB, `RecompileResult`s 31 KiB, sources 16 KiB, registry 11 KiB;
- none of these has a counter.

**What we don't know is the PC's split.**
- How many of Village's ~6,000 programs are prepared or drawn at the menu.
- How large its plans are. Its mesh modules are ~1M words, so its plans may be far larger than the harness's.
- What the heap's other ~3 GB is.

Milestone 2 needs those holders named before they can be cut. Windows has no heaptrack we can use there, so it has to come from counters.

**No game data:** synthetic shaders only.

## Steps

1. **Counters, on fork branch `exp/shader-heap-counters` on current upstream main.** For each holder, keep live count and estimated bytes:
   - decoded resource plans (`IrResourcePlan`);
   - heap SPIR-V copies (registration modules and specialized modules);
   - variant metadata (`ShaderInfo` with its runtime image modes and binding layouts);
   - `RecompileResult`s (registration results and the per-source memo);
   - recompiler sources and variants;
   - shader registry entries;
   - the draw and dispatch caches' entries.

   **How to count:**
   - Bytes are an estimate made where the object is created or changes size: sizeof plus the capacities of its vectors.
   - Use relaxed atomics at creation and destruction, and nothing per draw.
   - Print one line every 10 s when `APS5_PROFILE_HEAP=1` (a new variable, so the unprofiled memory runs can set it):
     ```
     [heap] shader holders: plans N (X MiB), modules N (X MiB), variant metadata N (X MiB), results N (X MiB), sources N (X MiB), registry N (X MiB); draw cache N (X MiB), dispatch cache N (X MiB)
     ```
2. **Check the estimates against heaptrack** on BF-054's harness (`agc_driver_shader_residency_tests`, N = 1,000, 50k words, eager, 100 drawn).
   - Each counter should land within ±20% of heaptrack's bytes for that holder.
   - Give both columns, and say what any counter misses.
3. **A ctest in the same commit:** register N synthetic programs, draw some, and check each counter's count. The bytes must be nonzero and bounded. After teardown the counts return to their start.
4. **Cost:** with `APS5_PROFILE_HEAP` unset, registration time and draw time must not move. Give the harness's numbers both ways.
5. **Portability:**
   - say whether the commit cherry-picks cleanly onto fork `test/three-title-base3a-6178` 32ac24cb32, the memory session's base;
   - if it doesn't, add a variant branch `exp/shader-heap-counters-base3a` on 32ac24cb32;
   - run `ctest -R '^(agc|shader)'` on each head.
