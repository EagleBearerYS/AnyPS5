## Why

Our draft #13251 (fork `fix/agc-storage-alias-device-handoff-v2` = **44b529e05d**: BF-290's handoff, BF-301's borrower fix, BF-303's keys fix, the harness, and a merge of main) borrows only an alias with the **same base, size and shape**.

Tonight's F-trace on Resident Evil Village (PPSA01556), fix tree v3 306fc4cfb4 with `APS5_TRACE_STORAGE_ALIAS=1`, shows **no borrow at all**: across the top-8 entries, "base differs" 769x, "size differs" 72x, "borrowed" 0x. The overlap is never zero: a median of ~1.3 GiB per 10 s at the menu, peaking at 4.7.

**Village's pairs.** One menu line, verbatim:
```
[refreshed 0x2017000000+0x10000 fmt 36 tile 7 dim 1 120x68 layers 1 mips 1 units block import yes keys uncompressed | flushed 0x2017000000+0x640000 fmt 36 tile 7 dim 1 960x1080 layers 1 mips 4 units block import yes keys uncompressed | size differs: 7 flushes, 0.4 MiB overlap]
[refreshed 0x2017000000+0x640000 fmt 36 tile 7 dim 1 960x1080 layers 1 mips 4 ... | flushed 0x2017020000+0x110000 fmt 36 tile 7 dim 1 120x2160 layers 1 mips 1 ... | base differs: 7 flushes, 7.4 MiB overlap]
[refreshed 0x2017000000+0x640000 fmt 36 tile 7 dim 1 960x1080 layers 1 mips 4 ... | flushed 0x2017130000+0x870000 fmt 36 tile 7 dim 1 1920x1080 layers 1 mips 1 units block import no ... | base differs: 7 flushes, 35.4 MiB overlap]
[refreshed 0x2017130000+0x870000 fmt 36 tile 7 dim 1 1920x1080 ... import no | flushed 0x2017640000+0x640000 fmt 36 tile 7 dim 1 960x1080 layers 1 mips 4 ... import no | base differs: 7 flushes, 23.6 MiB overlap]
```

**What they have in common:**
- every image is format 36, tile mode 7, 2D, one layer;
- every base is 64 KiB-aligned;
- every image uses block units;
- the keys are uncompressed.

What differs is the base, the size and the mip count. That's a transient pool whose images alias each other at other offsets.

**The idea (BF-290's D2, widened):** with the same 64 KiB tile mode and the same element size, a 64 KiB block of guest memory holds one whole tile of texels, in the same byte arrangement, in both images. That holds at least for every block that maps to one full tile of a mip level both images tile normally. So for each overlapping block:
- `sliceWindows` of the refreshed image for that block, and of the alias for the same guest block, are each one full-tile window of the same extent;
- one `vkCmdCopyImage` region from the alias's window to the refreshed image's window moves the block's bytes bit for bit, at different tile coordinates.

Blocks that don't map that way, such as mip tails, partial tiles at an edge, or different element sizes, keep today's path for that block only.
