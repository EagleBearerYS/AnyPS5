# BF-035: repro and fix: a late store of pending storage-image results overwrites data an APR file read put in guest memory (Epic Mickey: Rebrushed)

## Why

Epic Mickey: Rebrushed (PPSA15657, UE 4.27) on Linux (RX 7600, RADV), on main 5d9dcc42d + #6236. The reporter is johnmaia, on our PR #6636: issuecomment-6221124027, with an earlier trace at issuecomment-6206905584.
- **The A/B:**
  - with `APS5_STORE_AT_FLIP=1`, 0 of 16 runs fail before the first level;
  - without it, alternated with those runs, 3 of 8 fail (and 2 of 5 earlier).
- **The failures:** `ObjectSerializationError` on `SM_MachineSet_01b` ("Serial size mismatch"); `LowLevelFatalError [Line: 1609]` right after opening `/savedata0/ue4savegame.dpx.sav`; or a SIGSEGV in the title.
- **The earlier trace:**
  - A 64 KiB block was zeroed shortly after the title read file data from it.
  - The crashing pair's APR read landed on a block that had a storage-image write-back ~50 ms before.
  - When the read started, its destination was in neither the published pending-write snapshot nor `Recorder::PendingWriteOverlaps`.
- **The debt entry** (`docs/dev/debt/libSceAgcDriver.md:75`): "pending storage-image results are stored when something reads their memory, not when the GPU work that wrote them completes". On the console the GPU's results land before the file read overwrites them. Here a late store can land after the read.

**Code facts** (upstream main 66e290f1c0):
- **The APR read:** libkernel's `_readFile` (`core/libs/prx/libkernel/Apr/src/Apr.cpp:159-170`) opens a `GuestArena::HostWrite` scope and `std::ifstream::read`s straight into guest memory.
- **That scope does nothing on Linux:** `GuestArenaBeginHostWrite` / `EndHostWrite` go to `GuestWriteWatchBeginHostWrite` / `EndHostWrite`, which are no-ops except on Apple (`core/libs/prx/libc/src/GuestWriteWatch.cpp:676-694`). On Windows they handle shared-memory views only.
- **So nothing tells the driver about the write.** No host-write path flushes the driver's pending storage-image results first, and none stamps the range as CPU-written.
- **What protection exists:** `StorageTexture::FlushPending` → `writeBackLayers` keeps the 64 KiB blocks the write tracker shows written since the image was last in sync.
- **How the Linux tracker sees writes:** userfaultfd WP_ASYNC plus PAGEMAP_SCAN (`GuestWriteWatch.cpp:37-214`), with a `UFFD_USER_MODE_ONLY` fallback on EPERM. Whether a kernel-mode write (the `read()` behind `ifstream::read`) is recorded under each mode is the question.

## What to build

On a new fork branch, `fix/agc-host-write-pending-storage`, from upstream main 66e290f1c0 or newer:

1. **A repro test**, red before any fix: a storage image with pending results over a write-watched guest block (as `StorageFlushOrdering` / `TailBlock`-style tests set up), then a host write into that block.
   - Do the host write through the real APR `ReadFile` path if a test can reach it (libkernel's APR command buffer, with a temp file). Otherwise use the same pattern: a `GuestArena::HostWrite` scope plus a kernel `read()` from a file into the block.
   - Then trigger the store as a guest read would: `FlushPending` over the block, or the driver's flush hook.
   - Expect the file's bytes to survive.
   - **Report which write-watch mode your kernel gives:** full userfaultfd, `UFFD_USER_MODE_ONLY`, or unavailable, which falls back to the compare. If you can, run both modes. The title runs on a desktop distro where unprivileged userfaultfd may be off.
2. **If it's red, the fix.** Prefer ordering, so that before a host write into guest memory, the driver's pending storage-image results over the range are stored first. The image's texels land, then the file's bytes overwrite them, as on the console.
   - One way: libc gets a registration (like `GuestAllocationsSetGpuMapObserver`) for a "before host write" hook. The driver registers `FlushPending` for the range there, and `GuestArenaBeginHostWrite` calls it on every platform. Every `HostWrite` user then gets it: APR, AIO, `read`, `recv`, the WebKit file calls.
   - Measure its cost on a host write with nothing pending (it must be cheap: one check of the pending registry), and say whether any caller holds a lock under which a flush could deadlock.
   - **If it's not red,** say why the late store can still overwrite the read in the title. For example: a race between the read on an I/O thread and a store on another thread, or the write-back's sync point moving between write-backs. Build the repro for that order instead, then fix it.
3. Keep the debt entry accurate: update it if the fix changes what it says.
