# PM-010: depth read through an aliased mapping — code map and a red test
from: AnyPS5 Project Manager
for: any
priority: normal

Code analysis plus, if feasible, a failing test. No fix and no PR. It prepares the fix for Resident Evil Village's "blur" stop. All facts below come from the Village team's runs on the PC; you need no game data.

## What we know
- Village's first 3D scene renders its lighting, fog and depth of field from a 1920x2160 R32F surface at guest VA 0x20298b0000. In AnyPS5 that surface is all zeros, so everything reads as infinitely far and the scene fogs away, leaving only lamp glows.
- A compute shader reads 0x20298b0000 as a plain buffer (a V#) and hands it to the blend passes as depth.
- 0x20298b0000 is never a depth surface in AnyPS5. The CPU writes it once, early in boot (zeros), and nothing AnyPS5 emulates writes it again.
- Working theory: on a PS5 this VA is a second mapping (an alias) of the same direct memory as the real depth buffer, which the GPU renders at another VA. AnyPS5 keeps depth only inside the GPU's image: see the "Reused depth storage" entry in docs/dev/debt/libSceAgcDriver.md, where depth rendering isn't written back to guest memory and only a compatible storage-image view of the plane is filled from the depth image. So the alias sees the boot-time zeros.
- The Village team is confirming the theory on the PC from the game's mapping calls. Your work is the code side.

## Questions (on current upstream/main)
1. **Aliases:** how does AnyPS5 handle two guest VAs that map the same direct memory? Look at sceKernelMapDirectMemory, MapNamedDirectMemory, a mmap of the same offset, and anything else that can alias. Are both VAs backed by the same host memory? Are the AGC driver's surfaces, resources, mirrors and imports keyed by VA? Can a resource registered at VA1 be found from a VA2 access?
2. **The read:** when a depth target lives at VA1, resident in a GPU image and never written back, what does a compute shader's buffer read at VA2 see? Name each code path it goes through, with file:line.
3. **A red test,** if it's feasible on lavapipe in the existing AGC driver test style:
   - map one direct-memory range at two VAs;
   - render or clear depth into a depth target at VA1;
   - read VA2 through a buffer in a compute dispatch;
   - check that the values equal the depth written.
   It should fail on main. Register it as the project does. Also run the same test with a single mapping (a buffer read at VA1 itself), so we see whether the alias matters or only the missing write-back.
4. **Fix options:** sketch the smallest ones, with the code they'd touch. For example:
   - write the depth plane back to guest memory, alias included, before a buffer read overlaps its range;
   - resolve VA2's read to the depth image.
   Say what each costs per frame and how it relates to the debt entry and to these open PRs: #5113, #5446, #4722, #4873, #5499 and #1409.
