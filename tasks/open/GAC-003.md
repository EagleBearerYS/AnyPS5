# GAC-003: AGC: run the out-of-place depth expand for indirect draws too (follow-up to GAC-002)
from: Game Agent Coordinator
for: any
priority: high

## Context

GAC-002 put the out-of-place DB depth expand on the fork's `fix/agc-db-depth-expand-out-of-place` (test 5e2f355b54, fix 0a4f810051). In Resident Evil Village it throws about 18 s into boot:

```
AGC driver: indirect DB expands are unsupported
```

Village issues the same expand pass as an indirect draw (DRAW_INDIRECT or DRAW_INDEX_INDIRECT), with the game's own register values (text):

```
rc=00000060 zinfo=20000183 sinfo=20000181 zread=00202a8a00 zwrite=0020298b00 view=00000000 dctl=00000000 cctl=00cc0000 tmask=ffffffff smask=00000000 size=086f077f
```

That's the GAC-002 shape at 1920x2160. The pass already runs during the boot screens, and at first player control it runs 4 times per frame. A local experiment that runs an indirect expand like a direct one, over the whole surface, is being checked in game now; you'll get the result.

**Added 13:45, a second case from the same run.** During boot, Village issues the expand before any depth surface exists at the read base. GAC-002's execution step throws there ("no depth surface at the read base"). The local experiment skipped it, logging:

```
[re8-expand] a DB expand from 0x202a8a0000 before any depth surface there is skipped
```

**A visual result:** with GAC-002 plus these two local experiments, Village's title screen is lit with real surfaces instead of a dark silhouette in fog. At first control, the first 3D scene renders sharp instead of soft light discs. The fix works in game.

**Added 13:55, a third case from the frame trace at first control.**
- **Texture reads are served:** all 27 texture reads of the write base 0x20298b0000 come from the expanded image (`src=s copy0 from 0x20298b0000 f22`).
- **The compute copy is not:** shader 0x203f1ea500, 8160x1x1 thread groups, reads the write base 3 times as a raw buffer (V#), and guest memory there was still all zero (nz=0.00) at bind. So its outputs at 0x2018470000 and 0x2019730000 are zero copies, and later blend draws sample 0x2019730000 as depth.
- **So:** the expand's pending storage image is apparently not stored before a GPU dispatch's buffer (V#) read of that range. GAC-002's test only covered a CPU `GuestMemory::Read`, which flushes.

## Task

Work on the same branch, `fix/agc-db-depth-expand-out-of-place` on the fork. Add new commits on top; don't rewrite 5e2f355b54 or 0a4f810051. Rebase onto upstream main only if needed, and say so.

1. **Red test:** extend `agc_driver_depth_expand_out_of_place` with the indirect variants of the same expand:
   - DRAW_INDIRECT and DRAW_INDEX_INDIRECT, with the arguments in guest memory, issued through PM4 the way the driver's other indirect execution tests do;
   - and one case whose indirect count is 0, which must leave the write base untouched.
   It must fail at the current head with the "indirect DB expands are unsupported" throw.
2. **The fix:** let the indirect expand run.
   - Prefer reading the indirect arguments the way the driver already does for other indirect work on the CPU path, then running the full-surface pass when the vertex or index count and the instance count are nonzero.
   - The draw's geometry isn't checked on the direct path either: the pass is accepted when viewport and scissor cover the surface. Keep that rule, and keep every existing refusal.
   - If the arguments can only be known on the GPU (for example, written by an earlier dispatch that hasn't completed), say how the driver orders that elsewhere and follow it. If that isn't possible, keep throwing for that case, with a clear message.
3. **No depth surface at the read base yet.** Decide what the expand should do when no live depth surface exists at the read base. Add a test for it.
   - **The likely console behaviour:** the DB writes the read surface's current contents uncompressed. AnyPS5's best equivalent is the read base's guest bytes. If the driver tracks a pending HTILE fast clear for that surface (see `NoteHtileDepthClear` / `HtileDepthClearAddress` in DepthSurface.cpp), it's the clear value.
   - **Options:**
     - copy the read base's guest bytes to the write base, same size and swizzle;
     - or write the tracked clear value;
     - or, if neither is sound, skip with the reason in the debt doc, rather than throwing at boot.
   - Say which you chose and why.
4. **A GPU buffer read of the write base after the expand.**
   - **The test:** after the expand, a PM4 compute dispatch reads the write base through a buffer V# (raw dwords, as Village's copy shader does) and stores it elsewhere. Read the destination back and check that it holds the depth (detiled with the SW_64KB_Z_X equation). Red if it reads zeros.
   - **The fix:** make the pending expanded image reach guest memory before a dispatch's or draw's buffer V# reads that range, the way other pending storage results are stored before GPU buffer reads. If the driver's address-based builds snapshot guest memory first, say where the flush has to go.
5. **Green:** the extended test passes. Run `ctest -R '^agc'` with CI's flags against the current head, and report any change in status.
