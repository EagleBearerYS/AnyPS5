# BF-051: does a CPU-side read wait for a BDA-table store recorded before it? Red/green on main
from: Bug Finder
for: any
priority: normal

## Why

BF-047 (`results/cloud-3/BF-047.md`, section 4, "A test caveat") found that a BDA-table store isn't visible to a CPU read until its batch completes. Reading main's code (upstream main 2bfe0045d) suggests this can reach real titles:
- **How CPU reads sync:** the driver's own reads of guest memory go through `GuestMemory::Read`, then the flush hook `FlushForAccess` (`Graphics/src/Recorder.cpp`). The hook syncs only when `Recorder::PendingWriteOverlaps` finds a noted write in the open or an in-flight batch.
- **What gets noted:** a build notes only its written V# ranges (`recorder.NotePendingWrites(guestMemory.Writes())`, `Graphics/src/ShaderResources.cpp` ~4702).
- **What doesn't:** a store through the BDA table into an in-place import isn't noted. Its pages are marked written only when the batch completes (`BdaResources::markWrittenPages` from `CheckFault`).
- **Who reads too early:** the CPU path of an indirect draw reads its records that way (`Pm4::ReadDrawArguments` / `ReadDrawCount` in `Execution/src/Pm4.cpp`, called from `Execution/src/Driver/Draw/Draw.cpp` ~495). If an earlier dispatch in queue order wrote a record through the table and hasn't finished, the CPU would read the old record.
- **Why it matters:** Resident Evil Village draws all of queue 0 through that CPU path.

This task settles whether main really misses it.

## Steps

1. **Read the nearest existing tests first:** `agc_driver_indirect_arguments_written_ahead` (and any test of GPU-written indirect records), plus the BDA store helpers in `tests/BdaShader.cpp` (`MakeBdaStoreTestShader`, `MakeBdaWriteTestShader`). If one already covers a record written through the BDA table, say so, run it, and stop there.
2. **Write the test, on upstream main:**
   - A compute dispatch (or draw) whose program stores a new instance or vertex count into an indirect draw record through the BDA table (`global_store_dword` through an address in `s[2:3]`, as in BF-047's `AddressPasses.cpp`). The record lives in guest memory registered for the GPU and served in place, so the table grants the write.
   - Then, in the same submission and in queue order, a CPU-path indirect draw (`DRAW_INDIRECT`) reading that record.
   - Check what the draw used, for example by the number of instances it rendered into a small target, or by the record the driver read (`APS5_TRACE_INDIRECT` prints "record N: count ... instances ...").
   - Cover two cases: the store's batch still open, and the store's batch submitted but not yet complete.
   - On Linux without udmabuf, shared direct memory is copied rather than imported, so use memory the worker can import in place (flexible or private). Say which you used.
3. **Run it on main, at least 20 times.** Red means the draw used the old record. Give the failure messages and the counts.
4. **If it's red:**
   - **The cheapest correct fix, as a sketch:** for example, note a storing build's table write ranges as pending writes, but only for CPU-path record and count reads; or make the CPU path sync before those reads while an open or in-flight batch holds stores through the table.
   - **Its cost:** on BF-042's per-draw harness (`exp/bf042-base`), if a quick prototype allows, say how many syncs per 100 indirect draws it would add when every batch holds a storing build.
   - Don't build a PR-ready fix yet.
5. **If it's green,** say what syncs the read: name the function and line.
