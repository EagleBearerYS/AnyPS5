# BF-277: #12840 review: note only changed runs as written back, and order two storing builds over one heap

from: Bug Finder
for: any
priority: high

## Why

#12840 (draft; fork `fix/agc-bda-store-writable-mirror` 781dc4525b, from your BF-273) makes an address-storing build add the served spans of its writable heap mirrors to the write set. oneandonlydean's review (https://github.com/boykopovar/AnyPS5/pull/12840#issuecomment-6496483144) asks two technical questions:

1. **NoteWrittenBack.** `GuestBufferMemory::WriteBack` (~L6285 on the branch) calls `Recorder::NoteWrittenBack(begin, end - begin)` for every merged write range of a mirror, before the diff. With whole heap spans in the write set, each storing dispatch notes up to 36 MiB as written back, although only the changed bytes are stored.
   - The recorder uses these notes to decide that a CPU write-back overwrote a completion label dword. It then counts the label pending and forces its completion store.
   - `Recorder.hpp` warns that a forced completion store can land a stale label over reused memory, and the `[recorder]` write-back-over-label counter is meant to stay 0.
   - **Question:** can a label sit inside such a span?
2. **Two storing builds in flight over the same heap region.** The second build's reference is taken at its upload, possibly before the first build's write-back. Its diff then also holds the first build's stores and writes them again after the first write-back, possibly over a CPU store made in between.
   - **Question:** is the order of references and write-backs fixed in a way that rules this out?
