## 2. A once-per-ABI first use (a new commit on top)

The description says "Two threads making the first use at once may each prepare an entry". The reviewers want the first use of a deferred ABI made once: the second thread waits for the first, and then uses its result.
- Make the deferred entry's first preparation happen exactly once, for example with a per-entry state (not started / preparing / done) plus a wait, or a per-entry `std::once_flag`-like guard.
- A failure in the first thread must not leave the second waiting forever: it either retries or gets the same error.
- Keep the hot path's cost after the first use at what it is now, an atomic load.
- **The test:** two or more threads making the first use of the same deferred ABI at the same time, for example with a barrier. It must show one preparation (the existing counters, or a new one), and that each thread gets the same prepared entry.
  - Red without the guard: it shows two preparations, at least sometimes, so run it until-fail.
  - Green with it.
  - Register it as its own ctest or as a case in `agc_driver_lazy_resolved_abi`. It's the same commit as the guard.

## 3. The deferred-ABI line behind a profile switch (a new commit on top)
