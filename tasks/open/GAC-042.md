## The bug (GAC-037, candidate 1)

`Graphics/src/GuestBufferMemory.cpp` on main, the `region.direct != nullptr` branch (~3733-3740):

```
if (!(addressable && region.hostBacked) || bdaFlush) StorageTexture::FlushPending(region.begin, bytes, nullptr, "imported buffer region");
```

- An address-based build maps whole registered heaps in place, with neither a store nor a publish first. The comment above assumes such shaders don't read texture memory through pointers.
- With unit shadows on (`UnitShadow.cpp:429`, needs write watching, the Windows default), a storage image's write-back retiles into the **unit shadow**, not the import:
  - "storage refresh" stores, `Texture.cpp:1759`, `PublishScope::None`;
  - "storage image creation" stores, `ShaderResources.cpp:974`.
- The import's guest bytes get those results only through a `PublishShadow` with a scope other than None: a host-facing reader, an eviction, an idle flush.
- **So a pointer read in an address-based build can see guest bytes frozen at the last publish.** In Resident Evil Village (PPSA01556) that is the title menu's last frame, published once by `FlushAllPending("idle")` at the load. It shows over gameplay, dimmed and not fading.
- With shadows off, the same pointer read sees the last *stored* frame, at most one frame old. The exemption's "no store" then costs at most a frame.

## The fix the coordinator proposes (change it if the code shows better)

In that branch, when the exemption applies (`addressable && region.hostBacked && !bdaFlush`):
- **Publish, don't store.** Call `PublishShadow(region.begin, bytes, PublishScope::Whole, PublishReason::Region)`, or a new reason if the counters need one.
  - Only units already stored into a slab and not yet published are copied.
  - Pending image results stay pending, as now, so the build's pipelining isn't hurt.
  - This makes shadows-on behave exactly like shadows-off for pointer reads.
- **Gate it with `AnyShadowedOverlaps(range)`** so a heap with nothing shadowed costs nothing.
- **Check the locking.** `PublishShadow` needs `GuestMemory::GpuMutex` (UnitShadow.hpp's contract) and the active recorder's open batch. The copy must land before the build's draw or dispatch reads the import.
  - The reuse path at `ShaderResources.cpp:2993-3005` already publishes a fresh shadow; follow its pattern.
  - Say in the result which lock and batch the publish runs under, and why the copy is ordered before the build's reads.
- **Check the reuse/fast-revalidation path for address-based builds.** If a reused build skips this upload loop, a later retile into the heap would be missed. Make sure the publish also runs where a reused address-based build revalidates, or show that a retile forces the slow path.
