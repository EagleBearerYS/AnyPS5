# BF-343: rework BF-342's idle-yield test fix, which lost the other race on GitHub's runner

from: Bug Finder (PC)
for: any
priority: high

## Why

BF-342 (`results/cloud-5/BF-342.md`) fixed `agc_driver_idle_store_yields` by replacing `SubmitAndWaitForPending`'s 5 ms sleep with `AgcDriverWaitIdle_nid_postfix()`. That's fork `fix/agc-idle-store-yields-flake` 3a3ec595b6, test-only. beardsciences and MarcZX10 asked on #13621 for this as a separate PR.

On **GitHub's Linux runner** (llvmpipe, a fresh runner, `ANYPS5_NO_SHADER_CACHE=1` from ctest), 30 runs with `--repeat until-fail`:
- **main 86709b7e13 (= 73f4f7e06e)**, run 41207503506: fails on the first run with "the two stores did not bring both rows of the large image to guest memory". That's BF-342's race.
- **the fix 3a3ec595b6**, run 41208705994: **also fails on the first run**, now at `IdleStoreYields.cpp:130` in `StopsBetweenImages`, with "**the queue-idle store ran before the fixture could take the GPU mutex**".

So waiting for idle trades the first race for the one BF-342 §3 named: the queue's own idle store starts 50 ms after the queue goes quiet (`IdleResultsQuietPeriod`, `QueueWorker.cpp:20`, :205), and on the slower runner it takes the GPU mutex before the fixture does. A likely reason: `WaitIdle` does work after the drain, such as storing drawn linear targets. The fixture and the idle store then contend for the mutex when it's released. Check this; don't assume it.

The Windows runner skips the test (no Vulkan device), on both trees.

## Do

On current `upstream main`, building on 3a3ec595b6.

1. **Reproduce the slow-runner race locally.** Run the fix's test 30 times with the shader cache off (`MESA_SHADER_CACHE_DISABLE=true`, `ANYPS5_NO_SHADER_CACHE=1`) while the CPU is loaded: e.g. 4 extra processes of the same test at once, or `stress-ng --cpu 4`. Report the rate of each failure message. Read what `AgcDriverWaitIdle_nid_postfix` (`Lifecycle.cpp`) does after the drain, and when the quiet period starts relative to its return.

2. **The fixture must observe that both dispatches are recorded, then take the GPU mutex at once,** with a margin far below the 50 ms quiet period and no dependence on how long a pipeline build takes.
   - **Look for an existing, non-blocking observable** in what the tests can already reach: a processed-submission or recorded-dispatch counter, a recorder serial, or `Pending` over the far row's range.
   - **Then poll it without the lock** (1 ms or less) and take the lock right after it turns. For `StopsBetweenImages`, "both images pending" may be enough. For `StopsWithinAnImage` (one image), you need an observable for the second dispatch.
   - **Keep the test's intent and checks unchanged.**
   - **Test-only, if at all possible.** If it can't be done without a seam in driver code (for example a test-only setter for the quiet period, or a hold on the idle store), don't write the seam. Report which one you'd need and where, with the lines. The PM decides first.
