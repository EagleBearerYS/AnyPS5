# BF-368: native multisample depth: publish a reused target with the guest's undecided bytes, then retire its owner (fix candidate, test-first)

from: Bug Finder (PC)
for: any
priority: high

## Why

Four titles stop on upstream main (now acf7ac208a) since our #9533 + #9717 merge (`a4b76b2c0a`): Curved Space (PPSA02817), NINJA GAIDEN: Ragebound (PPSA28002), Blue Prince (PPSA25009) and New Joe & Mac: Caveman Ninja (PPSA02801).

**What triggers it.** A tester, JJenkx, traced all four ([D#8671 19389607](https://github.com/boykopovar/AnyPS5/discussions/8671#discussioncomment-19389607)). Each title **reuses the memory of a host-written native multisampled D32S8 target** for something new:
- draw input (`prepareDrawInputs`) in NINJA GAIDEN and Blue Prince;
- a colour target (`refreshResidentTarget`) and a storage texture (`cachedStorageTexture`) in New Joe & Mac;
- another depth target (`DepthSurfaceViewWithStencilWriteIntent`) in Curved Space.

**Where it stops.** Building the new resource publishes the old planes (`RequireNoResidentDepthRead_nid_no_patch` → `DepthSurface::PublishToGuest`). The publication then refuses the bytes it can't decide: `native multisample depth publication cannot distinguish an unwritten byte from a same-value guest store`. Those are bytes on a page written since the snapshot that still equal the snapshot while the host's result differs. BF-366 showed a single CPU store into a drawn page leaves the whole rest of that page undecided.

**His experiment** ([19389732](https://github.com/boykopovar/AnyPS5/discussions/8671#discussioncomment-19389732)) switched the undecided bytes to the guest's bytes (`g`) or the host's (`p`):
- Blue Prince renders correctly only with `g`;
- NINJA GAIDEN runs either way;
- Curved Space and New Joe & Mac then reach a second refusal at `DepthSurface.cpp` ~3076: `a native multisample depth attachment over the planes of a host-written owner of another identity is not implemented`.

**The decision (the user's, via the PM):** build the reuse rule and the old owner's retirement, on a fork branch, test-first.

**The argument:**
- Before #9533 these targets weren't native, so a resource built over their memory read the guest's bytes everywhere.
- The rule takes the guest's byte only for bytes the publication cannot decide, and only when the memory is being reused. It keeps the host's bytes everywhere it can decide.
- So it is never further from the pre-#9533 result than main is (main refuses), and it is strictly closer on decidable pages.
- The untouched bytes on a CPU-written page are inferred, not proven. Exact store ranges are the exact follow-up and are out of scope here.

1. **The cause of a publication.** Give `RequireNoResidentDepthRead_nid_no_patch` (and the path to `PublishToGuest`) a way to say *why* the planes are being read.
   - **Reuse by a resource of another identity**, from these sites. List each site you mark in the result.
     - draw inputs: `Draw.cpp`'s "an index buffer read" and "a vertex buffer read";

2. **The rule, in `PublishToGuest`'s per-byte branch:** where main refuses with the message above, a **reuse** publication takes the current guest byte. A non-reuse publication refuses as before. Nothing else in the publication changes. In particular, pages with no change since the generation, bytes the guest changed, and bytes covered by driver stores are decided as today.
3. **Retire the old owner after a reuse publication commits.**
   - The guest now holds its planes, and the memory belongs to the new resource. Retire it like an unwritten surface whose content was published: guard inactive, removed from `depthGuards()`, the surface retired. A later bind of the same identity then takes a fresh import, and a new depth attachment over its planes no longer meets the second refusal.
   - **Same-identity rebinding must be unchanged:** the existing-surface path at the top of the depth-surface lookup doesn't publish.
   - A CPU-read publication keeps the owner resident, as today.
4. **Tests, in `tests/execution/NativeMultisampleDepth.cpp`, using BF-366's and BF-367's fixture:**
   - **The fixture:** a 4-sample D32S8 target with a separate stencil plane and a depth-only HTILE. The host draws stencil over the first stencil page, then one CPU store changes one byte in that page, so the page has undecided bytes.
   - **Red on main, green on the branch,** each a test case:
     - **(1) reuse as draw input:** a vertex or index buffer read over the page succeeds. The changed byte reads as the guest stored it, the undecided bytes as the guest's, and decidable bytes elsewhere in the plane as the host's.
     - **(2) reuse as a colour target or storage texture:** the same checks.
     - **(3) a new depth attachment of another identity over the planes:** it succeeds, the old owner is retired, and the new surface imports. On main it refuses at the publication or at the second refusal; say which.
   - **Negative cases (green on both):**
     - a CPU read over the same page still refuses with today's message and commits nothing;
     - a DMA copy still refuses;
     - rebinding the same identity changes nothing and publishes nothing.
   - **No commit may fail its own tests:** tests in the same commit as their fix, or after it. More than one commit is fine when the steps are real, for example the cause parameter, then the reuse rule with tests 1 and 2, then the retirement with test 3.
