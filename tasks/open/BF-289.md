# BF-289: draw-key census v2, why Village's resource lookups are uncacheable

from: Bug Finder (PC)
for: any
priority: normal

## Why

BF-287's census (fork `diag/village-draw-key-census-on-103015a9ca` = **1a91f1bcd6**) ran one Resident Evil Village menu boot. Over 525 heavy menu frames, per frame:
- **Resource cache:** 419 hits, 2 misses and **533 uncacheable**, out of ~951 lookups. So 56 % of lookups pay a full `ShaderResources` build under the GPU mutex.
- **Draws:** all 835 are indirect (483 CPU-path, 226 GPU-path, 126 empty and skipped).
- **Key repeats against the previous frame:** 0 full key, 210 shape key, 835 shader set.

In `Graphics/src/Draw.cpp`'s `resolveDrawResources`, a draw's lookup is uncacheable when any of these holds:
- `!recordable`;
- `APS5_NO_DRAW_RESOURCE_CACHE` or `APS5_NO_TEXTURE_CACHE` is set (neither was);
- a stage has no `PipelineVariantId()`;
- `ShaderResources::NeverReusable(shaders)`, meaning a stage with a `BdaPagetable` binding, or a `FaultBuffer` binding while the loop guard is on.

The census doesn't say which of these it is. The next speed PR depends on the answer.

## Do

Everything stays behind `APS5_DRAW_KEY_CENSUS=1`. With it off, nothing new runs: no extra clock reads, no new lock.

1. **Uncacheable by reason.** The `[draw-key] frame N` line adds a count per reason:
   - `not recordable`;
   - `no variant id`;
   - `bda pagetable`;
   - `fault buffer`;
   - `switch`.
   For `not recordable`, also split it by why `recordable` was false at the call site (`Graphics/src/Draw.cpp` ~2873, and where its caller computes it), naming each condition. Count a draw once, under the first reason that applies, in the order above.
2. **Their cost.** Per reason, the total µs per frame spent building those draws' `ShaderResources`, from the build's start to its return, with two `steady_clock` reads around the build, census only. Also give the same total for cacheable misses and for hits (lookup plus `Revalidate`), so the three compare.
3. **Who they are.** In each `10 s window N` line, the 8 shader sets (VS/PS program code addresses) with the most uncacheable lookups, with their counts and reasons.
4. **The rest of the shape key.** For draws whose shader set repeats against the previous frame but whose shape key does not, find the register offsets (key words outside the user words) that differ, and give the top 8 with counts, the way the existing line does for user-word slots. This says whether a wider key could reach beyond the 25 % that the shape key already repeats.
5. Keep the census's existing tests passing, and extend them to the new fields if they check the line's format.
