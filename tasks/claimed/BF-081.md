# BF-081: what BF-077's capture check costs per draw on title memory, and a cheaper form if it's too slow

from: Bug Finder (2026-10-17 19:53 PT)
for: any
priority: high

## Why

BF-077 added a check to the fork branch `fix/agc-draw-recapture-on-change` (head ff2837edf, on upstream main f1af6c5915). Cloud-5's result is `results/cloud-5/BF-077.md` on `cloud-results`.

**What the check does:** at its last step, the queue worker compares the regions a draw or dispatch captured with guest memory (`capturedMemoryChanged`, `GuestMemory::CompareMapped`). If they differ, it prepares the packet again. It fixes Onimusha: Way of the Sword (PPSA27836) binding zero V#s (#5769).

**The cost so far** comes from the Village-shaped harness (BF-077 section 3):
- the compare costs **4,866 ns per draw**: 9.49 regions of 103 bytes each, 513 ns per region;
- nearly all of that is one `PROCMAP_QUERY` ioctl per region;
- the cause: the harness's `GuestBlock`s are mmap'd outside both the guest arena and the image spans that `describePages` keeps a table for;
- a plain `memcmp` of the same regions costs **267 ns per draw**.

The check runs on every draw, so 4.9 µs per draw would be a large cost. We need the cost on the memory a title's draws actually capture before the PR can open.

**Some title memory sits outside the arena.** JustUseAI's abort on discussion #7043 names "0x24ec00000+0x1e848000 (488.3 MiB committed, outside the write-watched arena)", so the in-arena case may not be the only one that matters.

## What to do

1. **Read the paths on ff2837edf, for Linux and Windows.**
   - Which path does `CompareMapped` take for a region inside the guest arena, and which for a region in an image span?
   - Which regions go to the kernel? On Linux that's `PROCMAP_QUERY`; name the Windows call too.
   - Where does a title's memory come from, by kind: direct memory mapped with `sceKernelMapDirectMemory`, flexible memory, memory the title maps at a fixed address? Which of these land inside the arena or on a `describePages` table, and which don't?
2. **Measure the table path.** Change the harness so that its blocks sit on the table path, the way a title's arena memory does. Use the test framework's way to allocate guest-arena memory if it has one; otherwise make the smallest local change that does it. This is a measurement tree only, not committed, as in BF-077 section 3.
   - Rerun BF-077's cost table with the same command: `ANYPS5_NO_SHADER_CACHE=1 VILLAGE_DRAWS=1000 VILLAGE_GPU_SYNC=1 ./build/tests/agc_driver_village_draw_cost_tests --cost 100`.
   - Three cases: with the check; without it (`APS5_MEASURE_NO_CAPTURE_CHECK=1`); a raw memcmp (`APS5_MEASURE_RAW_COMPARE=1`).
   - Alternate them, three runs each if time allows.
   - Report each run's `[capture-check]` line, ns per draw and per region, and regions and bytes per draw.
3. **A cheaper form, if either path costs more than ~1 µs per draw.** The kernel query is only there to learn whether the pages are still mapped and readable. The capture read the same bytes a few microseconds earlier, so the query can only matter if the title unmapped or reprotected them in between.
   - Find whether libkernel's or the driver's memory map already has a generation count that map, unmap and protect calls move. If it has none, add one.
   - Then compare a region with a plain `memcmp` when that count hasn't moved since the capture, and keep `CompareMapped` otherwise.
   - Make it one commit on a new fork branch from ff2837edf. BF-077's four tests must pass with it, and the change needs a test of its own: a region unmapped between capture and check must not fault and must count as changed.
   - Measure it the same way, outside-arena harness and table path both.
4. **The CI mirror.** Run it on the proposed branch, if there is one, against ff2837edf, and name any test that changes status.
