# BF-160: #9941's case 6 must keep only the FMASK's settle pending, so the FMASK commit has a red

for: any

## Why

**#9941** (draft, fork `fix/agc-sync-settle-initial-dcc-main2`, head af1fa8edb3) is the Windows fix for #9724, Rush 2 Recompiled (PPSA69423) and Wave Race 64 Recompiled (PPSA69424). Its last commit is af1fa8edb3, `fix(agc): settle a pending import before the FMASK checks of an initial multisampled DCC import`. That commit makes #7948's two FMASK checks in `MultisampleTarget.cpp` (the initial import at `:579`, reuse at `:619`) call `WatchedAfterSettle` instead of `GuestMemory::Watched`. Its test is case 6 of `settleInitialDccTests` (`tests/Recorder.cpp`, `Case::PendingFmask`, ctest `agc_import_settle_initial_dcc`).

**On an RTX 3070 (Windows, NVIDIA 617.42) tonight, case 6 isn't red.**
- **Green 5/5:** `(m) initial DCC over an eight-sample target whose FMASK has its own pending settle (import 589824 bytes): accepted; 2 settle reads submitted, 2 back in the write watch`.
- **The red arm** (`MultisampleTarget.cpp` from 39ef39855e, the commit before af1fa8edb3, with the test kept) prints the same line 3/3, accepted.
- **Why:** case 6 imports both the color+DCC+CMASK region and the FMASK region off the GPU lock, so both settles are pending. When the color loop's `WatchedAfterSettle` runs, `settleImportsNow` submits a batch through #8527's `submitSettleBatch`. That batch carries **every** wanted settle, the FMASK's included (2 settle reads). So by the time the FMASK check runs, the FMASK import is back in the watch, and the old plain `Watched` passes too.

Cases 1-5 are fine: their reds hold on the 3070 (3/3 earlier today, at 973af43dc6).

## The change (test only)

**Base and branch:** a new fork branch `fix/agc-sync-settle-fmask-case6` from af1fa8edb3, with one commit on top. Don't push to `fix/agc-sync-settle-initial-dcc-main2`; the PR Manager moves #9941's head.

**Rework case 6** (or add a case 7 and keep case 6 as "both pending, accepted"; say which) so that **only the FMASK's settle is pending** when `initialDccClear` runs:
- The color, DCC and CMASK planes must be **watched with no pending settle** before the target is first used. Use whatever the code makes reliable: no host import over them at all, or an import made and settled before the FMASK import is made, under the GPU lock with a reaped batch. Say which.
- The FMASK region must be **its own sub-1 MiB import, made off the GPU lock, with its settle pending (Wanted)**, in its own region with unregistered 64 KiB gaps (BF-155's lesson), so it can't join the color region.
- **Preconditions the test checks itself,** with BF-155's `describe` on failure:
  - before the use: color, DCC and CMASK `Watched`, and no compared import covers them;
  - the FMASK import `unwatched`, `!Watched`, pending.
- **Settles submitted during the color loop:** the test must show none were submitted before the FMASK check. If the existing counters can't separate the two checks, require `settle reads submitted == 1` for the whole use, and say so.
- **Green (af1fa8edb3's `MultisampleTarget.cpp`):** accepted. Afterwards the FMASK is watched and not `unwatched`, the resolve reads the clear, and a CPU store into the FMASK refuses at re-acquire with `writes to a resident native FMASK are not implemented`.
- **Red (`MultisampleTarget.cpp` from 39ef39855e, test kept):** refused at the FMASK check with `native FMASK contents require watched guest memory`, and 0 settle reads submitted.
- **Precondition skip:** if the device lacks 8x color or multisampled storage images, print the existing `(m) … not tested` line and return, as case 6 does now.
