PR boykopovar/AnyPS5#9969 adds the test `agc_driver_pointer_vsharp_child_key_arm_table`:

Use the PR's head `5f70ec884e` (`upstream refs/pull/9969/head`), or the candidate `2a082ea647` on the fork branch `prm/9969-st89`. They differ only in a base merge and the FormatVersion line.

**Where it passes and fails:**
- It passes on NVIDIA (Windows and Linux), AMD Radeon 780M (RADV) and llvmpipe.
- It fails on every run on two Intel iGPUs on Windows: UHD `8086:9a60` with driver 101.7085, and another with driver 101.70xx.
- No VUID appears anywhere.
- It still fails with `APS5_SINGLE_LANE=all` and with `APS5_NO_SPANNED_WAVE=1`.
- Its sibling `agc_driver_pointer_vsharp_child_key_table` (shader `PointerChildKeyCode`, without the arm) passes on Intel.

**Intel fails at the test's first check.** In that check `Keys[g*4+3]` is 0, so no group takes the arm (`s_cmp_eq_u32 s19, 0` / `s_cbranch_scc1`). The failures look like this:
- `[gpu] deferred write-back failed: image table: shader ... stage 4 pc 0xfc selected the descriptor at 0xde8f3fd840: poison entry 255842560` (mrfelek);
- `... selected the descriptor at 0x24c1bfd640: poison entry 1103091456` (gabichuuuuu);
- once, with no fault: `group 0 lane 16 is 0x00000000, expected 0xc27e0000 (palette 1, key 5)`.

**Our reading of the report path** (`Graphics/src/BdaResources.cpp` `checkFault`; `SpirvBackend/src/SpirvImageEmitter.cpp` `EmitTableFault` and its callers around lines 2250-2310):
- "poison entry N" is the faulting word with `ImageTableAbi::PoisonFlag` (0x80000000) cleared. The report prints it raw because N is past the poison list.
- So the shader at pc 0xfc took 0x8f3fd900 or 0xc1bfd700 as a word read from the table map: a key's code (`word.code`), a record's flags (the `rejected` path), or its fault word (the `driverFault` path). Our 11-07 comment printed 1103091456 as 0x41c00000. That was wrong: it is 0x41bfd700.
- **Exact pattern (the main clue).** With the poison bit put back, each value is the selected descriptor's address low word plus 0xC0:
  - mrfelek: 0x8f3fd840 (descriptor 0xde8f3fd840) + 0xc0 = 0x8f3fd900;
  - gabichuuuuu: 0xc1bfd640 (descriptor 0x24c1bfd640) + 0xc0 = 0xc1bfd700.
  The selected descriptor is the T# at key 2, palette + 0x40, so the value is palette + 0x100. That could be the next palette's base, the end of the V#'s 0x100-byte range (base + size), a V#'s dword 0, or a record pointer. It may be a stored word or a value the SPIR-V computes.
- Neither is a value the driver writes into the table map.

## Goal

Find a mechanism by which the generated code can read a wrong table-map word (or a wrong record) on one driver but not on others. Use lavapipe and the code. If our side isn't at fault, rule it out with evidence. There is no Intel hardware, so don't claim an Intel driver bug unless you can show it.

## Lead to test first (added 11-12 18:0xZ)

This matches a gap we parked on 11-02 (tracker `lead-intel-windows-sampler-fusion`). The mechanism comes from Mesa issue 16622, fixed in MR !37394, "nir/brw: Fix texture/sampler accesses with EU fusion on Gfx12.X HW", in Mesa 25.3 and later. On Gfx12, two fused threads run in lock step and can't hold different texture or sampler handles, so one workgroup gets the other's (Capmare on #7395, issuecomment-6263589980). Intel's Windows driver doesn't have the fix: an Arc on 101.9150 failed #7395's two sampler-table tests until the program was spanned. UHD `8086:9a60` is a Tiger Lake part, which is Gfx12.

How the code fits (#9969's head, and the same on `main`):
- **The fallback.** `Recompiler.cpp` ~719-723: when the spanned emit throws `SpannedWaveUnsupported`, the program falls back to two lanes per invocation. The arm shader logs that fallback on NVIDIA and on Intel.
- **No NonUniform after the fallback.** `SpirvEmitter.cpp` ~327-329: at two lanes per invocation, `oneSubgroup` is true, so `tableIndexNonUniform` is false. The table image and sampler indices get no `NonUniform` (`SpirvDescriptors.cpp` ~74).
- **`selected` columns.** `SpirvImageEmitter.cpp` ~2283-2284: a `selected` table column (`tableAccess.uniform`) skips `NonUniform` in every mode. That could be why `APS5_SINGLE_LANE=all` still fails.

Check these first:
- **a.** At host subgroup size 32 with spanned waves on, does the arm program fall back and the sibling stay spanned? llvmpipe's subgroup size isn't 32, so use a recompiler-level harness, `core/shader/recompiler/tests/SpannedUniformityTests.cpp` style, or whatever reproduces the target. What exactly is the barrier at block %77 of function %72, and why is its condition per-invocation, when the guest branch is on a scalar (`s19`)?
- **b.** In the fallback module, list every table image or sampler access, every buffer-descriptor array access, and whether each has `NonUniform`. Can any value that reaches the pc 0xfc fault record (`word.code`, the flags, the fault word) come from such an access? This matters for the +0xC0 words.
- **c.** Prototype the narrowest fix: decorate the table indices `NonUniform` whenever the program isn't spanned (and for `selected` columns), or only on Intel, through a target flag set from the vendor ID. Add a recompiler- or SPIR-V-level test that fails on the old code (no `NonUniform` in the fallback module) and passes with the fix. Run `^agc_driver_(pointer_chase|pointer_vsharp|image_table|nested)` and `^agc_shader_` on lavapipe before and after, and report anything that changes. Same conventions as step 5; push to `prm/9969-intel-fix`.

Then do the steps below only as far as they still add something.
