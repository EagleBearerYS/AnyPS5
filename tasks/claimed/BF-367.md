# BF-367: native depth publication: keep the host bytes in a page that only complete driver stores changed (fix candidate, red/green)

from: Bug Finder (PC)
for: any
priority: high

## Why

Four titles stop on upstream main 1c8c0efc8c with `native multisample depth publication cannot distinguish an unwritten byte from a same-value guest store` (`DepthSurface::PublishToGuest`, from #13021). They are Curved Space (PPSA02817), NINJA GAIDEN: Ragebound (PPSA28002), Blue Prince (PPSA25009) and New Joe & Mac: Caveman Ninja (PPSA02801).

The tester's prints show the trigger is **memory reuse**: a new colour target, storage texture or depth target is bound over a native multisampled D32S8 target's memory (`refreshResidentTarget`, `cachedStorageTexture`, `DepthSurfaceViewWithStencilWriteIntent`), and creating it publishes the old planes.

BF-366 showed that **any** change to a 4 KiB page the host drew makes the page's untouched bytes "ambiguous". The per-byte check `UnchangedSinceLastCollect(byte)` is page- and block-granular, and `StoredAllSince` covers only bytes inside recorded driver stores.

**The case this task fixes:** a page that no CPU store touched since the generation, changed only by the driver's own **complete** stores (`storeOwn`, which records exact ranges in `driverPieces`).
- For example, the write-back of a resource that reused the memory.
- A byte outside those recorded ranges was written by nobody since the generation, so the host's byte is right. Today it refuses.
- **Not this case:** a page with a CPU store since the generation, or with an incomplete ("possibly written", `MarkPossiblyWritten`) store or a refusal over it. That is genuinely ambiguous and must keep refusing.

The tracker already separates these:
- `WriteTracker::cpuUnchanged` (per page where `cpuPages` has the block, else per block);
- `refusedSince`;
- the `complete` flag on `noteDriverStore`.

The public `UnchangedSinceCollected` (`GuestMemory.hpp`, "whether no CPU write touched the range since generation") collects first.
