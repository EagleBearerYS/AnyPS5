# BF-303: close the keys gap a kept storage alias opens (a follow-up commit for BF-290's fix)

from: Bug Finder (PC)
for: any

## Why

BF-290's fix (fork `fix/agc-storage-alias-device-handoff` = **a7e04ab973**, on upstream main 08a10d2253) is about to open as a draft PR. Reading it on the PC turned up one gap a reviewer will press on. BF-290's own result names it under "Not changed, and worth knowing".

Line numbers are on a7e04ab973, in `Graphics/src/Texture.cpp`:
- **Where the alias is kept:** L2197, when `ProvedClearKeys(descriptor, guestBytes, keyProof) == Uncompressed`. From L2215 on, `refreshingAlias` exempts it from every FlushPending on the thread (L4215).
- **Where the keys are proved again:** L2283, `keys = ... ProvedKeys()`, after the refresh's flush. That flush "may store keys itself", in main's own comment above L2196.
- **The gap:** if `keys != Uncompressed` there, the borrow block (L2349) doesn't run. Yet the alias stays exempt: its results never reach guest memory, and X uploads stale bytes in those units.
  - Y stays pending on them, and later supersedes nothing, because only borrowed units are superseded.
- **Scope:** on main the same gap exists only through the import path (`direct`). The fix widens it to every surface.

- **Close the gap for both paths** (import and no import). The intended shape: when the alias was kept but `keys != Uncompressed` at the borrow decision, drop the exemption and store the alias over the surface, as main's non-alias path would have, before anything reads the surface for the upload.
