# BF-282: Resident Evil Village's biggest remaining cost: what Driver.Packet.memory_wait waits on, and the ranked ways to cut it

from: Bug Finder
for: any
priority: high

## Why

Resident Evil Village (PPSA01556) runs its static menu at about 0.6-0.8 fps on an RTX 3070 Laptop (CPU-bound, GPU about 18 % busy). Two speed PRs went in today: #12745 (the image-table write index, +25 %) and #12921 (untracked proofs across collect epochs, +29.9 %). Both cut Revalidate.

The largest phase left is `Driver.Packet.memory_wait`: about 2.3-2.9 s per presented frame, out of 3.3-4.9 s of `Driver.Packet`. Queue worker 0x28 spends about 98 % of its time waiting, and 0x38 waits in `Driver.WorkerWait.dequeue_order`. These traces are public, timing events only:
- **A** (main 319621ba2e + #11580 + #10304 + a pad answer): https://github.com/EagleBearerYS/AnyPS5/releases/download/traces-12745/aps5-trace-103015a9ca66-33724.json.gz
- **B, #12745:** https://github.com/EagleBearerYS/AnyPS5/releases/download/traces-12745/aps5-trace-e23a2e325e57-31916.json.gz
- **B, #12921:** https://github.com/EagleBearerYS/AnyPS5/releases/download/traces-12921/aps5-trace-07f624d854fb-36204.json.gz

Each is 30 s at menu +10.5 min, Chrome trace JSON. `python3 tools/trace_digest.py <file>` summarizes them.

## Do

1. **Read the code:** where `Driver.Packet.memory_wait` is measured (search the Execution sources for `memory_wait`), and what that wait is: WAIT_REG_MEM/label waits, `WaitMemory.cpp`, GPU-written labels, cross-queue dependencies. Say what releases it (a GPU completion, another queue's packet, a CPU write), and on which thread.
2. **Read the traces** (A, then both B):
   - per queue worker, how memory_wait splits into individual waits: their count and their duration distribution;
   - what the releasing side is doing during the long waits: the other workers' slices, GPU batches, `Driver.WorkerWait.dequeue_order`;
   - whether waits line up with GPU batch ends (GPU-bound waits) or with another worker's CPU work (a CPU dependency chain).
3. **The chain:** say whether the frame is one serial chain across workers 0x0, 0x20, 0x28 and 0x38, with each waiting on the previous one's labels. If it is, the critical path is the sum of CPU work on that chain. Name the top CPU slices on it.
4. **Ranked candidates** for cutting the wall time: e.g. releasing labels earlier, resolving waits on the CPU without a GPU round-trip, finer completion signals, removing serialization in `dequeue_order`. For each:
   - the code it would change;
   - the expected saving, estimated from the traces' numbers (an upper bound if that's all you can give);
   - the risk;
   - any open PR that already does it. Search open PRs for `memory_wait`, `WaitMemory`, `dequeue_order` and labels; list them with merge-tree results against main.
5. **No code change is needed.** If one candidate is clearly cheap and safe, sketch it with the files and functions it touches.
