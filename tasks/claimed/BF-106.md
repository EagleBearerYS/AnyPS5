# BF-106: why `GuestMemory::Rewatch` costs ~440 µs per restored 64 KiB span on Windows: a phase split, then a fix
from: Bug Finder
for: any
priority: normal

## Why

BF-104's bench (fork `exp/rewatch-cost` **4ef027a78**, test `agc_driver_retired_import_rewatch_cost`, mock device) ran on GitHub's Windows runner in [run 39580615406](https://github.com/EagleBearerYS/AnyPS5/actions/runs/39580615406). The output is in that run's `verify-windows` artifact, `rewatch-cost.txt`.

Over Resident Evil Village (PPSA01556)'s load-sized workload (2,077 retiring refreshes, 5,765 retirements: 5,278 of 64 KiB, 487 of 4 MiB):

| | main | #8926 (3 runs) |
|---|---|---|
| retiring refreshes, total | 9.3 ms | 2,784–2,796 ms |
| median per refresh | 3.0 µs | ~620 µs |
| a refresh retiring 1 piece (64 KiB), median | 2.8 µs | ~450 µs |
| a refresh retiring 2 pieces (one 4 MiB), median | 4.0 µs | ~1,450 µs |
| the refresh retiring 1,412 pieces | 0.87 ms | ~750 ms |
| the collect of a 32 MiB range after a serial bump | memo hit, 0.1 µs | 152 µs |

BF-104's estimate from the code was ~3 µs per 64 KiB span. The measured ~440 µs fixed cost per span is two orders of magnitude more. All of it is in #8926's `rewatchRetired` plus `GuestMemory::Rewatch` (`Execution/src/GuestMemory.cpp`). `Rewatch` already serves deferred settles on main, so a cut helps main too.

What one span goes through, as BF-104 read it:
- **`rewatchRetired`:** the `imports` lookup and walk, and `StorageTexture::AnyLiveOverlaps` (no live textures on the mock).
- **`Rewatch`:** the tracker lock, `coverage.Covers`, then `walkWrites` → `collectWindowsWrites` → `GuestArenaCollectWrites` → `WindowsMappings::Collect` (`core/libs/prx/libc/include/WindowsMappings.hpp`). That runs:
  - `collectable()` (the `collectableRanges` map, else `VirtualQuery` per region);
  - the `cleanRanges` walk;
  - `viewAt` per 16 KiB view;
  - for resident memory, `collectResident()`, which may call `armResident()` (a `VirtualProtect` of the span to read-only when its resident run is 256 KiB or more), then `GetWriteWatch(WRITE_WATCH_FLAG_RESET)`, then `rememberClean`.
- **Then:** `coverage.Restore`, `noteCpuStore`, and the per-block `driverPieces.erase` and `stamp`.

   - Add timers, behind a cached env flag or the bench's own switch. Time with `QueryPerformanceCounter` around:
     - `rewatchRetired`'s import walk and `AnyLiveOverlaps`;
     - `Rewatch`'s lock acquire, `Covers`, `walkWrites`, `Restore`, `noteCpuStore` and the block stamps;
     - inside `WindowsMappings::Collect` (one call per span): `collectable` (split out `VirtualQuery`), the clean-range walk, `armResident`'s `VirtualProtect`, `GetWriteWatch`, `rememberClean`.
   - Count `VirtualQuery`, `VirtualProtect` and `GetWriteWatch` calls per span. Have the bench print the totals per phase and per span at the end of its block.
2. **Read the code for anything that grows with the arena or the mappings,** not with the span: a linear scan of `views`, `cleanRanges` or `collectableRanges`, a map rebuilt per call, a `VirtualQuery` over a huge placeholder reservation, a lock that waits on another thread. The bench registers 5,765 pieces over its run, so state that grows with the number of registrations would show as a cost that rises through the run. Print the per-span cost for the first and last 500 spans to check that.
3. **Push `exp/rewatch-phases`.** The PC runs it on GitHub's Windows runner. Say in your result which phase you expect to dominate, and why.
4. **If the split from your reading is clear enough to fix without the Windows numbers** (for example a scan you can bound, or a `VirtualProtect` that `armResident` doesn't need for a span that is about to be restored), make the fix on a separate branch `perf/agc-rewatch-span-cost` on upstream main.
   - Keep #8926's code out of it if the cost is in main's `Rewatch` or `WindowsMappings`, so it stands as a main PR. Otherwise base it on acc7b1792e.
   - Correctness tests: the write-watch and settle tests (`agc_heap_mirror_*unwatch*`, `agc_driver_graphics`, the libc `GuestArena`/`WindowsMappings` tests), and what the fix needs in addition.
   - The cost number comes from the PC's Windows run of the bench on top of the fix.
