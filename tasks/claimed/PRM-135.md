## Background

Read `results/cloud-3/PRM-130.md`, `PRM-132.md`, `PRM-133.md` and `PRM-134.md` first. The latest from mrfelek is at https://github.com/boykopovar/AnyPS5/pull/9969#issuecomment-6839182328 (Intel UHD, Gfx12, Windows, driver 32.0.101.7092).

**`prm/9969-intel-split` (Volatile header loads) still fails on Intel:** trace 4 of 4, plain 4 of 4, with the same decoder output as before. The upper child-header words depart in 16-lane blocks: `child.baseLow` = 0x104 or base + 0x14, and `child.fault` = the other slot's record pointer. NVIDIA passes everything.

**His own variants all fail on Intel too:**
- `Volatile` on every table-map load;
- `SubgroupUniformControlFlowKHR`;
- `v_readfirstlane` as a shuffle or as an `OpGroupNonUniformBitwiseOr` reduction;
- 64-bit `OpIAdd`/`OpISub` as 32-bit carry pairs;
- `DontInline` changed to `None`/`Inline`;
- `spirv-opt -O`/`-Os`;
- `VK_PIPELINE_CREATE_DISABLE_OPTIMIZATION_BIT`.

`MaximallyReconvergesKHR` crashes igc64.dll.

**What does line up.** He read `VK_KHR_pipeline_executable_properties` statistics. The arm program (two-lane, subgroup 32) is the only pipeline in the test that Intel compiles with register spills: 28,938 instructions, **7,872 bytes of scratch**. The test's other 42 pipelines have 100 to 1,813 instructions and 0 scratch. Every failing variant spilled 7,296 to 8,160 bytes. His reading, still an inference: the wrong words are other live values, the kind a spill or fill going wrong would produce.

**He can now report Intel's instruction count and scratch size with pass/fail for any build.** That's a direct signal whether a change stops the spill. He suggested lowering register pressure in the two-lane lookup, "for example the slot loop not unrolled, or fewer values live across the lookup".

**His correction:** `APS5_SINGLE_LANE=all` stops before the arm dispatch (`the 32-lane host build did not run two lanes per invocation`), so it never ran the failing pipeline.

## What to do

1. **Find what makes the arm's two-lane module heavy.** Use the module from `RecompileTwoLanes` (subgroup 32, spanned waves off), untraced, at `992d97fae8` (the trace branch).
   - Instruction mix and size by region: the waterfall/slot loop, the three nested lookups, the image ops, the BDA helpers, the per-half duplication. Is any loop unrolled? What is mrfelek's "slot loop" in this module?
   - **A register-pressure proxy.** Write a small liveness script over the SPIR-V: SSA values live at each point, per function after inlining, or per block if that's easier. Report the maximum and where it occurs. Run it on the arm module and the sibling's (`--pointer-vsharp-child-key`; its pressure on Intel is unknown, but it passes there per mrfelek's ctest 30/31) for comparison.
   - Say which values are live across the pc 0xfc lookup, and why. For example: both lane halves' guest registers held at once, the trace's 24 words (only in trace builds), and so on.
2. **One variant branch, `prm/9969-intel-pressure`, on `prm/9969-intel-trace` (992d97fae8), so the trace still works.** Make the one change that, by your proxy, cuts the peak live values the most for this module, without changing what the program computes. Possible directions; pick from what step 1 shows, don't take these as given:
   - emit a loop that is unrolled now as a real loop;
   - finish one lane half's work before the other's, where the emitter now interleaves them and keeps both live;
   - stop carrying values across the lookup that can be rematerialized after it.
   - Keep it as small as possible, applied in the two-lane path only. Every other layout must emit byte-identical SPIR-V; show that with `cmp` on the 8-lane lavapipe modules.
   - If no change under ~150 lines gives a clear cut, say so and don't build one. Give the numbers and the two best candidates instead.
3. **Lavapipe proof:**
   - spirv-val on the changed modules;
   - the trace 3 of 3 decoding 256/256;

   - the proxy's peak before and after.
