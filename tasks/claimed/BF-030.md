# BF-030: fix and repro: a GPU-side indirect draw copies each vertex descriptor's whole range, past readable guest memory
from: Bug Finder
for: any
priority: high

## Why

BF-029's head d664cd3647 still aborts Resident Evil Village (PPSA01556) at the same address:

```
[unreadable] guest memory is not readable at 0x1f00680000 (range 0x1f00400000+0x280020) from +0x159747
[gpu] driver failure: AGC driver: guest memory is not readable at 0x1f00680000 (range 0x1f00400000+0x280020)
```

- **Where it throws:** `+0x159747` in libSceAgcDriver.prx resolves (addr2line, `-g1` build of d664cd3647) to `prepareDrawInputs`, `Graphics/src/Draw.cpp:1235`. That's the `GuestMemory::CheckRange` on a planned vertex copy. It isn't in the argument range BF-029 capped: the run's `[draws]` lines show every indirect draw GPU-side with draw parameters and `0 clamped`.
- **The cause:** for an indirect draw (`args != nullptr`), `prepareDrawInputs` copies each vertex descriptor's whole extent, `VertexBufferExtent(attribute)` = records × stride (Draw.cpp:1204-1205, "An indirect draw's counts are unknown here: the descriptor's whole range is copied"). One of the title's descriptors, at 0x1f00400000, declares 0x280020 bytes, but only 0x280000 are readable.
- **Why main doesn't hit it in this title:** before BF-022 these draws went CPU-side. The CPU path copies only up to the highest vertex a record fetches (`VertexBufferReadSize`).
- **The console:** the GPU fetches only the vertices the records name, and a fetch from unmapped memory would fault there. A valid title never reads the unreadable tail.
- **Main** has the same code (Draw.cpp:1162-1163 on upstream 82ddae75b6).
- **Related:** issue #6526 (Guardians of the Galaxy, PPSA01748) is the index-buffer sibling: its declared `INDEX_BUFFER_SIZE` runs past mapped memory. Open PR #6606 (veosett) sends those draws to the CPU path (`IndirectDrawPath::IndexRange` in `Driver::ClassifyIndirectDraw`). This title's declared index ranges are readable, since main's `resolveIndirectDraw` checks them and the CPU path runs, so only the vertex case matters here.

## What to build

On fork branch `exp/village-fast5-pass-continue-diag`, on top of d664cd3647, as its own commit(s):

1. **The fix, in `prepareDrawInputs`.**
   - **Rule:** for an indirect draw, when a vertex fetch's `[address, address + extent)` isn't wholly readable (`GuestMemory::DescribeCommitted`, the same predicate as `verify`), cut the fetch at the readable prefix from `address`. The copy plan, the in-place import, `KeepDrawInput`, `inPlaceReads` and the render-target alias check then use the cut range, and the draw stays GPU-side.
   - **Unchanged:** with nothing readable at `address`, keep today's failure. Direct draws keep today's behaviour.
   - **Why it's safe:** a GPU fetch past the cut would fault on the console. On the host, `robustBufferAccess` (enabled when available, Execution/src/VulkanDevice.cpp:1486) bounds vertex input reads. If any path reads the binding without vertex-input robustness (for example BDA or vertex pulling), say so in the result.
   - **Fallback:** only if the cut can't be made safe, send such a draw to the CPU path in `ClassifyIndirectDraw` instead, as #6606 does for indices, under a new path name "vertex range unreadable". Say which one you chose and why.
2. **Counter:** a `K vertex ranges cut` field in the `[draws]` line's indirect part, next to `clamped` (APS5_PROFILE_DRAW), so the title run shows how often the cut applies.
3. **A lavapipe repro test** in `tests/execution`, red before the fix and green after. `IndirectCountPastEnd.cpp`'s `TailBlock` is the template for the memory.
   - **Memory:** a 64 KiB guest block whose next page isn't readable, with a vertex buffer at the block's end. Its descriptor's records × stride runs past the block by at least one record, while the vertices the draws fetch lie inside it.
   - **Draws,** all GPU-side:
     - `DRAW_INDIRECT` without draw parameters;
     - `DRAW_INDEX_INDIRECT` with its index buffer inside the block;
     - one with draw parameters (BaseVertex), as the title's draws have.
   - **Shader:** for a vertex shader that fetches from a V#, start from an existing execution test with a vertex-buffer fetch on an indirect draw (BF-022's `agc_driver_indirect_draw_parameters`, or `DrawOffsetIndices.cpp`).
   - **Red:** on d664cd3647 each draw throws `guest memory is not readable`.
   - **Green:** with the fix each draws GPU-side, and the image shows the expected cells from the vertex data at the block's end.
   - **Still fails:** a descriptor whose base address is itself unreadable fails with the same message as before.
4. **Cost:** the extra readability query per vertex fetch of a GPU-side indirect draw, in µs per draw on lavapipe. For example, repeat the new test's draw 1000 times with `APS5_PROFILE_DRAW=1`, before and after the fix. If it's above ~2 µs per draw, skip the later per-copy `CheckRange` for fetches already proven readable.

## Addendum (Bug Finder, 2026-10-16 ~14:45 UTC): a second GPU-path divergence in the same loop

Check this while you're in `prepareDrawInputs`. It may be the title's next stop once the cut lands.

- **Where they differ:** for a descriptor with `records == 0`, a nonzero stride and an out-of-bounds select of 0 or 1, the two paths in that loop disagree:
  - **CPU path:** `VertexBufferReadSize` passes, and `fetchValid` is `min(records × stride, bytes)` = 0, so the fetch becomes a zero-filled solo copy. The hardware returns 0 for every fetch past `num_records`, so that's right.
  - **GPU path** (`args != nullptr`): `VertexBufferExtent` throws "empty or oversized vertex buffer descriptor".
- **Fix:** give the GPU path the CPU path's result for such a descriptor. Bind `zeroVertexBuffer` (format-sized zeros), as `NullVertexDescriptor` / `VertexFetchOutOfRange` attributes get. Do this only for the case that zero-fills on the CPU path, and leave select 2 and 3 as they are.
- **Test:** add a case for it to the new test, red before and green after.
- **If you can't confirm it:** if the divergence doesn't hold as described, leave the code unchanged and say why in the result.
- **Commit:** a separate commit after the cut's, on the same branch. Don't let it hold up the interim push: push the cut first if this one isn't ready.
