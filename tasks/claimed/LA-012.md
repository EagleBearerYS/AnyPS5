## Why

Two of LA-004's open problems (`results/cloud-5/LA-004.md` on `cloud-results`) are still open. They are numbered as in LA-004.

- **5, correctness: part (f) reads zeros without eager write-back.**
  - **Setup:** a heap cap of 2, host imports and `APS5_GPU_PATH=1`.
  - **What happens:** the warm draw reads zeros, "(f) the warm draw: pixel (0, 0) channel 0 is 0, expected 160", in 3 of 3 runs.
  - **The other configurations** pass without eager write-back. The harness parts all keep eager write-back on, so they never cover this case.
  - **What (f) exercises:** a program whose key finds no heap slot falls back to the CPU table path. Its warm draw then comes from the draw cache on the CPU table. In this configuration that warm draw reads zeros, and nothing reports it.
- **4, cost: every unwatched entry is re-checked every frame.**
  - **What it is:** with host imports, a host import unregisters its allocation from the write watch, so lane A re-checks every live entry once each time the collect epoch moves.
  - **What it costs:**
    - about 150–170 µs per entry on cloud-5;
    - 40–50 µs per draw at 256 entries, growing with live entries;
    - most of the difference between the import path's ~82 µs per draw and the copy path's ~30 µs on LA-004's Village-shaped bench.
  - **LA-004's suggested direction:** a finer test, using the driver's `NewestStamp` over the entry plus the storage cache's own state, without the epoch.

## Note from lane A's PC session (10:32 PT): take driver CPU by process, not by threads

The bench under "Tests" asks for "driver CPU µs per draw, by the thread-CPU method". Use LA-006's method instead (`results/cloud-2/LA-006.md` §1.1). The PM made it the method for lane A from now on.

- **Driver CPU:** the process's utime+stime from `/proc/<pid>/stat` over the measured frames, which keeps the CPU of threads that exited, minus lavapipe's threads (`llvmpipe-0/1` and lavapipe's queue thread; a gdb backtrace at the window's start names them).
- **Why:** LA-004 §6's thread method sums only the threads alive at the window's end. The queue-0 worker (`Driver::enqueue`'s thread) sometimes exits inside the window, and its CPU is lost. A check run gave 147.1 µs per draw by process against 84.1 µs by threads.
- **Before and after both by the process method.** The ~82 µs (imports) and ~30 µs (copies) under "Why" are LA-004's thread-method figures and may be low. Take the "before" again on 9673cb568 rather than quoting them.
- If you have already taken thread-method numbers, keep them in the result, labelled as such, beside the process-method ones.
- Re-checks per frame, inserts and refreshes are counts, so they don't change.

## Note from lane A's PC session (11:36 PT): LA-008 found one cause of part (f)'s zeros; check it before writing a fix

LA-008 is done (`results/cloud-1/LA-008.md`, fork `exp/lane-a-expect` fa7bcb91b, on `exp/lane-a-v2` b63fa365d). Its commit **7ba9be127** carries a fix that may be part 1 of this task. In LA-008's words:
- A key expected before its draw has host-imported the guest memory holds a copied texture.
- Its next refresh finds the imported storage view and replaces it, taking a second slot while the first is still held.
- Under `APS5_HEAP_SLOT_CAP=2`, LA-010's margin (cd9222772 on v2) leaves the table one usable slot. The replacement found none, dropped the key, and part (f)'s warm draw read zeros: "(f) the warm draw: pixel (0, 0) channel 0 is 0, expected 160".
- **The fix** (`DeviceImageHeap::Slot`, `lookupKey`): a replacement may take one slot of the margin. The slot it replaces is released when its batch completes, so net use is unchanged.

What to do with it:
- **Check whether part (f)'s zeros on 9673cb568 without eager write-back come from the same replacement** (a refresh that swaps a copied texture for the imported view and finds no slot).
- **If they do,** take that hunk from 7ba9be127 as its own commit on your branch, with LA-008's reasoning and commit named in the body, instead of writing a second fix. LA-008's expectation code itself is not for this task.
- **If they don't,** fix the cause you find, and say how it differs from LA-008's.
