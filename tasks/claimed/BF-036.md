# BF-036: architecture ceiling: how far multi-threaded queue-0 draw recording can go (lavapipe, throwaway)
from: Bug Finder
for: any
priority: high

## Why

The user wants the architecture track to give the largest gain it can ("no performance target, just as good as you can possibly do") across three titles: Resident Evil Village (PPSA01556), Planet of Lana (PPSA19450, Unity) and Animal Well (PPSA22520). All three are CPU-bound on queue 0's single thread:
- **Resident Evil Village's menu:** ~1 ms per draw packet in `Driver::draw` / `Graphics::Draw`, with bindings, resource lookup and readTarget the big parts.
- **Planet of Lana:** the queue-0 worker ~92% busy, `DRAW_INDEX_2` taking 8.2 s of every 10 s.
- **Animal Well:** draw recording, much of it inside the Vulkan driver.

One candidate is recording queue 0's draws on several threads. Main pipelines decode and commit on two threads already: #1201/#1202, the `DrawPipeline::Queue0` committer, depth 8, default on. #1896 pipelines indirect draws. Issue #5485 (eliyarson's `APS5_MT_RECORD`) was closed in favour of #1201/#1202. No path records into secondary command buffers today: `vkCmdExecuteCommands` doesn't appear in the driver.

This task measures the ceiling: how much of a draw's driver time could run on K threads, and what a throwaway prototype gets.

## What to build

On a new fork branch `exp/mt-record-ceiling` from upstream main 66e290f1c0 or newer. Throwaway, no PR.

1. **A harness:** an execution test with a `--cost N` mode, like BF-030's `IndirectVertexPastEnd`. One submission on queue 0 carries M direct draws, for M = 64, 512 and 2,048. Each draw has the same pipeline and binds a realistic set: a few vertex buffers, 8-16 textures, one or two constant buffers. Each draw changes only its user-data words, as a title's per-object draws do. Run it warm (second submission onwards).
2. **The Amdahl split,** per draw, µs, median of ≥5 windows:
   - total driver time on the packet worker and on the committer;
   - time inside `GuestMemory::GpuMutex`;
   - time inside Vulkan calls (`vkCmd*`, `vkUpdateDescriptorSets`, allocation);
   - time in the driver's own work (decode, `ShaderResources` build or lookup, `prepareDrawInputs`, barriers and passes).
   - Say what holds the GPU mutex per draw and why, by function. That number caps any parallel recording.
3. **A ceiling prototype:**
   - split a submission's draw run, between render-pass, barrier and label boundaries, into K chunks;
   - record each chunk on its own worker into a secondary command buffer (with `VK_COMMAND_BUFFER_USAGE_RENDER_PASS_CONTINUE_BIT`, or dynamic rendering's inheritance);
   - execute them in order from the primary.
   - Per-thread descriptor pools and staging; shared caches behind finer locks, or per-thread caches. Hold the GPU mutex only where guest memory or the recorder's shared state is touched.
   - Measure µs per draw (wall, per submission) at K = 1, 2, 4 and 8, against main's path.
   - **List what's unsafe as built:** flush hooks, pending writes, labels, the pipelined committer. Those are the work a real version must do.
4. **Map the hard parts** for the design: which driver state is per-submission or per-draw today and would need to become per-thread (recorder batch, pending-write registry, resource caches, descriptor set pools, the ShaderResources cache), with file:line pointers.

## Addendum (Bug Finder, 2026-10-16 ~19:45 UTC): the title's GPU mutex numbers, and moving resolution out of the lock

In Resident Evil Village's profiled menu (`[lock]`, 11-s windows), the GPU mutex is the serial point for every queue:
- **Queue 0** holds it 4,851 ms of each 11 s for draws: 3,585 holds, 1.35 ms each, max 77.8 ms. It holds it 541 ms more for dispatches.
- **Queue 0x20** holds it 850 ms, almost all for dispatches.
- Queue 0 waits 828 ms for the mutex, mostly behind 0x20's dispatches.
- **In code:** `Driver::commitDraw` (Execution/src/Driver/Draw/Draw.cpp, about line 612 on main) takes the mutex around the whole `VulkanDevice::Draw`: resource resolution (images, bindings, lookup, readTarget) and recording. Since #1201/#1202, only capture, recompile and vectors run before it, unlocked.

So in the title, parallel recording pays only once the resolution leaves the lock. Please add to items 2-4:
- **In item 2's split,** put "inside the GPU mutex" next to "resolution inside the mutex" (`ShaderResources` build or lookup, image lookup and validation, bindings) and "Vulkan recording inside the mutex".
- **In item 3, a variant (b) next to the secondary-buffer prototype (a):** resolve a draw's resources *before* taking the mutex. Do it against the same stamps or epochs the resolution reads (the write tracker's state for the bound images and buffers, the texture cache's generation). Then, under the mutex, recheck those stamps and redo the resolution only if one moved. Report:
  - the time per draw inside the mutex, before and after;
  - how often the recheck fails;
  - (b) alone, and (b) under (a) at K = 1, 2, 4 and 8.
- **Prior art to read (ideas only; if code is reused, it keeps him as author or names him):** fable-void's public fork, https://github.com/fable-void/AnyPS5, branch `wip/new-gpu-path`, moves work before the device lock in these commits:
  - `0a54c54654`: acquire an address-based dispatch's address space before the device lock;
  - `c75afe5ebd`: rebuild a stale address space before a draw takes the device lock;
  - `fbec52d92d`: build a draw's shader library parts before taking the GPU lock;
  - `4ebb2c4785`: create compute pipelines before taking the GPU lock;
  - `77fe410874` and `f0df63746b`: create graphics pipelines and library parts outside the store locks.

  His design differs from main's (resources read on the GPU at run time), so take only the lock-scope ideas. If the fork can't be fetched from there, skip it.
- **In item 4's state map,** mark which state the under-lock recheck must cover for (b) to be exact.
