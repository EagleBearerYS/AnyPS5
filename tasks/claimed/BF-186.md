# BF-186: span table-reading wave64 programs by default on Intel drivers that share handles across fused EU threads, stacked on #7395
from: Bug Finder (2026-10-24 18:00 PT)
for: any
priority: high

## Why

On Intel Gfx12 (Xe-LP, Xe-HPG, Xe-LPG), two EU threads run fused in lock step and share one sampler/texture handle.
- **Where it breaks:** a single-wave wave64 compute program with 64 threads, on a 32-lane host subgroup, runs at two guest lanes per invocation (`laneCount == 2`). That makes a workgroup one SIMD32 thread, so a fused pair can be two workgroups.
- **Why our SPIR-V allows it:** the emitter marks the table index uniform there (`tableIndexNonUniform` false, `SpirvEmitter.cpp` ~L319 on #7395's head). Workgroup 1 then reads workgroup 0's sampler.
- **Evidence:**
  - Mesa issue 16622, fixed by Mesa !37394 in 25.3 ("Fix texture/sampler accesses with EU fusion on Gfx12.X HW").
  - Capmare's ANV trace: [7395 c6254952671](https://github.com/boykopovar/AnyPS5/pull/7395#issuecomment-6254952671) and [c6263589980](https://github.com/boykopovar/AnyPS5/pull/7395#issuecomment-6263589980).
  - BKlaasWerkman's Arc runs on Intel's Windows driver 101.9150, which has no fix: [7395 c6369252849](https://github.com/boykopovar/AnyPS5/pull/7395#issuecomment-6369252849) and [9969 c6369308193](https://github.com/boykopovar/AnyPS5/pull/9969#issuecomment-6369308193). `agc_driver_nested_sampler_table` and `agc_driver_pointer_phi_sampler_table` fail 3 of 3 by default, pass 3 of 3 with `APS5_SPANNED_WAVE=1`, and an RTX 3060 Ti passes both.
- **Why spanned waves fix it:** they make the workgroup two full 32-lane subgroups, so the fused pair stays inside one workgroup.
- **Ruled out:** a `NonUniform` index and `OpGroupNonUniformBroadcastFirst` (Capmare, ANV: no change).
- **Cost of spanning, measured (10-24):** on Resident Evil Village (PPSA01556), with `APS5_SPANNED_WAVE=1` forcing every qualifying program to span, there was no measured cost on one CPU-bound title (RTX 3070 Laptop GPU, clocks not locked). Over menu + 5..15 the arms ran at 0.325-0.398 fps (spanned) and 0.350-0.437 fps (default), inside the spread between runs of the same arm, with 0 fallback lines, 0 device faults and no hang. A GPU-bound title could still show a cost this one can't.

**Two constraints:**
- **Spanned waves can hang.** They exchange ballots, shuffles and reductions through workgroup memory and barriers, and `docs/dev/debt/shader.md` (~L180) says an exchange emitted inside per-lane control flow would hang a spanned wave. The emitter has no uniformity check. Table programs exchange, since their key comes from a ReadFirstLane.
- **lavapipe can't run the spanned path.** Its subgroup is 8, so `computeFullSubgroups`, and with it `spannedWaves`, stays off. GPU evidence for the spanned path comes from NVIDIA and Intel testers, not from this machine. Linux evidence here is emitter-level: modules, spirv-val, and the choice per program.

## What to do

1. **Detection** (`Execution/src/VulkanDevice.cpp`, beside the driver properties ~L1273 and the subgroup setup ~L1974-1989). Add a pure function, unit-testable, from `driverID`, `driverInfo` and `computeFullSubgroups` to "this driver shares texture and sampler handles across fused threads":
   - `VK_DRIVER_ID_INTEL_PROPRIETARY_WINDOWS`: yes, at any version (no fixed version is known; 101.9150 is affected);
   - `VK_DRIVER_ID_INTEL_OPEN_SOURCE_MESA`: yes when the Mesa version parsed from `driverInfo` is below 25.3. If unparsable, yes, with a log line;
   - everything else: no;
   - always no without `computeFullSubgroups`.
   - **Optional Gfx12-only filter:** Xe2 and later have no EU fusion. Check Mesa's ANV source for what it reports as `minSubgroupSize` per generation (8 on Gfx12, 16 on Xe2?). Add the filter only if the source confirms it, and quote the line. Otherwise leave it out and say so.
   - Log the decision once at device creation.
2. **The switch.** `APS5_SPANNED_WAVE` becomes a value:
   - unset: the narrow default from step 3, only where step 1 says yes;
   - `1`: every single-wave wave64 compute program, as today;
   - `0`: never;
   - `tables`: the narrow set on any device with `computeFullSubgroups`, so it can be checked on NVIDIA.

   Anything else is refused with a clear message. Update `docs/dev/ENVIRONMENT.md` (the row at ~L384 says "presence" today) and the debt entry in `docs/dev/debt/shader.md` (~L198) to match.
3. **The narrow default** (`SpirvTarget`, `Recompiler`, `SpirvEmitter.cpp` ~L305-319). A new target option (name it, for example, `spanTableWaves`) spans a program only when all of these hold:
   - it already qualifies for `spannedWave` (halfHost, compute, no derivatives, 64 threads);
   - it reads an image or sampler table through a per-workgroup index (the path where `tableIndexNonUniform` would be false). Find the cheapest pre-emission predicate (program metadata or bindings) and say which.

   Everything else keeps two lanes per invocation. The option goes in the cache key (`CacheKey.hpp` ~L324), the request serializer (`RequestSerializer.cpp` ~L876/936, with a version bump) and `FormatVersion` (`ShaderDiskCache.hpp`; #7395's head is at 50 and main at 47, so take 51 and say so; other stacks use 49-52, and the number is settled when it opens).

Track in the emitter state when it is inside a construct it opened per lane, meaning a selection or loop whose condition differs per invocation, and list each such construct you find. The emulated 64-bit LDS atomics' lock loop (`LockedLdsUpdate`, `SpirvMemoryInstructions.cpp`) is the known one; per the debt entry it already ballots within its own subgroup.
   - When a spanned exchange (`SpannedBarrier` in `SpirvSubgroup.cpp`) would be emitted inside one, throw `SpannedWaveUnsupported` with the construct named.
   - `Recompiler.cpp` (~L656) already catches it and re-emits at two lanes. Make it clear the new option too.
   - Make the fallback's log line say that the fused-thread hazard remains for this program.
