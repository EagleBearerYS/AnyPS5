  - **The stop:** `shader 0xc28131ee00 stage 5: device image interface: two image interfaces share the id 0x26f9d359bfa6fb8e`, at 171 s and at 316 s, with `APS5_GPU_HEAP=1 APS5_GPU_PATH=1`.
  - **The tree:** main 73f4f7e06e + #7978 + #9183 + #9950 + #13146 + #13147 + #10193's head 8403a9b05c.
  - `ImageResource` is the same at #10193's head as at #7642's.
- **The code:** at 22cead42b2, `core/shader/recompiler/Optimization/src/ResourceMaterializer.cpp`, from our commit b9232e5980.
  - `ResourceMaterializer::RegisterDeviceImageInterface` (about line 2745) keys the registry by `DeviceImageInterfaceId(image, modes)`.
  - It throws at line 2757 when an entry with that id exists but `same()` fails.
  - `same()` compares `entry.image != deviceInterfaceImage(image)` and each mode the same way. That's `ImageResource`'s **defaulted `operator==`**: every field.
  - `deviceInterfaceImage` clears only `source`, `firstUsePc` and `table`, for a table image.
  - The id comes from `mixImageInterface`, which mixes an explicit field list.
- **The gap, read by the PR Manager:** five fields of `ImageResource` (`IrMetadata/Resources.hpp`) are compared by `==` but not mixed into the id:
  - `adjustedSample`;
  - `dimensionQueryOnly`;
  - `sampledOnly`;
  - `optionalDescriptor`;
  - `targetMerge`.
  So two device-table images (or modes) that differ only in one of those fields get the same id, and the second registration throws. A true 64-bit collision is not a credible reading. **Confirm this, or show it wrong.**
  - `targetMerge` is read 5 times in `core/shader/recompiler/SpirvBackend`. The other four aren't read there, but are read elsewhere (6-11 uses each in `core/shader` and `libSceAgcDriver`).

## What to do

1. **Read** each of the five fields' uses at 22cead42b2, and decide per field:
   - **(H) hash it:** the field changes what the device image path emits or binds for that image or mode. That covers the SPIR-V, the runtime image modes, `ExpectedDeviceImages`, the driver's `DeviceImageTable` / `LookupDeviceTableTexture`, and the `deviceImageUses` checks.
   - **(N) normalize it:** clear it in `deviceInterfaceImage`, because the interface doesn't depend on it, so equal interfaces merge.
   - **If a field's effect isn't clear, take (H).** Two ids for one interface costs a registration; a merged pair that differs is wrong code.
   - Give file:line for each decision.
2. **Check persistence:**
   - Is the id, or anything derived from it, stored in the shader disk cache? `ShaderDiskCache` compares `deviceImageInterfaces` at `tests/ShaderDiskCache.cpp:200`.
   - Is it baked into emitted code, or into a pipeline key?
   - If a changed id can meet an entry cached under the old hash, the fix needs the cache's format-version bump, as other recompiler changes do. Say which, with lines.
3. **The fix:** one commit on 22cead42b2, branch `prm/7642-interface-id` on the fork. Push it to the fork, not to the PR branch.
   - Make `mixImageInterface` and `deviceInterfaceImage` together cover exactly what `==` compares.
   - **The test, in the same commit:** extend the existing interface test in `tests/execution/DeviceImageTable.cpp` (about lines 715-735, the one that checks `DeviceImageInterfaceId` / `RegisterDeviceImageInterface`). For each of the five fields, an image differing from the base only in that field registers without throwing. For an (H) field its id differs; for an (N) field it equals. Do the same for one mode differing in one (H) field.
   - **Red:** the new cases on 22cead42b2 without the fix fail with "two image interfaces share the id". Show the line.
4. **Runs** (CI's Linux flags, lavapipe, as `runner`, `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx`):
