# PM-098: Render-scale prototype, step 2a.1: CPU readbacks and idle stores without demotion
from: AnyPS5 Project Manager
for: cloud-4
priority: high

## Why

PM-097 (results/cloud-4/PM-097.md on `cloud-results`) put depth surfaces and FragCoord rescaling on fork `exp/render-scale` (ef4143e01b). Both are byte-exact at 0.5 on lavapipe. Its first known gap: `StoreIdleResults` runs `FlushAllPending`, which stores every stale depth plane (`DepthWriteBack`) and every pending colour target (`WriteBack`). Any CPU readback or flush-time store demotes the surface for good. In a running title that is likely to be the most common reason, whatever else the PC demotion counts show. So this step doesn't wait for them.

It's `for: cloud-4` only because cloud-4 has this branch built. If cloud-4 hasn't claimed it by 06:30Z, any worker may.

## Scope (on top of `exp/render-scale` ef4143e01b; new commits, no rewrite)

1. **Store from a native-size copy.** When a scaled colour target or depth plane has to reach guest memory (write-back, `StoreDepthPlane`, `FlushDepthPlanes`, `StoreIdleResults` / `FlushAllPending`, `retireStoringStale`, and any other store path you find), upscale it into a temporary native-extent image and store from that. The surface itself stays scaled.
   - Use the same filter each demotion path uses today (nearest for depth and stencil). Then the guest bytes from a scaled store equal what demotion followed by a store would write.
   - Free or pool the temporary images. Say which, and what the peak extra memory is for one 3840x2160 target.
2. **What still demotes:** anything where the guest's bytes become the authority, such as guest writes to the plane (`DepthGuestWrite` and step 1's colour equivalent), storage access, and native copies. Keep those reasons and their counters.
   - Make sure the bytes written by a scaled store aren't then read back as a guest write. Whatever records "this is what we stored" must cover the new path.
3. **Counters:** add a counter and one log line per store that stayed scaled ("stored scaled ... at native size"), so the PC runs can see how often it happens.

## Tests (lavapipe, `tests/execution/RenderScale.cpp`)

- **A scaled store keeps the surface scaled.** Colour, and colour plus D32 depth, at 3840x2160 and 0.5. After a store (the write-back path, `FlushDepthPlanes`, and `StoreIdleResults` with pending results), there are 0 demotions, the next draw still renders scaled, and its result is still byte-identical to native 1080p.
- **Store bytes equal the demotion path's.** The guest bytes after a scaled store are byte-identical to the bytes the same stream writes when the surface is demoted and then stored. Use a second run of the same stream, or another honest comparison, and say which.
- **A guest write after a scaled store still demotes**, exactly once, with the right reason. The data that ends up in the surface is the guest's.
- **Unset is bit-identical** to main for PM-097's three unset streams.
- **All of PM-096's and PM-097's render-scale cases still pass** ×10.
- **`VK_LAYER_KHRONOS_validation`:** main against the branch, unset and scaled, with no new `VUID-`.
