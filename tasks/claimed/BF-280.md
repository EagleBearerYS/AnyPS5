  - `addAddressStoreSpans` adds every writable heap mirror in `space->base`, which here includes the title's 2,712 MiB main heap.
  - Then `growResident` binds the whole span.
- **A data point, not a fix** (issuecomment-6498764009): with those unreferenced `space->base` heaps filtered out, the title ran 240 s with no stop. That's the loss case itself, though: stores into those heaps would be lost.
- **91e4d82e7c still scales with the span in three places:**
  - the GPU reference copy is the whole span;
  - `growResident` binds the whole span;
  - `RecordCopyBacks` reads the whole span back on resident mirrors.

  On top of that, BF-277's Q2 trace shows the whole-span pending-write note makes every later address-based build over that heap `Recorder::Sync()`.

## Hard constraints

1. **Nothing scales with the committed heap:** no mirror residency, reference copy, readback or pending-write note. A storing dispatch over a multi-GiB heap must run within a small `APS5_HEAP_MIRROR_MIB`.
2. **No store is lost,** the first dispatch's included.
3. **CPU bytes written during the dispatch survive,** sub-dword ones included. The report's original store was 1 byte.
4. **No placeholder-throw assertions.** An overflow may refuse loudly, as the written-page record already does.

## Facts to build on

- **The written-page record** (`BdaAbi.hpp`: `WrittenPageShift = 12`, 2048 slots, `note_bda_write` after every successful Write lookup) already tells the host, after the dispatch, which 4 KiB pages were stored to.
- **A mirror's bytes equal guest memory at upload,** for every served page, after `FlushChanged`. So for a stored page whose guest bytes are unchanged since upload (write-watch, `UnchangedSince`), guest memory itself is the reference, and no pre-dispatch copy is needed. The only open case is a page the CPU also wrote during the dispatch.
- **Resident mirrors bind only nonzero blocks.** A store into an unbound block is dropped by Vulkan, which is why 781dc4525b binds the whole span.

## Do

Design, then build. Explain the choice against the alternatives you considered. The directions to weigh, which are mine:

- **Per-byte store masks in the written-page slots** (core/shader is allowed now: `SpirvBdaLookup.cpp`/`BdaAbi.hpp`; move the shader cache key).
  - **The mark:** each store also sets mask bits for the bytes it wrote, an atomic OR, in a 512-byte mask beside its page slot.
  - **The write-back:** copy only the masked bytes from the mirror to guest memory. Then no reference is needed at all, CPU bytes survive at byte granularity, and the pending-write note can be just the stored pages, recorded after the dispatch. Say whether the note has to be known before the dispatch for ordering. If it does, what's the narrowest correct note?
- **Stores into unbound resident blocks:**
  - **Redirect** them into a zeroed slot page (the block was all zero in guest memory). Reads in the dispatch would check the slot first, with a per-block residency bit in the table. After the dispatch, bind just those blocks (`growResident` per block) and fill them from the slot.
  - **Or** show that another approach meets constraints 1 and 2, e.g. binding a block on first need between dispatches is impossible mid-dispatch, so say what you'd do instead.
- **Guest-as-reference instead of masks:** say what happens on a page the CPU also wrote during the dispatch, and whether that case can be made safe.
- **In-place import:** check why Ghost's main heap is a mirror at all, rather than imported in place (`APS5_HOST_IMPORT_MIB`, a driver refusal?). If a storing build could import in place within the import budget, say so. That's an option, not the answer.
