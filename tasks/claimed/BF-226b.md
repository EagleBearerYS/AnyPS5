- BunnyFl's first comments: argument checks. #10879 https://github.com/boykopovar/AnyPS5/pull/10879#issuecomment-6397162725 and #10890 https://github.com/boykopovar/AnyPS5/pull/10890#issuecomment-6397162960. BF-226's task file (`tasks/done/BF-226.md`) quotes both in full.
- BunnyFl's table comment, #10879 https://github.com/boykopovar/AnyPS5/pull/10879#issuecomment-6397362281:
  - **IDs:** the request ID comes from the NP service. Create asks it for one and returns whatever positive value it gets, so the module doesn't show the first ID or whether IDs count up or get reused.
  - **Capacity:** the library keeps its own 64-slot mask. The 65th live request gives `0x80559D05` without contacting the service, and deleting a request frees its slot.
  - **Create edge cases:**
    - a negative service answer is returned as is, and the slot released;
    - an answer of 0 returns 0 with nothing recorded;
    - an already-live ID makes Create delete the new one at the service and return `0x80559D03`, as does a failure to allocate the record.
  - **Delete:** it always forwards to the service first. Then:
    - an ID not in the local table (never created, already deleted, 0, -1) gives `0x80559D0A`;
    - a live ID is unlinked and freed, returning 0;
    - one still in use by a running call is marked deleted, left in place, and the service's answer returned.
  - **Abort:** it only forwards to the service and returns its answer. There's no local lookup, and a later Delete still returns 0.
  - **Not initialized** (no service client yet): all three return `0x80550002`.

## Commit 1 v2, for #10879
**Branch:** `fix/npmanager-idmapper-measured-v2` on the fork: one commit on #10879's head 5997af6c13.

- **`sceNpIdMapperNpIdToAccountId` and `sceNpIdMapperOnlineIdToAccountId`:**
  - **Arguments:** 7, as e722b5a50d declares them: `int reqId, int userId, const void* input, void* output, uint32_t value, uint8_t, uint64_t`.
  - **Refusals:** request ID ≤ 0 → `0x80553085`; then user ID -1, a null input or output, or the value outside 1..1000 → `0x80553083`. The byte and the 7th argument aren't read, and there's no init or signed-in check.
  - **Past the checks:** answer `SCE_NP_ERROR_SIGNED_OUT` (offline model), writing nothing.
- **IdMapper requests are created, aborted and deleted on the service.**
  - `sceNpIdMapperCreateRequest` takes an ID from an IdMapper counter or table in the offline model, its own, not `sceNpCreateRequest`'s.
  - `sceNpIdMapperAbortRequest` and `sceNpIdMapperDeleteRequest` refuse ID ≤ 0 with `0x80553085` first. Past that they give the offline model's answers for that table, as #10879's original lifecycle did: abort keeps the request live, and delete frees it.
- **NpManagerInt Create, Abort and Delete:** BunnyFl's table, minus the init branch.
  - **Create:** a local 64-slot table; the 65th live request gives `0x80559D05` without asking the service. Otherwise it takes an ID from the offline model, its own counter for this family.
  - **Delete:** "forward to the service" (offline model, which accepts it). Then an ID not in the local table gives `0x80559D0A`; a live one is freed, returning 0.
  - **Abort:** returns the offline model's answer, with no local lookup, and leaves the request live.
  - **Edge paths:** implement the negative-answer, zero-answer, duplicate-ID and in-use paths as measured where the offline model gives a way in. Where it can't reach them, say so in the result; they're untested.
- **Error names:** e722b5a50d's `NP_ID_MAPPER_REFUSED_*` constants are fine. Add names for `0x80559D05`, `0x80559D0A` and `0x80559D03` the same way (no `SCE_` prefix, since the SDK names are unknown). #9726 adds `InvalidId = 0x80550015` next to `RequestNotFound`; keep both sides if that conflict shows.
- **Tests (`guest_np_manager`):**
  - the lookups: one case per refusal, each with only that fault; the order case; an output canary that survives; and SIGNED_OUT past the checks, also with value 1000, byte 0xff and an all-ones 7th argument;
  - IdMapper: Create gives a positive ID; Abort and Delete of ≤ 0 give `0x80553085`; the live and freed behaviour past that, with no cross-family ordering;
  - NpManagerInt:
    - 64 Creates succeed and the 65th gives `0x80559D05`;
    - after one Delete, the next Create succeeds;
    - a second Delete of an ID gives `0x80559D0A`, as do 0, -1 and a never-created ID;
    - Abort leaves the request live: a later Delete gives 0;
    - Abort of an unknown ID gives the offline model's answer.
- **Debt:** rewrite this PR's entries in the two-part form, credit BunnyFl's two #10879 comments, and record the init gap.
