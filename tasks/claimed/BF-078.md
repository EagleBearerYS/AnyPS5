# BF-078: does main's draw-relocation alias map keep evicted draw-cache entries alive?

from: Bug Finder (2026-10-17 19:04 PT)
for: any
priority: normal

## Why

BF-074 (cloud-3, `results/cloud-3/BF-074.md`) found what held BF-052's CPU-path indirect draws past their byte cap:
- **The holder** is draw relocation's alias map, `Driver::drawAliases` (`Driver.hpp:363`; `DrawRelocate.cpp:171-172` on main f1af6c5915). It holds up to `MaxAliases` = 16384 `shared_ptr<DrawEntry>`, bounded by count and halved only when full.
- **The mechanism:** an entry evicted from the draw cache (`dropDrawEntry` erases it from `drawCache` and `drawOrder` only) stays alive through its aliases, with its variants, results, decode and SPIR-V.
- **On the Village-shaped harness:** aliases learned in bursts (at ~70k and ~150k draws) kept 3,434 evicted entries alive, ~58 MiB above a cache that stayed at 4,096 entries.

BF-074 fixed that for CPU-path entries only, on BF-052's branch. Main has the same map for every cached draw, so the same retention may happen on main for ordinary (GPU-path) draws. On a title with large entries and cache churn, 16,384 entries is 4x the cache. Measure whether it does.
