# BF-323: design pass, read-only: reuse an address-based draw build whose snapshots moved (per-draw constant rings)

from: Bug Finder (PC)
for: any
priority: high

## Why

BF-322 (`results/cloud-3/BF-322.md`) found that address-based (BDA) draws re-prove unchanged state: about 955 of 1,126 µs per draw, with an upper bound of −2.64 s of the committer's 6.95 s per 10 s at Resident Evil Village's menu. Its S1 was a port of our closed #6636, and that **already failed on this title**:
- **q6636p (10-21, #6636 at fc9c5416fc, Village's static menu, profiled):** 17,613 proofs, **0 reused**. Every proof was refused for snapshots, with about 3 in-use refusals per proof.
- **BF-105 (qbf105, its diagnostic `d6dd7b0c3` on fc9c5416fc):**
  - 2,295 proofs, 0 reused;
  - the first failing check was **address 2,185**, then count 108;
  - **55 % of refusals came from 10 draw keys with 9+ addresses each:** per-draw constant rings of 0x50/0x70 bytes in 0x230200000+0x30100000;
  - so a per-key build set (BF-322's S3) doesn't rescue them.
  - Read BF-105's result and #6636's closing comment (https://github.com/boykopovar/AnyPS5/pull/6636#issuecomment-6316179021).

**The question:** can a build be reused while those moved snapshots are treated as **data**? Each use would re-copy its 0x50-0x70 bytes and re-point that range's page-table entry, instead of requiring the same address.

## Do (read only, no code)

Base: upstream `main` plus #12745's head (`pull/12745/head`), as in BF-322, with #6636's head b38ea43841 for its reuse proof (`SameSnapshots` and its address check).

1. **How a BDA draw reads its snapshots.**
   - Does the shader reach a snapshot range only through the BDA page table (`BdaResources`, the table built from the space's regions), or also through descriptor-bound buffers, SRT words or user data baked into the build?
   - Give the `file:line` of every place a snapshot's address enters the build: the table entry, the descriptor set, push constants, the recompiled program's constants, and any shader cache key.
   - **This decides whether re-pointing is exact.**
2. **What changes between uses of a ring draw:** the snapshot address only, or the size, the number of snapshots, or other bindings too. Infer it from BF-105's lines and the code's key, and say which fields #6636's proof compares.
3. **The per-use re-point, designed exactly:**
   - copy the moved bytes into the use's own storage (a slot like #8963's, or the build's copy region);
   - write that use's page-table entry for the guest range;
   - say how a use is ordered against the previous use's GPU reads, against GPU stores through BDA into the ring, and against the recorder's pending writes.
   - Also say whether a page-table rewrite per use needs a fresh table (the table cache, `BdaResources.cpp` ~115-209) or a per-use table slice.
4. **Can it be checked per use as cheaply as a `memcmp` of the moved bytes?** Give a per-use cost estimate in µs, built from the counters and the code:
   - the copy;
   - the table write or slice;
   - the descriptor or set work (`AllocateRewritten`, or a dynamic offset);
   - the fault record.

   **If it can't be exact at below ~300 µs per use, say so plainly.** The lane is then parked behind BF-321.
5. **Composition:**
   - #8963 (fault slots);
   - #12745's index (snapshots that didn't move);
   - #12840 (store pages);
   - #8104 (overlays);
   - BF-322's S4 and S5.
   Include a claim check of open PRs touching BDA tables or snapshot reuse since BF-322's.
6. **The exact change,** if there is one: PR-sized steps, each with a red test and a first-boot bar. The bar is the reused share of Village's 4,276 BDA draws per 10 s, read from #6636's `[rescache] address-based draws: reused / refused by reason` line.
