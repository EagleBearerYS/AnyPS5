# BF-064: pin Resident Evil Village's large private blocks to their allocation sites (lane B, memory budget milestone 2)
from: Bug Finder
for: any
priority: normal

## Why

Memory is a goal of the redesign. Milestone 2 is ≤ ~6 GB of the emulator's own private memory at Resident Evil Village (PPSA01556)'s menu, down from ~15–20 GB. Before cutting, the holders have to be named.

A read-only census of the PC's Village process at the menu (2026-10-17 09:39 PT, statistics only; base3a-family tree with BF-052, `APS5_LAZY_SHADER_PREPARE=1 APS5_NO_GPL=1`) found the emulator's private committed memory outside the guest spans is 15.3 GiB.
- **Sampling method:** 16 pages per allocation; a page "has data" if any byte is nonzero.
- **About 3.7 GB of that is pages that hold only zeros.**

The large blocks, by size class:

| size (MiB) | count | data share | what the first bytes look like |
|---|---|---|---|
| 768 | 1 | 38% | not a heap block; from byte 28, 32-bit pairs 0x30/0x10, 0x50/0x30, 0x70/0x50… (prev/next links 0x20 apart). The size fits 3 bytes per 4 KiB page over 1 TiB |
| 250 | 1 | 12% | known: `PageSpan::allocate()` in `Execution/src/GuestMemory.cpp` (BF-063 covers it) |
| 62.5 | 3 | 8% | malloc'd heap blocks; likely the write-watch tables (BF-063 looks for them) |
| 128 | 1 | 6% | heap block, zero at its start |
| 31.9 | 12 | 36% | heap blocks, zero at their start |
| 15.9 | 14 | 37% | heap blocks, zero at their start |
| 16, 32, 44 | 5, 2, 1 | 6–25% | heap blocks |
| 8.4 | 8 | 55% | heap blocks; data: repeated 32-bit 0x0b000000 |
| 4.0 / 2.0 / 1.5 | 40 / 67 / 21 | 8–16% | mostly zero |
| 2.1–3.3 and 1.4 | ~60 and 83 | 100% | heap blocks whose data starts with {a pointer into the block, 0xc2, 0x1, zeros…} |
| 24.6, 25.2 ×2 | 3 | 75–84% | floats; vertex-like data |

The process heap (one heap, 0x6d0000) is 6.3 GB in 400 segments, and 72% of its pages hold data.

**Size hints** (the PC's guest span is 0xFA00000000 bytes = 1000 GiB, from 0x200000000):
- **250 MiB** = 262,144,000 bytes = one byte per 4 KiB page over the 1000 GiB span. That's the page-state table.
- **62.5 MiB** = 65,536,000 bytes = one byte per 16 KiB page (`PS5_PAGE_SIZE`) over the same span. So look for three per-PS5-page tables of one byte each, allocated through the heap (new, vector or calloc).
- **768 MiB** = 0x30000000 = 12 bytes per 16 KiB page over 1 TiB, or 3 bytes per 4 KiB page over 1 TiB, or 24 Mi nodes of 32 bytes.
  - It's not a heap block, so something VirtualAllocs or mmaps it directly: our code, a library, or the Vulkan driver.
  - The Bug Finder ruled out these sites in our code: `GuestMemory.cpp:375` (250 MiB), the import probe at `GuestBufferMemory.cpp:2427` (16 MiB), the libSceFiber stacks (`Export.cpp:277`), and libkernel's mmap shim (`DirectMemory.cpp:84`, which places inside the guest arena).
  - Its first values step by 0x20, like the next/prev links of 32-byte nodes.
- **24.6 and 25.2 MiB float blocks** may be Vulkan host-visible memory the driver allocated (staging or mirrors). Say whether our code allocates host-visible buffers of that size class.

**No game data:** use synthetic harnesses and the code only.

## Steps

1. **Find the allocation sites on fork `test/three-title-base3a-6178` 32ac24cb32**, the closest tree to the PC's.
   - Run harnesses that bring up the device, guest memory, the write watch and the shader registry (for example `agc_driver_shader_residency_tests --measure 100 blocks 10`, or a draw-cost harness) under heaptrack, or another way to see where each allocation of 1 MiB or more comes from.
   - Match sizes against the table. Several are probably sized from the guest span, the page count or a pool constant, so the harness should reproduce them at the same size.
   - Also read the code for anything that VirtualAllocs or mmaps directly, like the 768 MiB block.
2. **For each size class you can pin, give:**
   - the allocation site (file:line, function);
   - what it holds;
   - whether it's committed or zeroed up front, and how much of it a typical run touches;
   - a cut proposal: commit on touch, a sparse or two-level structure, a smaller default, release when idle, or a pool cap. Give the expected saving at Village's data share above.
3. **The process heap's zero pages (~1.8 GB):** say whether they're more likely never-allocated committed tails or zeroed live objects.
   - On Linux, measure how glibc and a Windows-like policy differ on the same harness.
   - Propose a Windows experiment the PC can run, for example `HeapSetInformation(GetProcessHeap(), HeapOptimizeResources, …)` at start, or the segment heap through the app manifest. Say what it would change and what it could cost.
