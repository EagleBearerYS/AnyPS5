# BF-111: make BF-107's big-allocation counter capture call stacks on Windows (the boot got totals but 0 frames)
from: Bug Finder
for: any
priority: high

## Why

BF-107's counter (fork `exp/big-alloc-sites` **735b5f01c4**, `core/libs/prx/libc/src/BigAllocations.cpp`) booted Resident Evil Village (PPSA01556) on the PC (qbf107).
- **Totals: it worked.** Live big blocks grew from ~2.1 GB at the menu to ~6.6 GB eight minutes later, against +5.4 GB of private memory:
  - every 10 s, ~2,300–2,700 blocks are allocated and ~2,200–2,650 freed;
  - the size split at the peak: 1 MiB ×1,872, 2 MiB ×770, other ×1,359.
- **Stacks: none.** Every `(10 s)` line says "1 stacks, 0 stale". The `#1` line ends "... frames" with no frames, so everything fell into one empty stack.
- **The likely cause:** `CaptureStackBackTrace` (`RtlCaptureStackBackTrace`) unwinds through x64 SEH unwind data (`.pdata`/`.xdata`). The project builds MinGW code with `-fno-asynchronous-unwind-tables`; `core/libs/CMakeLists.txt` has to add `-fasynchronous-unwind-tables` back for `windows_write_watch_tests`. If the hook function itself has no unwind data, the first unwind step fails and the capture returns 0 frames.

## What to do

Branch `exp/big-alloc-sites-v2`: one commit on top of 735b5f01c4.

1. **Build `BigAllocations.cpp`** (at least the hook functions and whatever they call up to `CaptureStackBackTrace`) with `-fasynchronous-unwind-tables` (`set_source_files_properties` or a target option), so unwinding starts out of the hook.
2. **A fallback, when `CaptureStackBackTrace` gives fewer than 3 frames:** scan the current thread's stack from the hook's frame upward, at most 32 KiB, and never past the stack base from the TEB (`NtCurrentTeb()->StackBase`).
   - Keep the qwords that point into an executable section of a loaded module (from the module list the hook installer already walks).
   - Keep only those whose preceding bytes decode as a `call`: `E8 rel32` 5 bytes before, `FF /2` with a ModRM 2–7 bytes before, or `41 FF /2`.
   - Take the first 16, and mark the line "scanned" so a reader knows the frames are heuristic.
3. **Keep the output format.** Frames as `module+0xoffset`, plus a per-stack flag for unwound or scanned.
4. **Test what you can:**
   - Under Wine with MinGW (BF-109 ran Wine 9.0 there): a Windows test executable that allocates 1 MiB through `malloc` and `operator new`, from two named functions compiled without unwind tables, with the hooks installed.
     - The `[bigalloc]` stacks must name both functions after `tools/resolve_bigalloc.py`, by unwinding or by the scan.
     - The red is 0 frames, as on the boot.
   - On Linux, the existing test still passes.
5. **MinGW:** a syntax check of the changed files. The PC runs GitHub's Windows build before the boot.
6. **Also, from qbf107's newest-block samples**, say what these likely are, so the stacks have candidates:
   - 2,097,176-byte blocks (2 MiB + 24) whose records are 16 bytes: `0001002075000000 30005004007f8000 000400203f19d4c8 0000520400002000 001000204f800000 0000520400200000 003000204d400000 0000520400008000`. Each record looks like a guest address with a 16-bit tag in the high bits, then a size with flags `0x5204`/`0x3000_5004` in the high bits. Search the driver and recompiler for a 16-byte struct like that, e.g. `ShaderRecompiler::MemoryRegion`, a packed region or a capture record.
   - ~790 KB blocks that start with a host pointer, then a small count (0x60/0x70/0x90/0xa0), then guest pointers (0x2_62fb…, 0x2_63e…).
   - The draw cache (`Execution/src/Driver/Draw/DrawCache.cpp`) is already known to hold ~2.1 GB at the menu (BF-108 fixes it). Say whether these structures are draw-cache variant members (`runs`, `words`, `captured`, `spans`) or something else.
