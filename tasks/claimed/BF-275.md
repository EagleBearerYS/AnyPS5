# BF-275: B266-1 ft_mem_qrealloc from a count of 0 zero-fills, as FreeType 2.4.12

from: Bug Finder
for: any
priority: high

## Why

BF-270 (`results/cloud-5/BF-270.md`) compared FreeType 2.4.12 with 2.13.3 for the eight `ft_mem_*` rows on fork `feat/libSceFreeTypeOt-sourced-b266-1`, head e70e5ecd0a. They differ in one observable place:
- **2.4.12:** `ft_mem_qrealloc` with `cur_count == 0` calls `ft_mem_alloc`, which zero-fills ([ftutil.c L146](https://github.com/freetype/freetype/blob/cecf93ef90c660a8b0b45e5adbbfb5ea443fb6b9/src/base/ftutil.c#L146)).
- **2.13.3:** it calls `memory->alloc` directly, with no zeroing. The branch follows this today.

**The decision:** take 2.4.12's behaviour for this function, and cite 2.4.12 as the basis for all eight rows.
- `libSceFreeTypeOt` also exports `FT_QAlloc`, `FT_Realloc` and `FT_QRealloc`, which only 2.4-era builds have (`FT_CONFIG_OPTION_OLD_INTERNALS`).
- santhoshkumar-dev's #12373 `FT_QRealloc` zero-fills from 0 as well.
- Zero-filling is also valid under 2.13.3, since a caller can't rely on the new block's contents.
- The source rule is met: 2.4.12's `ftutil.c` names this function's own behaviour.

## Do

1. **The commit:** one new commit on top of e70e5ecd0a (don't amend or rebase the branch), pushed to the same fork branch:
   `fix(libSceFreeTypeOt): zero-fill ft_mem_qrealloc from a count of 0, as FreeType 2.4.12 does`.
   - **Code:** when `cur_count == 0`, `ft_mem_qrealloc` takes the same path as `ft_mem_alloc(memory, new_count * item_size, &error)`, so the new block is zero-filled. Keep every other path unchanged, including the error codes and the size checks.
2. **The test:** in `GuestFreeTypeOtMemory.cpp`, the test's guest allocator must return blocks filled with a nonzero pattern (e.g. 0xCD), so the check discriminates.
   - Assert that `ft_mem_qrealloc(memory, item, 0, n, nullptr, &error)` returns a block whose `n * item` bytes are all zero.
   - Keep the existing qrealloc cases. A grow from a nonzero count must still leave the grown tail untouched, since `qrealloc` doesn't zero it in either version; check that against the pattern too.
