## Why

On Resident Evil Village's menu, two storage images over the same guest memory round-trip through host memory on every refresh. The `[storage]` line (`Graphics/src/Texture.cpp` ~177) shows:
- **"storage refresh" write-backs:** ~4.7 GB per 10 s;
- **"flushed" CPU re-uploads:** ~4.8 GB per 10 s, which `Texture.cpp:97` defines as "another image's results were stored over the surface by this refresh";
- **the device alias path:** 0 bytes.

BF-290 (another worker) is reading the code toward a device-side handoff. **This task is the test side,** so the fix has its red/green the moment it exists. Don't write the fix itself.

Your BF-293 read (stage B, `StorageTexture::refresh`, `FlushPending`, the recorder) is the right background.

1. **The case.** A Recorder-fixture test (lavapipe/llvmpipe, `tests/Recorder.cpp` style, or a new `tests/execution/` file) that reproduces the pattern:
   - **(a)** Two storage images X and Y over the same guest memory, with different descriptors.
   - **(b)** A GPU dispatch writes through Y, leaving Y's results pending.

   The content checks **must pass on main.** This commit must not fail its own tests: **no** assertion on the byte counts yet.
