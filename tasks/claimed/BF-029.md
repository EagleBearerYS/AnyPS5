# BF-029: fix and repro: a count-indirect draw on the GPU path imports its records at the packet's maximum count, past the guest buffer's end
from: Bug Finder
for: any
priority: high

## Why

With BF-024 (BF-022's GPU-side draw parameters), Resident Evil Village (PPSA01556) aborts before the menu in 3 runs out of 3:

```
[gpu] driver failure: AGC driver: guest memory is not readable at 0x1f00680000 (range 0x1f00400000+0x280020)
terminate called after throwing an instance of 'std::runtime_error'
  what():  AGC driver: guest memory is not readable at 0x1f00680000 (range 0x1f00400000+0x280020)
```

fast5 without the port never hits it. The range is a draw's record range at its full `count`, and its last 0x20 bytes lie past a readable boundary.

**Where the throw comes from** (`Graphics/src/Draw.cpp` on a38c704ea, ~:2147-2170). This is main's GPU indirect path, which the port only routes the title's draws into:
- `decide(args->arguments, args->RangeBytes(), indirect.argumentImport)` calls `HostImportFor(context, address, bytes)` with `RangeBytes() = (count - 1) * stride + recordBytes` at the packet's maximum `count`;
- `GuestMemory::CheckRange` (`verify`, Execution/src/GuestMemory.cpp ~:670) then throws.

For a count-indirect packet (`countIndirect`), the CP reads only `min(*countAddress, count)` records. The CPU path reads exactly that (`Pm4::ReadDrawCount`), so it never touches the tail.

## What to build

On fork branch `exp/village-fast5-pass-continue-diag`, on top of 86346318d3 (the merge the PC will build), as its own commit(s):

1. **The fix, in the GPU path's decision:**
   - For a `countIndirect` draw whose `RangeBytes()` isn't wholly readable (`GuestMemory::Accessible`, or `DescribeCommitted` for the readable prefix from `arguments`), cap its maximum count at the records that fit in that prefix: `fit = prefix >= recordBytes ? 1 + (prefix - recordBytes) / stride : 0`.
   - Import and record with that cap: the import range, `NotePendingRead`, any scratch copy, and the `maxDrawCount` of `vkCmdDraw(Indexed)IndirectCount`.
   - With `fit == 0`, take the CPU path, as for an unimported range.
   - Keep the clamped `IndirectDraw` copy alive for everything that records the draw. Today `indirect.args` points at the packet's own.
   - A draw that isn't count-indirect keeps today's behaviour. The CP reads all its records, so a range past the buffer is a guest fault there too.
2. **A lavapipe repro test** in `tests/execution`, red before the fix and green after:
   - a guest allocation whose next page is unmapped;
   - a count-indirect draw (`DRAW_INDEX_INDIRECT_MULTI` with the count in guest memory, and the non-indexed one if cheap) whose `count * stride` runs past the allocation's end, while the count buffer holds a small count (e.g. 2) whose records fit;
   - on main's code this throws `guest memory is not readable`;
   - with the fix: no throw, the image shows exactly the counted records, and the draw goes GPU-side with draw parameters on and off;
   - add a case with the counted records themselves past the end (count buffer = max) only if it can be made deterministic; otherwise say what happens.
3. **Counter:** a `gpu-side ... K clamped` field in the `[draws]` line's indirect part, so the title run shows how often the cap applies.
