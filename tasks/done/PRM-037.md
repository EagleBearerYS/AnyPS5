# PRM-037: trophies: unlock through "count" statistics and property-filtered rules
from: AnyPS5 PR Manager

priority: normal

## Why

Fork branch `feat/np-trophy-stats` (head **9b17080b06**: trophies parts 1 and 2, merged with upstream main 0906c64501) unlocks a title's trophies through its statistics. It reads the title's `/app0/sce_sys/uds/udsNN.ucp` (`stats_definition.json`, `stats_extraction.json`) and `/app0/sce_sys/trophy2/trophyNN.ucp`, with the code in `core/libs/prx/libSceNpTrophy2/src/TrophyPackage.cpp` (`readStat`, `readRule`, `ParseStatRules`) and the UDS event path in libSceNpUniversalDataSystem. Today it supports only:
- stats with `"aggregation": "latest"` and `"dataType"` `uint32` or `uint64`;
- rules whose `condition` is `eventName` alone, with an `action` that has an `input` of the form `"$.name"` and an `output.statId`.

On this PC, Planet of Lana (PPSA19450) parses its trophy package (25 trophies, 1 group), but part 2 reads **0 stats and 0 rules** from its UDS file. A local read of the file's structure (only the shapes below leave the PC, no values or names):
- 24 of its 25 trophies (all but the platinum) have an `unlockCondition` on one of 24 stats, each defined as `{"statId": N, "dataType": "uint64", "aggregation": "count", "minValue": 0, "maxValue": 1, "initialValue": 0, "routes": [{"postEventInterface": ..., "eventToStatsLocation": ...}], ...}`.
- Each of those 24 stats has one extraction rule: `{"condition": {"eventName": "<event>", "property": {"path": "$.<name>", "comparator": "==", "value": "<string>"}}, "action": {"output": {"statId": N, "statName": ..., "sourceId": ...}}}`, with no `input`. Across the file there are 7 distinct event names. Every property condition uses `"=="`, a top-level `"$.name"` path and a string value.
- Its other stats ("collection"/"enumSet", "eachLatest"/"enumStatusSet", and "latest" on enum types) feed activities, not trophies; leave them as they are (skipped with their reasons).

## What to build

On top of 9b17080b06, as new commits on a new fork branch `feat/np-trophy-stats-count` (each commit with its own tests, never a test before its fix):
1. **`"aggregation": "count"`** for `uint32`/`uint64` stats: each event that matches the stat's rule adds 1, clamped to `maxValue` and kept at or above `minValue`; the stat starts at `initialValue` when present (which must lie within `minValue`..`maxValue`, else the stat is skipped with a reason, like part 2's other checks). Counts persist like part 2's latest values.
2. **Property conditions:** a rule's `condition` may carry one `property` object with `path` `"$.name"` (a top-level event property), `comparator` `"=="` and a string `value`. The rule matches only when the posted event has that property and it is a JSON string equal to `value`. Any other comparator, path form or value type: skip the rule with a reason, as part 2 does.
3. **Rules without `input`:** allowed for `count` stats (the action only counts). A rule without `input` for a `latest` stat stays skipped.
4. Trophy unlocks through these stats use part 2's existing `unlockCondition` handling. A count reaching its target unlocks the trophy once, and the unlock is recorded and reported through Trophy2 as part 1 does.

**Tests**, all with synthetic files built in the test the way `tests/TrophyPackage.cpp` and `tests/TrophyStore.cpp` build theirs (no title data): a count stat with a property-filtered rule unlocks its trophy on the first matching event and not on an event with another property value or without the property; counting stops at `maxValue`; `initialValue` outside the range skips the stat; a `"!="` comparator, a nested path and a numeric value each skip the rule with a reason; a count rule without `input` works and a latest rule without `input` is still skipped; the platinum stays computed as before.

Also update USAGE's trophy section and the debt entry for what's supported, in the same commits as the code.
