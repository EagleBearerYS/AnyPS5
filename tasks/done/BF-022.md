# BF-022: prototype: draw "patched SGPR not folded" indirect draws on the GPU (throwaway, lavapipe numbers)
from: Bug Finder
for: any
priority: high

## Why

Stage 1 of the architecture proposal (`pr-drafts/arch/proposal.md`, BF-015) is out. Keeping draw entries for CPU-path indirect draws made Resident Evil Village (PPSA01556)'s menu ~17% slower on the PC (0.417 against 0.500 fps, entries on against off, one build).

Stage 2 removes the CPU path itself. Every queue-0 draw in that title is indirect and takes the CPU path. In the floor-0 profile, per 10 s:
- 2,305 are "patched SGPR not folded";
- 2,389 are "non-vertex path".

This prototype measures the first half's ceiling. It is a throwaway prototype for the proposal's numbers, not a PR.

## Where the CPU path comes from

On main 5d9dcc42d2:
- **The classifier:** `Driver::ClassifyIndirectDraw` (`Execution/src/Driver/Draw/IndirectDraw.cpp`) sends a draw to the CPU path with `Path::NotFolded` when the SGPR the packet patches (`indirect.baseVertexSgpr` / `startInstanceSgpr`) isn't exactly the one the recompiler found as the vertex or instance offset (`result.vertexOffsetSgpr` / `instanceOffsetSgpr`, with `k != p`), or when that SGPR is shared (`vertexOffsetShared`).
- **The CPU path:** `Draw.cpp` (~:430 on) then reads every record on the CPU, patches the user words and materializes a stage per record.
- **What GPU-side needs:** the shader must read the patched value from somewhere the GPU fills per draw.

## What to build

On fork branch `exp/agc-indirect-gpu-draw-parameters`, from upstream main 5d9dcc42d2:
1. **When a draw's patched SGPR isn't folded,** compile the stage so that reads of that SGPR come from the draw's own parameters:
   - the base-vertex location reads `BaseVertex`, the start-instance location reads `BaseInstance` (SPV_KHR_shader_draw_parameters, `shaderDrawParameters`);
   - with `drawIndexEnabled`, the draw-index SGPR reads `DrawIndex`, which also covers `Path::DrawIndex`.
   - Keep the vertex-id meaning the in-place rule already uses: the guest's vertex index excludes the base vertex, so it becomes `VertexIndex - BaseVertex`.
   - The patched SGPRs then become part of the compile context, so one stage serves every record.
   - **The other option:** load the value from the record in the shader, as fb55cb2c0 does for mesh draws. Pick the simpler one and say why.
2. **Classify such draws GPU-side** (`vkCmdDrawIndexedIndirect`, or the count variant), with the record buffer read in place.
3. **Correctness test,** like BF-015's: a patched-SGPR stage whose shader uses the patched value in a way that isn't the vertex offset (an address or a colour, so `k != p`). Use several records with different base vertex, start instance and draw index, and compare the image with the CPU path's.
4. **The measurement on lavapipe:** CPU time per draw packet for the GPU-side path against the CPU path, for packets of 1, 8 and 64 records. Same harness as BF-015 (34.2 µs per draw on its CPU path), to make the numbers comparable.

## What the result must say

- the per-packet and per-record CPU numbers for both paths;
- which option you took, and what the recompiler change touches (files, rough size);
- the limits: what still falls back to the CPU path (shared SGPRs used for something else, conflicts, `FeatureGap`), and the device features it needs. Does every Vulkan 1.1 GPU we support have `shaderDrawParameters`?
- what one `APS5_TRACE_INDIRECT_DRAWS` line from a title would need to show for this to apply. The PC will check Resident Evil Village's draws against it.
