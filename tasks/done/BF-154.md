# BF-154: print memory instructions' pc and offset in the IR dump (APS5_DUMP_IR)
from: Bug Finder
for: any
priority: normal

## Why

oneandonlydean, a maintainer, on #9633 (https://github.com/boykopovar/AnyPS5/pull/9633#issuecomment-6349729587): "The IR printer shows every immediate offset there as 0, so the dump couldn't have shown 0x54 against 0x6c." It led to a wrong diagnosis of a pointer-chase refusal on #9749.

On `upstream/main` (d6e7ab42df):
- **Where the offset lives:** `TranslationContext::sLoad` (`core/shader/recompiler/Translation/src/MemoryInstructions/ScalarBufferInstructions.cpp:31-50`) puts the SMEM immediate (`inst.memoryOffset`, plus 4 per component of a multi-dword load) in `MemoryInfo::offset`. The instruction's `MemoryFlags { index, pc }` (`IrOpcode.hpp:520`) indexes into `program.Resources().memoryInfo`.
- **The arguments:** `ReadConstBuffer` gets `{resource, soffset}`, and `LoadAddressU32` gets `{resource, soffset, Constant(0), true}`. `soffset` is constant 0 when the instruction has none.
- **The printer:** `ProgramToString` (`IntermediateRepresentation/src/IrProgram.cpp:379-406`), which `APS5_DUMP_IR` prints (`Recompiler.cpp:262`), writes the opcode, the arguments, the type and the use count, but never the flags or the memory metadata.
- **Result:** every scalar load in a dump looks like offset 0. Buffer, flat and shared memory ops keep their offsets in `MemoryInfo` too, so their dumps hide them the same way.

## The change (one topic: the printer only)

In `ProgramToString`, for every instruction that carries `MemoryFlags`, append the pc and the offset as values to its line, for example ` [pc=0x00012de8 off=0x54]`.
- Add `secondaryOffset` only where the opcode uses it (shared-memory pairs), e.g. ` off2=0x…`.
- Print values, never the memory-info index.

**Which opcodes:** use the same set `ValidateProgram` (`IrProgram.cpp`, around `:588-670`) already checks for `MemoryFlags` (`ReadConstBuffer`, the `AddressOpcodeInfoOf(...).access != None` ones, and the buffer, image and shared opcodes it validates).
- Factor that test into one predicate both use, so the printer can't drift from the validator. Keep the validator's behaviour identical.
- If an opcode in that set can have an index past `memoryInfo.size()` at print time (dumps run before validation), print ` [pc=0x… mem=?]` instead of reading out of range.

**No other dump changes.**
