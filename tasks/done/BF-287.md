# BF-287: a draw-key census for one Resident Evil Village boot: how often its draw keys repeat across frames, and what stops reuse (a diag branch, timing and counts only)

from: Bug Finder
for: any
priority: high

## Why

QRMOE diagnosed RESIDENT EVIL requiem (PPSA31246), which runs on the same engine as Resident Evil Village (PPSA01556), in D#11599 (https://github.com/boykopovar/AnyPS5/discussions/11599#discussioncomment-19275021). Their draws never reuse anything across frames:
- **Builds:** 971,000 `ShaderResources` builds in one run. The draw cache and the draw recipes get 0 hits in the first level.
- **Keys:**
  - the **full draw key** matches the previous frame's for 0 % of draws;
  - the **shape key** (registers without the user words) for 95-99 %;
  - the **shader set** for 99.7 %.

  So only the user-data pointer words change: the moved buffer bases, and the content read through them.
- **Where the draws go:**
  - about 44 % are CPU-path indirect, which `cacheDrawStages` never caches;
  - about 38 % are refused by `admitDrawKey`;
  - 17 % are admitted, and about 1 % hit.
- **`DrawRelocate.cpp`:** relocation is learned for only 22 shader sets and is never productive, because the alias key hashes the content read through the moved words.
- **The resource cache** stays at its 1,024-entry floor, because its keys never repeat.
- QRMOE used temporary instrumentation that isn't published.

**Why it matters:** Village's static menu runs at about 0.7 fps, CPU-bound, and its cost is per-draw resource work under the GPU mutex (BF-282). If Village's keys behave like requiem's, a draw key that carries the user words as refreshed inputs, not as part of the key, is our next speed PR. No open PR does that. Before building it, we need Village's own numbers from one boot. The PM OK'd this in the user's name.

   - Branch: fork `diag/village-draw-key-census-on-103015a9ca`.
   - **Keep every change out of `core/shader/recompiler/`** so the Village shader cache key stays the same, and say so.
2. **Read the code on 103015a9ca first:**
   - the draw path from `Driver::draw` to the draw cache: the draw key, `admitDrawKey`, `cacheDrawStages`, draw recipes, `DrawRelocate.cpp`'s learning and alias key;
   - the resource cache and its key;
   - the CPU-path indirect draw path;
   - where a presented frame ends: the flip or VideoOut submit that `Driver.Present` or the trace summary uses.

   Say in the result what each key covers, with file:line.
3. **Counters, behind `APS5_DRAW_KEY_CENSUS=1` (off by default, no cost when off).** Print one line per presented frame, or per 10 s if per-frame is too noisy, prefixed `[draw-key]`, to the same log the `[...]` profile lines use. Counts and slot indices only, never memory contents or addresses:
   - **draws:**
     - total;
     - CPU-path indirect, inline and queued;
     - reaching the draw-cache lookup;
   - **`admitDrawKey`:** admitted, and refused by reason;
   - **hits:**
     - draw cache;
     - draw recipes;
     - relocation applied and productive, with the number of learned shader sets;
     - resource cache hits, misses and size;
   - **key repeat against the previous frame:** keep per-frame hash sets of three keys and count this frame's draws whose key was in the previous frame's set:
     - (i) the full draw key;
     - (ii) the shape key, i.e. the same registers with the user-data words left out;
     - (iii) the shader set;
   - **draws whose shape key repeated but whose full key didn't:**
     - a histogram of which user-data slot indices differ from the previous frame's draw with the same shape key, as a top-8 of slot index → count;
     - how many of the differing words look like GPU addresses: inside a mapped guest range, per the existing range lookup;
   - **for draws that miss with a repeated shape key:** whether the *content* behind the changed pointer words also changed, where the existing code already hashes it (the relocation alias key). Give the count, not the content.
4. **Overhead:** the census may cost something when on, but say how much on the Village harness (`agc_driver_village_draw_cost`, as BF-265 ran it: per-draw lookup and wall, on against off, 4,096 entries, median of 3). It must cost nothing measurable when off.
5. **A unit test is optional.** This is a diag branch, not a PR. But add a small check that the counters are consistent (repeat ≤ total, the shape-key repeat ≥ the full-key repeat), if one of the existing draw-cache tests can run with the switch on.
