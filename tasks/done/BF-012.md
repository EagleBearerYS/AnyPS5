# BF-012: prove an unchanged resident colour target in O(1), not by walking its pages on every draw
from: Bug Finder
for: any
priority: high

No PR from you. The result is a fork branch. A PC session opens it upstream with a Village pair, after PM-038 v3's pair.

## Why

The user, 2026-10-15 00:03 PT: our fixes must be comprehensive, so that no newer PR can post a better version.

Village's static title, profiled on the PC (ranking only):
- queue 0 runs 2,524 draw packets per 10 s at 3.54 ms each;
- the `readTarget` draw phase costs 515 ms of that per 10 s (5.8%);
- in that time, 5,340 resident colour-target lookups walk about 5.5 M pages, about 1,030 pages (4 MiB) each;
- the CPU never writes those targets. Re-proving them is the whole cost.

The path on upstream main (34454bd835 at writing), `core/libs/prx/libSceAgcDriver/Graphics/src/Draw.cpp`:
- `refreshResidentTarget` (about line 1228) runs once per colour attachment per draw;
- it is called from the draw path (about line 1999) and the recipe path (about line 2592);
- its comment names the proof: `StorageTexture::Refresh` does FlushPending, then CollectWrites over the target's pages, then the DCC key scan of `TextureClearKeys`, then UnchangedSince;
- "pages walked" in the `[draws]` line is `GuestMemory::ThreadCollectedBytes()` / 4096 over that call.

So it is not a search through a list. The proof is O(target pages) on every draw, even when nothing changed.

## Task

1. **Measure first, on current upstream main.** Use a microbench or a test-mode bench, dropped before the PR, like PM-032's.
   - The setup: a resident colour target of about 4 MiB (and 8 MiB) in write-watched guest memory, drawn N times with no CPU write.
   - Report the time per lookup and the pages walked, split into FlushPending, CollectWrites, the DCC key scan and UnchangedSince.
   - Find out why repeated proofs re-walk the pages. In particular, whether the queue worker's collect memo (`CollectEpoch()`, which #6082's description mentions) covers this path, and if not, why not.
2. **Make the unchanged proof O(1), or O(changed pages),** on the dominant step or steps. The design is yours. Some options:
   - a per-target memo of the last proof, keyed by a write generation that every way of writing that range bumps;
   - a summary over the tracker's stamps (for example the newest stamp per 2 MiB block) so that CollectWrites and UnchangedSince skip unchanged blocks;
   - extending the collect memo to this path, if it is safe there.

   Reuse an existing mechanism where one fits: PM-032's O(1) unchanged-column proof (results/cloud-3/PM-032.md), #6060's stamps, the collect memo. Don't build a parallel one.
3. **A changed target must still be re-proved,** with a red/green test for each case:
   - a CPU write into the target's memory: watched, and unwatched or partly watched;
   - a DMA_DATA fill or copy into it;
   - a compute dispatch writing it through a buffer;
   - a DCC key change, that is a fast-clear code written over its keys;
   - a GPU write-back of its pending results (FlushPending);
   - another mapping (alias) of the same memory written;
   - eviction and re-import of the target's allocation;
   - a second target that overlaps it, and one that is only adjacent;
   - a 2D-array or 3D target, so every slice is covered;
   - an MRT draw (`state.colors`);
   - the recipe path.
   Each test fails without the change it pins, where that applies (the proof skipped wrongly), and passes with it.
4. **Siblings:**
   - check depth and stencil targets' residency proofs (DepthSurface) for the same O(pages) re-proof;
   - check the storage-image and sampled-texture residency proofs that call the same `Refresh`;
   - fix the ones that are contained, and list the rest with numbers.
5. **Cost:**
   - at Village's scale (5,340 lookups per 10 s over about 1,030 pages each), the unchanged proof must be at least 10x cheaper;
   - give the worst case, every proof finding a change, and show it is no slower than main within noise;
   - give the memory the memo or summary uses.

## Addendum (Project Manager, 2026-10-15 ~05:10 PT): the write tracker's stamp hole

- **If your unchanged proof relies on write-watch stamps or epochs** (as PM-032 and #6060 do), it inherits the hole PM-037 found on main:
  - `MarkWritten` and `storeOwn` stamp nothing for a store over a **partly watched** range (GuestMemory.cpp, PM-037 §1 gap 1);
  - such a store into a resident target would leave it "unchanged", and the draw would use stale bytes.
- **The fix exists, held for a title:** PM-040's standalone branch `fix/agc-stamp-partly-watched-stores` on the fork (89343ba7f3, the fix, and b7c33252c6, its test, rebased onto post-#6060 main).
  - If BF-012's proof depends on stamps, take those two commits first, unchanged, and add a red/green case for "a CPU store across a watched target's edge and unwatched memory is seen".
  - The PR then carries the stamp-hole fix as a needed part, which gives PM-040 its title.
  - If PM-040's branch isn't on the fork when you start, cherry-pick the two commits from `followup/pm028-partly-watched-stamps`.
- **If the proof doesn't use stamps,** say why the hole can't reach it.
