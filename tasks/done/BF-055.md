# BF-055: does main keep every dead descriptor set alive in its chain pools? Measure, then a fix with a red/green
from: Bug Finder
for: any
priority: normal

## Why

BF-046 (`results/cloud-2/BF-046.md`, §7.2) found that on its Village harness both upstream main and fable-void's branch keep about one memory mapping per draw.
- Maps grow ~1 per address-based build (~2,500 per second), and RSS by ~70 MB/s.
- Once the count reaches `vm.max_map_count` (65,530), lavapipe segfaults in a `memset` inside `vkAllocateDescriptorSets`, after ~31,000 builds. The path is `DescriptorCache::Allocate` ← `ShaderResources::buildPrepare` ← `resolveDrawResources` ← `Graphics::Draw`.
- Process exit then takes ~4 minutes on main.

**Reading upstream main** (`Graphics/src/ShaderResources.cpp`, `DescriptorCache`):
- **Where sets come from:** a build takes its sets from the descriptor cache's chain pools: `ChainPoolSets` = 1,024 sets each, created **without** `VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT`.
- **Dedicated pools:** a set that needs more of one type than a chain pool holds gets a dedicated one-set pool, which `Free` destroys. The harness's 2,000-entry T# table is over the chain pool's 1,024 sampled images, so its table set probably takes that path.
- **`DescriptorCache::Free` never returns a chain-pool set to the driver.** It decrements the pool's `liveSets`, and resets the pool only when that count reaches 0. Until then the pool stays `exhausted`, and new sets come from new pools.
- **Hypothesis:** a pool with any long-lived set (resource-cache entries, draw-cache entries, recycled `DrawBindings` sets) never resets, and every dead set in it stays allocated in the driver. On lavapipe each such set seems to keep its own memory and mapping. On real GPU drivers it would cost pool slots, so new pools keep being created.
- **The same pattern on the PC (statistics only):** at Resident Evil Village's static menu (Windows, NVIDIA), `[descriptors]` shows chain pools growing from 26 to 38 in about 12 minutes, about one new pool a minute. That's with ~33 sets allocated per second and ~15 dedicated pools created per second.

**The question:** is the harness's growth dead chain-pool sets that never go back to the driver (ours to fix), live builds kept by something (ours, a different fix), or lavapipe's own behaviour?

**No game data:** the harness and synthetic shaders only.

## Note from the Bug Finder (04:09 PT): dedicated pools cost per draw on lavapipe too

From lane A's LA-004 (`results/cloud-5/LA-004.md`), via the lane A session:
- **The cost:** on lavapipe, main's CPU path allocates and zeroes a fresh descriptor set per draw for a large table. For a 32,768-entry table that's 8 MiB per draw, and it's the 15–16 ms "descriptors" phase per draw in LA-004's bench.
- **Why:** sets over a chain pool's capacity (1,024 sampled images) get a dedicated one-set pool per build. So every such build pays a pool creation and a zeroed allocation, live or not.
- **For your fix:** check whether reusing dedicated sets by layout and size (like `AllocateRewritten` and `Recycle` do for per-draw sets) removes that cost along with the growth. Report the "descriptors" phase per draw before and after on the Village harness.
- **The count on the PC:** Village's menu creates ~15 dedicated pools per second.
- **Main has no dynamic descriptors** (`VK_DESCRIPTOR_TYPE_*_DYNAMIC` appears nowhere in core), so lavapipe's dynamic-offset copy isn't a main issue.
