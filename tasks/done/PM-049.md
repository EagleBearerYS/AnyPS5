## Context

- On our Resident Evil Village (PPSA01556) fast tree, with every import settled (`APS5_SETTLE_FLOOR_KIB=0`), the static menu runs at 0.5 fps with private memory flat at ~18.2 GB.
- In the first scene, private memory grows ~200 MB a minute (23.9 → 24.9 GB in 5 min), so a session ends at the PC's commit watchdog after ~15–20 min.
- There the host import budget is pinned at its 6400 MiB setting, with 7.1 M address-based build refusals; at the menu there were none.
- **The leading suspicion** (from GAC-041's result §2, `results/cloud-3/GAC-041.md`): each refused import is served by a host-visible stand-in copy (`copyBufferProperties(false)`, kept in the buffer pool's retention tiers) or a heap mirror (`APS5_HEAP_MIRROR_MIB`, 24 GiB by default). If those are retained per build, per range or per epoch and not reclaimed, memory grows with the refusal count.
- The Bug Finder is reading the profiled scene from this PC and may add an addendum with its numbers. Read `tasks/claimed/PM-049.md` again before you finish, in case it has.

## Addendum from the Bug Finder (2026-10-16 ~02:10 UTC): bf-floor0's profiled scene

From this PC: Resident Evil Village (PPSA01556) on the fast tree with every import settled, `APS5_HOST_IMPORT_MIB=6400`, `APS5_PROFILE_DRAW=1`. Times are seconds since launch. The scene loads from ~1,360 s, and control is ~2,600-3,200 s.

**Bounded, so not the growth:**
- **Heap mirrors.** `[buffers] image mirrors` grew during the scene load, from 5,702 ranges (384 MiB) to 8,349 ranges (621 MiB, all writable heap mirrors), then stayed at 8,349 / 620.8 MiB through control.
  - Their refreshes keep climbing: ~3.9 M in total, ~0.3 M per 10 s, all through the write watch, with almost no block compares.
- **The texture cache.** `[texture-cache]` grew from 904 to 1,887 MiB in 4,399 entries, against a budget of 2,048 MiB. Mostly device-local.
- **The buffer pool.** `[bufferpool]` stayed flat: small ~63 MiB, large ~490-503 MiB, device 955 of 1,002 MiB.

**What grows:**
- **Private bytes:** 18.3 GB at the menu, 22.4 GB at ~1,990 s, 25.2 GB at ~3,180 s, so about +140 MB/min through the scene.
  - GPU dedicated went from 3.8 to 6.3 GB. GPU shared stayed ~7.2 GB: the 6.4 GB of imports plus the mirrors.
  - Commit free fell to 3.1 GB, and system free RAM is 0.2-0.6 GB.
- **The working set is ~1.1 GB of the 25 GB private,** so most guest memory is paged out. `[guestmem] write-changed` runs at ~5 calls, ~61 MiB and ~4.5 s per 10 s, about 13 MB/s.
- **Refusals keep counting:** `6568465 imports (448219 MiB) refused so far, 6554440 of them remembered, last 0x2409800000+0x10000 by map`. Imports made at map time are refused too, not only address-based builds.

**What the profile can't say:** where ~2 GB or more of the private growth goes. None of the profile's MiB figures grows by that much.
- One candidate isn't a leak at all: the guest committing more of its own memory as the scene touches it. So first separate the guest arena's committed bytes from host allocations, in the repro and in a counter we could run here.
- Then split the host side by category:
  - host-visible Vulkan memory for stand-in copies, staging and mirrors;
  - descriptor pools: `[descriptors]` reports ~20,600 dedicated pools, up from ~20,100 at the menu;
  - snapshot copies;
  - the import table's remembered refusals (`state.refusals`): one entry per distinct refused (base, size), each holding a `Mapped` vector of range references. The 6.5 M above are refusal events, mostly repeat hits on existing entries, so the map is much smaller, but its size isn't printed. Please measure it.

### Addendum 2: system memory held for the GPU (Bug Finder, 2026-10-16 ~02:30 UTC)

Also measure the system memory held for the GPU, separately from the guest's own pages. On this PC it's the bigger problem:
- GPU shared memory is 7.0 GB from ~3 min after launch, and 7.25 GB in the scene. The game's working set is 1–2 GB.
- Imports are pinned. Heap mirrors and stand-in copies are host-visible system memory too (`Buffer`'s default `HOST_VISIBLE | HOST_COHERENT`, `copyBufferProperties(false)`). So a lower import budget moves bytes from pinned guest pages to duplicated copies.

In the repro, report per build series:
- bytes in live imports (host-pointer and dma-buf, separately);
- bytes in heap mirrors and stand-in copies, by memory type (device-local or host-visible);
- how many of the live imports a build actually reads, against how many it imports or refreshes because they're in the lease.

If you can, run a second series with half the import budget. Does the total held for the GPU (imports plus host-visible copies) fall, or only move?
