# BF-155: fix BF-150's case 5 ("explicitly unwatched DCC keys"), which fails its own precondition on a real Windows GPU
from: Bug Finder
for: any
priority: high

## Why

BF-150's Windows test `agc_import_settle_initial_dcc` ran on the RTX 3070 (NVIDIA 617.42) at 12:4x PT on 2026-10-22, on `fix/agc-sync-settle-initial-dcc-main` 580a37ce8e.

**What held:**
- **Red:** with `core/libs/prx/libSceAgcDriver/Graphics` at 973af43dc6, case 1 is refused 3/3: `(m) an initial multisampled DCC import over a pending settle was refused: AGC graphics: initial multisampled DCC contents require watched guest memory`, with `0 settle reads submitted, 0 back in the write watch`.
- **Green, cases 1-4:** each behaves as designed, 5/5:
  ```
  (m) initial DCC over a pending settle (import 327680 bytes): accepted; 1 settle reads submitted, 1 back in the write watch
  (m) initial DCC over an import of whole and partial 64 KiB blocks (import 802816 bytes): accepted; 1 settle reads submitted, 1 back in the write watch
  (m) initial DCC over a compared import in its last 64 KiB block (import 802816 bytes): AGC graphics: initial multisampled DCC contents require watched guest memory; 1 settle reads submitted, 0 back in the write watch
  (m) initial DCC over deferred settles off (import 327680 bytes): AGC graphics: initial multisampled DCC contents require watched guest memory; 0 settle reads submitted, 0 back in the write watch
  ```
- **#8527's ten `agc_import_settle*` / `agc_import_watch*` tests:** all pass.

**What failed:** case 5 fails 5/5 before it reaches the DCC import:
```
AGC graphics: (m) the target's import of 327680 bytes was not compared at first
```
That's the precondition at `core/libs/prx/libSceAgcDriver/tests/Recorder.cpp:2491` on 580a37ce8e: `import != nullptr && import->base == address && import->bytes == importBytes && import->unwatched && !Watched(address, importBytes)`.

**Likely cause (unverified, so check it):**
- Case 5 allocates `block = AllocateWatched(reserved, unit)` (`reserved` = 0x50000), then `keys = AllocateWatched(unit, unit)` (`:2433-2434`).
- Both are 64 KiB-aligned watched regions made back to back, so `keys` likely lands at `block + 0x50000`.
- Both are registered (`mutation.Add`, `:2479-2481`).
- If `HostImportFor(context, address, importBytes)` builds its import over the contiguous registered run, the import covers `block` and `keys`: `bytes` ≠ `importBytes`, and possibly not `unwatched`, because `keys` was `Unwatch`ed at `:2484` before the import.
- Cases 1-4 allocate no second region there, so they don't hit it.

## The change (test only)

1. **Make case 5's allocations unable to merge into one import.** For example:
   - reserve one region for the color block, a 64 KiB gap and the keys, and register only the block and the keys, leaving the gap unregistered;
   - or allocate the keys first, then a guard reservation, then the block.

   Use whatever `AllocateWatched`/`ReleaseWatched` allow without leaking. Keep case 5's meaning: the color import is a sub-1 MiB compared import with a pending settle, and the DCC keys sit in separate, non-imported memory that is explicitly `Unwatch`ed. The DCC import must still be refused, and the refusal must come from the keys.
2. **Make the precondition self-explaining.** On failure it prints `import` base, bytes, `unwatched` and `Watched(address, importBytes)`, and does the same for the case-3 neighbour precondition at `:2488`. That way the next Windows run shows what was wrong if the guess above is not it.
3. **Check cases 1-4** for the same hazard, for example `dest` from `VirtualAlloc` landing next to `block`. `dest` isn't write-watched, but it is registered (`:2480`). Say whether `HostImportFor` could merge it into the target's import, and fix it the same way if so.
