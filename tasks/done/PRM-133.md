## Background

Read `results/cloud-3/PRM-132.md` on `cloud-results` first. Branch `prm/9969-intel-diag`, head `400b86ce93` (`bfa86d196c` the trace, `400b86ce93` full subgroups).

On Intel UHD (Gfx12, Windows), mrfelek's last 6 runs of `--pointer-vsharp-child-key-arm` on `99dabd0848` all **faulted**:
- 4 runs: `image table: ... pc 0xfc selected the descriptor at D: poison entry N`;
- 2 runs: `selected the descriptor at 0xffffb8a2` (`outside the snapshot` in one, `outside the key domain` in the other).

None was the wrong-texel form, the only form PRM-132 exercised (its forced failure was a texel mismatch).

**The gap.** PRM-132's own run 4, the armed variant, faults by design ("outside the snapshot"), and its trace came back empty: `run 4: map 0 words, 0 rows written`. The fault is logged by `BdaResources::checkFault` (it throws `image table: ...`, which ends up in the dispatch log), and `Execute` returns normally. But nothing the shader stored reached `TraceOutput`, not even the rows of groups 1-3 or group 0's map copy. So, as built, a faulted Intel run would print an empty trace in exactly the forms we need.

## What to do

1. **Find why a faulted dispatch's stores never reach guest memory.** For example: the output is copied back from a mirror only on success, or stores are gated on a fault state. Name the code path (file and line) in the result.
2. **Make the trace survive a fault, in trace mode only.** Choose whichever is smaller and leaves the normal path untouched, for example:
   - keep or copy back the output buffer's contents when the dispatch faults, only while `APS5_DIAG_TABLE_TRACE` is set;
   - or send the trace to a buffer that is read back regardless of faults.
   With the variable unset, the emitted SPIR-V and the driver's behaviour must stay as they are on `400b86ce93`. Show the SPIR-V part with `cmp`, as in PRM-132.
3. **Lavapipe proof, using run 4 as the stand-in for Intel's faults.**
   - Run 4 prints map words and rows.
   - Group 0's faulting lanes show the poison code in `code` (row word 15) and in whichever earlier word produced it.
   - Groups 1-3 show the expected lookups.
   - The decoder handles a faulted run (step 4).
   - The normal arm and sibling tests still pass 10 of 10, the trace test 3 of 3, and the 51-test set as in PRM-132.
4. **Commit the decoder to the branch**, so a Windows tester can run it from the tree. For example `tools/diag/image_table_trace_decode.py`. No comments in it, and it runs with plain `python` on Windows (no `python3`-only paths, no non-ASCII output). Extend it:
   - **Faulted runs.** Take the `image table: ... selected the descriptor at 0x<D>[: poison entry N]` line from the log when present. Report which lanes' `code` equals the reported word (`N | 0x80000000`, or the poison code behind the reason name), and for each such lane, the first step where its row departs from the lookup recomputed from the map. If no row departs, say so: then the fault comes after the lookup.
   - **A short report a tester can paste.** By default, print at most ~40 lines in total:
     - the bases line;
     - one summary line per run;
     - for the first departing or faulting lane of each run, its row with field names, plus only the map words its lookup read (root header, the selected record, child header, `mapped`, the image record and driver fault slot), each with its index.
     Add a `--full` switch for everything.
   - **Marker.** Report any lane whose marker bits 6-11 differ from bits 0-5 when the module runs at two lanes per invocation, so on a 32-wide device. It's fine to make this a separate summary line that is skipped on lavapipe's subgroup 8.
5. **Windows build.** Nothing here should need anything Linux-only. Use `_putenv_s` under `_WIN32` as the branch already does. Check that the new code compiles cleanly under the project's Windows compiler flags as far as you can tell from reading the CMake files, and list anything you're unsure of.
