## Why

I#6558: queue 0x20 `WAIT_REG_MEM` (function 3, ref 0x1) times out on a label that holds an address-like value. A tester ran our label-wait diagnostic v3 on Stray (PPSA02100):
- **The diagnostic:** fork `fix/agc-label-wait-timeout-reason-v3`, commits 5fab0c120c + 55315c802b. The tester rebased them onto main 673fa865f4.
- **What the tester's rows show** (all six, from their public comment 6512870804, are below):
  - **5 of 6 say "stores newest first: none recorded":** table miss, no open batch, no snapshot overlap, write generation seen == now.
  - **1 of 6** has a satisfying store of 1 from queue 0x0, opcode 0x49 (RELEASE_MEM), 1,406 stamps before the wait's submission, after an opcode 0x50 (DMA_DATA) store of 0. By submission the slot held 0x21036100.

**The values at submission look like pointers.** They are the low halves of addresses near each label:

| label | value | value minus label's low half |
|---|---|---|
| 0x102104de80 | 0x2104c560 | −0x1920 |
| 0x1020fad980 | 0x21036100 | +0x88780 |
| 0x102108fd80 | 0x2108fd60 | −0x20 |
| 0x10210982e0 | 0x21098300 | +0x20 |
| 0x102105f7c0 | 0x2105a780 | −0x5040 |
| 0x102108e040 | 0x21075fa0 | −0x180a0 |

That fits a freed and reused label slot (an allocator's link words). Before we reply to the tester, we need the code to say which of these is true:
- **(a) the store of 1 happened but our history lost it:** capacity, eviction or a table miss;
- **(b) a writer stored 1 that the history never records:** shader stores, CPU stores, SDMA, a library's CPU-side label write;
- **(c) the slot was reused before our queue 0x20 reached the wait,** because we process the wait later than the title expects.
