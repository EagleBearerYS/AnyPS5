## Why

Lane A reads image tables at run time through a device key table on PR 6947's heap. Read `results/cloud-*/LA-002.md` through `LA-005.md` on `cloud-results` first.

**Today a key's first use reads zeros.** A key the table doesn't hold yet reads zeros in the batch that first uses it and appends a miss. The driver resolves it after the batch, so the next batch has the texels.
- **Work redone every frame** shows at most one frame of zeros.
- **One-shot work keeps the zeros:** a draw or dispatch that samples a texture once and keeps the result, such as a LUT, a mip or IBL prefilter, or a copy done by sampling.
- **Two tests show it,** failing with `APS5_GPU_PATH=1` (LA-004 §7, LA-005 §6):
  - `agc_driver_image_sint8`: "8_SINT image table entry 0: image_sample_lz read 0x00000000, expected 0xffffff80";
  - `agc_driver_image_table`: "an entry under a linear direct S# differs from the direct binding".
- **The AnyPS5 Project Manager's decision:** this gap must be closed before any lane A pull request. The Bug Finder's: no default-on step while these fail.

**fable-void's branch closes it with a pre-pass.** On fork `fable-void/wip/new-gpu-path` (head ed8f2d7a2e), from cff47a8102 "perf(agc,shader): read compute images through the device image table" on:
- **The recompiler predicts the keys.** `ResourceMaterializer::ExpectedDeviceImages` (`Optimization/src/ResourceMaterializer.cpp` ~1317) evaluates the plan's `deviceImageUses` against the current guest memory and user data. It uses the same evaluator as the CPU path's SRT reads and follows `controlFlow` where branch conditions evaluate. The result is the keys each use will read: T#, sampler words and class, and interface id. A use that can't be pinned to one value gives candidates. If a use can't be evaluated at all, `deviceImagesComplete` is false.
- **The program carries the expectations.** They are `RecompileResult::deviceImages` and `deviceImagesComplete` (Recompiler.hpp ~570). They are filled at each materialization (Recompiler.cpp ~1143, ~1296, ~1303, ~1544, ~1728), and named by `DeviceImageTableAbi::NameInterfaces`, using `Expectation` in `DeviceImageTableAbi.hpp` ~68.
- **The driver inserts them before the batch.** The driver calls `ShaderResources::ExpectDeviceImages` (ShaderResources.cpp ~2719; from Draw.cpp ~1460 and ~1961, and VulkanDevice.cpp ~3859), which calls `DeviceImageTable::Expect` (DeviceImageTable.cpp ~89). That gathers the keys the table lacks, and `BeforeDispatch` resolves them before the work is recorded.
- **What it costs and gains.** On BF-046's harness it expected and inserted all 1,448 T#s with 0 misses, at about 44 µs per draw: the pre-pass phase in `results/cloud-2/BF-046.md`.

Lane A's port left all of this out. The join has no `Expectation`, `deviceImageUses`, `ExpectedDeviceImages` or `deviceImagesComplete`.

## What to do

1. **Port the expectations.** Bring over:
   - **the recompiler half:** the plan's `deviceImageUses` with `firstUsePc`, `levelZero` and sampler; `ExpectedDeviceImages`; the `RecompileResult` fields with their codec and cache-key mixing; `Expectation` and `NameInterfaces` in the ABI;
   - **the driver half:** `ExpectDeviceImages`, and `DeviceImageTable::Expect` with resolve-before-record.

   Use `git log -S<symbol> fable-void/wip/new-gpu-path` to find every commit that shaped them. Fit them to lane A's table, its seam (`DeviceImageHeap`) and LA-004's resolve and fallback rules. Bump `FormatVersion` if the artifact format changes.
2. **Resolve before the batch.** Before the first draw or dispatch of a batch that uses the table, insert every expected key the table lacks. Resolve it as a miss is resolved: the CPU table path's checks, a heap slot, and the bucket upload.
   - A rejected descriptor raises the CPU path's error at that point. That also fixes LA-004's open problem 6, where the fault came one batch late.
3. **A use that can't be expected must not read zeros.**
   - When a draw's or dispatch's expectations are incomplete (`deviceImagesComplete` false, or a candidate set over a limit you choose and report), route its program to the CPU table path **before** the work is recorded. Use LA-004's per-program fallback (`fallBack`, `EntryOutcome::DeviceImageFallback`), but have this draw prepare its CPU artifact too, not only from the next recompile.
   - If some path can't do that, throw rather than read zeros, and say which.
   - fable-void instead waits on the batch with unnamed misses (`missWaits` in his `BeforeDispatch`). Say whether that is ever correct for one-shot work. I think it isn't, because the batch with the misses has already run.
4. **Keep steady state near free.**
   - Skip the evaluation when nothing it read has changed. Memoize per (program, stage, user data) with the guest ranges the evaluator read, checked against their write generations: the table's 64 KiB block index, collect epochs and `OwnWriteSerial`.
   - This is BF-046 §6 change 3, "run the pre-pass only for a new user-data shape", made safe against memory changes.
   - **Budget:** at most ~20 µs per draw in steady state on LA-004's Village-shaped bench, inside lane A's ~80 µs bar. Report the cold frame's cost separately.
5. **The miss ring stays as a safety net.** With complete expectations, both first use and steady state should show 0 misses. Report any miss as a bug, with its pc.

## Note from lane A's PC session (10:32 PT): take driver CPU by process, not by threads

The result asks for "driver CPU per draw, by the thread-CPU method". Use LA-006's method instead (`results/cloud-2/LA-006.md` §1.1). The PM made it the method for lane A from now on.

- **Driver CPU:** the process's utime+stime from `/proc/<pid>/stat` over the measured frames, which keeps the CPU of threads that exited, minus lavapipe's threads (`llvmpipe-0/1` and lavapipe's queue thread; a gdb backtrace at the window's start names them).
- **Why:** LA-004 §6's thread method sums only the threads alive at the window's end. The queue-0 worker (`Driver::enqueue`'s thread) sometimes exits inside the window, and its CPU is lost. A check run gave 147.1 µs per draw by process against 84.1 µs by threads.
- **Take the base's number the same way** on the head you measure against, so before and after match.
- **The ~20 µs budget** is judged by the expectation phase's own timer, cold frame and steady state, as the brief lists. That doesn't change.
- If you have already taken thread-method numbers, keep them in the result, labelled as such, beside the process-method ones.
