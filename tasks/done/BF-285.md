## Why

BF-283 (`results/cloud-3/BF-283.md`) merged #12921 into #12745 and found an interaction. With both PRs in and `APS5_TABLE_INDEX=1`, two of #12921's tests fail 20 of 20, at their path assertions:
- `agc_untracked_revalidate`;
- `agc_untracked_hint_proof`.

The assertions expect a full walk after a collect epoch. #12745's index proves unwatched sampled elements by looking them up again (`reresolveElements(comparedTextures)` → `IndexOutcome::Accepted` → `indexProved`), and that re-lookup re-reads the memory:
- **storage views:** `refreshForView` → `StorageTexture::Refresh` → `compareUntracked`;
- **CPU snapshots:** `equalsCommitted`, or the hint key's `kept()`.

So the content follows every store, and the proof is reported `Fast`. It isn't a stale accept, but the tests read it as one. BF-283's probe table:

| step | index off | index on |
|---|---|---|
| store 4 KiB, then new collect epoch | Full, image version 1 → 2 | **Fast**, version 1 → 2 |
| new collect epoch, no store (no hint on Linux) | not fast | **fast** |
| store in the same epoch | fast, version 2 → 2 | fast, version 2 → 2 |

With the switch off (the default), nothing fails. But #12745's body claims a full ctest run with `APS5_TABLE_INDEX=1`, and a reviewer running that on a main with both PRs would see the two failures. The PM wants the fix ready now, for whichever PR merges second.
