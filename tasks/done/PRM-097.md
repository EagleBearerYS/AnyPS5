### 2. Which lock serialises `RetakeSpace` / `ReleaseSpace` / `SpaceHeld`

- **The concern:** `GuestBufferMemory::space` and `releasedSpace` are plain members of a `ShaderResources` that `SharedResourceCache()` hands to every draw. `resolveDrawResources` (`Graphics/src/Draw.cpp` ~1919-1965) does `SpaceHeld()`, then `RetakeSpace()`. The reviewer asks which lock keeps two threads from doing that on the same entry, and wants it asserted.
- **Find the lock:** we believe it's the draw's `GuestMemory::GpuMutex` hold, since `Recorder::Commands` and `Recorder::Submit` assert it. Establish it from the call chain into `Draw()` / `prepareDraw()` and the dispatch path's equivalent, if any reaches these functions. Don't just assume it.
- **Assert it** with `GuestMemory::AssertGpuLockHeld("<function name>")`, as `Recorder::KeepThroughHold` does, in `GuestBufferMemory::RetakeSpace`, `ReleaseSpace` and `SpaceHeld`, or at the one place that guards all three if that's cleaner.
  - The assert is active only under `APS5_ASSERT_GPU_LOCK=1` (`Execution/src/GuestMemory.cpp:2481`).
  - Any test or thread that reaches these without the lock will abort. Find out with the runs below.
- **If a path reaches them without the GPU lock,** stop and report it, with the stack, instead of adding a lock.
- The statement for the description comes from you: which lock, and which caller takes it. No code comment.

### 3. A verification switch for served hits

- **The ask:** the reuse is on by default and proven by containment, a snapshot compare and counters, but nothing checks a served hit against a fresh build. The reviewer asks for a switch in the style of the other `APS5_VERIFY_*` checks. On a hit, either:
  - build the resources anew; or
  - compare the snapshot and table bytes the hit relies on.
  Stop on a difference.
- **Name:** `APS5_VERIFY_ADDRESS_DRAW_REUSE`.
- **Pattern:** follow how `APS5_VERIFY_DRAW_DATA_HITS` and `APS5_VERIFY_DRAW_RECIPE` verify their hits: what they compare, how they stop and what message they print.
  - Pick the comparison that actually proves the served build matches what a fresh build would bind. Say in your result why it's sufficient, and what it doesn't cover.
- **Docs:** list the switch where the other `APS5_VERIFY_*` switches are listed (`docs/dev/ENVIRONMENT.md` or wherever they are). Mention it in the debt entry from point 1.
- **Tests:**
  - **Green:** the switch is on for a registration of the existing `agc_driver_address_draw_space_reuse` cases, and the hits verify.
  - **Red:** a stale hit makes the verifier stop with its message. Find the smallest way to produce one, for example a test-only path that skips the snapshot compare, if the code has a test seam. Don't add a production knob just for the test.
  - If no clean red is possible, say so; don't fake one.

### 4. `HeldSpace`'s destructor must not throw or allocate

- **Where:** the `HeldSpace` cleanup in `Graphics/src/Draw.cpp:3823-3832`. Its destructor calls `Recorder::Keep`, which calls `ensureOpen()` and `open->kept.push_back(...)` (`Recorder.cpp:2761-2764`).
  - An allocation failure there escapes an implicitly `noexcept` destructor and terminates the process. That includes cleanup after an early return or after another exception.
  - The reviewer's probe (a throwing `Keep`) ends in `SIGABRT`.
- **The ask:**
  - Retain any GPU work already recorded through an ordinary checked path, where an exception propagates normally.
  - Leave a nonallocating cleanup fallback that still keeps the backing memory alive as long as recorded GPU work can use it.
- **What we know:**
  - The normal recorded path already does `recorder.Keep(...ReleaseSpace())` in `recordPreparedDraw` (`Draw.cpp` ~2241). So the destructor matters only for early returns and exceptions after the space was retaken in `resolveDrawResources`.
  - The resources need `space` held while they are recorded, so releasing earlier isn't an option.
  - **Find out whether the open batch can change between the retake and the recording** (a submit or flush mid-draw), since that decides where a pre-reserved keep can live.
- **One possible shape, not prescribed:** reserve the keep in the checked path when the hit is taken, as a small object kept by the batch that will hold the commands. Then fill or clear it in the destructor with only `noexcept` moves. Choose what is correct, and explain it in the result.
- **Test:** a failure-injection test for the three paths, if feasible without production test hooks:
  - an unrecorded early return;
  - an exception during preparation;
  - a successful recording.
  The reviewer calls it optional; the fix is the ask. At least show the probe's red, `SIGABRT` with a throwing `Keep` before your change, and that it no longer aborts after it. A local probe that isn't committed is fine for that.
