## Why

sktharunbalaji13-cmd's Ghost of Tsushima Director's Cut (PPSA02225) run on Windows (RTX 4060 Laptop) posted three native multisample depth stops, each with a local change: https://github.com/boykopovar/AnyPS5/issues/5166#issuecomment-6495502628. With all three they ran 600 s, rendering 3D targets up to t=459 s. Their tree is main plus our depth stack: #9533 a7697941f3, #9742 97c707a4f1 and #9717 9846498dc7, all ours, held by the PR Manager, plus #12792. Their line numbers match #9742.

This is the same job as BF-273: for each change, a red on the code it changes, whether the change can lose data, and the correct form.

1. **t=277 s, "native multisample depth clear has no complete tracked HTILE store"** (DepthSurface.cpp `CheckCurrent`, the `gpuFill` lines, L481 and L499 on #9742).
   - **Our code**, from c11074be82 (m.peau, "prove a whole HTILE fill still queued on the GPU from its pattern") and 90d652a1ed (ours, the stencil plane), both in #9533: `gpuFill = clearPattern && clearFillNote != 0u && (queuedFill || newestHtileNote == 0u)`.
   - **Their change:** `gpuFill = clearPattern && (newestHtileNote == 0u || (clearFillNote != 0u && queuedFill))`, and the same for stencil. That accepts the clear when nothing is pending over HTILE, even if no fill note was ever found, and skips `StoredAllSince`.
   - **Their reading:** the fill settled (retired) before `CheckCurrent` caught its note, so `fillNoteAfter` returned 0.
   - **The risk:** accepting guest HTILE words that weren't stored since the clear. The words would still pass `htileProvesClear`, but would be stale, e.g. a clear whose fill never ran, with HTILE left over from an earlier identical clear.
2. **t=279.2 s, "sample-preserving guest publication of native multisample depth is not implemented",** from `GuestBufferMemory::UploadFinish`.
   - **Main's code:** UploadFinish runs `RequireNoResidentDepthRead_nid_no_patch(begin, bytes)` for every declared write (L5419 on main 5454cd2e45). That throws when the range overlaps a resident native depth surface whose host image has newer samples (`hostWritten`).
   - **The trigger:** compute dispatch 0x20001f3500.
   - **Their change:** a new `RetireResidentDepth_nid_no_patch` that retires the depth guards over the write ranges without the `hostWritten` check. Their reasoning: GPU buffer writes clobber the memory (aliasing), so nothing reads the old samples.
   - **The risk:** a declared write range that covers the surface only partly, or a range wider than the actual stores. `WriteBack` stores only changed bytes, so the host's newer samples outside the stores would be dropped. The write-back's reference and any read of the old bytes would also see stale guest depth.
3. **t=302.8 s,** the same message from `ShaderResources` `cachedTexture`, `cachedStorageTexture` and `RepeatStorageSurface`.
   - **Main's code:** `RequireNoMultisampleTarget` (MultisampleTarget.cpp L1466, which calls `RequireNoResidentDepthRead`) runs before `DepthSurfaceTexture`/`DepthSurfaceStorage`, at ShaderResources.cpp L733, L1193 and L1554 on main. In `cachedTexture`, L716 already tries `DepthSurfaceTexture` first for multisample views.
   - **Their change:** try the depth handlers first, and keep `RequireNoMultisampleTarget` as the fallback.
   - **What to check:** do `DepthSurfaceTexture`/`DepthSurfaceStorage` really serve a storage view of a native multisample depth surface? Do they publish or refuse correctly when the host has newer samples? Does returning one skip a guard that still matters?
