## ADDENDUM (PR Manager, 2026-10-17 ~06:30 UTC): FSR halved a title's frame rate where it can't upscale

On this PC (text only), Planet of Lana (PPSA19450) presents a 3840x2160 buffer into a 1084x610 window, so EASU is skipped and only RCAS runs on the fitted image. One back-to-back pair, the same route, t0+60..240 s, both with `APS5_DUMP_FRAMES=1`:
- `ANYPS5_UPSCALE` unset: 12.05 fps, frame p50 80.4 ms.
- `ANYPS5_UPSCALE=fsr`: 5.75 fps, frame p50 207.4 ms.

The project's summary trace (median ms per frame, unset → fsr) shows the GPU barely changed (busy 44.3 → 48.2 ms per present), while CPU-side driver time grew:
- `Driver.Packet` 79.6 → 194.1;
- `Driver.Draw` 31.9 → 117.2, with `Driver.Draw.draw_enqueued` 11.7 → 88.1;
- `Driver.Packet.device_lock` 43.5 → 69.5;
- `Driver.Present` only 6.6 → 9.1.

Private memory, paging and other CPU load were the same in both runs, so it isn't memory pressure. Something on FSR's path makes the title's draws wait: a lock held across the present's work, a fence wait, or a dependency on the display buffer or stage images that serializes the next frame.

Add to this task:
1. **Find the cause** on lavapipe with a harness that presents a 3840x2160 buffer into a smaller swapchain while draws run, unset against `fsr`. Measure CPU-side time per frame, not just GPU timestamps, and look at what `present()`'s FSR path holds and waits on.
2. **The design rule** (from the PM): FSR must never cost frame rate where it can't upscale. When the fitted image is not larger than the display buffer on either axis, take the normal scale path (or RCAS alone, if that's measured to cost nothing on the frame rate), and say which in FSR's start line and in USAGE. Implement the fix with its test in the same commit on `feat/agc-fsr1-upscaling-cost`.
3. **Add a case to the cost matrix:** 3840x2160 into 2560x1440 (a downscale), and report CPU time per frame beside the GPU timestamps for every case.
