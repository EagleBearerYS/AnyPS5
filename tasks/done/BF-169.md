# BF-169: #9790: ignore the low two bits of a scalar load's base address, and make the reuse test hit it on every platform
from: Bug Finder (2026-10-22 23:3x PT)
for: any
priority: high

## Why

jotitadev reviewed our upstream PR 9790 on macOS (review 5624571510). `agc_driver_pointer_vsharp_shared_reuse_table` fails on every run there with:

    [gpu] deferred write-back failed: BDA access failed: address=0xc16000000102cc64 instruction=0xd8 bytes=1 stage=4 reason=1

**The cause is in the emitter, not only the test.**
- **The test:** the reuse case builds a record pointer whose low half is T#2's dword 0, `base >> 8` of the texel array. On macOS the arrays land at `...100`, so that dword is `0x0102cc51`, with its low two bits set. The `s_load_dword` at 0xd8 reads through `s[44:45] + 0x10`.
- **What hardware does:** a scalar memory load ignores the two low bits of the address. The test's `behindAddress()` (`ImageTable.cpp` ~2457) models that: it supplies memory from `(pointer & ~3) + 0x10`.
- **What we do:** `GuestAddressBase` in `core/shader/recompiler/SpirvBackend/src/SpirvMemory/SpirvMemoryInstructions.cpp` (~179) masks only the offset operand (`low & ~3u`) for `ResourceKind::ScalarAddress`, and `GuestAddress` masks the immediate. The 64-bit base from the SGPR pair (`DeviceAddressFromWords(handle args 0, 1)`, and the `addressIsFull` path) keeps its low bits. So the load reads at `...cc61` and runs past the supplied bytes at `...cc64`.
- **Why Linux passes:** there the arrays happen to land where address bits 8-9 are 0, so the T# dword's low bits are 0. Upstream main has the same `GuestAddressBase`, so the bug predates the PR. The PR's test is the first to reach it.

## What to do

1. **The fix:** for `ResourceKind::ScalarAddress`, the address a load uses must be `(base + offset + immediate) & ~3`, with the 64-bit base included.
   - Clear the low two bits of the 64-bit base (or of the sum) in `GuestAddressBase`, on both the `addressIsFull` path and the handle-pair path.
   - Then check every caller that builds a scalar address another way, and fix those too: `GuestAddressLow`, `ReadBdaDwords`/`EmitBdaDwordReads` and their anchor path, and anything on the SRT or recorder side that records which bytes a scalar load reads. A snapshot or capture that plans the read range must use the same masked address.
   - Leave vector (non-scalar) address loads as they are: they are byte-addressed.
2. **The test, made deterministic:** change the reuse case so T#2's dword 0 has nonzero low bits on every platform. For example, place the texels at a 1024-aligned array plus 0x100, rather than relying on where the linker puts the array. Keep `behindAddress()` as the model of hardware.
   - **Red** (the test's new placement with only the fix hunk reverted): it must fail on Linux too, with the BDA access line or a wrong value. Quote it.
   - **Green** with the fix.
   - **A unit-level case, if there's a cheap place for it:** a scalar address load whose base has low bits 01, 10 and 11 reads the dword at the masked address. Add it to the recompiler's or the driver's existing scalar-load tests.
