# BF-107: name what allocates the 1 MiB and 2 MiB blocks that grow at Resident Evil Village's menu: a big-allocation call-site counter for one PC boot

for: any

## Why

At Resident Evil Village (PPSA01556)'s warm static menu, private memory grows ~0.52–0.64 GB/min with graphics pipeline libraries off. This is lane B's top lead.
- **The runs:** qbf098a and qbf098b, on the fix tree fork `test/f6457-bf092` **af0821dddb**: #8926's fix plus BF-092's `[buffers]` counter, on main 1ff5c8ac5c.
- **The driver's host-visible buffers stay flat:** `[buffers]` 749 → 757 MiB.
- **The census** (`anyps5_large_block_census.py`, read-only) at menu +0:21 and +6:00 shows the growth is **ours**: memory outside the guest spans grew +3,176 MiB in 5:39. The growing classes, each about 36 new blocks a minute:
  - "a table of guest addresses", in **1 MiB** blocks (more than half of the first 4 KiB is guest addresses): +202 MiB;
  - "heap large block or linked arena", in **2 MiB** blocks (the first two qwords point at other allocations, as an NT heap large block's list links do): +389 MiB, +202 allocations;
  - NT heap segments: +210 MiB.
- NVIDIA's driver arena and the write-combined memory are flat.

These look like large `malloc`/`new` blocks: containers or arenas of ours that keep growing or are never freed. One boot with a counter of big allocations by call site names them.

## What to do

Branch `exp/big-alloc-sites`: **one commit on af0821dddb**, so it builds into the PC's tree as is. It's a diagnostic, not a PR.

1. **A big-allocation tracker:**
   - With `APS5_PROFILE_BIG_ALLOCS=1` set at startup, every allocation of **≥ 512 KiB** through global `operator new` and `operator new[]` (all sized, aligned and nothrow forms) and through `malloc`/`calloc`/`realloc`/`free`, where you can hook them in this build, records its size and a stack of up to 16 return addresses (`CaptureStackBackTrace` on Windows, `backtrace` on Linux).
   - It aggregates by stack.
   - The matching free removes the record. Keep a side table keyed by pointer; don't put headers in the blocks, which would change the census's view.
   - Without the variable it costs one cached flag test per allocation, or nothing if you can install the hooks only when it's set.
   - The replacement `operator new` must be defined once in the executable: put it where only the main executable links it, and say where.
   - Hooking `malloc` on Windows (MinGW with UCRT): if a safe way doesn't exist, cover `operator new` only and say so. Our containers use `new`.
2. **Output,** every 10 s and once at exit, under one line kind, e.g. `[bigalloc]`:
   - totals: live bytes and count, and allocated and freed since the last line;
   - the top 12 stacks by live bytes. Each gives live bytes, live count, allocations and frees since the last line, the size histogram (1 MiB, 2 MiB, other), and its frames as `module+0xoffset`, using `GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS | ...UNCHANGED_REFCOUNT)` and `GetModuleFileNameW`.
   - Also, for the top 3 stacks, the first 64 bytes of their newest live block, as hex. That ties a stack to the census's content classes.
3. **Resolving the frames on the PC:** Windows Release builds from MinGW are not stripped.
   - Give the exact command to turn `module+0xoffset` into a function name from the built `.exe`/`.dll` with MinGW binutils: `addr2line -f -C -e <module> 0x<imagebase+offset>`, or nearest-symbol lookup with `nm -C`.
   - Write a small script for it under `tools/` on the branch, which can take the log and print the resolved stacks.
4. **Test on Linux:** a unit case that allocates three 1 MiB vectors from one function and frees one. The line must show 2 live in that stack, and the stack must resolve to that function's name with the script's Linux path (`addr2line` on the test binary).
5. **MinGW:** `x86_64-w64-mingw32-g++-posix -std=c++20 -fsyntax-only -Wall -Wextra` on the changed sources (BF-104 found this machine can't cross-build; the PC runs GitHub's Windows build).
6. **From the code, while it builds:** search our tree for containers or arenas that could reach 1 MiB or 2 MiB blocks and keep growing at a static scene. List them so the PC's stacks have candidates:
   - `reserve` or `resize` to 1 MiB, 2 MiB or a page count;
   - vectors of guest addresses: page lists, range tables, lookup logs, capture records, BDA ranges;
   - 2 MiB arenas or chunk pools;
   - caches with no bound.
