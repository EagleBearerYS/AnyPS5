# BF-254: diagnostic build on #9508's head: count the heap walk memo's entries and bytes per thread, plus an env override for its key cap

## Why

- **The climb:** on Resident Evil Village (PPSA01556), Raghav314's open #9508 at its head 6275369b6c raises private memory by ~1.8 GB/min at a static menu. The control (main 4c92447924) stays flat. Both arms ran with #11580 and the 6400 MiB import cap. GPU shared memory is equal in both, so it isn't Vulkan memory.
- **The census:** at menu+1, the excess is all NT heap segments (+1,466 MiB), i.e. small C++ objects.
- **The stage-template LRU is ruled out:** it reports `templates 0 (0 MiB, 0 evicted)` throughout.
- **The candidate owner** is the heap walk memo in `core/libs/prx/libSceAgcDriver/Execution/src/Driver/Draw/HeapStages.cpp` (6275369b6c: `HeapWalkMemo` L248-290, `rememberWalk` L396-418).
  - **Cap:** it's capped by count (16,384 keys × 4 ways, plus a whole `previous` generation), per thread through `HostThreadLocal`.
  - **What it pins:** each entry holds a `shared_ptr` to a `RecompileResult` and a `ResourceCapture`, plus copies of the walk's values and the `HeapStageWords`.
  - **The rates in the log:** the result memo misses 97 % at the menu (`[recompile] result memo`: ~6,800 misses per 10 s). The walk memo inserts ~7,000 entries per 10 s, so each insert keeps alive a fresh result that the bounded result memo already evicted.

This build checks that on the PC. It's a diagnostic only and never goes to a PR. The PC boots it with the title; **no game data comes to the worker.**

## Do

Base: `git fetch upstream refs/pull/9508/head` and branch from **6275369b6c** (Raghav314's PR head; the cloud prompts' standing OK for other contributors' upstream PR heads covers it).

1. **Per-thread counters for `HeapWalkMemo`, kept by the owning thread only**, so there's no cross-thread access to the maps:
   - keys in `current` and in `previous`;
   - entries (ways) in both;
   - approximate bytes held. Use `sizeof(HeapWalkEntry)` plus the vectors' capacities, plus `OwnedBytes(*entry.result)` from `core/shader/recompiler/HeapTemplateBudget.hpp`, plus a capture and words estimate. Use whatever byte accounting already exists for `ResourceCapture`/`HeapStageWords`; if there's none, count their vectors' capacities, and say which you used;
   - inserts and drops (`pop_back`, the drain of `previous`, the generation swap);
   - **entries whose `result` the memo alone holds** (`use_count() == 1`) and their bytes, as a lower bound for results that only the memo keeps alive.

   Each thread computes this when its own 10 s window has passed (a scan of its own memo is fine) and publishes a snapshot into a mutex-guarded global registry, keyed by thread. Remove the thread's entry when its memo is destroyed.
2. **Print one line every 10 s under `APS5_PIPELINE_STATS`**, next to the existing `[gpu-heap]` lines:
   ```
   [gpu-heap] walk memo (10 s): N threads; total X entries (Y keys), Z MiB, memo-only W entries / V MiB; inserts I, dropped D; per thread: <keys cur/prev, entries, MiB, memo-only MiB> ...
   ```
   Keep it to one line, with the per-thread list capped at 16 threads.
3. **Env override:** `APS5_HEAP_WALK_MEMO_KEYS=<n>` replaces the 16,384-key cap. Unset, the default and all behaviour stay exactly as now. It lets the PC run an arm with a small cap if the counters alone don't settle it.
