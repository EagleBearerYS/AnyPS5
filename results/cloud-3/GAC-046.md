# GAC-046: the sample order planning test's "leak" is a data race on its mock, not a leaked object

From: AnyPS5 Cloud 3 (Linux worker).

**Branch:** `fix/agc-sample-location-grid-exact` on the fork. New head **e030401916109c45b47eacca60ed3b94c3a3ce27** (e03040191): one new commit on e6068b79a6, a fast-forward with no amends.

| Commit | What it is |
|---|---|
| e03040191 | `test(agc): keep the sample order pipeline test's mock on the test thread`. One added line in `tests/Graphics.cpp`: the loop's context sets `context.pipelineLinkTimeOptimization = false;` next to `context.graphicsPipelineLibrary = libraries;`. |

There's no driver commit, because the driver doesn't leak (see below).

## What held the object

Nothing holds an object at the check. The count itself is wrong.

1. **A second thread calls the mock.**
   - With `context.graphicsPipelineLibrary = true`, `Pipeline` links from libraries (`LinkPipelineFromLibraries`).
   - `Context::pipelineLinkTimeOptimization` defaults to true (`Context.hpp:228`). So each linked pipeline also queues an optimized link on the pipeline-library worker thread (`enqueue` → `runJobs`, `PipelineLibrary.cpp:255`).
   - That job calls the context's `vkCreateGraphicsPipelines`. Here that is `sampleOrderCreateGraphicsPipelines`, which does:
     - `pipelineSampleMasks.push_back`;
     - then `sampleLocationCreateGraphicsPipelines`, which does `makeHandle` (`mock.next++`) and `++mock.live`.
   - If the pipeline was released first, the job also calls `vkDestroyPipeline` (`--mock.live`).
2. **The test thread uses the same globals at the same time.** While a job runs, the test thread builds `native` (shader modules, library parts, layouts) and then destroys both pipelines.
   - `MockVulkan::live` is a plain `std::int64_t`, `next` a plain counter, and `pipelineSampleMasks` a plain vector.
   - So one thread's `++`/`--` can overwrite the other's. `live` then ends at ±1, and `Require(mock.live == 0, …)` reports "sample order pipeline tests leaked Vulkan objects".
3. **Nothing is pending at the check:**
   - `ClearPipelineLibraries` waits for the device's pending jobs (`store.idle.wait(… pending[device] == 0)`) before it destroys the libraries.
   - `OptimizedPipeline::Release()` and the job's second `released` check hand the optimized pipeline over through seq_cst atomics, so exactly one of them destroys it.
4. **Why only this test:** the other mock tests that use libraries, `sampleLocationGridFallbackTests` and `pipelineLibrarySetTests`, only prebuild. `LinkPipelineFromLibraries(…, partsOnly = true)` returns before it queues the optimized link, so this was the only mock test that started the worker.

### Why it isn't fixed by draining

- A drain before the check already happens: `ClearPipelineLibraries` waits for the worker.
- I tried `WaitForOptimizedPipelines(context.device)` right after each `Pipeline` constructor (not committed). ThreadSanitizer still reported a race in 2 of 3 runs: the job's `++mock.live` against `mockDestroyShaderModule`, called from `Pipeline::Pipeline` itself.
- The cause is the constructor's order. After it queues the link, it destroys the shader modules a cached library part didn't keep (`Pipeline.cpp:565`). A wait from the test can only start after the constructor returns, so it can't close that window.
- So the test now doesn't queue the optimized link at all, as on a device without link-time optimization. The test checks nothing about the optimized pipeline.
- The other way to keep it would be a thread-safe mock (atomic counters, a lock around the recorded vectors). That is a bigger change to the shared mock than this test needs.

## Evidence: ThreadSanitizer

Setup:
- `tests/Graphics.cpp` compiled with `-fsanitize=thread -O1 -g` using the build's own compile command.
- Linked against the tree's normal `libSceAgcDriver.prx`.
- Run as `runner` under `setarch -R`, because gcc 13's TSan needs ASLR off on this kernel.

Results:
- **e6068b79a6:** data races in every run: 11 of 11 runs, 6 to 12 reports each. The first run's reports:
  - `mock.live` (`Graphics.cpp:4978`, `++mock.live` in `sampleLocationCreateGraphicsPipelines`), on worker thread T1, in the `LinkPipelineFromLibraries(…)` lambda run through `std::function`. It races with `mockCreateShaderModule` (`Graphics.cpp:3618`) in `Pipeline::Pipeline` on the main thread, building the next pipeline.
  - `mock.next` in `makeHandle` (`Graphics.cpp:3422`), between the same two threads.
  - The `pipelineSampleMasks` vector's `push_back` and reallocation (`Graphics.cpp:5154`), from both threads.
  - The rest are allocator and shared_ptr reports. Some of those come from instrumenting only the test file.
- **Draining after each constructor:** races in 2 of 3 runs, as above.
- **e03040191:** no reports in 20 of 20 runs. Each prints "Sample order checks passed".
