## Summary

- **The fix:** a build (`buildComplete`) and a full walk now mark where their own lookup records start. When the log reaches its 1,024 bound, the trim drops only records older than that mark. Lookups outside a build keep main's rule. A build therefore never loses its own records, at any size.
- **Effect on BF-033's harness, plain program, 2,000 textures:**
  - **4,674 → 749 µs per dispatch** with memory unchanged, and 4,550 → 728 µs with one word changed;
  - per 10 s window, from 12,057 full walks (all `no record`) to 63,230 fast proofs and no full walks;
  - 16 and 128 textures are unchanged within noise;
  - the fix matches the raised-bound run (779 µs).
- **Test:** red 5 of 5 on main's `logLookup` ("a set over 1500 textures took the full walk with its memory unchanged after the build"), green 20 of 20 with the fix.
- **Checks:** `^agc` 627/627 with the fix (main: 626/626) and the same 44 skips. Registration, conventions and the comment grep are clean.
- **Build cost:** a 2,000-texture build costs the same with the fix as with the raised bound.
  - Both pay about 0.3 ms more per build or full walk than main, in `captureValidation`'s reverse search, which is quadratic in the texture count.
  - Main is cheaper there only because it has lost half the records.
  - This is a follow-up (§6), not part of the PR.
- **Memory:** a record is 136 bytes, so 2,000 records are 272,000 bytes while a build runs.

## 1. The fix

On main, `logLookup` (`ShaderResources.cpp:390` on f474fb7768) drops the oldest 512 records whenever the log holds 1,024. Its comment assumed "one build's lookups (a few dozen at most) are the newest records". A build that binds 2,000 textures through an image table breaks that assumption: the trim at its 1,025th lookup drops its own first 512 records. `captureValidation` then finds no record for those textures, and every later fast proof fails with `no record`.

The fix (lines on bde2a8f0af):
- **A start mark:** a thread-local `buildLookupsStart` (`:386`) holds the index of the current build's first record, or "no build".
- **The trim:** `logLookup` (`:394`) drops at most `min(512, buildLookupsStart)` records and moves the mark down by what it dropped. With no build in progress, the minimum is 512, exactly main's rule.
- **`BuildLookups` (`:406`)**, an RAII guard, sets the mark on entry and clears it on exit, also on an exception. A nested guard keeps the outer mark. Two places open one:
  - the top of `buildComplete` (`:1918`). Every texture lookup of a build runs there: the deferred image bindings (`:1927`) and the image tables (`:1938`). So does the capture (`noteReusable` → `captureValidation`, `:2103`).
  - the full walk in `Revalidate`, right after its existing `lookupLog().clear()` (`:2864`). Its capture is at `:2931`.
- **The removed comment:** the "a few dozen at most" comment in `logLookup` is deleted, since it is now wrong. CONVENTIONS allows no added comments, and deleting one is allowed.

**The counter** is appended to the existing `[rescache] revalidate` profile line as `lookup log: N builds and full walks kept their records past the bound`. The task asked to count any trim that would drop a record of the current build, and for that count to stay 0. With the fix, that count is 0 by construction, because the trim stops at the build's first record, so printing it would only print a constant. The line counts instead the builds and full walks whose trim was held at their first record, which are exactly the ones that lost records on main. In the harness it read 1 at 2,000 textures (the one build) and 0 at 16 and 128.

**The consumers, all read:**
- `captureValidation` (`:2476`) finds each texture's newest record by searching the log backwards, then clears the log. It now finds them all.
- The full walk clears the log before its lookups, as before; the guard comes after that clear.
- `resolveImageTables` (`:4309`) reads `log.back()` right after `cachedTexture` to see whether a table element is reusable. The trim runs before the push, so `back()` is still the record just made. This is unchanged.
- The writers, `cachedTexture` (`:586`) and `fastTexture` (`:3920`, the stage-A record hit), are unchanged.
- **Lookups outside a build** keep the old bound: `CachedSampledTexture` (`:1070`, the public lookup tests use) and lookups during a build that throws (the guard clears the mark on unwinding).
- **Deferred compute builds:** `buildPrepare` runs at dispatch time and `buildComplete` later, possibly on another thread. Neither the lookups nor the capture are in `buildPrepare`, so the thread-local log and mark are per `buildComplete`, as before.

## 2. The test

`tests/execution/LookupLogFitsBuild.cpp`:
1. Opens the Vulkan test device and takes its graphics context through `VulkanDeviceTestAccess::ContextOf`, as `DepthPlaneSampling` does.
2. Compiles BF-033's plain program (a texture heap indexed dynamically) against a heap of **1,500** T#s. Each T# is an 8×8 RGBA8 surface in a write-watched, non-imported guest block.
3. Builds a `ShaderResources` for it directly, checking that it is reusable and binds 1,500 sampled textures.
4. Then calls `Revalidate` with a `ProofReport` and requires, in order:
   1. the fast path, with memory unchanged after the build;
   2. after a store of an unchanged byte into texture 500, the full walk;
   3. if that walk proved the set current, the fast path again (this covers the full walk's own capture);
   4. after a real change to that byte, the full walk and a refused proof (the fast path stays exact).

The test keeps its two guest blocks registered until the process exits, like `ImageTableCacheBounds`. Freeing the imported block right after a build made outside the driver's dispatch path waits on a lease that only the driver's own flow releases (60 s, then a pin error).

**Red, with only the fix reverted:** 5 of 5 fail, each with
`AGC graphics: lookup log: a set over 1500 textures took the full walk with its memory unchanged after the build`.

**Green, with the fix:** 20 of 20 pass, each printing the three checks and `lookup log fits build tests passed`. The ctest entry takes 0.68 s.

### The build's own time at 2,000 lookups

The address-based program at 2,000 textures rebuilds its resources on every dispatch, since main never reuses an address-based object. That makes it a build-time benchmark. The capture time comes from separate 34 s runs with a temporary timer around `captureValidation`; the timer was never committed.

| run | driver total (µs per dispatch) | device call | `captureValidation` per build | records it searched |
|---|---|---|---|---|
| main's bound (1,024) | 8,605.7 (8,028.3–8,712.2) | 7,904.3 | 800–862 µs | 976 (half the textures have no record) |
| raised bound (8,192) | 9,271.1 (8,730.5–9,955.8) | 8,575.1 | 1,029–1,100 µs | 2,000 |
| fix | 8,798.0 (7,921.8–9,342.0) | 8,080.2 | 1,096–1,171 µs | 2,000 |

- **The fix and the raised bound do the same work in a build.** Their totals differ by less than the window ranges.
- **Both pay about 0.3 ms more per 2,000-texture build or full walk than main**, all of it in `captureValidation`. That function looks up each texture's record by scanning the log from the end, so its cost grows with textures × records.
- **Main's capture is cheaper only because it searches 976 records and finds half the textures missing.** On every later dispatch, main then pays a 4.3 ms full walk. The fix saves about 3.9 ms on each unchanged revalidate, against 0.3 ms once per build.

### Memory per record

`sizeof(LookupRecord)` is **136 bytes** on this build; 88 of them are the `GuestTextureResource`, measured by the compiler.
- **One build:** 2,000 records are **272,000 bytes** (266 KiB) in the build's log while it runs. The capture then clears the log.
- **Per thread:** the thread-local vector keeps its capacity, 2,048 × 136 = 278,528 bytes, on each thread that has run such a build. Main caps it at 1,024 records (139,264 bytes).

## 6. Other readers of the lookup log, and follow-ups

- **`captureValidation`'s reverse search** is the only consumer whose cost grows with the change (§3). A one-pass capture is a separate change. A trial version that maps each object to its newest record (a hash map rebuilt per capture) took 470–510 µs at 2,000 textures, against 1,100 µs, and 6.7 µs at 16. Most of its cost was the map's node allocations, so a flat structure should do better. It would also make each changed-memory full walk at 2,000 textures about 1 ms cheaper. The trial was measured, then dropped; it is not on either branch.
- **`resolveImageTables`' `log.back()` read** is unaffected (§1).
- **Thread-local capacity:** the log's vector keeps the capacity of the largest build its thread ran (§3).
- **No open PR was checked for overlap;** the task did not ask for it. The change is confined to `logLookup`, two guard lines, and the `[rescache]` print in `ShaderResources.cpp`.

## PR text (draft)

> **fix(agc): keep a build's own texture lookup records past the log bound**
>
> The sampled-texture lookup log dropped its oldest half at 1,024 records. A build or full walk with more lookups, such as a draw or dispatch binding ~2,000 textures through an image table, lost its own earliest records. Its resource object then had no validation record for those textures, so every later `Revalidate` failed the fast proof with `no record` and walked every texture.
>
> A build (`buildComplete`) and a full walk now mark where their records start, and the bound trims only older records. Lookups outside a build keep the old bound. The `[rescache] revalidate` line counts the builds and full walks that kept their records past the bound.
>
> - lavapipe, 2,000 textures, memory unchanged: 4.67 ms → 0.75 ms per dispatch, with all proofs fast (they were all `no record` full walks).
> - 16 and 128 textures are unchanged.
> - New test `agc_driver_lookup_log_fits_build` (1,500 textures): it fails on the old bound and passes with the fix. `^agc` passes.
