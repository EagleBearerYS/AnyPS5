## 1. Port 1: #1201 02cafe391 (cheaper captures), resolved in part

### 1.1 What was ported and what was not
- **Kept** (ShaderMemory and profiling):
  - the valid/read/recent marks as 64-bit word arrays scanned with countr_zero;
  - pages from a per-thread pool (64 kept), found through a short sorted vector with a last-page shortcut;
  - a page no recorded GPU work writes gets the whole-page flush hook once, then has each 16-word (64-byte) block copied when a word of it is first read;
  - `APS5_PROFILE_DRAW`'s `[capture]` line split into SRT evaluation and materialization, and printed once per 10 s instead of every 500 captures.
- **Skipped** (the SRT evaluator half):
  - the stamped per-thread memo array;
  - the 32-byte compact plan copy;
  - the `BasicEvaluator<TNode>` template, and `APS5_VERIFY_SRT_COMPACT`.
- **Why skipped:** main's **#5181** (ThatsLeo, "compact resource plans") rebuilt both things those parts were written against.
  - It moved plan storage into an `IrValueArena` that keeps original value ids, which the disk cache relies on.
  - It gave the evaluator `MayEvaluate`, an active mask and its own open-addressing memo.
  - 02cafe391's memo, compact copy and template assume the old plan layout and dense ids. Carrying them over would mean rewriting them on the hottest path of every draw, not porting them, and the result would not be #1201's tested code.
  - What Village loses: 02cafe391 measured the memo at 5.3 → 3.6 µs and the compact walk at 3.6 → 2.7 µs per capture in GTA V. Main's own memo (#5181) may already recover part of the first.

### 1.2 Conflicts and hand-resolved hunks
- Against the tree's tip, the pick conflicts in six files:
  - ShaderMemory.cpp, ResourcePlan.hpp;
  - ResourceMaterializer.hpp and .cpp;
  - SrtEvaluator.hpp and .cpp.
- Four more files merge as text, but only work with the skipped evaluator template: SrtInstructionPredicates.hpp/.cpp, SrtDescriptorEvaluation.cpp, SrtWalker.cpp, and tests/ShaderMemory.cpp.
- How each was resolved:
  1. **Evaluator files, the four above and tests/ShaderMemory.cpp:** the tree's version is kept, so 02cafe391's changes there are dropped (§1.1). The test's one changed line calls the dropped template.
  2. **ShaderMemory.hpp/.cpp:** 02cafe391's page store, as written.
  3. **`ShaderMemory::readWords` (hand-written).** Main added it for image tables after #1201 branched, and it still used the old bitsets.
     - It now serves a run straight from the page once the page is lazy or fully valid.
     - Before serving a lazy page, it copies the 16-word block of each word not yet valid, as `read()` does for one word.
     - Then it sets the read and recent marks word by word.
     - Pages over pending GPU writes, and unmapped pages, still go through `read()` word by word.
  4. **ResourceMaterializer.hpp/.cpp and the recompiler CMakeLists export list.** 02cafe391's `EvaluateNanoseconds` / `MaterializeNanoseconds` counters are re-applied to main's materializer: around `EvaluateRuntimeSources` and around `Materialize`'s body. The tip's `TableReuse()` accessor (PM-028) stays next to them.

### 1.3 The fix the new tip needed
The tip's PM-028 commits add three image-table hooks to ShaderMemory: `stampWrites`, `unchangedSince` and `supplyWords`. Two of them used the old `std::map` page store and bitsets.
- **`stampWrites`** now looks for an already-fetched page in the range with `std::lower_bound` on the sorted page vector.
- **`supplyWords`** adds a missing page to the vector without fetching it, through a small `insertPage` helper. The helper is split out of `page()` and holds the pool logic that used to be inline there.
  - The supplied words become valid, read and recent word by word.
  - Such a page is neither lazy nor word-wise. Its other words go through the hook one at a time, as they did before on main.
- `readWords`' lazy branch tests every word of the run, not one word per block, so a block that holds only supplied words is still copied before it is served.
- `unchangedSince` needed no change.

## 2. Port 2: #1201 pipelined draws (449e69422 + cc34394d2 + 31c9a0f2e)

### 2.1 What it does
- With `APS5_PIPELINED_DRAWS=1`, queue 0's worker decodes, captures and recompiles a draw, then hands it to a committer thread. The committer records it under the GPU lock.
- Labels, the end of a submission, the title's buffer fill kernels and (opt-in) DMA_DATA become commit items. Any packet the pipeline cannot order drains it.
- `epochCollectMap` (`APS5_NO_EPOCH_COLLECT_MAP`) is **dropped**, as the task asked. Its three GuestMemory.cpp hunks were taken out, and nothing else used them.
- cc34394d2 and 31c9a0f2e picked cleanly on top.

### 2.2 Conflicts and hand-resolved hunks (all in commit d0dafcd4c)
Three files conflicted as text. Two more merged cleanly as text but were wrong for this tree (items 4 and 5). The epoch collect map came out as asked (item 6).

1. **BufferFill.cpp (text conflict).** This tree split the fill into `fillBuffer`, which reads the inputs, and `storeBufferFill`, which stores. #1201 wrapped an inline store lambda instead.
   - The port queues `storeBufferFill` as the commit item from `fillBuffer` for queue 0, with the fill range as its write range. `APS5_PIPELINE_DRAIN_FILLS=1` still drains instead.
   - Three of the tree's fill paths read their pattern, range or value from guest memory under the GPU lock: the memory-value fill, the pattern fill kernel and the buffer-pattern kernel. Each now drains the pipeline before it locks, so it does not read bytes a queued commit has yet to write.
   - The input lock is released before the store is queued. Otherwise a full pipeline would wait in `Enqueue` holding the GPU lock its committer needs: a deadlock. #1201's own pattern-fill path had that wait under the lock too.
2. **Submission.cpp (text conflict).** Both sides kept:
   - the tree's submission-capture helpers and `capture->Take`;
   - #1201's `releasedTails` / `noteReleasedTails`, and `enqueuedAt` set on every submission. `copySegment`, which `noteReleasedTails` calls, is identical in both.
3. **ShaderResources.cpp/.hpp (text conflict).** This tree's `DescriptorCache::Allocate` takes `updateAfterBind` and a variable descriptor count, which #1201's base did not.
   - `AllocateRewritten` now passes `updateAfterBind` through, so a set comes from the pool kind its layout needs.
   - A set with a variable descriptor count (an image table) is freed, never recycled. A recycled set from another table size would carry the wrong count.
   - The thread's `selected` scratch vector (#1201) sits beside the tree's unwritten-snapshot stamp variables.
4. **Draw.cpp (clean as text, wrong as code).** The commit lambda moves the draw's owners into the committer. On this tree, stage programs and snapshots also point into two locals #1201's base did not have:
   - `compiledStages`, which owns each freshly materialized stage's result;
   - `stageData`, which holds a stage data hit's patched program and the words its regions span.
   - The lambda now owns both. Without that, a stage data hit committed after `draw()` returned would read freed memory.
5. **PacketExecution.cpp (clean as text, wrong as code).** This tree hangs EOP flips on a RELEASE_MEM packet (`submission.flips` at that cursor), not only on the flip packet.
   - #1201 would turn that RELEASE_MEM into a label commit and skip the flip, so the frame would never be presented.
   - Such a cursor now stays on the worker, after the usual drain.
6. **GuestMemory.cpp:** the epoch collect map is removed (above).

### 2.3 What I checked in the auto-merged files
- **The commit path (`commitDraw`)** matches this tree's non-pipelined tail line for line: lock, `recordLabelsForPacket`, `noteDrawWriters`, recipe, `Draw`, `attachDrawRecipe`.
- **Label commits** use `WriteLabelOnGpu`'s codes as this tree's label path does: 0 or 5 means stored on the GPU, and 1–4 means a CPU write. #1201's checks for code 6 are dead here.
- **thread_local:** `deferredLabels()` is thread-local on this tree too, so the worker's check before pipelining a draw still holds.

- **Locks:** `SlimMutex` replaces `std::mutex` only for the pending-image and unit-shadow registries. Every use of those two locks on this tree is a `lock_guard`: no condition variable, no `unique_lock`. `PendingList::MayOverlap` exists on this tree.

### 2.4 My two commits on top (drop either if you'd rather run #1201 as written)
- **a81674948 fix(agc): drain the draw pipeline before worker steps that read or record past it.** Three places in #1201 itself, not only on this tree, let queue 0's worker see guest memory, or record GPU work, ahead of queued commits:
  1. **Draw and dispatch cache validation** compares a variant's runs with guest memory.
     - A queued WRITE_DATA or fill into constants the variant read would still show the old bytes, so the hit is taken with stale constants.
     - Example: constant = 1 → draw → WRITE_DATA constant = 2 → draw. The second draw matches the first's variant.
     - `validateVariant` now drains when the runs overlap a queued commit's writes, as a capture's reads already do. That needs a new `DrawPipeline::Overlaps(span)` that takes the lock once.
  2. **A draw's precheck** records the CB metadata pass (and this tree's DB expand pass) on the worker, ahead of queued draws to the same surfaces. Both drain first.
  3. **An indirect fill kernel** reads its dispatch arguments on the worker. It drains first, as an indirect draw already does.
- **ccbc69741 perf(agc): look past an emptied buffer pool size class.**
  - #1201 keeps an emptied size class in the free map, to avoid node churn. The device tier's search over classes up to 2× the request then stopped at the first class it found, even an empty one, and missed a larger class that still had a buffer. That would be one more allocation on every such miss, in the default path too.
  - The search now goes on past empty classes. The buffer pool test gains a case: a 7 MiB request whose class is empty takes a retained 12 MiB buffer.

## 5. Env switches
| switch | default | effect |
|---|---|---|
| `APS5_PIPELINED_DRAWS` | off | `1` turns on the draw pipeline with depth 8; `N` sets the depth (at most 256). It is off whatever its value while `APS5_LOCKED_DRAW_PREPARE`, `APS5_DRAW_DRAIN`, `APS5_DRAIN_ALL` or `APS5_NO_WORDWISE_CAPTURE` is set |
| `APS5_PIPELINE_DRAIN_LABELS` | off | `1`: labels and same-queue waits drain the pipeline instead of becoming commit items. It also turns off the ordered submission end (the next row) |
| `APS5_PIPELINE_DRAIN_SUBMISSIONS` | off | `1`: the end of each queue-0 submission drains; completion is not deferred to the committer |
| `APS5_PIPELINE_DRAIN_FILLS` | off | `1`: fill kernels drain instead of queueing their store |
| `APS5_PIPELINE_DMA` | off | `1`: DMA_DATA immediates and copies become commit items. **Leave it off on this tree** (§6.2) |
| `APS5_EXACT_DRAW_WRITES` | off | `1`: a queued draw's color and depth write ranges are the targets' exact layout bytes, not the 2× + 64 KiB estimates. That means fewer false drains, but it trusts the layout sizes |
| `APS5_SUBMISSION_EPOCH_EACH` | off | `1`: bump the collect epoch at every submission, as before port 2. **This affects the default path**, not only the pipeline (§6.1) |
| `APS5_PROFILE_DRAW` | off | `[capture]` now splits materialize / SRT evaluate time and prints every 10 s. With the pipeline on, a `[draw] pipelined (10 s, depth N)` line counts commits, enqueue waits and drains by reason and by opcode |

## 6. Risks for the first Windows boot

### 6.1 Default path: active without any new switch
1. **Lazy capture pages (port 1).** A page no recorded GPU work writes is flushed once, then copied 64 bytes at a time as the capture first reads each block. A guest CPU store landing inside one draw's capture, between the flush and a block's first read, is now seen. Main would have kept the earlier bytes. This is the same kind of race main's word-wise pages already have, and it changes nothing on the GPU side.
2. **Collect epoch across a backlog (port 2).**
   - A submission the title made before the worker's last epoch bump now keeps that epoch. CPU write collection, and this tree's once-per-epoch image mirror compare (9d1031138), run once per catch-up, not once per submission.
   - The reasoning holds: those CPU writes happened before the bump.
   - If Village shows CPU-written data that doesn't update (textures, constants) where the parent tree was right, try `APS5_SUBMISSION_EPOCH_EACH=1` first.
3. **Recycled descriptor sets (port 2).**
   - Draw-snapshot descriptor sets without a variable count are reused per layout once their batch is done: up to 4,096 per layout, guarded by the recorder's `Keep`.
   - A recycled set holds its pool, so descriptor pool memory stays at its peak instead of resetting.
4. **Spinning registry locks (port 2).**
   - The pending-image and unit-shadow registries now spin (128 pauses, then `yield`) instead of sleeping.
   - Under heavy contention that burns CPU instead of blocking. #1201 chose it because winpthreads mutex contention cost kernel events.
5. **Buffer pool size classes are kept when empty (port 2).** With commit 6 the device tier still finds larger classes. The free map grows with every (size, usage, memory) class ever used.
6. **Windows-only traps (the PM-031 checks), clean on this diff:**
   - no `far`, `near` or `small` used as an identifier;
   - every new `thread_local` is a bool, an integer, a time point or a `ThreadOwned` slot pointer: none has a destructor in the prx;
   - the page pool and released-tail queue use `HostThreadLocal`.

### 6.2 Pipelined path (`APS5_PIPELINED_DRAWS=1`)
1. **A commit that throws** a `std::exception` is printed (`[draw] pipelined commit failed`, the first 20) and that draw is dropped. Any other exception is rethrown at the next enqueue or drain. Expect a missing draw rather than a crash.
2. **Worker steps still not ordered against queued commits:**
   - a draw-cache miss's vertex-fetch decode (`DecodeVertexStageInfo` reads the fetch shader and vertex buffer descriptors);
   - whatever the packets the pipeline keeps read (NOP variants of 0x10, EVENT_WRITE other than sample dumps).
   - Captures, cache validation, precheck passes, fill inputs and indirect arguments all drain.
3. **`APS5_PIPELINE_DMA=1` on this tree is correct but slower.** A data fill above 64 KiB would be stored by the CPU after a GPU idle wait, not by this tree's GPU buffer fill (#5788). Copies the device refuses become CPU copies, without the tree's copy-to-host path. Leave it off.
4. **Device replacement while commits are queued:** draws, labels and DMA stores re-load the device at commit, but a queued fill keeps the device it was queued with.
5. **The committer** is one `std::thread`, started at the first commit and never joined. It records under the GPU lock, so the worker's own GPU-lock work (dispatches, flushes, worker-side labels) waits on it.
6. **The speed claim:** #1201's 11.7 → about 20 fps (GTA V, RTX 5080) was measured with the full 02cafe391. Port 1 here leaves out its evaluator half.

### 6.3 A boot order that separates the two
1. Boot once with no new switch. Only §6.1 is in play, and the result should match the parent tree's.
2. Then boot with `APS5_PIPELINED_DRAWS=1 APS5_PROFILE_DRAW=1`. The `[draw] pipelined` line every 10 s shows commits per second and what drains the pipeline (reason, top opcodes). Many packet drains on one opcode name the next thing to order.
3. If the pipelined boot glitches, bisect with `APS5_PIPELINE_DRAIN_LABELS=1`, then `APS5_PIPELINE_DRAIN_FILLS=1`, then `APS5_PIPELINE_DRAIN_SUBMISSIONS=1`.
