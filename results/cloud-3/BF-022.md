# BF-022: GPU-side indirect draws for patched SGPRs that are not folded (prototype)

Worker: cloud-3. Branch `exp/agc-indirect-gpu-draw-parameters` on the fork, from upstream main
5d9dcc42d2, head e280ce9d5 (throwaway, no PR). Lavapipe (llvmpipe, LLVM 20.1.2) numbers only.

## Summary

- Option taken: **(a), draw-parameter built-ins**. A vertex stage compiled for a GPU-side indirect
  draw reads the CP-patched SGPRs from `BaseVertex`, `BaseInstance` and `DrawIndex`, and its
  vertex and instance index VGPRs are `VertexIndex - BaseVertex` and `InstanceIndex -
  BaseInstance`. One stage serves every record; the records are read in place by
  `vkCmdDraw(Indexed)Indirect` or the count variant.
- Correctness: a new test draws records with different base vertex, start instance and draw index
  through a stage that uses all three as data (none added to the vertex index), for
  `DRAW_INDIRECT_MULTI` and `DRAW_INDEX_INDIRECT_MULTI`, and compares the image with the CPU path's:
  identical, read in place and from CPU-read records. Red as on main and under three more
  mutations. `^agc` 607/607 (43 feature skips), new test 10/10.
- Cost on lavapipe, BF-015's harness (section 3). Driver thread per packet: CPU path 50.8 /
  283.7 / 1357.7 µs for 1 / 8 / 64 records (50.8 / 35.5 / 21.2 per record); GPU-side 52.5-67.7 /
  59.8-73.2 / 65.6-133.4 µs (52.5-67.7 / 7.5-9.2 / 1.0-2.1 per record). Wall per packet
  (unprofiled, median of 9): GPU-side **loses at 1 record** (68-91 vs 49-65 µs: main's GPU
  indirect path begins a render pass per indirect draw, which lavapipe executes slowly) and wins
  2.8-4.2x at 8 and 12-44x at 64 records.

## 1. What was built

### Option (a) over (b), and why

(b), loading the record in the shader as fb55cb2c0 does for mesh draws, needs a record address in
push constants (two free push dwords exist only on the mesh path), a physical storage buffer
pointer (bufferDeviceAddress), and still needs either `DrawIndex` to find the record of a
multi-draw or one draw command per record with its own push constant (a CPU loop per record, and
no count variant). (a) needs none of that: the three values already arrive as SPIR-V built-ins
(`DrawParameters` capability, core in SPIR-V 1.3 / Vulkan 1.1 behind the `shaderDrawParameters`
feature, which AnyPS5 already queries and enables when present, VulkanDevice.cpp:1475), one
`vkCmdDraw*Indirect` covers all records including the count variant, and the recompiler change
is a prologue substitution. The only thing (a) costs that (b) does not is the feature bit.

### Recompiler change (commit 4ff529dcd, 11 files, +49 −6)

- `Recompiler.hpp`: `DrawParameterSgprs {enabled, baseVertex, startInstance, drawIndex}` in
  `ShaderVertexStageInfo` (so it is part of the compile context; `CacheKey.hpp` keys it, the
  driver's draw key and `sameVertexInfo` compare it).
- `InstructionTranslator.cpp` (`emitEntryPrologue`): when enabled, the user-data SGPRs named there
  are set from `GetBuiltin(BaseVertex | BaseInstance | DrawIndex)` instead of `GetUserData`, and
  v5/v8 are `VertexIndex - BaseVertex` / `InstanceIndex - BaseInstance` instead of
  `VertexIndex - user(k)`. Every read of a user SGPR goes through the prologue's `SetScalarReg`
  (the only other `GetUserData` is the mesh index buffer), so "shared" uses are covered.
- `StageIO.hpp`, `SpirvEmitterHelpers.cpp`, `SpirvModuleSetup.cpp`, `SpirvModuleEmitter.cpp`,
  `ShaderInfoCollector.cpp`: `BaseVertex` and `DrawIndex` stage inputs beside the existing
  `BaseInstance` (signed 32-bit, `DrawParameters` capability).
- `ShaderInputInfoBuilder.cpp`, `ShaderStageInputInfo.hpp`: carry the field (vertex stage only).
- `Graphics/src/ShaderValidation.cpp`: accept the two built-ins.
- Not done: the debug request serializer does not carry the field (bumping its version breaks
  byte-pinned fixtures in `request_serializer` and `agc_shader_memory`); a dumped request of such
  a stage replays as a plain stage.

Why this is exact: on the hardware v5 is the raw index (index buffer value, or the auto index from
0) and v8 the raw instance; the CP writes the record's base vertex, start instance and draw index
into the SGPRs. Vulkan's `VertexIndex` is the index plus the draw's vertex offset (or first
vertex), `BaseVertex` that offset, `BaseInstance` the first instance, `DrawIndex` the draw's index
in the multi-draw. So the substitution gives the stage exactly the hardware's v5, v8 and SGPRs,
whatever the shader does with them (offset, data, pointer arithmetic, several adds).

### Driver change (commits 599cce948 and 2444149ce, 9 files, +143 −11)

- `IndirectDraw.cpp`: `IndirectDrawParameters` decides before compiling (device has
  `shaderDrawParameters`, plain vertex path, front stage a vertex stage, at least one patched SGPR
  in it, and none of the fallbacks the stage cannot remove: `GE_INDX_OFFSET != 0` on a non-indexed
  draw, count without `drawIndirectCount`, count or draw index with `count > 1` without
  `multiDrawIndirect`, start instance without `drawIndirectFirstInstance`).
  `ClassifyIndirectDraw` with draw parameters: no `draw index`, `patched SGPR not folded` or
  `fetch offset unknown` failures for the SGPRs themselves; a patched dimension is `InPlace`, a
  dimension the CP writes nowhere keeps the folded constant. One rule stays (commit 2444149ce):
  the GPU path fetches attributes with the fixed-function vertex input at `VertexIndex` /
  `InstanceIndex`, so a dimension with attributes at its rate needs the fetch to add the patched
  SGPR itself (k == p, no conflict), else it falls back as before.
- `Draw.cpp`: the decision is made where the patched SGPRs are located; the patched user words
  are zeroed so their stale values neither key nor shape the stage; `decodeVertexInfo` sets the
  field on stage 0; a CPU fallback clears it and folds each record as before.
- `IndirectDrawKey`: a register-keyed draw entry of an indirect draw also mixes the packet fields
  the decision reads (locations, draw-index enable, indexed, `GE_INDX_OFFSET != 0`, count kind,
  `count > 1`, the off switch), since its stage now differs from a direct draw's.
- `Graphics/src/Draw.cpp`: when the graphics side still reads the records on the CPU (records not
  imported, pending image, label or copied write), a stage that reads `DrawIndex` gets the records
  uploaded to a scratch copy and drawn by one multi-draw (a plain draw per record would read
  `DrawIndex` 0); the pass is not continued for it.
- `VulkanDevice`: `DrawIndirectSupport().drawParameters`.
- `APS5_NO_INDIRECT_DRAW_PARAMETERS=1` turns it off (read per draw, used by the test and the
  benchmark). `APS5_TRACE_INDIRECT_DRAWS` prints `-> gpu draw-parameters vertex=... instance=...`.

Reading:

- The GPU-side packet does no capture, decode or recompile, and its cost hardly grows with the
  record count; the CPU path builds a stage and records a draw per record.
- At one record per packet the GPU side is not cheaper: main's GPU indirect path records the
  argument barrier outside the pass and begins a new render pass for every indirect draw (soak:
  44096 passes begun, 0 continued, vs the CPU path's 2595 passes for 163486 continued draws), so
  `Graphics::Draw` is 41-57 µs against 20 µs, and lavapipe then executes one pass per packet
  (profiled soak wall 204-221 µs per GPU-side packet vs 58 µs on the CPU path). Letting a
  GPU-side indirect draw continue the open pass when its records need no barrier (already
  visible, no rewrite) would be the follow-up for one-record packets.
- With the start instance written nowhere, the 64-record GPU-side packet pays 68 µs for main's
  Constant rewrite (a scratch buffer and one `vkCmdUpdateBuffer` per record). With draw
  parameters that dimension could be drawn in place when the stage has no per-instance
  attributes (its value no longer matters), given `drawIndirectFirstInstance`.

## 4. Limits

No longer a reason to fall back (with draw parameters):

- a patched SGPR that the stage also uses for something else (`shared`: copies of v5/v8, data,
  addresses, carries), since every read of it gets the record's value and v5/v8 are the CP's;
- `k != p` when the dimension has no fixed-function attributes (a fetchless or self-fetching
  stage), and `conflict` (two SGPRs added into one index) under the same condition;
- the draw index (`Path::DrawIndex`): `DrawIndex` gives the record's index in one multi-draw.

Still falls back to the CPU path (same reasons and counters as main):

- `NotFolded` / `FetchUnknown` for a dimension **with attributes at its rate** (per-vertex for
  the base vertex, per-instance for the start instance) whose fetch does not add the patched SGPR
  itself, or adds two: the fixed-function fetch reads at `VertexIndex` / `InstanceIndex`, which
  include the record's value. Fixing that needs the fetch moved into the shader (index from v5 +
  the shader's own adds) for such stages, which the recompiler can do for embedded fetches but
  the prototype does not.
- a patched SGPR outside the front stage's user data (`locs ... (s-1)`): the CP writes a register
  another stage reads (main treats that dimension as Constant; unchanged).
- `GE_INDX_OFFSET != 0` on a non-indexed draw (v5 would need `+ GE_INDX_OFFSET`; it could join
  the compile context as a constant).
- `FeatureGap`: count without `drawIndirectCount`; count, or a read draw index, with `count > 1`
  without `multiDrawIndirect`; a patched start instance without `drawIndirectFirstInstance`; a
  dimension the CP writes nowhere (Constant rewrite) with `count > 256` (main's cap; with draw
  parameters that dimension could be drawn in place instead, since the stage no longer depends on
  the draw's offset, but then a garbage record value lands in `VertexIndex`).
- `NonVertexPath` (tessellation, geometry, mesh/NGG, rect list) and `VertexRange`: unchanged.
- a device without `shaderDrawParameters`: everything as on main (the decision is made per device).
- the graphics side's own CPU reads (records not imported, pending image results, pending label
  or copied write): records are read and waited for as before, but drawn with the one stage (no
  per-record stage build); a stage reading `DrawIndex` gets the records uploaded for one
  multi-draw.

Required features: `shaderDrawParameters` (always); `drawIndirectFirstInstance` when the start
instance is patched; `multiDrawIndirect` for more than one record when the stage reads the draw
index (and, as before, for multi-draws without a per-record loop); `drawIndirectCount` for the
count packets.

**Does every supported Vulkan 1.1 GPU have `shaderDrawParameters`? No guarantee.** AnyPS5 requires
Vulkan 1.1 (VulkanDevice.cpp:959/1033). `VK_KHR_shader_draw_parameters` was promoted to 1.1, but
the feature bit (`VkPhysicalDeviceShaderDrawParametersFeatures` /
`VkPhysicalDeviceVulkan11Features::shaderDrawParameters`) was added precisely so an implementation
can report it unsupported, and shaders must not declare the `DrawParameters` capability unless it
is enabled. AnyPS5 already queries it and adds the capability only when present
(VulkanDevice.cpp:1475-1477); lavapipe reports it. I did not verify per-vendor coverage here
(no network survey); the prototype keeps main's behaviour on any device that lacks it, so a
missing bit costs speed, not correctness.

Cost of the prototype's own shape:

- a stage that turns out to fall back after the draw-parameter compile (the fetch rule above, or
  `VertexRange`) is compiled once with draw parameters and then per record as before; the first
  compile is a shader-cache hit on later packets but still a capture and lookup per packet.
- each GPU-side indirect draw begins its own render pass plus an argument barrier (main's GPU
  path does the same); with one record per packet that costs more than the CPU path's draws,
  which continue one pass (section 3).

## 5. What an `APS5_TRACE_INDIRECT_DRAWS` line must show (on main) for this to apply

Main's line: `[draw] indirect <op> args <a> stride <s> count <n>[ (indirect)] locs base=<loc>(s<p>)
inst=<loc>(s<p>) idx=<loc>(s<p>)[ (enabled)] analyzer v=<k> i=<k> shared=<v>/<i> conflict=<v>/<i>
indx=<x> -> cpu (<reason>)`. It applies when all of these hold:

- the reason is `patched SGPR not folded`, `draw index` or `fetch offset unknown` (not
  `non-vertex path`, `GE_INDX_OFFSET`, `feature gap` or `vertex range too large`; main reports the
  first failing reason in that order: non-vertex, draw index, feature gap, per-dimension, range);
- at least one of `base`, `inst`, `idx (enabled)` shows a register in the front stage, `(sN)` with
  N >= 0;
- `indx=0` for the non-indexed opcodes (0x24, 0x2c);
- per patched dimension: `v=N` equal to the `base=...(sN)` register (`shared=1` is fine), or
  `v=-1` with `conflict=0` and a stage without per-vertex attributes (the line does not show
  attributes; with `v=-1` and attributes it stays on the CPU); the same for `i=` against `inst=`
  and per-instance attributes. `v=N` with N different from the base register means the fetch adds
  another SGPR: stays on the CPU.
- `(indirect)` (count packets) only with `drawIndirectCount`; `idx=...(sN) (enabled)` with
  `count > 1` only with `multiDrawIndirect`; `inst=...(sN)` only with
  `drawIndirectFirstInstance` (all three present on desktop drivers and lavapipe).

With the branch the same line ends `-> gpu draw-parameters vertex=in-place|const C
instance=in-place|const C` when it applied, or the remaining CPU reason. Examples from the new
test: switch off `... base=0x8c(s8) inst=0x8d(s9) idx=0x8e(s10) (enabled) analyzer v=-1 i=-1
shared=0/0 conflict=0/0 indx=0 -> cpu (draw index)`; on: `... -> gpu draw-parameters
vertex=in-place instance=in-place`.
