# BF-101: what graphics pipeline libraries hold and keep creating (cloud-3)

Base: upstream main **9be6ccf60** (Merge pull request #8255), fetched 07:35 UTC.

## 1. What the code does (upstream main 9be6ccf60, Merge pull request #8255)

Paths are under `core/libs/prx/libSceAgcDriver/` unless they start with `core/shader/`.

**Is a fast-linked pipeline destroyed once its optimized replacement binds?** No.
- `Pipeline::Continue` binds the optimized handle when the background link has stored one, and the fast link otherwise (`Graphics/src/Pipeline.cpp:755-757`). Nothing destroys the fast link at that point.
- Both handles are destroyed together, only when the `Pipeline` itself is destroyed: `Pipeline::release` calls `OptimizedPipeline::Release` and then `vkDestroyPipeline` on the fast link (`Pipeline.cpp:616-631`, `Graphics/src/PipelineLibrary.cpp:311-314`).
- A `Pipeline` dies when the last `shared_ptr` goes. That happens in one of three ways:
  - the store's LRU evicts an entry nobody else holds (`use_count() == 1`, `Pipeline.cpp:1100-1108`; the bound is 1,024 entries, `APS5_PIPELINE_STORE_ENTRIES`, `Pipeline.cpp:995-998`);
  - `ClearCachedPipelines` runs at device teardown (`Pipeline.cpp:1128-1140`);
  - a recorded draw that holds it (`keepRecordedDraw`, `Graphics/src/Draw.cpp:1651-1654`) completes after its eviction.
- So batches in flight are safe today. The cost is that every live pipeline holds two linked pipelines once its relink finishes.

**Are libraries ever evicted or destroyed before the device is?** No.
- The four library kinds are cached per device in `DeviceLibraries::parts`, keyed by part key and context key (`PipelineLibrary.cpp:40-48, 197-243`). An entry is added at `PipelineLibrary.cpp:243` and never removed.
- `ClearPipelineLibraries` is the only place that destroys them (`PipelineLibrary.cpp:331-344`). It also destroys the library layouts and the kept shader modules, and it runs from `ClearCachedPipelines` at device teardown.
- Evicting a whole pipeline from the 1,024-entry store frees its fast link and optimized link, but never the libraries it was linked from.

**Do libraries keep link-time-optimization info, and for how long is it needed?**
- Every library is created with `VK_PIPELINE_CREATE_LIBRARY_BIT_KHR | VK_PIPELINE_CREATE_RETAIN_LINK_TIME_OPTIMIZATION_INFO_BIT_EXT` (`PipelineLibrary.cpp:198`), whether or not this device will ever link with LTO.
- The info is needed only by a link created with `VK_PIPELINE_CREATE_LINK_TIME_OPTIMIZATION_BIT_EXT`, which is the background relink (`PipelineLibrary.cpp:280-300`, flag at 286).
- That relink exists only when `optimize = backgroundLinking && context.pipelineLinkTimeOptimization` (`PipelineLibrary.cpp:183-184`).
- `context.pipelineLinkTimeOptimization` is `PipelineLinkTimeOptimizationUsable(driverID)` (`Execution/src/VulkanDevice.cpp:1526`). That returns false for `VK_DRIVER_ID_NVIDIA_PROPRIETARY` (`Execution/include/PipelineLinkOptimization.hpp:8-10`).
- So on the PC's NVIDIA driver no relink is ever made, yet every library is still asked to retain its LTO info until the device is destroyed. With `optimize` on (lavapipe, AMD, Intel), the info is needed:
  - once per fast link, until its relink runs;
  - for a journal-replayed pipeline, until its first draw schedules the relink (`PipelineLibrary.cpp:301-306`, `OptimizedPipeline::Schedule`);
  - since libraries are shared, for as long as a future link may name the library.
- With `optimize` on, the library's shader modules are also kept in `DeviceLibraries::modules` until teardown (`PipelineLibrary.cpp:244-252`). Without it they are destroyed after the create (`Pipeline.cpp:571-572, 591-592`).

**What do prebuilds create, for which shaders, and when?**
- `PrebuildStageLibrary` (`Execution/src/Driver/Shaders/ShaderRegistry.cpp:1026-1036`) queues a task on the registration prebuild pool (`SubmitLibraryPrebuild`, `ShaderRegistry.cpp:1373`).
- The task calls `VulkanDevice::PrebuildGraphicsLibraries` (`VulkanDevice.cpp:3835-3871`). That builds a stub state: R8G8B8A8_UNORM color (`:3843`), one sample, a triangle list and a stub partner stage. It then calls `Pipeline::Prebuild` (`Pipeline.cpp:602-610`), which runs the pipeline constructor with `partsOnly` (`Pipeline.cpp:569-574`).
- `LinkPipelineFromLibraries` then builds whichever of the four library parts are missing and returns before linking (`PipelineLibrary.cpp:256`). So a prebuild makes libraries only: no fast-linked, optimized or whole pipeline.
- Each prebuilt library stays in `parts` until the device is destroyed, even when no draw ever uses that key. A draw whose formats, sample count, blend or attachment context differ from the stub misses it and builds its own.
- Prebuilds are triggered in two places:
  - **Registration.** `PrepareRegistered` prebuilds the fragment stage of a shader registered with `registrationModules` (`ShaderRegistry.cpp:1047-1052`). This happens when the title registers the shader, not when it draws.
  - **ABI resolve.** `Driver::ResolveGraphicsStagesAbi` prebuilds each stage that has a registration result (`ShaderRegistry.cpp:1463-1468` collects them, `:1566` submits).
- `APS5_NO_LIBRARY_PREBUILD` turns both off (`ShaderRegistry.cpp:1020`).
- The ~1,400 `shader library prebuild skipped: image table snapshot disagrees with the static tables` lines are prebuilds that are *not* made: `RegistrationResult` throws at `core/shader/recompiler/Optimization/src/ResourceMaterializer.cpp:1635`, and the catch at `ShaderRegistry.cpp:1033/1051/1467` logs it.
- Prebuilds run for every newly registered or newly resolved shader, so they keep running while the title keeps registering or resolving, whether or not it draws them. Nothing repeats a prebuild for a shader that is already registered, so a static scene that registers nothing new makes none.

**Does any key change from frame to frame for the same draw?** Nothing in the driver changes it per frame, but two inputs can.
- The library keys are built in `libraryKeys` (`Pipeline.cpp:207-310`) and combined with the attachment and layout context (`PipelineLibrary.cpp:170-181`). The store key is built in `pipelineKey` (`Pipeline.cpp:830-940`).
- Neither key holds a frame counter, an address or a handle, and the dynamic states (viewport, scissor, depth bias and bounds, stencil masks and reference, cull mode, front face, depth and stencil test and ops; `PipelineLibrary.cpp:20-36`) stay out of both.
- **Blend constants.** They are not a dynamic state.
  - `State.cpp` reads `CB_BLEND_RED..ALPHA` for every color target with blending on (`Graphics/src/State.cpp:1442`, inside `if (state.blendEnable)`), whether or not any blend factor uses a constant (that is tested only afterwards, `:1443-1452`).
  - The constants go into both the fragment-output key (`Pipeline.cpp:276`) and the store key (`Pipeline.cpp:878`).
  - So a title that rewrites those registers (an animated fade, or values left behind by another pass) makes a new fragment-output library and a new pipeline for each distinct value, even for blended draws that never read a constant.
  - The pipelines are evicted past 1,024; the libraries never are. Section 3's churn harness shows this.
- **Program identity.** The shader program's `Identity()` goes into the pre-rasterization and fragment keys. A title or recompiler path that keeps producing new program variants (new code addresses, folded constants) would make new libraries for each.
- Neither changes on lavapipe for the bench, whose frame repeats with the same registers.

## 2. The counter

**Branch:** fork `exp/lane-b-gpl-counter` = **0a59ed820** "feat(agc): count graphics pipelines and libraries by kind", one commit on upstream main 9be6ccf60. Yunus Shaikh is author and committer, with no trailers.

**What it prints.** With `APS5_PROFILE_DRAW` set, one line:

`[pipelines] live (created since the last line): vertex input N (+M), pre-rasterization N (+M), fragment shader N (+M), fragment output N (+M), prebuilt libraries N (+M), fast-linked N (+M), optimized N (+M), whole N (+M), queued: N background links, N prebuilds`

- **The four library kinds** are counted when a library enters `DeviceLibraries::parts`. A library built twice by a race counts once (the one dropped is never counted). They are forgotten in `ClearPipelineLibraries`.
- **Prebuilt libraries** are the libraries among those four that a `partsOnly` prebuild made. Each also counts under its part kind.
- **Fast-linked** pipelines are counted after the link and forgotten in `Pipeline::release` or `Abandon`.
- **Optimized** pipelines are counted when the background relink is created, before its handle is published, so a `Release` that races it never makes the count drop below zero. They are forgotten when `OptimizedPipeline::Release` or the relink destroys the handle, or in `Abandon`.
- **Whole** pipelines are each pipeline made without libraries, including the second-channel and back-face pipelines.
- **Queued background links** is the library store's job queue length.
- **Queued prebuilds** is incremented when `SubmitLibraryPrebuild` queues a task. It is decremented when the task starts, or when the pool drops it unrun: a shared guard object does that, so #8678's drop-on-close is counted right too.
- **When it prints:** at most every 10 s, from `CachedPipeline` and between command buffer packets (`PacketExecution.cpp`, right after `flushBetweenPackets`). The packet hook matters because a draw-recipe hit reuses its pipeline without calling `CachedPipeline`. It prints once more in the device teardown, before `ClearCachedPipelines`.
- **Cost without the switch:** `CountsPipelines()` is a function-local `static const bool` from `getenv`, the same pattern as BF-092's `BufferPool::CountsHost()`. Each counting site and both report sites test only that flag. Compute and utility pipelines aren't counted.
- **Docs:** a `docs/dev/BUILD.md` profile-table row ("live: held when printed; created: since the previous `[pipelines]` line") and a paragraph on the kinds.
- **No new `APS5_*` name and no new ctest executable.** The tests are new modes of `agc_driver_recorder_tests`, which is already in the WIN32 `PATH` list. The three new test names are added to that list too.

**Test:** `agc_driver_recorder_tests --pipeline-counts-only`, registered three ways. Each looks up one pipeline (the TRIANGLE shaders), then checks the counts.

**What to look for on the PC** (Village at the static menu, `APS5_PROFILE_DRAW=1`, GPL on). The line every 10 s tells which kind keeps being created:
- **Fragment output rising each line, with fast-linked and optimized near 1,024 or below:** the fragment-output key is churning. Blend constants are the first suspect (section 1); the libraries pile up because nothing evicts them.
- **Pre-rasterization or fragment shader rising:** new program variants (new identities) at a static scene.
- **Prebuilt libraries rising:** registrations or ABI resolves keep coming. Compare a run with `APS5_NO_LIBRARY_PREBUILD=1`.
- **Every kind flat while memory still grows:** the growth isn't pipeline objects. The fixed GPL cost (retained LTO info, the second link per pipeline) is then a fixed hold, not the growth.
- **With `APS5_NO_GPL=1`**, the `whole` count should stop at 1,024 or less (the store's bound), whatever the title does.

## 4. The open PRs

- **#6743** (JJenkx, draft, d5ec29e08e): first-use preparation, only under `APS5_LAZY_SHADER_PREPARE`. It avoids registration-time prebuilds for shaders that are never drawn. It doesn't free libraries or fast links, and it is off by default.
- **#8678** (CPritch, 8cd100e486): drops library prebuilds still queued when the prebuild pool closes at shutdown. Nothing changes while the title runs.
- **#5925** (adriadam10, head 3339ddd3af on an old base e34c47921):
  - Its journal commits are already on main as #5875 (4aafda8e3; `PipelineJournal`, the deferred relink).
  - Its own commit adds a submission lookahead pool. That pool builds pipelines ahead on background threads, default on, with `APS5_NO_SUBMIT_LOOKAHEAD` to disable it.
  - It creates pipelines earlier and frees nothing.
- **#7985 / #8115** (milescoviello, c46005c996 / 7e5351d579):
  - They add attachment sample counts to linked pipelines, and #8115 adds one-sample color beside multisampled depth (`truncatedCoverage`).
  - They add one key byte to the fragment and store keys and pass the sample counts to the fast and optimized links.
  - They have no memory effect.
- **#8928** (milescoviello, 48549d1a9c): resolves a committed ABI without the preparation lock. No effect on pipelines.
- **#7644** (ours, 1ba22061e3): under `APS5_LAZY_SHADER_PREPARE`, it leaves a resolved ABI's preparation, and so its library prebuild, to the shader's first use. That avoids prebuilds for resolved ABIs that are never drawn, in lazy mode only.

## 5. No fix

The bench (steps 2 and 3) shows nothing growing, so there is no cause it can show and no fix to red/green against it. Following the task, I stopped after step 4. The counter is the deliverable, for the PC to boot.

Section 1 and the churn harness do show where GPL is unbounded or holds more than it needs. These are the cuts I would make once the PC's lines say which one Village hits:
- **If fragment output (or another library kind) keeps climbing,** evict libraries that no live pipeline and no pending relink use.
  - Library handles would need a reference count from the fast link, the optimized slot and the relink lambda.
  - A pipeline is destroyed only when its last `shared_ptr` goes, including the recorded draws that hold it until their fence, so in-flight batches stay safe.
  - Prebuilt libraries would need an age or count bound instead, since no pipeline holds them by design.
  - If blend constants are what changes, a narrower cut is to key `state.blendConstants` only when an enabled blend factor uses a constant (zero them otherwise in `State.cpp` near `:1442`). Rendering doesn't change, because Vulkan ignores constants no factor reads.
- **If the counts are flat but the NVIDIA arena is large,** create libraries with `VK_PIPELINE_CREATE_RETAIN_LINK_TIME_OPTIMIZATION_INFO_BIT_EXT` only when `optimize` is true (`PipelineLibrary.cpp:198`), and add `optimize` to the library context key. Then a library made without the info is never named by an LTO link, for example by a test context that forces `pipelineLinkTimeOptimization`. On NVIDIA no LTO link is ever made (`PipelineLinkOptimization.hpp:8-10`), so the retained info is pure cost there.
- **On LTO drivers (not the PC's),** destroy a pipeline's fast link once the optimized link has been bound and every batch that bound the fast link has completed. Today each live pipeline holds both until it dies.

None of the seven PRs does any of these.

RESULT:
- **Step 1, on main 9be6ccf60** (`Graphics/src/...` under `core/libs/prx/libSceAgcDriver/`):
  - **Fast link after the optimized link binds:** not destroyed. `Pipeline::Continue` binds the optimized handle once it exists (`Pipeline.cpp:755-757`). The fast link and the optimized link die together in `Pipeline::release` (`Pipeline.cpp:616-631`), when the last `shared_ptr` goes: on store LRU eviction past 1,024 entries (`Pipeline.cpp:996, 1100-1108`), at `ClearCachedPipelines` (`:1128-1140`), or when a recorded draw that holds it completes.
