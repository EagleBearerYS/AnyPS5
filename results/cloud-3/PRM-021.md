## Step 5: #1747's ahead-of-run dispatch capture against #6454, #6475 and #6243

Line numbers are those of the merges. #6454, #6475 and #6243 all leave main's Dispatch.cpp lines below unchanged. None of the three touches DispatchAhead.cpp, DispatchLookup.cpp, PacketExecution.cpp, DrawPipeline.cpp or WrittenBuffers.cpp.

### What #1747 changes, and when

Everything new in #1747 is behind `APS5_PIPELINE_DISPATCH` (Dispatch.cpp:22-28 `DispatchItemsEnabled`), which is off by default. Its only test, `agc_driver_pipelined_dispatch_item`, sets the switch.

With the switch off, queue 0 behaves as before: `pipelineCandidate` is false, so `dispatch` drains the draw pipeline before the lookup (Dispatch.cpp:131).

With the switch on, a queue-0 dispatch is a candidate (Dispatch.cpp:118) when all of these hold:
- it is not resolving ahead, adopted from an ahead run, indirect, or an HLE copy kernel;
- no deferred labels are pending.

The candidate path runs in this order:

1. **The guard, taken before the cache lookup** (Dispatch.cpp:271-290). The guard is computed before any lookup or capture. It holds only if:
   - the dispatch-cache entry already exists;
   - stamp validation and data-hit verification are off;
   - no region of any variant of that entry (`appendEntryRegions` over `variant.runs`, :278) overlaps a write range queued in the draw pipeline (`DrawPipeline::Queue0().Overlaps`, :286).

   If the guard fails, the pipeline is drained (:289).
2. **The lookup** (`lookupDispatch`, :309) validates the cached variant against live memory while the pipeline may still be busy. The guard makes that safe only because the regions it checked are the ones the validation reads.
3. **Back to a plain dispatch** (:314-323). The lookup may miss, the hit may have no recipe, or the shader may write through a page table, GDS or fault buffer (`DispatchWriteRanges`, WrittenBuffers.cpp:53-75, sets `bounded` false). In each case the pipeline is drained (:323) before the miss path captures (:329-342). So every capture still runs on an empty pipeline.
4. **Otherwise the dispatch becomes a pipeline item** (:442-496). It carries:
   - the compiled result;
   - the `snapshots` built from the lookup's regions (:406);
   - its write ranges (`Enqueue(..., std::move(itemWrites))`, :447, :495).

   The item records later on the committer thread, through the recipe (:468) or, when the recipe misses or asks for a rebuild, through `PrepareDispatch`/`Dispatch` over `snapshots` (:458, :476).

`resolveGroupAhead` (DispatchAhead.cpp:105) returns at once for queue 0 unless `APS5_GROUP_CAPTURE_ALL_QUEUES` is set (:106-107). #1747 only adds a second skip, for queue 0 under `APS5_PIPELINE_DISPATCH` (PacketExecution.cpp:317-320). On the other queues it still resolves a group ahead as before: it refuses a later dispatch whose captured regions overlap an earlier one's writes or labels (DispatchAhead.cpp:167-177), and adopts the parked result (Dispatch.cpp:93-100, :291-307).

### #6454 (image tables shared through capture, compare and descriptors; vouched validation)

The assumption holds. Every whole-span check #6454 adds goes through `Driver::QueryPendingSpan` (WriteEvidence.cpp:218-228). When the pipeline is busy and overlaps the span, it answers `Sync` (:221). That pipeline is the one #1747 enqueues dispatch items into, with their write ranges (Dispatch.cpp:447-495 → DrawPipeline Enqueue/Overlaps). So a queued dispatch's writes refuse a vouch the same way a queued draw's do.

Each check, in the order it happens:

- **Stamp before the pending query.** `ShaderMemory::stampWrites` (ShaderMemory.cpp:395-406) flushes GPU writes, collects the write generation, and only then asks `pendingSpan` (:404). A write that starts after the stamp is caught by `UnchangedSince` later.
- **Vouch re-asks the pending query every time.** `ShaderMemory::Vouched` (:408-414) queries pending writes on each call (:411) before `UnchangedSince` (:414). `VouchSharedRegions` (:740) calls `Vouched` for every block on every validation, and `validateVariant` passes `&QueryPendingSpan` to it (VariantValidation.cpp:103). Nothing memoizes a vouch past the pending query.
- **The guard covers the vouched words.** #6454 leaves `appendEntryRegions` as main has it (VariantValidation.cpp:12-21), and `variant.runs` still lists every captured word, shared table columns included. So #1747's guard (Dispatch.cpp:278, :286) checks exactly the words the vouch would skip.
- **Per-record fallbacks drain where main drains.** They go through `queryPendingWrite`, which drains on a pipeline overlap (WriteEvidence.cpp:207-215).
- **Write ranges are complete.** #6454 does not change how `guestDescriptor` is filled, so `DispatchWriteRanges` still sees every written storage image. Image tables cannot be stored through on main (docs/dev/debt/shader.md:38: such stores fault and are dropped), so leaving `ImageTable` out of the write ranges loses nothing.

### #6475 (read guard over a capture's lazy pages and raw word reads)

The assumption holds. #6475 runs `GuardRead` where a capture first touches a page (ShaderMemory.cpp:192), and before a raw word read (:253).

- **Captures run on an empty pipeline.** Under #1747 a capture happens only on the miss path, after a drain (Dispatch.cpp:289 or :323, then :329-342). The guard therefore sees every target that queued draws register. Queued dispatch items are recorded only on a recipe hit and never capture.
- **The raw path decides after any overlapping item has drained.** The raw-word decision comes from `queryPendingWrite`, which drains the pipeline on an overlap first (WriteEvidence.cpp:207-215).
- **Ahead runs are unchanged.** Ahead runs on the other queues capture in `dispatch(scratch, …)` (DispatchAhead.cpp:160), so the guard runs at resolve time on the worker, as before #1747.

#6475's stated limit (a later block copy of an already-touched page is not checked again) is unchanged by #1747.

### #6243 (T# record selection at capture)

The assumption holds.

- **Selection only happens on an empty pipeline.** The record is selected during the capture's materialization, so on the miss path after the drain (Dispatch.cpp:323 → :339-353).
- **The key and the selected record are validated words.** Both are captured regions (#6243's own test: ShaderMemory.cpp test "image table SRT key", `TableCovered(compiled.regions, &guest.srt[16], …)` and `&heap[2]`). They are therefore in `variant.runs`, validated on a hit, and covered by #1747's guard.
- **A changed key misses rather than reusing the old record.** The SRT evaluator records the key read as an `otherReads` address, because it is not the flat leaf (SrtEvaluator.cpp:249-250). `DataWordPositions` then treats a leaf at that address as aliased, not as a data word. A changed key gives a miss and a new selection, never a data hit that patches the key and keeps the old record.
- **Direct-bound T# writes are covered.** A T# that #6243 binds directly because the table cannot express its operation (stores, atomics) is a `GuestImages` binding. `DispatchWriteRanges` covers it from the selected record's words (WrittenBuffers.cpp:58-72).

### Found on main while reading (not one of our PRs): a pipelined data hit's snapshots outlive their words

Under `APS5_PIPELINE_DISPATCH=1`, an item whose lookup was a data hit keeps snapshots that point into `dispatch`'s local `liveWords` (Dispatch.cpp:222), which is freed when `dispatch` returns.

1. On a data hit, `lookupDispatch` copies the variant's words into the caller's `liveWords`, patches the data words, and builds the regions over that buffer (DispatchLookup.cpp:122-125). `captured` takes those regions (:137).
2. `dispatch` builds `snapshots` as spans over `captured` (Dispatch.cpp:406).
3. The item's closure captures `snapshots` but not `liveWords` (:447), and `dispatch` returns right after enqueuing it.
4. When the item runs, it reads `snapshots` whenever `PrepareRecipe` misses (template or objects gone, device changed: VulkanDevice.cpp:4151-4168), when `DispatchRecipe` asks for a rebuild (:458 after `continue`), when it falls back to `Dispatch` (:476), or when `APS5_VERIFY_RECIPES` is set.

Data hits are on by default (DispatchCache.cpp:12-15). Non-data hits are safe: their regions point into `variant->words`, which the captured `keepVariant` keeps alive.

Proposed fix (one line): add `liveWords = std::move(liveWords)` to the closure's capture list at Dispatch.cpp:447. Moving a vector keeps its buffer, so the spans stay valid.
