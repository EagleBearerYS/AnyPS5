## Change 1: separate cleared stencil plane (7d6e968d6)

The Grinch's target is a two-sample D32S8. Its stencil is a plane of its own (`stencilAddress` set), and its HTILE is depth-only: `DB_STENCIL_INFO.TILE_STENCIL_DISABLE` gives `htileDepthOnly` 1, so `htileStencil` is 0.

**What changed in `prepareDepthSampling`:**
- A new case, `stencilPlane = D32S8 && !htileStencil && htileDepthOnly`, is accepted.
- The depth keeps its HTILE clear proof. The per-word HTILE stencil proof is skipped for this case.
- Instead, the plane is read once (`GuestMemory::Read`) and every byte must equal `DB_STENCIL_CLEAR`. Otherwise the import refuses "native multisample stencil plane does not hold its clear value".
- The scan happens after the ranges' generations are taken and before the final `UnchangedSinceAll`, so a racing write still refuses.

**The stencil range** was already one of the import's ranges (#6300's `state.initial[2]`): accessible, watched, generation-checked, guarded against guest publication and checked for overlap. A later CPU or GPU write to it refuses sampling, and the test checks this.

**The host image** is created cleared to `{clearDepth, clearStencil}` with the stencil aspect, as for #6300's targets.

**Whole-HTILE fill.** A depth-only HTILE fill now proves and clears **only the depth**: `clearAspects` takes the stencil bit only when `htileStencil` is set. Before this change:
- a clear-1.0 depth-only fill refused, because its 0xfffffff0 words don't prove SMem 0;
- a clear-0 fill reset the host stencil to `DB_STENCIL_CLEAR` while the guest plane was unchanged.

**Refusals kept, each with its own text:**
- a stencil plane that isn't all clear (the new text above);
- a stencil in neither HTILE nor its own plane ("requires HTILE stencil metadata", still checked by CheckEligibility case 11);
- D16S8 ("stencil or depth format import is not implemented");
- HTILE words that don't prove a clear;
- an unaligned stencil base;
- an HTILE mask clear of a stencil surface.

**Stencil plane alignment.** The plane needs 64 KiB alignment, the same as the depth plane:
- both planes use SW_64KB_Z_X (`depthSwizzle` 24);
- `State.cpp` takes the pipe/bank XOR from the depth base's low 16 bits and masks both the depth and stencil bases to 64 KiB;
- #6300's `(stencilAddress & 65535) != 0` refusal is kept for this case too.

The Grinch's sizes agree with the driver's footprints: `MultisampledDepthBytes(2560x1440, 4, 2)` = 0x1e00000, `MultisampledDepthBytes(2560x1440, 1, 2)` = 0x780000 (the stencil plane BunnyFl printed), and `HtileMetadataBytes` = 0x48000.

## Change 2: sampling without HTILE (5be005ea1)

**What changed in `CheckResource`.** It now accepts either of two descriptors when address, format, pipe/bank XOR and ITERATE_256 match and `dccAlphaOnMsb` is clear:
- one whose metadata is the target's HTILE (`dccAddress == htileAddress`, pipe alignment equal), as before;
- one with **no metadata at all** (`dccAddress == 0`, not pipe-aligned).

A descriptor with any other metadata keeps refusing "native multisample depth sampled metadata or XOR mismatch".

**The sampling assumption** (also in the commit message and the debt entry):
- The host image holds the decompressed depth. On hardware, a no-metadata read returns the decompressed depth only once the guest has expanded the plane, with an in-place expand that disables compression.
- Main draws an in-place expand as an ordinary draw that writes the depth attachment: DB_RENDER_CONTROL's compress-disable bits aren't refused (`State.cpp:385` counts them as a depth write). The host image under it already holds decompressed depth. The out-of-place DB expand (#6146) covers single-sample planes only and is not on main.
- So nothing here observes whether the guest expanded first. A title that samples the plane unexpanded gets the decompressed values instead of raw plane bytes.

## Tests (`tests/execution/NativeMultisampleDepth.cpp`, mode `--separate-stencil`, ctest `agc_driver_native_depth_separate_stencil`)

The new test is added to the TIMEOUT/ENVIRONMENT/SKIP_RETURN_CODE list and to the WIN32 `PATH` list.

`CheckSeparateStencilTarget(samples, clear 0/1, fill, fault)`:
- **The target:** D32S8, a separate plane filled with `DB_STENCIL_CLEAR` (0 for clear 0, as in The Grinch; 0x5a for clear 1), and a depth-only HTILE of clear words.
- **(1), in commit 1:**
  - imports, then samples the clear depth;
  - stencil-tests the clear stencil, with a miss for clear+1 and a hit for clear;
  - with fill: REPLACEs the stencil with 0xc3, then does a whole depth-only HTILE fill. The depth returns to clear and the stencil keeps 0xc3 (an EQUAL 0xc3 hit and an EQUAL clear miss);
  - the guest stencil plane is left unchanged.
- **(1b), in commit 1:** one stencil byte not clear → "native multisample stencil plane does not hold its clear value". Also a later CPU stencil write → "guest writes over native multisample depth", and an unwatched plane → "watched accessible guest memory".
- **(2), in commit 2:** the same target is sampled through a descriptor with no metadata:
  - word 6 without META_DATA_ADDRESS, META_PIPE_ALIGNED and COMPRESSION_EN, and word 7 = 0;
  - it gets its own reused view;
  - it reads the depth before and after the raster writes and after the depth-only fill.
- **(2b), in commit 2:** the same descriptor with another XOR refuses "…metadata or XOR mismatch". One naming other metadata (metadata address + 64 KiB) refuses the same.

lavapipe has D32S8 MSAA at four samples only, so each run checks 4 cases at four samples. The 8 two- and eight-sample cases are reported unavailable: "cases checked=4 unavailable=8". The two-sample loop runs where the device supports it.
