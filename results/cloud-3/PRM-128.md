## 3. Semantic read (report only)

### (a) Can a constant (embedded) sampler be a device-path sampler, and does the device path sample with the right words?

**Yes, a constant sampler can be a device-path sampler.**
- `collectConstantSampler` marks a sampler constant whenever `table == NoTable` and its four source dwords are immediates (`ShaderInfoCollector.cpp:587-600`).
- Device-path samplers are always `NoTable`, because `EmitDeviceTableAccess` refuses table samplers (`SpirvImageEmitter.cpp:2371`). Nothing excludes a sampler paired with a `deviceTable` image.

**Within one stage, the words are right:**
- **The lookup key carries no sampler words.** The device table lookup keys on the descriptor words, the interface id and the sampler *class* only: `DeviceSamplerClassBase + memory.sampler` at `SpirvImageEmitter.cpp:2384`, with the key's sampler words fixed at 0 at `:2468`.
- **How the sample loads its sampler:** through `MakeSampledImage` → `LoadSamplerDescriptor` (`SpirvDescriptors.cpp:305-314`, `:261-303`).
  - The device image's mode has `table != NoTable`, so `point = TablePointSampled(mode)` (`:264`) and the element is `ResourceForDescriptor + point` (`:279`).
  - For a constant sampler in heap mode it loads the embedded variable at set 6, binding = that element (`:282-290`), instead of the heap slot word.
- **The planner gives both elements their words.**
  - A table-image pair sets `samplerModes |= 3` (`DescriptorBindingBuilder.cpp:537`), so both the normal and the point element are active (`:590`).
  - Each element gets `samplerEmbedded = originals[element]` (`:656`) and its own four words (`:657-660`).
  - The point element is point-filtered unless `tablePointOnly && ReducesBetweenTexels`. That is the same rule the heap path applies through `samplerFilterElements` (`:653`).
- **The heap mapping matches.** It maps set 6, binding `samplerEmbedded[element]` to a sampler built from exactly those words and that element's compare, unnormalized, integer-border and coordinates-ignored flags (`BindlessHeap.cpp:1110-1149`, `:1177-1190`).
- **The class and the embedded words agree.** The device sampler class loop (`DescriptorBindingBuilder.cpp:540-549`) reads the snapshot words. For a constant sampler these are the same immediates: the snapshot evaluates the same descriptor source (`ResourceMaterializer.cpp:1623-1633`), and samplers get no GCN word conversion.

**Across stages, the device path can sample with another stage's words.** That is a #9508 bug and the reason for the stop:
- **Where the embedded samplers live:** they are baked into the compute pipeline's descriptor heap mappings when the pipeline is created (`VulkanDevice.cpp:6041`, which passes `&shader.bindings`).
- **The cache key:** compute pipelines are cached by `ComputePipelineKey{shader.Identity(), pushConstants}` (`VulkanDevice.cpp:445-450`). `computePipeline` returns the cached entry for an equal key (`:6083-6094`).
- **What the identity hashes:** `RecompileResult::Identity()` (`Recompiler.hpp:875-891`) hashes the SPIR-V, the specialization constants, the subgroup and LDS flags, and each binding's set, binding, kind and count. It does **not** hash `samplerEmbedded`, `samplerEmbeddedWords` or the sampler flag vectors.
- **The words aren't in the SPIR-V or the specialization either.** The embedded variable carries only `DescriptorSet 6` and `Binding n` (`SpirvDescriptors.cpp:282-290`).
- **The result:** two stages whose code differs only in a constant sampler's immediates get one pipeline, and the second samples with the first stage's sampler. §3e shows this.
- **Graphics pipelines are not affected.** They key on per-result variant ids (`VulkanDevice.cpp:5500`, `:6166`; `HeapStages.cpp:47`).
- **The pipeline journal names stages by the same identity** (`PipelineJournal.cpp:824`, `:944`, `:1446`), so a replay can prebuild one stage's pipeline under the other's identity.

## 4. Smallest fix (not written)

**Change:** in `RecompileResult::Identity()` (`Recompiler.hpp:875-891`), inside the bindings loop, mix the embedded sampler state for every element whose `samplerEmbedded` isn't `NoEmbeddedSampler`:
- its binding number;
- its four `samplerEmbeddedWords`;

That is the same 5-word key `BindlessHeap.cpp:1111-1118` builds, and it takes about four lines.

**Why `Identity()` and not the pipeline key:**
- Mixing only embedded elements leaves every non-embedding stage's identity, and its journal entries, unchanged.
- Fixing `Identity()` covers both the compute pipeline cache and the pipeline journal. Fixing `ComputePipelineKey` alone would leave the journal colliding.

**Red test:** a recompiler-only check like §3e, which compiles the border and wrap variants of `ConstantSamplerCode` under a `gpuResolvedImages` target and requires different `Identity()`. It fails on 73c5187825 and passes with the fix, without needing a heap device. On a heap device, `HeapEmbeddedSampler.cpp` could also dispatch both and require the wrap stage to read `SampleTexel`.

**Where it belongs:** the bug is in #9508's 73c5187825 alone, so the fix belongs on #9508. This merge needs no change of its own.
