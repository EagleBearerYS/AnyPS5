## 1. Why the pipelined item never reads the dangling words

PRM-021's reading of the structure is right. On a data hit, `lookupDispatch` copies the variant's words into the caller's `liveWords` and builds the regions over it (DispatchLookup.cpp:122-125). `captured` takes them (:137), `snapshots` span `captured` (Dispatch.cpp:405-406), and the closure at Dispatch.cpp:447 keeps `snapshots` but not `liveWords` (Dispatch.cpp:222), so the spans dangle once `dispatch` returns (:496-497).

The bytes are never read, though:
1. A dispatch is pipelined only when its variant already has a recipe (Dispatch.cpp:315).
2. A recipe is built only over a reusable template (VulkanDevice.cpp:4850: `cacheable && resources->Reusable() && ...`), and `DispatchRecipe` throws on a non-reusable one (:4885).
3. `ShaderResources::noteReusable` leaves `reusable = false` for any program with a BDA binding (ShaderResources.cpp:2081, `|| usesBda ||`).
4. The only code that dereferences a `GuestMemorySnapshot`'s bytes on the dispatch side is `GuestBufferMemory::AddSnapshot` (its `memcmp` at GuestBufferMemory.cpp:3150, or the copy at :3172). It is called only from `prepareAddressBindings` (ShaderAddressResources.cpp:34), under `if (usesBda)` (:29). Every other consumer (`ShaderResources`' constructors, `PrepareDispatch` at VulkanDevice.cpp:4201, `dispatch` at :4750) passes the spans on to `prepareAddressBindings` or stores the span.
5. `usesBda` comes from the program's bindings, which are fixed per variant, and the data hit's `patchDataWords` copy keeps them. So a variant that can be pipelined never builds address bindings, and its item never reads a snapshot's bytes.

That holds on every path the reading listed: a recipe miss (template or objects gone, device changed), a `DispatchRecipe` rebuild, the fall-back to `Dispatch`, and `APS5_VERIFY_RECIPE`. Note the switch is spelled `APS5_VERIFY_RECIPE` in the code, not `APS5_VERIFY_RECIPES`. On its own the verify switch does not even rebuild resources: with template data refresh on (the default), `DispatchContentKey` leaves the data words out of the key, so the data hit finds the template in the resource cache.

Evidence, from a draft of the test under ASan with `APS5_PIPELINE_DISPATCH=1`:
- The draft queued a data hit behind a gate item (`drains=0`, three queued items: the gate, the data hit, the submission's completion), so `dispatch` had returned.
- It cleared `SharedResourceCache()` while the item waited, then released the gate.
- Temporary local prints (never committed) showed the item with `dataHit=1 recipe=1 recipeHit=0` and `PrepareDispatch cached=0 snapshots=3`. The item therefore built a fresh `ShaderResources` from the three snapshots. ASan reported nothing.
- An address-based variant of the shader (a GLOBAL store, then a GLOBAL load with a MUBUF store) never pipelined. It drained every time, `prepareAddressBindings usesBda=1`, and never got a recipe.

## 2. The reachable path: dispatches resolved ahead

`execute` sets `gateOpened()` at the start of every submission (PacketExecution.cpp:159). At the first dispatch it then calls `resolveGroupAhead` whenever `!pipelineDispatch() || submission.queue != 0` (:316-319). `resolveGroupAhead` returns early only for queue 0 without `APS5_GROUP_CAPTURE_ALL_QUEUES` (DispatchAhead.cpp:107). So by default every compute-queue submission resolves its dispatches ahead.

Resolving runs `dispatch` with `resolving` set. On a data hit it parks the result:
- `parked.captured = captured;` and `parked.liveWords = liveWords;` (Dispatch.cpp:386-387) are copies. The copied regions still point into the local `liveWords`, which is freed at the `return` (:395).
- The real dispatch adopts the parked entry: `captured = std::move(ahead.captured); liveWords = std::move(ahead.liveWords);` (:296-297). Its regions now point into memory that is already freed, not into its own `liveWords`.
- An adopted dispatch is always synchronous (`pipelineCandidate` requires `!fromAhead`, :118). It builds `snapshots` from `captured` (:405-406). For an address-based program the resources are never reusable, so every dispatch builds them: `PrepareDispatch` / `dispatch` → `ShaderResources::Complete` → `prepareAddressBindings` → `AddSnapshot`, whose `memcmp` reads the freed words.

### The test

`DispatchDataHitWords` registers one address-based compute shader:
- `s_load_dword s8` of a constant;
- a `global_load_dword v3` through `s[2:3]` from a zero block;
- `v2 = s8 + 1 + v3`;
- `buffer_store_dword` through `s[4:7]`.

It submits it five times on ACB queue 0x20 (`sceAgcDriverSubmitAcb`), changing the constant every round. The first round misses and inserts; the next four are data hits, each resolved ahead and adopted. It checks every lane is `constant + 1`.

Temporary local prints (never committed) confirmed this on the fixed tree: 4 × "data hit resolving=1" from `lookupDispatch`, then 4 × "adopted dataHit=1" and 1 × "adopted dataHit=0" (the first round's miss) at the adoption.
- No switch is needed. The default ctest entry (`agc_driver_dispatch_data_hit_words`, `ANYPS5_NO_SHADER_CACHE=1`) runs it, and it behaves the same with `APS5_PIPELINE_DISPATCH=1`, since queue 0x20 always resolves ahead.
- The output check polls (with `FlushGpuWrites`) until the lanes change, then compares.

## 4. Fix and green

Commit **ada526a206**, `fix(agc): keep a data hit's live words with the regions that span them`, on 4524944396. It touches `Dispatch.cpp` (3 lines) and adds the test:

```
-        parked.captured = captured;
-        parked.liveWords = liveWords;
+        parked.captured = std::move(captured);
+        parked.liveWords = std::move(liveWords);
...
-        DrawPipeline::Queue0().Enqueue([this, localDevice = std::move(localDevice), result = compiledResult, snapshots = std::move(snapshots), groups, ...
+        DrawPipeline::Queue0().Enqueue([this, localDevice = std::move(localDevice), result = compiledResult, snapshots = std::move(snapshots), liveWords = std::move(liveWords), groups, ...
```

Why the moves are enough:
- A moved vector keeps its buffer, and the buffer now travels with the regions: local → `parked` (a node of a `std::map`) → `ahead` (Dispatch.cpp:95, moved) → the adopting dispatch's locals (:296-297).
- Both moves happen right before a `return`, and nothing reads `captured` or `liveWords` after them.
- Nothing else copies a `ResolvedDispatch`. `resolveGroupAhead` reads `found->second.captured` only for addresses and sizes (`OverlapsLabel`, `OverlapsRange`), and so does `IndirectDispatch.cpp:40`.
- For the item: `DrawPipeline::Enqueue` moves the callable into `items` and `run()` invokes it in place, so the item's `liveWords` buffer is the one its `snapshots` span.

The pipelined half cannot be shown red (section 1). It costs nothing, and it removes the trap if address-based programs ever get recipes.

Green, same test, on the fixed tree:
- ASan (`build-asan`): **10/10 passed**, no AddressSanitizer report, no "guest snapshot differs".
- Plain (`build`): **10/10 passed**, no "guest snapshot differs".
- Output: "dispatch data hit words: 4 data hits resolved ahead read their own live words".
