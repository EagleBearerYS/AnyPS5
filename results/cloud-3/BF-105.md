**`Graphics/src/GuestBufferMemory.cpp` / `.hpp`: the proof says which check failed.**
- `SameSnapshots` is now `SnapshotDifference(snapshots) == SnapshotMismatch::None`. Its checks and their order are those of fc9c5416f:

  2. **address**, then **size**: the first index whose address or size differs from the build's `snapshotUses`;

## 2. The lines

**Every 10 s (only in a window with proofs):**
```
[snapshots] (10 s) <P> proofs checked their snapshots, <R> refused; by the first failing check: count <n>, address <n>, size <n>, live bytes <n>, copied bytes <n>, region lookup <n>; snapshots per proof: 0-1 <n> 2-2 <n> 3-4 <n> 5-8 <n> 9-16 <n> 17-32 <n> 33-64 <n> 65-128 <n> 129+ <n>; bytes per snapshot: <=16 <n> <=64 <n> <=256 <n> <=1024 <n> <=4096 <n> <=16384 <n> <=65536 <n> <=262144 <n> >262144 <n>
```
- P is the proofs that reached the snapshot check, so it excludes "in use" and "not reusable".
- The histograms count over those P proofs: each proof's snapshot count, and the size of every snapshot it carried.

**For the first 16 refusals of a window:**
```
[snapshots] refusal <k> of the first 16 in this window: <reason> at snapshot <index> of <old count> old / <new count> new; old <addr>+<size> (read live|copied); new <addr>+<size>, address delta <±hex>, size delta <±dec>; from <source>, <stage> stage|no stage; <reference>; <allocation>; <how the build serves it>[; first difference at +<off>, <n> of <size> bytes differ; <old side>[+<window>]: <16 bytes>; <new side>[+<window>]: <16 bytes>]; draw stages: <stage> variant 0x<id> ...
```

The fields:
- **Old and new:**
  - "old" is the build's use, read live or from its copy;
  - "new" is this draw's snapshot;
  - a count refusal names the first index whose address or size differs ("the first snapshot that differs in address or size") and gives whichever side has that index.
- **The reference** comes from a scan, in 4-byte steps, of the draw's other snapshots for a word that points at this snapshot's address. It prints one of:
  - "a 64-bit pointer to it is at snapshot <j> +0x<off> (a pointer or descriptor table)";
  - "a V# base names it at snapshot <j> +0x<off> (a data range a buffer descriptor reads)", for a 48-bit match;
  - "no other snapshot of the draw points at it (the user data or the SRT names it)".

  That tells an SRT or a top table from a nested table or a buffer.
- **The allocation:**
  - "in registered guest allocation <base>+<size> (writable|read-only)", or "not in a registered guest allocation";
  - from `GuestAllocationsLookup_nid_postfix`.
- **How the build serves it:**
  - "the build serves it from <region kind> <base>+<size>", for live, copied, imported or mirrored regions;
  - or, for a build holding an address space, "the build reads it through its address space (an import or a mirror), not a region of its own".
- **The byte windows (bytes reasons only):**
  - copied bytes: `build` vs `this draw`;
  - live bytes: `memory now` vs `captured`;
  - each window is the 16-byte-aligned 16 bytes holding the first difference, cut at the snapshot's end.

## 6. Step 7: which captures add snapshots, and which can differ on a static scene

A draw's snapshot list is its `memory` regions, sorted by address then size (`Draw.cpp:499-503`). It holds four kinds:

1. **The programs' code and headers** (`AppendProgramMemory`). This kind is static unless the game rewrites shaders.
2. **The stage resource capture** (`CaptureInvocation` through `ShaderMemory`; `memory = shaderMemory.Regions()` at `DrawCapture.cpp:66`). It covers:
   - every range the SRT walk read: the SRT and tables the user data points at, nested pointer tables;
   - T#, V# and S# words;
   - scalar loads the recompiler folds.

   This is where per-frame data lives.
3. **A draw-cache stage hit's words** (`appendEntryRegions` over the variant's runs, with the words captured at insert or, for a data hit, the live words). These are the same ranges as 2. They are split at relocatable words when draw relocation applies (`DrawRelocate.cpp:96-108`), and the hit adds its vertex decode reads to the runs (`DrawCapture.cpp:174-175`).
4. **The vertex decode reads** (`DecodeVertexStageInfo`): V# and fetch-shader words, appended at `Draw.cpp:439-441` on both paths.

Constant buffers that a shader reads through the BDA table are not snapshots.

**The point the PC's lines should be read against: the cache holds one build per key.** The resource cache keeps one build per content key, and every new build replaces it:
- `ResourceCache::Insert` erases the old entry (`ShaderResources.cpp:3864-3873`), and `Draw.cpp:2466` inserts every reusable recorded build.
- The key is the device, the stages' compiled content (`AppendContentKey` with movable buffers) and the attachment count. With the default trim it leaves out the target and index ranges (`Draw.cpp:780-803`).
- Draws that share shaders and binding layout but read different data therefore share one key.
- A key's build is refused "in use" until its draw completes (`Draw.cpp:1455-1456`). Each such draw builds its own and inserts it.

So with N same-key draws per frame:
- the cache ends the frame holding the **last** one's build;
- the next frame's first same-key draw proves against it, and that is a different draw unless all N read the same data.

The boot's ~12 "in use" refusals per proof (887 vs 75) fit many same-key draws per frame. That kind of refusal happens however static the scene is.

**Readings for each reason the PC may print:**

| what the lines show | what it means | next step |
|---|---|---|
| **address**, small deltas (tens of bytes to a few KiB) that vary from line to line, at a stage-capture snapshot that another snapshot points at, or that the user data or the SRT names, with ~12 "in use" per proof | sibling draws of one key whose per-draw constant or descriptor blocks sit at different places in the frame's command or constant memory | keep a few builds per key, chosen by snapshot addresses, instead of one; or include the user-data pointers in the key |
| **address**, one large delta repeating window to window, or 2–3 deltas that alternate (a double or triple buffer), at the same snapshot index | a per-frame ring of descriptor tables or SRTs | the proof could compare by content and re-point, which is a much larger change |
| **copied** or **live bytes**, same address, few bytes differing at the same offset in every line (a float that steps, a counter) | per-frame constants rewritten in place: time, frame counters, TAA jitter, a pulsing UI colour | address reuse can't help that draw; look at the snapshot cost instead |
| bytes differing in a 64-bit pointer or V# base word | the tables are rewritten in place each frame with new ring pointers | as for a ring |
| **live bytes** in general | memory changed between this draw's capture and its `Revalidate`: the CPU writing the next frame's data, or GPU writes the capture didn't wait for | — |
| **count** or **size** that repeats | the capture shape changes between draws of one key. The two paths differ: a compiled draw's list is `ShaderMemory::Regions()` plus its decode reads, while a hit's is runs that already include the decode reads (`DrawCapture.cpp:174-175`) plus the decode reads again (`Draw.cpp:439-441`), and relocation splits regions. Each refusal rebuilds and re-inserts, so this should be one refusal per path switch | if it repeats every frame, it is a capture bug |
| **region lookup** | the build's own copy can't be found for a snapshot the build copied | a bug in #6636's region bookkeeping |
