## 0. Bottom line

**Most likely (A): a DCC fast clear the driver does not note is lost for sampled reads of a surface whose GPU results are still pending.**

What happens:
1. AnyPS5 keeps a render target's results in its host image ("pending") and stores them to guest memory only when something reads that memory through a flushing path. Images larger than 64 KiB are never stored at a flip (`Execution/src/Driver/Packets/PacketMemory.cpp:198`, `Graphics/src/Texture.cpp:3481-3499`, `SmallStoreBytes` at `Graphics/include/Texture.hpp:198`).
2. Suppose the title then fast-clears the surface by writing clear codes into its DCC keys, through any path that does not reach `StorageTexture::NoteKeysFill`. Such paths include a CP DMA fill of at most 64 KiB, a compute kernel the fill HLE does not take, or a CPU store.
3. Every later sampled read then keeps serving the pending image, which holds the title-scene pixels:
   - the sampled lookup gives the pending image up only for a noted key fill or comp-to-single keys;
   - it refreshes the image only when the colour bytes change, not the keys.
4. The target and storage path (`Refresh`) does the opposite with the same keys: "new keys that are a clear code make every result dead on hardware too".

How long it lasts:
- **Until** the surface is next bound as a render target or storage image, or its image is evicted.
- **So it persists** for a surface that is drawn while the title is up, then only cleared and sampled after the cut. A composited layer (a foreground or near-field depth-of-field layer, say) or a history/previous-frame surface that is not redrawn would show exactly the reported ghost: dimmed, not fading.
- **A history surface that is redrawn every frame** would heal at its next bind.

Next candidates, ranked (details in section 4):
- **B.** Shaders that read memory through pointers (address-based shaders) skip the step that stores pending results first, so they read the guest bytes last stored, possibly title-era. `APS5_BDA_FLUSH=1` turns the exemption off.
- **C.** Clears that never reach the image: DCC keys of mipmapped targets are ignored, unencodable or mixed keys read as stored, a failing register clear is swallowed, and the multisampled and HTILE limits.
- **D.** Late or ordering-sensitive stores when memory is reused: debt L56, #1970.
- **E.** Two pending images at one address, where the first registered one is served.
- **F.** Virtual aliases of the same physical memory are invisible, because every lookup is keyed by virtual address.

**One run on the PC decides between A and B** (section 6). Its parts:
- existing switches `APS5_TRACE_DCC_KEYS`, `APS5_TRACE_UPLOAD`, `APS5_TRACE_FLUSH`, `APS5_TRACE_FILL_COVER`, `APS5_TRACE_DRAWS`, `APS5_LOG_TIMESTAMPS`;
- optionally three small debug lines on a `test/` build, which name A or B directly;
- `APS5_EAGER_WRITEBACK=1` and `APS5_BDA_FLUSH=1` as one-switch confirmations.

## 2. Reusing memory for a new target (question 2)

**Caches and keys.**
- **Storage-image cache.** It covers render targets, storage images and the images behind sampled views.
  - It is keyed by `SurfaceKey` (`ShaderResources.cpp:833-836`): base address with pipe/bank XOR, width, height, last slice and mip count, tile mode, dimension, base array slice, and the Vulkan storage format. Guest formats that store in the same Vulkan format share one image.
  - Eviction is LRU under a budget (`APS5_TEXTURE_CACHE_MIB`, else `TextureCacheBudget`, `:486-497`). Evicting an image stores its pending results first (`evictStorage`, `:819-830`).
  - Freeing or reusing memory never retires an image.
- **Sampled cache** (`ShaderResources.cpp:72-147`, lookup `525-755`). It is keyed by the 8 T# dwords, swizzle and depth-compare. Each entry is either a CPU snapshot checked by write stamps, or a view of a storage image.
- **`Graphics::TextureCache`** (`TextureCache.cpp`) is constructed but has no caller.
- **Depth surfaces and multisampled targets** are matched by address plus shape and live as long as the device (debt L34, L96).
- **Other caches** — draw/dispatch caches, draw input snapshots, unit shadows, image tables — hold decoded state, buffers or pipelines, never texels of colour targets. Each re-proves its objects on use.

**Invalidation by writer.**
- **Every lookup** first stores other images' pending results over its range (`FlushPending`).
- **CPU writes** are stamped per 64 KiB block when a lookup collects them.
- **GPU and driver writes** call `GuestMemory::MarkWritten`.
- **A pending unit stamped after its generation** loses its results (`Texture.cpp:1913-1921`).
- **Writes that are not seen at all:**
  - DCC key-only clears, as seen by sampled reads (A);
  - reads through pointers, which skip the store of pending results (B);
  - writes through another virtual alias (F);
  - copies, kernels and CPU writes into multisampled colour memory (L93, L94).

**Reuse of the same memory.**
- **Same `SurfaceKey`:** the same Vulkan image keeps the old contents, as the console's memory would.
- **Another key** (other format, extent or tile mode): the old image's pending results are stored first ("storage image creation", `ShaderResources.cpp:911`), then the new image uploads from guest memory, or is cleared on the GPU when the keys hold a clear code (`Texture.cpp:2178-2237`).
- **Never undefined.**
- **The old image stays cached** and catches up at its own next lookup.
- **The late store of #1970** (debt L56) cannot land over a new image, but it can land over bytes written by writers that do not flush first (D).

**Exact-address keying.**
- cloud-1's PM-010 finding holds for identity.
- Coherence between different images over the same memory works by overlapping ranges and stamps.
- A T# at an interior address gets its own image.
- `BASE_ARRAY` is in the key, but `ArrayLayersServeView` (`Graphics/src/GuestTextureResource.cpp:258-263`) lets a sampled read use the pending array image.
- Virtual aliases of one physical range are invisible, because the stamps are per virtual block (F).

## 3. History reads (question 3)

**Which image a T# over a former target reads** (`cachedTexture`, `ShaderResources.cpp:525-755`):
1. **The pending image** with the same base (`StorageTexture::FindPending`, `Texture.cpp:3519-3531`), when `Texture::CanCopyFrom` holds.
   - It is a view of the target's own VkImage in the T#'s format, in the GENERAL layout.
   - So UNORM vs sRGB, or R32_UINT over RGBA8 or 10_11_11, read the same image.
   - Comparison and block-compressed reads get copies that follow the image's version.
2. **Otherwise the storage image** for the T#'s key, refreshed: other pending images are stored first, and changed blocks are re-uploaded.
3. **Otherwise a CPU snapshot**, after `FlushPending` stored the target's results (`:629-633`).

**Ordering.**
- All queues record into one batch under the GPU mutex, so recording order is GPU order (`Graphics/include/Recorder.hpp:29-37`).
- A pass that samples an image another pass wrote or attached is split, with a barrier (VkImage identity, `Graphics/src/PassHazards.cpp:45-57`).
- Uploads, clears, copies and write-backs close the pass first.
- So a reset that writes the history memory, or leaves results pending, is seen by the next sampled read.
- The exceptions are a keys-only reset (A) and a reader through pointers (B).
- A pass that samples X and a later pass that writes X are separated by a barrier.

**Feedback in one draw** (sampling the target being drawn).
- A new pass with a barrier is forced first (`Draw.cpp:1720-1721`, `1752`).
- Within the draw, texels the same draw writes read back undefined.
- That is transient, not persistent.

**Copies that could go stale:** none found for texels. Draw input snapshots are buffers (debt L55), and the caches hold descriptors and pipelines only.

**If Village resets its TAA through a shader constant** (a "reset history" flag) instead of a texture write, none of the texture paths apply. The constant buffers are revalidated per use like any input.

## 4. Mechanisms, ranked

**A. Sampled reads keep a pending image over a DCC fast clear the driver did not note.**
- **Deciding code** (`ShaderResources.cpp`):
  - `:567` `auto source = StorageTexture::FindPending(address, guestBytes);`
  - `:573` `if (source != nullptr && resource.dccAddress != 0 && IsDccClear(source->FilledKeys()))` → the only clear that ends the pending view;
  - `:588` comp-to-single;
  - `:621` refresh only `if (!GuestMemory::UnchangedSince(address, bytes, source->Generation()))`, which looks at the colour bytes, not the keys;
  - the cache hit at `:669-677` and the fast path at `:3825-3831` keep the view. The comments at `:2588-2591` and `:2475-2480` say the lookup "prefers them to the clear".
- **Why the keys are trustworthy:**
  - After the first draw under clear keys, the driver itself stores uncompressed keys (`MarkDirty`, `Texture.cpp:3077-3081`).
  - The image's own `Refresh` treats new clear keys as killing every result (`Texture.cpp:1913-1914`).
  - So the two paths disagree on the same state.
- **Who notes key fills:**
  - only `storeBufferFill` (`BufferFill.cpp:291-300`, and the GPU variant `:335`);
  - small DMA fills go to the packet-store path instead (`PacketMemory.cpp:117-147`), and `NoteColorMetadataFill` (`:63-69`) only serves multisampled targets (`MultisampleTarget.cpp:514-525`).
- **Sizes:** a 1920x2160 or 1920x1080 surface with 4-byte texels has 64,800 or 32,400 key bytes, both under the 64 KiB store limit. A 3840x2160 4-byte surface has 129,600, above it.
- **Persistence:** it heals at the next target or storage bind (`Refresh`), or when the image is evicted or stored. It persists for a surface that is only cleared and sampled after the cut.
- **Related open PR, #4794** ("flush pending results at staged-clear sampled reads"):
  - It resolves the same ambiguity the other way: Bendy stages a clear *before* sampling its feedback loop, so the results must win there.
  - A fix for A must keep that case: its test `StagedClearSampledRead` is on the PR branch.
- **Not documented** in the debt file. The nearest entries are L56, L103 and L104.

**B. Reads through pointers skip the store of pending results.**
- Deciding code: `GuestBufferMemory.cpp:3563`, `if (!(addressable && region.hostBacked) || bdaFlush) StorageTexture::FlushPending(...)`.
- The comment says such shaders "do not read texture memory through pointers". If an RE Engine pass does (history, exposure or luminance read as raw memory), it reads the bytes last stored, possibly from the title, for as long as no flushing access stores the results.
- Not documented in the debt file.

**C. Clears that never reach the image.**
- DCC keys of mipmapped colour targets are ignored (`State.cpp:1224-1233`).
- Unencodable, mixed or unreadable keys read texels as stored (`DccMetadata.cpp:526-535`; L103, L114).
- A failing register-clear materialization is caught and the image used without the clear (`Draw.cpp:1229-1238`). Its message "stays non-resident" is misleading: the image stays resident.
- CMASK is applied only at a bind or eliminate (L86).
- Multisampled CMASK and colour memory are seen only through noted fills (L91-L96).
- HTILE limits for depth (L23-L26, L87).

**D. Stores that land late or out of order when memory is reused.**
- Pending results are stored when something reads their memory (L56, #1970).
- Writers that do not flush first can be overwritten by those stores, or win over them: pointer stores (stamped only at completion), and CPU stores that rewrite the baseline bytes (L100; L57, L59).
- Usually washed out by TAA unless combined with A or B.

**E. Two pending images at one base.**
- `FindPending` returns the first registered one with that base and size (`Texture.cpp:3519-3531`). Images register on their clean→dirty transition (`:3155-3158`).
- Self-healing in the sequences traced (the next write to the memory refreshes). Not documented.

**F. Virtual aliases of the same physical memory.** Stamps and lookups are per virtual address (PM-010). This persists if the engine maps a history buffer twice. Not documented.

## 7. Fix direction for A (not built)

Two options, which are not exclusive:
- **Note key writes on the other paths.**
  - In the packet-store path (`PacketMemory.cpp:117-147`), call `ClassifyFill` and, for a uniform byte over an image's keys, `NoteKeysFill`, as `storeBufferFill` does. This covers DMA fills of 64 KiB or less.
  - Compute kernels writing keys would still be missed. #5497 is one kernel.
- **Decide by order rather than by noting.** Over a pending image, clear keys win when the key range was stamped after the image's results were produced. Results win when the keys are older: the Bendy case of #4794, test `StagedClearSampledRead`.

Either option needs red/green tests:
- a pending DCC target, then a 32 KiB DMA key fill to 0x00, then a sampled read: today it returns the old texels, and it must return the clear;
