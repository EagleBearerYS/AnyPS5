# PM-011: why #5851's alias imports take write faults, and fault-free options (cloud-3)

Analysis only: nothing was built, changed, posted or pushed except this file.

**Sources.** Line numbers are on upstream/main ea30c9274a. #5851 is refs/pull/5851/head 22091410a6, 3 commits on 28b6f1987. Its files are unchanged on main except for the 3+2 lines it edits:
- `WindowsMappings.hpp` on main is identical to the PR's base.
- `importRunAt` is at the same lines.

Other refs:
- #5596 is the merge 3e4fe4ce3 (d9852df2a, 71da166a1).
- The closed framers are #5052 (fab7d203f) and #5640 (cef664f77).

## Summary

- **What #5851 does.** It routes GPU imports of resident direct memory through `MapAlias`. `MapAlias` demotes the resident runs from private `MEM_WRITE_WATCH` memory into views of the direct-memory section.
- **Why that faults.** Section views cannot be write-watched on Windows. So their CPU writes are tracked by arming the views read-only and resuming each first write in a vectored exception handler. Windows builds the exception frame directly below the faulting RSP, which destroys a System V leaf's 128-byte red zone before any handler runs. No handler-side fix exists.
- **Why audio threads dominate.** Heap mirrors collect, and so re-arm, whole heap spans on every refresh. Every CPU-written 4 KiB page inside an imported heap faults again after each refresh, whether or not the GPU ever reads it.
- **Recommendation.**
  1. First, probe on Windows hardware whether direct host imports can stay watched; that is option 1 below. If they can, drop #5851's demotion and keep #5596's private write-watched pages: fault-free, with no comparisons.
  2. If the probe fails, keep #5851. Add two things: classify runs by their `GetWriteWatch` history before demoting them, and stop re-arming pages the CPU writes every collect. That reduces faults to rare first touches. It is not strictly fault-free.

## 1. The mechanism

**Before #5851: resident runs are private and write-watched (fault-free).**
- `Map` makes a direct-memory page mapped at one guest address part of a resident run (`WindowsMappings.hpp:101-129`).
- The run is committed as private memory with `MEM_WRITE_WATCH` (`commitResident`, `589-592`).
- Its writes are collected with `GetWriteWatch` (`collectResident`, `538-573`; the call is at `545`). No protection, no faults.
- Runs never cross a 2 MiB boundary (`110`, `chunkBytes = 0x200000` at `481`).

**#5851 sends GPU imports of those runs through an alias:**
- `GuestBufferMemory.cpp:980` changes from `bool writable = true;` to `writable = !GuestArenaResidentSpan(...)`. Any import range that overlaps a resident run now takes the `!writable` path to `GuestArenaMapAlias` (`1001-1018`; the call is at `1008`).
- `MapAlias` (`WindowsMappings.hpp:251-290`) used to refuse runs that extend past the range (`263`). #5851 replaces that check with a loop that returns null on an open host write. It then demotes every resident run the range touches (`265-268`).
- `MapAlias` maps a second, read-write view of the section for the driver (`283`, `MapViewOfFile3 ... PAGE_READWRITE`). The import uses that alias, so it stays watched (`GuestBufferMemory.cpp:1029`, `watchedHostPointer = entry.alias != nullptr || ...`).

**What `demote` does** (`WindowsMappings.hpp:610-637`):
- Fences the run `PAGE_READONLY` (`615`).
- Copies it into the section through a window (`617-620`). This is the ~12 GiB copy Sevthered measured.
- Releases the private pages, keeping the placeholders (`621`).
- Maps each 16 KiB page as a section view (`624-625`, `mapShared` at `594-600`: `MapViewOfFile3` with `MEM_REPLACE_PLACEHOLDER`, then `VirtualProtect` to the view's protection).
- Clears `resident`, `seen` and `armed` (`627-629`).

From then on the pages are shared views, and `GetWriteWatch` no longer applies to them.

**How a shared view is write-protected: arming, not guard pages.**
- A clearing `Collect` over a shared view arms every settled 4 KiB subpage of every non-resident writable alias of the page (`WindowsMappings.hpp:401-415`).
- Arming is `protectSubpages(alias, arming, PAGE_READONLY or PAGE_EXECUTE_READ, "arm shared memory write tracking")` at `412-413`, plus `armed |= arming`.
- Subpages under an open host write stay unarmed (`408-410`).

**The fault path:**
1. A guest store to an armed subpage raises a write access violation.
2. `ReportCrash`, the first vectored handler (`CrashReport.cpp:566`, `AddVectoredExceptionHandler(1, ReportCrash)`), calls `GuestArenaHandleWrite` (`CrashReport.cpp:293`, `GuestArena.cpp:319-321`).
3. That reaches `WindowsMappings::HandleWrite` (`182-197`). Under the global mappings mutex (`183`), it bumps the subpage generation (`invalidate`, `193`), makes the subpage writable again (`194`, "resume shared memory write") and clears the armed bit (`195`).
4. The handler returns `EXCEPTION_CONTINUE_EXECUTION`, and the store re-executes.

**Why the red zone breaks, and why the handler cannot help.**
- Windows x64 has no red zone. The kernel builds the exception frame on the faulting thread's own stack, directly below RSP, before user-mode dispatch reaches any vectored handler.
- #5052's commit message states the same: "Windows writes an exception frame directly below RSP, so a fault resumed on a guest thread overwrites values a System V leaf function keeps in its red zone".
- When `ReportCrash` runs, the bytes are already gone.
- The emulator's own guest exception delivery does skip the red zone (`libkernel/System/src/Exception.cpp:135`, `289-292`), but host-raised faults never go through it.

**What the tracking feeds.**
- `collectWindowsWrites` (`Execution/src/GuestMemory.cpp:1104-1127`) calls the three `GuestArenaCollect*Writes` and stamps 64 KiB blocks with generations (`stampWrittenRun`, `1085-1101`).
- Consumers compare those generations:
  - heap mirrors: `refreshHeapMirrors`, `GuestBufferMemory.cpp:1481-1494`; `appendChangedBlocks`, `1459-1479`;
  - sparse heap mirrors: `1587-1595`;
  - writable mirrors: `refreshMirror`, `1452-1457`;
  - the texture and buffer caches and the import windows (`ImportWatched`, `GuestMemory.cpp:1265-1317`).
- So yes, the tracking feeds GPU import coherence, the heap mirror and CollectWrites. In each case the question is the same: which guest blocks did the CPU change since the GPU-side copy or derived data was made.

## 2. Where the faults come from after #5851, and how #5596 avoided them

**Yes, section views are the reason the faults came back.** The chain:
1. On Windows the driver may not import the guest's own pages as a watched range. `decideImportWatch` sets `unwatchImports = true` unconditionally (`GuestBufferMemory.cpp:634-640`), and logs "Windows direct host imports use comparisons; separate shared aliases retain guest write tracking".
2. The earlier message, which 20cfc0130 replaced, gave the reason: "host imports are compared on Windows because driver writes can arrive after the import window".
3. So a watched GPU import needs a second mapping, the alias.
4. Only a section can be mapped twice, and section views cannot carry `MEM_WRITE_WATCH`, which is for private `VirtualAlloc` memory. `GetWriteWatch` is called only on resident runs (`545`) and on private non-view memory (`447`).
5. Moving the pages into the section therefore forces protection-based tracking, and every first write after each arming faults.

**How #5596 avoided faults, and what it cost.**
- #5596 (d9852df2a) keeps singly mapped direct memory private and write-watched. Only a page mapped at a second address is demoted.
- A GPU import of a resident range was then a direct host-pointer import (`writable` true at `980`). On Windows that is unwatched (`1029`, `1047`). Its range leaves guest write tracking (`GuestMemory::Unwatch` at `1134`, which excludes it from coverage at `Execution/src/GuestMemory.cpp:1240-1263`).
- Every use of the range was then compared on the CPU: each 64 KiB block of a mirror over it was compared with the mirror's shadow, and copied if changed (`compareBlock`, `GuestBufferMemory.cpp:1288-1330`).
- **The cost** is proportional to the imported bytes on every refresh, not to the bytes written. That is the 2.5–6x #5851 removes. It is visible as `compareUs`/`blocksCompared`/`blocksCopied` on the `[address]` line of `APS5_PROFILE_DRAW` (`GuestBufferMemory.cpp:1201-1212`).

## 4. Threads that don't need tracking, and tracking fewer regions

- **Heap mirrors re-arm whole heaps every refresh.**
  - `refreshHeapMirrors` calls `CollectWrites` over each contiguous span of heap mirrors (`GuestBufferMemory.cpp:1486-1489`).
  - That clearing `Collect` re-arms every settled subpage in the span (`WindowsMappings.hpp:401-415`).
  - Audio and movie buffers that titles keep in the same GPU heaps are re-armed on every refresh. Their next CPU write faults again, about once per page per frame. That matches 10,000 faults per 10 s with most of them on audio threads.
  - The GPU never needs most of those pages. Movie frames are the exception, because they become textures.
- **The PR's whole-run demotion adds little on top.** It demotes every resident run the range touches (`WindowsMappings.hpp:265-268`), but runs end at 2 MiB boundaries (`110`). So the excess beyond the import is at most part of the two end runs.
- **Ways to track fewer regions:**
  1. Arm only blocks a GPU consumer referenced since the last collect. The AGC would pass a referenced-block mask, or collect only referenced blocks, and refresh an unreferenced block when it is next referenced.
  2. Option 2 above, for pages the CPU writes every collect.
  3. Leave CPU-only mappings out of the alias: pages mapped without GPU protection bits (prot without 0x10/0x20) need no GPU tracking. This helps only if the audio buffers are mapped CPU-only rather than inside a GPU-mapped pool, which is measured below.
- **Lock contention.** `HandleWrite` takes the global mappings mutex (`183`). Audio threads faulting during a collect wait for it, which is a possible audio-stall source of its own.

## 5. Recommendation

1. **Measure first** (section 6), then **try option 1.** It is the only option that is fault-free, compare-free and smaller than #5851's follow-ups, and it also removes the demote copy. Its risk is driver behaviour, so it needs the probe on each GPU, as Linux does.
2. **If the probe shows late driver writes,** keep #5851 and add, in this order:
   - option 2 (no re-arming of hot pages), the smallest change, removing the repeat faults;
   - the referenced-block arming gate from section 4, removing faults on CPU-only data in GPU heaps;
   - option 3b, if first-touch faults still crash.
   Together these leave rare first-touch faults, not none, so the #361 class becomes rare but stays possible. Option 4 is the only fully fault-free design that is independent of the driver; it is a separate project.
3. **Don't pursue 6a or 6b** as the fix. 6a cannot work, and 6b cannot cover all guest code.

## 6. What to measure on Village

All on the 3D scene, in 10 s windows, with the local fault counter, on main 23be5a02b+#5851 and on main alone:
1. **Fault breakdown** for each resumed write fault:
   - inside a MapAlias-moved run or another shared view (a second mapping or a JIT/shm section);
   - the thread;
   - the 4 KiB page, which gives distinct pages against total faults: the repeat factor is option 2's gain;
   - whether the page is inside a heap mirror span, and whether a GPU command referenced its 64 KiB block that frame;
   - the guest protection of its mapping (GPU bits or CPU-only).
2. **The baseline:** the same counter on main without #5851, for the faults #5851 did not add.
3. **The compare cost #5851 removed:** the `[address]` line (`compareUs`, `blocksCompared`, `blocksCopied`, `APS5_PROFILE_DRAW=1`) and the frame time, on main and with #5851. This bounds options 3 and 3b.
4. **The option 1 probe on the PC's GPU:**
   - import write-watched scratch pages directly;
   - run a GPU read and a GPU write over them;
   - wait well past the import window;
   - count the pages `GetWriteWatch` reports: after the import, after the read and after the write.
5. **Fault cost:** total time in `HandleWrite` (with `VirtualProtect`), plus mutex wait time, per second.
6. **Crash rate,** whichever option is chosen: parl0v's Sword of the Sea run (1 crash in 6 now), at least 20 runs.

RESULT:
- **Mechanism:**
  - #5851 sends resident GPU imports to `MapAlias` (`GuestBufferMemory.cpp:980/1008`);
  - `demote` moves the runs into section views (`WindowsMappings.hpp:610-637`), which cannot be write-watched;
  - clearing collects arm the views `PAGE_READONLY` (`401-415`);
  - `ReportCrash` (`CrashReport.cpp:293`) resumes writes via `HandleWrite` (`182-197`);
  - Windows has already written the exception frame over the 128-byte red zone below RSP, and no handler can prevent that.
- **Why the audio threads:** heap mirrors collect whole heap spans every refresh (`GuestBufferMemory.cpp:1481-1494`), so CPU-written pages in GPU heaps fault again every frame.
- **#5596:** fault-free through private `MEM_WRITE_WATCH` pages, but Windows direct imports are unwatched (`634-640`, `1029/1047/1134`), so mirrors compared every block on every refresh (`1288-1330`). That is the cost #5851 removes.
- **Recommendation:** probe whether Windows direct imports can stay watched (option 1: fault-free, compare-free, replaces the demotion). Otherwise use #5851 with hot-page exemption, a referenced-block arming gate and run classification (options 2 and 3b). Not 6a or 6b.
- **Measure on Village:** fault breakdown by region, thread, page repeat, GPU reference and protection; the baseline without #5851; the `[address]` compare cost; the option 1 probe on the PC's GPU; `HandleWrite` time; the crash rate.
