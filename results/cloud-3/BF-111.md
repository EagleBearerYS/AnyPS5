# BF-111: make BF-107's big-allocation counter capture call stacks on Windows (cloud-3)

Base: fork `exp/big-alloc-sites` **735b5f01c** (BF-107's counter, as qbf107 booted it).

## 1. Why the boot got totals and 0 frames

The task's diagnosis holds.
- **No PE unwind data.** On MinGW, `core/libs/CMakeLists.txt:38-44` builds every library with `-fno-asynchronous-unwind-tables`. With WinLibs GCC 15.2 that gives DWARF exceptions: an `.eh_frame` that `configure_windows_unwind` (`:47-57`) renames to `.ehfram`, and **no `.pdata`** for the project's functions. That covers `hookMalloc`, `record` and every `.prx` frame.
- **The walk dies in skipped frames.** `CaptureStackBackTrace` steps with `RtlVirtualUnwind`, which treats a frame without `.pdata` as a leaf, so the first step out of `record` is already wrong. 735b5f01c asks it to skip 2 frames (`record` and the hook), and on Windows the walk ends inside those, leaving depth 0. Every allocation then lands in the one empty stack.
- **Reproduced under Wine** (section 3). Wine's walk doesn't stop at the bad step; it returns 16 junk words instead. The allocating function never appears in either case.

**Task step 1 (`-fasynchronous-unwind-tables` on `BigAllocations.cpp`) is not in the commit.** Two measured reasons:
- **Alone, it gets one frame.** The hook and `record` would get `.pdata`. `CaptureStackBackTrace` would get out of the hook, but it stops being right at the first DWARF-only `.prx` frame.
  - Measured: the first frame is right, then junk such as `0xae msvcrt.dll+0x14ee0 0x1 0x7ffffe7956c0 …` (variant `step1`).
  - Junk that holds stack and heap addresses differs from call to call. It would split one call site into many stacks and break the top-12 aggregation.
- **It would stop the better walk at the hook.** With that flag, GCC emits SEH `.pdata`/`.xdata` and no DWARF CFI for the TU (checked with `objdump`). libc's own unwinder (below) declines `.pdata` in any module that has `.ehfram` (`exception/Unwind.cpp:269`), and `libc.prx` has `.ehfram` (`core/libs/CMakeLists.txt:88`). So the walk would end at the hook.
  - Measured (variant `green-seh`: this branch's tracker built that way, in a DLL with libc's DWARF unwinder): 0 unwound frames, and every stack fell to the scan.

## 2. The change

- 7 files, +315/−44.

**Capture: libc's unwinder (`core/libs/prx/libc/src/BigAllocations.cpp`).**
- On Windows, `captureStack` calls `_Unwind_Backtrace_nid_postfix`, libc's own unwinder, which `Backtrace.cpp` already uses for `sceLibcBacktraceSelf`.
- That unwinder steps each frame by one of two sources:
  - the module's DWARF records in `.ehfram` (or the relinked image's `.ehmeta`), for the project's `.prx` frames;
  - `RtlVirtualUnwind` and `.pdata`, for modules without those tables: `libstdc++-6.dll`'s `operator new`, system DLLs, `libwinpthread-1.dll`.
- It skips `captureStack`, `record` and the hook, and keeps up to 16 return addresses.
- Linux keeps `backtrace`, with the skip moved by one for the new `captureStack` frame.

**Fallback: a stack scan when unwinding gives fewer than 3 frames.**
- **Start:** each hook passes its own return-address slot, `__builtin_frame_address(0) + 8`. It is checked against `__builtin_return_address(0)` and dropped if they differ.
- **Range:** from that slot upward, at most 32 KiB, never past the TEB's `StackBase`. It does nothing if the slot isn't between the TEB's `StackLimit` and `StackBase`, as on a stack the TEB doesn't describe.
- **What is kept:** a qword is kept when it passes three checks:
  1. **Code range:** it lies in an executable section of a loaded module. `patchModules` collects these from the module list the installer already walks, sorted and published lock-free; a binary search finds the range.
  2. **Readable:** `VirtualQuery` says the 7 bytes before it are committed, readable code. That guards a module unloaded since.
  3. **Call before it:** the bytes before it end a call: `E8 rel32` 5 bytes back, or `FF /2` whose ModRM, SIB and displacement fill exactly the 2–7 bytes back. A REX prefix such as `41 FF D0` comes before the `FF`, so it passes too.
- **Limits:** the first 16 are taken, and the scan replaces the unwound frames only when it found more.
- **Output:** each `#n` stack line now says how it was taken, with the format otherwise unchanged:
  - `... other <n> unwound frames <module>+0x<offset> ...`
  - `... other <n> scanned frames <module>+0x<offset> ...`
  - The flag is part of the stack's identity. `tools/resolve_bigalloc.py`'s line regex (`.* frames (…)`) still matches.

**Re-entry and the unwinder's lock.**
- **A thread-local flag** stops nested recording: a big allocation made while a stack is being taken is not recorded. The only such allocation is the unwinder's own frame index.
- **`IndexFrames`** (`exception/Unwind.cpp:222-249`) now builds a module's FDE index outside its mutex and inserts it under the lock. Before, an index past 512 KiB (a large module's first index, built during a C++ exception with the hooks on) would reach the hook and the unwinder again, and wait on the lock the same thread held.
- **Lock order:** no lock is held across the capture, and the tracker mutex is taken only after it, as before.

**Resolver.** `tools/resolve_bigalloc.py` couldn't read a frame of a module whose name contains `+`, such as `libstdc++-6.dll+0x131dcc`, the boot's `operator new` frame; it printed "(no module)". The frame regex is now `^(?P<module>\S+)\+0x…`.

**Cost:** one libc unwind per allocation of 512 KiB or more, with the switch on. qbf107's rate was ~250 such allocations per second. Not measured on Windows.

## 4. Step 6: what the qbf107 samples likely are

### The 2,097,176-byte blocks (2 MiB + 24)

**What they hold.** They hold buffer descriptors (V#s), not driver records. Each 16-byte record decodes as an RDNA V#:

| record | dword0 + dword1[15:0] (base) | dword1[29:16] (stride) | dword2 (`num_records`) | dword3 (sel/format/OOB) |
|---|---|---|---|---|
| 0 | `0x20_75000000` | 1 | `0x7f8000` | `0x30005004` (OOB_SELECT 3, raw) |
| 1 | `0x20_3f19d4c8` | 4 | `0x2000` | `0x5204` |
| 2 | `0x20_4f800000` | 0x10 | `0x200000` | `0x5204` |
| 3 | `0x20_4d400000` | 0x30 | `0x8000` | `0x5204` |

- The "16-bit tag" is the stride, the "size" is `num_records`, and the "flags" are dword3.
- So a block is a host copy of a guest buffer-descriptor table, about 131,072 V#s. The records are 16-byte aligned from offset 0, and the size is exact: one copy of one guest range that starts at the table.

**Not what BF-108 found in the draw cache.** BF-108 matched the census's 1 MiB blocks of (begin, end) pairs (32-byte T# ranges spaced 0x30) to draw variants' `runs`, and 2 MiB blocks to their `words`. These blocks hold V#s instead, and `runs`, `spans` and `captured` hold no descriptor words.

**Size class.** `sizeClass` tops the 2 MiB class at exactly 2 MiB, so these blocks count as "other", not "2 MiB". qbf107's "other ×1,359" at the peak includes them.

**Candidates, most likely first:**
1. **An address-based build's copied snapshot, `GuestBufferMemory::Region::snapshot`.**
   - `AddSnapshot` (`Graphics/src/GuestBufferMemory.cpp:4178`) copies a draw snapshot that no registered region holds, sized exactly to it. Such a copy lives as long as the build: its `ResourceCache` entry, or the recorder's kept objects.
   - **The rate fits:** ~2,300–2,700 big allocations per 10 s in qbf107, against ~2,000 address-based builds per 10 s at the same menu in q6636p's `[address]` line (BF-105).
   - **Frames to look for:** `GuestBufferMemory::AddSnapshot` ← `ShaderResources::ShaderResources` ← `resolveDrawResources` (`Graphics/src/Draw.cpp:1460`).
2. **A draw- or dispatch-cache variant's `words`.**
   - The size is exact only when the variant's capture was that single range, since `tagVariantRuns` (`Draw/DrawRelocate.cpp:91`) resizes per region, or for a copy such as a data hit's `hit.words = variant->words` (`Draw/DrawLookup.cpp:132`).
   - **Frames:** `Driver::tagVariantRuns` / `cacheDrawStages`, or `lookupDraw`.

**Ruled out:**
- `ShaderMemory` pages: 4 KiB each.
- The SRT walk's column memos: 16 entries and 4 Mi words per thread (`ResourceMaterializer.cpp:486-487, 1207-1215`).
- `heapReferences`: only written heap-mirror ranges, cleared at write-back (`GuestBufferMemory.cpp:5366-5377, 5463`).
- `Region::uploaded`: only regions the GPU writes (`:4843-4854`).

### The ~790 KB blocks

**What they hold.** They fit vectors of 24-byte `{guest address, data pointer, byte count}` records:
- `ShaderRecompiler::MemoryRegion` (`shader/recompiler/Recompiler.hpp:32-35`);
- `Graphics::GuestMemorySnapshot` (`Graphics/include/GuestBufferMemory.hpp:23-26`);
- `ShaderMemory::initial`'s pairs.

**How the dump reads that way.** From the second qword, such a vector reads exactly "host pointer, 0x60–0xa0, guest pointer 0x2_62fb…". The 0x60–0xa0 values are each region's byte count (96–160 bytes), and guest addresses are arena pointers at 0x2_0000_0000 and up. 786,432 bytes is exactly a doubling vector's capacity of 32,768 such records (16,385–32,768 regions).

**Which holders:**
- **Long-lived:** a dispatch variant's `captured`, a copy of its capture's regions (`Dispatch/DispatchInsert.cpp:57`, `Dispatch.cpp:349`).
- **Transient:** a draw's `memory` and `snapshots` (`Draw/Draw.cpp:234, 499`). They are freed after the draw, so they'd show as churn, not growth.
- **Not the T# table:** the byte counts aren't its 32-byte T# ranges, so the regions come from another table.
- **Frames to look for:** `ShaderMemory::Regions`, the dispatch insert, or the draw's `snapshot` lambda.

### The draw cache

- **The V# blocks:** not `runs`, `spans` or `captured`. They could be `words` only for a variant whose capture was that one table range.
- **The ~790 KB blocks:** in this tree a variant's `captured` is filled only on the dispatch path, so if they are variant members they are dispatch-cache `captured`. Draw variants keep `runs`/`words`/`shared`/`memory`.
- The v2 frames will decide between these, and the `#1`–`#3` newest-block dumps keep working.
