# BF-015: why CPU-path indirect draws miss every draw reuse, and a prototype that lets them hit

From: AnyPS5 Cloud 3 (Linux worker). Base: upstream main 5d9dcc42d2. Line numbers are on main unless a branch is named.

Short answer: the two reasons are the driver's GPU-side rules for an indirect draw.
- "patched SGPR not folded": the packet asks the CP to write the record's base vertex or start instance into a user SGPR that the stage reads in some way other than one foldable fetch add.
- "non-vertex path": the stage set is tessellation, a rect list, or the mesh-emulated geometry path outside its one GPU-side case.

Both rebuild the front program for every record. CPU-path draws were kept out of draw entries because those per-record stages were never kept, so an entry would have held only the stages compiled on the register words.

The prototype, `exp/agc-indirect-cpu-draw-entries`:
- lets these draws insert their entry;
- keeps each per-record stage with the inputs it was built from (the record's argument words, the patched user words, the compile-context draw parameters);
- takes a kept stage only when those inputs are equal and its own captured reads still validate.

In a synthetic repeated indirect draw it removes every capture and the decode. On lavapipe:
- repeating one record: 34.2 µs per draw on main, 21.8 µs on the branch;
- record changing every draw: 37.6 µs on main, 27.0 µs on the branch, since the base entry still hits.

## 1. The four questions

### Q1. The two reasons

Where the decision is made:
- `Execution/src/Driver/Draw/Draw.cpp:348-349`. The front program's compiled result goes to `Driver::ClassifyIndirectDraw` (`Execution/src/Driver/Draw/IndirectDraw.cpp:24-67`).
- `fail` (`IndirectDraw.cpp:30`) keeps the first reason. The names are `Graphics/src/Draw.cpp:345`.

**"patched SGPR not folded" (`Path::NotFolded`)**

- `IndirectDraw.cpp:38-48`, the `dimension` lambda, runs once per dimension (`:49` vertex, `:50` instance). Its inputs:
  - `k`: the SGPR the recompiled stage adds to the vertex or instance id VGPR, `result.vertexOffsetSgpr` / `instanceOffsetSgpr`.
  - `p`: the SGPR the packet names for the CP's write, `indirect.baseVertexSgpr` / `startInstanceSgpr`. `Draw.cpp:179-189` (`sgprOf`) sets it: BASE_VTX_LOC / START_INST_LOC located in the front program's user words, or -1 if absent or not in program 0.
- What `dimension` decides:
  - `p < 0`: `Rule::Constant`. The record's base field is rewritten on the GPU with GE_INDX_OFFSET + user[k]. This is the `count > 256` limit at `:52`.
  - Otherwise, `conflict`: `FetchUnknown`.
  - Otherwise, `k != p || shared`: **`NotFolded`** (`:45`).
  - Otherwise, `x != 0`: `IndxOffset`.
  - Otherwise: `Rule::InPlace`. vkCmdDraw*Indirect takes the record as is, and the folded fetch reads the base through gl_VertexIndex / gl_InstanceIndex.
- Where `k`, `conflict` and `shared` come from, in `core/shader/recompiler/Translation/src/EmbeddedVertexFetch.cpp`:
  - `:407-428`: a user-SGPR add (`v_add_i32` / zero-`v_sad_u32`) into the vertex (v5) or instance (v8) index VGPR, seen before the first fetch load.
  - `:571-581`: set as `vertexOffsetSgpr` / `instanceOffsetSgpr` at the first formatted buffer load indexed by that VGPR.
  - `:603-614`: `conflict` means two different SGPRs were added; `shared` means any other instruction touches the SGPR (`touchesSgpr`).
- So `NotFolded` means the CP's write of the record value into s[p] is observable beyond one foldable fetch add:
  - the stage has no recognised fetch add (`k = -1`), for example it reads s[p] as data or pulls vertices with its own address math;
  - or it adds a different SGPR (`k != p`);
  - or it also reads s[p] elsewhere (`shared`).
- `tests/execution/IndirectPatchedStage.cpp` is such a stage: it exports s8 as depth with BASE_VTX_LOC = s8.
- What the GPU side would need: every reader of s[p] must see the record's dword per record. Two options:
  - (a) Translate reads of the patched user SGPR into the BaseVertex / BaseInstance built-ins (SPV_KHR_shader_draw_parameters, `shaderDrawParameters`), and the id VGPR into VertexIndex - BaseVertex (InstanceIndex - BaseInstance). Every value then matches the hardware for any use. DrawIndex does the same for the draw-index SGPR (`Path::DrawIndex`, `:35`).
  - (b) What fb55cb2c0 did for mesh draws: put the argument record's device address in push constants and load the SGPR's value from the record in the shader.
  - Either way the compiled stage stops depending on the record values, so one stage serves every record and the record buffer can stay on the GPU. GE_INDX_OFFSET (`IndxOffset`) needs the same, since a GPU record can't have X added.

**"non-vertex path" (`Path::NonVertexPath`)**

- `IndirectDraw.cpp:32-34`: `meshPath = mesh && !tessellation && !rectList`.
  - `meshGpuSide` holds only for an indexed draw with `count == 1`, no count buffer, and no base-vertex, start-instance or draw-index location.
  - Otherwise any `stages.path != Vertex` or `rectList` fails `NonVertexPath`.
- The matching refusal in Graphics: `Graphics/src/Draw.cpp:1026`, `Require((!state.stages.mesh || draw.indexed) && !state.stages.tessellation && !state.rectList, "indirect draw on a non-vertex path must be resolved by the driver")`.
- Paths (`Graphics/src/State.cpp:849`): Tessellation (HS_EN), or Geometry (GS_EN or a vertex program that needs a workgroup), which is emulated as a mesh program (`State.cpp:880-899`, `MeshConfiguration`).
- Why each needs the CPU:
  - **Tessellation:** the TCS/TES are compiled with the draw's index address, index count and instance count in their compile context. See `Execution/src/Driver/Draw/DrawCapture.cpp:26`, `GraphicsCompileContext{... {indexAddress, indexCount, indexSize, instanceCount}}`. The CPU path rebuilds them per record with that record's `direct` parameters (`Draw.cpp:464-468`, `:487`).
  - **Rect lists:** they are expanded by driver-built tessellation stages (`buildRectList`, `Draw.cpp:382-399`, `DrawRectangle`).
  - **Mesh path:** the program takes its index count and first index from push constants. Since fb55cb2c0 it can instead take them from an argument record, but main uses that only in the `meshGpuSide` case. Everything else (non-indexed, `count > 1`, a count buffer, a patched SGPR) goes to the CPU. There the hidden index-buffer words are rewritten per record (`setMeshIndexBuffer`, `Draw.cpp:148-154`, `:479-482`) and the front program is rebuilt.
- What the GPU side would need:
  - Mesh path: extend fb55cb2c0's argument record and `MeshArguments.comp` to non-indexed draws (auto index from first vertex and count), to `count > 1` and count buffers (vkCmdDrawMeshTasksIndirectCountEXT with one prepared record per draw plus DrawIndex), and to patched SGPRs (load them from the record like the index count).
  - Tessellation: the TCS/TES emulation would have to read index count and instances from a record at run time, not from the compile context.
  - Rect lists: #5979 does this for rect lists without mesh or tessellation stages.
- Which sub-case Village's 2389 draws per 10 s are can't be read from the profile line. `APS5_TRACE_INDIRECT_DRAWS=1` (`DrawPrecheck.cpp:31`) prints the decision per draw, but not the stage path. One extra field in that line (`graphics.stages.path`, `rectList`) would tell.
- Both reasons rebuild the front program on every record. For NotFolded, the patched word is in program 0 by construction (`sgprOf`). For the mesh path, `patched.insert(0)` (`Draw.cpp:481`).
- Note also the second-level refusals inside Graphics, `Graphics/src/Draw.cpp:2104-2140`: pending image, pending label or copied write, not imported, disabled. They read the records on the CPU in `Graphics::Draw` for draws the driver already classified GPU-side. Those draws keep the normal driver path and do insert draw entries.

### Q2. The exclusion

- **The line:** `DrawCapture.cpp:139`, `if (useDrawEntries && !drawHit && !(drawParameters.indirect && indirectCpu) && (verifyHit || admitDrawKey(...)))`.
- **Where it came from:** 29b4601564 (devilismyfriend, 2026-09-27). The comment it carried, removed later with the no-comments rule, said: "A miss inserts its stages' fresh variants (the CPU path of an indirect draw recompiles on patched words below: nothing of it is kept)".
- **The CPU path itself:** `Draw.cpp:430-506`, which reads, patches and draws per record.
- **Why it was excluded:** the variants built before the record loop (`Draw.cpp:312-357`) are compiled on the register words. The stages actually drawn are rebuilt per record on the patched words (`Draw.cpp:483-490`) and were never stored. An entry would have held only the register-word variants, and a hit would still rebuild every patched stage, so nothing was cached.

**What in a captured stage depends on the arguments (per record):**
- **Patched user words** (`Draw.cpp:455-463`): base vertex (`vertexOffset` for 20-byte records, else `firstVertexOrIndex`), start instance, and the draw index (the record number). They end up in the patched stage's push constants. If the stage uses them as an address or offset, they also change its capture's reads; the prototype's test covers that.
- **Tessellation stages:** rebuilt per record with `direct` in their compile context (`Draw.cpp:469-478`, `:487`):
  - index address = INDEX_BASE + firstIndex × size;
  - index count clamped to INDEX_BUFFER_SIZE;
  - instances.
- **Mesh path:** the hidden index-buffer words come from `direct` (`Draw.cpp:479-482`).
- **Vertex info:** the patched program's vertex info is decoded again on the patched words (`Draw.cpp:486`).
- **Not in the stage:** the fold into the Vulkan draw's first vertex / instance (`Draw.cpp:491`, `IndirectDraw.cpp:15-22`) and the record's counts (`direct`, `Draw.cpp:469-478`). These go into the draw call and are recomputed every record anyway.

**Would keying or validating an entry on those words make a hit correct?** Yes, under these conditions (the prototype does all of them):
1. The argument words are still read at every draw, where they are now: after this queue's queued labels, through the flush hook (`Draw.cpp:442-446`).
2. Per record and patched program, the stage's inputs are compared exactly:
   - the record's argument words;
   - the program's user words after patching, which include the mesh hidden words;
   - the compile-context draw parameters (`direct` for TCS/TES, else the packet's).
3. The kept stage's own captured reads are validated like any draw variant (`validateVariant`, `Dispatch/VariantValidation.cpp:81`). A patched word can redirect the capture to memory the register-word capture never read.
4. The base entry still hits as before: same register key, every pre-loop variant validated.

**What would make it wrong:**
- Not reading the arguments, for example trusting words or a hash taken at insert.
- Comparing the arguments but not the patched capture's reads.
- Reading the arguments before queued labels or a producing batch land (a WRITE_DATA, or a dispatch earlier in the same submission). The prototype leaves the read where it is, and its test covers WRITE_DATA.
- Keying a multi-draw on the record count alone. The prototype keys per record, so a new count only changes how many records are drawn. A count buffer is read at every draw as before (`Pm4::ReadDrawCount`).
- Arguments written by GPU work queued *after* the draw can't matter: the CP reads them at the draw too.
- GPU stores the driver doesn't see (FLAT/GLOBAL stores without udmabuf) are wrong on the CPU path today, cached or not.

### Q3. The other reuse paths

- **Draw recipes:** `Draw.cpp:509`, `if (registerKey && !drawParameters.indirect && !patchedStages && Graphics::DrawRecipes())`.
  - Every indirect draw is excluded, the GPU-side ones too. The CPU path returns earlier (`Draw.cpp:505`) and never reaches it.
  - The replay can't take one either: `Graphics/src/Draw.cpp:2569`, `Require(!draw.indirect, "a draw recipe covers direct draws only")`. `DrawWithRecipe` has no argument import or record rewrite.
  - The reason differs from the entry exclusion: a recipe replays a draw recorded from fixed parameters.
  - Each CPU-path record does end in a direct `localDevice->Draw(graphics, direct, stages, snapshots)` (`Draw.cpp:501`), so recipes per record (keyed by the record stages) are possible in principle. Neither main nor the prototype does it.
  - `!patchedStages` (56bb6377d) also keeps stages whose data words were refreshed away from recipes.
- **Data-only hits:** `Draw.cpp:100`, `if (drawDataHits() && !drawParameters.indirect)`.
  - Every indirect draw is excluded. This came with 58b6ddf72 (Michon, 2026-10-13), whose message gives no reason. The candidate validation also needs `stages.path == Vertex` (`DrawLookup.cpp:208`).
  - For CPU-path draws this was moot on main: they never insert, so no shape entry existed from them.
  - With the prototype, a data hit would also have to bring the record stages over. They are keyed by the user words, which differ by definition, so the exclusion stays.
- **Stage data hits** (56bb6377d, `EqualData` in `lookupDraw`): they apply to the base entry's variants of any hitting draw, CPU-path ones included with the prototype. The prototype's record stages accept only `EntryOutcome::Equal`.

**What it does:**
- **Insert:** `DrawCapture.cpp` drops the CPU-path exclusion unless `APS5_NO_INDIRECT_DRAW_ENTRIES=1` is set, so the base entry (decode plus register-word variants) is inserted like any draw's.
- **Keep:** in the CPU record loop (`Draw.cpp`), every stage built on a record's patched words is kept on the draw's entry (`DrawEntry::indirectStages`, at most 64), as a `DispatchVariant`. Its runs and words are the capture's regions plus the decode reads, as `cacheDrawStages` builds them. It is stored with its inputs:
  - program index and push offset;
  - the record's five argument words;
  - the compile-context index address, index count, index size and instance count;
  - the program's user words after patching.
- **Reuse:** a later draw whose base entry hits looks up each patched program's inputs. On an equal entry it validates the stage's own runs with `validateVariant` (pending writes, queued labels, pending images, forget serial, contents). On `Equal` it takes the kept compiled result and its regions instead of decoding and capturing; otherwise it builds the stage again and keeps it.
- **Carry-over:** `insertDrawEntry` and the hit-rank rotation carry `indirectStages` over, as they do for recipes.
- **Counters:** the `[draw-cache]` profile prints "CPU-path indirect record stages (10 s): N reused, M built".

**The test** is `tests/execution/IndirectDrawEntries.cpp`. It's registered by the execution-test glob, plus `agc_driver_indirect_draw_entries_off` (`APS5_NO_INDIRECT_DRAW_ENTRIES=1`) and `_inline` (`APS5_PIPELINED_DRAWS=0`) in `CMakeLists.txt`. It goes through `sceAgcDriverSubmitDcb` with DRAW_INDIRECT records:

1. **"Patched SGPR not folded"** (triangle list; the vertex shader exports s8 as depth, BASE_VTX_LOC = s8, and the register word is a clipped depth):
   - four identical draws insert once, hit twice, and reuse the record stage twice;
   - the result matches a direct draw of record {3, 1, 0, 0};
   - the record's vertex count going 3 → 2 rebuilds the stage and draws nothing;
   - its patched word going 0 → clipped rebuilds and draws nothing;
   - back on the first record, all four reuse;
   - a draw of the clipped record, then a WRITE_DATA of its first vertex to 0, then the same draw: the second draws the triangle, so the post-write record is what's read.
2. **"Non-vertex path"** (rect list, primitive 17): the same sequence, against a direct rect-list draw.
3. **Its own reads:** a vertex shader that loads its depth through the pointer s[8:9], with the record patching the pointer's low word. Changing only the depth the record points at, while the register's depth is unchanged, keeps the base entry hit but rebuilds the record stage and draws nothing.

How to read it:
- On a hit, all three captures per draw are gone: the two register-word stages and the record stage. Decode is gone too.
- When the record changes every draw, the base entry still saves two captures and the decode, and the record stage is built (+1.8 µs of vectors for keeping it).
- Village's packets spend capture 232 + recompile 107 + decode 25 µs on queue 0, against ~12.8 µs here, so the share a hit removes there is far larger than this synthetic stage's.

Two things found while measuring:
- **The first stage list cost too much.** It deep-copied up to 64 kept stages and compared every old stage against every new one on each attach. That made the always-changing case slower than main: 43.2 against 38.8 µs in one run. The pushed head keeps `shared_ptr` stages and compares old stages only against the newly built ones.
- **Don't measure with a linear target in plain memory.** It is not resident, so every draw is synchronous (`[draws] ... 25068 synchronous avg 333 us ... because: non-resident target 25068`). That hides the driver-side difference: about 392 against 428 µs per draw.

## 3. What the prototype doesn't cover, and what an upstream version would still need

- **No GPU-side path for either reason.** The records are still read on the CPU at every draw. That wait for the producing batch is in Village's "argument reads 270.4 ms" per 10 s. The prototype only removes decode, capture and recompile after the read. Taking these draws to the GPU needs the built-in or record-load translation in Q1.
- **Multi-draw:**
  - Each record keeps its own stage, at most 64 per entry, so a draw with more than 64 differing records always rebuilds the rest.
  - Records are still drawn one Vulkan draw each, with no vkCmdDraw*IndirectCount batching.
  - Two identical records in one draw are built twice: reuse consults only the stages kept before the draw.
- **GPU-written arguments** are handled as before: read at the draw, after the queue's labels, through the flush hook. A title whose GPU writes new arguments every frame rebuilds every patched stage every frame, though its base entry still hits (decode and the register-word stages are saved). The test covers a CP WRITE_DATA, not a compute producer.
- **Keyed strictly on argument words, as specified.** A record whose count alone changes rebuilds the patched stage, though that stage doesn't read the count. A finer key (only the words that reach the stage) would avoid that.
- **Not accounted.** Kept record stages aren't counted in the draw cache's variant and byte totals (`accountDrawVariant`), and have no LRU of their own beyond the 64 cap. They go away with their entry.
- **No verify mode.** `APS5_VERIFY_DRAW_ENTRIES` turns hits off, so record stages are neither reused nor compared. An upstream version should build and compare like the other verify modes.
- **Wasted miss work.** On a miss the base entry still compiles the patched program once on the register words, a variant used only for classification and as a fallback. Skipping that capture would save one capture per patched program on every miss.
- **A copy per record.** A reused stage is copied into the draw's result slot (`result = *compiled`), as the miss path does. Pointing the stage at the kept result, as hits do for `programResults`, would avoid copying the compiled module per record.
- **Recipes and data-only hits** still exclude every indirect draw (Q3). #1896's pipelined loop would need the same reuse.
- **Village's sub-case is unknown.** The rect list stands in for "non-vertex path"; a mesh-path (NGG geometry) indirect draw was not built in a test here. The mechanism is the same: the front program is the patched stage and the hidden index words are part of its inputs. It is untested.
