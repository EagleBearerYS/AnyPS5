## The fix (`ResourceTracker.cpp`)

**1. Planning.** `PlanTableColumns` now does the following:
- It saves the tracker state that planning changes: `m_sources`, `m_tableColumns`, `m_tablePlanningReads` and `m_tablePlanningMemory`. Planning changes no IR.
- It runs one planning pass, `PlanTableColumnPass`, which is the old body.
- It then asks `PlannedWithinLimits()`. If the answer is no, it:
  - takes `LargestSelectedGroup()`;
  - adds that group's image handles to a new `m_unselectedHandles` list;
  - restores the saved state and plans again.

  It repeats this until both fit or no group is left. If none is left, `Collect` refuses as before.

**2. Unselected reads.** In `TryMakeTableColumn`, a handle in `m_unselectedHandles` does not get `selected`/`selection`. That is the only change to the column itself.
- On the next pass, `InternSource` therefore dedupes all of that heap's reads into one column, exactly as `main` before #6243 did.
- The existing shared-column update makes that column the union of their key domains, `unkeyed` if any read is unkeyed, and the largest `maxKey`.
- Because the pass is rerun, no orphaned per-key or selection sources are left in the plan.

**3. Groups.** A group is the set of planned column sources that are equal (`TableColumn::operator==`) once `selected` and `selection` are cleared. Only groups with at least two sources and at least one selected column count. The largest goes first; on a tie, the first in plan order. Every plan pointing into the group is re-pointed, because all their handles are replanned unselected.

**4. Estimate (`PlannedWithinLimits`).** It walks the image instructions the way `Collect` does:
- the same skips: BVH, non-image kinds, `planningOnly` and table-planning memory;
- for images, the planned column source from `FindTableColumn`, or else the direct handle;
- for samplers, the planned sampler column source, or else the direct sampler handle.

It then counts what `AddImage` and `AddSampledPair` would add:
- **Images** are keyed by `ImageKey()`/`SameImageKey()`. I factored those out of `AddImage`, which now uses them too, so the estimate and `Collect` key images identically. The field assignments are unchanged.
- **Pairs** are (image, sampler).

It is read-only. In particular it doesn't call `MakeSource`, which can allocate IR constants.

**What the estimate errs toward:**
- **Images are exact.** A direct image source is the handle's eight words compared with `EquivalentValue`, as `GetHandle` + `InternSource` compare them.
- **Pairs can only be overestimated.** A direct sampler is told apart by its raw handle words (`SameHandle`) plus whether the sample adjusts. That comes before the dword-3 canonicalization `MakeSource` applies, which can only merge samplers further.
- **Unvalidated handles are counted.** A handle `Collect` would reject is still counted rather than skipped.

So the estimate can only push toward merging, never toward a refusal that `main` before #6243 wouldn't have had.

**5. A shader within both limits** runs exactly one planning pass, as now.

## The test (in `tests/ShaderMemory.cpp`, next to #6243's selected-record tests)

There are two new ctests on `agc_shader_memory_tests`: `agc_shader_selected_records_image_limit` (`--selected-records-image-limit`) and `agc_shader_selected_records_pair_limit` (`--selected-records-pair-limit`).

**The shader.** `TableManyKeyCode(first, second, twoSamplers)` builds a wave64 compute shader. Each read:
1. loads its key from its own SRT word (`s_load_dword s16, s[0:1], 0x50+4·read`, so the CPU evaluates it, as in `verifyImageTableSrtKey`);
2. computes `s_lshl_b32 s16, s16, 5` and `s_buffer_load_dwordx8` of the T# from heap A (`s[4:7]`) or heap B (`s[40:43]`);
3. runs `image_sample_lz`, with one sampler or with two (`s[8:11]`, `s[12:15]`);
4. accumulates the result, which is stored at the end.

I checked the encodings with llvm-mc. The heap has 128 distinct T#s, and keys run from 2 upwards.

**Image test:**
- **64 reads:** 64 images, all selected tables, and 64 pairs. #6243's split is kept at the limit.
- **65 reads:**
  - one image, table 0, one pair;
  - its column is unselected, with `selection` 0, keyed (not `unkeyed`) and holding 65 key domains;
  - the compiled snapshot holds one table in which keys 2, 34 and 66 bind `heap[key]`, while keys 1 and 67 are "outside".
- **Two heaps, 40 + 30 reads (70 images):** 31 images. Heap A's 40 reads merged into one unselected table with 40 key domains, and heap B kept its 30 selected tables. So the largest heap goes first, and the split is kept where it fits.

**Pair test:**
- **32 reads × 2 samplers:** 32 selected tables and 64 pairs, kept.
- **33 × 2:** one image and two pairs, with the same column and snapshot checks (keys 2, 18, 34 bound; 1 and 35 outside).

#6243's "image table key union", "late key" and "unkeyed access" tests are unchanged and pass, in `agc_shader_bindless`.

## FormatVersion: no bump (stays at 37 on main; 41 not used)

- **Shaders that planned before plan identically.** A shader within both limits runs the same single pass, and the estimate is read-only. The fingerprint comparison above confirms this over the whole suite.
- **Only refused shaders change.** Merging happens only for a shader that `main` refused with "image resource limit exceeded" or "sampled image/sampler pair limit exceeded". Such a shader never planned.

**Is a refusal stored anywhere a later run reuses?** No:
- **Disk cache:** `ShaderDiskCache::StorePlan` runs only after `ResourceProgram` returns. A throw skips it (`Recompiler.cpp`, the `try` around `ResourceProgram resource(...)`, ~445–462).
- **Failure memo:** it is in memory only. `CachedSource::planFailure` and `emissionFailures` live in the per-process source cache, and `APS5_NO_FAILURE_MEMO` only turns that off (`Recompiler.cpp` ~330 and ~386–459).
- **Pipeline journal:** it records only compiled pipelines (`RecordGraphicsPipeline` from `Pipeline.cpp`, `RecordComputePipeline` from `VulkanDevice.cpp`), which a refused shader never gets.

Also, the cache's source version is a SHA-256 manifest of the recompiler sources, so this change already moves the cache to a new directory.
