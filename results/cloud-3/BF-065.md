# BF-065: VideoOut's present loop and the AGC teardown at close

cloud-3, 2026-10-17. Upstream main was 66702f1cf, read and built here: CI Release flags, gcc, lavapipe (Mesa 25.2.8), Xvfb. 32ac24cb32 was compared from the code only.

**The short version:**
- On main and on 32ac24cb32, the present loop cannot present while AGC tears down: the presenter thread runs the teardown itself, after its loop has ended.
- The PC's stack fits that teardown, not a present-time flush:
  - `presentLoop` → `AgcDriverShutdown_nid_postfix` → `Driver::stop` → `device.Reset()` → `~VulkanDevice` → `State::~State` → `Recorder::Sync` → `Submit` → `endOpenRenderPass`.
  - I reproduced this exact path on lavapipe with `APS5_NO_GPL=1`.
- `APS5_NO_GPL=1` matters for a concrete reason: with GPL off, draws use real `VkRenderPass`/`VkFramebuffer` objects. `endOpenRenderPass` then issues `vkCmdEndRenderPass` against them. With GPL on, it issues `vkCmdEndRendering`, which reads no framebuffer object.
- So the fault is an object of the last draw's still-open classic render pass being freed before teardown ends that pass. I did not find which object. The color targets, framebuffer and pipeline are kept by the batch, and the depth surfaces outlive the recorder.
- **No test or fix is pushed.** The race the task describes doesn't exist on main, so there is no red to turn green. Branch `fix/videoout-stop-presenter-before-teardown` was not pushed. What would find the freed object is at the end.

## 1. The shutdown order on main 66702f1cf

### Registration (who runs first)

- `VideoOutDriver::VideoOutDriver` calls `AgcDriverWaitIdle_nid_postfix()` (core/libs/prx/libSceVideoOut/src/VideoOutDriver.cpp:283). That constructs `Driver::Get()`, whose constructor registers AGC's libc shutdown (core/libs/prx/libSceAgcDriver/Execution/src/Driver/Lifecycle.cpp:144).
- Only then does VideoOut start the presenter (VideoOutDriver.cpp:286) and register its own shutdown (VideoOutDriver.cpp:297).
- `LibcRunShutdown_nid_postfix` runs the callbacks in reverse (core/libs/prx/libc/src/Process.cpp:88). So VideoOut's `Shutdown` always runs before AGC's.
- The only other registration is AudioOut's (AudioOutShutdown.cpp:23), which doesn't touch AGC.

### Close by the window (SDL_QUIT), the PC's case

1. The presenter polls `SDL_QUIT`, calls `LibcRequestExit_nid_postfix(0)` and throws `ProcessShutdown` (VideoOutDriver.cpp:670). Any flip already taken from the queue is dropped, not presented.
2. The presenter leaves the loop and calls `AgcDriverShutdown_nid_postfix()` itself (VideoOutDriver.cpp:741). It then calls `hdrProbe.Release()` and `window.Destroy()` (VideoOutDriver.cpp:747).
3. Concurrently, `LibcRequestExit` starts a detached thread: `LibcExitWithoutHandlers` → `LibcRunShutdown` (Process.cpp:173). That thread runs VideoOut's `Shutdown`, which sets `stopping`, requests stop and blocks in `presentThread.join()` (VideoOutDriver.cpp:330) until step 2 has finished.
4. AGC's own callback then finds `stopped` and returns.

### Close by the guest (`exit`, return from main)

`LibcExit` runs `CxaFinalize`, then `LibcRunShutdown` (Process.cpp:167), then `std::exit`.
- VideoOut's `Shutdown` stops and joins the presenter.
- The presenter finishes the flip it is in, sees the stop token, leaves the loop, and again runs the AGC teardown at VideoOutDriver.cpp:741.
- `~Driver` at `std::exit` finds `stopped`.

### What the teardown does, on the presenter thread (`Driver::stop`, Lifecycle.cpp:103)

1. `LibcRequestShutdown`; `stopping = true`; the workers' pending submissions are cleared.
2. The queue workers are joined (Lifecycle.cpp:119). A worker finishes the submission it is executing first.
3. `DrawPipeline::Queue0().Stop()` (Lifecycle.cpp:122).
4. `StopWorkerSampler`, `CloseRegistrationPreparation`, `Graphics::StopPipelineLibraryWorker()` (Lifecycle.cpp:125).
5. The GPU mutex is taken and `device.Reset()` is called (Lifecycle.cpp:127). If that was the last reference, `VulkanDevice::State::~State` (core/libs/prx/libSceAgcDriver/Execution/src/VulkanDevice.cpp:694) runs:
   1. The pipeline-journal replay is cancelled and waited for (VulkanDevice.cpp:697).
   2. `vkDeviceWaitIdle` (VulkanDevice.cpp:711); in-flight present slots are retired and settled.
   3. `PublishAllShadows(context, Teardown)` and `recorder->Sync()` (VulkanDevice.cpp:729–730).
      - `Sync` → `Submit` (core/libs/prx/libSceAgcDriver/Graphics/src/Recorder.cpp:3285) → `if (open->renderPass.open) endOpenRenderPass();` (Recorder.cpp:3296).
      - → `EndRenderPass(context, open->commands)` (Recorder.cpp:1414). **This is the PC's faulting frame.**
   4. `DestroyShadows`; then `recorder.reset()` (VulkanDevice.cpp:736). `~Recorder` frees the spare command buffers (Recorder.cpp:1173).
   5. `ClearCachedPipelines` (VulkanDevice.cpp:739); the depth, multisample and texture caches.
   6. `pipelineCache.reset()` (VulkanDevice.cpp:769). **This is the pipeline cache's final save** (`~PipelineCache` → `save(true)`, core/libs/prx/libSceAgcDriver/Graphics/src/PipelineCache.cpp:83).
   7. Fences, semaphores, swapchain; `vkDestroyCommandPool` (VulkanDevice.cpp:791); `vkDestroyDevice`.
6. After the device: `FlushPipelineJournal`, `ShutdownGuestBufferWorkers`, `StopCompareHelpers`, `ShaderDiskCache::Shutdown`, the logs.

### The window

**The window the task describes doesn't exist on main.** That window is `presentLoop` still calling into the recorder (a present-time flush: `processFlip` → `AgcDriverPresentBuffer` → `Driver::Present` → `PresentDisplayBuffer` → `SubmitRecorded(false)`, VulkanDevice.cpp:3164) after its command buffers or pool are freed.
- Every route into `Driver::stop` runs on the presenter after its loop ended, or on another thread after the presenter was joined.
- The only callers of the AGC teardown are VideoOutDriver.cpp:741, the libc callback (Lifecycle.cpp:144) and `~Driver`.
- The pool and command buffers are freed only inside step 5, under the GPU mutex.

**The window that does exist** is between two points:
- the last draw that left its render pass open: `recorder->LeaveRenderPassOpen` (core/libs/prx/libSceAgcDriver/Graphics/src/Draw.cpp:1872);
- the teardown's `Sync` (step 5.3), which is the first thing that ends that pass once shutdown has begun.

At close, that window spans all of step 2's worker join, steps 3–4, and step 5.1's journal-replay wait, and guest threads keep running throughout. The pass's framebuffer, pipeline and color targets are held by the batch's `Kept` (Draw.cpp:1506), so they live. What else the pass reads at `vkCmdEndRenderPass` is where the freed object must be. I ruled out the depth views: depth surfaces are freed only in `ClearDepthSurfaces`, after `recorder.reset()`. I did not get further.

**Why the PC's frame fits teardown.** The stack has only two named frames: `endOpenRenderPass` and `libSceVideoOut.prx+0x3c5b7` "in presentLoop's `TimedWait::WaitUntil`". With `-g1` there is no inline information, so the line given for a return address inside `presentLoop` is not reliable. The call just before 0x3c5b7 decides it:
- if it calls `AgcDriverShutdown_nid_postfix`, the crash is the teardown path above;
- if it calls `AgcDriverPresentBuffer_nid_postfix`, it is a present.

On main only the first can reach `endOpenRenderPass` after shutdown has started.

### Why `APS5_NO_GPL=1`

- `APS5_NO_GPL` turns off graphics pipeline libraries (VulkanDevice.cpp:1437).
- With them off, `Pipeline` is built with `dynamicRendering(context.graphicsPipelineLibrary)` false (Graphics/src/Pipeline.cpp:294). Draws then begin real render passes on a `VkFramebuffer`, and `EndRenderPass` records `vkCmdEndRenderPass`.
- With GPL on, `vkCmdEndRendering` is recorded instead, which reads no render pass or framebuffer object.

That separates the 2-of-2 NO_GPL closes from the 0-of-9 mostly-GPL closes better than the timing guess does. A longer teardown with monolithic pipelines may also be true: the worker join in step 2 waits out a submission that compiles monolithic pipelines. That would only stretch the window.

### 32ac24cb32 compared with main

- **VideoOutDriver.cpp, Presentation.cpp, EntryPoints.cpp, `~State` and `~Recorder`:** identical. The VulkanDevice.cpp and Recorder.cpp hunks are elsewhere: device features, compute replay, and `FlushForAccess`'s publish scope.
- **`Driver::stop` on 32ac24cb32** lacks two stops:
  - `DrawPipeline::Queue0().Stop()`, added by 966da79fc "stop and join the draw pipeline's committer at shutdown";
  - `Graphics::StopPipelineLibraryWorker()`, added by 0ba4f056c.
  - So there, the draw committer can still run queued commits after `device.Reset()`. A pipelined draw commit holds its own `localDevice` reference (core/libs/prx/libSceAgcDriver/Execution/src/Driver/Draw/Draw.cpp:582), so a queued commit can keep the device alive past `stop`. `~State` would then run on the committer when it drops that reference, without the GPU mutex.
  - That would fault on the committer's thread, not 'presenter', so it doesn't explain this crash. It is a reason the PC tree should carry 966da79fc anyway.
- **`Process.cpp` on 32ac24cb32:** `StartExit` runs `LibcRunShutdown` before `CxaFinalize`; main runs it after. It's the same thread either way.
- The PC tree 7b093d5fbc is not on the fork or on upstream, so I could not read it.

## 2. What ran here (lavapipe, main 66702f1cf)

- **The teardown path, under gdb.** `APS5_NO_GPL=1 agc_driver_draw_cache_reuse_tests` with breakpoints on `Driver::stop` and, once stop has started, on `Recorder::endOpenRenderPass`. The draws' last pass was still open at shutdown and was ended by the teardown:

- **The same test under the Khronos validation layer** (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, `APS5_NO_GPL=1`): rc=0. There were 2 validation messages, both `VUID-VkDeviceCreateInfo-pNext-pNext`: the layer (header 275) doesn't know a newer device-create struct (VkStructureType 1000574000). There was no destroyed-object or threading error at teardown.
- **`video_out_flip_tests`** under Xvfb (`SDL_VIDEODRIVER=x11`) with the validation layer and `APS5_NO_GPL=1`, modes lifetime, aftergpu, present, backtoback, pacing and labels: all rc=0, with only the same pNext message.
  - With the CMake default `SDL_VIDEODRIVER=offscreen`, every flip test skips here (rc 77, "Vulkan support is either not configured in SDL or not available in current SDL video driver (offscreen)").
- **An aside:** `video_out_flip_tests eop` fails on main here, with and without the layer: "RELEASE_MEM invalid packet size", then "EOP packet did not finish its label and reserved flip". The test builds a 7-dword RELEASE_MEM. Under CI's offscreen driver it skips, so the failure goes unseen there.

These runs only show that ending an intact open classic pass at teardown is clean on lavapipe. The PC's freed object is something these simple draws don't create.

## 3. The fix

**None is pushed.**
- The suggested fix, "stop and join the present loop before the recorder and device are torn down", is already what main does: the presenter is the thread that tears down, after its loop.
- The alternative, "have the present-time flush take the lifecycle lock and skip once teardown has started", has nothing to guard: no present-time flush can run after `Driver::stop` begins.
- A test that holds the presenter inside its flush and then starts the close would be green on main, so it has no red half.

**Saving the pipeline cache at the start of shutdown is safe and would bound the loss.** Today the final save is in `~PipelineCache` (PipelineCache.cpp:83), reached from `~State` after the recorder teardown (VulkanDevice.cpp:769). A crash in step 5.3 skips it, and the work since the last periodic save is lost: at most 10 s (`PipelineCache::run`, PipelineCache.cpp:254).

Calling `PipelineCache::SaveNow()` (PipelineCache.cpp:250) at the top of `Driver::stop`, while the device is alive, is safe:
- `save` takes the cache's snapshot lock around `vkGetPipelineCacheData`/`vkMergePipelineCaches`, and the file path's lock;
- the device and cache stay alive until `device.Reset()`;
- pipelines compiled later in the teardown are still written by the final save when the teardown completes.

The cost is one extra `vkGetPipelineCacheData` and file write per close. It needs a small accessor from `Driver` to the device's cache. I didn't add it: it isn't the crash fix, and the task asked only whether it is safe.

## 5. What would find the freed object (for the PC)

1. **Disassemble the call before the return address:** `objdump -d --start-address=0x3c590 --stop-address=0x3c5c0 libSceVideoOut.prx` on the PC's build. The `call` just before 0x3c5b7 names either `AgcDriverShutdown_nid_postfix` (teardown) or `AgcDriverPresentBuffer_nid_postfix` (present).
2. **Close Village once with `APS5_NO_GPL=1` and the Khronos validation layer** (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`). Core validation checks the command buffer before the call reaches the driver, so if a bound object was destroyed, a message of this form prints before the crash: "vkCmdEndRenderPass(): ... VkCommandBuffer ... is invalid because bound VkFramebuffer/VkImageView/VkRenderPass 0x... was destroyed". That names the object's type, which points to its owner.
3. **The PC tree's `Driver::stop`:** whether 7b093d5fbc has 966da79fc and 0ba4f056c.

With the destroyed object's type known, the fix is to keep that object in the draw's `Kept` (Draw.cpp:1506), or to end the open pass before its owner frees it. A lavapipe test can then destroy that owner while a classic pass is open and check the end under the validation layer.
