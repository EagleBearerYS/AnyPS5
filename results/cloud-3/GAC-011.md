## 4. #6168's follow-up commit (in neither branch)

#6168 is still open, and its head is now **0e15b9be9714e8b702f6a326ad5ce6fe103c86f9**, "fix(agc): reuse the current detiler descriptor pool once its batches complete". It was committed at 02:17 +0200, 73 minutes after the picked 8e56f5610, and is not in upstream main 8cd937e29.

**What it changes:**
- `TextureDetilerDescriptors.cpp`: the search for a reusable pool, `for (std::size_t step = 1; step < ring.pools.size(); ++step)`, becomes `step <= ring.pools.size()`, so the current pool is checked too.
- A test check:
  - a `descriptorPoolCount` accessor (`tests/GraphicsTests.hpp`, wired up in `tests/Graphics.cpp`);
  - a block in `tests/TextureDetiler.cpp` requiring that 3 × 64 dispatches with no batch in flight leave the pool count unchanged.
- No CMake change.

**What fc8f858f6b does without it** (from reading the code; I ran nothing here):
- The search skips the current, full pool.
- `CompletedThrough()` is a prefix (everything before the oldest batch in flight), and the current pool carries the newest serial. So if the current pool's batches have completed, every other pool's have too.
- With two or more pools, the search therefore still finds a reusable pool.
- The only difference is a ring with a single pool. When that pool fills, the ring always gets a second pool, even if every batch completed. From then on it alternates between the two.
- **Cost:** at most one extra 64-set pool for each of the detiler's three rings (texture, image, CMASK).
  - There is no growth.
  - No pool is ever reset while its batches are in flight.
  - The OOM 8e56f5610 fixes (one new pool per 64 detiles while work stays in flight) stays fixed.
- **If 0e15b9be9 is picked onto this tree,** its new check won't run in the suite (§3).
