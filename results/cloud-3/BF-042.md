# BF-042: the open draw-cache PRs on BF-036's harness

Worker: cloud-3 (Linux, lavapipe). Machine: Intel Xeon @ 2.80 GHz, 4 cores, 15 GiB RAM. lavapipe from Mesa 25.2.8 (LLVM 20.1.2), GCC 13.3, Release build. One run at a time, otherwise idle, as `runner`.

## Summary

1. **On BF-036's harness as written, no PR can change anything. The per-draw re-capture it measured is a harness artifact.**
   - The harness's vertex shader loads its vertex-buffer table through `s[0:1]`.
   - The driver puts a vertex stage's user data at `s8`, after 8 hidden system words (`DrawDecode.cpp`, `hiddenUserWords = 8`; `firstUserSgpr` 8 for non-pixel stages). So the capture reads the table pointer as null: `APS5_SRT_DEBUG` prints "[srt] 12 reads through a null user-data pointer: zero words".
   - The vertex result therefore has `poisonedSrtReads = 12`. `CacheableResult` is false, so the vertex stage is never inserted.
   - Every lookup finds an entry whose vertex stage has no variant and misses with "layout (push offset)", in every arm: 73,604 of 73,784 lookups per 10 s on base, the rest "no entry".
   - BF-036's "both stages re-captured although only user data changes" was this, not the object V#.
   - The plain check still passes, because the output byte doesn't depend on what the vertex shader fetches.
2. **With the table read from `s[8:9]` (`DRAW_RECORD_COST_VERTEX_SGPR=8`) and the same objects every frame, main already hits.** Base gets 105,757 hits of 110,117 lookups per 10 s:
   - capture 1.7 µs and recompile 2.8 µs per draw;
   - worker CPU 33 µs, against 109 as written;
   - 84 µs per draw, now bound by the committer (78 µs CPU).
3. **When the per-object constant buffers move every frame** (`DRAW_RECORD_COST_OBJECT_SETS=4`: 8,192 distinct V#s, more than the 4,096-entry cache), **main misses every draw, and none of the three PRs changes that:**
   - every lookup is still "no entry";
   - capture 34–43, recompile 27–33 and key/lookup/validate 41–46 µs per draw;
   - 138–153 µs per draw.

   This is the draw shape the task described: only the object V# in `s[4:7]` changes. Here is why each PR misses it:
   - **#5609's relocation** keys on user words used as base pointers for scalar loads. Here the V# sits in the user SGPRs as a descriptor. Its `[draw-relocate]` line never printed: fewer than 100,000 alias lookups in the run.
   - **#5656** compares only the user words a stage reads, but the pixel stage reads all of `s[4:7]`.
   - **#6539** relocates value words; a V# is not one.
4. **When the per-object data reaches the pixel shader only as a user word value** (`DRAW_RECORD_COST_OBJECT_MODE=value`, plus moving sets), **only #6539 hits.**
   - It relocates every draw: "100000 alias lookups … 100000 hits through a relocated entry".
   - Capture 0.0 and recompile 1.9 µs per draw; worker CPU 57 against 119–131; **80 µs per draw against 136–147**.
   - **#6539 also has a heap-use-after-free at process exit** in its pooled clones (12a5f02d10). Every #6539 run in this mode aborts at teardown with "malloc_consolidate(): invalid chunk size" or "corrupted size vs. prev_size in fastbins". ASan names the cause (§4). The draws themselves are right: the plain check passes before the abort.
5. **Static objects:** #5609, and #6539 which contains it, are 7–9 µs per draw faster than their own main, all on the committer (66–67 against 73 µs CPU).
6. **Always-miss moving case:** #5609 adds about 14 µs per draw (capture +8, recompile +6) and #6539 about 8 µs, against the same main.

## 4. #6539's heap-use-after-free at exit

ASan report, value mode, plain run:

```
ERROR: AddressSanitizer: heap-use-after-free … WRITE of size 8 … thread T0
  #0 std::_Sp_counted_deleter<DispatchVariant*, RelocationPool<DispatchVariant>::Take()::{lambda…}>…
  #1 RelocationPool<DrawEntry>::~RelocationPool()
  #2 __run_exit_handlers
freed by thread T0 here:
  #1 RelocationPool<DispatchVariant>::~RelocationPool()
  #2 __run_exit_handlers
previously allocated by thread T24 here:
  #1 std::_Sp_counted_deleter<DispatchVariant*, RelocationPool<DispatchVariant>::Take()::{lambda…}>…
  #3 Driver::relocateDrawEntry(...)
  #4 Driver::draw(...)
```

**The cause, in 12a5f02d10 ("a relocation reuses the variants and entries it clones"):**
- `variantPool()` and `entryPool()` are function-local statics. Their `shared_ptr` deleters capture `this` and push the object back into the pool.
- At exit, static destruction runs in reverse order of construction. `entryPool` is constructed first (in `relocateDrawEntry`), so `variantPool` is destroyed first.
- `~RelocationPool<DrawEntry>` then deletes its spare entries. Their pooled variants' deleters call `Return()` on the destroyed `variantPool`, writing into its freed `spare` vector.
- `~Driver` releasing pooled entries can hit the same thing.

In a normal build this corrupts the heap at shutdown, after the work is done. Making the pools immortal (`static auto* pool = new RelocationPool<T>`) or giving the deleters shared ownership of the pool would fix it; I did not build a fix.

## Which PR removes the per-draw capture and recompile for this draw shape

- **BF-036's draw shape (only the per-object V# base in `s[4:7]` changes):**
  - When the same objects come back every frame, main already removes the capture and recompile once the harness's vertex user data is in the right SGPRs.
  - When the constant buffers move every frame, **none of the three PRs does**: #5656, #5609 and #6539 all re-capture and recompile every draw.
  - #5609's base relocation would need V#s that the shader loads through a user-data pointer, not V#s held directly in user SGPRs.
- **Per-object data passed as a user word value:** **#6539 does.** Capture and recompile go to about 0. What remains:
  - on the worker: key/lookup/validate about 33 µs and decode about 12 µs;
  - on the committer: about 63 µs.

  It must not land with the exit-time use-after-free.
- **#5656:** no effect in any of the four configurations.

## Paragraphs for the PR Manager (plain data)

**#5656 (Raghav314, head 1b62f59277).** Measured with BF-036's queue-0 draw-record harness on lavapipe, at 2,048 draws per submission, split layout, against main f474fb7768 (which the head has merged). Across all four draw shapes, #5656 changed no draw-cache counter and no per-draw phase: same hits, misses and capture/recompile time as main.
- **Shapes tested:** the same objects every frame; objects whose constant-buffer V# (user SGPRs 4–7) moves every frame; per-object data passed as a user word value that changes every draw; and the original harness.
- **Why the value case misses:** every lookup is "no entry". The changed user word is part of the draw key, and no stage data hit is recorded.
- **Plain runs** pass in every arm.

**#5609 (TheAggie, head 09238da820).** Measured on the same harness against its merge base 244f41ed24.
- **Static objects:** draws are about 9 % faster (72.4 against 79.9 µs per draw). The gain is on the committer (66 against 73 µs CPU), probably from 18acdbf4a's dynamic-state skip.
- **Moving V# bases** (per-object constant-buffer V# held directly in user SGPRs 4–7, a new base every frame): the PR does not reuse cached stages. Every lookup is "no entry", no `[draw-relocate]` report appears, and capture plus recompile stay at about 76 µs per draw. That is about 14 µs more than its merge base on this always-miss path (152.9 against 138.7 µs per draw; capture +8, recompile +6).
- **Plain runs** pass.

**#6539 (TheAggie, head 12a5f02d10, which contains #5609).** Measured on the same harness against 244f41ed24.
- **Effect on the value case:** with per-object data passed as a user word value that changes every draw, the relocation hits every draw (100,000 of 100,000 alias lookups). Capture drops to 0 and recompile to 1.9 µs. Worker CPU falls from 123 to 57 µs, and the draw from 137 to 80 µs.
- **The use-after-free:** every run in that mode aborts at process exit with heap corruption ("malloc_consolidate(): invalid chunk size"). ASan reports a heap-use-after-free in `RelocationPool<DispatchVariant>`'s deleter, called from `~RelocationPool<DrawEntry>` during static destruction.
  - The DispatchVariant pool, a function-local static constructed after the DrawEntry pool, is destroyed first.
  - The spare entries the DrawEntry pool then deletes still hold pooled variants, and those return themselves into the freed pool.
  - The pools come from 12a5f02d10.
  - The draws themselves are correct: the plain check passes before the abort.
- **Moving V# bases:** no hits, and about 8 µs per draw slower than its merge base.
