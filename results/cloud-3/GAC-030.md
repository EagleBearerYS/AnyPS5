## 1. The fix

**Root cause.** These are main's lines at f633042df.

- `decodeSampleLocations` (State.cpp:475–490) sets `state.sampleLocationGrid` when any pixel of the guest's 2x2 pattern differs from pixel 0. `PA_SC_AA_SAMPLE_LOCS_PIXEL_X0Y0_*`, X1Y0, X0Y1 and X1Y1 are read in that order, so pixel 0 is X0Y0.
- `ValidateSampleLocations` (Pipeline.cpp:120) then required a 2x2 grid for the draw's sample count. That is `context.sampleLocationGridSampleCounts`, which VulkanDevice.cpp:1271 sets only when `maxSampleLocationGridSize` is even in both directions.
- The RTX 3070 Laptop GPU reports 1x1 for every count, so Village's 2x checkerboard threw before its title.

**What the commit changes.**

- **Pipeline.cpp:118, ValidateSampleLocations.** The grid `Require` is gone. The extension and depth-compatibility requirements stay.
- **Pipeline.cpp:184–189, `hostSampleLocationGrid(context, state)`.** A new file-local function returns the guest's grid (`SampleLocationGrid(state)`) when the pattern is uniform or the device has the grid for `state.samples`. Otherwise it returns `{1, 1}`.
- **What a 1x1 grid draws.** `SampleLocations(state)` lists the grid's pixels in Vulkan's `(x + y * width) * samples + sample` order. A 1x1 grid with `samples` locations therefore takes the first `samples` entries, which are pixel (0,0)'s locations.
- **Logging.** The first fallback of each sample count logs once (an atomic bit mask):
  ```
  [gpu] no 2x2 sample location grid at sample count 2 on this device: sample locations varying between pixels take pixel (0,0)'s in every pixel
  ```
- **The Pipeline constructor** (Pipeline.cpp:300) stores the decision in a new member `sampleLocationGrid` (Pipeline.hpp:94, a `VkExtent2D`). It uses that member for `VkPipelineSampleLocationsStateCreateInfoEXT` (Pipeline.cpp:477).
- **`Pipeline::Begin`** (Pipeline.cpp:707) uses the same member for `VkRenderPassSampleLocationsBeginInfoEXT`, both the depth attachment's initial locations and the subpass's. Main recomputed the grid from the state there.
- **Keys are unchanged.**
  - The pipeline-store key and the library keys still hold the guest's grid flag and every pixel's locations.
  - On a device without the grid, two patterns that differ only in pixels 1–3 get separate, identical pipelines. This is correct, because the keys over-specify.
  - Keeping the decision out of the keys and the State means a journaled or prebuilt state (#5875, #5925, `Pipeline::Prebuild`) is decided again by the device that builds it.

**Which pixel, and why (0,0).**

- **It is the pattern's first entry.** Pixel (0,0) and "the pattern's first entry" are the same here: `PA_SC_AA_SAMPLE_LOCS_PIXEL_X0Y0_0..3` (0x2fe–0x301) are the pattern's first registers.
- **It is exact where the grid is anchored.** The guest's grid, and main's 2x2 Vulkan grid, are anchored at the framebuffer origin. So pixel (0,0)'s pattern is exact at every pixel with even x and even y.
  - For Village, X1Y0 equals X0Y0, so all even rows are exact.
  - Odd rows have the same two positions with the indices swapped (section 2).
- **It costs no code.** A 1x1 grid already reads pixel 0's entries, which is how a uniform pattern is drawn.
- **It is what the experiment did.** The experiment 4d9965407 that let Village run past stop 15 used the same pixel. It decided at decode time, on every device.
- **The alternatives** (a majority pixel, a centred pattern, a parity split) are weighed in section 6.

**The switch.** The experiment's `APS5_RE8_STRICT_SAMPLE_LOCATIONS` is not carried over. No environment switch was added.
- The strict behaviour is now only what a device with the grid does.
- The tests pick the device through a mock `Context` (`sampleLocationGridSampleCounts`).

**Debt.** `docs/dev/debt/libSceAgcDriver.md`, the "Custom MSAA sample locations" entry:

- "and throw on others" became a description of the stand-in.
- It names the 3070's 1x1 grid.
- It says what differs from the console and which effects can show (section 2 has the detail).

**Depth images created `SAMPLE_LOCATIONS_COMPATIBLE_DEPTH`.**

- **One set of locations per depth image.** On a device without the grid, every pipeline and every render pass begin built for a given guest pattern use the same stand-in.
  - The pipeline draws with pixel (0,0)'s pattern.
  - The render pass's initial (layout transition) and subpass locations use that same pattern.
  - So a depth image is never drawn with one set of locations and transitioned with another.
  - The test checks this on the render-pass path: the depth attachment's initial locations and the subpass's equal the pipeline's.
- **Later draws stay consistent.** A later draw with the same guest pattern depth-tests against values written at the same positions with the same indices. On the console, by contrast, odd rows store sample 0 at the other position.
- **Patterns that differ between draws.** A depth image used by draws with different patterns is the same case as main's uniform patterns that differ between draws: render passes end at pattern changes, and depth stays in GENERAL. The stand-in is a uniform pattern, which main already supports on every device with the extension.

**Village's case: one set of positions per pixel, swapped indices on odd rows.**

- **The positions are preserved.** With pixel (0,0)'s 2x pattern (sample 0 at x = +4/16, sample 1 at -4/16, y = 0) in every pixel, each pixel has exactly the console's two positions. Even rows are exact. Odd rows have the indices swapped: the console puts sample 0 at -4/16 and sample 1 at +4/16 there.
- **Coverage.** Each pixel covers the same number of samples, at the same positions, as on the console.
- **Resolves see the console's values.**
  - A box resolve averages a pixel's samples.
  - So do a MIN or MAX depth resolve, and a coverage count.
  - Each of these works on the same set of (position, value) pairs, so it gives the console's value.
  - This holds with per-pixel shading (one colour per covered sample) and with per-sample shading.
  - Centroid interpolation also matches, because it depends on the set of covered positions.
- **Sample-indexed reads see the swap.**
  - On odd rows, a `texelFetch`/`Load2DMS` of sample i returns what the console stores in sample 1 - i.
  - Per-sample shading's `SampleID` sees the swap too: the invocation for sample 0 runs at the console's sample 1 position.
  - So do the coverage and sample-mask inputs.
  - A sample mask that keeps only some indices (`PA_SC_AA_MASK_*`, or a shader's sample-mask export) keeps the other position on odd rows.
  - The effect on checkerboard reconstruction: the reconstruction maps sample index and row parity to an output pixel, so it puts the two output pixels of each odd-row pair in each other's place. That can show as combing along vertical edges, and as reconstruction errors where the previous frame is blended.
- **#5907's one-sample case.**
  - #5907 rasterizes Village's depth-only checkerboard pass as one sample at sample 0's location.
  - Under the fallback that single position is +4/16 on every row, against -4/16 on the console's odd rows.
  - So odd rows test and write the other half-pixel. Later draws with the same stand-in stay consistent with it.

**#5907's one-sample grid queries.**

- **What #5907 changes.**
  - It adds `VK_SAMPLE_COUNT_1_BIT` to the VulkanDevice loop.
  - It lets `SampleLocationsCompatibleDepth` accept one sample.
  - It requires `samples > 1 || customSampleLocations` for `enabled`.
  - `rasterizeSampleZero` makes a one-sample state whose `sampleLocationGrid` is set when sample 0's location varies by row.
- **The fallback is generic over the sample count** (`context.sampleLocationGridSampleCounts & state.samples`), so it needs no change for one sample:
  - **3070:** one-sample custom locations are supported (grid 1x1, non-zero), with no one-sample grid, so the fallback applies: one sample at (0.75, 0.5).
  - **AMD:** has no one-sample custom locations. #5907's `ValidateSampleLocations` decides, and throws "custom sample locations require VK_EXT_sample_locations support for the draw's sample count". That is #5907's open question; this change neither causes nor fixes it.
  - **A device with a one-sample grid** keeps the 2x2 grid.
- **The test** builds #5907's one-sample state by hand (samples 1, sample 0 of each pixel, the grid flag set) and runs it through both pipeline paths:
  - without a one-sample grid, it gets `{1,1}` with (0.75, 0.5);
  - with one, it gets `{2,2}` with (0.75, 0.75, 0.25, 0.25).

## 6. Adversarial review: is one pixel's pattern the best stand-in?

| Stand-in | Village (2x, one set of positions, indices swapped on odd rows) | Other patterns | Cost | Verdict |
|---|---|---|---|---|
| **Pixel (0,0)'s pattern (chosen)** | every position exact; indices exact on even rows, swapped on odd rows; resolves and coverage exact; index reads swapped on odd rows | exact on pixels that share (0,0)'s pattern | none per draw; one decision per pipeline | chosen |
| Centre the locations (all samples at the pixel centre, or each sample at its mean over the four pixels) | each sample's mean x is (4 + 4 − 4 − 4)/4 = 0, so both samples land on the centre: every position is wrong in every pixel, a primitive covers 0 or 2 samples (no edge anti-aliasing), and the two half-pixels a checkerboard reconstruction takes from the samples become one value | positions wrong everywhere; coinciding samples collapse MSAA | same as chosen | worse on every axis except symmetry |
| Rasterize at the pixel's average (one location per pixel at the mean of its samples) | the mean of each Village pixel is the centre, so it is the same as the row above | loses the set wherever a pixel's samples are spread | same | same as centring |
| Split the draw by row parity with two pipelines | exact | exact for row-only or column-only patterns; a full 2x2 variation needs four | every such draw recorded and rasterized twice; restricting a pipeline to its rows needs a recompiled pixel-shader variant that discards by `FragCoord.y` parity (late depth, new variants, and a shader for depth-only passes, which Village's checkerboard pre-pass is), or a stencil parity mask (an extra pass, colliding with the title's stencil); two patterns in one subpass need `variableSampleLocations`, otherwise a render pass per half; and a sample-location-compatible depth image would be drawn with two patterns | rejected: per-draw cost and depth-image risk for an artifact that is visible only in index-dependent passes |
| Majority pixel (the pattern most pixels share) | 2-2 tie, so pixel (0,0) anyway | better when three pixels agree and (0,0) is the odd one | same as chosen, plus a tie rule | not needed now; no known title has such a pattern |
| Swap indices instead of positions (keep (0,0)'s positions, remap the sample index on odd rows wherever one is observed: `SampleID`, sample masks, `Load2DMS`, resolves) | exact | exact only for same-set patterns | every consumer of the image has to be patched, and images drawn this way have to be tracked | a possible follow-up if NVIDIA shows reconstruction artifacts |
| A partial grid where the device has one (1x2 for a pattern that varies only by row) | exact on such a device | exact for row-only or column-only patterns | small: keep the largest grid per count in `Context` | does not help the 3070 (1x1); the RTX 5070's 1x2 at 8 samples would qualify; a follow-up |

**Why pixel (0,0).**

- **Positions.** On the motivating pattern it keeps every sample position, so everything that depends only on positions matches the console: coverage, depth, resolves and centroid. Centring and averaging put both of Village's samples on one point.
- **Cost.** Nothing changes on the draw path and nothing changes in the shaders. The parity split doubles draws, needs shader variants or stencil passes, and draws a depth image with two patterns.
- **Predictability.** It is deterministic and has no tie rule. It is where the guest's and Vulkan's grids are anchored, and it is what the 1x1 grid already reads for uniform patterns.

### What

A draw whose MSAA sample locations vary between the pixels of the guest's 2x2 pattern (`PA_SC_AA_SAMPLE_LOCS_PIXEL_*`) threw

    AGC graphics: sample locations varying between pixels require a 2x2 sample location grid for the draw's sample count

on a device whose `maxSampleLocationGridSize` for the draw's sample count is not a multiple of 2x2 (#5861's refusal, `ValidateSampleLocations`). An RTX 3070 Laptop GPU reports 1x1 for every count, so Resident Evil Village's 2x checkerboard pattern stops there before the title.

The pipeline now decides the grid when it is created:

- **No grid for the count.** Such a pattern is drawn through a 1x1 grid with pixel (0,0)'s locations. Those are the pattern's first registers, `X0Y0`, and the pixel the guest's grid is anchored at.
- **Logging.** The first such pipeline of each sample count logs `[gpu] no 2x2 sample location grid at sample count N ...`.
- **Render pass begin.** `Pipeline::Begin` takes the pipeline's grid for `VkRenderPassSampleLocationsBeginInfoEXT`, so a sample-location-compatible depth image is begun with the locations it is drawn with.
- **Unchanged.** Devices with the grid (AMD's 2x2) keep it, and uniform patterns are unchanged.
- **Keys.** The pipeline keys and the decoded State are unchanged, so a journaled or prebuilt state is decided again by the device that builds it.

**What differs from the console** (recorded in `docs/dev/debt/libSceAgcDriver.md`):

- **Village's pattern** puts its two samples at x = +4/16 and -4/16 and swaps them on odd rows. The stand-in keeps both positions in every pixel, so coverage, depth and resolves match the console.
- **On odd rows sample i holds what the console stores in sample 1 - i.** A pass that reads samples by index, as checkerboard reconstruction does, exchanges the two half-pixels of odd rows. That can show as combing on vertical edges.
- **Patterns whose pixels hold different positions** draw pixel (0,0)'s positions in each pixel whose own differ.

Considered and rejected:

- **Centring the samples, or each pixel's average.** For Village this puts both samples on the pixel centre.
- **Splitting each draw by row parity into two pipelines.** Each such draw would be recorded twice and need a parity discard in the pixel shader or a stencil pass, and the depth image would be drawn with two patterns.

The pipeline-creation cost is two branches. On the draw path, `Pipeline::Begin` loses one call (`SampleLocationGrid(state)` becomes a member load), and the store lookup and `Continue` are unchanged.
