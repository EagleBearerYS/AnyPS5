## Counting mechanism

There is no counter of bytes copied on the CPU that a test can read. The upload's own byte totals are only printed under `APS5_PROFILE_DRAW` or `APS5_PROFILE_GPU`, so reading them would need new code:
- `CopyStats::gpuCopyBytes` (`Graphics/src/GuestBufferMemory.cpp:5230`), printed every 2000 uploads at 5846;
- the `EndGpuTiming(timing, copiedBytes)` bytes at 6061.

The test uses three existing hooks instead (paths under `core/libs/prx/libSceAgcDriver/`).

1. **Bytes copied for the region:** `GuestBufferMemory::CopiedBytes()` (`Graphics/include/GuestBufferMemory.hpp:383`).
   - It sums each region's copy buffer extent, whichever side filled it.
   - The test requires it to equal the region's 3 MiB. The region is exactly the view (`addDescriptorRegion` rounds only to DWORDs, and the view and size are DWORD-aligned).
2. **Bytes the GPU copied:** the read note that `recordGpuCopies` leaves.
   - When it copies the region straight out of the import, it notes a pending read of exactly `[region.begin, region.end)` with `Recorder::ReadKind::GpuCopy` (`Graphics/src/GuestBufferMemory.cpp:6035`).
   - It notes nothing when it copies from a CPU `memcpy` input snapshot instead (6003-6010).
   - The CPU path `copyRegion` (5869; its `GuestMemory::Read` is at 5903) notes nothing either.
   - The test reads the note through three recorder hooks:
     - `Recorder::ReadCounts().noted` (`Graphics/include/Recorder.hpp:180-184`): exactly one read noted during the upload;
     - `Recorder::DescribePendingRead` (`Recorder.hpp:177`): the read is in the open batch and its kind is `GpuCopy`;
     - `Recorder::PendingReadOverlaps` (`Recorder.hpp:166`): it covers the region's first and last DWORD and neither DWORD just outside it.
   - Together these mean one GPU copy of exactly the region's bytes.
3. **None on the CPU:** this follows from the first two hooks plus the existing wait check.
   - The bytes held by the region's copy buffer equal the bytes the one GPU copy wrote.
   - The input-snapshot `memcpy` is excluded, because it would have noted no read.
   - A CPU copy through `GuestMemory::Read` over a range with a write pending in the open batch must submit and wait. The existing check excludes that: `ThreadHookWaits() == 0`, `Submissions() == 0`, and the write is still open.
   - The readback check also catches stale producer bytes.

## Test

- The existing case is now a helper, `pendingUploadGpuCopy(device, recorder, producedOffset, producedBytes)`. Both tests use the same misaligned 3 MiB view at block + 4100 B.
  - `agc_buffer_upload_pending_gpu_copy` keeps its 1 MiB write at 1 MiB.
  - The new `agc_buffer_upload_pending_gpu_copy_bytes` (`--pending-upload-gpu-copy-bytes-only`) puts a 4 KiB write at 2 MiB.
- Both tests now run the two counting assertions. So the existing test gains them, and its messages now name the write's size.
- The new case is also added to the binary's default run list, next to the existing one, and registered in `tests/cmake/agc_driver_recorder_tests.cmake` with the same skip code and Windows `PATH` setup.
