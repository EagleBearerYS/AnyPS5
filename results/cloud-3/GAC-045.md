## How the port fits #6457's blocks

- **Eviction never takes an import this build holds.** `pointerHeld` is `lastUse >= buildFloor`, and `evictable` also needs 256 lookups since the last use.
  - A range served by the covering reuse is inside an import the same build looked up a moment earlier, so that block is held.
  - `importRunAt` refuses (or steps down) instead of replacing a held import.
  - So the `covering` pointer can't be retired under the loop by the port's retry.
- **A pending (recorded, not yet executed) build whose block import the retry evicts** is safe:
  - `retireImport` hands the retired import to the recorder (`KeepThroughHold`). The open batch keeps it until that batch completes, and that batch is submitted after any recorded work that still points at the import. It also lives through the current GPU hold;
  - the retire moves the import epoch, which Upload and the address-space cache honour;
  - the evicting build itself doesn't publish its address space (`importsEpoch` moved).
- **The retry can import a larger block than the range.** With `evict=true`, `importAllocation` passes `importRun` a budget of 0. That skips the remembered-refusal check, and `importRun` stops skipping remembered block refusals. It may then pick an aligned block of adjacent ranges up to the 8 MiB block window (`SetHostImportWindow(8 MiB)` in VulkanDevice). The eviction then frees room for that block, possibly more than the range alone needs.
  - For a range larger than the window, like Village's 768 MiB heap, the run is the range itself, so this doesn't change the case the port was written for.
  - A smaller range near the cap could evict for a whole block. Asking for the range alone (`largest` = the range's bytes) would avoid that, if the PC wants it.
- **LRU eviction retires whole block imports.** One eviction can uncover several ranges at once.
  - The 256-lookup protection counts lookups. With the covering reuse a block costs one lookup per build, so blocks the last builds used stay protected.
  - Ranges later in the *same* build that were not looked up yet are not protected by `buildFloor`; the same holds for the port on main.
- **Refusals that are not budget refusals don't trigger the retry:** an overlapping held import (`held`, then `nullptr` without step-down) and a failed `vkAllocateMemory` (`failures` / `failedBlocks`). Such a range still copies, and can still reach the FATAL cap, as on main.
  - With #6479, an allocation failure near the budget lowers the budget to the live imports, so the refusals after it are budget refusals and do count.
- **A stale remembered refusal is harmless.** It stays after the retry imports the range, but `importAllocation` checks `findImport` first. If that import is evicted later, the next refusal of the range is answered from memory and counted; the new test covers that path.
