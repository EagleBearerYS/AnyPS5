## 5. Eviction read, on the merged tree

Paths are under `core/libs/prx/libSceAgcDriver/Graphics/`. Line numbers are the merged tree's.

### (a) Can evictLocked or ReleaseSlots free or reuse a slot that a live DeviceImageTable entry points to, while a batch may still read the table?

**evictLocked: yes, it can evict that slot.** It does not free it at once.
- **A table entry's slot is touched only when it is taken.** That's `touchLocked` on the found path (`src/BindlessHeap.cpp:372`) or the new-slot path (`:382`), reached from `lookupKey`'s `slots.take` (`src/DeviceImageTable.cpp:364`).
- **Nothing touches it afterwards.** `TouchSlots` only touches a stage's own `stageState.slots` (`src/ShaderResources.cpp:7225`), and an entry served from the table never goes through `take` again.
- **So the heap sees a live table slot as idle** once `EvictIdleSubmissions` (2, `src/BindlessHeap.cpp:288`) submissions pass. The scan picks it up at `:509-513`.
- **Under pressure it is evicted.** That happens from `noteTakenLocked` (`:483`), or from `Submitted` while `refused` (`:1485`). Eviction:
  - erases the key (`:520`) and the owner record (`:521-527`);
  - bumps the generation (`:528`);
  - queues the slot in `retiring` with serial 0 (`:529`);
  - bumps `slotSerial` (`:532`).
- **The serial and the return to the free list come later.** The next `Submitted(recorder, serial)` gives the slot that batch's serial (`:1486-1489`). That call runs just before `vkQueueSubmit`, at `src/Recorder.cpp:4030`. `reclaimLocked` returns the slot to the free list only once that serial has completed (`:537-549`). It is called from `Submitted` (`:1490`), or from `imageSlot` when the pool is empty (`:377`, which may wait).

**ReleaseSlots: no, not for a live entry.**
- It frees at once: `freeSlotLocked` calls `SlotPool::Free`, which bumps the generation and pushes the slot onto the free list (`:388-406`, `:416-423`, `:443-446`).
- But it only runs from the owner's destructor (`HeapSlotOwner::ReleaseHeapSlots`, `include/BindlessHeap.hpp:246-249`). The owner is the `Texture` (`src/BindlessHeap.cpp:352-355`).
- A live entry holds `shared_ptr<Texture>` (`hold`, `src/DeviceImageTable.cpp:401-412`). A dropped entry hands it to `recorder.Keep` (`:432`). So the owner outlives every batch up to the one that dropped the entry.

### (b) Does retainSlots keep those slots off eviction, and does SlotGeneration change on reuse?

**retainSlots does not keep them off eviction.** `retainSlots` (`src/DeviceImageTable.cpp:436-447`) neither touches nor pins slots. It detects an eviction or free after the fact:
- `SlotSerial` moved (`:437-439`);
- an entry's recorded `slotGeneration` (`:370`) differs from `SlotGeneration(slot)` (`:442`).

It then drops those entries (`release`, `:445`) and their keys (`keys.Retain`, `:446`). It runs first in `Prepare` (`:162`) and in `Expect` (`:174`).

**The generation changes before any reuse.** It changes on eviction (`src/BindlessHeap.cpp:528`) and on free (`:444`). `Take` (`:429-441`) doesn't change it. So a reused slot never matches an entry's recorded generation: the sweep itself is sound.

### (c) Is there a path where the table serves an evicted, reused slot? **Yes.**

**The gap.** The sweep only protects draws recorded after a `retainSlots`. If a submission happens between a `Prepare`'s `retainSlots` and the draw's commands, an eviction at that submission can lead to:
- the slot being given the serial of the batch just submitted;
- the slot being reused while the next batch still reads the stale table entry.

**`Prepare` makes that submission itself:**
1. Draw D has a device-table stage. `writeHeapStage` (`src/ShaderResources.cpp:7204`, `:7236`) calls `writeHeapTableMap`, which calls `DeviceImageTable::Prepare` (`:6898-6904`). Every draw path refreshes the heap stage this way: a fresh build (`:1876`), a deferred compute (`:1861`), or a template hit (`src/Draw.cpp:2100`). Recipes are never made for heap shaders (`src/Draw.cpp:3224`).
2. `Prepare` (`src/DeviceImageTable.cpp:159-169`) runs `retainSlots` (no sweep, since nothing has moved), `resolve`, `refresh`, `evict`, `upload` and `chunkFor(recorder, true)`:
   - `upload` records batch N's table update, which still maps key K to slot S;
   - `chunkFor(recorder, true)` is at `:167`.
3. All 16 miss-ring chunks (`include/DeviceImageTable.hpp:86`) belong to batches still in flight, and `Reap` frees none (`:626-631`). So `chunkFor` calls `recorder.Sync()` (`:632-634`).
   - `Sync` (`src/Recorder.cpp:4188-4202`) calls `Submit`, which calls `BindlessHeap::Submitted(N)` (`src/Recorder.cpp:4030`).
4. S is evicted with serial N, by either of two routes:
   - in `Submitted`, the heap is `refused` and short, so `evictLocked` (`src/BindlessHeap.cpp:1485`) evicts S;
   - or S was already evicted inside this same `Prepare`, after `retainSlots`. That's `resolve`, then `lookupKey`'s `take` (`src/DeviceImageTable.cpp:364`), then `noteTakenLocked`, then `evictLocked` (`src/BindlessHeap.cpp:483`).

   Either way, retiring S gets serial **N** (`:1486-1489`). `Sync` then waits for N to complete (`src/Recorder.cpp:4196-4200`).
5. `Prepare` returns, and `Trailer` is called (`src/DeviceImageTable.cpp:246-250`). D is recorded into batch **N+1**.
   - The GPU table still maps K→S: batch N's upload put it there, and no `retainSlots` has run since.
   - If a later device-table stage of the same draw runs its own `Prepare`, that sweeps K first. So the path needs D's last device-table stage to be the one that synced, for example a fragment-only device table.
6. S returns to the free list at the next `reclaimLocked`, because serial N is complete:
   - either an `imageSlot` with an empty pool while N+1 is recording (`src/BindlessHeap.cpp:377`);
   - or `Submitted(N+1)` (`:1490`).
7. The next `Take` (`:376`, `:431-435`) hands S to another texture. `writeImageSlot` then writes the new descriptor **by CPU into the host-visible resource heap** (`:872-894`). Batch N+1, recorded or in flight, reads K through the table and gets **S's new descriptor**, which is another image.

**Not a candidate path: the early submit.** de1bbf1af3's early submit (`Recorder::BoundDrawBatch`, `src/Recorder.cpp:3100`) runs at the draw boundary, before `Prepare` (`src/Draw.cpp:3223`, `:4144`). The next `Prepare` sweeps first, so it opens no window by itself.
- It does mean more batches per frame. That makes "all 16 chunks in flight" in step 3 more likely.

**Without #9508's eviction there is no such path.** On 715097ee91, a live entry's slot can only be freed by `ReleaseSlots`, which (a) rules out. The hazard comes from combining 36caa8b0fe / 097833507b's eviction with #7642's table.

**How likely it is.** It needs all three of:
- a heap near its slot margin;
- 16 batches in flight at the moment of a `Prepare`;
- the syncing `Prepare` belonging to D's last device-table stage.

That is rare, but nothing in the code prevents it. I didn't reproduce it, because the task says to stop after this report.

**Fix sketches** (not implemented). Any one of these closes the window:
1. Take the miss-ring chunk at the start of `Prepare`, before `retainSlots`, so any `Sync` comes before the sweep.
2. Or re-run `retainSlots`, and `upload` if needed, after `chunkFor` whenever `SlotSerial` moved.
3. Also worth having: let the table mark its entries' slots used each `Prepare`, via `TouchSlots` over the live entries' slots. Eviction would then stop picking live table slots first, which also avoids evict–miss–reinsert churn.
