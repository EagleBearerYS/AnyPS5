## The counter

**The query.** libc gains `GuestArena::GuestArenaUsage_nid_no_patch(GuestArenaUsage*)`. It returns private, shared, direct and reserved bytes from running totals: one lock and a copy, with no walk of the address space.

**Windows** counts inside `WindowsMappings`, under its existing mutex:
- **`Commit`** adds each placeholder it replaces with private memory. Pages that are already committed are only re-protected and add nothing.
- **`Map`:**
  - `GuestArenaMap` (shared memory) adds each shared view page.
  - `GuestArenaMapDirect` adds each resident run and each view page as direct.
  - A view now carries a `direct` flag.
- **`reset`** subtracts each allocation once it has been released:
  - a view by its flag;
  - a resident run as direct;
  - any other private memory as private.
  
  `reset` covers `GuestArenaReset` and also runs as the first step of every `Map`. So a remap (a `Map` over a mapped or committed range) moves the bytes between kinds exactly.
- **Demoting a resident run** to views (when the same direct memory is mapped a second time) keeps the bytes direct.
- **Not counted**, because they live outside the arena: the host-side read-write aliases of shared memory (`MapAlias`), the saved copies of unmapped resident direct memory, and the windows opened on sections.

**Linux:**
- The arena counts what `GuestArenaCommit` commits as private, in an interval map, so a commit over committed pages counts them once. `GuestArenaReset` removes whatever it covers.
- libkernel maps flexible, direct and shared/file memory with `mmap` itself on Linux (`MapPlaced`, `PhysicalBacking::Map`, `DoMapShared`, `DoMapFileBacked`). So on Linux the line shows only what goes through the arena: the guest heap and other `GuestArenaCommit` callers. Shared and direct stay 0 there.
- If Linux numbers are wanted, the next step is libkernel telling the arena what it maps.

**macOS:** the arena is unavailable, so everything stays 0 and the test skips (exit 77, `SKIP_RETURN_CODE 77`).

**Reserved** is the address space the arena has handed out: the bytes in its used-range map beyond the host regions and holes it starts with. That covers allocations (`Allocate`, `AllocateFromHint`), fixed mappings (`MarkUsed`), and on Linux the commits that claim an unclaimed range, less releases. It is kept as a running total next to the map.

**Release** (`GuestArenaRelease`) changes only reserved, on both platforms: the arena's release is bookkeeping. libkernel and the guest heap reset a range before releasing it.

## The output

Under `APS5_PROFILE_DRAW=1`, right after the 10 s `[guestmem]` line:
```
[arena] committed X MiB (private Y, shared Z, direct D), reserved W MiB
```
Nothing prints without profiling, because the whole report sits under `MemoryProfiled()`. It's a separate `[arena]` line, as other subsystems have their own lines. The `| arena 0x…` field already on `[guestmem]` is the page-state cache's range, not this.

**Sample from a synthetic run:**
- The harness is a scratch program, not committed. It's built with `agc_write_tracking_tests`' own compile and link commands and runs as `runner` with `APS5_PROFILE_DRAW=1`.
- It allocates 96 MiB and commits 64 MiB of it. It then allocates 8 MiB, commits all 8 and resets 4. Finally it makes one `GuestMemory::Read`.

```
[guestmem] read 0 calls 0 MiB 0.0 s compare 0 calls 0 MiB 0.0 s ... verify 1 calls 0 MiB 0.0 s ...
[arena] committed 68.0 MiB (private 68.0, shared 0.0, direct 0.0), reserved 104.0 MiB
```

That is 64 + 8 − 4 = 68 MiB committed and 96 + 8 = 104 MiB handed out.

## The test

`guest_arena_committed` lives in `core/libs/tests/GuestArenaCommitted.cpp`. It is registered in `core/libs/prx/libkernel/CMakeLists.txt` right after `guest_memory` and `guest_mmap_fixed_anonymous`, the tests that already exercise the arena. It links only libc.

Each line is the change since the start, in 16 KiB pages. Output on Linux:
```
allocate 8 pages: private +0, shared +0, direct +0, reserved +8 pages
commit 4 of them: private +4, shared +0, direct +0, reserved +8 pages
commit the same 4 pages again: private +4, shared +0, direct +0, reserved +8 pages
commit 6 pages over them: private +6, shared +0, direct +0, reserved +8 pages
reset 2 pages in the middle: private +4, shared +0, direct +0, reserved +8 pages
reset the whole block: private +0, shared +0, direct +0, reserved +8 pages
release the block: private +0, shared +0, direct +0, reserved +0 pages
commit 2 unclaimed pages, which claims them: private +2, shared +0, direct +0, reserved +2 pages
reset them: private +0, shared +0, direct +0, reserved +2 pages
release them: private +0, shared +0, direct +0, reserved +0 pages
guest arena committed bytes checks passed
```

On Windows, committing unclaimed pages doesn't claim them, so the reserved expectations there are 0. The Windows build then adds these steps:

| Step | Expected change |
|---|---|
| Map 2 shared pages | +2 shared |
| Map 2 pages of direct memory once (a resident run) | +2 direct |
| Map the same direct memory a second time (this demotes the first mapping to views) | +2 direct |
| Commit 2 more pages, then map shared pages over them | −2 private, +2 shared |
| Reset the first direct mapping | −2 direct |
| Reset every other mapping, then release every block | back to 0 everywhere |

The Windows part compiles under MinGW but has not been run, since this worker has no Windows. The PC's 3070 or the verify workflow can run it.
