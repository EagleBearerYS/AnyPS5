## Cause

The guess was right.
- With `importWindow` at 0, `importRun` (GuestBufferMemory.cpp, `leasedRun(lease, first, last)`) joins every registered range adjacent to the one asked for into one import, as long as `continuesRun` holds: same readable, writable and gpu flags.
- Case 5 made `block = AllocateWatched(0x50000, 64 KiB)` and then `keys = AllocateWatched(64 KiB, 64 KiB)`. The guest arena hands them out back to back, so `keys` sits at `block + 0x50000`.
- Both are registered with the same flags (`mutation.Add(block, importBytes, true, true, true)` and `mutation.Add(keys, unit, true, true, true)`). `HostImportFor(context, address, 0x50000)` therefore imported 0x60000 bytes, and `import->bytes == importBytes` failed.
- Cases 1-4 allocate nothing after `block`, so the GPU run never hit it there.

## The change (test only, `core/libs/prx/libSceAgcDriver/tests/Recorder.cpp`, `settleInitialDccTests`, +17/−7)

1. **One region per case, with unregistered gaps.** Each case now takes a single `AllocateWatched` region laid out as `[64 KiB gap][block: reserved][64 KiB gap][keys: 64 KiB, case 5 only]`. Only `block` (`importBytes`) and `keys` (`unit`) are registered, as before.
   - The gaps are never registered, so no import run can join `block` to `keys`, to a still-registered arena neighbour before `block`, or to anything after the region.
   - The region is released with one `ReleaseWatched(region, regionBytes)` (previously `ReleaseWatched(block, reserved)` plus `ReleaseWatched(keys, unit)`), so nothing leaks and nothing is released twice.
   - Case 5 keeps its meaning. The color import is a 0x50000-byte (sub-1 MiB) compared import with a pending settle. The keys are separate, unimported memory, `Unwatch`ed explicitly over `dccBytes`, and they sit in their own 64 KiB tracker block behind a gap.
2. **Self-explaining preconditions.** A `describe` helper is appended to both preconditions: the target's import check (old `:2491`) and the case-3 neighbour check (old `:2488`).
   - It prints the import found (base, bytes, `unwatched`), the range asked for and `Watched` for it. With no import it prints `no import of …, watched N`.
   - Example of the new failure text: `(m) the target's import of 327680 bytes was not compared at first: import 0x…+0x60000, unwatched 1, for 0x…+0x50000, watched 0`.
3. **The refusal must come from the keys.** After case 5's refusal (still required to be "initial multisampled DCC contents require watched guest memory"), the test now also requires `Watched(address, importBytes) && !Watched(keys, dccBytes)`, printing `describe(settled, …)` otherwise.
   - BF-150's `initialDccClear` runs `WatchedAfterSettle` over color, then DCC, then CMASK. So the color import is settled back into the watch before the keys are refused, and a refusal with the color watched and the keys unwatched can only be the keys'.

**Item 3, cases 1-4:**
- `dest` comes from `VirtualAlloc`, outside the guest arena's reserved ranges. It could have joined `block` only if `block` sat at the very edge of an arena range next to it.
- The likelier hazard was any arena allocation still registered just before `block`.
- Neither showed on the GPU run (cases 1-4 checked `import->base == address && import->bytes == importBytes` and passed 5/5). With the gaps on both sides of `block`, neither is possible any more, so cases 1-4 need no change of their own.
- The case-3 neighbour still starts `tail` (0x4000) bytes after the import and ends at `block + reserved`, so it remains its own import as designed.
