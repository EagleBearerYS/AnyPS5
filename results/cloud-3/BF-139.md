## What blocks what

**The trace build.** The scratch edit adds timestamped prints with each Blocker's address. It also makes `Finish` wait 20 s and then up to 100 s more.

Hung run 4c/200:
```
[trace 0.193] submit behind blocker 0x7fffaedd635f
[trace 0.694] blocker 0x7fffaedd635f enqueued, outstanding 4
[trace 0.694] test 1 releases blocker 0x7fffaedd635f, outstanding 4
[trace 0.694] finish waits, outstanding 4
[trace 0.697] finish done after 0.003 s
[trace 0.697] submit behind blocker 0x7fffaedd656f
[trace 0.697] blocker 0x7fffaedd635f runs (release 0)
[trace 1.200] blocker 0x7fffaedd656f enqueued, outstanding 3
[trace 1.200] test 2 saw outstanding 3
[trace 1.700] test 2 releases blocker 0x7fffaedd656f, outstanding 3
[trace 1.700] finish waits, outstanding 3
[trace 21.701] finish still waiting after 20 s, outstanding 3
(exit 1 at 121.9 s: not resolved after 120 s)
```

**The committer is running test 1's Blocker (`…635f`) during test 2,** and reads its `release` as 0. Test 1 had set it to 1 at 0.694.

**1. Test 1's blocker is queued last.**
- `SubmitBehind` holds the GPU lock for 500 ms after `Submit`.
- In that time the queue worker puts three items on the draw pipeline: the two draws and the submission's deferred completion. `Driver::deferCompletion` (`Execution/src/Driver/Queues/QueueWorker.cpp:65`) enqueues the completion as a pipeline item of its own.
- The committer is blocked on the GPU lock while committing the first draw.
- So the blocker is enqueued fourth: outstanding 4 at its enqueue in all 400 trace and fixed runs.

**2. Nothing waits for that blocker.**
- `Finish()` waits on `Driver::WaitIdle`, which returns when the completion item, the third, has run.
- The blocker belongs to no submission, so `WaitIdle` doesn't wait for it. `Flush(FirstMemory/SecondMemory)` waits only for the draws' writes.
- So `IndirectDrawsQueueBehindTheCommitter` can return, and its stack `Blocker` go out of scope, while the blocker item is still queued.

**3. Usually the race is harmless; under load it isn't.**
- Normally the committer starts the item within microseconds and reads `release == 1` from the still-intact stack slot.
- Under load the test thread is already in test 2 by then. Test 2's frame reuses that stack.
- The dangling read (`[this]` captured in `Blocker::Enqueue`) then returns 0, and the item spins forever.

**4. Everything behind it waits.**
- Test 2's label, draw and blocker queue behind the orphan.
- The worker drains at `Draw.cpp:45`, because test 2's indirect draw reads a record that a queued label writes, and parks at `DrawPipeline.cpp:211`.
- `WaitIdle` (`Lifecycle.cpp:230`) waits for the worker. Test 2's `release = true` goes to its own Blocker (`…656f`), which never reaches the front.

**Verdict:**
- **Not a real cycle.** The worker waits on the pipeline, and the pipeline waits on freed test memory. Nothing in the driver waits on the worker or could release the committer.
- **Not slow work.** It stays stuck with 120 s, and it is CPU-idle.
- **It is undefined behaviour in the test:** a pipeline item outlives the `Blocker` it reads.

**Frequency of the bad order:** in the trace build, test 1's blocker started after test 1's `Finish()` returned in 4 of 200 runs. One of those read 0 and hung; the other three still read the intact 1.

**The driver behaved as designed:**
- Draining before an indirect draw whose record a queued label writes is what keeps that draw correct.
- A title's pipeline items are the driver's own commits. None of them waits on a flag in freed memory.
- These runs give no sign of a hang a title would hit.

## The other two load failures

**Test 1's window (4c run 61, 10.8 s):**
- The message was "the indirect draws drained the pipeline instead of queuing behind it (1 items outstanding, expected the blocker and two draws)".
- The test polls `Outstanding() < 3` only after `SubmitBehind` has dropped the GPU lock. The committer can commit the three items queued ahead of the blocker before the first poll, which leaves 1.
- **Test 2 has the same window,** in `while (Outstanding() < 2 && … < 10 s)`. That loop has no `Require`, so it waits the full 10 s and then releases. That is every 11.7–11.9 s pass above.
- While test 2 polls, the worker sits in the same `Draw.cpp:45` drain until the release.
- This is a test race, and it is load-sensitive.

**`agc_driver_pipelined_fill` (3b run 5):**
- The message was "a satisfied WAIT_REG_MEM skipped an overlapping queued write".
- The check gives the WAIT_REG_MEM submission 3 s to request its drain (deadline at `PipelinedFill.cpp:208`, checked at `:219`), and under load it can miss that.
- It is not a hang, and it wasn't investigated further.
- **The fill test's Blocker:** it has `~Blocker() { release = true; }`. That narrows the dangling read above, but storage reused after the destructor can still be read as 0.
- **The prefetch test's Blocker:** it has no such guard. It passed 200/200 here.

## Checked fix (scratch only, reverted)

Two changes to `PipelinedIndirectDraw.cpp`:
- **Blocker lifetime:** `Blocker` gets `queued`/`done` flags (`done` set at the end of its item). `~Blocker()` sets `release` and waits until the item has finished, so `this` is valid whenever the item runs.
- **Outstanding count:** `SubmitBehind` stores `Outstanding()` before it drops the GPU lock, and both polls accept that count.

Under the step-4 `^agc` load: **200/200 passed, 0 hangs, 0 runs over 10 s.** The late start (test 1's blocker running after its `Finish()`) happened in 11 of those 200 runs and was harmless.

The same lifetime guard would close it in `PipelinedPrefetch.cpp` and `PipelinedFill.cpp`. The fill test's destructor would need the wait as well as the store.

RESULT:
- **Base:** upstream main `4a17c71757`, CI Linux flags, 4 vCPU lavapipe, run as `runner`; read-only, nothing pushed.
- **Counts (`indirect_draw` / `fill` / `prefetch`):**
  - Alone `until-fail:100`: 100/100 each.
  - 4 busy loops `until-fail:50`: `indirect_draw` failed on run 40 ("deadlocked", 22.4 s); 50/50 and 50/50.
  - Parallel `ctest -R '^agc' -j4`, `until-fail:50`: `indirect_draw` failed on run 33 ("deadlocked", 21.7 s); `fill` failed on run 5 (its 3 s WAIT_REG_MEM window, `PipelinedFill.cpp:208`); `prefetch` 50/50.
  - Step 4: 200 direct runs under busy loops did not hang. Under the `^agc` load it hung on run 8, and again on run 200 of 200 in the trace build. In all, 4 hangs in 781 runs, all under load.
- **It fired, and it is not a driver deadlock.** The stacks:
  - **Queue worker:** `Draw.cpp:45`, `pipeline.Drain(DrainReason::Indirect)`, waiting at `DrawPipeline.cpp:211` for an empty pipeline. Test 2's indirect draw reads a record that a queued label writes.
  - **Draw committer:** `PipelinedIndirectDraw.cpp:144`, `while (!release.load())` in **test 1's** Blocker. That Blocker went out of scope when the case returned. Its item was queued after the case's draws and after the submission's completion item (`QueueWorker.cpp:65`), so neither `WaitIdle` nor `Flush` waits for it. Its `release` now reads test 2's stack (0).
  - **`WaitIdle`:** `Lifecycle.cpp:230`, waiting for the worker.
- **No real cycle and no slow work.** The process is CPU-idle (only the 1 ms sleep loop runs), and it was still stuck at 120 s. It is a use-after-scope in the test. The 20 s wait isn't too short.
- **Also under load:** a 10 s window race in both cases (`Outstanding()` read after the GPU lock drops). It gives test 1's "drained … instead of queuing" failure and the 11.7 s passes in test 2.
- **Scratch fix:** `~Blocker()` waits for its item, and the count is taken under the GPU lock. 200/200 under the same load, 0 hangs, 0 slow, with the bad order hit 11 times.
- **Siblings:** `PipelinedPrefetch.cpp` and `PipelinedFill.cpp` have the same Blocker pattern. The fill test's `~Blocker() { release = true; }` only narrows the window.
