## The new line format

Under `APS5_PROFILE_DRAW`, the `collect` entry of `fast-fail by reason` in `[rescache] revalidate (10 s)` becomes:

```
fast-fail by reason: ... collect N (unwatched N, outside N, incomplete N; sampled N, storage N; ranges: <reason> 0x<address>+0x<bytes> x<count> ...) ...
```

- **unwatched / outside / incomplete:** why `collectWrites` returned 0, for the fast proof's failed collects only. All three are always printed.
- **sampled / storage:** which collect failed. `sampled` is the sampled-element collect (main's `ShaderResources.cpp:3104`, `:3177` on the branch). `storage` is the storage-image collect (main's `:3161`, `:3237` on the branch).
- **ranges:** up to 8 distinct (reason, address, bytes) ranges with their counts, taken only from the fast proof's failures. They are cleared at each report. `; ranges:` is left out when none was taken.
- **Totals:** `collect N` = sampled + storage = unwatched + outside + incomplete, apart from a count that lands while the report is being read.
- **Unchanged:** the entry is printed only when N > 0, as before. The other reasons, `full by reason` and the rest of the line keep their format. `fastRevalidateEach` (the `APS5_NO_EPOCH_REVALIDATE=1` path) counts no collect failure, so it adds nothing here, as before.

A real line from this machine's profiled `^agc` run (test `agc_driver_storage_cache_budget`, lavapipe):

```
[rescache] revalidate (10 s): 1 calls 1.0 ms (full walks 0.9 ms, their image tables 0.0 ms): fast 0, full 1, failed 0; fast-fail by reason: collect 1 (unwatched 0, outside 1, incomplete 0; sampled 0, storage 1; ranges: outside 0x7fa59d5f0000+0x100000 x1); full walks: ...
```

## How it works

- **GuestMemory.cpp:**
  - `thread_local CollectFailure lastCollectFailure`. `collectFailed` sets it next to its existing count, after its `MemoryProfiled()` check, so nothing is stored without the switch.
  - The reason enum moved from the anonymous namespace to `GuestMemory.hpp`. The header also gains `LastCollectFailure()` and `CollectFailureName()`.
- **ShaderResources.cpp:** at both `fail(FastFail::Collect)` sites the fast proof calls `countFastCollect(address, bytes, storage)`. It returns at once unless `BuildProfiled()` (the same `APS5_PROFILE_DRAW`). It reads the thread-local and counts per reason and per site. It keeps the ranges in an 8-entry table under its own mutex.
- **Cost when off:** the success paths gain nothing. A failed collect gains one call that tests a static bool.
- **One behaviour change, in `[guestmem]` too:** `collectWrites`' early return for an empty or wrapping range (`bytes == 0`, or `address + bytes` overflowing) now goes through `collectFailed(Outside)`.
  - Before, it returned 0 uncounted (BF-232 noted this). It would then have left the previous failure's reason in the thread-local, and the fast proof would have counted a stale reason.
  - So `[guestmem]`'s `outside` total and ranges now include such ranges too.
  - In the probe below these cases record `outside`. No `[guestmem]` sample in the profiled `^agc` run shows one (all its ranges have bytes > 0).
- **Comments:** the diff adds 0 comment lines (`git diff a9f338d3da d373e5566c | grep '^+' | grep -cE '//|/\*'` = 0).

## The counts for the PC look

- Read the `collect N (...)` split on each `[rescache] revalidate` line.
- A fast proof returns on its first failing element, so N is the number of proofs that went to the full walk because of a collect. The sampled/storage split says which element type blocked it, and the ranges name the blocking elements.
- Mapping to BF-232's ranking:
  - mostly `outside` on `storage` ranges that repeat at the proof rate supports fix A (the untracked-hint acceptance);
  - `incomplete` supports fix B;
  - `unwatched` points at the tracker itself.
- The `[guestmem]` totals still mix every caller. The new split doesn't.
- No game data was used. Only test-suite output and addresses.
