# BF-371: #9790 plans a waterfall-keyed nested S# whose word has another user, then the dispatch segfaults on lavapipe: find why (cloud-3)

Worker: cloud-3. The build used CI's configure flags (Ninja, Release, gcc 13.3, ccache, SPIRV-Tools ON). Tests ran as `runner` on lavapipe, with `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1 APS5_NO_PIPELINE_JOURNAL=1`. The driver is Mesa `mesa-vulkan-drivers` 25.2.8-0ubuntu0.24.04.4: llvmpipe, LLVM 20.1.2, 256 bits, `driverVersion` 0x6402008. No game data was used. Nothing was pushed except this file.

**Short answer: lavapipe's bug, not ours, and not the waterfall key. Per step 2, I stopped there: no fix commits, and no branch was created on the fork.**
- **The null:** the guest address of the record behind the pointer (`records[...]`, the V# at record word 40) is not in the dispatch's BDA table, because BF-370's W harness passed no `GuestMemorySnapshot`s. So the shader's page-table lookup (`get_bda_pointer`) returns physical address 0.
- **What our code does with it:** the SPIR-V guards the load, and so does lavapipe's own final NIR: `if (physical == 0) break/return`, and only then an 8-bit `load_global`. In SPIR-V and NIR semantics, that load does not run.
- **What llvmpipe does:** it runs the load anyway, from address 0. The crash is `movzbl (%rcx),%ecx` with rcx = 0.
- **It is not specific to the waterfall key, or to W+S#:**
  - #9790's own scalar-keyed consumer case segfaults the same way once its two snapshots are removed (§2.2). It passes at the head only because it hands `records` and `palettes` to the dispatch as snapshots.
  - W+S#, and the T# sibling (a T# word with a second user), plan and sample correctly at both #9790 and #9969 once the same two snapshots are passed (§2.3).
- **The proof (§4):** a 166-line standalone Vulkan program with a 20-line GLSL compute shader segfaults lavapipe the same way.
  - It uses no AnyPS5 code: a uniform 8-bit buffer-reference load guarded by `if (physical == 0) return` inside a loop the compiler can't unroll.
  - The validation layer reports nothing, and the program works when the address is mapped.
  - The same holds for a plain `if (address != 0) load` (8-bit and 32-bit).
- **This is BF-149's finding** (cloud-2, "a BDA miss of a uniform scalar load crashes lavapipe"), now reduced to the API: llvmpipe executes a uniform physical-pointer load that control flow has excluded.
- **No fix branch, no commits, no checks run.** Steps 3 and 4 were not reached. `ShaderDiskCache` `FormatVersion` was not touched.

### 2.2 Why #9790's scalar-keyed case passes and W+S# doesn't

**The difference is the harness, not the shader.** #9790's scalar case calls `run(consumer, 64u, live)`, where `live` holds `GuestMemorySnapshot`s for `records` and `palettes` (`ImageTable.cpp:1908-1912` at ebaa9b1565). BF-370's W harness called `Execute(..., 32u)` with no snapshots.

**What the snapshots do.** At dispatch, a shader that uses BDA builds its address table from the registered guest memory plus the snapshots (`ShaderResources::prepareAddressBindings`, `ShaderAddressResources.cpp:234-241`). The test's stack arrays are not registered guest memory, so without snapshots their addresses are not in the table.

**Why only the consumer variants read that memory.** #9790's "a real V# for the other users" path re-points a kept S# word read at an unrewritten copy of the V# handle (`ResourceTracker.cpp:159-172`). That copy's four word loads stay real BDA loads through the record pointer. In the IR after resource tracking (`APS5_DUMP_IR=all`, pass `resources`), at c147aa8647:

| Variant | `LoadAddressU32` at pc 0x9c (V# words through the record pointer) | `ReadConstBuffer` at pc 0xac (S# words) |
|---|---|---|
| W | 0 | 0 (every S# read is a planned table column) |
| W+S# | 4 (`off=0xa0` to `0xac`) | 1 (`off=0x4`, the word `v_mov_b32 v7, s33` uses) |

So W and W+T# never read `records` or `palettes` at run time, and W+S# does.

**The scalar case fails the same way without its snapshots.** I ran #9790's own scalar-keyed consumer case (`NestedSamplerCode` + `0x7e0e0221` at +31, wave64) with `run(consumer, 64u)` instead of `run(consumer, 64u, live)`, at ebaa9b1565:

```

```

So the waterfall key and its loop play no part. Any kept V# word read whose guest memory is not in the BDA table crashes lavapipe.

### 2.4 The code is right

**The validation layer is clean.** I used `VK_LAYER_KHRONOS_validation` 1.4.341, loaded with `VK_LAYER_PATH=/home/user/vvl/src/build/layers VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`; the loader log confirms "Insert instance layer". It printed 0 messages for W+S# without snapshots (rc 139) and 0 with them (rc 0). So no binding is left unwritten.

**The SPIR-V guards the load.** W+S#'s module was dumped from `RecompileResult::spirv`. `main` calls `read_bda_span_stop` for the V# at `0xa0` (instruction `0x9c`, mask 15). With the span unmapped, that calls `read_bda_dword_bytes_stop`, which returns before any load whose physical address is 0:

```
%read_bda_dword_bytes_stop = OpFunction %v2uint DontInline %397
        ...
        %453 = OpFunctionCall %ulong %get_bda_pointer %452 %uint_1_8 %434
        %454 = OpIEqual %bool %453 %ulong_0
               OpSelectionMerge %456 None
               OpBranchConditional %454 %455 %456
        %455 = OpLabel
               OpReturnValue %398
        %456 = OpLabel
        %457 = OpConvertUToPtr %_ptr_PhysicalStorageBuffer_uchar %453
        %458 = OpLoad %uchar %457 Aligned 1
```

This is `EmitBdaByte` (`SpirvBdaRead.cpp:39-50` at ebaa9b1565): `StopBdaInvocationIf(physical == 0)`, then `OpConvertUToPtr` and an 8-bit `OpLoad`. `main` has no physical-pointer loads of its own, and `%458` and its non-stop twin `%426` are the module's only 8-bit loads.

**lavapipe's final NIR keeps the guard.** This is `LP_DEBUG=cs`, the NIR llvmpipe compiles. It is taken from the run with snapshots, which compiles the same module, because the crashing run's stderr is held by the harness's `StderrCapture` and lost with the process:

```
                                block b77:    // preds: b46 b76
                                64     %541 = phi b46: %68 (0x0), b76: %540
                                1      %542 = ieq %541, %68 (0x0)
                                if %542 {
                                    block b78:    // preds: b77
                                    32x2   %543 = load_const (0x00000000, 0x00000001)
                                                  break
                                } else {
                                    block b79:  // preds: b77, succs: b80
                                }
                                block b80:    // preds: b79
                                8      %544 = @load_global (%541) (access=none, align_mul=1, align_offset=0)
```

**And yet it faults on that load.** The crash (BF-370 §6.4, reproduced here) is a byte load through a null pointer, on four threads at one JIT address: `movzbl (%rcx),%ecx`, rcx = 0.
- The module has two 8-bit global loads, `%544` and `%926`. They are the inlined copies of `%458` for `main`'s two `read_bda_span_stop` calls: the V# words at pc 0x9c, and the S# word at pc 0xac.
- Both sit after the same `ieq ..., 0` → `break` guard. Each is reached only through the `physical != 0` arm.
- The first one a run reaches is `%544`, for the unmapped V# words.

## 3. Why the waterfall form "gets there" and the scalar form doesn't

It doesn't. Both shapes reach the same kept, real BDA read of the V# words through the record pointer. The only difference was that #9790's scalar test backs `records` and `palettes` with snapshots, and BF-370's W harness did not (§2.2). With the snapshots, W+S# is correct under the waterfall key at both heads (§2.3).

BF-370's "planned, then fault" for W+S# at #9790 and #9969 should therefore read: **planned and correct, provided the record and palette memory is mapped.** Without that mapping, lavapipe crashes where a correct implementation would report `BDA access failed ... reason=8`.

## 4. Standalone repro: llvmpipe runs a guarded uniform physical-pointer load

The program creates a 1.2 device with `bufferDeviceAddress`, `storageBuffer8BitAccess` and `shaderInt64`. It binds one storage buffer, `{uint64_t address; uint values[32]}`, and dispatches one group of 32.
- In `mapped` mode it stores the device address of a 16-byte buffer whose byte 0 is 0x41.
- In `null` mode it stores 0.
- It uses no AnyPS5 code.

Build and run:

```
glslang -V --target-env vulkan1.2 loop3.comp -o loop3.spv
g++ -std=c++17 -O1 -I3rdparty/Vulkan-Headers/include repro.cpp -o repro /usr/lib/x86_64-linux-gnu/libvulkan.so.1
GALLIUM_OVERRIDE_CPU_CAPS=avx ./repro loop3.spv mapped
GALLIUM_OVERRIDE_CPU_CAPS=avx ./repro loop3.spv null
```

```glsl
    return guest == 0ul ? 0ul : guest + uint64_t(io.values[31]);
}
uvec2 readBytes(uint64_t guest) {
    uint value = 0u;
    for (uint index = 0u; index < 4u + io.values[30]; ++index) {
        uint64_t physical = translate(guest + uint64_t(index));
        if (physical == 0ul) return uvec2(0u, 1u);
        value |= uint(Bytes(physical).value) << (index * 8u);
    }
    return uvec2(value, 0u);
}

    uvec2 result = readBytes(io.address);
```

**Reading:**
- NIR keeps the load behind the guard, so no NIR pass speculates it.
- llvmpipe's code generation still performs it when the address is uniform and every invocation has already left: through a uniform `break` (`loop3`), or a uniform `if` that is false (`select`).
- With a divergent address it does not (`select-divergent`).
- Once the loop is unrolled, or the return is in `main`, the guard becomes a real branch and the load is skipped.

This is a lavapipe defect. The SPIR-V is valid, and the load is not executed by the shader's semantics. I did not test real GPU drivers here.

## Summary for the Bug Finder

**Not a #9790 bug, and not the waterfall key.**
- W+S#'s V# words are re-read for real through the record pointer, as #9790 intends. BF-370's W harness never put `records` and `palettes` in the dispatch's BDA table, so the lookup returned physical 0.
- Our SPIR-V, and lavapipe's own NIR, then skip the load. llvmpipe (Mesa 25.2.8, LLVM 20.1.2) runs it anyway, because the address is uniform and the excluding `break`/`if` is uniform.
- **#9790's scalar-keyed consumer test passes only because it passes those two snapshots.** Without them it segfaults the same way.
- **With the snapshots, W+S# and its T#-word sibling plan and sample correctly at both #9790 (ebaa9b1565) and #9969 (c147aa8647).**

**A 20-line GLSL shader with no AnyPS5 code reproduces it standalone**, validation-clean (§4). It is the same lavapipe behavior BF-149 found and worked around with snapshots.

**What it means for real use:** a guest whose record pointer is mapped is unaffected. A bad or unmapped pointer, on lavapipe only, crashes the process instead of logging `BDA access failed`. Two options if that is worth handling:
- **Make the emitted loads harmless on lavapipe:** select a known-mapped dummy address in place of 0 before the `OpConvertUToPtr` in `EmitBdaByte`, `read_bda_dword_bytes_stop` and their siblings.
- **Or report it to Mesa,** with §4's `loop3.comp` and `repro.cpp`.

I did neither.

**For tests that keep V# or T# words real,** like W+S#, the harness should pass the record and palette memory as snapshots, as #9790's own tests do.
