## 1. The plain answer

**Can a deferred preparation ever run with state different from what eager resolution would have used? No.**

The first use builds its state from inputs that cannot change between resolution and first use:
- **The snapshot's own `registeredState` and code/header copies.** Both are immutable and are taken at registration.
- **The ABI's context and primitive registers.** They are copied by value at resolution (`ShaderRegistry.cpp:1447-1449`), not referenced.
- **The device captured at resolution**, held as a `weak_ptr`.

`PlanRegistered` reads only these inputs, the device's target and process-wide statics; it reads no guest memory (`:785-887`). Each snapshot has its own `PreparedShaders` (`ShaderRegistry.hpp:94`), so a queued ABI can only be prepared with the snapshot it was resolved against.

The tests in section 3 compare the entries, the library prebuilds and the shader-cache keys with eager preparation. They also cover overwritten register arrays, two ABIs on one shader and a header replaced while queued.

**Two ways the end state can differ, neither with wrong state:**
- **The device is gone by the first use:** the queued ABI is skipped (`:947-948`), so the shader has fewer entries than eager and its draw prepares its own.
- **Two threads make the first use at once:** the second does not wait for the first's queued preparation, so it may prepare its own entry next to the ABI's (finding 3).

### Should fix

**1. BF-059's own test fails when the switch is exported. Fixed in 8743fac71.**
- **Cause:** `agc_driver_lazy_resolved_abi` spawns its eager reference with the inherited environment and sets `APS5_LAZY_SHADER_PREPARE` only afterwards. With the switch exported, as in a CI run of the suite with lazy preparation, the child is lazy too and fails.

- **Green:** both registrations pass, and with the switch exported:
  ```
  lazy resolved ABI: 2 of 4 ABI-resolved shaders drew; the 2 that never drew hold no prepared entries, and a drawn one drew the same 65536 bytes as with eager preparation
  ```

**2. `agc_driver_prepared_shaders_abi_deferred_compute` fails with the switch exported.** It is the one #6366 test that BF-059 newly breaks under the switch (section 6).
- **Cause:** the test requires the ABI resolution to attempt the front end once, and BF-059 moves that attempt to the first dispatch.
- **Is the behaviour right?** Checked:
  - lazy registration defers the shader (computed `s_swappc_b64` target);
  - resolution plans only;
  - the first dispatch's queued preparation fails once and is logged (`could not be prepared at its first use for its resolved ABI (... computed/data-dependent s_swappc_b64 call target ... is not statically resolvable)`);
  - the dispatch then links its callees and writes `3 * (5 + 64)` in every lane.
- **db0ac5219** makes the test assert lazy semantics when the switch is set (no front-end build at either resolution, the same dispatch check) and adds `agc_driver_prepared_shaders_abi_deferred_compute_lazy`. This is a test change, not a fix.

**3. A concurrent first use does not wait for the queued preparation. Not fixed: I have no deterministic test.**
- **Where:** `PrepareDeferredAbis` swaps the queue out under the snapshot mutex (`:944`) and prepares without holding it. Both lookups check the queue only once (`SourceHandleFor :514`, `InvocationFor :671`).
- **What happens:** a second lookup of the same shader on another thread meanwhile finds the queue empty and no ABI entries yet, and prepares its own artifact. Correctness holds: its own artifact is valid for its draw. But it repeats work eager preparation would not, and leaves an extra entry next to the ABI's.
- **Reachable when:** the same shader is first used concurrently on two threads, for example a compute shader dispatched on queue 0 and an async compute queue, or `DataHitVerification` racing a dispatch.
- **Proposed fix:** mark the snapshot `pending` while `PrepareDeferredAbis` runs and clear it with `settled.notify_all()`, so `AwaitRegisteredPreparation` makes the second lookup wait, as it does for registration preparation.
- **Why it isn't pushed:** a test needs two first uses of one shader in flight together, which the public entry points cannot make happen deterministically.

### Notes

4. **A rolled-back preparation scope keeps its queued ABI.**
   - The lazy branch records the ABI key inside the transaction but pushes the queue entry after `transaction.Commit()`, outside it (`:1445-1451`). Only the root transaction applies changes (`:337-363`).
   - If an enclosing `ShaderPreparationScope` aborts, the key is dropped but the queue entry stays. The shader's first use then prepares entries that eager resolution would have discarded, and a repeat resolve queues the ABI again (the second preparation is deduplicated by artifact).
   - It happens only on an aborted scope, which already fails the title's call. The cost is extra work, not wrong state.
5. **A queued ABI whose device has gone is dropped without a log** (`:947-948`). Eager resolution prepared it at resolve time. Draws prepare their own.
6. **Resolution under lazy preparation cannot see an unresolvable `s_swappc_b64` target.**
   - `PlanRegistered` runs `UnresolvableSwappcTarget` only when given a `deferred` pointer (`:874-875`), and the lazy branch passes none (`:1437`). The ABI is therefore queued and fails once at first use, logging the full request dump.
   - Eager #6366 also attempts and fails once, at resolve. So the cost is the same, only moved to the dispatch.
7. **Rect-list rectangles are built at the first rect-list draw.**
   - Every lazily resolved shader is marked `deferred` (`:1444`), and `ResolvePreparedGraphics` skips a stage that is deferred and has no entries (`:1576`). So `ResolveGraphicsAbi` builds no rectangles for an ABI-resolved pixel shader before its first use.
   - The draw path prepares both stages before `DrawRectangle` (`Draw.cpp:436`), so the rectangles are built at the first rect-list draw.
   - Plain lazy registration already behaves this way; it is a latency note only.
8. **`APS5_LAZY_SHADER_PREPARE=0` turns lazy preparation on.** `LazyShaderPreparation` tests `!= nullptr` (`:477`). This comes from #6366's `RegisterShader`; BF-059 only moved it into the function.
9. **With the switch exported, these tests fail on #6366's 8cd0b37a5 as well,** because they assume eager registration (section 6):
   - the six `abi_deferred_*` tests: `pixel`, `stages`, `undecodable_state`, `registration_failure`, `vertex_inputs`, `rectangle_pairs`;
   - `agc_driver_preparation_scope_settle`. It fails deterministically under the switch: 0/10 alone on both 8cd0b37a5 and db0ac5219, with "the link did not wait for the vertex shader's registration preparation". With the switch unset it passes 10/10 alone on both.
10. **`guest_audio_in_capture` aborted once,** on 1bfddbc99 with the switch exported, and passed in the five other full runs. It is unrelated to the shader registry.

## 3. The deferred state and equivalence with eager, as tests

All in `agc_driver_lazy_resolved_abi`. It now runs one scenario twice, as an eager child and as the lazy parent, and the parent compares its result with the child's report.

**0372098c8, `test(agc): compare a lazily resolved ABI's entries, libraries and cache files with eager preparation`.**
- **What the comparison covers:**
  - **Entries:** each drawn shader ends with the entries eager resolution and its draw made, fingerprinted by SPIR-V content hash and source key. A draw with the ABI's state finds the ABI's entries; a draw with another state adds its own.
  - **Nothing at resolution:** nothing is prepared or prebuilt when the ABI is resolved, and shaders that never draw hold no entries.
  - **Libraries:** the pipeline libraries built, counted after the prebuild pool drains, equal eager's. So the first use prebuilds the registration module's library, as resolution did.
  - **Disk cache:** both runs share one shader disk cache, and the lazy run writes no file the eager run did not.
- **The comparison leaves out registration-only entries.** Eager registration prepares entries for the registered state, and lazy registration prepares none by design (plain lazy, not BF-059). For a shader none of whose ABIs is the registered state, the expected lazy entries are therefore the eager entries minus those made at registration.
- **Test API:** `Driver::PreparedEntryHashes` and `Driver::PrebuiltLibraries` expose the fingerprints and counts to the test.
- **Mutation checks** (not committed), showing the comparison can fail:
  - without `plan->prebuildDevice = device` in `PrepareDeferredAbis`, the test failed with "the pipeline libraries built differ from eager preparation (eager 1 2 2 1; lazy 1 1 1 1)";
  - without applying the ABI's context registers, the test failed with "drawn shader 4 holds other prepared entries than eager resolution and its draw made".

**317b46291, `test(agc): compare stale-state cases of a deferred ABI with eager preparation`.** It adds the task's cases to the same comparison:
- **Registers rewritten between resolve and first use:** after resolution, the context and primitive register arrays the ABIs were resolved with are overwritten (every value inverted).
- **The same shader resolved twice with different ABIs before any use:** one shader is resolved with its registered state and with its draw's state.
- **A header replaced while its preparation is queued:** a second header is registered for a shader whose ABI is queued, and a draw uses it (it prepares its own). Then the first header is registered again and drawn (it finds its queued ABI's entries).
- **Resolve on one thread, first use on another:** every draw in the test already does this. Resolution runs on the test thread, and the first use runs on the queue-0 worker that decodes the draw. The truly concurrent case is finding 3.

Green, as committed (db0ac5219 build):

## 4. The first-use cost

**When Village pays it.** The first use prepares every ABI queued on the shader, then looks up the draw's own artifact. The queued preparation is extra work whenever the draw's state differs from every queued ABI's state. That happens when the title's `sceAgcDriverResolveShaderAbi` registers are not the state it draws with, for example:
- context registers the ABI omits;
- a different `SPI_PS_INPUT_CNTL` count;
- another color export format.

On BF-059's harness, where every draw differed, it cost +146 ms and +548 KB per drawn shader. The counter on BF-062's arms (`[shaders] deferred ABIs: N ..., F found ..., O prepared their own; U of E entries never matched`) measures this on Village:
- **F close to N:** the queued preparation is the draw's own work and costs nothing extra;
- **O close to N with U close to E:** it is all extra.

**Is "drop the queued state" safe? Yes for correctness.**
- **What the policy is:** BF-059 §3's one-line alternative: record the ABI key at resolution and queue nothing.
- **Why it is safe:** a draw never depends on the ABI's entries. On a miss it prepares its own, as the "own" cases in section 3 show with eager and lazy alike.
- **What it loses**, all latency, not output:
  - the ahead-of-draw variants: a pixel shader's push-constant-free variant and a compute shader's partial-threads variant, which a later draw or dispatch would prepare at use;
  - the registration module's library prebuild: 0372098c8 shows the first use does make it (libraries 1 2 2 1 against 1 1 1 1 without it), and a dropped ABI would build that library at pipeline creation instead;
  - the ABI entries' rect-list pairs.
- **Recommendation:** if Village's counter shows O close to N, dropping is the better policy. If F is a large share of N, keep 1bfddbc99's.

## 5. The disk cache and the pipeline journal

**Disk cache, cold start.** The first use compiles the ABI's artifacts and persists them, as resolution did. The requests are the same, so the keys are the same.

**Disk cache, warm start.** In 0372098c8, the eager child populated a fresh cache (42 files in the final scenario), and the lazy parent then registered, resolved and drew the same shaders. It wrote no new file: every artifact and plan its first uses needed was a hit on a key eager resolution had written.

**The pipeline journal is independent of the registry.**
- **Replay:** it builds pipelines from the modules it recorded (`PipelineJournal.cpp`, `Replay::replay` reads `loaded.modules`) on its own threads at device creation, whatever the registry holds.
- **Recording:** it records pipelines when they are built. Under lazy preparation, the ABI's library is prebuilt at first use instead of at resolution, so its record is written later in the run, but its content is the same.
- **Not tested:** the tests run with `APS5_NO_PIPELINE_JOURNAL=1`; no journal test was added.
