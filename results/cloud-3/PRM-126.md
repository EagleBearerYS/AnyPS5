### (A) Sketch 2: sweep again after `chunkFor`, and upload once, after that sweep

`Prepare` (`src/DeviceImageTable.cpp:160-172`) now runs in this order:
- `retainSlots` (:163), then `resolve`, `refresh` and `evict`;
- then `chunkFor(recorder, true)` (:167);
- then `retainSlots` (:169), `upload` (:170) and `touchSlots` (:171).

The upload that used to come before `chunkFor` is gone. The one upload now follows the last sweep.

**Why sketch 2 and not sketch 1.** `chunkFor`'s `Sync` isn't the only point where `Prepare` can submit. `resolve` runs `lookupKey`, which runs `LookupDeviceTableTexture` and then `cachedTexture`, and that path can refresh a texture and flush other images' results. So a submission can also fall between the first sweep and `chunkFor`.
- Sketch 1 (take the chunk before the first sweep) would leave that gap open.
- Running the sweep after the last point that can submit covers every one of them.
- The cost is low: `retainSlots` returns at once when `SlotSerial` hasn't moved (:441-443), and `upload` returns at once when nothing changed. So the common path adds one serial load.

**Other paths that sweep, checked.**
- **`Expect` (:174-200):** it sweeps (:177) and may then submit inside `lookupKey`. But it never uploads. What it inserts reaches the GPU only through the next `Prepare`'s upload, which now comes after that `Prepare`'s last sweep. So it needs no change.
- **`RingChunk` (:255-260):** it calls `chunkFor(recorder, true)` but doesn't sweep or upload, and only tests call it.
- **`Trailer` (:249-253):** it uses `chunkFor(recorder, false)`, which never waits.

### (B) Live table slots are touched each `Prepare`

- **New member:** `Slots::touch(std::span<const std::vector<std::uint32_t>> slots, std::uint32_t touched) -> std::uint32_t` (`include/DeviceImageTable.hpp:75`).
  - The constructor now requires it.
  - `HeapSlots` maps it to `BindlessHeap::TouchSlots` (`src/DeviceImageTable.cpp:92`). That's the same per-epoch touch heap stages use: it stores the current `useEpoch` in `slotUses` and returns early when `touched == epoch` (`src/BindlessHeap.cpp:491-500`).
- **`touchSlots()` (:454-463)** keeps a list of the live entries' slots:
  - it rebuilds the list only when `hold` (:416) or `release` (:438) changed the entries;
  - it then calls `touch` with the last epoch it touched, so the heap does the O(entries) work once per epoch, or once after a change.
- **The tests' `FakeSlots`** gets the same member (`tests/execution/DeviceImageTable.cpp:132-139`). It records each slot's epoch in a `uses` map and counts the calls that do work.
- **Effect:** `evictLocked` takes a slot only when `use + EvictIdleSubmissions <= epoch` (`src/BindlessHeap.cpp:509-513`). So a slot that any `Prepare` touched in this batch or the previous one is no longer a candidate. Table entries now leave only through the table's own budget eviction (`evict`, :557-589), which releases them through the recorder and uploads before the next draw.

## 3. The tests (in the fix commit, `tests/execution/DeviceImageTable.cpp`, ctest `agc_driver_device_image_table`)

### `SweptWhileWaitingForAChunk` (:310), the window

**What it does:**
1. Uses `FakeSlots` and inserts the five formats.
2. Opens 16 batches. Each takes a miss-ring chunk (`Trailer`) and is submitted. `Submit` doesn't reap, so all 16 chunks stay held.
3. Batch 0 carries an `OnComplete` that sweeps key 2's slot in the fake heap, moving its generation and serial.
4. A 17th `Prepare` then finds no free chunk, so `chunkFor` reaps or syncs. Batch 0 finishes inside `chunkFor`, after the `Prepare`'s first sweep. That is exactly the window.

**What it checks:**
- `chunkWaits` grew by 1, so the chunk path was taken.
- The slot's generation is 1.
- Key 2 is no longer served, and the other four are.
- The table read back from the device equals the host's buckets.

### `LiveSlotsTouched` (:347), the touch in (B)

**It checks:**
- A table without entries touches nothing.
- The `Prepare` that inserts the keys marks every live slot used in the heap's epoch (1 touch).
- A second `Prepare` in the same epoch touches nothing again.
- A `Prepare` in a later epoch touches every live slot again.
- After a sweep, the swept slot keeps its old epoch while the others move on (3 touches).

## 4. The eviction read on the fixed tree (92c6dab397)

Paths are under `core/libs/prx/libSceAgcDriver/Graphics/`. `BindlessHeap.cpp` is unchanged from PRM-125, so its line numbers are the same.

**(a) Can `evictLocked` or `ReleaseSlots` free or reuse a slot that a live entry points to while a batch may still read the table?** No.
- **`evictLocked`** picks only slots whose `use + 2 <= epoch` (`src/BindlessHeap.cpp:509-513`). Every `Prepare` now touches all live entries' slots in the current epoch (`src/DeviceImageTable.cpp:171`, :454-463, then `src/BindlessHeap.cpp:491-500`). So a live slot can only be picked after two submissions in which no `Prepare` ran, which means no draw or dispatch in those batches read the table. Even then the slot returns to the free list only once the serial that covers it completes (`src/BindlessHeap.cpp:529`, :1486-1489, :537-549).
- **`ReleaseSlots`** runs only from the owner's destructor (`include/BindlessHeap.hpp:246-249`). The entry holds the texture (`src/DeviceImageTable.cpp:404-417`), and a dropped entry hands it to `recorder.Keep` (:436). This is unchanged from PRM-125.

**(b) Does `retainSlots` keep those slots off eviction, and does `SlotGeneration` change on reuse?**
- `retainSlots` (:441-452) still only detects moves after the fact, through `SlotSerial` and each entry's generation.
- Keeping slots off eviction is now the job of the touch in (B) (:171).
- `SlotGeneration` changes on eviction (`src/BindlessHeap.cpp:528`) and on free (:444), before any reuse. `Take` doesn't change it (:429-441).

**(c) Is there a path where the table serves an evicted, reused slot?** **No.**
- **Inside `Prepare`:** the last sweep and the upload now run after `chunkFor` (:167-170), and nothing after them in `Prepare` submits.
- **After `Prepare` returns:** the draw's commands go into the same open batch. This is the GPU-heap path's own invariant:
  - the miss-ring chunk the `Trailer` hands out belongs to the open serial (:249-253, :637-660);
  - the heap ring chunks are stamped with the batch serial at `Submitted` (`src/BindlessHeap.cpp:1492-1497`);
  - the early submit (`Recorder::BoundDrawBatch`, `src/Recorder.cpp:3100`) runs before `Prepare` (`src/Draw.cpp:3223`, :4144).
- **Eviction later in that batch** (another stage's `TextureSlot`, then `noteTakenLocked`, then `evictLocked`, `src/BindlessHeap.cpp:483`) can't take a slot that was just touched. And whatever it does take gets that batch's serial (:1486-1489), so it isn't reused before the batch completes.
- **A second safety margin:** if one submission ever did fall between `Prepare` and the draw, (B) still keeps the slot off eviction for one more submission.
- The PRM-125 path (`chunkFor` → `Sync` → `Submitted` → `evictLocked` at :1485, then reuse while batch N+1 reads K→S) now ends with K swept and uploaded before N+1's draw. That's the red/green test in §3.
