## Per function

### Implemented: `sceVideodec2GetHevcPictureInfo` (`core/libs/prx/libSceVideodec2/Export.cpp`)

- **Signature `(const OutputInfo*, HevcPictureInfo*)`:** from three sources that agree.
  - [SharpProspero Videodec2.cs L766-L769](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Video/Videodec2.cs#L766-L769) (the commit the debt file already cites);
  - [shadPS4 `videodec2.h` L292](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/videodec/videodec2.h#L292);
  - [Orbital's PS4 IDA type database](https://github.com/AlexAltea/orbital/blob/cc408367da6a6ebbf5ac1ac559fefeadc73b2831/tools/ida/db_types.json) line 2402: `int32_t sceVideodec2GetHevcPictureInfo(const struct *pOutputInfoIn, SceVideodec2HevcPictureInfo *pPictureInfoOut)`.
- **Layout, 0xb8 bytes:** [SharpProspero L404-L630](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Video/Videodec2.cs#L404-L630) and [shadPS4 `OrbisVideodec2HevcPictureInfo` L176-L253](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/videodec/videodec2.h#L176-L253) (`static_assert(sizeof == 0xB8)`) list the same fields in the same order. EVO-PLAYER-PS5's `sce_videodec2.h` (`9715f6ee9bf9`, the debt file's other source) has no HEVC picture info and no `GetHevcPictureInfo`.
- **Same as Vdecsw's `HevcPictureInfo`?** Yes, byte for byte. I worked out SharpProspero's offsets field by field:

  | Offset | Fields |
  |---|---|
  | 0x28 | width |
  | 0x30-0x32 | bit depths, timing flag |
  | 0x34-0x3c | tick, scale, aspect flag |
  | 0x40 | idc |
  | 0x42, 0x44 | SAR |
  | 0x46-0x4d | video signal, 8 bytes |
  | 0x50 | picStruct |
  | 0x5c | conformanceWindowFlag |
  | 0x60-0x6c | window |
  | 0x70-0x80 | default display window, 5 words |
  | 0x84-0x87 | chroma location, 4 bytes |
  | 0x88-0x92 | present flags, 11 bytes |
  | 0x93 | IDR |
  | 0x97 | profile |
  | 0x98-0x9a | source flags |
  | 0x9b | level |
  | 0x9c-0xa4 | sub-layer, 9 bytes |
  | 0xa5 | frameCroppingFlag |
  | 0xa8-0xb4 | crop |

  Every offset `libSceVdecsw/Export.cpp` asserts matches.
  - **The difference is only in spelling:** Vdecsw groups `videoSignal[8]`, `defaultDisplayWindow[5]`, `chromaLocation[4]`, `presentFlags[11]`, `generalSourceFlags[3]` and `subLayer[9]` as arrays.
  - **Videodec2's new `SceVideodec2::HevcPictureInfo` names every field**, as SharpProspero and shadPS4 do, and asserts the same offsets plus 0x70 and 0x84.
  - **I did not change Vdecsw**, to stay off #10381's library.
- **Built the way `GetAvcPictureInfo`/`GetVp9PictureInfo` are:**
  - **Picture lookup:** it finds the decoder that last wrote `output->frameBuffer` with the same owner loop as `GetVp9PictureInfo`.
  - **Unknown buffer:** a buffer no decoder owns gives `isValid = false` and returns 0, as the AVC and VP9 calls do.
  - **What throws:** null pointers, `info->thisSize` below 0xb8, an output too small to hold `frameBuffer`, and a picture of another codec. That is the VP9 rule, written down in the VP9 debt entry. Console error codes are unknown.
  - **Size field:** `thisSize` is the caller's and is kept.
- **Fields filled:** the same set Vdecsw fills, now kept per picture in Videodec2. Everything else is 0, as in Vdecsw; the decoder does not keep it.

  | Field | Value | Source |
  |---|---|---|
  | timestamps | pts, dts, attached | as for AVC |
  | coded width, height | the picture's own decoded size | stored per picture, so a caller who edits `output.frameWidth` still gets the picture's size (as the VP9 info does) |
  | `bitDepthLuma/ChromaMinus8` | the picture's 0 or 2 | FFmpeg's HEVC decoder refuses unequal luma and chroma depths |
  | `idrPictureFlag` | main's existing `hevcIdr` | the first VCL NAL is type 19 or 20 |
  | `irapPictureFlag` | FFmpeg's key flag | FFmpeg sets `AV_FRAME_FLAG_KEY` exactly when `IS_IRAP` (`hevcdec.c` L3234-L3237 in FFmpeg n7.1; the bundled build is libavcodec 61.19.101) |
  | `generalProfileIdc`, `generalLevelIdc` | the decoder's latest profile and level | as for AVC and Vdecsw |
  | `conformanceWindowFlag` and `confWin*Offset` | the frame's crop, divided by the chroma subsampling, in chroma samples as in the SPS | see the note below |
  | `frameCroppingFlag`/`frameCrop*` | repeat the conformance window | as in Vdecsw; the unit is unknown |

  Notes on the conformance window:
  - **The crop is the SPS window exactly:** FFmpeg's crop is the SPS window times SubWidthC/SubHeightC (n7.1 `ps.c` L1243-L1250). `apply_defdispwin` is 0 by default, so the default display window is not added (L1534). With `AV_EF_EXPLODE` set, invalid offsets are an error rather than zeroed (L1542-L1555).
  - **Chroma formats:** the divisor comes from the decoded format's `log2_chroma_w/h`, so 4:2:2, 4:4:4 and monochrome HEVC streams get the right units. Vdecsw divides by 2 for every format, which is wrong for 4:2:2 and 4:4:4. That is outside this task and next to #10381's lines, so I left it; it is a possible follow-up.
  - **The flag:** it is set when any offset is nonzero. An SPS with `conformance_window_flag` 1 and all-zero offsets reports 0.
- **`sceVideodec2GetPictureInfo`** (and `GetAvcPictureInfo`, which shares its body) now writes this layout for an HEVC picture, as its VP9 branch does for VP9. Before, it threw "picture info is only implemented for H.264 and VP9". Sources:
  - SharpProspero's doc comment on `GetPictureInfo`: "Fills a codec-appropriate picture-info structure … the other codecs fill only the first";
  - shadPS4's `GetHevcPictureInfo`, which is `GetPictureInfo(output, info, nullptr)` (`videodec2.cpp` L278-L282).

  An AVC-sized (0x38) structure for an HEVC picture still throws, so the existing `testClip` and `testPictureOwnership` checks keep passing.
