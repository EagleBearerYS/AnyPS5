## 1. Design

### 1.1 Where the time went (main)

At every capture, `TableSnapshotter::Column` (ResourceMaterializer.cpp) does three things for each table column:
- plans the records' dword runs, asking for every page's accessibility;
- reads every run through `SrtRuntime::readWords` (ShaderMemory copies each 4 KiB page from guest memory);
- looks every record up in the snapshot's distinct-descriptor index (`WordsIndex`).

The earlier profile of a 32,768-record column of distinct T#s: `WordsIndex` was 57% of the samples, malloc 10–17%, the reads and region bookkeeping most of the rest.

Village's title captures such columns on nearly every draw-cache miss. PM-026 found 32,768 keys per table and narrowing applied to 0 of 34,294 snapshots.

### 1.2 The column memo (ResourceMaterializer.cpp:399-445, 672-678, 786-915)

- **Key:** `ColumnKey` is everything the walk depends on besides memory:
  - heap base and size, record and key counts;
  - stride, addend, offset and dword count;
  - `maxKey`, the folded addend and carry;
  - pointer or buffer column, sampler or image.
- **Value:** `ColumnMemo` holds:
  - the dword runs read and their words;
  - each record's state;
  - each record's code, as an index into the memo's own distinct T#s;
  - the distinct T#s, in first-occurrence order;
  - the read ranges and pointer-column bounds;
  - the write stamp.
- **What is kept:**
  - Not kept: narrowed columns (their keys come from memory), pointer-indirect columns (`column.indirect`), and any column with an Unmapped record.
  - Carried records (offset carry) and out-of-buffer dwords are kept. They depend only on the key.
- **Bounds:**
  - At most 16 columns per thread (`ColumnMemoEntries`) and 4 Mi 32-bit words of footprint per thread (`ColumnMemoWords`, 16 MiB). The footprint counts words, codes, states, distinct T#s (9 words each), runs and ranges.
  - Least recently used goes first out. A column bigger than the cap is not kept.
  - A 65,536-record column of distinct T#s is about 1.2 Mi words, so three fit.
  - An entry is updated in place, reusing its vectors' capacity, so a column that changes every capture doesn't allocate.
- **Threads:**
  - The memo is per thread (`thread_local` through `ThreadOwned`, freed at thread exit), so a capture never shares it.
  - The counters are relaxed atomics.
  - The `ShaderMemory` behind the callbacks belongs to one capture.
- **Switch:** `APS5_NO_TABLE_SNAPSHOT_REUSE=1` turns the memo off. The column is then walked exactly as on main.
- **Counters:**
  - The `[image-table]` profile line (`APS5_PROFILE_DRAW`) adds "reused N unwritten / M compared".
  - `ResourceMaterializer::TableReuse()` returns monotonic totals (unwritten, compared, words read) for tests and benches.

### 1.3 Reuse without per-record work (`Apply`, ResourceMaterializer.cpp:838)

The kept states, codes and read ranges replace the walk's, so the result must be what a fresh walk would make.
- **The snapshot's first column (`tables.words` empty):** the distinct T#s are taken as they are, and the codes are the memo's.
  - `WordsIndex` builds its hash index lazily (`indexed`) only if a later column needs it.
- **Otherwise:** one `WordsIndex` call per distinct T#, in first-occurrence order, gives the same global order the per-record walk gives. The codes are then remapped.
- Recompile hashes the whole snapshot. The test asserts `reused.tables == fresh.tables`, and the CompileTable check resolves keys through a reused table.

### 1.4 Skipping the read: three optional `SrtRuntime` callbacks (SrtWalker.hpp:17-24, 47-49)

- `stampWrites(address, bytes) → SrtWriteStamp{generation, layout}`
  - Called once per kept column before planning reads anything of it.
  - The span is the heap from its base to the last record's last dword.
- `unchangedSince(address, bytes, stamp) → bool`: nothing wrote the range since the stamp.
- `supplyWords(address, values, count) → bool`: hands the capture words equal to guest memory as if it had read them.
  - They stay in the captured regions the draw cache compares on later hits, and they are marked read and recent.

`Unwritten` (ResourceMaterializer.cpp:805) works like this:
- It needs a valid memo stamp.
- It asks `unchangedSince` for every run, then supplies every run.
- If any answer is no, `Compared` reads the runs through `readWords` and compares them with the kept words.
- On a match, the memo's stamp moves to this capture's stamp.

### 1.5 How ShaderMemory vouches (ShaderMemory.cpp:271-332)

- **`stampWrites`** returns no stamp when:
  - the range overlaps the request's initial regions;
  - any page of it was already fetched by this capture (a read made before the stamp would not be covered);
  - recorded GPU work writes it (`pendingWrite != None`).

  Otherwise it calls `GuestMemory::FlushGpuWrites(range)`. The stamp is then `{GuestMemory::CollectWrites(range), GuestAllocationsGeneration()}`. A zero generation (unwatched or partly unwatched memory) means no stamp.
- **`unchangedSince`** answers no when:
  - the mapping generation moved;
  - recorded GPU work writes the range.

  Otherwise it calls `FlushGpuWrites(range)`, then `CollectWrites(range)`, which must be nonzero. The answer is then `GuestMemory::UnchangedSince(range, stamp.generation)`.
- **`supplyWords`** works page by page:
  - A page not yet captured must be accessible (`GuestMemory::Accessible`).
  - A word-wise page (pending GPU writes) refuses.
  - A page with no valid word gets a memcpy. Otherwise only its invalid words are filled.
  - Valid, read and recent are set for the run's words.
- **The flush** does what a read would do first. A read through `GuestMemory` calls the hook (GuestMemory.hpp:189-195), and so does the dispatch cache before it validates (VariantValidation.cpp:90-100). It runs only after the pending-write check, so it adds no GPU wait that the capture's own evidence policies (KnownValue, Raw) would have avoided.
- **Epochs:** a CPU store between two collects of one collect epoch (same thread, no ordering point) is seen at the next epoch, as for every other stamp in the driver. A re-watch (`watchPrivateMapping`) stamps every block.

### 1.6 A changed column (commit 5, ResourceMaterializer.cpp:748, 818-836)

When `Compared` finds a difference, it leaves its words with the snapshotter. The fresh walk then takes them instead of reading again whenever its plan has the same runs (`runs == comparedRuns`), which is the normal case. A word the capture has already read reads the same again. So a capture after a change reads each word once, as main does.

### 5.3 What the worst case still pays, and follow-ups not in this branch

**Costs:**
- The compare: a memcmp of the run words.
- Keeping the column: copying the distinct T#s (65,536 × 36 bytes), codes and states into the memo entry.
- The two flush-hook calls per column.

With 16 distinct T#s these costs are smaller than the lazy words index saves, hence the gain.

**Possible follow-ups:**
- Share the distinct-T# vector between the snapshot and the memo instead of copying it.
- Stop keeping a column after N consecutive changes.
- Reuse the whole snapshot (and its hash) when every column was an unwritten skip. SleglJan's 16c4c7466 explores this.

The bench runs without the Recorder, so the flush hook is empty here. In the driver, each kept column adds two FlushForAccess calls per capture, where main makes one per 4 KiB page fetched.

```cpp
std::uint32_t WordsIndex(const DescriptorValue& value) {
    for (; indexed < tables.words.size(); indexed++) wordsIndex.try_emplace({tables.words[indexed].dwords, tables.words[indexed].dwordCount, tables.words[indexed].availableDwordMask}, static_cast<std::uint32_t>(indexed));
    const auto [found, inserted] = wordsIndex.try_emplace({value.dwords, value.dwordCount, value.availableDwordMask}, static_cast<std::uint32_t>(tables.words.size()));
    if (inserted) {
        tables.words.push_back(value);
        indexed = tables.words.size();
    }
    return found->second;
}
```

## 7. Draft PR text

Title: `perf(shader): skip an image table column's read while its memory is unwritten`

```markdown
### What
Every draw-cache miss of a shader with an image table read every record of each table column from guest memory and looked each record up among the snapshot's distinct descriptors. A 32,768-record column of distinct T#s cost 6.0 ms per capture, a 65,536-record heap 15.4 ms.

`TableSnapshotter` now keeps the last 16 column snapshots per thread (at most 4 Mi words in all, least recently used first out; `APS5_NO_TABLE_SNAPSHOT_REUSE=1` turns them off): the runs read, their words, each record's state and code and the distinct T#s. A narrowed or pointer-indirect column, or one with an unmapped record, is not kept. A capture of a kept column takes its codes and distinct T#s with no per-record work, so the snapshot is the one a fresh walk makes.

The column is not even read while `ShaderMemory` vouches for its runs through the write tracker:
- the runs were stamped by `GuestMemory::CollectWrites` before any page of them was read;
- no block of them was stamped since (collected CPU stores, the driver's `Write`, `WriteChanged` and `StoreOwnBytes`, `MarkWritten`);
- no recorded GPU work writes them;
- the guest mapping generation is the stamp's.

Before the stamp and before the check, `GuestMemory::FlushGpuWrites` stores what a read would store first: storage image results kept on the GPU, unit shadows and queued labels. The words are handed to the capture as read (`SrtRuntime::supplyWords`), so they stay in the captured regions the draw cache compares. Otherwise, outside the write watch for example, the runs are read and compared: equal, the snapshot is reused; different, the column is walked afresh from the words just read.

The same approach was prototyped in SleglJan's `share/007-tables-v1` experiments (cdbf8dbbe and follow-ups); this is an independent implementation on current main.
```
