## Q1: NoteWrittenBack over whole heap spans

### Can a label sit inside such a span? Yes.

- A label reaches the GPU only through a host import of its own few bytes: `HostImportFor(context, address, bytes.size())` (`Execution/src/VulkanDevice.cpp:2509`).
- An address-storing build serves the same heap through a mirror, and `addAddressStoreSpans` puts the mirror's whole served span in `writes`.
- On `781dc4525b`, `WriteBack` notes that whole merged span (`GuestBufferMemory.cpp:6285`), so a label anywhere in the heap is "written back" even when no thread stored to it. Three things follow:
  - `writeBacksOverLabels` goes up (`Recorder.cpp:3588`), the `[recorder]` counter that must stay 0;
  - a GPU-stored completion label (`AfterCompletions(..., storedOnGpu=true)`, used when a copied writer overlaps the label) is counted pending (`:3600`);
  - its completion store is forced (`writtenBackSince` is true at `:3533`), so the stale label value lands over whatever the CPU wrote there since.

### The change (`bf54c5e942`)

- **`GuestMemory::WriteChanged`** gets an overload that also returns the byte runs it stored (`Execution/src/GuestMemory.cpp:2868`, runs appended at `:2908`/`:2916`). They come from the diff's existing per-16-byte change masks, so there is no second compare. The other overloads are unchanged.
- **`storeChanged` / `storeSparse`** take an optional output for those runs (`Graphics/src/GuestBufferMemory.cpp`).
- **`WriteBack`**, for a merged range in a writable heap mirror of an address-storing build (`:6305`):
  - declared write ranges (`writes` before `addAddressStoreSpans`, kept by index, `:6260`) are noted whole, as today (`:6310`);
  - the rest is noted only for the runs actually stored, minus the declared parts (`outside`, `:6189`; notes at `:6336` and `:6349`).
  - Every other region keeps today's single note.
- **`Recorder::NoteWrittenBack(span)`** (`Graphics/src/Recorder.cpp:3614`) joins runs across gaps that hold no tracked label (one table lock; `pendingLabelInLocked`, split out of `PendingLabelIn`, `:3444`), then notes each joined range as before.
  - Without the join, a scattered store pattern could produce millions of runs and overflow the 16,384-entry ring. `writtenBackSince` then answers "true" for every label, which would be worse than today.
  - The join is exact: a label dword that starts before a gap but reaches into it already overlaps the run before the gap. The ring and the counters only ever ask about label ranges.
- **`Recorder::WriteBacksOverLabels()`** (`:3628`) exposes the `[recorder]` counter for the test.

## Q2: two storing builds in flight over one heap

**The order rules it out.** B can't take its reference while A is unfinished. Lines are at `781dc4525b`, and the commit doesn't change any of them.

1. **A notes its whole heap span as a pending write** when it is recorded. `recordDispatch` → `MarkGpuWrites` (`Execution/src/VulkanDevice.cpp:5329`) → `recorder.NotePendingWrites(guestMemory.Writes())` (`Graphics/src/ShaderResources.cpp:5854`). `Writes()` holds the spans `addAddressStoreSpans` added (`GuestBufferMemory.cpp:5617`).
2. **A's write-back runs only when its batch finishes.** `OnComplete` → `kept->WriteBackBuffers()` (`VulkanDevice.cpp:5346-5352`) runs inside `Recorder::finish` (`Recorder.cpp:4224`), and batches finish front-first.
3. **B refreshes the heap mirror before it takes any reference.**
   - `prepareAddressBindings` → `guestMemory.AcquireRegistered()` (`ShaderAddressResources.cpp:146`) → `refreshHeapRuns` / `refreshHeapMirrors` (`GuestBufferMemory.cpp:4643-4644`).
   - These call `prepareRange` over **every whole heap run**, before any changed-block check (`:3070`, `:2934`).
   - `prepareRange` → `syncRange` (`:2810-2823`): `if (recorder->PendingWriteOverlaps(...)) recorder->Sync();`. `PendingWriteOverlaps` scans the open batch and every in-flight batch (`Recorder.cpp:3126-3135`).
   - So A's span is pending, B does a full `Sync()`, and A's dispatch and write-back are complete before B goes on.
   - Only then does B's `UploadFinish` call `takeHeapReferences()` (`GuestBufferMemory.cpp:5618`).
4. **All of this is under one `GuestMemory::GpuMutex` hold per dispatch,** so nothing interleaves between A's reference and A's pending-write note, or between B's sync and B's reference.

So B's reference already holds A's stores, its diff never repeats them, and a CPU store made after A's write-back is pulled into B's refresh and kept.

**Two side notes for the PR (no change made):**
- **Untested:** the existing test helper `WaitIdle`s after every dispatch, so no test builds B while A is in flight. A test with two storing dispatches and no wait between them would pin this down.
- **A cost on top of the per-dispatch cost already measured in BF-273:** while a storing build is in flight, every later address-based build that maps the heap does a full `Recorder::Sync()` in `syncRange`, which serializes them. BF-278's stored-block bitmap doesn't remove that by itself, because the pending-write note is still the whole span.

## Paste-ready text

**Q1 (labels in a heap span).** Yes: a label is stored through a host import of its own bytes (`VulkanDevice.cpp:2509`) while an address-based build serves the same heap through a mirror. On 781dc4525b, `WriteBack` noted the whole served span (`GuestBufferMemory.cpp:6285`), so such a label was counted pending, its completion store forced, and the `[recorder]` write-back-over-label counter went up. bf54c5e942 (fork `fix/agc-bda-store-writable-mirror-review`) keeps declared write ranges as they are and notes the rest of an address-store span only for the runs `WriteChanged` actually stored. The recorder joins them across label-free gaps, so the note stays exact without overflowing the write-back ring. `LabelTests` in `tests/execution/BdaStoreHeapMirror.cpp` checks this: a label the dispatch doesn't touch keeps the CPU's bytes and the counter stays 0, while a label a thread stores over is still noted. It is red on 781dc4525b and green ×10.

**Q2 (two storing builds over one heap).** The order rules it out. A's whole heap span is a pending write once it is recorded (`MarkGpuWrites` → `NotePendingWrites(Writes())`, `ShaderResources.cpp:5854`). Before B takes any reference, its `AcquireRegistered` refreshes every heap run through `prepareRange` → `syncRange` (`GuestBufferMemory.cpp:3070`, `:2934`, `:2810-2823`), which calls `Recorder::Sync()` when a pending write overlaps the run. So A's dispatch and write-back (its batch's `OnComplete`, `VulkanDevice.cpp:5346-5352`) finish before B's `takeHeapReferences()` (`:5618`). B's reference therefore already contains A's stores, and B's diff never repeats them. The cost is that later address-based builds over that heap serialize behind a storing build in flight.
