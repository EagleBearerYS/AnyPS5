## Change 1 (770a499ba): non-pipe-aligned depth-only HTILE

- **Before:** `prepareDepthSampling` refused any HTILE that was not pipe-aligned.
- **Now:** a depth-only HTILE that is neither pipe-aligned nor ITERATE_256 is imported when every word over `HtileMetadataBytes(extent)` is the same word and proves the clear.
  - Pipe alignment only moves words between tiles, so one repeated word proves the same thing in any order.
  - A non-pipe-aligned HTILE whose words differ is refused: "native multisample depth HTILE that is not pipe-aligned holds more than one word".
  - An HTILE that holds stencil keeps the alignment refusal.
- **Range:** `HtileMetadataBytes(1920x2160)` = 10 blocks × 32 KiB = **0x50000**, which is exactly Ghost's HTILE fill.
- **Tests:** every `--separate-stencil` case also runs with `pipeAligned = false` (and so ITERATE_256 off), sampled through the HTILE descriptor and through the one without metadata. One differing word is refused.

## Change 2 (90d652a1e): whole stencil plane fill as a stencil clear

`NoteDepthMetadataFill` now handles a fill over the separate stencil plane of a sampling-active target with a depth-only HTILE. It is proven at the next sample the way #6300 proves a whole-HTILE fill:

- no CPU write since the fill;
- complete tracked stores since the fill, unless the fill is the plane's newest queued GPU write;
- once the fill has landed, every plane byte equal to the fill byte.

The host image's stencil aspect is then cleared to that byte (`RecordClear(VK_IMAGE_ASPECT_STENCIL_BIT)`).

Refused fills:
- part of the plane: "native multisample stencil plane partial fill transition is not implemented";
- a pattern that is not one repeated byte: "…fill of more than one byte value…";
- unwatched memory: "…fill over unwatched memory…";
- a second fill before the first is proven: "overlapping native multisample stencil plane fills are not implemented".

`MultisampledDepthBytes(1920x2160, 1 byte, 2 samples)`:
- the 64 KiB block is 128x256, so the plane is 1920x2304x2 = **0x870000**;
- that is exactly Ghost's stencil fill, so `PlaneFillCovers` takes it.

## Step 3: what still refused Ghost's two fills, and the fix

### 1. DMA_DATA fills larger than 64 KiB (0e17d12ff)

Both of Ghost's fills are larger than 64 KiB.

- **The order in the driver:**
  - `preparePacketMemory` calls `NoteDepthMetadataFill` first, at PacketMemory.cpp:66-73.
  - The fill is stored later, at PacketMemory.cpp:194-200: `storeBufferFill(…, noteMetadata = false)`.
  - When the range has a host import, `VulkanDevice::FillBuffer` then records the GPU fill: `NotePendingWordFill` and `MarkWritten`.
- **Why it refused:** at the time of the note, `LastWriteNote` found no write, so the fill's note was 0.
  - The first sample in the same batch saw the queued fill as a foreign write: **"external GPU writes over native multisample depth are not implemented"**.
  - This happens to the HTILE fill first, then to the stencil plane fill.
- **Not affected:** a compute fill. `storeBufferFill(…, true)` notes after it records the write, and #6300's queued-fill test models that order.
- **The fix:** when the fill had no note, the sample looks at the writes recorded over the HTILE (or plane) since the note.
  - It takes that write's note when it is the **only** such write, covers the whole range, and is a word fill of the noted pattern.
  - A later queued write, a different word, or a queued fill of part of the range still refuses with the same text.

### 2. Compute memory-value fills (5daa8cb7a)

- **Why it refused:** this kernel is noted twice.
  - Dispatch.cpp:132 (`MatchMemoryValueFill`) notes it before the fill runs.
  - `storeBufferFill` notes it again after `FillBuffer` (BufferFill.cpp:423).
  - The second note refused: "overlapping native multisample depth clear transitions are not implemented" for the HTILE, and the same refusal for the stencil plane.
- **The fix:** a second note of a pending fill counts as the same fill when all of these hold:
  - the pattern is the same;
  - the first note had no write note;
  - the one write recorded since the first note is a word fill of the whole range with that pattern.
- **Still refused:** two notes with no such write between them refuse as before. #6300's FillOverlap case still passes, and there is a new stencil plane case.
- **Not handled:** a memory-value fill that falls back to CPU stores (no host import of the range) is still refused as overlapping.

### 3. "native multisample depth metadata fill transition is not implemented"

- **Where the text comes from:** on #6300 (c11074be8, DepthSurface.cpp:1382), `NoteDepthMetadataFill` sets it for a fill over the HTILE in two cases:
  - the fill does not cover the whole HTILE, or
  - the target's sampling never activated.
- **What it means for Ghost:** Ghost's fill covers exactly 0x50000, so its target's sampling was most likely refused at creation.
  - #6300 assigned `sampling.refusal` directly, so the fill's text replaced the creation reason.
  - The same overwriting is what Gashrod1 described for DAVE THE DIVER.
- **On this branch:** the merge with main brought `DepthSamplingState::Refuse`, which keeps the first refusal. A new test checks that a target refused at creation still reports its creation reason after both fills.
- **On Ghost's creation:**
  - milescoviello's latest stop, with the handoff branch merged, is "native multisample stencil import requires HTILE stencil metadata". BF-122's change 1 removes that refusal for a depth-only HTILE with a separate plane. The next creation check, pipe alignment, is removed by change 1 here.
  - One assumption remains unproven: **is Ghost's target cleared when the driver first creates it?** That needs all HTILE words to be one clear word and every stencil plane byte equal to `DB_STENCIL_CLEAR`.
  - If Ghost binds the target before these fills while the memory still holds older content, creation refuses and eligibility is never retried. The next run would then print that creation reason, e.g. "native multisample stencil plane does not hold its clear value" or "…HTILE that is not pipe-aligned holds more than one word".
  - No log shows when creation happens relative to the fills. If that is the next stop, the fix would be to re-arm eligibility after whole fills of both the HTILE and the stencil plane, which together decide the whole target. That is a new rule, so I did not add it.

## Tests

All tests are in `agc_driver_native_depth_separate_stencil` (`--separate-stencil`).

- lavapipe samples D32S8 only at 4 samples, so 2 and 8 samples are reported as unavailable. Ghost's target is 2-sample; its sequence runs at 4 here.
- The extent is 5x3, not 1920x2160.

**(1)/(1b):** separate-stencil cases on pipe-aligned and non-pipe-aligned depth-only HTILE; one differing word is refused.

**(2)/(2b):**
- For each of clear 0/1 and pipe-aligned or not, after a draw that replaces the stencil with 0xc3, the test fills the HTILE, the stencil plane, or both.
- It then checks the sampled depth (the clear after an HTILE fill, else the drawn depth) and which stencil reference the next draw passes (the fill byte after a plane fill, else 0xc3).
- Refused fills: partial, two-byte pattern (0x00010001), unstored, CPU-raced.

**(3) Ghost's sequence**
- Setup: creation of a D32S8 target with a depth-only HTILE that is neither pipe-aligned nor ITERATE_256, a separate stencil plane, clear 0 and stencil 0. The depth plane holds 0x5c garbage.
- Then a whole-HTILE fill of 0 and a whole stencil plane fill of 0, and then the first sample.
- The fills arrive in four orders:
  - stored (CPU path);
  - queued after the note (DMA_DATA order);
  - queued before the note (compute order);
  - noted, queued and noted again (memory-value compute).
- Each order samples depth 0 on every sample, passes stencil reference 0 and misses reference 1.
- Faults, each queued after the note:
  - a later queued stencil byte write, a queued HTILE fill of 0xfffffff0, and a queued fill of the HTILE minus 4 bytes all refuse "external GPU writes over native multisample depth are not implemented";
  - a stencil plane fill noted twice with no write between refuses "overlapping native multisample stencil plane fills are not implemented";
  - a target refused at creation keeps "native multisample depth HTILE that is not pipe-aligned holds more than one word" after both fills.
- **Modelling note:** a queued fill stores its content and stamp when it is queued, as #6300's queued-fill test does, not when the GPU write lands. How a real host import stamps the landed write is not exercised here.
