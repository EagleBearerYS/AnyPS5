## The case

There is one write-watched guest block: a 256x256x4 = 256 KiB surface plus 64 KiB, 64 KiB-aligned and registered as a guest allocation. X and Y are two `StorageTexture`s on the same base address with different descriptors. One frame is one round:

1. **Y looked up** (`Y->Refresh()`): X's pending results go to guest memory as a "storage refresh" write-back, and Y is uploaded again.
2. **Y written**: a GPU write through Y (`vkCmdClearColorImage` of a per-round value, then `MarkDirty`) leaves Y's results pending. This is the same pending-write fixture as `clearHandOverTests`.
3. **X looked up**: (c) of the task. Y's results are written back over X's memory ("storage refresh") and X is uploaded again ("flushed").
4. **X written**: X's own write, also left pending.

There are 4 rounds. The values written differ every round and between X and Y, so a stale image or stale memory fails the checks.

The parametrized pairs all cover exactly 256 KiB of the same memory:

| pair | X | Y |
|---|---|---|
| same format, other dimensions | R32_UINT 256x256, R 64 KiB X | R32_UINT 512x128, R 64 KiB X |
| other format, same bytes per texel | R32_UINT 256x256, R 64 KiB X | RGBA8 UNORM 256x256, R 64 KiB X |
| tiled against linear | R32_UINT 256x256, R 64 KiB X | R32_UINT 256x256, linear |

A pair for Village's real images is one more row in `pairs` once BF-290 names them.

The guest-memory modes each run all three pairs:
- **copied guest memory** (`context.hostImportAlignment = 0`): write-backs are stored through staging into write-watched memory, so every block keeps a generation. This is the mode that produces Village's labels: "storage refresh" write-backs and "flushed" uploads.
- **imported guest memory** (the device's own import decision): on lavapipe the import probe makes imported ranges "compared", so the same re-uploads are labelled `cpu`. A compared block cannot tell who wrote it.

I left out forcing watched imports on lavapipe (`APS5_WRITE_WATCH_IMPORTS=watch` / `SetImportWatch(Watch)`). It labels round 0 "flushed", but llvmpipe's GPU writes through the import are CPU stores that the write watch reports late. From round 1 the driver then sees a "CPU" write over X's pending results and correctly drops them, so Y misses X's results. That is why `clearHandOverTests` skips this mode when the probe says "compared". Village's Windows path settles its imports and keeps them watched, which gives the same labels as the copied mode here.

### Two passes per pair

Each pair runs twice: a measured pass, then a flushing pass.
- **The measured pass** prints the traffic of every step and checks only GPU contents. It never flushes in the middle, so a device-side handoff that leaves Y's results in X on the GPU is neither punished nor masked, and the counts contain only the driver's own traffic.
- **The flushing pass** runs the same rounds. After each lookup it also calls `FlushPending(surface, PublishScope::Whole)`, publishes any unit shadow, waits, and compares guest memory. That is the "guest memory equals it after a flush" check. On main these flushes find nothing pending, because the lookup already wrote the other image's results back.

## Content checks (all pass on main and on 41ef8ff856)

Checked after every lookup, in both passes, by reading the image back on the GPU (`vkCmdCopyImageToBuffer`, then submit and wait):
- `Y does not hold X's last results after its lookup`: round 0 checks the initial 0x5a fill.
- `X does not hold Y's results after its lookup`.

Checked in the flushing pass only, after a flush:
- `guest memory does not hold X's last results after Y's lookup and a flush`
- `guest memory does not hold Y's results after X's lookup and a flush`

Checked at the end of each pass (X's own later writes are kept):
- `X's last results were not pending at the end`: X's last write must still be pending.
- `guest memory does not hold X's last results after the final flush`
- `X lost its last results`: X's image still holds its last write after the final flush.

There are no assertions on byte counts.

## Which pairs reproduce "flushed" on main

All three pairs do, in the copied mode. The bytes per step are the same for every pair, on main and on 41ef8ff856, and the same in all 10 runs on each:

| step | copied guest memory | imported guest memory (compared on lavapipe) |
|---|---|---|
| round 0, Y looked up | none | none |
| Y written / X written (every round) | none | none |
| round 0..3, X looked up | write-back 'storage refresh' 1x 262144 B; upload 'flushed' 1x 262144 B | write-back 'storage refresh' 1x 262144 B; upload 'cpu' 1x 262144 B |
| round 1..3, Y looked up | write-back 'storage refresh' 1x 262144 B; upload 'flushed' 1x 262144 B | write-back 'storage refresh' 1x 262144 B; upload 'cpu' 1x 262144 B |

Per pair, over the measured pass (4 rounds, 8 lookups):

```
copied:   'storage refresh' write-backs 7x 1835008 bytes, 'flushed' uploads 7x 1835008 bytes, guest memory write-watched;
          all traffic: upload 'first' 2x 524288 bytes; upload 'flushed' 7x 1835008 bytes;
                       write-back 'storage alias round trip test' 1x 262144 bytes; write-back 'storage refresh' 7x 1835008 bytes;
imported: 'storage refresh' write-backs 7x 1835008 bytes, 'flushed' uploads 0x 0 bytes, guest memory compared;
          all traffic: upload 'cpu' 7x 1835008 bytes; upload 'first' 2x 524288 bytes;
                       write-back 'storage alias round trip test' 1x 262144 bytes; write-back 'storage refresh' 7x 1835008 bytes;
```

The 2 'first' uploads create X and Y. The one 'storage alias round trip test' write-back is the test's final flush of X's last write.

So each aliased lookup costs one full surface each way (256 KiB down, 256 KiB up). That is the shape of Village's ~4.7 GB "storage refresh" and ~4.8 GB "flushed" per 10 s.

## Acceptance condition for BF-290's fix commit

With the fix on main, `ctest -R '^agc_storage_alias_round_trip$'` must pass. That means every content check above passes, in both passes, both modes and all three pairs (plus Village's pair once named). In addition:

1. **Copied guest memory** (the case Village hits), each pair's summary line reads
   `'storage refresh' write-backs 0x 0 bytes, 'flushed' uploads 0x 0 bytes`
   instead of `7x 1835008` each, or at most the fraction BF-290's design names, stated against that 7 x 262144 B baseline. No other reason may take their place in "all traffic": only `upload 'first' 2x`, plus the test's own final write-back of X's last results, which must still happen and land in memory.
2. **Imported guest memory**: likewise 'storage refresh' 0. With nothing written back, nothing changes the compared memory, so the 7 'cpu' re-uploads go too.
3. **The step lines** of every lookup read `no storage traffic`, or carry only the device-side handoff if BF-290 counts it under a new reason. That new reason is then the one to report, and it moves no bytes through host memory.

To make it binding, the fix commit can turn (1)–(2) into assertions on `StorageTexture::CumulativeTraffic()` deltas, which the test already computes per step and per pair.

The red stays C1's: skipping the write-back with no handoff fails at `X does not hold Y's results after its lookup`.
