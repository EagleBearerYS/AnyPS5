## 0. Bottom line

- **The one public fact about the choice.** KytyPS5 answers `sceVideoOutGetOutputStatus` with resolution class **2 (4K) on the main output unless the title's param.json grants resolution detection**.
  - That's `attribute3` bit 0x4, which KytyPS5's comment calls "param.json Video-out Info".
  - With the grant, the class is 1 below 3840x2160.
  - KytyPS5 commit 61761b65 (2026-09-21, "Honor PS5 title output-resolution detection permission") changed it from the rule AnyPS5 has today: "1 until the title's own buffers are 4K".
- **What that means for titles,** as KytyPS5 models the console: a PS5 title without the grant is always told "4K". It has no reason to look further, so it renders 4K display buffers and the console scales them to the real output. Only a title with the grant can be told "HD" and pick 1080p.
- **What AnyPS5 answers today:** class 1 (HD) at boot to every title.
  - The VideoOut config starts at 1920x1080 (VideoOutDriver.hpp:48-49, 129-130).
  - It becomes class 2 the moment the title registers or presents a 3840x2160 buffer (Buffer.cpp:118-119, VideoOutDriver.cpp:615-616). It echoes the title's own choice.
  - So AnyPS5 already tells Village "not 4K" before registration, and Village still registers 3840x2160. That fits a title without the grant: it never asks, or ignores the answer.
  - PM-015's `ANYPS5_OUTPUT_RESOLUTION` changes the same two answers, which explains why it can't move Village.
- **Nothing else AnyPS5 answers points to 4K:**
  - Pro ("Trinity") mode is 0/false (Process.cpp:615-617, Platform.cpp:11-15).
  - The safe area is 1.0.
  - No SystemService parameter about resolution is known.
  - AnyPS5 doesn't export `sceVideoOutGetDeviceCapabilityInfo`, and nor does KytyPS5's PS5 export table.
- **The deciding question is Village's param.json `attribute3` bit 0x4,** plus whether it calls `GetOutputStatus` before `RegisterBuffers2`.
  - The patch on `test/trace-display-queries` prints both in one boot with `APS5_TRACE_DISPLAY_QUERIES=1`: one `[display-query]` line per distinct call and result, nothing per frame (§3).
- **For FSR:**
  - **If Village lacks the grant,** no VideoOut answer will shrink its buffers, and FSR (an upscaler) never engages for it. The levers left are the title's own modes, or a render-scale feature, which is a much larger, non-generic change.
  - **If it has the grant,** the fix is to make every query it reads follow the option (§4).

## 2. What a title uses to choose its display-buffer size

Public, SDK-independent facts, all from KytyPS5's source:
- **The query is `sceVideoOutGetOutputStatus`.** It is the PS5 table's only output-resolution query; `sceVideoOutGetResolutionStatus` and `GetDeviceCapabilityInfo` are absent there (src/libs/libVideoOut.cpp).
  - Resolution class 1 means below 3840x2160; 2 means 4K.
  - The main output reports 2 unless param.json `attribute3` & 0x4 grants detection (src/graphics/presentation/videoOut.cpp:1790-1798, commit 61761b65).
  - The comment reads: "Primary output reports 4K unless param.json Video-out Info enables resolution detection".
- **WQHD (1440p) reporting** needs `sceVideoOutAllowOutputResolutionWqhdDetection` on that handle. The value reported for WQHD isn't public; both emulators make the call a no-op.
- **HDR** is reported (`dynamicRange` 2) only when param.json `attribute` & 0x20000000 allows it and the host supports HDR (videoOut.cpp:1791-1799).

The PS4 parallel, from shadPS4's public source (GPL-2.0, github.com/shadps4-emu/shadPS4, read at ab1dd38):
- param.sfo `ATTRIBUTE` bit 23 is "Supports PS4 Pro (Neo) mode" and bit 29 (0x20000000) is "Supports HDR" (src/common/elf_info.h:40-56).
- `sceKernelIsNeoMode` is true only when the emulated console is a Pro **and** the title sets bit 23 (src/core/libraries/kernel/process.cpp:19-25).
- `sceVideoOutGetResolutionStatus` returns the configured output size (src/core/libraries/videoout/driver.cpp:43-47).

The system answers capability queries in the light of what the title declares in its param file. KytyPS5 applies the same pattern to PS5: `attribute3` 0x4 for resolution detection, and `attribute` 0x20000000 for HDR, the same bit position as PS4's.

So the typical PS5 title has two paths:
- **Without the grant,** it targets 4K display buffers. The system tells it 4K whatever the TV, and scales.
- **With the grant,** it reads the class (and WQHD after opting in), sizes its buffers accordingly, and can follow `sceVideoOutAddOutputModeEvent`.

**Which AnyPS5 answers say "4K" or default to it:**
- `GetOutputStatus` and `GetResolutionStatus` say 4K only after the title registers or presents a 4K buffer. They are a mirror of the title's choice, not an input to it. Before registration they say 1920x1080 / class 1, the opposite of the KytyPS5 model for a title without the grant.
- `ParamGetInt` answers 0 to every unknown ID. That is a "default" only if a title reads a display parameter AnyPS5 doesn't know; the trace lists every ID.
- Nothing else defaults to 4K: Trinity mode is off, the safe area is 1.0, and no capability query exists.
- Hollow Knight: Voidheart Edition presenting 1920x1080 (#5593) fits a title with the grant (a Unity player) following AnyPS5's class 1. The trace can confirm that too.

## 3. One-boot logging plan

**Existing switches don't cover it:**
- `APS5_TRACE_CALLS` (libc/src/specifics/windows/CallTrace.cpp; docs/user/USAGE.md:189) is Windows-only and needs an executable converted with `--trace-imports`.
- It records only a call's entry, not its arguments or result, and prints only inside crash and abort reports.
- No other `APS5_TRACE_*` touches VideoOut, SystemService or param.json.

**The patch:** fork `test/trace-display-queries` (b2cecfc2f, one commit on main a077a88df; files listed in §7).
- `APS5_TRACE_DISPLAY_QUERIES=1` prints `[display-query] <call> = <result>` to stderr, once per distinct line (at most 4,096). A query a title polls every frame prints once, and again only when its answer changes.
- Without the variable, nothing changes: each call site costs one function call and a cached `getenv`.
- **Lines** (each shows the arguments and every returned field):
  - `param.json <title id>: attribute …, attribute2 …, attribute3 0x…`, once, when the title metadata loads at window creation;
  - VideoOut: `sceVideoOutOpen`, `…AllowOutputResolutionWqhdDetection`, `…GetOutputStatus`, `…GetOutputStatusWithVrr`, `…GetResolutionStatus`, `…IsOutputSupported`, `…ConfigureOutput`, `…SetWindowModeMargins`, `…SetBufferAttribute2`, `…RegisterBuffers2`, `…SubmitChangeBufferAttribute2`, `…AddOutputModeEvent`;
  - SystemService: `…GetDisplaySafeAreaInfo`, `…GetHdrToneMapLuminance`, `…ParamGetInt` (with "(not implemented, answered 0)" for unknown IDs), `…GetStatus`;
  - kernel and Agc: `sceKernelIsTrinityMode`, `sceKernelGetOperationMode`, `sceKernelGetMainSocId`, `sceAgcGetIsTrinityMode`.
- **Verified here.** Ten VideoOut and SystemService ctest entries (guest_system_service*, guest_video_out_*, video_out_output_mode_policy, video_out_flip_controls, video_out_flip_labels_main) were run under Xvfb on lavapipe with `APS5_TRACE_DISPLAY_QUERIES=1`. All 10 pass. Excerpt (test titles, not a game):

**The boot (PC side):**
1. Build the branch, or merge it with `feat/videoout-output-resolution`. The only conflict is `docs/user/USAGE.md`, which PM-015's branch already has with current main: take main's text and add PM-015's lines (§5).
2. Run Village to the title screen with `APS5_TRACE_DISPLAY_QUERIES=1`, then send back the `[display-query]` lines (a few dozen).

**How to read the result:**
- `attribute3` without 0x4, and no `GetOutputStatus` before `RegisterBuffers2` → Village always picks 4K. No VideoOut answer changes that (§4, case A).
- `attribute3` with 0x4, `GetOutputStatus` answering 1 before registration, and still 3840x2160 registered → something else decides. The other lines (ParamGetInt IDs, Trinity, safe area, an unimplemented ID) name the candidate.
- `GetOutputStatus` answering 2 before registration → the title registered once, then asked. Look at the order of the lines.

## 4. Fix proposal

**Case A, Village lacks the grant (what the public model predicts):**
- No answer can make it render less. Its display buffers are 4K on hardware too.
- FSR on the fork upscales only when the window is larger than the buffer, so it can't help this title.
- Paths that would: the title's own modes, if it has one that lowers its internal resolution; or a general "render scale" in the AGC driver (shrink render targets and the display buffer). That is a large, risky change, not proposed here.

**Case B, Village has the grant:**
- Make every query it reads follow the option, from the first call.
- PM-015 already does `GetOutputStatus(+WithVrr)` and `GetResolutionStatus`. Add whatever the trace shows next.

**Either way, model the permission as KytyPS5 does,** in `outputStatus` (Output.cpp:20-28):

| title | `resolution` | `GetResolutionStatus` |
|---|---|---|
| without `attribute3` & 0x4 | 2 (4K), whatever the window or option | 3840x2160 for those titles |
| with the grant | from `ANYPS5_OUTPUT_RESOLUTION` (else the window or host display): 1 below 3840x2160, 2 at 4K | the option's size, as PM-015 does |

- Read `attribute` and report `dynamicRange` 2 only with 0x20000000 and a host HDR display.
- Raise `VIDEO_OUT_EVENT_SET_MODE` if the reported class changes at run time (a window move to another display, a resize, the option).
- Keep WQHD reporting out until the value for WQHD is public. With the WQHD opt-in, 2560x1440 still reports 1.

**Risks:**
- **Titles that assume 4K output** (no grant): reporting 2 to them is what hardware does. A title that today picks 1080p only because AnyPS5 says 1 would move to 4K buffers and get slower. Only a trace of such titles (Hollow Knight, Animal Well) shows whether any exist.
- **Titles with the grant but 4K-only assets:** UI scaled for 4K, or IME coordinates (`OptionUseOver2K`). Following a 1080p answer is what hardware does for a 1080p TV, so the risk is the title's own handling, as on hardware.
- **HDR:** gating `dynamicRange` on the param bit can switch a title's output path between SDR and HDR. Titles that today see HDR because the host has it but whose param.json doesn't allow it would see SDR, as on hardware.
- **VRR:** `GetOutputStatusWithVrr` returns zeros after the first 40 bytes, so a title reading VRR state sees "off". Unchanged by the proposal.
- **120 Hz:** already gated on `attribute3` & 0x40. The reported `refreshRate` follows the configured mode. Unchanged.
