## 1. What the port does (unchanged from #1896)

**At the top of the draw:**
- With the switch on, an indirect draw no longer drains the queue-0 pipeline (`Execution/src/Driver/Draw/Draw.cpp`, start of `Driver::draw`).
- With it off, the drain is exactly main's.

**After capture:** if the draw's captured regions overlap a pending pipeline write, the pipeline drains (reason `capture`) and the draw is translated again, the same `return draw(...)` retry main uses for queued labels.

**CPU-side indirect draws** (`indirectCpu` set, no deferred labels, not a rect list) take a new branch:
1. Drain only if the argument records or the count word overlap a pending pipeline write. That is the `IndirectArgsDrain` event, under drain reason `indirect`.
2. Read the records on the packet thread.
3. Expand every record: patch the user words, re-materialize the patched stages, and keep a per-record copy of the stage list, the snapshots and the patched results.
4. Enqueue all of the packet's records as one pipeline commit, covering the union of their draw write ranges. That is the `IndirectCommit` event.
5. If a record is rejected, the records before it are enqueued first, then the draw returns `Rejected`, as the drained path would leave it.

**Other indirect draws:**
- A CPU-side draw that is a rect list, or has deferred labels, drains and takes main's drained path.
- GPU-side indirect draws are enqueued like any pipelined draw, which also notes an `IndirectCommit`.

**Pipeline additions** (`DrawPipeline.hpp/.cpp`):
- `PipelineIndirect()` and `DrainIfOverlaps(ranges[, bounds])`, which tests the pending items' write ranges under the pipeline lock, after a bounding-range pretest.
- `DrainBeforeRead()`, the `queryPendingWrite` drain moved out of `WriteEvidence.cpp` with the same semantics.
- The `Event` counters, the depth default and the extended `[draw] pipelined` profile line.

**Test:** #1896's `tests/execution/DrawPipelineCommits.cpp` is applied unchanged.
- Its three cases: indirect arguments over a pending draw; a label between a dispatch and draws, which checks `PendingLabel` and FIFO order; and a hook read over a pending dispatch.
- The `tests/execution/*.cpp` glob registers it as `agc_driver_draw_pipeline_commits`.

## 2. Adaptations to main (where main differs from #1896's base 569252baf)

`git cherry-pick -n ae7542cde8` applied to all five files with no textual conflict. These are the changes on top of it, all in the new CPU-side branch of `Draw.cpp`:

1. **`compileDrawStage` is `materializeDrawStage` on main**, with the same parameters. Main's `ShaderMemory` is a `std::unique_ptr`, so the call passes `*shaderMemory`. Without this change the branch does not compile.
2. **Tessellation follows main's drained path.**
   - Since #1896's base, main re-materializes the tessellation control and evaluation stages for every record and passes them the record's own `direct` parameters (the other stages get the packet's).
   - The pipelined branch does the same: TCS and TES join `patched` on tessellation draws and are materialized with `direct`.
   - #1896's base had no such step, so a straight port would give a pipelined tessellated indirect draw stale per-record stages.
3. **The commit keeps `stageData` alive.**
   - Main added stage-data hits: a stage's program can be `stageData[i].compiled`, owned only there.
   - Main's own pipelined (non-indirect) commit captures `stageData`. The indirect commit now does too, alongside everything #1896 captured.
4. **Everything else is #1896's code as written:**
   - main's `Outstanding()` stays;
   - `run()`'s failure and shutdown handling is untouched;
   - the rect-list exclusion and the deferred-label precondition are kept;
   - the barycentric geometry stage, built once before the loop, is shared by the expanded records, as in main's drained path.

**Lifetime check for the deferred commits** (why per-record snapshots stay valid until the commit runs):
- The snapshots are spans into the draw's `memory`. After each record's re-materialization, `materializeDrawStage` resets that to `shaderMemory.Regions()` plus the matched regions of stages not recompiled.
- `ShaderMemory`'s pages are heap `Page` objects that stay put while it lives, and a re-read of a valid word leaves it alone (`Execution/include/ShaderMemory.hpp:101-120`).
- The commit owns `shaderMemory`, `matched`/`matchedRegions`, `programs`/`decode` (the initial code and header regions) and, per record, the patched results.
- So nothing a deferred record reads is freed or rewritten by a later record's expansion.

**Not changed, worth knowing:**
- Main already drains at variant validation for every pipelined draw (`Execution/src/Driver/Dispatch/VariantValidation.cpp:83-86`), which #1896's base lacked.
- #1896's capture-overlap retry therefore mostly duplicates that drain. What it adds is coverage of the decode reads.
- It costs one bounded scan per indirect draw, only with the switch on.

## 5. Which profile counters show indirect commits being pipelined

With `APS5_PROFILE_DRAW=1`, the queue-0 pipeline prints this line every 10 s (on an enqueue at least 10 s after the last report):

```
[draw] pipelined (10 s, depth 64): N commits at X us each on the committer (Y % busy), F failed; E enqueued behind Q on average, waiting W us per draw for room; indirect commits I, indirect drains (args overlap) A; drains: packet .. flush .. labels .. capture .. indirect K (.. ms) submission ..; packet drains by opcode: ..
```

- **`indirect commits I`** is the Bug Finder's "pipelined indirect commits". It counts one per pipelined indirect packet: one per CPU-side packet, whose records all go in one commit, and one per GPU-side indirect draw. A nonzero `I` in a profiled Village boot with `APS5_PIPELINE_INDIRECT=1` is the bar.
- **`indirect drains (args overlap) A`** counts the drains forced because a pending draw writes the arguments or the count.
- **`drains: indirect K`**:
  - With the switch off, it is one drain per indirect draw. Going by the Bug Finder's counts, that is about 1,600 per 10 s on Village's queue 0.
  - With it on, it should fall to `A` plus the fallbacks: rect lists and draws with deferred labels.
- **`depth 64`** confirms the switch is active.

Two existing lines put this in context:
- `[draw] ... indirect: gpu-side N (R rewritten), cpu-side M (<reasons>), argument reads X ms` (`Graphics/src/Draw.cpp:545-549`) shows how Village's indirect draws split between the GPU-side and CPU-side paths.
- `[packets] queue 0x0 ...` (`Execution/src/Driver/Packets/PacketTiming.cpp:46`) shows queue 0's time by packet. With the switch on, the indirect draw opcodes' time should drop from draining to enqueueing.
