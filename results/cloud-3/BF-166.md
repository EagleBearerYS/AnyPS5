**The bounds change itself:**

- **API:** `RedZoneFunction {Begin, End}`, and `FrameRedZoneFunctions` takes a `functions` list.
- **Function loop:** candidate functions are the given ranges instead of call targets and aligned code after int3.
- **Decoding:**
  - each function is decoded on its own, from its FDE start to its FDE end, stopping at int3;
  - a branch out of `[start, FDE end)` is "branch leaves the function";
  - the segment-wide scan is kept only for branch targets, with call targets no longer counted.
- **Conversion:**
  - it reads the ranges with the existing `UnusedNidFilter::ReadExceptionFunctions`;
  - it throws "Red-zone framing needs function bounds from the executable's .eh_frame, and it has none" when there are none;
  - there is no fallback.

**Beyond the bounds change**, I found two things:

- **Sites taken across functions:** sites added for one function now count as taken for the next (`taken.emplace_back` in `addSite`). This stops two adjacent functions' sites from overlapping.
- **Tests:** his two new tests, `framesAPointerOnlyFunctionByItsOwnBounds` (two adjacent leaves, one reached only through a pointer) and `leavesCodeWithoutAFunctionRange`.

Nothing in it is unrelated to the framer.

## Step 3: our commit (a376e37b8)

`fix(relinker): decode each red-zone leaf over its whole FDE range`. Four files, +50 −31.

**FDE bounds on every path.** Since his loop, every candidate start is an FDE start and every body is its FDE range. The frameless, depth-shift, `sub` and operand-stub paths all run on that body, so nothing else needed changing.

**#5640's body cut is dropped entirely.** That is the padding check, `jumpTarget`, and the breaks at aligned code after a `ret`/`ud2` or at a `jmp` target.

- **Fallback:** his commit keeps no fallback (code outside every FDE is not framed, and no FDE at all throws), so none is kept.
- **The int3 stop:** his, and kept.

**Dropping the cut fixes a real bug.** At 606fa2ef9 the cut ends a body at aligned code after a `ret`, but `functionEnd` is already the FDE end.

- A cold block after the `ret` inside the same FDE is reachable by a branch (not "leaving"), but it is never decoded.
- So its rsp operands are not moved and its exit is not stubbed.
- The new test `keepsColdBlocksAfterARetInsideTheFde` is red there and green here.

**The throw is as he wrote it:**

- **No FDE at all:** "Red-zone framing needs function bounds from the executable's .eh_frame, and it has none".
- **A malformed `.eh_frame`:** the error comes from `ReadExceptionFunctions`, whose messages begin "Strict filter:" because the strict NID filter shares that reader. They read oddly for framing (see Notes).
