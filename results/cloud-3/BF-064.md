# BF-064: Resident Evil Village's large private blocks and their allocation sites

Worker: cloud-3 (Linux, 4 cores, lavapipe from Mesa 25.2.8). Tree: fork `test/three-title-base3a-6178` at **32ac24cb3**, built with CI's flags. Line numbers are at 32ac24cb3 unless they name another commit. Synthetic harnesses and code only; no game data. No code was pushed.

**How I looked:**
- **Code reading:** every `VirtualAlloc`, `mmap` and span-sized container in `core/`.
- **An allocation census:** an `LD_PRELOAD` shim logged every `malloc`/`calloc`/`realloc`/`posix_memalign`/`aligned_alloc` and anonymous `mmap` of 1 MiB or more, with a backtrace resolved by `dladdr` and `addr2line`. I ran it across all 1,039 `agc`, `guest` and `video` ctest tests of 32ac24cb3: 529 processes and 16,563 large allocations.
- **A heap report:** a second shim interposes `AgcDriverShutdown_nid_postfix`. Before teardown it counts the present and all-zero pages of every anonymous read-write mapping outside the guest arena (through `/proc/self/pagemap`) and reads `mallinfo2`.

The shims are scratch tools on this VM (`/home/user/bf064/bigalloc.c`, `heapreport.c`), not repository code.

**What Linux cannot show.** The large blocks Village holds at the menu come from two places, neither of which a Linux harness reproduces:
- Windows-only paths: the write-watch tables and the `WindowsMappings` eviction copies;
- workload pools sized by the title's own buffers.

Those I pinned from the code, at the confidence each row says. The census confirms the cross-platform sites, and shows that our other large allocations are transient (SPIR-V validation, pipeline creation, shader specialization) and freed.

### How the 768 MiB candidate fits

- **The data pattern:** the block's first values ("from byte 28, 32-bit pairs 0x30/0x10, 0x50/0x30…", links of 32-byte nodes) look like a guest allocator's free list. `evict` copies guest bytes verbatim.
- **The data share:** 38% at the census's 4 KiB sampling fits a copy committed in 16 KiB pages that each hold some data.
- **Not a heap block:** `VirtualAlloc` directly.
- **The size:** 768 MiB would be one direct-memory run of that size.

### PC checks that would settle the open rows

- **768 MiB:** in WinDbg, `bp KERNELBASE!VirtualAlloc ".if (@rdx >= 0x10000000) {k; gc} .else {gc}"` while booting to the menu shows the stack of every reservation of 256 MiB or more. VMMap's "Private Data" view gives the block's base address to match.
- **Every heap class at once:**
  1. `gflags /i <exe> +ust`;
  2. run to the menu;
  3. `umdh -p:<pid> -f:menu.txt`.
  
  UMDH lists every live heap allocation with its stack, grouped by size. That pins the 31.9/15.9/8.4/4/2/1.5/1.4–3.3 MiB classes in one run. Turn `+ust` off afterwards; it costs memory and time.
- **24.6/25.2 MiB:** arm 4 of BF-062 (`test/three-title-base3a-6178-bf059-spirv`) with `APS5_PROFILE_DRAW=1` prints `[buffers] host-visible, live: … guest ranges X KiB in N …`. If guest ranges hold about 75 MiB in three buffers, these blocks are our uploads.

## 2. The process heap's zero pages (~1.8 GB of 6.3 GB)

**Likely answer: mostly never-written committed memory, not zeroed live objects.** The only large zeroed live objects I found are Windows-only (the write-watch tables).

**The measurement.** The same harness under three glibc policies: `agc_driver_shader_residency_tests --measure 200 50 10` (residency branch build, 200 synthetic programs of 588 words, 10% drawn), heap report taken just before shutdown.

| Policy | Run time | Present outside the arena | Zero pages among them | malloc arena (in use / free) | mmapped chunks |
|---|---|---|---|---|---|
| glibc default | 124 s | 549 MiB | 11.0 MiB (2%) | 602.5 MiB (408.8 / 193.7) | 250.3 MiB in 2 |
| fixed `mmap_threshold` = 512 KiB (Windows' large-block cutover) | 127 s | 476 MiB | 9.5 MiB (2%) | 526.6 MiB (411.9 / 114.7) | 251.5 MiB in 3 |
| one arena, no trimming (`arena_max=1`, `trim_threshold` huge) | 509 s | 437 MiB | 8.4 MiB (2%) | 452.4 MiB (405.7 / 46.7) | 250.0 MiB in 1 |

**What the table shows:**
- **Same code, few zero pages:** under every glibc policy, only 2% of the present memory is zero pages. So our cross-platform code does not hold large zeroed live objects in this harness.
- **Freed memory isn't zero:** freed memory keeps its old bytes, so it shows as data. Never-touched memory, like the 250 MiB `calloc`, is never present.
- **What the policy changes** is how much freed memory stays present: 194, 115 or 47 MiB.
- **Contention:** the single-arena run is 4× slower, from lock contention.

**Why a Windows heap shows zero pages that glibc does not.** A page that reads as zero in a committed Windows heap region is most often one committed but never written, because zero is what a fresh committed page holds:
- **Segment commit ahead of use:** the NT heap commits segment space ahead of allocation.
- **Large heap blocks:** above roughly 508 KiB on x64 the heap serves a block from `VirtualAlloc`, committing all of it at allocation; whatever the owner has not written yet reads as zero.
- **Reading doesn't help:** the census reading those pages makes them present but leaves them zero.

**Zeroed live objects do exist, on Windows only:** the three write-watch tables (~172 MiB of zero, section 1) and `WriteWatchCoverage::excluded` (15.6 MiB).

**A PC check that splits the 1.8 GB** (cheap; the census tool can add it): walk the process heap with `HeapWalk`, and for every entry sample its 4 KiB pages for all-zero:
- zero pages inside `PROCESS_HEAP_ENTRY_BUSY` entries are zeroed or not-yet-written live objects;
- zero pages inside free entries are committed free space;
- `PROCESS_HEAP_UNCOMMITTED_RANGE` entries are not committed and don't count.

## 3. A Windows experiment for the PC

Run each variant from a cold start to the menu, then read private bytes, the heap's committed and free bytes (from `HeapWalk`), and the frame time over 60 s.

**A. `HeapSetInformation(GetProcessHeap(), HeapOptimizeResources, &info, sizeof(info))`**, with `HEAP_OPTIMIZE_RESOURCES_INFORMATION{HEAP_OPTIMIZE_RESOURCES_CURRENT_VERSION, 0}`.
- **What it does:** it is a one-shot pass that decommits free heap memory and trims the heap's caches (Windows 8.1 and later).
- **When to call it:** once at the menu (for example after the first presented frame) and then every 60 s, behind an environment switch. Calling it at start only would trim an empty heap.
- **What it changes:** committed free blocks in segments are decommitted. That reduces private commit by about the free share of the heap. It cannot reduce committed-but-never-written space inside live large blocks, nor live data.
- **What it costs:** a pass over the heap per call, and demand-zero faults when the freed space is reused. Watch the frame time around each call.

**B. The segment heap**, through the application manifest:
- **How:** `<heapType xmlns="http://schemas.microsoft.com/SMI/2020/WindowsSettings">SegmentHeap</heapType>`.
- **What it changes:** the UCRT's `malloc` and `new` use the process heap, so this changes every heap allocation. The segment heap decommits free pages more readily and fragments less, so expect lower private bytes for the same live set.
- **What it costs:**
  - CPU in allocation-heavy paths: the segment heap is often slower than the NT heap's low-fragmentation front end for small blocks, and the shader recompiler and SPIR-V tools allocate heavily;
  - it is a process-wide change, so measure shader preparation time and frame time as well as memory;
  - it needs Windows 10 2004 or later.

**C. A control:** the same build with neither change, measured the same way.

## 4. Proposed order of cuts

1. **The Windows write-watch tables:** about 172 MiB for a known amount of work. Reuse the Linux two-level leaf code at `GuestMemory.cpp:773-779` and allocate a leaf on its first stamp.
2. **The page-state table** (BF-063): about 220 MiB of commit, via commit on touch.
3. **The eviction copies,** once the PC confirms the 768 MiB block is one: up to about 476 MiB, by copying non-zero 4 KiB subpages only.
4. **UMDH at the menu** to pin the remaining heap classes before cutting them.
