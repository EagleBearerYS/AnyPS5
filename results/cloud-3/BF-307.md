## 1. The read (main `f7f03daf52`, `core/libs/prx/libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp`)

**Where the CPU waits:**
- `copyRegion` (`:5676`) opens `ReadSiteScope(ReadSite::BufferUpload)` (`:5704`) and reads the region with `GuestMemory::Read` (`:5710`).
- That read goes through the flush hook (`Recorder.cpp:1036`–`:1044` on main). A pending write over the range is a pending-write sync, source 1: `SyncThrough`, which submits the open batch.
- Pending storage results or unit shadows are a recorded-store sync, source 2 (`:1059`–`:1090`).
- `copyRegion` runs from:
  - UploadPrepare's last loop (`:5415`), with no device lock (a build's stage A);
  - UploadFinish (`:5639`).

**a) Size.** A misaligned region inside an import takes the GPU copy only when `gpuCopyEligible` (`:5192`–`:5195`) holds. That needs `region.end - region.begin <= gpuCopyLimit()` (`:5024`–`:5030`, `APS5_GPU_COPY_MAX_KIB`, 1024 KiB).
- In UploadPrepare, `if (!gpuCopyEligible(region)) continue;` (`:5388`) leaves a larger region to the CPU copy at `:5415`. UploadFinish asks the same at `:5589`.
- Village's rows (average access 11,632 KiB) are above the bound. So if their regions lie inside one import, this is why they wait.

**Why the bound is there:** the code doesn't say. It predates main's visible history (the squashed early commits); the only text is the comment at `:5017`–`:5018`. From the two paths:
- **It isn't staging memory.** The GPU copy's buffer is the same host-visible buffer the CPU copy allocates (`copyBufferProperties(false)`, `:5390`, against `:5700`).
- **It's a cost choice.** A region that no GPU work covers is copied on the CPU without waiting. On the GPU path, `recordGpuCopies` would first snapshot it on the CPU anyway (`:5810`–`:5816`, no pending writer and not written) and then also pay a transfer.

**Is it safe to lift for a range behind a pending GPU write? Yes.** What the GPU path already records is enough:
- **Order.** The copy goes into the open batch after the producer, behind the leading barrier (`:5780`–`:5784`: ALL_COMMANDS|HOST writes → TRANSFER read).
- **Queued stores.** Queued DCC-key and label stores over the range are recorded first (`:5768`–`:5771`).
- **Storage results.** They are recorded ahead of the copy by `StorageTexture::FlushPending(… "copied buffer region")` (`:5621`). Its default `PublishScope::Whole` also publishes unit shadows.
- **Writes that land on the CPU.** These are a copied buffer's completion write-back and completion labels. UploadFinish syncs through them at its start (`CompletePendingCpuWrites`, `:5442`; `ShaderResources.cpp:3514`–`:3532`, `CountSync(4)`). Any pending write still noted when the copy is recorded therefore lands in the import on the GPU.
- **The bytes.** They are the producer's: the content check below proves it.

**b) Outside an import.** UploadFinish tries `importAccess(… ImportRequester::Build)` (`:5551`). With no import, the region takes `copyRegion` and still waits; this change does not reach it.
- **Does the GPU have the producer's bytes?** The pending writers whose bytes the CPU waits for here all store in place into imports: dispatch regions bound in place, `RecordCopyBacks`, GPU-direct storage stores, unit-shadow publishes, and CP/DMA writes. Writers that store back on the CPU were already synced by `CompletePendingCpuWrites` (source 4, not a "buffer-upload" row). So the producer's bytes are in some import.
- **Why it is still "outside".** `findImport` needs one import covering `[begin, end)` (`:5362`, `:5548`). A large region crossing registered allocations has none. Village's rows fit that shape: an 11.6 MiB access over a 3.1 MiB noted range.
- **What it would take** is a copy per import the region spans. That is exactly `e10f59a483`'s `importSpans` / `copySpans`, which also copies back per piece (see the claim check), with a CPU copy kept only for any uncovered, unwritten part.
- **Which case Village hits** isn't something the `[hooksync]` rows can tell. The `[buffers] … completed CPU-copy operations … misaligned in imports … outside imports` line (`copyRegion`'s profile, `:5753`–`:5756`, `APS5_PROFILE_DRAW`) names it per run. On a profiled boot of the port, the "buffer-upload" pending-write syncs that remain are the outside-import case.

**c) The 0x28 recorded-store syncs.** Source 2 means the access found a storage image's results, or unit shadows, still unstored over the range. The hook recorded their store and then waited for it.
- The bytes are a storage image's results that the next dispatch binds through a V# as a buffer.
- On the GPU path, that store is recorded ahead of the copy in the same batch (`:5621`), so the same change answers them. `copyBehindGpuWork` counts `StorageTexture::AnyPendingOverlaps` and `AnyShadowedOverlaps` as GPU work, not only pending writes.
- They are not the storage-alias family (`fix/agc-storage-alias-device-handoff-v2`). That family is an image-to-image round trip; here the consumer is a buffer.
- The limit from 1b applies here too: inside one import only.

## 2. The change

In `GuestBufferMemory.cpp`:
- **New member `copyBehindGpuWork(region, locked)`.** It holds for a region that is GPU-copy material (GPU copies on, not sparse, host-backed or written) when the active recorder has any of these over it:
  - a pending write,
  - pending storage results (`StorageTexture::AnyPendingOverlaps`),
  - a unit shadow (`AnyShadowedOverlaps`).
- **Locking.** `locked` says whether the caller holds the GPU mutex:
  - UploadFinish asks the recorder itself (`PendingWriteOverlaps`).
  - UploadPrepare asks the published, lock-free pending-write snapshot (`Recorder::SnapshotWriteOverlaps`), the same one the flush hook trusts.
  - The two registry queries take their own locks.
- **The two call sites.** UploadPrepare's `!gpuCopyEligible(region)` gate becomes `!gpuCopyEligible(region) && !copyBehindGpuWork(region, false)`. UploadFinish's GPU-copy condition gains `|| copyBehindGpuWork(region, true)`. A region the snapshot flagged but the recorder no longer sees as pending takes the CPU copy in UploadFinish, which does not wait. The buffer made in UploadPrepare is kept, as before.

**Behaviour.** Above the bound, a misaligned in-import region behind GPU work is now copied by the GPU, bit-exact and without a CPU wait. Below the bound nothing changes. Regions behind no GPU work keep the CPU copy, which never waits for them.

**Where the CPU still really needs the bytes:**
- a region outside any one import (1b);
- `APS5_CPU_COPIES=1`, which disables every GPU copy;
- sparse regions;
- a build without an active recorder (tests).

There is no new switch. `APS5_CPU_COPIES=1` gives the A/B on Village.

## 3. The test (red/green)

`agc_buffer_upload_pending_gpu_copy` (`agc_driver_recorder_tests --pending-upload-gpu-copy-only`, `pendingUploadGpuCopyTests` in `tests/Recorder.cpp`); the full recorder run includes it too.
- **Setup.** A 4 MiB write-watched block is registered and host-imported.
- **Producer.** A `vkCmdCopyBuffer` writes a 1 MiB pattern into the import at +1 MiB, in the open batch, and the range is noted as a pending write.
- **Build.** The build uploads a 3 MiB readable region at +4100. That offset is DWORD-aligned but off `minStorageBufferOffsetAlignment`, so it is misaligned in the import and three times the old bound. The upload runs under the GPU mutex.
- **Wait check.** The upload makes 0 flush-hook waits (`Recorder::ThreadHookWaits`) and 0 submissions, and the producer is still pending in the open batch.
- **Content check.** A GPU copy of the descriptor's bound range is read back. It must equal the producer's pattern over the produced megabyte and the original bytes elsewhere. Guest memory must hold the pattern after the sync.
- **Scope.** The check is at the build's upload stage: the readback is a transfer read of exactly the buffer range the dispatch would bind. It is not a recompiled dispatch.

**Red** (main `f7f03daf52` plus the test only):
```
AGC graphics: the upload of a misaligned 3 MiB region over a pending GPU write waited for it on the CPU (1 flush-hook waits, 1 submissions)
```

**Green** (the commit): `uploads behind a pending GPU write tests passed`.

**Teeth.** The mutation makes `recordGpuCopies` copy from a CPU snapshot even behind a pending writer: `if (!pendingWriter && !writable)` → `if (!writable)` (`:5810`). The copy then takes the bytes as they were before the producer ran. It fails the content check at the first produced byte:
```
AGC graphics: the region uploaded behind the pending GPU write misses the producer's bytes at byte 1044476 of the view
```
(1044476 = 1 MiB − 4100.)

**A mutation llvmpipe can't catch.** Dropping the leading barrier (`:5781`–`:5784` not recorded) passes 3 of 3 runs, because llvmpipe executes a batch's transfers in order. I don't count it as teeth on this VM; the snapshot mutation is the one that fails.
