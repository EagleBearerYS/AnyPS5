# BF-054: what holds the emulator's own memory after shader registration, and whether it can drop SPIR-V

Worker: cloud-3 (Linux, 4 cores, 15.7 GiB, lavapipe from Mesa 25.2.8). Everything below is on **upstream main 5f61879a9**, the fork branch `exp/shader-memory-residency`'s base, and uses synthetic shaders only.

## 1. Holders, lifetimes and load times (read on main)

### What the SPIR-V words are, physically

`SharedSpirv` either owns a `std::vector<std::uint32_t>` (heap) or views memory that an `owner` keeps alive.
- **A disk-cache hit is a view into the memory-mapped artifact file** (`MapFile`, ShaderDiskCache.cpp 195–235): Linux `mmap(PROT_READ, MAP_PRIVATE)`, Windows `MapViewOfFile(FILE_MAP_READ)` of a `PAGE_READONLY` section.
- The `MappedFile` lives as long as any holder above keeps the variant, so **every loaded artifact stays mapped for the whole run**.
- A fresh compile is written to the cache and replaced by a mapped view (`Persist`) when it can be.
- Specialized modules and some results are heap copies.

**Consequence for the PC's numbers:** a read-only file view on Windows is not charged as private bytes (commit); it shows as mapped file.
- The PC run read 8.32 GiB of artifacts and has "8.6 GB more mapped outside the guest spans". **Those are very likely the same bytes.**
- So **the SPIR-V the disk cache serves is kept for the whole run, but as mapped file pages, not in the 19.7 GB of private memory.** Its pages are clean and file-backed, so Windows can drop them under pressure without paging.
- The private 19.7 GB has to be held by something else. Step 2 measures what, on lavapipe.

### When an artifact is read

- **Default (asynchronous registration preparation):** `Register` runs `PlanRegistered` (decode and request), then `PrepareRegisteredInBackground` → `PrepareRegistered` → `PrepareShader`.
  - `PrepareShader` runs `getSource` (the plan from the disk cache) and `findOrCompileVariant` (a disk-cache `Load`, which gives a mapped view).
  - That's 2 variants for a pixel shader (with and without push constants), and 2 for a compute shader (with partial threads).
  - **Each registered pixel shader also prebuilds a graphics pipeline library** (`PrebuildStageLibrary`), unless `APS5_NO_LIBRARY_PREBUILD=1`.
- **`APS5_LAZY_SHADER_PREPARE=1`:** `Register` only plans: it decodes, throws the plan away and marks the shader deferred. No artifact is read at registration; the first draw or dispatch prepares it.
- **But `Driver::ResolveShaderAbi`** (ShaderRegistry.cpp 1277) plans and **prepares** every shader whose ABI is resolved, whatever `APS5_LAZY_SHADER_PREPARE` says.
  - A title that resolves the ABI of all its shaders therefore reads all its artifacts with lazy preparation on.
  - That would explain why the PC's lazy run still read all 12,252. A counter of `ResolveShaderAbi` calls on the PC would confirm it.

## 2. Synthetic registration-heavy measurement

### Setup

- **Binary:** upstream main 5f61879a9 plus counters only (SPIR-V bytes per holder kind and the recompiler's source map). The counters are part of the branch's first commit.
- **Harness:** `tests/execution/ShaderResidency.cpp --measure N blocks percent` on the branch.
  - It registers N distinct pixel programs: a `v_mov` with a unique literal, 16 texture samples, and `blocks` blocks of 8 multiplies.
  - Registration goes through `AgcDriverRegisterShader`. Preparation is settled through `Begin`/`EndShaderPreparation`.
  - Then `percent` % of the programs draw, one DCB each.
- **Module sizes:**
  - "50k": 0 blocks, 188 code words. Each variant's artifact holds about 48k SPIR-V words (188 KB mapped per variant; file 200,568 B).
  - "500k": 465 blocks, about 500k words.
- **Memory measures:**
  - `/proc/self/smaps_rollup`: Anonymous is the private heap side, which is what Windows counts as private bytes; Pss_File is the file-backed side.
  - The branch's counters: SPIR-V held, split heap / mapped.
- **Conditions:** warm disk cache (populated by an earlier run of the same binary), pipeline journal off, lavapipe, 10 % drawn. Single runs.
- **Modes:**
  - eager: the default.
  - no prebuild: `APS5_NO_LIBRARY_PREBUILD=1`.
  - lazy: `APS5_LAZY_SHADER_PREPARE=1`.
  - lazy + ABI: lazy, plus `AgcDriverResolveShaderAbi` per shader.
- **Process start:** 61–62 MiB anonymous, 64 MiB file-backed.

### Answer to the kill hint

**SPIR-V words are kept after pipeline creation, so the task goes on to step 3.** Two kinds of holder keep them:

1. **Every disk-cache artifact stays mapped for the run.**
   - Size: 1.84 GiB for 5,000 programs (two variants each).
   - Holder: `SourceEntry::variants` holds it, never cleared.
   - Not private: file-backed and clean. On Windows this is the "mapped" figure, not private bytes.
2. **Every specialized module stays on the heap for the run.**
   - Holders: `registrationModule`'s, `specializeModule`'s and `preparedBindingPlan`'s static maps, never cleared.
   - Registration builds one per pixel program for the library prebuild: 170 KiB each, 850 MiB for 5,000, private. Each drawn state adds another.
   - The `VkShaderModule`s themselves are destroyed after pipeline creation (step 1).

**The other big private holder is not SPIR-V.** The decoded resource plans and the variants' image-mode tables come to about 260 KiB per program here. Draws need them for the CPU-side resource walk, so they are not part of this cut.

**`ResolveShaderAbi` defeats lazy preparation.** Lazy + ABI matches eager on every counter, as step 1 predicted from the code.

The 1,000 × 500k cold populate compiled about 2.5 programs per 10 s, so registration alone took over an hour. Its rows follow in the next push.
