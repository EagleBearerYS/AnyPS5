# BF-054: what holds the emulator's own memory after shader registration, and whether it can drop SPIR-V

Worker: cloud-3 (Linux, 4 cores, 15.7 GiB, lavapipe from Mesa 25.2.8). Steps 1 and 2 are on **upstream main 5f61879a9** plus counters only. That commit is the base of the fork branch `exp/shader-memory-residency`, whose head **a3bf3fa29** carries steps 3 and 4 and the counters asked for in the Bug Finder's note (section 5). Everything uses synthetic shaders only.

## Summary

- **What holds the memory after registration.** Measured case: 5,000 programs with 50k-word modules, eager registration, lavapipe. Totals: **2,553 MiB private, 1,977 MiB file-backed.**
  - **Private bytes:**
    - about 260 KiB per program of recompile results that draws need (decoded resource plans, variant image-mode tables);
    - **170 KiB per program of heap SPIR-V** (the module built for the library prebuild, 850 MiB in all);
    - about 39 KiB per program of prebuilt driver libraries.
  - **File-backed:** every disk-cache artifact stays mapped for the run, 1.84 GiB.
  - **With `APS5_LAZY_SHADER_PREPARE`:** private bytes drop to 108 MiB, but `ResolveShaderAbi` undoes it (lazy + ABI ≈ eager).
- **SPIR-V is kept after pipeline creation, so the kill hint does not apply.** Both kinds are held for the whole run: mapped artifacts and heap-specialized modules.
- **The prototype** is behind `APS5_RELEASE_SPIRV=1` (default off), on fork `exp/shader-memory-residency`. Its head is **a3bf3fa29**, which also adds the host-visible buffer counter by purpose (section 5).
  - **What it does:** drops both kinds once a pipeline, specialization or registration has been built from them, keeps the disk-cache key, and reloads on demand.
  - **5,000 × 50k, eager:** private 2,553 → **1,748 MiB** (−805 MiB, −32 %); file-backed 1,977 → **62 MiB**; after drawing 10 %, 2,817 → 1,945 MiB.
  - **200 × 500k:** mapped 761 MiB → 0.
- **The cost is reloads.**
  - A shared module (here the common vertex shader) is reloaded for every new pipeline: 2 reloads per draw, 14.7 ms on average. A 64 MiB budget (`APS5_RELEASE_SPIRV_BUDGET_MIB`) removes that.
  - A reload re-runs specialization: **118 ms for a 44.5k-word module, 1.7 s for a 500k-word one, on the draw path.**
  - Kept keys cost 4.5 KB (50k) and 19 KB (500k) per artifact.
  - Persisting specialized modules in the disk cache, so a reload maps a file, is the next step.
- **Tests:** `ctest -R '^(agc|shader)'` passes 652/652 with the switch off and 652/652 with it on. A new test reloads a released program and draws the same 65,536 bytes.
- **Counters:** the `[spirv]` and `[buffers]` lines under `APS5_PROFILE_DRAW` (steps 4 and 5).
- **Heap per shader** (section 5): decoded resource plan 231 KiB, heap SPIR-V copies 200 KiB (each under 0.5 MB), variant metadata 57 KiB, `RecompileResult`s 31 KiB, sources 16 KiB, registry 11 KiB.

### What the SPIR-V words are, physically

`SharedSpirv` either owns a `std::vector<std::uint32_t>` (heap) or views memory that an `owner` keeps alive.
- **A disk-cache hit is a view into the memory-mapped artifact file** (`MapFile`, ShaderDiskCache.cpp 195–235): Linux `mmap(PROT_READ, MAP_PRIVATE)`, Windows `MapViewOfFile(FILE_MAP_READ)` of a `PAGE_READONLY` section.
- The `MappedFile` lives as long as any holder above keeps the variant, so **every loaded artifact stays mapped for the whole run**.
- A fresh compile is written to the cache and replaced by a mapped view (`Persist`) when it can be.
- Specialized modules and some results are heap copies.

**Consequence for the PC's numbers:** a read-only file view on Windows is not charged as private bytes (commit); it shows as mapped file.
- The PC run read 8.32 GiB of artifacts and has "8.6 GB more mapped outside the guest spans". **Those are very likely the same bytes.**
- So **the SPIR-V the disk cache serves is kept for the whole run, but as mapped file pages, not in the 19.7 GB of private memory.** Its pages are clean and file-backed, so Windows can drop them under pressure without paging.
- The private 19.7 GB has to be held by something else. Step 2 measures what, on lavapipe.

### When an artifact is read

- **Default (asynchronous registration preparation):** `Register` runs `PlanRegistered` (decode and request), then `PrepareRegisteredInBackground` → `PrepareRegistered` → `PrepareShader`.
  - `PrepareShader` runs `getSource` (the plan from the disk cache) and `findOrCompileVariant` (a disk-cache `Load`, which gives a mapped view).
  - That's 2 variants for a pixel shader (with and without push constants), and 2 for a compute shader (with partial threads).
  - **Each registered pixel shader also prebuilds a graphics pipeline library** (`PrebuildStageLibrary`), unless `APS5_NO_LIBRARY_PREBUILD=1`.
- **`APS5_LAZY_SHADER_PREPARE=1`:** `Register` only plans: it decodes, throws the plan away and marks the shader deferred. No artifact is read at registration; the first draw or dispatch prepares it.
- **But `Driver::ResolveShaderAbi`** (ShaderRegistry.cpp 1277) plans and **prepares** every shader whose ABI is resolved, whatever `APS5_LAZY_SHADER_PREPARE` says.
  - A title that resolves the ABI of all its shaders therefore reads all its artifacts with lazy preparation on.
  - That would explain why the PC's lazy run still read all 12,252. A counter of `ResolveShaderAbi` calls on the PC would confirm it.

### Answer to the kill hint

**SPIR-V words are kept after pipeline creation, so the task goes on to step 3.** Two kinds of holder keep them:

1. **Every disk-cache artifact stays mapped for the run.**
   - Size: 1.84 GiB for 5,000 programs (two variants each).
   - Holder: `SourceEntry::variants` holds it, never cleared.
   - Not private: file-backed and clean. On Windows this is the "mapped" figure, not private bytes.
2. **Every specialized module stays on the heap for the run.**
   - Holders: `registrationModule`'s, `specializeModule`'s and `preparedBindingPlan`'s static maps, never cleared.
   - Registration builds one per pixel program for the library prebuild: 170 KiB each, 850 MiB for 5,000, private. Each drawn state adds another.
   - The `VkShaderModule`s themselves are destroyed after pipeline creation (step 1).

**The other big private holder is not SPIR-V.** The decoded resource plans and the variants' image-mode tables come to about 260 KiB per program here. Draws need them for the CPU-side resource walk, so they are not part of this cut.

**`ResolveShaderAbi` defeats lazy preparation.** Lazy + ABI matches eager on every counter, as step 1 predicted from the code.

### A limit of these synthetic programs

The programs differ only in a `v_mov` to a register nothing reads, so after `spirv-opt` their specialized modules are word for word the same. Two consequences:

- **The pipeline-side memory above is a lower bound.** Draws and library prebuilds find each other's pipelines by content identity, so lavapipe builds one pipeline where a title with distinct shaders builds one per program.
- **The SPIR-V and recompiler holders are per program regardless.** Each program keeps its own 170 KiB copy of an identical module: nothing deduplicates SPIR-V by content.

## 3. Prototype: drop the SPIR-V once something is built from it, reload on demand

**Branch:** fork `exp/shader-memory-residency`. The step 3 measurements ran at 346640421; the head is now **a3bf3fa29**, which adds section 5's buffer counter. Commits on upstream main 5f61879a9:
- 6d77adfe9 `feat(shader): release SPIR-V once pipelines are built, behind APS5_RELEASE_SPIRV`
- 9b7a920a2 `feat(agc): report SPIR-V residency under APS5_PROFILE_DRAW`
- 346640421 `fix(agc): release SPIR-V on pipeline-cache hits and keep recent modules under a budget`
- a3bf3fa29 `feat(agc): count live host-visible buffer bytes by purpose`

### The rule

**Switch:** `APS5_RELEASE_SPIRV=1`, off by default. It is neutral for the disk cache key, so the switch-off and switch-on runs share cache entries.

**Two holders become releasable.**
1. **Disk-cache artifacts.** Every artifact loaded from or persisted to the shader disk cache drops its mapped view.
   - It keeps its disk-cache key. The key embeds the guest code: 4.5 KB per variant for the 50k programs, 19 KB for the 500k ones.
   - It reloads with the new `ShaderDiskCache::Reload`, which is counted apart from hits, so `[shader-disk-cache]` hit counts keep their meaning.
2. **Specialized modules** (registration and draw modules). Each frees its heap words.
   - It keeps the artifact, vertex classes, constants and target it was specialized from.
   - It reloads by specializing again.

**Release points.** The words go once something has been built from them:
- a graphics pipeline or library: when built, and also when a draw finds its pipeline in the cache;
- a compute pipeline: when built, or found;
- a specialization: releases the artifact it read;
- registration preparation: releases the artifacts it loaded;
- the pipeline journal's writer: after it encodes a module.

**Budget.** Pipeline-side releases go through a retirement list. `APS5_RELEASE_SPIRV_BUDGET_MIB=n` keeps the most recently retired n MiB resident and releases the oldest first. When it is unset, words are released at once.

**Safety.**
- Readers on the pipeline path hold a lease (`SharedSpirv::Hold`).
- Any other read pins the module for the run and is counted. It stayed 0 in every run here.
- A reload checks the word count, the header and the content hash taken when the module became releasable, and throws if any differs.

**Kept without the words:** size, header words, content hash (the pipeline identity), reload source.

**Not touched:** resource plans, variant `ShaderInfo` and bindings. Draws need them.

### Reload counts and times

The counters add a module reload's own nested artifact reload into both reloads, so each pair below is quoted as one cost.

| case | reloads | time |
|---|---|---|
| 5,000 eager, switch on, drawing 500 programs | 1,000: 2 per draw | 14.7 s in all |
| the same with a 64 MiB budget | 2 | 31 ms |
| a 44.5k-word pixel module and its artifact, reloaded for a new pipeline (redraw, 64 MiB budget) | 2 | 118 ms |
| 200 × 500k eager, switch on, drawing 20 | 40: the vertex shader's pair, 2 per draw | 554 ms |
| the same with a 64 MiB budget | 0 | |
| **a 500k-word module and its artifact, reloaded for a new pipeline** (redraw, no budget) | 2 | **1.72 s**: the redraw took 1.9 s with the switch on, 0.0 s with it off |

**Why 2 reloads per draw without a budget.** Every draw shares one vertex shader.
- Each draw's pipeline lookup released that vertex shader's module.
- The next draw's validation (a memo miss, since its pixel program is new) reloaded it, re-specializing from its reloaded artifact.

That is the churn the budget exists for: with 64 MiB, the draws needed 2 reloads instead of 1,000.

**Effect on draw time** (500 draws, 5,000 eager): 64.8 s off, 76.0 s on, 59.0 s on with the budget. Re-specialization runs SPIRV-Tools twice, so a module reload costs about as much as the first specialization did.

### Correctness

- **Test suite.** `ctest -R '^(agc|shader)'` on the prototype build at 346640421 (lavapipe, `GALLIUM_OVERRIDE_CPU_CAPS=avx`):
  - 652/652 pass with the switch off;
  - 652/652 pass with `APS5_RELEASE_SPIRV=1` exported to every test;
  - 47 skip in each, the same set.
- **New and extended tests:**
  - **`agc_spirv_residency`** (no GPU): a lease blocks a release; an unleased read pins; `Copy`, `Hold` and unleased reads reload; a reload with a different word or a missing word is refused; the counters return to their start.
  - **`agc_spirv_residency_off`**: nothing is released with the switch unset.
  - **`agc_driver_shader_residency`**: a draw whose new pipeline needs released modules reloads them (4 reloads, 127–141 ms over four runs) and **draws the same 65,536 bytes**. A registered and drawn program then leaves no SPIR-V resident and none pinned.
  - **`agc_driver_shader_residency_budget`**: under 64 MiB, a second program sharing the vertex shader draws without a reload, and everything resident is in the budget list.
  - **`agc_shader_disk_cache`**: a reload is counted as a reload, not a hit.
- **Repo checks:** `tools/check_conventions.py --base 5f61879a9` passes; `tools/check_test_registration.py` reports nothing new unregistered.

### What the prototype found along the way

1. **Draws can find their pipeline without building it.** The first version released only after a build, so a draw whose module had the same identity as a cached pipeline kept its module for the run. With the fix, a drawn program leaves nothing resident; a test checks it.
2. **Shared modules churn without a budget.** See the reload table. A title's common vertex shaders would be reloaded for every new pipeline that uses them.
3. **Module reloads are as expensive as specialization**, and they happen on the draw path. For big shaders that is a stall (1.7 s for one 500k-word module here, on a 4-core VM). Persisting specialized modules in the disk cache, so a reload maps a file instead of re-running SPIRV-Tools, would make reloads cheap. It is the obvious next step and is not done here.
4. **The pipeline journal.** With the journal on (the default; these runs had it off), each newly journaled module is reloaded once on the journal writer's thread to be encoded, then released. A module already in the journal costs nothing.
5. **Windows.** A mapped artifact view is not private commit. On the PC the private saving is the heap modules, and the mapped saving is the "8.6 GB mapped".

## 4. Counters for a profiled title run

On the prototype, under `APS5_PROFILE_DRAW`, every 10 s:

```
[spirv] X MiB held (heap H, mapped M) by N modules; releasable R, resident S, pinned P; released A, reloaded B (C in the last 10 s, D ms reloading in all); K kept under the B MiB budget (W MiB)
```

| asked for | field |
|---|---|
| SPIR-V bytes held | `held`, split heap / mapped. Mapped is file-backed. On Windows only heap is private bytes. |
| artifacts resident | `resident` (of `releasable`); `kept` is the part the budget holds on purpose |
| reloads per 10 s | `C in the last 10 s`; `D ms reloading in all` is the cost |
| health | `pinned` must stay 0. If it climbs, some reader bypasses the lease and that module is never released again. |

With the switch off the line still reports held bytes and modules (`releasable 0`), so the same line measures main's holders on a title.

**Suggested PC run:** the title's usual scene, three runs:
1. switch off;
2. `APS5_RELEASE_SPIRV=1`;
3. `APS5_RELEASE_SPIRV=1 APS5_RELEASE_SPIRV_BUDGET_MIB=256`.

Compare private bytes, mapped, the `[spirv]` reloads per 10 s, and frame times. Reload stalls would show as frame-time spikes on new pipelines.

| other | 10 | | |
| `GuestMemory`'s page-state table, one per process, mostly untouched pages | 250 | | |

**What this means for the PC's 6.2 GB of small heap objects.**
- **Per shader, the largest are the resource plan and the heap SPIR-V copies.** Each specialized module (one for the library prebuild, one per new draw state) is a separate heap object below 0.5 MB unless the shader is big.
- **Then the variant metadata and the `RecompileResult`s.** None of these is ever freed: the source map and the module maps are never cleared (step 1).
- **The part that grows in the menu** would be new draw states adding specialized modules and `RecompileResult`s.
- **The prototype's `[spirv]` line counts the heap SPIR-V share directly:** `held (heap …)`.
- **The other holders have no counters.** This table's per-object sizes are the way to scale them.

### Host-visible `Buffer` bytes by purpose

New on the branch (a3bf3fa29): every `Graphics::Buffer` names its purpose and, if it asked for host-visible memory, counts its capacity under that purpose while it lives.

**Buckets:**
- heap mirrors (`GuestBufferMemory`'s mirrors);
- BDA tables and fault buffers;
- guest ranges (guest buffer copies and snapshots);
- staging and readbacks (texture and target transfer, dumps, readbacks);
- uploads (vertex and index copies, mesh arguments, shader data and image-table buffers);
- other (the empty buffer, seeds, counters).

**Where it shows:**
- `LiveHostVisibleBuffers()` reads the counts.
- Under `APS5_PROFILE_DRAW`, every 10 s:

```
[buffers] host-visible, live: T MiB (other …, heap mirrors X MiB in N, BDA tables …, guest ranges …, staging …, uploads …)
```

The heap-mirror field is the live heap-mirror counter the note asked for.

**Limits:**
- Buffers the pool keeps idle are not counted; `BufferPool`'s own 0.56 GB on the PC is apart.
- A buffer that asked for device-local memory is not counted, even where the driver backs it with host-visible memory.

**On lavapipe the synthetic harness uses almost none of this.** At 1,000 × 50k after drawing 100: staging 64 KiB in 1 buffer, uploads 210 KiB in 212, other 6 KiB, no heap mirrors, BDA tables or guest ranges. **The split the note asks for has to come from the PC:** run Village's menu with `APS5_PROFILE_DRAW` on the branch, switch off.

**Test:** `agc_driver_pooled_buffer_range` now checks:
- a host-visible heap mirror is counted once under its purpose;
- a device-local buffer is not counted;
- a buffer without a purpose counts as other;
- destroyed buffers leave the counts as they were.

**Repo checks:** `ctest -R '^(agc|shader)'` at a3bf3fa29 passes 652/652 with the switch off and 652/652 with `APS5_RELEASE_SPIRV=1` exported. `check_conventions` passes.
