## Part 1: the fix

### What it does

In `importRunAt` (`Graphics/src/GuestBufferMemory.cpp`), a request that may evict now remembers its **final** budget refusal: the one taken when no smaller block is left to try. It stores the run (base, bytes, ranges), the range holding the requested address, and the state at the refusal (see the rule below).

A later evicting request computes its run as before. If the run, its ranges and the containing range match, and the memory is still current, the request is answered before the held-import loop and the walk. It still counts as refused and as remembered.

- **Not remembered:** joins, and refusals that step down to a smaller block.
- **Unchanged:** requests that may not evict keep #6457's memory and behaviour.
- **Housekeeping:** `refreshImports` drops stale entries, and a device change and `ClearHostImports` clear them.
- **Debt doc:** the debt entry ("Host import windows and budget") said "a request that may evict always tries again". It now describes the new memory.

### The memory rule, and why it is safe

**Refusal condition.** Without a held overlapping import, the budget check `live + bytes > budget + evictable` reduces to:

> refused ⇔ (bytes of non-evictable imports outside the run) + run bytes > budget

That's because `live` is every import outside the run, and `evictable` is the evictable part of them. So the refusal can only turn into a success if one of these happens:

- that non-evictable sum drops: an import is retired, or an import becomes evictable;
- the run or the budget changes;
- a step down to a smaller block becomes possible: the import window changes, or a request comes for a smaller range of the same block.

**Validity check.** The memory is current while all of these hold (`evictingRefusalCurrent`):

1. `epoch` and `liveBytes` are unchanged: no import retired or made.
   - A make can't free room. Expiring on it anyway errs toward retrying, as the task asked.
2. The budget is unchanged.
3. The import window is unchanged. The window decides whether a step down is possible.
4. The run's ranges are the same objects, and the requested address lies in the same range. Without the range check, a request for a smaller range of the same block could have stepped down and fit.
5. No import outside the run could have become evictable since the refusal. `evictable` needs `lastUse + 256 < useCounter`, and also `lastUse < buildFloor` (not held). `lastUse` only grows. The walk the refusal already made records, at no extra cost, the first use count at which each non-evictable import could pass the recency test, keeping held imports (`readyHeld`) apart from the others (`ready`). The memory is current while:

   `useCounter < ready && (buildFloor <= floor_at_refusal || useCounter < readyHeld)`

   - An unheld import can't age out before `ready`.
   - A held one stays held while the floor hasn't risen, and even after a rise it can't pass the recency test before `readyHeld`.
   - A floor that drops only re-holds imports.

Every condition is exact or errs toward retrying: no remembered refusal can hide a request that would succeed.

### How often the memory expires in a steady state (~72 address-based builds/s)

Each address-based build that hits the space restamps every import the space maps, and raises the floor. So a remembered refusal survives a build only while fewer than 257 uses have passed since the held imports' last stamp. It is walked again **at most once per build**, and less often when fewer than 257 uses pass between builds.

From part 2's run, walks per build with builds running were 0, 0.16, 0.50 and 1.00 at 1, 40, 120 and 250 uses between builds; that is about min(1, uses/257).

At ~72 builds/s that is at most 72 walks per second per refused run, instead of one per request. bf-settle's scene had 37,627 refusals per present. The memory also expires when an import is made or retired, the budget changes, or the run's ranges change.

## Part 2: the frozen import set

**Setup** (local experiment on the branch, mock device, never committed):

- 33 separate 64 KiB pieces registered, with a budget for 32;
- the address space cache on (`AddressSpaceCounters().enabled`);
- one address-based build (`AcquireRegistered`, `Upload(true)`) imports the 32 lowest pieces and refuses the 33rd.

**Rounds.** Each of 100 rounds is:

1. one address-based build: a space hit, which restamps every mapped import and raises the floor;
2. N regular uploads (`AddReadable` + `Upload(false)`), all on one import;
3. 10 evicting requests (`HostImportFor`) for the 33rd piece.

Then builds stop: one regular upload on that one import, then one evicting request, repeated until it is granted.

| regular uploads (uses) per build | while builds run (1,000 evicting requests) | walks per build with the fix | once builds stop: granted after |
|---|---|---|---|
| 1 | 0 granted (1,000 refused) | 0.00 | 256 uploads |
| 40 | 0 granted | 0.16 | 217 uploads |
| 120 | 0 granted | 0.50 | 137 uploads |
| 250 | 0 granted | 1.00 | 7 uploads |
| 300 | granted on the first round (1 space rebuild, then hits) | 0 | (already imported) |

All runs had 100 space hits and no rebuilds, except the 300 case (99 hits, 1 rebuild).

**Answer.** Confirmed. While address-based builds come more often than the 256-use protection, the new range is refused on every request:

- each space hit restamps every import the space maps to the build's floor;
- the build's `UploadFinish` then sets `buildFloor` to that floor;
- so those imports are always held or recent, and `evictable()` never passes.

Once the builds stop, a regular upload raises the floor above their stamps, and the request succeeds as soon as 257 uses pass without a restamp. The 300 row shows the same from the other side: with more uses than the protection between builds, eviction works even while builds run.

**Sketch: freeing room without letting a fresh space thrash.** Not built.

1. **Space stamps don't count as a use for eviction.** Split the stamp in two. `lastUse` would keep only real lookups (region lookups, CPU accesses) for recency. A per-build hold would mark the imports the current build has mapped, while its pointers are live (UploadPrepare to record): a hold serial or the lease, instead of `lastUse >= buildFloor`.
   - **Gain:** imports reached only through the space age out under regular use, and an evicting request can take them.
   - **Risk:**
     - An import the shaders read only through pointers has no use signal at all, so it is evicted first.
     - The next build's walk (non-evicting) can't re-import it. The range is then copied on the CPU every build.
     - If an evicting request asks for it back, it evicts another space import, rebuilding the space each time. That is a ping-pong.
   - **Guards it would need:** a cooldown per evicted range, and a cap on eviction-driven space rebuilds per present.
2. **Evict the least recently used import that no build has used since the last space rebuild, then rebuild the space.**
   - **How:** keep a space generation, and per import the generation of its last real build use (a region lookup or an access, not the space stamp). The candidates are the imports whose generation is older than the current space's. Evict the least recently used one, bump the epoch, and the next build rebuilds the space.
   - **Thrash guard:**
     - Right after a rebuild every import looks unused, so don't consider candidates until the new space has served K builds, enough for the imports builds really use to be marked.
     - Allow at most one eviction-driven rebuild per window.
     - Keep the evicted range in the walk's existing non-evicting refusal memory, so the next walk doesn't fight for it.
   - **Cost:** one rebuild (a walk over the registered ranges) per window, instead of 37,627 refused requests per present.

**Preference.** Option 2 with the warm-up window. Its signal (a build used the import since the space was made) is what eviction should protect. Option 1 drops the only signal for pointer-only data and needs extra machinery to stay safe.
