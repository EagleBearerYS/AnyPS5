## 1. Overlay hooks

### What main draws over the game today

- **One thread, one hook.** The presentation thread is `VideoOutDriver::presentLoop` (`VOD:659`, a `std::jthread` started at `VOD:309-316`). Each iteration it:
  1. polls SDL (`VOD:698-710`), feeding `padInput.HandleEvent` (`:704`) and `imeTextInput.HandleEvent` (`:708`);
  2. runs `padInput.Update` (`:711`);
  3. presents a flip through `processFlip` (`:719`), which calls `AgcDriverPresentBuffer` or `AgcDriverPresentClear` (`VOD:616/618`), reaching `VulkanDevice::present` (`VD:3513`).
  Pad sampling, host-keyboard text and drawing therefore all run on the same thread.
- **The only overlay is the performance overlay.**
  - `VD:3546` reads `PerformanceOverlay::Visible()`.
  - `VD:3676-3680` creates it lazily, then calls `NotePresent` and `Record(commands, slot, swapchainImage, surfaceFormat, colorSpace, extent, initialLayout, PRESENT_SRC)`.
  - The initial layout is COLOR_ATTACHMENT_OPTIMAL after a drawn frame, or TRANSFER_DST after a blit.
  - The same code runs on Windows and Linux: there is no `#if` in `VD:3513-3700`, and both go through the SDL window and Vulkan swapchain.
- **What it can draw: solid rectangles only.**
  - Each `OverlayRect{x, y, width, height, color}` (`POH:115-121`; 20 bytes, `PO:32`) becomes one instanced quad (`vkCmdDraw(commands, 4, rects.size(), 0, 0)`, `PO:776`), recorded into a render pass on the swapchain image.
  - Colours come from a 3-entry palette, Background / Text / Graph (`POH:123-124`). It is converted for sRGB or PQ surfaces by `OverlayPalette` (`POH:175`).
  - Text is a **5×7 bitmap font**: `OverlayMetrics` (`POH:150-161`) and `OverlayGlyph` (`POH:163`, table `PO:274-344`). `LayOutOverlay` (`PO:448`) turns each lit glyph pixel into a rect.
  - **Glyph coverage:** digits, space, `.`, `:`, `/`, and the capitals A–X except J, Q, Y and Z. There is no lowercase and no other punctuation. Any other character throws "the performance overlay font has no glyph" (`PO:342`).
  - **Not available:** font rasterising, glyph atlases and textures. FreeType is in `3rdparty/` for libSceFreeType and libSceFont, but the tree ships no font file, and system fonts are Sony assets we can't ship.

### What the keyboard needs

- **(a) A generic rect recorder.** `PerformanceOverlay::Record` builds its rects from `OverlayContent` (`POH:191-192`, `PO:719-776`). Split out a `Record(commands, slot, image, …, std::span<const OverlayRect>)` that the performance overlay and the keyboard both use. That reuses its render pass, pipeline and per-slot rect buffer (`POH:196-214`).
- **(b) A wider palette.** The keyboard needs: panel, text-field background, key, selected key, key text, hint badge and caret. Either extend `OverlayColor` to about seven entries, or let a rect carry an sRGB colour that `OverlayPalette` converts.
- **(c) Glyphs.**
  - Needed: all printable ASCII; the non-ASCII characters on the source's pages (€, ‘ ’ ‚ “ ” „ ‹ › « », ¡ ¿ ° ª º × ÷ ¤ ¢ ¥ £ ₩ § ¦ µ ¬ ¹ ² ³ ¼ ½ ¾ № ·, and the accented letters of the Specials page); and the function-key symbols (shift arrow, backspace, ◀ ▶ ▼ ▲).
  - A 5×7 cell has no room above a capital for a diacritic, so the keyboard needs a taller cell, for example 5×9 with two rows for marks.
  - Text the game pre-fills that has no glyph (CJK, for example) needs a fallback box. It must not reach `OverlayGlyph`'s throw.
  - The glyph data is new hand-made data in the repo. A third-party bitmap font would have to be a submodule, per AGENTS.md.
- **(d) Getting the dialog's state to the driver.**
  - libSceAgcDriver does not depend on libSceIme; libSceVideoOut already depends on both (`libSceVideoOut/src/ImeTextInput.cpp:2` and `PI:291` for libSceIme, `VOD:616` for the driver).
  - Proposal:
    1. libSceImeDialog publishes a view snapshot (text, caret, page, selected key, case state, Done label) to libSceIme. That is the same hub its host-text sink uses (`IME:363-389`).
    2. `presentLoop` reads the snapshot each iteration.
    3. It hands the snapshot to the driver through one new `AgcDriverSetSystemOverlay_nid_postfix(const SystemOverlayView*)` in `Execution/include/Presentation.hpp`.
    4. `VulkanDevice::present` lays out and records it after the game image and before or with the performance overlay (`VD:3676`).
- **(e) Cadence.** The keyboard is redrawn only when `presentLoop` presents a flip (`VOD:715-719`). A title that stops flipping while it waits on `sceImeDialogGetStatus` would show a frozen keyboard. This is a risk; see §8.

**Layout model:** a pure function `LayOutKeyboard(const SystemOverlayView&, VkExtent2D) -> std::vector<OverlayRect>`, in a new `Execution/src/KeyboardOverlay.cpp`. It can be unit-tested like `LayOutOverlay` (`libSceAgcDriver/tests/PerformanceOverlay.cpp`). It draws:
- the panel, centred in the bottom half;
- the text field, with a one-glyph-wide caret bar;
- a 10-column key grid with each key's label, and the selected key with a 2-glyph-pixel border, as in `SH:ime_kb_layout.cpp:2049-2093`;
- small hint badges ("L2", "△", "□", "R2", "L1", "R1", "L3") as in `SH:ime_kb_layout.cpp:2096-2125`.

It has no animations, gradients or fades: those are shadPS4 extras (`SH:ime_dialog_ui.cpp:801-806`, `src/imgui/imgui_std.h:67`).

## 2. The input hand-off

### Where pad state enters, on main

1. **SDL events** → `PadInput::HandleEvent` (`PI:250-299`).
2. **`PadInput::Update`** (`PI:301-331`) calls `SDL_GameControllerUpdate`, then `sampleController` per slot (`:313`) and `keyboardMouse.Advance`.
3. **`publish`** (`PI:339-348`):
   - slot 0 is `keyboardMouse.Compose(controller state)` → `PadPublishInput_nid_postfix` (`:342-343`);
   - other slots go to `PadPublishInputForPort_nid_postfix` (`:346`).
   - With a controller connected, slot 0 is published every loop iteration (`PI:323-325`).
4. **libScePad `PadPublishInputForPort`** (`PS:454-476`):
   - ignores an unchanged state (`:459-463`);
   - latches newly pressed buttons for the next `ReadState` (`:464-472`);
   - queues the sample for `scePadRead` (`:474-475`).
5. **The game reads** through `scePadReadState` → `Pad::ReadState` (`PX:323-330`, `PS:250-266`) or `scePadRead` → `Pad::Read` (`PX:309-321`, `PS:268-289`).
   - These are the only reads that return data. `scePadReadStateExt` (`PX:492`), `scePadReadExt` (`:301`), `scePadUiReadState` (`:726`) and `scePadReadHistory` (`:1109`) are `NotImplemented` stubs.

### Main's closest existing behaviour

The host-keyboard IME already holds input back from the game. While libSceIme or the dialog has the keyboard, `PI:291` drops `SDL_KEYDOWN` before the keyboard-to-pad mapping (`if (event.type == SDL_KEYDOWN && ImeCapturesKeyboard_nid_postfix()) return;`). Key-ups still pass, so keys held across the capture release cleanly. A key pressed during the capture is not seen as pressed afterwards.

### Proposal: the same shape for the pad

- **In `PadInput::publish`:** when the new `ImeCapturesPad_nid_postfix()` (libSceIme) is true:
  - send the composed slot-0 state to `ImePublishPad_nid_postfix(buttons, sticks, analog L2/R2)`, which forwards to the dialog's pad sink the way `IME:371-379` forwards text;
  - publish a **neutral** state to libScePad instead: buttons 0, sticks 128, triggers 0, touch off. libScePad's `connected` flag is not touched (`PS:442-452`).
- **libScePad's read paths need no change.** `ReadState`, `Read`, the queue and the latch all see the neutral sample.
- **Which pad drives the dialog:**
  - shadPS4 reads the pad of `Param::user_id` first, then any connected one (`SH:ime_ui_shared.cpp:89, 100-116`).
  - Main maps a user to a port in PadInput's slots. Slot 0 is the composed keyboard+controller pad.
  - Recommendation: the dialog takes the pad of the user that opened it (`Param::user_id`, `core/libs/SceTypes.hpp:1356`), falling back to slot 0. See §8.

### What the game's own reads return meanwhile

**The source** (`SHP:pad.cpp:376-388`): while ImGui holds the gamepad capture (`SH:ime_dialog_ui.cpp:410` acquires it, `:640` releases it), every sample is:
- zeroed, then `buttons = Intercepted` (`0x80000000`, `SHP:pad.h:149`);
- sticks `{128,128}`, orientation identity;
- `connected`, `timestamp` and `connectedCount` kept;
- triggers, motion and touch zero.

This applies to `scePadRead`, `ReadExt`, `ReadState` and `ReadStateExt` (`SHP:pad.cpp:432-478`).

**Ours:** the same neutral buttons, sticks and connected=true. Two differences:
- **The Intercepted bit.** Main has no such constant (`libScePad/include/PadInputTypes.hpp:30-47`), and `scePadSetForceIntercepted` is a stub (`PX:649-652`). The source sets it, so the build should too. It needs a `bool intercepted` in `PadInputState` (`libScePad/include/PadState.hpp:21-33`), set by PadInput while captured, which libScePad's `BuildData` ORs into `buttons` as `0x80000000`. Whether the PS5 system IME sets it is unverified (§8).
- **Motion.** The source zeroes motion. Our neutral `PadInputState{}` keeps gravity on Y (`PadState.hpp:29`). Recommendation: publish the neutral state with `hasMotion = false`.

### Edge handling

- **A press is seen once.** The dialog's pad model keeps the previous buttons and acts on `pressed = buttons & ~previous`. Repeats come from its own timers. The source uses ImGui's `KeyRepeatDelay` and `KeyRepeatRate` (`SH:ime_ui_shared.cpp:756-757, 946-947`), which shadPS4 leaves at ImGui's defaults; the values aren't in the source.
- **Buttons held when the dialog opens don't type.**
  - The source seeds `prev_virtual_buttons` with the buttons held on the first frame (`SH:ime_ui_shared.cpp:934`), so a held button gives no edge.
  - Cross is also disarmed until it has been seen released (`SH:ime_dialog_ui.h:107`, `SH:ime_dialog_ui.cpp:889-897`).
  - **Gap in the source:** the repeating buttons (□, L1, R1, △, D-pad) keep their own "previous" flags, which start false (`SH:ime_dialog_ui.h:127-133`). So a □ held at open is latched on frame 1 and then auto-repeats, deleting text (`SH:ime_ui_shared.cpp:647-651, 664-668`).
  - Recommendation: seed every button's previous state, and its repeat state, from the first sample.
- **Buttons held when the dialog closes**, for example R2 still down after Done:
  - With the plan above, the first real sample after capture ends reaches libScePad as a new press (`PS:464`), and the game may act on it.
  - The source does nothing about this: nothing in it masks held buttons after close.
  - Main's keyboard capture effectively masks them: key-downs during capture never reached the mapping (`PI:291`).
  - Recommendation, following main's closest behaviour: when capture ends, PadInput masks the buttons still held until each is released. This is a PM call (§8).

### The host keyboard path (#6504) alongside

It is unchanged:
- `SDL_TEXTINPUT`/`SDL_KEYDOWN` → `ImeTextInput::HandleEvent` (`libSceVideoOut/src/ImeTextInput.cpp:8-42`, called at `VOD:708`) → `ImePublishInput_nid_postfix` (`IME:363-380`) → the dialog's `Receive` (`ID:71-109`) under `g_mutex`.
- The pad sink edits the same `Dialog::text` and `caret` under the same mutex.
- Both run on the presentation thread, so a host key and a pad press in one loop iteration apply in SDL-event order, then pad order.
- Keyboard keys don't double as pad buttons for the OSK, because `PI:291` already drops them.

- CapsLock uses the uppercase page (`:1208-1209`).
- The starting page follows the game's priority option (`SH:ime_ui_shared.cpp:218-244`). The cursor starts on `g`, row 2 col 4 (`:249-263`).
- `[..]` below is the hint badge the source draws on the key; `_` is an empty cell.

- Specials page 2 (`:827-888`) repeats `ÿ ź ż ž ð þ`. Switching family resets the page (`SH:ime_ui_shared.cpp:285`) and no key pages to it, so it is unreachable.

- Build these pages and function rows as listed.
- Leave the ⌨ key, the "..." key and the R3 key as empty cells: they have no behaviour without ImGui (§0).
- Keep ▼/▲. They move the caret to the end or start in single-line text (`SH:ime_dialog_ui.cpp:1707-1718`).

## 5. Build plan

**Size:** roughly 1,800-2,400 added lines. About half of it is glyph and layout data.

**Commits, in order**, each with its own tests, no comments in code, and Conventional Commits subjects:

1. **`feat(libSceImeDialog): add the pad keyboard model`**
   - New `core/libs/prx/libSceImeDialog/src/PadKeyboard.cpp` and `include/PadKeyboard.hpp`. Pure: no SDL and no locks.
   - Contents: the pages of §4 as data; `PadKeyboardState` (page, family, case state, selected row/col, previous buttons, per-button repeat timers, Cross armed); and `PadKeyboardStep(PadKeyboardState&, const PadSample&, Clock::time_point) -> EditAction`. `EditAction` covers Insert(text), Backspace, ClearAll, CaretLeft, CaretRight, CaretHome, CaretEnd, Done, Cancel or None.
   - It encodes §0's priority order, edges and repeats; L2's cycle and re-arm; L2+△, L3 and the paging keys; and seeding from the first sample.
   - New test `libSceImeDialog/tests/PadKeyboard.cpp`, registered in `libSceImeDialog/CMakeLists.txt`.
   - About 700 lines.
2. **`feat(libSceIme): route a captured pad to the dialog`**
   - In `libSceIme/include/ImeInput.hpp` and `libSceIme/Export.cpp`: `ImeCapturesPad_nid_postfix`, `ImePublishPad_nid_postfix`, `ImeSetHostPadSink_nid_no_patch`, and a view provider (`ImeSetKeyboardViewProvider_nid_no_patch` / `ImeReadKeyboardView_nid_postfix`). These are modelled on the text sink at `IME:363-389`.
   - Tests extend `core/libs/tests/GuestImeOpen.cpp` or add a small libSceIme test.
   - About 150 lines.
3. **`feat(libSceImeDialog): drive the dialog from the pad`**
   - In `ID`: register the pad sink and view provider in `Init`; apply `EditAction` to `Dialog` (reusing `Insert`, and the `Receive` cases for caret and backspace); release them in `Finish`, `Term` and `ForceClose`.
   - Tests extend `core/libs/tests/GuestImeDialog.cpp` (§6).
   - About 200 lines.
4. **`feat(libSceVideoOut): hand the pad to an open keyboard and hold back the game's reads`**
   - In `PI:339-348`: publish neutral and forward while captured; mask buttons still held at release (if the PM agrees, §8). In `PadState.hpp` and `PS`, add the `intercepted` bit.
   - Tests extend `libSceVideoOut/tests/PadSdl.cpp` (§6).
   - About 150 lines.
5. **`feat(agc): draw the system keyboard over the presented frame`**
   - The generic rect `Record` (`POH:191-192`, `PO:713-776`); the palette entries; the keyboard glyphs and fallback, in a new `Execution/src/KeyboardOverlay.cpp` and `include/KeyboardOverlay.hpp`; `LayOutKeyboard`; `AgcDriverSetSystemOverlay_nid_postfix` in `Presentation.hpp`; and the record call at `VD:3676`.
   - `VOD:686-743` fetches the view from libSceIme and passes it on before `processFlip`.
   - Tests in a new `libSceAgcDriver/tests/KeyboardOverlay.cpp`: layout rects and glyph coverage.
   - About 800-1,200 lines, mostly glyph data.

## 8. Risks and open questions for the Project Manager

1. **No flip, no keyboard.** The keyboard is drawn only when a flip is presented (`VOD:715-719`). If a title stops flipping while it waits on the dialog, the keyboard freezes or never appears. Settling this needs a run of PvZ Replanted and Octopath Traveler 0. If either stops flipping, the build needs a re-present of the last frame from `presentLoop`, which main doesn't have.
2. **The Intercepted bit (0x80000000).** The source sets it while the dialog has the pad (`SHP:pad.cpp:380`). Is that what the PS5 system IME does? A title that checks the bit might behave differently. The plan follows the source; a hardware or title check would settle it.
3. **Held buttons after close.** Not in the source. The plan follows main's keyboard-capture behaviour (`PI:291`) and masks them until released. PM's call.
4. **The source's repeat-at-open gap** (§2). The plan seeds every repeat state from the first sample, which is stricter than the source. PM's call.
5. **Which user's pad.** The source uses `Param::user_id`'s pad, then any. Main has a user-to-port mapping in libSceUserService and PadInput slots. The plan's fallback to slot 0 needs checking with a second controller.
6. **Live buffer writes and the game's text filter.** The source writes the buffer on every edit and calls the game's filter on each `GetStatus` (`SH:ime_dialog.cpp:964-965`); main does neither. The build keeps main's behaviour. A title that reads the buffer while the dialog is up (for a live preview) would only see the text on Done.
7. **`GetResult` and `Term` while running.** Main returns `NotOpened` and tears down; the source returns `DIALOG_NOT_FINISHED` and refuses (§3). Out of this build's scope; a separate fix if the PM wants it.
8. **Glyphs.** Hand-made 5×9 glyphs for about 190 characters are tedious and easy to get wrong. The layout test only proves each glyph exists, not that it looks right, so a reviewer screenshot (`AgcDriverRequestScreenshot`, `PI:296`) should be in the PR.
9. **Japanese or other non-Latin input.** The source's pages are Latin, Symbols and Specials only, so a title that sets a Japanese priority gets Latin (`SH:ime_ui_shared.cpp:218-244`). The same holds here.
10. **Multiline.** No page has NewLine, and main's `Insert` drops `\n` (`ID:63`). A title that opens a multiline dialog can't add line breaks from the pad (nor from the source).
11. **Title runs needed:** PvZ Replanted at the profile name (D#6404), and Octopath Traveler 0 at the favourite-food prompt. Confirm the dialog opens, the game keeps flipping, the name is accepted, and the menu doesn't move while typing.
