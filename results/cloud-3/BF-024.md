1. `core/shader/recompiler/IntermediateRepresentation/include/IntermediateRepresentation/IrMetadata/StageIO.hpp`:
   fast5 (2cd0c9107, pixel shaders the guest does not iterate per pixel) appended
   `BaryCoordSmoothCenter`, `BaryCoordNoPerspectiveCenter`, `BaryCoordSmoothSample`,
   `BaryCoordNoPerspectiveSample` to `StageInputKind` after `BaseInstance`, where BF-022 appended
   `BaseVertex` and `DrawIndex`. Kept fast5's four first and BF-022's two after them, so no existing
   value moves.

2. `core/libs/prx/libSceAgcDriver/Execution/src/Driver/Draw/Draw.cpp`: the only textual conflict was
   the head of the inline CPU-path branch (`if (drawParameters.indirect && indirectCpu)`), where
   fast5 drains the pipeline (`if (pipelined) Drain(DrainReason::Indirect)`, needed because with
   `APS5_PIPELINE_INDIRECT` the up-front drain is skipped) and BF-022 clears the draw-parameter mode
   before the per-record builds. Kept both: drain, then clear.
   One non-textual change: #1896's pipelined record branch (`indirectCpu && pipelineIndirect &&
   no deferred labels && !rectList`) rebuilds each record's stage too, so it also clears the
   draw-parameter mode first (otherwise a draw that fell back after its draw-parameter compile, the
   k == p rule or `vertex range too large`, would rebuild records with draw parameters on and draw
   them direct, wrong).
   Order: BF-022's decision (`IndirectDrawParameters`, where the patched SGPRs are located) runs at
   the same place as on main, before the stage lookup and compile and so before both #1896 branches;
   a draw-parameter draw is classified GPU-side (`indirectCpu` empty) and never enters #1896's
   record pipeline.

## What #1896's path changes for these draws

Nothing made a draw fall back that does not on main; the classification is the same code. The
differences are in when and where a GPU-side draw is recorded, and only with
`APS5_PIPELINE_INDIRECT=1` (off by default; `DrawPipeline::PipelineIndirect`):

- **Off (default):** every indirect packet drains the pipeline first (Draw.cpp:39), exactly as on
  main, and a draw-parameter draw is recorded inline. Same behaviour as BF-022 on main.
- **On:** the up-front drain is skipped. A draw-parameter draw has no `indirectCpu`, so it skips
  both CPU branches and reaches the whole-draw commit at the end of `draw()` (`pipelined &&
  (!indirect || pipelineIndirect)`), like fast5's existing in-place GPU-side indirect draws: it is
  enqueued and recorded on the pipeline's committer, counted as an indirect commit
  (`[draw] pipelined ... indirect commits 46784` in a 10 s soak of 8-record draw-parameter packets,
  vs 0 with the switch off). The records are still read in place by the GPU when the batch runs;
  ordering against later packets holds because every packet other than register writes and draws
  drains the pipeline (PacketExecution.cpp:192), and `DrainIfOverlaps(capture)` still re-runs the
  draw when its captured memory overlaps queued writes (the draw-parameter decision is simply made
  again). Depth goes from 8 to 64 queued draws.
- A draw that is compiled with draw parameters but then falls back (the k == p rule for fetched
  dimensions, `vertex range too large`) can now take #1896's pipelined record branch; that branch
  clears the mode before its per-record rebuilds (the resolution's second change). Without that the
  records would have been drawn with a draw-parameter stage and a direct draw, so `BaseVertex`,
  `BaseInstance` and `DrawIndex` would have read the direct draw's values, not the record's.
- #1896's record branch is not taken for rect lists or with deferred labels; those, like a
  fallback with the switch off, use the inline CPU branch, which drains first as before.

On the title's numbers in the task: the menu's CPU-path packets (capture 232, vectors 273,
recompile 107, decode 25 µs) are exactly what a draw-parameter packet skips (soak on lavapipe:
capture 0.0, recompile 0.0, decode 0.3-0.4, vectors 1.3-1.7 µs per packet); what it adds is
main's GPU-path render pass and argument barrier per indirect draw (`Graphics::Draw` 41-57 µs per
one-record packet on lavapipe vs 20 µs for a CPU-path draw continuing a pass), which the title's
CPU path mostly pays already.

## Counter

The `[draws]` profile line's indirect part now reads `indirect: gpu-side N (M rewritten, K draw
parameters), cpu-side ...`. Draw-parameter draws read in place were already counted in N (path
`Gpu`); K counts the ones among N whose stage reads the patched SGPRs from the draw (counted in
`CountIndirectDraw` from the draw's `IndirectDraw::drawParameters`, for the inline and the recorded
draw path, so also for draws #1896 commits on the pipeline worker). A draw-parameter draw whose
records the graphics side read on the CPU (not imported, pending image, label or copied write)
keeps its CPU reason, as before. The PC reads it with `APS5_PROFILE_DRAW=1` (the line is printed
every 10 s); K over N is the share, and `cpu-side (patched SGPR not folded ...)` shows what still
falls back.

Measured (10 s window of a profiled soak of 8-record draw-parameter packets): `indirect: gpu-side
49217 (0 rewritten, 49217 draw parameters), cpu-side 0 ()`; with `APS5_PIPELINE_INDIRECT=1`:
`indirect: gpu-side 46385 (0 rewritten, 46385 draw parameters), cpu-side 0 ()`.
