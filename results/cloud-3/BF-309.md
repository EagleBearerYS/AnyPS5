## How the two compose (UploadFinish on the branch)

For a region no single import covers:

1. **Main's own pre-pass tries a joined import first** (`importJoined`, `:5521`, JJenkx's #9652). That succeeds when the region starts at the run's base, or when every range in the run exceeds the import window (8 MiB in production, `VulkanDevice.cpp:1620`). A joined import is a single import, so BF-307's GPU copy at any size applies to it.
   - **Spans therefore matter on main only when:** the region starts inside a run and crosses into a range of at most 8 MiB, or the join fails (alignment, budget, refusals).
   - Whether Village's 11.6 MiB accesses are such regions is what the profiled boot's `[buffers]` line ("… outside imports") must show.
2. **Otherwise his `importSpans` cuts the region into the imports of the ranges it covers,** and the GPU copies it piece by piece. The pieces are given up when an import was retired while they were collected: the epoch bumps on retirement (`:446`), not on a new single import.
3. **Our follow-up adds the BF-307 condition to that gate:** `spanCopyEligible(region) || copyBehindGpuWork(region, true)`.
   - Behind a pending GPU write, pending storage results or a unit shadow, the region takes the span copy whatever its size. Behind no GPU work the 16 MiB bound stands.
   - Without this, a 20 MiB spanning region behind a GPU write still waits (red B below).
4. **No CPU wait on that path:**
   - UploadPrepare leaves import-less regions pending (`:5394`–`:5397`), so it makes no stage-A CPU copy.
   - UploadFinish records `FlushPending(… "copied buffer region")` ahead of the copy.
   - `recordGpuCopies` flushes queued key and label stores, then records the leading barrier (ALL_COMMANDS|HOST writes → TRANSFER read). With a pending writer there is no CPU snapshot, so the spans are copied after the producer in batch order.
5. **Copy-back:** `RecordCopyBacks` writes each written sub-range back piece by piece into the span imports (his code). Test case 3 checks the guest bytes on both sides of the boundary.
6. **Reuse:** a build with a span region is never reused (`:6450`–`:6451`: not `direct`, not staged). That errs on the safe side.

`docs/dev/ENVIRONMENT.md`'s `APS5_GPU_COPY_MAX_KIB` row now says: spanning regions up to 16 MiB (or the cap, if larger), and whatever their size behind such GPU work.

## The tests (red/green)

`agc_buffer_upload_span_gpu_copy` (`agc_driver_recorder_tests --span-upload-gpu-copy-only`, `spanUploadGpuCopyTests` in `tests/Recorder.cpp`, also in the full recorder run). It extends BF-307's test.

**Setup:**
- With the import window at 16 MiB, two adjacent 16 MiB write-watched ranges are registered.
- Each is imported apart; the test requires two imports meeting at the boundary.
- Main's join does not apply to them: neither range exceeds the window, and no view starts at the run's base.
- For each case, a `vkCmdCopyBuffer` producer writes 1 MiB across the boundary into both imports. It is noted as a pending write and left in the open batch, **with no barrier of its own**, so only the driver's barrier orders the copy behind it.

**Cases:**

| case | view | written |
|---|---|---|
| 2 MiB | +15 MiB+4 … +17 MiB | no |
| 20 MiB | +8 MiB+4 … +28 MiB | no |
| written 2 MiB | +15 MiB+4 … +17 MiB | yes |

In each case the upload under the GPU mutex makes **0 flush-hook waits** (`Recorder::ThreadHookWaits`) and **0 submissions**, and the producer is still pending in the open batch. Then:
- **Read cases:** a GPU read of the descriptor's bound range holds the producer's bytes and the original bytes around them. After the sync, guest memory holds the producer's bytes.
- **Written case:** a simulated shader store of 512 KiB across the boundary goes into the bound buffer, and `RecordCopyBacks` runs. After the sync, guest memory holds the copied-in bytes with the store applied, on both sides of the boundary.
