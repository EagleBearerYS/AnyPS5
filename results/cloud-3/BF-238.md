# BF-238: is there a lock self-deadlock when a multisampled colour target is resolved for a read? (cloud-3)

## Verdict: not on main, and not with our stack

- **Main:** on upstream `main` **d2b3ee3bcc** (fetched 2026-10-25 ~15:30Z, after #9186), the "resolve or sample a multisampled colour target for a read, then create or refresh its storage texture" path has no self-deadlock and no lock-order inversion.
  - Every lock on the path is taken in one acyclic order (graph below).
  - The only lock re-entered on one thread is `GpuMutex`, which is recursive.
- **Our stack:** #9533, #9717, #9742 and a2911ffb72 add one new edge (`surfacesMutex` → `targetsMutex` → `guardedMutex` shared), always under `GpuMutex` and with no reverse edge. They make no cycle.
  - BF-236's branch `fix/agc-msaa-depth-alias-same-value-fill` isn't on the fork yet (cloud-2 claimed BF-236 at 14:59Z), so it isn't covered.
- **The function they named doesn't exist upstream.** `PrepareMultisampleTargetRead` is in no upstream file: `git log -S PrepareMultisampleTargetRead upstream/main` is empty, and no fetched upstream or fork ref contains it. The deadlock they decoupled was in code that isn't on main: their local tree, or a non-upstream branch.
- **No branch was pushed.** Without a real deadlock there's no test and no fix, so `fix/agc-msaa-resolve-lock-order` was not created.

## The path on main (d2b3ee3bcc)

`MS` = `Graphics/src/MultisampleTarget.cpp`, `SR` = `Graphics/src/ShaderResources.cpp`, `DS` = `Graphics/src/DepthSurface.cpp`, `REC` = `Graphics/src/Recorder.cpp`, `GM` = `Execution/src/GuestMemory.cpp`, `XD` = `Execution/src/Driver/Draw/Draw.cpp`, `GD` = `Graphics/src/Draw.cpp`.

### Where the read and the resolve come from

- **Sampling a multisampled texture:**
  - `SR:714` `cachedTexture` → `MultisampleTargetTexture` (`SR:723`).
  - `SR:4855` → `MultisampleTargetFirstSample`.
  - `SR:4920` → `MultisampleTargetStorageView`.
  - No ShaderResources lock is held at any of these calls: none is taken earlier in `cachedTexture`, `resolveImageBinding`, `revalidateFull` or `resolveImageTables`.
- **The CB resolve:** `GD:3391` `RunColorMetadataPass` creates the destination storage texture first, `CachedStorageSurface` → `cachedStorageTexture` (`GD:3396`), with no multisample lock held. Only then does it call `ResolveMultisampleTarget` (`GD:3398`).
  - **Storage creation therefore never runs inside `targetsMutex`.** The tree ~5,665 commits behind main (0644811579, by `rev-list` count) has the same order (`GD:2782` then `:2784`).
- **The callers hold `GpuMutex`:**
  - Graphics draws reach `Graphics::Draw` only after `lockForDraw()` (`XD:1069-1074`, called at `:1186` and `:1232`), or inside `commitDraw` (`XD:1255`).
  - Dispatches take it at `Execution/src/Driver/Dispatch/Dispatch.cpp:88/487/546/580`.
  - `Recorder::Commands` asserts it (`REC:1574`), and `Sampled()`, `Storage()` and `FmaskSampled()` all require an active recorder.
  - `GpuMutexType` is recursive: it keeps an owner and depth (`Execution/include/GuestMemory.hpp:148-169`).

### Lock graph (→ = taken while holding)

```
GpuMutex (recursive; XD:1074, XD:1255, Dispatch.cpp:88/580)
 └→ targetsMutex  std::mutex (MS:762)
      taken at MS:1133 OrderTarget, :1139/:1146 TargetView, :1183 TargetTexture, :1206 FirstSample,
      :1229 MaterializeClear, :1234 StorageView, :1258 Storable, :1265 ResolveMultisampleTarget,
      :1289 ColorFillAbsorbs, :1300 NoteColorMetadataFill, :1327 FmaskTexture, :1341 ClearMultisampleTargets
      ├→ guardedMutex  std::shared_mutex (MS:677)
      │    exclusive: MS:751 guard (from acquire :799/:823 and createFilled :898), :777 holdHostOnly (from :1243, :1294),
      │               :792/:804 acquire, :1343 Clear, :1387 RequireNoMultisampleColorTarget (retire)
      │    shared:    MS:1378 RequireNoMultisampleColorTarget
      │    └→ observer mutex (MS:915-916), via InstallResidentImageReadGuard at MS:759 while :751 is held.
      │       It only does atomic loads and GuestAllocationsSetUnmapObserver, an atomic store
      │       (libc/src/GuestAllocations.cpp:630-631): a leaf.
      ├→ depthGuardMutex (DS:1868 shared, DS:1871 exclusive), via createFilled → RequireNoMultisampleTarget (MS:858)
      │    → RequireNoResidentDepthRead. It is released before guardedMutex is taken (MS:1361-1362), not nested.
      ├→ singleClearsMutex (MS:705), via ApplyFastClear → TakeMultisampledClear → recordedSingleClear (MS:998): a leaf.
      ├→ GpuMutex again (recursive, so no wait), via createFilled → GuestMemory::FlushGpuWrites (MS:859, :868)
      │    → Recorder FlushForAccess (REC:1017; GpuMutex at REC:1037; SyncThrough REC:1043)

      ├→ recorder internals, via Keep (MS:306-311), recordCommands (MS:119-126)

```

- **Storage texture creation:** `cachedStorageTexture` (`SR:1184`) runs `RequireNoMultisampleTarget` (`SR:1188`) before it takes the storage cache lock (`SR:1217`).
  - Under that lock it calls `StorageTexture::FlushPending`, `StorageTexture::Create` and `Refresh`. `Texture.cpp` contains no call into MultisampleTarget code.
  - So the storage cache lock never leads to `targetsMutex` or `guardedMutex`, and nothing under those leads to the storage cache lock.

### Threads outside GpuMutex

- **Host read hook (game threads in libkernel/libc HLE):**
  - `GuestArenaPrepareHostRead_nid_no_patch` (`libc/src/GuestArena.cpp:610`) → `PrepareHostRead` (`GM:2526`) → `guardReads` (`MS:692`) → depth guard, then `guardedMutex` (shared `:1378`, then exclusive `:1387`).
  - Each is released before `FlushGpuWrites` → `FlushForAccess` takes `GpuMutex`. Nothing is held across it.
  - The hook is only called explicitly (libkernel Stdio/Open/Aio/Udp/Process, libc), never from a fault handler, so it can't fire inside a locked driver section.
- **Unmap observer (game threads, inside a GuestAllocations mutation):**
  - `GuestAllocations.cpp:528/622/627` → `retireUnmapped` (`MS:726`).
  - It takes `singleClearsMutex` (`MS:721`), `depthGuardMutex` (`DS:1898`) and `guardedMutex` (`MS:729`) one after another.
  - None of those sections waits on `GpuMutex` or calls back into GuestAllocations. `RetireUnmappedDepth` (`DS:1894-1918`) is pure list work.
- **No cycle:** no driver thread holding `guardedMutex`, the depth guard or `singleClearsMutex` waits for the mutation lock or `GpuMutex`. Those sections are pure (only the leaf observer mutex above).

### Checked candidates for a self-deadlock on one thread

| Candidate | Why it doesn't deadlock on main |
|---|---|
| `createFilled` (under `targetsMutex`) → `FlushGpuWrites` → `FlushForAccess` → `GpuMutex` | `GpuMutex` is recursive and the caller already holds it. The queued-label recorder records labels, not draws. |
| `createFilled` → `RequireNoMultisampleTarget` → `guardedMutex` | The thread holds `targetsMutex`, not `guardedMutex`. |
| `guard()` holds `guardedMutex` → `InstallResidentImageReadGuard` | `call_once`, plus `SetReadGuard`, `SetUnmapObserver` and `GuestArenaSetHostReadHook`, are all atomic stores. The observer mutex is a leaf. |
| `ResolveMultisampleTarget` → storage texture | The storage texture is created before, at `GD:3396`, outside `targetsMutex`. |
| A host read or unmap on a thread holding `guardedMutex` | No `guardedMutex` section reads guest memory or unmaps. |

## #9186's effect

#9186 (fma-rc, merged 0658bc8749 at 2026-10-25T13:25Z) changed `MultisampleTarget.cpp` (+62 −20 lines):

- **New nested acquisitions:** three new exclusive `guardedMutex` sections inside `targetsMutex`:
  - `holdHostOnly` (`MS:776-781`), called from `MultisampleTargetStorageView` (`:1243`) and `MultisampledColorFillAbsorbs` (`:1294`);
  - `acquire`'s hostOnly block (`:803-806`);
  - `acquire`'s recreate path, which now marks `hostOnly` before `guard()`.
- **Retire path:** `RequireNoMultisampleColorTarget` used to take only a shared lock and throw. It now takes a shared lock, releases it, then takes it exclusively to retire undrawn filled targets (`:1377-1397`). The game thread's host read hook now writes under `guardedMutex`, but holds nothing else while doing so.
- **Net:** it added and moved `guardedMutex` sections, all in the existing `targetsMutex` → `guardedMutex` order. It added no reverse edge and no new callout under `guardedMutex`, so it created no deadlock path and removed none.

## What their Windows runs could have hit instead

- **Their own local code.** The function they changed has no upstream counterpart. A deadlock in a local helper of that name, or a local reordering of the resolve (for example, creating the storage texture inside `targetsMutex`), would fit their description and doesn't exist on main.
- **A GPU wait that looks like a lock hang.** `createFilled` (sampling a multisampled texture that no draw rendered to) and the flush hook can call `recorder->SyncThrough` (`REC:1043`) while holding `targetsMutex` and `GpuMutex`. If that wait never ends, every queue worker then queues on `GpuMutex`, and a debugger shows the multisample frames on the stuck thread. Examples: a lost device or TDR on Windows, or a label never written (the I#6558 / BF-209 pattern).
- **An older base:** about 5,665 commits behind is roughly 0644811579 (2026-10-18) by `rev-list` count. That tree's `MultisampleTarget.cpp` (912 lines) has the same `targetsMutex` and `guardedMutex` structure, and the same resolve order (`GD:2782` storage, then `:2784` resolve). The base alone doesn't explain it either.
- **To settle it** when they're back: their diff for `MultisampleTarget.cpp` and `Texture.cpp`, and a stack of all threads at the hang (Visual Studio "Parallel Stacks", or `gdb thread apply all bt` on MinGW builds).
