## Summary

- **The prototype removes nearly all of an address-based dispatch's binding cost.** With 16 textures, the driver thread drops from 342 µs (unchanged memory) and 838 µs (one word changed) to **65 µs in both cases**. That is within 10 µs of the non-address program's 54 µs, which takes recipes. The phase that moved is the **device call**, where the `shader_resources` build runs: 274–770 µs became 24 µs. With 2,000 textures, the time per dispatch drops from **8.2 ms to 0.98 ms**, against 0.68 ms for the non-address program with recipes.
- **The reuse costs only a revalidate.** With the prototype, the device call grows by about 0.19 µs per texture, most of it the fast proof (0.14 µs per texture). On main a rebuild grows by about 3.7 µs per texture. On the whole driver thread the slopes are 0.46 and 4.0 µs per texture. Most of a rebuild is the image resolution: stage B "images", 2.8 µs per texture.
- **At about 2,000 textures, a gap on main hides the gain.** A build logs at most 1,024 texture lookups (`ShaderResources.cpp:435` on main), so a 2,000-texture object has no record for half its textures. Its fast proof then fails with `no record` on every call, and `Revalidate` walks every texture: 4.1 ms per dispatch for the non-address program, 4.5 ms for the prototype. With the bound raised to 8,192 (`APS5_LOOKUP_LOG_BOUND`), these become 0.68 ms and 0.98 ms. This hits non-address programs on main too, for any draw or dispatch that binds more than about 1,000 textures. Resident Evil Village binds about 2,000 per draw.
- **The fast `Revalidate` split:** the per-texture loop takes three quarters of a proof, and `UnchangedSinceAll` most of the rest. `ScanPending` is small (4–9 %). Measured `CollectWrites` is mostly the timer around it: net of the clock pair, it costs under 35 ns per texture. See §3.
- **`^agc` with the prototype on has 11 new failures, all the same stall:** a guest free waits 60 s on a lease that a cached resource object holds (§4). This is the first thing that would break if it shipped as is. With the switch off, 625/625 pass at the branch head.

## 1. Harness

`DispatchBindingCost.cpp` writes a small GFX10 compute program into guest memory and dispatches it with `sceAgcDriverSubmitAcb` on ACB queue 0x20, waiting idle after each submit. Each dispatch is one wave of 64 lanes.

The programs:
- **(A) `plain`:** scalar-loads an SRT and reads a buffer element (MUBUF). It samples one texture from a texture heap, then stores the result through a second buffer (MUBUF). Its bindings are 2 buffers and an image table of N textures.
- **(B) `address`:** the same program plus a GLOBAL load and a GLOBAL store through a pointer it loads from the SRT. That makes it an address-based (`usesBda`) program with the same bindings.
- **(C):** (B) with N = 1, 16, 128 or 2,000 textures.

The heap is a buffer V# with N records of 32 bytes, so the build resolves an image table of N textures. Each texture is an 8×8 RGBA8 surface in its own 256-byte slot.

The memory setup:
- Code, SRT, buffers and heap sit in one 64 KiB-aligned block that the GPU can see (imported).
- The surfaces sit in a second block the GPU does not map, so they are write-watched. Putting them in the GPU block instead is the `gpu-surfaces` row in §2.
- In the **changed** runs, one word of the input buffer flips before every dispatch.

How it runs:
- Without arguments, the ctest entry runs a correctness pass: 4 plain rounds, then 6 address rounds that check the GLOBAL store (`GlobalOut = GlobalIn + 1`).
- The cost mode is `--cost <plain|address> <textures> <unchanged|changed> <seconds> [gpu-surfaces]`. It does 50 warm-up dispatches, then dispatches for the given time. It calls `FlushGpuWrites` on the output every 64 dispatches; without it the recorder's in-flight batch list grew without bound and slowed every build.

Measurement:
- Each configuration ran for 66 s with `APS5_PROFILE_DRAW=1`. The driver prints `[dispatch] driver phases other queues` every 10 s: the wall time of `Driver::dispatch` per dispatch, split by phase.
- The tables give the median of windows 2–6 (5 windows; the first window, which includes warm-up, is dropped) and the range of those windows.
- "Device call" is the `VulkanDevice` dispatch call, where the `shader_resources` build or reuse runs.
- `ANYPS5_NO_SHADER_CACHE=1` and `APS5_NO_PIPELINE_JOURNAL=1` were set for all runs.
- `APS5_IMAGE_TABLE_CAPACITY=4096` was set for every row except the `default capacity` row (see the note under the table).

- **`gpu-surfaces`:** when the textures themselves are in imported memory, the fast proof fails on `collect` every time. On lavapipe, host imports resolve write protection, so the driver compares imported ranges instead of watching them, and `CollectWrites` returns 0. The full walk then costs 17 ms at 2,000 textures. How often textures sit in imported memory on a real driver and a real title was not checked.

Which part dominates:
- **The per-texture loop: 75 % of a proof at every size, linear in the texture count.** As measured, `CollectWrites` is about 60 % of the loop. But each texture's measurement wraps one `CollectWrites` call in a clock pair that costs 41–62 ns, measured separately in the same run. Net of that, `CollectWrites` costs roughly 5–35 ns per texture: a write-watch query on an unwatched-and-clean range.
  - The rest of the loop costs about 40 ns per texture. That is the record checks plus the per-texture bookkeeping: the pending and unchanged query vectors, and the `query` closure for the pending registry, which runs on every proof here (next item).
  - So the loop is spread over small per-texture steps. No single call stands out.
- **`UnchangedSinceAll`: 28 ns per texture, about 20 % of the timed proof.** Net of the timers, that is about 30 % of an untimed one. It is the largest single named call: 55 µs at 2,000 textures, against roughly 10–70 µs net for all the `CollectWrites` calls together.
- **`ScanPending`: 5 ns per texture, 4–9 % of a proof.** It ran on every proof, because the pending registry's serial moved between dispatches each time (`pendingSerialSeen != serialBefore`). A proof that skipped it on an unchanged serial would save only this part.
- Without the per-texture clocks, a 2,000-texture proof would take about 160–190 µs (283 µs minus 2,000 clock pairs). That is the same order as the 0.3 ms per call the profiled boot showed.

The device-side `revalidate` phase at 2,000 textures (about 375 µs) is about the fast proof plus the rest of `Revalidate`: its pending-write completion over the direct regions, the prototype's snapshot compare, and the staging checks.

## 4. The prototype and what it would need to be sound

On main, an address-based compute object is never reusable: `noteReusable` returns early on `usesBda` and on `HoldsLease()` (`ShaderResources.cpp:2081`), and `HoldsLease()` is true while the object holds the cached address space. The prototype (`APS5_BDA_RESOURCE_REUSE=1`) is deliberately thin:

- **Reusable:** a compute object (`computeObject`) becomes reusable when three things hold:
  - its build took the cached address space (`space != nullptr`);
  - it holds no direct lease of its own;
  - that space has no mirrors (sparse, writable, heap) and no copied ranges (`GuestBufferMemory::SpaceReusable`).
- **Revalidate:** before the usual texture, import and staging steps, such an object also checks two things:
  - the space is still the published one, with the same device, registry generation and import epoch (`SpaceCurrent`);
  - every snapshot the build was given (the scalar-loaded SRT, the code and so on) is byte-equal to guest memory. This is a `memcmp` against copies kept at build time, because imported memory has no write-watch to prove it with.
- **No recipes:** address-based objects never get a dispatch recipe (the recipe condition at `VulkanDevice.cpp:4850` gains `&& !resources->UsesAddressTable()`), so the recipe path cannot skip those checks. Pipelining therefore stays off for them, as on main.
- **Data words:** with template data refresh (the default), `DispatchContentKey` leaves the data words out of the key. A data hit therefore finds the same object, and `RefreshData` patches the words, as for any template hit. The words a program reads from memory are covered by the snapshot compare.

### What would break if it shipped as is

1. **Guest frees stall: proven by the 11 failures above.** A space's lease pins its ranges while anything holds it. The pin waiter (`WaitForLeasesAndImports`, `GuestBufferMemory.cpp:2041`) drops only the address-space cache's own reference before it waits for batches. With the prototype, resource-cache entries hold spaces too, so a guest free or remap inside such a space waits on objects that leave only when the LRU evicts them. A real version must do one of two things:
   - let the waiter evict the resource-cache entries that hold the old space;
   - or make cached objects hold the space weakly and re-acquire it on reuse. The `SpaceCurrent` check already rejects a stale space, so a weak reference would only add the re-acquire.
2. **Mirrored and copied spaces are simply excluded.** On a hit, `AcquireRegistered` (`GuestBufferMemory.cpp:2675`) refreshes sparse mirrors, compares writable mirrors per build and re-adds copied ranges; a reuse would skip all of that. A title whose space has a heap or sparse mirror gets no reuse at all until that refresh moves into `Revalidate`. Such mirrors come from non-importable memory, or from NVIDIA's host-import budget.
3. **GPU writes still in flight.** The snapshot `memcmp` reads guest memory on the CPU and does not flush first. So a GPU write still pending over a snapshot range, such as a dispatch writing an SRT or a descriptor table, can be missed: `Revalidate` completes pending writes only over `directRegions`, described ranges and storage images. The dispatch cache validates the captured memory earlier and does handle pending writes, so this is probably covered in practice. The prototype does not prove it.
4. **The fault buffer and BDA tables are reused as built.** The table changes only with the space, which the generation and epoch checks pin. The fault buffer is reused across dispatches; whether fault reporting stays per dispatch (reset and read-back) was not checked.
5. **Import recency.** A build stamps `lastUse` on the space's imports, and a reuse does not. Under the host-import budget, an import that only cached objects use can then be retired. The epoch check catches that and the object is rebuilt, so it costs churn rather than correctness.
6. **Pending images and unit shadows.** `Revalidate`'s existing step covers these: `DirectRegions` returns the space's base regions, so pending storage-image results over them are flushed before a reuse. That was not tested beyond the harness.
7. **Draws are out of scope.** The switch applies only to compute objects; address-based draw resources stay non-reusable.

Also not covered:
- the `APS5_VERIFY_*` proofs;
- the indirect path (`DispatchIndirect`);
- a changed word inside a snapshot range, which should rebuild and was not timed.

## 5. What else this found

- **The lookup log bound (1,024 records).** It turns every resource object with more than about 1,000 texture lookups into a full `Revalidate` walk. Raising the bound took (A) at 2,000 textures from 4.1 to 0.68 ms per dispatch, a 6× change on main without the prototype. A real fix should size the log to the build's texture count rather than raise a constant. Records cost memory per object; that cost was not measured.
- **The image-table capacity.** On lavapipe it makes every rebuilt address-based dispatch cost 16–106 ms (§2). Any lavapipe timing of a title with address-based programs on main is dominated by it.
