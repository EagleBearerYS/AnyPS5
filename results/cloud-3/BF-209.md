### Can a label deferred on one queue's worker stay unrecorded while another queue's worker waits on it?

**Yes, by design, until the producer's own thread reaches a record point.**

**It is invisible to other queues until recorded:**
- `Graphics/include/Recorder.hpp:350-353`: "only a lookup made on the noting thread … takes its value; … other queues and the CPU see it once it is recorded";
- `Recorder::lookupLabel`, `Graphics/src/Recorder.cpp:3443-3453`: a queued entry is used only when `own->second.queue == tag`, and a recorded entry without a batch only for its own queue;
- `storedSince` (`src/Driver/Synchronization/LabelHistory.cpp`) only sees `noteLabelStore`, which a deferred label reaches in `recordDeferredLabels` (`DeferredLabels.cpp:130`).

**The waiter cannot record it for the producer:** everything that records on the waiting side acts on the calling thread's list only:
- `labelFlushDue` → `recordQueuedLabelsByTry` (`DeferredLabels.cpp:73-77`, `:202-212`), called from the wait loop (`src/Driver/Synchronization/WaitMemory.cpp:242`);
- the flush hook (`Graphics/src/Recorder.cpp:1026-1032`, with per-thread `QueuedLabelRanges`, `:549-553`).

**Where the producer's thread records:**

| Record point | Lines | How |
|---|---|---|
| Before its next non-label packet | `PacketExecution.cpp:330` → `PacketFlush.cpp:30-80` | a `try_lock`; outright once overdue |
| At the end of its submission | `PacketExecution.cpp:582-595` | outright. Queue 0 is the exception: with more submissions queued it skips (`:584-587`, `++costs.endSkipped`) and carries the list into its next submission. A queue 0x20-0x57 worker never carries one past a submission end. |
| At a suspend | `PacketExecution.cpp:182-191` | outright |
| At a flip | `PacketExecution.cpp:404` | outright |
| At a drain | `PacketMemory.cpp:250` | outright |
| At an end-of-pipe-interrupt label | `PacketMemory.cpp:40` | outright |
| At an immediate label | `PacketMemory.cpp:94` | outright |
| At a copy behind a pending source | `PacketMemory.cpp:132` | outright |
| Inside its own `WAIT_REG_MEM` | `WaitMemory.cpp:242` → `DeferredLabels.cpp:74` | a `try_lock` on every poll; no outright fallback anywhere in `waitMemory` |

**So a label stays unrecorded for long only if** its producer stops reaching these points, or every `try_lock` it makes inside its own wait fails.

### Is there a path where the producer's worker is itself blocked on the parked queue?

**I found no concrete one.**

- **Queue 0 as the producer.** This is the only queue that carries deferred labels across submissions (`PacketExecution.cpp:584`).
  - If its next submission waits on a label that the parked queue 0x20 writes after its own wait, queue 0 is blocked on the parked queue.
  - But it is blocked inside `waitMemory`, which tries a record on every poll (`WaitMemory.cpp:242`).
  - The parked 0x20 waiter does not hold the GPU mutex while it waits. Its entry and its polls both use `try_lock` by default (`WaitMemory.cpp:196`, `:209-218`, `:261`).
  - So queue 0 records the label as soon as one try succeeds. The label then enters the history with a stamp after 0x20's submission, and `storedSince` ends 0x20's wait (`WaitMemory.cpp:340-343`).
  - A hang needs every try to fail for the whole 120 s. I found no lock holder that would make that happen.
- **A queue 0x20-0x57 producer.** Its deferred labels are always recorded at its submission end (`PacketExecution.cpp:582-595`). It can only hold them inside a submission, for example in a later `WAIT_REG_MEM` of the same submission. That is the same try-per-poll case.
- **The order wait** (`QueueWorker.cpp:246-258`) parks a queue 0x20-0x57 submission behind queue 0 without recording anything. But:
  - It applies only to submissions with no wait packets, flips or rendering waits (`Submission.cpp:518-526`).
  - The worker's list is empty there, because it was recorded at that worker's previous submission end.
  - A producer whose `RELEASE_MEM` sits in such a submission has not executed it, so the label is unexecuted, not deferred.
  - The cycle "queue 0 waits on 0x20, 0x20 waits on that producer, the producer waits on queue 0" is broken by `orderReleased` (`Submission.cpp:540-546`). Line `:544` does not fire, since queue 0 awaits a dword the parked queue writes, not the producer. Line `:545` releases once no worker is running (both waiters stop counting as running, `Submission.cpp:556-566`), no completions are pending, and the awaited dword is not in the recorder snapshot.
- **So, per the task, no harness case was written** and no `test/6558-cross-queue-label` branch was created.
- **What Part 1's line would show.** A wait still parked at 120 s with the producer's store of 1 missing from "stores newest first" means the producer never recorded, or never executed, the `RELEASE_MEM` before the timeout. A store of 1 listed with a stamp below the submission stamp, next to `checked at submission: value 0x<another slot>`, means the 1 landed and was overwritten before the wait's submission.

### What each switch turns off

- **`APS5_LABEL_LOCK_EACH`** makes `DeferLabels()` false (`DeferredLabels.cpp:23`).
  - Turns off: the per-thread deferral and pipelined labels.
    - Every `RELEASE_MEM`/`WRITE_DATA` label without an end-of-pipe interrupt is written at its own packet, under the GPU mutex, and noted at once (`PacketMemory.cpp:89-106`).
    - Queue 0's label packets no longer go to the draw-pipeline committer, because `labelPacketQueues` returns false (`PacketMemory.cpp:384-389`).
  - Keeps: GPU-recorded stores, completion-gated stores (reason 5), and the GPU paths for DMA_DATA/WRITE_DATA.
- **`APS5_DRAIN_COMPLETION_LABELS`** does the same as `APS5_LABEL_LOCK_EACH` (`DeferredLabels.cpp:23`), and more.
  - Turns off, additionally: the completion-gated stores. `WriteLabelOnGpu` returns 2 instead of 5 for a label behind a copied writer or a pending completion store (`src/VulkanDevice.cpp:2444`, `:2479-2480`, `:2501`). That packet then drains the device and stores on the CPU (`PacketMemory.cpp:228-253`, then the packet's own CPU execution).
- **`APS5_NO_QUEUED_LABELS`** makes `QueuedLabelTable()` false (`DeferredLabels.cpp:28`). Deferral stays on, but:
  - queued labels are not noted in the recorder's table (`PacketFlush.cpp:17-18`), so there are no same-queue hits on unrecorded labels;
  - waits no longer try-record them (`DeferredLabels.cpp:74`);
  - a worker records outright before any packet `NeedsRecordedLabels` covers (`PacketFlush.cpp:34`, `:64`, `:73-74`), `WAIT_REG_MEM` included.

  It turns the try-before-a-wait into an outright record.
- **`APS5_DRAIN_ALL`** goes beyond all three.
  - At `PacketMemory.cpp:23` it turns off:
    - the GPU path for end-of-pipe-interrupt labels (`:32`);
    - deferral and GPU writes for every label (`:76`);
    - GPU stores for WRITE_DATA, DMA_DATA and 0x83 (`:117`);
    - GPU sample dumps (`:212`).
  - It makes every memory-accessing packet, plus 0x42, 0x46, 0x58 and flips, drain and run on the CPU (`:228-253`). The drain records queued labels and waits for the device idle under the GPU mutex, with the unlocked drain off (`:232`).
  - At `Draw/DrawPipeline.cpp:251` it sets queue 0's draw-pipeline depth to 0. So there is no committer thread: no pipelined draws, no committer-run labels, and no `DrawFinisher`-held labels.
- **How to read the three arms:**
  - **If one of the three removes the timeouts,** the cause is in what it changes:
    - the deferral and pipelined labels (`LABEL_LOCK_EACH`);
    - plus the completion-gated stores (only `DRAIN_COMPLETION_LABELS`);
    - the try-only record before waits (`NO_QUEUED_LABELS`).
  - **If none does but `DRAIN_ALL` still does,** the cause is in what only `DRAIN_ALL` changes. Narrower arms for that case:
    - `APS5_CPU_STORES=1` takes only the DMA_DATA/WRITE_DATA GPU stores off (`PacketMemory.cpp:116-117`);
    - `APS5_PIPELINED_DRAWS=0` takes only the queue-0 draw pipeline off (`DrawPipeline.cpp:250-254`).
