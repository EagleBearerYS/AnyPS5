### What I read for the replacement, and why none of it looks wrong

Lines are at 3b5c3e16fd; Resources.cpp and BufferPool.cpp are the same at both commits.

- `PerformanceOverlay.cpp:731-736`:
  - `slot.rects` is replaced by `std::make_unique<Graphics::Buffer>(context, capacity * sizeof(OverlayRect), VK_BUFFER_USAGE_VERTEX_BUFFER_BIT)` before the old one is released.
  - The `memcpy` then writes `rects.size() * 20` bytes through the new buffer's `Bytes()`.
  - `:781-782` binds `slot.rects->Handle()` at offset 0 and draws 4 vertices × `rects.size()` instances.
  - The binding is per-instance with stride 20 (`:667`), and the attributes R32G32B32A32_SINT @0 and R32_UINT @16 match the shader's `ivec4 area` / `uint color`.
- `Resources.cpp:40-107`, `Buffer::Buffer` with the default HOST_VISIBLE | HOST_COHERENT:
  - 30,360 bytes falls in size class 32,768 (`BufferPool::Capacity`, BufferPool.cpp:194-201), the same class as the 20,480-byte first buffer.
  - The pool's `Take` (BufferPool.cpp:216-244) misses: the key includes usage, no VERTEX_BUFFER allocation of that class has been released yet, and the old buffer is released only after the new one exists. So it takes the slab path (Resources.cpp:84-96).
  - The slab path makes a VkBuffer of exactly `size`, binds it at the slot's offset in a 2 MiB block (`TakeSlot`, BufferPool.cpp:83-125, slot index × 32,768), and maps it at `block.mapping + offset` (:91).
  - So `Handle()` is a buffer whose memory already starts at the slot, binding offset 0 is right, and `Bytes()` (Resources.cpp:132-135) is `{mapping, size}` over exactly that range.
- `BindExactBuffer` (Resources.cpp:18-36) runs only on a pool hit with a different exact size. It checks the size and alignment against the retained allocation, and binds at the same `offset`.
- Memory: `Context::BufferMemoryType` (Context.hpp:260-285) prefers HOST_CACHED, but only among HOST_COHERENT types. So no flush is needed, and none is missing. On RADV every host-visible type is coherent anyway.
- RADV-specific candidates I checked against this code:
  - **Instance count:** a plain `vkCmdDraw` with 1,518 instances, nothing near a limit.
  - **Buffer size:** exactly `rects.size() × stride`; per-instance fetch never reads past it.
  - **Alignment:** slab slots are 32 KiB apart, and `SlabEligible` (BufferPool.cpp:68-73) requires the buffer's alignment to divide the slot.
  - **Pipeline:** keyed by format and the same for every case.
- I found nothing on this path that RADV would treat differently from lavapipe, so I report no cause.

### The failing pixel's value

- The reviewer quoted the message without its number. That number would say what was drawn at 'P' (0,0).
- `requireTextDrawn` prints it as `"0x" + std::to_string(word)` (tests/PerformanceOverlay.cpp:277), so the digits after "0x" are **decimal**.
- With the full panel's clear colour (0.75, 0.5, 0.25, 1) in B8G8R8A8_UNORM:
  - **≈ 4283183898 (0xFF4C331A, the panel over the frame, ±1 per channel):** the text rect was not drawn there.
  - **4294967295 (0xFFFFFFFF):** it was white after all.
  - **Anything else, for example a green from the graph colour:** rects landed in the wrong place.
