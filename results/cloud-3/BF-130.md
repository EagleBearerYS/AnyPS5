## 1. The query and the known values

```cpp
enum class MultisampleColorContent { Unknown, Fill, FastClear, Clear, Drawn };
struct MultisampleColorAlias {
    std::uint64_t address = 0;    // the colour target's guarded footprint
    std::uint64_t bytes = 0;      //   (the same rule as guard(), now guardedColorBytes)
    VkFormat format = VK_FORMAT_UNDEFINED;
    std::uint32_t samples = 0;
    MultisampleColorContent newest = MultisampleColorContent::Unknown;
    std::optional<VkClearColorValue> value;  // the known uniform value
    std::optional<std::uint8_t> byte;        // that value as an R8 UNORM/UINT texel
};
std::optional<MultisampleColorAlias> MultisampleColorTargetOver(std::uint64_t address, std::size_t bytes);
```

(The comments above are for this note; the code has none.)

- **What it does:** returns the first active colour target whose guarded range (colour, DCC or CMASK) overlaps the range, and never throws.
- **Locking:** it takes `targetsMutex` and then `guardedMutex` shared, the same order as `acquire`. It is called with `surfacesMutex` held, and nothing takes `surfacesMutex` while holding `targetsMutex`.

**Newest content, in the order `TakeMultisampledClear` applies it:**
- **Unknown:**
  - a CMASK, colour-fill or HTILE refusal is pending;
  - a DCC/CMASK metadata fill is pending on a DCC target;
  - nothing proven was ever recorded. A target created by a draw is host-cleared to zero, which is not a guest value.
- **FastClear:** the CMASK keys are a pending Clear0000. The value is `fastClearColor(target)`, from the target's stored `CB_COLOR_CLEAR_WORD` pair. Caveat: that is the pair from its last acquire, not necessarily the register when the guest cleared.
- **Fill:** `MultisampledColorFill` holds an absorbed fill not yet applied (`Pending()`), and the pattern is exact in the format (`MultisampledFillClearColor`).
- **Drawn:** the target was drawn into since its last recorded clear. "Drawn" here means:
  - `MultisampleTargetView` (both overloads; the draw path takes the attachment view through them);
  - `MultisampleTargetOrderTarget`;
  - a storage write (`Storage`).
- **Clear:** the value of the last clear the target recorded with no draw since. That is:
  - `ApplyFastClear` applying a CMASK clear, an absorbed fill or a DCC refill;
  - a DCC target's initial or recreated clear, proven from its DCC keys.

**Import (`prepareDepthSampling`), before any flush or read:** every initial range (depth, HTILE, stencil plane) is queried.
- The stencil plane takes `alias.byte` when all of these hold:
  - the alias is R8_UNORM or R8_UINT, with the depth's sample count;
  - it covers exactly the plane's address and size;
  - its newest content is Fill, FastClear or Clear.
- The first host clear uses that byte as the stencil, in place of `DB_STENCIL_CLEAR`. The guest plane is not read.
- Anything else refuses with one of two texts:
  - `native multisample stencil plane aliases a multisampled colour target whose samples are only on the host`;
  - `native multisample depth or HTILE aliases a multisampled colour target whose samples are only on the host`.
- It also prints, at most 8 times:
  `[gpu] native multisample <plane> <range> aliases multisampled colour target <range> (vk format N, S samples), newest <fill|CMASK fast clear|clear 0xVV|drawn|unknown>`.

**`CheckCurrent`:** the same query runs for each range on every call.
- **Plane fill over an aliased plane:** proven when the alias's byte equals the fill byte. That replaces the tracked-store and byte checks, so the plane is never read.
- **No plane fill:** the alias must still hold the byte last taken. A colour draw, a changed value, or an alias that appeared after the import refuses with the stencil text.
- **Other guest-byte reads:** the only other read there is HTILE's (`std::memcpy` at the clear proof), and an aliased HTILE is refused before it.

**Regression `--aliased-stencil`:** 4 samples on lavapipe, on a 5x3 target whose guest plane bytes are 0xa5.
- **Cleared:** a 4-sample R8_UNORM target over the plane is created by a draw, then absorbs a fill of 0x5a (`MultisampledColorFillAbsorbs`, `NoteDepthMetadataFill`, `NoteColorMetadataFill`, as `BufferFill` does).
  - The D32S8 import samples.
  - A stencil EQUAL 0x5b draw misses and EQUAL 0x5a hits.
  - A second absorbed fill of 0x33 is proven from the colour target: EQUAL 0x5a then misses and EQUAL 0x33 hits.
  - A colour draw after that refuses the next sample.
  - The guest plane still holds 0xa5.
- **Drawn after its clear:** refused with the stencil text.
- **R8G8 target over the plane:** refused with the stencil text.
- **Another colour sample count:** refused (this needs 2 or 8 samples, which lavapipe lacks, so it did not run here).
- **No guarded read:** in all three refusal cases the message is the new reason, not the guard text.

## 2. DB_RENDER_CONTROL and the gate

**Where the driver decodes DB_RENDER_CONTROL (context register 0x000) on 5daa8cb7a9:**
- `State.cpp` `decodeDepth`:
  - `:356` refuses bits 0x101c (copy, resummarize, decompress);
  - `:357-358` take bits 0 and 1 as clears;
  - `:385` counts bits 5 and 6 as depth writes.
- `:1271-1272` and `:1476` read the clear bits.
- `DepthMaintenanceRejection` (`:1148`) lets bits 0x2fe3 through.
- An in-place expand has no depth test and no colour writes, so `DrawPrecheck.cpp` returned `DrawVerdict::Nothing` for it before `DecodeState` ran. It never reached `DepthSurfaceView`.

**What the commit adds:**
- **Decoder:** `DecodeDepthRenderControl(queue)` (`State.cpp:1158`) returns `{DB_Z_READ_BASE | HI << 40, masked to 64 KiB; samples from DB_Z_INFO[3:2]; DB_RENDER_CONTROL}`. It does so for a draw with a depth format and any of bits 0x63.
- **Precheck hook** (`DrawPrecheck.cpp:40`, before the resummarize and "draws nothing" exits):
  - for an expand, or a clear over an existing depth surface, it drains the draw pipeline;
  - it then calls `NoteDepthRenderControl` (`DepthSurface.cpp:2548`).
- **Marking a native multisample surface at that address and sample count:**
  - `control & 0x40` (DEPTH_COMPRESS_DISABLE) together with `control & 0x20` (STENCIL_COMPRESS_DISABLE) sets `expanded`. When the target has no stencil plane (D16, D32), `0x40` alone is enough.
  - Otherwise, `control & 0x3` (a clear draw) clears it.
  - The bits are Mesa's `S_028000_STENCIL_COMPRESS_DISABLE` (5) and `S_028000_DEPTH_COMPRESS_DISABLE` (6). radeonsi sets them for an in-place decompress (`db_flush_depth_inplace` / `db_flush_stencil_inplace`).
- **Also clearing the mark:**
  - `NoteDepthMetadataFill` over the surface's depth, HTILE or stencil plane;
  - `NoteHtileDepthClear` over its HTILE;
  - `DepthSurfaceView` when it takes a cleared HTILE.
- **Gate:** `CheckResource` (`DepthSurface.cpp:485`) accepts a descriptor with no metadata (META_DATA_ADDRESS 0, not pipe-aligned) only while `expanded` holds. Otherwise it refuses with the old text, `native multisample depth sampled metadata or XOR mismatch`. It prints at most 8 lines with the last DB_RENDER_CONTROL it saw, so a tester's log shows whether the title expanded and with which bits.
- **Choice:** a D32S8 target needs both bits, even with a depth-only HTILE whose stencil is never compressed. That is the task's wording, and the stricter reading. If The Grinch sets only bit 6, the refusal comes back with that evidence in the log rather than a guess.
- **Gap, also in the debt sentence:** a later depth write without the bits recompresses tiles on hardware, and that is not observed.

**Regression `--expand-gate`:** 4 samples, D32 and D32S8 with a separate plane.
- A bare sample before any expand is refused.
- On D32S8, a draw with only bit 6 is refused too.
- After the expand draw, the bare view samples the cleared depth and then a drawn one.
- Each of these refuses it again until the next expand:
  - an HTILE fill;
  - a clear draw (bit 0);
  - a plane fill (D32S8) or an HTILE mask clear (D32).

## Notes for the PR Manager

- **Ghost:** with these commits, the tester's run should either import or print one `[gpu] native multisample stencil plane ... aliases multisampled colour target ...` line.
  - It imports when the R8 target's newest content is a fill, CMASK clear or recorded clear with no draw since.
  - The printed line says which state the colour target was in. "drawn" means the copy in the new debt entry is the next step.
- **The Grinch:** the bare descriptor now needs an expand draw first. If it is refused, the `[gpu] ... before an in-place expand (last DB_RENDER_CONTROL 0x...)` line shows what the title sent: no expand, only bit 6, or a clear afterwards.
- **CMASK fast-clear value:** it comes from the colour target's stored clear words, taken at its last acquire.
- **Draw-pipeline drain:** an expand draw always drains the draw pipeline. A clear draw drains it only when a depth surface exists at its address. Both are rare: expands are per pass, and native depth clear draws are few.
