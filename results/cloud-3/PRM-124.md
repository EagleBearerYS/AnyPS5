## 4. Why the case runs here (step 4's question, answered for Linux)

**The tracker side** (`Execution/src/GuestMemory.cpp`). The tracker's `initialize()` (~:1126-1141), on non-Windows, sets `watched = GuestWriteWatch::GuestWriteWatchAvailable_nid_postfix()`, and `WriteWatched()` (~:2139) returns it.

**The libc side** (`core/libs/prx/libc/src/GuestWriteWatch.cpp`). The watch is compiled only when the headers define `PAGEMAP_SCAN` and `UFFD_FEATURE_WP_ASYNC`. On Linux these need kernel 6.7 or later, and both are defined here. `Watch::open()` (~:215-230) then needs, at runtime:
1. **`userfaultfd`.** If plain `userfaultfd` gets `EPERM`, as it does for an unprivileged user with `vm.unprivileged_userfaultfd = 0`, the code retries with `UFFD_USER_MODE_ONLY`.
2. **Async write protection:** `UFFDIO_API` reporting both `UFFD_FEATURE_WP_ASYNC` and `UFFD_FEATURE_WP_UNPOPULATED`.
3. **`/proc/self/pagemap`**, readable.
4. **A working `PAGEMAP_SCAN` probe.**

Each failure prints `[memory] write watch unavailable: <what> failed (…)`. `APS5_NO_WRITE_WATCH` turns the watch off.

**This machine has all four.** A standalone probe, run as `runner`, gave:
```
userfaultfd(): -1 errno=Operation not permitted
userfaultfd(UFFD_USER_MODE_ONLY): 3 errno=-
UFFDIO_API: 0 features=0x1ffff wp_async=1 wp_unpopulated=1
pagemap open: 4
```
The tests printed no "write watch unavailable" line, so the `PAGEMAP_SCAN` probe passed too.

## 5. One difference between the Linux run and the reported failure

`NewWatchedBlock` (`DepthExpandOutOfPlace.cpp` ~:129-141) is what the case allocates through while `WatchedBlocks` is true. Its read base, write base and copy blocks therefore come from different mechanisms on each OS:

| | Linux (this run) | Windows (the report) |
|---|---|---|
| allocation | `mmap` | `GuestArena::GuestArenaAllocate_nid_postfix` + `GuestArenaCommit_nid_postfix` |
| write watch | `GuestWriteWatch::GuestWriteWatchRegister_nid_postfix` (userfaultfd WP + `PAGEMAP_SCAN`) | the guest arena's own write watch (`GuestArenaWriteWatched`) |

So the Linux runs exercise the case's logic, the split ranges, one import and one heap mirror, under a different watch and allocator. They say nothing about the Windows arena path or the AMD driver. That is a statement of what was covered, not a diagnosis of the Windows failure.
