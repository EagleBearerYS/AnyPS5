## 0. Bottom line

**§1, the Windows re-watch.**
- Feasible with existing primitives: reset the range's OS write-watch bits, restore its coverage, and stamp its blocks "possibly written" (`ImportWindow`), all under the tracker lock.
- It must wait until the import's memory is **freed**, after the recorder's hold, not just retired. It must skip ranges a live import has taken since.
- Cost: nothing per build; one reset walk and one re-read of the range per freed un-watching import.
- About 100 lines with a Linux test. I didn't build it: the part that matters is Windows-only and can't be compiled or run here, it has to share #4448's `GuestMemory::Rewatch`, and the storage-image transition needs its owner's review.
- **Rank: keep eviction (PM-024) first, re-watch second. Both are needed** (§1.7).

**§2, eviction in the normal case.**
- **Why `evict = false`:** no reason is given anywhere. The build's own lookups are already excluded from eviction (`pointerHeld`), and PM-024 relies on that.
- **Who gets evicted (Village-like budget):** PM-024's rule frees 8 MiB, taking the least recently used imports this build hasn't touched: windows, and imports of ranges after the heap in address order.
- **Their cost next time:** those ranges get mirrors; windows are re-imported.
- **Thrash:** none in the expected pattern. One residual risk: the heap's own import goes idle when more than 256 lookups (fills, labels) happen between two address-based builds.
- **Per-build cost of a 768 MiB heap** (Linux, mock device):
  - **mirrored**: about 0.2 ms per collect epoch with nothing dirty, about 1.3 ms with about 200 dirty 64 KiB blocks per epoch, and about 3.5 µs on later builds of the epoch;
  - **imported**: about 0.3 to 0.7 µs per build.
- **PC experiment:** `APS5_HOST_IMPORT_MIB=6864` with `APS5_PROFILE_DRAW=1`. The lines to read are in §2.4.

## 1. Option 2: re-watch on Windows when an import is freed

### 1.1 How the Windows watch works

- **The OS tracks writes all the time.** Private guest memory is committed with `MEM_WRITE_WATCH` (`core/libs/prx/libc/include/WindowsMappings.hpp:53`). Its writes are read with `GetWriteWatch`, which also resets them when collecting (`WRITE_WATCH_FLAG_RESET`, WindowsMappings.hpp:458; resident runs at 557/563). There is no per-range "arming" to redo.
- **"Watched" is a software notion in the driver.** `WriteWatchCoverage` (`Execution/include/WriteWatchCoverage.hpp`):
  - `Exclude` (29-49) stops trusting 64 KiB blocks, rounding outward;
  - `Restore` (51-71) trusts them again. It takes only blocks fully inside the range (61-63), and only blocks excluded before the given generation.
- **An import that doesn't stay watched excludes its blocks** (`Execution/src/GuestMemory.cpp:1309-1313`, via `unwatchLocked` at 1240-1248) and starts hints for them (`startHints`, 847-858).
- **Excluded blocks are still read, as hints.** `walkHints` (1519-1533) collects their OS bits with reset into `hintBlocks`, and `UntrackedHint` (1538ff) lets storage images and snapshots compare bytes after a mark.
- **Why the watch can't be trusted while imported.** GPU or driver writes through an import don't pass through the CPU page tables, so `GetWriteWatch` misses them. The driver can also mark imported pages dirty after the import (debt L58).
- **Once the import's memory is freed, neither can happen.** But nothing restores the blocks:
  - `retireImport` (main:230-242) and `~RetiredImport` (main:212-219, `vkFreeMemory` at 215) never touch the watch;
  - `coverage.Restore` runs only in `watchPrivateMapping` (GuestMemory.cpp:1030-1042), for mappings a fresh `GuestArenaCommit` creates (`core/libs/prx/libc/src/GuestArena.cpp:390-397`);
  - debt L58 says so: "restoring tracking on import retirement without replacing the backing remains unimplemented".

### 1.2 The sequence

1. **Retire (unchanged).** `retireImport` keeps the import alive through the recorder's hold (main:240).
2. **Free.** In `~RetiredImport`, after `freeMemory` (main:215), if the entry was `unwatched` (set at main:1055), push `{base, bytes}` onto a small freed-range list.
   - The list has its own mutex, not the import lock. Without a recorder, the destructor runs inside `retireImport` under the import lock (main:239); otherwise it runs from a completion.
3. **Drain.** At the top of `refreshImports` (main:1106, before its early return at 1132), which every import path calls under the import lock. For each freed range:
   - skip it if a live import overlaps it (a new import of the range may exist by now; its own free will re-watch later);
   - skip it if the range is no longer registered (a fresh commit restores coverage by itself);
   - otherwise call `GuestMemory::Rewatch(base, bytes)`.
4. **`Rewatch` on Windows, under the tracker lock:**
   - a. Reset the range's OS bits: `walkHints(tracker, first, stop)`. That's `GuestArenaCollectWrites` with clear, i.e. `WindowsMappings::Collect` (WindowsMappings.hpp:317) and `GetWriteWatch(WRITE_WATCH_FLAG_RESET)` (458).
   - b. `tracker.coverage.Restore(address, bytes)`. If it changed nothing, stop here: the range is already watched, for instance after #4448's re-watch.
   - c. `++tracker.generation`, and stamp every restored block `StampKind::ImportWindow` (GuestMemory.cpp:736). **Not `Cpu`.** A `Cpu` stamp tells storage images with pending results that the CPU stored over them (debt L57), and they would drop those results. "Possibly written" makes them compare once instead. #4448 stamps the same on Linux.
   - d. `unwatchSerial.fetch_add(1)`. This invalidates collect memos and PM-024's `heapMirrorWatched` serial check.
5. **Why the order is safe.**
   - A CPU store before (a) loses its OS bit, but (c) stamps its block, so consumers re-read it.
   - A store after (a) is recorded, and the next collect sees it.
   - Collects take the same lock, so they never see a half-done re-watch.
6. **Mirror generations.**
   - An existing heap mirror refreshes the blocks whose tracker stamp is newer than its own `generations` (`appendChangedBlocks`, `GuestMemory::ChangedBlocks`). Every restored block qualifies, so it compares and copies them once.
   - A new heap mirror reads the whole range when it is made (main:1772-1786), and `CollectWrites` now covers the range.
   - So nothing stale is served.

### 1.3 Cost

- **Per freed un-watching import:**
  - a list push;
  - at the next `refreshImports`, an overlap check (logarithmic) and one `Rewatch`:
    - an OS reset walk over the range (`GetWriteWatch` with reset over 196,608 pages for 768 MiB; kernel time, not measurable here);
    - 12,288 block stamps;
    - one compare or copy of the restored blocks by each consumer: a full compare for an existing heap mirror, or the creation read for a new one (about 0.5 s for 768 MiB, §2.3).
- **Per build:** an empty-list check in `refreshImports`.

### 1.4 Risks

| Risk | Answer |
|---|---|
| The GPU still writing through the import | Re-watch only after the free, i.e. after the hold ended (main:240). A retire alone isn't enough: evictions and replacements retire imports that in-flight batches still use. |
| CPU stores in the gap | Covered by reset-then-stamp under the tracker lock (§1.2, step 5). |
| A new import of the range between free and drain | The drain skips ranges a live import overlaps. |
| The driver marking pages after the free (unpinning) | False positives only: extra compares. |
| Pending storage-image results over the range (debt L57) | The `ImportWindow` stamp makes them compare once (#4448's design for Linux). Needs review by that path's owner. **This is the main soundness risk.** |
| A 64 KiB block shared with a neighbouring import | `Restore` takes only blocks fully inside the range (WriteWatchCoverage.hpp:61-63), and live imports never overlap (`importRunAt` retires overlaps before inserting, main:977-981). A shared edge block stays excluded, which is conservative. |
| #6060 | With settled watched imports, `entry.unwatched` is false and nothing is queued: zero cost. |
| #4448 | It adds a Linux `GuestMemory::Rewatch` with the same name. The Windows branch belongs in that function. Its trigger (`RetireIdleImports`: unwatched imports idle 60 frames whose writes are settled) and this free trigger can coexist. Step 4b makes a second re-watch of an already-watched range a no-op. |

### 1.5 What else the PM asked about

- **"Windows can't re-arm a write watch on part of an allocation without a reset."** Right. And no arming is needed, because the OS never stops tracking. What's needed is the reset (step a) plus treating the blocks as changed once (step c).
- **Mirror generations:** step 6.

### 1.7 Ranked against eviction (PM-024)

1. **Eviction first** (in place on `test/address-copy-cap-fix`):
   - it prevents the abort whatever took the heap off the watch: a window import, a live window, a failed collect in `MarkWritten` (GuestMemory.cpp:1446-1447), a failed import walk (1315);
   - it's platform-neutral, tested, and costs about 0 normally;
   - it also lets a big heap be **imported**, which §2.3 shows is cheaper per build than mirroring it.
2. **Re-watch second.** It removes the Windows root cause, so a heap becomes mirrorable again once a stray window import is freed. It also covers the case eviction can't: nothing evictable, where the abort is otherwise the backstop.

**Both are needed.**
- Re-watch alone doesn't help while the un-watching window is still live at the build: the window is either refused as held, or counted as replaced and the import usually fits. And until the free, it can't act at all.
- Eviction alone leaves the heap unmirrorable for the session. On Windows, a whole-range import un-watches the whole heap too, so once its import is evicted the heap can only come back by eviction.

## 2. What eviction does to the normal case

### 2.1 Why the pass uses `evict = false`

- **Who introduced it.** e9249a0a4 (PR #290, 2026-10-12). It added eviction itself and opted out map-time imports (with a reason, "the map observer holds no GPU lock") and `AcquireRegistered` (no reason). The PR's other commits (c871b5893, c29e06c69) and debt L140 say nothing more. No test pins it.
- **Does eviction there drop imports the same build already looked up? No: they are already excluded.**
  - `evictable` (main:810-813) requires `!pointerHeld`, and `pointerHeld` (main:806-808) is `lastUse >= buildFloor`.
  - `buildFloor` is set when the build starts (main:2587-2588).
  - Every lookup stamps `lastUse = ++useCounter` (main:1162), every new import too (main:1092), and a cache hit stamps all its imports (main:2544-2546).
  - So everything the build has touched stays put. PM-024's last-resort eviction depends on exactly this; its tests evict an idle import the build hasn't looked up yet.
- **Caveat:** `buildFloor` is one global, but address-based builds run under the GPU lock (`Execution/src/Driver/Draw/Draw.cpp:394-399`; compute in `Complete()`).
- **The likely reason for the rule is stability across builds.** Unconditional eviction could rotate imports between builds (PM-024 §1). That's why PM-024 evicts only in a build that would otherwise abort.

### 2.2 A Village-like budget (5840 MiB budget, 5080 MiB live, one 768 MiB heap)

**When it fires.** With PM-024's rule, only in the build that would otherwise abort: the heap neither imported nor mirrored, and its copy past the cap.
- It needs 5080 + 768 − 5840 = **8 MiB**, after the heap's own windows count as replaced (main:954-962).
- In Village's logged refusal no window of the heap was live (PM-022 §1.1), so 8 MiB it is.

**Who gets pushed out.**
- `retireLeastRecent` (main:815-827, called at main:982) retires **whole imports, least recently used first**, until at least 8 MiB are freed.
- It picks only evictable ones: not used in the last 256 lookups, and not touched by this build.
- A pass walks the whole registry in address order (about 1,200 ranges per main:80), so the candidates are:
  - window imports made by fills, labels and copies;
  - the imports of ranges **after** the heap in address order (not yet looked up in this pass), if they're older than the last 256 lookups.
- It can free more than 8 MiB if the oldest candidate is large.
- With a hit-heavy address-space cache, a hit adds only 1 to the use counter (main:2544), while fills and labels add 1 per lookup. So which imports are older than 256 lookups depends on how many fills and labels run between builds.

**What they cost when next needed.**
- **An evicted range later in the same pass:** its import (without eviction) is refused, because the heap took the room. It then gets:
  - an **image mirror** (non-heap ranges: one read at creation; refreshed by compare if writable, main:55-60), or
  - a **heap mirror** (a watched heap).
  - Only an unmirrorable range is copied. If that copy would pass the cap, its own last resort can evict only imports not used yet, so it never cascades backwards.
- **An evicted window:** re-imported at its next fill, label or copy (`importAccess` evicts by default, main:1168), pushing out the next least recently used import. On Windows each such import takes its blocks off the watch again, which is the §1 problem.

**Does it thrash between builds? Not in the expected pattern.**
- After the one episode, the epoch moved (an eviction retires), so the next build runs the pass, finds the heap's import, stamps it and publishes the space.
- From then on every build stamps it: a pass at main:1162, a hit at main:2544-2546. The evicted ranges stay on their mirrors. Nothing is re-pinned per build.
- **Residual risk:** if more than 256 lookups (fills, labels) happen between two address-based builds, the heap's 768 MiB import becomes evictable, and a window import can push it out. The next build then evicts again to re-import it, a 768 MiB re-pin each time.
- **Raising the budget removes that risk** (§2.4).
- **Unconditional eviction** (PM-022's experiment A) would evict on every budget refusal. With the registered total over the budget, that rotates imports between builds.

### 2.3 Per-build cost: heap imported against heap mirrored

**Setup** (temporary `--heap-cost-bench` mode on the PM-024 branch, not committed):
- One registered, watched heap of **768 MiB**, `APS5_HEAP_MIRROR_MIB=24576`.
- Mirrored: the import budget set just below the heap. Imported: the default budget.
- A collect epoch is bumped every N builds.
- Before each build the CPU dirties D distinct 64 KiB blocks.
- 200 builds of `AcquireRegistered` + `Upload` + `WriteBack`, address-space cache on, Linux write watch, mock device, run as `runner`.

| heap | dirty blocks per build | epoch every | first build of an epoch, median (mean) | later builds, median | one-time first build |
|---|---|---|---|---|---|
| mirrored | 0 | 1 build | **205 µs** (212) | n/a | 0.51 s (creating the mirror reads 768 MiB) |
| imported | 0 | 1 build | **0.3 µs** | n/a | 4.0 s (see below) |
| mirrored | 4 | 1 build | **310 µs** (357) | n/a | 0.61 s |
| imported | 4 | 1 build | **0.4 µs** | n/a | 4.7 s |
| mirrored | 4 | 50 builds | **1.2 to 1.3 ms** (1.1 to 1.5) | **3.4 µs** | 0.49 to 0.53 s |
| imported | 4 | 50 builds | **0.4 µs** | **0.4 µs** | 5.4 s |
| mirrored | 64 | 50 builds | **8.1 ms** (6.6) | **3.5 µs** | 0.46 s |
| imported | 64 | 50 builds | **0.5 µs** | **0.7 µs** | 2.1 s |

**Reading it:**
- A mirrored heap pays, per collect epoch, a walk of the watch over the whole range (about 0.2 ms for 768 MiB here) plus a compare and copy of the blocks dirtied since the last epoch. Later builds of the epoch cost about 3.5 µs.
- An imported heap costs well under 1 µs per build, however dirty it is: zero copy.
- Both live in host memory (the mirror is a host-cached device buffer, main:55-60), so the GPU's access cost shouldn't differ.

**Per second:** cost ≈ collect epochs per second × (0.2 ms + dirty refresh). At 60 epochs a second that's about 12 to 80 ms of CPU per second for the mirror; the import costs nothing. Read the epoch rate from the `[guestmem]` line (§2.4).

**Caveats:**
- The one-time import of 2 to 5 s here is the Linux watched-import path. It saves the non-zero pages of the import window before importing (GuestMemory.cpp:1285-1298), and the bench fills the heap with non-zero bytes. A Windows direct import pins instead (not measured).
- These are Linux numbers. Windows walks `GetWriteWatch` over the range instead: same order expected, not measured.

**What it means for "cut #1".** If Village's heap is imported, its per-epoch walk and refresh disappear at the source. The ranges that eviction pushed out move to mirrors, but those are small idle ones.

**cloud-1's `--perdraw-bench`** (ce6959aba) models 383 heap runs of 128 KiB, mirrored only, with no import switch, on base 153d5d469. The focused bench above answers the imported-versus-mirrored question directly, so I didn't port it.

### 2.4 The PC experiment

**Setting:** `APS5_HOST_IMPORT_MIB=6864`, that is 5840 + 1024.
- It replaces the computed budget entirely (main:846-852), including its "largest host heap less 2 GiB" cap. That cap is what gave 5840 MiB on that PC (host heap about 7.7 GiB), so the reserve for type-3 mirrors, other host allocations and the hold's short double pins shrinks from about 2 GiB to about 1 GiB.

**Expected:**
- 5080 + 768 = 5848 ≤ 6864, so the heap is imported whole at its first address-based build, with no eviction.
- No refusal of 0x200200000+0x30000000, no heap mirror for it, and no abort, even on main.

**Lines to read:**
- `[gpu] host import budget: … refused so far, last …` (main:973): it should no longer name 0x200200000+0x30000000.
- With `APS5_TRACE_HOST_IMPORT=1`:
  - `[gpu] host import of 0x200200000+0x30000000 ok (… live, … MiB live, … MiB ever)` (main:1090), once;
  - `[gpu] host import of … retired: the range was mapped again` (main:1147), if it's dropped.
- `[gpu] host import of … failed at … falling back to copies` (main:1061): a pin failure, which is the risk of the smaller reserve. Also watch for Vulkan out-of-memory errors elsewhere.
- With `APS5_PROFILE_DRAW=1`, every 10 s:
  - `[address] N address-based builds (10 s), us per build: lease …, imports pass …, mirror prepare …, compare … (… blocks, … copied), …` (main:2500). "Mirror prepare" and "compare" are the heap mirror's per-build cost and should fall.
  - `[buffers] image mirrors: … (…, N heap X MiB), …, unwatched heaps U, M heap mirrors released for imports (Y MiB)` (main:1877). Heap MiB should drop by 768. If the heap was mirrored before the import fitted, "released for imports" counts it.
  - `[guestmem] … collect epochs E` (GuestMemory.cpp:319): epochs per 10 s, to turn the per-epoch costs of §2.3 into per-second costs.
- `[write-watch] Windows direct host imports use comparisons; …` (main:648): confirms that imports un-watch on that machine. It doesn't matter while the heap stays imported.

**Also switch on:**
- `APS5_PROFILE_DRAW=1` in **both** runs: a baseline at the default budget (preferably one that mirrors the heap) and the raised run, same scene and duration, so the `[address]` and `[guestmem]` lines compare.
- `APS5_TRACE_HOST_IMPORT=1` only in the raised run; it's verbose.
- Leave `APS5_ADDRESS_COPY_MAX_MIB` at its default.
- On PM-024's branch, a default-budget run may also print `[gpu] host import budget: 0x200200000+0x30000000 imported by evicting idle imports, as copying it would pass APS5_ADDRESS_COPY_MAX_MIB` (branch:2683) when eviction fires.
