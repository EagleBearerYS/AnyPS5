## 1. GPU time of EASU and RCAS

**Commit:** fork `feat/agc-fsr1-upscaling-cost` **30febcf78**, `test(agc): measure the GPU time of FSR's EASU and RCAS passes`, one commit on 3de3afd214, pushed.

`agc_driver_presentation_pass_tests --fsr-cost` is not registered with ctest. Registration still reports "933 test executable(s), 0 built and not run as recorded, none new", because the mode lives in an executable that is already registered.

**What one frame records**, all through the production calls, into B8G8R8A8_UNORM images, with a timestamp after each part (BOTTOM_OF_PIPE):
1. **The stage write:** `RecordStageTransferDestination` + `PresentationScaler::RecordStretchFrom` + `RecordStageWritten`, as `present()`'s direct path does it.
2. **`RecordPresent`, exactly as presented:** EASU then RCAS when upscaling, RCAS alone otherwise.
3. **EASU alone:** `RecordUpscale` into an image of the fitted size.
4. **RCAS alone:** `RecordPresent` from a second slot whose stage has the fitted size.
5. **Today's path:** `PresentationScaler::RecordBlitFrom`, a linear blit of the source into a window-size image, for comparison.

**How it's measured:**
- Frames: 20 warm-up, then 200 measured. Each frame is submitted and waited for, then released.
- Statistics: median and 95th percentile (nearest rank).
- GPU ms: `timestampPeriod`, masked to `timestampValidBits`. A queue with 0 valid bits prints that and exits 77.
- CPU µs: `steady_clock` around recording the stage write and `RecordPresent`, plus `Release(slot)` after the wait; for the blit, around its recording.
- Device name: printed on every line.

**Reading:**
- **The parts add up.** "EASU + RCAS as presented" matches EASU + RCAS measured alone (69.46 vs 42.13 + 28.09).
- **CPU time doesn't explain the slowdown.** Recording the FSR presentation costs 47–67 µs of CPU per frame against 2 µs for today's blit. Most of that is the per-present `vkCreateImageView` + `vkCreateFramebuffer` (PRM-033's L2). It's tens of microseconds, not the tens of milliseconds the PC lost.
- **Downscale on lavapipe:** FSR costs about 3.8x today's blit in GPU time, mostly RCAS.
- **To run it on the PC:** `agc_driver_presentation_pass_tests --fsr-cost` from the build, as the Windows tests are run.

## Addendum: why FSR halved the frame rate where it can't upscale

### The harness

Local only; it isn't pushed, because the task names two branches. It is BF-042's draw-record harness (`tests/execution/DrawRecordCost.cpp`, cherry-picked from fa8290816 and b4f2fa1b0 onto 30febcf78) with two changes:
- **A real 3840x2160 render target.** `DRAW_RECORD_COST_TARGET` sets CB_COLOR0_ATTRIB2.
- **A presenter thread.** It attaches a `VK_EXT_headless_surface` window of 1084x610 through `AgcDriverAttachWindow` and calls `AgcDriverPresentBuffer` every 33 ms, showing that same render target as the display buffer. That is the game's path through `Driver::Present`, the GPU mutex and `present()`.

**The workload:** the main thread submits windows of 2048 draws through `sceAgcDriverSubmitDcb` (queue 0, pipelined, committer thread).

**Present paths, counted with gdb breakpoints:**
- `rgba8` takes the **direct** path (`RecordStretchFrom` on each present).
- `bgra8` takes the **drawn** path (`PresentationPass::RecordStage`).

**Each run:** `--cost 20`, `APS5_PROFILE_DRAW=1`, two rounds each, interleaved.

That is the PC's symptom, reproduced on lavapipe:
- `fsr` roughly doubles how long the presenter holds the GPU mutex, and every draw pays about 30% more.
- The driver's own `[draw] pipelined` line shows where: draws wait for room in the draw pipeline. On the drawn path that's 115–134 µs per draw unset and 188–220 µs with `fsr`. This is the wait the PC trace reports as `Driver.Draw.draw_enqueued`.

### Where the presenter holds the mutex

I sampled the presenter thread's stack every 1 ms (`DRAW_RECORD_COST_SAMPLES`), direct path, then symbolized it against the libraries' symbol tables. The presenter is inside `Driver::Present`'s second locked block for all of the following:

| presenter samples | unset (214 presents) | fsr (269 presents) |
|---|---|---|
| `VulkanDevice::QueuePresent` → lavapipe's `vkQueuePresentKHR` | 841 (**3.9 ms per present**) | 2127 (**7.9 ms per present**) |
| `PresentationUpscaler::createView` / `transientFramebuffer` | 0 | 186 (0.7 ms per present) |
| `StorageTexture::Refresh` (compares the 3840x2160 resident image with guest memory) | 1043 (4.9 ms per present) | 1348 (5.0 ms per present) |

**The cause, as far as lavapipe shows it:**
- **`QueuePresent` holds the GPU mutex while `vkQueuePresentKHR` waits for the presentation's rendering.** Driver::Present calls it inside the second locked block; see Presentation.cpp:128 and :144.
- **FSR's stage write and RCAS lengthen that rendering.** Each extra millisecond of presentation GPU work becomes a millisecond of mutex hold, and the draw committer (`commitDraw`, Draw.cpp:615) waits behind it.
- **The per-present view and framebuffer creation adds more,** and lavapipe makes that slow (0.7 ms).

**What's open on the PC:** its trace says `Driver.Present` grew only 2.5 ms per frame, which caps this channel there. So the PC's 76 ms per frame may involve something lavapipe doesn't show, such as how NVIDIA's driver blocks in `vkQueuePresentKHR` or `vkQueueSubmit`. The fix below removes all of FSR's work in that case either way.

**For the PC:**
- `agc_driver_presentation_pass_tests --fsr-cost` gives the GPU times.
- `APS5_PROFILE_DRAW=1`'s `[lock]` holder matrix (presenter column) and `[draw] pipelined` line, from an unset and an `fsr` run, would show whether the hold or the pipeline wait grew there too.

### The fix: FSR stays off where it can't upscale

**Commit:** **50aa233a0** `fix(agc): keep FSR off for presentations it cannot upscale`, on `feat/agc-fsr1-upscaling-cost`, pushed.

**What changed:**
- `present()` uses the upscaler only when `PresentationUpscaler::Upscales(width, height, extent)` holds, so every other presentation records exactly what it records without `ANYPS5_UPSCALE`.
- RCAS alone was not kept for those presentations. It isn't free: on lavapipe it costs 2.8x today's blit at 2560x1440, as section 1 shows.
- **Start line:** "[present] ANYPS5_UPSCALE=fsr: FSR 1 EASU and RCAS when the window is larger than the display buffer, the normal scaler otherwise; RCAS sharpness 0.20".
- **USAGE:** "When it is the same size or smaller, FSR stays off for that frame, which is presented exactly as without `ANYPS5_UPSCALE`: RCAS alone would cost frame rate there without adding detail." The memory sentence now says it applies "While EASU runs".

**Test, in the same commit:** `agc_driver_present_upscale` (tests/execution/PresentUpscale.cpp, registered by the execution-test glob).
- It presents through `VulkanDevice` on a `VK_EXT_headless_surface` swapchain, 1084x610, and reads `VulkanDevice::UpscaledPresents()`, a new count of presentations that ran FSR.
- With `fsr`: 3840x2160, 1084x610 and 1920x1080 don't run FSR; 960x540 does.
- With the variable empty, nothing runs FSR.
- It skips when the extension is missing.
- Red/green:
  - With the gate removed, it fails: "FSR ran on a 3840x2160 display buffer in a 1084x610 window, where it cannot upscale".
  - With the gate, it passes.
  - Under sync validation it reports only the baseline `VUID-VkDeviceCreateInfo-pNext-pNext`, once per device.
- This is also the first CI-runnable test that goes through `present()` with FSR on; PRM-033's L6 asked for one.

**The harness again, with the fix** (b1736557b, the fix cherry-picked):

| case | path | unset µs per draw, round 1 / round 2 | fsr µs per draw | unset / fsr ms per present |
|---|---|---|---|---|
| 3840x2160 into 1084x610 | direct | 143.7 / 141.5 | 161.8 / 129.9 | 11.7 / 11.7, 11.3 / 11.1 |
| 3840x2160 into 1084x610 | drawn | 164.1 / 212.7 | 181.8 / 196.4 | 16.1 / 16.7, 17.6 / 17.4 |

Unset and `fsr` now swap order between rounds, so the difference is noise.

**Where FSR does upscale,** 960x540 into 1084x610 (EASU 1.13x), lavapipe still pays its GPU work under the mutex:

| path | presents unset → fsr | presenter hold, µs per draw | µs per draw, unset → fsr |
|---|---|---|---|
| direct | 5.1–5.4 → 18.6–19.1 ms | 13–15 → 111–129 | 114–117 → 214–241 |
| drawn | 8.7–8.9 → 17.9–19.4 ms | 26–29 → 99–135 | 119–126 → 202–240 |

On a real GPU, EASU + RCAS take a fraction of a millisecond, so this is mostly a lavapipe effect. It still points to a pre-existing design point outside FSR: **`QueuePresent` waits under the GPU mutex.** Moving `vkQueuePresentKHR` out of the mutex would stop any presentation GPU work from blocking the draws. It's not part of this fix; I'd raise it as its own task.
