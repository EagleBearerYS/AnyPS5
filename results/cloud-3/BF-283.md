## How the two interact

**Switch off (`APS5_TABLE_INDEX` unset):** every write-index path is gated by `GuestMemory::WriteIndexEnabled()`: the index proof (`:4010`), `subscribeBuilt` (`:1727`) and `cpuWriters` (`:3892`). Revalidation is therefore 24b56bc1b4's.

**Switch on.** `subscribeIndex` (`:3557-3652`) sorts every element into one of two groups:
- **Unwatched sampled elements** (`!GuestMemory::Watched`) go to `comparedTextures` (`:3585`). The index re-looks them up through `cachedTexture` on every proof (`reresolveElements(comparedTextures)`, `:3829`).
- **Per-element, bumped and looked-up elements, and storage images** go through `fastRevalidate(..., &check, true)` (`:3836`).
  - Here #12921's untracked branch applies to each one whose collect returns 0: a sampled surface needs its recorded stamp (`:3220`), a storage image its `storageUntracked` stamp (`:3280`).
  - So on this path the stamp applies as on 24b56bc1b4.

### Q1: Does the index ever take an untracked element's proof without the stamp?

**Yes, for unwatched sampled elements.** The index never reads #12921's recorded stamp for them, and it reports the proof as `Fast` whenever the re-lookup returns the same object (`reresolveElements` → `IndexOutcome::Accepted` → `indexProved`, `:4011`, `:4056`).

**It is not a stale accept, because the re-lookup reads the memory again:**
- **Views of a host-imported storage image** (both of #12921's tests): the hit calls `refreshForView` (`:945`), which runs `StorageTexture::Refresh`.
  - Its `compareUntracked` (`Texture.cpp:2598`) compares guest memory with the image's copy.
  - That compare is memoized under the same values #12921's stamp is built from: the hint (without one, the collect epoch), the newest stamp, the forget stamp and the newest write note (`Texture.cpp:2617`; the stamp is `untrackedRangeStamp`, `ShaderResources.cpp:3097-3103`).
- **CPU snapshots:** the hit needs one of three checks (`:974`):
  - `unchanged()`, which is never true for unwatched memory;
  - `kept()`, the hint key (`:970`), which applies only with a hint;
  - `equalsCommitted()`, a full byte compare.
  - So without a hint, the bytes are compared on every proof. A changed snapshot makes a new texture; a compute build then falls back (`:3721`), and a draw build rebinds and reports `Partial`.

**Probe:** a temporary print in both tests, reverted and not pushed.

| `agc_untracked_*` step | Index off | Index on |
| --- | --- | --- |
| store 4 KiB, then new collect epoch | path Full, image version 1 → 2 | path **Fast**, image version 1 → 2 |
| new collect epoch, no store (hint test, no hint on Linux) | not fast | **fast** |
| store in the same epoch | fast, version 2 → 2 | fast, version 2 → 2 |

- The content follows the store in both modes.
- The window within one epoch is #12921's own: with no hint, the proof follows the collect epoch. The index doesn't widen it.

**What follows from this:**
1. **Tests:** #12921's tests fail ×10 with the index on, at their path assertions, which expect the full walk after a collect epoch:
   - `tests/Recorder.cpp:5790`: "a sampled template over untracked memory kept its fast proof across a store and a new collect epoch";
   - `:5909`: "a proof over untracked memory without a write-watch hint stayed fast across a collect epoch".
2. **Cost:** every index proof re-looks up every compared element (a cache lookup and `CollectWrites`).
   - An unhinted snapshot also gets a full byte compare on every proof. On 24b56bc1b4 that happens once per collect epoch, through the walk.
   - Storage views are compared once per epoch, or once per hint key.
   - With a hint (Windows), both kinds are cheap.
3. **Not changed in this merge:** the task fixes the index to run as on e079ecb20e when the switch is on. Two options for whoever owns #12745/#12921:
   - (a) The two tests' path assertions accept an index proof that refreshed, by checking the image version as the hint test's `version()` already does.
   - (b) `subscribeIndex` sends an unwatched element that has a recorded stamp (`validatedTextures[i].untracked[0] != 0`) to `check` instead of `comparedTextures`, so `fastRevalidate`'s stamp branch decides. That changes #12745's behaviour, and after every epoch it turns the cheap re-lookup into a fallback to the full walk.

### Q2: Does the hint stamp ever accept something the index would bump?

**No.** The index bumps only elements in subscribed spans.
- Before any per-element proof, `SweepSubscription` collects every subscribed span and fails the whole index proof if any collect returns 0 (`GuestMemory.cpp:2198-2207`).
- #12921's stamp branch runs only when `CollectWrites` returns 0, i.e. the range isn't watched or covered (`:1819`) or the walk failed (`:1840`).
- So a bumped element has just been collected with a nonzero generation. Its `CollectWrites` in `fastRevalidate` is nonzero, and it takes the normal generation query, not the stamp.

### One cost-only interaction, left as is

This is outside the conflict and changes no proof.
- `reresolveElements` (#12745) rewrites `ValidatedSurface` records with the 8-field initializer (`:3748`), so a re-looked-up element loses #12921's `untracked` stamp.
- When the index falls back, the full `fastRevalidate` fails those elements with `FastFail::Collect`. That costs one full walk, and its `captureValidation` stamps them again.
- If this shows up in the Village numbers, the patch is to stamp in `reresolveElements` as `captureValidation` does (`:3130`).
