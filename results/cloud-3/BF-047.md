## 1. What main knows about an address-based build's accesses

A draw is address-based when its resources hold the allocation registry lease (`GuestBufferMemory::HoldsLease`). `prepareAddressBindings` (Graphics/src/ShaderAddressResources.cpp:108-138) takes the lease when a stage has a `BdaPagetable` binding. The recompiler adds that binding when `ShaderInfo::usesDma` is set (BindingAllocator.cpp:169-171), which happens in three cases:
- a buffer op whose V# fails `ValidateSource`: a run-time V# (`TakeGpuDescriptor`, Optimization/src/ResourceTracker.cpp:1387-1410);
- a scalar-address, flat or global access (ResourceTracker.cpp:1615-1643);
- BVH traversal (ResourceTracker.cpp:1586-1588).

| access | known at capture or build? | where |
|---|---|---|
| V#-bound buffer (V# computable from user data, SRT and raw reads) | **bounded**: [base, base + size), read/write split, register soffset checked against num_records | `DescriptorBinding::guestDescriptor`, ShaderResources.cpp:3544-3589; SpirvRuntimeBuffer.cpp:104-121 |
| storage image | **bounded** | WrittenBuffers.cpp:53-76 |
| captured SRT / snapshot words | **bounded** | Draw/Draw.cpp:460 |
| run-time V# (`gpuDescriptor`) | **unbounded**: the V# is loaded at run time | ResourceTracker.cpp:1387-1410 |
| scalar load at a register offset the SRT walker left as data | **unbounded today**; boundable when the offset register is capture-evaluable (the analogue of f5afeb1817) | SrtPlanBuilder.cpp:89-99; "[bda] ... (a register offset is not planned by the SRT walker)" |
| flat / global | **unbounded**: per-lane VGPR addresses | ResourceTracker.cpp:1615-1643 |
| BVH | **unbounded** | |

- **What the driver has for a table access:** the BDA table itself. `GuestBufferMemory::AddressRanges`, GuestBufferMemory.cpp:4176-4241, covers every readable GPU-flagged registered allocation (in place, mirrored or copied). Write permission goes only to writable regions served in place by an import, plus the build's written V# ranges (`addressRange`, :4121-4127; :4202-4239).
- **The write bound is enforced.** `get_bda_write_pointer` checks the permission and returns 0 otherwise. `EmitBdaStoreAt` (SpirvBdaRead.cpp:121-130) then skips the store, and the fault is reported and thrown by `BdaResources::CheckFault`.
- **No per-access record survives.** `ShaderInfo::bdaWrites` is dropped from the compiled result, so 9d10dc19b scans the SPIR-V for stores. The exact written pages are known only after the batch completes (`markWrittenPages`, BdaResources.cpp:307-330).
- **Share, in main's own tests** (`APS5_TRACE_BDA=1 ctest -R '^agc'`, 54 programs, 773 accesses counted):

  | kind | loads | stores | atomics | total |
  |---|---|---|---|---|
  | flat | 196 | 131 | 106 | 433 (56%) |
  | global | 127 | 134 | 55 | 316 (41%) |
  | scalar address at a dynamic offset | 24 | 0 | 0 | 24 (3%) |

  Only 3% could be bounded at capture. Run-time V# accesses are not traced. Titles will differ, but flat and global accesses are bounded only by per-lane values, which the capture never has.

## 2. f5afeb1817

It does not apply to main. It makes his pre-pass (`ResourceMaterializer::evaluateBufferSites`, `BufferStoreSite`, `BufferStoreExtent`) carry a register soffset as a fifth source word, so a site's extent includes it. Main has none of that machinery: `git grep` finds no `BufferStoreSite`, `BufferStoreExtent` or `evaluateBufferSites` in core/. The access he fixed, buffer_load_format idxen through a vertex-table V# at a scalar soffset, is already bounded on main by the V#: the emitted code checks soffset against num_records (SpirvRuntimeBuffer.cpp:104-121).

Main's own register-offset gap is the scalar load the SRT walker leaves as data (3% above). Bounding it would mean having SrtPlanBuilder plan the read when the offset register is capture-evaluable. That is a recompiler change with a disk-cache FormatVersion bump, worth doing only if a title shows those loads matter. Not done here.

## 3. The rule implemented (c44c9a670)

`recordDraw` (Graphics/src/Draw.cpp) builds `PassAccess` for an address-based draw:

| build | anyReads | anyWrites | writes |
|---|---|---|---|
| main, any address-based build | yes | yes | written V#s |
| reads only through the table (narrow rule, 1e5855066) | yes | no | written V#s |
| stores through the table, no copied writes (**new**) | yes | **no** | **the table's writable ranges** (`ShaderResources::AddressWrites`, from `GuestBufferMemory::WritableAddressRanges`: the write-permission ranges plus the written V#s, merged; computed once per storing build) |
| copied writes, or a lease without a table | yes | yes | written V#s |

`PassHazards::Check` then gives the narrower rule:
- **Unknown reads:** break only when the pass holds recorded range writes.
- **Bounded writes:** break when the pass holds unknown reads, or range reads they overlap.
- **Later draws:** a draw that reads those ranges, or has unknown reads, breaks.

`APS5_NO_BOUNDED_ADDRESS_PASSES=1` turns off both this and the read-only rule. `APS5_NO_ADDRESS_READ_PASSES=1` still turns off only the read-only rule.

**Why the queued-store flushes were left as they are:**
- `recordDraw` flushes queued DCC key and label stores when `HoldsLease()`, or when `touches` matches. `touches` includes `ReadsOverlap`, which is `InPlaceReads`. For an address-based build that is every in-place region of its leased space (GuestBufferMemory.cpp:4530-4542), which is exactly what it can read live through the table.
- Label stores are recorded only into host imports (`VulkanDevice::WriteLabelOnGpu`: `HostImportFor`), and key stores go to the same imported GPU memory. So a store an address-based draw could read is one `touches` already flushes for.
- For mirrored or copied regions the draw reads a snapshot taken at build time, so recording the store first would not change what it reads.
- Dropping `HoldsLease()` from the condition would therefore skip only stores outside the build's leased in-place memory, which on a console is no store at all. And it would make `ReadsOverlap` rebuild the space's region list for every queued store, a cost the short-circuit avoids today.
- So there is nothing to narrow on main. The harness queued no stores in any arm (0 flushes). The dispatch path (VulkanDevice.cpp:4414-4419) records outside render passes and flushes on the same grounds, so it is unchanged too.

## 4. Tests

`tests/execution/AddressPasses.cpp` (ctest `agc_driver_address_passes`; each case alone with `--readers`, `--store-beside-reads`, `--store-after-read`, `--read-sees-store`). It draws a triangle onto a 64 KiB guest block with pixel shaders that:
- export a constant;
- `global_load_dword` through `s[2:3]` and export it;
- `global_store_dword` 1.0 through `s[2:3]`.

The vertex buffers are in a block registered read-only. It reads pass counts from 8aacf56ca's `DrawPassTotals()` (APS5_PROFILE_DRAW).

| case | at 8aacf56ca (narrow rule only) | c44c9a670 with `APS5_NO_BOUNDED_ADDRESS_PASSES=1` (main's behaviour) | c44c9a670 |
|---|---|---|---|
| two draws reading through the table share a pass | green ("1 began a pass, 1 continued one") | **red**: "a draw reading through the table after another did not continue its pass: 2 address-based draws, 2 began a pass, 0 continued one" | green |
| a storing draw continues the pass of a draw that read only read-only memory | **red**: "a draw whose table grants no write over the pass's reads did not continue its pass: 1 address-based draws, 1 began a pass, 0 continued one" | **red** (same) | green ("0 began a pass, 1 continued one") |
| a storing draw after a draw reading through the table begins its own pass | green ("2 began a pass, 0 continued one") | green | green |
| a draw reading through the table what the previous draw stored sees it | green ("stored 1, brightest color byte 255", 2 passes) | green | green |

Two findings came out of writing the tests:
- **Copied reads leave no pass hazard.** A storing draw after a descriptor draw that read the same writable block continued the pass. The descriptor draw's small vertex buffers are copied at build time, so its pass records no live read. That is correct, so the third case uses a table reader instead.
- **A test caveat.** After `AgcDriverWaitIdle`, a CPU read of the stored word returned 0 until the color target was flushed. Recorded draws stay in the open batch, and table stores are not noted as pending writes until the batch completes, so `FlushGpuWrites` on the store address syncs nothing. This is main's behaviour too (`APS5_SYNC_COMPLETION_DRAWS=1` makes the store visible at once). The test flushes the target first. It is worth knowing for any test that reads table stores back.
