## G1: a store inside a completion action loses the results around it

### Path

A copied buffer's write-back (`GuestBufferMemory::WriteBack`, or a label or other CPU write run as a completion action) calls `GuestMemory::Write`/`WriteChanged`. That sets ReadSite::Store and calls the flush hook `FlushForAccess`. There is no gate: `FlushGpuWrites` always calls the hook. At e82f9f1a52, inside a completion (`completionDepth != 0`), the hook chose `PublishScope::None`:

- **Images pending over the range:** `FlushPending` stores them, retiled into the unit shadow when the import is watched, and publishes nothing.
- **Only shadowed units:** `PublishShadowsOnly` returns at once.

`PublishShadow` would have skipped the publish anyway: `Recorder::InCompletion() && site == Store`, counted as `skippedInCompletion`. Then the store lands in the import. Its stamp is newer than the shadow's generation for every unit it touches, so the next publish (a read, a build, a copy) drops those units as stale.

For a unit the store covers fully, dropping it is right. For a unit it covers partly, every other byte of the unit is lost. Those bytes are the storage results that were in the shadow, or that the hook had just put there.

The old comment said the copy "would land over the store later". That is true only if the copy isn't waited for. Inside a completion action, though, the hook already does a full `Sync()` whenever it stored or published.

### Fix (one commit, 6ee5a91b2a, 6 files)

- **The hook.** A store gets `PartialUnits` inside a completion action as well as outside one. It passes `waited = completionDepth != 0` through `FlushPending` and `PublishShadowsOnly` to `PublishShadow`.
- **`PublishShadow`.** It skips a completion store only when it is not `waited`. Other completion-time publishes are skipped as before.
- **Ordering.** The existing `if (stored || published) … if (… || completionDepth != 0) recorder->Sync();` now lands the copies before the store, as the full Sync already did for stored images.
- **Comments.** The 3-line hook comment that described the old behaviour is deleted. No comment lines are added.

### Cost

- **No live shadow in range** (the normal case): one more `AnyShadowedOverlaps` check per completion store. That is one SlimMutex hold plus a std::map walk over the few shadows overlapping the range, the same check every store outside a completion already pays. Before, `PublishShadowsOnly(None)` returned before it.
- **A partly covered live unit:** one copy per such unit, plus the full `Sync()` the hook already takes inside completion actions for stored images. It waits for the batches in flight, under the same nested-reap caveat as that existing path. This happens only where data was lost before.

### Test

It uses the same heap setup as #6682's test: a watched 2 MiB+64 KiB heap, imported, with an R64KBX 1024x512 RGBA8 storage image over it cleared red. A 4-byte `GuestMemory::Write` made from `recorder.OnComplete` lands at offset 16. The test then reads the heap through `GuestMemory::Read` and counts bytes that are neither red nor the store. It runs two variants, each on a fresh image and a fresh memset:

1. the image's results still pending;
2. the results already retiled into the unit shadow (`FlushPending(..., "storage refresh", PublishScope::None)`); the test checks the image is no longer pending.

## G2: #6636's reuse path skips #6682's publish

### Why it is a gap

- On main, an address-based build is never reusable: `noteReusable` returns for `usesBda` builds, so every such build runs `UploadFinish`.
- #6636 (followup/6636-review-f1-f3 3fe43a3ff) makes address-based draw builds reusable. `Revalidate` (ShaderResources.cpp:2821) calls `guestMemory.ResumeSpace()` (GuestBufferMemory.cpp:4603) and then `proveBuild`.
- `ResumeSpace` restamps imports and refreshes mirrors and heap runs. It publishes no shadow.
- Step (2) of `proveBuild` flushes, and so publishes, only:
  - `directRegions`: for an address-based build this is `SpaceRegions()` (ShaderResources.cpp:2093), the regions the space does **not** serve, empty when it serves them all;
  - `guestMemory.Writes()`: `DirectWrites()`, the descriptor-bound writable ranges.
- The heaps the build maps (`space->base`) are in neither list. So after #6682 merges with #6636, a reused address-based draw reads, through its pointers, import bytes older than the results in the shadow.
- It is worse than a stale read. A pointer store into a unit that is still live lands in the import, and the next publish copies the older slab unit over it.

### Where the fix must go

After `proveBuild`, not inside `ResumeSpace`. `proveBuild` repeats the storage-image lookups (and T1 refreshes), and `StorageTexture::Refresh` stores an alias's pending results with `PublishScope::None`. That retiles into the shadow after anything `ResumeSpace` could publish. This is the same reason #6682 publishes at the end of `UploadFinish`, after `buildComplete`'s lookups.

### Patch (for whichever of #6636 / #6682 lands second)

**Checked and not a gap.** The debug input capture (`Draw.cpp:1640`, `captureInputs`) compares the CPU's view of an in-place read with the GPU's. #6682's publish notes its ranges as pending writes (`UnitShadow.cpp:264`), so the capture skips those ranges ("gpu-writer") instead of reporting a false mismatch.

**Outside #6682 (pre-existing design limit).** Native guest stores aren't trapped either, on any platform. Write watching is async (WP_ASYNC / GetWriteWatch), so nothing can publish before such a store lands. A native store into a unit with live shadow results makes the unit stale, the publish drops it, and the GPU results in its other bytes are lost (counted as `staleDroppedCpu` in the `[shadow]` report). It is the same mechanism as G1, without a hook to publish first. Closing it would need a write fault before the first store into a live unit. That is a design question for unit shadows, not for this PR.

## 2. Correctness holes in #6682's publish

**Cost per build when nothing is pending.** `PublishShadowsOnly` → `AnyShadowedOverlaps(heapsBegin, span)` takes the registry's SlimMutex and walks the `std::map` of shadows overlapping the span (`UnitShadow.cpp:121`):

- each shadow with `liveUnits == 0` costs O(1);
- a shadow with live units exits at the first live unit inside the span, and then there *is* something to publish.

So the cost is O(log S + k) per address-based build, where k is the number of shadows (one per import that ever retiled, until retire) overlapping `[space->base.front().begin, space->base.back().end)`. That is usually every shadow, since the span covers all heaps. The `GpuMutex` is taken only when something is live. Per-unit scanning happens only for edge shadows that are partly inside the span.

A global live-unit counter in the registry would make the nothing-live case O(1) without the mutex. That is optional; at today's shadow counts it is a handful of map nodes.

**Ordering against pending GPU writes and labels.** `recordCopies` (`UnitShadow.cpp:228-265`) records:

- a leading barrier (ALL_COMMANDS|HOST, shader/transfer/host writes → transfer), so the copy follows every earlier writer of the import in the open batch;
- a trailing barrier to every later reader, the host included.

It keeps the slab alive and notes the ranges as pending writes, so CPU readers sync on it. A GPU write to the import recorded before the build has already published what it covered partly (fills, copies and labels publish `PartialUnits` first). So the units still live at the build are newer than, or disjoint from, those writes. A later label or store lands after the copy in queue order. Pending images stay pending by design (the address-based exemption, `APS5_BDA_FLUSH=1` to flush them).

**Shadows written while the publish runs.** A retile happens under the `GpuMutex` (`FlushPending` holds it across `writeBack`), and `PublishShadowsOnly` takes it for the publish, so the two never interleave. Within a build nothing retiles after `UploadFinish` (build order row above). A retile by another thread after the publish is recorded after the build's work, which is program order for a later store. One caveat: before G1, a completion store could retile with scope None at any time and leave units live. G1 publishes the units such a store covers partly; the rest of the stored layer stays live until a reader publishes it, as for any store.

## 3. Adversarial "better version" check

1. **Publish where shadows become pending, at retile time.** This removes every reader-side publish, and with it #6682, G1 and G2, and it shrinks the native-store window above. It defeats unit shadows, though: every retile would copy slab → import even when only the GPU reads the results (`ShadowSources` serves them from the slab). That would be costlier than writing the import directly. It wins only if nearly every retiled unit is read by the CPU or by an address-based build anyway.
2. **Key on the pending-image index, or a live-unit index.** Instead of walking shadows, consult an interval index of live units, or the pending registry's `MayOverlap`. Same correctness, lower constant. The global counter above gets most of it.
3. **Publish only what the shader can reach.** Image tables know their read ranges (`imageTableReadRanges`), but arbitrary BDA pointers don't. Publishing the whole heap span is the only safe choice for pointer reads, so #6682's scope is right.

**What #6682 needs to stay the better version:**

- (a) cover the reuse path (G2) when #6636 lands;
- (b) keep its one span check cheap (the optional counter).

G1 is not #6682's bug, but it is the same loss on another path, and it is fixed on the branch.
