# PM-079: Lane D: fable-void's device-lock moves, against upstream main

cloud-3, 2026-10-18. Checked against upstream `main` 218aa8f00 and against his `wip/new-gpu-path` at d8731cc72 (fetched with the task's command). Built and run on Linux with gcc and Ninja Release, CI's Linux configure flags plus `-DANYPS5_ENABLE_SPIRV_TOOLS=ON`, on lavapipe (Mesa 25.2.8, llvmpipe LLVM 20.1.2). Everything ran as the unprivileged user `runner`.

**Verdict:** only one of the named commits, 531e45035, fixes a lock wait that main also has, and it is the only one that ports on its own. I ported it as `exp/lane-d-lock-present-flush`, with a Linux test (see "The port"). Every other named commit removes a lock wait that exists only in his multi-stream recorder or his residency manager, neither of which main has. The port plan at the end gives the order they would need.

## 1. The named commits

All of them are new since ed8f2d7a2e, and none is on main. Main file:line references are to 218aa8f00.

**What main has, for reference:**
- **One recorder stream.** Main has one `std::unique_ptr<Batch> open;` (`Graphics/include/Recorder.hpp:812`). `Recorder::Submit` asserts the lock (`AssertGpuLockHeld("Recorder::Submit")`, `Graphics/src/Recorder.cpp:3308`) before its `vkQueueSubmit` (`:3356`).
- **The CPU-read flush hook.** `GuestMemory::Read` flushes through `FlushGpuWrites` (`Execution/src/GuestMemory.cpp:2145`), which calls `FlushForAccess`. That hook:
  - takes the lock only after the lock-free `SnapshotOverlaps` check (`Recorder.cpp:1022-1025`);
  - waits for the GPU with the lock released (`syncThroughUnlocked`, `:3670-3676`), but only when its hold is the outermost one (`DepthOnThisThread() != 1` refuses, `:3605`).

  A flush nested inside another lock hold therefore waits while holding the lock.
- **No residency layer.** There is no `ResidencyManager`, `ResidencyDriver`, dirty mirrors, `DeclareSection` or `DeviceImageTable`.

### 531e45035: wait for the display buffer's GPU writers before the presentation lock (+343: 13 production lines, 330 test lines)
- **What it changes.** `Driver::Present` calls a new `VulkanDevice::PrepareDisplayRead(*buffer)` between its first and second device-lock holds.
  - That function returns at once when `PresentableResident` finds a resident image (tiling mode other than 1, and `APS5_NO_RESIDENT_PRESENT` unset).
  - Otherwise it calls `GuestMemory::FlushGpuWrites(buffer.address, DisplayBufferSize(buffer))` at lock depth 1, so the hook waits for the writers without the lock.
  - The read under the lock still flushes, which covers any writer recorded in between.
- **What it needs from his tree.** The production code needs nothing: his `readyContext()` is main's `graphicsContext()`, renamed in e7d7eae84. His test, `agc_driver_cpu_read_lock_waits`, needs several things main lacks:
  - `NewPathFixture.hpp` (a5e4691ae);
  - `Residency().Manager()` (02827d79f, 8dee493c7);
  - `Recorder::LabelPendingAt`.

  It is also `#ifdef _WIN32` only.
- **On main: the same wait, on the same path.**
  1. `Execution/src/Driver/Presentation.cpp:108-109` takes the second lock (`GpuLockSite::Present`), and `:116` calls `PresentDisplayBuffer` under it.
  2. That reads guest memory in one of two places:
     - `VulkanDevice.cpp:3179`: `colorTransfer->Upload`, then `GpuColorTransfer.cpp:127` `GuestMemory::Read`, then `FlushGpuWrites`;
     - `ReadDisplayBuffer` (`VulkanDevice.cpp:3013`), which flushes through `DisplayBuffer.cpp:252`.
  3. The hook then takes the lock nested (`Recorder.cpp:1025`), and the depth check at `:3605` keeps it held through the GPU wait.
- **Ported:** see "The port".

### 700dbcdc9: order wait-free submissions after queue 0 without the device lock (+135/-4)
- **What it changes.** In his `Driver::execute`, a `waitFree` submission with `SeparateQueues()` used to take the lock (`GpuLockSite::Wait`) and call `OrderAfterQueue(0)`, which submitted queue 0's open batch.
  - Now it first tries `Recorder::OrderAfterQueueOnOwnStream`. That adds queue 0's future timeline value to the caller's own open batch's `waits`, under the recorder lock only, without submitting.
  - `submitStream` now submits any batch it awaits first.
  - `RecordLabelsOnOwnStream` loops on `awaitsUnsubmitted`. It waits on `orderWaitMutex`/`orderWaitChanged` without any lock, woken by `NotifyOrderWaiters()` from `submitStream` and from the unlock hook. It takes the device lock only with `try_lock`.
- **What it needs from his tree:**
  - the multi-stream recorder: `queueStreams`, `streamOfCaller`, per-queue VkQueues and timelines (ff0f399e7), plus `SeparateQueues` and `OrderAfterQueue` (7b86d364b), all older than ed8f2d7a2e;
  - the per-stream label registry (697bf6a7d);
  - d314223bd's own-stream machinery (`RecordingMutex` `ReleaseAll`/`Reacquire`, `RecordingHold`, `ownStreamRecording`, `streamOwnedByCaller`, per-stream pools).
- **On main: no.**
  - Main's `execute()` has no `waitFree` lock branch. `GpuLockSite::Wait` is used only in `WaitMemory.cpp:208`, the memory-wait path.
  - Main orders a wait-free submission behind queue 0 on the CPU, without the device lock (`Execution/src/Driver/Queues/QueueWorker.cpp:242-254`, `stall.Check("order behind queue 0 for event", …)` at `:253`).
  - With one VkQueue, GPU order is implicit in submission order.

### c09710145: keep the order-wait condition variable alive through process exit (+100/-3)
- **What it changes.** No lock change. It makes 700dbcdc9's namespace-scope `orderWaitChanged` a leaked `OrderWaitChanged()`, which avoids a Windows exit hang in `pthread_cond_destroy`. It adds the Windows-only test `agc_exit_with_busy_threads`.
- **What it needs from his tree.** 700dbcdc9 only.
- **On main: no.** Main has no `orderWaitChanged`. It already uses the same leaked pattern for its release queue (`Recorder.cpp:419-421`).
- **Port:** fold it into 700dbcdc9.

### d314223bd: record a queue's labels on its own stream without the device lock (+521/-33)
- **What it changes.** In his `Driver::execute`, the `GpuLockSite::End` lock around `recordDeferredLabels`/`SubmitRecorded` is skipped when the new `submitLabelsOnOwnStream` succeeds. That path goes `VulkanDevice::WriteLabelsOnOwnStream`, then `Recorder::RecordLabelsOnOwnStream`, which:
  - records the labels into the caller's own stream;
  - calls `submitStream` under a new recursive recorder lock (`RecordingMutex recording`), added to nearly every Recorder method;
  - gives each stream after the first its own command pool.

  It refuses, and falls back to the lock, in four cases:
  - a completion publication is pending;
  - the host import epoch changed, or the pages are mirrored;
  - another stream has an open barrier section;
  - the batch is not labels-only.
- **What it needs from his tree:**
  - the multi-stream recorder (ff0f399e7, 7b86d364b, 697bf6a7d), with `streams[].barrier` sections (7b86d364b);
  - his residency manager (02827d79f), with four newer commits: 244560917 (its own lock, so `AnyResident`/`AnyStaleOwned` run without the device lock), 8b310b5a8, df71e8348 and 7f8e5bc9f.
- **On main: the lock site exists, at `Execution/src/Driver/Packets/PacketExecution.cpp:435-440`** (`GpuLockSite::End`, `recordDeferredLabels(localDevice.get(), submission.queue)`, `SubmitRecorded(submission.queue == 0)`). But every queue records into the single `open` batch that queue 0 fills under the lock, so there is no own stream to record into. On main this would be a redesign, not a port.

### cb017b86c: keep the label flush deadline per recorder stream (+241/-14)
- **What it changes.** The global `pendingLabelSince` becomes `labelSince[stream]`. The deadline flushes in `waitMemory`, `recordLabelsForPacket` and `flushBetweenPackets` call a new `SubmitLabelled()`, which submits only the streams that hold a pending label. A label deadline therefore stops forcing out unrelated streams' batches under the lock.
- **What it needs from his tree.** Per-stream `opens[]`, `streams`, `submitStream` and `MaxRecorderStreams` (ff0f399e7), plus `anyOpen`/`awaitsUnsubmitted` (7b86d364b and 700dbcdc9).
- **On main: no equivalent.** With one batch, a deadline submit has no other queue's batch to spare. The deadline is set at `Recorder.cpp:3108-3109` and cleared at `:3379`. The flush sites are `PacketFlush.cpp:91`, `WaitMemory.cpp:301` and `DeferredLabels.cpp:148`.

### cc9335fe0: declare the objects of page-table sections and keep declarations per stream (+258/-16)
- **What it changes.** These now call `DeclareSection` with their objects plus `ResidencyDriver::SectionAccess(written)`, instead of acting as barrier sections:
  - page-table dispatches in `recordDispatch` and `DispatchContinuationRounds`;
  - address-based draws in `recordDraw`;
  - residency copies and `frameBoundary`.

  Declarations become per stream (`declarations[streamOfCaller()]`), and it adds `OrderSubmits`. As a result:
  - another queue's label no longer refuses the own-stream path, which submitted queue 0's batch, because of `streams[other].barrier`;
  - an own-stream label no longer consumes a lock holder's declaration.
- **What it needs from his tree:**
  - older than ed8f2d7a2e: `DeclareSection`/`beginSection`/`dependOn` (7b86d364b), streams (ff0f399e7), `ResidencyDriver` (8dee493c7) and `DeviceImageTable` (d35b01a5b);
  - newer: d314223bd, `DispatchContinuationRounds` (eb6a96743) and `NeedsDeviceTransfers` (255afccf9).
- **On main: none.** Main has no sections or streams, and a label always takes the lock (`PacketFlush.cpp:73-75`).

### f3f1a74eb: declare the objects of the remaining barrier sections (+367/-9)
- **What it changes.** The remaining undeclared sections now call `DeclareSection`:
  - `DeviceImageTable::record`;
  - texture and storage uploads, and `RefreshCopy`;
  - depth-surface work;
  - `recordCommands` in `MultisampleTarget.cpp`;
  - completion labels, which `dependOn` other streams' overlapping batches instead.

  Submission end and suspend call `SubmitCallerRecorded`/`Recorder::SubmitCaller()`, which submits the caller's stream only.
- **What it needs from his tree.** Everything cc9335fe0 needs, plus cc9335fe0 itself and cb017b86c.
- **On main: none.** `PacketExecution.cpp:105` and `:440` call `SubmitRecorded(submission.queue == 0)`, but with one batch there is no other stream to spare.

### 244560917: give the residency manager its own lock so settled CPU reads skip the device lock (+267/-16)
- **What it changes.** It adds a recursive `ResidencyMutex structure`, ordered after `GpuMutex`. It is:
  - taken in every public `ResidencyManager` method and in `UseForRead`, `BeforeWritingDispatch`, `Publish` and `NoteDriverWrite`;
  - released around GPU waits and retiles.

  `MirrorsDirty` checks `DirtyIn` first and takes `GpuMutex` only for a dirty or stale range. The new `FlushForCpuReadSettled` lets the write-back hook and `AccessFault` retire settled writers and re-arm guards under the structure lock alone.
- **What it needs from his tree:**
  - the residency manager (02827d79f), `ResidencyHooks` (c472afc72) and `TokenSignaled` (697bf6a7d);
  - access guards and dirty mirrors (2dbedc672, f25e6d230), stale/owned pages (caea3b7f5, 8b310b5a8);
  - 910e5112b, 39e8b8119 and 08baca73b.
- **On main: none.** There is no residency hook, access-fault handler or `MirrorsDirty`. Main's `StoresPendingOver` (`VulkanDevice.cpp:2176-2179`) uses `AnyShadowedOverlaps`, which takes no `GpuMutex`.

### 08baca73b: wait for a CPU read's mirror writers and write-back without the device lock (+158/-29)
- **What it changes.** `FlushForCpuRead` gets an unlocked variant, `FlushForCpuReadUnlocked`. It waits for writer and write-back tokens through `IResidencyDevice::WaitUnlocked`, then `Recorder::WaitTokenUnlocked`, which copies out the timeline points, unlocks and checks `RecorderAlive`. After each wait it re-evaluates the range under the lock. `writeBack` and `AccessFault` use it at lock depth 1.
- **What it needs from his tree:**
  - the residency manager (02827d79f) and `AccessFault` (2dbedc672);
  - multi-stream `Token`/`AllToken` (7b86d364b) and `TimelinePoints` (ff0f399e7);
  - 39e8b8119's `addUnsettled`/`CpuReadSettled`, and 8b310b5a8's `staleIn`/`retileStale`.
- **On main: none.** Main has no residency wait. Its recorder-side CPU-read wait is already unlocked at depth 1 (`Recorder.cpp:3670-3676`).

## 3. Port plan for the rest

None of the rest gives main anything on its own. Each removes a lock wait that one of his two layers introduced, so the order is set by those layers.

**Stream chain: lane D's "a Vulkan queue per guest queue".**
1. **The multi-stream recorder first,** about 1.5k lines older than ed8f2d7a2e:
   - ff0f399e7: a VkQueue and timeline per guest queue, `queueStreams`, `streamOfCaller`;
   - 7b86d364b: `SeparateQueues`, `OrderAfterQueue`, `DeclareSection`/`dependOn`, barrier sections;
   - 697bf6a7d: the per-stream label registry.

   Main needs this first; it is the real lane D work and is not a port of a lock commit. Main's `Recorder::Submit` lock assertion (`Recorder.cpp:3308`) and its single `open` (`Recorder.hpp:812`) are the places it replaces.
2. **d314223bd,** own-stream labels. Its residency refusals reduce to `StorageTexture::AnyPending` on main, which has no mirrors.
3. **700dbcdc9 with c09710145 folded in.** On main this also needs the `waitFree` branch of his `execute()`; main orders behind queue 0 on the CPU instead.
4. **cb017b86c,** the per-stream label deadline.
5. **cc9335fe0, then f3f1a74eb.** These need `ResidencyDriver::SectionAccess` and `DeviceImageTable` declarations; without residency, the `SectionAccess` arguments drop out. 218f572ae (sampled-image order across streams) goes with them, and needs `DeviceImageTable`/`DispatchTextures` (d35b01a5b, 5700cfe80).

**Residency chain: only if lane B takes his residency manager and mirrors.**
1. **The layer:** 02827d79f, c472afc72, 8dee493c7, 2dbedc672, f25e6d230, a93170ae6, caea3b7f5 and 8b310b5a8.
2. **Then, in order:** 910e5112b, 81c844d03, 39e8b8119, 08baca73b and 244560917. Each is small on top of the previous one. 08baca73b's `WaitTokenUnlocked` would be rewritten for main's single timeline if the stream chain has not landed.

If lane B does not take his residency layer, none of the residency chain applies to main. Main's own CPU-read path already has the lock-free snapshot gate and the depth-1 unlocked wait these commits add to his layer.

**What main can take now, besides 531e45035:**
- **The same nested-hold pattern elsewhere.** Any other `GuestMemory::Read`/`FlushGpuWrites` inside a device-lock hold waits with the lock held. Main already counts these with `APS5_PROFILE_DRAW=1`:
  - the `[recorder]` line's "hook waits … locked N" (`holdCounters.hookLockedWaits`, `Recorder.cpp:3510`) and its "top sync sites";
  - the `[lock]` line's locked GPU waits (`GuestMemory::NoteLockedGpuWait`, `Recorder.cpp:3799`).

  On a Village run these would show which nested holds remain, with this port's present among them on main, before anyone ports more.
- 078e1a24a's retirement half, for lane C.
