# BF-074: what BF-052's cached CPU-path indirect draws keep alive past their byte cap

cloud-3, 2026-10-18. Linux, gcc, CI's Release flags, lavapipe (Mesa 25.2.8), user `runner`. All runs are single runs.

**The short version:**
- **The holder** is draw relocation's alias map, `Driver::drawAliases` (Execution/src/Driver/Draw/DrawRelocate.cpp:171–172).
  - It keeps up to `MaxAliases` = 16384 `shared_ptr<DrawEntry>`.
  - A CPU-path entry that is evicted or swept from the draw cache stays alive through its aliases, with its variants, compiled results, decode and SPIR-V.
  - `dropDrawEntry` unpins its bytes from `cpuIndirectCharge` at that point, so the cap no longer sees them.
- **In the harness:** aliases learned after ~70k draws kept 3434 evicted entries alive (~58 MiB). Memory then stepped up again at ~150k.
- **The fix** releases a CPU-path entry's aliases when it leaves the cache. It moves them to the new object when the entry is replaced or rotated. On the harness, memory then stays flat (+2.3 MiB over the last 50k draws, against OFF's +2.7), and the cache still hits.

## 1. The harness

- **Starting point:** BF-046/BF-055's Village harness (`agc_driver_village_draw_cost_tests --cost N`): 850 draws a frame, 8 object V# sets with one per frame, 4 pixel programs, and `VILLAGE_GPU_SYNC=1`.
- **What I added:**
  - **`VILLAGE_INDIRECT=1`** turns every draw into a DRAW_INDIRECT record of 6 vertices. The record's base vertex goes to a third, unused vertex user SGPR (0x8e). With `APS5_TRACE_INDIRECT_DRAWS=1` the driver logs each such draw as `-> cpu (patched SGPR not folded)`, so every one takes the CPU path.
  - **`VILLAGE_FOOTPRINT_EVERY=<n>`** prints, every n draws: VmRSS, VmData, `CpuIndirectCacheSize()` (entries, counted bytes, budget, dropped, refused, alias counts), and the draw cache's hits and lookups.
- **Settings in every arm:** `VILLAGE_GPU_SYNC=1 VILLAGE_INDIRECT=1 VILLAGE_FOOTPRINT_EVERY=5000`, `--cost 110` (8 warm-up frames plus 110, so 100,300 draws).
- **Target:** 960x540 (`VILLAGE_WIDTH/HEIGHT`). That cuts lavapipe's GPU time from ~4.4 s to ~1.2 s a frame. The cache and holder state are the same at either size.

**Two shapes:**
- **"churn"** (the default 8 sets): 6800 distinct draws a cycle against the draw cache's 4096-entry limit, so entries keep being evicted. There are almost no hits.
- **"hit"** (`VILLAGE_SETS=4`): 3400 distinct draws, which fit, so ~99% of lookups hit after warm-up.

## 5. The holder

**I named it with counters in a temporary build** (not committed). They counted live `RecompileResult` objects from the memo path, the memo size, live `DispatchVariant` and `DrawEntry` objects, distinct results in the draw cache, and `drawAliases`. All are churn ON 64 MiB, at these draw counts:

| draws | live results | in the memo | distinct results in cached variants | live variants | live entries | aliases | aliased entries not in the cache | rss |
|---|---|---|---|---|---|---|---|---|
| 65,450 | 4249 | 1089 | 4161 | 8192 | 4096 | 0 | 0 | 380.3 |
| 75,650 | 5358 | 1089 | 4161 | 10072 | 5036 | 3434 | 931 | 398.2 |
| 85,000 | 7644 | 1089 | 4161 | 14980 | 7490 | 3434 | 3434 | 439.1 |

**Reading the table:**
- The draw cache stays at 4096 entries, 8192 variants and 4161 distinct results, and the memo at 1089.
- Yet 3394 more `DrawEntry` objects and 6788 more variants are alive after the step. Every one of the 3434 aliased entries is no longer in the cache.
- **So the owner is `drawAliases`.**
  - `learnPendingRelocation` stores `drawAliases[pending.alias] = inserted->second`.
  - `dropDrawEntry` erases the entry only from `drawCache` and `drawOrder`, and unpins its bytes.
  - The map is bounded at 16384 entries by count, not bytes, halving only when full.
  - Aliases are learned in bursts, when draw relocation's per-identity trial (`DrawRelocationTrial`: 1024-lookup windows, idle 16384 draws when unproductive) lets it compute alias keys. That explains the step at ~70k draws and the second at ~150k.

**OFF is unaffected:** CPU-path draws are not cached at all, so no alias holds one.

**`APS5_NO_RESULT_MEMO=1` (churn ON 64 MiB)** also showed no step, but for another reason. Without the memo, each entry owns its results, so 4087 entries filled the 64 MiB budget first. The cache then refused inserts rather than evicting, with 0 dropped, so no alias outlived its entry. RSS was flat at ~388 MiB.

**Why the PC can go far past the cap:**
- Up to 16384 dropped entries can stay alive (4× the 4096-entry cache) with none of their bytes counted.
- For Village's entries, which are larger than this harness's ~14 KiB counted each, that can reach well beyond 768 MiB.
- This matches the 1.7 GB rise and the steady 202 MB/min growth while new aliases keep being learned. I did not measure it on Village.

## 6. The fix (0b0862738 on `fix/agc-cpu-indirect-release-aliases`)

**Changes:**
- **Recording:** `DrawEntry` gains `aliases`, the alias keys learned for a CPU-path entry, recorded in `learnPendingRelocation`.
- **Drop:** `dropDrawEntry`, for a CPU-path entry, calls `releaseDrawAliases`, which erases each alias still holding that entry.
- **Replace and rotate:** `insertDrawEntry`'s replacement of an existing key and `lookupDraw`'s variant rotation call `moveDrawAliases`. That points the aliases at the new object, so no alias keeps an old copy alive.
- **Scope:** aliases of non-CPU-path entries are untouched (today's behaviour).
- **Diagnostic:** `CpuIndirectCacheSize()` gains `aliased` and `aliasedOnly`, and the profile line prints them.
- **Diff:** with the diagnostic commit, the branch changes 8 files, +123 −7 against 54bdd57ece.

**The cost:** a CPU-path donor evicted from the cache can no longer serve relocation hits through its alias. The cache's memory is now bounded by its charge, as BF-052 intended.
