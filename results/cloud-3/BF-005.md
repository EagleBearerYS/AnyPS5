**Why gating, not a count per instance folded once per capture:**
- **The readers allow it.** It's 4 lines with no header change and no new state.
- **It's the file's own pattern.** The page and word read times (110-112, 194) and the handle memo counts (276) are already counted only under `CaptureProfiled()`.
- **Profiled numbers stay exact.** With profiling on, the code path doesn't change, so the printed numbers stay exact everywhere, including captures that throw and captures running at once on several workers.
  - A per-instance fold would need two things to match that: a fold before the print, and a second fold on the exception path.
  - It would also change when other threads' captures in flight show up in the line.
- **The check is cheap.** `CaptureProfiled()` is a function-local static: a guard byte and a bool, both read-only after the first call.
  - In the built test binary they sit on a different cache line from the counters a capture updates for every word and page.

**The trade-off:**
- With `APS5_PROFILE_DRAW=1` the per-word atomic stays, which is what keeps the numbers exact. So profiled captures running at once still contend (§3, profiled rows).
- If profiled runs need to get cheaper too, the per-instance fold is the follow-up.

## 3. Microbenchmark

**How:**
- Commit 86232cada, `agc_shader_memory_tests --capture-read-bench`, with `BENCH_THREADS` 1, 2 or 4.
- `friend struct CaptureReadBench` gives the bench `ShaderMemory`'s private static `read`. That's the callback a capture's SRT walk calls for each word.
- **Each capture:**
  - a new `ShaderMemory` with one 256-byte initial region, standing in for a capture's code region, so `read` does its snapshot lookup;
  - then reads of 100,000 consecutive words from the thread's own 4 KiB-aligned buffer: 98 pages, each fetched whole on first touch, every word read once.
  - ns/word is the capture's time divided by 100,000, including construction, page fetches and destruction.
- **Threads:** 50 captures per thread. All threads start together, each with its own buffer and captures.
  - Each run prints the median and mean over all captures of all threads.
- **The binaries:**
  - **before** = upstream main 8cd937e29 plus the bench commit (scratch branch, not pushed);
  - **after** = the branch head.
  - Both are Release builds (`-O3`) from gcc 13.3.0, run as `runner`.
  - The two binaries sat side by side and runs alternated before, after, before, and so on: 3 rounds per configuration, 6 for one thread.
- **Machine:** a VM with an Intel Xeon @ 2.80 GHz.
  - 4 cores, 1 thread per core (no SMT), 1 MiB L2 per core, 33 MiB L3, 15 GiB RAM.
  - **AVX-512: yes** (F, CD, BW, DQ, VL).
  - Ubuntu 24.04.5, kernel 6.18.

**Profile off.** The table gives the median of the run medians in ns per word, with the range of the run medians in brackets.

| threads | before | after | change |
|---|---|---|---|
| 1 | 16.96 [16.83–17.05] | 16.07 [15.70–16.30] | −5% |
| 2 | 61.51 [55.13–63.89] | 17.02 [16.86–17.17] | −72% (3.6× faster) |
| 4 | 148.86 [137.29–162.64] | 17.16 [16.89–17.30] | −88% (8.7× faster) |

- One of the six one-thread "after" runs was disturbed (median 28.21). It's outside the range shown, but it is counted in the 16.07.
- **Per capture,** the 100k reads take:
  - 1.70 → 1.61 ms on one thread;
  - 6.2 → 1.7 ms each with two at once;
  - 14.9 → 1.7 ms each with four at once.

**`APS5_PROFILE_DRAW=1`.** Both binaries count here: the profiled path is unchanged by design.

| threads | before | after |
|---|---|---|
| 1 | 17.13 [16.99–17.32] | 18.15 [18.06–18.44] |
| 2 | 59.55 [56.66–63.33] | 60.58 [56.44–64.89] |
| 4 | 127.04 [116.05–141.31] | 162.76 [152.42–163.49] |

- One profiled thread is about 1 ns/word slower than before, from the extra flag check.
- The four-thread spread is the VM's: the same atomic path measured 116–163 ns/word across all the "before" runs, profiled or not.

**Caveat.** The bench isolates `read`.
- A real capture spends time in the SRT walk and in materialization between reads, so its threads hit the shared line less often.
- So the in-game gain will be smaller than these numbers. The Village trace pair decides.

**The new test:**
- **Setup.**
  - It captures the file's image-table request (128 records) through a counting runtime. That runtime is the file's `CountingRead`/`CountingReadWords`, counting every single read and every word of every run.
  - That count is N, the number of words the capture reads.
- **The checks,** on a `ShaderMemory`:
  - the first capture must add exactly N to `reads`;
  - it must add at least one page, and no word-wise page;
  - a second capture on the same `ShaderMemory` must add N again and no page.
- **Here N = 1040:** 1024 table words read as runs, plus 16 single reads. The first capture adds 3 pages.
- **Without `APS5_PROFILE_DRAW`,** the mode fails as it should: "capture read counts: a profiled capture did not add each of its word reads once".
- **What it covers:** it guards the profiled counts the fix has to keep. It doesn't measure the gain; the bench does that.
