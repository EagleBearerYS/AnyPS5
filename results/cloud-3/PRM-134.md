The field names after `;` are my annotations; spirv-dis prints none.

**Confirmed: eight adjacent `OpLoad`s of `header + k`, each through its own `OpAccessChain`** on the `table_map` SSBO, with `header` a per-lane `OpSelect`.
- Lines 3083-3104 of the disassembly cover the first lane half. The second half is the same block at lines 4460-4481 (ids `%7407`-`%7430`).
- The other two nested lookups have the same eight-load shape: the pc 0xa8 T# (fallback header 8) and the pc 0xfc S# (fallback header 24). That makes six such groups in the module.

**Nothing between the loads would stop a compiler combining them:**
- There is no `OpLabel` or branch, no barrier, no call, no store, and no memory operand on any of the eight loads.
- The next use comes right after: `OpISub`/`OpUDiv` on the key offset, then `OpULessThan` against `%4427`, the key count.
- No `Volatile` or `Coherent` appears anywhere in the module.

**Memory model and `table_map`:**
- `OpMemoryModel PhysicalStorageBuffer64 GLSL450`, which is not the Vulkan memory model.
- `%table_map` is an `OpVariable StorageBuffer` of a `Block` struct holding one `OpTypeRuntimeArray %uint` (`ArrayStride 4`).
- It is decorated `DescriptorSet 0`, `Binding 64`, `NonWritable`, and nothing else.
- So eight consecutive, read-only word loads at `base + 0..7`, with `base` only 4-byte aligned (the root codes 0x41, 0x7c are not multiples of 4 words), are a natural target for a backend to merge into wider or block loads.

**The reading fits the module but can't be proven from here.** The module offers no other way for a correct `mapStart`/`keys` to pair with a wrong `baseLow`/`fault` from the same `header`: the index arithmetic is shared, and each word has its own access chain. Whether IGC merges these loads is invisible at the SPIR-V level, and I can't run IGC here.

**The `0x290000000a4` fault address:**
- No row word holds it, which agrees with the decoder's "no row holds the reported word or address". The faulting values never appear in any of the 256 traced rows, all fault-free (`0 would fault`).
- **Low word `0xa4`** can be formed as `offset + 4`: the T# lookup's address is `baseLow + (offset & ~3) + column.offset`, with offset `0xa0` and column offset 0, so it would take a `baseLow` of 4. In this map layout 4 is `map[0]`, the header's version word, which the shader also reads through index 0 for unselected lanes.
- **The other candidate is the S# lookup at the same pc**, which this trace doesn't record. Its fault also reports pc 0xfc, and its address is `baseLow + 0x20` (the S# at V#+0x20). So `0xa4` there would take a `baseLow` of `0x84`, which is the `mapStart` word of the T#'s child header `0x7c` (`map[124]`).
- **High word `0x29`** is not the child header's `TableBaseHigh` (`0xbf` in his log) plus any carry. In this layout `0x29` is `map[40]`, the `mapped` word of the pc 0xa8 child `0x20`.
- **What this rules in.** Either value means an upper header word returned another load's value. That is the same signature as the poison form, where `baseLow` came back as `0x104` (lane header × 4) and `fault` as `0xeddfd600`. That is `map[189]`, a record word that only the root search of the *other* lanes reads: those holding pointer `records[1]`. The lane that showed it holds `records[0]`, whose search reads `map[186]` and `map[183]`. I can't tell from the quoted rows which of the two lookups recorded the fault.
- **A cheap next diagnostic** if this variant doesn't settle it: also trace the S# lookup at pc 0xfc.

## 2. The variant (`448c6ad5da`)

**The form: the `Volatile` memory operand on the dynamic-header field loads.**
- `LoadTableMap` and `TableMapAt` take an optional memory-access mask (default `None`, which emits the same instruction as before).
- `LookupTableWord`'s `field` lambda passes `spv::MemoryAccessVolatileMask` only when `dynamicHeader` is set.

**Why this form:**
- Under the GLSL450 memory model the `Volatile` operand is valid on `OpLoad`, and spirv-val accepts it.
- It is per load, so `mapped`, the image record, the root search and every static-header load stay as they were.
- Compilers treat each volatile access as its own memory operation: they won't merge, eliminate or reorder it against other volatile accesses. That is the property the experiment needs.
- No decoration could do this. `Coherent`/`Volatile` decorations apply to whole variables or members and would change every `table_map` load.
- In the emitter's own passes, `SpirvSpecialization`'s `PureInstruction` treats a load with a memory operand as impure, so specialization won't drop or move these loads either.

**Scope:**
- It is always on in this branch. The trace argument already bypasses the shader cache, and the plain tests run with `ANYPS5_NO_SHADER_CACHE=1` under ctest.
- It changes every nested lookup's child header, not only pc 0xfc's: in this module, the T# at 0xa8, and the T# and S# at 0xfc, in both lane halves.

## 4. Decoder fix (`c513beff6f`)

**Rule:**
- A line containing `[gpu]` or `image table:` takes the lines that follow it, joined with no separator, until a line that starts a known line.
- Known starts: an empty line, `[`, `trace `, `  map[`, `  trace g`, `AGC `, `pointer `, PowerShell's `At line` and `+ ` lines, and `<program>.exe : `.
- No separator is needed because a console wrap only inserts a line break, even in the middle of a number.

**Check 1: wrapped at 120 columns.** The fault line of `--pointer-vsharp-child-key-arm-trace`'s run 4, wrapped like this:

```
[gpu] deferred write-back failed: image table: shader 0x55e98165c310 stage 4 pc 0xfc selected the descriptor at 0xc16000
55e96a0bf0: outside the snapshot
```

- The decoder at `992d97fae8` read `fault: descriptor 0xc16000` and `no row holds the reported word or address`.
- At `c513beff6f` it reads `fault: descriptor 0xc1600055e96a0bf0: outside the snapshot, word 0x80000000` and `64 lanes hold it (code, root.code): g0 l0-63`.
- The whole report is byte-identical to the one for the unwrapped log (same md5).

**Check 2: PowerShell 5's form.** The line prefixed with `agc_driver_image_table_tests.exe : `, wrapped at 80 columns, followed by the `At line:1 char:1` / `+ ...` / `+ CategoryInfo` / `+ FullyQualifiedErrorId` lines, saved as UTF-16 with CRLF. Same report, same md5.
