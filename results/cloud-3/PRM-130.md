Worker: cloud-3.

**Setup:**

- Device: lavapipe, llvmpipe (LLVM 20.1.2, 256 bits), subgroup size 8. Mesa is 25.2.8.
- Tests ran as `runner` with `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1 APS5_NO_PIPELINE_JOURNAL=1`.
- There is no Intel hardware here.

## Short answer

1. **Lead a: the sibling isn't spanned on a 32-lane host either. Both programs fall back to two lanes per invocation.**
   - The barrier that forces the fallback belongs to the guest's waterfall loop, not to the `s19` branch.
   - The sibling has the same loop and falls back for the same reason. So "the arm falls back and the sibling doesn't" can't be what separates them.
2. **Lead b: neither two-lane module has a single `NonUniform` decoration.**
   - Arm: 0 of 48 sampled images decorated. Sibling: 0 of 24.
   - At subgroup 8 (lavapipe) and 64 (RADV), every sampled image is decorated in both programs.
   - The sibling passes on the same Intel GPUs with the same undecorated indices, and those indices also differ between workgroups.
   - More importantly, no value that can reach the pc 0xfc fault word comes from an image, sampler or buffer-array access. Only `table_map` loads (one storage buffer at a constant binding) and constants reach it.
   - So EU fusion mixing texture or sampler handles could give wrong texels. It can't produce the poison word (palette base + 0x100).
3. **Lead c: the prototype is on `prm/9969-intel-fix`.** It decorates the table indices at two lanes per invocation, with a test that fails on the old code and passes with the fix.
   - Red/green: shown below.
   - The requested set on lavapipe: 82 of 82 pass before the fix, 83 of 83 after (the 82 plus `spanned_uniformity`).
   - One existing assertion encoded the opposite design ("a single-subgroup workgroup was decorated NonUniform"), so the commit flips it.
   - **Prediction:** from 2, it should not change the pc 0xfc poison on Intel. One run on Intel would settle the EU-fusion lead either way.
4. **Steps 2-4: I found nothing on our side.**
   - Validation, including GPU-AV (which instrumented these dispatches) and sync validation, printed no messages for either test.
   - Both tests pass with every robustness setting.
   - The two-lane modules have no `OpUndef`, no Function or Private variables, no workgroup memory and no barriers. Their only subgroup ops are ballots plus two shuffles in uniform control flow, read from an active invocation.
   - The value (palette base + 0x100) is nowhere in the table map, nowhere in the dispatch's guest memory, and is not formed by any address arithmetic in the module.
   - So under SPIR-V semantics the module can't write that word. What's left is how the Intel driver runs this module. I'm not claiming a driver bug, since I can't show one. Next steps for someone with an Intel GPU are at the end.

## Lead a: the fallback at subgroup 32

```
sib: [spanned-wave] ... falls back to two lanes per invocation: an OpControlBarrier in block %73 of function %68 sits in control flow a per-invocation value decides
arm: [spanned-wave] ... falls back to two lanes per invocation: an OpControlBarrier in block %77 of function %72 sits in control flow a per-invocation value decides
```

The two programs fall back for the same reason.

**What the barrier is.** Both guest programs are a waterfall loop: `v_readfirstlane_b32 s20, v3` / `v_cmp_eq_u32` / `s_and_saveexec_b64` ... `s_xor_b64 exec` / `s_cbranch_execnz` (pc 0x60 to 0x110). Both texture samples sit inside it: pc 0xa8 and 0xfc in the arm, 0xcc in the sibling. In the spanned module:
- Function %72 is `main`, and block %77 is the first block of the waterfall loop body (loop header %76, merge %82).
- The block exchanges the wave's ballot through workgroup memory:

```
%77 = OpLabel
%1060 = OpGroupNonUniformBallot %428 %17 %1053        ; this subgroup's exec bits
%1067 = OpAccessChain %622 %620 %1066                 ; wave_ballot[parity*2 + subgroup]
        OpAtomicStore %1067 %109 %92 %1061
        OpControlBarrier %109 %109 %623
%1068 = OpLoad ... wave_ballot[parity*2]; %1070 = OpLoad ... wave_ballot[parity*2 + 1]
```

- The loop continues on `OpBranchConditional %3700 %76 %82`, where `%3700 = (wave_ballot[2p] | wave_ballot[2p+1]) != 0`. That is the exec mask, rebuilt from two workgroup-memory loads after the barrier.
- Every invocation loads the same words, so the value is uniform in practice. But `SpannedBarrierInDivergentFlow` treats a value loaded from workgroup memory as per-invocation. So the loop, and with it the barrier, counts as decided by a per-invocation value.

**Why that is per-invocation even though the guest branch is on a scalar.** The guest's `s_cmp_eq_u32 s19, 0` arm isn't involved. What decides is the waterfall exit, `s_cbranch_execnz`, an exec mask that the spanned layout has to rebuild across two subgroups. The sibling's block %73 of function %68 is the same code (ballot, `OpAtomicStore`, `OpControlBarrier`).

**Consequence.** On every 32-lane host with spanned waves on (NVIDIA, and Intel per the logs), both programs run the same two-lane module. NVIDIA passes with it. The table map is the same at subgroup 8 and 32: `diff` of the 232 map words printed by the replay is empty for the arm, and empty for the sibling's 191.

## Lead b: NonUniform and where the poison value can come from

**Counts.** The modules are the first check's request, replayed with the target overrides.

| module | sampled images | decorated `NonUniform` | `OpDecorate ... NonUniform` total |
|---|---|---|---|
| arm, subgroup 32, two lanes | 48 | 0 | 0 |
| sibling, subgroup 32, two lanes | 24 | 0 | 0 |
| arm, subgroup 32, spanned (kept) | 24 | 0 | 0 |
| sibling, subgroup 32, spanned (kept) | 12 | 0 | 0 |
| arm, subgroup 8 (lavapipe) | 24 | 24 | 99 |
| sibling, subgroup 8 | 12 | 12 | 62 |
| arm, subgroup 64 (RADV) | 24 | 24 | 99 |
| sibling, subgroup 64 | 12 | 12 | 62 |

The cause is `SpirvEmitter.cpp:327-329`. At two lanes per invocation `oneSubgroup` is true, so `tableIndexNonUniform` is false. Spanned builds behave the same way.

**Descriptor accesses in the arm's two-lane module.** All are without `NonUniform`:
- **Table images:** `table_images_{1,3,4,8,10,11,15,17,18}` (one view per mode), indexed by 4 element values. `%1836` and `%3149` are pc 0xa8's lanes A and B; `%4607` and `%5379` are pc 0xfc's. Each value is `HeaderElementBase` + the record's element, both read from `table_map`.
- **Table samplers:** `table_samplers`, 24 access chains with dynamic indices (pc 0xfc's S# at V# + 0x20, through table 2).
- **Guest samplers:** `%samplers[1]` (18 chains) and `%samplers[0]` (6 chains). The indices are constants; pc 0xa8's S# comes from the SRT.
- **Guest buffers:** `%buffers[0..2]`, 10 chains, all constant indices. The record pointer comes from `%buffers[1]`.
- **Other buffers:** `%table_map` (123 chains), `%bda_pagetable` (28), `%fault_buffer` (8) and `%flattened_srt` (3) are single storage buffers, not arrays.

The sibling has the same kinds of access, with half the image chains and no `%samplers`.

**What reaches the pc 0xfc fault word.** The first of the 16 fault calls at pc 0xfc, traced backwards:

```
%4541 = OpFunctionCall %void %record_bda_fault %uint_9 %4540 %4536 %uint_252   ; reason ImageTable, address, value, pc 0xfc
%4536 = OpBitwiseAnd %uint %4528 %uint_2147483647
%4528 = OpSelect %uint %4472 %4470 %4521        ; root.poisoned ? root.code : child word.code
%4470 = OpSelect %uint %4469 %4416 %4468        ; root fault word (table_map[23]) or the binary-search code
...   every leaf is an OpLoad from %table_map or a constant
```

- The other 15 calls are the image record's flags, the outside-snapshot constant and the driver fault word, each for lanes A and B and for the image and sampler lookups. Their leaves are the same.
- The only non-map inputs are the record pointer's low and high words, `%4260 = OpPhi %1389 %3154 %1576 %79` and `%4259`. That pointer is the guest's `s[44:45]`: either the `s_buffer_load` from `%buffers[1]` or the T#'s dwords read through BDA. It only takes part in the binary-search comparisons, and `word.code` is never assigned from it.
- **Conclusion:** no image, sampler or buffer-array access feeds the poison value. A handle mix-up under EU fusion could change a texel, such as the one "lane 16 is 0x00000000" report, but not produce palette base + 0x100.

## Lead c: prototype on `prm/9969-intel-fix`

- `ShaderMemory.cpp:4971`: the image table check builds a wave64, 64-thread request at subgroup 32, which is the two-lane case. It used to require no `NonUniform` there and now requires it.

## Step 3: SPIR-V audit of the arm's two-lane module (the one Intel runs)

- **`spirv-val --target-env vulkan1.2`:** valid, as are the sibling's module and both spanned modules.
- **`OpUndef`:** none.
- **Function or Private `OpVariable`s:** none. The spanned module has one, `%wave_ballot_parity`; the two-lane module has none.
- **Workgroup memory, `OpControlBarrier`, `OpMemoryBarrier`:** none.
- **Subgroup ops:** 12 `OpGroupNonUniformBallot` (11 in the sibling) and 2 `OpGroupNonUniformShuffle`, at the top of the waterfall loop (block %76).
  - The loop is subgroup-uniform: its exit comes from ballots.
  - The shuffle source is `FindILsb(ballot) & 31`, the invocation that holds the first active guest lane, which is active.
  - The sibling's 2 shuffles are the same.
- **`table_map` loads without a bounds check:**
  - Indexed by a constant (headers): fine.
  - `mapStart + record`: guarded, `Select(inMap, ..., 0)`.
  - Child-header fields at `root.code + i`, and record fields at `code + i`. For the first check these indices come from map words in {0x41, 0x7c} (image) and {0xc0, 0xcd} (sampler), plus 0 to 7, and from records {0x79, 0xb4, 0xc9, 0xd6} plus 0 to 2. All are below 232, the map's length.
  - Pointer binary search: `mapStart + mid*3 + {0,1,2}`, with `mid < count = map[hdr+1]` = 3.
  - So nothing in range for the first check's inputs reads past the map.
- **What the arm has that the sibling doesn't:**
  - an extra table-0 lookup at pc 0xa8 (the T# at V# + 0x4c0: a pointer-keyed root and a child with one key), sampled with a guest sampler (`%samplers[1]`) rather than a table sampler;
  - the `s19` phi on the record pointer, `%4259`/`%4260 = OpPhi (s_buffer_load pointer from %3154) (T# dwords 0-1 from %79)`, which keys the root lookup at pc 0xfc;
  - V# dwords reloaded through that phi (pc 0xc0 and 0xd4).
  - The sibling's root at pc 0xcc is keyed directly by the `s_buffer_load` pointer.
  - The two-lane module is 4572 lines in `spirv-dis` against the sibling's 3236. It has 123 `table_map` access chains against 83, and 48 sampled images against 24.

## Step 4: table words for the first check

Local run: palettes region at `0x7ffc416ed900` (P0), size 0x1000, so P1 = P0 + 0x800. Records region at `0x7ffc416ed700`, size 0x200: records[0] = P0 - 0x200, records[1] = P0 - 0x100.

**Header:** `[0..7] = 4, 0, 2, 0xc, 4, 0xe3, 0xe5, 3` (version, element base, 2 elements, 12 samplers, 4 poisons, element faults at 0xe3, sampler faults at 0xe5, 3 tables).

**Table 0, pc 0xa8.** Header at 8: map 0x38, 3 keys, size 0x40, base = `Table`.
- Root pointer records at 56: `(0, 0, 0x80000002)`, `(records[0], 0x20)`, `(records[1], 0x2c)`.
- Child 0x20: base P0, size 0x600, 1 key, map 0x28 → 0x29 → image record (flags 0, dword3 0x90000fac, element 0).
- Child 0x2c: base P1, map 0x34 → 0x35 → (0, 0x90000fac, element 1).

**Table 1, pc 0xfc.** Header at 16: map 0xb7, 3 keys.
- Root: `(0, 0, 0x80000003)`, `(records[0], 0x41)`, `(records[1], 0x7c)`.
- Child 0x41: base P0, 48 keys at 0x49. Key 2 → 0x79 → (flags 0, 0x90000fac, element 1). Every other key → 0x80000001, except key 0 → 0.
- Child 0x7c: base P1, 48 keys at 0x84. Key 5 → 0xb4 → (0, 0x90000fac, element 0).

**Table 2, the S# at 0x20.** Header at 24: map 0xda.
- Root: `(records[0], 0xc0)`, `(records[1], 0xcd)`.
- Child 0xc0 → sampler record 0xc9 (flags 0, element 0); its outside code is 0xcb (element 4).
- Child 0xcd → 0xd6 (flags 0, element 8).

**Per lane of group 0** (keys {1, 2}):
- Lanes 0-31: record 1 → records[1] → child 0x7c, key 5 → word 0xb4 → element 0, sampler element 8.
- Lanes 32-63: record 2 → records[0] → child 0x41, key 2 → word 0x79 → element 1, sampler element 0.
- No correct load on this path is poisoned, and the fault words at 0xe3 and 0xe5 are 0.

**Searching for palette base + 0x100.** Here P0 + 0x100 = 0x416eda00 and P1 + 0x100 = 0x416ee200. The "P" values in the issue's reports (mrfelek's descriptor 0xde8f3fd840 = palette 0 + 0x40, and gabichuuuuu's) are the same pattern.
- **In the table map:** 0 hits among all 232 words. The only palette-derived words are the child bases P0 and P1 (`map[36], [69], [196]` = P0; `[48], [128], [209]` = P1). Reading BaseLow by mistake gives P0, not P0 + 0x100.
- **In the dispatch's guest memory** (all 6 regions, scanned with `--mem`): 0 hits. P0 is records[0] dword 0 and P1 is records[1] dword 0.
- **In the SPIR-V:** every constant added in the arm's two-lane module is one of 0-8, 12, 32 or 1216 (0x4c0). The constants widened to 64 bits for address math are 0, 20 (0x14), 1216 (0x4c0) and 1220 (0x4c4). None is 0x100 or 0xc0; the only `%uint_192` is the pc argument of the reload's BDA fault calls. Palette-relative addresses come from the V# base plus 0x14 (key), 0x20 (S#), 0x4c0 (the arm's T#), and key*32 plus span offsets of 0-12.
  - The only way to form base + 0x100 is a key of 8 (a key word of `0x0008xxxx`). But then the reported "selected the descriptor at" address would also be base + 0x100, and it is base + 0x40 in both reports.
  - So the value isn't formed in SPIR-V and then sent to the fault word.
- **The fault record has one writer.** `record_bda_fault` takes slot 0 with `OpAtomicCompareExchange` 0→1, and only the winner writes reason, address, value, stage and pc. A record can't mix one fault's address with another's value.

## What I ruled out, and how

| candidate | ruled out by |
|---|---|
| arm falls back, sibling stays spanned | replay at subgroup 32 with spanned waves on: both fall back, same waterfall barrier |
| missing NonUniform makes the arm differ from the sibling | both modules have 0 decorations at 32; the sibling passes on the same Intel GPUs |
| a NonUniform-less descriptor access feeds the fault word | backward trace: only `table_map` loads (constant binding) and constants reach it |
| a wrong table-map word stored by the driver | the 232 map words, printed and checked: no palette + 0x100; same map at subgroup 8 and 32 |
| a guest word read through BDA | 6 regions scanned: no palette + 0x100 |
| a value computed in SPIR-V | no addition of 0x100 or 0xc0; a key of 8 would also move the reported address |
| `OpUndef`, an uninitialized variable, a shuffle from an inactive invocation, a race | none in the two-lane module (see step 3) |
| a torn fault record | single compare-exchange writer |
| a validation or robustness difference | GPU-AV and sync validation clean and instrumented; passes with robustBufferAccess2 off |

## Not tested, and what would settle it on an Intel GPU

1. **Run `prm/9969-intel-fix`** (or cherry-pick `99dabd0848` onto `2a082ea647`; it applies cleanly). If the arm then passes, the fused-EU lead holds after all, despite the trace above. If it still reports pc 0xfc, the lead is excluded.
2. **Capture the pipeline Intel builds:** `APS5_DUMP_COMPUTE_PIPELINES=<dir>` (in `VulkanDevice.cpp`, with `ComputePipelineCapture`). Then replay the capture here and on NVIDIA with `tools/ComputePipelineReplay.cpp`. That shows whether Intel received the module analysed above (subgroup 32, two lanes, required size 32), and replays its exact inputs elsewhere.
3. **A diagnostic build** that also stores, for each lane at pc 0xfc, the raw words the lookup read: `root.code`, the child's `TableFault`, `mapped`, the record's flags and the fault word. Stored into spare output words, it would name the load that returns base + 0x100 on Intel. I can prepare it as a branch if wanted.
4. **A spec note (not built).** The two-lane layout assumes the 32 invocations form one full subgroup. But `computeStageFlags` asks for `REQUIRE_FULL_SUBGROUPS` only when `fullSubgroups` is set, which is spanned builds only; two-lane builds get only `requiredSubgroupSize = 32`. Vulkan guarantees full subgroups only with that flag.
   - This affects the arm and the sibling alike, so it doesn't explain the split.
   - Requesting the flag for two-lane builds where `computeFullSubgroups` is true would remove the dependence.
