The resolution is the one PM-004's note 5 describes. The same resolution was used in all three branches; git's rerere recorded it from the merge and replayed it in the rebases.

- **The RCAS line does not conflict textually.** In test/fsr-on-overlay, git applies FSR's `RecordPresent(..., VK_IMAGE_LAYOUT_PRESENT_SRC_KHR)` cleanly, so the edit had to be made by hand in commit 0e6f4149e.
- Without that edit, with both features on, RCAS would leave the swapchain image in PRESENT_SRC while the overlay's render pass starts from COLOR_ATTACHMENT_OPTIMAL.
- In test/overlay-on-fsr the line falls inside the conflict hunk, so the recorded resolution covers it.
- **Why it is sound:**
  - RCAS's render pass ends in COLOR_ATTACHMENT_OPTIMAL with no layout change.
  - The overlay's render pass loads the image, and its external dependency waits on COLOR_ATTACHMENT_OUTPUT writes before its own colour reads and writes. That is the same dependency the overlay relies on after the drawn path.

## Anything that looked wrong with both on

Nothing functional. Notes:
1. **The silent RCAS edit.** The FSR-onto-overlay rebase needs the RCAS final-layout change described above, which git does not flag as a conflict. Whoever rebases the second PR must carry it; test/fsr-on-overlay has it in 0e6f4149e.
2. **Clear-only presents skip FSR** (FSR's `!clearOnly`), so on those frames the overlay draws over the unscaled clear. That is expected.
3. **The overlay is drawn at window resolution after RCAS,** so its text is neither upscaled nor sharpened. That looks intended.
4. **FSR's cost is not in the GPU line.**
   - The GPU line counts title batches only, not the present passes (cloud-2's notes), so EASU plus RCAS appears in FRAME and FPS but not in GPU.
   - On lavapipe that is up to tens of ms per frame at 4K (cloud-1's PM-004 numbers).
   - Worth a sentence in USAGE.md if users compare them.
5. **Limited validation coverage.** Validation is Ubuntu's 1.3.275 layer, which doesn't know VK_KHR_maintenance8 and says so. A current SDK layer would cover more.
6. **No hardware here.** No GPU, Windows or HDR display, so HDR10 with both on was not presented to a real HDR swapchain. The component tests cover it on lavapipe.
7. **My own slip, caught before pushing.** My first overlay-onto-FSR attempt committed conflict markers in USAGE.md, because a helper loop staged an unresolved file. The tree comparison with test/fsr-on-overlay caught it. I redid the rebase step by step, and only the clean result was pushed.
