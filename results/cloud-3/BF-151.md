## Step 2: what a compared import offers

**How comparison mode detects guest writes.** Nothing detects them at the import itself; each consumer compares a copy it keeps.
- The import unwatches the range. `importAllocation` (GuestBufferMemory.cpp:1755-1768) passes `watchedHostPointer = false` to `GuestMemory::ImportWatched`, and `ImportWatched` ends in `unwatchLocked`, which on Linux unregisters the pages from the write watch (`GuestWriteWatchUnregister`, GuestMemory.cpp:1514-1522 and 1594-1599). `refreshImports` repeats `GuestMemory::Unwatch` for every unwatched import whenever the registry changes (GuestBufferMemory.cpp:1911).
- After that the tracker no longer covers the pages. `Watched`, `UnchangedSince` and `UnchangedSinceAll` return false (GuestMemory.cpp:1640-1667), and `CollectWrites` returns 0.
- "Compared" means every consumer that derives state from those bytes keeps a copy and compares it on its own thread at use time, after `FlushGpuWrites` for the range:
  - writable image mirrors keep `shadow` and copy the 64 KiB blocks that differ on each build (GuestBufferMemory.cpp:55-80);
  - storage textures keep `original` and compare in `StorageTexture::compareUntracked` (Texture.cpp:2489-2530). This is memoized per collect epoch by {`UntrackedHint` or epoch, `NewestStamp`, `ForgetSerial`, recorder `NewestWriteNote`};
  - write-backs store only the bytes that differ from the uploaded copy (`WriteChanged`).
- GPU reads use the import in place and need no copy.

**A generation or "unchanged since" equivalent.** There is no CPU generation for a compared range. Driver and GPU stores into unwatched memory still leave a mark:
- `markWritten` and `storeOwn` call `noteUnstampedStore` (GuestMemory.cpp:1110-1119, 1693-1712, 1738-1748), and `NewestStamp` reads it (GuestMemory.cpp:1121-1129).
- The mark is coarse: 64 KiB block slots, folded into 65536 slots, so a store elsewhere in the same block counts too.
- So a cheap equivalent is "NewestStamp unchanged" (catches driver and GPU stores, same-value ones included) and "bytes equal a kept copy" (catches guest CPU stores of new bytes). A guest CPU store of the bytes already there cannot be seen in comparison mode.

**Ordering against device writes.**
- A recorded GPU write into an import is noted pending in the recorder, and the fill path calls `MarkWritten` at record time (VulkanDevice.cpp `FillBuffer`: `NotePendingWordFill`, then `MarkWritten`). `NewestStamp` therefore moves before the bytes land.
- `checkDccCurrent` already refuses while `PendingWriteOverlaps` holds.
- Reads through `GuestMemory::Read` and `EqualsCommitted` go through the flush hook, which waits for pending results over the range.
- `LandedUniformMetadataByte` takes the keys of a still-pending fill from the recorder.
- So a compare after the pending check sees landed bytes. The copy's stamp is taken after its read, because the read's own flush can store pending results.

**Why `initialDccClear` needs a write generation.**
- The target's samples exist only on the host. Draws never reach guest memory, and CPU reads of the three ranges are refused by the read guard.
- Its initial contents are a fast clear derived from the DCC keys and CMASK; the color bytes are not even read.
- The generation marks "guest memory as of the import". Every later use (`checkDccCurrent`, through `ApplyFastClear` on each acquire) checks it, so a guest change to any of the three ranges since then refuses instead of being ignored. Such a change could be new texels uploaded over the surface, a guest re-clear or decompress through the DCC keys, or a CMASK change.
- Without the check, the resident image keeps rendering over the old clear and the write is lost: stale pixels or a missing clear.
- `UnchangedSinceAll` at the end of the import makes sure the keys were not changed while they were read.
- `absorbDccFill` takes new generations after a whole fill is taken as a new fast clear, so later uses compare against the refilled keys.

## Step 3: the change (contained)

- **Accepting a compared range.** `ComparedHostImportCovers(context, address, bytes)` is true when a live host import marked `unwatched` covers the whole range. It returns false on Windows, so the Windows paths, BF-150's case included, are unchanged.
  In `initialDccClear`, a range that is not watched but is covered this way is read once (`GuestMemory::Read`) and kept as a copy, with `NewestStamp` taken after the read. Watched ranges take their generation as before, and only the watched ones go through `UnchangedSinceAll`.
- **Reuse.** In `checkDccCurrent`, a compared range is current when `NewestStamp` still equals the copy's stamp and its bytes equal the copy (`EqualsCommittedUnsynced`, which bypasses the read guard the resident target has).
  The compare is skipped while the collect epoch and `ForgetSerial` are the ones of the last equal compare, the same memo the texture compare uses. Otherwise the range gets the same refusals as a watched one: "writes to a resident multisampled DCC target or its metadata are not implemented (<plane> range …)", and the pending-write refusal.
- **Refill.** In `absorbDccFill`, metadata that is unwatched but compared, or covered by a compared import, takes the landed uniform key bytes as its new copy. A compared CMASK counts as written when its copy is no longer current. The whole-fill rules are unchanged.
- **Unchanged conditions.** A range unwatched without such an import, for example `GuestMemory::Unwatch` called explicitly, is still refused at the import. The same goes for a partial import, misalignment, overlapping planes, or a watched range that becomes unwatched after the import, unless a whole metadata fill is taken.
- **Debt.** The "Native multisampled DCC fast clears" entry in docs/dev/debt/libSceAgcDriver.md now says ranges may lie in a host import the Linux probe compares. It also says those are compared with a copy once per collect epoch, that a driver store over their 64 KiB blocks counts as a change, that a same-value CPU store is not seen, that a range compared only after the import throws at its next use unless a whole fill is taken, and that compared Windows imports still throw.

**Per-draw cost.** Each use of a resident target with compared ranges costs:
- one `NewestStamp` per compared range (the tracker lock plus a slot read per 64 KiB block);
- at most one memcmp of each compared range per collect epoch. Queue workers bump the epoch at submission start, at `WAIT_REG_MEM` and at drains. A thread that never bumps it (the presenter, the tests) compares on every use.

memcmp on this machine (Xeon @ 2.80 GHz, idle):

| Range | Compare time |
|---|---|
| 0xc4000 bytes | 40-44 µs |
| 1 MiB (the test's color plane) | 65-72 µs |
| 8 MiB | 0.7-0.87 ms |
| 1920x1080 RGBA8 at 4 samples (33 MB) | 6-7 ms |

Memory cost is one copy of each compared range, dominated by the color plane. Watched ranges cost what they did.

There is no per-draw full compare inside one collect epoch. A title that submits often against a large compared target still pays one compare per epoch. Avoiding that would need the color range back in the write watch while the device leaves it alone (not available on Linux: `Rewatch` is Windows-only) or a hash per 64 KiB block; neither is in this commit.

## Step 4: tests (each names its write-watch mode)

`agc_driver_msaa_dcc_compared_import_N`. Modes 0-4 and 6 run in comparison mode, the probe's own choice; mode 5 forces watched imports with `SetImportWatch(Watch)`.

| Mode | Write-watch mode | What it does | Expected |
|---|---|---|---|
| 0 | comparison | color, DCC and CMASK all imported | First draw imports the target; the resolve reads the DCC fast clear (0, 0, 0, 1) plus the drawn sample. A second draw reuses it and resolves the same. |
| 1 | comparison | CPU store of a new byte into the color plane | Next draw refused: "writes to a resident multisampled DCC" (color range, address, size and sample count checked) |
| 2 | comparison | CPU store of a new DCC key | Refused (DCC range) |
| 3 | comparison | same-value driver store (`GuestMemory::Write`) into CMASK | Refused (CMASK range), through `NewestStamp` |
| 4 | explicitly unwatched | color plane `GuestMemory::Unwatch`ed, nothing imported | Still refused at the import: "initial multisampled DCC contents require watched" |
| 5 | watched (control) | imports forced to stay watched | Imports stay watched and the target reads the right clear |
| 6 | comparison | only the DCC plane imported | Fails on main at the DCC range; passes with the change |

Other cases:
- `DccRefillTests` mode 6 (comparison mode forced with `SetImportWatch(Unwatch)`, metadata imported by a GPU `FillBuffer` after the target was made) used to expect "requires watched guest memory". It now expects the whole fill to clear the target to the new color, and requires the metadata to be unwatched exactly in that mode.
- The existing explicitly-unwatched negative case, `DccFastClearTests` mode 4 (`GuestMemory::Unwatch` over the DCC metadata, nothing imported), is unchanged and still refuses on both trees.
