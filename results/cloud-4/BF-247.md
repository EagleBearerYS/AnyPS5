## What each new number counts

### (a) `[mem-census] descriptor pools` and `[mem-census] descriptor pool probes`

**Tracking:** the census's `vkGetDeviceProcAddr` wrapper, installed only with the gate on, already wrapped `vkCreateDescriptorPool` and `vkDestroyDescriptorPool`. It now also wraps:
- `vkResetDescriptorPool`;
- `vkAllocateDescriptorSets` and `vkFreeDescriptorSets`;
- `vkCreateDescriptorSetLayout` and `vkDestroyDescriptorSetLayout`;
- `vkDestroyDevice`, which drops that device's records so a probe can never touch a dead device.

**Records:** for each live pool, its full create-info and every live set in it: layout, layout serial, variable count.

**Pool kind** comes from a thread-local `PoolScope` at the creation site:
- **chain:** `DescriptorCache`'s 1024-set pools, ShaderResources.cpp at `chain.push_back`;
- **dedicated:** `DescriptorCache`'s one-set pools for sets too big for a chain pool, the `CreateSetPool` call in `DescriptorCache::Allocate`;
- **other:** every other pool, e.g. the texture detiler, the presentation pass, LDS, and `ShaderResources`' own pools when the pool cache is off.

**First line, per kind:**
- live pools;
- the sum of requested `maxSets`;
- the sum of requested descriptors;
- live sets;
- the estimated driver bytes;
- create-infos probed and skipped (with their pools and descriptors).

**Then the probe as a whole:**
- create-infos probed: limit 16, and how many were cut by a 1 GiB budget;
- sets allocated;
- failures;
- the process's growth while the probe pools lived;
- the probe's time.

**How the probe measures (the task's preferred way):**
1. **Lock:** it runs under the census tally lock. Every wrapped pool, set, layout and `vkAllocateMemory` call takes that lock, so none of them can change while it runs.
2. **Grouping:** live pools are grouped by create-info (kind, flags, `maxSets`, pool sizes). Pools with a `pNext` chain are never probed.
3. **Order:** groups are sorted by requested descriptors × live pools, and the top 16 are probed. Only pools of the device the census noted are probed.
4. **Per group:**
   - create one pool with the same create-info and measure the delta;
   - allocate the live sets of the group's fullest pool (same layouts, same variable counts) and measure again;
   - keep the probe pools alive until the end, so a driver's freed memory can't be reused by the next probe;
   - destroy all of them.
5. **Measure:** Windows reads `PrivateUsage` (`K32GetProcessMemoryInfo`, `PROCESS_MEMORY_COUNTERS_EX`). Linux reads RSS from `/proc/self/statm`, which is page-exact on this kernel: a 16 KiB to 16 MiB touch read back exactly.

**Estimate per group** = live pools × pool delta + set delta × (the group's live sets ÷ sets probed); negative deltas count as 0.

**Second line:** one entry per probed create-info:
- its sizes;
- its live pools and sets;
- the measured pool KiB, and the KiB of the sets probed;
- sets that could not be allocated;
- the estimate.

**Limit:** the deltas are process-wide, so a probe that runs while other threads grow the heap over-counts:
- **Block 2 of run 1:** read 3044 MiB for the dedicated pools, while the draw cache was still filling.
- **Blocks 3 to 7:** read exactly 2176.5 MiB.

Static scenes, such as the PC's menu+15, are the right place to read the probe.

### (b) Owners nothing erases, on the `driver` line

Each is computed under the owner's own lock at census time. Byte figures are capacity estimates: element size × capacity, and hash nodes as value size + 2 pointers.

- **`resource cache N entries (keys and index, objects, table elements in table structures)`:** `ResourceCache::Measure`, under `GuestMemory::GpuMutex` then the cache's mutex. GpuMutex is held because cached `ShaderResources` are only mutated under it.
  - **Keys and index:**
    - the list and index nodes and the hash buckets;
    - both copies of each key's capacity;
    - the eviction and use trackers.
  - **Objects:** `ShaderResources::HeldBytes` per distinct object:
    - `sizeof(ShaderResources)`;
    - the capacity of its 34 other vectors;
    - the allocations' `dataWords` and the bindings' index vectors;
    - its table structures.
  - **Table elements:** `TableElements()`.
  - **Table structures:** `ShaderResources::TableBytes`, the table stages with their map, poison, messages, element textures and sampler rejections, plus the table writes' runs.
  - **Not counted:** objects held by `shared_ptr` (textures, samplers, BDA resources) or `GuestBufferMemory` internals.
- **`never erased: draw relocations`, `relocation trials`, `draw aliases`:** `Driver::DrawRelocationFootprint`, under `drawCacheMutex`.
  - **Entries:** of each map.
  - **Bytes:** hash buckets and nodes; for each `DrawRelocation`, the object, its control block, `words`, each word's `reads`, and `banned`.
- **`recompiler sources`:** `ShaderRecompiler::SourceFootprint`. It copies the `shared_ptr`s under the table's shared lock, then `try_lock`s each source. A source whose mutex is held (a compile in flight) is counted as busy and skipped, so the census never waits on a compile. Fields:
  - **Keys:** the map's entries.
  - **Sources:** the `SourceEntry` objects.
  - **Table:** buckets, nodes, key and bucket vectors.
  - **Code:** `SourceEntry`, `code` and `linkedCallFallbacks`.
  - **Plans:** the count, deduplicated by pointer, and their bytes: `IrResourcePlan`, its vectors, each arena value with its argument and use vectors, and each block with its predecessors, successors and instruction-list nodes.
  - **IR programs:** the ones held, with their blocks, instructions and resource plan.
  - **SPIR-V:** split into owned heap words and file-backed views, deduplicated by module (`SharedSpirv::OwnedBytes`).
  - **Memo tables:** count × `sizeof(ResultMemoTable)`.
  - **Memo results:** the existing `ResultMemoBytes()`.

### (c) Unattributed private memory, grouped

**Windows: `[mem-census] unattributed private`:**
- **Regions:** the existing `VirtualQuery` walk now keeps every committed `MEM_PRIVATE` region outside the guest arena: begin, end, `AllocationBase`, `Protect`.
- **Heap segments:** `HeapWalk` over every heap from `GetProcessHeaps`, each between `HeapLock` and `HeapUnlock` (RAII).
  - **During the walk:** nothing is allocated. Two vectors are reserved for 65,536 records before any lock, and the line says if they ran out. A heap whose `HeapLock` fails is counted as not walked.
  - **Region entries:** the region's `VirtualQuery` allocation base is taken after unlocking.
  - **Busy entries of 512 KiB or more:** noted the same way. Those whose allocation base isn't a segment are large heap blocks.
- **Grouping:** the private regions whose allocation base is not a heap segment are grouped by allocation base.
- **Printed:**
  - allocations and MiB;
  - a histogram by committed bytes (`<1`, 1-4, 4-16, 16-64, `>=64` MiB, count and MiB each);
  - the 16 largest allocations: base, committed MiB, region count, the protections seen;
  - tags: `(heap block)` for a large heap block outside the segments; `(device memory)` for an allocation holding a `vkMapMemory` pointer of a live allocation (`vkMapMemory`/`vkUnmapMemory` are now wrapped);
  - what was excluded: regions and MiB in segments; segments, with their `HeapWalk` committed bytes; heaps walked and not walked;
  - the heap walk's and the grouping's time.

**Linux: `[mem-census] anonymous private`:**
- **Input:** `SmapsParser`, with recording on, keeps every private anonymous mapping outside the arena: range, Rss, permissions, name.
- **Grouping:** contiguous mappings are grouped into one run, the Linux stand-in for an allocation base (a reservation plus its guard or committed parts).
- **Size:** by resident bytes.
- **Printed:** the same histogram and top 16, with the first name in the run (`[heap]`, `[stack]`, …).

## Findings

**Lavapipe's descriptor memory is per set, not per pool.** Every probe pool cost +0.0 KiB to create.
- **What costs:** each dedicated set of the Village layout costs **16,388 KiB**, measured by RSS on allocation.
  - The set was requested as 2000 sampled images, 2 samplers and 6 storage buffers, with variable count 2000.
  - The layout declares the image table binding with `context.imageTableCapacity` descriptors (`ImageTableCapacityFor`, from the device limits).
  - 16,388 KiB is consistent with lavapipe sizing a set by its layout's descriptor count rather than the variable count. I did not read lavapipe's source to confirm it.
  - Chain-pool sets cost 4 KiB each (136 sets, 544 KiB).
- **Totals:** 136 or 139 dedicated sets × 16,388 KiB = 2176.5 or 2224.5 MiB. That is the whole of the 2203 or 2227 MiB of shared views, apart from the ~23 MiB of device memory.
- **Correction to BF-245:** the 2.2 GB counts sets, not pools; a pool alone costs 0.
- **What this means for NVIDIA:** the PC's ~41.5k sets and ~423k descriptors could cost per set or per pool there. The probe line separates the two: `pool +X KiB` against `N sets +Y KiB` per create-info.

**The never-erased owners don't grow in this harness, block over block or run over run.**
- **Counts:** 4 relocations, 4 trials, 0 aliases and 6 source keys from the first block of both runs.
- **Why:** the harness replays one frame, so it can't show the PC's +922 MiB growth. On the PC, read those columns between menu+1 and menu+15.
- **Bigger holders here:** the draw cache, 255.9 MiB of variants at 3948 entries, and the recompiler's result memo, **124.3 MiB of memo results** under its 256 MiB budget. Both sit in glibc's heap (1372 MiB arena).
