## How #5404 maps onto main's draw cache

#5404 is one commit, 4a0512d742 on 18c438b109 (`Driver.hpp`, `Draw.cpp`, `DrawCache.cpp`, `DrawCacheStatistics.cpp`, +32/−1). #5407 has the same head.

| #5404 | main (this branch) |
|---|---|
| `drawCacheBypassed()`: a CAS countdown of `drawCacheBypassLeft` | `DrawCacheBypass::Skip()` (`DrawCache.hpp`/`DrawCache.cpp`), the same relaxed CAS countdown |
| `noteDrawCacheOutcome(hit)`: `Window = 2048`, `MinHitsPerWindow = Window / 20` (102), `BypassDraws = 16384`, relaxed atomics, window reset by `exchange`/`store` | `DrawCacheBypass::Note(hit)`: the same constants, with the minimum as `Window * percent / 100` (102 for 5, the same integer); the same atomics; `percent` 0 returns at once |
| `useDrawEntries = drawEntries() && !drawCacheBypassed() && ...` | the same position in `Driver::draw` (`Draw.cpp`). A bypassed draw is counted in `drawEntryCounters.bypassed` under `drawCacheMutex` |
| `if (useDrawEntries) noteDrawCacheOutcome(drawHit)` after `lookupDraw` | `if (stageEntries) drawCacheBypass.Note(drawHit \|\| verifyHit)` after `lookupDraw` |
| `APS5_NO_DRAW_CACHE_BYPASS` (presence) | `APS5_DRAW_CACHE_BYPASS_PERCENT` (integer, default 5, 0 = never) |
| one `ProfilePrint` line with the 10-s bypassed count, from a separate atomic | the same line in `profileDrawCacheLines`, from `counters.bypassed`, naming the percent |

**Two mapping choices, because main's statistics changed:**
- **What counts as a lookup.** Main passes `stageEntries` (that is, `useDrawEntries` except for tessellated, instanced, non-indirect draws) to `lookupDraw` as its gate, where #5404's base passed `useDrawEntries`. A draw that skips the stage lookup has no cache outcome, so it is not noted. Counting it as a miss would push tessellation-heavy scenes into the bypass.
- **What counts as a hit.** A hit is `drawHit || verifyHit`: every stage equal, the same event as `counters.hits` in the `[draw-cache] ... hits` line (BF-108's "~4% hits").
  - `verifyHit` is the same hit under `APS5_VERIFY_DRAW_ENTRIES`, which clears `drawHit`. Without it, verification would bypass the cache it is meant to verify.
  - Main's partial reuse — data-only hits (`dataHits`), register-key decode skips and stage data hits — doesn't count, as #5404 didn't count decode skips. The bypass gives it up for the bypassed draws, which is where the bench's decode and capture costs come from.

**What a bypassed draw skips:** everything `useDrawEntries` gates on main.
- the register key, the entry lookup and relocation;
- stage-entry lookups and inserts (`cacheDrawStages` requires `useDrawEntries`);
- data hits.

It takes the same path as `APS5_NO_DRAW_SRT_ENTRIES=1`, the "draw cache off" the PC measures.

## Red/green

**The test:** a new mode, `--low-hit-bypass`, in `agc_driver_draw_cache_reuse_tests` (`tests/execution/DrawCacheReuse.cpp`), with two ctest names:
- `agc_driver_draw_cache_low_hit_bypass` (default knob);
- `agc_driver_draw_cache_low_hit_bypass_off` (`APS5_DRAW_CACHE_BYPASS_PERCENT=0`).

It uses only counters main already has (`lookups`, `hits`, `inserts`), so it runs against main's code. It runs in a fresh process, about 22,500 draws, and takes 6.6 s on lavapipe.

| step | draws | default knob | knob 0 |
|---|---|---|---|
| a constant pixel shader at 0.25, cached path | 3 | 2 misses, 1 hit, writes 64 | same |
| a window with exactly 102 hits (102 / 2048 = 4.98%) | 2,045 (window total 2,048) | 2,048 lookups, 102 hits: **no bypass** (the next window is looked up) | same |
| a window with 101 hits | 2,048 | 4,096 lookups, 203 hits | same |
| the constant draw at 0.25, then at 1.0 | 2 | **not looked up, not inserted**, writes 64 (the cached path's value) and 255 | looked up (+2), same colours |
| the rest of the bypass | 16,382 | lookups and inserts unchanged | — |
| the draw after 16,384 bypassed draws | 1 | **looked up again and hits** | — |
| a window of repeated draws | 2,047 | all hit | — |
| 10 more draws | 10 | 10 lookups: a 100%-hit window **does not re-arm** | — |

**Resume:** yes. As in #5404, lookups resume after 16,384 bypassed draws and a new window is measured; a window at or above 5% keeps the cache on, and one below arms it again.

**Red (main's driver code, test kept):** `agc_driver_draw_cache_low_hit_bypass` fails with "with the default 5% bypass: draws after a window of 101 hits in 2048 lookups were still looked up or inserted". Its window counts (2,048 with 102 hits, 4,096 with 203) held on main, so the test's draw accounting is right. `_off` passes on main, as main never bypasses. The other 6 draw-cache-reuse entries pass. **1 of 1 new default case red.**

**Green:** 8 of 8 `agc_driver_draw_cache_(low_hit|reuse)` pass, both new cases included. That holds on 2800de0daf (main e05ba6feeb) and again on the final layout, 5729d4237b (red repeated there with the same message). Under the validation layer, all 17 draw-cache tests pass (below).

**Which head each run used:** the bench and the validation runs used 2800de0daf. Its driver code is the final head's, except that `bypassed` sits on a different line of `DrawEntryCounters`.

**Reading the bench:**
- **High-hit workload:** no slowdown. The bypass never arms, and wall and driver work match main's within run-to-run noise.
- **~4% workload, what it removes:** the bypass takes out the lookup (about 20 µs per packet) and almost all of the cache's memory: 7.8 to 0.2 MiB counted, and about 50 MiB of VmHWM.
- **~4% workload, what it costs:** about 7 µs more decode and 9–11 µs more capture and recompile per packet, as main's partial reuse goes too.
- **Wall time:** on lavapipe it is set by the GPU lock: about 150 µs of each packet is lock wait. So wall time doesn't move.
- **The prepare-thread saving:** against the same build at knob 0, it is +0.5 µs per packet at 1080p and −7.3 µs (−7.5%) at 64×64.
- **Where a gain could show:**
  - With the large captures BF-108's lane variant made (~1 MiB each; 6.8 against 3.75 ms per draw with the cache off), the bypass would avoid the capture-and-insert cost; this table mode doesn't show that.
  - A faster GPU path would also expose the prepare thread more than lavapipe does.
- **For Village:** whether either holds is the PC's run.

## Draft PR body

Title: `perf(agc): bypass the draw cache while its hit rate is under 5%`

```
### What
Ports #5404 by bcortezf (closed on 10-22) onto the current draw cache, with him as co-author. After a window of 2048 draw-cache lookups with fewer than 5% hits (every stage equal), the next 16384 draws neither look up nor insert draw entries; lookups then resume and a new window is measured. A draw that does not look up its stage entries is not counted, and a hit under APS5_VERIFY_DRAW_ENTRIES counts as a hit.

APS5_DRAW_CACHE_BYPASS_PERCENT sets the threshold (default 5, 0 never bypasses), so one build can compare main's behaviour with the bypass. A bypassed draw takes the APS5_NO_DRAW_SRT_ENTRIES path, so it also gives up main's partial reuse (register-key decode skips, data and stage-data hits). The profile prints `[draw-cache] bypassed N draws (10 s)`.

Village: pending (PC). Resident Evil Village (PPSA01556) measured +32% with the draw cache off on 10-21, with about 4% hits in its menu.

### Tested
Linux (Ubuntu 24.04, gcc 13.3, lavapipe), CI flags. agc_driver_draw_cache_low_hit_bypass checks that a window of 102 hits in 2048 lookups keeps the cache, 101 hits bypasses it for 16384 draws that are neither looked up nor inserted and still render the cached path's colours, and lookups resume and stay on after a full-hit window; it fails on main. agc_driver_draw_cache_low_hit_bypass_off checks that 0 never bypasses. The draw-cache tests pass under VK_LAYER_KHRONOS_validation with no VUID that main does not give. Lane bench (VillageDrawCost, 3 runs each, lavapipe): at 3.3% hits the bypass cuts the counted draw-cache memory from 7.8 to 0.2 MiB with ms per draw unchanged; at 96% hits there is no slowdown. Full ctest: 2168 passed, 91 skipped, 6 failed (the IPv6 socket tests; the test machine has IPv6 disabled). No title tested.
```
