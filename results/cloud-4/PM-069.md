## Findings, ranked

### Blocking

None. Nothing found makes the PR wrong with the variable unset, and with the variable set every behaviour is the documented one.

### Should fix

**1. The refusal applies to titles that never opted into resolution detection, which a console probably never refuses** (needs the user's decision; not pushed).
- **Code:** `exceedsConfiguredOutput` (Buffer.cpp:26-31) has no title condition. `sceVideoOutRegisterBuffers2` refuses on it (Buffer.cpp:173-180).
- **Evidence (not measured):** KytyPS5 at b82512be06, `VideoOutGetOutputStatus`:
  - `status->resolution = ((attribute3 & 4) != 0 && ctx->width < 3840 && ctx->height < 2160 ? 1u : 2u);`
  - under the comment "Primary output reports 4K unless param.json Video-out Info enables resolution detection".
- **What follows if that is the console's rule.**
  - A title with attribute3 & 4 clear is told 4K on every console. Resident Evil Village is one (PRM-036).
  - A console set to 1080p must then accept that title's 4K buffers, or the title would fail on every 1080p TV.
  - So the branch refuses exactly the titles least likely to have a fallback.
- **What such a title gets** (checked below): `sceVideoOutSubmitFlip` stops it, `sceVideoOutSubmitEopFlip` fails, and GPU flips show black.
- **Safer behaviour:**
  - Refuse only when `(GetAppAttribute3_nid_no_patch() & 0x4u) != 0`. That is one line in `exceedsConfiguredOutput`, plus a one-time log that the title doesn't declare resolution detection.
  - Planet of Lana and Animal Well have the bit (PRM-036), so they keep the refusal. Village would keep rendering 4K under the setting instead of risking a stop.
  - The tests' `VideoOutTestEnvironment` writes no attribute3, so the refusal cases would need it to write `"attribute3":4`, and one case without the bit that is not refused.
- **Why not pushed:**
  - It changes which titles the PR helps, and it rests on KytyPS5's unmeasured model.
  - If titles without the bit do fall back on a console, it removes the PR's effect for them.
- **To settle it:** one boot of Village with `ANYPS5_OUTPUT_RESOLUTION=1920x1080` on bfc348462a. Does it fall back, stop or show black?

**2. A title that retries the refused registration hangs after one log line.** Fixed: **ec4a01c07**.
- **Code:** Buffer.cpp:173-178 at bfc348462a logs behind a `static std::atomic<bool>`, once per process.
- **Checked by running** a scratch probe: a temporary mode of `guest_video_out_output_sequences`, not committed, file restored.
  - Under Xvfb with `ANYPS5_OUTPUT_RESOLUTION=1920x1080`, three 3840x2160 `sceVideoOutRegisterBuffers2` calls each returned INVALID_RESOLUTION, and stderr had one `[videoout] refused` line.
- **The fix:** log at the 1st, 2nd, 4th, 8th and later power-of-two refusals, with the count (`(refusal 2)`). The answers themselves are unchanged.
- **Untested:** these tests don't capture stderr, so no test checks it. Under Xvfb the sequence tests print "(refusal 1)" and "(refusal 2)" as expected.

### Fixed (tests and docs)

  - It registers a 2560x1440 set, which must stop with an error naming `ANYPS5_OUTPUT_RESOLUTION`.
- **Does the PS4 path refuse?** Yes, by throwing (`refuseUnknownResize`, Buffer.cpp:223). The debt entry says the console's answer there is unknown. That is AGENTS.md's rule for unknown behaviour, so it is not a finding.

### Notes (no change made)

**6. Error code and bus.**
- **Code:** `VIDEO_OUT_ERROR_INVALID_RESOLUTION = -2144796667` (VideoOutDriver.hpp:31) is 0x80290005.
- **Sources:**
  - shadPS4's `videoout_error.h` names it `ORBIS_VIDEO_OUT_ERROR_INVALID_RESOLUTION = 0x80290005`, next to INVALID_VALUE 0x80290001, INVALID_INDEX 0x8029000A and INVALID_HANDLE 0x8029000B, which match our constants.
  - SharpProspero names the same value. Its `DisplayDevice.Open` remark, quoted in PRM-036, is the source for "refused with 0x80290005".
- **Bus:** only `VIDEO_OUT_BUS_TYPE_MAIN` is refused (Buffer.cpp:17, :28). That fits a per-output rule, and the overlay and sub buses keep main's behaviour.
- **Not verified on a console.**

**7. Which calls refuse, and where the check sits.**
- **`sceVideoOutRegisterBuffers2` (Buffer.cpp:173):**
  - It returns INVALID_RESOLUTION after the argument checks and the guest-memory checks of the attribute and buffer array.
  - That is before `CommitBufferGroup` (Buffer.cpp:62-99) takes the port lock and runs its closing-handle, occupied-set and occupied-slot checks and `DescribeVideoOutBuffer`'s attribute validation (reserved bits, tiling, category, DCC).
  - So with the setting, a too-large registration that would otherwise throw for one of those (an unimplemented attribute, say) gets INVALID_RESOLUTION. The console's order is unknown. I would keep it: a title then falls back with the same attribute, and the throw follows.
- **PS4 `sceVideoOutRegisterBuffers` (Buffer.cpp:223):** throws after the option and tiling checks, before the pixel-format check and `CommitBufferGroup`.
- **`sceVideoOutSubmitChangeBufferAttribute2` (Buffer.cpp:261):** throws after the lock, index, occupied and attribute-memory checks, before each buffer's `DescribeVideoOutBuffer`.
- **Nothing else sets a size.** No other export sets a display buffer's size: `sceVideoOutSetBufferAttribute` and `sceVideoOutSetBufferAttribute2` only fill the structure, and the full export list of Buffer.cpp, Output.cpp and Event.cpp was checked.

**8. The reported resolution applies to every bus; the refusal and the log only to the main bus.**
- **Code:** `reportedResolution` (Output.cpp:38-41) has no bus check, so an overlay or sub port also reports the setting.
- **Overlay:** composited over the main output (debt entry "Overlay output bus"), so reporting the main output's resolution there is plausible.
- **Sub bus:** unknown.
- **Docs:** silent on both.

**9. 1440p reporting.** The 2560x1440 setting reports 2560x1440 to titles that never called `sceVideoOutAllowOutputResolutionWqhdDetection` (Output.cpp:131, unchanged). The first new debt entry already records this as unknown.

**10. With the variable unset: unchanged.**
- **By reading.** `ConfiguredVideoOutOutputResolution_nid_no_patch()` is `std::nullopt` for unset or empty, and then:
  - `reportRegisteredSize` returns at once (Buffer.cpp:17);
  - `exceedsConfiguredOutput` returns false (Buffer.cpp:28), so `refuseUnknownResize` and the refusal never fire;
  - `reportedResolution` returns the port's own size (Output.cpp:39-40), the same expression main used in `outputStatus` and `GetResolutionStatus`.
  - The only other new call is the parse in `sceVideoOutOpen` (Output.cpp:107), which with the variable unset parses nothing.
- **By running:** per-test JUnit comparison with main, below. `guest_video_out_output_resolution_unset` and `guest_video_out_output_sequences_unset` pass under Xvfb.

**11. Parsing and sizes.**
- **Accepted values:** exactly `1280x720`, `1920x1080`, `2560x1440` and `3840x2160`. Every other value throws at the first `sceVideoOutOpen` with the variable named (`_invalid` case). Empty counts as unset.
- **Odd inputs:** the unit test `video_out_output_resolution` covers 19, including case, spaces, a trailing newline, leading zeros, negatives and 0x0.
- **Real outputs:** all four are PS5 output resolutions.
- **Off-list buffer sizes** no larger than the setting are taken, as the debt entry says.

**12. The getters agree.** At every setting, `RequireReports` checks `GetResolutionStatus` full and pane, `GetOutputStatus`'s class, and `GetOutputStatusWithVrr`'s first 48 bytes (equal to `GetOutputStatus`), plus equal refresh rates. They passed at all 6 settings under Xvfb.

**13. Docs.**
- **The two new debt entries** (`docs/dev/debt/libSceVideoOut.md`) say what the code does: the class values, the main-output rule, the 1920x1080 exception, 2560x1440 at the two larger settings, the throws, and KytyPS5's competing model.
- **`USAGE.md`** is right after finding 5's fixes.

**14. Pre-existing, not this PR:** `sceVideoOutSubmitChangeBufferAttribute2` doesn't update `cfg.width`/`cfg.height` (Buffer.cpp:269, against :89-90 for a registration). So without the setting, `GetResolutionStatus` keeps reporting the registered size after an attribute change.

## A title that doesn't handle the refusal (checked)

The same scratch probe, `ANYPS5_OUTPUT_RESOLUTION=1920x1080`, Xvfb, after a refused 3840x2160 registration of set 0:
- `sceVideoOutRegisterBuffers2` 3840x2160 = INVALID_RESOLUTION, three times, with one log line (before ec4a01c07).
- `sceVideoOutSubmitEopFlip(handle, 0, …)` = 0x8029000a (INVALID_INDEX).
- `sceVideoOutSubmitFlip(handle, 0, …)` throws "sceVideoOutSubmitFlip: VIDEO_OUT_ERROR_INVALID_INDEX", which stops the title.
- **Not run:** a GPU (command-buffer) flip of the unregistered buffer presents black and completes (VideoOutDriver.cpp:83-85). The title would run and show nothing.

So it stops, loops silently (now with a rising count in the log), or shows black, depending on how it flips. Finding 1 is the safer behaviour for titles that never fall back.
