## 1. The reading: refuted by the code

The reading has two parts: a store counts only if it is newer than the stamp at which queue 0x20's *worker received* the wait; so a slot recycled between the 1 and the worker's receipt never satisfies the wait. **Main already counts both the value at submission and every store after submission:**

1. **The wait's stamp is its submission, not the worker's receipt.**
   - `Driver::Submit…` sets `submission.received = ++eventSerial` (`Execution/src/Driver/Queues/Submission.cpp:389`), on the submitting thread, under the driver mutex, before `enqueue`.
   - `PacketExecution.cpp:408` passes that `submission.received` to `waitMemory`.
   - The label stores are stamped when a worker executes them (`++eventSerial` at `PacketMemory.cpp:45`, `:367`, `:377`, `DeferredLabels.cpp:116`), and noted with `noteLabelStore` (`LabelHistory.cpp:9-19`).
   - So `storedSince` (`LabelHistory.cpp:21-41`, called at `WaitMemory.cpp:144` and `:339`) already accepts any matching recorded store **after the wait's submission**. That is the proposed fix.
2. **Main also takes the value at submission.** When a submission is accepted, `noteHeldAtSubmit` (`Submission.cpp:503-530`, called at `:253` for each packet) reads the awaited word of every memory `WAIT_REG_MEM`/`_64`. If that value already satisfies the wait, the cursor goes into `heldAtSubmit`, and `waitMemory` returns at once (`WaitMemory.cpp:143`). It skips this when:
   - the packet isn't a memory wait (`(packet[1] >> 4) & 3 != 1`);
   - the address is misaligned or not accessible;
   - an earlier `RELEASE_MEM`/`WRITE_DATA` in the same submission writes the dword (`labelWrites`);
   - the waiting queue's unfinished submissions write it (`unfinishedWrites`).
3. **So the scenario can't hang on main, whichever side of the submission the 1 lands on.** The scenario is: queue 0 stores 1, the label is recycled, and only then does the queue 0x20 worker reach the wait.
   - If the 1 was stored after the wait's submission, the history satisfies the wait.
   - If it was stored before, and nothing overwrote it before the submission, `heldAtSubmit` satisfies the wait.
   - The only remaining gap is an overwrite before the submission. Then the wait would also see the overwrite on hardware.

## 2. The model test: both cases pass on main, so there is no red

`LabelWaitHistory.cpp` uses queue 0 as producer (a DCB with `RELEASE_MEM` of 1, data_sel 1, int_sel 0) and queue 0x20 as waiter (an ACB with `WAIT_REG_MEM` function 3 equal on a gate label, then `WAIT_REG_MEM` function 3 equal ref 1 mask 0xffffffff on the label, then `WRITE_DATA` done = 1).
- **The gate:** the CPU writes it after overwriting the label, so the queue 0x20 worker reaches the label wait only after the recycle. It stands in for the worker's lag.
- **The overwrite:** the CPU writes `0x21061300`, a slot-address-like link.

| case | order | main | what satisfies it |
|---|---|---|---|
| `StoredAfterSubmission` | waiter submitted, then the producer's release (1), then the CPU overwrite, then the gate opens | ends within 800 ms | the store history |
| `HeldAtSubmission` | the producer's release (1) lands and the queue is idle, then the waiter is submitted, then the CPU overwrite, then the gate opens | ends within 800 ms | `heldAtSubmit` |

- **Trace of the second case** (`APS5_TRACE_GPU=1`): `queue 0x20 waits 0x…0100 == 0x1 (now 0x1)`, then `queue 0x20 waits 0x…0000 == 0x1 (now 0x21061300)`, then `done serial=2 queue=0x20` in the same millisecond.
- **Each case pins its mechanism** (scratch edits, not committed, sources restored afterwards):
  - With `storedSince` returning false: exit 1, `label wait history: a wait whose label was stored after the wait's submission and overwritten before the queue reached it did not end from the store history`.
  - With `heldAtSubmit` never filled: the first case passes, then exit 1, `label wait history: a wait whose label held its value at the wait's submission, and was overwritten before the queue reached it, did not end from the value at submission`.
- **No red for the reading itself.** A test meeting the task's conditions (store 1, overwrite, the wait received later, the submission before the overwrite) ends on main in both orders. That is why there is no fix commit, and the branch is `exp/…`. The test stays as a regression test for the two mechanisms.

## 3. Other readings that fit the posted lines

From #6558 (read on the public page; nothing posted):
- **Kena (run_111548):** the producer is `DMA_DATA 0x1021061280: 46306000 00000000 00000000 21061280 00000010 00000004`. Control `0x46306000` has src_sel 2 (data), data 0 and a 4-byte count: a reset to 0. It is followed by `RELEASE_MEM 0x1021061280: 0600c528 20010000 21061280 00000010 00000001` (data_sel 1, int_sel 0: writes 1, no interrupt, so it takes the deferred-label path).
- **The rerun:** "the stalled wait is the first of the five `WAIT_REG_MEM` of queue 0x20 #14 serial 7730". Wait 4's producer is in queue 0 serial 7729. The page doesn't say where wait 1's producer is. Queue 0x20 is itself a producer to these slots ("`DMA_DATA ... <addr> 00000010 00000004` followed by `RELEASE_MEM ... <addr> 00000010 00000001`, in queue 0x20 submissions").
- **Sifu:** `value 0x0`, then `recorder: table miss (refusal 0), open batch writes it 0, snapshot write overlaps 0, pending completion labels 0…`.

The readings that remain:

1. **The producer's 1 never executed by the time of the timeout.** The likeliest, given value 0: the producer's `DMA_DATA` reset ran but its `RELEASE_MEM` didn't, and Sifu shows no pending completion label for it. That would be a cross-queue ordering stall: the producer's submission sits behind another wait, possibly one that needs queue 0x20 to pass this very wait (queue 0x20 is single-threaded per queue id; each queue id 0x20-0x57 has its own worker, `Submit/src/Acb.cpp:13`). The watchdog's per-queue submission list (StallWatch) in the same log shows it. #6558's rerun has that list ("the watchdog prints recent submissions from each queue"), but the page doesn't quote wait 1's producer.
2. **`heldAtSubmit` skipped because queue 0x20 still had unfinished label writes to the slot** (`Submission.cpp:525`). Queue 0x20 also produces into these slots, so a pending earlier queue-0x20 submission that releases the same recycled slot turns off the at-submission check. The history then needs a store after the submission. In that case, a 1 stored before the submission and overwritten after it would hang. This is the narrowest path that reproduces the reading's symptom on main. It needs a pending queue-0x20 release to the same dword at the waiter's submission. It isn't modelled here, because whether hardware would also wait there depends on that release's value.
3. **The store-history capacity:** 4 stores per dword (`LabelStoreHistory = 4`, `LabelStores.hpp:9`). A slot that gets 4 or more recorded non-matching stores after the matching one, before the worker checks, loses it. With the producers' reset-then-release pattern each reuse records a 0 and a 1, so a 1 stays in the window unless resets pile up without releases.
4. **Stores that aren't recorded:**
   - CPU writes, by design;
   - stores over 64 bytes or misaligned (`KeepsLabelStore`);
   - end-of-pipe `RELEASE_MEM` labels whose `WriteLabelOnGpu` returns 2 or 3 (`PacketMemory.cpp:47-49` notes only 0, 1 and 5);
   - shader stores.

   A 1 written that way after the submission is invisible to the history. Kena's release has int_sel 0, so it isn't the interrupt path.
5. **The compare:** ruled out for these lines. Function 3 (equal), mask `0xffffffff`, 32-bit `WAIT_REG_MEM`; `storedSince` handles 4 and 8 bytes. PRAGMATA's `WAIT_REG_MEM_64` with `ref 0x63` is a different case.
6. **Hi-Fi RUSH's ~85 ms per frame with `table miss`:** these waits end, so it is not this hang. It is consistent with reading 1 (the producer runs late each frame), not with a recycle.
