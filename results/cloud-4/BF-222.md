### 2. `sceNpWebApiUtilityParseNpId`: pass

**Source:** [shadPS4 e0845a12dc `np_web_api.cpp` L598-L630](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/np/np_web_api/np_web_api.cpp#L598-L630), unchanged since 68818c769a, which BF-215 cited.
- A null JSON string returns `ORBIS_NP_ERROR_INVALID_ARGUMENT`.
- Otherwise it decodes the string as base64, splits at `@`, and takes the handle (at most 16 bytes) and the segments after `@` with `/` and `.` removed (the 8-byte `opt`).
- With a non-null `pNpId`, it clears the 36-byte record, copies the handle and `opt`, and sets `reserved[0] = 1`, which its comment says the PRX does.
- It returns 0.

**Layout:**
- shadPS4's `OrbisNpId` is `OrbisNpOnlineId handle` (16 + terminator + 3 = 20), `opt[8]`, `reserved[8]` = 36 bytes ([`np_types.h` L29-L39](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/np/np_types.h#L29-L39)).
- The tree already has this record as `NpIdFull` (`core/libs/prx/libSceNpCommon/include/Api.hpp:44`, `static_assert(sizeof(NpIdFull) == 36)` at `libSceNpCommon/Export.cpp:25`). `ParseNpId` should use that type, not a new local one.

**Is the shared `NpId` wrong? Yes.**
- `core/libs/SceTypes.hpp:1505`, `struct NpId { NpOnlineId online_id; std::uint8_t opaque[4]; }`, is 24 bytes, against the 36 of `OrbisNpId`, `NpIdFull` and Orbital's `SceNpId` users.
- Its users today don't read or write past byte 24: `sceNpGetNpId` returns signed-out without writing (`libSceNpManager/Export.cpp:802`); the `NpStateCallback` and `sceNpTssCreateNpTitleCtx` declarations only pass a pointer.
- So nothing misbehaves yet. The first function that fills an `NpId` would write 12 bytes too few, and `opt` and `reserved` would sit at the wrong offsets.
- Fixing it means replacing `NpId` with the 36-byte layout and checking `sizeof(NpId)` users. That is a separate change; it is not in this batch.

### 3. `sceNpWebApi2CreateMultipartRequest` and `sceNpWebApi2SendMultipartRequest`: pass

**Source:** shadPS4 implements both functions itself:
- [`np_web_api2.cpp` L52-L72](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/np/np_web_api2/np_web_api2.cpp#L52-L72) for `CreateMultipartRequest`;
- [L388-L399](https://github.com/shadps4-emu/shadPS4/blob/e0845a12dc05f2fde85e7b203c76de03f93a585d/src/core/libraries/np/np_web_api2/np_web_api2.cpp#L388-L399) for `SendMultipartRequest`.

**What each one does:**
- **`CreateMultipartRequest`:** a null `api_group`, `path` or `method` returns `INVALID_ARGUMENT` (0x80553402, `np_error.h:548`, the tree's constant). Otherwise it calls the shared `createRequest` helper with no content parameter and the multipart flag set, and writes the id only when `request_id` is not null.
- **`SendMultipartRequest`:** `part_index <= 0`, a null `data` or `data_size == 0` returns `INVALID_ARGUMENT`. Otherwise it calls the shared `sendRequest` with the part index.

**Twin rule:** both helpers (`np_web_api2_internal.cpp:483`, `:616`) are the code `CreateRequest` and `SendRequest` also call. So the rule's twin clause holds: a source shows they share code.

**What they would do here:** after their own checks, the tree's shared request model applies.
- Create hands out the next counter id, as `sceNpWebApi2CreateRequest` (`Export.cpp:64`) does.
- Send returns `UNAVAILABLE` 0x80553406, as `sceNpWebApi2SendRequest` does offline. The debt already records that no request reaches a service.

**Differs from the census:** BF-216 modelled Create on the tree's `CreateRequest`, which returns `INVALID_ARGUMENT` for a null `request_id` and doesn't check `api_group`, `path` or `method`. shadPS4's multipart wrapper does the reverse.
- The multipart row should follow shadPS4.
- The tree's own `sceNpWebApi2CreateRequest` also differs from shadPS4's (L74-L100) in the same two ways. I'm only reporting that here; it isn't part of this batch.

### 4. `sceBluetoothHidParamInitialize`: pass

**Source:** [SharpProspero 5dfdb4b0b1 `SceBluetoothHid.cs`](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Bluetooth/SceBluetoothHid.cs#L8-L53).
- **Recovered from the module:** the remarks at L14-L19 say "these signatures were recovered from the module itself", and L8-L13 say every function returns 0 on success.
- **What it writes** (`SceBluetoothHidParam`, L20-L33, and the doc at L43-L49): "Fills the caller's parameter block with value. The block is twelve bytes - the value and a word the device clears after it". Value at offset 0, cleared word at offset 8.

**Match with the tree:** this agrees with the tree's 16-byte `BluetoothHidParam` (`include/Api.hpp:17-21`: `threadParam` at 0, `reserved` at 8, padding at 12). It also matches the `reserved != 0` check in `sceBluetoothHidRegisterCallback` (`Export.cpp:40`).

**Implementation:** `param->threadParam = threadParam; param->reserved = 0; return 0;`, leaving the padding at 12 untouched. A null `param` throws, since no source names that case.

### 5. `sceBluetoothHidThreadParamInitialize`: drop

**Source** ([SharpProspero L51-L53](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Bluetooth/SceBluetoothHid.cs#L51-L53)): `int (uint* param, uint value1, ulong value2)`, "Fills the caller's thread-parameter block param from the given values".

**What the source doesn't say:**
- It doesn't say where `value2` goes or whether the block's `reserved` word (offset 16) or the padding at 4 is cleared.
- For `ParamInitialize`, the same file spells out the cleared word.
- The tree's offsets (`priority` at 0, `affinityMask` at 8, `reserved` at 16, from the asserts at `Export.cpp:10-12`) are in-tree only.

**Why it matters:**
- `sceBluetoothHidRegisterCallback` returns `INVALID_ARGUMENT` for a nonzero `threadParam->reserved` and throws otherwise.
- An implementation that leaves `reserved` alone can turn that throw into a silent `INVALID_ARGUMENT` for a stack block.
- One that clears it guesses.

**What would settle it:** a disassembly note on the export (NID `o+5KjZ3r4O4`) from the 13.60 module, or a published console dump of the block after the call.
