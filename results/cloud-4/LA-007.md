  The bench is now CPU-bound: its worker thread is busy 96% of the time.
- **New finding: the device path's ring-overflow fallback is timing-dependent.** In 5 of the 8 configurations measured, the cold first frame's misses overflow the 4,096-record ring in 3 batches in a row. The program then takes the CPU table path, whose 32,768-element sets OOM the bench at about 13 GB of lavapipe shmem, as in LA-004 before a8b93dc86.
  - **Before the fix:** this already happened with copies unprofiled (twice).
  - **After the fix:** it happens in every unprofiled run, imports and copies, and in the profiled copy run.
  - **Only profiled runs avoid it:** imports before and after, and copies before.
  - **Why** (`DeviceImageTable::drain`, DeviceImageTable.cpp:681-687): a batch counts toward the streak when it dropped records while no misses are pending. Batches recorded *before* the first drain's misses were inserted still overflow, and they drain after those misses were resolved. So when the CPU runs a few batches ahead, three of them count in a row, although none was recorded with the warm table.
  - **Not fixed here,** because step 2 says to change nothing else. A fix would count a batch only if it was recorded after the misses it overflows on were inserted, for example by tagging each chunk with the table's insert generation when it is taken. It needs its own commit and a test that drains three cold batches at once.

## 2. The fix: 421d8d343

`perf(agc): bind the device image heap apart from the device table's dynamic offset`.
- **The change:** `DeviceImageTable::Bind` makes two `vkCmdBindDescriptorSets` calls on the same pipeline layout:
  - set 2 (`DeviceImageHeap::Set`) alone, with no dynamic offsets;
  - then set 3 with its one ring offset.
- **Nothing else changes.** Set 2 stays bound across the second call because the layouts agree. The body records lavapipe's copy and the numbers above.
- **Tests:**
  - **Before:** the 8 `device_image*` tests passed on 26b0655dc: `agc_shader_device_image_tables`, `agc_device_image_keys`, `agc_driver_device_image_path`, `agc_driver_device_image_table`, `agc_driver_device_image_table_heap_cap`, `agc_driver_device_image_path_gpu_path`, `agc_driver_device_image_path_heap_cap` and `agc_driver_device_image_path_heap_cap_gpu_path`.
  - **After:** the same 8 pass on 421d8d343.
  - No bind-count hook was added.
- **Conventions:** `python3 tools/check_conventions.py --base upstream/main --head HEAD` reports "All conventions checks passed".

**The imports run with profiling:**
- `[gputime]` puts the draw class at 3,135–3,178 ms over 1,833–1,946 batches per 10 s window. At 86 µs per draw that is about 27 µs of GPU per draw.
- By thread CPU: the queue thread 10.88 s and the 4 rasterizer threads 4.30 s, over a 24.7 s window.
- Driver CPU: the worker 23.70 s, then the committer 0.50 s and the rest, which is 85 µs per draw.

**The OOMs:**
- **Where the memory goes:** a gdb breakpoint on the 16,388 KiB `mmap`s (152 hits) shows every one in `llvmpipe_map_memory` ← `lvp_descriptor_set_create` ← `lvp_AllocateDescriptorSets` ← `DescriptorCache::Allocate` ← `ShaderResources::buildPrepare`. These are CPU-table builds, each with a 32,768-element image set.
- **The fallback line:** `[device-images] the program … (identity dd951da7043907b1aa35c438fb612d1b) takes the CPU table path from its next recompile: its misses overflowed the ring of 4096 records in 3 batches in a row`.
- **Every killed run printed it,** the two before-copy runs included.

**Why profiling avoids it:** probably `APS5_PROFILE_GPU`'s timestamp queries make the recorder wait on lavapipe more often, so fewer batches are recorded ahead of the first drain. I didn't measure this.

**For the PC session:** on a GPU driver the copy never happened, so the fix changes only lavapipe numbers. The fallback race is not lavapipe-specific: it depends only on how many batches run ahead of the first drain.
