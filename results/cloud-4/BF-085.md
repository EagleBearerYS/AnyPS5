## The probe

**`tests/execution/ShutdownMidFrame.cpp`:**
- **Draws:** SampleMaskDraw's DCB (a full-target triangle into a 64x16 colour target in watched memory), 16 draw packets per DCB.
- **First frame:** ends with an end-of-pipe label and `AgcDriverWaitIdle`, so the boot device exists and has drawn.
- **Submitter:** a thread then submits label-less 16-draw DCBs in a loop. It counts accepted submissions and `ProcessShutdown` refusals, and stops at any other error.
- **Arguments:** `argv[1]` is how many ms the draws run before the shutdown; `argv[2]` picks one of the modes below.

| mode | who shuts down | what else runs |
|---|---|---|
| (none) | the main thread, not a queue worker | the submitter |
| `--register` | the main thread | the submitter, plus a thread registering new pixel shaders (`AgcDriverRegisterShader`, 64 code variants) in a loop |
| `--window` | the presenting thread, right after its last present | the submitter; the presenting thread calls `AgcDriverAttachWindow` with a `VK_EXT_headless_surface` window, then `AgcDriverPresentBuffer` on the colour target (linear, R8G8B8A8) in a loop |

**What happened across 54 runs under the layer:**

- draw time before the shutdown of 0 to 200 ms;
- 65 to 26,604 DCBs accepted;
- up to 76 presents per run;
- in `--register` mode, 284 and 332 shaders registered before the shutdown.

## Where the crash's state could still come from (read from main, not reproduced)

These are the orderings in `stop()` and `~State` (`Execution/src/VulkanDevice.cpp:697`) that would let NVIDIA's `vkCmdEndRenderPass` read freed memory. None happened on lavapipe, so none comes with a test:

- **Present slots retire before the recorder syncs.** `~State` retires every in-flight present slot (`RetireSlot`: `presentation->Release(slot)`, `slot.kept.reset()`) before `recorder->Sync()`.
  - **The risk:** if a pass is open at that point and uses an image only a present slot still holds, the image goes before the pass is ended and submitted.
  - **Here:** no pass was open at that point.
- **The two devices tear down one after the other.** The windowed device is destroyed first (`device.Reset()`), clearing the process-wide `SharedResourceCache` (`resourceCache.Clear()`) among others. Only then does `replacedDevices.clear()` sync the boot device's recorder.
  - **What is safe:** `PrepareForReplacement` (`VulkanDevice.cpp:2066`) idles the boot device and destroys its shadows and pipelines when the window attaches.
  - **What is not:** a pipelined commit captured with the old device and committed after the replacement would record on the boot device's recorder, which nothing submits until `stop()`.
  - **Here:** the probe submits across the replacement, but saw no such commit.
- **A guest thread can hold the device.** A guest thread that holds `device.Load()` across `device.Reset()` moves `~State` to that thread. That would run without the GPU lock and after `ShutdownGuestBufferWorkers()`; `Recorder.cpp:1133` warns about this case.
  - **Paths that hold it:** shader registration, the GPU map observer's import, `Driver::Present`, dispatch and draw.
  - **Here:** in every traced run the device died inside `stop()`.

The PC could run the same `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` on the NVIDIA build to see whether any of these occur in Village; lavapipe does not reach them.

## Side finding: a VkImage used across devices (not teardown)

`agc_driver_multisample_fill_host_only` keeps its own `OpenVulkanTestDevice()` alive while the driver creates its own device. The driver's command buffer then clears a multisample target image made by the test's device:
```
vkCmdClearColorImage(): image (VkImage 0x3a000000003a) was created, allocated or retrieved from VkDevice 0x5633f3ba9ac0[], but command is using (or its dispatchable parameter is associated with) VkDevice 0x7f0158049d80[].
```
This is twice, for images 0x3a…3a and 0x3f…3f, in the test body before "multisampled fill tests passed".
- **The cause:** the multisample target registry is keyed by guest address, not by device.
- **In a title:** this only matters if a title draws to a multisample target on the boot device and then on the windowed one.
