## 4. Step 4: copy-mode `memfd:` mappings

`--village-bench 0 <s>` on 22f604281 with `APS5_NO_HOST_IMPORT=1`, `/proc/<pid>/maps` counted every 3 s. The per-frame GPU wait is a scratch change, not committed: `frame()` calls `GuestMemory::FlushGpuWrites` over the color target after `AgcDriverWaitIdle` when `VILLAGE_GPU_SYNC` is set, as BF-055 did.

| run | `memfd:` lines | RSS | frames |
|---|---|---|---|
| switch on, wait, 90 s | 603 at 3 s, then 545–653 to 97 s, no trend | 294 → 320 MB, flat from ~57 s | 20 + 286, 392 µs per draw wall |
| switch on, no wait, 90 s | 716 at 3 s, then 579–735 to 97 s, no trend | 290 → 320 MB | 20 + 296 |

| switch unset, wait, `APS5_BUFFER_POOL_SLOTS=64` | 1,063 (3 s) → 1,860 (24 s) | 4.1 → 11.7 GB | none, OOM-killed |

- **Switch on (lane A's path): flat, with or without the wait.** LA-008's ~5,000 mappings a second on b63fa365d don't reproduce on this head. Its draws do 0 CPU table snapshots (17,000 device table prepares per 20 frames).
- **Switch unset (the CPU table path, main's code with lane A inactive): the first frame never ends.** In a guarded run (killed at 3.5 GB, 979 mappings) with `APS5_PROFILE_DRAW=1`, the first 10 s finished 1 draw on the worker and created 200 table textures. A gdb sample of `lvp_AllocateMemory` saw a 2 MiB `BufferPool` slot for `BdaResources` ← `ShaderResources::buildComplete` ← `resolveDrawResources` ← `Graphics::Draw` ← `VulkanDevice::Draw` ← `Driver::drawStages`. In that 6 s mappings rose by 239 against 1 allocation call, so most are lavapipe's own maps (`lvp_descriptor_set_create` → `llvmpipe_map_memory`, seen in the bench's stacks).
- **Whose code:** with the switch unset no lane A path runs, so it is #6947/main's CPU table path in copy mode: a frame's draws hold their builds until the batch retires, with nothing bounding them inside the frame (BF-055's finding, here within one frame). A per-frame wait can't help, and the pool bound isn't it. Not chased further: running the bench on #6947 alone needs the harness ported off lane A's counters.
