## What this moves, against BF-282's bound

BF-282's candidate 3 counted the committer's locked work while queue 0 waits: `Resources.Complete` 219–255 + `draw_and_resource_release` 118–169 + `Recorder.Sync` 69–79 ms per frame.

| BF-282 item | what it is | this branch |
|---|---|---|
| `Resources.Complete` | `ShaderResources::buildComplete`, **stage B** of a build: the image lookups (refresh, upload and flush through the recorder), `UploadFinish` (imports, writable mirrors, pending flush) and the descriptor writes | **stays under the lock.** Each of those steps mutates the texture caches, the import set or the recorder. |
| `Graphics.Draw.draw_and_resource_release` | recording the draw, and releasing its resources | **stays** |
| `Recorder.Sync` | GPU syncs inside the draw | **stays** |
| `Resources.Prepare` (stage A of a build) | not in BF-282's top slices | **moves out** for the committer's builds |
| the resource key and the cache lookup | not a separate BF-282 slice: inside the draw's resolve, under the mutex, on every committed draw | **moves out** for every committed draw |

**So the Village gain is bounded by the key + lookup per committed draw plus `Resources.Prepare` per build,** not by 420–470 ms.
- **On the harness that is ~0.37 ms per draw** at 4,096 entries. Village's real table sizes and its committer draw count per frame decide what it is there.
- **Queue 0's inline draws are not covered.** BF-282 counts 491–519 `Graphics.Draw` per frame on queue 0 itself, inline under the GPU mutex: CPU-expanded and GPU-path indirect draws, and direct draws while deferred labels are pending. They do not go through `commitDraw`, so nothing pre-resolves them. #1896 moves the CPU-expanded ones onto the committer, where they pre-resolve.
- **Moving stage B too would need a larger change.** The proof state that `buildComplete`'s lookups and `Revalidate` read would have to become readable without the GPU mutex: `StorageTexture::UploadedKeys`/`FilledKeys`/`KeyProof`, `GenerationFor` and `Version`, which `Texture.hpp` marks "under GuestMemory::GpuMutex only". That is not a re-check; it is a locking redesign of the texture caches, and it is not in this branch.

## Design

### Why not BF-036's (b)

(b) ran the whole `Revalidate` before the mutex and trusted the result when `GpuHoldSerial` had moved by exactly one. That can't be made correct by a check afterwards:
- **The fast proof reads state only the GPU mutex guards.** `Texture.hpp` says so: `StorageTexture::UploadedKeys`/`FilledKeys`/`KeyProof` are "Under GuestMemory::GpuMutex only, as Refresh is; never from a build's stage A", and `Texture::KeyProof` is "Under GuestMemory::GpuMutex only". `GenerationFor` and `Version` are plain fields that `Refresh` writes. Reading them while another holder refreshes the image is a data race, not a stale answer, so no recheck afterwards can fix it.
- **The proof also writes:** `FlushDepthPlanes`, `CompletePendingCpuWrites`, `StorageTexture::FlushPending`, `refreshOwnObjects`, `captureValidation`, `NoteProved`, `RecordStagingCopies`, `RefreshDepthCopy`, and the object's own records.
- **`GpuHoldSerial` is coarse and incomplete.** Any other holder forces a redo. A holder that took the mutex before the start and released it during the window passes the check.

### What this branch does instead

It applies the split main already uses for a dispatch (`VulkanDevice::PrepareDispatch`) to the committer's draws: what main allows without the device lock runs before the mutex, and everything else stays under it.

**Before the GPU mutex,** in `Driver::commitDraw` with `APS5_PRERESOLVE=1` (`Graphics::PreResolveDraw`):

| step | why it may run unlocked |
|---|---|
| resource cache key (`DrawResourceKey`) | a pure function of the commit's own stages (captured descriptor words), target and index range; the per-program memo is an atomic pointer |
| `SharedResourceCache().Find` | the map locks itself, and it returns a `shared_ptr` that keeps the object alive (`PrepareDispatch` probes it unlocked the same way) |
| **miss:** stage A of a deferred draw build | the deferred draw constructor from commit 1. `buildPrepare` is the stage `ShaderResources.hpp` documents as needing no device lock: the binding plan, samplers, data buffers, `UploadPrepare`, the set layout and descriptor set, and the image records with their precollect walks. BDA draws keep both stages for `Complete()`, as a compute build does. |

**Under the GPU mutex,** in `resolveDrawResources`. It is unchanged except that it takes what was prepared:
- **Hit:** the key is reused (it would be recomputed bit for bit), and the object found before the lock is proved by `Revalidate`, exactly as a map hit is on main.
  - If the proof fails, the entry is removed only if it still holds that object (`Remove(key, object)`), and the draw builds under the lock as on main.
  - This is how `VulkanDevice::Dispatch` treats `PrepareDispatch`'s object ("revalidated as a map hit would be (an entry replaced meanwhile is left alone by the pointer-conditional Remove)").
  - An object evicted between the lookup and the lock is still a complete build for this key; `Revalidate` decides whether its textures are current. A template hit is never re-inserted, so the eviction stands.
- **Miss:** `Complete()` runs stage B:
  - the `fastTexture` predicate per record (collect, pending registry, DCC keys re-read, storage image cached and unchanged, the entry still the cache's), else the full lookup;
  - then `UploadFinish` (it confirms imports against the registry epoch, refreshes writable mirrors, flushes pending results and copies the writable regions) and the descriptor writes.
  - As for a dispatch, there is no second `Find`: an entry inserted meanwhile is replaced at `Insert`.
- **When the pre-resolve is used:** only when the lock-time draw is the one it was made for, with the same device (the device can be replaced under the lock), `State` object, stage span, snapshot span and index range. Otherwise it is dropped (`unused`), and the draw resolves under the lock as on main.
- **When stage A throws:** the pre-resolve is dropped (`failed`), and the locked path throws, or not, exactly as main does. Empty draws (index or instance count 0) and indirect draws are not pre-resolved. Neither are recipe draws.

**The recheck is the work main already does under the lock.** Nothing computed outside the lock is used without it:
- the key is a pure function of the draw's own inputs;
- the object found is proved by `Revalidate`;
- stage A's results go through stage B's predicate and lookups.

A CPU store landing between stage A and the lock behaves as it does for main's own build precollect. The store is unordered with the draw, and the next collect epoch's walk sees it. The race tests show it is never lost.

**A hit's surfaces are not walked before the lock.** A first version precollected them, as `PrepareDispatch` does with `CachedPrecollect()`, and did the same for a recipe's template.
- **On the Village harness that cost 1.6 ms more per draw.** After the first draw of an epoch every surface is already a collect-memo hit, so the walk only doubled 4,096 memo lookups on the committer, which is the critical path there.
- **The in-lock lookup barely moved:** 2.05–2.27 ms per draw, against 2.25–2.28 on main. In steady state the proof's collects were memo hits already.
- So both walks went, and recipe draws are not pre-resolved.

**A hit is not looked up again under the lock.** A second version kept the key and looked the entry up again under the mutex, so that a replaced entry would be noticed. That second `Find` hashed and compared the 128 KB key again under the lock. The object found first is now carried in and proved, as a dispatch's is.

**What stays under the lock,** and why:
- `Revalidate`'s proof, which reads mutex-only state (see above);
- stage B, whose lookups refresh, upload and flush through the recorder;
- `UploadFinish` (imports, mirrors, pending flush);
- the descriptor writes, and recording.

So the hit path moves only the key and the lookup out of the lock. With a 4,096-entry table the key is about 128 KB, built and hashed per draw. On this VM the `[preresolve]` line puts the key and the lookup at 330–495 µs per draw (median 370), and the in-lock lookup drops by about that much (see the harness below).

**What it costs when off:** the deferred-capable constructor (the immediate one delegates to it), two switch helpers, and one predictable branch in `commitDraw` and `resolveDrawResources`. The `Draw`/`VulkanDevice::Draw` signatures gain a defaulted trailing parameter.

## Tests

Four new tests, plus the pipelined-draw tests run again with the switch on. Three are modes of the existing `agc_driver_recorder_tests` fixture (`tests/Recorder.cpp`). The fourth, `agc_driver_pre_resolve_sampled_draw`, is a new execution test (`tests/execution/PreResolveSampledDraw.cpp`, registered by the directory's glob).
- **What the three Recorder modes build:** `ShaderResources` objects from bindings-only programs. They read back what a build binds with the fixture's `SampleProgram`, a compute sample of the bound texture's view.
- **The lock:** the fixture's `main` holds the GPU mutex for every recorder mode, so these three modes release it first and take it back before returning. The steps meant to run before the lock really run unlocked. The tests take the mutex themselves around stage B, `Revalidate`, the recorder and the evictions, as the committer does.

| test | commit | what it checks |
|---|---|---|
| `agc_deferred_draw_build` | 1 | a draw build in two stages (`deferred`, then `Complete()` under the mutex) binds what memory holds **after** stage A, in each race case below |
| `agc_pre_resolve_hit` | 2 | a cached draw object found before the lock and proved by `Revalidate` under it (rebuilt under it when the proof fails, as `resolveDrawResources` does) binds the same, in the same cases |
| `agc_pre_resolve_draw` | 2 | `Graphics::PreResolveDraw` then `Graphics::Draw(…, preResolved)` on a real pipeline (Cover.vert/Cover.frag into a 64×64 target): each draw covers its target, and the counters move exactly by the path taken |
| `agc_driver_pre_resolve_sampled_draw` | 2 | the committer's two calls, `VulkanDevice::PreResolveDraw` and then `VulkanDevice::Draw(…, preResolved)` under the mutex, on recompiled GCN shaders: a vertex shader and a pixel shader that samples a 64×32 RGBA8 texture. Texture, target and vertices all sit in write-watched guest memory, and the target is read back after each draw. It checks every pixel and the counts in the 7 steps below. |
| `<name>_preresolve` (22 tests) | 2 | the pipelined-draw execution tests that already run as `<name>_draw_pipeline`, run again with `APS5_PRERESOLVE=1`: their own checks then cover the committer's pre-resolve end to end |

**The race cases.** A 64×64 RGBA8 linear texture in write-watched memory holds `0x20` at the start. Each case changes something between the unlocked step and the lock:

| case | change before the lock | the build must bind |
|---|---|---|
| unchanged | none | the same texture objects as an immediate build (sampled `0x20`) |
| driver store | `memset` + `GuestMemory::MarkWritten` (`0x40`) | `0x40` |
| eviction | `ClearCachedTextures` under the mutex | `0x40`, from a texture other than the evicted one |
| GPU write | a `StorageTexture` over the surface, cleared on the GPU to `0x80` and left pending (`MarkDirty`) under the mutex | `0x80`; after its write-back, guest memory holds `0x80` |
| CPU store | a plain `memset` (`0x60`), no stamp | `0x60` after the next ordering point (`BumpCollectEpoch`). The store is unordered with the draw, so a build in the same epoch may still bind `0x80`, but the store is never lost. |
