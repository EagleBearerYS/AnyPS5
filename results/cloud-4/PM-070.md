# PM-070: Output resolution version B: the setting applies only to titles that declare resolution detection (cloud-4)

**Branch:** fork `review/videoout-output-resolution-declared` at **55b538c94**. It is two commits on `review/videoout-output-resolution` ec4a01c07. That branch (ec4a01c07) and `followup/videoout-output-resolution-prm036` (bfc348462a) were not moved.

**Machine:** cloud-4: Xeon @ 2.10 GHz, 4 vCPUs, Ubuntu 24.04, gcc 13.3.0, wild 0.10.0, lavapipe (Mesa 25.2.8, LLVM 20.1.2), Xvfb 21.1.12. Tests ran as the unprivileged user `runner`, stdin from /dev/null.

RESULT:
- **Version B.** `ANYPS5_OUTPUT_RESOLUTION` now applies only when the title's param.json `attribute3 & 0x4` is set.
  - A title without the bit gets exactly what it gets with the variable unset:
    - every buffer size is taken through `sceVideoOutRegisterBuffers2`;
    - PS4 `sceVideoOutRegisterBuffers` never stops;
    - `sceVideoOutSubmitChangeBufferAttribute2` never stops;
    - the getters follow the port as on main.
  - It also gets one log line, once per process, naming the variable and the bit.
  - Titles with the bit keep everything ec4a01c07 does.
- **One gate.** The code change is in `ConfiguredVideoOutOutputResolution_nid_no_patch()` (Output.cpp). Every refusal, stop, report and log path in Buffer.cpp and Output.cpp reads the setting through it, so they all follow.
- **Tests:**
  - The existing output-resolution and sequence cases now run as a title with `"attribute3":4`.
  - Three new cases run as a title with Village's attribute3 0x8460440 (bit 2 clear):
    - the PS5 path with an attribute change;
    - the PS4 path;
    - the full sequence harness at 1920x1080, which must answer exactly as unset.
  - The new cases fail on ec4a01c07's code and pass on the head.
- **CI mirror, head 55b538c94:**
  - **1348 tests: 1264 passed, 79 skipped, 5 failed.** ec4a01c07: **1345 tests: 1264 passed, 76 skipped, 5 failed**.
  - No test changed status. The difference is the 3 new tests, which skip headless with "no display or Vulkan device", like the others.
  - `check_skips`: `guest_sce_net` only, on both.
  - Under Xvfb, the 38 VideoOut tests pass `--repeat until-fail:10` (25 passed, 13 skipped for their usual display reasons, the same 13 as before).
- **Conventions:** `python3 tools/check_conventions.py --base 0906c64501 --head HEAD` reports "All conventions checks passed".
- **Still different from unset, for a title without the bit:**
  - an invalid value still stops the first `sceVideoOutOpen`;
  - the one log line;
  - with the variable set, param.json is read at that first open.

## What still treats a title without the bit differently from unset

1. **An invalid value still stops it.** Anything but the four sizes or empty stops the first `sceVideoOutOpen` with the error naming the variable. The value is parsed before the bit is read. This is deliberate and documented in USAGE.md: a typo shouldn't silently do nothing for some titles. If you'd rather an undeclared title ignore even an invalid value, swap the two checks.
2. **The one log line** at the first `sceVideoOutOpen`.
3. **param.json is read** when the variable is set (`GetAppAttribute3_nid_no_patch()` → `ensureTitleLoaded`). A missing param.json then throws "param.json not found" at the first open, where unset never reads it. Every real title has one, and the VideoOut tests write one.

Nothing else: every other answer in VideoOut comes from `ConfiguredVideoOutOutputResolution_nid_no_patch()`, which returns no setting for such a title, and the three new tests check the PS5 path, the PS4 path, the attribute change and every getter against the unset answers.
