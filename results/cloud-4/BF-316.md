## 1. Where `refresh` gets `stampedBlocks` and `cpuWrote`

`StorageTexture::refresh` (`Graphics/src/Texture.cpp`):
- **`scanBlocks`** (2265-2285) calls `GuestMemory::ChangedBlocks(base, bytes, generations, stampedBlocks, cpuBlocks)` (2269):
  - a block is **stamped** when its stored stamp is newer than its unit's generation;
  - it is **CPU** when its CPU stamp is newer (`Execution/src/GuestMemory.cpp:2244-2260`, `stampOf` and `cpuStampOf`).
- **When the range is not covered by the write watch,** `ChangedBlocks` fills both with 1 and returns false (2245-2250). The refresh then compares the guest bytes with `original` (`compareUntracked`, 2273), and **`cpuBlocks = stampedBlocks`** (2279): every block that differs from `original` counts as CPU-written, whoever wrote it.
- **`cpuWrote`** is set by any CPU block with `compared || (tracked && generations[k] != 0)` (2337-2339).
- **It runs on two branches:** the keys-changed branch (2289-2294) and the stamped branch (2295-2309).
- **A stamp kind** (`GuestMemory.cpp:870`, `stamp()` at 1315-1326) sets the CPU stamp for `Cpu` and `ImportWindow`, and the stored stamp for every kind except `ImportWindow`.

## 2. Ranking against the report

The report: every one of the 510 blocks is stamped, `cpuWrote=1`, the keys are at the clear code, and it happens on the composite target that 1,724 draws hit and on the swapchain targets.

1. **W6, the compare path on an import kept compared. The best fit.**
   - **Why the range is compared:** presentation-sized targets are large host imports. While a live storage image overlaps an import, both rewatch paths leave it compared (W2's guard, `GuestBufferMemory.cpp:1186-1189`, `1672-1673`, counted as `settlesKeptCompared`). So the image's own range is never re-covered, and every refresh of it takes the compare.
   - **What then reads as CPU:** any byte change since `original`, for example the GPU drawing into the imported memory, another view's write-back, or a direct BDA write, marks those blocks stamped and CPU (2279).
   - **Why it fits:** a target that 1,724 draws hit, and swapchain images the GPU writes every frame, change in every block, so 510/510 and `cpuWrote=1` follow. These are the GPU's writes counted as CPU writes. That is what the reporter suspects: an accounting problem, not a real CPU write.
   - **Signature** (diagnostic below): `tracked 0 compared 1 watched 0 imported 1`.
2. **W1, the walk reporting writes:**
   - real CPU writes (unlikely for 33 MB of render target every frame);
   - or, if this Windows driver lets the write watch see GPU writes into an import that stays watched, the GPU's own writes stamped as CPU. The startup line `[write-watch] host imports resolve write protection: …` shows what the probe found on that machine.
   - **Signature:** `tracked 1 compared 0 watched 1`, with no `[refresh-stamps] rewatch|private mapping|refused walk|import window` line over the range.
3. **W4, a refused walk:** whole runs of unreported pages stamped CPU. **Signature:** a `[refresh-stamps] refused walk` line covering the range before the refresh.
4. **W5, the import window:** CPU stamps without stored stamps, so the `cpu` count exceeds `stamped`. That does not fit "all 510 stamped" unless something else stamped too.
5. **W3, a private mapping:** a real replacement of the memory. It doesn't fit a target that stays mapped.
6. **W2, `Rewatch`: ruled out for a live image.** Both callers skip a range a live storage image overlaps. An image created later has a generation newer than the rewatch stamp, so the rewatch doesn't show up at its refresh.

## 3. The DCC clear transition

**Where clear codes come from:** a storage image's keys become a clear code only through the **title's** writes to the metadata:
- a key fill that the fill HLE recognises, `StorageTexture::NoteKeysFill` (`Texture.cpp:5235-5262`). It maps 0x00/0x40/0x80/0xc0/0x20 to the clear codes and sets `filledKeys`. When the image's `uploadedKeys` already equal that code, it **re-arms** them to `Uncompressed` (5257-5258; `APS5_NO_KEYS_REFILL` turns that off), so the next refresh sees a key change;
- or the title's GPU kernel or CPU writing the key bytes directly.

**The driver itself only ever writes 0xff (uncompressed):**
- `MarkDccUncompressed`/`QueueKeyStore` (`DccMetadata.cpp:231-254`, `627-660`);
- its callers `Draw.cpp:432`, `451`, `471`, `3638`, `3923` and `Texture.cpp:3813`, `6176`, `6326`, `6470`.

**`clearHandOver`** (`Texture.cpp:5768-5800`) **reads** the clear keys, through `ProvedKeys`, and hands over the other images' pending units. It writes no keys.

**Can the key write be what stamps the blocks? No.**
- A key write, whether the title's fill (a driver `Driver` stamp through the fill HLE) or the driver's 0xff fill (`MarkWritten` at `DccMetadata.cpp:254`), stamps the **metadata** range. That is 1/256 of the surface, about 130 KiB for 510 blocks, never the texel blocks.
- None of these writers is a CPU stamp.

**What actually drops the results is the key flip, not the stamps.**
- At refresh, `keysChanged && IsDccClear(keys)` makes **every** unit droppable on its own (`droppable`, 2412), whatever the stamps say.
- So **if** the keys are truly at the clear code there, dropping the results is what the hardware does after a fast clear, and the "510 CPU-stamped" count is a side effect of `scanBlocks` running on the keys-changed branch (2294).

**Whether the keys should still be clear** depends on whether the surface was written since the fill. Two paths keep a clear code in guest metadata after the surface is written:
- **(a) Draws into a resident colour target never touch the guest keys** (`Draw.cpp:3628-3631`: "the results stay on the GPU"). This is fine while that same image holds them. Another view sees them only after `FlushPending` stores them, and that store's key marking has the condition in (b).
- **(b) `MarkDirty` (3811) and the three write-backs (6176, 6326, 6470) skip the uncompressed key store while `filledKeys` is a clear code,** but still set `uploadedKeys = Uncompressed` (6177, 6327, 6471).
  - `upload` resets `filledKeys` (2717), so this happens only when a key fill lands **after** the image's last upload and before its write or write-back. Examples: a fill from another queue, or one recorded while the image's results are pending.
  - Then the next refresh reads the keys as the clear code, against `uploadedKeys = Uncompressed`. That counts as a key change, drops every unit, and clears the image to the clear colour, although its texels in memory hold the stored results.
  - That gives black frames with exactly this signature. The `!IsDccClear(filledKeys)` condition is older than the repository's history (it is in the initial import, af1a8edfe1). Its purpose isn't stated; the later 63f06f2935 only added the `uploadedKeys` test.

## 5. A bug in our code?

**Suspected, not proven:** the clear-code exception in (b).
- **Where:** `Texture.cpp:3811` (`MarkDirty`) and the write-backs at `6176`, `6326`, `6470`. All four keep the guest keys at a clear code when a key fill has landed since the image's last upload, while 6177, 6327 and 6471 set `uploadedKeys = Uncompressed`.
- **What follows:** the next refresh then reads a flip to the clear code and drops every unit (2412).
- **The red test, sketched only, in `tests/Recorder.cpp`'s storage fixtures:**
  1. Make a cached storage image with DCC metadata over write-watched memory, and refresh it once (keys uncompressed).
  2. Write it on the GPU (`MarkUnitsWritten`) so its units are pending.
  3. Fill its key range with 0x00 through `StorageTexture::NoteKeysFill` (`filledKeys = Clear0000`).
  4. `FlushPending` the image, which writes back the texels, skips the key store and sets `uploadedKeys = Uncompressed`.
  5. Refresh with the same descriptor.
  - **Expected:** the stored texels are kept, because the image's writes came after the fill, as the hardware's DCC writes would record.
  - **On this tree, as I read it:** the refresh drops every unit and clears the image to Clear0000's colour.
  - **Before calling it a bug,** it needs the order confirmed: in the reported frames, did the fill land before or after the image's write? The `(filled …)` field of the diagnostic shows it.

**W6 is a design limit, not a bug in itself.** On an untracked range the compare cannot tell who changed the bytes (2279). Counting them as CPU writes is the conservative reading for the image's *own* stale content. But it also drops the image's pending results under any other GPU writer's change. Whether that loses newer results depends on order, which the compare doesn't record.
