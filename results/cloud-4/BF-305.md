## 2. The sites

### The scope

**`FallbackReadSiteScope`** (`Execution/include/GuestMemory.hpp:285-296`) sets the thread's read site only while it is `Unknown`, and restores the old site on exit. It is the existing `ReadSiteScope` with one test added.

**Why not a plain `ReadSiteScope`:** some of these reads also run under an outer scope, for example a storage upload under `texture-read` or a draw-input copy under `draw-cache`. A plain scope there would move rows that are already named, and today's numbers would no longer compare with earlier boots. With the fallback scope:
- a read that was "unknown" gets a name;
- every row that already had a name keeps it.

**What it changes:** nothing but the `[hooksync]` and `[guestmem]` attribution, at the cost of a thread-local read and two thread-local writes per scope.

## 3. `CaptureCallerOffsets` on Windows

**Why every frame printed `+0x0`:**
- The regular Windows build uses WinLibs GCC with DWARF exceptions. The libraries are compiled with `-fno-asynchronous-unwind-tables` (`core/libs/CMakeLists.txt:50`, after the `ANYPS5_MINGW_DWARF_EXCEPTIONS` check). The driver therefore has no `.pdata`/`.xdata`, only DWARF CFI in `.eh_frame`, which `configure_windows_unwind` renames to `.ehfram` (`CMakeLists.txt:54-64`; `libSceAgcDriver/CMakeLists.txt:468`).
- `RtlCaptureStackBackTrace` steps only with `RtlLookupFunctionEntry`/`RtlVirtualUnwind`.
- When a frame has no function entry, the walk treats it as a leaf and takes `[RSP]` as its return address. In `CaptureCallerOffsets` that is a stack slot, not a return address.
- So from the first skipped frame on, every captured "frame" is garbage outside the driver, and the old code wrote it as 0.
- **Answer to the task's question:** the capture was taken, but the frames it returned were not the callers', and fell outside the module. An MSYS2 (SEH) build has `.pdata` for the old code to walk.

**The fix** (`Execution/src/GuestMemory.cpp:470-516`):
- The driver's module is resolved once, as before. Its `.ehfram` section is indexed into a `DwarfFrames` (`Execution/include/StackWalk.hpp`, the worker sampler's unwinder).
- `RtlCaptureContext` starts the walk. Each frame is stepped:
  - through `RtlVirtualUnwind` when it has `.pdata` (system DLLs, or an SEH build);
  - otherwise through its DWARF record, with reads limited to the thread's stack (`NT_TIB` `StackLimit`..`StackBase`).
- The walk stops at a frame with neither. This is the same stepping as `WorkerSampler.cpp`'s `walk`, which documents it in `docs/dev/BUILD.md` (`APS5_SAMPLE_WORKER`).
- **Frame numbering is unchanged:** frame 0 is the hook's caller, after `1 + skip` frames.

**What was checked:**
- MinGW (`x86_64-w64-mingw32-g++-posix`, an SEH toolchain) compiles it with no new diagnostic.
- A probe copy, with `RtlCaptureContext` and `DwarfFrames::Unwind` renamed, fails at both names, which proves the branch is compiled and type-checked.
- **Not run:** this VM has no Windows and no Wine. The PC's boot is the first run.

**Linux is unchanged:** one frame, `__builtin_return_address(0)`, which is inside the flush hook. Linux frames were not part of the task.

## 4. The design

### What the rows are

Village's rows per 10 s (main ebb4075168 + #12478, profiled control boot) group into four families. Together they are all 512 syncs and 3,111 ms of the two lines.

| Family | Rows | Syncs | ms | Inside a resource build (C4 skipped it)? |
| --- | --- | --- | --- | --- |
| Storage refresh round trip | recorded-store `0x0 DISPATCH_DIRECT unknown` 145/468, `0x0 DRAW_INDIRECT unknown` 116/449, `0x20 DISPATCH_DIRECT unknown` 87/355 | 348 | 1,272 | yes |
| Indirect arguments | pending-write `0x0 DRAW_INDEX_INDIRECT indirect-args` 28/760 | 28 | 760 | **no**: prepareDraw reads them after `resolveDrawResources` (`Draw.cpp:2928`, read at `:3006`) |
| Buffer uploads | recorded-store `0x28 buffer-upload` 29/364; pending-write `0x0 DISPATCH_DIRECT buffer-upload` 65/238 | 94 | 602 | yes |
| WAIT_REG_MEM | recorded-store `0x0 WAIT_REG_MEM_64` 20/243; pending-write `0x0 WAIT_REG_MEM_64` 22/235 | 42 | 478 | **no** |

**Why the "unknown" build rows are the storage refresh round trip:**
1. **A recorded-store sync is a storage image's results.** The hook makes one only when it stored a pending image, published a unit shadow, or found a recorded write-back snapshot over the range (`Graphics/src/Recorder.cpp:1070`).
2. **One per refresh.** A refresh that finds another image's results pending over its surface writes them back first (`FlushPending(…, "storage refresh")`, `Texture.cpp:2211`). It then reads the surface's guest bytes through `upload`/`captureGuestBytes`. That read finds the recorded write-back and makes one recorded-store sync, which waits for a whole open batch, 3.7 ms on average here.
3. **The counts match.** The same boot's `[storage]` line has **356** "flushed" re-uploads per 10 s against **348** syncs in these three rows. A "flushed" upload is a CPU re-upload of a surface whose refresh stored another image over it.
4. **Nothing else fits.** Sampled reads are named (`texture-read`, `texture-compare`, per BF-295), and buffer uploads are named.

This is an inference from counts. On the PC's boot of this branch the three rows should print as `storage-upload`, or `storage-capture` or `metadata` for an unwatched or DCC surface.

### What the storage-alias fix covers

The base 306fc4cfb4 already carries b9df5d603d, f20935458c and 306fc4cfb4.
- **What it does:** for a refresh whose alias passes `pendingAlias()` (`Texture.cpp:5867`: cached, block units, the same dimensions, tiling and bytes per element), the units are borrowed on the device.
  - Neither the "storage refresh" write-back nor the "flushed" re-upload happens.
  - The refresh's read finds no recorded write-back, so **that sync disappears**.
- **What it can cover:** at most the whole family, 348 syncs and 1,272 ms per 10 s, or 41 % of the hook-wait time. C1, which skipped the whole round trip, measured +43 % (0.572 fps), the ceiling for the family.
- **The share not yet known:** how much of it Village's pairs actually let the fix take is not measured. The PC's boot of this branch with `APS5_TRACE_STORAGE_ALIAS=1` (the `[storage-alias]` trace, 69cc079c0c, is in the base) prints it in two places:
  - the `[storage-alias]` lines give each remaining round trip's refusal reason;
  - `[hooksync]` shows what is left of the three rows under `storage-upload`/`storage-capture`.
- **Below:** the family's remainder is item 4. Items 1-3 do not depend on that split.

#### 1. Indirect arguments: 760 ms, 28 syncs (27 ms each)

**The read:** an indirect draw on the CPU path reads its records through the flush hook (`Draw.cpp:3004-3006`: `Pm4::ReadDrawCount`, `Pm4::ReadDrawArguments`, site `indirect-args`, `Pm4.cpp:886`, `:895`).

**What already works:** the GPU path (`vkCmdDraw*Indirect` from the import, `Draw.cpp:1856-1865`) already accepts records that a batch in flight writes into the import.
- The decision (`Draw.cpp:2973-2997`) leaves the GPU path only for a pending storage image, a pending label or copied write-back, or records that are not imported.
- It also leaves it for the later demotions in `IndirectDrawPath` (`Graphics/include/Draw.hpp:126`: not folded, fetch offset unknown, index or vertex range, and so on).
- So these 28 waits are draws that took the CPU path for one of those reasons, and then waited for a GPU writer of their records. Village's menu has 483 indirect draws on the CPU path and 226 on the GPU path (BF-287).

**The change:** when the only thing the CPU needs is the values' arrival, take the GPU path. By case:
- **A demotion that needs a bound** (index range, vertex range): use the conservative bound, which is the whole index buffer or the import's extent.
- **A copied writer's write-back:** copy from the writer's device buffer into a scratch record buffer in batch order, and draw indirect from that.
- **A label the CPU stores at completion:** write its known value into the scratch with `vkCmdUpdateBuffer`.
- **Where a value truly decides CPU work,** keep the wait for that case only.

**Proof:**
- the producer's write (a shader store or a transfer into the import or scratch);
- then a barrier: `COMPUTE_SHADER|TRANSFER` / `SHADER_WRITE|TRANSFER_WRITE` → `DRAW_INDIRECT` / `INDIRECT_COMMAND_READ`, on the same queue in submission order, or with a timeline semaphore across queues.
- The draw then reads exactly the bytes the CPU would have read after its wait, so the draws are the same, with the same counts.

**Cost:**
- The zero-count skip moves to the GPU, where a zero-count draw is a no-op.
- Vertex inputs must cover the conservative range: in place, or a whole-buffer copy.
- Patched user words need #10359 or #9248's handling, or stay on the CPU.
- A scratch copy per record set in the copied-writer and label cases (count × stride bytes).

**C4:** not in it. This is on top of +54 %.

#### 2. Buffer uploads: 602 ms, 94 syncs

**The rows:**
- **Pending-write** (65/238): the build's CPU upload of descriptor regions (`Graphics/src/GuestBufferMemory.cpp:5680`, `buffer-upload`). BF-307 gives the average noted range as 3,162 KiB and the average access as 11,632 KiB, above the GPU-copy bound (`APS5_GPU_COPY_MAX_KIB`, 1024 KiB, `GuestBufferMemory.cpp:4990-5002`).
- **Recorded-store** (0x28, 29/364, 12.6 ms each): a storage image's results stored over a region the build uploads.

**The change:** a region covered by a pending GPU write becomes a GPU-ordered `vkCmdCopyBuffer` from the import, recorded after the producer, with no size bound for that case. The copy-back of written sub-ranges already exists (`RecordCopyBacks`).
- **The recorded-store rows reduce to the same change** when the image's write-back goes into the import on the GPU: the copy is simply recorded after the write-back.
- **When the surface has no import** (a CPU write-back at completion), there is no device source, and it becomes the storage family's slab (item 4, D3).

**Proof:**
- producer → `SHADER_WRITE|TRANSFER_WRITE` → `TRANSFER_READ`;
- copy → `TRANSFER_WRITE` → `SHADER_READ|UNIFORM_READ`;
- the dispatch.
- The bytes are the ones the CPU would have copied after its wait.

**Cost:** device memory for regions up to about 11.6 MiB per access, and copy bandwidth, which is small against 3.7 to 12.6 ms waits. Regions outside imports keep the wait unless the producer's own buffer holds the bytes.

**C4:** in it.

- #1364: budget accounting for retained draw uploads.

#### 3. WAIT_REG_MEM: 478 ms, 42 syncs

**The rows:**
- **Recorded-store** (20/243): the wait loop's held-results flush every 32 polls (`WaitMemory.cpp:362-365`, now `wait-flush`; `APS5_NO_QUEUED_DRAW_READ_ORDER` turns it off). It stores the pending images over the awaited dword and waits for the open batch.
- **Pending-write** (22/235): the wait's read of the awaited value, under the batch that writes it (`Pm4.cpp:572`, `wait`).

**Verdict: needed now.**
- The queue blocks until the value lands; that is what the packet means.
- The wait is unlocked: the loop holds no GPU mutex, so the hook's acquisition is outermost. It delays only this queue.

**A possible change, with a small gain:**
- For the recorded-store row, store only the unit that holds the awaited dword, and poll that batch's completion instead of `SyncThrough`. This shortens the store and lets the thread keep serving submits and reaps (`pollService`) while the batch runs.
- The value lands no sooner.
- The pending-write row has no change: the GPU write has to complete.

**C4:** not in it.

**Open PRs:** none does it. Adjacent: #7464 (Dean Galvin, Evgeniy Kazarin) and #10442 (Evgeniy Kazarin), the unimported-label syncs.

#### 4. The storage family after the alias fix: up to 1,272 ms minus the alias share

**What is left:** pairs that `pendingAlias()` refuses:
- different dimensions, tiling or element size;
- offset aliases;
- linear surfaces (no block units);
- images not from the cache.

**The designs (from BF-290):**
- **D2, offset aliases:** a 64 KiB-multiple base delta with equal tiling, pitch, bpp and mips. The windows shift by the delta.
- **D3, a device retile through a slab:**
  1. Y's write-back retiles its units into a device buffer in Y's guest layout (`writeBackWindows` with a slab target).
  2. The slab is registered as the newest content of those bytes.
  3. X's upload detiles from it (`uploadWindows` with a slab source).
  4. The CPU sees the slab only through a flush, which stores it to guest memory.

**Proof for D3:**
- The slab bytes equal what Y's write-back stores: the same retiler and keep rules.
- X's detile of the slab equals its detile of guest memory after that store.
- The ordering:
  - Y's writes → `SHADER_WRITE` → `SHADER_READ`;
  - the retile → `SHADER_WRITE` → `SHADER_READ|TRANSFER_READ`;
  - X's detile;
  - X's consumer.

**Cost:**
- several hundred lines, and a slab per surface;
- the pending registry gains a device-bytes source;
- geometry tests per tiling.
