## What changed from his code, and why

1. **Set 3 instead of device addresses.** His table and ring were buffer-device-address buffers named in a 16-word header the shader read through a pointer from the image table map. Here the header and buckets are set 3 binding 0 (a plain storage buffer: header words 0-15, buckets from word 16; address words stay zero), and the ring is set 3 binding 1, a dynamic storage buffer bound at the batch's chunk. No Int64 or BDA is needed.
2. **PR 6947's heap instead of his descriptor heap.** `Texture::SampledSlot` is replaced by `BindlessHeap::For(context).TextureSlot(kind, texture, view, layout)`. The kind is `DescriptorBindingForImage(mode)`, the view is `FirstLayerView` when a 2D mode reads a 2D-array surface (as the CPU element does), and the layout is `Texture::Layout()`.
3. **Fault value.** The bucket's `fault` is 1 + `ImageTableAbi::PoisonReason`, as the design fixes, not his 1 + rejection index. A drained fault record is matched to its rejection by key, and the reason comes from the bucket if the table no longer holds the rejection.
4. **Injected interface lookup.** `DeviceImageTable::Interface{id, image, modes}` comes from a `std::function` (the constructor, or `SetInterfaceLookup` on the device's table). His code called `ResourceMaterializer::FindDeviceImageInterface` directly; LA-002 has that registry with the same three fields, and LA-004 wires it.
5. **The mode check is main's.** `TryRuntimeImageMode`, then `ResolveImageTables`' multisampled and point-filtered reduction poisons; the shape check uses the mode's dimension (his `ImageShapeForResource` sits in the recompiler's anonymous namespace on main, and LA-002 exports it). A depth surface or a texture copied per use is not rejected with a fault, as his first version did: the CPU path serves both, so the key stays unresolved and its programs fall back.
6. **No expectations.** His pre-pass expectations (`Expect`, `deviceImagesComplete`, waits before unnamed uses) belong to LA-002/LA-004's later pieces. Here every key enters by a miss.
7. **Freshness by a block index.** His refresh walked every entry when any serial moved. Here it returns at once while the collect epoch, the unwatch, depth-surface and pending serials and the driver's own store count are unchanged. Otherwise, per run of adjacent 64 KiB blocks the entries cover, one `CollectWrites`, one `ChangedBlocks` and (when the pending registry moved) one `ScanPending` select the blocks, and only their entries are checked.
8. **Refreshed means the texture changed.** The texture cache returns the same `Texture` after a byte compare that finds no change, and a new one when the bytes changed. Only the latter remakes the entry (new slot and bucket) and counts as refreshed; the rest are counted as checked.
9. **Eviction recency.** The shader reports no hits, so "least recently used" is the last resolve or refresh (his `used` came from expectations). The byte budget's idle rule is his 0a90d704ec; the entry budget (16384) is new.
10. **Lifetime.** He handed dropped textures to the recorder too. Here that happens in the open batch at eviction, replacement and refresh, so the heap's sweep (which frees a slot only when the heap holds the last reference) cannot reuse a slot under a pending batch.
11. **Non-seamless cube samplers.** He rejected them unconditionally in the table; main's CPU path rejects them only without `VK_EXT_non_seamless_cube_map`, and LA-002 sets the class bit whatever the device supports, so the driver now decides (a500d67c8).

## The ABI as implemented (for LA-002 and LA-004)

- **Fixed lines, exactly as the design writes them:** `RuntimeAbi::DeviceHeapSet = 2u`, `DeviceTableSet = 3u`, `DeviceTableBucketsBinding = 0u`, `DeviceTableRingBinding = 1u` (right after `GpuDataSet`); `PipelineSpecialization::DeviceSamplerClassBase = 58368u` (right after `UnnormalizedBaseLevelBase`); `bool deviceImageTables = false;` in `SpirvTarget` (after `gpuConstantsVerify`) and in `CompiledShaderArtifact` (after `samplerSlotDword`).
- **Added in shared files, because the artifact field changes `sizeof`:**
  - `ShaderDiskCache.cpp` encodes and decodes `result.deviceImageTables` right after `samplerSlotDword` in the result codec;
  - the static asserts are 248 (`CompiledShaderArtifact`) and 568 (`RecompileResult`);
  - `FormatVersion` moves 40 -> 41.

  LA-002 made the same bump and encodes the field in "the info and the artifact codecs". LA-004 should keep one encoding of the artifact field: a duplicate line is harmless to merge but would encode the flag twice.
- **Reviewed names** added to `shaderCacheReviewedNames`: `DescriptorBindingForImage`, `ResourceMaterializer::TryRuntimeImageMode`. LA-002 adds the latter too, at a different line.
- **Set 3 layout:** binding 0 `STORAGE_BUFFER`, binding 1 `STORAGE_BUFFER_DYNAMIC` (range one chunk, `RingWords` = 4 + 4096 x 16 words; chunk stride rounded up to `minStorageBufferOffsetAlignment`). Both have stage flags VS | FS | CS, the same as PR 6947's heap set.
- **Header as uploaded:** word 0 `Version` (2), 3 `HeaderMask` = buckets - 1, 6 `HeaderRingCapacity` = 4096, every other word 0. Buckets follow from word 16, `BucketWords` (20) each: key 0-14, state 15, slot 16, mode 17, fault 18, samplerSlot 19 (0).
- **Ring:** count at word 0; records from word 4, 16 words each (key 0-14, pc 15, `FaultFlag` in the pc for a fault record); the count may pass the capacity (dropped = count - capacity). The driver resets the count of a chunk before its batch and reads it after the batch's fence.
- **Bind:** `vkCmdBindDescriptorSets(firstSet 2, {BindlessHeap::HeapSet(), table set}, 1 dynamic offset = chunk x stride)`, with every draw and dispatch whose `ShaderResources` has a device-table stage.
- **Pipeline layouts:**
  - graphics: `{set 0, fragment set or an empty layout, HeapLayout, table layout}`;
  - pipeline libraries: both parts' masks include sets 2 and 3, and the layout keys carry the markers 0x48454150 ("HEAP") and 0x5441424c ("TABL");
  - compute: `{set 0, workgroup memory set or an empty layout, HeapLayout, table layout}`.
- **API for LA-004:**
  - `DeviceImageTable::Existing(context)`, `SetInterfaceLookup(fn)`;
  - `Prepare(build, recorder, identities)`, `Bind(...)`;
  - `NoteProgram(result, codeAddress)`, `ServesProgram(codeAddress)`, `ServesIdentity(identity)`;
  - `Totals()`;
  - `VulkanDevice::DeviceImagesServe(codeAddress)`, `NoteDeviceImageProgram(result, codeAddress)`, `DeviceImagePath()`.
- **The interface:** `DeviceImageTable::Interface{std::uint64_t id; ImageResource image; std::vector<ImageResource> modes;}`, the same fields as LA-002's `DeviceImageInterface`. LA-004 can make one an alias of the other, or adapt in the lookup lambda.

## How freshness and slot lifetime work

- **Index:** `blocks` maps each 64 KiB tracker block an entry covers (`address >> 16` up to the last byte) to its keys, with the generation of the block's last check. It is updated when an entry is held or released, never rebuilt.
- **Per Prepare:** `refresh()` compares `{GuestMemory::ThreadCollectEpoch, UnwatchSerial, DepthSurfacesSerial, StorageTexture::PendingSerial, GuestMemory::OwnWriteSerial}` with the last check and returns when they are equal. That covers the CPU's stores (seen at the next collect epoch, as the CPU path sees them), the driver's own stores (`Write`, `WriteChanged`, `StoreOwnBytes`, `MarkWritten`) and the pending registry.
- **When the state moved:** for each run of adjacent blocks, `GuestMemory::CollectWrites(run)`, then `GuestMemory::ChangedBlocks(run, block generations)`; when the pending serial moved, `StorageTexture::ScanPending({run})`.
- **Checked entries:** in a changed block, an entry with `!UnchangedSince(entry range, entry generation)`, or one overlapped by pending results, is looked up again with `LookupDeviceTableTexture`. That runs `CompletePendingCpuWrites` and `cachedTexture`, as a direct binding does at each use: render-target and storage results reach the entry exactly as they reach a direct binding.
- **Outcome of a check:** a different `Texture` back means the entry is refreshed (a new heap slot, the bucket updated, the old texture handed to `Recorder::Keep`); the same `Texture` means only the generation is recorded. An unmapped entry, or one now rejected, is dropped and its key updated or removed.
- **Lifetime:** an entry holds its `std::shared_ptr<Texture>`, so `BindlessHeap::sweepLocked` (which frees a slot only at `use_count() == 1`) keeps its slot. Eviction, replacement and drops move the reference into the open batch's kept objects (`Recorder::Keep`). It is released after that batch completes, and so after every earlier batch, which are the only ones whose recorded draws could have sampled the slot; the next draws see the uploaded buckets without the key. The test watches an evicted texture's `use_count` stay up until the batch completes and drop after (the recorder's release thread).

## The fallback mechanism

- **Reasons, each logged once per program:** `[device-images] the program 0x<address> (identity <hi><lo>) takes the CPU table path from its next recompile: <reason>`.
  - (a) "the image heap has no free slot of kind K": `TextureSlot` returned none, even after the heap's own sweep;
  - (b) "the key table is full at N entries in B buckets, even after its budget evicted";
  - (c) "its misses overflowed the ring of 4096 records in 3 batches in a row" (a batch without overflow resets the count);
  - (d), added: the entry is a depth surface or a per-use copy, which the CPU path serves.
- **Attribution:** `Prepare` receives the pipeline identities of the stages with `deviceImageTables` (draws: the stages' results; dispatches: the shader's). The batch's ring chunk keeps them, so each drained miss carries the programs of its batch.
- **Request sites:**
  - after materializing, the draw capture and dispatch sites call `NoteDeviceImageProgram(result, codeAddress)`, which maps identity to code address;
  - before building a request, the draw capture, dispatch and registry sites ask `DeviceImagesServe(codeAddress)` and turn `deviceImageTables` off for a program in the set.
- **Speed:** the failure is decided when the failing batch's misses are resolved, at the next Prepare after it completes. The program's next draw or dispatch then builds a CPU-path request (a different cache key, so a recompile). Draws recorded in between read zeros for the unresolved keys, as any miss does.

## Costs (lavapipe)

- **CPU cost per batch with nothing changed:** 0.07-0.08 us per Prepare within a collect epoch (the serial compare, the chunk lookup). In a new epoch with nothing written, 11.0-12.4 us for 2000 entries: one scan over 32 blocks in one run.
- **Per inserted key:** 92-97 us. That is the texture-cache lookup that makes a new 4x4 texture, the heap slot, and the bucket insert.
- **Bytes uploaded per insert:** 80 (one bucket); the header (64 bytes) only when the bucket count changes. When an insert grows the table (here, in some runs, a probe sequence over 16 steps at 2000 keys in 4096 buckets), the whole table is copied: 655,360 bytes, about 328 bytes per insert for that batch. An empty table's rebuild is a fill, not a copy.
- **Per refreshed entry:** one store refreshed in 6.4-7.0 ms. Most of that is re-validating the 64 entries sharing its 64 KiB block (texture-cache lookups with a 1 KiB compare each); one is a new texture, which costs about one insert. The write tracker is block-granular, so small textures packed in a block share the check.

## Open problems

1. **Stages beyond VS/FS/CS.** PR 6947's heap set layout has stage flags VS | FS | CS, and the table's set 3 matches them. LA-002 qualifies device columns in any draw stage, so a device column in a tessellation, geometry or mesh stage would bind sets the stage cannot see. LA-004 must either widen the heap layout's stage flags (PR 6947's code) or keep device columns to those three stages.
2. **Eviction recency.** The shader reports no hits. An evicted entry that is still in use misses once (its draws read zeros for one batch) before it is resolved again. A hit stamp would need a bucket word (an ABI change), or LA-002's expectations.
3. **Attribution is per batch.** A key the heap or the table cannot take sends back every device-table program that prepared that batch, not only the one that missed. Exact attribution needs per-program ring chunks, or the interface id to program map that LA-002's registry could provide.
4. **The switch-over waits for a new request.** A draw or dispatch served from a cache that skips the request (draw recipes, the dispatch cache) keeps its device-table result until that cache misses. LA-004 should check that a fallback invalidates those caches for the program.
5. **GPU-written textures under an entry:** settled for what the texture cache handles. A pending GPU result over an entry's range triggers the re-check, and `cachedTexture` copies from the pending storage image as for a direct binding. Two cases are not served:
   - depth surfaces, which need per-use layout transitions;
   - textures the cache remakes or refreshes per use.

   Both stay unresolved and fall the program back (reason (d)). Serving them needs fable-void's per-use entries (his later commits), a later piece.
6. **Unwatched memory.** Entries over guest memory outside the write watch are re-checked at every epoch change (`UnchangedSince` is never true there), as his code did.
7. **Draws outside the recorder** (non-resident targets) that read device-table images throw "not implemented".
8. **Fault reporting** goes through the recorder's completion log, as the CPU path's recorded `CheckFaults` does; it is not rethrown to the submitting call.
9. **The 4096 slots per kind.** PR 6947's heap holds 4096 textures per kind, while Resident Evil Village's tables hold 32,768 records. The `[device-images]` line prints the peak distinct textures per kind, and LA-004's harness run should report it.
10. **The interface lookup** of the device's own table is empty until LA-004 sets it. Before then, a miss throws "a missed key names the image interface ..., which no compiled program registered" (no program sets `deviceImageTables` before LA-002 lands).
