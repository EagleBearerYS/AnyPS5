# BF-301 result: BF-296's round-trip harness on BF-290's fix, with byte assertions per pair

Worker: cloud-4 (Linux, 4 vCPU Xeon VM, lavapipe/llvmpipe only).

## In short

- **The harness found a correctness gap in a7e04ab973.** Once X and Y come from the texture cache (BF-296 makes them directly, so the handoff never engaged; see below), the flushing pass of the RGBA8/R32 pair fails at round 1: `Y does not hold X's last results after its lookup`.
- **The cause:** after a borrow, the borrower's generation stays at the moment of the borrow. Suppose the lender then stores those units (here the test's flush; in a game, any flush or CPU read of the range), and the borrower is written without another refresh. The borrower's own write-back then takes those blocks for CPU stores, keeps the guest bytes, and loses its newer results. Main has the same gap, but only with a write-watched host import.
- **The fix** is a second commit, **a038d69eb0**. A lender remembers its borrowers and advances them past its write-back's stamps, as the write-back already does for adjacent pending images.
- **So the branch has three commits** instead of the two asked for. a7e04ab973 is unchanged as commit 1, and the test is commit 3. Merging a7e04ab973 alone is not safe; it needs a038d69eb0.
- **With the fix, pair 2** (R32 against RGBA8, cached images, copied memory) moves no bytes through host memory in the measured pass. The new assertions say exactly that, and they fail with main's `Texture.cpp`.

### Commit 2 (a038d69eb0): `Graphics/src/Texture.cpp` +31 −1, `Graphics/include/Texture.hpp` +3

- **`borrowUnits`** records the borrower in the lender's new `borrowers` list (weak pointers, pruned).
- **`writeBackLayers`**, before it stamps anything, takes the borrowed units it stores (`borrowersUnchanged`). It takes only those that are:
  - still held at the version they were lent at;
  - not kept for the CPU by this write-back;
  - unchanged in memory since the borrower's generation.
- **In `settle`,** once the stamps are made, `advanceBorrowers` advances those units past the stamps and drops their `layerOriginal`. This mirrors the existing `adjacentPendingUnchanged` / `advanceAdjacent`. The saved guest bytes no longer match the memory, so the borrower's next write-back re-reads them.
- **Skipped when** the write-back stores drawn rectangles only.

**Why it is correct:** a unit still held at the lent version is byte-for-byte what the lender stored. With no other stamp since the borrower's generation, the only new stamps on those blocks are this store's, so the borrower's texels match the memory at the new generation.

**Why the other runs keep the round trip:**
