**Reasons for the new counters:**
- **`AddressCopyCounters`:** nothing counted the bytes address-based builds copy, or the size of a build against the cap. The cap check computed the sum and threw it away. The counter runs only in builds that copy something (a TLS lookup, 3 relaxed loads, 2 stores), in the `PacketCounters` pattern: owner-only stores, no read-modify-write, folded by the overlay.
- **`notImplementedCalls`:** no count existed. It is a `fetch_add` on the throw path, which is not hot: the call throws a `std::runtime_error` right after.
- **Render passes:** these are not a counter of their own. `PerformanceTrace::Count` uses the trace totals that lines 1-3 turn on anyway; while hidden it is the same `Recording()` check every `PerformanceTimer` already makes.

**Trace totals without `APS5_TRACE_*`** (`Execution/src/PerformanceTrace.cpp`, `PerformanceTraceThread.cpp`):
- **Switching it:** `PerformanceTrace::SetOverlayTotals(on)` (241) is a no-op when `Configured()`. Otherwise it sets `recording` and a binder function pointer. `Toggle()` (`PerformanceOverlay.cpp:833`) calls it under a mutex with `page == 2` for the new page, and `ANYPS5_OVERLAY=2` turns it on when the settings are first read (83).
- **Naming threads:** `BindThread` without `Configured()` now stores the thread's name only (219); it allocates nothing. The `Configured()` guards were removed at `QueueWorker.cpp:145` ("queue worker 0x…") and `ShaderRegistry.cpp:1502` ("shader prepare"). `DrawPipeline.cpp:191/373` already called it ("draw finisher", "draw committer"), and page 2 names the presenter (880). The "title" binding (`ShaderRegistry.cpp:1713`) is still `Configured()`-only, because it runs per call.
- **Binding:** a named thread is bound on its first `Thread()` call while the binder is set (`bindNamed`, 231). It gets 0 slice capacity and `buffering` stays false, so `TraceThread::Add` only runs `account()`. Unnamed threads are never bound, which keeps the session bounded: the GPU-map import spawns a host thread per mapping, for example.
- **Reading:** `ThreadTotals` (251) copies the names and totals under a **tried** session lock, and the overlay keeps the previous figures when it is busy.
- **Lock order:** the sampler runs on the presenter while it holds `GuestMemory::GpuMutex`.
  - **Tried locks:** `drawCacheMutex`, the two prepare pools' mutexes and the trace session mutex, so an unknown lock order cannot deadlock.
  - **Plain locks:** the imports lock, whose documented order is GPU mutex first (`docs/dev/ARCHITECTURE.md`, `settleImport` paragraph), and the pipeline store lock, which draws take while holding the GPU mutex.
  - **The refused-shader set's mutex** is a leaf.
- **An explicit `APS5_TRACE_*` run behaves as today:**
  - `SetOverlayTotals` does nothing;
  - `BindThread` binds exactly as before;
  - `Count` returns at the binder check;
  - page 2 shows lines 1-3 only while that trace records, and leaves line 4 out.

## Left out, and why

- **Upscaler mode:** PR 10043 is not merged into main ef0d8ae3b.
- **Shader disk-cache hit rate:**
  - **Why it's left out:** `ShaderDiskCache::Totals()` is fenced off from other sources by `shaderCacheReviewedNames` in CMake, so I didn't wire it. `HIT %` covers the draw cache and the in-memory pipeline cache (the pipeline store).
  - **For the PR:** the reviewers can say whether the disk cache's totals may be read here.
- **Busy % for threads other than queue workers:** none. The queue workers are the packet workers, one per queue, and `worker_busy_pct` counts only them. The draw committer, draw finisher and shader-prepare threads do appear in the phases.
- **Title threads in the phases:** only with `APS5_TRACE_*`. Page 2 binds only threads that named themselves. The "title" binding runs per `ResolveGraphicsStagesAbi` call and stays `Configured()`-only, so the hidden path gains no work.
- **GPU-time lines:** none on page 2, so no GPU query is added. `Q0 WAIT … GPU` is the CPU's time waiting for the GPU.
- **Submission stages:**
  - **What they are:** `Submission` stages such as `order_wait` and `flip_room_wait` (`QueueWorker.cpp` ~36-46).
  - **Why they're not in Q0 waits:** they feed `FrameTiming` only under `APS5_ENABLE_TIMING_LOG`, not the trace, so the Q0 wait split uses what the trace has: the packet memory and rendering waits, the GPU-mutex waits, and the recorder, serial and fence waits.
- **Platform differences:** no line is Windows-only or Linux-only. `COMMIT` and `FAULTS/S` have a source on each OS, named in USAGE.md. Linux's `CommitLimit` is enforced only with `vm.overcommit_memory=2`, which the docs say.
