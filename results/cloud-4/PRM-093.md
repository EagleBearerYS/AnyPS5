# PRM-093: #7642's six `agc_driver_heap_slots*` failures with `APS5_GPU_HEAP=1 APS5_GPU_PATH=1`

Worker: cloud-4 (lavapipe only; no device with `VK_EXT_descriptor_heap`).

**Verdict: (a), the tests' assumption.**
- **What the tests assume:** that the device's `BindlessHeap` doesn't exist until their own first `BindlessHeap::For`, which runs after they set `APS5_HEAP_SLOT_CAP`.
- **What happens with the path on:** `APS5_GPU_PATH=1` makes the `VulkanDevice` constructor create the device image table. Creating it calls `BindlessHeap::For`, which **builds the heap during device open**. The heap reads the cap only in its constructor, so it keeps its full slot count, and none of the refusals at 1 or 8 slots happen.
- **What the table doesn't do:** take, hold or keep heap slots at open, or anywhere outside a per-draw lookup.
- **The fix:** fork `prm/7642-heap-slots-gpu-path` = **3e36904802**, one commit on 88ad9e88d8. It moves the cap's `setenv` before the device opens.

- The local heaps in the no-argument run are built after `setenv`, so they are capped either way. Only the per-device heap behind `BindlessHeap::For` is affected.

## 2. What `APS5_GPU_PATH=1` changes: the call chain

1. **The switch:** `Graphics::GpuPathEnabled()` reads `APS5_GPU_PATH` once (`DeviceImageTable.cpp:126–129`).
2. **Device open:** `VulkanDevice.cpp:2309–2313` sets `state->deviceImagePath = !DeviceImagePathRefusal({GpuHeapEnabled(), DescriptorHeapEnabled()})`. That is true on a descriptor-heap device with `APS5_GPU_HEAP` set (`DeviceImageTable.cpp:131–135`).
3. **Still in the constructor**, once the context is ready, `VulkanDevice.cpp:2334–2338` calls `Graphics::DeviceImageTable::Create(state->context, …)`.
4. **The table** (`DeviceImageTable.cpp:117–124`) does `std::make_unique<DeviceImageTable>(context, lookup, HeapSlots(context))`.
5. **`DeviceImageTable::HeapSlots`** (`DeviceImageTable.cpp:85–93`) does `auto* heap = &BindlessHeap::For(context);`.
6. **`BindlessHeap::For`** (`BindlessHeap.cpp:222–237`): no heap exists for this `VkDevice` yet, so it builds one with `std::make_unique<BindlessHeap>(context)`.
7. **`BindlessHeap::BindlessHeap`** (`BindlessHeap.cpp:154`, lines 184–187) sets `slotCap = Abi::GpuImageHeapSlots` and applies `APS5_HEAP_SLOT_CAP` only if it is set **now**. It isn't, because the test sets it later. So the heap keeps the full `GpuImageHeapSlots`.

**Afterwards:** every `BindlessHeap::For(context)` in the test returns that same full-size heap. With `APS5_GPU_HEAP=1` alone, nothing builds it at open, so the test's first `For` builds it after the cap is set, and all six pass, as jotitadev saw.

**Does the table reserve or hold slots? No.**
- Its constructor (`DeviceImageTable.cpp:97–115`) allocates its own table and miss-ring buffers, writes the header, and reads `slots.serial()`. It calls no `slots.take`.
- `slots.take` has one caller, `DeviceImageTable.cpp:364`. That is a per-lookup `TextureSlot` while an entry is filled for a draw, and it is guarded by `slots.nearlyFull()`.
- The heap-slot tests record no draw, so the table takes no slot in them. It doesn't change the free-slot count those tests read; it changes only **when** the heap is built, and so its cap.

**Release order is fine in production:** `VulkanDevice.cpp:989–990` releases the table (`DeviceImageTable::Release`) before the heap (`BindlessHeap::Release`), so the table's cached `BindlessHeap*` never outlives the heap.
- The five modes call `BindlessHeap::Release(context.device)` themselves before the device closes. Nothing touches the table between that and device teardown, and the table's default destructor doesn't dereference the heap.

**Why (a) and not (b):** the table takes no slot it shouldn't, holds none, and leaves the heap's accounting alone. The only interaction is creation order. The tests read the cap through the environment, and the heap reads the environment once, at whatever moment it is built. **Compared with #9508's dfe95cc969:** that commit made its tests count the heap's extra variants when the heap is on (`HeapFragmentsEnabled() ? 2 : 1`, heap-variant stages, `gpuResolvedImages`). Here the tests need no recount, only the cap in place before anything can build the heap.

**Every check is kept** as it was: the same caps (1 and 8), the same boundaries and the same messages. The heap now gets the capped size whether the table builds it at device open (path on) or the test's first `For` does (path off).

**Path off is unchanged:** nothing builds the heap at open, and the cap was already set before the test's first `For`. `APS5_HEAP_SLOT_CAP` has one reader, `BindlessHeap.cpp:185`.

**What would make each test red:**
- **All six:** a heap that ignores `APS5_HEAP_SLOT_CAP`, or a device-open path that builds the heap before the cap applies again. Their refusal checks would fail, which is today's failure. The no-argument run fails in `viewSlots` first; the five modes at their `NearlyFull` checks (lines 169, 190, 219, 277, 290).
- **With the path on, now also:** a device image table, or anything else at open, that takes a heap slot. With a cap of 1, the no-argument run's first `ViewSlot` is refused ("a view keeps its slot", line 95). With a cap of 8, the five modes start with only 7 free slots, so "takes one of the eight capped slots" or the come-back checks fail.
- **A `NearlyFull` margin** that no longer flags one free slot of eight: the five modes fail at their `NearlyFull` lines.
