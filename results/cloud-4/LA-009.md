- **Commit:** 9737a1ab1 `fix(agc): count a ring overflow only for batches taken after their program's misses were resolved`. Author and committer Yunus Shaikh, unsigned, no trailers.
- **The counting rule as built** (`DeviceImageTable.cpp` `resolve`, `chunkFor`, `drain`):
  - `resolveGeneration` moves once for each resolve that has pending misses to work through.
  - Each chunk records the current generation when a batch takes it (`Chunk::generation`, set in `chunkFor`).
  - `overflowFrom[program]` is the generation from which that program's overflows count:
    - The first resolve that handles a batch containing the program sets it to that resolve's generation (`try_emplace`).
    - Each overflow that counts moves it to `resolveGeneration + 1`, the next resolve, which handles that batch's own misses.
  - In `drain`, a program is skipped entirely when it has no `overflowFrom` yet, or when the chunk's generation is below it. Such a batch was taken before the inserts that answer the misses it overflowed on. It does not count, and it does not reset the streak.
  - Otherwise:
    - An overflowing batch adds to the streak.
    - A batch without overflow resets the streak.
    - `OverflowBatches` (3) and the fallback message are unchanged.
- **Where the built rule departs from the task's "one way"** (chunk generation at or after the program's *last* insert generation):
  - **That literal form never counts with a deep pipeline.** The resolves of the in-flight stale batches keep moving the program's last insert generation past every chunk that is still in flight, so a real overflow would never fall back.
  - **The built rule waits for one resolve round per count.** With N batches in flight, a real overflow falls back after about 3 × N batches. It still falls back (test b).
  - **A batch on a cold table (before any resolve of the program's misses) no longer counts.** This is what gives "streak 0" in (a). It also means a program that overflows from a cold start falls back after 4 batches (1 cold, then 3 counted), not 3.
  - **The old `pending.empty()` condition is gone.** The generation rule already counts a group drained before one resolve at most once. The old condition also stopped counting whenever *another* program's misses were pending.
