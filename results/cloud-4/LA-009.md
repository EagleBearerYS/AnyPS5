## 1. The counting rule (9737a1ab1)

**As built** (`Graphics/src/DeviceImageTable.cpp` `resolve`, `chunkFor` and `drain`; `Graphics/include/DeviceImageTable.hpp`):
- **`resolveGeneration`** moves once for every resolve that has pending misses to work through.
- **`Chunk::generation`** is set in `chunkFor` to the current `resolveGeneration` when a batch takes the chunk.
- **`overflowFrom[program]`** is the generation from which that program's overflows count. Two things set it:
  - The first resolve that handles misses of a batch containing the program sets it to that resolve's generation (`try_emplace`, once per batch's program set rather than once per miss).
  - Each overflow that counts moves it to `resolveGeneration + 1`, the next resolve, which handles that batch's own misses.
- **In `drain`:**
  - If a program has no `overflowFrom` yet, or the chunk's generation is below it, the program is skipped for this batch. Such a batch was taken before the inserts that answer the misses it overflowed on. It neither counts nor resets the streak.
  - Otherwise an overflowing batch adds 1 to the streak, and a batch without overflow resets it.
  - `OverflowBatches` (3) and the message "its misses overflowed the ring of 4096 records in 3 batches in a row" are unchanged.

**Where it departs from the task's "one way"** (chunk generation at or after the program's *last* insert generation):
- **That literal form never counts once the CPU runs ahead.** Each resolve of a stale in-flight batch's misses moves the program's last insert generation past every chunk still in flight. A real overflow would then never fall back.
- **The built rule needs one resolve round per counted batch.** With N batches in flight, a real overflow falls back after about 3 × N batches, not 3.
- **A cold batch no longer counts.** A batch taken before any resolve of the program's misses is cold. This is what gives "streak 0" in (a). It also means a program that overflows from a cold start falls back after 4 batches (1 cold, then 3 counted) instead of 3.
- **The old `pending.empty()` condition is removed.** The generation rule already counts a group that drains before one resolve at most once. The old condition also stopped all counting whenever *another* program's misses were pending.

**New read-only accessors, for the tests:** `DeviceImageTable::LastFallback()` and `OverflowStreak(identity)`.

**Tests** (`tests/execution/DeviceImageTable.cpp`, ctest `agc_driver_device_image_table`):
- **(a) `OverflowsBeforeTheirInsertsDoNotCount`, new.**
  - **Setup:** five chunks are taken and overflowed (4,097 records each) before any resolve. Then the batches finish one at a time with `Recorder::FinishUpTo(serial)`, and each is followed by a `Prepare` that resolves. That is the CPU-ahead order LA-007 described.
  - **Red** (eb09b456e plus the two accessors and this test, without the rule): `streak 5, 1 fallbacks`, with the "overflowed the ring of 4096 records in 3 batches in a row" line.
  - **Green** (9737a1ab1): no fallback, and the streak is 0, read before the open batch's chunk drains.
- **(b) `WarmOverflowFallsBack`, new: real overflow still falls back.**
  - **Setup:** the five warm-up keys are resolved first. Then three synchronous batches each record 4,097 distinct keys (they differ in their sampler words), of which 4,096 fit and 1 drops.
  - **Each batch's misses are resolved before the next batch is taken:** 8,197 inserted, 3 dropped.
  - **Result:** exactly one fallback, and `LastFallback()` is exactly "its misses overflowed the ring of 4096 records in 3 batches in a row".
- **`OverflowFallsBack`, adapted to the cold rule.**
  - It now starts with one warm-up batch.
  - Its reset part runs the counts {1, overflow, overflow, 1, overflow, overflow} and expects streak 2. Without the reset the streak would be 4 and the program would fall back.
- **`OverflowsBeforeAResolveCountOnce`** (LA-004) passes unchanged. Under the new rule its four cold batches count zero times.

## 2. One record per missing key per batch (bdfc29f11)

**Layout** (`core/shader/recompiler/DeviceImageTableAbi.hpp`):
- Each ring chunk now holds the count word, then a **seen table** of `RingSeenSlots` = 4,096 words at `RingSeenWord` = 4, then the records at `RingRecordsWord` = 4 + 4,096.
- `chunkFor`'s existing memset of `RingRecordsWord` words now clears the count and the seen table together: 16,400 bytes each time a batch takes a chunk.
- The ABI `Version` goes from 2 to 3, and `ShaderDiskCache::FormatVersion` from 41 to 42.

**The device lookup's miss append** (`SpirvBackend/src/SpirvImageEmitter.cpp`, `DefineDeviceImageLookup`):
- A lane that misses takes the lookup's own Murmur3 key hash and sets `mark = hash | 1`.
- It probes up to `RingSeenProbes` = 8 slots, linearly from `hash & 4095`, with `OpAtomicCompareExchange(slot, comparator 0, value mark)` (device scope, relaxed):
  - **The slot was empty** (it read 0): the lane claimed it, and it appends the record as before.
  - **The slot holds its own mark:** the lane skips.
  - **The slot holds another mark:** the lane probes the next slot. After 8 other marks it appends anyway; these are the "plus collisions" records.
- **Faults are not deduplicated.** Every faulting lane still appends its `FaultFlag` record, as before, and the drain still throws on the first fault.
- **No per-wave election.**
  - A ballot needs `requirements.subgroupBallot` set before module setup, which drives the capability, and it needs ballot support in the fragment stage on every device the path serves.
  - The recompiler only gates this per program today, so the election is not cheap to add here.
  - The CAS replaces the per-lane `AtomicIAdd` on the count word, so contention on the miss path is no worse than before.
- **One known gap:** two different keys with the same full 32-bit hash in one batch. The second key is not recorded in that batch. It is recorded in the next batch, once the first key is in the table. I did not add a test for this.

**Tests** (`tests/execution/DeviceImagePath.cpp`, `agc_driver_device_image_path`):
- **What the new parts draw:** each draw goes into a new 512×512 target at block offset 0x400000.
  - The pixel program is `LargePixelCode`. It is `PixelCode` with u = 1.0, so it has its own identity.
  - Each draw covers 130,816 pixels.
  - The keys are 16 new 8_8_8_8 textures at table entries 1900–1915.
- **One batch per draw:** the harness forces eager write-back, so each draw is its own batch. In the 8-key submission, 7 of the 8 keys were already inserted before the submission ended.
- **The keys of one draw are wave-uniform,** as the guest T# is an SGPR. So several keys in one batch are shown by the bench's cold frame (256 distinct keys) rather than by this part.
- **(c) part `j`, `Deduplicates`:** one draw with 1 new key, then 8 draws with 8 new keys.
  - **Red** (the same harness, with the recompiler and ABI changes stashed): `(j) 1 draws of new keys into a 512x512 target, first batch: 4096 miss records and 126720 dropped for 1 missed keys on 130816 pixels per draw`, exit 1.
  - **Green with the switch on:**
    - 1 key: 1 record and 0 dropped. The next batch draws the texel with no records.
    - 8 keys: 8 records and 0 dropped. The next batch draws the texel with no records.
  - **Green on the heap cap,** in the new ctest `agc_driver_device_image_path_heap_cap_dedup_gpu_path` (`--heap-cap j`, `APS5_GPU_PATH=1`):
    - 1 key: 1 record. Then the texel.
    - 8 keys: 8 records and 0 dropped. Over the first two batches there are 6 lookups without a slot, and the program falls back once on heap-full, not on overflow. The third batch draws the texel through the CPU table.
  - **Switch off** (`agc_driver_device_image_path`): the texels come through the CPU table on the first draw.
- **(d) part `k`, `Streams`:** four batches each draw a new key first and the previous batch's key last, then a fifth batch draws only the last key.
  - **Red** (stashed as above): `(k) streaming, batch 1 with a new key: 4096 miss records and 126720 dropped ...`.
  - **Green:**
    - Each of batches 1–4 has 1 record and 0 dropped.
    - Batches 2–5 each draw the previous key's texel.
    - Batch 5 has 0 records.
    - There are no fallbacks and no CPU table snapshots, so the program stays on the device path.
- **Where the parts run:** they are in the default part list `abcdeghijk`. The heap-cap mode now takes a part list, defaulting to `f`.

**What the table shows:**
- **No run on either build falls back.** On eb09b456e, every unprofiled run fell back and was OOM-killed (LA-007).
- **The counting fix alone is enough for this bench.** Its cold frame still drops records, but those batches were taken before the inserts, so they no longer count.
- **With the dedup, the cold frame records each of the 256 distinct keys about once per in-flight batch:**
  - 256 drained with copies, where the CPU waits more;
  - 268–384 with imports;
  - 979 once, when frame 1's batches all drained after frame 2's first resolve.
- **Steady state has 0 records, 0 drops and 0 inserts on every run.**

**The profiled GPU difference:**
- **The measurements:** head 62–69 µs per draw in all 10 profiled runs that kept a thread window, out of 11; base 53–55 in 5 of 5. `[gputime]` agrees: the draw class is 4,095–4,386 ms per 10 s window over about 1,600–1,900 batches on head, against 2,908–3,265 ms on base.
- **Interleaved A/B:** three base/head pairs in alternating builds (`ab-*`) reproduce it: 53, 53, 54 against 64, 62, 63.
- **Where it sits:** all of it is on lavapipe's queue thread: 12.2–13.2 s per 25 s window in runs at the higher level, against 10.7–11.2 s in runs at base level. The four rasterizer threads stay at 0.95–1.14 s each on both builds, so it is not fragment shading time.
- **It is not the ring layout.** A build with the new layout but the old shader append was at base level in 3 of 3 runs (54 (38–39), draw class 3,000–3,398 ms).
- **It is not specific to the probe loop.** Each of these shader variants was at base level in some runs and at head level in others:
  - a single compare-exchange without probing, which is the task's suggested form: 2 of 5 runs at base level, 1 in between (61 µs) and 2 at head level;
  - the probe nested in the old append `if`: 1 of 2;
  - the 8 probes unrolled into nested `if`s: 1 of 2.
  
  The committed loop was at head level in 11 of 11.
- **Unprofiled runs show no difference:** 44 (36) on head against 45–46 (37) on base.
- **What gdb sampling of the queue thread showed:** descriptor-set copy and `munmap` (LA-007's `apply_dynamic_offsets` path) and fence waits. 12 usable samples were too few to tell the builds apart, and I found no cause.
- **For a GPU driver:** a branch with no active lane is skipped, so I expect no such cost on the PC. It is unmeasured there.
