## Recommendation (read first)

**Don't rebase #7642 onto 13764c98c as it stands. Measure first. If the numbers justify it, rebuild #7642's GPU lookups on #9508's descriptor heap as a per-column slot source inside his table map (route B below).** The deciding facts:

1. **#7642 depends on a heap that #9508 removed.**
   - #7642's only #6947 dependency is the *descriptor-set* bindless heap: `BindlessHeap::HeapLayout()`/`HeapSet()` bound as set 2, plus its slot allocation (`TextureSlot`, with our keep-free margin).
   - #7642 adds its own set 3 (key buckets, plus a miss ring with a dynamic offset).
   - #9508's `BindlessHeap` is a new `VK_EXT_descriptor_heap` implementation: pipelines map set 1 onto the heap (`HEAP_WITH_CONSTANT_OFFSET`, `D/Graphics/src/BindlessHeap.cpp:713-739`), and there is no `HeapSet()`.
   - In heap mode, any binding outside set 1 sends the draw down the per-draw path (`DrawUnmapped`, `BindlessHeap.cpp:648-711`).
   - So #7642's set 2/3 route has no counterpart on #9508.
2. **#7642 never served GPU-mode stages, and on #9508 those are exactly the stages with image tables.**
   - On #7642, device columns are switched off for GPU-mode stages (`R/Recompiler.cpp:298-301` on 7642: `... && !gpuModeStage`), and `D/Graphics/src/ShaderResources.cpp:1744` throws "a GPU-mode stage reading images through the device image table is not implemented".
   - #9508 moves image-table stages to GPU mode, with CPU-resolved per-element slot maps.
   - So our lookups only add value on #9508 if they *replace his per-element map for large tables*, inside GPU-mode stages. That is new work, not a carry-over.
3. **The #6947-era GPU walk is gone, and we never used it.** #6947 had `Graphics/shaders/HeapLookupResolve.comp`, a GPU hash probe that wrote slots into the ring. 9a1b77846 had it too, but #7642's own diff never references it (0 matches for `LookupResolve`). Losing it costs #7642 nothing.
4. **A mechanical rebase is mostly churn in plumbing that has to be rewritten anyway.** Three-way merge with base 9a1b77846: 26 files, 53 conflict hunks. Among them: 186 conflicting lines in `BindlessHeap.*`, a 253-line block in `ResourceMaterializer.cpp`, and 51 lines in `VulkanDevice.cpp`.
5. **The part worth keeping doesn't depend on the heap.** The keys and bucket table, the expected-image prediction, freshness, the CPU side of the miss ring, and the tests of those: about 55% of our product lines carry over with little change (table below).
6. **Unmeasured, and it decides the question: what #9508's per-draw map costs for a large table.**
   - `writeHeapTableMap` (`D/Graphics/src/ShaderResources.cpp:5946-6033`) rebuilds the map on the CPU on every refresh, with one `TextureSlot`/`StorageSlot`/`SamplerSlot` per element. It reuses the ring span only when the words are identical and the chunk is still held (6035-6042).
   - Village's ~21,500-entry table is 86 KB of slot words per stage per refresh, plus 21,500 slot lookups.
   - If that cost is small next to the rest of a draw, #7642's GPU lookups aren't worth re-hosting. Park the PR and keep the key and expectation code for later.
   - **Next step:** run the BF-108 bench (fork 413c412595, `VillageDrawCost`, table mode, `VILLAGE_TABLE=4096` up to a 21.5K-entry variant) on #9508 with `APS5_GPU_HEAP=1 APS5_PIPELINE_STATS=1`, and read the `[gpu-heap]` cost line.

## 1. #9508's image-table map

- **Where it's built:** `ShaderResources::writeHeapTableMap`, `D/Graphics/src/ShaderResources.cpp:5946-6033`, called from `writeHeapStage` at 6173 when `program.dataAddressPush` is set.
  - A stage's table goes on the heap only if `table.heap = gpuResolvedImages && dataAddressPush` (5030).
  - The trigger is `RefreshHeapStage` (5833-5836). It runs on every fresh build (1569, 1584), on every resource-template hit (`D/Graphics/src/Draw.cpp:1473`), and for dispatches at record time (`D/Execution/src/VulkanDevice.cpp:4868-4872`).
  - The inputs come from `resolveImageTables` and `addSamplerTable` (5093-5248).
- **What an element holds:** one u32 heap slot.
  - The slot words have no flags and no generation. Flags, dword 3 and the element number stay in the existing `ImageTableAbi` records (`R/ImageTableAbi.hpp:32-40`).
  - The map has five parts of `count` words each, at `map[HeaderElementBase]`: sampled slots, storage slots, sampler slots (4 per guest sampler), and, only when the table has atomics, atomic and atomic64 slots (6010-6029).
  - Missing elements get `AbsentSlot`.
- **Bounds:**
  - elements per stage = `HeaderElementCount`, at most `ImageElementBudget` 65,536; samplers at most 1,024 (`R/ImageTableAbi.hpp:53-54`);
  - the map must fit one 4 MiB ring chunk, or `Allocate` throws (`BindlessHeap.cpp:557`);
  - the shader clamps slots ≥ 4,096 (images) or ≥ 2,048 (samplers) to 0 (`R/SpirvBackend/src/SpirvMemory/SpirvDescriptors.cpp:95`).
- **The pushed words:**
  - The root starts at push dword 38 (`R/RuntimeAbi.hpp:57-69`): root dwords 0–1 are the 64-bit ring address, and each stage has a `TableMap` byte offset (push dword 51, 55, 59 or 63 for Main, Fragment, TC, TE).
  - So the "two dwords" are the shared ring address plus the stage's map offset. Strictly, the shader reads three root dwords for the map. Filled by `PatchDataAddresses` (5881-5944).
- **The shader side:**
  - `LoadTableMap` (`R/SpirvBackend/src/SpirvImageEmitter.cpp:1678-1689`) reads `ring + offset + index*4` through `EmitStageRingWordPointer` (`SpirvBufferAccess.cpp:45-86`).
  - `EmitTableAccess` maps key → record → element (1702-1858).
  - `tableHeapSlot` (`SpirvDescriptors.cpp:89-98`) reads `map[base + part*count + element]` and indexes the 4,096-entry (2,048 for samplers) set-1 arrays mapped onto the heap.
- **Lifetime:**
  - One 64 MiB ring in 4 MiB chunks (`D/Graphics/include/BindlessHeap.hpp:82,94-100`), with a bump allocator (`BindlessHeap.cpp:555-586`).
  - A chunk is reused after its batch serial completes (`enterChunk`, 588-601). That bumps `entries` and so invalidates its spans.
  - `Held(mark)` (537-553) keeps a span while its chunk hasn't come back.
  - `heapSpan` reuses the previous span when the words are equal and still held (6035-6042).
  - The heap walk memo (`D/Execution/src/Driver/Draw/HeapStages.cpp:203-405`, admitted on the second sighting) caches the CPU SRT walk, not the slots.
- **When it falls back to the per-draw path:**
  - `APS5_GPU_HEAP` is unset;
  - the device lacks `descriptorHeap` or `maintenance5`, `BindlessHeap::Fits` fails, or `maxPushDataSize < 256` (`VulkanDevice.cpp:1780,2073`);
  - the heap is nearly full: free slots below `min(1024, cap/4)` images or 512 samplers. That raises `HeapRefused()` (`HeapStages.cpp:85-108`), which clears after a sweep leaves twice the margin free. Dispatches ignore it (98-100);
  - per-stage reasons (`HeapStageReason`, `BindlessHeap.hpp:162`): disabled, pair refused, fragment off the heap, stage kind, no plan, plan stage, unresolved image source;
  - module bindings outside set 1 (`DrawUnmapped`/`DispatchUnmapped`);
  - a draw mixing heap and per-draw stages, whose retry refuses the pair (`D/Execution/src/Driver/Draw/Draw.cpp:837-870`).
  - Image atomics and thread-dimension dispatches no longer fall back. A full heap after a sweep is a hard `Require` (5969).
- **Room in the ABI:**
  - The ring has no header, records or version.
  - The root is full: `static_assert(RootDword + RootDwords == PushDataDwords)`, 64 dwords (`RuntimeAbi.hpp:69`).
  - Unused words: `ShaderData::reserved` (`RuntimeAbi.hpp:97`, never read), and the 4th dword of each buffer-address quad (written 0 at `ShaderResources.cpp:5861`).
  - `ImageTableAbi::Version` = 2. `RuntimeAbi::Version` stays at 14.

## 2. #7642's pieces on #9508

How a #7642 stage reaches the table today: set 2 is #6947's descriptor-set heap (`device_heap_<kind>[4096]`); set 3 binding 0 holds the bucket storage buffer and binding 1 the miss ring, as a dynamic storage buffer. There are no push constants. They are bound at `DeviceImageTable::Bind` (`D/Graphics/src/DeviceImageTable.cpp:337-345`), from `ShaderResources::BindHeap` (5315), and declared at `SpirvEmitterHelpers.cpp:418` and `Pipeline.cpp:380-386`.

- **Keys: survive.**
  - 15-word key: T# (8), 64-bit image interface id, sampler class, S# (4).
  - 20-word bucket: the key, then state, heap slot, mode, fault and sampler slot.
  - 32-bit Murmur-style hash, at most 16 probes, 10 MiB device buffer (`R/DeviceImageTableAbi.hpp`; `DeviceImageKeys.cpp` grows from 4,096 to 2^17 buckets).
  - The heap slot it stores means the same on #9508: an index into the per-kind heap arrays. `BindlessHeap::TextureSlot(kind, texture, view, layout)` exists there (`BindlessHeap.hpp:44`). Our `keepFree` parameter doesn't.
- **Expected images: survive, with conflicts.**
  - `ExpectedDeviceImages` (`ResourceMaterializer.cpp:1558` on 7642) and the memo `Driver::expectDeviceImages` (`DrawCapture.cpp:290`, 16,384 entries keyed by plan, code and user data) don't depend on the heap.
  - They conflict with #9508's heap-stage materialize, `MaterializeHeapStage` in `ResourceMaterializer.cpp` and `DrawCapture.cpp`.
- **Freshness: survives.**
  - `refresh` (`DeviceImageTable.cpp:546-634`: epochs, pending serial, `OwnWriteSerial`, storage-cache ownership, host imports) and `evict` (636, LRU) don't use the heap.
  - On #9508, our slots would also have to follow his sweep, which can free a slot we hold (slot generations; the sweep re-enables the heap at `BindlessHeap.cpp:410-425`). That is new.
- **Fallback: changes.**
  - Today a program falls back to the CPU table path: `FallBackProgram` and `DeviceImagesServe` at `Dispatch.cpp:155`, `DrawCapture.cpp:46`, `ShaderRegistry.cpp:1145`, `VariantValidation.cpp:86`, and `cpuImageTables` in `Draw.cpp:1055`.
  - On #9508, the natural fallback for a GPU-mode stage is his CPU-resolved map, so the target and the plumbing change.
  - "Outside the recorder" (`Graphics/src/Draw.cpp:2316`) and the journal check (`PipelineJournal.cpp:933`) carry over.
- **Miss ring: the CPU side survives; the shader side changes.**
  - The record format, `DecodeDeviceImageRing`, `drain` (739), `resolve` (404) and the overflow rule (3 batches in a row) stay.
  - Chunk selection by dynamic offset (`chunkFor`, 714) and the set 3 binding go: heap mode has no dynamic offsets. The shader would get the chunk's address instead.
- **Everything else:**
  - `ResourceTracker` column planning survives, but the `!gpuModeStage` gate flips.
  - The `SpirvImageEmitter` lookup (`device_image_lookup`, 1827) survives, apart from how it addresses buckets and ring and how it turns a slot into an image.
  - The set 2/3 declarations, the set-layout code in `ShaderResources`, `Pipeline` and `VulkanDevice`, and the `BindlessHeap` edits are replaced.
  - `ShaderDiskCache` needs a fresh format bump on top of #9508's.
  - Of the tests, `HeapSpaceWrites.cpp` is a #6947 heap test and is dropped.
- **#6947 code our pieces used that #9508 doesn't have:**
  - `BindlessHeap::HeapLayout()`/`HeapSet()` (the descriptor-set heap);
  - `TextureSlot(..., keepFree)`, `TextureSlotCap`, `TextureSlotMargin`, `takeSlotLocked(kind, keepFree)`;
  - `ImageHeapStages` (the stage mask for the set);
  - the heap features enabled in `VulkanDevice` when only the device path is on;
  - `stageCaptures[i].heapWords` pass-through in `drawStages`.

  We never used the heap ring words, heap templates, slot-word patching, `GpuDataSet`, the GPU-mode recompile or `HeapLookupResolve.comp`.

## 3. Route: how a GPU-mode shader on #9508 could reach our table

In every route the shader runs our `device_image_lookup` on the column's T#. The bucket's heap slot then indexes his set-1 heap arrays, exactly as `tableHeapSlot`'s map read does now. Device columns skip their map parts.

| route | ABI change on #9508 | fits his two-dword map? | per-draw cost |
|---|---|---|---|
| **A. An extra pushed address** | a bigger root | no: the root is full (64 dwords, static_assert), and `maxPushDataSize` is only required to be ≥ 256 | 2–4 push dwords per stage, free on the GPU, but not portable. **Reject.** |
| **B. A field in the ring's map (recommended)** | a trailer after the map parts (bucket address, miss-ring chunk address, table generation; 6 words); `ImageTableAbi::Version` 2→3; `writeHeapTableMap` writes it; `LoadTableMap`/`tableHeapSlot` read it | **yes:** reached through the existing stage `TableMap` offset, no third push dword | +24 B per stage map per refresh. For tables mostly served by device columns the map *shrinks*: no per-element slot parts, which is the point. One extra map load per invocation. |
| **C. A heap buffer slot** | a buffer kind and mapping range in his heap, at fixed slots for the bucket buffer and the ring | yes for the buckets. The per-batch ring chunk still needs a per-draw value (B's trailer or D's word) | 0 for the buckets, plus whatever carries the chunk. The most ABI on his side. |
| **D. `ShaderData::reserved` plus a per-batch header in the ring** | use the never-read `ShaderData::reserved` (1 dword) as the ring offset of a per-batch header holding our addresses | yes, no push change | ~0 per draw (one header per batch). It takes a field he reserved, and it is less explicit than B. |

**B** is closest to what Raghav314 offered: the ring's image-table map. It keeps his push layout and puts every addition in the image-table ABI he already versions.
