## Findings, ranked

### Blocking

None.

### Should fix (fixed)

**1. A removed unlock listener could still be called.**
- **Code:** at 0e1891f70f, `NpTrophy2RecordUnlock_nid_no_patch` copies the listener list under the registry lock (TrophyStore.cpp:154) and calls each callback after releasing it (TrophyStore.cpp:156).
- **The race:** a thread unlocking a trophy can run, or be about to run, a callback while another thread's `NpTrophy2RemoveUnlockListener_nid_no_patch` returns. A caller that frees the listener's context after removing it, the usual shutdown order, then has it used afterwards.
- **Who it affects:** part 1 registers no listener outside tests. Part 2's statistics path and the unlock-popup branch build on these listeners.
- **Fix, 28e495f1c:** dispatch and removal share a recursive lock (`Listeners::dispatch`).
  - Removal waits for a running dispatch.
  - A callback may still unlock a trophy (part 2's platinum chain) or remove a listener on its own thread.
  - A listener removed during a dispatch is not called by it.
- **Test:** in `np_trophy2_store`, `testListenerRemovalWaitsForItsCallback`. A callback sleeps 200 ms on an unlocking thread while the main thread removes its listener, and the callback must have finished when the removal returns.

### Docs (fixed)

**2. USAGE and debt didn't say what part 1 records or what stops a game.** Fixed: **68125962b**.
- **What part 1 records:** with no trophy data read, it stores every int32 `_trophy_id` of 0 or more, even one that would be the platinum, a progressive trophy or no trophy. The platinum is not unlocked when the rest are (UdsEvent.cpp:92-93, TrophyStore.cpp:105). Added to USAGE's trophy section and to the libSceNpTrophy2 debt entry.
- **A damaged record stops the game.** A line in `_trophy/<user>_<label>.txt` that is not a new `<id> <tick>` pair throws at the first query or unlock that reads the record (TrophyStore.cpp:75), with the file named. That includes a blank line or a line ending with a carriage return, which an edit on Windows would leave. Added to USAGE; the existing damaged-record test now also covers `"12 5\r\n"`.
- **"Every post returns success" was too broad.** The libSceNpUniversalDataSystem debt entry said so, but `sceNpUniversalDataSystemPostEvent` throws for a null event (Event.cpp:84) and for a pointer `sceNpUniversalDataSystemCreateEvent` didn't return or that was destroyed (Event.cpp:88). Main returned 0 for both. The entry now says which posts succeed.

### Notes (no change)

**3. Unlock semantics, against what's known.**
- **Double unlock:** the second post of the same id changes nothing. No new tick, no log line, no listener call, and the post still returns 0 (TrophyStore.cpp:105). Covered by `np_trophy2_store` and `guest_np_trophy_unlocks`.
- **Before the trophy context is set up:**
  - An unlock is keyed by the UDS context's user and service label (Event.cpp:49), not by a trophy context. So an unlock posted before `sceNpTrophy2CreateContext` is recorded, and a later trophy context of the same user and label reports it.
  - An unlock posted to a UDS context that was never created is logged as `ignored … the context does not exist` and returns 0.
  - What a console does in either case is not known. The debt entry says KytyPS5's error behaviour is not verified.
- **Hidden trophies:** part 1 doesn't read the trophy data, so it doesn't know which trophies are hidden. Queries report the placeholders and the stored unlock, as the debt entry says.
- **Platinum:** out of scope for part 1 (no trophy data), and now documented (finding 2). Part 2 awards it with the last trophy that names it (`PlatinumToUnlock`).
- **Error codes:**
  - Every created event posts with 0, including malformed unlocks (logged) and repeats.
  - Trophy queries on a context that was not created or was destroyed return 0 with no unlocks. The debt entry already says the console's errors there are unknown.

**4. Storage.**
- **Where:** `_trophy/<user id>_<service label>.txt`, under the resolved `/_trophy`, in the title's run directory (`TitleStore`, TrophyStore.cpp:126-127). That is one file per title, user and service label. Restart, two users and two labels are covered by `np_trophy2_store`.
- **Writes are atomic against a crash:** the whole record goes to `<file>.tmp`, then `std::filesystem::rename` replaces the record (TrophyStore.cpp:93-96). A crash before the rename leaves the old record and a stale `.tmp`, which the next save truncates. So a partly written record can't be read back.
- **Not durable across a power cut:** there is no fsync of the file or its directory before or after the rename. On a filesystem without ext4's replace-on-rename flush, a record could come back empty. A note, not fixed: the codebase's other record writers (via `RecordWrittenPath_nid_no_patch`) work the same way.
- **One process only:** each process caches the records it has read, and each save writes that process's whole set. Two processes of the same title running at once would overwrite each other's new unlocks. A real title runs once.
- **A damaged record** stops the game at first use (finding 2), naming the file. That follows the code base's "throw on what can't be handled" rule, and USAGE now tells users.

**5. Threads.**
- Store access is serialized by `TrophyStore::mutex`. Listener dispatch is now serialized by `Listeners::dispatch` (finding 1).
- **Checked by running** a scratch stress test (a temporary addition to `np_trophy2_store`, not committed, file restored): 16 threads each unlock 64 overlapping ids of 64 through `NpTrophy2RecordUnlock_nid_no_patch`. Three runs gave the same result: 64 recorded as new, 64 ids reported to a listener exactly once, 64 lines in the record, store count 64.

**6. UDS events.**
- **Properties kept:** an event keeps its name and a deep copy of its property object. `SetObject`, `SetArray` and the array setters store copies. So no cycle can form, and a title's later changes to the object it passed don't reach the event, as the debt entry says (KytyPS5's model).
- **Which events record an unlock:** only `_UnlockTrophy` with an int32 `_trophy_id` of 0 or more (UdsEvent.cpp:92-93). A `_trophy_id` of another type or below 0 is logged as ignored. `_UpdateTrophyProgress` is logged once per trophy and not stored.
- **Memory bounds:** there are none.
  - Events, property objects and arrays live until their Destroy call. Strings and binaries are copied in full (`Uds::Binary(bytes, bytes + value_size)`, EventPropertyObject.cpp:121), without a guest-memory check of the source range.
  - `sceNpUniversalDataSystemInitialize`'s pool size is not used, and `GetMemoryStat` reports zeros.
  - Main leaked the event structs too but stored no property data. A title that never destroys its events now grows by their property data.
- **Post/destroy race:** `sceNpUniversalDataSystemPostEvent` checks that it owns the event (Event.cpp:88), then reads it (Event.cpp:91) without holding the registry lock. A title that destroys an event on one thread while posting it on another could be read after the free. That is a title bug; noted only.
- **Unbounded log:** a malformed `_UnlockTrophy` logs an `ignored` line on every post (Event.cpp:43). Unlike progress events it isn't limited, so a title that posts one every frame floods the log.

**7. With no trophy data present (part 1 never has any), and with no unlock posted, main's answers are unchanged:**
- `sceNpTrophy2GetTrophyInfo` and `GetTrophyInfoArray`: `unlocked` false, tick 0.
- `sceNpTrophy2GetGameInfo`: `unlocked_trophies` 0 (`ContextUnlockCount`, GameInfo.cpp:29). Main's constant `NP_TROPHY2_UNLOCKED_TROPHIES` is also 0.

**API changes, against main:**
- `sceNpTrophy2CreateContext` (Context.cpp:31, :59) and `sceNpUniversalDataSystemCreateContext` (Context.cpp:47) return 1, 2, 3, … for successive contexts. Main returned 1 every time.
- `sceNpUniversalDataSystemPostEvent` throws for a null or foreign event; main returned 0.
- `sceNpUniversalDataSystemDestroyEvent` and `DestroyEventPropertyObject`/`Array` ignore a pointer they didn't create. Main called `delete` on it, which was undefined behaviour.

All of these are in the docs after finding 2. None depends on unlocks.

## Part 2's refusal (step 1)

**Does part 1 alone accept a posted unlock of an unknown, platinum or progressive trophy?** Yes. It records every `_trophy_id` of 0 or more (UdsEvent.cpp:92-93 → Event.cpp:49 → TrophyStore.cpp:100-110).

**Should ce30ebdac1 move into part 1? No.** Every refusal it adds needs part 2's trophy data:
- `NpTrophy2RecordUnlock_nid_no_patch` refuses only `if (const auto* package = NpTrophy2::Package(serviceLabel))`. `Package` is part 2's trophyNN.ucp lookup (6a1b673a21).
- The three reasons come from `PostedUnlockRefusal(const TrophyPackage& package, std::int32_t trophyId)` in part 2's `TitleTrophies.cpp`:
  - `package.trophies.find(trophyId) == end` gives "no such trophy";
  - `grade == GradePlatinum` gives "the platinum";
  - `progressive` gives "progressive".

  `TrophyPackage`, `GradePlatinum` and `progressive` all exist only in part 2.
- The rest of ce30ebdac1 splits the internal `NpTrophy2::RecordUnlock` (for the statistics path and the platinum award) from the posted path. Part 1 has neither caller, so moving it would add an unused function.

Without the data part 1 cannot tell a platinum or progressive id from any other. So it records them, and its docs now say so (68125962b).

**What a console does** with a posted unlock of a platinum, progressive or unknown id is not known here. Part 2 refuses all three on the strength of the trophy data. Titles post `_UnlockTrophy` for ordinary trophies, so part 1's acceptance changes a record only for a title that posts an id it shouldn't.
