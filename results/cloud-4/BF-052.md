# BF-052: keep CPU-path indirect draws in the draw cache: result (cloud-4)

**Outcome: the gate passes in the harness. Prototype, tests and harness are on fork branch `exp/cpu-indirect-draw-cache`, head `fdb45156c`.**

- **Base:** upstream main `17cfb1f4c` (14 commits past the board's baseline, none in the draw path).
- **Switch:** `APS5_CACHE_CPU_INDIRECT=1`, off by default.
- **PR 6539:** not needed (see below).
- **Gate (Village-shaped harness):**
  - main and PR 6539's head: 0% reuse, every lookup "no entry".
  - With the change: 100% reuse after warm-up, 7.6–8.3 µs validation per hit, 192 entries in ~0.45 MiB.
  - µs per draw packet, median of 3 runs: −34% at 1 record and −28% at 4 records on main; −31% and −32% on PR 6539.
- **Checks:** `ctest -R '^agc'`: 644 tests, 598 passed, 46 skipped as expected, 0 failed; the same with the switch forced on. `tools/check_conventions.py --base upstream/main --head HEAD` passes.
- **Next step:** a PC pair is now justified.
  - This harness's draw keys repeat with the ring's period of 3, as the gate specified.
  - The harness does not model a key that changes every frame (BF-022's 559 of 716 "no entry"). Only Village itself can show whether its keys stay stable with the CPU path cached.

Everything ran on cloud-4: Linux, lavapipe (Mesa 25.2.8, LLVM 20.1.2), 4 cores. Tests and the harness ran as an unprivileged user with stdin from /dev/null. µs figures are single-machine medians on a software rasterizer; single runs vary by about ±10%.

## Step 1: what the CPU path patches and recompiles (upstream main 2bfe0045d; the Draw/ files are identical at 17cfb1f4c)

Read: `Execution/src/Driver/Draw/Draw.cpp` 360-555, `IndirectDraw.cpp` (`ClassifyIndirectDraw`, `FoldDrawOffsets`), `DrawCapture.cpp` (`materializeDrawStage`, `cacheDrawStages`), `DrawRelocate.cpp` (`tagVariantRuns`, `applyShaderDataPatches`), `SrtEvaluator.cpp` (where `SrtUserDataUse` is filled), `SpirvModuleEmitter.cpp` (`EmitGetUserData`), `Recompiler.cpp` 960-1015.

**Words a record patches** (Draw.cpp 497-512). `locate()` maps a packet location to (program, user word) in any non-fragment, non-GS-back program:
- the base-vertex word gets `vertexOffset` for 20-byte (indexed) records, else `firstVertex`;
- the start-instance word gets `firstInstance`;
- the draw-index word gets the record number, for DRAW_INDIRECT_MULTI with the draw index enabled.
- Tessellation programs (TCS/TES) are always in the patched set.
- On the mesh path, stage 0's hidden mesh index-buffer words (`MeshIndexBufferUserWord`..+3) are rewritten from the record's `direct` parameters, and stage 0 is patched.
- Only the local `programs` copy changes. The queue's SGPR registers keep whatever the game wrote, and those are what the draw key hashes.

**Constants or pushed values.** Every program in the patched set is captured and materialized again through `materializeDrawStage` with the patched `userData` (Draw.cpp 535-540):
- `ShaderMemory::Capture` runs the SRT walk again (`SrtEvaluator`);
- `Materialize` reruns `DescriptorBindingBuilder::Populate` on the prepared variant.

A patched word can reach the result two ways:
- **Pushed value.** A `GetUserData` left in the IR is emitted as a load from shader data (`EmitGetUserData` → `EmitShaderDataDwordLoad`). `Populate` fills that data from the request's `userData`: slot k of `pushConstants` (or of the ShaderData binding's `guestDescriptor`) holds user word `shaderDataUserWords[k]`. Here the SPIR-V module, bindings and `variantId` don't depend on the value; only those push bytes do.
- **Walk input.** The SRT walk uses the word as a pointer base (`SrtUserDataUse::asBase`, SrtEvaluator.cpp 205) or evaluates it in its arithmetic (`asValue`, 422). Then the captured runs, the descriptors and possibly the variant depend on the value.

Neither the walk nor the backend folds a user word into the SPIR-V as an immediate: a value read only by the shader stays a pushed load. A word in `shaderDataUserWords` and in neither `asBase` nor `asValue` is pushed-only, so the stage can be reused with the push slot patched. That is the same test PR 6539 uses for `forwardedWords` (`tagVariantRuns`, 516b985e1). Main already has every input it needs: `shaderDataUserWords` is on main (Recompiler.hpp 648), and so are `SrtUserDataUse` and the `shaderDataPatches`/`applyShaderDataPatches` slot patcher (DrawRelocate.cpp 236-260).

Why these draws are on the CPU path at all (`ClassifyIndirectDraw`):
- "patched SGPR not folded" (`NotFolded`) means the packet's base-vertex or start-instance SGPR is not the one the embedded-fetch analyzer folds into Vulkan's `firstVertex`/`firstInstance` (`k != p`), or that SGPR is also read elsewhere (`shared`). By construction, then, the shader reads the patched word itself.
- `NonVertexPath` is any path other than the vertex path (and rect lists unless they go to the GPU).

So for the NotFolded draws the patched word is typically a pushed value. Whether Village's words also reach the walk can only be read from its own shaders (no game data here). The prototype checks this per stage at run time. When a word does reach the walk, it reuses the stage only at the values it was compiled with.

**What else the per-record recompile changes:**
- For every patched program, `decodeVertexInfo` runs again (fetch-shader decode from user words).
- TCS/TES compile with the record's `direct` parameters in `GraphicsCompileContext` (index address/count/size, instance count). Other stages get the packet's `drawParameters`.
- `fold(*programResults[0], direct)` adds the front program's `vertexOffsetSgpr`/`instanceOffsetSgpr` words to `direct`.
- If stage 0 was patched, a rect list is rebuilt.
- The guest memory snapshot is redone, and the push-constant size must not change.

Each record therefore pays a full capture and materialize per patched stage. With the pre-loop compile, a packet of N records captures each patched stage 1+N times.

**`cacheDrawStages`** (DrawCapture.cpp 141): `!(drawParameters.indirect && indirectCpu)` keeps every CPU-path indirect packet out of `insertDrawEntry`. The stages it would insert are the pre-loop ones (captured with the register values, before the per-record loop), so nothing per record would be kept anyway. Separately, data-only hits refuse indirect packets (Draw.cpp `drawDataHits() && !drawParameters.indirect`).

**PR 6539's head** (upstream `refs/pull/6539/head`, 12a5f02d1, stacked on PR 5609, head 09238da82):
- It keeps the exclusion verbatim (its DrawCapture.cpp 143).
- None of the 11 commits it carries beyond main, and none of its debt entries (`docs/dev/debt/libSceAgcDriver.md` at that head) mention the CPU path, or plan to lift the exclusion.
- Its forwarded words act only on relocation (learned in `learnPendingRelocation`, accepted in `relocateDrawEntry`, left out of the alias in `drawRegisterKey`). They never reach the per-record loop.
- Its new data-path fallback in `Draw.cpp` also requires `!drawParameters.indirect`.

## The gate

**Harness.** This is BF-042's per-draw harness (fork `exp/bf042-base` 9ac6d7dc8c, its 4 commits ported unchanged), plus one new mode, `DRAW_RECORD_COST_INDIRECT=1|4` (commit `fdb45156c`).
- **Draw packets.** Each of the 64 draws per frame is a DRAW_INDIRECT (1 record) or a DRAW_INDIRECT_MULTI (4 records, stride 16).
- **Patched words.** The base-vertex and start-instance words are patched into s10/s11 of a vertex shader that reads both as values: z = s10 + s11.
  - The driver classifies every packet `cpu (patched SGPR not folded)`, the same reason as Village. Checked with `APS5_TRACE_INDIRECT_DRAWS=1`: `analyzer v=-1 i=-1 -> cpu (patched SGPR not folded)`, 480 of 480 packets.
  - That is one patched vertex stage plus the pixel stage per packet. By the code path (not counted), main captures 1 + records times for the vertex stage and once for the pixel stage: 3 per 1-record packet, against Village's ~3.1.
- **Record churn.** Every frame rewrites every record: base vertex = 3 × serial, start instance = serial + 1, with the serial unique per frame, draw and record. No record value repeats across frames.
- **Pointer churn.** The pixel shader's SRT pointer and its per-draw object constant buffer (an inline V# in user data) move every frame through a ring of 3.
- **Shape.** The rest is BF-042's: 16 textures, 3 vertex buffers, 2 constant buffers.
- **Run.** 6 warm-up frames (two ring cycles), then 60 measured frames (3,840 draw packets). µs per packet = submission wall time / 64.
- **Counters.** They come from `Driver::DrawCacheCounters()` and a new `Driver::DrawCacheSize()`. Validation µs per hit needs `APS5_PROFILE_DRAW=1`, so it comes from a separate profiled run (its µs/packet is in the last column).
- **Pixels.** After the measured frames, each run redraws 16 draws through the same indirect path and checks the pixels (`16 draws sampled 16 textures`); every run below passed.

**How to read it:**
- **On main and PR 6539's head,** every lookup is "no entry". The packets are never inserted (the exclusion), so the ring's 3 keys never fill.
- **With the change,** the 6 warm-up frames insert each of the 64 × 3 keys on its second sighting; that is the draw cache's admission rule, unchanged. From then on every lookup hits.
- **Memory** is the draw cache's own accounting (`drawCacheVariantBytes`: variant words and runs, not the shared compiled results), the `~MiB` figure in the `APS5_PROFILE_DRAW` draw-cache line. I assume, without having checked, that it is the figure behind BF-022/BF-030's "~4 GB". Here it is 2.3 KiB per entry.
- **Where the time goes.** On a hit, a packet costs the key, the validation (~8 µs), the push-slot patch and the recording. Each extra record costs about 29 µs with the change, against about 38 µs on main (the slope from 1 to 4 records). That remainder is lavapipe's draw recording, not capture.
- **Bar.** Reuse far above BF-015's 5.6% (100% against at least 50%), and µs per draw below main at both record counts. **Passed; work continued.**

**Not modeled here,** and the reason the PC pair is still needed:
- draw keys that never repeat, for example pointers from a linear frame allocator rather than a ring;
- registers at the patched locations that the game rewrites per draw. The prototype keeps them in the key. PR 6539's forwarded words would drop them from the relocation alias (see the overlap section).

## The prototype (rule, branch head)

Fork branch `exp/cpu-indirect-draw-cache`, on upstream main `17cfb1f4c`. All author and committer `Yunus Shaikh <75296019+EagleBearerYS@users.noreply.github.com>`, unsigned, no trailers.
- `ab61c06c0` perf(agc): keep CPU-path indirect draws in the draw cache behind APS5_CACHE_CPU_INDIRECT
- `f11c82793` test(agc): a repeated CPU-path indirect draw hits the draw cache and each record draws its own patched words
- `08e07cd41`, `72e1fa51c`, `5d7b16be1`, `c08f1cae8`: BF-042's harness (exp/bf042-base, the same 4 commits, picked unchanged)
- `fdb45156c` test(agc): a draw-record harness mode for CPU-path indirect draws

The first two commits are the change. The last five are the harness and can be dropped for a PR. The harness adds the public `Driver::DrawCacheSize()` it reads.

**Rule** (`Draw.cpp`, only with the switch on, and not for tessellation, mesh or rect-list draws):
1. **Insert.** The packet's stages, as compiled before the record loop from the queue's registers, go into the draw cache like a direct draw's: same key, same second-sighting admission. `cacheDrawStages` gets `std::nullopt` for `indirectCpu`; the exclusion line is otherwise unchanged.
2. **Per record, per patched stage:**
   - **(a) pushed-only.** No patched word is a walk input (`SrtUserDataUse::asBase | asValue` of the stage's capture, or of the cached variant on a hit, kept as `DispatchVariant::walkedWords`), and none is a vertex-fetch table word. The record's values are written into the shader-data slots that forward those words (`patchPushedUserWord`: `pushConstants` slot k, or the ShaderData binding, where `shaderDataUserWords[k]` is the word). Nothing is captured or materialized.
   - **(b) walked, same values.** A patched word reaches the walk, and the record's values equal the ones the stage was compiled with. The compiled stage is used as is: keyed on its patched values, the one value the entry holds.
   - **(c) otherwise,** capture and materialize again, exactly as main does.
3. **Counters.** `DrawEntryCounters::cpuIndirectPatched / cpuIndirectReused / cpuIndirectCaptured` count (a), (b) and (c) per record stage, and `APS5_PROFILE_DRAW` prints them.

In the harness every patched record stage took (a). A longer profiled run (`--cost 1500`, 4 records) printed `[draw-cache] CPU-path indirect stages (10 s): 216768 record stages patched in their pushed words, 0 kept at the values they were compiled with, 0 captured again`. The harness's own counter deltas are only valid for runs under 10 s with profiling, because that report resets the counters; every gate run was 60 frames.

**Not done.** The prototype keeps no per-record variants for other values of a walked word. That is what BF-015 did, and in Village it reused 5.6%.

The draw cache admits a key on its second sighting (see `ThirdDrawHitsTheCache` in `DrawCacheReuse.cpp`), so "drawn twice, hit the second time" becomes "the second draw inserts, the third hits".

- **On upstream main `17cfb1f4c` + the test commit:** red (exit 1). "three CPU-path indirect draws of the same records and registers inserted 0 draw entries and made 0 draw-cache hits (0 by the third), expected the second to insert and the third to hit"

## Does it need PR 6539?

**No.** Main already has every input the pushed-only test needs:
- `RecompileResult::shaderDataUserWords` and `SrtUserDataUse` (`asBase`/`asValue`);
- the shader-data slot layout that `applyShaderDataPatches` already patches.

That is why the prototype is built on main.

**On PR 6539's head, one more hunk is needed.** PR 6539 binds relocation-patched push constants through a per-stage override (`CompiledShader::pushConstants`, from `DispatchVariant::patchedPushConstants`, its 18acdbf4a/a49eaae18). The CPU path's per-packet copy must take those bytes and clear the override, or a hit would draw the override instead of the patched record words. That port is `21c71fd0a`, on a local detached tree only and not pushed. It is the branch's `ab61c06c0`, with that 6-line hunk in the CPU-path copy loop plus the conflict resolutions (`cloneVariant` copies `walkedWords`).

## Overlap: PR 6539, PR 5609, issue 5806

**Upstream PR 6539** (Scott Schuster / TheAggie, "relocate cached draws across user words that only reach the shader as values", head `12a5f02d1`, stacked on PR 5609):
- **What it does.** It learns `forwardedWords` (user words in `shaderDataUserWords` and in neither `asBase` nor `asValue`) beside a shader set's pointer words. It leaves them out of the relocation alias, accepts them on a relocation, and patches them into the pushed data.
- **Same test, different moment.**
  - 6539 uses the pushed-only test when a queue register changes between draws, at key and alias time.
  - This change uses it when a record overwrites a word inside one CPU-path packet, per record, after the lookup.
- **Alone, it doesn't help these draws.** 6539 keeps the CPU-path exclusion, and its new data-path fallback also requires `!drawParameters.indirect`. On its own it gives these draws 0% reuse (table).
- **Stacked, they compose.** With this change, 6539 measures the same as main + change (61.2 / 138.6 µs against 58.2 / 145.7). The port needs the 6-line push-override hunk above.
- **Not measured.** A game that rewrites the patched registers itself per draw would, on 6539, have those forwarded words dropped from the alias. The harness keeps those registers constant.

**Upstream PR 5609** (TheAggie, head `09238da82`, 8 commits beyond main):
- **Its base** is `f9cacfadc` "find cached draws across moved user-data pointers", which reached main through upstream PR 4943.
- **What it adds:** per-stage relocation keyed by the prepared shader, and reuse of a stage whose buffer base addresses moved (`23ba4f743`, `a49eaae18`, …).
- **Why it doesn't show in the harness.** The harness's pointers move through a ring of 3, so keys repeat and the hits don't depend on relocation. With pointers that never repeat, relocation (main's `f9cacfadc`, then 5609 and 6539) is what this change would rely on to find an entry at all. That is the PC pair's question.
- **Shared code.** This change doesn't touch relocation. The only shared code is the variant copy: `walkedWords` is copied in `relocateDrawEntry` on main and in `cloneVariant` on 5609/6539.

**Upstream issue 5806** (open; Demon's Souls PPSA01342, with the same pattern reported for PPSA01341 and Village):
- **What it explains.** Why these draws take the CPU path: the packet patches the start instance into s10, and the embedded-fetch analyzer finds no instance offset (`i=-1`), so `ClassifyIndirectDraw` returns NotFolded.
- **The discussion.** It proposes reading the patched SGPR as `gl_BaseInstance` so the draws stay on the GPU. A maintainer answered that the CPU fallback is deliberate until a shader capture shows how s10 is used.
- **How this change relates.**
  - It leaves that classification and that decision alone.
  - It makes the CPU path itself cheap when s10 is a pushed value, which is what NotFolded with `i=-1` suggests.
  - If the issue's GPU-side route lands, fewer draws reach this path. Both can coexist.
- **Source.** The summary was read from the public issue page, and nothing was posted.

## Kill hint: patched words that reach the walk

**Harness.** No patched word reached the walk, so 100% of record stages were patched (a) and none were reused at compiled values (b) or captured again (c): 216,768 / 0 / 0 in the 10 s profile report.

**Village's own shaders decide the split; no game data was used here.** If its patched words mostly reached the walk, only case (b) would be left:
- **What (b) covers.** Records whose patched values equal the register values the stage was compiled with. A start instance of 0 over a register of 0 is the likely common one.
- **What is left.** The share of reuse left is the share of records with those values. Every other record recompiles exactly as on main, so the gain would collapse to roughly BF-015's 5.6%.
- **Telling the cases apart.** In a PC run, `APS5_PROFILE_DRAW=1` prints `[draw-cache] CPU-path indirect stages (10 s): N record stages patched in their pushed words, M kept at the values they were compiled with, K captured again`. N / (N+M+K) is the pushed-only share, read directly.
- **The fit with issue 5806.** Its traces show the start instance in s10 and no instance offset found by the analyzer, which is consistent with a word the shader reads as a value. That points to (a), but only a run shows it.

## Limits

- The draw key still hashes the queue's registers at the patched locations. The CPU path patches only its local program copy, never the queue registers, so those values stay whatever the game wrote, and in the harness they are constant.
- On a hit, a stage in case (c) appends the matched stages' regions to the draw's memory list again for every record (`materializeDrawStage`), as main does for misses.
- **Before a PR** (none was opened), the walked-word case (c) needs an entry in `docs/dev/debt/libSceAgcDriver.md`, and the speed claim needs `tools/trace_digest.py` summaries from a real scene (AGENTS.md).
- **Not run here:** Windows, a real GPU, game data. All numbers are lavapipe.
- **Co-author trailer:** none was asked for, and none was added. The PR 6539 credit is in the prototype commit's body.
