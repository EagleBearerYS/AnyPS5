### The shape (both variants)

1. Table, Keys, Output and sampler come from the SRT.
2. A waterfall loop over a per-lane key: `v_readfirstlane` and `s_and_saveexec`.
3. The record's dwords 2/3 are read with `s_buffer_load_dwordx2 s[44:45], s[4:7], (key << 4) + 8`.
4. `s_cmp_eq_u32 s18, 0` / `s_cbranch_scc1` / `s_mov_b32 s44, 0xea` merges the low word with the constant 0xea by a Phi. The high word is the record's dword 3 directly.

6. Two `s_buffer_load_dwordx8` through that V#: T#1 at 0x0 and T#2 at 0x4c0. Each is sampled with `image_sample_lz`.

## Fix 1: the shared V#

`ResourceTracker.cpp:743-749` is the nested branch of `TryMakeTableColumn` (#9457's `:735-739`).

- **Old rule:** every user of a parent V# word read had to be a `GetBufferResource` whose uses are all this T#'s reads.
- **New rule:** it may instead be a handle with the same words as this T#'s V# handle (`SameHandle`, `EquivalentValue` per argument) whose uses pass `DescriptorWordReads` (`:616`). That means every use is a `ReadConstBuffer` with at least one user, and all its users are `GetImageResource` or `GetSamplerResource`.
- **Still refused:**
  - A handle with any other use (a data read, a V# read through it, a word going elsewhere).
  - A handle built from other words.
- **A sibling descriptor that can't be planned** still makes the shader fail as before, because its words come through a V# that isn't a runtime source ("not a valid runtime value").

### How the parent is shared

- Each descriptor plans its child from its own handle (`%183` for T#1, `%192` for T#2).
- Both walks reach the same `LoadAddressU32` reads and record pointer. So the parent column interns to one source (`InternSource`, `:260`, compares the `TableColumn` and the `EquivalentValue` of each word).
- The materializer reads that parent's records once: `NestedColumn` takes them from the cached `Column(column.heapSource)`. Each child column keeps its own offset (0 and 0x4c0) and its own child map.
- Each handle still gets its own plan, because `Run()` rewrites each planned handle's arguments (`:154-160`).
- The parent's word reads become planning-only only once both handles are planned (`:1770-1781`).

### Limits

- The rule also accepts S# siblings ("T# or S#"), but only the T#+T# shape is tested.
- One handle shared by both T#s (if some pass merged them) still refuses at `:731`, unchanged (#9457's `:723`), which requires the V# handle's uses to be this T#'s reads. The front end makes one handle per `s_buffer_load`, as both this IR and Spider-Man 2's show.

## Fix 2: T# words with other uses

The check at `:739` (#9457's `:731`) stays.

**Why it exists:** it was added by d132754dbe, whose message says: "A T# read from a nested child table stayed a runtime read when one of its words also fed another instruction. That read goes through a V# that exists only in the snapshot, so the dispatch read a garbage address; lavapipe crashed in the shader."

**The lines that decide it:**
1. **The reads stay in the program.** `PlanTableColumnPass` marks a planned read planning-only only when every one of its users is a planned handle (`ResourceTracker.cpp:1770-1781`, `FindTableColumn(*user) != nullptr`). A T# word that also feeds a Phi keeps a real `ReadConstBuffer`.
2. **But it reads through the V# handle, and planning rewrites that handle.** `Run()` replaces every planned handle's arguments with the column offset, and for nested plans arguments 1/2 with the parent pointer's words (`:154-160`). The parent plan's handle is `%192`, so the kept read's buffer becomes (offset, pointer low, pointer high, offset).
3. **The V#'s own word loads are dropped.** The parent's `LoadAddressU32` reads become planning-only once both handles over them are planned (`:1770-1781`, then `:169-171`), and `LoadAddress` emits nothing for a planning-only read (`SpirvMemoryInstructions.cpp:599-601`).
4. So the kept T# read would address a V# that only the snapshot holds.

**Experiment** (temporary, not committed): at fix 1, I dropped the `:739` check and accepted sibling handles whatever their reads feed. `--pointer-vsharp-shared-reuse` then compiled and dispatched, and the process died with SIGSEGV (`Segmentation fault`, exit 139) on lavapipe, with no output. That is the same crash d132754dbe describes. The sources were restored, and the committed tree was checked.

**What taking it would need:** keep that V# alive for the extra users. That means an unrewritten copy of the `GetBufferResource` for the kept reads, plus real loads of its four words through the record pointer, which are then no longer planning-only. In turn, the record-pointer reads must stay real and their hop reads must not be marked planning-only. The extra users would then read the guest's real T# words, while the descriptor handles take the snapshot.
