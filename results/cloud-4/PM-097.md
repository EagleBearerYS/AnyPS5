## What scales now

The rule is still generic: one rule, no title special cases.

**A depth surface renders scaled when all of these hold:**
- the switch is set and a video-out buffer is registered;
- its extent is at least the video-out extent in both dimensions;
- it is single-sample and single-slice (`firstSlice == lastSlice == 0`);
- its host format supports `BLIT_SRC|BLIT_DST` (on lavapipe this held for D32_SFLOAT and D32_SFLOAT_S8_UINT; both are tested);
- it was never demoted. The registry is the step-1 one, keyed by address and extent, so demotion is permanent.

**A draw renders scaled when:**
- every colour target passes step 1's rule (resident, 2D, single mip and layer, no proxy, at least the video-out extent, never demoted), and
- its depth surface, if any, passes the depth rule above, and
- `samples == 1` and no target dump is active, and
- every pixel shader that reads `FragCoord` carries the new position-scale constant. All shaders compiled by this branch do; this check only refuses modules built some other way, with `FragmentPosition`.

**Depth-only draws** (no colour target) scale on the depth rule alone. Without this, a depth prepass would demote the depth surface before the scene pass.

Otherwise every scaled or scalable target of the draw demotes, with the reason (`MixedAttachment` for an unscalable colour target or MSAA, `DepthAttachment` for a depth surface that cannot scale, `FragmentPosition` as above).

### How depth scaling works (`Graphics/src/DepthSurface.cpp`)

- `DepthSurface::RenderScalable` / `RenderScaleTo` / `DemoteRenderScale` (:556-576) mirror `StorageTexture`'s.
- `swapImage` (:1095): creates the image from the saved create info at the new extent, blits depth (and stencil) with `VK_FILTER_NEAREST` (the only filter Vulkan allows for depth/stencil), retires the old image and its two views until the surface is released (recorded draws may still reference them), and clears the sampled-texture map so the next read builds views of the new image. The stage-A fast path already rechecks `DepthSurfaceHolds`, so stale views are never reused.
- `DepthSurfaceView` (:2109) takes the scaled extent from the draw. It scales the surface after `takePlanes`, `TakeStorage` and `SyncFromMemory` (which may demote it) and before the fast clear. A draw that is not scaled demotes a scaled surface (`MixedAttachment`).
- Draw.cpp: `renderScaledState` (:2241) decides for colour and depth together. `prepareDraw` passes the scaled depth extent (:2423) and demotes the colour targets if the depth surface ended up native (:2426). After resource resolution, if any colour target or the depth surface was demoted while the draw's resources resolved, all of them demote, and the depth view in the attachment list is refreshed (:2439).
- **Sampled depth reads stay scaled.** Single-sample `Sampled()` views use normalized coordinates, so they read the scaled image as it is. That covers shadow-compare reads too. Integer-coordinate reads and size queries demote depth like colour (`ShaderResources.cpp:4679`, `TexelFetch` / `SizeQuery`).
- **MSAA depth never scales** (`samples == 1` in the rule), so the sample-shadow, sample-order and sample-location paths are unchanged.
- `takePlane` (:1654): a plane copied between two surfaces of the same depth address scales the receiving surface to the owner's scaled extent when it can. Otherwise both demote (`DepthCopy`). `CopyAspectFrom` now copies the image extent and refuses mismatched sizes.

### FragCoord rescaling (recompiler)

- `InstructionTranslator.cpp:408-418, 443-444`: the guest-visible position VGPRs (`PositionX`, `PositionY`, and both halves of `PositionFixedPoint`) are multiplied by `bitcast<float>(FragCoordScale)`. That is a new builtin kind (`StageIO.hpp`), lowered in `SpirvModuleEmitter.cpp:178` to a `uint32` specialization constant, SpecId 8244, default `0x3f800000` (1.0).
- Internal uses of `FragCoord` (quad parity for sample order and dithered alpha-to-coverage) keep host coordinates, which is right at either size.
- The constant is **kept as a real Vulkan specialization constant** through prepared specialization, like the compute workgroup offsets (`PipelineSpecialization::SuppliedAtPipeline`, `Recompiler.cpp:769`). `RecompileResult::specialization` lists it with value 1.0 (`Recompiler.cpp:1144`). So one compiled shader serves scaled and unscaled draws.
- Scaled draws set `State::fragCoordScale = D/N` (2.0 at 0.5). `Pipeline` replaces the value for the fragment stage (`Pipeline.cpp:390`).
- The value is part of the pipeline key (`Pipeline.cpp:905`) **and of the fragment-shader library key** (`Pipeline.cpp:261`). Without the second one, a graphics-pipeline-library device reused a fragment library built for the other scale. The test's "unscaled draw with the scaled pass's shader" case caught this: before the fix it read `(0.00026041668, 0.000462962955)` at pixel (0, 0) instead of `(0.00013020834, 0.000231481477)`.
- Exactness: at 0.5 the scaled position is `(i + 0.5) * 2`, exact in float. `x * fl(1/3840)` equals `(x/2) * fl(1/1920)` exactly, because the factors differ by powers of two. That is why the scaled pass is bit-identical, not just close. Other scales (0.75) are correctly rounded but not guaranteed bit-equal to native.
- **Unscaled draws: identical results, not identical SPIR-V.** Pixel shaders that read their position gain one `OpSpecConstant`, one `OpBitcast` and one `OpFMul` per component, whether or not the switch is set. With the value 1.0, `x * 1.0 == x` for every finite `x`, and positions are never NaN or infinite. All other shaders' SPIR-V is unchanged.
- **Shader disk cache:** `FormatVersion` is unchanged (45). No serialized field changed: the new constant travels in the existing `specialization` list. Old cache entries are dropped anyway, because `SourceVersion` is the source hash.
- **Two existing tests changed their assertion, not their coverage:** `StencilReplay.cpp` and `StencilNullFeedback.cpp` required that no `OpSpecConstant` remain in a stencil-replay pixel module. Their message says the point is that "expected reference remains a pipeline specialization". The check now exempts exactly SpecId 8244 and still fails on any other remaining specialization constant. Stencil-replay draws scale like any other draw (each of the 256 replay pipelines gets the value).

## Demotion reasons

Step 1's reasons are unchanged; `DepthAttachment` now means "drawn with a depth attachment that does not scale". New:

| Reason | Text in the log | Detection points (DepthSurface.cpp) | Test (scale 0.5, 256x128 colour + depth) |
|---|---|---|---|
| `DepthGuestWrite` | guest memory written to a depth plane | `SyncFromMemory` (:931) when guest writes changed units; `StoreBackCovering` (:772), a storage image covering the plane stored back; `TakeStorage` (:786) | `--depth-guest-write`: a 16-byte `GuestMemory::Write` into the plane, then a draw |
| `DepthWriteBack` | depth plane stored to guest memory | `StoreDepthPlane` (:825): every `FlushDepthPlanes` store and `retireStoringStale` | `--depth-write-back`: `FlushDepthPlanes` over the plane (what a CPU read does) |
| `DepthStorage` | depth plane accessed as a storage image | `Storage` (:677), `StoreBack` (:752), `layeredSlices` (:2709, layered storage views) | `--depth-storage`: `DepthSurfaceStorage` with an R32_FLOAT view |
| `DepthCopy` | depth plane copied at native size | `CopySample` (DB depth copy), `takePlane` when the two surfaces cannot share a size, `DepthSurfaceTexture` slices for layered and integer views (DepthPlaneCopy) | `--depth-copy`: a two-layer R32_FLOAT array view of the plane |
| `StencilCopy` | stencil plane copied for sampling | `unormStencil` (:1171): R8_UNORM stencil reads go through a copy | `--stencil-copy`: D32_S8 surface, R8_UNORM view of the stencil plane |

Every case checks:
- the depth surface goes back to its native extent and the reason fires exactly once;
- the next colour-plus-depth draw demotes its colour target (`DepthAttachment` ×1), and nothing else fires;
- the demoted colour image holds the first draw's colour outside the second triangle and the second draw's colour inside it.

The `--depth` case does the same with a 4K surface. After `FlushDepthPlanes` the native depth image holds 0.5 at (100, 100) and less than 0.5 at (2176, 1080), the nearest upscale of the scaled image.

## Known gaps of 2a

- **Idle and flush-time stores demote.** `StoreIdleResults` (queue idle with pending results) runs `FlushAllPending`, which stores every stale depth plane (`DepthWriteBack`) and every pending colour target (`WriteBack`, as in step 1). In a running title this may become the most common reason; the user's counts will show it. CPU readbacks without demotion (a temporary native upscale for the store) would fix both.
- **No VRAM saving yet.** As in step 1, the native image stays retired until the surface is released.
- **Depth demotion is a nearest upscale.** A surface demoted mid-frame keeps blocky depth for that frame.
- **Slope-scaled depth bias** is not compensated. Slopes per pixel double at 0.5, so slope bias doubles relative to native. Constant bias is unaffected. LOD bias for sampled scaled surfaces is not compensated either (step 1 gap).
- **Large depth-only targets scale too.** Any single-sample depth surface at least the video-out size scales, including a 4096x4096 shadow map. Normalized shadow sampling stays correct at lower resolution; integer-coordinate PCF demotes it.
- **Untested here:** `TexelFetch`/`SizeQuery` demotion of a depth surface (the hook is the same loop as colour, `ShaderResources.cpp:4679`); `DepthCopy` from `CopySample` and from `takePlane`; D16 depth; scales other than 0.5 (0.75 is exercised by step 1's parse test only).
- **Demotions after the post-resolve check** (during recording) are still not handled, as in step 1.

## What step 2b (integer coordinates, compute) would need

1. **Integer coordinates rescaled instead of demoted.**
   - Per binding, from the existing `imageFetched` / `imageQueried` / `imageUnnormalized` flags: multiply `image_load` coordinates and unnormalized sampler coordinates by `N/D`, and `resinfo` results likewise.
   - Use one specialization constant per binding, or reuse the position-scale constant when the binding's surface is the scaled extent. The pattern that SpecId 8244 now proves out (kept through prepared specialization, replaced at pipeline creation, in both pipeline keys) carries over.
   - The hard part is knowing at pipeline creation which bindings view scaled surfaces. That is a per-draw property, so the key must include a per-binding scaled mask.
2. **Compute.**
   - A dispatch whose grid covers a scaled surface needs its grid scaled (the `WorkgroupOffset` constants show the dispatch-time specialization path), plus its image coordinates (item 1) and `SV_DispatchThreadID`-derived UVs.
   - Without that, `ComputeWrite` keeps demoting. RE Village's post chain is compute.
3. **CPU readbacks without demotion** (gap above): a native-size upscale into the store path, so screenshots, idle stores and `FlushDepthPlanes` keep surfaces scaled.
4. **Measurement first:** the user's three-title counts on this head will tell whether `TexelFetch`, `ComputeWrite` or `WriteBack`/`DepthWriteBack` dominates now that depth and position no longer demote.
