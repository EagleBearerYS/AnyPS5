## The timers added

All timers use `QueryPerformanceCounter`. They stay off, costing one relaxed atomic load per site, until the bench turns them on through its own switch. The bench reads and resets them around each timed retiring refresh only, so the probe collects and the setup refreshes stay out of the numbers.

**`rewatchRetired`** (`Graphics/src/GuestBufferMemory.cpp`):
- the `imports` walk;
- `StorageTexture::AnyLiveOverlaps`;
- the number of spans kept unwatched.

**`GuestMemory::Rewatch`** (`Execution/src/GuestMemory.cpp`):
- calls and total time;
- the tracker lock wait;
- per span: `coverage.Covers`, `walkWrites`, `coverage.Restore`, `noteCpuStore`, and the `driverPieces.erase` + `stamp` loop;
- spans in and spans restored;
- a record per span: begin, end, ticks, restored.

The control flow is unchanged, with the same short-circuit order of Covers, walkWrites and Restore. The API is `SetRewatchPhases`, `RewatchPhaseNow`, `AddRewatchPhase(Since)` and `ReadRewatchPhases` in `GuestMemory.hpp`.

**`WindowsMappings::Collect`** (`libc/include/WindowsMappings.hpp`), one call per span:
- calls and total time, and the `mutex` wait;
- `collectable()` calls and time when not memoized;
- **every `VirtualQuery` inside `Collect`**, in `collectable()` and in the private-memory walk: count, time, and how far each returned region runs from the queried address (`BaseAddress + RegionSize − address`). A thread-local flag keeps queries outside `Collect` (`Commit`, `split`, …) out of these counts;
- `armResident`'s `VirtualProtect`: count and time;
- `GetWriteWatch` in the private branch and both `collectResident` calls: count and time;
- `rememberClean`: count and time;
- the rest of `Collect`: total minus the timed parts (the clean-range walk, `viewAt`, bookkeeping).

libc exports them as `GuestArenaSetCollectPhases_nid_no_patch(bool)` and `GuestArenaCollectPhases_nid_no_patch(values, count, reset)`. They are declared under `_WIN32` in `GuestArena.hpp`, and libc has no export list, so MinGW auto-exports them like the other helpers.

**The bench's new lines,** after its existing block:
- **Per phase:** each phase's total µs, µs per span, and calls per span. The `VirtualQuery` line gives the average MiB from the queried address to the end of its region.
- **Rewatch per span over time:** the first 500 and the last 500 spans, each with count, median, mean and max.
- **Rewatch per span by distance to the end of the committed block:** buckets of 64 MiB, each with count and median.
- **Rewatch per span by size:** 64 KiB against 4 MiB, each with total, median, p99 and max.

## The code reading: what grows with the arena or the mappings, not with the span

**Per-span bookkeeping is all cheap.** None of it scans state that grows with the number of registrations or views:
- `rewatchRetired`: `imports.upper_bound` plus a forward walk over the imports that overlap the span. `AnyLiveOverlaps` sees no live textures on the mock.
- `Rewatch`: `coverage.Covers` and `Restore` touch the span's 64 KiB blocks in a vector (`WriteWatchCoverage`). `noteCpuStore` and the stamps touch the span's blocks and pages, and `leafFor` allocates a leaf only on the first touch of 4 GiB.
- `Collect`: `cleanRanges`, `collectableRanges`, `freshRanges`, `views` and `residentRuns` are `std::map`s searched by address (`upper_bound`, `lower_bound`, `viewAt`). `remember`/`forget` merge only the entries next to the range.
- So I expect no rising trend between the first and last 500 spans. The pieces are also shuffled, so position in the run doesn't track address.

**What is not cheap is three Windows calls per span on the bench's memory:**
- The bench's pieces are **private** memory: `GuestArenaAllocate` plus `GuestArenaCommit`, not views. So `Collect` takes the private branch.
- A new span misses the `collectableRanges` memo, which remembers only the span itself, so `collectable()` calls `query()` (`VirtualQuery`).
- The walk calls `query()` again to find where the region ends, then `GetWriteWatch(WRITE_WATCH_FLAG_RESET)` over the span.
- `armResident`'s `VirtualProtect` applies only to resident views (direct memory) in runs of 256 KiB or more, so never to the bench's memory.

**The suspect is `VirtualQuery` scanning to the end of one ~450 MiB private region, twice per span.**
- **The block:** the bench commits `bigSlots × 16 MiB + pieceSlots × 256 KiB + 32 MiB` = 64 + 353 + 32 = **449 MiB** with `granule = bytes`. `WindowsMappings::Commit` turns that into **one** `MEM_REPLACE_PLACEHOLDER` allocation with uniform protection.
- **The scan:** `VirtualQuery` returns `RegionSize`, the run of pages from the queried address with identical attributes. To find it, the kernel walks those pages, and here the run reaches the end of the allocation.
  - From a 64 KiB piece, that is 32 to ~385 MiB, depending on its slot.
  - From a 4 MiB piece, which lives in the first 64 MiB, it is ~385–449 MiB.
- **How it fits BF-104's numbers:**
  - The cost per span is about fixed, ~440 µs, whatever the span's size.
  - A refresh with a 4 MiB piece costs ~1,450 µs: its piece sits at the start of the block, where the scan runs farthest, and adds a 1,024-page `GetWriteWatch`.
  - The 1,412-piece refresh costs ~530 µs per piece.
  - The 32 MiB probe collect after a bump costs 152 µs: the probe is the last 32 MiB of the block, so its query runs only 32 MiB, plus a `GetWriteWatch` over 8,192 pages.
- **What the PC run should show** if this holds:
  - the `VirtualQuery` line with the bulk of `Collect`'s time, at about 2 queries per span;
  - a large average MiB per query;
  - Rewatch per span **falling** with the distance-to-end bucket;
  - the paged run's per-span cost far lower. With 16 KiB replacements, each query stops within 16 KiB, at the cost of 4 queries and 4 `GetWriteWatch` calls per 64 KiB span.
- **If it doesn't hold,** the next suspect is the fixed cost of `GetWriteWatch(WRITE_WATCH_FLAG_RESET)` itself: clearing the dirty bits needs a TLB flush on every processor the process runs on, which is slow on a VM runner. The paged run would then not get cheaper per span, and the `GetWriteWatch` line would carry the time.

**What this means for the title.** If the suspect holds, the 440 µs is mostly the bench's layout, not what Village pays per span:
- **Flexible memory:** libkernel commits it in 16 KiB granules, so its regions are at most 16 KiB long.
- **Direct memory:** it is mapped as resident views (`MapDirect`), and `Collect` never calls `VirtualQuery` for views. `collectable()` checks the views first.
- **The exceptions:** single large private commits are the guest heap (`GuestHeap.cpp`, chunks with `granule = bytes`) and the driver's own memory (`Lifecycle.cpp`, `DriverMemoryBytes` in one commit). A retired import inside a large heap chunk would pay the same scan.

## The fix: not made yet

I made no product fix, for three reasons:
1. Everything rests on `VirtualQuery`'s scan cost, which only the Windows numbers can confirm.
2. By this reading the cost is mostly the bench's single-replacement layout, which neither of the title's main memory paths shares. The paged run answers that directly.
3. The code involved, libc's Windows `Collect` path, has no tests that run here.

**If the PC run confirms it, the fix is small and stays in main's code** (`WindowsMappings`, not #8926's), so it can stand as a main PR on upstream main:
- Remember the extent of each private region `query()` measured inside `Collect`, in a `Ranges` map next to `collectableRanges`, cleared at the same points (`Commit`, `Map`, unmap, `Reset`).
- Then `collectable()` and the walk skip the `VirtualQuery` of a region they have already measured.
- A smaller variant passes `collectable()`'s query on to the walk, which halves the queries per span.

**Its tests** would be the ones the task names (`agc_heap_mirror_*unwatch*`, `agc_driver_graphics`, the libc `GuestArena`/`WindowsMappings` tests), plus a `WindowsWriteWatch` case:
- a collect across a region that a `Commit`, a `Map` and a `SetProtection` change in between must still see every write;
- it must refuse uncommitted memory.

If the paged run shows the bench overstated the title's cost, the right follow-up is to make the bench commit as the title does: the paged mode as the default.
