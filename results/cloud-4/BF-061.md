## Step 1: the counters

**Switch.** Everything is gated on `APS5_PROFILE_HEAP=1`, read once. Without it:
- nothing is counted;
- no wrapper is installed;
- no estimate is computed.

**How counting works** (`core/shader/recompiler/HeapHolders.hpp/.cpp`):
- Each holder keeps a live object count and estimated bytes in relaxed `std::atomic<int64_t>`s.
- Bytes are estimated where the object is created (sizeof plus the capacities of its vectors) and given back when it is destroyed:
  - `Track(shared_ptr, charges)` wraps an object at its creation site in a `shared_ptr` whose deleter gives the charges back;
  - `Held` is a member that gives back what it was charged;
  - the driver's caches add to their existing variant accounting.
- **Per draw:** a draw does nothing unless it creates an object: a draw-cache insert, a memo miss, or a module specialized for a new state. The one exception: a draw-cache hit that reorders an entry's variants copies one integer into the reordered entry.

**What each holder counts:**

| holder | objects (count) | bytes | created at |
|---|---|---|---|
| plans | `IrResourcePlan` | sizeof + value arena + each value's operand lists + blocks + every plan vector + `ShaderInfo` | `ResourceProgram` (built), `getSource` (disk `LoadPlan`) |
| modules | `SharedSpirv` holders that own words (not mapped) | word capacity × 4 | `SharedSpirv::Holder` |
| variant metadata | `CompiledVariant` | `ShaderInfo` with runtime image modes, both binding layouts | `findOrCompileVariant` |
| results | `RecompileResult` (registration, memo, materialization) | sizeof + artifact vectors + bindings and their vectors + push constants, attributes, image tables; plus, in bytes only, the binding plans `materializeResult` caches (`PreparedBindingPlan`, `PreparedModuleEntry`) | `materializePreparedMemoized`, `RegistrationResult`, `MaterializeShader`, `PreparedShaderInvocation::Materialize`, `RecompileImpl` |
| sources | `SourceEntry` | sizeof + code + call fallbacks + key; plus, in bytes only, each variant's sizeof and artifact vectors and each `SourceHandle`'s static key | `getSource`, `findOrCompileVariant`, `PrepareShader` |
| registry | `ShaderSnapshot` (registered, null pixel, raw-program cache) | sizeof + code + header + `PreparedShaders` + registered state's three register files (new `Registers::HeapBytes`) + the ABI key preparation moves in | `RegisterShader`, `ReadRawShader` |
| draw cache | entries in `drawCache` | sizeof + stage vectors + its `DrawDecode` (state colors and blends, programs and their user data, roles); plus the variants' bytes as `accountDrawVariant` counts them | `insertDrawEntry`, eviction, `eraseDrawEntry`, `~Driver` |
| dispatch cache | entries in `dispatchCache` | sizeof + the variants' bytes as `accountVariant` counts them | `insertDispatch`, eviction, the non-LRU clear, `~Driver` |

**Cache key.** `APS5_PROFILE_HEAP` is in the shader disk cache's `NeutralSwitches`. Its names were added to the recompiler's reviewed-names list.

## Step 2: estimates against heaptrack

**Run:** `agc_driver_shader_heap_holders_tests --measure 1000 0 10 2`, the step 3 harness file in its measure mode (BF-054's `ShaderResidency.cpp` adapted).
- **Programs:** 1,000 synthetic pixel programs of 188 code words, about 48k SPIR-V words per variant.
- **Mode:** eager, the default.
- **Drawn:** 100 programs (10 %), **each drawn twice**. BF-054's harness drew each once; a single draw leaves the draw cache at its one base entry, because a key is admitted at its second sighting.
- **Cache:** warm disk cache, written by one earlier run of the same binary.
- **Conditions:** `APS5_PROFILE_HEAP=1 APS5_NO_PIPELINE_JOURNAL=1 GALLIUM_OVERRIDE_CPU_CAPS=avx`, user `runner`, lavapipe.
- **Binary:** f46a3dc6a, the commit before the step 4 fix. Its counting code is identical to 8ccb8aef7; the fix adds one line to `NeutralSwitches`, a test mode and a doc sentence.

**How heaptrack was read:**
- **Cost type:** heaptrack 1.5.0, `heaptrack_print --disable-builtin-suppressions -F stacks --flamegraph-cost-type leaked`. The measure mode prints the counters after the draws and then calls `std::_Exit(0)`, so "leaked" is exactly the heap live at the moment the counters were read. This differs from BF-054, which used the cost at the heap's peak.
- **Sorting:** each stack goes to the first holder, in the order below, whose frames it passes through:
  1. modules: `ValidateAndOptimizeSpirv`, `buildSpecializedModule`, `SharedSpirv::`;
  2. plans: `ResourceMaterializer::ExtractPlan`, the disk cache's `decodePlan`;
  3. variant metadata: `decodeShaderInfo`, `decodeLayout`, `PrepareImageModes`, `RuntimeImageModes`;
  4. results: `materializeResult`;
  5. sources: `getSource`, `findOrCompileVariant`, `PrepareShader`, `DecodeEntry`, `Persist`, `ShaderDiskCache::Load`;
  6. draw cache: `insertDrawEntry`, `cacheDrawStages`, `decodeDraw` (after the draw-key admission filter `DrawKeySightings`, which is not an entry);
  7. dispatch cache: `insertDispatch`;
  8. `GuestMemory`, the device constructor and `Graphics::`, which are not shader holders;
  9. registry: `RegisterShader`, `PublishRegisteredShader`, `ReadRawShader`, `DecodeRegisteredState`, `InitialContextRegisters`, `BuildRegisteredAbiKey`.
- **Total live heap:** 839.6 MiB.

| holder | count | counter bytes | counter MiB | heaptrack bytes | heaptrack MiB | counter vs heaptrack |
|---|---|---|---|---|---|---|
| plans | 1,103 | 236,994,252 | 226.02 | 236,209,012 | 225.27 | +0.33 % |
| modules | 1,104 | 196,352,784 | 187.26 | 196,617,432 | 187.51 | −0.13 % |
| variant metadata | 2,104 | 58,591,090 | 55.88 | 58,591,090 | 55.88 | 0.00 % |
| results | 117 | 32,294,456 | 30.80 | 31,876,696 | 30.40 | +1.31 % |
| sources | 1,103 | 15,872,928 | 15.14 | 17,258,903 | 16.46 | −8.03 % |
| registry | 1,003 | 10,903,640 | 10.40 | 11,178,640 | 10.66 | −2.46 % |
| draw cache | 101 | 330,068 | 0.31 | 346,153 | 0.33 | −4.65 % |
| dispatch cache | 0 | 0 | 0 | 0 | 0 | — |

**Per registered program,** counter totals after the draws divided by 1,000: plans 231 KiB, modules 192 KiB, variant metadata 57 KiB, results 32 KiB, sources 15.5 KiB, registry 10.6 KiB. These are close to BF-054's §5 figures.

**The rest of the live heap** (heaptrack):
- 251.0 MiB `GuestMemory` (the 250 MiB page-state table);
- 28.8 MiB the Vulkan device constructor;
- 16.1 MiB `Graphics::` (pipeline libraries, detiler, resource cache);
- 16.8 MiB system libraries and the Vulkan driver;
- 0.3 MiB the draw admission filter;
- 0.15 MiB other driver.

**What each counter misses:**
- **plans:** nothing measurable. It counts 0.79 MB (0.3 %) more than heaptrack. I did not trace the difference; the instruction-list nodes, estimated at 24 B each, are the likeliest source.
- **modules:** the `SpecializedModule` objects around the words (their `bindings` vectors) and the module maps' entries and keys.
- **variant metadata:** nothing here. It equals heaptrack to the byte.
- **results:** nothing measurable on this harness. It counts 0.42 MB (1.3 %) over; I did not trace the difference. Result copies the driver makes on the draw path are not counted: `patchDataWords` per data hit, `applyShaderDataPatches` into a cached variant, the pipeline journal's copies. The harness makes none of them.
- **sources (−8 %):**
  - the source map's nodes and bucket vectors;
  - the growth of each source's `variants` vector and memo index;
  - the `make_shared` control blocks of sources, variants and handles;
  - `ResolveSource`'s handles (no key).
- **registry (−2.5 %):**
  - the registry map, which `PublishRegisteredShader` copies at each registration;
  - prepared state that grows after the snapshot exists: prepared entries, graphics ABI records, rectangles; only the ABI key moved in by background preparation is counted;
  - control blocks.
- **draw cache (−4.7 %):**
  - the decode's members other than state colors, blends, programs, user data and roles;
  - the variants' vectors that `variantBytes` leaves out (data positions, data slots, run bases, spans, shader-data patches);
  - map nodes.
- **dispatch cache:** the same `variantBytes` gaps. The harness has no dispatches, so neither column has any.

## Step 3: the ctest

**`agc_driver_shader_heap_holders`** is `tests/execution/ShaderHeapHolders.cpp`. It is registered by the execution-test glob, with `ANYPS5_NO_SHADER_CACHE=1` and skip code 77.
- **At start** it sets `APS5_PROFILE_HEAP=1` and `APS5_NO_PIPELINE_JOURNAL=1`, records the counters (all 0) and registers an `atexit` check. Then it does BF-054's base setup: a vertex and a pixel program, and 16 checked draws.
- **Registration:** it registers 8 synthetic pixel programs and settles preparation. Count checks:
  - registry, sources and plans: +8 each;
  - variant metadata: 8–16;
  - modules: 8–32;
  - results: 0–8;
  - draw and dispatch cache: 0.
- **Draws:** it draws 4 of them twice. Count checks:
  - registry: +0;
  - sources and plans: 0–4 (a state other than the registered one prepares at use);
  - variant metadata: 0–8;
  - modules: 0–16;
  - results: 4–8;
  - draw cache: exactly +4;
  - dispatch cache: 0.
- **Bytes:** wherever objects were added, the bytes are nonzero and under 16 MiB per object. The counted total must stay under the process's anonymous memory from `smaps_rollup`.
- **Teardown:** the `atexit` check runs after the driver singleton and the recompiler's static maps are destroyed. It was registered before they were constructed, so it runs after their destructors. Every counter's objects and bytes must equal the start.
  - This is the only teardown the product has: sources, plans, variants, modules and registry entries are never freed before exit (BF-054 step 1).
  - This run's line: "after teardown every counter is back to its start: … plans 0 (0.0 MiB) … dispatch cache 0 (0.0 MiB)".
- **What one run printed:**
  - registering 8 programs added: plans 8 (1,722,304 B), modules 26 (5,031,400 B), variant metadata 16 (422,464 B), results 0 (221,760 B of binding plans), sources 8 (118,720 B), registry 8 (87,040 B);
  - drawing 4 of them twice added: plans 4, modules 8, variant metadata 4, results 4, sources 4, registry 0, draw cache 4 (13,072 B).
- **Red:** with the sources decrement dropped in `Add`, the test fails with "after teardown sources holds 15 objects (76064 bytes), 0 (0 bytes) at start".

**`agc_shader_disk_cache`** gains `--load-plan-profile-heap`: a process with `APS5_PROFILE_HEAP=1` must load all stored plans and variants.
- **Red** without the `NeutralSwitches` line: "plan hits 0, plan misses 16, … variant misses 16".
- **Green** with it.

## Step 4: cost

**Setup:** `--measure 1000 0 10 2` on a warm cache, `APS5_NO_PIPELINE_JOURNAL=1 GALLIUM_OVERRIDE_CPU_CAPS=avx`, nothing else running. The times are:
- registration: all `RegisterShader` calls plus settling preparation and the library prebuilds;
- draw: 200 submissions (100 programs twice), each waited on.

**Builds compared:**
- **main:** 84b0d2f24 with the same harness file and a header shim in place of `HeapHolders.hpp`. It is a measurement tree, not pushed.
- **unset and set:** 8ccb8aef7 with `APS5_PROFILE_HEAP` unset or `=1`.
- **Order and cache:** the three alternated in each round. The branch cache was written by one cold run with the switch unset.

| | registration, runs 1 / 2 / 3 (mean) | draw phase, runs 1 / 2 / 3 (mean) |
|---|---|---|
| main | 63.94 / 63.09 / 64.45 s (63.83) | 11.97 / 11.83 / 11.93 s (11.91) |
| unset | 62.84 / 64.67 / 65.04 s (64.19) | 12.25 / 12.31 / 11.74 s (12.10) |
| set | 61.96 / 66.11 / 63.85 s (63.97) | 11.98 / 12.01 / 12.33 s (12.11) |

- **Registration:** the means differ by under 0.6 %. Each build's runs spread over 1.4–4.1 s.
- **Draw phase:** unset and set are 0.2 s (1.6 %) above main's mean, inside the unset runs' own 0.6 s spread. In the first series (f46a3dc6a), main's draw phase ran from 11.14 to 12.71 s.
- **Cache with the switch set:** the first "set" run (61.96 s) used the cache the unset run wrote.

**The bug this step found.** The first series ran on f46a3dc6a. Its first "unset" run took 239.7 s to register and 29.6 s to draw, a cold cache, though the "set" runs had warmed it. The disk cache key includes every `APS5_*` variable the recompiler reads unless it is listed as neutral, and `HeapHolders.cpp` reads `APS5_PROFILE_HEAP`.
- **Effect:** with that build, turning the switch on for a memory run would also have thrown away the warm shader cache.
- **Fix:** the line in `NeutralSwitches`, plus the disk cache test above. The fix is folded into the one commit, since the branch was not yet pushed.
- **Its other runs:** on f46a3dc6a they were 61.5–66.3 s registration and 10.96–12.71 s draw.

## Step 5: portability to base3a

**The cherry-pick:** `git cherry-pick 8ccb8aef7` onto 32ac24cb32 stops on one conflict, in `docs/dev/BUILD.md`. base3a does not have main's "GPU time per command class" section, and the new "Shader heap holders" section sits after it.
- **Code:** every code file merged without a conflict.

- **Check:** I compared the changed lines file by file with 8ccb8aef7. They are identical, except the one line the test change below removes.

**The test also needed changing.** The first full build of the variant failed on the new test alone:
```
ShaderHeapHolders.cpp:351:30: error: 'AwaitLibraryPrebuilds' is not a member of 'AgcDriver::DriverDetail'
```
- **Why:** main added `AwaitLibraryPrebuilds` in 81e3db853 ("fix(agc): drain library builds before device replacement"), which base3a does not have.
- **Change:** I amended the variant commit to drop that call from the test's `Settle`, leaving `EndShaderPreparation` and `WaitIdle`.
- **Stability without it:** the test passed 20 of 20 standalone runs on aaf03e9b1, with the same counts as on main (registration: plans, sources and registry 8 each, modules 26, variant metadata 16; draws: draw cache +4, results +4).

**`ctest -R '^(agc|shader)'`** (`--parallel 4 --timeout 120`, `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx`, as `runner`, full Release build with CI's configure):

**Main head, 8ccb8aef7:** full build (939 s), then `ctest`: **666 tests, 620 passed, 46 skipped, 0 failed**, in 71 s. Both `agc_driver_shader_heap_holders` and `agc_shader_disk_cache` ran and passed.

**base3a head, aaf03e9b1:** **644 tests, 600 passed, 43 skipped, 1 failed**, in 68 s. Both new checks passed.
- **The failure:** `agc_driver_preparation_scope_settle`, with "the link did not wait for the vertex shader's registration preparation".
- **Cause:** a race in that test. base3a's version queues blocking tasks on the preparation pool and does not wait until the workers are busy, so the vertex shader's preparation can run before them. Main fixed this today in 871232eed ("test(agc): wait for preparation workers before linking"), which is not in base3a and cherry-picks onto aaf03e9b1 without conflicts. I did not add it, since it is outside this task.
- **Failure counts, standalone runs** of that test's binary with the ctest environment:
  - aaf03e9b1: 1 failure in 30 runs, then 1 in 60;
  - its base 32ac24cb32 (built in the same tree): 0 in 60;
  - 8ccb8aef7 on main: 0 in 30.
  - `ctest --repeat until-fail:10` on aaf03e9b1 also failed once in one series and passed all 10 in a second.
- **Reading:** 2 failures in 90 runs against 0 in 60 is not enough to say the commit makes the race more likely; 60 clean runs at that rate would happen about one time in four. With the counters off, the commit changes no behaviour, only timing.
