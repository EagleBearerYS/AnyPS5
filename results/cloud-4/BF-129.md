## The trailer and what Version 3 means

A GPU-mode stage's heap table map (`writeHeapTableMap`) now ends with four words placed just before the element base:

| word | field |
|---|---|
| `map[HeaderElementBase] - 4` | bucket buffer address, low 32 bits (`TrailerBucketsLow`) |
| `map[HeaderElementBase] - 3` | bucket buffer address, high 32 bits (`TrailerBucketsHigh`) |
| `map[HeaderElementBase] - 2` | the open batch's miss-ring chunk address, low (`TrailerRingLow`) |
| `map[HeaderElementBase] - 1` | ring chunk address, high (`TrailerRingHigh`) |

- `ImageTableAbi::TrailerWords = 4` and `TrailerWord(base, field) = base - 4 + field`.
- `AppendTrailer` pushes the four words and sets `map[HeaderElementBase]` to the new size, so the element parts start right after the trailer. `ReadTrailer` returns nullopt when the base doesn't follow four trailer words.
- The words are **all zero when no device table is attached.** The shader treats a zero bucket address as "not attached": it misses and records nothing.
- **Version 3** means: "a heap map carries the 4-word trailer before HeaderElementBase." Every heap map carries it, zero or not, so slot parts and what a stage reads from them are unchanged.
- The trailer adds 16 B per stage map. For a table served only by device columns the map loses all its per-element slot parts.
- **Measured** (commit 3, `TrailerAddresses`): buckets 0x7f8d86aff000; ring chunks 0x7f8d866be000 and 0x7f8d86702010. The chunk stride is 0x44010 = `RingWords × 4`.

## Known gap (in `docs/dev/debt/libSceAgcDriver.md`)

A draw whose expected images the table can't take is still recorded with its device columns. That covers a T# from a lane or unreadable memory, more than 16 candidates, a full table, or a heap past its margin.
- A selected image that isn't resolved yet reads zeros in that batch. It is resolved from the miss ring for the next batch.
- Only later draws of the program take the CPU table map. Cached variants with device columns stop being reused (`DeviceImageFallback` in `validateVariant`).
- A dispatch is recorded again at once.
- #7642's per-draw re-recording (fa65ca3f9) was not ported.

## Open ABI questions for Raghav314

1. **Slot retention under his sweep.** A table entry holds its texture's `shared_ptr` (use count above `HeapHolds`), so his sweep never frees a slot the table points at.
   - The table also records each slot's `SlotGeneration`. When `SlotSerial` moves, it drops every key whose generation moved, before it uploads.
   - It takes no slot while `NearlyFull` (his margin `min(1024, cap/4)`) and reserves none.
   - The table can pin up to 16,384 entries' textures. Is pinning acceptable against his budget, or should the table release textures and rely on generations alone?
2. **His CPU map as the fallback.** Device columns write no map parts. A program the table can't serve (a miss-ring overflow in 3 batches in a row, a full table, no heap slot, an incomplete expectation) is recompiled with `deviceImageTables` off and gets his CPU map columns from its next recompile.
   - Is a recompile the right fallback?
   - Or should device columns also keep their map parts, so a single draw could fall back without one? That costs the map size the device path saves.
3. **Trailer size.** It is 4 words (two addresses), with no flags and no table generation. BF-127 sketched 6 words.
   - It is always written: zeros without a table, +16 B per stage map.
   - Is 4 enough, and is bumping `ImageTableAbi::Version` to 3 for it acceptable?
4. **Sampler class in heap templates.** A direct S# paired with a device column becomes specialization constant `DeviceSamplerClassBase` (58368) plus the sampler index. Does a per-class spec constant fit his heap templates and pipeline caching?
5. **The 7 #9508 tests above** fail on lavapipe at his head instead of skipping 77 without the descriptor heap.
