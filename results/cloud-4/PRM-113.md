## Short answer

1. **#9969 is not the top of the whole stack.** The stack forks at #9457:
   - #8939 → #9457 → **#9633 → #9749** (the pointer chase);
   - #8939 → #9457 → **#9790 → #9969** (nested children).
   - `git merge-base --is-ancestor` says #9633 and #9749 are not in #9969, and `git cherry` finds none of their 13 commits there under another SHA.
2. **The shape is a "pointer chase", and only #9633 and #9749 plan it.** A record pointer Phi has one arm that is a `ReadConstBuffer` through a V# whose four words are `LoadAddressU32` reads.
   - #9633's own test is that shape inside a waterfall: `agc_driver_pointer_chase_table` chases a T# at a record pointer up to twice, through a V# at pointer+0x60.
   - Every other head refuses that arm in `PointerRecordPairs`, because the arm's V# is not the record table's V#.
3. **At #9969's head the shape is not handled.** The smallest missing piece is #9633 + #9749's chase in #9969.
   - A merge of #9749 into #9969 has one code hunk, the `PointerRecordPairs` call in `TryMakeIndirectColumn`, plus disk-cache, CMake and debt-doc hunks.
   - **This holds only if LNEE's chase is not a loop.** If `0x720c` loads the V# through the Phi's own back-edge value, #9749 refuses it as a cycle too (below).

## The path every head takes for this T#

- **The T#** is `s_load_dwordx8 s[36:43], s[16:17]`: `GetImageResource` with 8 `LoadAddressU32` dwords, all read through `GetAddressResource(s16, s17)` at an immediate offset.
- **The splitter never sees it.**
  - `SplitDescriptorPhis` (#9969 :2048) collects Phis from the descriptor dwords with `CollectDescriptorPhis` (:1406-1427).
  - That walk follows only `ReadFirstLane` and `IsRuntimeUniformOp` opcodes. `LoadAddressU32` is not one (`SrtWalker/SrtInstructionPredicates.cpp:69-123`), so the Phi in the address is never found.
  - So no "; descriptor web: …" text is added. That matches the reported message.
- **The table planner** is `PlanTableColumnPass` → `PlanTableColumn(image, …)` (#9969 :2194) → `TryMakeTableColumn` (:847).
  - The 8 reads are address reads with an immediate offset, so it returns `TryMakeIndirectColumn(...)` (:934-935).
  - In there, the pointer-hop loop stops at once, because `s16` is a Phi, not a `LoadAddressU32` (:1246-1250).
  - `merged` is set because `UnwrapTableRead(s16)` refuses Phi arms that are different reads (:1279, :1181-1220). For an image this is `pointerKeyed`, and the Phi goes to `PointerRecordPairs` (:1284).
- **If no column is planned,** `Collect` takes `GetHandle` (#9969 :2709).
  - `ValidateSource` → `SrtWalker::ValidateRuntimeValue` reaches the Phi under `LoadAddressU32@0x7980`'s address.
  - The validator has no Phi rule: a Phi falls to `return finish(false)` (`SrtWalker/SrtRuntimeValidator.cpp:139-140`).
  - The result is "GetImageResource dword 0 is not a valid runtime value; chain: LoadAddressU32@pc=0x7980" (#9969 :2415).
  - The SrtWalker directory is identical in main and all six heads, so this fallback is the same everywhere.

So the question per PR is whether `TryMakeIndirectColumn` → `PointerRecordPairs` accepts every arm of that Phi.

## The stack as a whole, and the smallest missing piece

**At #9969's head: not handled.**
- `PointerRecordPairs` (#9969 :1120-1152) sends the `ReadConstBuffer` arm to `PointerRecordRead` (:1142), which refuses a read through another V# (:1115).
- **What it would need to accept:** at that step, a `ReadConstBuffer` at an immediate offset whose `GetBufferResource` words are 4 `LoadAddressU32` reads off one `GetAddressResource`, then the same walk from that pointer.
- That is exactly #9633's `ChaseRead`/`ChaseVsharp` and inner walk (#9749 :1017-1067, :1107, :1138-1172), with `TableColumn::pointerChases` and `pointerChaseDepth`, and the snapshot's chase closure (`ResourceMaterializer.cpp:1102` at #9749).

**The smallest piece: merge #9749 into #9969.** `git merge-tree --write-tree upstream/pr/9969 upstream/pr/9749` conflicts in 5 files, 6 hunks:
- `ResourceTracker.cpp`, **1 hunk, 3 lines against 3:** the `PointerRecordPairs` call in `TryMakeIndirectColumn` (#9969 :1284, #9749 :1307).
  - #9969 calls it for every merged pointer and removed `PointerRecordReads`.
  - #9749 passes `chases, chaseDepth` and still calls `PointerRecordReads` for a merged V# pointer.
  - The resolution is #9969's line with #9749's two out-parameters added.
  - A buffer (V#) column must not carry chases: #9749's disk cache rejects `pointerChaseDepth` without `pointerKeyed` (`ShaderDiskCache.cpp:1404`). So it also needs `if (buffer && chaseDepth != 0u) return false;`.
  - The walker bodies, `PointerFreeWord` with `DescriptorWordArm`, and the rest of `TryMakeIndirectColumn` auto-merge.
- `ShaderDiskCache.cpp`, 2 hunks, and `ShaderDiskCache.hpp`, 1 hunk: both sides bumped the format, #9969 to 60 and #9749 to 57; it needs a new number.
- `libSceAgcDriver/CMakeLists.txt`, 1 hunk (keep both registrations), and `docs/dev/debt/shader.md`, 1 hunk (keep both).

**Size:**
- The chase code already exists and is tested: #9633 + #9749 are +294 −53 in `core/shader`:
  - `ResourceTracker.cpp` +164 −29;
  - `ResourceMaterializer.cpp` +72 −19;
  - `ControlFlowInfo.hpp` +25 −1;
  - `ShaderDiskCache.cpp/.hpp` +33 −4.
- The merge resolution is about 5 to 10 lines plus the format bump.
- **No new test executable.** The chase cases are already in `agc_driver_image_table_tests`.
- One new case there (one more `Run…` in `ImageTable.cpp`) would cover LNEE's two differences: a dwordx4 record with the pointer in dwords 0-1, and the T# load behind an `s_swappc_b64` call that #8070 links.

**Not decided from the code: is LNEE's chase a loop?**
- **If acyclic,** #9749's chase plans it: `0x720c` loads the V# through the record pointer, or through an earlier chase step, at most 4 steps deep.
- **If cyclic, #9749 refuses it too:** `0x720c` loads through the Phi's own back-edge value, i.e. a list walked across the waterfall's iterations. The chase site's inner walk reaches the same site (#9749 :1138), `depthOf` returns nullopt on the cycle (:1148), and `PointerRecordPairs` fails.
  - #9633's ee8767ff0d only stopped a test from asserting that a looped chase is refused; the code still refuses it.
  - Handling a loop would need `PointerRecordPairs` to accept a cyclic site and the materializer's chase closure (`for depth < pointerChaseDepth`, `ResourceMaterializer.cpp:1102`) to iterate to a fixed point bounded by the snapshot.
  - That is about 60 to 120 lines, and a looped-chase case in the same executable.
- **Three facts in the public `--asm` listing decide it,** without the shader:
  1. **The base register and offset of `0x720c`'s `s_load_dwordx4`:** is the base `s[16:17]` as `0x444` wrote it, an earlier step, or the register the loop carries?
  2. **The offset of `0x7248`'s `s_buffer_load`:** it must be an immediate for `ChaseRead` (#9749 :1020).
  3. **The form of `vcc_lo` at `0x444`:** the record offset must be `key << n` or `key * imm`, plus an optional immediate (`MatchAffineOffset`, #9749 :1353). With a bare `SelectU32` and no scale, the column is refused there on every head.
