## 5. The first full 00897 message (before tree, run 1, test `agc_driver_presentation_fsr`)

```
Validation Error: [ VUID-vkCmdBeginRenderPass-initialLayout-00897 ] | MessageID = 0x961074c1
vkCmdBeginRenderPass(): pRenderPassBegin->renderPass (VkRenderPass 0x5d000000005d) was created with pCreateInfo->pAttachments[0].finalLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL, but VkFramebuffer 0x600000000060 pAttachments[0] (VkImageView 0x5f000000005f) references an image not created with the required VkImageUsageFlags.
VkImage 0x5a000000005a was created with VK_IMAGE_USAGE_SAMPLED_BIT|VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT, but VkImageViewUsageCreateInfo overwrote it with VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT.
The Vulkan spec states: If any of the initialLayout or finalLayout member of the VkAttachmentDescription structures or the layout member of the VkAttachmentReference structures specified when creating the render pass specified in the renderPass member of pRenderPassBegin is VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL then the corresponding attachment image view of the framebuffer specified in the framebuffer member of pRenderPassBegin must have been created with the VK_IMAGE_USAGE_SAMPLED_BIT or VK_IMAGE_USAGE_INPUT_ATTACHMENT_BIT usage flags set (https://docs.vulkan.org/spec/latest/chapters/renderpass.html#VUID-vkCmdBeginRenderPass-initialLayout-00897)
Objects: 4
    [0] VkImage 0x5a000000005a
    [1] VkRenderPass 0x5d000000005d
    [2] VkFramebuffer 0x600000000060
    [3] VkImageView 0x5f000000005f

Validation Error: [ VUID-vkCmdBeginRenderPass-initialLayout-00897 ] | MessageID = 0x961074c1
vkCmdBeginRenderPass(): pRenderPassBegin->renderPass (VkRenderPass 0x5d000000005d) was created with pCreateInfo->pAttachments[0].finalLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL, but VkFramebuffer 0x740000000074 pAttachments[0] (VkImageView 0x730000000073) references an image not created with the required VkImageUsageFlags.
```

The spec link is `https://docs.vulkan.org/spec/latest/chapters/renderpass.html#VUID-vkCmdBeginRenderPass-initialLayout-00897`.

**What the message confirms:** the render pass's attachment 0 has `finalLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL`, and the image was created with `SAMPLED|COLOR_ATTACHMENT`. But the framebuffer's view narrowed usage through `VkImageViewUsageCreateInfo` to `COLOR_ATTACHMENT` only. That is exactly the case bef132589c fixes.

**The 1.3.275-only message, the same in both trees:**

```
Validation Error: [ VUID-VkDeviceCreateInfo-pNext-pNext ] | MessageID = 0x901f59ec | vkCreateDevice(): pCreateInfo->pNext chain includes a structure with unknown VkStructureType (1000574000). This error is based on the Valid Usage documentation for version 275 of the Vulkan header. It is possible that you are using a struct from a private extension or an extension that was added to a later version of the Vulkan header, in which case the use of pCreateInfo->pNext is undefined and may not work correctly with validation enabled. …
```

- **The struct:** 1000574000 is `VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_MAINTENANCE_8_FEATURES_KHR` (Vulkan-Headers v1.4.341, `vulkan_core.h:1336`).
- **Why it appears here:** AnyPS5 chains `VkPhysicalDeviceMaintenance8FeaturesKHR` into device creation only when the device reports `maintenance8` (`VulkanDevice.cpp` around line 1681). This lavapipe (Mesa 25.2.8) does report it. The 1.3.275 layer predates the struct, and the 1.4.341 layer accepts it without a message.
- **Probably why GitHub's 1.3.275 runs are silent:** their drivers likely don't expose maintenance8, so the struct isn't chained. I didn't verify this on a runner.
- **Not from the fix:** it is identical in both trees.
