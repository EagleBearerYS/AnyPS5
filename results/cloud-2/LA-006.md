### 1.1 How each number was taken

- **Driver CPU:** process CPU over the measured frames, from `/proc/<pid>/stat` utime+stime (which includes threads that exited), minus lavapipe's threads.
  - Lavapipe's threads are `llvmpipe-0/1` and lavapipe's queue thread, which a gdb backtrace at the window's start identifies.
  - The figure includes lavapipe's `vkCmd*` recording, which runs on the driver's threads.
- **Why not the thread method:** LA-004 §6's thread method sums the threads alive at the window's end. The queue-0 worker (`Driver::enqueue`'s thread) sometimes exits inside the window, and a check run printed `THREADCPU exited 10264 … Driver::enqueue`: 147.1 µs per draw by process, 84.1 µs by threads. That artifact was the "about 100 or about 165 µs" bimodality of my earlier interim numbers. The earlier numbers taken that way undercount.
- **GPU:** the CPU of lavapipe's two rasterizer threads (BF-046 §3). `[gputime]` is unusable: its header reads "0 ms of GPU time", and its draw class spans 87–100% of each 10 s window.
- **Wall:** measured-frame submit-to-idle time divided by 17,000 draws.
- **Did lavapipe bound the run?**
  - **Yes at 1080p:** rasterizer CPU of about 1,440 µs per draw on 2 threads is about 720 µs of wall, against 775–830.
  - **No at 320×180:** the rasterizer threads are busy about 150 of the 194–258 µs per draw. The driver bounds it: the worker plus its lock wait.

### 1.5 The 80 µs verdict

**Missed by every arm.** The best is 155.3 µs (D, device path, 320×180).

**What holds the device path up** (§1.4):
- recording, 53;
- the worker's per-draw capture, recompile and key, 64;
- lookups, target refresh and the rest, about 30.

**What BF-046 §6's changes 3–5 would do here:**
- **3, make the per-draw pre-pass conditional.** Lane A's equivalent is the worker's per-draw capture and specialization. Every draw here is a template hit, yet each one is captured (29.5) and specialized (14.3), and keyed and validated (19.9), again.
  - Skipping that when a draw's user-data shape matches one already proven, and falling back to the miss ring when something new appears, would take most of the 64 µs off: to about 90 µs per draw.
  - This is the only one of the three that cuts CPU substantially.
- **4, batch the device-table refresh.** It has nothing to save here. The steady state shows 0 refreshes, with 40–57 scans per 10 s window.
- **5, take recording out of the GPU mutex.** Recording (53) runs under the mutex, and the worker waits 43 µs per draw for it. That would overlap the two threads and cut wall per draw, not CPU.
- **Reaching about 80 µs** needs change 3 and a cheaper record. Much of the 53 µs is lavapipe's own `vkCmd*` work on the driver thread, so the PC should measure it on a real driver.
- **For GPU mode, BF-046 change 1** (do not build per draw) comes first. That means keying heap templates without the per-draw buffer V# words.

## 2. Why indirect draws were excluded, and what was done

**Read:**
- PR 6947's `materializeDrawStage` gate, `(stage == Fragment || stage == Vertex) && !drawParameters.indirect && HeapFragmentsEnabled()`;
- the CPU path's per-record loop (`Graphics::IndirectDrawPath`, "patched SGPR", `Pm4::ReadDrawArguments`);
- `ClassifyIndirectDraw`.

**Two things depended on the gate:**
1. **A dangling heap pointer.** A CPU-path packet that patches a draw offset into user data (base vertex, start instance or draw index) re-materializes each patched stage once per record.
   - That resets `stageCaptures[i].heapWords` (`DrawCapture.cpp`: reset, then a new `make_shared`), but `stages[k].heap` still pointed at the words it replaced.
   - **Fix:** the record loop now points each re-materialized stage at its new words.
   - **No red possible:** the freed block is reused by the new allocation at once, so no test turns red without this, and valgrind cannot run this binary (it segfaults under memcheck). It is a real use-after-free, found by reading.
2. **Template V#s in the classifier.** `ClassifyIndirectDraw` sized vertex ranges (`APS5_INDIRECT_VERTEX_MIB`) from the template's `vertexAttributes`. A GPU-mode stage carries its real V#s in its heap words, so the classifier now reads those when present.

**Mesh stages are not heap candidates and stay out.** Draw count and draw index are handled by the CPU path's per-record loop as before. Each record's stage is materialized in GPU mode.

**The BF-051 stale-read risk:**
- The change adds no new CPU read: the arguments are read where they were.
- The reads that exist now finish pending table stores first (§5).
- GPU-side packets keep reading their arguments on the GPU. Part (l) shows that with records in registered guest memory.
- Records in an array of the test binary are not imported, and the driver reads them on the CPU. Part (b)'s records are in such an array.

## 3. The set layout

| set | graphics GPU mode with device tables | graphics device path (no GPU mode) |
|---|---|---|
| 0 | per-draw bindings | per-draw bindings |
| 1 | PR 6947's heap; the device lookup indexes the same arrays, reusing the stage's own heap variable of a kind or declaring that kind's array at set 1 | the fragment stage's per-draw set |
| 2 | PR 6947's data set (shader data and flattened SRT, 4 dynamic offsets) | the device image heap (the same heap set object) |
| 3 | the device table: buckets and miss ring, 1 dynamic offset | the device table |

**Details:**
- **The artifact** records the heap bindings only the device lookup declares (`deviceHeapBindings`, disk-cache format 42). So a specialized module leaves them out of its prepared plan, and validation checks them as device-heap arrays.
- **Compute GPU-mode stages keep the CPU table,** because their set 3 holds workgroup memory in device memory. A graphics stage needs no fifth set.
- **The per-device fallback** is the existing `DeviceImagePathRefusal`: a device with `maxBoundDescriptorSets < 4` is refused the device path, with its reason.
- **LA-002's rule** that GPU-mode stages keep the CPU table path is lifted for vertex and pixel stages.

## 7. Open problems

1. **The 80 µs bar** (§1.5). The device path is about 155 µs. The per-draw capture, recompile and key (64) and recording (53) are what remain.
2. **GPU mode builds every draw.** Its heap templates are keyed on the snapshot hash, which includes buffer V# words, so a per-draw object V# makes every GPU-mode draw a build: 0 template hits, 63 µs of resources and 15 of pipeline. GPU mode is about 75 µs per draw slower than the plain device path here.
3. **The miss flood.**
   - One miss record per lane. The first window drains 1.1 million records and drops 78 million for 1,449 distinct misses.
   - Convergence takes 8 + 21 to 25 warm-up frames.
   - Misses resolve only after a reap.
4. **Compute GPU-mode stages keep the CPU table** (set 3 is workgroup memory).
5. **The BF-051 wait is coarse.** It waits for every lease batch, store or not (5 ms to 211 ms per read on lavapipe). Dispatch argument reads wait only with PR 6786. The copy kernel's count record and the awaits-title checks don't wait (debt entry).
6. **BF-052 with GPU mode** needs the heap-word restore (§6).
7. **LA-004 §6's thread method undercounts** when a thread exits inside the window (§1.1). Driver figures taken that way, mine included, should be retaken by process CPU minus lavapipe.
8. **Part (b)'s indirect records** are in the test binary, so the driver reads them on the CPU ("not imported"). Part (l) covers GPU-side reads.
9. **Pre-existing failures, not new:**
   - `agc_driver_draw_cache_relocation` fails with `APS5_DRAW_PIPELINE=1` on the base and the branch;
   - LA-005's 8 fail with `APS5_GPU_PATH=1`;
   - D0 with GPU heap and the CPU table is OOM-killed (lavapipe's 32,768-element sets).
10. **The per-record heap refresh has no red** (§2): the allocator hides the use-after-free, and valgrind cannot run the binary.
