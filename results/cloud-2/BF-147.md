## The test (modes of `NativeMultisampleDepth.cpp`)

**Mode `--driver-path`** (commit 1) and **mode `--driver-queued-fill`** (commit 2):
- registered as `agc_driver_native_depth_driver_path` and `agc_driver_native_depth_driver_queued_fill`;
- in their own `add_test`/`set_tests_properties` block with `TIMEOUT 30`, `ENVIRONMENT ANYPS5_NO_SHADER_CACHE=1`, `SKIP_RETURN_CODE 77`, `WORKING_DIRECTORY` and the WIN32 `PATH` prepend.

The block is separate so it merges clean with #9717's registration (see Overlap). Both modes are dispatched first in `main`, before the harness's own device and its GPU-mutex lock. They set `APS5_PIPELINED_DRAWS=1` and `APS5_PIPELINE_DMA=1` before any driver call, as `PipelinedDma.cpp:77` does.

**`DriverDepthTarget`, the reusable helper** (target, fills, sampling), for #9717's stencil view and BF-144's depth-plane alias:

- **The target:** #9533's shape, D32S8 with a separate stencil plane and a depth-only, pipe-aligned HTILE, 5x3. Clear 0 uses HTILE words 0 and stencil 0. Clear 1 uses `0xfffffff0`, stencil `0x5a` and XOR `0x8c00`. It is built with `DepthSurfaceView` on the driver's device `Context`, sampled through `DepthSampleWords` / `CachedSampledTexture`, and read with the harness's `Fetch`/`FetchShader`. Draws use `DepthRaster`.
- **Sample counts:** 2, 4 and 8, counting the ones the device lacks. lavapipe runs 4; 2 and 8 are counted unavailable.
- **The HTILE block** is 128 KiB of write-watched memory: the 32 KiB HTILE plus spare. So a 131072-byte fill from the HTILE address covers it (`HtileFillCovers`) and touches neither plane. The block is registered as a GPU-visible guest allocation (`GuestAllocations::Mutation::Add`, removed on destruction), so the driver's fill takes the host-import GPU store path a title's memory takes.
- **Linux only:** host imports are pinned write-watched with `SetImportWatch(context, ImportWatch::Watch)`, as `DccKeysFirstWrite.cpp` and `AlphaToCoverage.cpp` do (see "lavapipe" below).
- **`Fill(bytes)`** submits `DMA_DATA` (source 2, data fill of the clear word) through `sceAgcDriverSubmitDcb`. It then runs `AgcDriverWaitIdle_nid_postfix` and waits for `DrawPipeline::Queue0().Outstanding() == 0` (20 s bound), the BF-141 lesson.
- **`Sample(drawn, offset, what)`** optionally rasterizes per-sample depths, re-fetches through the sampled view, syncs the recorder and checks every sample. `Sampled()` gives refusal checks access. The GPU mutex is taken inside, never across a driver submission.

## Deviations and findings

### 1. The three refills are not in the case

**Back-to-back refills.** Measured with a temporary variant switch (not committed), 4 samples, clear 0:

| Shape | Without the fix | With the fix |
|---|---|---|
| 1 queued 128 KiB fill, then sample (committed case) | external GPU writes … | **passes** |
| 4 queued 128 KiB fills back to back, then sample | external GPU writes … | overlapping native multisample depth clear transitions are not implemented |
| 4 whole-HTILE 32 KiB fills back to back, then sample | overlapping … | overlapping … |

- **The refusal on the second fill is #9533's own rule, not L307.** At `DepthSurface.cpp:2534-2535` (514643ab16), a same-pattern fill is accepted as a refill only while `clearFillNote == 0`, so that `fillNoteAfter` can still pick up its write.
- **The queued store notes after its GPU write is recorded**, so the first queued fill sets `clearFillNote` at once (`:2541`). The second one then refuses as overlapping.
- **The small path refuses too.** The 32 KiB fills give the same refusal with and without the fix.
- **So any title that fills the HTILE twice before sampling** is refused on #9533 by both paths. If JJenkx's three refills were back to back, that is a #9533 gap to raise with them.

**Fill-then-sample rounds** can't be checked on Linux CI (point 2). Rather than commit a red case, I kept one fill, then the sample.

### 2. lavapipe on Linux: the queued case can only sample once

- **lavapipe's device writes are CPU stores.** A fill into a host-imported HTILE therefore trips the CPU write watch.
- **The driver's probe sees this** ("host imports resolve write protection: yes") and compares imports instead of watching them. Native multisample depth needs watched memory, so with the default the queued fill gives:
  - without the fix: "native multisample depth requires watched accessible guest memory";
  - with the fix: "native multisample depth metadata fill over unwatched memory is not implemented".
- **#9533's debt entry already lists this:** private imports that lose tracking.
- **Pinning the imports watched** (as the DCC key tests do) gives the behaviour of a GPU whose writes don't fault. But once lavapipe actually runs the fill, its stores look like guest writes:
  - sync before the first sample: "CPU writes raced native multisample depth clear";
  - a second sample or draw after the first: "guest writes over native multisample depth are not implemented" (`:478`).
- **So the committed case samples once, while the fill is still queued on the recorder.** That sample passes with the fix and refuses without it.
- **Where this doesn't arise:** on a real GPU (where the probe keeps imports watched) and on Windows' shared aliases. Windows CI skips `agc*` tests (no Vulkan driver), so only the MinGW compile applies there.

### 3. A possible #9533 follow-up, not fixed here (only `:307` may change)

- **The trigger:** when the HTILE is not host-importable, `storeBufferFill` falls back to a CPU store (`BufferFill.cpp:410-419`) and only then notes (`:422-423`).
- **What #9533 does with it:** the native branch collects `clearGeneration` after that store, so `StoredAllSince` can never hold. The sample refuses with "native multisample depth clear has no complete tracked HTILE store" (measured with the fix and an unregistered HTILE block).
- **Why only this path:** the synchronous and small paths note before storing.

### 4. Environment

- On this VM, as the unprivileged runner, llvmpipe needs `GALLIUM_OVERRIDE_CPU_CAPS=avx` (CI sets it).
- Without it, the existing `agc_driver_native_depth_separate_stencil` on the untouched base also segfaults: an aligned AVX store to a 16-byte-aligned stack slot in JIT code, in 3 worker threads.
- All runs here use the CI environment.
