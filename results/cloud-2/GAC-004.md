## 2. What was fixed, and what went into the debt entry

### PM-019's four limitations: documented, not fixed

None is a small or obviously sound change, so each is stated in the entry.

1. **Integer views of the copy throw.** A 32-bit integer (depth-bits) view of the write base still throws "32-bit integer read of the depth-layout texture …, which is no depth surface drawn with, is not implemented" (`ShaderResources.cpp`, the rule in `cachedTexture`).
   - That rule predates the expand and covers every depth-layout texture without a depth surface.
   - Serving such a view from the expand's R32F image needs an integer view of that image, which the storage cache does not make.
   - The entry says the copy serves R32F views and raw buffer and CPU reads only.
2. **The whole plane is written.** Only the viewport and scissor are checked, not what the primitives cover. A partial-coverage expand would overwrite texels the console leaves alone.
3. **The expand's pixel shader never runs**, so any memory it writes is lost.
4. **A later depth target at the write base** starts from its own image, not from the copy: `takePlanes` moves planes only between depth surfaces, and a new depth surface never loads guest bytes. The next expand into it throws "into a live depth surface".
   - Fixing this means loading a new depth surface from a storage image, which is a change to depth surfaces in general.

Also in the entry: the skip rule, the store ahead of address-based builds, the first-upload cost, the read-only stencil, and `agc_driver_depth_expand_review`.

### Cost: skip unchanged expands (fixed)

`RunDepthExpandPass` now remembers, per write base (device, address):

- the live depth surface it copied, and that surface's write serial `written`;
- the write base's storage image (as a `weak_ptr`) and its content version after the write.

When all four are unchanged, the expand records nothing.

**Why that is sound.** Everything that can change the surface or the image bumps one of the two:

- the surface's serial: draws that bind it (`DepthSurfaceView`, called by both the normal and the recipe draw paths), fast clears (`ApplyFastClear`, applied before the check), and stores of its storage views;
- the image's version: uploads (the cache's `Refresh` after a CPU write to the write base) and writes (`MarkDirty`).

All of these precede the expand's packet in queue order.

**DepthPlaneCopy's caveat does not apply here.** That code does not trust the serial of the latest drawn surface, because the draw that binds a surface can make a plane copy during its own resource build and be recorded after it. The expand is a packet of its own, recorded after every earlier draw, so the caveat does not arise.

**Scope:**

- Expands without a depth surface at the read base always write.
- A replaced or evicted image fails the `weak_ptr` check, so the expand copies.
- A recreated surface has a new serial, because serials are global, so the expand copies.

### Cost: GAC-003's per-expand store, moved ahead of address-based builds (fixed)

GAC-003 (1027f2bdc) stored each expand's plane into a host-imported write base at once, for address-based readers. On lavapipe that write-back took each 1920x2160 expand from about 3 ms to 35–50 ms. A local build with the store disabled measured 2.5–3.0 ms per expand.

Now:

- The plane stays pending, and the expand notes its write base.
- `GuestBufferMemory::UploadFinish` calls `StoreDepthExpandWrites` for address-based builds, before the imported heaps are bound. That function stores the noted planes that are still pending in host-imported write bases, recording the store into the import, and forgets the notes.
- Every other reader stores the plane itself before it reads, as for any written storage image.
- Several expands before the next address-based build cost one store; with no such build, none.
- The buffer-read cases now pin the counts: no store at the expand, one ahead of the address-based copy, none for the plain copy.

### A one-pass copy: not done

The copy is depth image → staging buffer → R32F image. Copying a depth aspect straight into a color image needs `VK_KHR_maintenance8`, or a compute or fragment pass, and the skip already removes the repeated copies. The two-step copy stays; it is a follow-up if the GPU numbers in game call for it.

### Nits

1. **`DepthSurfaceAt` scanned every device** (fixed, 7a9f73c87). The expand now refuses a live depth surface at the write base only for its own device: `planeSurface(context.device, …)` under the surfaces' lock. `DepthSurfaceAt(address)` stays for its other caller in `ShaderResources.cpp`. There is no test, because it would need two Vulkan devices.
2. **The wasted first upload** (documented, not fixed). The first expand into a write base, or the first after its image leaves the cache, uploads the guest bytes that the copy then overwrites: 41.7–51.6 ms at 1920x2160 on lavapipe, once per image.
   - Avoiding it needs a create-without-upload mode in the storage cache, keeping the write-back's baselines (generation, saved bytes for unwatched memory) right. That is more than a nit.
3. **The read-only stencil refusal was broader than needed** (fixed, 321867132).
   - A depth view with `STENCIL_READ_ONLY` on a moving depth plane is now taken: such a stencil plane already counts as not moving, and the expand copies only depth.
   - The refusal now covers a base slice or a mip level, and says so.
   - `agc_driver_graphics` takes the game's expand with that view and refuses it with a mip level added.

## 3. Copy counts and cost, before and after

### Copy counts (`agc_driver_depth_expand_out_of_place repeated-expand`)

The case runs seven expands into one write base:

1. three in a row;
2. one after a sampled and a raw read of the write base;
3. one after an address-based buffer copy of it;
4. one after a second depth draw, 0.25 deeper;
5. one after a CPU write of 0.5 over the write base.

It requires a copy only after the first draw, the second draw and the CPU write.

### Cost at 1920x2160

The harness is a scratch 1920x2160 variant of the test: the same registers, a 15.9 MiB plane, timing Submit+WaitIdle of each packet. It is not committed. Lavapipe in this VM: 4 vCPUs, CPU Vulkan, so these are upper bounds.
