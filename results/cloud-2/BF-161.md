## The change

- **`DriverTestAccess`** (`:59`) gains `static void Stop() { Driver::Get().stop(); }`.
  - `Driver::stop()` (`Lifecycle.cpp:145`) is idempotent (`stopped`). It joins the workers, takes the GPU lock and calls `device.Reset()`.
  - `Shutdown()` is not used, so a stored failure is not rethrown.
- **`CheckDriverPath`** runs everything after `UseDevice(device)` in an immediately invoked lambda, `const int result = [&] { … }();`. Then it calls `device.reset()` and `DriverTestAccess::Stop()`, and returns `result`.
  - Both returns after `UseDevice` go through that release: the Windows queued-fill skip (`return VulkanTestSkipped;`) and the pass (`return 0;`).
  - The release calls are explicit, with no destructor-based guard.

### Why a lambda instead of a release call at each `return`

The cases' `const auto context = VulkanDeviceTestAccess::ContextOf(*device)` is a `Graphics::Context`. It holds a `std::shared_ptr<BufferPool>`: `VulkanDevice::graphicsContext()` copies `state->bufferPool` into it (`VulkanDevice.cpp:3787`). `~State` resets its own two references (`:820-821`), so on 1582cf6cc0 the test's copy is the pool's last reference, and that copy dies when `CheckDriverPath` returns.

If the device were released at a `return` statement while `context` is still alive, `~VulkanDevice` would destroy the VkDevice first. `~BufferPool` (`BufferPool.cpp:51`) would then free its buffers and memory on a destroyed device. With the lambda, `context` and everything else from the cases is gone before `Stop()`.

I tried that simpler shape: `device.reset(); Stop();` before each `return`, with `context` alive. Under `VK_LAYER_KHRONOS_validation` both tests then crashed with signal 11 (rc 139). The layer also reported 8 `VUID-vkDestroyDevice-device-05137` errors in each mode, for 4 VkBuffers and 4 VkDeviceMemory objects still alive at `vkDestroyDevice`, which are the pool's. That variant was not committed.

### The exception path is left as it is

A failing `Require` inside the lambda throws through `CheckDriverPath` to `main`'s catch. The driver keeps the device until static destruction, as on 1582cf6cc0. The test is failing by then anyway.
