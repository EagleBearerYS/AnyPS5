## The rule

`sameDepthAlias`, `DepthSurface.cpp:103-111` at 96cf351df8. It is called from CheckCurrent's alias loop at `:454`, for the depth plane only (`index == 0u`). The function stays as it was, plus one case:

```cpp
const bool refilled = recorded.newest == MultisampleColorContent::Clear && current.newest == MultisampleColorContent::Fill && current.fills == recorded.fills + 1u && current.filledBytes >= current.bytes;
return current.active == recorded.active && current.contents == recorded.contents && (current.newest == recorded.newest || refilled) && sameValue;
```

`recorded` is the alias taken at import (`soleDepthAlias`, `:97`). `current` is the sole colour target over the plane now.

**New fields:**
- `MultisampleColorAlias::filledBytes` and `fills` (`MultisampleTarget.hpp:74-75`).
- `MultisampledColorFill::noted` with `Noted()` (`MultisampleTarget.hpp:52`, `:59`), incremented at `MultisampleTarget.cpp:1130` for every fill that overlaps the target.
- `Alias()` sets `fills` at `:557`, and `filledBytes = MultisampledColorBytes(target)` only when a fill is pending (`:574`).

**The four conditions:**

1. **The fill covers the whole alias range.**
   - A target's newest is Fill only while `colorFill.Pending()` holds a pattern. `NoteFill` (`MultisampleTarget.cpp:1128`) sets it only for a fill covering `[target.address, target.address + MultisampledColorBytes)`; anything partial sets a refusal, and `Alias()` then says Unknown.
   - The alias range is `guardedColorBytes(target)` (`MultisampleTarget.cpp:118`). It equals `MultisampledColorBytes` for 64 KiB render-target tiling but can be larger for 4 KiB or standard-64 KiB tiling. So the rule also requires `filledBytes >= bytes`.
2. **The fill's value equals the recorded clear bit for bit.**
   - This reuses the comparison the function already had: `sameValue` is a `memcmp` of the whole 16-byte `VkClearColorValue`.
   - Both sides come from the same decoder. The recorded clear is the value `ApplyFastClear` cleared with (`MultisampleTarget.cpp:349`): `MultisampledFillClearColor`, `fastClearColor` or a DCC clear, all through `FillClearColor` (`Texture.cpp:1649`) on a zeroed value. The fill's value is `MultisampledFillClearColor(target, pattern)`. So equal bits mean the same clear command and the same texels.
   - **-0.0:** bit-different from 0.0, so a fill of `0x80000000` over a clear of 0.0 refuses (`NegativeZeroFill`).
   - **NaN and 32-bit denormals:** `FillClearColor` refuses them (`Texture.cpp:1682`). Such a fill is neither absorbed nor decodable: the alias reads Unknown and refuses (`NanFill`), and in a real fill `BufferFill` writes guest memory. A recorded clear can never be a NaN for the same reason.
3. **Nothing else was recorded on the alias in between.**
   - `contents` must be unchanged. It is bumped by every applied clear or fill (`ApplyFastClear`, `MultisampleTarget.cpp:351`), `Recreate` (`:366`), a storage write (`:410`), a sample-order target (`:1172`) and every draw view (`:1180`, `:1189`).
   - `fills` must be exactly one more than at import, so any other fill in between refuses: partial, full, of another value or the same.
   - `newest` must go from Clear to Fill. Any other change, such as a CMASK fast clear, a DCC fill or a HTILE refusal, makes it FastClear or Unknown, which refuses.
4. **The HTILE still proves the clear at the sample.** This is shown from code, unchanged by this commit:
   - CheckCurrent ends with `Require(GuestMemory::UnchangedSinceAll(sampling.initial), "guest writes over native multisample depth are not implemented")` (`DepthSurface.cpp:506`).
   - `sampling.initial[1]` is the HTILE range. Its generation was taken at import, where every word had to prove the clear, or at a later HTILE fill/clear, whose words are re-proved one by one at `:494`.
   - Queued GPU writes over it refuse at `:450`.
   - The control `HtileWordThenSameFill` writes one HTILE word before the same-value fill. With the commit it refuses at `:506`; at a2911ffb72 it refused earlier, at the alias check.

**Where these are shown from:** the code at a2911ffb72, which is #9742 plus BF-220, because main has no alias model (`MultisampleColorAlias`, the recorded clear, `sameDepthAlias`). Main (3a2c51afd2) does have every piece the four conditions rest on, unchanged apart from #9186's host-only flag:
- the full-or-refuse rule in `NoteFill` (`MultisampleTarget.cpp:1101` on main);
- the absorb rule in `BufferFill` (`BufferFill.cpp:391`);
- `FillClearColor`'s NaN and denormal refusal (`Texture.cpp:1682`);
- CheckCurrent's final guest-write check (`DepthSurface.cpp:369` on main);
- the HTILE word re-proof.

None of the four needed anything main lacks besides #9742 itself.

**What the acceptance leaves unchanged:**
- **Guest memory checks:** an absorbed fill writes no guest memory (`BufferFill.cpp:391`), so accepting the alias skips none of them. A fill that isn't absorbed still writes the depth plane, which then refuses at `:450` or `:506`.

## #9186 (fma-rc, merged 13:25Z as 0658bc8749)

**What it changes** (lines at main 3a2c51afd2):
- **`hostOnly` flag:** each multisampled colour target and its guarded ranges now carry one.
- **Set to true:**
  - on every reuse or recreation through `acquire` (`MultisampleTarget.cpp:798`, `:806`), which is how a render target is bound and how `MaterializeMultisampleTargetClear` works;
  - when a fill is absorbed (`MultisampledColorFillAbsorbs` → `holdHostOnly`, `:1287-1294`);
  - for a storage view (`holdHostOnly`) and for a target created for a storage write (`createFilled(..., true)`, `:1250`).
- **Set to false** only for a target created because a draw sampled memory no draw had rendered (`createFilled(..., false)`, `:897`, `:1198`, `:1221`).
- **Retirement:** `RequireNoMultisampleColorTarget` (`:1365`), called for guest reads (a CPU read through the guard, a DMA copy source, index and vertex reads, texture and storage reads, cached image access), now retires targets that are not host-only instead of throwing (`:1382-1392`).

**What it doesn't change:**
- how a fill is recorded on a colour target: `NoteColorMetadataFill` and `MultisampledColorFill::NoteFill` (`:1093`, `:1299-1303`) are untouched;
- which fills are absorbed: the same address, footprint and decodable value, now also marking the target host-only;
- anything on a fill path: fills never retire a target.

**So DtD's Clear→Fill still happens on main + #9186** (with #9742, which brings the alias bookkeeping; main has no `MultisampleColorAlias` or recorded clear):
- The absorbed same-value fill is still noted as pending, and it makes the target host-only, so #9186 can't retire it afterwards.
- The one window #9186 opens: the target was created by sampling, its fill was applied by that sample (Clear recorded, still not host-only), and a guest read hits it before the next fill. Then it is retired and there is no alias at the sample at all.
- In that case a later full fill isn't absorbed and writes guest memory over the depth plane, which refuses at the guest-write check instead.
- I can't tell from here which path DtD's R32F target takes. If it was ever bound as a render target (`acquire`), it is host-only for good, and the Clear→Fill path above holds.
