## 2. Semantics: what each one covers, and whether they compose

### Where each one acts

A table's cost has three layers: the **capture** (the snapshot of the table's records in `ResourceMaterializer`'s `TableSnapshotter`), the **resolution** (the driver's `ShaderResources::resolveImageTables`, one texture per element), and the **descriptor writes** (`ShaderResources::buildComplete`).

- **v3** acts on all three:
  - **Capture:** a thread-local memo of up to 16 columns, keyed by the column's geometry (base, size, records, keys, stride, addend, offset, dwords, max key, carry fold, pointer or buffer, sampler). It has two hits:
    - the **no-read hit**: the heap is unwritten since the stamp, so the vouch supplies the stored words by reference and reads nothing;
    - the **compare hit**: the heap was written, so the stored runs are read again and compared, and on equal words the column is shared by reference.
    - Both hits share the column by identity, which feeds the resolution memo (`ResolveImageTablesShared`), the draw-cache identity compare and the supply of words by reference.
    - On a miss (changed words, no entry, another thread's entry) v3 walks the column from scratch. It reuses only the words its compare already read.
  - **Resolution:** a whole-table replay. When every element of a kept table is current, it places the cached textures without running each element's bind checks again.
  - **Descriptors:** kept sets. A freed set keeps its table descriptors, and a later build that binds the same image infos skips `vkUpdateDescriptorSets` for them.
  - **Not covered:** narrowed columns (`memoized` requires `!records.narrowed`), indirect and selected columns.
- **#6440** acts on the capture only, with a process-wide memo of up to 512 columns and 256 MiB.
  - **Key:** shader code address, descriptor source, base, size, key count and a hash of the narrowed states. A column is kept from its second sighting.
  - **Every capture reads every word.** A candidate is used when the `TableColumn`, the narrowed states and every recorded page-accessibility answer are equal.
    - **Hit:** the words equal the stored words, so the descriptors are taken again with one index lookup per distinct descriptor.
    - **Layout reuse:** the words differ but the layout holds, so the walk (locate, page checks, runs) is skipped and only the descriptors are assembled again.
  - It covers narrowed columns and pointer columns. It doesn't share by identity: each capture builds new codes and words.
- **#6340** acts on the resolution only, through per-element reuse.
  - **Before (main):** the whole-table reuse (`ReusedTable`) needed every element unchanged and cached.
  - **After:** an element is reused when its own texture is unchanged since its generation, no pending storage write overlaps it, and its texture is still cached. Only the others are resolved again.
  - **Mixed tables:** an element that can't be kept (a DCC surface, a texture another queue has a pending storage write to) no longer stops its siblings from being reused.

### The PM's expected split, checked against the code

- **v3's no-read hit covers an unwritten heap:** yes.
- **"#6440's memo covers a heap that was written but whose words are equal":** v3 covers that case too, with its compare hit. Both read the words once. v3 then shares the column by identity, so the resolution and draw-cache identity checks hit downstream. #6440 rebuilds the codes from its stored descriptors, and the downstream identity checks miss. On a written heap with equal words, v3's hit is the cheaper one, and #6440's memo is never reached in the merged tree.
- **#6440's memo is reached only on v3's misses.** There, it adds three cases v3 doesn't cover:
  1. **Changed words, same layout:** a heap rewritten every frame. v3 walks the whole column again; #6440 replays the recorded page answers and keeps the layout.
  2. **Narrowed columns:** v3 never memoizes them; #6440 keys them by their narrowed states.
  3. **Columns v3's per-thread memo doesn't hold:**
     - a column first captured on another queue thread;
     - more than 16 columns, or more than 4 Mi words, on one thread;
     - the same heap read through different column geometries.

     #6440's process-wide memo still holds these and turns them into hits. Each hit still reads every word, but skips the walk and the descriptor assembly.
- **#6340 reuses per entry:** yes, and it's the only one of the three that does. v3's resolution replay and main's reuse are all-or-nothing per table.

### Does v3's miss path plus #6440's memo give strictly more than either alone?

- **Coverage: yes.** Every case either one covers is covered by the union:
  - **Unwritten heap:** v3's no-read hit.
  - **Written, equal words:** v3's compare hit when its memo holds the column; otherwise #6440's hit, from the third sighting on.
  - **Changed words:** #6440's layout reuse, from the third v3 miss of that column.
  - **Narrowed columns:** #6440 only.
  - **Other threads, evicted columns:** #6440's hit.
- **Cost: not strictly cheaper in every case.**
  - **Extra work on each v3 miss.** The union adds a lookup under #6440's global mutex (one `std::map` find, plus a sighting scan of up to 4,096 entries on a key not yet admitted).
  - **Double storage.** From a column's second sighting, a miss stores the column in both memos: v3's thread-local copy of the runs and words, and #6440's copy of the words, descriptors, record map and layout. Memory per column is then about twice either alone.
  - **When these costs show.** On v3's misses. Measured in §3.3 on the 19k column:
    - **One record changed** (v3 misses, #6440 reuses the layout): 2.85–2.92 against v3's 2.69 ms (+6–9 %). That's less than the round-to-round spread, but the merges sit above v3's median in 16 of their 18 rounds.
    - **A base never seen** (both miss): 2.87–2.91 against 2.86 ms, within noise. #6440 alone costs +18 % over main here.
- **#6440's admission interacts with v3.**
  - A column is admitted at its second sighting, and in the merged tree only v3's misses are sightings. While v3 keeps hitting a column, #6440 never stores it.
  - So #6440's layout reuse starts from the third v3 miss of a column. On a heap written every frame, that's the third written frame.

### Order

1. v3's no-read vouch (one span query, no read);
2. v3's compare (one read, an identity share on equal words);
3. #6440's memo (the layout replay; on equal words, the stored descriptors; otherwise a rebuild over the reused layout);
4. the full walk.

This is the order in `test/v3-x-6440`. Steps 2 and 3 share one read. When #6440's layout runs equal the runs v3's compare read, its words are taken from the compare, which they always do while the page answers hold.

Running #6440's memo before v3's compare would cost one more read whenever v3's compare would have hit, and would lose the identity share. Running it after the full walk would never save anything. The resolution layer is independent: #6340's per-element loop runs inside `resolveImageTables` whatever the capture did.

### Is anything in #6440 or #6340 more general than v3 (gate step 5)?

Yes, four things, which v3 should take as follow-up commits in v3's own style rather than by merging the PRs:

1. **#6340's per-element reuse** (resolution).
   - v3's replay needs the whole table to be current, so one changed, evicted, pending-written or DCC element sends v3 down the full resolve of every element.
   - **How v3 should take it:** take #6340's per-element loop and replay each reused element's recorded bind result when the table's image samplers and sampler words equal the recorded ones. This is the resolution in `test/v3-x-6340`. v3's replay and kept-descriptor checks pass there (§1).
   - **Keep the whole-table replay as the fast path.** In the Village-like bench (§3.4), on tables whose entries are all current, #6340's per-element loop doubles `resolveImageTables`: 1.05 → 2.10 ms over main, and 0.68 → 1.69 ms over v3's replay. v3 should replay the whole table, as it does now, when every entry is current, and fall back to per-element reuse only when some aren't.
2. **#6440's layout reuse on changed words** (capture).
   - v3's memo keeps the runs and words, but not the per-record slot map (whole or split records, unread dwords) or the recorded page answers, so a compare miss walks again.
   - **How v3 should take it:** keep the layout (`ColumnLayout`: states, whole and split slots, runs, read ranges, checks) in v3's memo entry. On a compare miss, replay the recorded checks and rebuild the descriptors from the compared words over the kept layout. That's one read and no walk.
3. **#6440's narrowed columns** (capture).
   - **How v3 should take it:** put the narrowed states in v3's key, compared element by element as #6440 does, and drop the `!records.narrowed` condition. The stamp and vouch need no change, since the read ranges are the layout's.
4. **#6440's process-wide memo** (capture).
   - v3's memo is per thread. PM-037 already listed "a device-wide memo, instead of the per-thread one" as v3's goal, and #6440 shows the bounded form: LRU over entries and bytes, with admission at the second sighting.
   - **How v3 should take it:** v3's entries are immutable once remembered (`SharedValues`, shared `SrtGuestWords`), so they can move to a shared, sharded store without changing the hit paths. Admitting at the second sighting would keep one-off columns out.

v3 is more general than both in the other direction:

- the no-read hit on unwritten heaps;
- the identity share that the resolution memo, the draw-cache compare and the shader memory's supply build on;
- the kept descriptor sets.

#6440 and #6340 have no equivalent of these.

### #6402

- **What it does:** #6402 stores to images selected through image tables. Its `resolveImageTables` skips the table reuse when any element is written (`storageTable`), and it adds a storage table binding at 260, moving the sampled table to 261 (`RuntimeAbi` `Version` 12 → 13).
- **Merges:** clean with #6440. It conflicts with v3 and with #6340 in `ShaderResources.cpp` (merge-tree).
- **Composition:** the written-element guard has to hold in every reuse path. Whichever of v3 or #6340 lands after it carries the guard into the per-element loop and v3's replay. v3's kept sets record only `VK_DESCRIPTOR_TYPE_SAMPLED_IMAGE` table bindings, so #6402's storage table binding is never kept.

### #6488 and #6481 (addendum)

#### #6488: waterfall loops over per-lane T#s through image tables

- **What it does.** It recognises a waterfall loop over a T# that each lane loaded with IDXEN buffer loads, and plans it as one image table access per lane.
  - **New column kind:** `TableColumn::laneKey`, keyed by the lane's buffer index.
  - **Its own record walk:** the materializer reads such a column with `LaneRecords`. That is a walk of its own over up to 65,536 records, at the V#'s stride and `NUM_RECORDS`.
  - **ABI changes:** the record count goes into the table header (`TableRecordCount`, so a header is 9 words instead of 8, and `ImageTableAbi::Version` goes from 2 to 3).
  - **Whole-table faults:** two new ones, `LaneRecordLayout` and `LaneModes`. The `LaneModes` check runs in `ResolveImageTables` on tables marked `sharedMode`.
- **How it composes with v3.** Lane columns return from `ReadColumn` before v3's memo, as v3's selected and indirect columns do.
  - So neither of v3's capture hits applies to them: every capture reads every record.
  - v3's map resolution memo (`ResolveImageTablesShared`) compares the columns' shared contents by identity, so it never shares their map either.
  - v3's driver-side replay and kept sets still apply to lane tables, because they key on the table's descriptor words and image infos, not on the capture.
  - The result is correct, and neither PR needs anything from the other.
  - #6440's memo is bypassed the same way: in #6440 + #6488 the lane branch also returns before `FindColumnMemo`.
- **What it changes on v3's measured paths:** nothing measurable. On the columns v3 memoizes, #6488 adds one branch on the column kind and one header word per table, so I didn't bench it.
- **What v3 could take later:** a lane column is a plain strided array of whole records. v3's key plus `laneKey` would cover it with both hits unchanged, since the vouch spans the walk's `[low, high)` and the compare can read `LaneRecords`'s runs. That's a follow-up for whichever lands second, not a condition of the merge.
- **The cache format.** #6488 sets `FormatVersion` 37, as v3, #6243, #6280 and #6412 do (main is 36; I checked all five heads).
  - #6488 and v3 each add two `TableColumn` fields to the encoded plan.
  - Whichever lands after the first needs the next number. Git won't flag it, because the line is the same on both sides.

#### #6481: fault table entries the device or guest memory cannot hold

- **What it does.** Before an entry's guest memory is read or any image is created, `resolveImageTables` now checks the entry two ways:
  1. **Device limits.** The image is checked against `vkGetPhysicalDeviceImageFormatProperties`: extent, array layers and level-0 bytes, cached per device, format, type and flags. An unsupported combination is refused.
  2. **Registered memory.** The surface must overlap a readable registered guest allocation (`RegisteredReadableOverlaps`) instead of any committed host page.

  A refused entry faults when it is selected. A `VulkanError` (device loss, allocation failure) from the checks or the texture lookup now reaches the draw, where it used to fault the entry.
- **How it composes with v3.** The checks run only where an entry is resolved. v3's whole-table replay, like main's whole-table reuse, replays a refused entry's recorded fault without checking it again. That stays correct for both checks:
  - **The device limits** depend only on the T# words, which `SameTable` compares.
  - **The registry check** depends on the guest allocations. Their generation is part of `TableState`, so a table remembered before a registration changed is dropped.
  - **v3's kept sets** compare the image infos each build writes, so they follow whatever #6481 refuses.
- **With #6340.** #6340's per-entry loop reuses only entries with a cached texture, so a refused entry is never reused. Its checks run again on every build, where v3's replay and main's reuse replay the fault. In `test/v3-x-6340` + #6481 (merge-tree: only the debt doc conflicts) the checks land in the per-entry resolve path.
- **Cost.** On v3's replay (the hit path) it costs nothing. On a fresh resolution, each entry gets #6481's two checks instead of main's mapping check. v3's bench measures that path in its unwatched configuration, and §3.5 finds the two checks cheaper: 0.2–0.3 µs per entry against 0.7–1.2 µs.

#### Gate step 5 for the addendum's PRs

Neither #6488 nor #6481 reuses anything, so neither has a case v3 should take for gate step 5. #6488's lane columns are one more column kind that v3's capture memo could cover later (above).

## 3. Benches

**Machine and trees.**

- **Machine:** one Linux VM (Xeon 2.8 GHz, 4 cores, lavapipe, Mesa 25.2.8). Every tree was built Release by the CI mirror.
- **Trees, run in turn:** main 0029e62f9, #6440 cdb140f49d, #6340 ef724aad62, v3 5a31a9c674, v3 ∪ #6440 (`test/v3-x-6440`), v3 ∪ #6340 (`test/v3-x-6340`) and v3 ∪ #6440 ∪ #6340 (`test/v3-x-6440-6340`).
- **Alternation:** each round runs all seven trees, and the order rotates from round to round.
- **Instrumentation:** the bench sources and PM-038's step timers were applied to each tree as uncommitted local edits, identical in every tree, and removed afterwards. None of it is on the fork branches.

**Statistics used.**

- p50 and p90 are the medians of the rounds' p50 and p90.
- The worst case is the maximum over all rounds.

### 3.1 #6440's 19k-entry bench

**#6440's diff has no bench.** Its three files are `ResourceMaterializer.cpp`/`.hpp` and `tests/ShaderMemory.cpp`, which holds only tests. Its commit message gives the 007 First Light figures (columns "of up to 19k records", 1.49 → 0.62 ms per snapshot), and the "19k-entry bench, 1947 → 838 µs" figure must come from a harness that isn't committed.

**So I wrote the equivalent:** `TableCaptureBench.cpp`, a standalone executable linked like `agc_shader_memory_tests`.

- **Table:** one whole-table image column of **19,000 T# records** at a 32-byte stride (152,000 words).
- **Memory:** the column lives in a guest-arena block that is write-watched, as v3's tests set it up.
- **What is timed:** each `AgcDriver::ShaderMemory::Capture()` of the column, the capture path a dispatch takes, one capture at a time.
- **Run size:** 5 warm-up and 200 timed captures per case, 9 rounds per tree.
- **Path check:** v3's and #6440's own counters (`ResourceMaterializer::TableReuse()`, `ColumnMemoCounts()`) record which path each capture took.

| Case | What changes before each capture | Path |
|---|---|---|
| **unchanged** | nothing | hit |
| **written-equal** | one record is stored again with its own bytes, so the heap is written but its words are equal | hit |
| **one-changed** | one record gets a new T# | miss |
| **many-tables** | 40 tables of 19k records, captured in turn | the hit or miss path depending on the memo's capacity |
| **cold-base** | a base never seen before (shifted by one record each capture) | the worst-case miss |

## 4. Draft for v3's description: "Overlap"

Neutral, and limited to what the diffs and the runs show. Paste as is, or trim the bench lines.

> ### Overlap
>
> Five open PRs change the same image table code.
>
> - **#6440** (a column memo in `ResourceMaterializer`).
>   - **What it does:** keeps a column's layout, its words and its distinct descriptors in a process-wide memo, keyed by shader, descriptor source, table base, size, key count and narrowed states. Every capture reads the column's words. When they are equal, the stored descriptors are used; when only the words changed, the stored layout is.
>   - **What this PR does instead:** skips the read while the heap is unwritten. On a written heap it compares the words and shares the column, and what is built from it, by reference.
>   - **How they compose:** this PR's two paths run first, and #6440's memo serves their misses: changed words over the same layout, narrowed columns, and columns another thread captured or this PR's per-thread memo no longer holds.
>   - **Conflicts:** `ResourceMaterializer.cpp`/`.hpp` and `tests/ShaderMemory.cpp`. A resolution that runs both is on `test/v3-x-6440`; it passes `ctest -R '^agc'` 606/606, including both PRs' tests.
> - **#6340** (per-entry reuse in `ShaderResources::resolveImageTables`).
>   - **What it does:** reuses the unchanged entries of a table whose other entries changed or could not be kept.
>   - **What this PR does instead:** replays a whole reused table's bind results without checking each entry again, and keeps the table's descriptor set.
>   - **How they compose:** per-entry reuse, with each reused entry's recorded bind result replayed.
>   - **Conflicts:** `resolveImageTables`. The composed resolution is on `test/v3-x-6340`.
> - **#6402** (stores through image tables).
>   - **What it does:** adds a storage table binding and skips table reuse for tables with written entries.
>   - **How they compose:** it conflicts with this PR and with #6340 in `resolveImageTables`, and not with #6440. Whichever lands after it keeps its written-entry guard in the reuse paths.
> - **#6488** (waterfall loops over per-lane T#s through image tables).
>   - **What it does:** plans a waterfall loop over T#s that each lane loaded from a buffer as one image table access per lane. It does this through a new lane-keyed column with its own record walk.
>   - **How they compose:** lane columns are read in full on every capture. This PR's capture reuse doesn't cover them; its driver-side replay and kept sets do. Neither PR needs anything from the other.
>   - **Conflicts:** `ControlFlowInfo.hpp`, `ResourcePlan.hpp`, `ResourceMaterializer.cpp`, `Recompiler.cpp` and `tests/ShaderMemory.cpp`, all unions of both sides. Four further changes are needed that git doesn't flag:
>     - `WordsIndex(records, value)` in `LaneRecords`;
>     - `return;` in the `void` `ReadColumn`;
>     - `fieldCount<TableColumn>() == 19`;
>     - the next free `FormatVersion`.
> - **#6481** (faults table entries the device or guest memory cannot hold).
>   - **What it does:** checks each entry against the device's image limits and the registered guest allocations before resolving it, and lets Vulkan errors reach the draw.
>   - **How they compose:** the checks run where an entry is resolved. This PR's replay keeps a refused entry's fault while the table is current, and the guest allocation generation in the table state drops the table when the registry changes.
>   - **Conflicts:** `docs/dev/debt/libSceAgcDriver.md` only.
>   - **Bench (PM-038's load):** its checks cost 0.2–0.3 µs per entry, less than the 0.7–1.2 µs mapping check they replace. Table dispatches/s don't change beyond noise.
>
> **Disk cache format:** this PR, #6243, #6280, #6412 and #6488 each set `FormatVersion` 37 (main is 36). Whichever lands after the first needs the next number, and git won't flag it.
>
