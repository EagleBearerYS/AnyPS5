# BF-036: how far multi-threaded queue-0 draw recording can go (lavapipe, throwaway)

**Worker:** cloud-2.

**Machine:**
- 4 vCPU Intel Xeon @ 2.10GHz, 15 GB RAM, Linux 6.18.
- lavapipe from mesa-vulkan-drivers 25.2.8 (llvmpipe, LLVM 20.1.2, 256 bits), so the GPU work runs on the same 4 CPUs as the driver's threads.
- gcc 13.3.0, Release, CI Linux mirror flags. The harness and the tests run as `runner` with `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1`.

**Reading the numbers:**
- Run-to-run noise on this VM is about ±10%, so the tables give medians over windows and over interleaved runs, with the individual runs listed.
- lavapipe's `vkCmd*` cost is reported separately and is a lower bound for a desktop driver. The driver's own time carries over to a desktop driver unchanged.

## Answers first

1. **Recording on K threads, variant (a), is worth at most about 10% here,** and only when the committer is the bottleneck.
   - Of the committer's 118-128 µs per draw inside the GPU mutex, `vkCmd*` recording is only ≈ 4 µs (+ ≈ 2.5 µs of `vkUpdateDescriptorSets` and ≈ 5 µs per draw of per-batch `vkBeginCommandBuffer`). The rest is the driver's own resolution and bookkeeping.
   - Measured: −10% at K = 2, −5% at K = 4/8, +10% at K = 1 (shared layout, 5 runs).
   - With the textures watched (split layout), the queue worker becomes the bottleneck and (a) gains nothing measurable.
2. **Resolving before the lock, variant (b), is what shrinks the mutex.**
   - **Time inside the GPU mutex per draw:** 67.2 → 42.2 µs (split layout), 117.7-130.9 → 43.0 µs (shared layout). Medians of 170-300 windows; the matrix's 40-window runs give 68.5 → 40.7 and 128.3 → 35.8.
   - **Another thread** taking the mutex for 100 µs every 1 ms waits 87 → 55 µs (split) and 180 → 35 µs (shared) per acquisition.
   - **Recheck failures:** 0% alone; 3% (split) and 7.5-9% (shared) against that contender.
   - Queue 0's own µs per draw doesn't move: the work only moves out of the lock. (b) under (a) behaves like (b).
3. **The per-draw ceiling** is set by two serial stages, neither of them recording:
   - **the worker:** ≈ 95-105 µs CPU per draw, mostly capture + recompile + key/lookup of both stages on every draw;
   - **the committer's resolution:** ≈ 28 µs per draw when the fast proof holds, ≈ 82-89 µs when it doesn't.
4. **A harness finding that matters for titles:** a texture in the same allocation as a host-imported buffer is never write-watched on Linux. Revalidate then takes the full walk on every draw: 56-63 µs, `fast 0 / full 64146`.

## The harness

`tests/execution/DrawRecordCost.cpp` → `agc_driver_draw_record_cost`.

**What a submission is:** one queue-0 DCB of M direct draws, `DRAW_INDEX_AUTO`.
- **Pipeline:** one pipeline throughout.
- **Vertex shader:** 3 vertex buffers fetched through V#s from a table.
- **Pixel shader:**
  - samples 16 linear 4×8 textures (one S#);
  - multiplies by one frame CB (SRT) and one per-object CB (user data `s[4:7]`);
  - writes a resident, tiled (mode 0x1b) 64 KiB colour target.
- **What changes per draw:** only `SET_SH_REG 0x010..0x013`, the object CB's V#.

Every draw is "recorded": resident target, pipelined, template hit, continued pass.

**Plain run (ctest):** 16 draws must write byte 64.

**`--cost N` mode:**
- M = 64/512/2048, run warm.
- N timed windows of submit + `AgcDriverWaitIdle`.
- Per window it reports µs per draw, the worker's and the committer's CPU time (per-thread CPU clocks) and, under `APS5_PROFILE_DRAW`, the GPU mutex hold time per holder/site.

**Options:**

| switch | what it does |
|---|---|
| `DRAW_RECORD_COST_LAYOUT=split` (default) | textures, buffers and target in three allocations |
| `DRAW_RECORD_COST_LAYOUT=shared` | one allocation (the first version of the harness) |
| `DRAW_RECORD_COST_CONTEND=H:P` | a thread that takes the GPU mutex for H µs every P µs and reports its wait, standing for another queue's dispatches |
| `DRAW_RECORD_COST_SAMPLES=<file>` | 1 ms wall-clock stack samples of both threads (Linux), symbolized offline |

**Why the layout matters:**
- The driver host-imports the vertex and constant buffers. On Linux a host import takes its range off the write watch ("host imports resolve write protection: yes … imported ranges are compared": `GuestMemory::ImportWatched` → `Unwatch`, `GuestBufferMemory.cpp:1154-1173`, `:1260`).
- In the shared layout the 16 textures sit in that range. So `CollectWrites` returns 0, `fastRevalidate` fails with `FastFail::Collect`, and every draw takes the full walk.
- The run prints it, e.g. "write watch (split layout): … covers the textures 1, CollectWrites 12" against "(shared layout) … covers the textures 0, CollectWrites 0".
- **Split** is the common case for titles. **Shared** stands for draws that fail the fast proof every time, as Village's 1.35 ms per locked draw suggests.

**Destroying the commit closure costs the committer ≈ 18 µs per draw**, 12% of its samples.
- The closure holds `decode`, `stages`, `snapshots`, `recipe`, the programs, results, captures, `shaderMemory` and the draw-cache entries (Execution `Draw.cpp:582` on main).

### Amdahl

- **Queue 0 is a two-stage pipeline, and both stages are serial.**
- **MT recording can only take the `vkCmd*` part off the committer:** ≈ 4 µs, plus the cheaper per-batch primary.
  - At best that is a ≈ 10% gain in the shared case.
  - In the split case the committer isn't the bottleneck, so nothing.
- **To go further:**
  - make the resolution cheap or move it out (the split layout's fast proof already cuts `lookup` from ≈ 85 to ≈ 28 µs);
  - then take on the worker's per-draw capture + recompile + key/lookup (≈ 95-105 µs). That is the next ceiling, and no lock is involved in it.

## 2. What holds the GPU mutex per draw, and why

**Who holds it:** only the committer on this path, once per draw. It takes the mutex at `Driver::commitDraw` (`Execution/src/Driver/Draw/Draw.cpp:614-615`: `TagGpuLockSite(Draw)` + `lock_guard`) and holds it across all of `VulkanDevice::Draw` → `Graphics::Draw` (`Graphics/src/Draw.cpp:1917`).

**The worker** decodes, captures, recompiles and looks up without it: its hold is below 0.01 µs per draw, because `lockForDraw` (`Draw.cpp:593`) isn't taken for pipelined direct draws.

## 3. The prototypes

### (a) Recording on K threads into secondary command buffers: `APS5_MT_RECORD=K`

`Graphics/src/MtRecord.cpp`, with hooks in `Recorder.cpp`, `Pipeline.cpp` and `Draw.cpp`.

**The committer still prepares every draw serially under the GPU mutex:**
- resources, descriptor writes, `StartDrawPass`'s continue/hazard decision, Keep, the pass's barriers, push-constant assembly.
- For a direct draw that continues or opens a pass, it then builds a closure instead of recording. The closure holds the pipeline handle, a copy of the state, the sets, the push block and the VB/IB handles.

**Chunks:**
- Closures go into contiguous chunks of `APS5_MT_RECORD_CHUNK` draws (default ⌈64 / K⌉: a batch holds at most 64 draws, `APS5_BATCH_CAP`).
- A full chunk goes to recording thread `chunk mod K` right away. That thread records it into a secondary command buffer from its own `VkCommandPool`, with `RENDER_PASS_CONTINUE` and dynamic-rendering inheritance (formats and samples from the pipeline; legacy render pass + framebuffer otherwise). It holds no GPU mutex.

**The pass:**
- An MT pass is begun with `VK_RENDERING_CONTENTS_SECONDARY_COMMAND_BUFFERS_BIT` (or `VK_SUBPASS_CONTENTS_SECONDARY_COMMAND_BUFFERS`).
- `Recorder::endOpenRenderPass` dispatches the last chunk, waits for all of them, and runs `vkCmdExecuteCommands` in order.
- Command buffers go back to their thread's list when the batch retires.

**Draws that leave the MT path:** capture-inputs, indirect, mesh, stencil replay, split faces or channels, proxies, sample counting, and draws without bindings. Such a draw ends an MT pass and records inline.

**`APS5_MT_RECORD_RELEASE=1`** destroys the commit closure on a release thread instead of the committer.

**Correctness check:** at every K the 16-draw check still writes byte 64, and the counters confirm the path ran, e.g. "4 threads, 32784 draws recorded in 2152 secondary command buffers over 513 render passes".

### (b) Resolving before the mutex, rechecking under it: `APS5_PRERESOLVE=1`

1. **Before the lock.** `Driver::commitDraw` calls `VulkanDevice::PreResolveDraw` before `lock_guard(GpuMutex)`, for non-recipe draws. That runs the expensive half of `resolveDrawResources` without the mutex:
   - `DrawResourceKey` (ContentKey);
   - `SharedResourceCache().Find`;
   - `ShaderResources::Revalidate`.

   It keeps the key, the object and `GuestMemory::GpuHoldSerial()` from before it started.
2. **Under the lock,** `resolveDrawResources` takes that result only when two things hold:
   - `GpuHoldSerial()` is the start value + 1: only the committer's own outermost acquisition, so no other thread held the mutex in between;
   - `Find(key)` still returns the same object.

   Otherwise it resolves again as before. `MovedReadOnlyBuffers`, `CheckBufferAliases` and everything after them stay under the lock.
3. **Counters:** used, redone (another holder), not cached, revalidation failed, entry replaced, not used.

**Reading:**

**(a), recording on threads:**
- **Where it helps:** when the committer is the bottleneck. The best case is about −10% (K = 2). That is the ≈ 4-6 µs of `vkCmd*` plus a cheaper per-batch primary, moved off the committer.
- **K = 1 is slower:** the committer waits at every pass end for the whole pass to be recorded.
- **K ≥ 4 adds nothing.** On 4 vCPUs the recording threads compete with the worker, the committer and llvmpipe's rasterizer threads.
- **The mutex hold barely moves** (128 → 114). Everything that needs the mutex is still done before the closure is built.
- **In the split layout** the worker is the bottleneck, and every (a) row is within noise of main.

**(b), resolving before the lock:**
- **The mutex hold drops by** the resolution's share:
  - shared layout: −92 µs per draw, −72%, from the full walk;
  - split layout: −28 µs, −41%, from ContentKey + the fast proof.
- **Other queues gain directly:** the contender's wait per acquisition drops 1.6× (split) and 5× (shared).
- **The recheck redoes:**
  - 0% of draws alone;
  - 3% (split) and 7.5-9% (shared) against a 10%-duty contender. The coarse "nobody else held the mutex" test fails whenever the contender happens to take it during the unlocked window.
- **Queue 0's own µs per draw is unchanged within noise.** The committer does the same work and now runs part of it unlocked. Single-queue throughput gains only where the committer was waiting for the mutex.

**(b) under (a)** behaves like (b): the hold stays at ≈ 37-40 µs and the contender's wait at ≈ 28-44 µs. Queue-0 throughput stays within noise.

### What's unsafe as built

These are the work a real version must do.

#### (a), recording on threads

1. **Flush hooks.**
   - Every pass end goes through `endOpenRenderPass`, which finishes the run: `Commands` `Recorder.cpp:1367`, `StartDrawPass` `:1391`, `:1566`, `:1638`, `:1955` and `Submit` `:3296` on main. So a `FlushForAccess` → `SyncThrough` → `Submit` (`:1024`, `:1064`) stays ordered.
   - But it now **waits for recording threads while holding the GPU mutex**.
   - The worker's flush path releases the mutex around its wait (`:3651-3662`), so another thread can append to, or end, the same MT pass mid-hook.
   - A recording thread's Vulkan error surfaces at the pass end, attributed to the wrong draw, and leaves the primary inside a pass.
2. **Pending writes.**
   - A draw's GPU writes are noted when it is prepared (`MarkGpuWrites` `ShaderResources.cpp:4658-4682`; `noteDrawWriters`; `publishPendingWrites` `Recorder.cpp:2773-2822`), before it is recorded.
   - That is harmless only because nothing executes before Finish + Submit.
   - **"Noted ⇒ recorded in `open->commands`" no longer holds.** `NoteSampledDraw` is given the primary, and the sample-segment logic compares command buffer handles (`Recorder.cpp:1977`).
3. **Labels.**
   - Stores and deferred labels are recorded outside passes (`Commands()` ends the pass first), so they still land after the secondaries.
   - **Not checked:** the queued-label table (`labelTableMutex`, `Recorder.hpp:538`) and DrawPipeline label items (`DrawPipeline.hpp:43-57`).
   - With the release thread, a commit closure can outlive `Drain(Labels)`.
4. **The pipelined committer.**
   - A pass opened by the worker's locked draw (`lockForDraw`, `Draw.cpp:464-480`) can be continued or ended by the committer. Thread-locals that assume one recorder thread now span three kinds of threads: `DeferredBatches` `:341`, `TraceBatchTag`, the `Context::Function` counters, the Pipeline key storage.
   - **`APS5_MT_RECORD_RELEASE` destroys the closure after the item is popped.** So `DrawPipeline::Drain` (`DrawPipeline.cpp:160-175`) can return while a commit's ShaderMemory, snapshots and stages are still alive.
5. **Captured state.** Each closure copies `State` (allocations every draw) and binds a raw `Pipeline*`. It relies on `keepRecordedDraw` keeping the pipeline, framebuffer and VB/IB alive, and on descriptor sets not being rewritten before execution. Both hold today, but nothing enforces them.
6. **Teardown and platforms.**
   - Recording threads' pools are never destroyed (a leak and invalid usage at `vkDestroyDevice`), and the threads are detached.
   - Linux/lavapipe only. Windows was not built for this branch. The legacy-render-pass inheritance is written but never ran, because lavapipe takes dynamic rendering.

#### (b), resolving before the lock

1. **`Revalidate` runs without the mutex.**
   - In steady state it only reads.
   - **When something changed, it can mutate GPU-mutex state:**
     - `StorageTexture::Refresh` uploads;
     - `CompletePendingCpuWrites`;
     - `StorageTexture::FlushPending` records into the batch;
     - `refreshOwnObjects`;
     - `captureValidation`.
   - **Two failure modes:**
     - another thread holding the mutex meanwhile (the worker's reap or locked draw, another queue) is a data race that the serial check detects only after the fact;
     - Recorder calls outside the lock assert only under `APS5_ASSERT_GPU_LOCK`.
2. **The fix is the refuse-and-retry shape** fable-void's `0a54c54654` uses for host imports. A scope flag, set while resolving outside the lock, makes every mutating path refuse: leave the state as found and report "needs the lock". The resolution is then redone under the mutex. On top of that, objects looked up unlocked need an epoch-style keep-alive (his "retired sets").
3. **The recheck is coarse.**
   - Any other mutex holder, even an unrelated dispatch, forces a redo: 3-9% here.
   - Guest CPU writes in the window aren't rechecked. They race on main too, but (b) reads the stamps earlier.
   - The exact recheck is listed in the state map below.
4. **Coverage:** only the committer pre-resolves. The worker's locked draws and recipe draws don't.

## What it would take to go further

1. **Make (b) exact and safe:**
   - refuse-and-retry for every mutating path in the unlocked resolution;
   - a per-object recheck (the (b)-recheck rows above) instead of "nobody else held the mutex", so other queues' unrelated dispatches stop forcing redos (3-9% here).
   - In Village that frees most of queue 0's 1.35 ms per locked draw for queue 0x20.
2. **Make the fast proof hold** where textures share an allocation with imported buffers (the shared layout). Watch the texture sub-ranges of such an allocation, or prove them by the import's compare. That takes ≈ 56-63 µs off every draw there, inside or outside the lock.
3. **Then attack the worker:** ≈ 95-105 µs per draw, no lock involved. Both stages are re-captured on every draw although only user data changed: capture 40-77, recompile 31-38, key/lookup 20-26.
4. **Recording on threads comes last.** On a desktop driver its share grows with the driver's `vkCmd*` cost. The −10% here is lavapipe's floor, and it pays only when the committer is the bottleneck.
