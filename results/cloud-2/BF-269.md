# BF-269: generation 0 at `StorageTexture::markLayersPending` (PPSA02225 report)

Worker cloud-2, Linux, lavapipe (llvmpipe, LLVM 20.1.2), gcc, CI flags (`-G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON -DANYPS5_ENABLE_SPIRV_TOOLS=ON`).
Base: upstream/main 4c7d275bef. Head: fork `fix/agc-pending-layer-generation` 87b51a63b9 (one commit on 4c7d275bef).

## Verdict

- The state is real: a layer pending at generation 0 over memory that still reads as write-watched. Its cause is a page walk that fails while the range stays watched.
- The loss the reporter saw is reproduced on main (red, 10 of 10). The gen-0 unit is not what gets lost. The units that lose their GPU results are the ones *with* a valid generation: the failed walk reports the rest of its range as written by the CPU, and the drop rule (or the keep-blocks rule) hands those blocks to the CPU.
- The reporter's fix (stamp `collectedLayerGeneration(layer, CollectWrites())` at the mark) does not fix the red, and it adds a new loss: a CPU store between the refresh and the pending mark is hidden, and the image keeps the stale texel.
- The fix on the branch treats a surface whose own collect fails as untracked in the refresh and the write-back, so the existing compare against the saved bytes decides. Green 10 of 10; all four controls pass.

## 1. Paths that leave generation 0 for a watched range

Every generation stamp takes a `CollectWrites` result (or a per-layer collect through `collectedLayerGeneration`, Texture.cpp:3811-3816, which collects each layer when the whole-surface value is 0). So a layer is at 0 exactly when the collect of its range returned 0 at its last stamp:

| Stamp site (Texture.cpp) | Value |
|---|---|
| constructor `layerGeneration.assign(trackedLayers, 0)` :1458, then `Create` → `upload` ("first") :1416 → `stampLayers` :2687 with `now = CollectWrites(...)` :2677 | collect of the surface, else of each layer |
| refresh, unchanged :2364, unstamped block units :2284, borrowed units :2458 (`currentFor`, :2217-2220) | `CollectWrites` of the surface :2211, else per layer |
| write-back `settle` :6103 | collect of the stored span, else per layer |
| DCC key fill :5305, fills :5459, :5467, :5591, :5618, adjacent advance :5683, :5794 | the fill's collect |

`CollectWrites` returns 0 (GuestMemory.cpp `collectWrites` :1568) in two cases:

- **Unwatched (:1603).** The range is not watched or not covered. `Watched()` (:1929) is false as well, and `markLayersPending` saves the guest bytes (Texture.cpp:3862). This is not the reported state.
- **Incomplete walk (:1624, `if (!walkWrites(...)) return 0`).** The tracker still covers the range, so `Watched()` stays true. This is the reported state:
  - **Linux:** `GuestWriteWatch::Collect` (libc GuestWriteWatch.cpp:101) fails in `takeFresh` (:106, `protect` failure :167) or in `scanWritten` (:195-197, a failing `PAGEMAP_SCAN`). Both report the rest of the range as written (`written(context, cursor, end)`), and the caller stamps it as CPU stores (`stampWrittenRun` GuestMemory.cpp:1471, called with `StampKind::Cpu` from :1624). Reached in the test by remapping one watched page with `mmap(MAP_FIXED)`, which leaves the uffd registration behind while `Watch::_ranges` still covers it. I found no production Linux path that does this: libkernel unregisters or registers around its own maps (DirectMemory.cpp:631-643, :784, :810, :979, :1165).
  - **Windows:** `collectWindowsWrites` fails (GuestMemory.cpp:1554), then `noteRefusedWalk` (:1532-1547, :1563) stamps the pages the arena reports as unreported and records the refused blocks. Not runnable here.
- **Host imports:** with imports on, lavapipe's import takes the range off the watch ("imported ranges are compared"), so the state is not reached; with `APS5_NO_HOST_IMPORT=1` it is. The reporter's `APS5_HOST_IMPORT_MIB=0` is not "imports off": 0 means the default budget (GuestBufferMemory.cpp:1725-1736). `APS5_WORKING_SET_MIB` is read on Windows only (VulkanDevice.cpp:1576).

At the mark (Texture.cpp:3844-3862), `unsaved` needs generation 0, and the capture runs only when `!Watched(...)`. So a layer whose walk failed becomes pending at 0 with nothing saved and nothing stamped. In the test, only unit 3 (the remapped page) is at 0; units 0-2 keep their generations (trace: `units 11 12 13 0`), and the surface's `generation` (the minimum) reads 0.

## 2. The refresh branch it takes

256x256 R32_UINT, 64 KiB block units (4 units), result in unit 0:

1. `current = CollectWrites(surface)` (:2211) fails, and the failed walk stamps every block as CPU-written.
2. Block-unit branch (:2277-2290): `UnchangedSince(surface, generation = 0)` is false, so `scanBlocks` runs. `ChangedBlocks` reports tracked; units 0-2 read `BlockWritten` after their generations, and unit 3 reads `BlockWritten` because its generation is 0.
3. Loop (:2418-2441): every pending unit has changed, so `pendingResults` is set. `droppable` (:2393-2401) is true for units 0-2 (tracked, generation ≠ 0, stamped, whole 64 KiB) and false for unit 3 (generation 0). Trace: `drop-unit unit=0 generation=11 stamped=1`, then units 1 and 2.
4. The line is printed (:2445). `writeBackLayers` stores unit 3 only (:2447), then `upload(&changed)` (:2462) re-reads units 0-2 from guest memory (`reason=cpu`), and the GPU results are gone.

In the layer model (no block units) the same stamps make `writeBackLayers` skip those blocks as CPU-written (:6036-6046), with the same loss (from the code; the test covers block units). The upload cannot read memory before a write-back lands: the CPU path waits (`batch.SubmitAndWait()` :6386), and `ReadCommitted` flushes pending GPU writes (GuestMemory.cpp:2758-2764). Nothing is stored for those blocks in the first place.

## 4. Is the reporter's fix correct?

No.

- **It does not reach the loss (cases 1-2).** At the mark, the whole-surface `CollectWrites` fails, and the per-layer collects restamp units 0-2 (`units 15 15 15 0`). The refresh's own failing walk then stamps them newer again, so they are still dropped (6 `drop-unit` lines, unchanged from main). Unit 3 stays at 0.
- **It hides CPU stores (case 3).** Stamping at the mark declares the layer current with memory as of the mark. A CPU store between the refresh and the mark is collected into that stamp, the next refresh reads "unchanged", and the image keeps the stale texel. A later GPU read sees the stale value.
  - On Linux the CPU write-back is diff-based (`WriteChangedCommitted` against `original`, :6408), so guest memory keeps the word.
  - An import write-back copies whole stored ranges into the import (:6239) and would overwrite it (from the code, not run).
- **Partial GPU writes.** A scissored draw or an 8-texel dispatch writes part of a layer, and the stamp claims all of it. That holds only if the image was current before the write, and a layer at 0 was never shown to be current. Over a failed walk the stamp is 0 anyway (unit 3).
- **Stamping only fully covered current layers** would not help: the lost units already have valid generations.
- **Capturing the guest bytes at the mark (as #7048 does)** gives the gen-0 unit a baseline, but leaves units 0-2 to the false stamps.

## 5. The fix (87b51a63b9)

`Texture.cpp`, 8 lines:

- **`refresh` `scanBlocks`:** `tracked = current != 0 && ChangedBlocks(...)`. When the surface's own collect failed, the blocks read as unknown, with the same fill `ChangedBlocks` gives untracked memory, and the existing compare against `original` (`compareUntracked`) decides which blocks the CPU changed.
- **`writeBackLayers`:** `walked = CollectWritesUncached(span) != 0`, and `tracked = walked && ChangedBlocks(...)`, so the existing untracked path compares the saved layers and stores the rest.

No stamp is added at the mark. The debt entry in `docs/dev/debt/libSceAgcDriver.md`, under Functional, records what stays open:

- a unit with no saved bytes over a failed walk is handled as outside the watch, so storing it throws;
- a failed walk of a *larger* range stamps the blocks of a surface whose own collect succeeds, and those still read as CPU stores.
