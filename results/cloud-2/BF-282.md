# BF-282: what Village's `Driver.Packet.memory_wait` waits on, and what to cut instead

Worker cloud-2.
- **Code:** read at upstream main **bb04a4f1ea**.
- **Traces:** the three public timing traces (A, B #12745, B #12921), analysed with `tools/trace_digest.py` from main plus scratch scripts, which are not committed.
- **No code change, no PR, nothing upstream.**

## Answer first

**`memory_wait` is not on the frame's critical path.**
- Nearly all of it (2.5-2.6 s per presented frame) is on the async compute workers 0x20 and 0x28.
- Their long waits start early in the frame and end late in it. All that time, queue worker 0x0 works without a break.
- Queue 0 itself waits on memory for only 0.6-1.5 ms per frame.
- Worker 0x38's `dequeue_order` (1.41-1.46 s/frame) is the same shape: a wait-free submission held until queue 0 has passed it in submission order. 0x38 then does 1-4 ms of work.
- Making every one of these waits zero would leave the frame where it is.

**The frame is one serial chain on queue worker 0x0.** In all three traces queue 0 is 98-99 % busy over 1.50-1.59 s frames: it does its own CPU work, or it is blocked on the draw committer, the GPU mutex or the GPU.
- **Own work:** 865-917 ms/frame.
- **Blocked:** 666-672 ms/frame, of which:
  - 470-510 ms on the draw committer: the GPU mutex for inline draws, room in the draw pipeline, the hook lock and drains;
  - 104-127 ms on the GPU mutex for dispatches, held mostly by worker 0x20;
  - 40-50 ms on GPU fences.
- **The GPU** is busy 15-16 % of the time.

So the levers are:
- the work done under the **GPU mutex**: the committer commits each draw under it (`Draw.cpp:1283`), about 700 ms/frame;
- the **inline draws** queue 0 still records under that lock;
- the **GPU syncs** taken while holding it.

They are ranked under Ranked candidates below.

## 1. The wait mechanism

**The phase.** `Driver.Packet` is a `PerformanceTimer` per packet (`Execution/src/Driver/Packets/PacketExecution.cpp:276`).
- Its last mark is `memory_wait` for PM4 opcodes 0x3c and 0x93 (`:565`). The code names these WAIT_REG_MEM and WAIT_REG_MEM_64 in its stall message (`WaitMemory.cpp`).
- The segment runs from the `prepare_memory` mark (`:367`) to the end of `waitMemory(...)` (`:457`).
- On queue 0, two early exits leave the packet before any mark, so they are not counted: a value a pipelined label will store (`:283-292`) and a wait already satisfied at entry (`:293-299`).

**`Driver::waitMemory`** (`Execution/src/Driver/Synchronization/WaitMemory.cpp:108`) runs on the waiting queue's own worker thread. In order:
1. **Satisfied at entry** (`:143`), **or held at submit** (`:148`): return.
2. **`storedSince`** (`:149`): the driver's label history holds a store, made after this submission entered the driver, with a value the compare accepts. The wait passes when another queue's label packet is *executed or recorded on the CPU*; it does not wait for that label's GPU completion.
   - If another queue stored it, the wait is noted (`notePendingWait`) and landed later, before a guest read (`landPendingWaits`, `:79-106`).
3. **The recorder's label table**, unlocked first (`LookupLabel`, `:205`), then under the GPU mutex (`PendingLabel`, `:228`): a label recorded into an open or submitted batch with the right value releases the wait at once. Here too it is the recording that counts, not the GPU completion.
4. **The poll loop** (`:344`):
   - it spins with `_mm_pause` for 1.5 ms on queue 0 or 100 µs elsewhere (`:339`), then sleeps 200 µs per poll (`PollSleep`, `:356`);
   - every poll re-checks memory and `storedSince`;
   - `pollService` (`:243-326`) repeats the table lookup when the write generation moves, `try_lock`s the GPU mutex (`:266`) to submit the open batch when it writes the awaited range, and reaps completed batches (`ReapRecorded`, `:317`), whose completion actions store CPU-side completion labels.

**So what releases a wait** is a CPU action:
- another queue's label packet executed on that queue's worker (`noteLabelStore`, `PacketExecution.cpp:559`);
- a queued label the draw committer stores;
- a batch's completion labels stored when someone reaps it;
- a guest CPU store.

The waiting worker notices it on its own next poll. A GPU completion releases a wait only through a reap (step 4), and the waiter's own poll can do that reap.

**`dequeue_order`** is the mark in the worker loop (`Queues/QueueWorker.cpp:276`):
- **A queue 0 submission** waits while a wait-free submission of another queue that arrived earlier is unfinished (`waitFreeBefore`, `Queues/Submission.cpp:542`; `QueueWorker.cpp:256`).
- **A wait-free submission of another queue** waits until queue 0 has no earlier submission left (`orderReleased`, `Submission.cpp:554`; `QueueWorker.cpp:269`). A submission is wait-free when it has no WAIT_REG_MEM, flip or rendering wait (`waitFree`, `Submission.cpp:520`).
- **The exceptions:** it also runs when queue 0 is blocked on a label that this queue will write, or when everything is idle.
- 0x38's waits are this second case: "order behind queue 0 for event".

**How the long waits end:**
- **Not on GPU completions.** No 0x20 release, and only about a fifth of 0x28's, has a GPU batch ending within 0.5 ms before it.
- **On queue 0's CPU progress.** The releases come when queue 0, or the committer working through queue 0's items, reaches the label packets near the end of its frame work. That fits steps 2-3 above.
- **0x28's short frame-start waits** end within 1 ms of a queue 0 `Recorder.Submit` about 40 % of the time.
- **Queue 0 is never idle** during these waits. The rest of its time is blocked on the committer, the mutex or the GPU (below), not on 0x20 or 0x28.

## 3. The chain

The frame is **one serial chain on queue worker 0x0**, not a chain across 0x0, 0x20, 0x28 and 0x38. Queue 0 never waits for the async queues' labels, and 0x20, 0x28 and 0x38 wait for queue 0. The two places another thread enters queue 0's critical path are:
- **the draw committer**, through the GPU mutex and the draw pipeline's room;
- **0x20**, whose dispatches hold the GPU mutex queue 0's dispatches need.

### The cheap, safe one

**Candidate 2's core is one predicate at `Graphics/src/ShaderResources.cpp:3423`** in `CompletePendingCpuWrites`. Main syncs the recorder through the range (`SyncThrough`, counted as sync reason 4) whenever any completion is pending and **any** pending label lies in the range, including labels the GPU stores in stream order. Waiting only for labels the CPU stores at completion (`CompletionLabelIn`, which `VulkanDevice` already uses) keeps the GPU-ordered ones ordered by the stream.

That is exactly #9858 (older) and #11847 (with a test). Both are clean against main and with each other, so take one of them and close the other.

**Before claiming a speed-up,** measure Village with `APS5_PROFILE_DRAW=1`. Its `[recorder]` line splits the syncs by source and top site; reason 4 shows how much of the 150-175 ms is this sync. Then compare `tools/trace_digest.py` summaries of main and the change, from the same machine and scene.

**Candidate 1 is the biggest single lever** and already exists as #1896's `APS5_PIPELINE_INDIRECT` switch. A Village A/B with it set is the next measurement I'd ask for.

## Method notes

- **Busy and blocked** come from self-time segments per thread. Waits are the slices named in the tables; everything else counts as work.
- **Thread overlap** is the clipped intersection of the other thread's segments with queue 0's blocked intervals.
- **GPU busy** is the union of `batch` ranges.
- **Folding:** the trace folds slices under 20 µs, so queue 0's "untraced" time includes that folded work. In B #12921 it is 97 ms/frame against 13-14 ms in the other two.
- **Lock holders:** the trace has no lock-holder events. "Committer busy 99 % during queue 0's draw-lock waits" is inferred, not observed. The code shows the committer holds the GPU mutex for every commit (`Draw.cpp:1283`).
- **Console behaviour:** I make no claim about it. Everything above is about the emulator's own code and these traces.
