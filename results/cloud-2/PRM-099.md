## 3. Does #13648's GPU clear compose with #7642's device table?

**`LookupDeviceTableTexture` → `cachedTexture`:**
- A cleared texture comes back only when the DCC keys say "full clear" (`IsDccClear(keys) && keys != ClearRegister`), with no depth compare and a plain colour format (`SampledClearColor`).
- The texture is made by the same `Texture(context, detiler, ...)` constructor with `clear != nullptr`:
  - the image goes `UNDEFINED → TRANSFER_DST`, then `vkCmdClearColorImage`, then `TRANSFER_DST → SHADER_READ_ONLY_OPTIMAL` over all mips and layers;
  - the views (`view`, `FirstLayerView`) are created after the clear/upload branch in both cases.
- So a cleared texture served through the device table has:
  - a valid `View()` and `FirstLayerView()`;
  - `Layout()` = `SHADER_READ_ONLY_OPTIMAL`, the `layout` member's default (`Texture.hpp:154`) and the same as an uploaded texture;
  - `CopyKind()` = `PerUseCopy::None`, the default that the clear path never changes. It is not depth, so `LookupDeviceTableTexture`'s refusals don't apply.

**`DeviceTableTextureCurrent`:**
- A cleared entry has empty `bytes` and its DCC-clear `keys`, so `it->keys != DccKeys::Uncompressed` (line 5696) returns false.
- `DeviceImageTable.cpp:498` then marks the entry stale on an untracked epoch move, and it is looked up again through `cachedTexture`, which checks the keys again.
- **This is the intended outcome.** It is the same handling every DCC-keyed entry already had before #13648. The keys check is also what keeps the empty `bytes` from comparing "equal" (`EqualsCommitted(address, {})` would be true).
- With tracked memory (`entry.generation != 0`), freshness comes from `UnchangedSince` over the surface range, as it did for DCC snapshot entries before. #13648 does not change that path.

No behaviour decision was needed.
