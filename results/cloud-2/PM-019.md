> 1. **Indirect expands throw (blocking).** Village issues the expand as an indirect draw (DRAW_INDIRECT or DRAW_INDEX_INDIRECT), so the run stops about 18 s into boot with "indirect DB expands are unsupported" (`DrawPrecheck.cpp:27`). My `BufferReadAfterExpand` passes here, but it reads 4 KiB V# windows in single-group dispatches. It does not reproduce Village's dispatch (8160 groups, the whole plane through V#s), so my "GPU buffer reads flush first" holds only for the path that test takes.

## Findings, ranked

### Blocking

None.

### Should-fix

1. **The debt entry leaves out four limitations** (`docs/dev/debt/libSceAgcDriver.md:9`). Each is either refused with a clear message or does not matter to Village's use (it samples the copy as R32F), but CONTRIBUTING asks for known gaps to be recorded.
   - **Integer views of the copy throw.** A 32-bit integer ("depth bits", e.g. R32_UINT) view of the write base throws the existing "32-bit integer read of the depth-layout texture …, which is no depth surface drawn with, is not implemented" (`Graphics/src/ShaderResources.cpp:541`). I hit it with an R32_UINT read in my first version of the end-to-end test. The rule predates the fix and fires on main too. The copy is served only to float R32 views and to raw buffer and CPU reads.
   - **The whole plane is copied.** Only the viewport and scissor are checked (`Graphics/src/State.cpp:1352-1369`), not what the draw's primitive covers. A partial-coverage expand would overwrite texels the console leaves alone.
   - **The expand's pixel shader never runs.** Any memory writes it makes are lost (the decoder does not look at the shader).
   - **A later depth target at the write base does not see the copy.** A depth surface created there starts from its own image, because `takePlanes` moves planes only between depth surfaces. Once the write base is a live depth surface, the next expand into it throws "into a live depth surface" (`Graphics/src/DepthSurface.cpp:992`). The Village run should show the expand line every frame and never this error.
2. **Per-frame cost: each expand copies the whole plane twice and is never skipped.** `RunDepthExpandPass` → `DepthSurface::CopyDepthTo` → `copyPlane` (`Graphics/src/DepthSurface.cpp:237`, `:281-301`) copies depth image → staging buffer → R32F image. That is 2 × 15.8 MiB of image data with three global barriers, two of them ALL_COMMANDS-wide, on every expand, even when nothing changed since the last one. See **Cost** for numbers.
   - **Skip unchanged copies.** Skip the copy when the source surface's `written` serial and the destination image are the ones of the previous expand to that destination; the serial is bumped whenever a draw binds the surface. This needs the four Village draws identified first; GAC-002 open question 1 asks the same.
   - **Halve the traffic.** A one-pass shader copy, or a depth→color image copy where `VK_KHR_maintenance8` is present, would halve it.

### Nits

3. **The device-wide refusal check.** `DepthSurfaceAt(std::uint64_t)` (`Graphics/src/DepthSurface.cpp:980`), used for that refusal (`:992`), scans the surfaces of every Vulkan device. The owner lookup two lines further down is per device (`depthOwners().find({context.device, …})`). A stale surface of another device at the write base would refuse a valid expand. Games run one device, so the impact is low.
4. **A wasted first upload.** The first expand into a write base, or the first after the image is evicted, makes its storage image through `CachedStorageSurface` (`Graphics/src/DepthSurface.cpp:1005` → `ShaderResources.cpp:912`). That flushes, detiles and uploads 15.9 MiB of guest bytes, which the copy then overwrites entirely. On lavapipe the first expand took 35–37 ms against 3–4 ms later. It happens once per image lifetime.
5. **A refusal message that is broader than needed.** A read-only stencil plane (DB_DEPTH_VIEW bit 25) together with a moving depth plane throws "of a depth view with a base slice, a mip level or a read-only plane" (`State.cpp:1350`). That is conservative and fine, though the stencil plane would not move.

## Review questions

### Correctness of the decode change (`Graphics/src/State.cpp:1317-1382`)

**Which combinations take the new path.** A draw enters only when both hold (`:1321`, `:1333-1335`):
- `DB_RENDER_CONTROL & 0x60` is non-zero;
- the depth plane moves (format valid, `Z_READ_ONLY` clear, `DB_Z_WRITE_BASE` != `DB_Z_READ_BASE`), or the stencil plane moves (format valid, `STENCIL_READ_ONLY` clear, stencil write base != stencil read base).

Of those draws, exactly one shape returns a pass:
- `DEPTH_COMPRESS_DISABLE` set, and no `DB_RENDER_CONTROL` bits besides 0x60 and 0x2000;
- no stencil, Z, Z-write or bounds enables and no color-on-depth bits (`DB_DEPTH_CONTROL & 0xc000000f`);
- no color writes;
- Z_32_FLOAT, NUM_SAMPLES 0, SW_64KB_Z_X, no PRT or MAXMIP, `DB_DEPTH_VIEW` 0;
- 64 KiB-aligned bases, no window offset and VTE 0x43f;
- a viewport and scissor covering `DB_DEPTH_SIZE_XY`;
- a stencil plane, if any, expanded in place.

**Every other entering combination throws** with one of 12 reasons. Four sources pin this:
- the fix's `depthExpandPassTests`;
- my additions:
  - Z_16 and Z_24 with and without stencil;
  - SW_64KB_Z, SW_4KB_Z_X, SW_64KB_R_X and SW_VAR_Z_X;
  - a stencil plane that moves while the depth stays in place;
- the precheck refuses indirect expands (`Execution/src/Driver/Draw/DrawPrecheck.cpp:27`);
- `RunDepthExpandPass` refuses a write base that is a live depth surface, a missing read surface, and a read surface of another extent, format or sample count (`Graphics/src/DepthSurface.cpp:992-1013`).

**Ordinary always-pass draws are not misrouted.**
- **Equal bases.** `depthMoves` is false, so the decoder returns `std::nullopt` before any check and the draw takes the normal path, whatever `DB_RENDER_CONTROL` and `DB_DEPTH_CONTROL` say.
- **No depth or stencil target.** Neither plane can move, so the decoder returns `std::nullopt`.
- **Pinned at decode level:** `DB_DEPTH_CONTROL` 0x76 with and without 0x60, no planes, and a read-only stencil with another stencil write base.
- **Pinned end to end:** `InPlaceUnchanged` and `AlwaysPassEqualBases` pass on both main and the fix.

**Behaviour change against main (narrow).** Main's `DepthMaintenanceRejection` (`State.cpp:728-736`) accepts the 0x2063 bits. So an out-of-place draw with compress-disable plus clear or resummarize bits used to be drawn, or refused as depth read and written at different addresses. It now throws the expand message. Throwing with a reason is the project's rule.

### Stencil

- **Stencil bases differ:** throws "of the stencil plane", whether the depth moves too (the fix's test) or stays in place (my decode test).
- **Stencil present with equal bases:** it is left alone. `StencilKept` draws stencil 0x5a with the depth, then expands with the game's registers. Afterwards:
  - all 15360 stencil texels still read 0x5a through an R8_UINT view;
  - the read base, stencil and HTILE guest bytes are byte-identical to before the expand;
  - the write base holds the depth.
- **No stencil plane:** `DepthOnlySurface` expands a D32_SFLOAT surface correctly. This branch of `RunDepthExpandPass` was not covered before.

### HTILE and compression

- **The write base.** It becomes a plain R32F `SW_64KB_Z_X` storage image, with no HTILE and no compression state. On a flush it reaches guest memory uncompressed, in the Z swizzle. Raw CPU reads and GPU buffer loads detile to exactly the read surface's depth. That is what `DEPTH_COMPRESS_DISABLE` implies.
- **The read surface.** It is unchanged: its depth reads back identical after the expand, and its HTILE guest bytes are untouched.
- **HTILE itself** is not modeled, as the debt entry says.
- **The one HTILE-adjacent gap** is the later depth target at the write base (should-fix 1, fourth item).

### Formats and modes

| Case | What happens |
|---|---|
| Z_32_FLOAT, SW_64KB_Z_X, 1 sample, with or without stencil | Correct, end to end |
| Z_16, Z_24 (with or without stencil) | Refused: "of a depth plane other than Z_32_FLOAT" |
| SW_64KB_Z, SW_4KB_Z_X, SW_64KB_R_X, SW_VAR_Z_X, linear | Refused: "in a swizzle mode other than SW_64KB_Z_X" |
| Multisampled depth (NUM_SAMPLES ≠ 0) | Refused: "of a multisampled depth surface" |
| 2 raster samples over a 1-sample surface (the game) | Taken; the sample count is not checked (in the debt entry) |
| A 32-bit integer view of the copy afterwards | Refused by the existing depth-layout rule (should-fix 1) |

Nothing in this list is silently wrong.

### Ordering

- **The copy is ordered after earlier work.** It is recorded under the GPU mutex at the draw's place in the stream, after the packet's labels (`DrawPrecheck.cpp:26-35`). `Recorder::Commands()` ends any open render pass, with its trailing barrier, before `copyPlane` records. `copyPlane` waits for all earlier work (ALL_COMMANDS → TRANSFER).
- **Later work is ordered after the copy.** `copyPlane` ends with a TRANSFER → ALL_COMMANDS barrier carrying MEMORY_READ|WRITE. GAC-002's synchronization-validation run found no hazards.
- **GPU texture reads** find the pending image. This is checked after one expand, after a second expand of changed depth (`ExpandedAgain`), and for two write bases filled in one submission (`TwoDestinations`).
- **GPU buffer reads** flush the image first. `BufferReadAfterExpand` reads the write base with `buffer_load_dword` right after the expand, before any CPU flush, and gets all 15360 texels right.
- **CPU reads through `GuestMemory`** flush it, as the fix's test shows.
- **Title CPU loads that bypass `GuestMemory`** see the bytes only after a flush (`APS5_STORE_AT_LABEL`, `APS5_STORE_AT_FLIP`). That holds for every GPU-written storage image, so the fix adds no new gap.

### Cost (1920x2160, Z32)

- **Size.** The plane is 16,711,680 guest bytes (15.94 MiB: 15 × 17 blocks of 64 KiB) and 15.8 MiB of image data.
- **Per expand:**
  - two transfer copies of the plane, through the per-surface staging buffer: about 31.6 MiB copied, about 63 MiB of memory traffic;
  - three barriers, two of which drain the pipeline;
  - a map lookup and a decode on the CPU.
- **Village's 4 per frame:**
  - about 127 MiB copied and about 253 MiB of traffic per frame, about 15 GB/s at 60 fps;
  - estimated GPU time per frame: about 0.6 ms at 400 GB/s, about 1.3 ms at 200 GB/s, about 4 ms on a 60 GB/s iGPU, plus four drains.
- **Measured on lavapipe** (this VM, 4 vCPUs, CPU Vulkan; an upper bound) with a scratch timing harness on the fix:

| | Time |
|---|---|
| A baseline submission without a draw | 0.05 ms |
| The 1920x2160 depth draw | 10 ms |
| First expand into a write base (storage image created and uploaded) | 35–37 ms |
| Each later expand | 3.0–4.2 ms; 12–15 ms for four |
| A 1024-texel texture read of the write base after an expand | ~10 ms (2.4 ms for the same read of the depth surface itself), so one more plane copy per sampled use |
| A flush of the write base (write-back of 15.94 MiB) | ~40 ms (197 ms the first time) |

- **The real per-frame cost depends on the PC's path.** With host-imported memory a sampled view can use the storage image directly. Without it, a raw read means a readback, a CPU copy and a wait. GAC-002 open question 2 says the same, and the Village run's frame times will settle it.
