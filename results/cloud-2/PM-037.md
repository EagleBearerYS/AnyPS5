## 1. PM-028 v2: perf/shader-image-table-unwritten-reuse-v2 @ 142bdd55a9

### Verdict
**Don't open v2 as it is.**
- **Speed:** PM-038 (from the Village PC run) found that the HIT path costs +58% of `capture_resources` per draw against cut #3. That is a speed result, not a correctness one, and v3 (PM-038, cloud-3) is the replacement.
- **Correctness:** the vouching rules are exact except for the write-tracker holes below. The one that matters (gap 1) is in GuestMemory, not in PM-028. It breaks the premise that v2, v3 and #6060's compare-free vouch for Windows imports all rest on: every GPU write into an import stamps the blocks it wrote. The follow-up fixes it at the source.

### What the reuse relies on
`ShaderMemory::stampWrites` (ShaderMemory.cpp:271-282) takes a generation:
1. it refuses a range a page fetch already touched;
2. it refuses a range with a pending write;
3. it runs `FlushGpuWrites`;
4. it calls `CollectWrites`.

`unchangedSince` (ShaderMemory.cpp:284-291) vouches when all of these hold:
- no pending write;
- `FlushGpuWrites`;
- `CollectWrites != 0`;
- `GuestMemory::UnchangedSince(range, generation)`;
- the same allocation layout.

So a GPU write into an imported range must:
- stamp the blocks it writes (`MarkWritten`);
- be noted pending from record time until it lands.

### Gaps

**1. MEDIUM: a store over a partly watched range stamps no block. Fixed by the follow-up.**
- *What happens:* `MarkWritten` and `storeOwn` only note the store as unstamped. That note is read by `NewestStamp`, not by `UnchangedSince`, `StoredOver` or `WrittenSince`. So the watched blocks the store wrote keep their old stamps and read as unchanged.
- *When it happens:* whenever a GPU write range crosses from watched memory into an unwatched import:
  - on Windows, for every import (`decideImportWatch`, GuestBufferMemory.cpp:642-649);
  - on Linux, after `APS5_WRITE_WATCH_IMPORTS=unwatch` or a probe verdict (:659-672).
- *Under PM-028:* a stale column is reused.
- *Under #6060:* the compare-free vouch for Windows private imports (GAC-019, relayed in PM-038) breaks in the same way.
- *Second effect:* `StorageTexture::blocksKept` (Texture.cpp:3607-3626) and `StorageTexture::evictStale` (:3680-3725) can't see such a store either, so a write-back can land over newer driver bytes.

**2. LOW: two write paths stamp before they note the write pending.**
- *Where:* VulkanDevice.cpp:2029→2032 and :2490→2494.
- *Why it races:*
  - draw preparation runs without the GPU mutex by default (Draw.cpp:42-60; `APS5_LOCKED_DRAW_PREPARE` is opt-in);
  - `stampWrites` queries pending writes before it takes its generation (ShaderMemory.cpp:276-279).
- *Effect:* a capture on another queue worker that runs between the two steps vouches the pre-store bytes at a post-store generation. Once the batch is reaped nothing stamps again, so the stale column is reused until the next write.
- *Why LOW:* it needs a cross-queue reader without a wait, which is a title race on hardware too, though only a transient one there.
- *Fix:*
  1. note before stamping in both paths;
  2. in `stampWrites`, take the generation before the pending query.
- *Not built:* both paths are shared by every write-tracker user, and the CopyBuffer order is deliberate. The owner needs to decide, and the fix needs a two-thread test.

**3. LOW: BDA stores are stamped only at reap.**
- *Where:* `markWrittenPages`, BdaResources.cpp:307-329. They are never noted pending.
- *Why LOW:* main also reads such tables at record time, so PM-028 adds only the window between GPU completion and the reap.

**4. INFO: some columns are never vouched.**
- A column on a page that ShaderMemory already fetched in the same capture (ShaderMemory.cpp:274-275).
- Pointer-indirect columns (`!column.address`, ResourceMaterializer.cpp:738) and narrowed columns (:737) are never memoized.

## 3. Copy-cap: fix/agc-address-build-copy-cap @ 5ee93b98ad

Commits: 25c333e47, b8cf1b510, 74640d655, 5ee93b98a, on 6239ceffc. GBM below means GuestBufferMemory.cpp at 5ee93b98ad. The relevant files are unchanged between 6239ceffc and main d92a8dad3.

### Verdict
**Ready for its scope.** The fix covers the two causes it names:
- A range whose first import the budget refused, and whose copy would pass the cap, now evicts idle imports and retries instead of copying (GBM:2676-2685; FATAL at :2700-2704).
- A heap mirror whose range left the write watch is planned again (`heapMirrorWatched`, GBM:1704-1710, used at :1737 and :2566).

### Root cause and siblings
The build copies a heap that is neither imported nor fully watched, so it is not mirrored either.

**Sources of unwatched heap blocks.** These bump the unwatch serial:
- imports with `staysWatched=false`: always on Windows (GBM:648); on Linux after an unwatch request, a probe verdict or a probe failure (:662-683);
- `GuestMemory::Unwatch`, whose only caller is GBM:1145;
- failed import-window walks (GuestMemory.cpp:1315);
- `MarkWritten`'s incomplete collect.

These do **not** bump it:
- a failed collect walk with no unwatch (GuestMemory.cpp:1191);
- libkernel's own unregisters on Linux (DirectMemory.cpp:501-502 for alias mappings, :664 for unmap, :964 for file-backed).

### Gaps
**1. MEDIUM: an import that failed for a non-budget reason is never retried.**
- *Failure kinds:*
  - a cached failure (GBM:948-951; a `vkAllocateMemory` failure is cached at :1063 and cleared only at :1155 when the run changes);
  - a held window (:960-963);
  - page checks (:996, :1008, :1031).
- *Effect:* such a heap is copied, and the build FATALs past the cap.
- *Example:* a Windows 768 MiB flexible heap shares a 64 KiB block with an imported neighbour, so it is not fully watched. The neighbour's first import failed at `vkAllocateMemory`. Every build now copies 768 MiB and aborts with "heap not fully write-watched".
- *Related:* #5870 would close the held-window case.

**2. MEDIUM: the retry depends on order.** Only the range that crosses the cap is retried (GBM:2676).
- Earlier budget-refused copies that stayed under the cap are never revisited.
- If the crossing range can't be imported and nothing is evictable (GBM:902-908 skips what was looked up since `buildFloor` and the last 256 lookups, :813), the build aborts. Evicting for an earlier, larger copy would have fit.

**3. MEDIUM: a refresh after an unwatch the serial misses throws** (an exception, not FATAL).
- The heap-mirror refresh requires a non-zero collect (GBM:1559 per build, :1696 on a cache hit, :1661 for sparse mirrors).
- Unwatches that don't bump the serial let the mirror be reused and then throw. These are a failed walk, or a Linux DirectMemory alias unregister.
- Sparse heap mirrors are not covered by `heapMirrorWatched` at all (:1661 via :1741, :2577).
- An import made later in the same pass (now including the eviction retry) can exclude a mirrored heap's last 64 KiB block on Windows. The refresh then throws (:2774 → :1559).

**4. LOW: a cache hit re-adds copied ranges without the cap check or a retry** (GBM:2588, re-measured at :2804). This holds only while every registry change moves the generation.

**5. LOW: descriptor-only builds have no cap.**
- They copy at GBM:3423 and :3634.
- `bindSparseMirror` falls back to copies (:2935-2939).
- A late import retirement can fall back to `copyRegion` at :3634.

**6. INFO: some failures throw even when eviction would have worked:** a heap mirror over its budget, or a failed mirror buffer allocation (GBM:1783-1791).

### Tests per variant
Present:
- BdaResources.cpp (+120): an address-based build of a partly unwatched heap over the import budget; a heap mirror whose range leaves the write watch is planned again.
- Graphics.cpp (+26).

Missing:
- a non-budget import failure (a cached allocation failure, a held window);
- two budget-refused copies where only the first is large;
- a refresh after an unwatch the serial misses (a failed walk, a DirectMemory alias);
- a cache-hit re-add;
- a descriptor-only build.

### Cost
The retry runs only when a build would cross the cap, so the normal build is unchanged.

### Related open PRs
- **None supersedes it.** No open PR edits the copy loop, `AddressCopyOverflow` or `copyLimit`.
- **Complementary:**
  - #5870 (closes gap 1's held window);
  - #6097 (fewer spurious held refusals);
  - #6060 (Windows settle; removes the main Windows unwatch source);
  - #4448 (Linux: re-watch idle unwatched imports).
- **Conflicts:**
  - #3248, a textual conflict with b8cf1b510 at GBM:1770-1781. When resolving it, the stale-drop must subtract `heapFootprint`.
  - #2434 and #5905, a small HostImports conflict at GBM:188-189. #2434's `DmaBufImportFailure` throw would escape the retry.

### Follow-up
**None.**
- Gaps 1 and 3 change the import retry policy and the mirror refresh contract (throw → plan again) across GuestBufferMemory. Each needs the owner's design call.
- Each also needs a GPU-backed test with forced `vkAllocateMemory` failures or DirectMemory unregisters, which I'd rather propose than build blind.

### A better version would…
1. Retry every budget-refused copy, largest first, whenever the total crosses the cap, not only the crossing range.
2. Also retry heaps whose import failed for a non-budget reason, after clearing the cached failure for that build.
3. Treat a refresh that finds the range unwatched as "drop the mirror and plan again" instead of throwing. That covers gap 3's missed unwatches, the in-pass case and sparse mirrors.
4. Apply the cap, or at least the retry, on cache hits and descriptor-only builds.

## 5. FSR 1: feat/agc-fsr1-upscaling @ f51b5d5473

### Verdict
**Complete for its scope.** There is no correctness gap in the branch itself. There is one merge hazard with #6012.

**Off path.** The upscaler is built only with `ANYPS5_UPSCALE=fsr` (VulkanDevice.cpp:1880-1884). When `upscaled` is false, the commands are the same as main's (2999, 3049, 3149). Cost when off: two `getenv` calls at device creation and one bool per present.

**Present paths:**
- drawn: presentation pass into the stage, then `RecordStage`;
- blit: scaler or `hdrScaler` `RecordStretch`;
- direct resident: `RecordStretchFrom`;
- uniform clear: `scaler->RecordClear`, then the stretch;
- `clearOnly`: not upscaled.

**HDR10:** the scaler is `hdrScaler` for passthrough when not drawn (2994), and `whiteNits` is bound before `RecordStage`. The swapchain is B8G8R8A8_UNORM sRGB-nonlinear (1835) or A2B10G10R10/A2R10G10B10 HDR10 PQ (2595), so FSR always runs on perceptual values.

**EASU:** `FsrEasuCon` with viewport = size = stage, `textureGather`, clamp to edge.

**RCAS:**
- `texelFetch` clamped to the rect, black bands, output clamped to [0,1];
- sharpness 0 is the sharpest (USAGE says so).

**Slots:** sized once (1873, 1882). The stage and output surfaces are re-created after a format or extent change, but only once the slot has retired.

### Gaps
1. **MEDIUM at merge time: the hazard with #6012** (overlay, fork 62022e9362).
   - *Textual:* `git merge-tree` conflicts in CMakeLists.txt (adjacent shader blocks and sources) and in VulkanDevice.cpp (state member, reset, final barrier).
   - *Semantic:* the overlay draws on the swapchain image after the presentation. It expects COLOR_ATTACHMENT_OPTIMAL (drawn) or TRANSFER_DST_OPTIMAL (blit), but RCAS leaves the image in PRESENT_SRC_KHR.
   - *The trap:* the obvious textual resolution, `if (overlay) {…} else if (!drawn && !upscaled)`, records the overlay from the wrong layout under FSR.
   - *Correct resolution:*
     ```
     upscaler->RecordPresent(..., overlay ? VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL : VK_IMAGE_LAYOUT_PRESENT_SRC_KHR);
     overlay->Record(..., (drawn || upscaled) ? VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL : VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL);
     ```
     The overlay then draws at window resolution over the sharpened image, which is right: the text is not upscaled.
   - *Who does it:* whichever PR lands second should carry this resolution, plus a test that presents with both FSR and the overlay on.
2. **LOW: #4040** (output gamma, upstream, not ours) records a compute pass on the swapchain image after the presentation. It has the same layout hazard if FSR lands first.
3. **LOW: #4891** (screenshot key) saves "the displayed frame". Under FSR, the dump and screenshot path records the source, not the FSR output (3123-3140).
4. **INFO, cost:**
   - `FsrEasuCon` and `FsrRcasCon` run per fragment (FsrEasu.frag:32, FsrRcas.frag:33), about 20 ALU per pixel. AMD's samples pass them as uint4 constants instead.
   - Upscaling adds two full-window passes per frame, plus a transient view and framebuffer per pass per frame (the same pattern as PresentationPass).
5. **INFO: EASU is designed for up to 2× per axis.** 720p→2160p (3×) works but is softer, and no doc note says so.

### Tests per variant
