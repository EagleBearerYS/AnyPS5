# BF-046 result (cloud-2): per-draw CPU and GPU cost on a Village-shaped harness, today's path against fable-void's GPU path and a floor

## Setup

- **Machine:** Linux VM `vm`, 4 vCPU Xeon @ 2.80 GHz, 15 GiB RAM.
- **GPU:** lavapipe (Mesa 25.2.8-0ubuntu0.24.04.4, llvmpipe on LLVM 20.1.2).
- **Build:** CI's Linux configure (Release, Ninja, gcc 13.3, ccache, `-DANYPS5_ENABLE_SPIRV_TOOLS=ON`, Wild 0.10.0).
- **How every number was taken:**
  - as the unprivileged `runner`, on an idle machine, one run at a time;
  - with `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1 LP_NUM_THREADS=2`.
- **Why `LP_NUM_THREADS=2`:** with lavapipe's default of 4 rasterizer threads, the 1080p draws keep all 4 cores busy and inflate the driver threads' CPU. Two threads leave 2 cores for the worker and the committer.

## Summary

- **K4: holds on CPU, not on GPU.**
  - **GPU:** arm B's GPU cost per draw is half of arm A's (342 against 687 µs per draw of rasterizer CPU), so the "more than 30% above arm A" part does not hold.
  - **CPU:** arm B's CPU per draw is 173 µs (runs 164–178), above ~80 µs.
- **K2 (harness version): does not hold.** Arm C, the floor, costs 57.5 µs of driver CPU per draw (runs 56–73), under ~150 µs.
- **Where arm B's remaining CPU per draw goes** (§4, profiled steady state on its one thread):
  - per-draw resource build, including descriptor sets: 80 µs (descriptor sets 32);
  - recording: 55.5 µs;
  - pre-pass over guest words: 44 µs;
  - target refresh: 10.9 µs;
  - index scan: 0 µs;
  - the rest: about 30 µs.

  All of `Graphics::Draw` (about 156 µs) runs under the GPU mutex.
- **One table lookup per sample** doesn't resolve above noise here: at most about 10 µs of rasterizer time per draw, about 3–4 µs per sample (§5).
- **Arm B: no refusals and no zero reads.** The pre-pass named every T# before its first use: 1,448 expected and inserted, 0 misses, 0 rejected, 0 thrown packets.
- **Found on the way** (§7):
  - fable-void's branch does not build on Linux as is.
  - **Main and his branch both keep about one memory mapping per draw** for this draw shape, and segfault inside lavapipe after about 31,000 draws (about 36 frames).
  - `[gputime]` timestamps are unusable on lavapipe on both branches.

## 1. The frame shape used

- **Target:** 1920×1080 RGBA8 colour target (tile mode 0x1b), cleared once.
- **Draws:** 850 per frame, one DCB per frame, `DRAW_INDEX_AUTO` with 6 vertices each.
  - The first 85 (10%) cover the whole target.
  - The other 765 are 48×48-pixel quads at 64 positions.
  - Vertices come from a vertex V# table that the vertex shader reads through `s[8:9]`. The table pointer changes per draw when the position does.
- **Pixel programs:** four, sampling 1, 2, 3 or 4 textures. A program is chosen per run of 8 draws, so programs cycle 1→4.
  - Each sample works as follows:
    1. the shader reads 4 indices from the object constant buffer, through the V# in user SGPRs `s[4:7]` (offset 0x10);
    2. it shifts each index by 5;
    3. it loads the T# with `s_load_dwordx8 s[16:23], s[2:3], s36` from a **2,000-entry T# table** whose pointer is in user SGPRs `s[2:3]`.
  - The sampler and the frame constant V# come through a root pointer in `s[0:1]`.
  - Per draw the shader samples 1–4 different 4×8 RGBA8 textures; the frame uses 1,448 of the 2,000 entries.
  - The output is the texel sum × frame constant × object constant.
- **Per-object constant V#s in `s[4:7]`:** a new one every draw. There are 8 sets of 850 object buffers, one set per frame, so 6,800 distinct V#s against the 4,096-entry draw cache. This is BF-042's moving shape: today's path misses every draw.
- **Run length:** 8 warm-up frames (one per set), then 20 measured frames.
- **Index variants for §5:**
  - `VILLAGE_INDEX=constant`: the same table, at a constant immediate offset per slot.
  - `VILLAGE_INDEX=immediate`: the same textures' T#s built from `s_mov_b32` literals, with no table read.
- **Check:** each mode draws one full-target draw for each of 1–4 samples and requires the exact sum of the texel bytes. It passes on all three arms in all three modes. Arm C's check draws are each the first draw of their program, so they take the normal path.

The harness is `tests/execution/VillageDrawCost.cpp`: `--cost N` measures N frames, and without arguments it is a ctest (`agc_driver_village_draw_cost`, about 7 s). Its switches are `VILLAGE_DRAWS`, `VILLAGE_TABLE`, `VILLAGE_FULL_PERCENT`, `VILLAGE_SETS`, `VILLAGE_PROGRAM_RUN`, `VILLAGE_WIDTH`, `VILLAGE_HEIGHT` and `VILLAGE_INDEX`.

## 6. K2 and K4

| criterion | threshold | measured | holds? |
|---|---|---|---|
| K4, GPU | arm B more than 30% above arm A | B 341.9 against A 686.5 µs per draw (−50%) | **no** |
| K4, CPU | arm B CPU per draw above ~80 µs | B 173.0 (164–178) | **yes** |
| K2 (harness) | arm C CPU per draw above ~150 µs | C 57.5 (56–73) | **no** |

So K4 fails on CPU only. The floor shows that today's decode, record and passes, without resolution, cost about 57 µs, in reach of the 50–80 µs design target. Arm B is about 115 µs above that floor.

**What I'd change in the binding scheme**, in the order of what it would save on arm B (µs per draw from §4):
1. **Stop building a `ShaderResources` per draw: about −80.** On his path a draw's T#s, V#s and SRT are read at run time, yet every draw still makes a fresh address-based build: "per kind: BDA" for all draws, with its own descriptor sets (32 µs) and bindings and other work (47 µs).
   - Key the build by program pair, pipeline layout and target formats only, and keep it for the whole program.
   - The per-draw part should be the user-data patch into push constants or a per-draw ring.
   - This is what arm C does, unconditionally, to reach its 43 µs committer.
2. **Drop per-draw descriptor sets.** Bind the descriptor heap and the device image table once per command buffer or pipeline layout (`BindHeap` is already there), and pass per-draw data through push constants.
3. **Make the pre-pass (44) conditional.** `EvaluateBufferSites` and `ExpectedDeviceImages` run for every draw, although in steady state they name nothing new (0 expected, 0 inserted per window). Skip them when a draw's user-data shape matches one already proven, and fall back to the miss ring (the zero read and insert at the next dispatch, which is already implemented) when something new appears.
4. **Batch the device-table refresh** (part of record's 55.5): about 1.7 scoped refreshes per draw. Refresh once per submission against the write watch, instead of per draw.
5. **Take recording out of the GPU mutex.** On his branch the whole `Graphics::Draw` (about 156) runs under it (129 held per draw), on the same thread as decode and the pre-pass. A committer thread like main's would overlap the pre-pass with the previous draw's recording.

## 7. Found on the way (Linux and lavapipe)

### 7.1 fable-void's branch on Linux

- **It doesn't build as is.** In `core/shader/recompiler/ShaderDiskCache.cpp:85-117` (the block under `#if defined(__linux__) && defined(__x86_64__) && defined(__GLIBCXX__)`), 12 of the 31 `sizeof` asserts fail, and a 13th error is that `BufferResource` is undeclared there (`did you mean IrType::BufferResource`). He builds only on Windows, so they never fire for him.
  - The portable field-count asserts below them pass.
  - **Local fix, commit 6fe26aef7 on `exp/bf046-fable`:** drop that block. That doesn't verify the encoders.
- **One test fails to link with CI's Wild 0.10.0:** `tests/guest_ampr_cpp_error_tests` stops with `wild: error: Failed to copy section .rodata from file .../GuestAmprCppError.S.o`. His e3cef332e ("feat(libc): implement generic error category messages") changed that `.S`; it links on main. I didn't try GNU ld, and I worked around it by building only the needed targets.
- **Registration fails on Linux:** `agc_driver_bda_import_eviction_tests is built but no ctest test runs it`.
- **Windows-only parts by code reading:** `Execution/src/GuestMemory.cpp:1968-2040`. `GuardWrites`, `UnguardWrites`, `WriteGuarded`, `Aliases`, `Backing` and the guard observer are no-ops on Linux, so the residency and unit-shadow write guards never engage there. The harness doesn't depend on them.

### 7.2 Today's main and his branch keep about one mapping per draw

- **What grows:** with per-object V#s that move every frame, every draw is a new address-based resource build.
  - The process's memory mappings grow by about 1 per draw (about 2,500 per second), and RSS by about 70 MB per second.
  - Arm A sampled 364 → 23,324 → 48,830 → 62,642 maps, then segfaulted.
- **The crash:** once the count reaches `vm.max_map_count` (65,530 by default), `mmap` fails and lavapipe segfaults in a `memset` inside `vkAllocateDescriptorSets`. The path is `DescriptorCache::Allocate` ← `ShaderResources::buildPrepare` ← `resolveDrawResources` ← `Graphics::Draw` on the committer.
  - That happens after about 31,000 builds, about 36 frames of this shape.
  - Arm B crashes the same way, after about 31,000 builds.
  - So I kept every measured run at 28 frames. For the 120-frame profiled runs only, I raised `vm.max_map_count` to 1,048,576.
- **With the higher limit, long runs degrade:**
  - arm A had one frame of about 211 s during the run, which ended at 107,516 maps (its median frame was still 289 ms);
  - arm B stopped making progress after about 103,000 draws (209,698 maps, 3.4 GiB RSS), with both rasterizer threads busy for more than 13 minutes; I killed it;
  - arm C (wrong output by design) stalled in its long profiled run, with both rasterizer threads at about 90% in JIT code and every driver thread idle; I killed it after an hour. Its short runs were all clean.
- **Process exit is slow too:** after a 28-frame run, exit (static destruction after `AgcDriverShutdown`, which itself returns at once) takes about 4 minutes on arm A (run total 272–275 s against about 30 s of check and frames) and about 10 minutes on arm B (662–669 s).
- **What this suggests:** this shape (Village's) needs the per-draw builds released or reused on both branches. A real game reaches 31,000 draws in under a minute.

### 7.3 GPU timestamps on lavapipe

`APS5_PROFILE_GPU=1`'s `[gputime]` can't be used on either branch:
- main reports a draw class of 114,225 ms of GPU time per 10 s window (`draw x10136`);
- his branch reports 22,793 ms per 10 s window (`draw x128`), and 208,562 ms in another window.

The ranges overlap or don't close on lavapipe. So §3 and §5 use the rasterizer threads' CPU time as the GPU cost: a relative measure for this machine, which the PC should replace with real timestamps.

## RESULT

- **Arms at 850 draws per frame, 1080p, 2,000-entry T# table, moving object V#s** (lavapipe, `LP_NUM_THREADS=2`). Driver CPU per draw, with GPU per draw as rasterizer CPU:
  - A, today: 471 µs (worker 145 + committer 313), GPU 687;
  - B, fable-void's path: 173 µs on one thread, GPU 342;
  - C, the floor: 57.5 µs (16.5 + 42.9).
- **K4:** CPU part holds (B 173 > ~80); GPU part does not hold (B is −50% against A).
- **K2:** does not hold (C 57.5 < ~150).
- **Arm B's CPU by phase:** resource build 80 (descriptor sets 32), record 55.5, pre-pass 44, target refresh 10.9, index scan 0, rest about 30; `Graphics::Draw` (156) entirely under the GPU mutex.
- **Arm B:** no refusals and no zero reads (all 1,448 T#s named by the pre-pass, 0 misses, 0 rejected, 0 thrown).
- **Lookup cost:** not resolvable on lavapipe: at most about 3–4 µs per sample, inside run-to-run noise.
- **On the way:**
  - his branch needs a Linux build fix (stale size asserts), and one test fails to link with Wild;
  - **main and his branch both keep about one mapping per draw on this shape and crash after about 31,000 draws**;
  - lavapipe's `[gputime]` is unusable.
