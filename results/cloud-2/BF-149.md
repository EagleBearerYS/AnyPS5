## The change (ResourceTracker.cpp)

1. **Planning accepts the extra users** (nested branch of `TryMakeTableColumn`, `:761-773`).
   - `otherUsers` is set when a word read of this T# or S# has a user other than an identical descriptor handle. Before, d132754dbe's check at #9457's `:731` refused that case outright.
   - `RereadableVsharp` (`:637-644`) requires each V# handle argument to be the parent plan's read for that dword itself: a `LoadAddressU32` through the record pointer, whose memory the SRT plan has not made planning-only.
   - `otherUsers` without a re-readable V# returns false as before.
   - Fix 1's sibling rule now calls `DescriptorWordReads(handle, rereadable)` (`:630-635`). With a re-readable V#, each sibling read needs at least one T# or S# descriptor user and may also have other users. Without one, the old rule applies: only descriptor users.
   - A read with no descriptor user (a data read through a handle on the V#'s words) still fails. So does every other refusal.
2. **The V#'s loads stay real while a kept read uses them** (`PlanTableColumnPass`, `:1794-1811`).
   - A plan read becomes planning-only only when every user is a planned handle and every buffer read through that handle is planning-only itself.
   - The rule runs to a fixpoint, so a parent V#'s four `LoadAddressU32` stay in the program whenever a child read through one of its handles is kept.
   - The record-pointer reads behind them are `ReadConstBuffer`s through the table V#, which are never plan reads. Buffer parents have no hop reads (`TryMakeIndirectColumn` refuses hops for them).
3. **Kept reads go through an unrewritten copy** (`Run()`, `:153-166`, before the loop that rewrites planned handles).
   - The trigger is any plan read that is not planning-only and whose handle is a planned (so rewritten) `GetBufferResource`.
   - It gets a copy of that handle, emitted just before the original (`EmitCopy`, one copy per handle), with the original four word values.
   - `ReplaceArgument(0, copy)` then points the read at the copy.
   - The original handle is rewritten as before and is only read by planning-only reads.
   - `Collect` had already marked the kept read `gpuDescriptor` (its V# words are not runtime values), so it is a BDA read at `V# base + offset`. Its V# words are the guest's V#, loaded at dispatch through the record pointer.
4. **Descriptor handles still take the snapshot.** Nothing in the column, materializer or image-table path changed.

**Why d132754dbe's crash no longer happens:**
- That crash came from a kept read through the rewritten handle `(offset, pointer low, pointer high, offset)` while the V#'s loads were planning-only.
- Now no kept read goes through a rewritten handle (step 3).
- The words its copy reads are emitted (step 2), so it addresses the guest's palette.

## Finding: a BDA miss of a uniform scalar load crashes lavapipe

**What happened:**
- The first build of the change ran the old nested consumer tests unchanged, with no snapshots. `agc_driver_nested_image_table`, `agc_driver_nested_sampler_table` and the reuse test died with SIGSEGV inside llvmpipe's JIT code.
- **Faulting instruction:** `vpbroadcastd (%rax),%ymm1` with `rax` = 0.

**Cause:**
- The stack arrays were not in the BDA table, so the lookup returned 0.
- `StopBdaInvocationIf` returns the invocation (`SpirvBdaFault.cpp:110-124`), but llvmpipe still performed the uniform load from address 0.

**What was ruled out:**
- **Not caused by this change.** It occurs with records mapped and palettes not, with palettes mapped and records not, and for the reuse test's plain data `s_load` through T#2's words when only those addresses are missing. That load's emission is untouched by this commit.
- **Not new.** A temporary probe shader, with no image table, ran through the same harness. It loads `s_load_dword` through a per-group pointer read from a buffer:
  - mapped pointer: reads 0x12345678;
  - pointer 0x10000: segfaults.
  - Same result on the red tree (ResourceTracker.cpp at 0e78959001) and on the commit.
  - The probe was never committed.

**Impact:**
- The kept re-reads inherit this lavapipe-only behavior, like every missed scalar BDA load.
- With mapped guest memory, which the tests now provide and a guest has, they read the guest's bytes.
- `BdaExecution`'s unmapped cases pass on lavapipe, so this looks specific to uniform scalar loads after a stop.
