## 1. The window and the fix
### 1.1 The window (GAC-025 §4.1)
At 5b7c4efcb (TEX:1057-1081 there), `Create` constructed the image, ran `upload()` and `createView()`, and only then counted the key address and listed the image.
- `upload()` reads the guest keys at TEX:2185 there (`ProvedClearKeys`, a direct load in `readDccKeys`, DccMetadata.cpp:488-516).
- The count was at TEX:1070-1074 there, after `createView()`.
- A key store executed by the CPU on another queue (PacketExecution.cpp:322-325: `Pm4::Execute`, then `noteLabelStore`) runs the gate before the GPU mutex (LabelHistory.cpp:19-20).
- If that gate ran between the key read and the count, it found no count and returned. The image kept the keys it had read before the store.

### 1.2 The fix (0acc87be0)
```cpp
auto texture = std::shared_ptr<StorageTexture>(new StorageTexture(context, detiler, descriptor, mipLevel));
KeyAddressCount counted(texture->descriptor.dccAddress);
uploadReason = "first";
texture->upload();
texture->defaultMip = mipLevel;
texture->view = texture->createView(mipLevel, false, texture->storageFormat);
{
    auto& live = Live();
    std::lock_guard lock(live.mutex);
    live.textures.push_back(texture.get());
}
counted.Keep();
```
- `countKeyAddress` and `uncountKeyAddress` (TEX:177-188) are the two bodies that `Create` and the destructor had inline, unchanged. The destructor now calls `uncountKeyAddress` (TEX:4997).
- **Why it closes the window:** the gate's lookup (`KeysLiveAt`, TEX:3929-3933) and the count both take `keysMutex`, so every store's gate runs either after the count or before it.
  - **After:** the gate says yes and the store waits on the GPU mutex (LabelHistory.cpp:20). `Create`'s caller holds it until the image is listed (§5.1). `ClassifyFill` then finds the image, and `NoteKeysFill` notes the fill.
  - **Before:** the store's guest write (`Pm4::Execute`) came before its gate, which came before the count, which comes before `upload()`'s key read. So `upload()` reads the new keys.
- **Its cost:** the same lock and map increment as before, moved up, plus the guard's compare with 0 (§3).

### 1.3 Exception safety
- **`upload()`, `createView()` or the push throws:** `counted` was declared after `texture`, so it is destroyed first and uncounts. Then `~StorageTexture` finds the image unlisted (`listed` is false) and uncounts nothing. That's exactly one uncount. `create-fails-at-upload` tests this path.
- **The push throws** (`push_back`, `bad_alloc` only): the inner block's `lock_guard` has already released `live.mutex` when the guard runs. Neither mutex is taken under the other, so both stay leaves.
- **The count itself throws** (the map insert): nothing was counted, so the guard's destructor doesn't run, and the `shared_ptr` destroys an unlisted image.
- **After `Keep()`:** nothing between the push and `Keep()` can throw, so a listed image always owns its count. The destructor uncounts it after unlisting it, as before. GAC-025's superset argument (§4.1 there) still holds: an image is counted before it is listed and uncounted only after it was unlisted.

## 2. The tests
### 2.1 The hook, and why the getter
- **The narrowest existing injection point is the guest-read flush hook.** Every read through `GuestMemory` calls `GuestMemory::SetFlushHook`'s hook first (`FlushGpuWrites`, GuestMemory.cpp:1998-2000). Tests already swap it: tests/Pm4.cpp:403-412, 629-652, 696-709 and 1202-1204, and tests/execution/DepthPlaneGuestLayers.cpp:258-299. No failure-injection hook exists in `Create`, `upload()` or the live list.
- **It lands exactly in the window:**
  - `upload()` reads the keys with a direct load (`readDccKeys`), which doesn't call the hook.
  - Its next hooked read is of the surface itself, through `GuestMemory::ReadCommitted` (for example `stampLayers`, TEX:2198).
  - So a hook that pauses or throws on the surface address does so after the key read and before the old count position: after the new count, and before the image is listed.
- **Nothing is added to `Create`.**
- **The getter:** in this test process the driver's own hook is installed, Recorder.cpp's `FlushForAccess` (Recorder.cpp:1223). `Create`'s reads rely on it to sync pending GPU writes.
  - The existing tests set their hook and reset it to nullptr afterwards. Here that would drop the driver's hook for the rest of the process, including the cases after these.
  - `FlushForAccess` sits in an anonymous namespace, so a test can only chain to it and restore it through the hook pointer.
  - `InstalledFlushHook()` (GuestMemory.hpp:194-195, GuestMemory.cpp:2002-2004) returns that pointer and changes no behavior. It is the smallest addition that does this.

### 2.2 `write-data-while-creating` (KeysClearOverPending.cpp:409-492)
1. **Setup:** a new target (drawn results, keys uncompressed). The WRITE_DATA packet writes the 0000 key code over the target's 0x200 key bytes.
2. **The hook:** `PauseCreateForKeyWrite`, chained in front of the installed hook. On the first read of the surface it sets stage 1, then waits for stage 2: the write has landed (10 s limit). Then it waits up to 300 ms for stage 3: the note has returned. Every read is passed on to the chained hook.
3. **The other queue (a thread):** at stage 1 it runs `Pm4::Execute(packet, QueueState)` (stage 2), then `noteLabelStore` with the decoded label (stage 3). That's PacketExecution.cpp:322-325's sequence.
4. **The creator:** it holds the GPU mutex, as every driver caller does (§5.1), and calls `StorageTexture::Create` for the target. A guard restores the hook, releases the other thread if it was never released, and joins it.
5. **The check:** under the lock, the image's `UploadedKeys` must be `Uncompressed` (the upload read the keys before the write) and its `FilledKeys` must be `Clear0000` (the write was noted).
- **Why it's deterministic:**
  - **Red:** the gate says no and the note returns at once, so stage 3 comes within the pause and `Create` then finishes with the old keys.
  - **Green:** the gate says yes and the note blocks on the GPU mutex the creator holds. The pause times out at 300 ms, and the note runs once `Create` returns and the lock is released.
- **It can't pass vacuously:** it requires that the hook was reached, that the write landed during the pause, and that the upload read the old keys. Otherwise it fails with its own message.
- `DriverTestAccess` (the friend GAC-025 added) gained `NoteLabelStore` (KeysClearOverPending.cpp:54).

### 2.3 `create-fails-at-upload` (KeysClearOverPending.cpp:494-537)
- `FailCreateAtSurfaceRead` throws `std::runtime_error` at the image's first surface read, the same point where the first case pauses. The throw leaves `upload()` and `Create` through `ReadCommitted`, after the count.
- The case requires three things:
  - no image with the target's keys is live before the call;
  - `Create` threw exactly that error;
  - `KeysLiveAt(keys)` is false afterwards.

## 5. Adversarial review
### 5.1 The precondition: `Create`'s callers hold the GPU mutex
The "after" branch of §1.2 needs `Create`'s caller to hold the GPU mutex until the image is listed.

**By reading the code.** The four call sites are reached only from locked driver work:
- **`cachedStorageTexture`** (ShaderResources.cpp:928, 960) is reached from:
  - `sampledStorageSource` (:637, 645);
  - `CachedStorageSurface` (:1118), used by the draw path (Graphics/src/Draw.cpp:2001-2005, 2663-2674) and by `AliasCopy` (VulkanDevice.cpp:2256);
  - `ShaderResources::Revalidate` (:2847) and stage B's `resolveImageBinding` (:4013).
- **DepthSurface.cpp:221 and :552** build a draw's depth storage.
- **The driver takes the GPU mutex before any of them:**
  - draws: `lockForDraw` (Execution/src/Driver/Draw/Draw.cpp:398) or the `lockedPrepare` path (:48);
  - dispatches: Dispatch.cpp:398;
  - copies: BufferCopy.cpp:150, PacketMemory.cpp:151.
- A build's stage A runs unlocked, but it only plans bindings. The image lookups belong to stage B, under the mutex (ShaderResources.hpp:127-128, 374-375).

**With a probe** (not committed): six lines at the top of `Create` record, for every call, whether the thread holds the mutex and which queue tagged it. I ran it over all of `^agc`:

| tree | `Create` calls | on a queue worker: held / not | untagged thread: held / not |
|---|---|---|---|
| e4c982c7e, the head before the amend (base 2559e96233) | 329 | 39 / 0 | 121 / 169 |
| e4c982c7e merged into main 8dc92ae29, default (pipelined draws) | 336 | 32 / 0 | 133 / 171 |
| the same, `APS5_PIPELINE_DMA=1` | 335 | 31 / 0 | 133 / 171 |

- **Every call through the driver's packet path held the mutex,** pipelined or not.
- **The unlocked calls come from device-level unit tests:** 31 executables at the head, plus `agc_driver_reversed_order_blend_tests` on main.
  - None of them uses the driver. Each calls `VulkanDevice::Dispatch` or `Draw` directly from its main thread, for example ImageTableReuse.cpp:180, StorageCacheBudget.cpp:70, ImageStorePacked.cpp:188 and DepthStorageDispatch.cpp:163, 268, 354.
  - No other thread stores keys there, so the window can't open.
  - Even without the mutex the fix is no worse than 5b7c4efcb: a store that sees the count would classify before the listing and skip, as it did before.
- **I didn't add an `AssertGpuLockHeld` to `Create`:** under `APS5_ASSERT_GPU_LOCK=1` it would abort those 32 tests.

### 5.2 Can the creating thread itself note a key store from inside `Create`?
**No.** That would take a key store that the creating worker queued (a deferred label), recorded and noted from inside `Create` after the key read. Nothing in `Create` does that:
- **Queued labels are recorded from a CPU access only through `FlushForAccess`,** and only when the access overlaps one of them (Recorder.cpp:1012-1019).
  - The key read in `upload()` is a direct load and never calls the hook.
  - The surface read does call it, but records only labels over the surface.
- **The worker has none queued when it reaches `Create`.** Every locked driver step that can reach `Create` records the worker's queued labels right after it takes the GPU mutex:
  - draws in `lockForDraw` (Execution/src/Driver/Draw/Draw.cpp:408, `recordLabelsForPacket`);
  - dispatches (Dispatch.cpp:401);
  - copies (BufferCopy.cpp:153; PacketMemory.cpp:153, `recordDeferredLabels`).
- **Locked note callers can't interleave.** GAC-022's rows 3-8, including main's `commitLabel` and `commitDmaStore`, hold the GPU mutex when they note, so they can't note during another thread's `Create`.

### 5.3 A store between the count and the key read is both read and noted
- **What happens:** such a store is read by `upload()` and also noted once `Create` returns.
  - `NoteKeysFill` marks the fill on an image whose upload already used those keys (TEX:3954-3958).
  - For a clear it also resets `uploadedKeys`, so the next refresh rechecks the keys.
- **This is d71ef7b1e1's behavior.** Before the gate, every store that met a `Create` waited on the GPU mutex and then noted the new image, whichever side of the key read it landed on. GAC-021 and GAC-025 found that correct.
- The fix brings that back for stores that land during `Create`, and keeps the gate's saving for every other label.
- **When it can happen:** only when a title writes a surface's keys on one queue while another queue starts using that surface, with no synchronization between them (GAC-025 §4.1).

### 5.4 Memory order across queues
Unchanged from GAC-025 §4.2:
- The count is still a `keysMutex` unlock that comes before the listing and before anything the creating queue does afterwards, including its later labels. It only moved earlier.
- A queue that waits for such a label and then stores keys on the CPU sees the count. That rests on the same x86-64 assumption the driver already makes for every handoff through guest memory.

### 5.5 The other note callers, and fills
- **Only two callers run the gate without the GPU mutex:** GAC-022's rows 1-2, PacketExecution.cpp:208-209 (a flip's EOP `RELEASE_MEM`) and :322-325 (0x49 or 0x37).
  - Both are `Pm4::Execute`, then `noteLabelStore`: the sequence `write-data-while-creating` reproduces for 0x37.
  - The fix covers both, because the count it moves is the one their gate reads.
- **Every other caller** (rows 3-8, including main's pipelined `commitLabel` and `commitDmaStore`) runs the gate under the GPU mutex. So no `Create` is in progress on another thread when its gate runs.
- **Every image is listed, and counted, in `Create` alone.** There is one `live.textures.push_back` (TEX:1101) and one count increment (TEX:180), and the descriptor never changes (GAC-025 §4.1).

## 6. Scope: `storeBufferFill` (paragraph for the PR text)
> **Out of scope: the fill path.** `ClassifyFill` has one other caller, `Driver::storeBufferFill` (BufferFill.cpp:291). It is reached from DMA_DATA fills (PacketMemory.cpp:173) and from the fill-kernel replacement (BufferFill.cpp:255), and it keeps walking the live list for every fill, as on main. The key-address gate can't serve it. A fill needs the full coverage class (`Exact`, `Inside`, `Around`, `Straddle`, `Several`, `Layer` or `Keys`), not only "a live image's keys start here", and it takes the GPU mutex for its own work anyway (BufferFill.cpp:277), to record the fill or store it on the CPU. Taking the walk off this path needs an interval index over the live images' surface and key ranges, kept with the list under `live.mutex`. That's a separate change with its own tests. Fills are the title's clears and memsets, while labels come with every end-of-pipe event, WRITE_DATA and release. On a title, `APS5_PROFILE_DRAW=1` bounds their share: the `[fill]` line (BufferFill.cpp:380) prints the cumulative fill count and the `classify` phase's held milliseconds.
