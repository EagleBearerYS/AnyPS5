## Short answer

The failure is not #9647's dangling blocker, and #9647's pattern alone does not fix it. It is a one-item leftover in the draw pipeline when a case returns.

With ordered completion (the default), a submission that has nothing left open doesn't drain at its end. It queues a completion item instead (`Driver::deferCompletion`, QueueWorker.cpp:73-75, reached from PacketExecution.cpp:525-528). That item's commit calls `completeSubmission`, which wakes `WaitIdle`. The committer pops the item and decrements `Outstanding()` only after the commit returns (DrawPipeline.cpp:179-184). So `Finish()` can return while `Outstanding()` still counts that item, for about 0.2 ms.

`SatisfiedWaitDrainsOverlappingQueuedWork` (case 4) starts right after case 3. Its wait loop ends as soon as `Outstanding() >= 2`. With case 3's completion item still counted, its own blocker makes 2 at once. The loop exits before the WAIT_REG_MEM has asked for a drain, which gives "a satisfied WAIT_REG_MEM skipped an overlapping queued write".

## Fix

Three changes, all in `PipelinedFill.cpp`:
- **#9647's blocker shape.**
  - `Blocker` keeps its `release` and a new `done` flag in a `std::shared_ptr<State>` that the queued lambda captures by value. `target` is captured by value too; it points at a static.
  - The lambda sets `done` after taking and dropping the GPU lock, as #9647's does. `Release()` replaces the direct `release = true`, and `~Blocker()` still releases.
  - `Join()` waits for `done`, with a 20 s `Require` ("the blocker never ran"). Each of the four cases calls `blocker.Join()` right after `Finish()`, before its assertions.
- **The case-end wait.** `Finish()`, after `WaitIdle` returns, waits until `DrawPipeline::Queue0().Outstanding() == 0`, with a 20 s `Require` ("the draw pipeline kept an item after the queue went idle"). Each case therefore leaves the pipeline empty and the next one starts clean. This is the change that removes the failure.
- **The 500 ms sleep in `SubmitBehind` stays.** The brief asked to replace it with a wait on `Outstanding()` or the drain request, but this case has neither signal:
  - The sleep lets the queue worker reach the scratch fill while the pipeline is still empty. A gdb sample of the final binary taken during the sleep shows the queue worker in `GpuMutexType::lock` ← `Driver::fillBuffer` ← `Driver::dispatch` ← `Driver::execute`. That is the pattern fill's `inputLock.lock()` (BufferFill.cpp:283), blocked on the GPU lock that `SubmitBehind` holds, with the test thread in `SubmitBehind`'s sleep.
  - `Outstanding()` stays 0 through that (150 of 150) and no drain is requested on that path.
  - **Removing it (stage A):** 72 of 72 loaded runs failed with "the queue worker never reached the fill". gdb on a stuck run showed:
    - the queue worker in `DrawPipeline::Drain` called from `Driver::execute`, before the fill, waiting behind the blocker;
    - the committer in the blocker lambda;
    - the test thread in `ReleaseWhen`, which never sees 4 items.
  - Nothing a test can read shows "the worker is waiting for the GPU lock in the fill", so I kept the sleep and dropped no assertion.

**Stage A′.** #9647's shape with the sleep kept and without the case-end wait gave 67 passes and 5 WAIT_REG_MEM failures in 72 loaded runs. That is the evidence that #9647's pattern alone does not fix this test.

## Siblings

**`PipelinedPrefetch.cpp`: no change needed.** On a passing run, the case can't return before its lambda has returned.
- The `[this]` blocker (lines 42-49) is enqueued before the submission (line 70, then `sceAgcDriverSubmitDcb` at line 74), so it sits ahead of everything the submission queues.
- Prefetch case: the label is queued behind the blocker (`outstanding >= 2`, line 80). The submission's completion item comes after both. The pipeline has one committer and is first in, first out: it runs `items.front()` (DrawPipeline.cpp:156) and pops it after the commit (DrawPipeline.cpp:179). So the blocker's lambda has returned before the completion item wakes `WaitIdle` in `Finish()` (line 85). `Label[0]` landing (line 87) also needs the label behind it to have committed.
- Copy case: the DMA_DATA copy drains the pipeline (`copied.drains == 1`, line 111). `Drain` waits for `items.empty()` (DrawPipeline.cpp:211), which includes the blocker.
- The completion-item leftover found above can't hurt it either. The second call waits 1500 ms before it reads `Outstanding()` (line 80), and the leftover clears in under 1 ms. The first call has nothing before it.
- The dead-frame read is possible only after a failed `check` (line 87) throws while an item is queued. `release` was set at line 84 first, and `main` then shuts down, so it can only turn an already-red run's exit into a hang.
- Loaded on main: `agc_driver_pipelined_prefetch` passed 72 of 72.

**`ImageTableCacheBounds.cpp` (`QueuedDraw`, lines 256-264, ctest `agc_driver_image_table_vouch_queued_draws`): no change needed.**
- On a passing run `VouchUnderQueuedDraws` waits for all three lambdas:
  - `elsewhere` and `between` are released at lines 325-326, and `settle(1u)` (line 327) waits until `Outstanding()` is 1. Both items are popped, so their lambdas have returned; `into` was enqueued after them.
  - `into` is released at line 329, and `pipeline.Drain(Capture)` at line 330 waits for `items.empty()`.
  - Nothing in this case is submitted, so there is no completion item to leave behind.
- Only the failure paths can unwind with items still queued: `vouch`'s `Require`s at lines 306-307 after `releaseAll()` at line 305, and `settle`'s timeout at lines 312-314. Both come after a red result.
- Loaded on main: 72 of 72 passed.
- Note: this ctest is not matched by `-R 'pipelined|image_table_cache_bounds'`. `agc_driver_image_table_cache_bounds` runs the binary without `--queued-draws`.
