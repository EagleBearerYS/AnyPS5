### Setname functions

All five work the same way:

- A non-null object pointer and a non-null name of any length return 0.
- A null object pointer or a null name throws `std::invalid_argument`.

Why 0 and no stored name: the tree keeps no name for any of these objects, and nothing reads one back. `scePthreadMutexInit` and `scePthreadCondInit` take the name as an unnamed parameter. `scePthreadRwlockInit` and `scePthreadSemInit` do `(void)name`. No `*_getname` exists for these objects. A stored name would therefore be unobservable.

Why a null name throws: shadPS4 is inconsistent on it. Its mutex form substitutes `SceNoNameMutex` and returns 0. Its cond and rwlock forms return `EINVAL`. Its semaphore form returns -1 with `errno` `EINVAL`.

Why any length is accepted: no shadPS4 form checks the length.

### pthread_rwlockattr_settype_np

Source: the SCE twin `scePthreadRwlockattrSettype` (`src/Rwlock.cpp:176`), with the file's `toPosix` conversion. This is PM-088's A basis.

shadPS4 registers `posix_pthread_rwlockattr_settype_np` (`rwlock.cpp` L282-L289) under this name (NID `8NuOHiTr1Vw`). It also registers it under the SCE twin's NID `h-OifiouBd8`.

Behaviour comes from the twin:

- Any type is stored.
- A null or uninitialized attribute throws `std::runtime_error`, as the tree's other POSIX rwlock attribute setters do. shadPS4 returns `EINVAL` there instead.
- The type is not applied, because `scePthreadRwlockInit` ignores its attribute. The debt entry says so.

### scePthreadMutexIsowned

Sources:

- FreeBSD 11 libthr `_pthread_mutex_isowned_np` (`releng/11.0` `thr_mutex.c` L1133-L1149) returns the 1/0 boolean.
- The tree's own SCE boolean twin, `scePthreadEqual`, returns `pthread_equal`'s value.

Results:

- 0 for a zero, static or destroyed handle.
- A null mutex pointer throws `std::invalid_argument`, from `IsOwned`.

**Caveat, for the PM to weigh:**

- shadPS4 registers this NID as `ORBIS(posix_pthread_mutex_isowned_np)` (`mutex.cpp` L542).
- Its generic `OrbisWrapperImpl` (`kernel.h` L25-L39) adds `0x80020000` to any nonzero return. Under shadPS4, a held mutex therefore returns `0x80020001`, not 1.
- shadPS4 registers `scePthreadEqual` without that wrapper. So the wrapping looks mechanical, but that is not proven.
- Both readings are truthy and both give 0 when the mutex is not held. Only a caller that compares with `== 1` would see a difference.
- The debt entry records this. The commit is standalone (`12377b2ffa`) and can be dropped if this counts as a guess.

### scePthreadMutexattrSetkind

Sources:

- FreeBSD 11 libthr `_pthread_mutexattr_setkind_np` (`thr_mutexattr.c` L108-L120) stores the kind as `m_type` and returns 0.
- FreeBSD `pthread.h` L129-L133 numbers the types: ERRORCHECK 1, RECURSIVE 2, NORMAL 3, ADAPTIVE_NP 4. That is the mapping `scePthreadMutexattrSettype` uses.
- shadPS4 registers `ORBIS(posix_pthread_mutexattr_setkind_np)` under this NID (`mutex.cpp` L569-L570). The wrapper returns 0 on success.

The call goes through `scePthreadMutexattrSettype`.

Throws `std::invalid_argument` in two cases:

- **A kind outside 1 to 4.** FreeBSD stores it unchecked, and a later `pthread_mutex_init` then fails `mutex_check_attr` (`thr_mutex.c` L209-L220) with `EINVAL`. The tree cannot store an invalid type.
- **A null or uninitialized attribute.** FreeBSD returns -1 with `errno` `EINVAL`. The SCE result for that is unknown: shadPS4's wrapper would turn -1 into `0x8001FFFF`.
