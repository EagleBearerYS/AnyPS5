## 1. The rule (dc96a083d6)

Line numbers are in `core/libs/prx/libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp` at a612fca7b2.

- `HostImport` gains `spaceUse` (`GuestBufferMemory.hpp:44`).
- **An address-space hit** writes its stamp to `spaceUse` (`:2936`), not to `lastUse`.
- **`pointerHeld`** (`:994`) is `max(lastUse, spaceUse) >= buildFloor`.
- **The age test** (`aged`, `:1002`) is `!pointerHeld && lastUse + 256 < useCounter`.

**A correction to the task's mechanism.** At 9c308c739b, `findImport` itself stamps `lastUse` (`:1365` there, `:1450` here). So uploads, the space walk, `UploadPrepare` and `HostImportFor` all keep an import young.

Before this change, one stamp kept the space's imports young without any lookup: the space hit's (`:2846` at the base). It is the only stamp moved. "Imports only the address space keeps young" are exactly the imports whose `spaceUse` is within the last 256 uses while their `lastUse` is older (`spaceOnlyUse`, `:1006`).

**Why I kept the split stamp rather than BF-018's option 2** (per import, the space generation of its last real build use):
- **Lookups.** Option 2 needs real uses told apart from the rebuild walk's lookups. Both go through `findImport` (the walk at `:2983`'s pass, `UploadPrepare` at `:3728`, `UploadFinish` at `:3912`). Without that split, every rebuild marks every space import as used by the current space, and the set freezes again.
- **Age measure.** "Older than the current space" ties a candidate's age to how often the space is rebuilt (generation changes, waiter drops). The split stamp keeps the existing 256-use measure.
- **Held rule.** The split stamp keeps the held rule exact for the running build, unchanged otherwise.
- **The shared weakness.** BF-018 warned that imports shaders read only through pointers have no use signal, so they are evicted first. That holds for both signals. The guards in part 2 bound what it can cost.

## 2. The thrash guards (a612fca7b2)

All three apply only to space-only imports. Imports old by both stamps are evicted exactly as before.

1. **Warm-up.** A space-only import is not a candidate until the current space has served 16 address-based builds:
   - `state.spaceBuilds` counts address-based builds with the cache on (`:2931`);
   - `state.spaceBuiltAt` is set by every build that rebuilds the space (`:2984`).
2. **Window.** At most one request per 256 address-based builds may retire space-only imports:
   - `spaceEvictedAt` is set after the retirement loop (`:1042`), so one request can still retire several imports to make room;
   - every such request bumps the epoch once, so space-only retirements cause at most one space rebuild per 256 builds.
   - **The window:** 256 address-based builds, about 3.5 s at Village's ~72 builds/s. It's counted in builds, not time, so it scales with the frame rate and is deterministic in tests. The 16 and 256 are choices, not measured; the debt doc says so.
   - `ClearHostImports` and a device change reset it.
3. **The walk's memory.** The retired run goes into `state.refusals`, the non-evicting refusal memory from #6457 (`:1046`).
   - It records the live bytes after the import it made room for (`making` is passed in), so the memory is exact: it expires as soon as live imports drop below that.
   - If the new import then fails, live stays below the recorded value, and the walk tries again.
   - Joined imports are not recorded.

**BF-018's evicting memory stays exact.**
- `evictableBytes` (`:1122`) puts a guarded import, aged but space-only with the guard closed, into the `ready` horizon by `spaceUse + 257` (when it stops being space-only).
- It records `opens`, the build count at which the guards open (`:1132`). `evictingRefusalCurrent` (`:1019`) also needs `spaceBuilds < opens`.
- The guards only open by build count or by aging, and a rebuild only moves `opens` later. So a remembered evicting refusal can't hide a request that would succeed.

**New counter:** `copiedBytes`, the bytes of the ranges the cached space copies, counted per hit (`:2958`). The `[address]` line prints it as `copied ranges N KiB per hit`. That is the CPU-copy cost of a retired range, readable in a Village run.

## 3. Why a running build can't lose an import it uses

1. **One floor at a time.**
   - Address-based builds run whole under `GuestMemory::GpuMutex` (`ShaderResources.cpp:1224-1228`: "device-lock work, so their whole build waits for Complete()").
   - A descriptor-only build can run `UploadPrepare` unlocked, but `UploadPrepare` only looks imports up and sets the build's own `importFloor` (`:3712`). It never imports, retires or writes `buildFloor`.
   - `buildFloor` is written only by the space-less walk of `AcquireRegistered` (`:2983`) and by `UploadFinish` (`:3815`, under the lock), the only path that may evict for a build.
2. **A space hit holds the space's imports.**
   - `importFloor = useCounter + 1` and the stamp is `++useCounter`, the same value (`:2932-2936`, under the import lock).
   - `UploadFinish` sets `buildFloor = importFloor`.
   - So every import the space maps has `spaceUse == buildFloor` for the rest of the build: neither evictable nor replaceable (`importRunAt`'s held check, `:1213`).
   - Before `UploadFinish`, the floor is an earlier build's, which is at most the stamp.
3. **Imports the build looked up itself** are stamped by `findImport` at or above the floor (`:1450`).
4. **The old space's pointers.**
   - They are used only on a hit whose `importsEpoch` equals the epoch (`:2928`, under the import lock).
   - Every retirement bumps the epoch (`:279`).
   - `UploadFinish` checks again before any space pointer is dereferenced (`:3866`). It dissolves the space with `resolve = true`, and every region re-resolves its pointer (`:3910`).
5. **The GPU side.** A retired import's buffer and memory stay alive through the recorder hold (`KeepThroughHold`, `:284`).
6. **Tested:** an import request in the middle of a build (`HostImportFor`) is refused, and no import serial changes (part 4).

## 4. The tests

All are in `tests/BdaResources.cpp`, run by ctest `agc_driver_graphics`. Common setup:
- address-space cache on; each test skips with a message when it's off;
- 64 KiB pieces, `hostImportAlignment` 64 KiB, `SetHostImportWindow(0)`;
- `SetHostImportBudget(live + 4 pieces)`;
- separate ranges `at(0..3)` (read-only) that the first address-based build imports;
- writable ranges refused by that walk.

**`spaceOnlyEvictionTests`** (`:1222`): one hot range R.

| step | asserted |
|---|---|
| 300 address-based builds | 300 hits; the space copies R: 64 KiB per hit |
| an import request in the middle of a build (`HostImportFor` on R) | refused, no import serial changed, no retirement |
| an upload that needs R in place | R imported; 1 space-only retirement (`at(0)`, the least recently looked-up); `at(1..3)` unchanged |
| next address-based build | `rebuiltEpoch` +1, rebuilds after retirement +1; the walk answers `at(0)` from memory (build `remembered` +1); the BDA range over `at(0)` reads the guest's 0x40 at both ends |
| 20 rounds of upload + address-based build | R's serial unchanged; 0 upload refusals; 0 more retirements or rebuilds; 20 hits; the space copies `at(0)`: 64 KiB per hit |

**Steady state: 1 retirement and 1 rebuild in total.** The read of the retired range costs one 64 KiB CPU copy per address-based build: `copyRegion` reads it from guest memory, `GuestMemory::Read` at `:4061`. That's the same as R's copy before the retirement.

**`spaceEvictionWarmupTests`** (`:1335`):
- after a rebuild and 300 lookups that age `at(0..2)`, 3 hits;
- an upload that needs R is refused, with no retirement;
- after 16 hits, the same upload retires `at(0)` and is imported.

**`spaceEvictionWindowTests`** (`:1391`): two hot ranges, R1 from round 0 and R2 from round 1. Each round is upload R1, upload R2, then an address-based build; 600 rounds.
- R1 is imported in round 0.
- R2 stays refused until round 256 (asserted ≥ 256 and ≤ 257), then takes a second space-only import.
- Totals: 2 retirements and 2 rebuilds, the second 256 builds after the first.
- No ping-pong: neither range's import serial ever changes once made, and the two retirements took `at(0)` and `at(1)`.

## 7. What a Resident Evil Village run should show

The PC runs it in a slot. Before (bf-settle), with the 6400 MiB budget full:
```
[gpu] host import budget: 6399 MiB live of 6400 MiB (APS5_HOST_IMPORT_MIB); 5978411 imports (634831 MiB) refused so far, 5315222 of them remembered, last 0x2372400000+0x80000 by build
```

**Expected on this branch:**
- **Retirements and rebuilds.**
  - A range an upload first needs in place takes the least recently looked-up import that only the space uses, once that space has served 16 builds.
  - From then on, the uploads use that range in place.
  - The `[address]` line shows `space-only evictions N, rebuilds after them M`. At most one event per 256 builds, which is at most ~2 per 10 s line at 72 builds/s, and it should go to 0 once the scene's upload ranges are in.
  - At shutdown: `[gpu] address space at shutdown: N imports retired that only the address space kept in use, M space rebuilds after them`.
  - N growing by about 2 every 10 s for the whole run means the window keeps being used. In that case, send the `copied ranges … KiB per hit` figure as well.
- **The refusal line.**
  - The per-use refusals of upload ranges stop once those ranges are in.
  - The line need not disappear while the budget is full. Each address-based build makes one evicting request for every range the space copies, and it is refused while the build holds the space's imports.
    - In the steady-state test that was one refusal per build for the retired range.
    - BF-018's memory answers repeats inside a build. Its `readyHeld` expires at the next floor rise, so each copied range still costs one walk per address-based build, BF-018's stated bound.
  - Ranges waiting for the window or the warm-up are refused from BF-018's memory until `opens`.
  - So expect `refused so far` to grow at about (copied ranges × address-based builds) rather than per use of every refused range, with the window waits counted as `remembered`.
- **CPU copies.**
  - Per upload, the in-place range's copy and its write-back diff are gone.
  - Per address-based build, the space copies the retired range instead (`copied ranges … KiB per hit`).
  - The retirement picks the least recently looked-up import, whatever its size. So the total goes down when the retired ranges are no larger than the upload ranges, or when per-upload copies dominated, as bf-settle's ~1 GB per present suggests.
  - Compare `copied ranges … KiB per hit` and the `[resources]` lines before and after. `APS5_TRACE_BIGBUF=1` lists copied regions of at least 1 MiB.
  - If the per-hit figure rises by more than the upload copies saved, the follow-up is to weigh size in `retireLeastRecent` among space-only candidates. That is left out of this branch.
