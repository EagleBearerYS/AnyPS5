**Which path the store takes.** I used a temporary, uncommitted probe: one `fprintf` in `writeBackLayers` printing the flush reason, the path, the segment count and the stored ranges. It was reverted and rebuilt before the `^agc` run, and is not on any branch.

| Case | Write-backs of the plane |
|---|---|
| both ranges imported (`split-imported-buffer-read`, `split-imported-pointer-read`) | One: `reason DB expand: GPU path, 2 segment(s), 131072 bytes: [0x0+0x20000]`. No `StorageTexture writeback submit` line (the CPU path's log). |

(The probe printed the offsets in decimal behind an `0x`. The ranges above are converted to hex.)

**Answer: GPU for a plane across two imports.**
- Main's `writeBackLayers` now records the store into each range's import. When no single import holds the image, `importSegments()` (ea3a2152d, `Texture.cpp`) builds one segment per registered piece and `writeBackWindows` copies into each segment's import.
- The CPU path ("after a wait for the expand") is left only for a plane that is partly not imported. `importSegments()` returns nothing when any registered piece under the image has no import.

## (c) Anything redundant, wrong or double-storing given ea3a2152d?
- **No double store.** In all four split cases, every 64 KiB block of the plane is written back exactly once:
  - both imported: one GPU write-back of all 128 KiB through two segments;
  - mixed: the mirror's or copy's flush stores the second block, and the fix stores only the first.
  - After a store the plane is no longer pending, so the later flushes in `UploadFinish` and the mirror refresh find nothing to store again. The tests' `expanded planes stored ahead of the copies: 1` agrees.
- **No store into an import the build doesn't read.**
  - `StoreDepthExpandWrites` runs in `UploadFinish`, after `AcquireRegistered` has looked up or made the build's imports.
  - Those imports count as held for the build (`buildFloor`), so B3's eviction can't retire them in between.
  - The GPU write-back records into those same imports, and the CPU write-back writes the guest pages the imports map.
- **Redundant, but harmless:** `if (HostImportFor(context, address, bytes) == nullptr && !HostImportOverlaps(context, address, bytes)) continue;` in `StoreDepthExpandWrites`. An import that holds the whole plane also overlaps it, so `HostImportOverlaps` alone gives the same answer. The extra `HostImportFor` is one lookup per pending plane per address-based build. Left as is.
- **Out of date, in prose only: the fix's debt entry.** `docs/dev/debt/libSceAgcDriver.md`, "Out-of-place DB expand", added by the fix, says the plane is stored "through the CPU, after a wait for the expand, when imports hold only parts of it (a write base across two registered ranges imported apart)".
  - On main, that example takes the GPU path through each range's import (the probe above). The CPU path remains only when part of the plane has no import.
  - The fix's commit message says the same. That is fixed history, and I didn't rewrite it.
  - I found this after the fast-forward push; it changes no behaviour or test.
  - **Proposed change** (one line in the debt entry, not committed or pushed): replace "and through the CPU, after a wait for the expand, when imports hold only parts of it (a write base across two registered ranges imported apart)" with "into each range's import when every registered range under the plane has one (a write base across two ranges imported apart, through the split write-back), and through the CPU, after a wait for the expand, when part of the plane has no import (an imported range next to a heap-mirrored or copied one)".
  - If you count this as a (c) problem, reset the branches to 4d9965407 and dcdd11c62, or tell me to add the one-line debt correction on both.
- **Not a problem, but a possible saving:** in the mixed case the fix's store waits for the expand and goes through the CPU, because `importSegments()` refuses a plane with any un-imported piece. Storing only the imported piece on the GPU, and leaving the mirrored piece to its refresh, would avoid that wait. That is an optimization, not needed for correctness.
