## PR text draft

Title: `fix(agc): note DCC key fills made by small packet stores`

Base: `main`. Head: `EagleBearerYS:fix/agc-note-dcc-key-packet-stores`.

````markdown
### What

A title can fast-clear a colour target by writing a clear code into its DCC keys instead of its texels. When it writes the keys with a CP DMA fill of at most 64 KiB, the driver resolves the fill to its bytes and records it as a packet store, so the fill never reached `storeBufferFill`, the code that notes key fills.

If the target was drawn and its results were still pending on the host (targets over 64 KiB are not stored at a flip), a sampled read recorded after such a clear kept reading the pending image. It returned the drawn texels instead of the clear colour, while the image's own `Refresh` drops those results for the same keys at its next bind. A surface that is only cleared and sampled afterwards kept showing its last drawn frame.

The packet store now notes a store of one key code that `ClassifyFill` places over an image's keys, as `storeBufferFill` does for larger fills. The sampled lookup then reads the clear through the noted-fill branch it already has. The sampled lookup itself does not change.

A CPU store of the keys stays unnoted on purpose. It is not ordered against the work already queued: a title may stage its next clear while a pass that samples the results is still in flight, which is #4794's case. So the drawn results keep winning over a CPU store.

Whether `main` shows the drawn texels depends on the target's host import:
- A target whose import stays write-watched keeps a write generation, and the lookup trusts its pending image. That is a title's direct memory on Windows, imported through a separate alias.
- A target whose import is compared instead is refreshed at every lookup, and that refresh already drops the results under the clear keys. That is private memory on Windows, or Linux when the import probe says so.

Related:
- #4794 flushes pending results at staged-clear sampled reads. It covers the CPU-staged keys this PR leaves unnoted; the two merge and pass together.
- #5497 memoizes the keys behind an SGPR pattern-fill kernel's fast clear. That kernel's clears stay unnoted here.
- #6108 calls `NoteKeysFill` in its test.
````
