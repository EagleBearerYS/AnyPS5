# PM-012: how a 2-sample depth surface sits in guest memory (Village's blur) (cloud-2)

This is research from code and public sources only. No game data, no fix, no PR.

## Short answer

1. **Layout.** On GFX10 a depth surface's Z plane is a single plane that starts at the Z base and grows upward.
   - With 2 samples, the two samples of each pixel are interleaved 4 bytes apart inside each 64 KiB block. There is no separate plane per sample, and no part of the surface lies below its base.
   - For 1920x2160 D32 with 2 samples, the Z plane is **0x1FE0000** bytes.
   - Stencil (if any) and HTILE live at their own base registers. They are not at offsets from the Z base.
2. **The address.** 0xFF0000 is exactly the size of a **1-sample** 1920x2160 32-bit surface in 64 KiB blocks (15x17 blocks of 128x128).
   - So the "R32F" range [0x20298b0000, 0x202a8a0000) is a separate one-sample surface allocated directly before the depth target. It is not a sample plane or the first half of the depth target.
   - When the rasterizer has more samples than the depth target (EQAA, the case the Village stack's approximations cover), the DB stores only DB_Z_INFO.NUM_SAMPLES samples. The extra coverage sample is not stored anywhere.
   - **Verdict:** not part of the depth surface, about 95% confident. The range is most likely a one-sample depth plane or depth copy that the console's DB writes and AnyPS5 never writes back to guest memory. That is about 70% for a DB-side writer, against about 30% for a shader resolve. One logged frame settles it (plan at the end).
3. **AnyPS5 main (cb893e0ff):**
   - It never computes a depth surface's guest layout from DB_Z_INFO.SW_MODE.
   - It requires the depth target's sample count to equal the rasterizer's.
   - It keeps depth only in host images and never writes depth to guest memory.
   - It throws on DB depth copies.
   - Open PR #5499 implements exactly "DB depth copy into a 1-sample R32F target".
   - The Village stack's approximations correspond to open PR #5907.

## Q1: a 2-sample 32-bit depth surface on GFX10

### Registers

These come from `registers/gfx10.json`; "ctx" is AnyPS5's context index, (address − 0x28000)/4.

| Register | Address (ctx) | Fields that matter |
|---|---|---|
| DB_Z_INFO | 0x28040 (0x010) | FORMAT[1:0] (3 = Z_32_FLOAT), **NUM_SAMPLES[3:2] = log2**, **SW_MODE[8:4]** (24 = SW_64KB_Z_X, 28 = SW_VAR_Z_X), MAXMIP[19:16], TILE_SURFACE_ENABLE[29] |
| DB_DEPTH_SIZE_XY | 0x2801c (0x007) | X_MAX[13:0] = width−1, Y_MAX[29:16] = height−1. For 1920x2160 the value is 0x086f077f. |
| DB_Z_READ_BASE / WRITE_BASE (+_HI) | 0x28048 / 0x28050 (0x012 / 0x014; _HI at 0x01a / 0x01c) | address >> 8. Expected 0x202a8a00 for this Z base. |
| DB_STENCIL_INFO / READ_BASE / WRITE_BASE (+_HI) | 0x28044 / 0x2804c / 0x28054 (0x011 / 0x013 / 0x015; _HI at 0x01b / 0x01d) | Its own base. |
| DB_HTILE_DATA_BASE (+_HI) | 0x28014 (0x005; _HI at 0x01e) | Its own base. |
| DB_DEPTH_VIEW | 0x28008 (0x002) | SLICE_START, SLICE_MAX, Z_READ_ONLY[24], MIPID |

Mesa programs these for GFX9 and later (including GFX10) in `common/ac_descriptors.c`:
- `:943-944` sets `db_depth_base = va >> 8` and `db_stencil_base = (va + stencil_offset) >> 8`.
- `:956-958` sets `NUM_SAMPLES(util_logbase2(num_samples))` and `SW_MODE(swizzle_mode)`.
- `:970-971` sets `DB_DEPTH_SIZE_XY`.
- `:985` sets `db_htile_data_base = (va + meta_offset) >> 8`.

So the hardware addresses Z, stencil and HTILE from three independent bases. Mesa happens to put all three in one allocation: stencil after Z (`common/ac_surface.c:2148-2154`), then HTILE. A PS5 allocator can place them anywhere.

### The Z plane

- **Block size.** It depends on the sample count (`addrlib/src/core/addrlib2.cpp:1674-1701`, `ComputeThinBlockDimension`): `log2NumEle = log2BlkSize − log2(bytes) − log2(samples)`. For an even block size the width gets the extra bit only when log2(samples) is even. So a 64 KiB Z_X block of 32-bit texels is 128x128 at 1 sample and **64x128 at 2 samples**.
- **Plane size.** `addrlib/src/gfx10/gfx10addrlib.cpp:4057-4058` gives `sliceSize = pitch × height × bpp/8 × numFrags`, so **one plane holds all samples**. For depth, Mesa sets `numFrags = numSamples` (`common/ac_surface.c:2587-2591`; color surfaces use storage samples instead).
- **Sample interleaving.** 2-sample Z uses the dedicated `GFX10_SW_64K_Z_X_2xaa(_RBPLUS)_PATINFO` swizzle patterns. They are selected at `gfx10addrlib.cpp:4624-4629` and defined at `gfx10SwizzlePattern.h:765` and `:2539`.
  - The harness, asking addrlib for byte offsets from the Z base, gets s0 at +0x0 and s1 at +0x4 for pixel (0,0), and s0 +0x8 / s1 +0xc for (1,0).
  - Across all 4,147,200 pixels, sample 0 lies in [0, 0x1FDFFFB] and sample 1 in [0x4, 0x1FDFFFF]. That holds in all four configurations.
- **Stencil.** Mesa computes it as a second surface with bpp 8 and the same sample count (`common/ac_surface.c:2751-2766`).
- **HTILE.** It has no sample-count input (`ADDR2_COMPUTE_HTILE_INFO_INPUT`, `addrlib/inc/addrinterface.h:2890-2899`). It is 4 bytes per 8x8 tile, padded to metablocks, and is the same for 1 and 2 samples.

Results for **1920x2160, Z_32_FLOAT**, from addrlib on all four configurations:

| Plane | 1 sample | 2 samples | Notes |
|---|---|---|---|
| Z, SW_64KB_Z_X | 128x128 blocks, 1920x2176, **0x00FF0000** | 64x128 blocks, 1920x2176, **0x01FE0000** | Same in every configuration. Base alignment 64 KiB. |
| Stencil 8-bit, SW_64KB_Z_X | 256x256 blocks, 0x00480000 | 128x256 blocks, 0x00870000 | Own base register. |
| HTILE | 0x50000 (1024x512 metablocks, 10 per slice; align 0x8000) | the same | Navi10-like (16 pipes, no RB+) and RB+ with 8 packers. |
| HTILE | 0x60000 (1024x1024 metablocks, 6 per slice; align 0x10000) | the same | RB+ with 16 packers (Navi21-like). |
| Z, SW_VAR_Z_X (RB+ only) | 0x01200000 or 0x01100000 | 0x021C0000 or 0x01FE0000 | Depends on the pipe count. Only if DB_Z_INFO.SW_MODE is 28. |
| SW_4KB_Z_X | refused by addrlib for this depth surface | refused | |
| R32F color for comparison | SW_64KB_R_X: 0x00FF0000; SW_LINEAR: 0x00FD2000 (pitch 1920) | | |

**Offsets from the Z base for a 2-sample 1920x2160 D32 surface:**
- The Z plane occupies [Z base, Z base + 0x1FE0000), which ends at 0x202c880000 for this base.
- Stencil and HTILE are wherever DB_STENCIL_*_BASE and DB_HTILE_DATA_BASE point. In Mesa's one-allocation layout that would be stencil at +0x1FE0000 (0x870000 bytes) and HTILE at +0x2850000.
- With 1 sample the Z plane is [Z base, Z base + 0xFF0000).

**Fewer depth samples than coverage samples (EQAA).** radeonsi's comment, written by AMD's driver developers, describes which register holds each kind of sample count (`si_state.c:3467-3477`):
- Coverage samples are PA_SC_AA_CONFIG.MSAA_NUM_SAMPLES.
- "Z: Z/S samples (up to 8x, must be <= coverage samples …) – Value seen by DB (DB_Z_INFO.NUM_SAMPLES) … Missing samples are derived from Z planes if Z is compressed (up to 16x quality), or from the closest defined sample if Z is uncompressed."
- radeonsi programs `DB_EQAA.MAX_ANCHOR_SAMPLES = log2(z samples)` (`si_state.c:3547-3559`).

So a 1-sample depth target rasterized at 2 coverage samples is a plain 1-sample surface (0xFF0000 here). The "Z planes" in that comment are HTILE's compressed plane equations, not a second memory plane. The DB stores nothing for the missing sample.

## Q2: is the R32F range part of the depth surface?

**No, about 95% confident.**
- The DB addresses every sample of a GFX10 depth surface upward from DB_Z_READ_BASE/WRITE_BASE. No sample plane or "first half" sits below the base.
- A 2-sample plane is one interleaved 0x1FE0000 range starting at the base, as addrlib's own address function shows.
- A Z base register cannot point into the middle of its surface: pixel (0,0) sample 0 is at base + 0. A pipe/bank XOR only permutes addresses inside the block.
- If the console's depth target is 1-sample under 2x coverage (EQAA), there is no second sample in memory at all.
- The remaining uncertainty is only that the PS5's DB might deviate from AMD's public GFX10 behaviour.

**What the range most likely is.** It is a separate 1-sample 1920x2160 32-bit surface, about 90% confident.
- Its length, 0xFF0000, is exactly addrlib's size for such a surface in 64 KiB Z_X or R_X tiles.
- It is also exactly AnyPS5's own `DepthSliceBytes({1920, 2160}, 4)` (`Graphics/src/DepthSurface.cpp:681-687`).
- A linear R32F of this size would be 0xFD2000, or 0xFE0000 rounded up to 64 KiB. So the allocation was most likely sized as a tiled render or depth target.

Candidates for its writer, ranked:

1. **A 1-sample depth plane that the DB writes, either as a depth target at 0x20298b0000 or through a DB depth copy into a CB there. About 70% for the two together.**
   - *Depth target at 0x20298b0000.* This fits every observation. AnyPS5 keeps depth only in host images.
     - `docs/dev/debt/libSceAgcDriver.md:36`: "Depth rendering is not written back to those guest bytes."
     - Buffer, DMA and CPU reads of a depth surface's range are not redirected. The only DMA guard covers multisampled color (`Execution/src/Driver/Packets/PacketMemory.cpp:64`).
     - So a compute shader reading the range as a plain buffer sees the CPU's boot-time zeros, and AnyPS5 sees "no writer" because DB writes are not guest writes for it.
   - *DB→CB depth copy.* This is the GFX10 hardware way to copy one depth sample into a color target. DB_RENDER_CONTROL sets DEPTH_COPY[2], COPY_CENTROID[7] and COPY_SAMPLE[11:8].
     - radeonsi uses it per sample: `si_blit.c:115-182` and `si_state.c:1841-1844`.
     - It exists only before GFX11 (`si_blit.c:124` asserts `gfx_level < GFX11`), and a Z_32_FLOAT copy gives exactly a 32-bit float color image.
     - On main such a draw throws: `Graphics/src/State.cpp:258` rejects DB_RENDER_CONTROL bits 0x1f9c with "depth copy, resummarize or decompress draws (DB_RENDER_CONTROL) is unsupported".
     - A throwing draw is logged as `draw-error … reason=` and fails the submission (`Execution/src/Driver/Packets/PacketExecution.cpp:300-303`). So on an unmodified build this shows up as an error, not as silent zeros. The PC logs can rule it in or out at once.
     - Open PR #5499 implements this path.
2. **A shader resolve, where a pixel shader into a CB, or a compute shader, writes the R32F range. About 30%.**
   - AnyPS5 would emulate such a write and could see it, which conflicts with "nothing AnyPS5 emulates writes it again".
   - A shader that sampled the multisampled depth would throw on main (`Graphics/src/DepthSurface.cpp:127`).
   - It remains possible if the write lands in a host-only image that the later buffer read does not see.

## Q3: AnyPS5 on upstream/main cb893e0ff

### How the depth layout is derived from DB_Z_INFO, DB_DEPTH_SIZE_XY and NUM_SAMPLES

Everything is in `decodeDepth`, `Graphics/src/State.cpp:257-332`.

- **NUM_SAMPLES:** `:280`, `depth.samples = 1u << ((read(cx, 0x010) >> 2u) & 3u)`.
- **Format:** FORMAT is `:265`. Z_24 throws (`:267`). FORMAT 1 maps to D16 and 3 to D32 (`:291`).
- **Extent:** `:285-286`, `{(size & 0x3fff) + 1, ((size >> 16) & 0x3fff) + 1}`.
- **Bases:** Z read base `:281` and stencil read base `:282`, each `(HI & 0xff) << 40 | LO << 8`. The write bases must equal the read bases (`:283-284`).
- **HTILE:** `:294-296`, only when TILE_SURFACE_ENABLE is set.
- **Rejected bits:** MAXMIP and PARTIALLY_RESIDENT throw (`:263`).
- **DB_Z_INFO.SW_MODE (bits 4-8) is never read.** No guest Z, stencil or HTILE layout is computed from the registers.
  - The only size helper is `DepthSliceBytes` (`Graphics/src/DepthSurface.cpp:681-687`): 128x128 (32-bit) or 256x128 (16-bit) blocks, with **no sample factor**. It is used for slice offsets (`State.cpp:287-289`).
  - `HtileMetadataBytes` (`DepthSurface.cpp:870-873`) is 32 KiB per 1024x512, so 0x50000 here. That matches addrlib's 16-pipe non-RB+ and 8-packer RB+ results but not the 16-packer one (0x60000). It also has no sample factor, which is correct for HTILE.
- **No guest load.** A new surface starts cleared to DB_DEPTH_CLEAR (`DepthSurface.cpp:85`), not loaded from guest memory.

### What it does with a 2-sample depth target

- **Equal counts required.** `State.cpp:805`: `Require(!result.depth || result.depth->samples == result.samples, "the depth target's sample count differs from the rasterizer's")`.
  - The rasterizer count comes from PA_SC_AA_CONFIG (`decodeSamples`, `:413-424`), and exposed samples must equal it (`:422`).
  - More than 1 sample requires MSAA_ENABLE (`:807`).
  - The 1-sample-into-multisampled-color fallback is skipped whenever a depth target exists (`:874`).
- **Host image.** With equal counts it creates a real 2-sample Vulkan depth image (`DepthSurface.cpp:52`). SAMPLED usage is set only at 1 sample (`:54`), and the image is sample-location compatible when the device allows it (`:46`).
- **Identity.** The sample count is part of the surface identity (`:586`), and contents carry over only between equal counts (`:621`).
- **Nothing reaches guest memory.** Rendering stays in that image: the depth attachment uses LOAD and STORE on the host (`Graphics/src/Pipeline.cpp:653-654`).
- **Reading it throws:**
  - sampling it: `DepthSurface.cpp:127`, "sampling a multisampled depth surface is not implemented";
  - a storage view: `:186`;
  - a 2D-MSAA texture descriptor over it: `Graphics/src/MultisampleTarget.cpp:421`, "… which no draw rendered to, is not implemented", reached from `ShaderResources.cpp:528`.
- **No resolve.** There is no reduce or resolve for depth. DB depth copy, resummarize and decompress throw (`State.cpp:258`).
- **DB_EQAA** (ctx 0x201) is only read for dithered alpha-to-coverage (`State.cpp:140-144`).
- **The Village approximations are not on main.** Neither quoted phrase ("…its color and depth targets agree on…", "…depth target's fewer samples") appears in main.

### Does sample-location handling change what gets written?

- **What main does.** `decodeSampleLocations` (`State.cpp:426-441`) reads PA_SC_AA_SAMPLE_LOCS_* (ctx 0x2fe-0x30d) as signed 4-bit sixteenths.
  - It uses VK_EXT_sample_locations (enabled at `Execution/src/VulkanDevice.cpp:1230-1244`).
  - `sampleLocationGridSampleCounts` (`VulkanDevice.cpp:1241`, `Graphics/include/Context.hpp:227`) admits per-pixel 2x2 grids when `maxSampleLocationGridSize` is a multiple of 2x2.
  - Locations reach the pipeline and render pass at `Pipeline.cpp:442-447` and `:671-681`.
- **Effect.** They change which samples a host draw covers and the depth computed at each sample, inside the host image only. Since depth is never written to guest memory, they cannot change what guest bytes, or a buffer read, see.

## Q4: what to log on the PC to settle it in one run

Run one frame of the first 3D scene, with the same build and settings as the blur repro. Use these existing switches:
- `APS5_TRACE_DRAWS=1`;
- `APS5_TRACE_DISPATCH_IO=1` with `APS5_SYNC_DISPATCH=1`, which prints every dispatch's resources after write-back;
- `APS5_TRACE_GPU=1` for CP packets.

Add these temporary log lines, filtered to the window **W = [0x20298b0000, 0x202c880000)**, which is the R32F range plus the largest possible depth plane.

1. **Every draw or clear with any target base in W.** The bases to check are:
   - DB_Z_READ/WRITE_BASE (ctx 0x012 and 0x014, _HI at 0x01a and 0x01c);
   - DB_STENCIL_READ/WRITE_BASE (0x013 and 0x015, _HI at 0x01b and 0x01d);
   - DB_HTILE_DATA_BASE (0x005, _HI at 0x01e);
   - CB_COLORn_BASE (0x318 + 15n, with BASE_EXT at 0x390 + n) for each n enabled in CB_TARGET_MASK (0x08e).

   Log the submission serial, the packet offset, the VS/PS addresses or hashes, the primitive type and count, and these context words:
   - DB_RENDER_CONTROL 0x000: DEPTH_COPY[2], COPY_CENTROID[7], COPY_SAMPLE[11:8], DECOMPRESS[12].
   - DB_DEPTH_VIEW 0x002, DB_DEPTH_SIZE_XY 0x007 (expect 0x086f077f), DB_DEPTH_CLEAR 0x00b.
   - DB_Z_INFO 0x010 (FORMAT, NUM_SAMPLES[3:2], SW_MODE[8:4]) and DB_STENCIL_INFO 0x011.
   - DB_DEPTH_CONTROL 0x200 (Z enable and write), DB_EQAA 0x201 (MAX_ANCHOR_SAMPLES[2:0] and the rest), DB_SHADER_CONTROL 0x203, DB_HTILE_SURFACE 0x2af.
   - CB_COLOR_CONTROL 0x202, CB_TARGET_MASK 0x08e, CB_SHADER_MASK 0x08f.
   - SPI_SHADER_Z_FORMAT 0x1c4 and SPI_SHADER_COL_FORMAT 0x1c5.
   - PA_SC_MODE_CNTL_0 0x292 (MSAA_ENABLE), PA_SC_MODE_CNTL_1 0x293, PA_SC_AA_CONFIG 0x2f8 (MSAA_NUM_SAMPLES[2:0], EXPOSED[22:20]), sample locations 0x2fe-0x30d, PA_SC_AA_MASK 0x30e-0x30f.
   - For each such CB n: INFO 0x31c + 15n (FORMAT[6:2], NUMBER_TYPE[10:8]), ATTRIB 0x31d + 15n (NUM_SAMPLES[14:12], NUM_FRAGMENTS[16:15]), ATTRIB2 0x3b0 + n (MIP0 size) and ATTRIB3 0x3b8 + n (COLOR_SW_MODE[18:14]).
   - AnyPS5's own outcome: drawn, skipped or thrown with the reason, and which local approximation (if any) changed the sample count.
2. **Every dispatch with a V# or T# overlapping W.**
   - Log the CS address or hash, the thread groups, and each overlapping resource: a V#'s base, NUM_RECORDS × STRIDE and format; or a T#'s base, size, format, SW_MODE, sample count and dimension.
   - Log whether the shader reads or writes it.
   - Log whether AnyPS5 has a live host depth surface at that address at that moment (`DepthSurfaceAt`).
3. **Every DMA_DATA, COPY_DATA, WRITE_DATA or CP or SDMA fill or copy with a source or destination in W.**
4. **CPU writes to [0x20298b0000, 0x202a8a0000) after boot, through write watching.** This confirms that only the boot write happens.

Reading the result:

- **A draw with DB_Z_READ/WRITE_BASE = 0x20298b00 and depth writes on.** The range is a 1-sample depth plane of its own, and AnyPS5 leaves its guest bytes at zero.
  - Direction for a fix: before a buffer, DMA or CPU read of a live depth surface's range, write the host depth back in the DB_Z_INFO.SW_MODE layout, or serve the read from the host image.
  - Also check that the compute shader reads it with the Z_X swizzle, or in an order-independent way.
- **A draw with CB0_BASE = 0x20298b00, DB_RENDER_CONTROL.DEPTH_COPY = 1, and Z base 0x202a8a00.**
  - It is a DB→CB depth copy. Main throws here. PR #5499 handles it, unless CB0 is linear (ATTRIB3 COLOR_SW_MODE = 0), which #5499 refuses.
  - COPY_SAMPLE or COPY_CENTROID tells which sample the console copies.
- **A dispatch or PS draw that writes W.** It is a shader resolve. Look at why its result does not reach guest memory before the buffer read; see the storage write-back rules in the debt doc.
- **Nothing in W is written all frame.** The console's writer is something AnyPS5 does not decode or is not logging, such as SDMA or another queue. Widen item 3.
- **In every case, also record the Z surface's own DB_Z_INFO.**
  - With NUM_SAMPLES = 0 (1 sample), the Z plane is 0xFF0000 bytes and ends at 0x202b890000.
  - With NUM_SAMPLES = 1 (2 samples), it is 0x1FE0000 bytes and ends at 0x202c880000.
  - SW_MODE 24 confirms SW_64KB_Z_X.

## Appendix: the addrlib harness

`addr_probe.cpp` is built with Mesa 25.2.8's `src/amd/addrlib` sources, compiled with `-DADDR_FASTCALL= -DLITTLEENDIAN_CPU -DDEBUG=0` and the include directories from `addrlib/meson.build`.

- **Inputs:** for each configuration it calls `AddrCreate` with chip family FAMILY_NV, the chip revision and the `GB_ADDR_CONFIG` value. Then it calls `Addr2ComputeSurfaceInfo` with 1920x2160, 1 slice, 1 mip, numSamples = numFrags = 1 or 2, using `flags.depth` with bpp 32 or `flags.stencil` with bpp 8, and SW_64KB_Z_X, SW_4KB_Z_X or SW_VAR_Z_X.
- **HTILE:** `Addr2ComputeHtileInfo` is called with pipeAligned and rbAligned, as `ac_surface.c:2230-2238` does.
- **Sample map:** `Addr2ComputeSurfaceAddrFromCoord` is called for every pixel and sample.

| Configuration | Chip revision | GB_ADDR_CONFIG |
|---|---|---|
| Navi10-like (no RB+) | 0x01 | 0x044 |
| Navi21-like (RB+, 16 pipes, 16 packers) | 0x28 | 0x444 |
| Navi22-like (16 pipes, 8 packers) | 0x32 | 0x344 |
| Navi22-like (8 pipes, 8 packers) | 0x32 | 0x343 |
