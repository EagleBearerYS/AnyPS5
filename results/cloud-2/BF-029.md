## Verdict

- **The fix: done.** A count-indirect draw now goes GPU-side when its record range at the packet's maximum count runs past readable memory. It records only the records that fit before the end. Green in both modes, x10, with no new `^agc` failures.
- **The abort: not reproduced on Linux, and `decide` is not where it comes from.**
  - On 86346318d3, `HostImportFor` never calls `CheckRange`. It returns no import, so the draw falls back to the CPU path (`NotImported`) without throwing.
  - So the red test fails on the base with `the draw was not recorded GPU-side`, not with the abort's message (see §3).
  - The fix probably still removes the abort: with the cap, nothing downstream sees the past-the-end range. But that is not proven.
  - **The PC can find the real throw site with one run** of the same build plus `APS5_TRACE_UNREADABLE=1` (§3.3).
- **Main 5d9dcc42d2:** has the same `decide` code and the same import behaviour, so the same draws can't go GPU-side there. The fix applies there unchanged; the counter doesn't (§5).

## 1. The rule, and why it's exact

`Graphics/src/Draw.cpp`, `Draw()` (`:2232-2259` at d664cd364), runs before `decide` for a `countIndirect` draw:

```
readable = GuestMemory::DescribeCommitted(arguments, RangeBytes())    // the same page test as Accessible/CheckRange
if (!readable.whole):
    prefix = readable.ranges.front().second - arguments     if the first readable run starts at `arguments`, else 0
    fit    = prefix >= recordBytes ? 1 + (prefix - recordBytes) / stride : 0
    fit != 0 -> clampedArgs = *args; clampedArgs.count = min(fit, count); decide on clampedArgs' range
    fit == 0 -> IndirectDrawPath::NotImported (the CPU path, as for an unimported range)
```

If `decide` returns `Gpu` (records and count word both imported), then `args` and `indirect.args` point at `clampedArgs`, and `indirect.clamped` is set. `clampedArgs` is a local `std::optional` in `Draw()`. That keeps it alive for everything that records the draw:
- `recordDraw` runs inside `Draw()`;
- `indirectRecordCheck` copies `*args`.

So every consumer sees the capped range:
- the import (`decide`, `HostImportFor`);
- `NotePendingRead`;
- the DCC key-store and label `touches` checks;
- `passReads`, `argumentRanges`/`IndirectArgumentsVisible` and the barrier-validation reads;
- the rewritten-record scratch copy and its `cmdUpdateBuffer` loop;
- the `maxDrawCount` of `vkCmdDraw(Indexed)IndirectCountKHR`.

**Why it's exact:**
- **The records drawn are unchanged.** The CP draws `min(*countAddress, count)` records. The GPU now draws `min(*countAddress, fit')`, with `fit' = min(fit, count)`.
  - When the guest's count is at most `fit'`, which is every count whose records are all in readable memory, the two agree, record for record.
  - Only a count that names records past the readable end is cut to the ones that exist. On the console the CP would read unmapped memory there, a guest fault. The CPU path would throw in `Pm4::ReadDrawArguments` for that record.
- **`fit` is the largest n whose n records lie wholly inside the prefix:** record i spans `[i*stride, i*stride + recordBytes)`, so it fits iff `i*stride + recordBytes <= prefix`.
- **The prefix starts at `arguments`.** `describePages` clips its first run to the queried address, so `ranges.front().first == arguments` exactly when the first byte is readable. The fix never looks past a hole.
- **`DrawIndex` and the count are unchanged.** The draw stays one multi-draw, and the clamp only lowers `maxDrawCount`.
- **Other draws keep today's behaviour:**
  - A draw that isn't count-indirect is untouched. The CP reads all its records, so a range past the end is a guest fault there too.
  - A draw whose range is wholly readable is untouched too: `whole` is true, so there is no copy.
  - With `APS5_NO_GPU_INDIRECT_DRAW=1`, nothing changes.
- **The CPU path is unchanged.** It still reads `min(ReadDrawCount, args->count)` records from the packet's own parameters.

**Cost:** one `DescribeCommitted` page walk per GPU-eligible count-indirect draw, the same walk `Accessible` makes. Draws that aren't count-indirect pay nothing.

**Counter:**
- `CountIndirectDraw` takes `bool clamped` (default `false`) and counts it only for `Gpu`.
- The `[draws]` line's indirect part reads `; indirect: gpu-side N (R rewritten, P draw parameters, K clamped), cpu-side …` under `APS5_PROFILE_DRAW`. It resets with the other fields.
- Both GPU-side count sites pass `indirect.clamped`: the lean `recordDraw` (`:1939`) and the synchronous path (`:2537`).

## 2. The test: `agc_driver_indirect_count_past_end`

`tests/execution/IndirectCountPastEnd.cpp`, picked up by the `tests/execution/*.cpp` glob.
- **`TailBlock`** maps a 64 KiB-aligned 64 KiB block and leaves the page after it `PROT_NONE`. On Windows it reserves the region and commits only the block, so the next page is reserved, not committed. Only the 64 KiB block is registered (`GuestAllocations::Mutation::Add`).
- **The draw:** a count-indirect packet with `count = 8`, the count word at block offset 0, and its records at the block's end. Only 4 (or 3 indexed) records fit, so `RangeBytes()` runs past the block. The shaders are those of `IndirectDrawParameters.cpp`.
- **Each case requires exactly 1 GPU-side indirect pass** (`IndirectPassCounters`) and the exact set of covered cells in the target:

| case | guest count | records drawn | cells |
|---|---|---|---|
| `DRAW_INDIRECT_MULTI`, draw parameters (s8–s10 patched) | 2 of 8 | 2 | (0,0) (1,0) (5,1) (6,1) |
| `DRAW_INDEX_INDIRECT_MULTI`, draw parameters | 2 of 8 | 2 | (2,0) (7,1) (8,1) |
| `DRAW_INDIRECT_MULTI`, draw parameters, **counted records past the end** | 8 of 8 | 4 (capped) | the two above plus (11,0) (7,1) |
| `DRAW_INDIRECT_MULTI`, no draw parameters, constant records (`Widening`, rewritten scratch path) | 2 of 8 | 2 | (0,0) (1,0) (2,0) |

**The "count buffer = max" case is deterministic** with the fix: the cap stops at the 4 records that exist, and the GPU never reads the protected page.
- Without a cap there is no deterministic GPU outcome. lavapipe reads the host pointer directly, so it would segfault.
- I checked this with a probe: an import made while the tail was readable, the tail then protected, and the base code. The count-2 cases drew; the count-8 case crashed the process with `SEGFAULT`.

- If the unreadable page is registered as part of the allocation instead (my first layout), `importAllocation`'s `GuestMemory::Accessible` check fails (on Windows, the `VirtualQuery` loop does). That also gives `failedImport()` and null, with no throw.
- Either way the draw reads its 2 counted records on the CPU and draws correctly, just not GPU-side.

### 3.3 Where the title's abort comes from: what I ruled out, and how to find it

The message format is `verify`'s (`Execution/src/GuestMemory.cpp:674`), and only `CheckRange` throws it. `CheckRange` is called by `Read`, `Write`, `WriteChanged`, `ImportWatched` (page-aligned ranges only) and direct callers.

On 86346318d3 (= a38c704ea for these files), nothing that gets `(arguments, RangeBytes())` calls one of those:
- **`decide`'s steps:**
  - `StorageTexture::FlushPending`/`PublishShadow` work on image and import ranges;
  - `PendingLabelIn` and `CopiedWritesOverlap` are overlap tests;
  - `HostImportFor` uses `Accessible`/`VirtualQuery`, plus `ImportWatched` on the aligned run.
- **The 10 `RangeBytes()` uses in `Draw.cpp` and the one in `Execution/src/Driver/Draw/Draw.cpp:452`** only build ranges for overlap and hazard lists (`NotePendingRead`, `PassAccess`, `IndirectArgumentsVisible`, `DrainIfOverlaps`) or size the scratch copy (a GPU copy).
- **The GPU path itself** didn't throw in the probe above, with an import covering the protected tail.

`0x280020` fits `RangeBytes()` only as a non-indexed draw with stride 16 and `count = 0x28002`; the Bug Finder's log can confirm that.

**To find the throwing caller, the PC can rerun the abort with `APS5_TRACE_UNREADABLE=1`:**
- `CheckRange` then prints `[unreadable] guest memory is not readable at … from +0x<offset>`;
- `Read` adds `[unreadable]   read from +0x<offset>`.

Each offset is a module offset of the caller (`ModuleOffset(__builtin_return_address(0))`) and can be resolved against the build's symbols.

With the fix, a count-indirect draw whose range crosses the readable end no longer goes through the CPU path. If it goes GPU-side, it carries only the readable range. So any consumer of the full range is out of the picture, but only the title run can show the abort is gone.

## 5. Main 5d9dcc42d2

- **The `decide` block is byte-identical** to 86346318d3's: one `decide(args->arguments, RangeBytes(), …)` at the packet's maximum count.
- **Main's import code has the same design.** `HostImportFor` → `importAccess` (`runCovers`, else `findImport`) → `importAllocation` with `GuestMemory::Accessible` (`:1138`).
- **So main has the bug as a lost GPU path:** a count-indirect draw whose maximum-count range crosses readable memory always takes the CPU path. It doesn't throw there either. Main has no draw parameters, so that only costs speed: the CPU path draws correctly.
- **The fix applies to main unchanged.** `git apply --reject` there applies the `IndirectRecord::clamped` field, the `clampedArgs` declaration and the `decide` block cleanly.
- **The counter doesn't apply.** Main's `CountIndirectDraw(path, readMs, rewritten)` has neither the `drawParameters` nor the `nonVertex` argument, and its `[draws]` line is `gpu-side N (R rewritten)`. So the Draw.hpp signature, the `DrawProfile` field and its reset, the print and the two call sites need a small port, a later PR. Nothing was pushed for main.
