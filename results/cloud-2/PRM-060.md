### The both-on recipe, as adapted

#6012's overlay code in `present()` is the same at ca7ea10d30 (main) as at 84cae0bda (r3's merge). So e7905ca8db's recipe applied unchanged:

- `upscaler->RecordPresent(commands, slotIndex, width, height, barrier.image, state->extent, overlay ? VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL : VK_IMAGE_LAYOUT_PRESENT_SRC_KHR);`: with the overlay on, RCAS leaves the swapchain image in `COLOR_ATTACHMENT_OPTIMAL`.
- `state->overlay->Record(..., drawn || upscaled ? VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL : VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL, VK_IMAGE_LAYOUT_PRESENT_SRC_KHR);`: the overlay records from `COLOR_ATTACHMENT_OPTIMAL` when the frame was drawn or upscaled. Otherwise it records from `TRANSFER_DST_OPTIMAL`, as on main.
- `} else if (!drawn && !upscaled) {`: the final transfer-to-present barrier, only when neither path ended in present layout.

FSR's own gate is kept: `const bool upscaled = state->upscaler != nullptr && !clearOnly && PresentationUpscaler::Upscales(width, height, state->extent);`.

Check: every `VulkanDevice.cpp` line containing `upscal`, `Upscal`, `overlay` or `Overlay` was compared between e7905ca8db and the head. Two kinds of difference turned up:
- the order of `upscaler`/`overlay` in `State` and in the teardown (r3 had `upscaler` first; main's `overlay` is first now);
- 7 lines of main's own compute "dispatch overlay" code, which is unrelated to the performance overlay.
