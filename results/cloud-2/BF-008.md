## How selected columns and the reuse interact
**Decision: a selected column is skipped, because it is already cheap.**

- **Where:** in `TableSnapshotter::Column()` at the head:
  - `if (column.selected) { Select(column, records); return records; }` is at line 689;
  - main's `if (column.indirect)` branch is at 705;
  - PM-028's `const bool memoized = TableSnapshotReuse() && !records.narrowed && records.keys != 0u;` is at 737.
  - A selected column never reaches the memo. It is never kept, compared, stamped or vouched for, and it never counts in `reused … unwritten / … compared`.
- **Why not reuse it while its record is unwritten:**
  - **What `Select()` does per capture:** it evaluates the offset on the CPU and reads one record of at most 8 dwords. It also records the range it read.
  - **What vouching would add per column:** a pre-read stamp (`stampWrites`), an `unchangedSince` check and a `supplyWords` call. On top of those come the two flush-hook calls that 3cb669cb24 makes before vouching (PM-028's §5.3). That is more work than reading 8 dwords.
  - **The record moves:** its position comes from the offset evaluated at each capture, so a memo key would have to carry that value. A different offset is a different record anyway.
- **Folded selected records** keep cut #3's handling (`RecordState::Carried` in `Select()`). PM-028's keep rule never sees them.
- **Whole tables** (per-lane, readfirstlane and narrowing-skipped keys) are memoized exactly as on PM-028's branch. The reuse test's `TableWholeCode` is such a table and passes here.
- **`WordsIndex`** catches up its lazy index before every lookup, so `Select()` and the reuse can share one snapshot in any order (as in BF-007).
