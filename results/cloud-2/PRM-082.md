## Starting the thread

**A successful registration starts it if none is running:**
- `StartEventDelivery()` does nothing if `callbacks.worker` is set. So these reuse the running thread:
  - a replacing registration;
  - a registration after an unregister in the same session, because unregister leaves the worker in place;
  - a registration from inside a callback.
- NOT_INITIALIZED and PARAMETER return before the call, so they start nothing.

**If `scePthreadCreate` fails:** the code still does what bc6b4d76f9 did in Initialize3. It throws `std::runtime_error`, now named for `sceSaveDataRegisterEventCallback`. The thread starts before the callback is stored, so a failed start stores nothing, and the locks unwind. There is no new error code and no test asserts the throw.

## Lock order on every path

Registration keeps bc6b4d76f9's `calling` → `g_slots_mutex` → `callbacks.mutex`.

| Path | Locks, in order | Waits while holding |
| --- | --- | --- |
| `sceSaveDataInitialize3` | `g_slots_mutex` | nothing; it no longer touches the callbacks |
| `sceSaveDataRegisterEventCallback` | `calling` → `g_slots_mutex` → `callbacks.mutex` in `StartEventDelivery` (released) → `callbacks.mutex` (store) | `scePthreadCreate`, while holding `calling`, `g_slots_mutex` and `callbacks.mutex`. The new thread's first act is to wait on `callbacks.mutex`, and it takes no other lock until it delivers, so nothing waits on it here. |
| `sceSaveDataUnregisterEventCallback` | `calling` → `callbacks.mutex` | nothing |
| `sceSaveDataTerminate` | `callbacks.mutex` (`InEventCallback`, released) → `g_slots_mutex` → `callbacks.mutex` (detach) → both released → `JoinEventDelivery` | the join, with **no** lock held, and only if a worker was taken out |
| Delivery thread (`DeliverEvents`) | `callbacks.mutex` (wait, released) → `calling` → `callbacks.mutex` (pop, released) → callback runs holding `calling` → `callbacks.mutex` (clear `delivering`) | the guest callback, with `calling` held |
| Callback calling back into SaveData | (`calling` held) → any API: `g_slots_mutex` → `callbacks.mutex`. `calling` is recursive, so a registration from inside the callback works. | — |
| `sceSaveDataBackup`, `umountWithBackup` → `DeliverEvent` | `g_slots_mutex` and `g_state_mutex` in scopes closed before the call → `callbacks.mutex` | nothing |

**What rules out a deadlock:**
- No path takes `calling` while holding `g_slots_mutex`.
- No path waits for the delivery thread while holding `g_slots_mutex` or `calling`.
- So the delivery thread (`calling` → `g_slots_mutex`) and registration (`calling` → `g_slots_mutex` → `callbacks.mutex`) agree on order.
- A terminate from inside a callback returns BUSY at `InEventCallback`, before it takes `g_slots_mutex`.

## Handing over the thread handle

`callbacks.worker` holds the current session's `EventWorker*`, and only one session's worker is ever stored there.

**At the final terminate:**
- Inside the terminate's `g_slots_mutex` section, `DetachEventDelivery` takes `callbacks.mutex`.
- It clears the callback, userdata and pending queue, and swaps the worker out (`std::exchange(callbacks.worker, nullptr)`).
- It sets the worker's `stopping`, and returns the pointer to the terminate as a local.
- The terminate releases `g_slots_mutex` and joins only that local pointer.

**If the next session starts while that join is still running:**
- An `Initialize3` → `Register` there finds `callbacks.worker == nullptr` and stores a new worker.
- The terminating thread never reads `callbacks.worker` again, so the handle it joins can't be overwritten.
- The old thread never pops a delivery after `stopping`. It checks `worker->stopping` under `callbacks.mutex` after its wait and again before its pop, so it exits on its next pass.
- The new thread can't deliver until the old one releases `calling`, which keeps delivery FIFO.

**Without a registration:** a session that never registers leaves `callbacks.worker == nullptr`, so its final terminate gets `nullptr` back and joins nothing. A terminate that isn't the last one never reaches the detach.

## Tests

These are in `core/libs/tests/GuestSaveDataEventCallback.cpp`, in the same commit.

**`CheckSessionsWithoutRegistration`** (all platforms), run first:
- `Initialize3` → `Terminate` → `Initialize3` → `Terminate`, each returning 0, with no registration.
- On Linux it also checks that the process's thread count doesn't change at either `Initialize3`.

**`CheckDeliveryThreadStartsAtRegistration`** (Linux only):
- **How it counts threads:** it counts `/proc/self/task`, the same `/proc/self/task` technique `core/libs/tests/GuestPthreadStack.cpp` already uses.
- **Why that and not something else:** nothing in the guest API lists threads. libkernel names host threads only on Windows (`SetThreadDescription`), so a thread can't be looked up by name on Linux.
- **No hook was added to the library.**
- **What it checks:**
  - `Initialize3` adds no thread;
  - a PARAMETER registration adds none;
  - the first registration adds exactly one;
  - a replacing registration, an unregister and a registration after it keep it at one;
  - the final terminate, under the watchdog, brings the count back within 5 s.
- **Windows:** the case is skipped there, because thread counts on Windows include loader and thread-pool threads that come and go on their own.

**Restart is already covered** by `CheckIdleTerminateAndRestart`. After a full terminate, the new session's `Initialize3` and backup run with no callback; then `Register(First)` starts the thread and its backup is delivered ("the event after the restart").

**The race path, `CheckRegisterRacingFinalTerminate`, is unchanged and still passes.**
- The racing registration now also starts the thread: in the plain iterations, every OK registration starts one, which that terminate then joins.
- In the held iterations, the `Holding` registration starts it.
- The fence step's `Register(Fence)` starts the next session's thread.
