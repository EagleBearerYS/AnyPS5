### a581de867 (3a1faef0a5)

**`Execution/src/VulkanDevice.cpp`, the dispatch path, against main's 89d255c5f3.** Main's change serves a cached compute template when only its read-only buffers moved (`MovedDispatchBuffers`, a moved-buffer descriptor set in `RecordedDispatch::bindings`).

How the two paths order and where they meet:
1. **PrepareDispatch (off the mutex).** It makes the movable content key and finds the cached build. Main then runs the moved-buffer proof as a filter. On a refusal it switches to the exact key (`prepared->exact`).
   - That proof refuses every address-based build (`usesBda`, `MoveRefusal::Shape`).
   - So the filter now runs only when the cached build is not address-based (`!cached->ReusesAddressSpace()`).
   - Otherwise an address-based hit would count a `Shape` filter refusal, look up the exact key, and on a miss build again under the exact key.
2. **The dispatch (under the mutex).** A found build is revalidated with `Revalidate(shaders, nullptr, snapshots)`.
   - For a non-address build this is main's `Revalidate(shaders[0])`: without `addressReuse`, it goes straight to `proveBuild`.
   - For an address-based build it is BF-040's address branch: snapshots, cached space, proof and imports. When it passes, the space is left resumed for this use.
3. **Main's moved-buffer step** runs after a passing `Revalidate` only for a non-address hit (`DispatchMove() && !exactEntry && !cached->ReusesAddressSpace()`). It is unchanged otherwise: a refusal goes to the exact key and revalidates the entry found there, with the same call.
   - An address-based hit is never refused after its `Revalidate` passed.
   - This matters because only `resources` is released at the end of the dispatch (`SpaceRelease`), not the abandoned `cached`. If the move step could still refuse an address-based hit, its space would stay resumed.
4. **Counting.** A hit counts `AddressReuse::Reused` when the build it ends with is address-based (`resources->ReusesAddressSpace()`). On the exact-key fallback, that is the build actually used.
5. **Recording.**
   - `record.bindings = overlay` and `record.threadGroup` are main's.
   - `record.use = resources->BeginDispatchUse()` is BF-040's. It is null for any build without `addressReuse`.
   - `recordDispatch` binds main's moved-buffer set when there is one. Otherwise it calls `BindUse`, which binds the use's spare-record set or, without one, the build's own set.
   - The two never coexist: a moved-buffer set needs a non-address build, and a use needs an address-based one.
   - The completion is BF-040's: `CompleteDispatchUse` for a use, else main's.

So a dispatch that main serves from a template with moved read-only buffers is still served that way. BF-040's per-use fault record and proven-space reuse apply only on the address-based path.

**`Graphics/src/BdaResources.cpp/.hpp`: main's SRT guard (c9e38be25) composed with BF-040's per-use records.**
- Main added `SrtGuardWord` to the fault buffer, zeroed it in the build's buffer, and read it in `checkSrtGuard()` from the build's buffer.
- With a record per use:
  - `checkSrtGuard(Buffer& faults)` reads the guard from the record that `CheckFault(record)` checks;
  - `FaultRecord()` zeroes the guard word of a spare record as the constructor does for the build's own buffer.
- The parameter is `faults`, because main's function has a local named `record`; the first build stopped on `declaration of 'const auto record' shadows a parameter`.

**`docs/dev/debt/libSceAgcDriver.md`.** The "Reused address-based draw builds" line was the same on both sides. It is replaced by the branch's "draw and dispatch builds" entry, and main's new entries after it are kept.

**Main moved since 6e5b5bdf4b, found by building and reading:**
- `Fault::reserved` is now `otherFaults`. BF-040's `CheckFault(Buffer&)` took main's line as it merged.
- **c0588d274 and e6cb236d6, the unaligned BDA access.** Main's `WriteBackBuffers` now publishes a dispatch's writes before it reports an unaligned access.
  - Address-based dispatches used to complete through that path. With BF-040 they complete through `CompleteDispatchUse`, which threw before `MarkWritten`.
  - `CompleteDispatchUse` now catches `BdaUnalignedAccess`, marks the build non-reusable, marks the use's address writes, and then rethrows, as main does.
  - A new `unaligned` case runs it: a reused dispatch whose `global_atomic_add` is 2 bytes off.
  - **Not red on lavapipe:** the case passes with this hunk reverted. There, a GPU write to an imported page trips the write watch by itself (`APS5_WRITE_WATCH_IMPORTS=watch`: `watched=1 collected=17 unchanged=0` with the hunk reverted), or imported ranges are compared, not watched (`watched=0`). So the extra `MarkWritten` is not observable here.
  - #6636's own `CompleteUse` for address-based draws has the same order (fault check, then `MarkWritten`). It was left as it is, since it is #6636's code.
- **`APS5_NO_ADDRESS_DISPATCH_REUSE`.** Main's `check_conventions.py` now requires every read `APS5_*` name to have a row in `docs/dev/ENVIRONMENT.md`. The row is added in a581de867, next to `APS5_NO_ADDRESS_DRAW_REUSE`.
- `importAllocation`'s step-down, `pinnedBytes` and `spaceMirrorsKept` at ResumeSpace merged without a conflict or a build error. BF-040's code does not touch them, and the `free` case (a guest free with a cached and an in-flight reused build) passes at the head.
