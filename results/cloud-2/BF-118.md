## 2. Where main counts stage hits

The `[draw-cache] 10 s:` trace line (`DrawCacheStatistics.cpp:34`, under `APS5_TRACE_DRAW_CACHE`) prints `data-only hits (stages: N reused, M compiled; …)`.

- **Where N is counted:** `Draw.cpp`'s stage loop, `if (dataEntry != nullptr && reused[i]) ++dataStagesReused;`. It is summed into `drawEntryCounters.dataStagesReused` after the loop.
- **What it is:** the stage reuse that works when a whole draw misses. The draw's shape matches a data-only candidate, and its compiled stage is used without a build.
- **The other stage counters don't fit:**
  - `stageDataHits` is counted only on whole-draw hits.
  - `stageEqual` counts matched stages of a draw that then misses. Those stages are built again, so they save no work.

## 3. Commit 2: whole-draw hits plus reused stages (Dean's point 2, first option)

- **What it counts:** the window now counts whole-draw hits and reused stages (`dataStagesReused`) separately. The cache is bypassed only when **both** stay under the threshold.
- **What a bypass switches off** stays as in #5404: `useDrawEntries` is false, so entries are neither looked up nor inserted.
- **The values** are #5404's.

  - The relocation trial is untouched.
- **The helper:** `DrawCacheBypassWindow` (`Execution/include/Driver/Draw/DrawCacheBypass.hpp`, `Execution/src/Driver/Draw/DrawCacheBypass.cpp`) needs no device.
  - `Bypass()` counts down a running bypass.
  - `Note(hit, stages)` counts one lookup and returns true when it starts a bypass.
  - At this commit it still holds #5404's separate atomics, moved unchanged apart from the stage counter.
  - `Driver` keeps `drawCacheBypassed()`, which applies the switch and counts bypassed draws, and `noteDrawCacheOutcome(hit, stageHits)`.
- **Where the note moved:** from after `lookupDraw` to after the stage loop, the first place the reused stages are known.
  - **Consequence:** a draw that returns `Rejected` while a stage is being built is no longer noted. The commit message says so.
- **Text:**

## 4. Commit 3: one compare-exchange on a packed counter (Dean's point 3)

- **The packing:** lookups, whole-draw hits, reused stages and the bypass countdown share one `std::atomic<std::uint64_t>`, 16 bits each.
  - A `static_assert` checks that `Window` and `IdleDraws` fit in 16 bits.
  - Reused stages saturate at 0xffff.
- **The updates:**
  - `Note` is a compare-exchange loop: it either increments the three counters, or closes the window by zeroing them and setting the countdown, all in one step.
  - `Bypass` is a compare-exchange decrement of the countdown.
- **Test (c):** 4 threads note 256 all-miss windows of 2,048 lookups, released together, and expect exactly 256 bypass starts.

**What it shows:**
- **The head never bypasses in this mode.**
  - **Evidence:** a traced head run (`APS5_TRACE_DRAW_CACHE=1`, 20 frames) shows, per 10 s, 5,198–6,952 lookups with 0–4 whole-draw hits, and 489–644 reused stages (9,899–13,260 compiled).
  - **Per window,** that is about 9–11% of lookups, or about 190–210 reused stages per 2,048, against a threshold of 102.
  - **Result:** commit 2's rule keeps the cache on, as Dean's point 2 asks.
- **#5404 alone bypasses about 90% of draws.**
  - **Per run:** two bypasses of 16,384 draws were printed, 4,097 lookups ran, and a third bypass was still running at the end, unprinted (40,800 draws in total).
  - **Saving:** about 31 µs per draw in key/lookup/validate.
  - **Cost:** about 8 µs more decode, since register-key decode skips are lost, about 7 µs more recompile, since the data-only stage reuse is lost, and about 2.5 µs more vectors.
  - **Net:** about 15–20 µs per draw of driver work (about 10%).
- **Wall time per draw is the same in every arm, within noise.** On lavapipe the rasterizer dominates (llvmpipe CPU 1,400–1,700 µs per draw over 4 threads), so the driver saving doesn't reach the frame time here. The PC's measurement is the one that decides.

**Caveat for the maintainer:**
- **The two thresholds aren't the same strength.** Both are 5% of the window's lookups, i.e. draws, but a draw has about 2 stages.
- **Here,** the reused stages are 5.1% of the stages built (591 of 11,506 in one window) but about 10% of lookups.
- **Counted as a share of stages,** this frame would sit right at the threshold. Counted against draw lookups, it is twice over.
- **Whether that reuse is worth keeping the cache on for:** on this harness it saves about 15 µs and costs about 31 µs of lookup per draw.

**Also seen:** the `[draw-cache] bypassed` line is printed only from the lookup path (`maybeReportDrawCache`), so draws bypassed at the end of a run go unreported until the next lookup. This is #5404's behaviour, kept unchanged.
