## Choice: case 7 added, case 6 kept

Case 6 stays as the case where **both** settles are pending. Only its label changes, to "an eight-sample target whose color and FMASK imports both have pending settles". It keeps documenting the shared-batch path, which is accepted with or without af1fa8edb3.

**Case 7, `Case::PendingFmaskAlone`**, is new. It is labelled "an eight-sample target whose FMASK alone has a pending settle". Its target and memory are the same as case 6's: 128x128 R8G8B8A8, 8 samples, `RenderTarget` tiling, pipe-aligned DCC, CMASK fast clear, import 589824 bytes, FMASK 65536 bytes.

### Why case 6 could not fail

Case 6 imports both regions off the GPU lock, so both are Wanted. Then the color loop of `initialDccClear` (`MultisampleTarget.cpp:562`) calls `WatchedAfterSettle` on the color range. That calls `settleImportsNow` (`GuestBufferMemory.cpp:1144`), which puts the color import first in `settleWanted` and calls `submitSettleBatch` (`:1008`). The batch loop (`:1035`) takes **every** Wanted settle, up to 256, so the FMASK's settle goes in the same batch. `settleImportsNow` then waits for that batch, reaps it and rewatches both imports. By the time the FMASK check runs at `:579`, the FMASK is already watched, so the old plain `GuestMemory::Watched` passes too. That is the "2 settle reads submitted, 2 back in the write watch" the 3070 printed on both trees.

### How case 7 keeps only the FMASK's settle pending

Option used: **the target's import is made and settled before the FMASK's import exists, under the GPU lock with a reaped batch.**

1. All three allocations are registered first, in one `GuestAllocations::Mutation`: the target's 589824-byte block, the 65536-byte FMASK, and the 64 KiB-aligned resolve destination. The FMASK is in its own registered allocation, with unregistered 64 KiB gaps on both sides, so it can't join the color import (BF-155's lesson).
2. The target's import is made off the GPU lock with `HostImportFor(context, address, importBytes)`. The existing check says it starts compared: base, bytes, `unwatched`, `!Watched`.
3. Under `std::lock_guard gpu(GpuMutex())`, `WatchedAfterSettle(context, address, importBytes)` must return true. This takes the `settleImportsNow` path:
   - the Wanted settle is submitted;
   - the test waits on that batch (`waitSettleBatch`);
   - `reapSettleBatches` and `rewatchSettledImports` run.

   The counters must show at least one settle submitted and one rewatched in that call. At this point the FMASK has no import, so this batch cannot carry it.
4. **Precondition: the planes are watched.** For each of the color (`address`, 524288 bytes), DCC (`address + colorBytes`) and CMASK planes, `Watched` must hold, and `ExistingHostImportFor` must give no import or one with `unwatched == false`. On failure the message names the plane with `describe`.
5. The counters are snapshotted (`quiet`). Then the FMASK's import is made off the GPU lock with `HostImportFor(context, target.fmaskAddress, fmaskBytes)`.
   - Off the lock, `settleUnwatchedImports` returns early (`:1135` requires the GPU mutex), so nothing is submitted.
   - Base and size are whole 64 KiB blocks, so the import enters `pendingSettles` as Wanted. It does not get `settleOnDemand` (`importAllocation`, `:1878-1884`).
6. **Precondition: the FMASK is pending.**
   - The FMASK import's base and bytes match, it is `unwatched`, `!settleOnDemand` and `!Watched`.
   - `describe` now also prints "settled on demand %d" (its buffer grew from 224 to 256).
   - No accessor exposes the settle phase, so this is how the test checks "Wanted". The green run's single settle read is what confirms the FMASK was pending.
7. **Precondition: nothing was submitted before the use.** The GPU lock is taken, `before = HostImportSettles()`, and `before.submitted == quiet.submitted` must hold.

**What the use then does.** Nothing between `MultisampleTargetView` and `initialDccClear` imports or settles. `acquire` makes a new target, and its constructor calls `initialDccClear` first.
- **Color loop:** the target's import over color, DCC and CMASK is no longer `unwatched`, so `settleImportsNow` finds nothing it needs and returns before submitting.
- **The FMASK check is the only place a settle can be submitted:**
  - **With af1fa8edb3:** `WatchedAfterSettle` submits, waits for and rewatches the FMASK's settle alone.
  - **Without it:** plain `Watched` is false, and the target is refused.

**Settle counts.** The counters don't separate the two checks. So the case requires **exactly 1 settle read submitted and 1 back in the write watch for the whole use**. Since the color, DCC and CMASK planes had no pending settle (step 4), that one read is the FMASK's.

### Case 7's checks after the use (green)

These are the existing case 6 checks, which case 7 shares:
- Accepted, with `after.submitted - before.submitted == 1` and `after.rewatched - before.rewatched == 1`.
- The target's import is still watched and not `unwatched`.
- The FMASK is `Watched`, and its import is not `unwatched`.
- The resolve into the destination reads `0xffffffff` everywhere: the DCC fast clear.
- After a CPU store of `0x22` into the FMASK, re-acquiring the target refuses with `writes to a resident native FMASK are not implemented`.
