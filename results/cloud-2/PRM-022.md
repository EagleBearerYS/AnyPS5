### 2.1 The `agc_driver_graphics` abort

**It is main's failure.** It reproduces on main eb901bcf4e alone, 0 of 5, with the identical message.
- It is absent at main 3f171d03e0: #6641, which merged that main, passes the test alone.
- So it arrived with one of main's merges between them: #5875, #5884, #5886, #5804, #5899, #5914, #5872 or #6784.

**Where it throws.** gdb with a breakpoint on `__cxa_throw`, on main's build:

```
ShaderRecompiler::DecodeRdnaVop2(...) [clone .cold]
ShaderRecompiler::DecodeRdnaInstruction / DecodeRdnaProgram / RdnaInstructionDecoder::Decode
ShaderRecompiler::ShaderPreparationContext::AcquireFrontend
ShaderRecompiler::PrepareResourceProgram / RecompileImpl / Recompile
(anonymous namespace)::orderedPixelShaderTests()::{lambda(std::span<std::string_view const>)#1}::operator()
(anonymous namespace)::orderedPixelShaderTests()
```

**What it decodes.** The lambda is `vertexWords` (#5804's vertex BDA terminate test, main `tests/Graphics.cpp:5780-5795`).
- A breakpoint on `DecodeRdnaProgram` shows the two pixel shaders' 12-word spans as written (`0x7e040f00 0x7e060280 0xdc208001 …`).
- The vertex lambda's span points at **12 zero words** (`ptr=0x555555762520`, in the test executable's data region).
- Word 0 then decodes as VOP2 opcode 0, which isn't in `vop2Opcodes`. That throws `VOP2 opcode is not implemented`.
- None of the shader's real VOP2 words (0x25, and 0x02/0x03 if misaligned) is unimplemented.

**Why.** `vertexBdaCode` is a **non-static `constexpr` local** `std::array`. The `[&]` lambda puts it into `request.shader = {…, vertexBdaCode, …}`.
- GCC 13.3 at -O2/-O3 emits a zero-filled object in its place.
- A 30-line standalone program with the same shape reproduces it:
  - `g++ -std=c++20 -O2/-O3` reads 0 instead of 0x7e040f00;
  - -O0 reads it correctly;
  - clang++ -O3 reads it correctly;
  - `static constexpr` or plain `const` read it correctly.
- GitHub's ubuntu-24.04 runner uses the same g++ 13.3, which is why the PR's Linux job fails.
- The GitHub Windows job "passed" because it ran 72 tests with 47 skipped. `agc_driver_graphics` needs a Vulkan device, which that runner lacks.

**Where it stops in the log.** The content-key lines are the last stdout before the abort: `ResourceContentKeyTests` runs at main `Graphics.cpp:7805` and `orderedPixelShaderTests` at `:7823`. The tests in between print nothing.

**Which part of #6454 meets which main change:** none. #6454 changes neither the decoder (`RdnaDecoder/` is identical to main's) nor this test.

**Fix:** fork **`followup/6454-main-merge` = 11f43871d** on 51d4babc64, one commit: `test(agc): keep the vertex terminate test's code in static storage`.
- `vertexBdaCode` becomes `static constexpr`, as the pixel shader's `OrderedBdaPixelCode` already is at namespace scope.
- It belongs on main too; it applies there unchanged.
- **Red:** 51d4babc64 and main eb901bcf4e, `agc_driver_graphics` alone 0 of 5.
- **Green:** main + the same one-word change: 3 of 3 passed. At 11f43871d, the full Linux job:
  - `99% tests passed, 6 tests failed out of 1298` (88 s): the 5 IPv6 tests and the settle flake (alone 5 of 5 passed);
  - `agc_driver_graphics` alone 5 of 5 passed;
  - `check_skips`: `guest_sce_net` only;
  - `tools/check_conventions.py --base 51d4babc64 --head HEAD`: `All conventions checks passed.`, 0 added `//` lines.

### 3.2 Composition: #5872's lazy preparation, #6366's deferral, and main's async driver log

- **#5872 × #6366:** fccb6ff76c's `ShaderRegistry.cpp`/`.hpp` are byte-identical to PRM-018's resolution (`integration/6366-x-5872` 65a4d2c4be). `PreparedShaders.cpp` differs only by:
  - the `AsyncLog.hpp` include;
  - the two `FlushAsyncLog_nid_no_patch()` calls (`:790`, `:803`).
- **How the async log works:**
  - `InstallAsyncLog_nid_no_patch()` (driver constructor, `Execution/src/Driver/Lifecycle.cpp:132`) installs the sink at `AsyncLog.hpp:194`.
  - After that, every `APS5_LOG_*` line goes to the logger thread (`LogMacros.hpp:62` → `AsyncLog::Write`, `AsyncLog.hpp:97`).
  - Plain `fprintf(stderr)`, `LogCoalescedStderr_nid_no_patch` (`:387`) and the PM4 ring's direct writes stay synchronous.
  - `Flush()` (`:156`) waits until the logger has written every line queued before the call, from any thread (4e2647260).
- **Is the flush enough for every check that reads the driver's log?** Yes.
  - **Counts:** every line `Deferrals()` counts (`:838`) is ShaderRegistry.cpp:924's `APS5_LOG_ERR` ("…when the title created its pipeline (%s)…"). It is logged on the caller's thread inside `AgcDriverResolve*Abi`, before `Finish()`'s flush.
  - **Reason strings:** the checked reasons (`is not a valid runtime value`, `statically bound vertex attributes …`, `custom per-vertex interpolation …`, the VGT one) are the `%s` of that same line.
  - **Absence check:** the one absence check (`:1114`, `has no artifact prepared at registration`, ShaderRegistry.cpp:486) is logged on the queue worker during the draw. `AgcDriverWaitIdle_nid_postfix()` inside the action returns only after it, so it is queued before the flush.
  - **Leak-in:** the constructor's flush keeps earlier lines out of a capture.
  - **Coalescing:** `Write` never coalesces, so counts can't be cut.
- **Are there other deferred lines a test counts?** No.
  - **Other stderr captures in the merged tree:**
    - `Flip.cpp` reads `[gpu] driver failure` (fprintf + fflush, `Lifecycle.cpp` PrintFailure);
    - `Pm4.cpp` reads `[pm4 ring]` lines (direct `write`, `SubmissionRing.cpp`);
    - `ComputeTableCalls.cpp`, `GuardedNullPointer.cpp` and `ImageTable.cpp` read BDA fault reports. `BdaResources::CheckFault` throws, and `Recorder.cpp:3844` prints through `LogCoalescedStderr_nid_no_patch`, which is synchronous.
  - All of these are synchronous, and #6366 adds no log line they read.
  - **#6366's only new line** is ShaderRegistry.cpp:924, read only by the flushed capture.
  - **ctest regex checks:** the only `FAIL_REGULAR_EXPRESSION` near this code is the draw-cache reuse tests' `FATAL:`, unrelated to #6366.
  - **One caveat on main's side:** `LogCoalescedStderr` drops the 4th and later identical lines within 10 s (`Admit`, `:131`). A test that checks the same BDA fault message per run more than three times inside 10 s would lose lines. None does today, and #6366 doesn't change that path.

### 4.1 Composition: #1747 (pipelined dispatch) and #4855 (submission ring) against #6641's shutdown order

**Verdict: nothing new outlives the stop-and-join.**

**#6641's order** (`Execution/src/Driver/Lifecycle.cpp:102-133`):
1. `stopping` is set and every worker's pending work is cleared;
2. the workers are joined;
3. `DrawPipeline::Queue0().Stop()` (`:121`);
4. the worker sampler and registration preparation stop, then the pipeline-library worker;
5. `device.Reset()`;
6. the guest-buffer workers, compare helpers and shader disk cache are shut down;
7. the async log is flushed.

**#1747's pipelined dispatch uses the same, single committer** (`DrawPipeline::Queue0()`, a leaked singleton). There is no second pipeline or thread.
- **Every `Enqueue` site runs on the queue-0 worker:**
  - the dispatch commit (`Dispatch.cpp:447`);
  - the draw commit (`Draw/Draw.cpp:588`);
  - the queued fill, only for `queueId == 0` while `DrawPipeline::Active()` (`BufferFill.cpp:407`);
  - the end-of-submission `submitOpenWork` and `deferCompletion` (`PacketExecution.cpp:410-414`, `QueueWorker.cpp:65-75`).
- So nothing can enqueue after step 2.
- **`Stop()` drains before it joins** (`DrawPipeline.cpp:176-187`). `run()` breaks only once `items` is empty (`:141`), so every deferred completion and dispatch commit runs, before `device.Reset()`.
  - Those commits capture the `Driver` singleton, which never dies, plus `shared_ptr`s and copies.
  - A completion's `submitOpenWork` records on the device, which is still alive.
  - `completeSubmission` only marks, forgets and notifies. It starts no worker: `Submission.cpp:462` starts one only in `Driver::enqueue`, a submit.
- **Late or failing commits:**
  - An `Enqueue` after `Stop()` runs inline (`closing`, `:78-82`).
  - A commit that throws during `Stop()` goes to `Driver::ReportFailure` (`Lifecycle.cpp:193`). That takes `mutex`, not the `shutdownMutex` that `stop()` holds, so it can't deadlock, and `Shutdown()` rethrows it.

**#4855's submission ring starts no thread:**
- its storage is a leaked heap singleton (`SubmissionRing.cpp:59`);
- `PrepareSubmissionRing` registers only a `noexcept` failure-report hook (`:206`), which reads the ring under its mutex;
- `StallWatch::Check` (`:265`) runs inline on a waiting thread.

So nothing of the ring outlives the sequence, and its dumps after shutdown read only owned copies.
