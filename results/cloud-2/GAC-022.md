## Summary
- **Lock safety: no deadlock at any caller.** One correction to the task's premise: `GuestMemory::GpuMutex()` is not a `std::mutex`. It is `GpuMutexType`, which wraps a `std::recursive_mutex` (GuestMemory.hpp:127-152, "The mutex is recursive"), on d71ef7b1e1, 634e869a57 and upstream/main.
  - Every caller except two already holds the mutex, so the note's `lock_guard` only re-enters it.
  - The two exceptions are the labels the CPU executes, at PacketExecution.cpp:209 and :325. They take the mutex fresh while holding only the shared device-use gate. That is the same state in which main's own code takes it in the same packet loop, so no new lock order or wait appears.
- **Cost: a zero label now costs O(live storage images), all under the GPU mutex.**

  | Live images | Added per call, warm caches | Added per call, caches evicted |
  |---|---|---|
  | 0 | +0.05 µs | +9 µs |
  | 3 | +0.07–0.17 µs | +10 µs |
  | 259 | +1.7 µs | +47 µs |
  | 3,000 | +117 µs | +560 µs |

  - A label with value 1 costs about 30 ns on both builds. Main's `noteLabelStore` costs 29-35 ns, whatever the image count and contention.
  - When a second thread holds the mutex in short sections, 13-27 % of zero labels wait (p99 40-110 µs with 0-3 images). That thread's own sections also drop from 206-230k/s to 104-107k/s with 0 images, and to 5.6-9.2k/s with 3,000.
- **Why it scales:** `ClassifyFill` walks the whole live list twice for every one-value store. Yet an 8-byte store can only be a key fill of an image whose `dccAddress` is the store address and whose guest bytes are under 2,304 (1,280 for 4 bytes). A gate on an index of live `dccAddress`es would make the common miss O(1), with no GPU lock (§2.4, proposal only).
- **Sample-time alternative:** cheaper per call and independent of labels. The check costs 0.65-1.2 µs per sampled pending DCC image when the keys are unchanged. After a CPU write it costs 2.2-9 µs, plus a 1.1-15 µs re-scan, once per write. But `UnchangedSince` counts the title's CPU stores, so it would serve the clear that #4794 exists to ignore (§3).

## 1. Lock safety (code reading at d71ef7b1e1 and 634e869a57)
**What the note locks** (LabelHistory.cpp:18-27): `OneByteValue` first, then `lock_guard(GpuMutex())`, then `ClassifyFill`. A Keys result also calls `NoteKeysFill`.
- Both take `live.mutex`, a leaf (Texture.cpp:163-164). Nothing takes another lock under it.
- The mutex is released before `noteLabelStore` takes `labelStoresMutex` (:32-33). So the note adds no GpuMutex → `labelStoresMutex` order that main didn't already have at callers holding the mutex.

**When a re-entry can block:** a recursive acquisition by the holding thread never blocks. Only a thread that doesn't hold the mutex can wait, so the question per caller is whether the mutex is already held.

**`WriteLabelOnGpu`'s callers:** PacketMemory.cpp:42, :91 and :131, and DeferredLabels.cpp:117. All four are under the mutex (rows 3-6), and each is followed on the same thread, under the same lock, by its `noteLabelStore`. (tests/execution/UnimportedLabelOrder.cpp:71 is a test.)

**Why rows 1-2 cannot deadlock.** They are the only fresh acquisitions. The thread holds the device-use gate (shared), plus the flip hold in row 1.
- **Same state as main:** main's code takes the GPU mutex fresh in exactly that state, in the same loop:
  - every draw and dispatch packet: `deviceUse` at :130, then Draw.cpp:49 or Dispatch.cpp:39;
  - this flip's own flush, a few lines later at :220;
  - for row 2, `preparePacketMemory`, which took it at PacketMemory.cpp:86 for this same packet before refusing the GPU write.
- **No reverse order exists:**
  - `deviceReplacement` is taken only at PacketExecution.cpp:130 (shared, at the top of each packet, with no GPU lock held) and at Presentation.cpp:46 (`AttachWindow`: unique, then the GPU mutex at :48). That is the same order.
  - No path holds the GPU mutex while acquiring `deviceReplacement`, which is the edge the writer-preferring gate would need for a cycle.
- **Same waits as before:** any wait-for cycle that "worker blocked on the GPU mutex" could close already exists on main through those draw and flip acquisitions.
- The note's unlock there is outermost, so it runs the GPU unlock hook (GuestMemory.cpp `GpuMutexType::unlock`), as every outermost unlock does. The hook must not take the mutex (GuestMemory.hpp:155-157).

**-ports:** #1201's pipeline guards the one dangerous pattern itself. `Drain` throws if called under the GPU lock (DrawPipeline.cpp:146), and `Enqueue` can block only on the pipeline's own depth. Rows 7-8 add only a re-entry. Whether -ports' own acquisitions are safe is #1201's question and is not changed by the note.

**Verdict:** safe at every caller. The note's only effect on locking is new contention: rows 1-2 and their -ports twins now take the GPU mutex for every one-value label the CPU executes, and every caller now holds it for the length of `ClassifyFill`, measured below.

## 2. Cost (Linux, lavapipe, Release)
### 2.1 Method
- **Harness:** scratch `tests/execution/NoteLabelStoreCost.cpp`, built as an execution test with the CI mirror's flags (`-O3`, GCC 13), at d71ef7b1e1 and at 2559e9623. Both builds use the same harness source.
  - It calls the real `Driver::noteLabelStore` on `Driver::Get()`. A member pointer is taken through an explicit template instantiation, which C++ exempts from access checks, so no driver code changes.
  - The library check: the fix's `libSceAgcDriver.prx` holds the `[dcc-keys] title stores keys … in a packet store` string, and main's does not.
- **Live images:** made with `StorageTexture::Create`.
  - Each is a 128×128 RGBA8 64 KiB-tiled surface with its DCC keys right after it (`dccAddress` = base + 64 KiB, keys 0xff), one per 128 KiB slot.
  - Creating 3,000 took 1.6-1.8 s.
  - The label is 8 bytes in a separate buffer. Before each step the harness checks that `ClassifyFill(label, 8)` is None and that no image's `dccAddress` is the label.
- **Machine:** 4-vCPU Xeon @ 2.80 GHz VM (L2 4 MiB per core, L3 33 MiB), llvmpipe (LLVM 20.1.2), `GALLIUM_OVERRIDE_CPU_CAPS=avx`. The measuring thread is pinned to CPU 1, and the contender to CPU 2. Nothing else ran.
- **Statistics:**
  - "hot" is the median of 7 batch means, each about 200 ms long;
  - percentiles come from individually timed calls (`steady_clock`, its 20 ns overhead subtracted);
  - "cold" streams 64 MiB between calls, which flushes L1-L3 and the TLBs, and times only the call.
- **Contended:** a second thread loops `lock_guard(GpuMutex())`, spins for the hold, unlocks, then spins for the gap. Two settings were run: 2 µs hold / 2 µs gap, and 20 µs / 20 µs. A call "waited" if it took more than the uncontended p99 + 1 µs.
- Two full runs per build. The ranges below cover both.

### 2.3 Breakdown (fix build, warm caches)
- `GpuMutex` lock + unlock alone, uncontended: 32-60 ns.
- `ClassifyFill(label, 8)` alone with the mutex held: 22-73 ns at 0-3 images; 1,605-1,796 ns at 259; 105,331-112,172 ns at 3,000. Main's build gives the same numbers (1,616-2,025 and 121,783-128,858), since the code is identical.
- So a zero label's added cost is the lock plus `ClassifyFill`. `ClassifyFill` makes two passes over every live image:
  - the `overlapsLive` loop (Texture.cpp:3826-3828);
  - with nothing covered, the `keysFillMatches` `any_of` (:3868).
- Each pass reads several fields of a separately allocated `StorageTexture`: about 6-8 ns per image while the list fits in cache (259), and 35-43 ns per image at 3,000, where it no longer fits in L2 or the TLB.

### 2.4 Why the scan is almost always wasted, and a cheaper gate (proposal only)
`keysFillMatches` (Texture.cpp:3071-3075) returns true only when `descriptor.dccAddress == address` and `bytes >= guestBytes / 256`. So:
- an 8-byte store can be a key fill only for an image at exactly that `dccAddress` with fewer than 2,304 guest bytes;
- a 4-byte store, only for one with fewer than 1,280;
- `ClassifyFill` answers Keys only through that test.

A gate keyed on the address would make the miss cheap without changing any answer:
- keep the live images' `dccAddress`es in an index, a hash set or sorted vector maintained where `Live()` is already updated under `live.mutex`;
- check the store address before taking the GPU lock, and only on a hit take the lock and run `ClassifyFill` as now.

Expected cost of a miss: one leaf-mutex hash lookup (tens of ns). Rows 1-2 would no longer touch the GPU mutex for ordinary labels, and the contention above would disappear. The packet-store and WRITE_DATA tests (`dma-fill`, `write-data`, KeysClearOverPending.cpp) write at a `dccAddress`, so they would still be noted. Not built: the task is report only.

## 3. The sample-time alternative
PM-037 §2 suggested deciding at sample time instead: when `UnchangedSince` over an image's key range fails, re-read the keys before serving its pending results. Most of that machinery already runs in the sampled-texture lookup at d71ef7b1e1:
- it scans the keys of every sampled DCC surface with pending results (`scanKeys()` for the ClearSingle check, ShaderResources.cpp:626);
- it collects and stamp-checks the texel range (:658-659).

Today a clear found in the keys replaces the pending results only when the driver noted that fill on the image (`IsDccClear(source->FilledKeys())`, :611), which is what this fix's write-side note feeds.

**What the alternative would cost** (second scratch harness, write-watched memory, warm):
- **Per lookup, keys unchanged:** `CollectWritesUncached` + `UnchangedSince` over the key range costs 645-1,165 ns (p50), for a 128×128 surface's 256 key bytes and for a 3840×2160 surface's 130,560 alike. The harness thread has no collect epoch, so every call walks; on a queue worker a repeat within one epoch is a memo hit.
- **Right after a CPU write:** the check costs 2.2-3.1 µs (256 B) or 7.6-8.9 µs (130 KB), because the walk re-arms the written pages.
- **The re-read:** 1.1-1.5 µs or 6.1-14.9 µs, once per write.

It is paid per sampled pending DCC image per draw, independent of labels and of the number of live images. Compare the write side's +1.7 µs (259 images) to +117 µs (3,000) per one-value label, under the GPU lock.

**Why it changes #4794's CPU-store policy:** `UnchangedSince` counts every writer, and the title's CPU stores to key memory are collected and stamped like any other write.
- **What main does:** a clear the title writes from the CPU while results are pending is not served over those results, because only driver-noted fills are.
- **What #4794 adds** (head c8159c564, ShaderResources.cpp): it pins that rule down for Bendy, which stages its next frame's clear keys behind a feedback loop. It flushes the pending results at a staged-clear sampled read and reads the keys as uncompressed for that read.
- **The conflict:** a re-read triggered by `UnchangedSince` would serve exactly that staged clear over the drawn results, which is the bug #4794 fixes. Adopting it means deciding that CPU-written keys do apply to pending results, the opposite of #4794 and of main's refusal.
- **Keeping #4794's rule:** the check would have to use the CPU/driver split the tracker keeps per 64 KiB block (`UnchangedSinceCollected`, `ChangedBlocks(…, cpu)`).
  - Driver-executed stores go through `GuestMemory::Write` (`StoreOwnBytes`) and are stamped as the driver's, so they would still count.
  - But a block that both the title and the driver wrote since the draw reads only as CPU-written, so the driver's key write would be missed.
  - Shader and BDA stores reach the tracker only when written back.
  - So most of the "catches every writer" gain is lost.
- **Outside the write-watched arena** (host imports that are compared, not watched), `UnchangedSince` is always false. The check would need a byte snapshot of the keys taken at draw time instead.

That is why the owner has to choose the CPU-store policy before the sample-time check can be built.
