## 1. #5703: fix(libkernel): commit a reserved host stack before protecting it (head 187e5fc0ac)

### Verdict
**Correct for the case it targets.** On Windows, a guest protecting its host thread's whole reported stack, reserved pages included, now works instead of throwing "mprotect of uncommitted memory outside the guest arena" (DM:134-135 on main).

There are two real gaps:
- **The same call fails on Linux's main thread.** Fixed by the follow-up.
- **On Windows the fix drops the thread's guard page.** Proposal only, because it is Windows code.

DM below means `core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp`, TH means `…/Pthread/src/Thread.cpp`, and DMX means `…/DirectMemory/Export.cpp`; line numbers are on main unless noted.

### Root cause and the earliest point
`sceKernelIsStack` reports the range from `HostStackLimits`:
- **Windows:** `GetCurrentThreadStackLimits`, which includes the reserved pages and the guard page.
- **Linux:** `pthread_getattr_np` (TH:174-194). For the main thread that range is sized by RLIMIT_STACK and is mostly unmapped.

The guest then protects pages the host never made accessible. The fix can live at either end:
- **Report only usable pages.** #5918 does this for adopted Windows threads.
- **Make the range usable when it is protected.** That is #5703 on Windows and the follow-up on Linux.

A more general version would commit or map the reported range once, when the thread is adopted, and keep a guard page below it, which is what the PS5 reports. Every later protect would then work and the guard would survive.

### Siblings

| Path | OS | Covered by #5703 | Note |
|---|---|---|---|
| Main thread, whole or low-part protect | Windows | yes | the new commit of reserved pages |
| Adopted host threads | Windows | yes | same path |
| Guest threads from `scePthreadCreate` | Windows | n/a | the reported range is fully committed (TH:699-724) |
| Host stack inside the arena interval | Windows | yes | `Owns` skips the placeholder commit |
| The PAGE_GUARD page and the reserved tail | Windows | **no** | `VirtualProtect` clears PAGE_GUARD (DM:130-133); see gap 2 |
| PROT_NONE over reserved stack pages | Windows | **no** | silently skipped (DM:134); stack growth later commits them read-write |
| Fiber host stacks (libSceFiber/Export.cpp:274-287) | Windows | commit n/a, guard **no** | a fiber's no-access guard page inside a non-adopted thread's reported range would be reprotected (inferred) |
| **Main thread** | **Linux** | **no** | the range is mostly unmapped; `mprotect` fails with ENOMEM (gap 1) |
| Adopted host threads | Linux | no (a different problem) | mapped, but the range holds the thread's TCB and static TLS, with no host-only guard (TH:276-292 covers only guest stacks); a guest read-only or PROT_NONE protect there would break the host thread (inferred, LOW) |
| Guest threads, the guard, the margin and the TCB | Linux | n/a | already guarded with EACCES and tested (GuestKernelStackProtect.cpp:117-121) |

### Gaps
**1. MEDIUM, Linux main thread: the protect fails. Fixed by `followup/5703-linux-main-stack`.**
- *Why it is reached:* the guest's `main` runs on the kernel's grows-down main stack. The Linux entry stub does not switch stacks (relinker `EntryStubBuilder.cpp:15-38`).
- *What `pthread_getattr_np` reports:* on glibc 2.39 here, 0x7fd000 bytes, of which only 0x23000 are mapped.
- *Where it fails:* `mprotect` over the reported range fails with ENOMEM at DM:1053. The posix `mprotect` then returns EINVAL (PosixMemory.cpp:198-218), and `sceKernelMprotect`, `sceKernelMtypeprotect` and `sceKernelBatchMap` (DMX:227-229, 348-350, 471-474) let the exception through, which stops the title.
- *Tests:* #5703's new test is `#ifdef _WIN32`.

**2. MEDIUM, Windows: stack-overflow detection is lost after a whole-stack protect.**
- *How:* `CommitReservedPages` commits the reserved tail, and `VirtualProtect` clears PAGE_GUARD on the guard page. The thread is left with no guard page and no reserved tail, so an overflow corrupts the memory below instead of raising a stack overflow. The PS5's reported range excludes the guard.
- *Proposal:* commit and protect only above the guard. Query the guard page (PAGE_GUARD) and the bottom reserved page of the allocation, clip `inside` to start above them, and leave them as they are. #5918's reported range already does this for relinked games' main threads.

**3. LOW-MEDIUM, Windows: a partial range breaks growth.**
- *How:* a range that starts above the bottom of the reservation but covers the guard page leaves reserved pages below with no guard above them. Normal stack growth into them then faults instead of committing. On main the same call failed cleanly. Inferred, not run.
- *Proposal:* the same clip as gap 2.

**4. LOW, Windows: PROT_NONE over reserved pages is still a silent no-op.** The commit happens only for other protections, so a guest's PROT_NONE on not-yet-committed stack pages is lost once the stack grows into them. The Linux follow-up maps those pages and applies PROT_NONE.

**5. LOW: error codes.**
- The new throws carry Windows error codes, but the posix `mprotect` compares them with POSIX numbers. A commit-limit failure (1455) becomes EINVAL instead of ENOMEM.
- Pages are committed read-write before the final protection, with no rollback if a later step throws.

**6. INFO:**
- The commit charge is the whole reserved range: about 60 KiB on a relinked game's main thread, up to about 2 MiB on a MinGW test binary's main thread, and 1 MiB on the PR's test thread.
- `Owns` scans the host-region list on every call (GuestArena.cpp:280-285).
- Relinked games are not HIGH_ENTROPY_VA (WindowsPeWriter.cpp:35), so their main stack is probably below the arena and `Owns` mostly matters for test binaries (inferred).

### Tests per variant

Every protect, partial or whole, PROT_NONE or not, would then keep a working guard and never touch host-only state.


## 2. #5966: fix(libSceNet): let a datagram receive on an unbound socket wait on Windows (head 4211a41177)

### Verdict
**Correct for what it targets, but it adds one hang.**
- *What it fixes:* on Windows, `sceNetRecv`, `sceNetRecvfrom` and `sceNetRecvmsg` on a datagram socket with no local address now wait until a bind, connect or send gives it one. Winsock fails such a receive with WSAEINVAL; FreeBSD 11.4's `soreceive_dgram` waits.
- *What it breaks:* the wait ignores `sceNetShutdown`, so a blocking receive with no timeout on an unbound socket now waits until a bind or close. Before the PR it failed at once; FreeBSD returns 0.

E below means `core/libs/prx/libSceNet/Export.cpp` on main; PR5966 lines are on the PR head.

### Root cause and the earliest point
**Root cause:** Winsock refuses to receive on a socket that has no local address, and FreeBSD does not.
- *A fix at socket creation* (bind every datagram socket at once) would change what `getsockname` reports. FreeBSD reports 0.0.0.0:0 until the first bind or send, and main already emulates that (E:1156-1160).
- *So the receive side is the right place,* and the PR's wait is reasonable.
- *A more general version* would share the wait with libkernel's own socket layer. That layer has the same Winsock error on the same receive paths and is not covered (gap 2).

### Siblings

| Path | Unbound UDP on Windows | #5966 |
|---|---|---|
| `sceNetRecv` (E:886-905), `sceNetRecvfrom` (E:907-932), `sceNetRecvmsg` (E:993-1037) | WSAEINVAL → EINVAL | **covered** (PR5966:879, 904, 993) |
| libkernel `recv`, `recvfrom` and `recvmsg` on libkernel's own sockets (Socket/src/Udp.cpp:973-987, 1081-1107, 1152-1199) | still WSAEINVAL → 22 | **not covered** (gap 2) |
| `read`, `readv` and `sceKernelRead` on libkernel sockets (Stdio.cpp:822-834, 1056-1075 → Udp.cpp:1396-1428) | same | not covered |
| `sceNetEpollWait` and libkernel `select`/`poll` on libSceNet fds (E:1277-1367) | readiness only; WSAPoll on an unbound socket not verified | not touched |
| `sceNetGetsockname` on an unbound socket | already 0.0.0.0:0 on main (E:1156-1160) | n/a |
| `sceNetShutdown` (E:1039-1049) | sets no flag and wakes nothing | **regression** (gap 1) |
| `sceNetListen` on an unbound stream socket (E:781) | Winsock fails WSAEINVAL; FreeBSD binds an ephemeral port | not covered (LOW, different class) |
| zero-length receive | FreeBSD returns 0 at once (`soreceive_dgram`: `uio_resid == 0`) | now waits (LOW, gap 3) |

**Socket types:**
- `sceNetSocket` accepts types 1-3 only (E:680-682), so `== NET_SOCK_STREAM` (PR5966:500) is right today.
- #5836 (P2P types, open) stores the transport type, so it stays right after that lands.

**Blocking modes:**
- `SO_NBIO` and `fcntl(O_NONBLOCK)` give EAGAIN at once.
- `MSG_DONTWAIT` already fails EOPNOTSUPP on Windows before the wait.
- `SO_RCVTIMEO` ends the wait with EAGAIN. As the PR's debt note says, a whole call can take up to twice the timeout.
- Abort and close end it.

### Gaps
**1. MEDIUM, Windows, introduced by the PR: shutdown doesn't release the wait.**
- *How:* `sceNetShutdown` sets nothing and calls `g_cv.NotifyAll()` nowhere. The loop at PR5966:507-518 exits only on close or abort, a local address, or the deadline.
- *What FreeBSD does:* `soshutdown` on an unconnected datagram socket returns ENOTCONN but still calls `sorflush`. Its comment says this is so applications can unblock a receive. `soreceive_dgram` then returns 0. Source: FreeBSD 11.4, `sys/kern/uipc_socket.c`, `soshutdown` and `soreceive_dgram`.
- *Effect:* a title that shuts the socket down to stop a receiver thread, then joins it before closing, hangs on Windows.
- *Proposal:* not built, because the code is Windows-only and the fork's Build workflow runs only on pull requests, which I may not open.
  1. In `sceNetShutdown`, when `how != SHUT_WR`, set a `readShut` flag on the `g_socks` entry and call `g_cv.NotifyAll()` after the host `shutdown`. Keep its ENOTCONN result.
  2. `wait_for_local_address` returns a distinct value for `readShut`.
  3. The three receives return 0 for it.
  4. Test: a thread blocked in `sceNetRecvfrom` on an unbound UDP socket with no timeout returns 0 within a second of `sceNetShutdown(s, SHUT_RD)` from the main thread. This passes on Linux natively; on Windows it is red at #5966's head.

**2. LOW-MEDIUM: libkernel's own sockets aren't covered.** The same WSAEINVAL happens for POSIX `recv*` and `read` on libkernel sockets. Those come from libkernel `socket`, and from #5992's `__sys_socketex`. Fixing it needs the wait in the libkernel socket layer, or a shared helper.

**3. LOW: zero-length receives on an unbound socket wait.** FreeBSD returns 0 at once (`uio_resid == 0`).

**4. INFO, cost:**
- Every waiter calls `getsockname` every 10 ms while holding the global `g_mutex` (PR5966:507-517). Bind sets `bound` (E:768), but connect and sendto don't, and none of the three wakes a waiter (E:766-769, 879, 969-972). Detection therefore lags by up to 10 ms.
- Waking waiters there would remove most of the polling.
- Nothing is added on Linux, or for bound and stream sockets.

**5. INFO:** the `Sock` copy (PR5966:499) cannot miss a bind, because `getsockname` is checked again on every pass.

### Tests
- The PR's GuestSceNet.cpp cases cover blocking, non-blocking, the timeout and a late bind.
- Missing: shutdown, zero length, and the libkernel receive paths.

### Related open PRs
- **#5836:** P2P types. Complementary.
- **#5930:** recvmsg guards. Its write guards stay open during the wait.
- **#5992:** `__sys_socketex`. Creates the libkernel sockets of gap 2.
- No PR supersedes it. Merges are clean, including with #5967.

### A better version would…
1. Move the unbound-datagram wait into one helper that libSceNet and libkernel sockets both use.
2. Wake waiters on bind, connect, sendto, shutdown and close instead of polling.
3. Return FreeBSD's 0 for a shut-down or zero-length receive.
4. Keep one deadline across the wait and the host receive, so a timeout is never doubled.

## 3. #5967: fix(libSceNet): read SO_RCVTIMEO and SO_SNDTIMEO as a timeval in sceNetSetsockopt (head 7f82da1080)

### Verdict
**Correct.**
- `sceNetSetsockopt` and `sceNetGetsockopt` now take 0x1005/0x1006 as FreeBSD's 16-byte timeval through the shared `set_kernel_timeout` (Export.cpp:364-387). Sony's 0x1105/0x1106 stay an int of microseconds.
- The flip is backed by the ProsperoLight console log the debt entry cites, and by FreeBSD's `sosetopt`/`sogetopt`.
- Readback truncates to the caller's length, as `sooptcopyout` does.

### Every user of the timeout fields
All in microseconds:
- **Writes:** `set_kernel_timeout` (:383-384, clamped to INT_MAX at :382) and `sceNetSetsockopt` for 0x1105/0x1106.
- **Reads:**
  - `sceNetGetsockopt`;
  - `receive_error` (:472, only `> 0`);
  - #5966's deadline (PR5966:503-505);
  - #5967's timeval conversion.
- **To the host:** only `set_native_timeout` (:350-362).
  - Windows rounds up to whole milliseconds (:353), so 1-999 µs becomes 1 ms and never 0 (infinite). It clamps at MAXDWORD.
  - Linux passes the exact timeval.

All units are consistent.

### Gaps (all LOW; most predate the PR)
1. **Clamp mismatch.** A timeval longer than INT_MAX µs (about 35.8 minutes) reaches the host in full but is stored clamped. Readback and #5966's deadline then disagree with the host.
2. **POSIX `getsockopt` on a sceNet fd fails with EBADF.** The libkernel layer has no getter hook into libSceNet (Socket/include/SocketPoll.hpp:19-36, Udp.cpp:835-844). `setsockopt` already routes there and uses a timeval.
3. **`sceNetGetsockopt` rejects `*optlen < 4` for every other option** (:1103), where FreeBSD truncates. #5967 does this only for the two timeout options.
4. **Interplay with #6142.** It sends `sceNetSetsockopt` on a libkernel fd to libkernel's `setsockopt`, bypassing #5967's routing, so 0x1105/0x1106 would fail there with 42. #5617 adds the timeval wait for libkernel's own sockets but not 0x1105/0x1106.
5. **INFO:** the special case at :589-593 becomes redundant.
6. **INFO, ABI change:** an int passed to 0x1006 now fails with EINVAL and leaves no timeout. This is intended and backed by the console log; main's old tests asserted the opposite.

### Tests
- The PR's `CheckKernelTimeouts` and `CheckReceiveTimeout` cover the timeval set and get, both short-length errors, truncation, and 0x1105/0x1106.
- Missing: a timeval above INT_MAX µs, and POSIX `getsockopt`.

### Related open PRs
- **#5617:** libkernel socket timeouts.
- **#6142:** see gap 4.
- No PR supersedes it. Merges are clean, including with #5966.

### Follow-up
**None.** Every gap is LOW, predates the PR, or belongs to another PR (#5617, #6142).

### A better version would…
1. Route POSIX `getsockopt` on a sceNet fd to libSceNet, as `setsockopt` already is.
2. Store the timeout in 64 bits, so readback matches the host.
3. Truncate every option's readback the way `sooptcopyout` does.
