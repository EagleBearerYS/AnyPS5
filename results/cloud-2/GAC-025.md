## 3. A test for the map's counting
**Added as `write-data-shared-keys`** in `tests/execution/KeysClearOverPending.cpp`, commit **5b7c4efcb** on top of 8e5b0022cb, pushed as a fast-forward (`8e5b0022c..5b7c4efcb`).

**The case:**
1. Draw to a target, leaving its image A pending under uncompressed keys, as `write-data` does.
2. Create a second storage image B directly with `StorageTexture::Create`, over **another surface** that uses **the same keys address**. B is listed, and the key address is counted twice.
3. Destroy B.
4. Write the 0000 key code over A's pending results with WRITE_DATA.
5. Require that A notes the write and that its sampled read is the clear colour.

**Why another surface, not the same surface viewed twice:**
- Creating any image over A's surface uploads that surface through `GuestMemory::ReadCommitted` (TEX:2174, 2378).
- The guest-read hook stores pending results in the range first (`FlushHook` → `FlushPending`, TEX:1367-1368, set at 3152).
- So a second format or mip of A's surface would write A's results back before the key write, and the case would no longer be a key write over pending results.
- A second surface sharing A's keys isolates exactly what the map has to get right: two listed images at one key address, one of them gone.

**Reaching it took two things:**
- **The driver's device.** `Driver::device` is private. The commit adds `friend struct DriverTestAccess;` to Driver.hpp, the same pattern as VulkanDevice's `friend struct VulkanDeviceTestAccess;`. The test defines both access structs. The case uses the driver's own context and detiler, because a second `VulkanDevice` would switch the process-wide host-import state to itself.
- **B's actual destruction.** `upload()` keeps B in the active recorder's open batch (`Recorder::Keep`, TEX:2210, 2302). A finished batch's kept objects go to the release thread at the outermost GPU-mutex unlock (Recorder.cpp:316-330, 459).
  - So the case calls `WaitIdle()` under the lock, which submits and finishes the batch.
  - After unlocking, it waits up to 10 s for B's `weak_ptr` to expire, and requires that it did.

**Red, then green.** Red is a local variant that drops the address on any destruction (a set instead of a count): in the destructor, `if (found != end) erase(found)` replaces `if (found != end && --found->second == 0) erase(found)`.

## 4. Adversarial review
Paths: TEX = `core/libs/prx/libSceAgcDriver/Graphics/src/Texture.cpp`, LH = `…/Execution/src/Driver/Synchronization/LabelHistory.cpp`. Line numbers are 8e5b0022cb's.

### 4.1 Can the gate say no when `ClassifyFill` would say Keys at the same moment?
**No.** At any single moment, the map holds a superset of the listed images' key addresses, and `Keys` needs a listed image whose `dccAddress` equals the store's address. The details:
- **`Keys` needs an exact key address.** `ClassifyFill` returns `Keys` only through `keysFillMatches` (TEX:3875-3876). That requires `!released && descriptor.dccAddress == address` (TEX:3080).
- **An image is counted before it is listed, and uncounted only after it was unlisted.**
  - `Create` counts it (TEX:1070-1074) before it pushes it to `live.textures` (1075-1079).
  - The destructor uncounts only when `std::erase` removed it (TEX:4966-4978).
  - So the map always holds every listed image's key address.
- **Released images:** they stay listed and counted. `keysFillMatches` refuses them, so the gate says yes and `ClassifyFill` says no, as on d71ef7b1e1.
- **The descriptor never changes.** It is set once in the constructor's initializer list (TEX:1089) and assigned nowhere in Graphics/ or Execution/.
- **Every image comes from `Create`.** The constructor is private (Texture.hpp:356-357), and `Create` (TEX:1065) is the only `new StorageTexture`.

**One new window between two moments.** The gate runs before the GPU lock, while images are created under it. On d71ef7b1e1, a CPU-executed key store blocked on the GPU lock until a concurrent `Create` finished, and then `ClassifyFill` saw the new image.
- With the gate, the bad sequence is:
  1. `Create`'s `upload()` reads the guest keys (TEX:1067).
  2. Another queue's packet writes new keys (PacketExecution.cpp:323-325: `Pm4::Execute`, then `noteLabelStore`).
  3. The gate runs before `Create` counted the image (TEX:1070), says no, and the note is skipped.
- The image then keeps the keys it read before the write.
- **When it can happen:** only when a title writes a surface's keys on one queue while another queue starts using that surface with no synchronization between them. That is a race on the GPU too. With the title's sync, either the write comes before the use, so `upload()` reads the new keys, or the use comes before the write, so the count is visible (§4.2).
- **The fix is cheap:** count right after construction, before `upload()`, and uncount if `upload()` or `createView()` throws. While `Create` runs, the gate is then already open and the store blocks on the GPU lock as before. I didn't build this: a red test needs a reproducible interleaving that only a test hook inside `Create` could force. It is a proposal for the owner.

### 4.2 Memory order across queues, with the title's own label and wait
The case: queue A uses a surface, so its worker runs `Create` under the GPU lock. A then writes a label, and queue B waits for that label and then executes a key store on the CPU. Does B's gate see A's count?
- **A's side:**
  - A's count is a `keysMutex` unlock (TEX:1072-1073), which precedes the list push and everything after it in A's program order, including A's later label write.
  - A CPU-executed label is a plain store through `Pm4::Execute` (PacketExecution.cpp:208, 323).
  - A GPU-written label lands after a `vkQueueSubmit` of work recorded after the count.
- **B's side:**
  - B's wait reads the label with `volatile` loads (`Pm4::WaitSatisfiedUnchecked`, Pm4.cpp:554-558; WaitMemory.cpp:118, 377).
  - B's gate then locks `keysMutex` (TEX:3905-3909).
- **Result:** on x86-64 (TSO), a store that B observes cannot be seen before A's earlier stores, and B's lock is a locked read-modify-write after B's load. So B's lookup sees A's count.
- **This assumption isn't new.** Formally, a `volatile` poll isn't a C++ happens-before edge. But the driver already relies on the same thing for every handoff through guest memory, including `ClassifyFill`'s view of the live list on d71ef7b1e1. The gate adds no new assumption.

### 4.3 Exception safety of counting before listing
- **If `upload()`, `createView()` or the map insert throw** (TEX:1067-1073): nothing is counted, and the `shared_ptr` destroys an unlisted image, which uncounts nothing.
- **If the list push throws** (`std::vector::push_back`, `bad_alloc` only, TEX:1078): the count stays, because the destructor finds the image unlisted (`listed` is false, TEX:4971).
- **Effect of a leaked count:** the address stays in the map for good, so the gate stays open for it. That costs the old lock-and-classify path for stores at that one address and nothing else. The map is never missing an address, so correctness is unaffected.
- **If wanted:** a scope guard that uncounts when the push throws would close even that.

### 4.5 Sibling paths: the other `ClassifyFill` caller
- **The only other caller is `storeBufferFill`** (BufferFill.cpp:291). It is reached from DMA_DATA fills (PacketMemory.cpp:173) and from the fill-kernel replacement (BufferFill.cpp:255). It walks the live list twice per fill, just as a label did.
- **The gate can't serve it, for two reasons:**
  - A fill takes the GPU lock for its own work anyway (BufferFill.cpp:277): it records the fill or stores it on the CPU.

- **Verdict:** scope for a separate PR, not this one.

| `APS5_PIPELINE_DMA=1` | ← `commitDmaStore` ← `DrawPipeline::run` | ← `commitLabel` ← `DrawPipeline::run` | **2** / 7 | 4 → 4 → 4 |

- **Every key store** reaches `noteLabelStore` with 0x200 bytes. `KeysLiveAt` is called from `noteLabelStore` (`NoteKeysStore` is inlined), `ClassifyFill` follows from the same frame, and then comes `[dcc-keys] title stores keys 0x…+0x200 with 00 in a packet store (queue 0x0)`. Each case then prints `the image's noted key fill is 0000`, `reads the 0000 fill, not the pending image` and `PASS`.
- **The other 5 `commitLabel` hits** in the pipelined modes are the cases' 4-byte labels. Their values are not one repeated byte, so `noteLabelStore` returns before the gate. That accounts for 5 of the 9 `noteLabelStore` hits in each mode.
- **`cpu-store`'s keys** come from the CPU block write-back, as before: `[dcc-keys] uncompressed store by block write-back (sampled texture) …`.
- **Where the pipeline sends what:** the worker offers labels and DMA packets to the pipeline (PacketExecution.cpp:176). `enqueueLabelPacket` (PacketMemory.cpp:343) takes RELEASE_MEM and WRITE_DATA. `enqueueDmaPacket` (PacketMemory.cpp:270) takes DMA_DATA only with `APS5_PIPELINE_DMA`.

**What the gate saves on current main.** It depends on whether the caller already holds the GPU lock:
- **Callers that hold it:** the three paths this test exercises, `preparePacketMemory` (PacketMemory.cpp:36, :88, :126), `commitDmaStore` (:320) and `commitLabel` (:378). There the gate saves `ClassifyFill`'s two walks of the live list under the held lock (1.6 µs at 259 images, about 100 µs at 3,000), not the lock itself.
- **Callers that don't:** the CPU-executed label paths (PacketExecution.cpp:274 and :391, the base's :209 and :325). There the gate saves the lock as well. The harness's contended rows measure this case.
