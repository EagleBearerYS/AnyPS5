### 4.2 The unwatch serial: does PM-028's reuse stay correct under #6060? **Yes. Risk: `MarkWritten` coverage of GPU writes into imports.**
- **How PM-028 actually depends on the serial:**
  - `ShaderMemory::unchangedSince` (`ShaderMemory.cpp:371-378`) does not read `UnwatchSerial()`. Its steps are: pending-write check, `FlushGpuWrites`, `CollectWrites`, `UnchangedSince`.
  - The serial only keys `CollectWrites`' memo (`GuestMemory.cpp:1159`).
  - "No import took memory off the watch" is enforced by `tracker.covers` in `UnchangedSince` (`GuestMemory.cpp:1353`), which reads `blocks` (`unchanged`, 967-971).
  - The direct readers of `UnwatchSerial()` are d9e47d1e98's `CurrentTableState` (`ShaderResources.cpp:1390`) and the heap mirrors (`GuestBufferMemory.cpp:1830`, `1885`).
- **What #6060 changes:** a settled import never calls `unwatchLocked` (`GuestMemory.cpp:1254-1262`), so the serial does not move and `covers` stays true. That is right, because the range really stays on `GetWriteWatch`.
- **Can a store inside the import window be missed? No.**
  - **The lock:** `ImportWatched` (`GuestMemory.cpp:1279-1331`) holds the tracker lock through the whole window: the saved copy (1299-1313), `before` (a resetting collect, 1314), the import plus `settleImport` (1320; `GuestBufferMemory.cpp:1155-1165`), and the walk against the saved copy (1328-1329).
  - **New bytes:** a page written with new bytes in the window gets a `Cpu` stamp in `blocks` (`stampWrittenRun`, 1094; `stamp`, 995-1007). PM-028's `UnchangedSince` then fails and the column is read again.
  - **Same value:** a same-value store gets `ImportWindow` (`cpuBlocks` only). PM-028 may vouch, and the words it supplies still equal memory.
  - **The reset race:** a store landing after its page's reset but before the compare dirties the page again, and the next collect stamps it.
  - **A failed settle:** `ImportWatched` returns at 1322 without the second walk. The window's marks stay in the write watch, and the next collect stamps them `Cpu`, which is conservative.
  - **Tested:** #6060's `CheckImportWindowOtherThread` pins the new-bytes and same-value cases, and it passed 5 of 5 in `agc_write_tracking`.
- **The risk:**
  - **Before #6060:** a Windows private import took its blocks off the watch, so PM-028 always re-read or compared those columns.
  - **Now:** it vouches for them with no compare. GPU writes through the import are invisible to `GetWriteWatch`; `decideImportWatch` requires `writtenAfterFill == 0` (`GuestBufferMemory.cpp:757`).
  - **What correctness rests on:** `MarkWritten` at record time, plus the pending-write note until completion (`ShaderMemory.cpp:374`). The sites I read all mark:
    - `MarkDirectWrites` (`GuestBufferMemory.cpp:4296-4303`, called at `ShaderResources.cpp:4663`);
    - `WriteBack` (`GuestBufferMemory.cpp:4388-4389`);
    - the storage-image block write-back (`Texture.cpp:4692`);
    - labels and DMA (`VulkanDevice.cpp:2062`, `2071`, `2101`, `2282`, `2523`).
  - **Coverage:** Linux on real GPUs already relies on this contract, and `agc_shader_table_snapshot_reuse` pins the `MarkWritten` case. But lavapipe's probe here reports `4 after a GPU write`, so Linux CI compares imports. A GPU write path that skipped `MarkWritten` would show up only on Windows or a real Linux GPU. I did not audit every GPU write path, address-based builds' in particular.
- **Not correctness:** the settle round trip runs under the tracker lock, so every `UnchangedSince` and `CollectWrites` that misses the memo waits for it, PM-028's included.

### 4.3 Lazy capture pages (-ports port 1, 04e3448c4): can they miss a store inside an import window? **No.**
- **How a lazy page works:**
  - `ShaderMemory::page` (`ShaderMemory.cpp:168-193`) reads word by word when the pending-write query says recorded GPU work writes the page (182).
  - Otherwise it calls `FlushGpuWrites(base, PageBytes)` and sets `lazy` (188-190).
  - Each 64-byte block is then copied directly from guest memory on first use (`read`, 216-220; `readWords`, 302-310).
  - It never consults the tracker, the serial or the import state.
- **What an import changes under #6060:** neither guest bytes nor mappings.
  - `settleImport` copies 4 bytes out of the import into its own target buffer (`GuestBufferMemory.cpp:658-737`).
  - The driver's asynchronous marks only set write-watch bits.
  - A CPU store inside the window is therefore in memory before a block's copy or not, exactly as for a whole-page read at that moment.
  - With #5851 reverted, an import no longer moves a resident run into the section (a remap). That removes, rather than adds, a way for a page to change between `page()` and a later block copy.
- **The coupling with PM-028 stays safe:**
  - `stampWrites` refuses a range once any of its pages is in the page vector, lazy or not (`ShaderMemory.cpp:362`).
  - `supplyWords` fills only words not yet valid (397).
- **Side note, not #6060:**
  - Lazy pages skip `GuestMemory::Read`'s read guard (`GuestMemory.cpp:2018`), which port 1's parent used for the whole page (04e3448c4^ `ShaderMemory.cpp:112`).
  - That guard is the multisample one (`MultisampleTarget.cpp:232-233`, installed at 262). A capture whose first touch lands on a live multisample target's memory used to throw from `RequireNoMultisampleTarget`. Now it reads the guest bytes silently.
