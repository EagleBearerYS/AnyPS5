**B: `chore(agc): count the write index's fallbacks by reason and the templates the audit walks`** (a680c3ad55; bb35058d03 on the boot tree)
- **Every `Fallback` return of `indexRevalidate` is counted by reason:**
  - no subscription;
  - depth-plane flush;
  - sweep failed;
  - pending images over spans;
  - compared table span changed;
  - bumps since failed;
  - table span element bumped;
  - lookup re-resolve failed;
  - compare re-resolve failed;

  - bumped re-resolve failed;
  - second proof failed, also split by `FastFail` reason.

- **Output:** the `[rescache] write index` line ends with `; fallbacks by reason: …; audit walks: N over M templates (index fallback in the same call: …), most audited: shader set … n (reason n), …`.
- **With `APS5_PROFILE_DRAW` unset, both commits add only gated branches.** Two exceptions, neither of which changes an outcome:

## 3. The gap: sum against total

The pieces cover 97.0% (0%) and 97.9% (2%) of the revalidate line's total. The roughly 0.9 µs per call left over is code between pieces. To name it, I ran a scratch build (not committed) that timed every region between two pieces, at 0% writes:
- **About 0.37 µs per call: the first thread-local fetch in `revalidateFull`.** That is `overlappingSlot` through `ShaderRecompiler::ThreadOwned`, ShaderResources.cpp:4028-4029: a `__tls_get_addr` call plus a PLT call. The second slot (:4030-4031) costs under 0.1 µs.
- **The rest is spread over the piece boundaries**, about 0.05–0.15 µs each: the timers' own atomics and `now()` calls (`steady_clock::now()` costs about 28 ns here), the `serialBefore` load, the condition checks, and `report->path`.
- **No region between pieces holds real work.** At 2% writes the share falls to 2.1% because the index piece grows.

## 5. The template hit's data-buffer refresh

**It is outside Revalidate and outside this split.**

| | boot tree c3a17826c8 | 3b1178c9d5 |

| The line `template hits: N refreshed the data buffers (revalidate X ms)` prints | VulkanDevice.cpp:5718 | :5712 |
| The refresh runs in the dispatch record phase | `resources.refreshData` / `RefreshData` at :5203, timed as `PhaseRecordDataRefresh` (`recordStep` at :5211) | :5199, :5207 |
| The lookup calls Revalidate earlier | :5630 and :5665 | :5625, :5660 |
| The lookup's revalidate time is taken | from `subPhaseStart` (:5557) to :5686 | :5552 to :5681 |

- **"X ms"** is not the refresh's time. It sums `record.revalidateMs` (:5206), the Revalidate time of the dispatches whose buffers were then refreshed. That time *is* inside `revalidateFull` and counted on the revalidate line, but the refresh work itself is not.
- **Recipe hits** pass `revalidateMs` 0 (:5928 at 3b1178c9d5), so X leaves out their Revalidate time.
- **The refresh is dispatch-only.** The draw path's Revalidate (Draw.cpp:1761 on the boot tree, :1747 at 3b1178c9d5) has no data-buffer refresh: Draw.cpp has no `RefreshData` call. So the Village harness, which only draws, never refreshes.

## 6. What an exact change could remove, piece by piece

Lines are at 3b1178c9d5; boot-tree lines in brackets where they differ.

**guards: 11.7 µs per call.**
- **Breakdown** (scratch sub-timers, 0%):
  - `AnyPendingCpuWrites` (:3919 [3940]): about 1.0 µs.
  - The 3 `directRegions`' `FlushDepthPlanes` (:3920-3923): about 0.4 µs.
  - The `describedRanges` loop (:3924-3929 [3945-3950]): about 10 µs.
- **Work over ranges that didn't change: removable.**
  - The loop visits all 4,042 described ranges on every call; here all of them are image-table ranges (`imageTable` true, pushed at :5798 and :5919).
  - For a table range the multisample check is skipped, and with `cpuWriters` false (every call here: "cpu writers 0") `CompletePendingCpuWrites` is skipped too. The walk does nothing but miss the cache: about 226 KB of `DescribedRange` per call.
  - **Exact change:** keep the non-table ranges in their own list when the build fills `describedRanges`, walk only those when `cpuWriters` is false, and walk everything when it is true.
  - **Scratch result** (two runs each, alternated): guards 13.41/13.89 → 2.51/2.46 µs per call; Revalidate 34.13/35.11 → 23.83/22.32 µs per call. That is about **11 µs per call, about 140 ms per 10 s** at 13,000 calls here. (The scratch kept a hash lookup that a real list wouldn't need.)
- **Not removable:**
  - With CPU writers pending, each range needs its `CompletePendingCpuWrites`. The PC log's `(cpu writers N)` shows how often that happens.
  - The multisample check on non-table ranges (`RequireNoMultisampleColorTarget`, :3925) isn't a repeat of an index proof. No bump covers multisample colour targets (BF-321 row 10), and it returns at once while nothing is guarded.
  - `FlushDepthPlanes` over `directRegions` covers imported buffer regions, not the index's spans, so it is not a repeat either.

**index: 16.5 µs per call at 0% writes, 30.2 µs at 2%.**
- **Breakdown** (scratch laps, 0%):

  | part | lines | µs per call |
  |---|---|---|
  | depth flush over the spans | :3794-3796 | 0.5 |
  | sweep | :3797 | 0.85 |
  | pending scan | :3798-3807 | 0.05 (skipped by the memo) |
  | compared table spans | :3808-3810 [3829-3831] | **14.5** |
  | generation and bumps | :3811-3846 | 0.7 |
  | re-resolve and inner proof | :3847-3868 | 0.2 at 0%; **14** at 2% |
  | the end | :3869-3880 | 0.45 |

- **Work over a range that didn't change, removable only by watching it.**
  - Every proof compares one 128 KiB copy (the 4,096 × 32-byte T# table) with guest memory.
  - The copy is taken in `subscribeIndex` (:3633-3637 [3654-3658]) because `GuestMemory::Watched` fails for the span. In the harness the span is in the host-imported data block, which lavapipe's import leaves unwatched.
  - While a span is unwatched, the memcmp *is* the proof; no exact shortcut exists.
  - **Exact change:** get the span under the write watch. It is then subscribed at :3630-3632, the table-span bump covers it, and about 14.5 µs per call goes.
  - **On the PC the span may be watched.** No current line shows compared table spans. One more field on B's line (spans and bytes compared per window) would show it; I didn't add it, as it is outside the counters asked for.
- **Not removable:** the 2% growth is the bumped elements' per-element proofs. That is work for ranges that did change, and it stays.
- **No index step repeats a proof made elsewhere in the same call.**

**fast, t1, walk: 0 calls (index-proved).** Under forced fallback (§4), fast costs 1,036 µs per call. It walks every element (`CollectWrites` and keys per element) whether or not anything changed, which is what the index exists to avoid.

**pending: 0 runs per window; skipped every call by `pendingSerialSeen` (:4131).** Nothing to remove.

**imports: 0.39 µs per call.** `HostImportsUnchanged` (GuestBufferMemory.cpp:6526) is one mutex plus `importsStale`, and the serial loop was skipped every call. Nothing material.

**staging: 1.21 µs per call, 0 copies.**
- **The cost is not copies.** It is `ResidentBuffer::FlushChanged` (ResidentMirror.cpp:601-633), which `RecordStagingCopies` runs first (GuestBufferMemory.cpp:6480) on every reuse. It takes the devices mutex, walks every resident memory of every device, and swaps the pending list.
  - **Exact change:** an atomic "flush queued" flag, set where a memory turns unzeroed or a buffer is queued, and checked before the locks. That saves about 1 µs per call.
- **Copies re-recorded for unchanged data: none here.** `RecordStagingCopies` (:6484-6497) re-records a copy-in for every `gpuCopy && deviceLocal` region on each reuse, whatever the import holds. It is not removable as the code stands: the device-local shadow is per use, not resident (comment at :5053). The PC's `(<n> copies)` shows whether Village has any.

**rest: 0.15 µs per call.** Nothing to remove.

**Against the bar (about 0.043 ms per call that an exact change removes):**
- On lavapipe the two removable items are the guards' table walk (about 11 µs) and the table compare (about 14.5 µs, only while the span is unwatched). Neither reaches 43 µs alone.
- The PC's Revalidate is 3.5× this one (0.107 ms), so the boot tree's split line is what decides. Its guards field and its `(cpu writers N)` count show at once whether the table walk scales with it.
