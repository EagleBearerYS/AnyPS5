## Short answer
- **Where a lookup's time goes.** On the real draw path, an unchanged 4 MiB DCC target costs **18.8 µs per lookup** on Linux, 1,028 pages walked. That is the same shape as Village's PC profile (1,030 pages, ~96 µs).
  - **60% is `CollectWrites` over the target:** 11.3-13.0 µs for 1,024 pages, the kernel's dirty-page walk (userfaultfd WP_ASYNC + `PAGEMAP_SCAN`).
  - **11% is `CollectWrites` over the keys:** 2.0 µs for 4 pages, all fixed cost.
  - **The rest is small:** `CompletePendingCpuWrites` 1.0, `UnchangedSinceAll` 0.8, the recipe's target checks 1.2, the two `materialize*Clear` calls 1.1 µs.
  - **The pieces the task names are off this path in steady state.** `FlushPending` and the DCC key scan are not on the steady-state path: main's per-image proof (`refreshProved`, e8b43459a) answers 4,094 of 4,095 lookups.
  - **At 8 MiB the walk doubles:** 18.9-23.4 µs for 2,048 pages.
- **The collect memo covers this path, including with the pipeline on.** Within one collect epoch the walk is skipped: the lookup costs 0.37-0.41 µs and walks 0 pages. The committer thread follows the worker's epoch (`DrawPipeline::FollowEpoch`, Draw.cpp:530-532).
  - **Why every lookup still walks:** each lookup is its target's first in a new epoch. Epochs end at every submission start, satisfied wait, EOP drain and reap.
  - **Here:** each draw ends two epochs (`epoch bumps: submissions 4066, waits 0, drains 4065, reaps 78` per 10 s).
  - **On the PC:** the same `epoch bumps:` field of the `[packets] queue 0x0` line names Village's.
- **An O(1) unchanged proof needs the OS to report the first CPU write**, so that "nothing written since" costs no walk. The kernel walk (Linux) and GetWriteWatch (Windows resident direct memory) are O(pages) by construction.
  - **The only O(1) source is a fault on the first write:** mprotect or VirtualProtect read-only over a proven target, with a SIGSEGV or VEH handler that disarms.
  - **That breaks guest I/O:** the HLEs `pread`, `recv` and `ReadFile` go straight into guest buffers, and those fail on a read-only page. The sites are libkernel `File/src/Stdio.cpp:225` and `:312`, `Aio/src/Aio.cpp:72`, `Socket/src/Udp.cpp:989`, and `libSceNet/Export.cpp:900`.
  - **The bracket API exists but isn't used:** `GuestArenaBeginHostWrite`/`EndHostWrite` was made for host writes like these, but only a test calls it.
  - **So this is a cross-module change** (libc write watch, libkernel I/O, libSceNet, the driver), with Windows parts I can't run. §2 gives the options; I recommend staging it (§2.3).
- **The ≥10× bar can't be met without it.** Trimming everything but the walk saves at most ~8%. With first-write arming, the split says `Refresh` would fall from 16.9 to ~3.5 µs (~4.8×) by skipping both walks. With `CompletePendingCpuWrites` and `UnchangedSinceAll` made O(1) too, it would be ~2.0 µs (~8.5×). Below that is `Refresh`'s own bookkeeping (~1.6 µs), so 10× needs trimming that as well.
- **Stamp hole (addendum):** main's existing proof already depends on stamps (`refreshProved` → `UnchangedSinceAll`). So the partly-watched hole reaches resident targets on main today, independent of BF-012. Any O(1) proof would rely on stamps for driver stores too, so its PR must carry PM-040's two commits (89343ba7f, b7c33252c).
- **Siblings:**
  - Depth and stencil targets (DepthSurface.cpp:322-327), sampled textures (ShaderResources.cpp:663, :677, :2523), storage images (the same `Refresh`) and write-backs (Texture.cpp:4632, :4726) all walk their ranges once per epoch, at the same cost per page.
  - None can be made O(1) by itself, for the same reason.

With `APS5_PIPELINED_DRAWS=0`: 598 of 598 passed, 41 skipped. `check_skips`: `41 test(s) skipped, all expected` in both runs. `check_conventions` passes (`All conventions checks passed.`).

### 1.4 Why repeated proofs re-walk: the memo covers the path, the epochs don't last
- **What the memo is.** `CollectWrites` skips the walk when the calling thread already walked the range in its current collect epoch (GuestMemory.cpp:1157-1185, the per-thread ring and the epoch map). §1.3's "one epoch" rows show it working on this path: 0.05 µs, 0 pages.
- **With the pipeline on**, the lookup runs on the committer thread. Before each commit, the committer adopts the worker's epoch through `DrawPipeline::EpochToken`/`FollowEpoch` (Draw.cpp:530-532, DrawPipeline.cpp:44-54, bumped in `Driver::bumpEpoch`, WaitStatistics.cpp:33-38). So the memo does cover the recipe path, and #6082's mention of `CollectEpoch()` holds for it.
- **The epochs end at the queue's ordering points (`bumpEpoch`):**
  - each submission start (PacketExecution.cpp:156);
  - a satisfied WAIT_REG_MEM (WaitMemory.cpp:132);
  - an EOP-interrupt drain (PacketMemory.cpp:34, :210, :367);
  - a reap (QueueWorker.cpp:122);
  - every packet under `APS5_PACKET_EPOCH` (PacketExecution.cpp:164).
- **A target looked up once per epoch walks on every lookup.** In this bench every draw starts two epochs.
- **Village's 5.5 M pages for 5,340 lookups** say the same: one walk per lookup. The PC's `[packets] queue 0x0 … epoch bumps: submissions S, waits W, drains D, reaps R` line names which ordering points separate them.

### 1.5 What the walk is, per platform
- **Linux** (`GuestWriteWatch.cpp:47-200`, the kernel here has `PAGEMAP_SCAN` and `UFFD_FEATURE_WP_ASYNC`):
  - Guest memory is write-protected through userfaultfd in **asynchronous** mode: the kernel resolves the first write itself and tells no one.
  - A collect asks `PAGEMAP_SCAN` for written pages and re-protects them, a walk of every PTE in the range.
- **Windows** (`WindowsMappings.hpp`):
  - **Resident direct memory** (`MEM_WRITE_WATCH`) is collected with `GetWriteWatch` plus a per-page loop in `collectResident` (lines 550-583), which also allocates one pointer per page.
  - **Shared views** are tracked by protection faults (armed read-only, page generations) and skip clean ranges in the user-space map.
  - Village's ~90 ns a page fits the resident path. I can't measure Windows here; §6 says how the PC can.

## 2. Design: why no O(1) proof was built, and the options
**What the proof needs** is "no CPU store reached these pages since the last proof".
- **Driver stores** (write-backs, DMA, labels, fills, `MarkWritten`, `StoreOwnBytes`) already stamp the tracker. They are O(1) to check once a stamp summary exists.
- **CPU stores are the problem:** only the OS sees them, and both write watches report them only when walked.

### 2.1 The options
| Option | What it is | Gain (from §1.2) | What blocks it |
|---|---|---|---|
| **A. First-write arming** | After a proof finds a target unchanged, make its pages read-only; a SIGSEGV (Linux) or VEH (Windows) handler marks the target written and opens the page. The next proof skips both walks while the target is still armed. | `Refresh` 16.9 → ~3.5 µs (~4.8×) by skipping both walks; ~2.0 µs (~8.5×) with O(1) `CompletePendingCpuWrites` and a stamp summary for `UnchangedSinceAll`. Lookup 18.8 → ~5.4 µs, ~3.8 µs with both. | Kernel writes into guest buffers fail on read-only pages (EFAULT, ERROR_NOACCESS): `ReadFile` (libkernel `File/src/Stdio.cpp:225`), `pread` (`Stdio.cpp:312`, `Aio/src/Aio.cpp:72`), `recv` (`Socket/src/Udp.cpp:989`, `libSceNet/Export.cpp:900`), and any others an audit finds. `GuestArenaBeginHostWrite`/`EndHostWrite` exist for this but only `core/libs/tests/GuestMemory.cpp:1695` calls them. Also: the handler must be async-signal-safe and chain correctly; mprotect splits the userfaultfd-registered VMA; disarm on guest protection changes, unmap, unwatch and eviction. |
| **B. Fewer ordering points** | Keep the memo across ordering points that can't expose a CPU write to a target. | Up to the memo's 0.4 µs per lookup when it applies | A change to the sync model. It needs Village's epoch-bump split first; drains and waits each have reasons on main (an EOP interrupt runs title code; another queue's label may order CPU work). |
| **C. Huge pages for guest direct memory** | `PAGEMAP_SCAN` would read one PMD per 2 MiB. | The walk would read 2 PMD entries per 4 MiB instead of 1,024 PTEs | Linux only (Windows can't write-watch large pages); a global memory-layout change; a CPU write then dirties 2 MiB. |
| **D. Safe trims** | Merge the keys collect into one tracker call; skip `CompletePendingCpuWrites` when nothing is pending; summarize stamps per 2 MiB. | ≤ ~1.5 µs of 18.8 (≤ 8%) | Nothing, but it misses the bar. |

### 2.2 Why I stopped at measurement
- **A is the only option that meets the bar,** and its blocker is outside the driver: any HLE that hands a guest pointer to a kernel write.
- **Built blind, it turns a perf change into data loss:** a `pread` into a target's memory after the title reuses it would fail silently.
- **Its Windows half** (VirtualProtect plus the arena's VEH on resident memory) can't be run here. CI's Windows job builds three execution tests and stubs the rest.
- **The upside is bounded:** Village's `readTarget` is 5.8% of queue 0's time (515 ms of ~8.9 s per 10 s). The 3.54 ms per draw packet is elsewhere.

### 2.3 If the Project Manager picks A: a staged plan, each stage its own PR with its own tests
1. **Bracket every HLE kernel write into guest memory** with `GuestArenaBeginHostWrite`/`EndHostWrite`, which opens armed pages. Start with the five sites above, then audit libkernel, libSceNet and the other HLEs for host syscalls given guest pointers.
   - Tests: a `pread`, a `recv` and a `ReadFile` into an armed range must land and be seen.
   - This may also matter for the Windows arena's armed alias views today. I haven't verified that.
2. **An arming API in the write watch**, Linux and Windows: arm a range, ask "written since armed?" in O(1), disarm on a fault, a host write, a protection change, unregister or unmap.
   - Tests: user and kernel writes, alias mappings, partial pages.
3. **The driver's O(1) proof**, on top of PM-040's two commits:
   - arm proven resident colour targets and their keys;
   - make `refreshProved` skip both collects while armed;
   - the same for depth and stencil (DepthSurface.cpp:322-327);
   - the red/green tests for all 11 change kinds of the task.

## 3. The stamp hole (addendum)
- **Main's proof already uses stamps.** `refreshProved` asks `UnchangedSinceAll` (Texture.cpp:2012-2034 on main), and `Refresh`'s slow path uses `UnchangedSince`/`ChangedBlocks`.
- **So the hole reaches resident targets on main today.** `MarkWritten`/`storeOwn` stamp nothing for a store over a partly watched range (PM-037 §1 gap 1), so such a store into a resident target leaves it "unchanged" now. That is with or without BF-012.
- **Any option above keeps that dependence:** driver stores are seen only through stamps. The PR that builds the O(1) proof must take 89343ba7f and b7c33252c first, as the addendum says, with the edge case added to its tests.
