# BF-081: what BF-077's capture check costs per draw on title memory, and a cheaper form (cloud-2)

## RESULT

**Title memory sits on the arena table.** On Linux, almost all of a title's memory is in the guest arena:
- direct memory, flexible memory, memory mapped at a fixed address, the guest heap, guest thread stacks.

On Windows the same holds, plus one exception: a fixed-address map outside the arena falls back to plain `VirtualAlloc`.

**The #7043 range is in the arena.** The range in JustUseAI's abort (0x24ec00000+0x1e848000) lies inside the arena (base 0x2_0000_0000, 1000 GiB). "Outside the write-watched arena" means the range is not covered by the write watch, not that it lies outside the arena address range.

**What still goes to the kernel:**
- the main executable and PRX modules on Linux (the loader places them outside the arena, and Linux has no image table);
- modules and host stacks on Windows;
- that Windows fallback;
- any host memory a capture reads, which is the harness's case.

**Cost** (ff2837edf; Village harness; 100-frame runs, two rounds; 9.49 regions and 978 bytes compared per draw):

| path | ns per draw | ns per region |
|---|---|---|
| table path, arena memory (the title case) | **742 / 787** | 78 / 83 |
| outside the arena, PROCMAP_QUERY per region (BF-077's case) | **5,054 / 5,069** | 533 / 534 |
| raw memcmp, either placement (round 1 only) | 286 | 30 |

**The proposal:** fork branch **`perf/agc-capture-check-readable-runs` = bc3851d97**, one commit on ff2837edf: `perf(agc): reuse the kernel's answer for a captured region until the registry changes`.
- It brings the outside-arena path to **982 / 924 ns per draw**, about 5.5x less.
- It leaves the table path unchanged: 709 / 816 ns, within noise of base.
- What it does:
  - Each thread keeps the last 8 readable mappings the kernel reported, with the registry generation read before each query.
  - `CompareMapped`/`CopyMapped` read from those mappings while the generation is unchanged.
  - The capture check now counts an unmapped region as changed.
- **New test case:** a dispatch whose table is unmapped between capture and check.
  - It does not fault; the packet is prepared again once.
  - That second preparation reports the unreadable table.
  - Red on ff2837edf's code: "prepared again 0 times, not once".
  - Red as a SegFault on the proposal with the generation check removed.

**Mirror**, proposal vs ff2837edf:
- both: 1,411 tests, 5 failed (this VM's IPv6 tests), `check_skips` flags `guest_sce_net`;
- **no test changes status**;
- BF-077's four tests pass on bc3851d97.

**Not measured:** Windows (`VirtualQuery` cost, the image table). Windows checks are not this worker's.

## 1. The paths on ff2837edf

All references are on ff2837edf. GM = `core/libs/prx/libSceAgcDriver/Execution/src/GuestMemory.cpp`.

**The check.** `Driver::capturedMemoryChanged` (`Execution/src/Driver/Synchronization/DeferredLabels.cpp:205`) calls `GuestMemory::CompareMapped` once per captured region (`:209`). Only `Differs` counts as a change (`:210`); `Unmapped` does not.

**`CompareMapped`** (GM:2153) walks the region with `describePages` (GM:516) and memcmps each readable run. `describePages` answers a page in one of two ways:

- **From a page table.** If the page lies in a table span and its byte there is non-zero (GM:522-528), it is served from that byte: a byte load and a run scan (`PageSpan::runEnd`), no syscall. There are two spans (`PageStates`, GM:420):
  - **Arena:** the whole guest arena, `GuestArenaRange` (GM:481), on Linux and Windows.
  - **Image:** the main image (the PE at 0x7ff6…), Windows only (GM:484-500). On Linux there is no image table.
  - Only readable pages are stored (`PageStates::record`, GM:437-446). A stored page is dropped again when the registry generation moved during its query (GM:445), or when the libc invalidator reports its range (`ForgetPages`).
- **From the kernel.** Any other page, and a table page whose byte is still zero, is a kernel query:
  - **Linux:** `ioctl(fd, PROCMAP_QUERY)` on `HostMapping::QueryFd()` (GM:572-590). The fallback is a `/proc/self/maps` scan (GM:599).
  - **Windows:** `VirtualQuery` (GM:543), with the arena's logical protection read back through `GuestArenaProtection` (GM:557).
  - The answer is recorded in the table only when the page lies in a span (GM:562, 588, 621). Outside the spans, every compare of every region asks the kernel again.

**Which regions go to the kernel**
- **Linux:** every region outside the arena:
  - the main executable and its PRX modules (`dlopen`), which the loader places outside the arena (the image is PIE);
  - host stacks and TLS;
  - any host memory a capture reads.
- **Windows:** every region outside both the arena and the main image:
  - PRX modules (`LoadLibraryExW`);
  - host thread and fiber stacks;
  - the one guest fallback outside the arena: a fixed-address flexible, anonymous or reserve map outside the span becomes a plain `VirtualAlloc` (DirectMemory.cpp:101-103).

**Where a title's memory comes from** (survey of `core/libs/prx/libkernel/DirectMemory` and `libc`):

| kind | Linux | Windows | in the arena / on a table |
|---|---|---|---|
| direct memory (`sceKernelMapDirectMemory`, `…2`, `MapNamedDirectMemory`, AMM) → `DoMapDirect` (DirectMemory.cpp:906-939) | `MapAligned(PROT_NONE)` in the arena, then the memfd mapped `MAP_SHARED\|MAP_FIXED` (DirectMemory.cpp:246-258, 331-336, 582-600) | placeholder, then `GuestArenaMapDirect` (DirectMemory.cpp:333) | **yes**, arena table |
| flexible memory, anonymous `sceKernelMmap` → `DoMapAnon` (Export.cpp:108-120, 239-283) | `GuestArenaAllocate` + `mmap MAP_FIXED` (DirectMemory.cpp:764-770) | `GuestArenaCommit` (DirectMemory.cpp:71-83) | **yes**, arena table |
| fixed address (`MAP_FIXED`, `sceKernelReserveVirtualRange` then map) | inside the arena; a fixed address outside it is refused (DirectMemory.cpp:728-729, PosixMemory.cpp:112-114) | inside the span: arena; **outside the span: plain `VirtualAlloc` for flexible, anonymous or reserve memory** (DirectMemory.cpp:101-103) | yes, except that Windows fallback, which is **not** on a table |
| guest heap / libc `malloc` (`GuestHeap`, or the title's own allocator over direct or flexible memory) | `GuestArenaAllocate` + `GuestArenaCommit` (GuestHeap.cpp:48-133) | the same, with `MEM_WRITE_WATCH` | **yes**, arena table |
| main image and PRX modules | the loader places them (PIE), outside the arena | the main image is on the image table; modules are outside | Linux: **no**. Windows: main image yes, modules no |
| guest thread stacks | `DoMapAnon` in the arena (Thread.cpp:112-123) | host `_beginthreadex` stacks | Linux yes; Windows no |

- **The #7043 range is in the arena.** 0x24ec00000 lies inside it: base 0x2_0000_0000, 1000 GiB (GuestArena.cpp:40-43). The abort text "outside the write-watched arena" comes from `GuestBufferMemory::AcquireRegistered` (GuestBufferMemory.cpp:2857). It is chosen when the range's mirror fails because `CollectWrites` found the range not covered by the write watch, not because it lies outside the arena address range. That range's draws would therefore compare through the arena table.
- **The registry generation** (`GuestAllocationsGeneration`, GuestAllocations.cpp:165) moves at the end of every registry `Mutation` (GuestAllocations.cpp:135) and on `GuestAllocationsInvalidate` (:174). Every guest map, unmap and protect goes through one, but so does every guest `malloc` and `free` (GuestHeap.cpp:242). In a running title it therefore moves with heap traffic, not only with mapping changes.
- **Paths that change host mappings with no Mutation or Invalidate:**
  - the guest-stack `mprotect` fast path (DirectMemory.cpp:1087-1105) and `RestoreStackPages` (Thread.cpp:223-231);
  - `dlopen`/`LoadLibrary`, and the module unmap after its Mutation ends (DynamicLoader.cpp:42-51, 256);
  - `GuestHeap::abandon` (GuestHeap.cpp:135-138);
  - the Windows write-tracking protection flips (WindowsMappings.hpp), which `GuestMemory` reads back as logical protection.

## 2. The table path, measured

**The measurement tree** (not committed):

- **Timer** in `capturedMemoryChanged`. At exit it prints "[capture-check] N checks, N regions, N bytes, N ns in the compare, N found a change", and it has BF-077's two switches:
  - `APS5_MEASURE_NO_CAPTURE_CHECK=1` returns before comparing;
  - `APS5_MEASURE_RAW_COMPARE=1` replaces `CompareMapped` with a plain `memcmp`.
- **`APS5_MEASURE_CLASSIFY=1`**, used only for diagnosis, counts regions outside the arena by 64 KiB block. It is a static flag, so it is off and free in the timed runs.
- The proposal's measurement copy is the same diff applied on bc3851d97's tree (`/home/user/bf081p`, uncommitted).

**The table-path switch, `VILLAGE_ARENA=1`.** The harness has no arena helper on Linux: its `GuestBlock` `mmap`s outside the arena there, and uses `GuestArenaAllocate` + `GuestArenaCommit` only on Windows. With the switch set:
1. Each block comes from `GuestArenaAllocate(bytes, 65536)` + `GuestArenaCommit(block, bytes, 0x04, bytes)`, with the same `GuestWriteWatchRegister` as before.
2. **Moving the blocks alone was not enough.** A 2-frame run still cost 3,883 ns per draw, with 0.45 ioctls per region under strace (42,576 ioctls on 94,918 regions; 79 without the check). `APS5_MEASURE_CLASSIFY` showed 4 of the 9.49 regions per draw outside the arena, all in the test executable's image (0x55…).
3. **The outside regions were the shader programs**, 36-byte vertex and 160/204-byte pixel code. The draw packets carry the static arrays' addresses (PGM_LO/HI), and on Linux the image has no table.
4. So the switch also:
   - copies the vertex and pixel programs into an arena block, and points the packets and registrations at it;
   - places the shader headers there;
   - submits each command set from its own arena block, which is never rewritten while the set is unchanged.

   Then **0 of 94,918 regions** were outside the arena. That is the shape of a title whose shaders and commands live in direct or flexible memory.

## 3. The proposal

**Branch:** fork `perf/agc-capture-check-readable-runs` = **bc3851d97** on ff2837edf. Pushed; no PR.
- Author and committer are Yunus Shaikh; unsigned; no trailers.
- 3 files, +90 −8.
- Added `//` lines: 0. `check_conventions --base ff2837edf` passes.

**The count.** I looked for a generation count that map, unmap and protect move. libc's registry generation (`GuestAllocationsGeneration`, `GuestAllocations.cpp:165`) is that count:
- It moves at the end of every `Mutation` (`:135`) and on `GuestAllocationsInvalidate` (`:174`).
- Every guest map, unmap and protect (libkernel `DirectMemory.cpp`) and every guest heap block goes through one.
- The arena page table already relies on it: `PageStates::record` drops a page whose query overlapped a generation change (`GuestMemory.cpp:445`).

No new count was added.

**Why not "memcmp when the count hasn't moved since the capture"?**
- **Where the regions come from.** The regions a draw checks are assembled from each program's captured memory and the decode reads (`Draw.cpp:224-229`, `:426`). Programs can come from cached preparations. So "since the capture" would need a generation stored with every capture and carried through every cache and pipeline. If one region's bytes predate an unmap, a bare memcmp there faults.
- **What the proposal anchors to instead.** It anchors to the kernel's answer rather than the capture. The rule is the one the arena table uses: an answer counts while the generation it was read under is current.
- **Heap churn.** The registry generation moves with every guest `malloc`/`free` (`GuestHeap.cpp:242`), not only with mapping changes. A per-answer cache refills once per mapping per generation, so it survives that churn. A capture anchor would fall back to the kernel whenever any heap call landed between capture and check.

**The change:**
- **`GuestMemory.cpp`:**
  - `ReadableRuns` is a per-thread ring of 8 `{begin, end, generation}`.
  - `describePages` takes `readOnly`. For a page outside both table spans, it first looks for a remembered run under the current generation.
  - After a kernel answer that says readable (`PROCMAP_QUERY`, `/proc/self/maps`, `VirtualQuery`), it remembers the whole mapping with the generation read before the query.
  - Only `CompareMapped` and `CopyMapped` pass `readOnly`. They ignore write access, which the Linux write watch flips by `mprotect` without a mutation (`GuestWriteWatch.cpp`).
  - Arena and image pages keep their tables, unchanged.
- **`DeferredLabels.cpp`:** `capturedMemoryChanged` returns true for any outcome but `Equal`, so a region that is no longer readable counts as changed.
- **`DispatchRecaptureOnChange.cpp`:** a fourth round, last because a failed preparation leaves the driver failed.
  1. It dispatches once through a fresh table block, unhooked.
  2. Then the hook unmaps that block after the capture: a registry `Remove`, then `munmap` on Linux, or `GuestArenaReset` on Windows, where the block is in the arena.
  3. It requires: the hook ran once; the packet was prepared again exactly once; and that preparation failed naming the table ("guest memory is not readable at 0x<table>").
  4. Shutdown must report the same failure or nothing.

  On Linux the block is outside the arena, so the round goes through the new cache. The first dispatch remembered the block's mapping, and the `Remove` moved the generation.

**Red and green** (as `runner`, `ctest -R recapture_on_change -V`):

| build | `agc_driver_dispatch_recapture_on_change` / `_items` | the two draw tests |
|---|---|---|
| ff2837edf's `GuestMemory.cpp` + `DeferredLabels.cpp` with the new test | **Failed**: "dispatch recapture: a dispatch whose captured table was unmapped was prepared again 0 times, not once" ("the table was unmapped 1 time(s), 0 packet(s) prepared again"). ff2837edf records from the stale capture and reports nothing. | n/a |
| bc3851d97 with `endOf` ignoring the generation (a stale cache) | **SegFault** (both): the check memcmps the unmapped page | n/a |
| **bc3851d97** | **Passed**: "the table was unmapped 1 time(s), 1 packet(s) prepared again, and preparing it again reported: compute shader 0x…: AGC driver: guest memory is not readable at 0x7ff8ac3e0000 (range 0x7ff8ac3e0000+0x4)" | Passed |

**What the change does to an unmap inside that window.** Counting it as changed means the packet is prepared from current memory. A dispatch whose user-data table is gone then fails the way any dispatch would if it were prepared after the unmap: the debt entry's record-time throw. On ff2837edf it would silently bind the stale capture.

**Cost:** see section 2. With bc3851d97:
- outside the arena: 982 / 924 ns per draw (103 / 97 ns per region), against 5,054 / 5,069;
- table path: 709 / 816 ns per draw, against 742 / 787, within noise.

The remaining ~75-100 ns per region over a raw memcmp is `describePages`' own walk on both paths: the span lookup, the per-thread ring or the table byte, and the run emit.

## 5. Notes

- **Windows was not run.**
  - On Windows the image table already covers the main image.
  - The harness's `GuestBlock` already allocates from the arena there, so BF-077's harness would measure the table path on Windows as is.
  - The proposal's `VirtualQuery` branch remembers mappings the same way, untested here.
- **Paths that change host mappings with no registry mutation.** The new cache, like the existing arena table, would not see these:
  - the guest-stack `mprotect` fast path (DirectMemory.cpp:1087-1105) and `RestoreStackPages` (Thread.cpp:223-231);
  - `dlclose`/`FreeLibrary`, after their mutation (DynamicLoader.cpp:42-51, 256);
  - `GuestHeap::abandon` (GuestHeap.cpp:135-138).

  None of these is memory a draw normally captures: stacks, modules, freed heap. A capture that did read one would carry the same exposure the arena table has today.
- **A mutation in progress.** A mutation applies its unmap before its `End` moves the generation. A compare that lands in that window trusts the old answer, as the table and the uncached path already do between their query and their memcmp.
- **Runs, outputs and trees on this VM:**
  - runs: `/home/user/logs/bf081c-*.out`;
  - mirror logs: `ctest-bf081-base.*`, `ctest-bf081p-head.*`;
  - trees: `/home/user/bf081` (ff2837edf plus measurement code) and `/home/user/bf081p` (bc3851d97).
