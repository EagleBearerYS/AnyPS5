## The bug, confirmed in the code at 514643ab16

- `PacketExecution.cpp:242-247`: for a pipelined queue-0 packet, `enqueueDmaPacket(...)` returning true makes the loop `continue`. `preparePacketMemory` (line 328) never runs for that packet.
- `PacketMemory.cpp:67-73` (`preparePacketMemory`): the synchronous path notes a DMA_DATA data fill (source 2, destination not GDS) with `Graphics::NoteDepthMetadataFill(address, bytes, pattern)` and `NoteColorMetadataFill`. Its later `storeBufferFill(..., false, false)` at line 198 can therefore pass `noteMetadata = false`.
- `PacketMemory.cpp:293-312` (`enqueueDmaPacket`), the large fill:
  - It needs `APS5_PIPELINE_DMA`, opcode 0x50, queue 0, `DrawPipeline::Active()`, no deferred labels, source 2, more than 65536 bytes, a destination other than GDS, 16-byte alignment, writable memory and an existing driver device (`device.Load()`, line 303).
  - It queues `storeBufferFill(queue, fillAddress, fillBytes, {pattern×4}, localDevice, false, false)` at line 307, with `noteMetadata = false`, and increments `dmaFills` at line 308.
  - So nothing notes the fill.
- `PacketMemory.cpp:326`: the small queued store path in the same function does note it (`NoteDepthMetadataFill(fillAddress, fillBytes, pattern)`). Only the large-fill branch misses it.
- `BufferFill.cpp:422-425`: with `noteMetadata && uniform`, `storeBufferFill` notes depth and colour metadata after the store. JJenkx's one-argument change at line 307 therefore gives the queued fill the same note the synchronous path makes, and the refusal goes away.

## Why the harness can't show it

**Where the refusal comes from.**
- `DepthSurface::CheckCurrent` (DepthSurface.cpp:423) refuses "external GPU writes over native multisample depth are not implemented" only when `recorder->PendingWriteOverlaps(...)` holds for the HTILE range.
- `recorder` is `RecorderFor(context)` (DepthSurface.cpp:44-47): the single global `Recorder::Active()`, and only if its device is the target's `context.device`.
- `Recorder::Activate()` (Recorder.cpp:1286-1293) makes one recorder process-wide active.

**Where the queued fill is recorded.** On the driver's own `VulkanDevice`, through `storeBufferFill(..., localDevice, ...)`.
- The driver keeps that device private (`DevicePointer device`, Driver.hpp:408).
- It creates the device lazily on its first draw or dispatch (`device = std::make_shared<VulkanDevice>()` in Draw.cpp:69/77, Dispatch.cpp:87, DrawPrecheck.cpp:23/34 and ShaderRegistry.cpp:1845, or Presentation.cpp:54 with a window).
- Nothing lets a test read or inject that device.

**Where the harness puts its targets.** `NativeMultisampleDepth.cpp` builds its own `VkInstance` and `VkDevice` (`class Device`, from line 43), its own `Context` and `Recorder`, and host SPIR-V shaders (`FetchShader`, `DepthVertexShader`). Its native target is never on the driver's device.

**So a DCB submitted from this harness can't affect its target:**
- the driver's queued fill sits in the driver's recorder, never the harness's;
- the global active recorder can match only one of the two devices;
- the harness's target would see neither the pending write that refuses nor the queued-write note that `CheckCurrent` matches against `clearFillNote` (DepthSurface.cpp:412-415).

Any red or green such a test produced would depend on which recorder was activated last, not on line 307.

The existing `ClearSource::QueuedFill` case (lines 829-835) gets around this by recording the fill on its own recorder (`QueueTargetFill`) and calling `NoteDepthMetadataFill` itself, which is the fake the brief rules out. `DepthFastClearSubmit.cpp` mixes a test `VulkanDevice` for draws with driver DMA fills too. That works there only because a single-sample depth surface reads the global note and has no recorder check, and its HTILE (32 KiB) takes the synchronous path.

## What is reachable

The queued DMA path itself is reachable:
- `PipelinedDma.cpp` (`agc_driver_pipelined_dma`) sets `APS5_PIPELINED_DRAWS=1` and `APS5_PIPELINE_DMA=1` and submits DMA_DATA through `sceAgcDriverSubmitDcb`. `Driver::execute` sets `DrawPipeline::Active()` for a pipelined queue-0 submission.
- Its fills are small, so it never takes the >64 KiB branch.
- A driver-level test could take that branch with a first draw or dispatch, so the driver's device exists, then a DMA_DATA fill over 64 KiB. `DriverDetail::dmaFills` would prove it, as `tests/Submit.cpp:543-549` does for the synchronous path.

What's missing is the native multisample depth target on that same device.

## What is missing, and the options

1. **A driver-level PM4 fixture (JJenkx's kind).** All through `sceAgcDriverSubmitDcb`, so the driver's device owns everything:
   - **Create the target:** a draw with a 4-sample D32S8 depth target and HTILE. That means `DB_Z_INFO` with 4 samples, the depth and stencil bases, `DB_DEPTH_SIZE_XY`, `DB_HTILE_DATA_BASE`, a pipe-aligned `DB_HTILE_SURFACE`, the stencil-disable bit for the depth-only HTILE case, `PA_SC_AA_CONFIG` with 4 samples, `DB_RENDER_CONTROL` and `DB_DEPTH_CONTROL`. It also needs guest VS and PS binaries, registered as `StencilKnownReplace.cpp` and `MsaaEnableSingleSample.cpp` do. That file already sets up single-sample depth and stencil draws.
   - **Fill:** a DMA_DATA fill (source 2) over HTILE larger than 64 KiB. JJenkx used 131072 bytes, three refills each.
   - **Sample:** a guest shader that samples the 4-sample depth through a T# with the HTILE address (an MSAA `IMAGE_LOAD` with a fragment index). No existing driver-level test has one; it would be hand-written RDNA code.
   - The red is the refusal coming back from the sampling submission; the green is the cleared depth sampled after line 307 is fixed.
   - This is a new test file, not a mode of `NativeMultisampleDepth.cpp`, and well beyond a "case or mode". I'd estimate a day of work, mostly the guest shaders and the driver's eligibility rules for a native target.
2. **A test seam in product code**, for example a way for a test to get or supply the driver's `VulkanDevice`. The existing harness could then build its target in the driver's `Context`, with only a small change to the test. The brief says nothing else in product code may change, so this needs the PM's decision.
3. **JJenkx's private fixture**, if they will share it or the parts it needs (the PM4 sequence and the sampling shader).

The fix itself is ready: the one-argument change at `PacketMemory.cpp:307`, with the `Co-authored-by: JJenkx <31495916+JJenkx@users.noreply.github.com>` trailer. I held it back because the brief wants it in one commit with a test that is red without it.
