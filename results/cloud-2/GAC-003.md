- No rebase: the branch still sits on upstream 9f03c4fe0, and nothing on these paths needed upstream's newer main.

Summary:

- **Indirect expands run** (fix 1). DRAW_INDIRECT and DRAW_INDEX_INDIRECT read their records on the CPU, the way the draw path's CPU route does (details in section 3). The full-surface pass runs when a record has a nonzero vertex or index count and instance count; otherwise nothing is written. No case needs to throw: arguments written by earlier GPU work are waited for through the flush hook.
- **No depth surface at the read base** (fix 2):
  - With a pending HTILE clear tracked for the surface (`NoteHtileDepthClear`), the write base gets the clear value (`DB_DEPTH_CLEAR`).
  - Otherwise it gets the read base's guest bytes, same size and swizzle.
  - Village's boot expand no longer throws or needs skipping.
- **GPU buffer read of the write base** (fix 3). The root cause is address-based builds. A program that makes a flat/global access, or reads a V# the resource tracker cannot follow, maps the registered heaps whole and reads imported memory in place. It never stores the results pending there, even with `APS5_BDA_FLUSH=1`, because the cached address space skips that flush. An address-based copy of the write base read **0 of 15360 texels**, which matches Village's "nz=0.00 at bind". The expand now stores the written plane into a host-imported write base at once, as a recorded GPU-direct store with no wait.
- **`agc_driver_depth_alias_read_single` is not fixed by this** (still 0 of 32 lanes), so it stays off this branch.
- **`ctest -R '^agc'` with CI's flags**: 557/557 pass, 40 skipped, both at 0a4f81005 and at 1027f2bdc. No status changed.

### The test cases

`agc_driver_depth_expand_out_of_place` now runs nine cases. All use a 160x96 Z_32_FLOAT SW_64KB_Z_X surface with stencil, and Village's register state for the expand (`DB_RENDER_CONTROL` 0x60, two raster samples). A case name on the command line runs that case alone; with no argument (as ctest runs it) all nine run in order.

1. `direct`, `direct-two-samples`: the two existing cases, unchanged in substance. Shared code was factored out (`NewSurfaces`, `DrawnDepth`, `Expanded`, `Dispatch`, `TexelOffsets`).
2. `draw-indirect`, `draw-index-indirect`: the expand issued through PM4 as Village issues it.
   - Packets: `SET_BASE` (0x11, base index 1) of the draw indirect base, then `DRAW_INDIRECT` (0x24) or `DRAW_INDEX_INDIRECT` (0x25) at offset 0.
   - The indexed form first sets `INDEX_TYPE` 32-bit, `INDEX_BASE` and `INDEX_BUFFER_SIZE` 3, with indices 0, 1, 2.
   - The record sits in a guest block: {3, 1, 0, 0}, or {3, 1, 0, 0, 0} for the indexed form.
   - The write base must hold the read surface's depth, sampled and read raw after a flush.
3. `empty-indirect`: the CPU fills the write base with 0.5. Then two `DRAW_INDIRECT` expands run, records {0, 1, 0, 0} and {3, 0, 0, 0}. All 32768 dwords must still be 0.5 after a flush.
4. `cleared-read-base`: no depth surface ever exists at the read base.
   - The read base holds 0.5 written by the CPU, and its HTILE is 0xffffffff (expanded).
   - RADV's HTILE update kernel then runs through PM4 (`DISPATCH_DIRECT`, 32 groups of 64), clearing ZMASK. The driver recognises it with `HtileDepthClearAddress` and records a pending clear.
   - The expand runs with `DB_DEPTH_CLEAR` = 0.375, and the write base must hold 0.375 everywhere.
5. `guest-read-base`: no depth surface and no clear, with HTILE 0xffffffff.
   - The CPU writes a gradient (0.25 + x/65536 + …) into the read base, tiled with the SW_64KB_Z_X equation.
   - The write base must hold it, and its 131072 bytes must equal the read base's.
6. `buffer-read`: right after the expand, one `DISPATCH_DIRECT` of 32 groups x 1024 threads copies the write base.
   - Each thread copies one raw dword: `buffer_load_dword` through a V# covering the whole plane, `buffer_store_dword` to a guest block.
   - The copy, detiled with the SW_64KB_Z_X equation, must equal the read surface's depth.
7. `address-based-buffer-read`: the same copy with one `global_load_dword` of a zero dword added to each value. `APS5_TRACE_BDA=1` confirms the program is address-based: `[bda] LoadAddressU32 at pc 0x00000018: global access, offset immediate`.

## 3. How the indirect arguments are read, and what still throws

`Driver::precheckDraw` (`DrawPrecheck.cpp`) decodes the expand first. Any refusal of `DecodeDepthExpandPass` throws exactly as before. If the draw is indirect, the precheck then:

1. Records the queue's deferred labels (`recordQueuedLabelsBeforeRead`), as the draw path's CPU route (`Driver/Draw/Draw.cpp:307`) and `dispatchIndirect` do before every CPU read of indirect arguments.
2. Reads the count, `min(ReadDrawCount, packet count)` for the count-address forms, and each record (`Pm4::ReadDrawArguments`). This is the same code and the same `min` as the draw path's CPU route (`Draw.cpp:309-311`, `Graphics/src/Draw.cpp:2046-2048`).
3. Runs the pass if any record has `count != 0 && instances != 0`. Otherwise it returns `DrawVerdict::Nothing`, so nothing is written. The multi forms (0x2c, 0x38) take the same path.

**Arguments written by earlier GPU work.** Both reads go through `GuestMemory::Read` and its flush hook, `Recorder.cpp FlushForAccess`. The hook:

- records a queued label of this queue that overlaps the range;
- syncs the recorder through any recorded GPU write noted over the range (`SyncThrough`);
- stores pending storage-image results over the range.

So records written by an earlier dispatch or label on the queue are complete when they are read, in packet order, as the CP would see them. Data another queue writes later is ordered by the guest's own `WAIT_REG_MEM` or labels, which run first. This is how the driver orders every CPU-side indirect read: dispatches, the draw path's non-GPU route, and `INDEX_ATTRIBUTES_INDIRECT`. I found no case where the arguments can only be known on the GPU, so nothing new throws.

**The draw's geometry is not checked**, as on the direct path. The pass is the whole surface when viewport and scissor cover it; the records only decide whether it runs.

One difference from the draw path: an indexed record whose first index is at or past `INDEX_BUFFER_SIZE` still counts as drawing. The draw path skips such a record, `Draw.cpp:337`. The task's rule is count and instances, and I kept it.

**What still throws**, unchanged from 0a4f81005:

- **Decode refusals** (`State.cpp DecodeDepthExpandPass`):
  - a moved stencil plane;
  - clear, copy, resummarize or decompress bits, or no `DEPTH_COMPRESS_DISABLE`;
  - depth, stencil or bounds tests, or color writes;
  - a depth plane other than Z_32_FLOAT, a multisampled surface, or a swizzle other than SW_64KB_Z_X;
  - a partially resident or mipmapped surface, or a view with a base slice, mip or read-only plane;
  - bases that are not 64 KiB aligned;
  - a window offset, VTE other than 0x43f, or a viewport or scissor that does not cover the surface.
- **`RunDepthExpandPass`**:
  - "into a live depth surface";
  - "from a depth surface of another extent, format or sample count";
  - "without a storage image of the write base" (or "of the read base"), which cannot happen while the storage cache works.
- **The indirect reads themselves** throw as any indirect draw's do: unreadable record memory (`GuestMemory::CheckRange`), and `resolveIndirectDraw`'s "indirect draw base has not been set", record-range overflow and missing `GE_INDX_OFFSET` or `INDEX_BUFFER_SIZE`.
- **Indirect CB metadata passes** (`DecodeColorMetadataPass`) still throw "indirect CB metadata passes are unsupported". That was not in this task.

**Removed:** "indirect DB expands are unsupported", and "without a depth surface at the read base".

## 4. No depth surface at the read base: what I chose

`RunDepthExpandPass` (`DepthSurface.cpp`) now picks what the DB reads:

1. **The live depth surface at the read base** (`depthOwners`), copied as before.
2. **No surface, and a pending HTILE clear covering the read surface's HTILE** (`clearedHtiles`, filled by `NoteHtileDepthClear` from the HTILE kernel the dispatch path recognises): the write base's storage image is cleared to `DB_DEPTH_CLEAR` (`vkCmdClearColorImage`).
   - On the console every tile reads as cleared, so the DB writes the clear value.
   - The pending clear is only looked at, not taken (`findClearedHtile`; `takeClearedHtile` now uses it). The expand changes nothing at the read base, and a surface created there later still starts at its own clear value.
3. **Otherwise: the read base's guest bytes.** The storage image of the read base's R32F SW_64KB_Z_X view, uploaded from guest memory or holding newer results still pending, is copied image to image into the write base's (`vkCmdCopyImage`).
   - Same size and swizzle; the test checks the write base's bytes equal the read base's.
   - This is what the DB does for tiles whose HTILE says expanded: it writes their bytes out as they are.
4. In every case the write base's image is then marked dirty.

**Why not skip:** both values are sound where they apply. The clear value is what the console writes for cleared tiles; the guest bytes are what it writes for expanded ones. Skipping leaves the write base at whatever the CPU last wrote there.

**The limit, written in the debt entry:**

- The HTILE words in guest memory are not read. An HTILE that the CPU or a DMA fill cleared before any surface existed is taken as expanded: `NoteDepthMetadataFill` updates only existing surfaces, and `NoteHtileDepthClear` is the only path that tracks a clear without a surface.
- A per-tile decode of guest HTILE would need the HTILE addressing equations, which the driver does not have.

In game, the boot expand from 0x202a8a0000 now logs one of:

- `[gpu] DB expand: 0x202a8a0000 (1920x2160) has no depth surface; DB_DEPTH_CLEAR (an HTILE clear is pending) is written at 0x20298b0000`
- `… has no depth surface; its guest bytes are written at …`

The line is printed once per kind. It replaces the experiment's `[re8-expand] … skipped`.

## 5. The GPU buffer read of the write base

### Root cause

Before this, the expanded plane was only pending in the write base's storage image (`MarkDirty`). Readers store pending results first, by range, through:

- `FlushPending` before an in-place bind (`GuestBufferMemory.cpp UploadFinish`, the `region.direct` branch);
- the flush hook on CPU copies (`copyRegion`) and on mirror refreshes (`syncRange`).

An **address-based build** is one with `info.usesDma`: a flat/global/raw scalar access (`ResourceTracker.cpp:1631`) or a V# whose words the tracker cannot follow (`:1407`). It leases every readable GPU range and binds each imported one whole, in place.

- The per-region store is exempt for those (`if (!(addressable && region.hostBacked) || bdaFlush)`).
- With the cached address space (the default), the imported ranges move into `space->base` and are not in the loop at all. So even `APS5_BDA_FLUSH=1` does not reach them.
- The program reads the import, which holds the CPU's bytes.

This reproduces Village's symptom. Its copy shader 0x203f1ea500 read the write base through a V# and found it all zero at bind. I cannot see from here whether that shader is address-based. The in-game check is `APS5_TRACE_BDA=1`: a `[bda] … access` line for it means it is.

### Where the flush has to go

Not in the address-based build. It cannot know which of its leased heaps the program reads, and storing every pending image in them is the cost the exemption avoids.

So the store goes at the expand. After `MarkDirty`, if the write base is host-importable (`HostImportFor`), `StorageTexture::FlushPending(writeBase, planeBytes, nullptr, "DB expand")` runs:

- The write-back into an import is the GPU retiler, recorded into the open batch with no wait.
- Anything recorded later, an address-based dispatch or draw included, reads the plane from the import.

A write base that is not imported keeps the plane pending, as before. Nothing binds such memory in place, and the copy and mirror paths store it first.

**Diagnostics for GAC.** `APS5_TRACE_FLUSH=1` shows the store at each expand. In game it should read `[flush] image 0x20298b0000+0xff0000 for DB expand 0x20298b0000+0xff0000`; in the test it reads `[flush] image 0x556d619f0000+0x20000 for DB expand 0x556d619f0000+0x20000`. Before this branch, `APS5_NO_ADDRESS_SPACE_CACHE=1 APS5_BDA_FLUSH=1` was the only setting that made an address-based reader see the plane, and it is expensive.

**Cost.** One write-back of the plane per expand into an imported write base: 16,711,680 bytes for Village's 1920x2160 (2176 rows).

- It replaces the store a buffer reader's flush would have made anyway.
- It is extra only when nothing ever reads the bytes, and texture reads are still served from the image.
- At 4 expands a frame that is about 64 MiB a frame written by the GPU into host memory, on top of the two plane copies GAC-004 asks about. I did not measure it on a real GPU; it belongs in GAC-004's cost numbers.
