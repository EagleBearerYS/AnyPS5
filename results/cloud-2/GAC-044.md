## 1. What Windows imported differently

From the verify run 38824453012, Windows job 116728502077. Both runs, with main's implementation and with the fix, stopped in setup:
```
[gpu] host import budget: 3 MiB live of 3 MiB (APS5_HOST_IMPORT_MIB); 1 imports (0 MiB) refused so far, last 0x200400000+0x10000
AGC graphics: the idle and busy ranges were not imported
```

**Where the ranges were:**
- On Windows, `RunHeapMirrorUnwatchTests` takes its three pieces from `GuestArenaAllocate`, in order: heap (2 MiB allocation, 2 MiB range), idle (2 MiB allocation, 1 MiB range), busy (64 KiB).
- The busy range at 0x200400000 is the arena's start plus 4 MiB. So the arena packed them: heap 0x200000000-0x200200000, idle from 0x200200000.

**Why the idle import took the heap:**
- `continuesRun` (main GBM:812) holds for two registered ranges when one ends where the other begins and their readable, writable and gpu flags agree. The test registers all three with the same flags.
- With no import window (`importWindow` 0, as the tests leave it), main's `importRun` (GBM:826) extends a run over every continuing neighbour.
- `HostImportFor(idle, 64)` therefore imported heap + idle as one 3 MiB run.
- The 3 MiB budget (heap + idle + busy, less one block) then refused the busy range.

**Why Linux never saw it:** on Linux each piece is its own `mmap` with a block of slack for alignment. Every range ends before its mapping does, and the next mapping starts after that, so two ranges never touch.

**The reproduction on Linux:** I mapped the pieces back to back from one reservation, in the arena's order (local patch, not committed). Every test then failed exactly as on Windows:
```
[gpu] host import budget: 3 MiB live of 3 MiB (APS5_HOST_IMPORT_MIB); 1 imports (0 MiB) refused so far, last 0x7f0e3c400000+0x10000
AGC graphics: the idle and busy ranges were not imported
```
A probe after the idle import printed `3145728 bytes live, heap covered 1, heap+idle adjacent 1`.

## 2. The fix

```diff
-    const std::array<std::pair<std::size_t, std::size_t>, 3> sizes{{{heapBytes, heapBytes}, {heapBytes, idleBytes}, {busyBytes, busyBytes}}};
+    const std::array<std::pair<std::size_t, std::size_t>, 3> sizes{{{heapBytes + block, heapBytes}, {heapBytes + block, idleBytes}, {busyBytes + block, busyBytes}}};
```

- **Why it holds by construction:**
  - Each allocation is now one 64 KiB block longer than its registered range.
  - Every range starts at its allocation's start: on Windows the arena pointer, on Linux the aligned pointer inside the mapping.
  - So every range is followed by at least one unregistered block. No two of the test's ranges can be adjacent, whatever the allocator's order or packing.
  - The setup's existing check (`HostImportLiveBytes() == idleBytes + busyBytes` and the heap not covered) fails loudly if that ever changes.
- **The heap and idle allocations stay one size**, because the test swaps their pointers when the allocator puts idle lower (Linux `mmap` grows down).
- **Each test's point is unchanged:**
  - the first build refuses the 2 MiB heap and mirrors it;
  - the second build, after the heap's range leaves the watch, must not reuse the mirror.
- **The setup line now reads the same on both layouts:** `1 MiB live of 3 MiB ...; 1 imports (2 MiB) refused so far, last <heap>+0x200000`.
