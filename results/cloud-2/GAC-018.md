## 4. Step 3: where `NoteKeysStore` runs relative to the bytes' store
The test didn't fail with the pipeline on, so this is the code reading at a5285f9c4b, for both pipeline modes.

- **With `APS5_PIPELINED_DRAWS=1` only, there is no queued commit for the store, and the order holds.**
  - **Not queued:** `PacketExecution.cpp:179` queues a packet as a commit only through `enqueueLabelPacket` (0x49 and 0x37) or `enqueueDmaPacket`. `enqueueDmaPacket` returns false unless `APS5_PIPELINE_DMA` is set (`PacketMemory.cpp:290`).
  - **Drain first:** at `PacketExecution.cpp:195`, DMA_DATA (0x50) is not a packet that `keepsDrawPipeline` lets through. So with commits queued, the worker drains the draw pipeline before the packet.
  - **Then the store:** `preparePacketMemory` stores the bytes (`WriteLabelOnGpu`, or the CPU write), then calls `noteLabelStore` and `NoteKeysStore` (`PacketMemory.cpp:153`), all under the GPU lock, on the worker.
  - The draw that left the pending results is therefore recorded before the store and before the note. That matches the passes above.
- **With `APS5_PIPELINE_DMA=1` as well, `NoteKeysStore` doesn't run at all.**
  - **The commit:** `enqueueDmaPacket` turns a queue-0 DMA_DATA with immediate data (source 2, up to 16 MiB), or a copy, into a `DrawPipeline::Queue0()` commit that calls `commitDmaStore` (`PacketMemory.cpp:328`).
  - **What it skips:** that function stores the bytes and calls `noteLabelStore`, but has no `NoteKeysStore` call. So the key fill is never noted, before or after its commit, and a later sampled read keeps the pending image.
  - **Where it would go (not done, report only):**
    - **Option 1:** call `NoteKeysStore(address, bytes, queue)` in `commitDmaStore` beside `noteLabelStore`. The commit runs in stream order after the queued draws, so the note would land after them, as on the unpipelined path.
    - **Option 2:** have `enqueueDmaPacket` decline a store that `ClassifyFill` places over an image's keys, so it takes the drained path.
