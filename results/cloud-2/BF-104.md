### Workload

The workload is Village's import trace (qf6457), times the percent.
- The schedule:
  - 1,648 refreshes retiring 1 piece;
  - 339 retiring 2;
  - 60 × 4, 20 × 16, 6 × 64 and 3 × 361;
  - 1 retiring 1,412 at once.
- That makes **2,077 retiring refreshes and 5,765 retirements**.
- Of those, **487 are 4 MiB pieces** (one in each 2-piece refresh, and 148 spread evenly over the 1-piece ones). The other **5,278 are 64 KiB**.
  - The task's 5,279 + 487 sums to 5,766, one more than its total of 5,765. The bench keeps the total, so it has 5,278 of 64 KiB.
- In all that is **2,277.88 MiB**.
- The order is shuffled with a fixed LCG, so both arms run the same sequence.

**How a retirement happens**, as in Village ("retired: the range was mapped again"):
- Each piece is a guest-arena range, registered as a guest allocation.
- It is imported on its own by `HostImportFor(…, ImportRequester::Map)`. The settings are an alignment of 64 KiB, the device's 8 MiB import window, unwatched imports, and no deferred settles.
- Then its neighbour is registered:
  - a 64 KiB piece sits at a 128 KiB-aligned slot with a 64 KiB neighbour;
  - a 4 MiB piece sits at a 16 MiB-aligned slot with a 4 MiB neighbour, which fills its 8 MiB block.
- The run grows into an aligned block, so the next refresh retires the piece's import. Gaps keep the slots independent.

**Each round:**
1. Register the round's pieces and import each one.
2. The CPU stores to every 4th page of each piece while it is unwatched.
3. Register the neighbours.
4. `BumpCollectEpoch` and a `CollectWrites` of a 32 MiB probe range, which memoizes it.
5. The CPU stores to every 16th probe page.
6. **The timed refresh:** `HostImportSerial(…, true)` runs `refreshImports` alone.
7. Two timed probe collects.
8. Check each piece: is it retired (`!HostImportCovers`), and is it watched again (`Watched`)?
9. Unregister the round and refresh, untimed.

**Build phase (32 rounds, before the workload):**
- A 64 KiB piece is imported unwatched, written, and retired by its neighbour.
- Then, with a 4 KiB budget so that no import fits, as in `retiredImportWatchTests`:
  - the first `GuestBufferMemory` lease and `Upload(true)` after the retirement is timed;
  - then the same build again.

**Copy cap:** the bench never builds during the workload. Each build in the build phase registers only the piece and its neighbour, so main's arm copies at most that one 64 KiB piece per build, far under the 64 MiB cap. `APS5_ADDRESS_COPY_MAX_MIB` is not set for either arm.

**Time:** the workload stops after 75 s and says so ("stopped by the 75 s cap"). The 100% workload took 2.0 s in the Linux dry run (§2).

### What it prints

The block goes to stdout and, when `GITHUB_WORKSPACE` is set, is appended to `%GITHUB_WORKSPACE%\verify-logs\rewatch-cost.txt`. The directory is created if missing.

The first line labels the block by what the run saw:
- `[rewatch-cost] retired ranges rewatched: N of M retired (X MiB)`;
- or `[rewatch-cost] retired ranges left unwatched: M retired (X MiB), 0 rewatched`.

Then:
- size, setup, and done (refreshes and seconds);
- imports made, unwatched and failed, and retirements seen;
- retiring refreshes: count, total, median, p99 and max µs, overall and by 1 / 2 / 3–64 / over 64 pieces;
- `UnwatchSerial` bumps: how many refreshes bumped it, and the total;
- retired spans watched again, and their MiB;
- the 32 MiB probe's collect after a refresh that bumped the serial, and after one that did not, against the same collect again with no bump between;
- the build phase: rounds, how many pieces were imported unwatched and how many were watched again, the first build after the retirement against the same build again (count, total, median, p99, max);
- the workload's wall time, and the ms of it spent in retiring refreshes.

### Limits

- **Mock device:** the mock has no live storage textures, so `AnyLiveOverlaps` scans none. The mock allocates host memory for each import, the same on both arms. There are no settle reads.
- **The memo drop:** the collect after a bump is measured on one 32 MiB range. A real build collects many ranges.
- **The harness may revert the registration.** The ctest registration is in `core/libs/prx/libSceAgcDriver/CMakeLists.txt`. If the verify harness reverts every non-test file to main's, that file goes back too, and the main arm has no `agc_driver_retired_import_rewatch_cost` test. In that case, run `agc_driver_graphics_tests --retired-import-rewatch-cost` directly. The mode itself is entirely in `tests/` files.

## 3. From the code: what #8926 adds per retiring refresh, and the estimate for Village

Per retired import, in `refreshImports`' retire loop or `retireLeastRecent`:
- `noteRetiredUnwatched`: a test of `entry.unwatched`. For an unwatched import, per registered range it holds (one here):
  - `leasedRangeOwner(lease, address)`, a `lower_bound` over the lease. That is about 12 steps for Village's roughly 3,000 registered ranges ("2960 registered ranges" in the abort);
  - a clamp and a `push_back`.
- About **0.1 µs**.

Once per refresh that retired an unwatched import:
- **`rewatchRetired`.** Per span:
  - one `imports.upper_bound` (about 12 steps over the live imports), and a walk of the imports that overlap the span. That is normally none: the grown block is not imported in the same refresh;
  - **`StorageTexture::AnyLiveOverlaps`** for that one span: the live-texture mutex, then an overlap test against every live storage texture.
  - About 0.2 µs, plus T × about 5 ns, where T is the number of live storage textures.
- **`GuestMemory::Rewatch(spans)`.** The tracker mutex is taken once. Then, per span:
  - bounds and alignment checks, and `coverage.Covers` (1 mask for 64 KiB, 64 masks for 4 MiB);
  - `walkWrites`: `++generation`, then one clearing collect through `GuestArenaCollectWrites` → `WindowsMappings::Collect` (its mutex, plus clean-range and view lookups):
    - for private (resident) memory, **one `GetWriteWatch(WRITE_WATCH_FLAG_RESET)`** over the span: **16 pages for 64 KiB, 1,024 pages for 4 MiB**. A `ResetWriteWatch` follows only if the page buffer fills;
    - for shared views, a `VirtualProtect` per run of written subpages, to re-arm them;
    - each page found written is stamped;
  - `coverage.Restore` (1 or 64 masks, and the generation map erase);
  - `noteCpuStore`: per 64 KiB block one `cpuPages` entry and 16 page stamps;
  - per block: `driverPieces.erase` and `stamp` (a leaf lookup and 3 stores). That is **1 block for 64 KiB, 64 for 4 MiB**.
- **About 2–4 µs per 64 KiB span**, dominated by the write-watch syscall, and **about 15–40 µs per 4 MiB span** (the kernel walks 1,024 PTEs; 64 block notes and stamps cost 3–5 µs).
- **One `unwatchSerial` bump** per refresh that restored anything.

**Estimate for Village** (2,077 retiring refreshes; 5,765 retirements, 5,279 × 64 KiB + 487 × 4 MiB):

| part | estimate |
|---|---|
| bookkeeping (`noteRetiredUnwatched`, the span lookups) | 5,765 × ~0.3 µs ≈ **2 ms** |
| `AnyLiveOverlaps` | T = 100: **≈ 3 ms**; T = 1,000: ≈ 30 ms |
| `Rewatch`, 64 KiB spans | 5,279 × ~3 µs ≈ **16 ms** |
| `Rewatch`, 4 MiB spans | 487 × ~25 µs ≈ **12 ms** |
| tracker locks | 2,077 × < 0.1 µs, negligible |
| **direct total** | **≈ 30–35 ms over the load** (T ≈ 100) |

**Per refresh:**
- about 15 µs on average;
- a median refresh (one 64 KiB piece) costs about **+3 µs**;
- one with a 4 MiB piece costs about **+25 µs**;
- the 1,412-piece refresh costs about **+4–6 ms**.

**Indirect costs:**
- **The memo drops.** There are up to 2,077, one per retiring refresh. Each drop makes every range collected again in the same collect epoch walk once more, instead of hitting the memo. The epoch ends at the next ordering point anyway (a submission start, a wait, a drain).
  - Worst case: about 200 ranges × about 3 µs ≈ 0.6 ms per drop, so **≤ ~1.2 s across the load**.
  - In practice it is lower. The grown block's own import unwatches its range when it is made, and that bumps the same serial on main too.
- **The stamps.** The next build that uses each restored range reads it once in full (a heap-mirror refill). That is 2,278 MiB ≈ 0.3–0.6 s at 4–8 GB/s.
  - On main, the same ranges stay unwatched and are copied on **every** build that touches them. That is the 185 MiB copy that passed the 64 MiB cap and aborted Village.
  - So this replaces a per-build cost with a one-time one.

**What the Windows run should show if this estimate holds.** The bench's mock has T = 0.
- Retiring-refresh total: #8926's arm about **20–30 ms** above main's at 100%.
- 1-piece median: about +2–4 µs.
- `UnwatchSerial` bumps: main **0**; #8926 **2,077**, one per retiring refresh.
- Rewatched: main 0; #8926 5,765 spans (2,277.88 MiB).
- The probe collect after a bump: a walk of 32 MiB with 512 written pages, against a memo hit of about 0.1 µs.
- Build phase: the piece is watched again in 32 of 32 rounds on #8926 and in 0 on main.
