## What each FMASK path changes, and whether the titles need part 2

**FMASK is eight-fragment only on `main`:**
- `initialDccClear` takes an FMASK range only `if (use.samples == 8u && use.fmaskAddress != 0u && use.cmaskAddress != 0u)` (main `:572`; `:620` on A, `:573` on B).
- `checkDccCurrent`'s FMASK checks run only `if (fmaskRange)`.
- The read guard adds the FMASK plane only for 8 samples (main `:734`).
- `FmaskSampled` requires `target.samples == 8u` (`:284`/`:285`).

**For 4-sample targets such as Rush 2's,** neither `:578` nor `:618` is ever reached, so parts 2A and 2B change nothing for them. A compressed FMASK read whose descriptor matches a resident 4x target refuses in `FmaskSampled` with `native FMASK sampling requires a tracked eight-fragment DCC target`. One with no matching resident target refuses in ShaderResources.cpp:691 with `compressed FMASK sampling without a matching resident native target is not implemented`. Neither message involves watched memory, and neither branch changes them.

**For 8-sample targets** whose FMASK lies in a compared Linux import (part 2A) or a pending Windows settle (part 2B), the target now gets past `native FMASK contents require watched guest memory` (`:578`), and resident reuse past `native FMASK sampling requires watched guest memory` (`:618`).

**So for the titles:** if the FMASK stops the reporter saw after the local settle floor are on 4x targets, the titles do not need part 2. Their next stop would be the 4x/no-owner refusal above, which is #8429's area (`fix(agc): read FMASK of up to 8 samples in every storage width`) and not a watched-memory question. Part 2 matters only if those targets are 8x. The reporter's refusal text would tell which:
- `native FMASK contents require watched guest memory` or `native FMASK sampling requires watched guest memory`: 8x, part 2 needed.
- `requires a tracked eight-fragment DCC target` or `without a matching resident native target`: not part 2's.
