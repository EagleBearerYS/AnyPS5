## 1. Overlap

### The central question

**His heap does hold the images of a guest image table: every element gets a heap slot, and the shader picks it at run time by the table index. But the images are still resolved on the CPU, per draw.** The shader never reads or hashes a T#. This is the second model in the question: images resolved on the CPU and written into heap slots per draw.

How it works, step by step:
1. **The CPU decodes the table.** `ShaderResources::resolveImageTables` (`Graphics/src/ShaderResources.cpp:5030-5079`) walks each table element's T# words from the guest table. It gets each texture from the texture cache (`cachedTexture`) and places it in `table.elementTextures[element]` (`:5053-5058`). Heap stages also fill `elementStorage` (`:5045`).
2. **The CPU turns textures into slot numbers.** `ShaderResources::writeHeapTableMap` (`:5868-5955`) converts each element's texture into a heap slot, using `BindlessHeap::TextureSlot`, `StorageSlot` and `SamplerSlot` (`:5890`, `:5900`, `:5907`, `:5917`). It appends the slot numbers to the stage's table map. b969a808d adds two more map parts for 32- and 64-bit atomic views (`:5921-5951`).
3. **The map goes into the ring.** `heapSpan` (`:5957-5964`) writes the map into the heap's ring, or keeps the previous span when its words are unchanged and still held. `PatchDataAddresses` puts the span's offset in the push root as `RootStageField::TableMap` (`:5841`). It runs for every heap stage from `writeHeapStage` (`:6095`).
4. **The shader indexes the map at run time.**
   - It computes the record from the table offset it loaded: `(offset − addend) / stride` (`Spirv/SpirvImageEmitter.cpp:1650-1655`).
   - It reads that record's element from the map, then the element's slot: `LoadTableMap` (`:1607-1618`) loads ring words through the root, `TableMapAt` (`:1739-1741`) and `tableHeapSlot` (`Spirv/SpirvMemory/SpirvDescriptors.cpp:89-98`) do the lookups.
   - It then indexes a `GpuImageHeapSlots`-element heap array, non-uniformly (`SpirvDescriptors.cpp:102-111`). That array is declared at set `FragmentDescriptorSet` (`Spirv/SpirvMemory/SpirvEmitterHelpers.cpp:550-558`).
5. **A record outside the CPU's snapshot reads poison.** It gets `OutsideSnapshotPoison` (`SpirvImageEmitter.cpp:1658`, `:1678`).

So the run-time part is the **index into a map the CPU built from its own decode of the table**. It is not a lookup of the T#.

Two more facts about his branch:
- **The other files have no table logic.** `DescriptorHeapObjects.hpp:10-28` only records `VkImageViewCreateInfo` and `VkSamplerCreateInfo` per handle, because `vkWriteResourceDescriptorsEXT` and `vkWriteSamplerDescriptorsEXT` need create infos (`BindlessHeap.cpp:585-620`). `HeapStages.cpp` only decides which stages are eligible (`:115-123`). b969a808d removes the `AtomicTableImage` refusal there.
- **#6947's `HeapLookupResolve` pass is gone.** That was a compute shader that probed a hash table for CPU-supplied keys and patched slot words (`BindlessHeap::AddLookupFixup` at 9a1b77846). afa7b387f drops it, and CMake no longer lists `agcHeapLookupShaderHeader`.

**Bind split notes:**
- **Heap pipelines have no descriptor sets.** They are built with `VK_PIPELINE_CREATE_2_DESCRIPTOR_HEAP_BIT_EXT` and `layout = VK_NULL_HANDLE` (`Graphics/src/Pipeline.cpp:597-604`). Pipeline library parts are built the same way (`PipelineLibrary.cpp:210-217`).
- **Bindings reach the heap through `DescriptorHeapMappings`** (`BindlessHeap.cpp:691-750`):
  - set-1 image and sampler bindings map to the heap at a constant offset per kind;
  - workgroup memory, GDS and the fault buffer map to push addresses.
- **Any other set or binding makes the stage unmappable** (`heapBindings`, `BindlessHeap.cpp:662-665`). So a #7642 stage that uses set 2 (heap) and set 3 (buckets and ring) cannot be a heap stage.
- **Mixing heap and set-based stages in one pipeline is refused** (`Pipeline.cpp:383`).
- **Compute is already on the heap**, which is what fd5ae0e15 wanted: `ComputeTarget` sets `gpuResolvedImages = HeapComputeEnabled()` (`Execution/src/VulkanDevice.cpp:3660`), and the dispatch maps to the heap at `:5023-5024`.
- **b05de0193 has nothing to fix.** It worked around lavapipe copying a dynamic-offset set, and there are no sets here.

**His heap's own fallbacks:**
- `HeapFallback` reasons (`BindlessHeap.hpp:159`);
- refused stage pairs (`HeapStages.cpp:131-146`);
- `NearlyFull` → `HeapRefused` (`:85-87`);
- an ineligibility memo, and a retry with `gpuResolvedImages = false` (`Execution/src/Driver/Draw/DrawCapture.cpp:58-80`);
- the pipeline journal under `--gpu-heap`.

**An inversion that matters for any port:**
- #7642 keeps device tables **off** the stages that #6947 compiles in GPU mode. 0282fe5ae: "Stages that PR 6947 compiles in GPU mode … keep the CPU path"; ba03fc8a7: GPU mode "is refused with device tables here".
- On his branch the heap is reachable **only** from GPU-mode stages, through heap pipelines.
- So a device-table stage on his heap must be a GPU-mode stage: the opposite of #7642's current gate.

## 4. What #7642 would add, and what it needs from his code

His heap resolves on the CPU, so #7642's idea is still new on top of it.

**What #7642 adds:**
- **No per-draw table work on the CPU.** The CPU would no longer decode table elements or rebuild the slot map each draw: `resolveImageTables` (`ShaderResources.cpp:5030-5079`) and `writeHeapTableMap` (`:5868-5955`) are today's per-draw costs for heap stages.
- **Tables the CPU can't snapshot.** A column read at a key the CPU cannot evaluate before recording would work. Today it reads `OutsideSnapshotPoison` (`SpirvImageEmitter.cpp:1658`).
- **The supporting pieces:**
  - the persistent T#-keyed table with its miss ring;
  - expected images (pre-insert, so a first use doesn't read the null slot);
  - freshness re-checks on long-lived entries (imports, GPU-written storage);
  - eviction under a budget;
  - the fallback set back to the CPU table path;
  - profile counters.

**What it needs from his code:**
1. **`BindlessHeap::TextureSlot`, `StorageSlot`, `SamplerSlot`, `AbsentSlot`** and the sweep and generation API. These are present with the same shape (`BindlessHeap.hpp:42-52`), plus re-applying `keepFree`, `TextureSlotCap` and `TextureSlotMargin` (b8a5b93df, 677abc883).
2. **The heap arrays a GPU-mode shader already declares:** set `FragmentDescriptorSet`, binding `NativeBinding(Pixel, kind)`, `GpuImageHeapSlots` elements (`SpirvEmitterHelpers.cpp:550-558`), mapped by `DescriptorHeapMappings` (`BindlessHeap.cpp:701-718`). The device lookup samples those instead of #7642's set 2.
3. **A way for a heap-mode shader to reach the bucket buffer and the ring chunk.** That means two buffer addresses in the push root, which already carries ring, pagetable, fault and GDS addresses (`ShaderResources.cpp:5845-5864`), or new `PUSH_ADDRESS` mappings. `heapBindings` must then stop refusing them (`BindlessHeap.cpp:662-665`).
4. **Running inside his GPU-mode decision:** a device-table stage must be a GPU-mode stage. That means his eligibility code (`HeapStageIneligibility`, `HeapStages.cpp:115-123`), his pair refusals, and his `writeHeapTableMap` skipping device columns, so that both paths can coexist in one stage.

**#7642 pieces that become redundant on his branch:**
- **The whole bind split:** sets 2 and 3, `ImageHeapStages`, library layout agreement, the dynamic-offset workaround (b05de0193), the set validation, and the compute-on-heap-set commit (fd5ae0e15). Heap pipelines have no sets, and compute is already on the heap.
- **The mesh visibility half of 022703ecf.**
- **78e66b37b's 4-set / update-after-bind / 28×4096 descriptor-count refusals.** These become "has the descriptor heap and enough push data".

**#7642 pieces that stay needed:** the keys table, the device table's CPU side, the shader lookup's hashing and probing, expected images, freshness, eviction and fallback.

**Lavapipe can't run any of it** (§3): Linux CI would test only the refusal and fallback paths, plus key-table unit tests. GPU-path coverage would need RADV on Mesa 26.2 or later, ANV on 26.2 or later, or NVIDIA 595/610 or later.
