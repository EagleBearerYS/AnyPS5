# PRM-004: performance overlay test frames as PNG (cloud-2)

Result: three PNGs of the overlay drawn by its own Vulkan code on lavapipe over a synthetic gradient. Each is 390x198 RGB and under 3 KB. Nothing was committed or pushed except this file.

## Head

- `git fetch origin feat/videoout-performance-overlay` then `git checkout --detach FETCH_HEAD`.
- The head is **7126e05ca3b8f7fc7372b46aca5dcadfbac1f8bf**, not 98b9b57ef. It is one commit newer: `7126e05ca docs: say what the overlay's FPS and GPU lines count`.
- That commit changes only `docs/user/USAGE.md` (+2/−2): `git diff --stat 98b9b57ef 7126e05ca` lists only that file. The code is identical to 98b9b57ef, so the frames are the same as at 98b9b57ef.
- Ran `git submodule update --init --recursive`. The tree was clean before the local change and is clean again after it.

## How the frames were rendered

- **Local change:** a local, uncommitted change to `core/libs/prx/libSceAgcDriver/tests/PerformanceOverlay.cpp` (diff below). It was built with the existing `agc_performance_overlay_tests` target and run on lavapipe (llvmpipe, LLVM 20.1.2), as an unprivileged user, with:
  ```
  ANYPS5_OVERLAY_SAMPLES=<dir> ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx build/tests/agc_performance_overlay_tests
  ```
  The file was then restored with `git checkout --`, and the target rebuilt from the committed source.
- **Drawing:** the frames come from the overlay's production code: `PerformanceOverlay::Record`, `LayOutOverlay` and the shaders, the same code the presenter uses.
- **Format:** `VK_FORMAT_B8G8R8A8_UNORM` with `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`, the SDR swapchain format the device picks: sRGB-encoded 8-bit values. I read "B8G8R8A8 sRGB" as that colour space, not as the `_SRGB` format.
- **Background:** a horizontal gradient across the full frame width, from (0.05, 0.10, 0.25) at x = 0 to (0.90, 0.55, 0.20) at the last column. It is interpolated per column in encoded values and rounded to 8 bits, and is the same on every row.
- **Content:** `ComposeOverlay(statistics, true, true)` over an `OverlayStatistics` fed 121 presents:
  - 120 frame intervals of 16.7 ms, except 33.0 ms spikes at intervals 11, 24, 38 and 52. These are all older than the last second, so they don't move FPS.
  - GPU and driver totals growing by 9.8 ms and 4.2 ms per frame.
  - The composed lines are exactly `FPS: 59.9`, `FRAME: 16.7 MS`, `MIN/AVG/MAX: 16.7/17.2/33.0`, `GPU: 9.8 MS` and `DRIVER: 4.2 MS`.
  - FPS is 59 intervals over 985.3 ms = 59.88. The average is (116 × 16.7 + 4 × 33.0) / 120 = 17.24.
- **Corner:** top left for A and B. For C, `AgcDriver::ParseOverlaySettings("1", "br").corner`, the value `ANYPS5_OVERLAY_POS=br` yields.
- **Crop:** the panel plus 48 px on each side, clamped to the frame. The panel sits 8 px from the frame's edges (the 4-unit margin at scale 2). So the crop keeps only 8 px of margin at the top and left of A and B, and at the right and bottom of C; the other sides get 48 px.
- **Encoding:** Python's standard library only (`zlib`, `struct`, `hashlib`, `base64`). The PNGs are RGB with 8 bits per channel (alpha was 255 everywhere). Each row uses whichever PNG filter (None/Sub/Up/Average/Paeth) gives the smallest sum of absolute bytes, then zlib level 9. Chunk CRCs were checked after writing, and `file` reports "PNG image data, 390 x 198, 8-bit/color RGB, non-interlaced". The base64 is wrapped at 76 characters.

### Scale

B is drawn at the **same scale as A**: scale 2, a 334x142 panel. The overlay's scale is `max(1, (height + 240) / 480)` with integer division, reduced only when the panel would not fit. That is 1 below 720 px, 2 from 720 to 1199, 3 from 1200 to 1679, 4 from 1680 to 2159, and 5 at 2160. So 720p and 1080p use the same glyph size. B shows the panel covering a larger part of the frame (26% of its width against 17% for A), not smaller glyphs. If the PR needs a smaller-scale image, a frame under 720 px tall shows scale 1, and one 1440 or 2160 px tall shows 3 or 5.
