## 1. The counter

### Line format

The counter prints one line under `APS5_PROFILE_DRAW`. It prints at most every 10 s, from the first `BufferPool::Take` after the interval has passed. It prints once more when the device shuts down:

```
[buffers] host-visible memory: <MiB> MiB in <n> allocations; other <MiB> MiB (<buffers>), heap mirrors ..., image mirrors ..., copies ..., staging ..., write-back ..., device spill ..., shader data ..., BufferPool <MiB> MiB (<n> retained, <MiB> MiB free in <n> slab blocks)
```

Example (counter branch, Village bench, imports on, end of `--cost 20`):

```
[buffers] host-visible memory: 246.4 MiB in 120 allocations; other 0.0 MiB (3), heap mirrors 0.0 MiB (0), image mirrors 0.0 MiB (0), copies 0.0 MiB (10), staging 0.0 MiB (0), write-back 8.4 MiB (1), device spill 0.0 MiB (0), shader data 167.0 MiB (20884), BufferPool 71.0 MiB (4096 retained, 38.3 MiB free in 119 slab blocks)
```

### Mechanism (file:line at `7e992a8e3`)

- **Owners.** `HostOwner` is in `Graphics/include/BufferPool.hpp:20`. The owner is set by a thread-local `HostOwnerScope` around each creation site:
  - heap/image mirror: `GuestBufferMemory.cpp` `acquireMirror`;
  - copies: snapshot copies, `UploadPrepare`/`UploadFinish`/`recordGpuCopies`, draw-input copies (`Draw.cpp`), and storage snapshots (`ShaderResources.cpp`);
  - staging: texture, storage and depth uploads, `Recorder::DrawUpload`, colour-target transfer buffers, `GpuColorTransfer`;
  - write-back: storage-texture write-back and saved bytes;
  - shader data: `addDataBuffer`, moved-word buffers, image table maps, and the BDA table and fault buffer in `BdaResources.cpp:131`.
- **Live counts.** `Buffer::countHost` (`Resources.cpp:116`) adds a buffer's `allocationBytes` under the scope's owner, and only when its requested properties include HOST_VISIBLE. `Buffer::release` subtracts them. A `DeviceBuffer` the pool placed in host memory counts as device spill (`Resources.cpp:202`). The counts are relaxed atomics in `BufferPool::CountHost` (`BufferPool.cpp:374`).
- **Pool memory.** The pool's idle memory is summed when the line is printed (`BufferPool::HostVisible`, `BufferPool.cpp:387`): retained host-visible tier slots, plus the free slots of mapped slab blocks.
- **Allocation count.** It adds buffers with their own `VkDeviceMemory`, retained non-slab slots, and slab blocks.
- **Printing.** `BufferPool::ReportHost` (`BufferPool.cpp:417`) is called from `Take` (`BufferPool.cpp:496`) and at device teardown (`VulkanDevice.cpp:761`, before the caches are cleared).
- **Cost when off.** One cached `getenv` flag test per buffer creation, and nothing on release.
- **Not counted:** images placed in host memory by the pool's image fallback (the existing `[bufferpool]` message covers those), direct `vkAllocateMemory` sites outside `Buffer`/`DeviceBuffer` (unit shadows, settle targets), and #7647's resident mirror blocks, which it allocates itself.
- **Docs.** A row and a paragraph were added under "Driver profile lines" in `docs/dev/BUILD.md`.

### Test

`agc_driver_host_visible_owners` (`tests/execution/HostVisibleOwners.cpp`) runs with its own context copy. That copy sets `hostImportAlignment = 0` and `sparseBinding = false`, so the whole-range mirror path is used even with #7647 merged.

- A 4 MiB buffer counts as other while it lives (+1 allocation). Once released it counts under BufferPool, with the total unchanged. A staging scope then takes it from the pool and it counts as staging.
- A 1 MiB registered heap built without imports gives heap mirrors +1.0 MiB (1), cross-checked against `MirrorCounters()`. The line contains ` heap mirrors 1.0 MiB (1),`. Once the range is gone, the memory moves to BufferPool with the total unchanged.
- `agc_driver_host_visible_owners_off` (`--off`, registered at `CMakeLists.txt:1891` with the WIN32 PATH list) checks that nothing is counted without the switch.

Both tests also pass on each of the four PR merges.

## 4. The heap mirror path, and the cut

Line numbers are in `GuestBufferMemory.cpp` at `7e992a8e3`.

### When a heap can't be imported, is the whole heap mirrored or the touched pages?

The whole range.

- A build calls `acquireMirror(context, range, blocks, range->releasable)` (:3769) when `importsNow` (:2617) fails. That happens when imports are off, past `APS5_HOST_IMPORT_MIB`, refused, or the range is not write-watched.
- The mirror is one host-visible buffer of `mirror->bytes = sparse ? sparseExtent(...) : range->bytes` (:2655), allocated at :2693.
- It is filled whole: `GuestMemory::Read` of the range (:2706). For a partly committed range ("sparse" in main), the extent from the first to the last committed piece is read piece by piece and the holes are memset (:2710, :2714).
- Later refreshes copy only the 64 KiB blocks whose write-watch generation changed (`compareBlock`, :2246).

### When is a mirror released?

Only in these cases:

1. When its registered `Range` expires (the guest unmaps, frees or reprotects it). The next sweep, `sweepMirrors` (:2742, called at :3886 and on the budget path :2687), drops it.
2. When an import takes the range over: `releaseImportedMirrors` (:2767, called at :3793).
3. When the device changes: `acquireMirror` clears all mirrors (:2628).
4. If it would pass `APS5_HEAP_MIRROR_MIB` (default 24576), a sweep is tried first, and the build then throws.

Nothing ages a heap mirror. Every address-based build includes every registered range, so a mirror is never idle in that sense. A released mirror's buffer goes back to the BufferPool large tier (512 MiB budget), or is freed when it is larger.

### Does a 768 MiB writable mirror need all its bytes resident?

On main it is all resident: the fill writes every byte. Measured: +769.8 MiB RSS with only 16 MiB written.

It does not need to be:
- Write-back reads only the declared written sub-ranges (`takeHeapReferences` :5340; the heap branch of `WriteBack`, `storeChanged`/`storeSparse` :5384).
- Refresh copies only written blocks.
- Unwritten blocks only have to read as zero.

#7647 does exactly that and measures +34.3 MiB.

### Cut: stopped, because #7647 covers it

The only thing that removes this residency is not backing the untouched blocks at all. That is #7647's sparse aliased mirror. Around it:
- #8016 moves a mirror whose host allocation failed to device-local memory.
- #7292 and #8762 widen imports, so fewer ranges are mirrored.

What #7647 does not cover is a device without sparse residency aliasing, which keeps main's whole copy. I built and measured two switch-guarded cuts for that case, and neither reduces residency:

| prototype | mechanism | 768 MiB heap, 16 MiB written: off → on | why |
|---|---|---|---|
| v1, `APS5_HEAP_MIRROR_SKIP_ZERO=1` | Fill and refresh in 64 KiB blocks. Skip a block that is zero in the guest and already zero in the mirror (compare, then copy; correct for stale pooled memory). | +770.2 → +769.7 MiB | Comparing reads the mirror. Lavapipe's host memory faults pages in on read: a fresh 256 MiB buffer is +0.0 MiB after allocation and +256.0 MiB after one read pass. |
| v2, `APS5_HEAP_MIRROR_ZERO_INIT=1` | Enable `VK_EXT_zero_initialize_device_memory` when present. Give heap mirrors a fresh `VK_MEMORY_ALLOCATE_ZERO_INITIALIZE_BIT_EXT` allocation that bypasses the pool. Copy only the nonzero guest blocks, never reading the mirror. | +769.8 → +770.4 MiB (3840 of 4096 blocks skipped at 256 MiB) | Lavapipe implements the zero-init flag by filling the memory: a zero-initialised 256 MiB buffer is +256.0 MiB at allocation, against +0.0 for a plain one. On discrete drivers, host-visible system memory is pinned when allocated, so skipping writes can't reduce residency there either. |

Neither prototype is on the branch. Both patches are kept locally, so there is no red/green test and no cut-off/on bench beyond the numbers above.

### Next candidate
