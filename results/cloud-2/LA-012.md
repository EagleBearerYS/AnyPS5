# LA-012: lane A, part (f) without eager write-back, and finer re-checks of imported entries (cloud-2)

**Branch: `exp/lane-a-fresh` at 7df7e7008**, 4 commits on `exp/lane-a-recorded` 9673cb568, not rebased. No PR was opened and nothing was posted.

**Machine:** cloud-2: Intel Xeon @ 2.80 GHz, 4 vCPUs, 15 GiB, Ubuntu 24.04, gcc 13.3.0, wild 0.10.0. lavapipe is Mesa 25.2.8 (LLVM 20.1.2), at its default thread count; there is no `/dev/udmabuf`.
- **Build:** CI's Linux configure.
- **Runs:** as `runner`, stdin from /dev/null, with `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1`.

RESULT:
- **(f)'s cause: the device path's first-miss latency, not a cache or fallback bug.**
  - Without eager write-back, the warm draw is prepared in batch 2 while batch 1, which holds the cold draw's miss, is still in flight. Batch 1 was submitted when the guest submission ended, and nothing waited for it: `AgcDriverWaitIdle` waits for the driver to process submissions, not for the GPU. So its miss is not drained yet, and the warm draw misses too and reads zeros.
  - Eager write-back waits for every batch, which hid it.
  - A trace of `DeviceImageTable::Prepare` shows the cold draw at "open serial 1, chunk 0" and the warm draw at "open serial 2, submissions 1, chunk 1 (chunk 0 still busy), entries 0".
- **(f)'s fix is in the harness.** Part (f) reads the target back after each cold draw, as part (b) already does, and a new `lazy` argument leaves eager write-back off.
  - **Red:** "(f) the warm draw: pixel (0, 0) channel 0 is 0, expected 160", 3 of 3 runs.
  - **Green:** 3 of 3 in all 8 configurations, and 24 of 24 lazy runs with the switch, four copies at a time.
  - **A first version** read back only after the first key. It failed 4 of 12 such runs: "did not send the program back to the CPU table path (heap full 0, fallbacks 0)". The commit now reads back after every cold draw.
  - **Reaping in `Prepare`** was tried and dropped: it was not the cause, and it showed no gain.
- **The re-check rule.**
  - **Before:** an entry on host-imported memory, which is unwatched, was stale at every collect-epoch move and was looked up again in full. That is every live entry, every frame.
  - **After:** it stays fresh across an epoch move if no driver store has landed in it since its lookup (`NewestStamp`, as before), and its texture still holds guest memory's bytes. For a storage image's texture, the new `StorageTexture::UntrackedUnchanged` decides: it is `Refresh`'s own memoized compare against the upload, provable only while the image still holds its upload. For a snapshot texture, the new `DeviceTableTextureCurrent` decides: the texture cache must still hold that texture, and its snapshot must equal guest memory. Anything else is re-checked in full.
  - It keeps all three required cases:
    - **(c), a CPU write:** caught; 1 re-check instead of 13, and the written texels drawn;
    - **(g)/(h), GPU-written texture:** (h) reads the producer's texels;
    - **a dropped texture:** caught; the harness also passes with a 1 MiB texture cache.
- **The bench (`--village-bench 0 0`, switch on), interleaved, medians of 5:**

  | | before (6945ef32d) | after (7df7e7008) |
  |---|---|---|
  | imports: re-checks per frame | **256** (5,120 per 20 frames) | **0** |

  | inserts and new textures in steady state, every run | 0 | 0 |

  - **On this base a re-check costs about 14 µs, not LA-004's 150–170.** That is about 4 µs per draw, so the saving (about 3.5 µs per draw) is within run-to-run noise in driver CPU.
  - **"Imports close to copies" no longer applies here.** On this base, imports (about 95 µs) are already four times cheaper than copies (about 383 µs). LA-004's copies at about 30 µs were on an older base.

## 1. Part (f) without eager write-back

**Reproduction.** I added a `lazy` argument so the harness does not set `APS5_EAGER_WRITEBACK`, and ran `--heap-cap f lazy` in the 4 heap-cap configurations: switch unset and set, host imports and copies.
- Only switch on with host imports failed: "(f) the warm draw: pixel (0, 0) channel 0 is 0, expected 160", 3 of 3.
- The failing check is the first one. It is the second draw of key 1546, before any fallback or draw-cache reuse.

**What the counters and a trace showed** (temporary instrumentation, not committed):
- **Counters after each draw, with no read in between:**
  - after the cold draw: miss records 0;
  - after the warm draw: still 0;
  - only the final read-back drained them, both at once: miss records 2, inserted 0.
- **The `Prepare` trace:**
  - the cold draw: `open serial 1, submissions 0, chunk 0`;
  - the warm draw: `open serial 2, submissions 1, chunk 1, entries 0`.
- **Reading those:**
  - Batch 1 was submitted when guest submission 1 ended.
  - It was still in flight when the warm draw was prepared: its ring chunk was still busy, so a second chunk was taken, and its miss wasn't drained.
  - So the key wasn't in the table, and the warm draw missed as well.
- **With eager write-back:** each batch is waited for. The warm draw was prepared after chunk 0 was drained ("chunk 0, entries 1") and read the texel.
- **What the harness's `AgcDriverWaitIdle` does** (`Driver::WaitIdle`, Lifecycle.cpp:180): it waits until the driver has completed the accepted submissions, not for the recorder's batches on the GPU.

**What it is not:**
- **Not the draw cache or the fallback.** With a read-back after the cold draw, so the batch finishes and is drained before the warm draw, (f) passes lazily in all configurations, its four warm draws after the fallback included.
- **Not a missing reap.** A version that reaped finished batches at the start of `Prepare` still failed: batch 1 hadn't finished yet. Without that reap, a 300 ms sleep after the cold draw also passed, because the draw path reaps a finished batch before `Prepare` anyway. So reap-at-`Prepare` was dropped.

**The latency is the device path's design.** A missed key reads zeros until the batch that recorded it has finished and been drained. Without eager write-back, which is the default at run time, that batch can still be in flight at the next guest submission, as here.

**The fix (231e6fe52), in the harness:**
- Part (f) reads the target back after each cold draw, as part (b) does. That waits for the batch through the flush hook.
- It does so for all four keys. A first version read back only after key 1546. Lazy runs then failed 4 of 12 under four parallel copies, as in the CI mirror and scope: "(f) a heap capped at two slots per kind did not send the program back to the CPU table path (heap full 0, fallbacks 0)". Whether keys 1–3 were resolved before the check depended on GPU timing.
- A third argument, `lazy`, leaves eager write-back off.
- 6945ef32d registers `agc_driver_device_image_path_heap_cap_lazy` (switch unset) and `_heap_cap_lazy_gpu_path` (switch set).

**Green:**
- (f) passes 3 of 3 in each of the 8 configurations: switch unset and set, imports and copies, eager and lazy.
- With the switch, eager and lazy now give the same counts: "1 without a slot, 1 fallbacks (CPU table snapshots 4, CPU table bindings 2, device table prepares 4, miss records 3)".
- It passes 24 of 24 lazy runs with the switch, four at a time.

## 2. Re-checks of imported entries

**Before** (`DeviceImageTable::refresh`):
- A host import takes its allocation out of the write watch, so its entries have generation 0.
- Their blocks read as changed in every scan.
- Each key was fresh only while the collect epoch hadn't moved: `!epochMoved && NewestStamp(entry) <= entry.stamp`. The epoch moves every frame, so every live entry was looked up again in full each frame: `lookupKey`, then `LookupDeviceTableTexture`, then `cachedTexture`.
- On this base that costs about 14 µs per entry: 24 scans, 6,144 entries and 85.8 ms with temporary timing. That is 3.5 ms per 850-draw frame at 256 entries.

**Why not just drop the epoch term** (LA-004's suggestion of `NewestStamp` alone):
- On Linux, `GuestMemory::UntrackedHint` returns 0. So a guest CPU write to unwatched memory leaves no stamp, and only a content compare can find it.
- Harness part (c) with imports makes exactly such a write.

**After (bfb20f709, 7df7e7008).** Across an epoch move, an unwatched entry is fresh when nothing the driver stored has landed in it since its lookup (`NewestStamp`), and its texture still holds guest memory's bytes. Which check decides depends on the texture:
- **A texture viewing a storage image** (every entry on the bench with host imports): `StorageTexture::UntrackedUnchanged`.
  - It is the same memoized compare `Refresh` makes for memory outside the write watch (`compareUntracked` against the image's upload).
  - It is true only while the image still holds its upload, so no GPU write may have replaced it.
  - It also needs no DCC, uncompressed uploaded keys and no unit kept at unwatch.
- **A snapshot texture:** `DeviceTableTextureCurrent`.
  - The texture cache must still hold that very texture for the surface: same key, same object, uncompressed, fully resident.
  - No recorded write may be pending over it.
  - Its snapshot must equal guest memory: the same compare `cachedTexture` makes on a hit.
- **Anything else** is re-checked in full, as before:
  - a CPU write found by either compare;
  - a driver store;
  - a GPU-written image;
  - a texture the cache dropped, or a storage image no longer cached (`!image->Cached()`, as before);
  - DCC;
  - partial residency.

**Re-checks per frame, harness parts, before (6945ef32d) and after (7df7e7008):**

| configuration | (c), one CPU write | (g), four draws, one submission | (h), GPU-written texture |
|---|---|---|---|
| switch on, host imports, eager | 13 re-checked → **1** | 13 of 14 → **0** of 14 | producer's texels, 0 new textures (both) |
| switch on, host imports, lazy | 13 → **1** | 13 of 14 → **0** of 14 | producer's texels, 0 new textures (both) |
| switch on, copies, eager | 13 → 13 (1 new texture) | 0 → 0 | producer's texels; 1 new texture in frame 3 (both) |
| switch on, copies, lazy | 13 → 13 (1 new texture) | 0 → 0 | producer's texels (both) |
| switch unset (4 configurations) | 0 (CPU table) | 0 | 0 |

- (c) requires the written texture's texels and at least one re-check, and passes in every configuration.
- (g) requires re-checks ≤ entries. (h) requires the producer's texels.
- With copies the memory is watched, so the rule doesn't change anything there.
- **A dropped texture:** all parts also pass with `APS5_TEXTURE_CACHE_MIB=1`, imports and copies, eager and lazy.

## Open problems

1. **The first-miss latency spans guest submissions without eager write-back.** A key's first use reads zeros until the batch that recorded it has finished and been drained. That batch can still be in flight at the next submission. Only reading the ring of a batch that hasn't finished could shorten it, which is not possible.
2. **Part (j) fails with the switch unset, copies and lazy write-back:** "8 draws of new keys into a 512x512 target: the draw covered no pixel". It fails deterministically, before and after this branch, on the CPU table path. It is not investigated, because the task doesn't cover it.
3. **Copies are about four times slower than imports on this base** (about 383 against 95 µs of driver CPU per draw on the bench), unlike LA-004's base. That is not investigated.
4. **Windows has a write-watch hint for imported memory** (`UntrackedHint`), which could skip the compare when nothing wrote. It isn't used, so the rule compares there as well. The rule is correct on both platforms, but the compare isn't needed on Windows.
5. **LA-004 §6's thread method undercounts** when a thread exits inside the window. The process figures above don't have that problem.
