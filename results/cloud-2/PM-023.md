## 1. The red test: `agc_driver_keys_clear_over_pending`

File: `core/libs/prx/libSceAgcDriver/tests/execution/KeysClearOverPending.cpp`. It runs PM4 through `sceAgcDriverSubmitDcb`, on lavapipe.

- **Target.** 256x128 RGBA8 (128 KiB, SW_64KB_R_X). Guest bytes hold 0x40 (0.251 per channel) and its DCC keys, in their own block, hold 0xff.
- **Draw.** A full-screen triangle into the target exports 1.0. `CB_COLOR0_INFO` has DCC_ENABLE and `CB_COLOR0_DCC_BASE` points at the keys. The results stay pending on the host.
- **Clear.** A DMA_DATA fill (source DATA, pattern 0x00) covers the key extent: 0x200 bytes, the T#'s `DccKeyCount`.
- **Read.** A compute dispatch samples texel (5, 1) through a T# of the same surface that names the keys.
- **Cases:**
  - `dma-fill`: draw, fill, read. On main the read makes a view of the pending image.
  - `dma-fill-after-read`: draw, read (caches the view), fill, read. On main this read misses the fast path on the key change, then hits the cached view.
  - `cpu-store`: draw, CPU `memset` of the same keys, read. It expects the **drawn results**.
    - This deliberately inverts "a CPU store should read the clear". A CPU key store over pending results is exactly #4794's `StagedClearSampledRead` sequence, where the results must win.
    - So the two can only both be kept if the rule depends on the write's path. GPU-ordered key stores win over the results; CPU stores, which have no place in the command stream, lose to them.
    - The case pins that boundary: an order-based rule that let CPU-staged clears win would turn it red.
- **Path checks inside the test:**
  - The fill raises the packet-store counters (`storesOnGpu + storesBehindCompletions + storesOnCpu`) by exactly 1 and `dmaFills` by 0. So it went through `PacketMemory.cpp`'s store branch, not `storeBufferFill`.
  - `FindPending` returns the same image after the fill.
  - The keys read back as 0x00.
  - The image's noted fill is printed: `uncompressed` on main, `0000` with the fix.
- **Traces on main** (`APS5_TRACE_DCC_KEYS=1 APS5_TRACE_UPLOAD=1 APS5_TRACE_FLUSH=1`): there is **no** `[dcc-keys]` line of any kind. That means no "title fills keys", no "key fill over", no "refresh … -> 0000", no "sampled … reads the 0000 fill", and no flush. The read is served by the pending image's view, exactly the path PM-021 names: `ShaderResources.cpp` 587-608 keeps the source, and 641 does not refresh because the colour bytes are unchanged.

### Why the surfaces' imports are kept watched

On this VM the startup probe reports "host imports resolve write protection: yes … imported ranges are compared". An imported surface then has no write generation (`CollectWrites` returns 0), so `cachedTexture`'s `UnchangedSince` fails on every lookup and calls `Refresh`. `Refresh` sees the new clear keys and drops every pending result. So on this VM main already returns the clear for both DMA cases (log: `[dcc-keys] refresh … keys uncompressed -> 0000 (dirty 1, 2 pending units …)`), and also for the CPU case.

On Windows, `decideImportWatch` compares direct imports of private memory too. But memory that is not plain private read-write is imported through a separate alias (`GuestArenaMapAlias`) and stays watched (`watchedHostPointer = entry.alias != nullptr || …`, GuestBufferMemory.cpp ~1037). A title's direct memory is exactly that: `PhysicalBacking` is a `CreateFileMappingW` section. So on Village's PC the targets are watched, their generations are valid, no `Refresh` runs at the read, and A shows. This is from the code; I did not run Windows here.

The test therefore maps its blocks as shared sections on Windows (the pattern of `DccKeysFirstWrite`'s shared block) and sets `APS5_WRITE_WATCH_IMPORTS=watch` on Linux, without overriding a value already set. It can be run with `APS5_WRITE_WATCH_IMPORTS=unwatch` to see the compared mode. The Windows branch compiles only on Windows and was not built here.

## 2. The fix (21c4fde93)

- returns unless the bytes are one byte value (`OneByteValue`: the bytes equal themselves shifted by one, a `memcmp`);

## 4. Fast-path cost

**Code.** The fix does not touch `ShaderResources.cpp` or `Texture.cpp`. `fastTexture`, `cachedTexture` and the resource-cache revalidation run the same instructions. There is no key check added per sampled lookup.

**Measured.** I used a scratch benchmark (not committed): direct `VulkanDevice::Dispatch` on lavapipe, with `APS5_PROFILE_DRAW=1` lookup outcomes read on the calling thread. Each case is 2000 reads after one warm-up, over 2-3 runs. The un-noted and noted rows are main's case and the fix's case.

| sampled surface | image lookups per read | time |
|---|---|---|
| pending image, uncompressed keys | 0 (the resource cache revalidates) | — (565-632 µs per dispatch wall, all lavapipe) |
| pending image, **un-noted** 0000 keys (main's A) | 1 full lookup every read | "sampled hit cleared view" 7.7-9.4 µs + 2 key scans of 1.8-2.2 µs each |
| pending image, **noted** 0000 keys (the fix) | 1 at the first read, then 0 for 2000 reads | "sampled hit snapshot" 11-18 µs + 1 scan of 1.0-1.5 µs, once |

**The fix's own work is on the packet-store path, per store that lands:**

- `OneByteValue` (with a compiler barrier per call):
  - 3.8 ns for an 8-byte label store;
  - 83 ns for a 4 KiB uniform store and 1.5 µs for a 64 KiB uniform store (non-uniform bytes stop at the first difference).
- Only uniform stores call `ClassifyFill`: 32-60 ns with 3 live storage images, 1.6-2.0 µs with 259.
- A store that covers an image's keys adds `NoteKeysFill`: 66-105 ns in all with 3 images, 2.6-3.5 µs with 259.

For scale, the existing packet-store path already builds the store's bytes in a byte loop and records them on the GPU.

## 5. B: address-based reads of pending results

This is a scratch test, not on a branch: the task names only the two A branches, and on the fix branch it would fail. It reuses the red test's PM4 draw, without DCC, into a 256x128 RGBA8 target over 64 KiB holding 0x40. Then one compute dispatch copies the target's 128 KiB into a buffer, in 32 groups of 1024 threads:

- either with GAC-003's `BufferCopyCode`, buffer loads through a V#, a bound build;
- or with `AddressBasedCopyCode`, the same plus one `global_load_dword`, which makes the program address-based so its build leases the heaps whole.

Results are identical on main (red build) and the fix build. Imports were watched; the exemption itself does not depend on the import mode.

| environment | bound copy | address-based copy |
|---|---|---|
| default | 131072 of 131072 bytes drawn (results stored: `[flush] image … for imported buffer region`) | **0 of 131072 drawn, 131072 stale (0x40); results still pending after the copy** |
| `APS5_BDA_FLUSH=1` | same | **same: all stale** |
| `APS5_BDA_FLUSH=1 APS5_NO_ADDRESS_SPACE_CACHE=1` | same | 131072 drawn, results stored first |
| `APS5_NO_ADDRESS_SPACE_CACHE=1` | same | all stale |

**Answer.** Yes, main's exemption makes an address-based program read stale bytes of a drawn target. The exemption is `GuestBufferMemory.cpp` 3563-3564: `if (!(addressable && region.hostBacked) || bdaFlush) FlushPending(…)`. The program reads whatever guest memory held before the draw, for as long as nothing stores the results.

`APS5_BDA_FLUSH=1` alone changes nothing. With the default address-space cache, the heaps a build maps are the cached space's `base` regions, which `UploadFinish` serves in place without passing that per-region loop. The switch only works together with `APS5_NO_ADDRESS_SPACE_CACHE=1`. This is the same finding as GAC-003, for an expanded plane.

**No fix.** A real fix would store every pending image over the leased heaps ahead of each address-based build. That is a flush per address-based dispatch of every pending result, which the exemption exists to avoid, so it is not trivial. A small debug-only change would make `APS5_BDA_FLUSH` also flush the cached space's host-backed `base` regions (a few lines in `UploadFinish`). I did not make it, because the PC run can set both variables.

## 7. Debt-entry drafts (for `docs/dev/debt/libSceAgcDriver.md`, not committed)

- [DCC clear keys over pending results](../../../core/libs/prx/libSceAgcDriver/Graphics/src/ShaderResources.cpp) (libSceAgcDriver) - a sampled read of a surface whose results are still pending on the host reads those results, not the clear, when the title wrote clear keys over it through a path the driver does not note. Buffer fills and packet stores (CP DMA fills of at most 64 KiB, COPY_DATA, DUMP_CONST_RAM) of one key code over an image's keys are noted, and the read then sees the clear. Not noted:
  - a CPU store, deliberately: it is not ordered against the queued work, and a title may stage its next clear behind a pass that still samples the results;
  - a compute kernel other than the recognized fills (the SGPR pattern-fill kernel only memoizes its keys);
  - WRITE_DATA;
  - a packet store the driver drains and runs on the CPU;
  - a fill that does not start at the image's `dccAddress` or is shorter than its keys.

  When the surface's host import is compared rather than watched (Windows private memory, or Linux when the import probe says so), the image has no write generation, every lookup refreshes it, and the refresh drops the results under any clear keys, CPU-staged ones included.
- [Address-based reads of pending results](../../../core/libs/prx/libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp) (libSceAgcDriver) - a shader made address-based by a flat or global access, or by an untraceable V#, maps the registered heaps whole. Its upload stores no pending storage results first: the per-region flush exempts the host-backed regions of an addressable build. So it reads the bytes guest memory held before those results; a raw copy of a drawn 256x128 target reads every byte stale. `APS5_BDA_FLUSH=1` stores them only together with `APS5_NO_ADDRESS_SPACE_CACHE=1`, because the cached address space serves its regions without the per-region loop.

```cpp

    0xd7460001u, 0x04011410u, 0x34020282u, 0xe0301000u, 0x80000201u, 0xbf8c3f70u, 0xe0701000u, 0x80010201u, 0xbf810000u,

    0xd7460001u, 0x04011410u, 0x34020282u, 0xe0301000u, 0x80000201u, 0x7e060280u, 0xdc308000u, 0x03080003u, 0xbf8c3f70u, 0x4a040702u, 0xe0701000u, 0x80010201u, 0xbf810000u,
};
constexpr std::uint32_t CopyThreads = 1024;

void Copy(const Target& target, bool addressBased, const std::string& what) {
    const auto& kernel = addressBased ? std::span<const std::uint32_t>(AddressBasedCopyCode) : std::span<const std::uint32_t>(BufferCopyCode);
    std::memcpy(target.code, kernel.data(), kernel.size_bytes());
    std::array<std::uint32_t, 16> userData{};
    const auto read = BufferDescriptor(Address(target.surface), 0u, SurfaceBytes, 0x31016facu);
    const auto written = BufferDescriptor(Address(target.copy), 0u, SurfaceBytes, 0x31016facu);
    std::copy(read.begin(), read.end(), userData.begin());
    std::copy(written.begin(), written.end(), userData.begin() + 4);
    userData[8] = static_cast<std::uint32_t>(Address(target.zero));
    userData[9] = static_cast<std::uint32_t>(Address(target.zero) >> 32u);
    std::vector<std::uint32_t> words;
    const auto code = Address(target.code);
    SetRegister(words, SetShReg, 0x20c, static_cast<std::uint32_t>(code >> 8u));
    SetRegister(words, SetShReg, 0x20d, static_cast<std::uint32_t>(code >> 40u) & 0xffu);
    SetRegister(words, SetShReg, 0x207, CopyThreads);
    SetRegister(words, SetShReg, 0x208, 1u);
    SetRegister(words, SetShReg, 0x209, 1u);
    SetRegister(words, SetShReg, 0x213, (static_cast<std::uint32_t>(userData.size()) << 1u) | (1u << 7u));
    for (std::uint32_t i = 0; i < userData.size(); ++i) SetRegister(words, SetShReg, 0x240 + i, userData[i]);
    words.insert(words.end(), {0xc0000000u | (3u << 16u) | (DispatchDirect << 8u), static_cast<std::uint32_t>(SurfaceBytes / 4u / CopyThreads), 1u, 1u, 0x41u});
    Submit(std::move(words), what);
}

    const auto target = NewTarget();
    Draw(target, what + ": draw");
```
