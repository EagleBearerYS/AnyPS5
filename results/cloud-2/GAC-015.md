## PR text draft

Title: `fix(agc): store an expanded plane that host imports hold only in part`

Base: `main`. Head: `EagleBearerYS:fix/agc-db-depth-expand-partial-import-v3`. It depends on #6146 (`EagleBearerYS:fix/agc-db-depth-expand`).

````markdown
### What

An out-of-place DB expand (#6146) leaves the expanded plane pending in a storage image at the write base. `StoreDepthExpandWrites` stores such planes ahead of an address-based build, because that build reads imported heaps in place and does not store results still pending in them. It stored a plane only when one host import held the whole plane.

Host imports are made per registered range. Adjacent ranges share one import only when they fill an 8 MiB aligned window, or once a buffer bound across them joins them. So a write base across the edge of two registered ranges imported apart, or of an imported range and one that is heap-mirrored or copied, was not stored ahead of the build. The address-based build then read the imported part in place, and copies of the write base made right after the expand held the guest bytes instead of the expanded depth. In the tests they held 0 of 15360 texels when both ranges are imported, and 3072 when the second range is heap-mirrored or copied, because that range's own refresh or copy stores its block. This is the symptom of Resident Evil Village's copy shader at its write base.

The plane is now stored when any existing import overlaps it (`HostImportOverlaps`):
- When every registered range under the plane has an import, the storage image's write-back records the plane on the GPU into each range's import, one segment per range (ea3a2152d on `main`).
- When part of the plane has no import (an imported range next to a heap-mirrored or copied one), the write-back goes through the CPU after a wait for the expand.
- A plane one import holds is still recorded into that import, and a plane no import touches still stays pending for the mirror refresh or the copy that reads it, so both cost what they did.

The `HostImportFor` check stays in front of the new one. `HostImportFor` reconciles the imports with the registry and makes an import on demand, so a plane inside one registered range is still stored into its import even when that import does not exist yet. `HostImportOverlaps` only looks at imports that already exist.
````
