## Short answer
1. **The coordinator's reading is right** on the loop, the exact-tiling rule and the missing refusal memory (§1, with main's line numbers). Two additions:
   - a single hole, or a window that is still being mapped, defeats the join just as a flag change does;
   - silent least-recent evictions, which print no line, are what keep a full budget churning.
2. **Every requester imports one range at a time. The address-space build is the one that imports the whole registry** (GBM:2767-2775).
   - At a full budget, each rebuild tries every refused range again and re-checks its heap mirror.
   - A rebuild follows every registry mutation and every import retire, evictions included (§3).
3. **Measured on Linux (§6): a rebuild costs about 1.8 µs per registered GPU range.**
   - That is 63 ms at Village's 27,300 ranges, against 0.54 ms for the same 3.3 GiB in 840 ranges.
   - About 72 % of it is `importRun` scanning each window's neighbours twice per range.
   - Joining imports alone doesn't help: a tiled window makes 64 imports and still costs 7.2 ms. The walk has to stop scanning per range.
4. **e34 against main (§4): code rules out the range layout and the loop.** The difference is in run-time inputs: how much GPU memory the title has mapped against the budget, how many builds use BDA tables, and how often the space is rebuilt. One `APS5_PROFILE_DRAW=1` run per tree pins it down.
5. **Open PRs (§5): none fixes the churn.**
   - #5372's bind-time joins have a window-cap gap, found by reading its code, not by running it.
   - #6097 and #5870 are compatible.
   - #4448, #4449 and #2434 set constraints.
   - #1324 conflicts with joins.
6. **Fix (§7), in order:**
   1. F1: compute each window's run once per lease, join aligned blocks, and skip covered ranges in the walk.
   2. F7: rebuild only when the space's own imports or GPU ranges change.
   3. F6: remember refusals. It saves at most 1.2 µs per refused range per rebuild (measured).
   4. F3: a device budget for vf3's failures.

   Two options I don't recommend:
   - **Small ranges by mirror (F8):** it doesn't shrink the walk, and on Linux the fallback is a copy.
   - **"Import only what the build needs":** no bound exists, because a BDA miss is fatal.

7. **Arm B's 30× refusals against vf3 (addendum 3, §8) don't need a different layout.** vf3's excess mostly failed at the driver's ceiling, and failures are remembered. Arm B's excess is budget refusals, which aren't. Only a full budget makes lookups evict, and each eviction forces an epoch rebuild.

## 1. The coordinator's reading, point by point (main)
**"The loop" is confirmed.** The address-space build is `AcquireRegistered`'s rebuild branch (GBM:2744-2810). It walks every range of the lease (2767), skips the ones that aren't readable or GPU-mapped (2768), and calls `importAllocation(context, state, range->address, lease, 0, false)` once per range (2775). A refused range becomes a heap mirror (`acquireMirror`, 2786-2799) or, failing that, a per-build copy (2801-2809). Copies beyond 64 MiB abort the process (2813-2821; the -ports copy cap replaced this abort). e34 has the same loop (e34 GBM:2511-2519) and the same abort (e34:2561).

**"No join" is confirmed, and there are three ways it happens.** `importRun` (GBM:826-850) returns more than the containing range only when ranges that continue each other (`continuesRun`, 812-814: adjacent, readable, equal `writable` and `gpu`) tile the aligned 8 MiB window **exactly** (845). In the window [0x2041000000, 0x2041800000), any of these makes every 64 KiB range its own import:
1. The 4 MiB range and the 64 KiB ranges differ in `writable` or `gpu`, which is the coordinator's guess.
2. Any 64 KiB of the window is unregistered or unreadable. A single hole defeats it (measured, §6).
3. The window wasn't complete yet when its ranges were imported. Map-time imports (R1) and builds made while the title is still mapping the window import each range as it stands. Later, a tiled window replaces the singles only when an address-space walk or an access asks for the whole window, none of the singles is held by a build (GBM:1066-1068), and the window fits the budget (1071-1073). At a full budget it never fits, because evict=false refuses it (§1, "the budget").

The log can't tell (1) from (2) or (3). The `[gpu] host import` trace prints neither the flags nor the neighbours. The diagnostic in §7 step 0 does.

**"The budget" is confirmed, with one number corrected.**
- Budget refusals are not remembered. The refusal branch (GBM:1071-1084) returns null without touching `failures`. `failures` is written only for misalignment, inaccessible or read-only memory, alias failures and `vkAllocateMemory` failures (1049, 1102, 1114, 1128, 1137, 1176).
- So every rebuild of the space tries every refused range again: `importRun`, three map lookups, the held scan, then the refusal. After that it reuses the range's heap mirror on Windows; on Linux, where the arena isn't write-watched, it copies the range.
- The correction: "10.8 GiB imported ever" is cumulative and includes re-imports, so it isn't the lease's size. The proof that the lease exceeds the budget is the refusals themselves. Arm B's own numbers split the retired bytes:
  - 10,797 MiB ever − 6,863 MiB live = 3,934 MiB retired;
  - "mapped again" accounts for 285 × 4 MiB + 126 × 64 KiB ≈ 1,148 MiB;
  - the other ≈ 2,786 MiB were retired by replacements (window and run upgrades, joins at bind) or by **silent** least-recent evictions. Every lookup with `evict = true` evicts this way when the budget is full (`retireLeastRecent`, GBM:1090), and it prints nothing. That covers the 19 `HostImportFor` sites, joins at bind, sparse heap runs and write-back pieces.
- So "0 eviction lines" rules out the copy cap only. It doesn't rule out evictions.

**"What changed from e34" — code rules out the range layout, so the difference is in what the title maps and in the rebuild rate.** §4 has the details.
- The registration code is the same for the same guest calls.
- The loop, the window and join rules, the missing refusal memory and the rebuild triggers are the same code on both trees.
- What differs is at run time: whether the GPU-readable registry exceeds the budget, and how often the space is rebuilt. A single run with `APS5_PROFILE_DRAW=1` on each tree pins it down.

## 3. Why the churn, on main
### 3.1 One import per range
`importRun`'s exact-tiling rule (§1) makes every requester import one registered range at a time unless a whole aligned 8 MiB window is tiled. In Village's window, a 4 MiB range followed by 64 KiB ranges gives 1 + 64 imports instead of 1 (measured in §6).

### 3.2 R2 imports the whole registry, and only R2 does
- R1 imports what is mapped. The lookups import what is accessed.
- R2 imports **every** readable GPU range at the first address-based build after any change, whether or not the shader reads it. That is by design: a BDA table must cover every address a shader may dereference, and a miss is fatal (`BdaResources::CheckFault` throws "BDA access failed", BdaResources.cpp:240-296).
- So ~27k ranges give ~27k imports from a single build.

### 3.3 At a full budget, every rebuild re-tries and re-mirrors
`evict` is false in the walk, so once live imports reach the budget each remaining range is refused (GBM:1071-1084). The walk then takes the range's heap mirror, and the space is published.
- The next rebuild does it all again: refusals aren't remembered.
- Mirrors are reused only while the range stays the same registered object (`sameRange`, GBM:1834).
- A range that lost its import to an eviction gets a new 64 KiB mirror: a new buffer and a read of the guest bytes (1879-1903).
- A range that gains an import has its mirror released (`releaseImportedMirrors`, 2811).

### 3.4 What triggers a rebuild
The space is rebuilt when the registry generation moved (any map, unmap, protect or remap, GPU or not) or the import epoch moved (GBM:2702-2706). The epoch moves on **every** retire (`retireImport`, GBM:246). Retires come from:
- "mapped again": 411 in arm B;
- window and run upgrades;
- joins at bind replacing singles;
- at a full budget, every new import by a lookup with `evict = true`, which retires the least recently used idle import to fit (GBM:1090). On main that includes `importSegments`' per-piece write-back imports.

So at a full budget, the import traffic of ordinary draws (labels, fills, copies, indirect arguments, write-backs) keeps moving the epoch. Each move costs the next address-based build a full walk of the lease, plus the BDA table and space build.

### 3.5 The two numbers that decide it are in a log line Village didn't enable
With `APS5_PROFILE_DRAW=1`, `GuestBufferMemory::CountAddressBuild` (GBM:2643-2665) prints every 10 s:
- the number of address-based builds;
- µs per build for the lease, the imports pass, mirror preparation and comparison;
- space hits, and rebuilds by cause: generation, epoch, device, waiter drop, first.

The same line exists on e34 (e34 GBM:2387-2409).

## 4. e34 against main: what code rules out, and what's left
**Ruled out by code.** These are identical, or changed only in ways that don't affect how many imports are made or kept:
- the walk (e34:2511-2519 against main 2767-2775) and its copy abort;
- `importRun`, `windowRun`, `joinedRun`, the 8 MiB window (8da461ba5, before e34), and the refusal branch without memory;
- the rebuild triggers, and the epoch bump in `retireImport` (e34:227, main:246);
- the registration of ranges. Between e34 and main, only two commits touch it, and neither changes how many ranges a map, protect or remap registers:
  - 05ffb4516 (#5143) protects each registered span separately and returns EINVAL over holes. Splitting per span produces the same pieces as one `Protect` over the span, because `replaceRange` already cuts per range (GuestAllocations.cpp:483-490).
  - a016b4f2b (#5218) places a mapping below its hint when there's no room above it. That moves a mapping; it doesn't split one.

  #5596's private direct memory is in both trees.

**Not ruled out.** Main has the same code, so the difference must be in its inputs:
1. **Whether the GPU-readable registry exceeds the budget.**
   - Every import is a registered range, a join of ranges or a window of one. So live imports can reach the budget only when the GPU-readable registry exceeds it.
   - R2 imports the whole registry at the first address-based build.
   - So if e34 ran address-based builds and stayed under 6,864 MiB, its GPU-readable registry was under 6,864 MiB at that point. Arm B's wasn't.
   - Same code means the title mapped more GPU memory on main by then. A different path or speed through the load could do that.
2. **How many builds are address-based.**
   - R2 runs only for stages with a BDA table.
   - 73 recompiler commits since e34 change how shaders are resolved. Among them: image tables whose records hold a T# pointer (c794273ab), table columns that span two loads (55eefe9c5), table-call linking (9c8fb780e), and #4475's indirect columns.
   - These can move stages into or out of BDA tables, and I can't tell which way for Village without its shaders.
3. **The rebuild rate.**
   - Generation rebuilds follow the title's registry mutations.
   - Epoch rebuilds follow retires, and at a full budget main has one more source of them: `importSegments`.

**To pin it down: one run per tree, same scene and environment, plus `APS5_PROFILE_DRAW=1`.** Compare the `[address]` lines:
- **Builds per 10 s low on e34, high on main:** cause 2.
- **Rebuilds ≈ builds on main, mostly `epoch`:** cause 3, the retire-driven rebuilds of §3.4.
- **Mostly `generation`:** the title's own mutations. Then the per-rebuild cost (§6) has to come down, or the cache has to stop keying on non-GPU mutations (§7 F7).
- **Refusals** (`host import budget: … refused so far`) **on main only:** cause 1, which the step-0 diagnostic (GPU-readable registry size per rebuild) confirms.

## 6. Measured: what an address-space build costs on Linux
**Harness.**
- A scratch execution test, `tests/execution/ImportWalkCost.cpp`, in a local worktree of upstream/main 2c4574adf. Never committed.
- Built with the CI mirror's configuration (GCC, Release -O3, Ninja) and run on lavapipe (LLVM 20.1.2, 4 KiB import alignment, 4 cores).
- It registers GPU ranges in 8 MiB windows and opens a real `VulkanDevice`, whose import window is 8 MiB. Under the GPU mutex it times one address-based build: `GuestBufferMemory(context)`, then `AcquireRegistered()`, `Upload(true)` and `WriteBack()`.
- Three kinds of build are timed:
  - the first build;
  - cache hits;
  - rebuilds after a registry change. The change adds and removes an unrelated non-GPU range, which moves the generation and nothing else.

**Layouts, per 8 MiB window:**
- **pieces:** addendum item 2's window: a 4 MiB read-only range, then 64 × 64 KiB writable ones, so the flags differ at the edge.
- **gapped:** the same with equal flags and the last 64 KiB unmapped.
- **uniform:** the same with equal flags, so the window is tiled.
- **joined:** the same bytes as a 4 MiB and a 4 MiB range.

| gapped | 64 | 4,096 | 4,096 | 26.2 ms | 5.9 µs | 7.6 ms (8.9) |

**What the numbers say.**
1. **A rebuild costs about 1.8 µs per registered GPU range, however many imports serve them.** The tiled layout makes 64 imports instead of 4,160 and still rebuilds in 7.2 ms against 7.5. Where the time goes, from gdb stack sampling (60 samples during 3,000 rebuilds at Village's count; callgrind can't run this binary, since valgrind lacks userfaultfd and the runtime segfaults under it):
   - `importRun` is on the stack in 43 of the 60 samples, and is the leaf in 29. It runs once per import in the reconcile (`refreshImports` → `sameRange`, GBM:1257, 906-912) and once per range in the walk (`importAllocation`, 1023).
   - Each call scans the window's continuing neighbours (842-844), and when the window isn't tiled it throws the scan away (845). For 64 continuing pieces that is 64 steps for each of 65 ranges, twice per rebuild.
   - Another 10 samples are `Lease::held()`, which every `lease[index]` in that scan calls through the PLT (GuestAllocations.hpp:38, 44).

   **So joining imports doesn't by itself make a rebuild cheaper.** The per-range `importRun` calls must go too: F1 (i) and (iii) in §7.
2. **At Village's count a rebuild costs 63 ms (p90 76), and even a cache hit costs 154 µs.** The hit stamps every import the space holds (GBM:2709-2712). The same 3.3 GiB in 840 ranges costs 0.54 ms per rebuild and 1.6 µs per hit, about 117× and 96× less.
3. **A refused range adds about 1.2 µs to the walk** (10.0 ms against 7.5 ms with 2,080 refused). That is all that remembering refusals (F6) can save on the CPU.
4. **The fallback for a refused range is the expensive part.**
   - On Linux it is a per-build copy: 148 ms per build for 256 MiB, even on a cache hit. Copying everything costs 224 ms per build.
   - On Windows it is a heap mirror. Heap mirrors need the arena's write watch, which exists only on Windows (GuestArena.cpp:150-154, GuestMemory.cpp:809), so this harness can't time them. The PC can: it is the "mirror prepare" figure in the `[address]` line.
5. **For scale:** Village's 0.07 fps is about 14 s per frame. At 63 ms per rebuild, that equals about 220 rebuilds per frame. The `[address]` line will show how much of the frame this actually is. Windows adds per-import costs that Linux doesn't have:
   - `GuestMemory::Unwatch` for every unwatched import at every reconcile (GBM:1258). 64 KiB imports are below #6060's 1 MiB settle floor (GBM:654), so they are unwatched.
   - The driver's import calls.

## 7. Fix proposal (completeness gate), for upstream/main
### 7.1 Root cause
An address-space build costs O(registered GPU ranges × continuing neighbours per window). It runs again after every registry change and every import retire. An import is one registered range unless an aligned 8 MiB window is exactly tiled, so a title that maps its heap in 64 KiB pieces gets three things:
1. One import per piece, so ~27k imports fill the budget.
2. Rebuilds in which `importRun` scans each window's neighbours twice per range: 63 ms at 27,300 ranges (measured).
3. At a full budget:
   - every refused range is tried again, and its heap mirror re-checked, at each rebuild;
   - the evictions that make room for lookups keep moving the epoch that forces the next rebuild.

### 7.2 Changes, ranked
The numbering follows the first version and GAC-026:
- F1: blocks;
- F3: device budget;
- F6: refusal memory (new in GAC-026);
- F7: fewer rebuilds (new here);
- F8: small ranges by mirror (not proposed).

The other numbers are out of scope by the PM's call in GAC-026: F2 (bound `importSegments`), F4 (release write-back imports) and F5 (`MapAlias` demotion, -ports only).

**Step 0: diagnostics, no behaviour change.**
- (a) No code: run arm B and the e34 tree once each with `APS5_PROFILE_DRAW=1` (§3.5, §4).
- (b) Small code changes:
  - Add to the `[address]` line (GBM:2665) the last rebuild's GPU-readable ranges and MiB, and how many it imported, mirrored, copied and refused.
  - Add to the import trace (GBM:1177, 1206) the requester (map, space, access, join, sparse, segment).
  - For a single range inside a window, also say why the window didn't join: the first hole, or the first flag change.

**F1: compute each window's run once, join aligned blocks, and stop walking covered ranges.** This comes first, because it removes both the count and the per-rebuild scan.
- **(i) One pass per window per lease.**
  - The walk and the reconcile ask `importRun` for the run of every range and every import.
  - Compute each window's runs once for the current lease (keyed by the lease's generation and the window base) and look them up after that.
  - That turns 2 × N × W neighbour steps into one pass per window.
  - Also read the lease's vector once instead of calling `held()` per element.
- **(ii) Aligned power-of-two blocks.** This is the coordinator's "join within a window", but aligned.
  - When the window isn't tiled, the run of an address becomes the largest aligned block that contains it and is exactly tiled by continuing readable ranges. Blocks range from 2 × the import alignment up to `importWindow`.
  - In addendum item 2's window, if the 64 KiB ranges fill [0x2041400000, 0x2041800000) with equal flags, they form one aligned 4 MiB block, so 1 + 64 imports become 2.
  - Why aligned, rather than any compatible run in the window:
    - an unaligned maximal run changes whenever a neighbour is mapped or unmapped, and every change retires an import, which moves the epoch and forces a rebuild;
    - aligned blocks only grow by doubling, so a window that fills piece by piece is replaced at most log2(8 MiB / 64 KiB) = 7 times, all during loading.
- **(iii) The walk skips covered ranges.**
  - Once a range's import covers the ranges after it, push their regions without calling `importAllocation`.
  - Publishing already merges adjacent regions that share an import (GBM:2837-2850), so the space and its BDA table shrink to one region per import.
- **Constraints:**
  - The largest block is `importWindow`, not a constant (#4448).
  - A block whose import fails (Windows alias, dma-buf under #4449 or #2434, `vkAllocateMemory`) steps down to the next smaller block. Today a failed multi-range alias pins the span to single ranges for the session (GBM:1124-1132, `unaliasedSpans` at 846).
  - A block that doesn't fit the budget steps down too, for `evict = false` requesters.
- **Expected effect:** the measured "joined" rows bound it: 0.54 ms per rebuild and 1.6 µs per hit for the same 3.3 GiB, against 63 ms and 154 µs. The skip loop over the remaining 27k lease entries adds 27k comparisons.

**F7: fewer rebuilds.**
- **(a) Epoch.** Invalidate the cached space only when the retired import is one its regions point at.
  - Implementation: a flag on each import the current space references, and a counter that `retireImport` bumps only for those.
  - Both the cache check (GBM:2705) and `UploadFinish`'s dissolve check (3625-3628) must compare that counter. Today the dissolve check sends every region of a cached space down the per-build path after any retire. Other per-build checks keep using `state.epoch`.
  - Retiring one map node leaves pointers to the others valid.
  - Today a lookup's import of an unrelated range, evicted at a full budget, forces a full rebuild.
- **(b) Generation.** A mutation that touches no readable GPU range leaves the space's ranges as they are, but today it forces a rebuild, because the generation is global (GBM:2704).
  - The space's lease pins every range in it, so a freed non-GPU range would still drop the space through the pin waiter (GBM:78-91). Doing this properly needs a lease of the GPU ranges only.
  - That is a larger change, and its value depends on the `generation` count in the `[address]` line.
  - #1324's one-range lease is not this, and it conflicts with joins (§5).

**F6: remember budget refusals** (coordinator's option 2).
- In the refusal branch (GBM:1071-1084), record the refused run and the live bytes at the refusal.
- Skip a remembered run (same base, `sameRun`) while `liveBytes` hasn't dropped below that figure and the budget is unchanged.
- Every retire lowers `liveBytes`, including #4448's idle retires. A join's retire-and-replace doesn't lower it, which is correct.
- Measured saving: up to 1.2 µs per refused range per rebuild, plus the repeated refusal lines.
- Keep it inside 1071-1084 so it doesn't touch #5870's and #6097's hunks.

**F3: budget from the device.** Unchanged from the first version:
- the budget is min(configured, the host heap's `heapBudget` − (`heapUsage` − `liveBytes`) − a reserve);
- an adaptive ceiling after a `vkAllocateMemory` failure;
- live imports capped at `maxMemoryAllocationCount`;
- the query shared with #6174.

It fixes vf3's 992 failures and protects machines with less shared memory. Arm B shows it doesn't touch the churn.

**F8: small ranges by copy or mirror** (the Bug Finder's direction). Not recommended as the fix:
- Mirrors and copies are per range too, so the walk doesn't shrink.
- On Linux the fallback is a per-build copy: 224 ms per build to copy 512 MiB here.
- On Windows a heap mirror duplicates its bytes in host-visible memory and is checked per build.
- After F1, only isolated pieces stay small. Decide those after the PC's "mirror prepare" figure.

**"Import only what the build needs": no bound exists.**
- A BDA table must cover every address a stage may dereference, and a miss is fatal (BdaResources.cpp:240-296).
- The SRT plan and the V# ranges bound descriptor reads, not FLAT/GLOBAL dereferences of pointers loaded from memory.
- The lever is upstream of imports: fewer stages that need a BDA table at all. That removes R2 for those builds.

### 7.4 Cost
- **F1:**
  - one pass per window per lease, cached: one entry per window, about 420 for Village;
  - blocks pin registered GPU memory that R2 would import anyway;
  - up to 7 block replacements per window while it fills.
- **F7a:** one flag per import; no new work per build.
- **F6:** one map entry per refused run; an O(log n) check.
- **F3:** one `vkGetPhysicalDeviceMemoryProperties2` per N imports.

### 7.5 Adversarial review
1. **"Blocks pin memory nobody asked for."** Only registered GPU-readable ranges inside one aligned block, which R2 imports anyway, range by range.
2. **"A per-lease run cache goes stale."** It is keyed by the lease's generation. Any mutation moves the generation, and the next walk recomputes.
3. **"Skipping ranges loses regions."** Publishing already merges regions that share an import. The BDA table needs only the import's span.
4. **"F7a keeps a space whose refused ranges would now fit."** The same happens between rebuilds today, and the next generation change picks them up.
5. **"F6 hides freed budget."** `liveBytes` is its only input, and every retire lowers it.
6. **"F1 changes what the window tests assert."** With a 2-piece window the smallest block is the window itself.
7. **Not covered here:** these are Windows-only and need the PC:
   - the heap-mirror cost;
   - `Unwatch` per import at each reconcile;
   - aliases of large blocks;
   - T5's Windows variant.

## 8. Addendum 3 (item 6): why arm B refuses 30× more than vf3 with the same layout
The refusal count is (ranges refused per walk) × (walks after the budget filled). Two code effects make v6b1's count far larger than vf3's, and neither needs a different layout:
1. **vf3's excess mostly failed instead of being refused.**
   - vf3 hit the driver's ceiling first: 992 `vkAllocateMemory (-2)` failures at 6,557.7 MiB live, below the 6,864 MiB budget.
   - A failed import is remembered in `failures` (GBM:1176) and is not tried again until its run changes (1054-1057). It never reaches the budget check, so it isn't counted as a refusal.
   - v6b1 never failed. Its excess is budget refusals, which aren't remembered (1071-1084), so every walk counts them again.
2. **Only a full budget turns lookups into epoch rebuilds.**
   - Below the budget, a lookup with `evict = true` passes the budget check. It imports, or fails at `vkAllocateMemory`, and retires nothing.
   - At a full budget, every lookup that needs a new import retires the least recent idle one (GBM:1090). That moves the epoch (246), and the next address-based build rebuilds the space (2705).
   - So v6b1, sitting at its budget, makes epoch rebuilds that vf3, sitting under its driver ceiling, mostly didn't.

**The title runs fit the same picture:**
- 9b at the default budget: 304,394 refusals over about 12k ranges.
- tSpaceOff with the cache off, where every build is a rebuild: 6.7 million.

**To confirm on the PC,** with no code change, run each arm with `APS5_PROFILE_DRAW=1` and compare per 10 s:
- `rebuilds: … epoch N` (effect 2);
- the `refused so far` growth (effects 1 and 2);
- the count of `failed at vkAllocateMemory` lines (effect 1).

**What keeps unchanged ranges from being re-walked:**
- F7(a), which scopes the cache's epoch to the space's own imports. It is small: one flag per import and one counter, used by two checks (GBM:2705, 3625-3628).
- F6, which stops the retries.
- F1's per-window pass and walk skip, which make each remaining rebuild cheap.
