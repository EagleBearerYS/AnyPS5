## Short answer
- **No single path imports 64 KiB at a time; all of them can.** Every requester resolves "the run around an address" with `importRun` (GBM:722-746). That run is one registered range, unless an aligned 8 MiB window is exactly tiled by continuing ranges.
- **Village's +0x10000 imports are 64 KiB registered ranges,** one per GPU map call or fixed-remap piece. The 16 KiB views in the failure dump don't come from the title: on Windows, the import itself makes them when #5851's alias path demotes resident memory (§2.3).
- **Four kinds of requester create them at 4cd4260a9a (§1):**
  1. The **map-time observer** `ImportMappedRanges` (GBM:2448-2478) imports each GPU mapping as it is made. These are the boot-phase imports.
  2. **`AcquireRegistered`** (GBM:2660-2670) runs on the first address-based build after any registry change. It walks the **whole registry** and imports every readable GPU range it doesn't already hold, whether or not the shader reads it.
  3. **`importSegments`** (TEX:2624, on main since ea3a2152d7/db1ddb96ce) does one import per registered piece of a storage image being written back. These are the texture-time bursts.
  4. **The 20 access lookups** through `HostImportFor` and the build's region pass import the one range around an access that fits in it.
- **Larger imports happen only two ways:** a fully tiled 8 MiB window, or `, joined at bind` for a region that equals the crossed run (119 in the log).
- **e34c479210 has the same granularity code and requesters 1, 2 and 4.** The window and joins predate it: 8da461ba5, 230b5c268, e9249a0a4.
- **No change since e34 made imports per range. Three made per-range imports costly and frequent (§3):**
  - afe49470ba (#5851, -ports): alias plus demotion into 16 KiB views on Windows;
  - ea3a2152d7 + db1ddb96ce (main): per-piece write-back imports;
  - 237166cb15 (-ports copy cap): evict-and-import keeps live imports at the configured budget, which is above the driver's ceiling, so `vkAllocateMemory` fails 992 times from 6,557.7 MiB.
- **Fix (§4):**
  - Step 0: a requester tag in the trace.
  - F1: aligned power-of-two block joins inside `importRun`, which covers every requester at once.
  - F2: bound `importSegments`.
  - F3: a budget from `VK_EXT_memory_budget`, with an adaptive ceiling after a failure and an allocation-count cap.
  - F4/F5: lower priority.
  - Linux red tests T1-T6 use 64 KiB ranges, each backed by four separate 16 KiB memfd views.

### 1.3 How the write-back sites are reached (rows 5 and 7)
`writeBackLayers` is called from `Refresh` (TEX:1969) and from `writeBack` (TEX:4511). `writeBack` is called from:
- `Flush` (3189, cache eviction from `evictStorage` and `FlushCachedTextures`);
- `FlushPending` (3268). This covers the CPU-access hooks (`FlushForAccess`, Recorder.cpp:1054; `FlushHook`, TEX:1362), `FlushAllPending` at idle, label and flip, `StoreSmallPending` at flip, and about 30 direct callers (builds, copies, fills, labels, the DB expand);
- `WriteBack` (4184), only under `APS5_EAGER_WRITEBACK` or `APS5_NO_TEXTURE_CACHE`.

### 1.4 What each path imports beyond what it needs
- **R1** imports every GPU mapping when it is made, whether or not the GPU ever reads it, one range per mapping.
- **R2** imports the whole GPU-readable registry for one address-based build. With 27,636 ranges that is up to 27,636 imports, until the budget refuses, for a shader that may read a few. With address tables any pointer may be read, so this is by design, and it is where the per-range granularity costs most.
- **The access lookups** pin at least the whole containing range. A 12-byte indirect argument (row 20) or a label (row 14) pins its 64 KiB range, or a whole tiled 8 MiB window.
- **`importSegments`** imports every piece of the surface, not only the pieces holding the units being written back. When a later piece fails (for example the budget refuses it), it returns `{}` and the imports it already made stay live and unused until evicted.

## 2. Why ~27k separate 64 KiB imports instead of a few large ones
### 2.1 One import per registered range is the rule, not the exception
Every importing path resolves "the run around an address" with `importRun` (GBM:722-746). A run is joined from several registered ranges in only three cases:

| Join | Where | Condition | Logged as |
|---|---|---|---|
| **8 MiB window** | `importRun` (GBM:728-741), window set to 8 MiB by `VulkanDevice.cpp:1296` | The aligned window `[address & ~(8 MiB−1), +8 MiB)` must be **exactly tiled** by registered ranges that continue each other: adjacent, readable, with equal `writable` and `gpu` (`continuesRun`, GBM:708-710). If any 64 KiB of the window is unmapped, unreadable, or differs in a flag, the run is the containing range alone (GBM:741). | plain `ok` |
| **Joined at bind** | `importJoined` (GBM:930-937) from a build's region pass (GBM:3538) and sparse heap runs (GBM:3618) | `joinedRun` (GBM:767-775): one region must cross range boundaries, and either every crossed range is larger than the 8 MiB window, or the region equals the crossed run exactly. | `, joined at bind` (119 in the log) |
| **Range window** | `windowRun` (GBM:866-897) | A single registered range larger than 64 MiB is cut into 64 MiB cells. This only ever splits a range; it never joins. | plain `ok` |

So an import is exactly one registered range unless a full aligned 8 MiB window is tiled.

The log's +0x10000 imports are therefore 64 KiB **registered ranges**. Four 16 KiB ranges can't produce them:
- alone, a 16 KiB range is imported as +0x4000, or refused when the device's import alignment is 64 KiB (`importRunAt`, GBM:949), and the log has no +0x4000 imports to speak of;
- the only multi-range paths are the 8 MiB window and the join, which is logged.

### 2.2 Where the 64 KiB registered ranges come from
- **One range per mapping call.** `DoMapDirect` (DM:905-938) and `DoMapAnon` (DM:940-966) register one range per `sceKernelMapDirectMemory`/flexible mapping call.
- **A fixed remap splits a range.** `RemapFixedIntoRegistered` (DM:632-659) runs on a `MAP_FIXED` mapping into memory that is already registered. Its `mutation.Protect` splits the registered range into before / remapped piece / after (`replaceRange`, `GuestAllocations.cpp:483-490`). It also notes a GPU mapping (DM:657), which fires the map-time import below.
- **What Village's numbers show.** 27,636 distinct 64 KiB ranges over 0x1f00000000-0x23fbd50000 is about 1.7 GiB of 64 KiB pieces spread over a 20 GiB span, an average density of about 8 %. An 8 MiB window needs 128 consecutive continuing pieces.
- **A remapped piece is a new range.** The 479 "retired: the range was mapped again" lines come from `refreshImports` (GBM:1147-1158). An import whose registered range changed is dropped there, and its range is imported again at the next use (32,407 imports for 27,636 addresses).

### 2.3 The "16 KiB views" are made by the import, not by the title
- **What the title's pages look like before an import.** Since #5596 (in e34 too), singly mapped direct memory on Windows is private memory, committed in "resident runs" cut at 2 MiB (`WindowsMappings::Map`, WM:106-129, `chunkBytes` 0x200000, WM:495).
- **What #5851 changed.** afe49470ba ("import resident direct memory through a section alias", -ports only) sets `writable = !GuestArenaResidentSpan(…)` (GBM:995). So every import of resident direct memory takes the alias path, `GuestArenaMapAlias` (GBM:1022-1032).
- **What the alias path does.** `MapAlias` (WM:251-292) **demotes** every resident run the range touches (WM:267-270). `demote` (WM:624-651):
  - fences and copies the whole run, up to 2 MiB, into the section;
  - releases the private pages;
  - maps **one section view per 16 KiB page** (`split` + `mapShared` per page, WM:636-649).
- **Result.** A 64 KiB import leaves four MEM_MAPPED 16 KiB views, which is exactly what the failure dump shows (`state 0x1000 protect 0x4 type 0x40000`, printed by GBM:1071-1077 after the import failed). It also maps a fifth view for the alias itself (WM:285, or `mapAliasRuns` WM:841-866 when the physical pages aren't contiguous).
- **Before afe49470ba** (e34 and main), the same import of private resident memory was a plain host-pointer import: no demotion, no alias, no extra views.

### 2.4 Why the joins don't help Village
- **The 8 MiB window rule.** It needs exact tiling of an aligned 8 MiB window by continuing ranges. A heap of scattered 64 KiB pieces almost never tiles one. Where it does, the upgrade is still refused:
  - while any 64 KiB import inside the window is held by a build (`held`, GBM:962-966);
  - when the window doesn't fit the budget (GBM:969);
  - because access-based callers return an existing 64 KiB import first (`findImport` hit, GBM:915) and never ask for the window.
- **Joined at bind.** It only helps a region that itself crosses ranges, and only when the region equals the crossed run or every range is over 8 MiB (GBM:772-773). A 64 KiB-piece heap fails the second test, so only exact-run regions (sparse heap runs, 119 of them) join.

### 2.5 e34c479210 against 4cd4260a9a
The granularity machinery is **identical**: `importRun`, `joinedRun`, `windowRun`, `importAllocation`, `importJoined` and `importRunAt`.
- The diff of GBM between the two touches only the `budgetRefusals` counter and the `writable = !GuestArenaResidentSpan` line inside `importRunAt`.
- The window and the joins predate e34: 8da461ba5 "fix the host-import window at 8 MiB" (2026-10-11), 230b5c268 "join the imports of adjacent large ranges…" (2026-10-13) and e9249a0a4 "host import windows, least-recent eviction" (2026-10-14).
- The two per-range requesters are unchanged: the map-time observer → `ImportMappedRanges` (GBM:2448-2478, e34:2327) and address-based builds → `AcquireRegistered`'s import of every GPU-readable range (GBM:2670, e34:2519).

So on e34 the same heap was also imported 64 KiB at a time wherever those two paths ran. **What differs is what each import costs and how many extra requesters there are:** §3.


## 3. Which change introduced it
**No change between e34c479210 and 4cd4260a9a made imports per range.** That granularity is 8da461ba5's (the fixed 8 MiB window, 2026-10-11). Inside the import core (GBM:690-1182) the two trees differ only by a counter and one Windows line. Three later changes are what turn the same 64 KiB granularity into this run's picture:

| Change | In | What it changes for a heap of 64 KiB pieces | Which symptom |
|---|---|---|---|
| **afe49470ba** (#5851) "import resident direct memory through a section alias on Windows" | -ports only, not upstream | Every import of resident direct memory goes through `MapAlias`, which demotes each resident run it touches (up to 2 MiB) into one section view per 16 KiB page, plus an alias view (§2.3). | The 16 KiB MEM_MAPPED views in the failure dump. Windows' per-import cost: one fence, a copy of up to 2 MiB, a release, about 5 VA calls per 16 KiB page and the alias mapping, against one plain host-pointer import on e34 and main. At least 110k extra views for 27,636 ranges. |
| **ea3a2152d7** + **db1ddb96ce** "write back a storage image spanning adjacent registered ranges … through each range's import" / "count adjacent registered allocations as covering…" | main since 2026-10-13/14, after e34 | A storage image over several registered ranges is now written back on the GPU through one import **per range** (`importSegments`, TEX:2610-2635, reached from `writeBackLayers` TEX:4677-4678 when the whole image has no import). Before, it wasn't GPU-written-back at all. | New imports during the texture-time bursts, one per 64 KiB piece of each written-back image not already imported. |
| **237166cb15** (+18c114bced) copy-cap fix "an address-based build evicts idle imports instead of copying past the cap" | -ports only | Past 64 MiB of copies, `AcquireRegistered` imports with `evict = true` (GBM:2704-2713). That keeps live imports at the budget and evicts idle ones to make room. | With `APS5_HOST_IMPORT_MIB=6864` above the driver's real pinning limit, live imports climb to 6,557.7 MiB, where `vkAllocateMemory` starts failing (992 failures); eviction then re-imports evicted ranges. |

**New requesters since e34.** Of the 27 import sites in §1, only two are new in 4cd4260a9a. R3 is new as well, but it is a fallback of R2, not a new requester.
- `importSegments` (TEX:2624, ea3a2152d7). Its reach widened with db1ddb96ce: `RegisteredReadableCovers` now accepts a surface covered by several adjacent pieces (GBM:2480). On e34 the surface had to lie in one range (e34 GBM:2359).
- `StoreDepthExpandWrites` (DepthSurface.cpp:1181, e89e411df3). This one is bounded: one lookup per DB expand plane of an address-table build.

**The boot-phase imports.** These are the small imports "among shader-registration lines, with no texture created yet". They can only come from R1 (map time) or R2 (the first address-based draws and dispatches): `AcquireRegistered` can't run during registration or ABI resolution (§1.1). Both are unchanged since e34.

**What the log can't tell.** The `[gpu] host import of … ok` line doesn't name its requester, so the split between R1, R2 and the write-back bursts isn't recoverable from this log. One added word in that line settles it: a requester tag passed down to `importRunAt` (map, build, access, join, segment). That's a one-parameter diagnostic, proposed in §4 as step 0.


## 4. Fix proposal (completeness gate)
### 4.1 Root cause, in one sentence
An import is exactly one registered range unless an aligned 8 MiB window is exactly tiled. A title that maps or remaps its GPU heap in 64 KiB pieces therefore gets:
- one import per piece from every per-range requester;
- on Windows since #5851, a demotion of the whole surrounding resident run into 16 KiB views for each of them;
- a fixed-MiB budget that doesn't know the driver's pinning ceiling.

### 4.2 Proposed changes, ranked
**Step 0, diagnostic (no behaviour change).** Tag each `importRunAt` call with its requester (map, build, access, join, segment) and print it in the `APS5_TRACE_HOST_IMPORT` `ok` and failure lines (GBM:1068, :1097). One more Village run then confirms the split this report can only infer.

**F1, join aligned blocks in `importRun` (the count).** In GBM:728-741, replace "the exact aligned 8 MiB window, else the single range" with: the largest aligned power-of-two block, from 2 × the import alignment up to the window, that contains the address and is exactly tiled by continuing readable ranges, else the single range.
- **Stable:** blocks are aligned, so a block never shifts; growth upgrades a block at most log2(8 MiB / 64 KiB) = 7 times per window.
- **Exact:** it never spans a gap, so nothing unregistered is pinned.
- **Every requester is covered**, because they all resolve runs through `importRun`:
  - map-time (GBM:2468, 2472);
  - address-based builds (GBM:2670, 2707);
  - `HostImportFor` / `importAccess` (GBM:1173-1177, 2431-2446), and through it every caller in §1;
  - `importSegments` (TEX:2624);
  - region binds (GBM:3599, 3607).
- **Budget fallback:** when the chosen block doesn't fit the budget, or its alias fails on Windows, step down to the next smaller block. Today a failed multi-range alias marks the whole span unaliased forever (GBM:1030-1031 and 742), which pins it to single ranges.
- **Effect on Village:** wherever its 64 KiB pieces are adjacent (a multi-page resource mapped piece by piece), imports become 128 KiB-8 MiB blocks. Isolated pieces stay single, so F1 alone may not be enough if the heap is truly scattered; Step 0 tells which.

**F2, bound `importSegments` (the write-back bursts).** In TEX:2610-2635, use a piece's import only when it already exists or the piece is at least 1 MiB (one eighth of the window). Otherwise return `{}`, and the image takes the CPU write-back it took before ea3a2152d7.
- With F1 most adjacent pieces already resolve to one block import, so `HostImportFor` of the whole image (TEX:4677) hits and `importSegments` isn't reached.
- Alternative: #6197's `HostImportSpanning` (open), which joins exactly the crossed run. It is not aligned: two images crossing overlapping runs replace each other's joined imports, which is the churn the window was introduced to avoid. Prefer F1, and keep #6197's join as the fallback for runs that aren't block-aligned only if Step 0 shows the need.

**F3, budget from the device (the failures).** In `importBudget` (GBM:850-864), when the device enabled `VK_EXT_memory_budget` (`state->memoryBudget`, VulkanDevice.cpp:1287), use min(configured or default, the host heap's reported `heapBudget` − (its `heapUsage` − `liveBytes`) − a reserve).
- Re-read it at most every N imports, plus after any failure.
- After a `vkAllocateMemory` failure (GBM:1063-1068), drop an adaptive ceiling to the live bytes at the failure. Later imports are then refused, or evict to fit, instead of each failing (992 times here).
- Also cap live imports at `maxMemoryAllocationCount` less `BufferPool`'s share, as `BufferPool` already does for its slots (BufferPool.cpp:31). Imports don't check it today.
- Share the budget query with #6174 (open), which reads `heapBudget` for the staging pool.

**F4, release write-back-only imports.** Lowest priority. With F1 and F2 they become rare. Retiring them right after the write-back would re-import on every write-back (on Windows: alias plus demotion again); #4448 (open) already retires idle unwatching imports on Linux.

**F5, sibling for #5851's owner (Windows).** `MapAlias` demotes the whole resident run, up to 2 MiB, even for a 64 KiB import (WM:267-270 → `demote`, WM:624-651). Splitting the run at the import's edges and demoting only those pages would bound the copy and the new views to the import's size. With F1, demotion work per byte is unchanged, but aliases and imports drop by the join factor.

### 4.3 Tests (Linux, lavapipe; red on 4cd4260a9a and on main where noted, green with the fix)
**Setup:**
- lavapipe imports host memory with 4 KiB alignment. The tests copy the context with `hostImportAlignment = 65536`, as #6197's and the existing `importWindowTests` do (BdaResources.cpp:439-466), and `SetHostImportWindow(8 MiB)`.
- **Village-shaped memory:** each 64 KiB registered range (one `GuestAllocationsAdd`, readable, writable, GPU) is backed by **four 16 KiB views that are separate allocations**. These are `MAP_FIXED` maps of a memfd at non-adjacent file offsets, so the kernel can't merge them into one VMA. 64 such ranges tile a 4 MiB-aligned block.
- Counting needs one test hook, `HostImportLiveCount()`, beside `HostImportLiveBytes()` (GuestBufferMemory.hpp:70).

### 4.6 Adversarial review
1. **"Joining pins more than needed."** Only registered GPU ranges, inside one aligned block. Under a tight budget the block steps down (F1's fallback), so it never refuses what a single range would have got.
2. **"Remaps inside a block now retire more."** Yes: a remap of one piece drops the whole block's import (GBM:1147-1158), and the next use re-imports the largest tiled block. Village logged 479 such retires. Cost per retire: one block import instead of one 64 KiB import. Bounded by the remap rate and lazy (next use), as today.
3. **"Held imports block upgrades."** Unchanged from today (GBM:962-966); the smaller imports keep working.
4. **"Windows aliases of a block can fail."** Today a multi-range alias failure pins the span to single ranges for the session (GBM:1030-1031, 742). F1 must step down a block size instead; T5 should include a Windows variant.
5. **"F2 brings back CPU write-backs."** Only for images whose pieces are small and not yet imported, which is the e34 behaviour for them. Images over joined blocks keep the GPU path.
6. **"A memory-budget query can be stale or 0."** Fall back to the configured or default budget when it reads 0, as #6174 does. The adaptive ceiling after a real failure covers what the query misses.
7. **Not covered:**
   - a truly scattered heap still makes one import per piece; F1 can't join across gaps. F2 and F3 then bound the damage, and Step 0's data would show whether a sparse-heap path (mirror or copy) should take over.
   - Windows behaviour (F5, T7) can't be run here.
