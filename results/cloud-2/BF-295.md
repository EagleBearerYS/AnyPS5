## 1. The read: what the hook waits wait on

### The hook

- **Where it is called:** every `GuestMemory::Read`, `ReadCommitted`, `EqualsCommitted`, `Write` and `WriteChanged`, and every explicit `FlushGpuWrites`, calls the flush hook first (`Execution/src/GuestMemory.cpp:2918`, `:2925`, `:3034`, `:3050`, `:3109`, `:3145`).
- **Registration:** the recorder registers `FlushForAccess` as the hook (`Graphics/src/Recorder.cpp:1307`).

`FlushForAccess` (`Recorder.cpp:1025`) makes up to two GPU waits per access:

| Wait | Code | Waits for | Why the CPU must wait (base) |
| --- | --- | --- | --- |
| **pending-write sync** (source 1, [hooksync] "pending-write syncs") | `:1043`–`:1054`: `PendingWriteOverlaps`, then `SyncThrough(address, bytes, true)` (`:1052`) | the newest open or in-flight batch that notes a GPU write over the range: a store, write-back or fill into imported guest memory, a label or EOP store, a DCC key store | The GPU writes the imported guest memory itself. Until that batch completes, the bytes there are the old ones. Without the wait, the CPU read in a later packet sees the bytes from before an earlier packet's GPU store. |
| **recorded-store sync** (source 2, [hooksync] "recorded-store syncs") | `:1077`–`:1090`: after `StorageTexture::FlushPending` (`:1075`) or the C4 publish-only path (`:1069`–`:1073`), `SyncThrough(…, true)` (`:1090`), or `Sync()` inside a completion action (`:1089`) | the open batch the hook has just recorded into: it stores a storage image's results, which were kept only on the GPU, into the guest bytes (or publishes unit shadows) | The image's results reach guest memory only when that batch runs. `SyncThrough` submits the open batch, so the wait lasts a whole submit-to-signal (7.6–10.7 ms on Village's `[syncwait]` line). This matches the ~100 batches in flight at 360–397 syncs every 10 s. |

**`SyncThrough`** (`Recorder.cpp:3861`):
- It picks the target: the open batch if the open batch overlaps (`:3896`, which submits it and does a full `Sync()`), otherwise the newest overlapping batch in flight.
- It then finishes every batch up to that target. `finish()` waits on each batch's fence with `vkWaitForFences` (`:4198`) and runs its completion actions (CPU write-backs).

**Under the GPU mutex or not:**
- **The rule:** the wait releases the mutex only when the hook's own `lock()` is the outermost on the thread. `syncThroughUnlocked` (`:3985`) returns false when `GpuMutex().DepthOnThisThread() != 1` (`:3989`).
- **Locked waits:** the dispatch's resources phase, a draw's `resolveDrawResources` and the recipe proofs all run inside the worker's dispatch or draw hold. The hook's acquisition is nested there (depth 2), so the wait is **locked**: `SyncThrough`'s finish loop waits on fences while holding the GPU mutex (`[lock]` "locked GPU waits").
  - Every other queue worker queues behind it, which is the 0x0 and 0x20 alternation.
  - These waits are what `resources: hook waits` measures. That row is `Recorder::ThreadWaitedMs()` over `Execution/src/VulkanDevice.cpp:5556`–`:5703`, plus the recipe proof at `:5912`–`:5917`.
  - The row counts **every** fence and timeline wait of the thread in that span, so it also includes the build's direct syncs listed below.
- **Unlocked waits:** dispatch stage A (`PrepareDispatch`, `VulkanDevice.cpp:4962`–`:4983`) and `PreResolveDraw` (`Graphics/src/Draw.cpp:3828`, which runs only when the thread does not hold the mutex) are outermost. Their waits drop the mutex around `WaitTimeline` (`Recorder.cpp:4055`), and these are the `[syncwait]` "unlocked hook waits".

### Which reads in a resource build reach the hook, and the "unknown" site

**"unknown" means "no `ReadSiteScope`":** a read whose code names no site.
- **Where it shows:** `CurrentReadSite()` returns `Unknown` for it, and `[hooksync]` then attributes it by return addresses: the `+0x…/+0x…/+0x…` frames on the same line.
- **Named sites:** scopes exist only for `Capture`, `DispatchCache`, `DrawCache`, `TextureCompare`, `TextureRead` (DCC), `BufferUpload`, `MirrorRefresh`, `IndirectArguments`, `Registers`, `Wait` and `Store`. Their scopes are listed under `ReadSiteScope` in the sources.
- **Never set:** the `IndexBuffer`, `VertexBuffer`, `Label` and `Scanout` sites exist in the enum (`Execution/include/GuestMemory.hpp:270`), but no code sets them.

**Unscoped reads inside a resource build** (candidates for the "unknown" rows of DISPATCH_DIRECT and DRAW_INDIRECT):

| Read | Code | What it is |
| --- | --- | --- |
| storage image guest capture | `Graphics/src/Texture.cpp:2581` (`captureGuestBytes`: `FlushGpuWrites`, then unsynced reads), `:4388` | the guest bytes a storage image saves before the GPU writes it |
| storage image compare | `Texture.cpp:2607` (`compareUntracked`) | the untracked compare behind a template's proof |
| storage image upload | `Texture.cpp:2691`, `:2698`, `:2911` (`StorageTexture::upload`) | a new storage image initialised from guest memory |
| DCC/metadata reads outside the `TextureRead` scope | `Graphics/src/DccMetadata.cpp:593`, `:615` | metadata for an image the build binds |
| fetch-shader vertex descriptor reads | `Graphics/src/ShaderInputState.cpp:283`, `:288` | V#s a draw's vertex inputs read |
| depth surface and HTILE reads | `Graphics/src/DepthSurface.cpp:146`, `:233`, `:671`, `:1351` | depth sampled or imported by the build |

**What the recorded-store rows mean:** a storage image's results were pending over the range when the read happened. That is a compute or draw pass writing an image that the next dispatch or draw then binds through another storage view, which `StorageTexture::upload`/`captureGuestBytes` initialise from guest memory, all unscoped.

**Sampled textures are named, not unknown:** their snapshot goes through `ReadTextureSurface` (`ShaderResources.cpp:1023`, then `DccMetadata.cpp:777`–`:811`, site `texture-read`), and their hit compare is `texture-compare` (`ShaderResources.cpp:961`). Most sampled reads of a storage image's results are served from the image itself (`ShaderResources.cpp:940`–`:952`, `createTexture(source, …)`), not from guest memory. (`Graphics/src/TextureCache.cpp` is not used by the builds.)
- **What the frame offsets settle:** the `+0x` offsets on the PC's `[hooksync]` lines tell which of these rows it is. They are module offsets, so `nm -C` against the driver image resolves them (`Recorder.cpp:831`–`:833`, `GuestMemory.hpp:285`–`:289`).
- **Not identifiable here:** I could not do this from code alone, and the task's summary drops the frames.

**Not in a resource build:** these "unknown" rows come from elsewhere, and the switch leaves them alone.
- **0x0 WAIT_REG_MEM_64 "unknown" recorded-store syncs (20–22, 243–264 ms):** these come from the wait loop's unscoped `GuestMemory::FlushGpuWrites(awaited, awaitedBytes)` every 32 polls (`Execution/src/Driver/Synchronization/WaitMemory.cpp:362`).
  - The loop stores a pending image's results over the awaited address and waits for them to land.
  - The wait packet's own reads are scoped `Wait` (`Execution/src/Pm4.cpp:571`, `:600`, `:608`).
- **indirect-args syncs:** the indirect arguments are read while the packet is decoded (`Pm4.cpp:814`, `:886`, `:895`, `:1001`), not in the build.
- **0x28 DISPATCH_DIRECT buffer-upload:** this is the build's CPU upload of descriptor regions (`Graphics/src/GuestBufferMemory.cpp:5680`–`:5697`, scoped `BufferUpload`).

## 2. The switch

- **`APS5_DIAG_SKIP_HOOK_WAITS`** (presence) is read once (`Recorder.cpp:284`).
- **The guard:** `FlushForAccess` computes `skipWaits = resourceBuildDepth != 0 && completionDepth == 0 && SkipHookWaits()` (`:1042`). When it is true, both the pending-write block (`:1043`) and the recorded-store block (`:1077`) are skipped: no lock, no `SyncThrough`, no `Sync`.
- **What still runs:**
  - The queued-label record (`:1034`).
  - The pending-image store (`FlushPending` or the C4 publish-only path, `:1069`–`:1075`). Its copy goes to the open batch, so a later read outside a build still waits for it.
  - The CPU then reads whatever guest memory holds.
- **Unset:** `skipWaits` is false and the hook is exactly the base's. With the switch unset, the only extra work is a thread-local increment and decrement around each build, plus one bool test per hook call.

**The resource-build depth:**
- **Declaration:** the depth is a thread-local (`Recorder.cpp:247`), raised by `Recorder::ResourceBuildScope` (`Graphics/include/Recorder.hpp:456`, `Recorder.cpp:1414`).
- **Placement:** the scope wraps exactly the spans that `resources: hook waits` times, plus the draw side:

| Build | Scope |
| --- | --- |
| dispatch stage A (cache find, moved-buffer check, unlocked build) | `VulkanDevice.cpp:4962`–`:4983` (the pre-sync after it is outside) |
| dispatch resources phase (stage B `Complete`, `Revalidate`, full build, push constants) | `VulkanDevice.cpp:5556`–`:5702` |
| dispatch recipe proof (`ProveCurrent`) | `VulkanDevice.cpp:5912` |
| draw resolve (`Revalidate`, `MovedReadOnlyBuffers`, `Complete`, build) | `Draw.cpp:1741` (all of `resolveDrawResources`) |
| draw moved-buffer rebuild in `prepareDraw` | `Draw.cpp:3073` |
| draw recipe proof (`ProveCurrent`) | `Draw.cpp:3671` |
| `APS5_PRERESOLVE` unlocked build | `Draw.cpp:3828` |

**Left out on purpose:**
- **Accesses made by completion actions** (`completionDepth != 0`) keep their waits. A write-back store inside a completion must still order behind the batch it completes (`Recorder.cpp:1089`).
- **Accesses outside these spans** keep their waits: packet decode, indirect arguments, WAIT_REG_MEM, captures, cache validation, render-target reads in `prepareDraw`, and game threads. The depth is per thread, so another thread's access during a build is unaffected.
