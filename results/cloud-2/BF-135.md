## Part 2: #9508's 7 tests that fail on lavapipe

### Which still fail at 23b2a3fc2d, and why

All 7 still fail at `23b2a3fc2d` on lavapipe (Mesa llvmpipe, no `VK_EXT_descriptor_heap`), with the same messages as BF-129 found on `13764c98c`:

| test | message at 23b2a3fc2d | why |
| - | - | - |
| `agc_driver_heap_draw_sample_heap` | "the heap did not take the fragment stage" | `DescriptorHeapEnabled()` is false, so no stage can go on the heap |
| `agc_driver_heap_draw_sample_nogpl_heap` | "the heap did not take the fragment stage" | same |
| `agc_driver_heap_draw_sample_full_heap` | "a draw found the capped heap full and the heap was not refused" | same: there is no heap to fill or refuse |
| `agc_driver_heap_draw_sample_full_heap_pipelined` | same as above | same |
| `agc_driver_pipeline_journal_gpu_heap` | "first run: the sampling compute stage is not GPU mode" | same: no compute stage can run in GPU mode |
| `agc_driver_image_table_atomics` | "dispatch 0 texel 8 returned 13059, expected 5059" | not the heap; see below |
| `agc_driver_image_table_atomics_gpu_heap` | same | not the heap; see below |

For the five heap tests, `DescriptorHeapEnabled()` is `GpuHeapEnabled() && descriptorHeapDevice`, and VulkanDevice.cpp sets the device side as `SetDescriptorHeapDevice(state->descriptorHeap && maxPushDataSize >= PipelinePushConstantBytes)`. `state->descriptorHeap` needs the extension, maintenance5 and `BindlessHeap::Fits`. On lavapipe it is false, so these tests assert on something the device cannot do.

**The two atomics tests fail for another reason, and I left them alone.**
- They fail with and without `APS5_GPU_HEAP`, so the descriptor heap has nothing to do with it: `agc_driver_image_table_atomics` runs `--atomic-table` with only `ANYPS5_NO_SHADER_CACHE=1 APS5_NO_PIPELINE_JOURNAL=1`.
- The kernel computes `v_add_nc_u32 v17, 5, v0` and then `v_readfirstlane_b32 s16, v17`. It assumes a wave32.
- lavapipe runs the invocation in groups narrower than 32 lanes. Lanes past the first group then read their own group's first lane instead of lane 0, and the result is off by 8000 (13059 instead of 5059).
- Which texel goes wrong first depends on the CPU's vector width, not on the reported subgroup size (4 or 8). With `GALLIUM_OVERRIDE_CPU_CAPS=avx` it is texel 8; with the host's own caps it is texel 4.
- A descriptor-heap skip would hide this, so I did not add one. Several #9508 tests already skip this case with "skipped, subgroup size %u cannot hold a wave32": ReadLane.cpp, WriteLane.cpp, Permlane16.cpp and WindowLaneSpill.cpp. That would be the matching fix, and it is Raghav314's call.
