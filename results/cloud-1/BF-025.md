# BF-025 result (cloud-1): GPU-side indirect draws continue the open render pass when their records need no barrier

Fork branch `exp/agc-indirect-gpu-pass-continue` @ `088deebbf`, from BF-022's head `e280ce9d5`. It is a throwaway prototype and has no PR. The numbers are from lavapipe (llvmpipe, LLVM 20.1.2).

## Summary

- **What broke the pass:** `recordDraw` (Graphics/src/Draw.cpp) passes `forced = ... || gpuIndirect || ...` to `Recorder::StartDrawPass`. Every GPU-side indirect draw therefore begins its own pass, and records outside it:
  - the argument barrier;
  - for a Constant dimension, the scratch copy, one `vkCmdUpdateBuffer` per record, and two more barriers.
  - In BF-015's harness, with the start instance written nowhere, the Constant rewrite forces the pass break (and brings the barrier). With the start instance patched, the barrier alone forces it.
- **What changed:**
  - **The argument barrier is skipped when an earlier one in the same batch still covers the records.** No out-of-pass recording has happened since, and no draw since wrote memory overlapping the records. The draw then continues the open pass like a CPU-path draw.
  - **Under draw parameters, a dimension the CP writes nowhere is read in place** when no attribute is fetched at its rate (and the device has `drawIndirectFirstInstance` for the start instance), instead of being rewritten. This is a small change (12 lines).
  - **Counters:** the `[draws]` line now gives GPU-side passes begun and continued, and argument barriers recorded and skipped.
- **Numbers, BF-015's harness, wall time per packet, median of 9:**
  - At 1 record per packet, the GPU side goes from 61–80 µs (BF-022's behaviour, same build, same run) to 21–37 µs. The CPU path takes 42–61 µs.
  - At 8 and 64 records, the GPU side stays at 21–46 µs per packet.
  - In each 64-packet submission there is 1 pass begun and 1 barrier, against 64 of each before.
  - Driver thread per packet at 1 record: 30–34 µs, against 62–69 µs for BF-022's arm.
- **Checks:**
  - New test `agc_driver_indirect_pass_continue` ×10 and `agc_driver_indirect_draw_parameters` ×10: 20 of 20 passed.
  - `^agc`: 608 of 608 passed, 43 skipped.
  - Reds: three kinds of write, each red when the skip ignores it, plus one control that stays green (§3).

## 1. What broke the pass

**Main's GPU indirect path,** BF-022's head `e280ce9d5`, `Graphics/src/Draw.cpp`:
- `recordDraw` calls `recorder->StartDrawPass(passKey, capture || readsTarget || gpuIndirect || cpuDrawIndex || meshIndirect, ...)`. The `forced` argument is always true for a GPU-side indirect draw, so the open pass ends and a new one begins, even with the same pass key and no hazard.
- In the `!continued` branch, `recordIndirectArguments` records, outside the pass:
  1. **The argument barrier:** `ALL_COMMANDS|HOST` → `DRAW_INDIRECT|TRANSFER`, `SHADER_WRITE|TRANSFER_WRITE|HOST_WRITE` → `INDIRECT_COMMAND_READ|TRANSFER_READ`. This is what needs the pass to be closed, because Vulkan allows no such barrier inside a render pass.
  2. **For a Constant dimension (main's rule):** a scratch `DeviceBuffer`, `vkCmdCopyBuffer` of the records, a transfer barrier, one or two `vkCmdUpdateBuffer` per record, and a transfer → `DRAW_INDIRECT` barrier.
- **Nothing else ends the pass for it.** The pass key is the same as a CPU-path draw's into the same targets. The `PassAccess` hazards include the record range as a read, so a draw in the pass that wrote the records would break it, as for any reader.

**In BF-015's harness**, the depth stage into a 64 KiB tiled target, 64 `DRAW_INDIRECT_MULTI` packets per submission:

| Setup | What forces the new pass |
|---|---|
| Start instance written nowhere (BF-015's packet) | **The Constant rewrite**, with the argument barrier. With the barrier skip alone, these draws still begin a pass each: the case `UnwrittenStartInstanceReadInPlace(..., false)` under `APS5_NO_INDIRECT_IN_PLACE_CONSTANT=1` shows 2 passes begun and 2 barriers for two draws. |
| Start instance patched (into s9) | **The argument barrier alone.** There is no rewrite. |

## 2. The skip rule, and why it is exact

**The rule.** A GPU-side indirect draw on the recorded path records no argument barrier, and is not forced to begin a pass, when all of these hold:
1. The open recorder batch already recorded an argument barrier (`Recorder::NoteIndirectArgumentBarrier`, right after `recordIndirectArguments`).
2. Since then, nothing that can write memory was recorded outside a render pass. Each such path clears the state (`Recorder::hideIndirectArguments`):
   - every caller of the public `Recorder::Commands()`: dispatches, copies, uploads, texture refreshes and detiles, write-backs, fills, DCC key stores;
   - a label store run: the inline `vkCmdUpdateBuffer` in `flushPendingStore`, and the queued runs in `closeStoreRun`;
   - the query dumps (`dispatchDumps`).
   - Only three things keep the state: the pass's own start and end (`StartDrawPass` takes the batch through a new `passCommands()` that ends the open pass but does not clear it), and the GPU timing stamps. None of them writes memory.
3. The draws recorded in passes since then wrote nothing that overlaps the draw's record range or count dword. `LeaveRenderPassOpen` keeps every draw's `PassAccess` write ranges. A draw with unknown writes (address-based, address-table or copied) clears the state.
4. The draw needs no rewritten copy: no dimension is Constant.
5. There is a batch. A new batch starts without a barrier, and with no batch open the check is false.

The check runs once before `StartDrawPass`, and once more after the pass started. Starting the pass can close a pending label store run, which records its `vkCmdUpdateBuffer` then. In that case the second check fails and the barrier is recorded before the pass begins. `APS5_NO_INDIRECT_PASS_CONTINUE=1` turns the skip off; it is read per draw.

**Why it is exact.**
- **The earlier barrier covers everything before it.** It is a global memory barrier with `ALL_COMMANDS` as its first scope, and its second scope is the indirect read. So every write recorded before it in the batch, and every write in an earlier submission on the queue, is visible to any indirect read after it.
- **Later writes are either cleared or tracked.** A later write in the batch is either recorded outside a pass, which must end any open pass first and clears the state (rule 2), or recorded by a draw inside a pass, which is range-tracked (rule 3).
- **Host writes need no barrier.** Host writes before `vkQueueSubmit` are visible through the submission's own host-write dependency. Host writes while the batch executes are not covered by any barrier, as before.
- **The batch reset is structural.** The state lives in the `Batch`, and `ensureOpen` creates it empty. A later batch therefore records its own barrier for its first GPU-side indirect draw.
- **When unsure, it records the barrier.** Unknown writers and any out-of-pass recording clear the state. The state is cleared even when the write is elsewhere (a label store into unrelated memory, a dispatch writing another buffer). That only costs a barrier and a pass, never a missing barrier.

**The draw itself.** On the continued path, `recordIndirectArguments(..., barrier = false)` still notes the pending read and points the draw at the import. On a new pass with the barrier skipped, the pass begins without it.

## 3. Tests

`tests/execution/IndirectPassContinue.cpp` (`agc_driver_indirect_pass_continue`, picked up by the execution-test glob):
- **Setup:** BF-015's depth stage into a resident 64 KiB tiled target. One record of 4 dwords, in a guest block.
- **Records:** written by the fill kernel from `MultisampleFillHostOnly` (`buffer_store_dwordx4`, `vkCmdFillBuffer` on this driver), by a `WRITE_DATA` (a label store, `vkCmdUpdateBuffer`), or by the host. A fill of 0 draws nothing; 3 draws the triangle three times.
- **Counts:** from the new always-on `Graphics::IndirectPassCounters()`.
- **Skip:** it skips with a printed line if the device does not store compute fills into guest memory.

| Case | Expected | Green |
|---|---|---|
| Fill records := 3, then two draws | 1 pass begun, 1 continued; 1 barrier recorded, 1 skipped; image drawn | yes |
| Fill := 0, draw, **fill := 3** (a dispatch), draw | 2 begun, 0 continued; 2 barriers recorded, 0 skipped; image drawn by the second draw | yes |
| Fill := 0, draw, **`WRITE_DATA` := 3** (`vkCmdUpdateBuffer`), draw | The second draw reads its records on the CPU: main's `PendingLabelOrCopy` rule, since the label is pending over them. So 1 GPU-side draw (1 begun, 1 barrier); image drawn. If it went GPU-side, it must be 2 begun, 2 barriers. | yes (CPU path) |
| Host := 0, draw, batch ends; **host := 3**; new batch, draw | 2 begun, 2 barriers; image drawn by the second batch's draw | yes |
| Two draws whose start instance the CP writes nowhere (commit 2) | Read in place: 1 begun, 1 continued, 1 barrier, 1 skipped. With `APS5_NO_INDIRECT_IN_PLACE_CONSTANT=1`: rewritten per draw, 2 begun, 2 barriers. | yes |

**Reds** (`reds.py`: each mutation built and run, then restored; the tree is clean afterwards):

| Mutation | Result |
|---|---|
| A dispatch's `Commands()` no longer clears the state | **Red:** `records a dispatch rewrote between two draws: 2 passes begun, 0 continued, 1 argument barriers recorded, 1 skipped, expected ... 2 argument barriers recorded, 0 skipped` |
| Main's `PendingLabelIn` fallback removed (control) | **Green:** the second draw now goes GPU-side, and the store run's clear records the barrier (`the pass broke and the barrier was recorded`). |
| Fallback removed **and** store runs (`flushPendingStore`, `closeStoreRun`) no longer clear | **Red:** `records a WRITE_DATA (vkCmdUpdateBuffer) rewrote between two draws: 2 passes begun, 0 continued, 1 argument barriers recorded, 1 skipped` |
| The state carried across batches (recorder-level, and true with no batch open) | **Red:** `records the host rewrote between two batches: 2 passes begun, 0 continued, 1 argument barriers recorded, 1 skipped` |

- **The image can't show a missing barrier here.** On lavapipe, every red still draws the right image: lavapipe executes the fill and the update before the indirect read whatever the barriers. So the reds are the counted barriers, which is what the rule decides.
- **Why the host case first flaked.** An earlier version of it rewrote the records with a GPU fill and then wrote them from the host with no flush in between. The fill's pending write-back then landed over the host's records about half the time. The fill and the host write were unordered, which a guest would order by a wait. On this container the host write isn't trapped (imported ranges are compared, not write-protected). The case now settles earlier GPU writes and writes the records only from the host: 30 of 30 runs passed.

## 5. What still breaks passes

For a GPU-side indirect draw on this branch:
1. **The first GPU-side indirect draw of each batch:** one barrier and one pass per batch, as in the harness.
2. **Anything recorded outside a pass between two draws.** This ends the open pass for a CPU-path draw too, and also hides the records here: dispatches, copies and uploads, texture refreshes, detiles and write-backs, label store runs, DCC key stores, query dumps.
3. **A draw in the pass that writes memory overlapping the records,** or whose writes are unknown (address-based or address-table builds, copied writes).
4. **A Constant dimension that still needs the rewritten copy:**
   - without draw parameters (main's path);
   - with draw parameters, when attributes are fetched at that dimension's rate;
   - for the start instance, on a device without `drawIndirectFirstInstance`.
5. **The other forced causes, unchanged:**
   - `APS5_CAPTURE_INPUTS`;
   - a draw that reads its own target;
   - CPU-read records whose stage reads `DrawIndex` (the uploaded multi-draw copy);
   - mesh indirect draws (`recordMeshArguments`).
6. **Different pass keys** (targets, extent) and **`PassAccess` hazards,** as for any draw.
7. **The synchronous, non-lean path** (non-resident targets, `APS5_DRAW_TRANSITIONS`): it never continues a pass, and is counted as one pass and one barrier per draw.
8. **A label store pending over the records** sends the draw to the CPU path (`PendingLabelOrCopy`), as on main.

## 6. What a title's `[draws]` line must show for this to matter

The line now reads `...; indirect: gpu-side N (M rewritten), cpu-side ..., argument reads ...; gpu-side passes B begun, C continued; argument barriers R recorded, S skipped`. Its first part already gives `render passes X begun, Y draws continued one` for all recorded draws.

- **GPU-side draws per 10 s (N) in the thousands or more.**
  - The saving per draw that continues is about 35 µs of driver thread here (62–69 → 30–34 µs per packet), plus one render pass of GPU execution (lavapipe: about 165 µs per packet; a desktop GPU much less).
  - At 1,000 GPU-side draws per 10 s, that is about 0.35% of one thread; at 50,000, about 18%.
- **Before this change, passes begun per GPU-side draw is 1 by construction** (B = N, C = 0, as BF-022's soak and the BF-022 arm above show).
- **After it, the change matters when B/N falls well below 1.** That happens only if the title's own draws already continue passes: `render passes X begun` ≪ draws on the same line, as in the harness (2,398 begun for 153,447 CPU-path draws).
- **If a title begins a pass for most CPU-path draws anyway,** the cause is work between draws (labels, uploads, dispatches), and its GPU-side draws will mostly keep beginning passes. This branch can't remove those breaks. Resident Evil Village's menu, from BF-024's numbers, is such a title: 754 passes begun and 74 continued for 828 draws per 10 s.
