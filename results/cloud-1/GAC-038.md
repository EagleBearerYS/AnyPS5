- Branch `fix/agc-sample-location-grid-exact` (fork), pushed, head **e6068b79a6e14d9a8a5cdfb0eac3f90b2c58fbf5**: four new commits on 57ceb9e370, no amends.

## Causes

### 1. AMD, both failures: the color swap picked the wrong order word for pixel (0,0)

Code at 57ceb9e370:
- `Graphics/shaders/SampleOrder.comp:16` selects the word as `order.map[(at.x & 1u) | ((at.y & 1u) << 1u)]`. That is a push-constant `uvec4` indexed by a value that differs between the lanes of a wave. In SPIR-V it is `OpAccessChain %order %int_0 %52`, with `%52` computed per invocation.
- `:17` returns early for kept words, a branch that diverges within the wave.
- `:18-20` gathers the samples through `held[(map >> (index * 4u)) & 7u]`, a private array indexed per lane.
- The depth swap shader (`SampleOrder.frag:17`) selects its word the same way.

Why this is the cause:
- The 2x R8_UNORM round trip first stores and reads back every sample. That check passed (`tests/execution/SampleOrder.cpp:523`).
- Only `RecordSampleOrder` ran between that check and the failing one.
- Pixel (0,0)'s order word keeps its samples, and only the invocation of pixel (0,0) stores to it.
- Sample 0 then held 0xb1, the fill value of sample 1 (`((1 * 0x9e3779b1 + 0x1000) & 0xf8) | 1`). So that invocation ran the swap with a reordering word.
- The grid reference's "sample 0 of pixel (0,0) does not hold its own sample index" is the same swap shader on the RGBA16F target (RG32 alias).

Confidence: inferred from the code and the one reported sample. There is no AMD hardware here, and lavapipe compiles the same SPIR-V correctly.

### 2. 3070: depth drawn at custom sample locations was read back at the standard 2x locations

Neither the composite reference nor the 2x2 grid render held the guest's depth. Both held depth at the standard 2x locations:
- **Pixel (14,0), sample 0.** The reference held 0x3f00e5b5. That is slope A's plane at (14.75, 0.75), standard 2x sample 0, matching to 1 ulp.
- **Exact path, same sample.** It held 0x3f0153f8, the plane at (14.75, 0.5), which is the guest's sample 0 of that pixel.
- **Sample count.** A rasterization of the scene at the guest locations covers exactly **3005** samples with the slopes. That equals the reported depth mismatches, so every sloped sample was read elsewhere in one of the two renders.

Why:
- The depth image is created `SAMPLE_LOCATIONS_COMPATIBLE_DEPTH` (`Graphics/src/DepthSurface.cpp:134`).
- It is moved from UNDEFINED to GENERAL once (`:177-178`) and never transitioned again:
  - render passes keep it in GENERAL (`Pipeline.cpp:394,403-404`);
  - dynamic rendering keeps it in GENERAL (`Pipeline.cpp:690`);
  - the swap pass keeps it in GENERAL (`SampleOrder.cpp:348-354`).
- So no layout transition ever names the sample locations it was drawn with.
- VK_EXT_sample_locations makes such an image's layout depend on the last sample locations used to render it (Vulkan spec, synchronization chapter). Its contents become undefined if a transition omits those locations or names others.
- The 3070 returned that depth at its standard locations when a shader sampled it (the test's readback, `tests/execution/SampleOrder.cpp:1020`) and when it was copied.

What this did to the exact path:
- **Even rows came out right.** The swap's depth pass draws at the stand-in's locations into every tile and rewrites them.
- **Odd rows did not.** They came from `vkCmdCopyImage` in GENERAL (`SampleOrder.cpp:191`), read at the standard locations, then moved to the other sample.
- **The 10 colour mismatches follow from those odd-row values.** The shade triangle's LESS_OR_EQUAL test runs against them, and all 10 are in odd rows: (33,17), (38,19), (24,13).
- **The colour values themselves** are the clear and shade triangles' barycentrics at the pixel centre; the f16 store truncates. At (38,19) the two triangles simply landed on the other samples.

The "pixel (0,0)'s locations alone" run fits being read back at its *own* locations, unlike the composite and the grid run:
- Its 3031 differences = 3005 sloped samples (1499 in even rows, 1506 in odd rows, at the stand-in's locations instead of the standard ones) + 26 others, colour or edge samples.
- So the 3070 does not treat every read alike. That is why the fix names the locations explicitly instead of relying on whatever state a read finds.

### 3. 3070: why a device whose vulkaninfo says 1x1 drew a "native 2x2 grid"

- vulkaninfo prints `VkPhysicalDeviceSampleLocationsPropertiesEXT::maxSampleLocationGridSize`, the grid that every supported sample count allows.
- The device setup instead reads each count's own `VkMultisamplePropertiesEXT` (`Execution/src/VulkanDevice.cpp:1270-1276`).
- On the 3070 that grid is even at 2 samples, so the grid reference rendered through the real 2x2 grid (`tests/execution/SampleOrder.cpp:1137`).
- That render matched the composite in 0 samples because both were read back at the standard locations (cause 2).
- Latent bug: `:1276` tested only `% 2 == 0`, so a 0x0 grid would also have counted as 2x2.

## Commits

1. **2b4db6a3a** `fix(agc): pick each pixel class's sample order word through a constant index`
   - `SampleOrder.comp`: one invocation per 2x2 quad. Every class's word comes through a constant index (`order.map.x`..`.w`), kept classes return uniformly, and held samples are picked through selects (OpSelect). The dispatch covers quads.
   - `SampleOrder.frag`: the word is selected by selects.
   - Test (planning mock, `--sample-order`): no sample-order shader module may index a vector or array through a non-constant value.
     - Red on 57ceb9e370's shaders: `sample order shader 0 picks a pixel's order word or a held sample through an access chain into %23 through the non-constant index %52`.
   - A failed GPU round trip now also prints its wrong samples per pixel class, kept or reordered.
2. **d9bd0f9b4** `fix(agc): name a depth target's sample locations in the transitions around its reads`
   - The swap copies its depth target between GENERAL→TRANSFER_SRC_OPTIMAL→GENERAL transitions. Each transition chains `VkSampleLocationsInfoEXT` with the stand-in locations.
   - Every draw pass with custom sample locations and depth ends with `RecordDepthSampleLocations`: the same transition pair, naming the pipeline's own grid and locations. It runs after the samples are back in guest order, in both the recorder's after-pass hook and the batch path (`Draw.cpp`).
   - Test (planning mock): checks the barrier/copy/barrier sequence, its layouts and both aspects of D32S8. Also checks that a swap without locations still copies in GENERAL, and the 2x2-grid pair from `RecordDepthSampleLocations`.
     - Red with the copy transitions disabled: `the depth swap did not copy its target between transitions that name the stand-in sample locations it was rendered with`.
3. **f8e8dc6f6** `fix(agc): log each sample count's largest location grid and take no 0x0 grid for a 2x2 one`
   - Device setup logs every count's grid and keeps it in the context (`sampleLocationGridSizes`).
   - `HostsSampleLocationGrid` requires both sides to be nonzero and even. The planning test checks it.
   - The grid reference prints the grid at 2 samples.
4. **e6068b79a** `test(agc): place the grid reference's depth samples and skip where none reads back at the guest's locations`
   - The grid reference classifies every sloped depth sample of each render from the slopes' plane equations: at the guest's location, or at the standard 2x location (tolerance 1e-5; the two differ by at least 1.7e-3 here).
   - If even the composite is not read back at the guest's locations, the test skips with the counts. No render can then be compared with it bit for bit.
   - A wrong scene sample index is now printed.
   - The bench also times the swaps with sample locations named in the depth transitions.

On refusals: the driver refuses nothing new. No device property says whether a device honours the locations named in a transition, and lavapipe has no VK_EXT_sample_locations. The grid reference now measures it and skips with the counts if a device does not. If the 3070 skips (case B below), the follow-up is a one-time probe: draw a slope at custom locations, read it back through the swap, and refuse the depth reorder where it fails.
