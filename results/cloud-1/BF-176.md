## The test

**Platform:** Linux, lavapipe, no window. `Driver::Present` needs a swapchain, so it isn't reachable headless. `VulkanDevice::PresentDisplayBuffer` is: it runs the fix's sync and the whole DCC key check before `present()`, which then throws `Vulkan presentation: device has no swapchain`. The test calls it directly and requires exactly that error, so it knows the present got past the key check.

**Construction:**
- **Guards:** skips (77) without a device, and without timeline semaphores (`CanWaitUnlocked`), since the unlocked wait needs them. It also skips when a GPU fill of guest memory cannot be recorded (no host imports). These are the guards `DccKeyPresync.cpp` uses.
- **The display buffer:** 128x128, format 0x8000000000000000, tiled (`tilingMode` 0), with `dccAddress` pointing at its keys (`DisplayBufferKeyBytes` = 4096 here), in one 128 KiB guest block.
- **The keys start mixed:** the first 256 are 0x00 (a clear code) and the rest are 0xff (uncompressed).
- **The pending writer:** `DccKeyPresync`'s copy kernel, dispatched under the GPU mutex, copies 0xff over the first 256 keys. The test requires `DccKeyWritersPending` for the key range.
- **The present:** still holding the GPU mutex once, at depth 1 as `Driver::Present` does, the test reads `GuestMemory::GpuHoldSerial()` and calls `PresentDisplayBuffer`. That serial advances on every outermost acquisition, so it only moves if the mutex was released and taken again.
- **It requires:**
  1. **the present reached the swapchain.** The key check found uniform keys, so it read the kernel's 0xff after the writer landed. Before the writer, the keys are mixed and the present throws "presenting DCC metadata that is not uniformly uncompressed or fast-cleared is not implemented".
  2. **the hold serial advanced.** The presenter gave up the GPU mutex to wait for the key writer and took it back: the unlocked wait, `Recorder::syncThroughUnlocked`.
  3. **the key writer is no longer pending,** and the keys hold 0xff.
- **Control:** with the device idle and no writer over the keys, the same present must reach the swapchain and leave the hold serial unchanged. The unlocked sync gives nothing up when nothing is pending.

**What it shows:**
- **Without the fix,** the key check's own sync is `currentDccKeys` → `recorder->SyncThrough(keys, count)` from inside the presenter's hold. That is a nested, locked sync, so the writer is completed, and waited for if the GPU has not finished it, while the mutex stays held. The serial does not move; that is the red line.
- **With the fix,** the first statement syncs through the key range with the unlocked wait. The mutex is released and retaken (serial +1), and the key check then finds no pending writer.
- **Deterministic:** both runs read the same keys. The difference is only whether the mutex was released for the writer.
- **No GPU timing assumption:** the unlocked path releases the mutex whenever an overlapping batch is in flight or open, finished or not. The batch here is still the open batch when the present starts.
- **Seams:** no test-only hook and no product change. The test uses public `VulkanDevice::PresentDisplayBuffer`, `GuestMemory::GpuHoldSerial`, `Graphics::DccKeyWritersPending` and `DisplayBufferKeyBytes`.
- **Not asserted:** the counter commit's `[present]` count. It only moves when the wait actually blocked on the GPU, under `APS5_PROFILE_DRAW`, which would make the test timing-dependent.

**Registration:** the execution-test glob registers it like every other `tests/execution` source, with `SKIP_RETURN_CODE 77` and the WIN32 `PATH` entry from the same loop. CMake is unchanged.

**Building each commit:** a3af6b114 (fix and counter) was built with CI's flags before the test was added (exit 0). 96bccd4c9 alone was not built separately; it is one added line, and a3af6b114 rewrites that same line into a block.
