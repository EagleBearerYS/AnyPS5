### The fix (681fcee86e: 4 files, +13/-2)

- **What it adds.** `HostImportOverlaps(context, address, bytes)` (GuestBufferMemory.cpp +10, .hpp +1) reports whether any import of the device overlaps a range, under the import lock.
- **What changes.** `StoreDepthExpandWrites` (DepthSurface.cpp:1146) now also stores a plane that no single import holds but some import overlaps. `writeBack` then takes its CPU path: a download with a wait for the expand, then a store of the changed blocks into guest memory, which the host-pointer imports share.
- **What stays the same:**
  - A plane that one import holds is still recorded into that import on the GPU. `HostImportFor` returns it, as before.
  - A plane that no import touches still stays pending for the mirror refresh or the copy that reads it.
  - The extra cost lands only on planes that imports hold in part: one CPU store per expand, because the plane leaves `unstoredExpands` at its first address-based build.
- **Docs.** The debt doc's DB-expand entry (`docs/dev/debt/libSceAgcDriver.md`) now says so.

## Part C: a write base in resident direct memory imported through #5851's section alias

Code reading only. Line numbers are on #5851's head **22091410a** (base 28b6f1987) unless marked otherwise:

- `GBM` = core/libs/prx/libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp
- `WM` = core/libs/prx/libc/include/WindowsMappings.hpp
- `TEX` = core/libs/prx/libSceAgcDriver/Graphics/src/Texture.cpp

#5851 does not contain the expand, so `StoreDepthExpandWrites` is cited at 7ae42fd181 (DepthSurface.cpp). The import code it calls has the same lines and logic in both trees, apart from #5851's change at GBM:980-982.

### 1. How the import is made

1. `importRunAt` (GBM:927) handles both whole-run and 64 MiB window imports.
   - For a range that holds resident direct memory, `writable` starts false (GBM:980-982, `GuestArenaResidentSpan` → WM:206-214).
   - The page walk (GBM:985-998) finds private read-write pages, so `readOnly` is false and the import takes the alias branch (GBM:1003-1020).
2. `GuestArenaMapAlias` (GBM:1010 → WM:251-292) does three things:
   - It demotes every resident run the range touches into the section (WM:267-270 → `demote` WM:612-639: fence read-only, copy the private pages into the section, release them, map the section in place).
   - It maps a second read-write view of the section (WM:285).
   - `createHostPointerImport` imports that view, not the guest pointer (GBM:291).
3. The Windows default `unwatchImports = true` (`decideImportWatch`, GBM:636-640) does not apply to this import. `watchedHostPointer = entry.alias != nullptr || !state.unwatchImports` (GBM:1031) is true.
   - `ImportWatched(…, true)` (GBM:1037-1040) leaves the guest range tracked, and `entry.unwatched` is false (GBM:1049).
   - The entry is stored under its **guest** base and size (GBM:1087).
4. There are two exceptions:
   - **Open host write.** `MapAlias` returns null when a resident run it touches is under an open host write (WM:259-266, 22091410a). The import is then made, as before #5851, on the private guest pages and is unwatched (GBM:1031).
   - **Alias refused.** For a single-range run the refusal throws (GBM:1012), so the build fails. A run of several ranges is put in `unaliasedSpans` (GBM:1017), and `importRun` imports those ranges one at a time from then on (GBM:730).

### 2. `HostImportFor` and `StoreDepthExpandWrites`: yes, the store sees the import

- `HostImportFor` (GBM:2312-2327) and `findImport` (GBM:1150-1158) compare guest addresses (`entry.base`, `entry.bytes`) only. The alias is only the host pointer handed to Vulkan.
- So `StoreDepthExpandWrites` (DepthSurface.cpp:1131-1149 at 7ae42fd181; the check at 1146) treats a section-alias import like any other.
- **When one import holds the whole plane,** the plane is stored into it:
  1. `FlushPending` → `writeBack` finds the same import (TEX:4475).
  2. It records the copy into `import->buffer` (TEX:4569). That buffer is the section view, the same pages the guest view maps after the demote.
  3. It then calls `MarkWritten` (TEX:4595).
- **When none holds it,** `HostImportFor` makes one through `importAccess` → `importAllocation` with eviction (GBM:1160-1164, 900-916). For a range over 64 MiB that is a window of the cells the plane touches (`windowRun`, GBM:859-885). It goes through the same alias branch.

### 3. The address-based build

- **Lease regions.** `AcquireRegistered` imports each registered run whole or not at all: GBM:2521 calls `importAllocation(…, 0, false)`, which takes only a whole-run hit (GBM:908-912) and evicts nothing.
  - It binds the import in place (`hostBacked`, `direct`, GBM:2524-2530).
  - A range whose whole import is refused is heap-mirrored or copied. A window import is never bound in place by an address-based build, and the mirror and copy paths store pending results first.
- **V# inside one region.** A V# range inside one such region is served by it with no region of its own (`addDescriptorRegion`, `BaseOverlap::Inside`, GBM:2747-2752).
- **No flush.** In-place regions of an addressable build skip the flush unless `APS5_BDA_FLUSH=1` (`UploadFinish`, GBM:3434-3441). The cached address space's regions do not reach that loop at all.
- **So** `StoreDepthExpandWrites` is the only store ahead of an in-place read. With one section-alias import over the plane, the build binds the same `HostImport` the plane was just stored into, and the copy holds the plane.

### 4. Can the build read the plane in place without any store?

- **Yes, but not because of the alias.** It happens when in-place imports hold the plane between them but none holds all of it.
- **Why that happens.** Imports are per run, and the device sets an 8 MiB import window (VulkanDevice.cpp:1266 on #5851's head; `importRun`, GBM:710-734). Every registered range over 8 MiB is its own run, so a plane across the edge of two such ranges lies in two imports.
- **What then fails.** `HostImportFor` finds neither import, because `runCovers` fails at GBM:1161 and so does `findImport`. `StoreDepthExpandWrites` skips the plane, and the build reads both imports in place.
- **Part B reproduces this.** At 7ae42fd181 the copies held 0 of 15360 texels, or 3072 when the second range was mirrored or copied.
- **One V# across the edge is safe.** It is a partial overlap, so it gets its own region (GBM:2753-2756), which joins the two ranges into one import (GBM:3321-3325) and is flushed. So the failure needs one V# per range, or pointer reads.
- **#5851's part:**
  - On Windows it adds one more way to split a run (a refused alias, GBM:1011-1018, `importRun` GBM:730). With ranges over 8 MiB the split is the default anyway.
  - #5851-specific, and unlikely:
    - The demote at WM:612-639 does not wait for recorded GPU work. `importRunAt` retires overlapping imports only with a hold (GBM:969-973).
    - Suppose a non-alias import of the private pages exists, which only happens when `MapAlias` returned null for an open host write (WM:264). If a later import demotes its run, GPU writes recorded through the old import land in released pages, and the section keeps the bytes copied at the demote.
- **What #5851 does make visible.** Its alias imports stay watched, so a window import inside a heap-mirrored range no longer aborts the next build. GAC-006's separate defect reproduced here as "a heap mirror's range is no longer write-watched" and as the 64 MiB copy-limit FATAL in unwatch mode (Part B table 1).
  - Without #5851, every direct import on Windows is unwatched (GBM:638, 1031).
  - Village not aborting fits a write base that is not mirrored, or #5851.
