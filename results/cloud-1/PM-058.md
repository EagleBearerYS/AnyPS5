# PM-058 result (cloud-1): completeness review of #6443 (host stack protect: Windows guard page, Linux main stack)

## Verdict

- **#6443 is right on Windows as far as Linux can check, but its Linux half has three real gaps.** All three are fixed on fork `review/6443-stack-gaps` @ `9a48a9605`, three commits on top of the PR's head `f697e1a41b`. Each commit has its own red/green test.
- **The Linux gaps:**
  1. **G1 (high).** A second protect of the same main-stack pages fails. The first protect maps pages under the stack, and glibc then reports a smaller stack that starts above them.
  2. **G2 (high).** After a protect at the bottom of the main stack, a call that needs the megabyte of stack above it faults where the console has stack. Linux won't grow a stack to within its guard gap of a readable mapping.
  3. **G3 (medium).** Under `ulimit -s unlimited`, a protect over the whole main stack runs for hours, because it probes the stack page by page.
- **The PR's own tests pass, and so do mine.** The PR's tests only protect the main stack once, over its whole range. That is the one case none of the gaps hits.
- **Windows:** nothing new I could find. What remains is already documented in the PR's debt entry: a protection other than read/write doesn't hold near the guard page. I can't run Windows here, so it is checked by reading the code and by MinGW `-fsyntax-only`.
- **The sibling paths on current upstream main all reach this code.** `sceKernelMprotect`, `sceKernelMtypeprotect`, POSIX `mprotect`, the AMM/APR protect commands and the memory-pool batch protects all go through `DoMprotect`. So they get the PR and these fixes. Upstream main's only change near here is `sceKernelMprotect` masking `prot` with `0x3F7` (`Export.cpp:260`), which doesn't touch the stack branch.

## The fixes (fork `review/6443-stack-gaps`, on `f697e1a41b`)

| Commit | What |
|---|---|
| `d5c12169f` **fix(libkernel): map a host stack's unmapped pages in runs on Linux** (G3) | `MapUnmappedPages` finds each mapped run with one `msync` over the rest of the range, halving until it fits. It maps each unmapped run with one `mmap(MAP_FIXED_NOREPLACE \| MAP_NORESERVE)`, halving on `EEXIST`. No swap is reserved, as for the stack itself. The whole-stack protect under an unlimited limit now takes 32 `msync` calls and finishes in milliseconds. |
| `8d2053a21` **fix(libkernel): keep a host thread's stack range once queried on Linux** (G1) | `HostStackLimits` keeps each thread's first result in a `thread_local`. The main thread's range is therefore the one from before any protect, and it stays put. A thread's stack never moves, so this changes nothing for other threads, and it saves a `pthread_getattr_np` call per protect. |
| `9a48a9605` **fix(libkernel): map a protected main stack up to its top on Linux** (G2) | When the `mprotect` hits unmapped pages, `MapUnmappedPages` now covers everything from the bottom of the protect up to the top of the reported stack, not just the protected pages. The stack then never has to grow past the protect. The pages are mapped lazily with no swap reserved, so they cost nothing until touched. The debt entry's Linux sentence now says this, plus G4's limit. |

## Better-version check

- **Map the whole main stack at start-up instead of at the first protect.** At start-up or adoption, map the main thread's whole reported range read/write with no swap reserved, and fix the range then.
  - That makes every later protect a plain `mprotect` and covers G4.
  - But every process would pay for it, protect or not.
  - Under an unlimited limit it would map the heap's growth space (G5) unless the range were capped first.
  - With G5 fixed, it would be the simpler design. Until then, mapping on the first protect, up to the top, is the safer one.
- **Map the protected pages `MAP_GROWSDOWN`.** That would get past the guard-gap check, which skips a growsdown mapping below. But the stack still couldn't grow through the protect, and the protected pages themselves would grow downward with their own protection on a touch below them. No.
- **Windows:** the alternative is the one the debt entry names (no guard page, TEB stack limit kept by hand). Its risk is bigger than the gap it closes.
