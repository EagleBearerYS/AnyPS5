# BF-053: why mesh-path programs are ~1M SPIR-V words, and a prototype that shrinks them (cloud-1)

**Inputs:**
- Upstream main **52798f71d** (main at 07:55Z; it moved during the task, from f8b22edfb).
- Fork branch **`exp/mesh-module-size` at fe2aaded8**: one commit on 52798f71d, "test(agc): measure mesh-path module words against the vertex path on synthetic programs". It adds `core/libs/prx/libSceAgcDriver/tests/execution/MeshModuleSize.cpp` (ctest `agc_driver_mesh_module_size`) and nothing else.
- Synthetic shaders only:
  - the repo's own NGG fixture `tests/MeshGeometryFixture.hpp` (the program `agc_driver_mesh` draws);
  - the 20-dword vertex program `agc_driver_indirect_patched_stage` uses;
  - N generated instructions inserted into each.

**Machine:** cloud-1: Intel Xeon @ 2.80 GHz, 4 vCPUs, 15 GiB, Ubuntu 24.04, gcc 13.3.0, wild 0.10.0, lavapipe from Mesa 25.2.8 (LLVM 20.1.2; host subgroup size 8). CI's Linux configure. Runs as root; this environment refused creating an unprivileged user.

RESULT:
- **Gate not met: the cut is under 5×, so I stopped (no switch, no prototype).** The largest mesh-specific factor in the recompiler is **2.0×**, and only on a 32-wide host such as the PC's RTX 3070.
- **What doubles:** `laneCount = 2` (SpirvEmitter.cpp:272-274). A wave64 program on a 32-wide host with workgroup input, which the mesh stage has, emits every non-uniform IR instruction once per half (SpirvFlowEmitter.cpp:769-770). The vertex stage never does.
  - Measured mesh words at host 32 over host 64: 1.99–2.00× at 1,000+ items.
  - Removing it would need a spanned-wave mesh path, as compute has (SpirvEmitter.cpp:273). That is about 2× at best, and nothing on AMD or lavapipe.
- **Nothing is emitted per vertex slot, primitive or output.**
  - The merged ES/GS program is translated once: GeometryBack is skipped and reached through the front's code (ShaderRegistry.cpp:1153, :1160).
  - The mesh entry prologue is fixed (InstructionTranslator.cpp:242-322).
  - The output arrays are only types. Module words are identical at 3, 6 and 16 output vertices (the test asserts it).
- **Per guest instruction, mesh costs what vertex costs.** The same vertex program compiled as mesh is 1.000–1.008× its vertex module at host 64 (2.0× at host 32).
  - NGG fixture against plain vertex, host 64: ALU 0.93–0.98×, raw loads 1.18×, format loads 1.07×.
  - LDS is 2.0× in the NGG program, from bounds-checked accesses in a program with `s_barrier`. The same LDS ops in a barrier-free program compiled as mesh cost 1.008×.
  - Fixed mesh overhead is 7–13k words.
- **The 77-way switch** is `formatSwitch` (SpirvRuntimeBuffer.cpp:526-545). A formatted buffer access with a run-time-only format switches over all 77 `IrBufferFormat` values. It can occur on any stage and is not mesh-specific; it wasn't reachable synthetically (it needs an image table), so it isn't measured.
- **Step 2 table** (plain vertex / NGG as mesh, host 64 / host 32):
  - 1k ALU: 121,183 / 119,191 / 236,896 words.
  - 5k ALU: 602,183 / 566,191 / 1,130,896.
  - 20k ALU: 2,405,933 / 2,242,441 / 4,483,396.
  - About 120 words per ALU op on either stage. Of those, about 23 extra instructions per float op are FP32 flush-to-zero emulation, which every stage and target pays.
- **Pipeline creation on lavapipe:** mesh pipelines can't be built on llvmpipe (the existing mesh test skips; LLVM aborted on mine). Vertex modules:
  - 1,009 words: 48 ms.
  - 121k words: 2.6 s.
  - 602k words: past the driver's 5 s fence wait (VK_TIMEOUT).
- **Village's 15–20× is therefore the programs, plus the 2× halves.** Its NGG/merged ES-GS programs must be several times longer than its plain vertex programs and LDS-heavy.
  - The PC can confirm with words per guest instruction by class, mesh against vertex: if it is about 2× for wave64, the size is inherent.
  - The bigger lever is general: native FP32 flush instead of the emulation, for every stage. It's a separate decision and wasn't prototyped.
- **FormatVersion:** no change was made, so no bump. A lane-half change is covered by `SourceVersion()`; a run-time switch in the cache key would need `FormatVersion` 36 → 37 (ShaderDiskCache.hpp:16).
- **Branch head:** `exp/mesh-module-size` **fe2aaded8** on upstream main 52798f71d. It holds only the measurement test `agc_driver_mesh_module_size` (passes, 4.9 s); the conventions check passes.

## Step 1: how the mesh-path program is built, and what is (not) duplicated

**1. Which programs go down the mesh path.** `Execution/src/Driver/Draw/DrawDecode.cpp:108-110`:
- The front program at 0xc8 (type 2, a vertex program, or type 4, the ES half of a merged ES/GS) is decoded as `Stage::Mesh` (`Role::Main`).
- For type 4, the GS half at 0x88 (type 6) is added as `Role::GeometryBack`.
- `PrepareGraphicsStages` (`Execution/src/Driver/Shaders/ShaderRegistry.cpp:1153, :1160`) passes every program's memory to the request but **skips GeometryBack**. The back half is reached through the front program's code, so the merged program is **translated once**.
- A vertex program that needs a workgroup takes the same path with its type-2 program (`Graphics/src/State.cpp:865-866`).

**2. The mesh entry prologue is a fixed size.** `Translation/src/InstructionTranslator.cpp:242-322` builds:
- the subgroup's vertex and primitive counts;
- the strip and fan parity and restart;
- the index fetch;
- the hidden user words.

All of it is a fixed set of IR, independent of the program, the output limits or the slot count.

**3. The mesh outputs are sized by the limits, but the code isn't.** `SpirvBackend/src/SpirvModuleEmitter.cpp:718` (`DefineMeshOutputs`) and `:783` (`EmitMeshEntryPoint`):
- The Output arrays are sized by `maxVertices` / `maxPrimitives`. Those are types, a few words.
- The entry point copies each output once per lane half.
- Measured: the module is **byte-for-byte the same word count at 3, 6 and 16 output vertices**: 7,205, 18,616 and 119,191 words at 0, 100 and 1000 ALU ops, host 64. The test asserts this.

**4. The one duplication: lane halves.**
- `SpirvEmitter.cpp:272-274`: `halfHost = workgroup && WaveSize() == 64 && hostSubgroupSize == 32`, and then `laneCount = 2` (unless `spannedWave`, which is compute-only).
- `SpirvFlowEmitter.cpp:769-770` emits **every non-uniform IR instruction once per half**. Wave-uniform values (`WaveUniformValues`) are shared between the halves.
- Only stages with workgroup input get this, and mesh is one; the vertex stage never does.
- A wave64 program on a 32-wide host (the PC's RTX 3070) therefore gets about 2× words on the mesh path. A 64-wide host (AMD) and lavapipe (8-wide) get 1×.
- Measured, mesh words at host 32 over host 64: **1.99–2.00×** for every family at 1,000 items or more, and 1.80× for the empty program (its fixed part).

**5. Per guest instruction, the mesh path costs what the vertex path costs.** See the step 2 table.
- The same plain vertex program compiled as mesh is 1.000–1.008× its vertex module at host 64, and 2.0× at host 32.
- The NGG fixture's LDS accesses cost about 2× the same accesses in a barrier-free program. One `ds_write_b32` + `ds_read_b32` is about 47 SPIR-V instructions and 10 blocks: two bounds-checked if/else regions.
- That cost belongs to an LDS program with `s_barrier`, not to the mesh path. The same LDS ops in the plain program compiled as mesh cost 1.008× the vertex module.

**6. The 77-way switch** is `formatSwitch` (`SpirvBackend/src/SpirvRuntimeBuffer.cpp:526-545`).
- A formatted buffer access whose descriptor format is only known at run time switches over every `IrBufferFormat` (`Format32_32_32_32Float = 77`, `IntermediateRepresentation/.../BufferFormat.hpp:86`), with a decode per case.
- It is emitted for that access on any stage, not per vertex slot.
- I could not reach it synthetically. The SRT walker resolves a descriptor loaded from memory at compile time, and fails if the memory isn't in the request; the run-time form needs an image table. So it is not measured. Seven of them in an image-table module are seven run-time-format accesses.

**7. The base cost is general.** One `v_mul_f32` becomes 3 `OpFMul` plus about 23 integer and bit operations (Bitcast, BitwiseAnd, ISub, ULessThan, UGreaterThan ×3, IEqual, Select ×4 …) and three `NoContraction` decorations, about 140 words.
- That is the FP32 flush-to-zero emulation: denorm mode is MODE[5:4], read in `Translation/src/VectorInstructions.cpp:102`.
- `SpirvTarget` has `float16DenormPreserve` / `float64DenormPreserve` but no native FP32 flush, so this is emitted on every target and every stage.
- The mix (Select, BitwiseAnd, Bitcast, IEqual, UGreaterThan, LogicalAnd) resembles the PC's histogram of the largest module.

- "NGG as mesh": the fixture with N items inserted before its exports, as a mesh shader with `MeshConfiguration{4, 4, 12, 12, 4, 64, 1024, 0, 4}`.
- "plain vertex": the vertex program with N items, as a vertex shader.
- "plain as mesh": the same program as a mesh shader, the "vertex program that needs a workgroup" shape.

- The NGG program can't be compiled as a vertex shader at all: "s_barrier in a vertex program that accesses LDS … is not implemented".

## Step 3: the gate, and why there is no prototype

- **The gate needs a cut of at least 5× on mesh-shaped programs. The largest mesh-specific factor is the lane halves: 2.0×, and only on a 32-wide host.**
  - Removing them would mean running a wave64 mesh program at one guest lane per invocation across two subgroups, with cross-half operations through workgroup memory. That's what `spannedWave` does for compute today (SpirvEmitter.cpp:273).
  - Its ceiling is the measured host-32 / host-64 ratio, about 2.0×. On AMD hosts and lavapipe it would gain nothing.
  - Nothing else on the mesh path scales with vertex slots, primitives or outputs (findings 1–3).
- **So the cut is under 5×, and per the gate I stopped.** No switch and no new on/off test.
- **It also couldn't be validated here.**
  - llvmpipe has an 8-wide subgroup, so `laneCount` is always 1 on this VM and a lane-half change wouldn't run at all.
  - The mesh-emulation draw test skips on llvmpipe, so the byte-identical on/off check isn't possible on this machine.

**Why Village's modules are 15–20× its vertex modules.**
- The recompiler gives the same guest code at most 2× more words on the mesh path, and only on a 32-wide host. The rest has to be in the programs themselves. Village's mesh-path programs are NGG/merged ES-GS programs: the vertex shader plus the GS plus culling, with LDS traffic between them. They are presumably several times longer than its plain vertex programs, and their LDS ops with barriers cost about 2× ALU-like ops.
- At 112–240 words per ALU op, 651k words is roughly 2,700–5,800 guest instructions.
- **One PC check settles it without shipping game data:**
  - For a few mesh and vertex modules, count the guest program's instructions by class (VALU, SALU, `ds_*`, `buffer_*`, `image_*`), plus its wave size and MODE.
  - Compare words per guest instruction. If mesh ≈ 2× vertex (wave64) or ≈ 1× (wave32), the size is inherent to the programs.
- **The bigger lever is general, not mesh-specific:** the FP32 denormal emulation at about 23 extra instructions per float op (finding 7). A native flush-to-zero where the target supports it (float controls) could shrink ALU-heavy modules of every stage several-fold. That is a separate semantic decision; I didn't prototype it.

## Step 4: disk cache

- Nothing in the emitted SPIR-V changed, so no `FormatVersion` bump is needed (`ShaderDiskCache.hpp:16`, `FormatVersion = 36`).
- A lane-half change would change the emitted modules. Entries are already invalidated by `SourceVersion()`, the hash of the recompiler sources checked at load (ShaderDiskCache.cpp:1301).
- If the change is gated by a run-time switch, the switch has to enter the cache key. That changes the key layout and needs **`FormatVersion` 36 → 37**.
