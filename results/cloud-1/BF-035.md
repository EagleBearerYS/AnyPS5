## Mechanism

**It is red, but not quite in the order the task proposed.** A late store that never saw the read is not the only failure. More importantly, a store the driver made *before* the read can land *after* it.

**1. A storage image's store is recorded, not made, while a recorder is active.**
- `StorageTexture::writeBackLayers` (`Graphics/src/Texture.cpp:4529`) decides which 64 KiB blocks to keep for the CPU at one moment: `CollectWritesUncached` at `:4567`, then `ChangedBlocks`.
- It then records the retile and the copy into the host-imported guest memory into the recorder's open batch (`Recorder::Active()` at `:4712`, `recorder->Commands()` at `:4721`) and notes a pending write (`NotePendingWrite` at `:4800`).
- Only a store with no active recorder submits and waits (`batch->SubmitAndWait()` at `:4796`).
- The bytes land when that batch runs, which can be much later. On this worker, a `FlushAllPending` followed by `AgcDriverWaitIdle` left every texel of the image unstored. They landed only at a later sync, from the flush hook or an allocation change.

**2. A host write takes none of that into account.**
- The APR read (`libkernel/Apr/src/Apr.cpp:159-170`), like every libkernel, libSceNet, libc and WebKit host write, opens a `GuestArena::HostWrite` scope and writes the guest pages directly.
- On Linux that scope does nothing: `GuestWriteWatchBeginHostWrite` is Apple-only, `libc/src/GuestWriteWatch.cpp:676-694`.
- So nothing waits for writes the GPU has recorded or has in flight over the range, and nothing stores the results still pending there.

The driver already has the right operation: `FlushForAccess` (`Graphics/src/Recorder.cpp:1004`). It is reached through `GuestMemory::FlushGpuWrites` (`Execution/src/GuestMemory.cpp:2085`), and the driver's own guest stores call it under `ReadSiteScope(Store)` before writing (`Write` at `:2228`, `WriteChanged` at `:2190`). It does three things:
- it waits for every batch, open or in flight, whose writes overlap the range (`Recorder::PendingWriteOverlaps`, `:2831`, covers `open` and `inFlight`);
- it stores the results still pending there;
- it waits for that store too.

Host writes were the one writer of guest memory that skipped it.

**How this matches the reporter's trace:**
- The read landed on a block that had a storage-image write-back about 50 ms earlier, and the block was then zeroed after the read. That is case 1 below: a write-back recorded or in flight before the read landed over the file data after it.
- "When the read started, its destination was in neither the pending-write snapshot nor `PendingWriteOverlaps`" also fits a race on the title's two threads. The write-back's keep decision on one thread ran while the APR read on another was still filling the range, so the collect did not see all of the read. The recorded copy then landed after the read.
- The fix closes both orders the same way. The results pending over the range are stored, and every GPU write there completes, before the host write starts. A write-back that starts during the read finds nothing pending there.

**What the write watch sees.** The order where the results are still pending at the host write, and the whole 64 KiB block is written, passes on main in every mode (case 3). So the write watch, or the compare without it, does record the kernel-mode `read()`. A host write into *part* of a block still loses: the store keeps the whole block for the CPU, and the image's results in the rest of it never land (case 4).

## The fix

- **libc:** `GuestArenaSetHostWriteObserver_nid_postfix(void (*)(void*, std::size_t))`. `GuestArenaBeginHostWrite_nid_postfix` calls the observer first, on every platform, for a non-empty range (`libc/src/GuestArena.cpp:485-490`). Every `HostWrite` user gets it with no change at the call site: APR, AIO, `read`/`pread`/`readv`, `recv`/`recvfrom` (libkernel and libSceNet), the `fcntl`/`ioctl` outputs, libc's file read and WebKit's `mkstemp`.
- **Driver:** `GuestMemory::FlushBeforeHostWrite` (`Execution/src/GuestMemory.cpp:2104`) calls `FlushGpuWrites` under `ReadSiteScope(ReadSite::Store)`, as `GuestMemory::Write` does.
  - It is registered in `Driver::Driver` and cleared in `~Driver` (`Execution/src/Driver/Lifecycle.cpp:143`, `:90`), beside the GPU map observer.
  - The driver's own `HostWrite` scope, the macOS import window inside `ImportWatched`, runs under the tracker lock. That scope skips the hook through a thread-local guard (`OwnHostWrite`, `:1378`), so it cannot re-enter the tracker.

**Locks.** No caller holds a mutex when the hook runs:
- libSceNet's `g_mutex` is released before its `HostWrite`;
- `DescriptorControl`'s `lock` is the guest record-lock struct, not a mutex;
- every other site holds nothing.

The GPU waits inside `FlushForAccess` run with the GPU mutex released when the hook's acquisition is the outermost, as for any CPU access. A failure to store propagates out of the host write, as it does out of the driver's own `Write`.

**Debt entry** (`docs/dev/debt/libSceAgcDriver.md:75`), updated:
- Host writes are now ordered after pending results and recorded GPU writes.
- The title's own CPU stores still are not ordered after them. Those stores survive only in the 64 KiB blocks the watch saw written, and a store recorded before them can land after them (#1970).
- The title's CPU reads after a label still read stale memory.

## Test

`agc_driver_host_write_pending_storage` (auto-registered from `tests/execution/`). How each case runs:
- A compute dispatch writes a 128×120 RGBA16F, 64 KiB-tiled storage image over a 128 KiB write-watched guest surface. The test then waits for idle, so the image's results are pending.
- A file is read into the surface exactly as `_readFile` does it: `std::ifstream::read` inside a `GuestArena::HostWrite` scope.

## Cost

`--cost 200000`, run as `runner`. It times a 64 KiB `HostWrite` scope over a block with nothing pending over it, best of 5 passes, two runs:

| State | With the flush | Without |
|---|---|---|
| an image's results pending elsewhere | 82.5 / 97.7 ns | 6.9 / 7.1 ns |
| nothing pending | 85.4 / 89.9 ns | 6.9 / 7.0 ns |

So the hook adds about 75–90 ns to a host write that has nothing to wait for. It is the flush hook's fast path: the queued-label check, the lock-free pending-write snapshot, and the pending-image registry and unit-shadow checks. That is more than "one check of the pending registry", but it is well under the `read()` it precedes.

  - a SIGSEGV in the title.
- **To see the fix act**, add `APS5_TRACE_APR=1 APS5_TRACE_FLUSH=1`. An APR read over results still pending is now followed at once by the store the hook makes for it, before the read's bytes land:
  ```
  [apr] read <file> offset=... size=0x<n> -> 0x<dest>
  [flush] image 0x<base>+0x<bytes> for memory access 0x<dest>+0x<n>
  ```
  A read over a store that was only recorded logs no `[flush]` line. The hook waits for that store's batch instead. `APS5_PROFILE_DRAW=1`'s hook-sync counts include those waits as stores.
- **If it still fails without `APS5_STORE_AT_FLIP=1`, the overwrite comes from something other than a host write:** a title CPU store over a recorded store (#1970), or a GPU path. An `[apr] read` line with no failure near it, followed by the same zeroed block, is the case to report back.
