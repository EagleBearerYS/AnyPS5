## Verdict

**The suspected cause (write-watch stamp order) is refuted.** The real cause is in the Windows arena, not the tracker's stamps:
- `WindowsMappings` recognizes guest views of the same physical page by the section **handle value** they were mapped with.
- The test closes each section handle right after mapping it, and Windows gives that value to the next section created.
- So the four blocks of a test target (surface, keys, code, data) were taken for views of the same pages. Stores into the data or keys block marked the surface's first 64 KiB written, and the next refresh dropped the pending results there.

**Who it reaches.**
- The DCC keys test, and main's own tests that map sections the same way.
- Not titles today. By the code, the kernel's mappings (direct memory, JIT) keep their section handle open while mapped and call `ForgetSection` before closing it, so they never present a reused value.
- The fix makes the arena correct for any caller that closes its handle after `Map`, which `Map`'s own `DuplicateHandle` invites.
- So a green DCC case 2 on the 3070 will confirm the cause. I don't expect Village's frames to change from this fix: no title path reaches the stale key.

## 1. The suspected cause, checked against the code

1. **Stamps happen at the walk on both platforms**, not "at the write on Linux":
   - `walkWrites` bumps the generation and stamps every page its collect returns (`GuestMemory.cpp:1162-1174`).
   - The Linux watch (`GuestWriteWatch.cpp:58-170`) works like the Windows views:
     - a registered range starts "fresh" and unprotected;
     - the first full collect reports the fresh pages and arms them;
     - armed-only collects skip fresh pages.
   - The Windows views behave the same: `seen` 0 against `generation` 1, `collected` bits, `Collection::Armed` (`WindowsMappings.hpp:330-414`).
2. **The upload takes its generation from a walk.** `StorageTexture::upload` takes `now = CollectWrites(...)` before anything else (`Texture.cpp:2163`); the direct path's import comes after (`:2241`), and `stampLayers` assigns `now`.
   - The collect memo could return a generation without walking, but only within one collect epoch on one thread.
   - The queue worker bumps the epoch for every submission enqueued after its last bump (`PacketExecution.cpp:153-157`).
   - The test's memset comes before its draw's submission, so the upload's collect walks it.
3. **`ImportWatched`'s pre-walk only stamps real later writes** (`GuestMemory.cpp:1360`). It collects armed pages written since their last collect: writes after the generation that collect gave. A store made before the upload has already been consumed by the upload's walk, so it cannot come out newer than the image.

So, without another source of "written" pages, nothing in the draw stamps the surface after its upload. The source is the arena.

## Root cause (file:line on main `03c4cb5e78`)

1. **The key.** `WindowsMappings::Map` duplicates the caller's section handle (`WindowsMappings.hpp:86`). But it keys the shared page records by the caller's handle value: `physical[(section, offset)]` (`:89`).
2. **The test.** `KeysClearOverPending.cpp:126-133` (`NewBlock`) does `CreateFileMappingW`, then `GuestArenaMap`, then `CloseHandle(section)`. Windows hands the freed handle value to the next `CreateFileMappingW`, so all four blocks of `NewTarget` map under one value.
   - The keys, code and data views find the surface's `Physical` slots for offsets 0-0xffff.
   - They join the surface's `SharedPage`s as aliases (`:121`, `:140`).
3. **Arming.** The upload's collect of the surface arms every alias of each settled page (`:413-423`), which write-protects the data and keys blocks too.
4. **The stores.**
   - The frame's read clears its output at data+0x2000 (`Sample()`). That CPU store faults on the armed data view, and on its own it is enough for the failure.
   - The draw's end-of-pipe label at data+0x1000 does the same when the driver stores it from the CPU.
   - `HandleWrite` bumps the shared page's generation (`:182-195`, `:716-722`). The surface's view then reads that subpage as written (`:393`).
5. **The drop.**
   - The refresh at the frame's read collects the surface (`Texture.cpp:1764`) and stamps unit 0 newer than the image, so `UnchangedSince` fails (`:1813`).
   - Unit 0 has pending results and is a whole 64 KiB unit, so it is droppable (`:1915-1923`) and dropped (`:1949-1956`).
   - The log line is "guest memory changed while GPU results were pending; keeping the CPU's blocks". The sample reads 0x3e808081, the 0x40 bytes stored before the draw.
6. **Why only some cases fail.**
   - `cpu-store`: its keys memset faults on the keys view, which aliases the surface the same way.
   - `dma-fill` and the WRITE_DATA cases expect the clear colour. A keys change makes every unit stale anyway, so they pass either way.
7. **Why Linux passes:** `NewBlock` maps private anonymous memory there, and nothing is keyed by a handle.

## 2. Reproducing on Linux

**Not possible.** The table at fault exists only in `WindowsMappings` (compiled for `_WIN32` only). Linux tracks each mapping by address, with no handle-keyed table.

**The suggested tracker-level ordering test.** "A CPU write, then a generation taken without a walk, then a walk, must not look newer than that generation" fails on main on both platforms, by design:
- a memoized collect within one epoch returns the current generation without walking (`GuestMemory.cpp:1188-1206`), and its writes are stamped at the next walk;
- the test's write precedes its submission's epoch, so this is not what fails there;
- I did not add that test, and I did not change the memo.

**What I added instead:** a Windows check in `tests/WriteTracking.cpp`, `CheckReusedSectionHandle`, run by `agc_write_tracking`.
1. It maps a section and closes its handle, then creates sections until one gets the same handle value (up to 64; otherwise it prints that the check did not run) and maps it.
2. It collects both.
3. It stores into the second: the first must read unchanged and the second changed. Then the reverse.
- **Expected red on main:** "a store into a section mapped under a closed section's handle value marked the closed section's pages as written".
- **Expected green with the fix:** "write tracking tests passed".
- It compiles with MinGW-w64; it has not run (no Windows host here).

## 3. The fix (`WindowsMappings.hpp`, +14/-3)

- **Recording.** `Map` records which section object a handle value was first mapped for: `sectionOwners[value]`, the arena's own duplicate.
- **Checking.** When the value comes again, `Map` compares the stored section with the caller's using `CompareObjectHandles`. The arena already loads it as `sameSection` for `MapAlias`. It needs Windows 10 1607; the arena already needs `VirtualAlloc2`/`MapViewOfFile3` (1803).
- **A different section** means the value was reused. The old pages are forgotten first, exactly as `ForgetSection` does: `forgetSection(value)` erases the `physical` slots and the owner.
  - The closed section's views keep their own page records and tracking.
  - The new section starts with fresh records.
- **The same section** (the kernel mapping one backing several times, or `DccKeysFirstWrite`'s block and twin of one section) keeps its records, so real aliases still propagate writes.
- **Without `CompareObjectHandles`**, the old behaviour stays.
- `ForgetSection` (kernel) now also drops the owner.

## 4. Siblings

- **The other user of the same table: the resident direct-memory path.** `Map` with `resident` restores a page's `saved` bytes from its `Physical` slot (`WindowsMappings.hpp:111-117`). Under a reused value, that would have copied another section's evicted bytes into a new mapping. The same check prevents it. Unreachable from the kernel today (it forgets before closing).
- **Kernel callers:**
  - `PhysicalBacking` (`DirectMemory.cpp:318-321`) and `JitObject` (`Jit.cpp:64-68`) keep the handle open and forget it before `CloseHandle`. Unchanged behaviour.
  - `DoMapShared` is used for JIT objects only on Windows.
  - Shared-memory objects are host files on Linux only.
  - `CallTrace.cpp` and the shader caches map sections outside the arena.
- **Main's tests with the same pattern** (map, then close the handle without `ForgetSection`); with the fix none of these can alias by accident:
  - `Recorder.cpp:5625-5628` (a helper called per block);
  - `Recorder.cpp:7838-7842` (a loop);
  - `WriteTracking.cpp:286-339` (one section);
  - `DccKeysFirstWrite.cpp:100-106` (one section mapped twice on purpose; still aliased, since its handle is open for both maps).
- **The consumers named in the task:**
  - sampled textures (`Texture.cpp:1749/1792/1869/3349/4574`);
  - buffer mirrors (`GuestBufferMemory.cpp:1649/1735/1811`);
  - native MS depth (`DepthSurface.cpp:118/223/230`);
  - shader resource tables (`ShaderResources.cpp:1457/2623`);
  - unit shadows (`UnitShadow.cpp:186`);
  - the recorder (`Recorder.cpp:2609`).

  All read the same stamps. Under the aliasing, each could see false writes on Windows: a re-upload, a re-copy, a dropped unit, or `DepthSurface`'s "guest writes raced native multisample depth" `Require`. The fix removes the false stamps for all of them.
- **Generation and stamp order** (item 4's original question): no consumer needs a change. Every generation they compare comes from a walk or from the epoch memo, and the import's pre-walk stamps only writes made after it. See 1.

## 5. Cost

- **Upload and lookup paths:** nothing added. No code in `CollectWrites`, `UnchangedSince`, `ChangedBlocks`, the refresh or the import changed.
- **`Map`** (a guest mmap of shared or direct memory) adds:
  - one `std::map` lookup per call;
  - when the handle value is already known, one `CompareObjectHandles` system call per call, not per page.
- **Memory:** one map entry per section handle value in use.

## PR draft

**Title:** fix(libc): tell a section from a closed one whose handle value it reuses on Windows

```
## What

The Windows guest arena recognizes views of one physical page by the section
handle value and offset each was mapped with (WindowsMappings::Map), so a
store through one view marks the others written. Map duplicates the handle
it is given, and a caller may close its own right after mapping; Windows
then hands the same value to the next section created, and that section's
views were taken for views of the closed section's pages: arming one
protected the other, and a store into either marked both written.

In the DCC keys-over-pending-results test every block of a target (surface,
keys, code, data) is a section mapped under one handle value. The draw's
end-of-pipe label store and the frame's read clearing its output (data
block) marked the surface's first 64 KiB written, the refresh stamped them
newer than the storage image, and its pending results there were dropped
for the bytes stored before the draw ("guest memory changed while GPU
results were pending; keeping the CPU's blocks").

Map now keeps the section each handle value was first mapped for and
compares it with CompareObjectHandles when the value comes again; a
different section forgets the old one's pages first, as ForgetSection does.
The kernel's direct memory and JIT objects keep their handle open while
mapped and forget it before closing, so titles did not hit this; tests that
close the handle after mapping (Recorder, WriteTracking, the DCC tests) did.

## Cost

No change to collects, stamps, lookups or uploads. Map does one map lookup,
and one CompareObjectHandles when a handle value comes again.

## Tests

agc_write_tracking (Windows): two sections mapped under one handle value,
a store into each; the other must read unchanged.

## Evidence

WINDOWS: <agc_write_tracking red on main / green on the branch, the 3070>
WINDOWS: <agc_driver_keys_clear_over_pending: dma-fill-after-read and
cpu-store green with the fix, red without>
```

RESULT:
- **Repo:** fork EagleBearerYS/AnyPS5, `fix/agc-write-watch-stamp-order` `26254fbed` (1 commit on upstream main `03c4cb5e78`).
- **Root cause:** `WindowsMappings::Map` keys shared physical pages by the caller's section handle value (`WindowsMappings.hpp:89`).
  - The test closes the handle after mapping, and the next section gets the same value.
  - Its views alias the earlier section's pages, so stores into the data or keys block mark the surface written, and the refresh drops the pending results (`Texture.cpp:1813/1915/1949`).
  - The stamp-order theory is refuted (1). Titles are not reached (the kernel keeps its handles open and forgets them).
- **Fix:** `Map` checks section identity with `CompareObjectHandles` when a handle value repeats, and forgets the stale pages first.
- **Tests:**

  - Linux `^agc` 604/605 with 42 expected skips (the 1 also fails on pure main);

- **Cost:** nothing in the upload or lookup path; one syscall per repeated `Map` of a handle value.
