## 1. Stage flags: what changed in PR 6947's heap set, and why it's safe

**The change.** Only the stage flags change: the heap set's sampled-image arrays (bindings 65 + kind) and sampler array (122), and set 3's buckets and ring, gain `VK_SHADER_STAGE_MESH_BIT_EXT` when the device enables `VK_EXT_mesh_shader`. The flags go from 0x31 to 0xb1 on lavapipe.
- Types, counts, binding flags (partially bound, update after bind, variable count), the data set, the dynamic offsets and the pool sizes are unchanged.
- With no mesh shader the flags stay `VS | FS | CS` exactly as before.

**No task bit.** These are the flags main's mesh pipelines use:
- `VulkanDevice` enables `meshShader` only, never `taskShader`.
- The recompiler has no task stage: the GS path compiles as `ShaderStage::Mesh`.
- A `TASK_BIT_EXT` binding on a device without the `taskShader` feature would be invalid, and nothing could read it.

**Why it's safe for PR 6947's GPU-mode pipelines.**
- **Which stages are GPU-mode.** `gpuModeStage = target.gpuResolvedImages && (VS | FS | CS)` (Recompiler.cpp:298), and `DescribeSetLayouts`' `heapShader` applies the same filter. A mesh stage is never GPU-mode, so no GPU-mode pipeline gains a mesh shader.
- **Extra bits are harmless.** A set layout's stage flags may name stages the pipeline doesn't have, so GPU-mode VS/FS/CS pipelines and compute pipelines take the wider layout unchanged.
- **One layout per device.** All pipelines still share the one heap layout `BindlessHeap::For(context).HeapLayout()`, so set compatibility between GPU-mode pipelines and with the bound heap set is unchanged.
- **Per-stage limits.** Only the mesh stage's count grows, and only by the heap's arrays, which the pixel stage already counts. The validation layer reported no limit errors.
- **The journal's description is unchanged.**
  - `DescribeSetLayouts` keys a heap-stage pipeline's fragment set as the constant `{0x48454150}` ("HEAP"), with no stage flags.
  - Device sets 2 and 3 are not part of `mainLayoutKey` / `fragmentLayoutKey`.
  - Existing journal entries therefore still match, and replays build the layouts from the current device.
- **Run.** With the switch unset, `agc_driver_bindless_images`, every `_gpu_heap` variant and `agc_driver_device_image_table_heap_cap` pass on the head (mirror below). With `APS5_GPU_PATH=1`, `agc_driver_bindless_images` and the `heap_draw_sample` variants fail identically on the base and the head (section 6).

**Check: layouts with and without libraries.** `agc_driver_device_image_table` (`MeshLayouts`, run with `APS5_GPU_PATH=1` by the test itself):
- `ImageHeapStages` contains `VS | FS | CS`, nothing else besides MESH, and MESH exactly when `Context::meshShader`.
- A mesh+fragment `CachedPipeline` whose mesh stage has `deviceImageTables` gets `deviceHeap == HeapLayout()`, `deviceTable == table->Layout()` and `deviceGap == EmptyLayout()` from `DescribeSetLayouts`, the same function the journal's replay (PipelineJournal.cpp:965) and the draw path use. It is created both from pipeline libraries and without them. Output: "mesh pipeline with sets 2 and 3 from/without pipeline libraries (split sets 1): created, heap and table stages 0xb1".
- The mesh shader (`Triangle.mesh`) reads a set 2 heap image (binding 66), the set 2 sampler (122) and the set 3 bucket buffer (set 3 binding 0), so the validation layer checks every stage flag involved.

**Red/green under the validation layer** (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`):
- **Red:** a driver with the old set flags but `ImageHeapStages` still reporting MESH. It gives 9 × `VUID-VkGraphicsPipelineCreateInfo-layout-07988`, "SPIR-V (VK_SHADER_STAGE_MESH_BIT_EXT) uses descriptor slot [Set 3 Binding 0] / [Set 2 Binding 122] … but the stageFlags … do not include it".

## 4. Tests

### (a) a mesh program reading a T# from a 2,000-entry V# table

`agc_shader_memory` (`verifyDeviceImageTables`). The program is the repository's NGG fixture with 14 dwords inserted before its exports (the branch at dword 92 is moved past them):
- it loads the SRT pointer and key from user data 16-18;
- loads a V# for a 2,000-entry table;
- reads a T# through it;
- and samples it into a parameter export.

It is compiled as `ShaderStage::Mesh` (wave64, `MeshConfiguration{4,4,12,12,4,64,1024,0,4}`, SPIR-V 1.4, MeshShadingEXT) for host subgroups 64 and 32, with the option off and on.

**Option on:**
- the plan's column is `deviceTable`;
- `requiresSpecializationMemory` is false;
- the module has the device lookup, bucket buffer, miss ring and heap array;
- the capture reads none of the table's records;
- no CPU `ImageTable` / `ImageTableMap` binding.

**Option off:** the CPU table binding, and no device lookup.

Both modules pass `spirv-val` through `ValidateAndOptimizeSpirv` (the CI configure has SPIR-V Tools on). **Pass.**

**Not run:** the run-time half (first draw zeros and misses recorded, second draw the CPU path's texels, no snapshot). It needs a mesh draw, and llvmpipe aborts compiling these exact modules at their first draw (section 5). The same miss → insert → hit sequence runs on lavapipe for the vertex and pixel stages in `agc_driver_device_image_path` (LA-003/LA-004's parts), and the mesh stage reads through the same lookup, buckets and ring.

The stage loop in the same test compiles one table column (`DeviceTablePixelCode`, re-encoded for each stage's user data) as vertex, mesh and domain stages. Vertex and mesh: `deviceTable`, read at run time. Domain: CPU table. **Pass.**

### (b) tessellation and geometry stay on the CPU path

- **Domain** (`TessellationEvaluation`, with a `TessellationConfiguration`): the column keeps its CPU table (`deviceTable == false`, `requiresSpecializationMemory == true`). **Pass.**
- **Hull and local** can't be compiled stand-alone from this program: "tessellation ring base is used outside a lowered ring access" (they need ring programs). They take the same `deviceTableStage == false` branch, so they aren't in the test.
- **Geometry** is not a guest stage ("unsupported shader stage"), as above.

### (c) a CPU write to a T# record between two draws: `agc_driver_device_image_path` part (i)

The test points table entry 1545 at another texture of the same format between draws: textures 9 → 14, then back to 9.

**Next collect epoch** (a CPU write between two submissions):
- **Device path** (`APS5_GPU_PATH=1`): the first draw after the write reads zeros, because the new key missed (128 miss records). The second draw samples the new texture. It never samples the old texture.
- **CPU path** (switch unset): the first draw already samples the new texture.

**Same collect epoch.** The write happens after the queue worker decoded the draw and before the committer recorded it. A blocking committer item holds it there, as in `agc_driver_pipelined_indirect_draw`, with `Outstanding >= 3`.
- **Device path:** the first draw samples the new texture directly (0 miss records), and so does the next. The table's V# buffer binding is therefore not reused stale. It never samples the old texture.
- **CPU path:** the first draw samples the old texture, because the CPU table is taken when the draw is decoded. The next draw samples the new one.
  - This is by design on the CPU path, so there the test reports which texture was sampled and does not assert it.
  - "Never the old texture" is asserted on the device path.

All four ctest variants pass, and 5/5 repeats of the device-path run pass.

### (d) CPU writes to the table's memory while PR 6947's space reuse is active: `agc_driver_heap_space_writes`

**The program.** A pixel program (`BdaPixelCode`, from `HeapDrawSample`) reads a word through a read-only address-based space (`global_load`) and writes it as the alpha of a sampled texel.
- Its code, headers, texture and words sit in one registered 2 MiB guest block, so the address space alone serves the build (`GuestBufferMemory::SpaceOnly()`).
- With PR 6947's GPU heap, the build is cached with its space and retakes it on later draws.

**The sequence.** Before each pair of draws the CPU writes a new word:
- bytes 51, 102, 153, 204, 77 and 179, as byte/255 (exact in UNORM8);
- then word 64 = 128 and word 1 = 230.

Every draw must read the word written before it, including after a draw that read another word.

**Variants.**
- `agc_driver_heap_space_writes`: GPU heap off.
- `_gpu_heap`: `APS5_GPU_HEAP=1 APS5_DRAW_PIPELINE=1`, from `agcGpuHeapTests`.
- `_gpu_heap_mirrored`: also `APS5_HOST_IMPORT_MIB=1`. The block is past the import budget, so the import is refused and the space serves the block from a heap mirror (`[epoch-mirrors]`).

**Reuse is real.** During development I temporarily instrumented the reuse path. In `_gpu_heap` it showed 13 `GuestBufferMemory::RetakeSpace` and 13 `ShaderResources::Revalidate` calls on cache hits (Draw.cpp ~1333), so reuse is live in that variant. The instrumentation is not committed.
- My first version had the code and headers in static memory. They became regions, `SpaceOnly()` was false, and reuse never happened. That is why everything sits in one guest block.

**Result: pass.** Every draw reads the current word in all three variants, and 5/5 repeats of each `_gpu_heap` variant pass.
- **No bug found in PR 6947's space reuse** for CPU writes between submissions.
- **Not tested:** a CPU write inside the same collect epoch, after the draw was decoded. That is outside the epoch contract the reused space keeps, so this doesn't clear the Hades II report on that path.

- **(d) inside one collect epoch:** not tested. A write after a draw was decoded is outside the epoch contract that space reuse keeps.
