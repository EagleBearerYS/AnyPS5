**From event to unlock**

1. The game posts an event, such as `COLLECT {"counter":10}`, to a UDS context. The context gives the user and service label.
2. Rules for that event name in `udsNN.ucp` pick their `$.path` property. Each value is checked:
   - It is used if it is an integer of any width that is not negative, fits the statistic's type, and lies within `minValue`/`maxValue`.
   - Otherwise it is ignored, with one `[trophy] ignored <event> $.<path> for stat <id>: <reason>` line per rule: missing, negative, not an integer, or out of range.
3. A used value becomes the statistic's latest value and is saved to `<user>_<label>.stats.txt` when it changed.
4. If any statistic was set, every trophy in `trophyNN.ucp` is checked. The trophy needs:
   - a `udsStatId`, an unsigned `targetValue` and a known comparator;
   - a grade other than platinum;
   - a value for its statistic;
   - not to be unlocked yet.

   A statistic that was never set reaches nothing, so `le`/`lt` trophies do not unlock at a start value of 0.
5. Each reached trophy goes through `NpTrophy2RecordUnlock_nid_no_patch`, so the log line, listeners, file and platinum check are PM-016's.

**Choices the public data leaves open**

| Question | What the code does |
|---|---|
| Must the property's width match the statistic exactly? | No. KytyPS5 requires `uint32` for `uint32` statistics and `uint64` for `uint64` ones. I accept any integer width in range, so a game that sets a counter with `SetInt32` still counts. This is listed as debt. |
| Is the condition checked against the latest value or the event's value? | Against the stored latest value, which for `latest` is the same as the event's value. Storing it also gives progressive trophies their progress across runs. |
| Progress for a progressive trophy | `min(statistic, target)`, and the target once the trophy is unlocked. KytyPS5 reports 0 until the unlock. |
| Trophy or group id not in the file | The query throws `std::invalid_argument` naming the id and the file, following the convention that a function does its job or throws. KytyPS5 returns 0x8055390a or 0x8055390b, which are unconfirmed. |
| Base group | −1 (KytyPS5). It is listed first only when some trophy has no `groupId`. Placeholders keep PM-016's group 0. |
| Hidden trophies | Names and descriptions are reported as they are, as in KytyPS5. Whether the console blanks them is not known. |
| Language 30 (Ukrainian) | Tag `uk-UA`, an assumption: KytyPS5 lists only 0–29. A wrong tag only falls back to English. |
| File size cap | 256 MiB per `.ucp` (KytyPS5 allows 1 GiB). Larger files are logged and skipped. |

**The layout change** (commit 12d298d31)

- **Why it matters.** PM-016's `NpTrophy2Progress { uint32 value; }` had no public source, and its constants file already defined `NP_TROPHY2_PROGRESS_TYPE_NONE` without a field to hold it. Once queries return real names and whole arrays, the layout decides:
  - where a game reads `name` (offset 32, not 20);
  - the stride of `GetTrophyInfoArray` (1312 bytes, not 1300).
- **Source.** KytyPS5's `static_assert`s are the only public layout I found, so I adopted them and pinned all six sizes.
- **If it is wrong.** If a console trace or a game's stack use shows otherwise, this one commit is the one to revisit; the later commits only use `.type` and `.value`.

## Platinum

- **What is implemented.** After any new unlock, whether from `_UnlockTrophy` or from statistics, the trophy's `platinumTrophyId` is looked up. The platinum unlocks through the same path, with its own log line and listener call, when:
  - that id is a grade-P trophy in the file;
  - it is not unlocked yet;
  - every other trophy whose `platinumTrophyId` names it is unlocked.
- **What the public data establishes.**
  - The field and its meaning, "this trophy counts toward that platinum": KytyPS5 reads `platinumTrophyId` per trophy.
  - The behaviour players know: the platinum comes with every other trophy of the base set.
- **What it does not establish.**
  - Whether the console requires exactly the trophies that name the platinum, or every non-platinum trophy of the base group. These coincide when every base trophy names it.
  - Whether the platinum takes the triggering unlock's timestamp. KytyPS5 does that; here it gets its own tick, microseconds later.
- **Refusals.** KytyPS5 refuses direct `_UnlockTrophy` of a platinum or a progressive trophy. This branch keeps PM-016's behaviour and records them. It is listed as debt.

### Test-harness note (for whoever writes the next trophy test)

- **The problem.** An exception thrown inside a `.prx` aborts the process if it unwinds through a frame of the test executable that has its own cleanup: libc.prx raises it, and the executable's static `_Unwind_Resume` cannot continue it. ## What a Village run should log for a stat-driven unlock

Run with `APS5_TRACE_UDS=1`. The first trophy query or event reads the files, and every post is traced. A stat-driven unlock looks like this. The format is what `guest_np_trophy_stats` prints; the title id is Village's, and the counts and event names are made up:

```
[trophy] /app0/sce_sys/trophy2/trophy00.ucp: 52 trophies, 1 group, texts in en-US
[trophy] /app0/sce_sys/uds/uds00.ucp: 40 stats, 45 rules for 30 events
[uds] context 1 posted COLLECT {"counter":10}
[uds] stat 10 of user 268435456 is 10 (COLLECT $.counter)
[trophy] PPSA01556 unlocked trophy 1 for user 268435456
```

The counts in the first two lines will be Village's own. The platinum, when it comes, is a second `unlocked trophy` line right after the last one.

How to read a run that shows no unlock:

1. **`[uds] /app0/sce_sys/uds/uds00.ucp does not exist, so posted events update no stats`.** Village has no statistics rules at this label. Look for a `udsNN.ucp` with another number, which means the game uses another service label. If there is none, Village unlocks only through `_UnlockTrophy` (PM-016's path).
2. **`[trophy] /app0/sce_sys/…ucp is malformed, so …: <reason>`.** Send this line: it names the field or offset.
3. **`[trophy] /app0/sce_sys/uds/uds00.ucp: stat 50 has aggregation "sum"; only "latest" is supported`** (and similar `dataType`, `filters`, `reads` lines). Village uses a rule this branch does not apply. These lines are the list of what part 3 would need.
4. **`[uds] context N posted <event> {…}` with no `[uds] stat` line after it.** That event has no rule (normal for most events). If it should have one, look for `[trophy] ignored <event> $.<path> for stat <id>: <reason>`: the property is missing, negative, not an integer or out of range.
5. **`[uds] stat` lines but no `unlocked` line.** The value has not reached the trophy's `targetValue`. The progressive trophies' progress in the game's trophy list shows how far.
6. **`[trophy] … ignored … trophy progress is not recorded`.** Village posts `_UpdateTrophyProgress`, which is still log-only. Send one such line, because its properties would define part 3.

Without the variable, only the `[trophy]` lines appear: the file summary, skipped entries, `ignored` lines and unlocks.
