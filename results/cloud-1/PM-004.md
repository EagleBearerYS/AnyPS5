## Decision needed: the submodule's own submodules (about 0.3-1.5 GB per checkout)

Every FSR 1 release tag (v1.0, v1.0.1, v1.0.2) carries two submodules for AMD's sample app: `sample/libs/Cauldron` and `sample/media/Cauldron-Media` (glTF scenes and textures). The project fetches submodules recursively everywhere:

- CI's `actions/checkout` uses `submodules: recursive`.
- CI's PR-merge step runs `git submodule update --init --recursive` without `--depth`.
- release.yml fetches recursively as well.
- BUILD.md tells users to run `git submodule update --init --recursive`.

So every checkout now also pulls those two submodules, although the build reads only `ffx-fsr/ffx_a.h` and `ffx-fsr/ffx_fsr1.h` (243 KB).

   - BUILD.md would change the same way.
   - Anyone who still runs a plain `--recursive` gets the 2 GB.
3. **Vendor the files (my recommendation).**
   - Copy `ffx_a.h`, `ffx_fsr1.h` and `license.txt` from tag v1.0.2 (a21ffb8f6c13233ba336352bdff293894c706575) to the same paths under `3rdparty/FidelityFX-FSR/`.
   - Add a README giving the source URL, tag, commit and SHA-256 of each file:
     - `ffx_a.h`: f60e2722fcd13989523b9164d776ab382b3692791767f3bf8bb19967f763f3fb
     - `ffx_fsr1.h`: 93c3922362ea7fc99cbcc698ca30c98de4f8c246d1fbb0b09e015ddef38ce3a5

## Design

- **Settings.**
  - `ANYPS5_UPSCALE` and `ANYPS5_FSR_SHARPNESS` are read once, when a windowed `VulkanDevice` is created, by `SelectUpscaleMode` in `UpscaleMode.hpp`. This follows the same pattern as `ANYPS5_PRESENT_MODE`.
  - An empty value is the same as unset. Any other bad value throws, so the start fails:
    - "Vulkan presentation: ANYPS5_UPSCALE must be fsr or unset"
    - "... ANYPS5_FSR_SHARPNESS must be a number from 0.0 to 2.0"
  - When unset, no upscaler object exists. The only change to today's path is an `&& !upscaled` term in the two swapchain-barrier `if`s, which is always true then.
- **With `fsr`, `present()` first renders today's output into a per-slot stage image** in the swapchain format, instead of into the swapchain:
  - drawn path: `PresentationPass::RecordStage`, the same shader with the same decode and PQ encoding;
  - direct path: the same `vkCmdBlitImage` from the resident image as today (`PresentationScaler::RecordStretchFrom`);
  - shared path: the scaler's blit (`RecordStretch`).
- **Stage size.**
  - When the aspect-fit rectangle is larger than the display buffer on some axis (`PresentationUpscaler::Upscales`), the stage is the display buffer's size, copied 1:1. EASU (`FsrEasu.frag`) then scales it to the fit rectangle in a second per-slot image.
  - Otherwise, at 1:1 or when downscaling, the stage is the fit rectangle, made exactly as today, and EASU is skipped.
- **RCAS** (`FsrRcas.frag`) runs on every frame. It reads that image and writes the swapchain image: the sharpened fit rectangle with a black letterbox around it, ending in PRESENT_SRC like today's drawn path.
- **Shaders.**
  - They include AMD's `ffx_a.h` and `ffx_fsr1.h` from the submodule (32-bit path, `A_GPU` and `A_GLSL`). They are built to embedded SPIR-V by the same glslang step as the other presentation shaders.
  - `FsrEasuCon` and `FsrRcasCon` run in the shader, from 16- and 20-byte push constants.
  - EASU samples with `textureGather` on a NEAREST, CLAMP_TO_EDGE sampler. RCAS uses `texelFetch`, clamped to the image.
- **`PresentationUpscaler`** (new) owns:
  - the pipelines, one per format, final layout and filter, created under the pipeline-cache lock;
  - the per-slot images, created on first use and re-created when the format or size changes;
  - the per-frame views and framebuffers, freed when the slot retires.
- **Memory and passes.**
  - Two images per presentation slot. There are `FlipInFlight() + 1` slots.
  - Example: a 1080p buffer in a 4K window needs 7.9 + 31.6 MiB per slot.
  - Each frame costs two extra full-window passes.

## PQ handling (for the PR text)

- **What FSR sees.** FSR runs on the encoded values the display receives, never on linear light:
  - SDR: sRGB-encoded B8G8R8A8 values. The swapchain is UNORM with SRGB_NONLINEAR, so the shaders see encoded values.
  - HDR10: PQ (ST 2084) code values in A2B10G10R10.
  - There is no PQ-to-linear-and-back round trip.
  - AMD's header asks for channels in [0, 1] and a curve "as if presenting to sRGB display or similar". PQ is the HDR10 display curve and perceptually spaced, so it qualifies.
- **No overshoot:**
  - EASU limits each output to the minimum and maximum of the nearest 2x2 input texels (AMD's deringing), so it stays inside the input range.
  - RCAS solves for the strongest negative lobe that doesn't clip out of [0, 1]. Its final normalization uses AMD's approximate reciprocal, though, so the shader clamps the RCAS result to [0, 1] before writing.
  - So PQ output is always a valid code, with no excursions above the mastering peak.
- **Tested:**
  - EASU finite and inside [0, 1] on edges, thin lines and a gradient.
  - RCAS at sharpness 0 (the strongest) inside [0, 1] at 1:1 and 2x.
  - An HDR10 present of a PQ checkerboard at sharpness 0 into A2B10G10R10: valid codes, a flat region that stays flat, letterbox 0xc0000000.

## Not sure about / notes

1. **The nested-submodule cost above.**
2. **RCAS tonal shift.**
   - AMD's RCAS normalizes with an approximate reciprocal (`APrxMedRcpF1`), so flat areas shift uniformly by up to about 0.3%. Measured: 0.5 became 0.49966 at sharpness 2.0 and 0.49917 at 0.2.
   - Flat white can lose one 8-bit code. In HDR10 that's up to about 3 PQ codes near the top.
   - Fixing it would mean editing AMD's header, so I left it as is. The tests check uniformity, plus a 0.35% bound.
3. **lavapipe's float-to-10-bit conversion isn't round-to-nearest:** 63.798 stored as 63. Vulkan allows either neighbour, so the SDR and HDR10 tests accept a uniform result within one code.
4. **HDR10 is tested at the component level only.** lavapipe's X11 swapchain offers only SRGB_NONLINEAR, and an HDR10 swapchain is reachable on Windows hosts only.
   - There is no GPU here; everything ran on lavapipe. The PR's "GPUs tested" line needs a run on a real GPU, ideally on the Windows PC with an HDR display.
   - The Windows CI job wasn't run here. The new code is platform-neutral, and the test has the same WIN32 PATH setting as its neighbours.
5. **Overlap with cloud-2's PM-003 overlay branch** (fork head 7126e05ca). `git merge-tree` shows textual conflicts in `core/libs/prx/libSceAgcDriver/CMakeLists.txt`, `docs/user/USAGE.md` and `VulkanDevice.cpp`.
   - In CMakeLists.txt and USAGE.md both sides add next to each other; keep both.
   - `present()` needs one real resolution, because the overlay draws on the swapchain after the presentation:
     - pass `overlay ? VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL : VK_IMAGE_LAYOUT_PRESENT_SRC_KHR` to `upscaler->RecordPresent`;
     - give the overlay `drawn || upscaled ? COLOR_ATTACHMENT_OPTIMAL : TRANSFER_DST_OPTIMAL`;
     - keep `else if (!drawn && !upscaled)` for the final barrier.
   - Whichever branch merges second needs this rebase.
6. **The PR must state AI assistance.** CONTRIBUTING.md says "Say whether the change was written with AI assistance." I didn't open the PR.
7. **Sharpness 2.0 is the weakest setting, not off.** AMD's scale is in stops, and each stop halves the strength. With FSR selected, RCAS always runs, as the task specified for 1:1 and downscaling.
8. **No game data, dumps or Sony files were used.**
   - The VideoOut tests' frame dumps are their own synthetic frames.
