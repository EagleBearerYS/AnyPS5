## What his path is, and why that decides the porting

**His path.** It replaces main's CPU path (CPU capture of SRT/V# reads, draw and dispatch caches, recipes, CPU snapshots and host copies) with an in-place memory path:
- shaders read guest memory at run time through a GPU page table (013e8f65b, 4fed36d9c), and he deleted the capture (68cc97aed, efdc6a6f4);
- a residency manager keeps device-local mirrors of guest pages (02827d79f and about 100 follow-ups);
- guest memory is host-imported when the arena commits or maps it (c472afc72; Windows-only).

**What that means for porting.**
- His "keep GPU-written data in VRAM" work, for buffers and render targets, only pays off when GPU readers are redirected to the mirrors. That redirect is his page table, or sparse mirror binding (C5) plus binding changes.
- Main has neither, so most of piece C and D2 would do nothing on main, and some would add copies.
- For depth, main already keeps planes on the GPU:
  - 84e3b73f1 keeps stale D32/D32S8 1× Z_X planes on the GPU until a reader (DepthSurface.cpp:1700-1735);
  - f57bbc936 stores only the overlapped 64 KiB units;
  - fac197954 overlaps his 2726f5f8c.
- So his "depth is done" mostly brings his own path up to correct behaviour; it does not save VRAM over main.

**What does port cheaply.** The pieces that sit on code main still has: pattern fills, swept staging, unit-limited write-backs, pipeline-creation memory, and a few own-memory items.
