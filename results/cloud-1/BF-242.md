**The failing join (the Village log's first line):**
1. **Where it starts:** `UploadFinish`'s pre-pass (`:5003-5009`) calls `importJoined` (`:1772`, at `:5008`) for each pending region that no import holds and no single registered range covers. That is a view crossing adjacent ranges.
2. **`importRunAt` (`:1785`):**
   - For a join, `held` never protects an import (`:1826`). So the loop at `:1830-1833` counts every import inside the joined run as replaced.
   - **Before allocating, it retires them** (`:1866-1870`, `retireImport` at `:1868`; each retire moves `state.epoch`, `:390`), plus `retireLeastRecent` (`:1871`).
3. **`vkAllocateMemory` fails:**
   - It prints "falling back to copies, requested by join" (`:1972`).
   - It lowers the ceiling to the live bytes (`:1973-1978`, condition `:1975`). Because the run's own imports were retired a moment before, that live figure no longer includes them.
   - `failedImport()` records the run in `failedJoins` and returns null (`:1884-1888`).
4. **So the ranges that had imports have none afterwards,** and under the lowered ceiling they cannot be imported again. The log's next lines show this: "budget lowered…", then an import refused "by build".

**How a build's views find an owner after that:**
5. **Views the space serves (`addDescriptorRegion`, `:4336`):**
   - An address-based build that hit the cached space (`AcquireRegistered`, `:3908`) keeps no region for a view inside one of the space's base regions.
   - In the `Inside` case it returns at `:4353`, after `servedInsideBase` (`:4352`). The view's bytes are served by the base region, the registered range's import (`direct`).
   - A written view is only recorded in `writes` (`:4430`).
6. **The space dissolves after the failed join:**
   - The retires moved the epoch, so `UploadFinish` dissolves the space (`:5020-5022`, `dissolveSpace(true)`).
   - `dissolveSpace` (`:4270`) merges the base regions into the build's own list and marks the `direct` ones pending (`:4286-4290`).
7. **Re-resolution falls back to a copy:**
   - Main's loop re-resolves each pending region (`:5064`): the epoch differs, `findImport` finds nothing, and `importAccess` (`:5069`) is refused under the ceiling.
   - The base region then takes `copyRegion` (`:5157`).
   - **That region still carries its registered range's `writable` flag** (`:4032`, false for a range the CPU cannot write). The view that made it written has no region of its own to merge in, as `UploadPrepare`'s merge would do (`:4821`).
8. **Result: lost stores and a write-back abort:**
   - `copyRegion` keeps no reference copy (`written = region.writable && WritesOverlap(...)`, `:5226`).
   - `Descriptor` binds the copy, and the dispatch's stores land there.
   - `WriteBack` fails `Require(region.buffer != nullptr && region.writable && end <= region.end, "write-back range exceeds its GPU owner")` (`:5875`).
   - **The copy fallback the log announces does happen, but for a written view it is a read-only copy.**

## The fix (950722167b)

`GuestBufferMemory::dissolveSpace` (`:4270`), in the `resolve` branch (the dissolve `UploadFinish` makes after an import under the space was retired):

```
         for (auto& region : merged) {
-            if (region.direct != nullptr) region.pending = true;
+            if (region.direct == nullptr) continue;
+            region.pending = true;
+            region.writable = region.writable || WritesOverlap(region.begin, static_cast<std::size_t>(region.end - region.begin));
         }
```

- **Why here:** this is the one place where a space's imported region becomes the build's own and may then fall back to a copy, `UploadFinish`'s re-resolution at `:5064-5157`. At that point the views it served have left no region that could carry their writability.
- **Same as the per-build form:** writable is what the build's own form already gives the same views. `UploadPrepare` merges a view's region, always `writable`, into the registered range's region and ORs the flag (`:4821`).
- **Effect on the copy:** `copyRegion` then keeps the reference bytes (`:5226`), and `WriteBack` stores only the changed runs.
- **If the region is imported again,** it binds in place as before. Its BDA permission becomes Read|Write, as in the per-build form.
- **Mirror and snapshot regions are untouched.**
- **Not in the fix: the non-resolving dissolve** (`dissolveSpace(false)`, during registration). There, a later view that overlaps the region adds its own region and `UploadPrepare` merges it. I found no sequence where the region falls back to a copy with a written view and no region of its own, so I left that path as it was. The commit stays minimal and fully covered by its test.

## Draft PR body

Title: `fix(agc): write back a view whose space import a failed join retired`

```
### What
Resident Evil Village (PPSA01556) aborted on a Windows PC right after a joined host import failed at vkAllocateMemory ("host import of … failed at vkAllocateMemory (-2); falling back to copies, requested by join", then "host import budget lowered …"). Tracing that sequence on main shows how it breaks a written buffer view of an address-based build that hit the cached address space.

A view inside one of the space's imported ranges gets no region of its own: the space's region serves it in place. The join retires the imports of the ranges it joins before it allocates, so when vkAllocateMemory fails those ranges have no import left, and the ceiling, lowered to the live bytes after the retire, refuses a new one. UploadFinish then dissolves the space and the region falls back to a copy of the registered range. For a range the CPU cannot write, that copy is read-only, so the dispatch's stores land in a buffer that is never written back, and WriteBack fails with "write-back range exceeds its GPU owner".

The dissolve that re-resolves the space's imports now marks a region written by one of the build's views as writable, which is what UploadPrepare's merge does for a view that has a region of its own (the per-build form of the same build). The copy then keeps its reference bytes, and the stores are written back as changed runs.

Village's own abort was "guest buffer has no GPU owner" in Descriptor, which needs a view below every region of the build and of its space. I could not reach that from main's code (the trace is in the attached notes). This PR does not claim to fix it; it fixes the write-back half of the same sequence.
```
