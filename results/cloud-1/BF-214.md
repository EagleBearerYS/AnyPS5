## Part 1: the probe

### What it runs

**Run on Linux with ROCm** (HSA runtime) **or on Windows** (the driver's HIP runtime, through `oracle_hip.py`):

```
python3 tools/hw-oracle/probe_type0_store.py --json
```

**Each case:**
- runs one wave of 32 lanes, in its own child process with a time limit (60 s by default);
- assembles before the first dispatch, so a missing tool stops the probe before it touches the GPU.

**The cases run in this order**, control first:

| case | T# | access |
|---|---|---|
| `control-store` | valid 2D linear 64×1 `32_UINT` (format 20), TYPE 9, `DST_SEL` XYZW | `image_store v[30:33], v[34:35], s[8:15] dmask:0xf dim:SQ_RSRC_IMG_2D unorm` at x = lane, y = 0 |
| `type0-store` | Tamalero's words `04efd000 00040011 00017a00 00005204 0af00000 00000000 00000612 00fff000`, TYPE 0 | same store |
| `type1-store` | the same words with word 3 = `10005204` (TYPE 1) | same store |
| `control-atomic` | the TYPE 9 image | `image_atomic_add v36, v[34:35], s[8:15] dmask:0x1 dim:SQ_RSRC_IMG_2D unorm glc` |
| `type0-atomic` | TYPE 0 | same atomic |
| `type1-atomic` | TYPE 1 | same atomic |

**Options:**
- `--no-atomics` leaves out the three atomic cases, and `--case` picks cases.
- After a fault, hang or failed control, the remaining cases are reported `not run` unless `--keep-going` is given. #5828 saw a TYPE 2 T# leave the driver unusable until a restart.

**The usage text** (`--help`) carries the warning that the probe may fault or hang the GPU, the order, and the meaning of each output line.

**DIM:** the flags' `dimension 3` is the recompiler's `RdnaImageDimension::Dim2D` (`RdnaInstruction.hpp`: Unknown, 1D, 1DArray, 2D). The decoder maps MIMG `DIM` field 1 to `Dim2D` (`RdnaImageOpDecoder.cpp` `decodeDimension`). So "DIM 2D" and "the dimension the flags give" are the same encoding, `SQ_RSRC_IMG_2D` (field value 1), and one store variant covers both. The disassembly shows `F0201F08`, which is DIM field 1 and dmask 0xf.

**The base:**
- The kernel builds the T# in s[8:15] from the input buffer pointer. The base is the first 256-byte-aligned address at least 4 KiB into the probe's own buffer.
- Word 0 is replaced, and so is the low byte of word 1 (BASE_ADDRESS_HI). Words 1 to 7 otherwise keep the reported bits.
- The buffer holds dword i = `0xa5a50000 ^ i` from 3.5 KiB below the base to 60 KiB above it.

**After the access, the kernel:**
- waits for stores and atomics (`s_waitcnt vmcnt(0)`, `s_waitcnt_vscnt null, 0`);
- invalidates GL0 and GL1;
- reads back through the same T# (`image_load ... dmask:0xf glc`);
- scans the whole buffer with `glc dlc` loads, reporting per lane the count of changed dwords, the first and last changed offset and their values, the `image_load` result, the atomic's return and a completion sentinel.

**Why 32_UINT for both controls:** its unified format code is 20 on gfx1010, gfx1030 and gfx1100 (checked with `llvm-mc` on `tbuffer_load_format_x ... format:[BUF_FMT_32_UINT]`). By contrast, `32_32_32_32_UINT` is 75 on gfx10 and 61 on gfx11. `RESOURCE_LEVEL` (word 2 bit 31) is set for gfx10 targets and clear for gfx11, as Mesa does.

### Expected output

One line per case:

| outcome | line |
|---|---|
| control, as it must be | `control-store: ran; 32 dwords changed, first at base+0x0 = 5e5e0000, last at base+0x7c = 5e5e001f; image_load returned 5e5e0000 G B A`. Only the first word is checked: lane LL stores `5e5e00LL` at `base+4·LL`. The atomic control changes the same 32 dwords to the pattern plus `010000LL` and returns the pattern |
| control broken | the same line ending `; control failed`, and the probe stops, since the TYPE 0/1 lines could not be trusted |
| stores dropped (what the fix assumes) | `type0-store: ran; no dword changed in base-0xe00..base+0xf000; image_load returned 00000000 00000000 00000000 00000000` |
| stores write through the base | `type0-store: ran; N dwords changed, first at base+0x… = …, last at base+0x… = …; image_load returned …`: the fix would be wrong and the slot would need a real binding |
| fault | `type0-store: fault: the GPU or runtime reported an error (exit status S): <last stderr lines>`. With HSA, a memory violation aborts the oracle (status -6) after `Memory access fault by GPU node-…` |
| hang | `type0-store: hang: the dispatch did not finish within 5 s` (oracle.c's own limit), or `within 60 s` (the probe's limit, needed for HIP, whose `hipDeviceSynchronize` has no timeout) |
| skipped | `type1-store: not run` after a stop |

**Exit status:** 0 when every selected case ran and the controls held, 1 otherwise. `--json` adds every case's descriptor words, target and per-lane registers.

## Part 2: the fix

### What changes

- **Recompiler:** `nullImageDescriptor(const ImageResource&, const DescriptorValue&)` (`ResourceMaterializer.cpp` L83). A TYPE ≤ 1 T# in a slot with no image table is now null when the slot is read or written and not atomic (`(image.read || image.written) && !image.atomic`). Before, it had to be read and not written. Such a slot takes the path a zero-base T# already takes in a written slot: `storageMipCount` returns 1, and `inspectImageDescriptor` returns the null decode (Float, 2D, not cube) with the words unchanged. Atomic slots still throw `runtime image descriptor is invalid`, and so does TYPE 2 to 7 in any slot.
- **Driver:** `IsNullTextureResource` (`GuestTextureResource.cpp` L97) needed no change. It is a words-only test and has returned true for TYPE ≤ 1 in any slot since #5828 (`type <= 1`). The one driver change is `DrawWriteRanges` (`Execution/src/Driver/Memory/WrittenBuffers.cpp` L116), the draw path's list of the guest memory a written storage image changes. It skipped only a zero base, so a written TYPE 0/1 slot reached `DecodeTextureResource` and threw `unsupported image type 0`. It now skips `IsNullTextureResource` words, as `DispatchWriteRanges` (L71) in the same file already does.
- **Debt:** the TYPE 0/1 entry, `docs/dev/debt/libSceAgcDriver.md` L88, 982 characters. It now covers read and written static slots, says atomic slots throw, and keeps the read measurements: TYPE 0 on gfx1036 in #4139, and TYPE 1 on gfx1010 in #4139 and #5828, format 22 only. It says stores are not measured: a written slot is a null storage image, whose stores `nullDescriptor` discards, pending `probe_type0_store.py` on `test/hw-oracle-type0-store` (linked).

### How main binds a null image, and the storage paths

**How a null image is bound** (`Graphics/src/ShaderResources.cpp`):
- **On the binding path** (L4908 for storage and L4829 for sampled), an element whose words are `IsNullTextureResource` gets no allocation (`std::numeric_limits<std::size_t>::max()`).
- **When the descriptor set is written,** such an element becomes `absentImage(binding)` (L2417):
  - with robustness2 `nullDescriptor`, `VK_NULL_HANDLE`: Vulkan discards stores and reads zero;
  - without it, the heap's 1×1 placeholder image (`PlaceholderImages`, created when `!NullDescriptors()`, `VulkanDevice.cpp` L2153).
- **The placeholder is not a true null for stores:** it keeps stores, so a later read can return them. The existing debt entry at L124 already records this, for zero-base null storage images too. A written TYPE 0/1 slot now behaves exactly as a written zero-base slot already does.

**Every driver path that takes a static storage-image element, checked:**

| path | null check |
|---|---|
| binding (L4908) and stage-A precollect (L4717) | `IsNullTextureResource` |
| refresh and reuse checks (L3350, L3510) | `IsNullTextureResource` |
| deferred-compute surfaces (L5391) | `IsNullTextureResource` |
| `DispatchWriteRanges` (compute writes) | `IsNullTextureResource` |
| `DrawWriteRanges` (draw writes) | zero base only, **fixed** to `IsNullTextureResource` |
| the stencil-replay feedback check (`Graphics/src/Draw.cpp` L2666) | zero base only, unchanged (see below) |

**The stencil-replay check, a pre-existing gap:** this walks every `GuestImages` and `ImageTable` element of a draw replayed for stencil export. It decodes every element whose base isn't zero, so it throws on a TYPE 0/1 T# whether the slot is read or written. The read-only case has been reachable since #5828. A written slot now fails there the same way, so it still works the same way as the read-only null. Fixing it means replacing `words[0] == 0u && (words[1] & 0xffu) == 0u` with `IsNullTextureResource(words)` at L2666. It also touches image-table elements, so it belongs in its own change, with a case in `tests/execution/StencilNullFeedback.cpp` (whose null element has a zero base).

A static image slot (no image table) that is written, and not atomic, whose T# has TYPE 0 or 1 is now bound as a null storage image, as a read-only slot with such a T# has been since #4779, #5473 and #5828, and as a written slot with a zero base already is.
