- **How it works.** Before a draw stage or a dispatch is recorded, the driver:
  1. evaluates the program's device image uses for the stage's user data and current memory (fable-void's pre-pass, ported);
  2. names the keys with the result's interfaces and sampler classes;
  3. has `DeviceImageTable::Expect` resolve the missing keys under the GPU lock: look up, insert, hold the texture.

  The next Prepare uploads the bucket before the batch runs.
- **Rejected descriptors.** A rejected descriptor is inserted with its fault, so the batch that samples it raises the CPU path's error when it completes. LA-004's open problem 6 is fixed: the error ("invalid format", words and all) comes after the first batch, not the second.
- **Incomplete or unserved expectations** fall back before recording.
  - **Driver path:** the program goes to the CPU table path, and this draw or dispatch prepares its CPU artifact.
    - A draw stage is materialized again in place, which also works on the draw-finisher thread.
    - A dispatch is decoded again.
    - The CPU-indirect record loop materializes the record's stage again.
  - **Incomplete means:** a T# word from a lane or the workgroup id, memory the CPU can't read, or more than **16 candidate sets** (`MaxDeviceImageCandidates`, built over at most 4 rounds of phi/select expansion).
  - **Unserved means** an unservable descriptor, or a full heap or key table.
  - **Throws instead of reading zeros** in one path: a dispatch or draw recorded straight through `VulkanDevice::Dispatch`/`Draw` with a result from `Recompile(request)`, whose expected key the table can't serve. Nothing there can recompile.
  - **A `Recompile(request)` result** whose expectation is incomplete is recompiled for the CPU table instead.
- **`missWaits` is never correct for one-shot work.** fable's a0080950f finishes the previous batch with unnamed uses before recording the next one, so the dispatch that first selects a key still reads zeros. It only helps later uses within a submission, at the cost of a GPU sync each. It is not ported: an incomplete expectation takes the CPU table path instead.
- **Steady state is near free.** A per-thread memo per (plan, program, user data) keeps the words the pre-pass read and the state they were read in.
  - **Fast path:** while the collect epoch and the write serials haven't moved, the keys are taken without reading memory.
  - **Otherwise** the words are read again and compared.

## Open problems

1. **Draws outside the recorder** still don't serve device tables. This is why `image_table`'s graphics part and the six `heap_draw_sample` variants fail with the switch on.
   - `image_table` draws through `VulkanDevice::Draw` into a non-resident target, so its draw goes synchronous.
   - The driver path never reaches this, but a game draw with a non-resident target would throw the same error.
2. **Copy mode (`APS5_NO_HOST_IMPORT=1`) on the bench is already broken on the base.**
   - Every draw builds its resources (32,000 builds), including a 1.5 MB copy of the V# table, about 210 µs of guest read per draw.
   - lavapipe `memfd:allocation` mappings grow by about 5,000 per second, about 2 per draw. The stack runs through `DescriptorCache::Allocate` in `ShaderResources::buildPrepare`.
   - At the kernel's 65,530 map limit lavapipe segfaults in a memset, after about 12 s of steady frames.
   - Seen on b63fa365d itself with a 12 s window (SIGSEGV), and on the head. It now shows on the device path because copy mode no longer falls back.
3. **N=32 with imports costs about 10 µs more per draw than the base**, of which the expectation phase measures 4.3–4.9 µs. The rest is unexplained.
4. **`bindless_images` fails differently.** On the base it fails at "bindless shader has no image table map"; on the head, a step earlier, at "bindless table changed the compiled artifact".
   - Iteration 0's expectation is complete with no images; iteration 1's is incomplete, so the direct `Recompile(request)` takes the CPU table (variant 1, then 3).
   - The test asserts CPU-table behaviour in both cases. The direct-path choice is per request; the driver's fallback is per program and sticky.
5. **The memo keys on all of a program's user data.** A draw whose user data changes every draw, for example constants, misses it and pays about 14 µs per expectation on this bench.
6. **A guest write to a T# record between the expectation's read and the GPU's read**, in the same collect epoch, is not seen. The miss ring stays as the safety net.
   - Part (i)'s "rewritten after the draw was decoded" case read the new texture with 0 misses here.
   - No miss happened in any expectation-on run of this task (harness, one-shot, bench cold and steady), so there's no miss to report as a bug with its pc. With the kill switch, misses happen by design.
7. **`APS5_NO_DEVICE_IMAGE_EXPECT=1` is new**, so that (j), (k) and (l) keep testing the miss ring and its dedup. The miss-ring parts need it.
