### 2. d214fad61a: which lock serialises the space hand-off

For the PR description:

> `GuestBufferMemory::RetakeSpace`, `ReleaseSpace` and `SpaceHeld` read and write `space` and `releasedSpace` on a `ShaderResources` that `SharedResourceCache()` shares. Every call is inside `Graphics::Draw`:
> - `resolveDrawResources`;
> - `keepRecordedDraw`;
> - the transition path's rebuild in `prepareDraw`;
> - the `HeldSpace` cleanup.
>
> The lock is `GuestMemory::GpuMutex()`. The driver reaches `Graphics::Draw` only through `VulkanDevice::Draw` (`Execution/src/VulkanDevice.cpp:4391`), and every call to that holds the mutex:
> - **Inline draws:** `Driver::finishDraw` (`Execution/src/Driver/Draw/Draw.cpp`) calls `lockForDraw()` first. That function locks a `std::unique_lock` on `GuestMemory::GpuMutex()` (lines 1088–1093).
>   - It does so before the indirect inline draw (1205, then 1208) and before the direct one (1260, then 1273).
>   - With `APS5_LOCKED_DRAW_PREPARE`, the same lock is taken at line 372, and `lockForDraw` sees it is held.
> - **Pipelined draws:** `Driver::commitDraw` runs these, from the queue-0 draw committer and the draw finisher. It takes `std::lock_guard gpuLock(GuestMemory::GpuMutex())` at line 1283, before `localDevice->Draw` at 1299.
>

> - **The recipe path** (`DrawFromRecipe` → `Graphics::DrawWithRecipe`): no recipe is made from a space-reuse build, because the recipe condition in `recordPreparedDraw` requires `!resources->SpaceReuse()`.
> - **The dispatch path:** `spaceReuse` is set only for draw builds (`drawBuild` in `ShaderResources::noteReusable`).

### 3. 86b29f0d72: `APS5_VERIFY_ADDRESS_DRAW_REUSE`

With the switch on, every hit that is about to be served runs `verifyServedSpace` in `resolveDrawResources`. A hit here is a counted read-only space reuse; the check runs after the moved-buffer proof and before the hit is handed on.

- **What it does:** it builds the draw's resources anew from the same stages, colour target, index range and snapshots, as a miss would. It stops on the first of these that fails:
  1. **space reuse:** the fresh build must be a space-reuse build itself, which means space-only and read-only, so it copies no snapshot.
  2. **BDA table:** the BDA page table bytes (header and ranges) must equal the hit's (`ShaderResources::AddressTableBytes`, `BdaResources::TableBytes`).
  3. **snapshot ranges:** every snapshot must lie in readable (`BdaAbi::Read`) ranges of the hit's table.
  4. **snapshot bytes:** every snapshot must equal guest memory. This is compared directly, not through the hit's own `SnapshotsServedInPlace`.
  5. **sampled textures / storage images / set layouts:** these must be the same `Texture` objects, the same storage images with their written flags, and the same set layout keys.
- **How it stops:** like `APS5_VERIFY_DRAW_DATA_HITS`, it throws a `std::runtime_error`: "APS5_VERIFY_ADDRESS_DRAW_REUSE: a served address-based draw hit disagrees with a fresh build or guest memory in its <what> (BDA table N bytes served, M fresh; a / b sampled textures; k snapshots)". `AddressDrawReuseVerifications()` counts the verified hits.
- **Why it is enough:** a served hit binds the cached build's descriptor sets and BDA table, and reads its snapshots in place through that table. The checks make sure of three things:
  - the table is the one a fresh build would make now;
  - every snapshot can be read through that table and holds the bytes the stages were decoded from;
  - the fresh build has nothing to copy.
  Textures, storage images and layouts cover the rest of a fresh build's bindings for these draws.
- **What it doesn't cover:**
  - **Buffer descriptors** (each binding's `VkDescriptorBufferInfo`) aren't compared. A moved read-only buffer is rebound at record time by `MovedReadOnlyBuffers`, and the verifier doesn't repeat that proof.
  - **Push constants** aren't compared; they always come from the draw's stages.
  - **What the GPU reads later:** state is checked when the hit is taken. Writes after recording are the recorder's hazard tracking.
  - **Texture contents:** textures are compared by identity. Whether the contents are current is still `Revalidate`'s job.
  - **Shared bugs:** a bug that affects the fresh build and the hit alike, for example in `AddressRanges`, isn't caught. Checks 3 and 4 don't depend on that code.
  - **Cost:** it does a full build per hit, so it is a diagnosis switch. The fresh build takes a BDA fault slot and descriptor sets, and is dropped unrecorded, like a draw that throws before recording.
- **Docs:**
  - A row in `docs/dev/ENVIRONMENT.md`, just before `APS5_VERIFY_BDA_TABLES`. `env_reference.py --check` reports 0 undocumented; its one stale row, `APS5_PAD_SPEAKER_FALLBACK_DB`, is already stale at 7122193668.
  - One sentence in the debt entry.
- **Green:** `agc_driver_address_draw_space_reuse_verify` runs the default cases with the switch on, and requires every served hit to be verified (`verified == reused != 0`).
  - The tests' `Builds()` subtracts the verifications, since each fresh build makes one table.
  - It passed ×10 as one of the 12.
- **Red:** there is no clean red to commit, because the code has no test seam that serves a stale hit without a production knob:
  - The hit's proof covers everything a test can change: space identity, import epoch, registry generation, snapshot containment and bytes, textures and moved buffers.
  - A fresh build serves a changed live snapshot from memory too; `AddSnapshot` only logs the mismatch. That is why checks 3 and 4 are independent.

  So the red is a local, uncommitted mutation: `SnapshotsServedInPlace` loses its byte compare, and `--case counters` runs, which serves draws whose snapshot differs from memory.
  - **Switch on:** exit 1, "… in its snapshot bytes (BDA table 240 bytes served, 240 fresh; 0 / 0 sampled textures; 2 snapshots)". This was captured with the first wording of the message ("differs from a fresh build in its"); only the wording changed after it.
  - **Switch off:** the stale hits are served, and only the case's own counter check notices: "draws with a snapshot that differs from guest memory counted reused 2 for 2 draws, expected snapshot changed 2".
- **Found while writing it (not fixed, outside the four points):** the hit doesn't re-check `MultisampleTargetRangeGeneration()`.
  - A cached build keeps the BDA table it was built with. That table's exclusion of multisample targets is keyed by the guard generation of that time: `BdaResources(context, memory)` keys space tables by `(serial, guardSerial)`.
  - When a new resident multisample target inside the space bumps the generation, a hit still binds the old table. A fresh build would exclude the new target's ranges.
  - The verifier's table compare reports this. I didn't reproduce it, since that needs a resident multisample target inside the space.
  - **Possible fix:** keep the guard serial in the build, and refuse the hit as "space or epoch change" when the serial has moved.

### 4. 8a85451640: the `HeldSpace` cleanup no longer throws or allocates

**Can the open batch change between the retake and the recording?** Yes:
- `completeSnapshotWrites`, right after `RetakeSpace` in `resolveDrawResources`, calls `Recorder::SyncThrough` for a pending write over a snapshot. The `pending-snapshot-write` case reaches this.
- `RetakeSpace`'s mirror refresh can call `Recorder::Sync` (`syncRange`).
- `prepareDraw` syncs for the indirect arguments.

So a keep reserved when the hit is taken could sit in a batch that completes before the draw's commands do.

**The design:**
- **A recorded draw:** it reserves the keep through the ordinary, checked `Recorder::Keep` once it holds the command buffer it records into. On the lean path that is right after `StartDrawPass`; on the other recorded path, right after `Recorder::Commands()`.
  - The reservation is a `shared_ptr<shared_ptr<const void>>` holder that the batch keeps.
  - From that point to `keepRecordedDraw`, everything records into that one command buffer, so the batch can't change in between.
  - `keepRecordedDraw` moves `ReleaseSpace()` into the holder. That's a noexcept move, where it used to call `recorder.Keep(...)`.
- **Every other way out of `Draw`** (an early return, an exception during preparation, an exception during recording before the reservation): `Draw` reserves the holder in ordinary code, then rethrows.
  - This is `keepHeldSpace`, called after `prepareDraw`/`recordPreparedDraw` and in `catch (...) { keepHeldSpace(prepared); throw; }`.
  - It reserves in the batch open at that point. That batch holds whatever preparation recorded, and completes after every earlier batch.
  - An allocation failure here propagates normally. From the catch handler it replaces the in-flight exception.
- **The cleanup** releases a space the draw still holds and moves it into the holder, with noexcept moves only.
  - If no holder could be reserved, it leaves the space with the build and records the recorder's open serial (`HoldSpaceThrough(OpenSerial())`), a plain integer, without allocating.
  - The next hit on that entry calls `ReleaseCompletedSpace(CompletedThrough())`. It gives the space back once that serial has completed, and until then refuses the entry as "in use".

**Why the backing memory stays alive in every case:** the space owns the `GuestAllocations::Lease` that pins the guest allocations.
- On a recorded draw, and on any failure after a reservation succeeded, the lease sits in a holder kept by a batch that completes no earlier than every command the draw recorded.
- If every reservation failed, the build itself keeps the lease until the recorder has completed the serial that was open at the failure.

**The cost and the limit of that fallback:**
- A guest free inside such a space waits for the pin until a later hit gives the space back. If no hit comes within `APS5_PIN_WAIT_MS`, the free throws its "still pinned" error.
- If the cache entry is replaced before then, the space goes with the build. That only matters when the space has also been replaced, since a fresh build in the same space holds its own reference.
- All of this happens only after an allocation failure in the ordinary keep.

**Red and green, local and uncommitted:**
- **Standalone probe,** host g++ 13.3 and libstdc++, with the exact old and new cleanup bodies and a `Recorder::Keep` that throws `std::bad_alloc`:

  | mode | old cleanup | new design |
  |---|---|---|
  | unrecorded early return | exit 134, "terminate called after throwing an instance of 'std::bad_alloc'" | exit 0: `bad_alloc` from the checked reservation reaches the caller; space held by the build through the serial |
  | exception during preparation | exit 134, same | exit 0: `bad_alloc` from the checked reservation in the catch handler reaches the caller; space held through the serial |
  | recording | exit 134, same | exit 0: `bad_alloc` reaches the caller; space held through the serial |
  | no failure | n/a | exit 0: returned; space released into the batch-kept holder |

- **In-tree probe:** a throwing `Recorder::Keep` is armed right after one hit's retake (a one-shot hook), and the reuse test gets a `--probe` mode.
  - **Old code:** C++ exceptions in this test binary go through AnyPS5's own runtime (`__cxa_throw_nid_postfix` in `libc.prx`). That runtime didn't end the process when the old cleanup threw, which is a finding in itself; the standalone probe above is the SIGABRT red.
    - Early return: `std::bad_alloc` escaped the cleanup. gdb shows the throw in `Recorder::Keep` called from `Graphics::Draw`'s cleanup.
    - Exception during preparation: the cleanup's `bad_alloc` replaced the preparation exception.
  - **New code, all three modes:**
    - The draw's `bad_alloc` comes from the checked keep and reaches the caller.
    - The next draw counts "in use 1": the space is held through the serial.
    - The two draws after that count "reused 1" each: the serial completed and the space was given back.
    - Teardown is clean (exit 0).
- **No committed failure-injection test:** the reviewer called it optional, and a throwing `Keep` would need a production test hook.
