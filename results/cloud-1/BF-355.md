## 5. #7261's semantics for our space-reuse PRs

Line numbers are at the §4 local merge **f0535e2390** (c674f8c14d + #13858's 023b4a26d8), for both `Graphics/src/ShaderResources.cpp` and `Graphics/src/GuestBufferMemory.cpp`.
- #7642's merge has the same code, offset by its own changes.
- On main alone, `GuestBufferMemory.cpp`'s functions sit about 135 lines earlier, because #13858 changes the file: `HostImportsUnchanged` at 6709, `HostImportsReconciledUnchanged` at 6716, `++state.inserted` at 2273, `refreshImports` at 2323, `importsStale` at 2446.

**The two checks** (`GuestBufferMemory.cpp`):
- **`HostImportsUnchanged` (6844–6849)** passes when all of these hold:
  - the proof's device is the context's and the table's;
  - `state.epoch == proof.epoch`;
  - `state.refreshedGeneration == proof.refreshedGeneration`;
  - `!importsStale(context, state)`. That is, the live registry generation equals `state.refreshedGeneration` (2449–2451), so the registry hasn't changed since the proof at all.
- **`HostImportsReconciledUnchanged` (6851–6858)** first refreshes the table if the registry generation moved (`refreshImports`, 2326). It then passes when `state.epoch == proof.epoch && state.inserted == proof.inserted`.

**Not only stricter.** The two differ in both directions:
- **`HostImportsUnchanged` is stricter on registry changes.** Any registry change fails it, even one whose refresh retires nothing. The reconciled check survives that: `refreshImports` bumps `epoch` only when it retires an import (463), or on a device change (2362).
- **`HostImportsUnchanged` is looser on new imports.** A plain new import increments `state.inserted` (2276), but bumps `epoch` only on the join path, when the run didn't exist before (2023). It doesn't change `refreshedGeneration`, which only `refreshImports` sets (2368).
  - So after a non-joined import made with no registry change, `HostImportsUnchanged` still passes, while the reconciled check fails on `inserted`.
  - #7261's own test pins that case: `tests/execution/HostImportProofs.cpp:115`, "a new import kept the proof".

**For a space-reused object, the choice doesn't change any outcome:**
- **`directRegions` stays empty.** `noteReusable()` clears it (`ShaderResources.cpp` 2685) and returns at 2690–2694 (`if (spaceReusable) { spaceReuse = true; reusable = true; return; }`), before the only `directRegions.push_back` (2707). Nothing else adds to it: its other uses, 3643, 3831, 3847 and 3863, only read it.
- **The check only decides whether `serialLoop` runs.** In `revalidateFull`'s step (2), the check at 3856 does nothing else:
  - when it passes, `importSkips` is counted (3857);
  - when it fails, `serialLoop()` runs (3858) and `importsProof` is re-taken (3860).
- **The serial loop has nothing to check.** `serialLoop` (3830–3841) iterates `directRegions` only. With it empty, it returns true, so step (2) never fails for a space-reused object whichever check is used.
- **The pending-image flush doesn't read the check.** It runs before the check, over `directRegions` and `guestMemory.Writes()` (3843–3854), and is the same either way.
- **What does depend on the choice:**
  - the `importSkips` profile counter;
  - whether `importsProof` is re-taken. It starts empty, so the first revalidation always fails the check, runs the empty loop and takes it.
- **Where the space-reused object's protection is:** in the space-reuse checks (`spaceReuse` at 5689, 5814, 5975), not in step (2).

**So keep-both is safe for #7642 and #13858.** A space-reused object loses nothing by using `HostImportsUnchanged`. The looser direction can't let a stale import through, because such an object reads no import directly.
