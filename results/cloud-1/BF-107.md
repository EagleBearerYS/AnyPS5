## 1. Where the hooks live and what they cover

**Why not a replacement `operator new` in the executable.** There is no host executable of ours on Windows to put one in:
- The game process's `.exe` is the relinked title. Its entry stub is generated code (`WindowsEntryStubBuilder`), and it loads the host `.prx` DLLs.
- On MinGW the DLLs link libstdc++ dynamically: `core/libs/CMakeLists.txt` drops `-static-libstdc++` for everything under `core/libs`. So `operator new` in each DLL is `libstdc++-6.dll`'s.
- The AGC driver defines its own (`Execution/src/HostAllocator.cpp`, a per-thread cache over `std::malloc`).
- Windows has no symbol interposition, so a replacement in one module never sees another module's allocations. Both kinds of `operator new` end in `malloc` through each module's import table.

**Windows: covers `operator new` and `malloc`/`calloc`/`realloc`/`free` alike.** Code in `core/libs/prx/libc/src/BigAllocations.cpp`, inside `libc.prx`, the first host module every game loads.
- **What is patched:** with `APS5_PROFILE_BIG_ALLOCS` set, a reporting thread started from libc's static initialiser patches the import address table of every loaded module outside the Windows directory, for these functions:
  - `malloc`, `calloc`, `realloc`, `free`, `_aligned_malloc`, `_aligned_realloc` and `_aligned_free`;
  - `LoadLibraryA`/`W`/`ExA`/`ExW`, so a module loaded later is patched as soon as its load returns.
- **Coverage:** that includes `libstdc++-6.dll` (every `operator new` and `delete`), the AGC driver's own allocator, the `.prx` DLLs and the game `.exe`.
- **Install timing:** the thread starts from libc's static initialiser but runs only after the loader lock is released. Nothing is patched while the loader holds it.
- **Re-scans:** every 10 s. A slot the loader has not bound yet (its value is not inside a loaded module) is left for the next scan.
- **Originals:** one original per function name, taken from the first bound slot. A module whose slot points at a different CRT is skipped for that function.
- **When the variable is unset:** nothing is patched and no thread starts. The only cost is libc's one `getenv` at load.
- **Not covered:**
  - direct `HeapAlloc`/`VirtualAlloc` calls;
  - allocations a module made before its import table was patched (their frees are ignored);
  - modules under `C:\Windows` (the Vulkan loader, the NVIDIA driver).
- **mimalloc:** with `APS5_MIMALLOC` set, mimalloc's redirect sits behind the patched slots, so it is counted the same way. The census runs used the NT heap.

**Linux: `operator new` only, in the executable that wants it.** libc hooks nothing.
- An executable defines the replacement `operator new`/`delete` forms itself, calling `BigAllocationsNote_nid_no_patch(block, bytes)` and `BigAllocationsForget_nid_no_patch(block)`. Only `big_allocation_sites_tests` does (`core/libs/tests/BigAllocationSites.cpp`).
- The forms must stay out of line (`[[gnu::noinline]]`). The note drops its own frame and its caller's, the `operator new`, so the first frame is the allocating code. GCC inlined the replacement into the test function before I marked it, and the stack began one frame too high.
- The relinked Linux title has no such executable, so a Linux boot gets the reporting lines but no records.

**The tracker** (both platforms):
- **Threshold:** blocks of at least 512 KiB.
- **Stack:** up to 16 return addresses, from `CaptureStackBackTrace` on Windows and `backtrace` on Linux, captured before taking the tracker lock.
- **Storage:** records go in a side table keyed by address; nothing is added to the blocks. Records are aggregated by stack.
- **Free path:** a 64 K-bucket counter filter means a `free` of an untracked block takes no lock.
- **Recursion:** allocations the tracker itself makes while holding its lock are not recorded (it compares an owner thread id; no `thread_local`).
- **Report:** formats module names (`GetModuleHandleExW` with FROM_ADDRESS and UNCHANGED_REFCOUNT plus `GetModuleFileNameW`, or `dladdr`) after releasing the lock. A thread inside the loader that allocates a big block therefore cannot deadlock against it.
- **At exit:** the report waits at most 2 s for the lock. On Windows a DLL's `atexit` runs after the process has ended its other threads, which may have held it.

## 2. Line format

All lines go to stderr, 10 s apart and once at exit.

```
[bigalloc] hooked <N> heap and LoadLibrary import slots in: <module> <module> ...        (Windows, when modules are patched)
[bigalloc] (<10 s|exit>) live <MiB> MiB in <n> blocks; since the last line +<n> blocks <MiB> MiB allocated, -<n> blocks <MiB> MiB freed; <n> stacks, <n> stale; hooked <n> import slots in <n> modules
[bigalloc] #<rank> live <MiB> MiB in <n> (+<allocs> -<frees>) sizes 1MiB <n> 2MiB <n> other <n> frames <module>+0x<offset> ... (up to 16)
[bigalloc] #<rank> newest 0x<address> (<bytes> bytes): <qword> x 8      (ranks 1-3: the first 64 bytes of the stack's newest live block, as 8 little-endian qwords)
```

- **Ranks:** the 12 stacks with the most live bytes.
- **`+allocs -frees`:** counted since the previous line.
- **`sizes`:** live blocks whose requested size is within 64 KiB below 1 MiB, within 64 KiB below 2 MiB, or neither.
- **`stale`:** records dropped because a new block came back at a still-recorded address, meaning its free went around the hooks.
- **Frames:** return addresses, as module basename + offset from the module's load base.

## 3. Resolving frames

`tools/resolve_bigalloc.py [log] --search <dir> [--search <dir> ...] [--module NAME=PATH] [--addr2line TOOL] [--nm TOOL]`:
- It reads the `[bigalloc]` stack lines from the log or stdin.
- It finds each module by name in the search directories, searching recursively if needed.
- **Address:** it adds the image base to the offset (the PE `ImageBase`, or the lowest `PT_LOAD` of a non-PIE ELF, else 0) and subtracts 1 to land in the call instruction.
- **Lookup:** it runs `addr2line -f -C -e <module>` on all the module's addresses in one call. It prefers `x86_64-w64-mingw32-addr2line` for PE files when one is on PATH.
- **Fallback:** where addr2line gives `??`, it falls back to the nearest text symbol from `nm -C --defined-only`.
- **Output:** each stack line, followed by one `    <frame>  <function>  <file:line>` line per frame.

On the PC, from an MSYS2 MinGW shell, point `--search` at the directory holding the `.prx` files and `libstdc++-6.dll` the run actually loaded:

```
python3 tools/resolve_bigalloc.py run-stderr.log --search <dir with the loaded .prx files and libstdc++-6.dll>
```

The same by hand for one frame `libSceAgcDriver.prx+0x1a2b3c`:

```
objdump -p libSceAgcDriver.prx | grep ImageBase                 # e.g. 0000000180000000 (sizes vary per module)
addr2line -f -C -e libSceAgcDriver.prx 0x18001a2b3b             # ImageBase + offset - 1
nm -C --defined-only libSceAgcDriver.prx | sort | less          # nearest symbol at or below that address, if addr2line prints ??
```

On Linux: `python3 tools/resolve_bigalloc.py log --search build/tests`. The address is offset − 1 for PIE executables and shared objects.

## 6. Candidates that could reach 1 MiB or 2 MiB blocks and keep growing at a static scene

**Size rule:** with libstdc++, `push_back`/`emplace_back` grow to powers of two. A vector of 8-byte elements becomes a 1 MiB block at 131,072 capacity and a 2 MiB block at 262,144; 16-byte elements at half those counts.

**Shape matches for the census classes** (checked in the code):
1. **2 MiB "first two qwords point at other allocations": the readable lease.**
   - `GuestAllocationsAcquire_nid_postfix`, `libc/src/GuestAllocations.cpp:634-643`.
   - A `vector<shared_ptr<const Range>>` built by `push_back` with no `reserve`. It is exactly 2 MiB for 65,537–131,072 readable ranges, and its first two qwords are a `Range*` and its control block.
   - Rebuilt on the first acquire after any registry change, and every guest malloc registers a range.
   - Held by `registry().readableLease`, `AddressSpace::lease` and `GuestBufferMemory::lease` (`Graphics/src/GuestBufferMemory.cpp:102`, `3871`; dropped in `WriteBack`, `:5460-5462`). A generation stays alive while anything holds its AddressSpace.
   - Caveat: a held lease also pins its ranges, and a guest free of a pinned range waits up to 60 s and then throws (`GuestAllocations.cpp:396-425`). A plain leak of leases would show `[gpu] leased allocation … still pinned`.
   - Note: the census's view of "the first two qwords" may be the NT large-block header's list links, which every large block has.
2. **1 MiB "table of guest addresses": `AddressSpace::directReads`.**
   - `Graphics/src/GuestBufferMemory.cpp:96-128`, built at `:3866-3895`.
   - Guest begin/end pairs grown by `emplace_back`: exactly 1 MiB for 32,769–65,536 direct regions.
   - `AddressSpace::ranges` (32-byte `BdaAbi::Range`) is 1 MiB at 32 K entries and 2 MiB at 64 K.
   - One AddressSpace per registry generation. `directReads` is also kept by recorder batches (`NotePendingReadList`, `Recorder.cpp:3160-3171`) until the batch finishes.

**Hosts that can hold many of them, or grow on their own:**

3. **ResourceCache templates.**
   - `Graphics/src/ShaderResources.cpp:3788-3826`. Capacity `InitialEntries` 1024 → `MaximumEntries` 16384 (`ShaderResources.hpp:711-712`).
   - Each entry keeps a whole `GuestBufferMemory` (snapshots, uploads, writes, and the lease and space above).
   - Reusable templates complete with `CheckFaults`, not `WriteBack` (`VulkanDevice.cpp:4882-4885`).
   - Cross-check: `[rescache] … entries` and the "capacity A -> B" messages.
4. **Shader recompiler caches, never evicted:** `Recompiler.cpp:448` (sources, each with a 256-entry result memo), `:880` (registration modules), `:930` (prepared binding plans keyed by descriptor dwords) and `:959` (specialised modules). No counter today.
5. **Dispatch and draw caches.**
   - `DispatchCache.cpp:22-53` (up to 8192/16384 entries × 4 variants) and `DrawCache.cpp:59-65` (4096).
   - The 256 MiB budget's `variantBytes` counts only words, shared, runs and headers. It leaves out ShaderMemory pages, compiled results and the data patch vectors, so `[dispatch-cache] … MiB` understates.
6. **`copiedWriters` and `DrawCopiedWriters`** (`VulkanDevice.cpp:431`, `4889-4898`; `Draw.cpp:847-850`, `1683-1692`). Each entry keeps a `ShaderResources` alive until its batch's completion runs.
7. **`DecodeMemo`** (`ResourceMaterializer.cpp:1537-1566`): grows to 2^20 entries before `clear()`, which keeps the bucket array. This is small nodes, and shows as NT heap segments rather than large blocks.
8. **`labelStores`** (`Driver.hpp:411`, `LabelHistory.cpp:9-19`): one entry per label dword address, never erased.
9. **`drawRelocations` / `drawRelocationTrials`** (`Driver.hpp:381`, `384`; `DrawRelocate.cpp:172`): never erased. Only `drawAliases` is capped, at 16384.
10. **WindowsMappings** (`libc/include/WindowsMappings.hpp`): `physical` (`:1015`), per-16 KiB `views` (`:1004`) and `SharedPage::aliases` (`:519`).
    - The temporary `found` in `collectResident` (`:599`) is an exact shape match: 1 MiB for a 512 MiB resident run, 2 MiB for 1 GiB, holding guest page addresses. It is freed on return, so it is not a leak by itself.
11. **GuestMemory WriteTracker** (`Execution/src/GuestMemory.cpp:862`, `889`, `980-981`): a 512 KiB page-address vector allocated once, plus `cpuPages`/`walkPages`, which are never erased.
12. **StorageTexture host copies** (`Graphics/src/Texture.cpp:2411-2412`, `2475`, `2491-2494`): 1 MiB for 512×512 RGBA8 and 2 MiB for 1024×512, alive as long as the texture. The texture cache's budget counts only Vulkan bytes.
13. **Recorder batches** (`Recorder.hpp:546-674`): per-batch `writes`, `reads`, `readLists`, `kept`. `holdKept` grows over one GPU hold (`Recorder.cpp:2692-2704`).
14. **BufferFill per-thread block** (`Driver/Memory/BufferFill.cpp:414-417`): 1 MiB per thread on the CPU fill path. It leaks only if threads churn.
15. **ShaderRegistry `ReadRawShader`** (`ShaderRegistry.cpp:106-145`): the code vector can double to 1 MiB, and the cache counts `size()`, not `capacity()`.

**Bounded or opt-in, so unlikely:** SnapshotCopies (16 MiB), BDA TableCache (8), `writtenBack` (16384), lookup log (1024), the env-gated trace rings.

**Already printed every 10 s under `APS5_PROFILE_DRAW`, for cross-checking the stacks:** `[address]` (space rebuilds by generation), `[rescache]`, `[dispatch-cache]`, `[draw-relocate]`, `[descriptors]`, `[recorder]`, `[bufferpool]`, `[guestmem]`.

**No counter today:** 4, 7, 8, 10. Their `size()` every 10 s would settle them quickly.

Candidates 3–15 come from a read-only code sweep; I opened 1, 2, 3, 8 and 10 to confirm the lines.
