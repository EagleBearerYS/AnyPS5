## 1. The change

In `Driver::tagVariantRuns` (`Execution/src/Driver/Draw/DrawRelocate.cpp`), just before the region loop:

```cpp
std::size_t total = 0;
for (const auto& region : regions) total += region.bytes.size() / sizeof(std::uint32_t);
variant.words.reserve(variant.words.size() + total);
if (relocatable == 0) variant.runs.reserve(variant.runs.size() + regions.size());
```

Nothing else changes: same words, runs, run bases and shared entries in the same order. Only capacities differ.

### Per vector

| Vector | Filled where | Final size known before the fill? | Done |
|---|---|---|---|
| `words` | `tagVariantRuns`, one `resize` + `memcpy` per region | Yes: the sum of the regions' word counts, on both paths | **Reserved** to `size + total` |
| `runs`, `relocatable == 0` | `tagVariantRuns`, one `emplace_back` per region (empty regions included) | Yes: `regions.size()` | **Reserved** to `size + regions.size()` |
| `runs`, relocatable path | `tagVariantRuns`, one run per change of `origin()` along each region's words | No. It takes the same per-word `origin()` binary search as the fill itself, so it is not a cheap count. | Left |
| `runBases` | relocatable path only, one per run | No, as for those runs | Left |
| `shared` | `AppendSharedWords` (`ShaderMemory.cpp:710`) | No. It pushes only for regions inside a supplied `SrtGuestWords` block, and merges an adjacent one into the previous entry. `regions.size()` is only an upper bound. | Left |
| `dataPositions`, `dataSlots` | `recordStageDataPositions` → `DataWordPositions` (`ShaderMemory.cpp:796`) | Already exact: `DataWordPositions` clears them, then `reserve(found.size())` before pushing (`ShaderMemory.cpp:829-830`). `recordStageDataPositions` then compacts out decoded positions with `resize(kept)`, which keeps that capacity. | Left. A `shrink_to_fit` there would be a shrink, not a reserve, and costs a reallocation. Draw variants with decode reads only. |

## 2. Measured per variant

Measured on the new test's draw, with a scratch `fprintf` in `accountDrawVariant` that was not committed.

### The draw

- One draw over the `WideStride` table: 32,768 records, stride 48, 32-byte T# records, 16-byte gaps.
- The pixel stage reads a lane-indexed T# (`v_mbcnt_lo` → `v_readfirstlane` → `s_mul_i32 48`), so the table goes through a materializer column (`columns 1`, 262,144 words read).

### It differs from BF-108's figures

- On this base (BF-108 rebased on main `fce8ecf162`), the column reads only the records' words. So the variant holds **32,897 regions**: one per record, plus records split at a page boundary, plus the SRT.
- BF-108's figure was 385 page regions covering the whole 1.5 MiB span. BF-108 measured on `8aa9d0a44`, before the rebase. I did not trace which main commit changed the capture.
- Each region becomes a run on the **relocatable** path (`relocatableWords 0x1`: the SRT pointer).

| Pixel variant | `words` size / capacity | `runs` | `runBases` | `variantBytes` |
|---|---|---|---|---|
| base `8d814ebbd4` | 262,152 / **524,288** | 32,897 / 65,536 | 32,897 / 65,536 | **3,211,616** |
| head | 262,152 / **262,152** | 32,897 / 65,536 | 32,897 / 65,536 | **2,163,072** (−1,048,544, −32.6%) |

- The vertex variant is 1,400 B in both (`sizeof(DispatchVariant)` 352 + `ShaderVertexStageInfo` 1,048).
- The test's other draw is `SrtMovingPerDraw`'s 2 MiB table, records back to back. Its `words` go from about exact (524,296 in 524,304) to exact (524,296 in 524,296). That case has 513 runs at capacity 1,024, also on the relocatable path.

### What is left on this draw

- **The relocatable path.** `runs` and `runBases` still hold 65,536 for 32,897 entries: 32,639 × 17 B = 554,863 B, about 26% of the head variant.
- **An exact count costs a second `origin()` pass over every word.** That pass is what the fill does itself, so I left it, as the task said.
- **A cheap upper bound exists.** On the relocatable path, each region gives one run, plus at most two more for each relocatable user-data read inside it. So `regions.size() + 2 × (reads with a relocatable origin)` bounds the count. Reserving that would over-reserve by at most 34 B per such read.
- **Measured (scratch, not committed).** That reserve on top of this head:
  - the wide variant: **1,608,481 B** (runs and bases 32,897 in 32,913, from 8 tagged reads); another −554,591 B, −50% against base;
  - the 2 MiB case: 2,106,529 B (runs 513 in 529).
- **Not in this commit.** The task asked to leave the relocatable path unless an exact count was cheap. It is a separate decision: it reserves an upper bound, not an exact count.

## 3. The test

**Where.** `WideTableDrawVariant` in `tests/execution/ImageTableCacheBounds.cpp`. It runs in the no-argument invocation (ctest `agc_driver_image_table_cache_bounds`, no new name), between `SrtMovingPerDispatch` and `SrtMovingPerDraw`. At that point the draw cache is empty.

**What it does.**
- Writes the 32,768 stride-48 records, all pointing at surface 5, with the gaps filled with `0x5a`.
- Writes a pixel shader at offset 1024: `TablePixelCode` with `s_lshl_b32 s16, s16, 5` replaced by `s_mul_i32 s16, s16, 48` (`0x9310b010`, the word `WideTableCode` uses).
- Puts the heap V# in key 0's SRT.
- Draws key 0 twice; a key is inserted on its second sighting.
- `Draw` gained a `pixelOffset` parameter, defaulting to `PixelOffset`.

**What it requires.**
- The brightest colour is 5.
- One insert and one entry.
- `DrawCacheSize().variantBytes <= bound`, where:
  - `captured = 32,768 × 32 + 32` = 1,048,608 B: the records' words plus the SRT's V# and S#;
  - `regions = 32,768 + 32,768 × 48 / 4096 + 1` = 33,153: one per record, at most one more per 4 KiB page for a record split at a page boundary, plus the SRT;
  - `perRegion = sizeof(run) + sizeof(run base)` = 17 B.
  - So `bound = captured + 2 × regions × perRegion + 2 × sizeof(DispatchVariant) + sizeof(ShaderVertexStageInfo)` = **2,177,562 B**.

**Why that bound.**
- The variant's parts besides its words are:
  - one run and one run base per region. On the relocatable path these grow by doubling, so their capacity is at most twice their count;
  - two `DispatchVariant` objects;
  - the vertex stage info.
- The words themselves must cost no more than their size.
- With doubling growth on `words` (the base), it adds 1,048,544 B, about 80 times the bound's 13,090 B margin over the head figure.
- With MSVC's 1.5× growth (not run), the head would sit about 288 KB under the bound. The red's `words` slack would land anywhere from 0 to 524 KB, so the red may not show on Windows.

**Red.**
- Setup: on `8d814ebbd4` with only the test hunk; the `DrawRelocate.cpp` reserve reverted.
- Result: **20 of 20 failed**, each with `AGC graphics: image table wide draw variant: the draw over the stride-48 table captured 1048608 bytes of words and holds 3213016 bytes in the draw cache, over the 2177562 its words, a run and a run base per region at up to twice their count, and its two variants allow`.

**Green.**
- Result: **20 of 20 passed**, each with `image table wide draw variant passed (1 inserts, 1 entries holding 2164472 bytes for 1048608 captured, bound 2177562)`.
- The existing case after it: `image table draw cache bounds passed (64 inserts, 58 evictions, 58 over the byte budget, at most 7 entries holding 14513 KiB)`. That is one eviction more than BF-108's 57, for the wide entry that now precedes it.
