## Gaps

### Gap 2: fixed, f2f52d08a, on top of 2697ae5d9's drain

**What.**
- **One outcome.** `precheckDraw` decodes the CB metadata pass or the DB expand as one outcome, then runs either the same way: 2697ae5d9's drain (that line is unchanged), the GPU lock, the packet's labels, the pass.
- **State-only refusal.** `DepthMaintenanceRejection` refuses an out-of-place expand with "an out-of-place DB expand (DB_RENDER_CONTROL 0x…) is run by the draw precheck, in order, and is not drawn".
  - `precheckDraw` never reaches this check, because it runs the expand first.
  - Every path that classifies a draw from its state alone now gets that rejection instead of Nothing or Proceed: `DecodeState` for a draw, and #6188's `precheckState` for its ahead records.
- **Inline variant.** `agc_driver_depth_expand_out_of_place_inline` runs the out-of-place cases with `APS5_PIPELINED_DRAWS=0`. This follows main's `agc_driver_pm4_failure_inline` and `agc_driver_draw_cache_reuse_inline`.

**Why this is as far as main allows.** Main has no ahead path. The decode is already pure (`DecodeDepthExpandPass` reads registers only), and its execution sits behind the drain. What remains is to make the state-only path refuse the expand, and to keep both passes in one block for the ahead PRs to hook.

**#6188 (0eb0d8903b).**
- **Its design.** It splits `precheckDraw` into a pure `precheckState`, which returns `DrawPrecheckOutcome {Proceed, Nothing, Rejected, MetadataPass}`, and an executor switch. `Driver::draw` skips the precheck for ahead records classified Proceed or Nothing.
- **Without f2f52d08a,** the expand reaches `precheckState` as an ordinary draw:
  - #6146's `DepthMaintenanceRejection` accepts 0x60;
  - the next check returns Nothing (no color writes, depth test and write off, no pixel shader) or Proceed;
  - either outcome is certain, so the expand is skipped, or drawn without being run, silently.
- **With it,** `precheckState` returns Rejected:
  - an ahead record is then not certain;
  - in order, the draw fails with the message above;
  - so a merge that forgets the expand fails loudly and the message says where the expand belongs.
- **The right merge** adds a `DrawPrecheckOutcome::DepthExpand` with an expand out-parameter next to MetadataPass, using the shared decode. For either outcome the executor drains, takes the GPU lock and runs the pass. The drain must stay in the executor: an ahead classification must not drain.
- **Merge-tree:** DrawPrecheck.cpp already conflicts between #6188 and #6146 (7809e9d443).

**#5925 (3339ddd3af).**
- **Its guard.** Its resolve-ahead walk calls `precheckDraw` ahead of time and guards only the CB metadata branch, with `if (resolvingAhead()) return DrawVerdict::Nothing;`.
- **On 2697ae5d9 the merge is clean but wrong.** #5925 merges with DrawPrecheck.cpp cleanly; its merge-tree conflicts come only from main's drift. The expand branch would stay unguarded, and the walk would drain, record labels and expand early.
- **With f2f52d08a,** DrawPrecheck.cpp conflicts. The guard's only place is the first line of the shared block, where it covers both passes. A resolution that dropped the guard would also drop it from #5925's own metadata pass.

### Gap 7: fixed on code analysis, 67a68a167; no red

**What.**
- `StoreDepthExpandWrites` only looks imports up, with `HostImportOverlaps`.
- A plane no import holds stays noted while `AnyPendingOverlaps` says it is pending.
- `UploadFinish` calls the store again after its region loop. A build that imports the range itself therefore stores the plane before reading it.

**Cost:** the second call is a lock and a scan of an empty map when no plane is noted.

**Why there is no red on lavapipe.** Every address-based build imports the registered ranges itself, through the cached space or per build.
- The old store's on-demand import only changes who makes the import, and with what eviction policy.
- **No room for imports (budget 1 byte):** the old store's import is refused, and its dropped note is invisible, because the later pointer copy still reads the plane.
- **Eviction:** the build holds the imports the store would have to evict. An unheld non-GPU import, budget set to the live bytes, did not reach eviction either.

**Regression case:** `store-without-import-room` is green before and after the fix. An address-based build that does not read the write base stores nothing, makes no import and dissolves no space, and a later pointer copy holds the plane.

### Gap 3, judged: scope

**The bits.**
- DB_RENDER_OVERRIDE (context 0x003) 0x28000000 is FORCE_Z_DIRTY | FORCE_Z_VALID, and 0x50000000 is FORCE_STENCIL_DIRTY | FORCE_STENCIL_VALID.
- Public facts give only these bit names. Neither the AMD register reference nor main's code says what the DB writes to a moving write base under them:
  - whether every covered tile is written, compressed or not, when DB_RENDER_CONTROL's compress-disable bits are clear;
  - what HTILE then holds.
- Without DEPTH_COMPRESS_DISABLE, the tiles can be written compressed, and only HTILE describes them. The driver models neither, and nothing is measured on the console.
- Main never decodes DB_RENDER_OVERRIDE. Such a draw goes down the ordinary draw path, and its write base is ignored, silently.

**#1395 (cedec6e1d5).**
- Its `DecodeDepthCopyPass` copies resident images for these bits when the bases differ, citing the AMD CIK 3D register reference pp. 215 and 225.
- It leaves guest coherence and HTILE resummarization unimplemented.

**Overlap.**
- The two decodes are disjoint: #6146 needs DB_RENDER_CONTROL's compress-disable bits, and #1395 keys on DB_RENDER_OVERRIDE.
- If both merge:
  - a draw with both should take the expand, which is the better-defined one;
  - #1395's copy should write through `RunDepthExpandPass`'s plane views and pending notes, so its result is guest-visible and import-neutral like the expand's.

### Gap 6, judged: scope

**What it would take.** An in-place expand leaves the read base as the live surface.
- The guest-visible result would be guest memory holding the uncompressed plane.
- `CachedStorageSurface` at the read base returns the live surface's own storage view (`cachedStorageTexture` → `DepthSurfaceStorage`, ShaderResources.cpp:931). `DepthSurfaceStoreBack` (DepthSurface.cpp:1296) flushes such a view back into the surface, not into guest memory.
- So an in-place store needs a new path: a guest write of a live surface's plane. That write goes stale at the next draw to the surface, and it would race draws still queued for it.

**Why it is not contained.**
- Reads through the surface (textures, the depth binding) already see the plane.
- A raw read (CPU, DMA, an address-based copy) of a live single-sample depth surface is stale with or without an expand: `RequireNoResidentDepthRead` guards only multisample targets (MultisampleTarget.cpp:540).
- Fixing that needs coherent read-back of live depth surfaces for raw reads, a general feature rather than part of the expand.
- A store-back on every in-place expand would cost a full-plane copy per expand, which games issue before sampling depth, for reads that mostly go through the coherent texture path.

### Gaps 9, 12, 13 and 14: scope

- **9 (medium-low), a guest CPU read after a label misses the plane.**
  - Pending planes are stored lazily: by an address-based build, a V#/pointer read, or a flush.
  - Storing them before a label becomes CPU-visible would put stores on the label path (WRITE_DATA, RELEASE_MEM and EOP events), ordered before the label write.
  - That changes coherence for every pending GPU result, not only expands. The doc half is in d3d4d32c1.
- **12 (low), no overlap check of the write base against live planes, the stencil plane or HTILE.**
  - The DB does no such check either; an overlap is a guest error.
  - A refusal would cost a surface-registry walk per expand, and no title is known to overlap them.
- **13 (low-medium), HTILE words are not read.**
  - The expand copies from the live surface. The emulator renders uncompressed, so that surface holds the right depth.
  - HTILE matters only when the guest wrote it itself, for example a clear through HTILE and no surface live. #5627 has the reader; once it lands, the guest-bytes branch can decode through it.
- **14 (low, perf), indirect expands read their records on the CPU and wait when the GPU wrote them.**
  - Correctness is kept.
  - Running the copy as an indirect dispatch would need a count-predicated copy pass, and no title is known to issue indirect expands often.
