# PRM-092: #10043 `agc_driver_present_upscale` segfaults on lavapipe from Mesa 26.0.3

Worker: cloud-1.

## Summary

- **The crash is in Mesa, not in #10043 or its test.**
  - Lavapipe 25.3.0 to 26.0.3 calls a NULL function pointer inside `vkCreateSwapchainKHR` on a `VK_EXT_headless_surface` swapchain.
  - It happens whenever lavapipe can export dma-buf memory (`/dev/udmabuf` is usable).
- **Top frames (26.0.3, gdb):**
  ```
  #0  0x0000000000000000 in ?? ()
  #1  wsi_create_native_image_mem ()            libvulkan_lvp.so (26.0.3)
  #2  wsi_create_image ()                       libvulkan_lvp.so
  #3  wsi_headless_surface_create_swapchain ()  libvulkan_lvp.so
  #4  wsi_CreateSwapchainKHR ()                 libvulkan_lvp.so
  #5  ?? ()                                     libvulkan.so.1 (loader)
  #6  AgcDriver::VulkanDevice::VulkanDevice(PresentationWindow const*, bool)   libSceAgcDriver.prx
  ```
- **Cause:**
  - Mesa 25.3.0 changed the headless WSI ("vulkan/wsi/headless: drop the wsi_create_null_image_mem override", 25.3.0 release notes). Since then a headless swapchain allocates its images as exportable dma-buf memory and fetches an fd with `wsi->GetMemoryFdKHR`.
  - For a software device such as lavapipe, the WSI never loads that pointer (`wsi_common.c:201-202`: `if (!wsi->sw) WSI_GET_CB(GetMemoryFdKHR);`), so the call jumps to address 0.
- **Already fixed upstream:**
  - Mesa 26.0.4 (2026-04-01) has "vulkan/wsi/headless: properly use CPU images for CPU devices" (Icenowy Zheng). From then on, software devices get CPU images and never reach that path.
  - Measured on Mesa 26.0.8 here: the test passes 3/3 with and without udmabuf.
  - Ubuntu's archive carries `mesa 26.0.8-1ubuntu0.3`.
- **The call AnyPS5 makes is valid.**
  - Every parameter meets the `VkSwapchainCreateInfoKHR` valid usage (§4).
  - A standalone program with no AnyPS5 code makes the same call and crashes the same way on 26.0.3, under the validation layer too.
- **No AnyPS5 change:**
  - Nothing to fix, and branch `prm/10043-present-upscale-mesa26` was not created.
  - A lavapipe version check in the test would be a workaround for a fixed Mesa bug, so I did not write one.

## 2. Reproduction

**udmabuf matters.**
- This VM's kernel (6.18.44-fc-v185) has `# CONFIG_UDMABUF is not set`, so `/dev/udmabuf` does not exist.
- Lavapipe can only export dma-buf memory through udmabuf (`llvmpipe_dmabuf_alloc`, `lp_texture.c:1426-1462`).
- Without it, 26.0.3 cannot allocate the headless swapchain's images and returns `VK_ERROR_OUT_OF_DEVICE_MEMORY` before reaching the NULL call.
- A desktop with udmabuf, like the reviewer's, gets the segfault.

**The udmabuf shim:**
- To run the path a udmabuf kernel takes, I used a small LD_PRELOAD shim, applied only when the caller is `libvulkan_lvp.so`. AnyPS5's own `/dev/udmabuf` probe still fails as before.
- It emulates exactly what lavapipe uses. `open("/dev/udmabuf")` returns a placeholder fd. `UDMABUF_CREATE` returns a duplicate of the sealed memfd lavapipe passes in, which is a mappable fd like the real dma-buf.
- Everything after the allocation is Mesa's own code. The appendix has the source.

**Commands:** as user `runner`, `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ctest --test-dir build -R '^agc_driver_present_upscale$' -V`.
- `--repeat until-fail:3` for the passing runs.
- `--repeat until-pass:3` for the failing ones, so all three runs execute.
- 26.0.x is selected with `VK_DRIVER_FILES=<install>/share/vulkan/icd.d/lvp_icd.x86_64.json`.

## 3. Backtrace and the faulting call

**The crash under gdb:** the test executable `build/tests/agc_driver_present_upscale_tests`, with the ctest environment plus the shim. gdb reports `Thread 1 "agc_driver_pres" received signal SIGSEGV`, `rip 0x0`, and the frames in the summary.

**The release build's symbols name every frame.** A `debugoptimized` build wasn't needed. The instruction that jumped to 0, in the standalone reproducer (§4), same frames:
```
<wsi_create_native_image_mem+352>: lea    0xb4(%rbx),%rdx        ; &image->dma_buf_fd
<wsi_create_native_image_mem+359>: movl   $0x200,0xf8(%rsp)      ; handleType = VK_EXTERNAL_MEMORY_HANDLE_TYPE_DMA_BUF_BIT_EXT
<wsi_create_native_image_mem+370>: call   *0x410(%rax)           ; %rax = chain->wsi
```

**The pointer it calls is NULL:**
- `*(wsi+0x410)` is `0x0`.
- Its neighbours are `*(wsi+0x408)` = `vk_tramp_GetImageSubresourceLayout` and `*(wsi+0x418)` = `vk_tramp_GetPhysicalDeviceFormatProperties`.
- That is the order of `WSI_CB(GetImageSubresourceLayout); WSI_CB(GetMemoryFdKHR); WSI_CB(GetPhysicalDeviceFormatProperties);` in `wsi_common.h:221-223`. The NULL slot is `wsi->GetMemoryFdKHR`.

**The 26.0.3 code path:**
1. `wsi_headless_surface_create_swapchain` (`wsi_common_headless.c:382`) passes `WSI_IMAGE_TYPE_DRM` image params for every device. It does that for software devices too, and no longer installs its own `create_mem`.
2. With `same_gpu = true` and `supports_scanout = true` (the default, `wsi_common.c:87`), `wsi_drm_image_needs_buffer_blit` returns false (`wsi_common_drm.c:893-903`), so the images use `wsi_configure_native_image` with `create_mem = wsi_create_native_image_mem` (`:716`).
3. `wsi_create_native_image_mem` (`:743`) allocates the image memory with `VkExportMemoryAllocateInfo{DMA_BUF}`. On lavapipe that needs udmabuf. Without it the allocation fails, which is this VM's -2.
4. If the allocation succeeds, `wsi_init_image_dmabuf_fd` (`:726-739`) calls `wsi->GetMemoryFdKHR`.
5. Lavapipe initialises its WSI with `.sw_device = true` (`lvp_wsi.c:38-43`), and for software devices `wsi_device_init` skips `GetMemoryFdKHR` (`wsi_common.c:201-202`). The call jumps to address 0.

**Why 25.2.8 doesn't crash:**
- Its headless swapchain set `chain->base.image_info.create_mem = wsi_create_null_image_mem`. That allocated plain memory and set `dma_buf_fd = -1`: no export, no `GetMemoryFdKHR`.
- 25.3.0 dropped that override, and 26.0.3 still has it dropped.

**The fix, as it stands in 26.0.8** (`wsi_common_headless.c`):
- `if (!wsi_device->sw && wsi_device->supports_modifiers)`;
- for `wsi_device->sw`, it passes `wsi_cpu_image_params{ .base.image_type = WSI_IMAGE_TYPE_CPU }` instead of the DRM params.

**Affected releases:**
- From the release notes: 25.3.0 brought the change, and 26.0.4 lists the fix.
- The 25.3.1-25.3.3 notes in the 26.0.3 tarball don't mention it. I did not check later 25.3.x releases.

## Appendix: the udmabuf shim (test aid, not committed anywhere)

```c
#define _GNU_SOURCE
#include <dlfcn.h>
#include <fcntl.h>
#include <linux/udmabuf.h>
#include <stdarg.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>

static int fake_fd = -1;

static int caller_is_lavapipe(void *address) {
    Dl_info info;
    return dladdr(address, &info) && info.dli_fname && strstr(info.dli_fname, "libvulkan_lvp");
}

static int fake_open(const char *path, void *caller) {
    if (!path || strcmp(path, "/dev/udmabuf") != 0 || !caller_is_lavapipe(caller)) return -2;
    return fake_fd = memfd_create("fake-udmabuf-device", MFD_CLOEXEC);
}

/* open, open64, __open_2 and __open64_2 call fake_open(path, __builtin_return_address(0)) first
   and fall through to the real symbol (dlsym(RTLD_NEXT, ...)) when it returns -2. */

int ioctl(int fd, unsigned long request, ...) {
    va_list args;
    va_start(args, request);
    void *argument = va_arg(args, void *);
    va_end(args);
    if (fake_fd >= 0 && fd == fake_fd && request == UDMABUF_CREATE) {
        const struct udmabuf_create *create = argument;
        return fcntl((int)create->memfd, (create->flags & UDMABUF_FLAGS_CLOEXEC) ? F_DUPFD_CLOEXEC : F_DUPFD, 0);
    }
    static int (*real)(int, unsigned long, ...);
    if (!real) real = dlsym(RTLD_NEXT, "ioctl");
    return real(fd, request, argument);
}
```
Built with `gcc -shared -fPIC -o fake_udmabuf.so fake_udmabuf.c -ldl`, used as `LD_PRELOAD=.../fake_udmabuf.so`.
