- **The fix:** `resolutionFootprint` adds `table.readRanges.size() * 4u` per table, the same as `ColumnRecords::Footprint()`. The function is used for both calls (tables and nested), so both are covered. Nothing else in the memo changed.
- **The test:** a boundary at the real 8M-word budget, with no test-only knob.
  - **Construction:** `verifyResolutionMemoReadRanges` in `tests/ShaderDiskCache.cpp` runs next to the existing `verifyNestedResolutionReuse`, on the same fixture snapshot. That is a real materialized plan snapshot with tables and nested tables.
    - It resolves the snapshot twice through `ResolveImageTablesShared` with the memo on.
    - It then gives the snapshot's table 2^21 read ranges, and in a second case gives the first nested table 2^21 read ranges, and resolves each twice under its own memo key.
    - 2^21 ranges at 4 words each is exactly `ResolutionMemoWords` (2^23), so an entry with them is over the budget by its own counted words.
  - **The bar:** the snapshot without ranges is memoized: 1 resolution, then 1 shared. With the ranges, a second identical resolve must not be shared: 2 resolutions, 0 shared, two different results with equal maps.
  - **Guard:** `verifyPlanRoundTrip` now requires that at least one fixture ran the check, so it cannot drop out silently. With `APS5_NO_TABLE_RESOLUTION_REUSE` set, the check is skipped, the same as the existing memo check.
  - **Size and time:**
    - 2,097,152 pairs of 64-bit values, 32 MiB per ranged snapshot, one at a time.
    - It runs for 2 fixtures per process, 32–43 ms each (three timed runs, with a timing print that was not committed). So it adds about 80 ms to `agc_shader_disk_cache`: 2.72 s on the head, 2.60–2.76 s after the change.
  - **Registration:** no new ctest. The check runs inside the existing `agc_shader_disk_cache` test, next to the image-table memo test, so the CMake WIN32 `PATH` list is unchanged.
  - **What is synthetic:** the ranges are injected into a captured snapshot, not produced by a guest capture.
    - One real table carries fewer ranges than this: an address-path table has at most one per key (65,536), and a nested parent at most one per distinct child.
    - So the test bounds the accounting at the budget, not a capture that reaches it on its own.
    - By my estimate, building the 8M words from real captures would take about 1.4M captured records (2 counted words plus 4 range words per record). That's the cost I avoided.
