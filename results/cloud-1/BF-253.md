# BF-253: "guest buffer has no GPU owner" after a failed join host import

Worker: cloud-1. Base: upstream/main 470a562903 (newer than f8f5b24b77).

## The path

`owner()` (core/libs/prx/libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp:4726) returns null only when neither `regions` nor `space->base` has a region beginning at or before the view. Every view gets a region of its own (`addDescriptorRegion`, :4765) or lies inside a base region, and every list `owner()` searches is sorted (UploadPrepare's merge, :5245-5292; `std::merge` in `dissolveSpace(true)`, :4702). So the null owner needs a region to be removed, and only one place removes regions other than overlays: `resolveOverlays` (:5187).

```
5193    std::vector<bool> drop(regions.size(), space == nullptr);
5195    for (std::size_t first = 0; space != nullptr && first < members.size();) {
...
5218    regions.erase(regions.begin() + static_cast<std::ptrdiff_t>(kept), regions.end());
```

`drop` covers every region, not just the overlay members. When the build has at least one overlay region and the address space was dissolved before `UploadPrepare` (`space == nullptr`), every entry starts as `true` and the loop that would clear them is skipped. `resolveOverlays` then erases every region of the build: the overlays, the merged base regions and every other view's own region. `Descriptor` (:5927) then finds no owner for any view: `Require(found != nullptr, "guest buffer has no GPU owner")` at :5931.

The sequence that leads there:

1. An address-based compute build that may stage (`AllowDeviceStaging`, dispatch of at least `APS5_BDA_STAGING_MIN_THREADS`, a recorder active) adds a written view inside one direct import region of the cached space. `addDescriptorRegion` makes it an overlay region (:4777, `overlayCandidate`, :5183).
2. A later view of the same build dissolves the space before upload, through `dissolveSpace(false)`. That happens for a written view crossing two base regions (`BaseOverlap::Partial`, :4789), a written view over a recorded read across base regions (`AddWritable`, :4881), a view past a mirror's served bytes (:4774), or a snapshot crossing base regions (`AddSnapshot`, :4904).
3. `UploadPrepare` → `resolveOverlays` (:5224) erases all regions. `Descriptor` throws.

Where the failed join comes in: a join import over two adjacent registered ranges fails at `vkAllocateMemory`. `importRunAt` retired the ranges' imports before the attempt (:2083-2087) and records the run in `failedJoins` (:2104), and `importJoined` never retries it (:1979). The budget is lowered to the live bytes (:2183). From then on, the two ranges stay imported apart, or one is refused and copied ("refused ... by build" in the log). A view that the joined import would have held inside one base region now crosses two base regions, so it is `Partial` and, when written, dissolves the space before upload (step 2). With an overlay made earlier in the same build (step 1), every region is erased. Before the failure, the joined import held such a view `Inside`, so the space stayed and `resolveOverlays` ran with `space != nullptr`. That explains why the abort comes only after the failed join, and only in compute shaders (overlays exist only in staged address-based builds, 5804207c50, 10-19).

#11148 (9da50eb84a) fixed the sibling where the space is dissolved *after* `UploadPrepare` (`dissolveSpace(true)` in UploadFinish, :5477). That dissolve runs after `resolveOverlays`, so it never reaches this path.

#6146 adds `reads.emplace_back` in `AddReadable` and `StoreDepthExpandWrites` / `StorageTexture::FlushPending` over the reads in `UploadFinish`. It touches neither `resolveOverlays`, `dissolveSpace`, `owner()` nor the add-time dissolves, so it doesn't change this path. The 10-25 aborts had no #6146, which fits.

## Notes

- The bug came in with 5804207c50 (Celegans12, 10-19, "stage the written elements of address-based compute builds in device memory"). Any staged compute build whose space dissolves before upload hits it, not only after a failed join. The failed join is what makes such a dissolve likely in Village's intro: the view the joined import held now crosses two imports, or an import and a copied range after "refused ... by build".
- Under host-heap pressure, a build whose import is refused or split (`budgetedImportPieces`: imported pieces plus a mirror remainder) dissolves on a written view that crosses a piece edge or runs past a mirror's served bytes. That reaches the same erase without any join, so the fix covers it too.
