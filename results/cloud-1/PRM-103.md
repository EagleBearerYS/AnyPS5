## The option: (b), and why not (a)

PRM-103n prefers (a) unless the case needs what comes before it. **It does**, so the commit takes (b).

**Why the case needs `EvictionTests`' journal:**
- The case checks the room a rewrite leaves. `EvictionTests` writes a journal past the 1 MiB cap and then records real pipelines, so the journal is rewritten. Its own checks confirm that: records evicted, and the file within the cap. The watermark case then records into that rewritten file.
- In an empty journal there's no rewrite before the three records. Three records into it can't trigger a rewrite whatever the target is, so the assertion would pass even if the rewrite went to the cap itself. That weakens the check, which PRM-103n point 2 rules out.

**(a) alone also wouldn't remove the size dependence:**
- A rewrite leaves the file at most at its target, which is `maxBytes - maxBytes / 4u` in production (`PipelineJournal.cpp`, `evictUnderLock`). With the test's 1 MiB cap, the guaranteed free room is 262,144 bytes.
- The three fixed 16 Ki-word records were about 93 KB each on main, 279,288 bytes for the three. That's more than that room.
- **Main** passed only because its rewrite happened to leave the file 36,880 bytes under the target: 749,552 of 786,432, per jotitadev's measurement.
- **This head:** each module is about 4,956 bytes larger, and in build A the three records end 92 bytes over the cap.
- Any journal that was just rewritten, set aside or not, has the same problem as long as the records are fixed.

**What (b) does:**
- **Per record:** for each of the three pipelines, the case encodes the fixture's module without user words, using `ShaderRecompiler::ShaderDiskCache::EncodeResult`, which is what the journal writes. It then gives the pipeline as many user words as make its records exactly one quarter of the room the target leaves: `(JournalCap - RewriteTarget) / 4` = **65,536 bytes**, module record and compute record together.
- **Total:** the three take three quarters of that room, 196,608 bytes, whatever the fixture's SPIR-V. The last quarter covers what `EvictionTests` records after its own rewrite.
- **Measured** (uncommitted prints, one run, build A at the new commit):
  - the module is 32,424 bytes without user words, plus 8,254 user words;
  - each record is 65,536 bytes;
  - the journal went 754,512 → 951,120, which is exactly 3 × 65,536, with **0** further evictions.
- **Format constants:** the record size helper uses the same layout the test already writes in `EvictionTests` and `AppendJournalRecord`: a 24-byte header, 8-byte alignment, a 20-byte module prefix and a 17-byte compute payload.
- **A guard instead of a silent weakening:** if a future fixture's module alone exceeds 65,536 bytes, the case fails with its own message ("the fixture's compute module alone takes … journal bytes, more than the 65536 each record may take after a rewrite").

## The check is not weakened (PRM-103n point 2)

The assertions are byte-identical before and after. Only how the three records are sized changed.

| | before (582e856556) | after (6bec085232) |
|---|---|---|
| journal cap | `APS5_PIPELINE_JOURNAL_MAX_MIB=1` (set in `main`) | same, unchanged |
| production rewrite target | `maxBytes - maxBytes / 4u` (unchanged production code) | same; the test sizes from `JournalCap - JournalCap / 4u` |
| journal the case starts from | the one `EvictionTests` just rewrote | same |
| the three records | `result.shaderDataUserWords.assign(16u * 1024u, salt);` (≈93–98 KB each, depending on the fixture's SPIR-V) | `result.shaderDataUserWords.assign(userWords, salt);` sized so module + compute record = 65,536 bytes each |
| assertion 1 | `Require(after.journal.recordedCompute == before.journal.recordedCompute + 3, "the records after the rewrite were not recorded");` | identical |
| assertion 2 | `Require(after.journal.writeFailures == before.journal.writeFailures, "the records after the rewrite failed to write");` | identical |
| assertion 3 | `Require(after.journal.evictedRecords == before.journal.evictedRecords, "three consecutive records after a rewrite triggered another rewrite");` | identical |
| assertion 4 | `Require(std::filesystem::file_size(path) <= 1024u * 1024u, "the journal exceeded its cap after the consecutive records");` | identical |

**Mutation check** (build A, local production change, reverted):
- With the production target raised to `maxBytes - maxBytes / 8u` (87.5 % of the cap), the new case fails: `AGC graphics: three consecutive records after a rewrite triggered another rewrite`.
- With `maxBytes - maxBytes / 16u` (93.75 %), it fails the same way.
- With the real `/ 4u`, it passes.
- So it still catches a rewrite target that leaves less room than three records need. It rejects any target above about 81 % of the cap, plus whatever `EvictionTests` appends after its rewrite.
- `git status` was clean after the reverts.
