## The predicate

`Graphics/include/VertexInput.hpp`, the existing `VertexFetchOutOfRange`, extended:

```cpp
return attribute.resource.fields[2] == 0 && (stride == 0 ? select == 2u || select == 3u : select <= 1u);
```

It used to be `stride == 0 && (select == 2 || select == 3) && records == 0`:
- The zero-stride shape is unchanged.
- The new arm covers records 0, a nonzero stride and select 0 or 1.

**How it is used:** it's the predicate already used where `zeroed[i]` is set (`prepareDrawInputs`, `Graphics/src/Draw.cpp`). So both paths now bind `zeroVertexBuffer(context, attribute)`, as they do for null descriptors.
- **GPU path:** no longer calls `VertexBufferExtent`, which throws for records × stride = 0.
- **CPU path:** binds the zero buffer instead of the zero-padded solo copy that read nothing.
- **Selects 2 and 3** with a nonzero stride and 0 records still fail as before, in `VertexBufferReadSize` ("record count") or `VertexBufferExtent`, and so does every other shape.

**Dropped: a stride-0 binding.**
- **What I tried first:** `BuildVertexInputLayout` gave these attributes a binding stride of 0, so every vertex would read the zero buffer in bounds.
- **What it broke:** `agc_vertex_input` failed with `record count rebuilt a vertex layout`. `VertexInputCache` is meant to never rebuild a layout when only the record count changes, records 0 included (tests/VertexInput.cpp:131-137, from 02e58e993 "bypass vertex layout cache churn").
- **What the commit keeps:** the binding keeps the descriptor's stride.
- **What that leaves:** with a format-sized zero buffer, only vertex 0 is in bounds, and later vertices get what `robustBufferAccess` returns for an out-of-bounds vertex fetch.
  - On lavapipe that's zero: a mutant run with the stride kept passed the cell checks below.
  - Vulkan without robustness2 also allows `(0,0,0,x)`.
  - So on a GPU that returns w = 1 there, the attribute's w would read 1, not 0.
  - The CPU path's old zero-padded copy was exact; it now has the same behaviour as the GPU path.
  - If that matters, the exact fix is a stride-0 binding whose layout key is decided per draw rather than in the record-count-blind cache. That is a larger change than this task's.

## Test

`tests/execution/IndirectVertexPastEnd.cpp`, extended in the same commit. The vertex buffer now holds three triangles, in cells 1, 2 and 3. A second shader fetches two attributes and exports A + B as the position:
- A from the vertex buffer, as before;
- B from a second V# at a readable address in the guest block, with **0 records, stride 16**.

A B that reads exactly zero leaves the cell-3 triangle in cell 3. A w of 1 would halve x and move it into cell 2, so the case is sensitive to more than "nothing drawn".

New cases (main's variant has no draw-parameter case, and no BF-025 pass counters to check):
- `DRAW_INDIRECT`, first vertex 6, B with OOB select 0, GPU-side: cell 3;
- the same with OOB select 1: cell 3;
- a **direct draw**, first vertex 6, B with select 0: cell 3. This shows both paths agree.
