## Design

### Recognition

`DecodeDepthExpandPass` (`Graphics/src/State.cpp:1317-1382`, `DepthExpandPass` at `Graphics/include/State.hpp:158`) runs in the draw precheck, before any other draw handling. It mirrors `DecodeColorMetadataPass` for the CB passes.

- **Not an expand** (std::nullopt, the draw goes on as before):
  - no DEPTH/STENCIL_COMPRESS_DISABLE bit (`DB_RENDER_CONTROL & 0x60`);
  - or neither plane moves. The depth plane moves when it is present, not read-only (DB_DEPTH_VIEW bit 24) and Z_WRITE_BASE != Z_READ_BASE. The stencil plane moves when it is present, not read-only (bit 25) and its write base differs from its read base.
- **The recognised expand** is exactly the game's shape:
  - DEPTH_COMPRESS_DISABLE set, and no bits besides the two compress-disable bits and bit 13 (accepted elsewhere since f2fe3f716);
  - no stencil, depth or depth-bounds tests in DB_DEPTH_CONTROL;
  - no color writes;
  - a single-sample Z_32_FLOAT SW_64KB_Z_X surface, not partially resident or mipmapped;
  - DB_DEPTH_VIEW 0;
  - 64 KiB-aligned bases;
  - no window offset and the standard VTE;
  - a viewport and scissor covering the surface (DB_DEPTH_SIZE_XY).

  The pass carries the read surface (address, stencil, extent, format, HTILE) and the write base. The rasterizer's sample count is not checked, since the game expands its single-sample surface with PA_SC_AA_CONFIG at 2 samples.

### The copy

`RunDepthExpandPass` (`Graphics/src/DepthSurface.cpp:985-1021`) is reached through `VulkanDevice::DepthExpandPass` (`Execution/src/VulkanDevice.cpp:3443`). It is called from the precheck (`Execution/src/Driver/Draw/DrawPrecheck.cpp:26-35`) under the GPU mutex, after the packet's labels, as the CB metadata pass is.

1. It refuses a write base that is itself a live depth surface.
2. It takes the storage cache's image of an R32F, SW_64KB_Z_X, 2D, single-level view of the write base (`CachedStorageSurface`), the way `RunColorMetadataPass` takes a target's resident image.
3. It finds the read surface: the latest owner of the depth plane at the read base, with the same extent, single sample, 32-bit float depth and host format.
4. It applies any pending fast clear and copies the depth aspect into that image (`DepthSurface::CopyDepthTo`, `:237`, the existing `copyPlane` through its staging buffer). Then it marks the image written (`MarkDirty`).

From there the existing machinery serves both consumers:

- A sampled R32F SW_64KB_Z_X view of the write base finds the pending image. The texture path views it, or stores and re-uploads it.
- A raw buffer read or a CPU read of the write base runs `FlushPending` over its range. The write-back retiles the image into guest memory in the Z swizzle.

The read surface is left as it was, and the stencil plane is untouched. The first expand logs one line:

```
[gpu] DB expand: the depth plane of 0x55dedbe50000 (160x96) is written at 0x55dedbec0000
```

### What still throws

Each of these out-of-place combinations throws "AGC graphics: an out-of-place DB expand (DB_RENDER_CONTROL …, DB_Z_INFO …, DB_Z_READ_BASE …, DB_Z_WRITE_BASE …) … is not implemented", naming:

- "of the stencil plane" (stencil write base != read base);
- "with clear, copy, resummarize or decompress bits";
- "without DEPTH_COMPRESS_DISABLE";
- "with depth, stencil or depth bounds tests";
- "with color writes";
- "of a depth plane other than Z_32_FLOAT";
- "of a multisampled depth surface";
- "of a depth surface in a swizzle mode other than SW_64KB_Z_X";
- "of a partially resident or mipmapped depth surface";
- "of a depth view with a base slice, a mip level or a read-only plane";
- "between bases that are not 64 KiB aligned";
- "over part of the depth surface".

The execution step also throws, "AGC graphics: an out-of-place DB expand from … to … is not implemented", when there is:

- a write base that is a live depth surface;
- no depth surface at the read base;
- a depth surface there of another extent, format or sample count.

An in-place expand still changes nothing modeled (HTILE is not modeled), as before.

Behaviour change against main: an out-of-place compress-disable draw with no depth tests was silently drawn without a depth target. It now runs (the game's shape) or throws (anything else). With depth tests it threw before ("depth read and written at different addresses is unsupported") and throws now with the expand message. A read-only depth or stencil view is not treated as an expand and draws as before.

- **Log line to look for:** a Village run with the branch should print the expand's one-time line, about `[gpu] DB expand: the depth plane of 0x202a8a0000 (1920x2160) is written at 0x20298b0000`. That shows the game reaches the code.

## Open questions

1. **Four expands per frame.** The task says the game issues 4 such draws per frame. If they expand the same surface to the same base, each one copies the plane again: 2 × 15.8 MiB of device-local copies per draw for 1920x2160, about 126 MiB a frame for four. A follow-up could skip a copy when the surface's write serial and the destination image are unchanged since the previous one. I did not add that without knowing what the four draws are.
2. **Write-back per frame.** The compute pass's raw read of the write base stores the image into guest memory: 15.8 MiB a frame, through the host import where there is one. On Linux without udmabuf, direct memory is copied rather than imported ("shared direct memory is copied instead of imported" on this machine), so the store becomes a GPU readback, a CPU copy and a wait. The PC's own path decides the real cost.
3. **HTILE.** Whether the console marks the read surface's HTILE expanded or writes metadata for the write base is not known. Nothing reads HTILE in AnyPS5, so only a later HTILE model would care.
4. **2 raster samples over a single-sample depth surface.** Taken as irrelevant to the DB copy. Not confirmed on the console.
5. **Viewport y.** The game's viewport y scale may be negative. Coverage is checked with |scale|, as the CB metadata pass does, so either sign is taken.
