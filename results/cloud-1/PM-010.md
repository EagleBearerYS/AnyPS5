# PM-010: depth read through an aliased mapping — code map and a red test (cloud-1)

Result: done. Code analysis on upstream/main **bebff8b0e** (the head at 18:42 UTC; I claimed on ea30c9274, and the 30 commits in between change nothing on these paths except line numbers in `DepthSurface.cpp` and libkernel's `DirectMemory.cpp`). Every file:line below is on bebff8b0e; paths are under `core/libs/prx/` unless they start with `docs/`.

- **The theory holds as far as the code can say, but the alias is only half of it.** AnyPS5 never writes rendered depth to guest memory, so a buffer (V#) read of a depth plane sees the CPU's bytes even at the depth target's own VA. Two gaps stack:
  1. depth lives only in a device-local VkImage that no buffer read consults;
  2. every driver lookup is keyed by the exact VA, so a read at VA2 cannot find anything registered at VA1.
  A fix needs both. A local experiment through the one existing route from depth to guest memory, a written storage view that leaves the plane pending at VA1, shows the split: the single-mapping run then passes, and the aliased run still reads 0 until something reads VA1 (section 3).
- **Red test**: `agc_driver_depth_alias_read` (aliased) and `agc_driver_depth_alias_read_single` (single mapping), one commit on `test/depth-alias-red` at **b3c988d36** on the fork, on top of bebff8b0e. No PR. On lavapipe both fail on main, the same way: the buffer read sees 0 in all 32 lanes, while the two controls pass (a storage image read of the plane sees 0.5, and a buffer read through the second view sees a CPU store made through the first).
- **Fix options** (section 4): the smallest is to make a drawn depth plane a pending result at its own address, stored on the next flush of that range like a written storage view of the plane already is, and to make flushes expand a range to its other direct-memory views through a libkernel resolver. A per-read redirect to the depth image is the alternative. None of the six named items does either; #1409 is an issue, not a PR.

## 1. Aliases

### libkernel: both VAs are the same host memory

- `sceKernelMapDirectMemory`, `sceKernelMapDirectMemory2` and `sceKernelMapNamedDirectMemory` (`libkernel/DirectMemory/Export.cpp:193`, `:198`, `:210`) all go to `DoMapDirect` (`libkernel/DirectMemory/DirectMemory.cpp:890-923`). It maps the physical range again wherever asked; nothing refuses a second view, and `sceKernelEnableDmemAliasing` just returns 0 (`Export.cpp:189`).
- **Linux:** all direct memory is one memfd (`DirectMemory.cpp:230-242`). `PhysicalBacking::Map` maps each view with `mmap(MAP_SHARED | MAP_FIXED)` at the physical offset (`:315-321`, the mmap at `:319`). Two views of one physical offset are the same host pages; a CPU store through one is read through the other. The red test checks exactly that before it draws.
- **Windows:** one section per backing (`CreateFileMappingW`, `:273`), each view mapped by `GuestArenaMapDirect` (`:317`). Before a new view is mapped, `RequireAliasesUnpinned` (`:598-615`) requires that no host import pins the other views. I did not run Windows.
- `sceKernelMmap` with a descriptor (`Export.cpp:237` → `PosixMemory.cpp:94-174`) maps only shared-memory objects and regular files (`PosixMemory.cpp:149`), so the `MapDirectMemory` family is the only way to alias direct memory. Shared-memory objects are a separate double-mapping path (`DirectMemory.cpp:1002`).
- **libkernel knows the aliases.**
  - `DirectMemoryState` (`DirectMemory.cpp:357-369`) keeps `directMappings` (VA → end, physical offset, memory type, backing) and `physicalSpans` (physical offset → the VAs mapping it).
  - `QueryDirectMapping` (`:1206-1217`) turns a VA into its physical offset; `DirectMemoryViews` (`:1219-1234`) turns a physical range into every VA that maps it.
  - Their only users are `sceKernelVirtualQuery` (`Export.cpp:275-292`) and `sceKernelReleaseDirectMemory`, which unmaps every view (`Export.cpp:248-257`).
  - `WatchMapping` (`DirectMemory.cpp:489-505`, Linux) turns off CPU write watching on both views wherever two views share pages, so the driver's write stamps do not see CPU stores into aliased pages. Stamp queries over unwatched memory answer "changed" (`libSceAgcDriver/Execution/src/GuestMemory.cpp:1334-1343`).
- **What the rest of the process is told:** `DoMapDirect` registers each view with libc's `GuestAllocations` as an independent range (`DirectMemory.cpp:911-912`). A range carries no physical offset (`libc/include/GuestAllocations.hpp:13`).

### AGC driver: everything is keyed by the guest VA, and nothing translates

| Registry | Key | Where |
|---|---|---|
| Host imports of guest memory (the normal binding of a V#) | allocation base VA | `libSceAgcDriver/Graphics/src/GuestBufferMemory.cpp:155-162` (`std::map<std::uint64_t, HostImport>`), `findImport` `:1148-1156`, host pointer = the VA `:290-300` |
| Image mirrors (executable ranges) | range base VA | `GuestBufferMemory.cpp:51-75`, `:1169-1176` |
| Pending results (storage images and colour targets not yet stored) | `descriptor.baseAddress` and its byte range | `Graphics/src/Texture.cpp:1146-1200`; overlap test `:2980-2982` |
| Recorder pending-write notes (GPU writes in flight) | `[VA, VA+n)` | `Graphics/src/Recorder.cpp:2647-2665`, `:2775-2790` |
| Unit shadows | import base VA | `Graphics/src/UnitShadow.cpp:99-101` |
| Resource cache, recipes | descriptor words, so the VA | `Graphics/src/ShaderResources.cpp:833-836` (`SurfaceKey`) |
| Depth surfaces | `{VkDevice, VA}`, exact equality | `Graphics/src/DepthSurface.cpp:595-598` (`surfaces()`), `:605-617` (depth and stencil owners), `:644-656` (`planeSurface`), `:974-977` (`DepthSurfaceAt`) |

- The one place that sees physical backing is the Linux dma-buf import fallback.
  - It asks libkernel for the memfd and offset behind a VA (`GuestBufferMemory.cpp:597-599` → `DirectMemory.cpp:509-531`), through the resolver libkernel registers with libc (`DirectMemory.cpp:1151-1152`, `libc/src/GuestArena.cpp:476-497`).
  - It shares one `VkDeviceMemory` per 64 MiB chunk of the memfd (key `:385`).
  - Imports are still entered per VA, and neither the flush nor the pending machinery consults it.
- libSceAgcDriver never calls `QueryDirectMapping` or `DirectMemoryViews` and does not include libkernel's `DirectMemory.hpp`.
- `GuestBufferMemory.cpp:3924` states one limit outright, for GPU stores into a page whose view is not writable: "a direct memory page shared by several views; aliased writes are not implemented".
- **So no: a resource registered at VA1 is not found from a VA2 access.** The bytes are shared; the bookkeeping is not.

## 2. What a compute buffer read at VA2 sees

The setting: a depth target at VA1, resident in its GPU image and never written back; a compute shader reads VA2 through a V#.

1. `Driver::dispatch` (`libSceAgcDriver/Execution/src/Driver/Dispatch/Dispatch.cpp:16`):
   - `ShaderMemory::Capture` reads user data and the V# words (`:246-262`);
   - `Materialize` (`:270`);
   - `PrepareDispatch` (`Execution/src/VulkanDevice.cpp:3996-4051`), then the GPU mutex (`Dispatch.cpp:397`) and the dispatch body (`VulkanDevice.cpp:4327`).
2. `ShaderResources::addGuestBuffer` (`Graphics/src/ShaderResources.cpp:3439-3480`) decodes the V#. `address = descriptor.Base48()` (`:3444`) is VA2, and `AddReadable` (`GuestBufferMemory.cpp:2820-2834`) makes the region `[VA2, VA2+size)`.
3. `UploadPrepare` (`GuestBufferMemory.cpp:3101-3268`) looks the region up by VA2: `findMirror` (`:3180`), `findImport` (`:3213`).
4. `UploadFinish` (`:3270-3493`):
   - `importAccess` (`:3383`) imports VA2's allocation: a host-pointer import at VA2 (`:290-300`), or on Linux a dma-buf of the memfd at VA2's offset (`:441-487`, `:597-599`).
   - Before the in-place bind, `StorageTexture::FlushPending(VA2 range)` runs (`:3432-3439`). It scans the pending registry by VA overlap (`Texture.cpp:3130-3204`, overlap `:2980-2982`) and finds nothing: nothing was registered at VA2, and the depth plane is not in the registry at VA1 either.
   - With no import, the CPU-copy fallback (`:3459-3461`) goes through `GuestMemory::Read` (`Execution/src/GuestMemory.cpp:2002-2017`). Its flush hook `FlushForAccess` (`Recorder.cpp:999-1070`) flushes by VA2 as well and finds nothing too.
5. The descriptor points at the VA2 import (`GuestBufferMemory.cpp:3743-3771`, `ShaderResources.cpp:1936`). The bind (`:4491-4494`) is followed by `vkCmdDispatch` (`VulkanDevice.cpp:4272`).
6. **The shader reads VA2's host pages, which are the shared direct-memory pages. They hold what the CPU stored there at boot: zeros.**

Why the depth never reaches those pages:

- A depth target is a `DepthSurface`: a device-local image of its own (`DepthSurface.cpp:34-94`, memory at `:57-64`). It is created cleared to `DB_DEPTH_CLEAR` (`:85-86`), not loaded from guest memory, and the file has no `GuestMemory::Write`.
- `DepthSurfaceView`, which a draw calls (`Graphics/src/Draw.cpp:1991`, `:2495`), only finds or creates the surface and bumps its write serial (`DepthSurface.cpp:726-751`). Nothing marks it pending; after a draw only colour targets are marked dirty (`Draw.cpp:1536`).
- The plane is reached only through T# lookups at exactly its address. `ShaderResources.cpp:534` → `DepthSurfaceTexture` (`DepthSurface.cpp:808`) gives sampling; `ShaderResources.cpp:878` → `DepthSurfaceStorage` (`:942`) gives a storage image filled from the depth image (`Storage` `:199-218`, copy `:275-296`). No V# path consults depth surfaces.
- **So the single-mapping case fails too:** a V# read at VA1 reads VA1's guest bytes. `agc_driver_depth_storage_reuse` already pins that guest bytes stay unchanged under a depth draw (`tests/execution/DepthStorageReuse.cpp:53`, `:68-70`).
- The one route from depth to guest memory: a shader that **writes** a storage view of the plane. That copy is marked pending at VA1 (`ShaderResources.cpp:4526-4530`) and reaches VA1's pages, and therefore VA2's, when something flushes VA1: a VA1 access, the idle `FlushAllPending` (`VulkanDevice.cpp:1891`), or, for images up to 64 KiB (`Graphics/include/Texture.hpp:197`), the flip-time `StoreSmallPending` (`Execution/src/Driver/Packets/PacketMemory.cpp:198`). A VA2 read does not trigger it. `docs/dev/debt/libSceAgcDriver.md:36` ("Reused depth storage") describes it.

### Experiment, not committed: the existing route from depth to guest memory

A temporary `--storage-write` mode wrote the plane through a matching storage view right after the draw. That is the one existing route: `MarkDirty` makes the plane's storage image, filled from the depth image, pending at VA1 (`ShaderResources.cpp:4526-4530`).

- **`--single --storage-write`: passed.** The buffer read at VA1 flushed the pending image: "32 of 32 lanes read 0.5", and the CPU then read 0.5.
- **`--aliased --storage-write`: failed.** The buffer read at VA2 still read 0 in all 32 lanes, and the CPU at VA2 read 0. Then:
  - a buffer read at VA1 read 0.5 (it flushed the image);
  - after that, the buffer read at VA2 read "32 of 32 lanes read 0.5" through the shared pages.

So a store of the plane at VA1 fixes the single mapping, and the alias then needs only a VA2 access to trigger VA1's flush (gap 2). The mode was removed before the commit, and the committed test was rebuilt and rerun.

## 4. Fix options

Sizes for Village's plane: 1920 × 2160 × 4 bytes = 15.8 MiB.

### A. Store a drawn depth plane on the next flush of its range, and flush every view of a range (smallest)

This reuses what a written storage view of the plane already does (debt `:36`: "a written view is also left pending … so the plane's content, drawn depth included, reaches guest memory on the next flush of that range").

1. **Know the DB layout.** `decodeDepth` (`Graphics/src/State.cpp:257-332`) does not decode `DB_Z_INFO.SW_MODE`, and `DepthTarget` (`Graphics/include/State.hpp:71-81`) has no tile mode.
   - Add it, or assume the 64 KiB Z swizzle that `DepthSliceBytes` already assumes (`DepthSurface.cpp:682-688`).
   - A V# reader expects the DB's tiled layout, not linear rows.
2. **Register the plane as pending after a depth write, lazily.**
   - Where: in `DepthSurfaceView` (`DepthSurface.cpp:726-751`, called from `Draw.cpp:1991`/`:2495`), or when the draw is recorded with depth writes.
   - What: give the surface the plane's `StorageTexture`, as `DepthSurface::Storage` does (`:199-218`), using a T# built from the target (R32F / R16 unorm, the extent, the DB tile mode). Then `MarkDirty` it (`Texture.cpp:3000-3007`), with no copy.
   - When the copy happens: the copy from the depth image (`copyPlane`, `DepthSurface.cpp:275-296`) is made by `FlushPending` (`Texture.cpp:3130-3204`) just before its `writeBack` (`:4303-4343`) retiles the image into guest memory (`TextureDetiler` with `retile`, `Graphics/include/TextureDetiler.hpp:46-51`).
   - So nothing is copied unless something reads the range: a V# read, a T# view that does not match, a CPU access, or a DMA.
   - The registry's ordering then applies, which keeps the debt entry's concern (memory reused for something else) from being clobbered:
     - a GPU fill or copy over the range drops the pending plane (`DiscardPendingInside`, `Texture.cpp:3618`; called from `Execution/src/Driver/Memory/BufferFill.cpp:302` and `Texture.cpp:4068`);
     - a CPU access to watched memory stores it first, through the flush hook.
     - On aliased pages CPU stores are not watched (section 5, item 5).
3. **Make flushes alias-aware.**
   - libkernel registers a resolver with libc, exactly like the shared-backing resolver it already registers (`DirectMemory.cpp:1151-1152` → `libc/src/GuestArena.cpp:476-497`). The resolver maps `[VA, VA+n)` to the other views of the same physical pages (`QueryDirectMapping` + `DirectMemoryViews`, `DirectMemory.cpp:1206-1234`).
   - `FlushPending` and `ScanPending` (`Texture.cpp:3130`, `:3597-3616`) flush the alias ranges too. That covers the hook (`Recorder.cpp:999-1070`), the upload flushes (`GuestBufferMemory.cpp:3279`, `:3432-3451`) and the cached-dispatch flush (`ShaderResources.cpp:2922-2946`).
   - Storing at VA1 is then visible at VA2 with no copy between views, because the pages are shared (section 1).
   - libkernel can keep a count of physical ranges with more than one view, so the resolver returns at once for titles that never alias.

Cost per frame:

- **Nothing** when no one reads the plane through anything but a matching T#.
- **When Village's compute pass reads it once a frame:**
  - two device-local copies of 15.8 MiB (depth image → staging → storage image);
  - one retile of 15.8 MiB into guest memory.
- **Where the memory is imported:** the retile is a GPU write over PCIe into system RAM (about 0.7 ms at 25 GB/s), and the compute pass then reads it back as it does today.
- **Where direct memory is copied rather than imported:** the store is a GPU readback plus a CPU copy, and the CPU waits for the depth pass mid-frame. Linux without udmabuf falls back to copying: this machine logs "[gpu] open /dev/udmabuf: No such file or directory; shared direct memory is copied instead of imported".
- **Alias resolver:** one map lookup under libkernel's lock per flushed range of aliased memory, and an atomic load otherwise.

What else changes:

- `agc_driver_depth_storage_reuse` asserts the opposite today and must change with the fix. It requires that guest bytes stay 0.25 after the depth draw (`DepthStorageReuse.cpp:53`) and that a non-matching view reads 0.25 (`:68-70`).
- The debt entry `:36` loses "Depth rendering is not written back to those guest bytes".

### B. Resolve a buffer read of a live depth plane to the depth image

- **Where:** in `UploadPrepare`/`UploadFinish` (`GuestBufferMemory.cpp:3101-3493`).
- **What:** a readable region that overlaps a drawn depth plane (directly, or through the same alias resolver as in A) is bound to a device buffer instead of the guest import. The buffer holds the plane in the DB layout, made on the GPU from the depth image (depth → staging → retile dispatch) and cached per surface and write serial.
- **Cost:** about 2 × 15.8 MiB of device-local traffic per frame per plane that is read (well under a millisecond on a discrete GPU). No PCIe round trip, no CPU wait.
- **Limits:**
  - Guest memory stays stale, so CPU reads, DMA, and address-based (FLAT/GLOBAL) shaders reading VA2 through the page table (`Graphics/src/BdaResources.cpp:132-201`) still see zeros.
  - Writes through such a V# need a path back.
  - The reusable-dispatch proofs (`ShaderResources.cpp:2007-2035`, `:2903-2946`) need a new region kind, or every such dispatch is rebuilt.
- More code in the hot binding path than A, but cheaper per frame where direct memory cannot be imported.

### Not enough alone: store at flip or idle

`APS5_STORE_AT_FLIP`, the idle `FlushAllPending` and the flip's `StoreSmallPending` (`VulkanDevice.cpp:2788-2789`, `:1891`; `PacketMemory.cpp:198`) only store results that are pending, which a depth plane never is. Even if it were, Village reads the plane in the frame that draws it, so a store at the flip would show the previous frame's depth.

## 5. Things that contradict or complicate the theory

1. **Zeros do not prove the alias.**
   - A V# read of any depth plane sees guest bytes in AnyPS5, even at the plane's own address (the single-mapping run). "0x20298b0000 is never a depth surface" and "it reads zeros" fit the theory but would also hold without it.
   - Direct confirmation on the PC: run with `APS5_TRACE_MEMORY=1` (`DirectMemory.cpp:214-227`). Each direct mapping logs `[memory] map direct <VA>+<len> phys=<offset> …` (`:921`; remaps log `remap fixed … phys=…`, `:624`).
   - The theory holds if the mapping holding 0x20298b0000 and the mapping holding the depth target's `DB_Z_READ_BASE` (`State.cpp:281`) cover the same physical offset, with 0x20298b0000 at the same offset into it as the depth target.
   - `sceKernelVirtualQuery` reports the same offset (`Export.cpp:275-292`).
2. **Layout.** On hardware a V# read of a depth plane sees the DB's tiled layout, not linear rows.
   - With HTILE enabled (`DB_Z_INFO` bit 29, `State.cpp:294`), the DB may also leave tiles compressed in memory until a decompress pass, so the raw bytes need not be per-pixel depth. AnyPS5 throws on decompress draws (`State.cpp:258`).
   - If Village's compute pass decodes the plane itself, a fix must write the DB layout. With a compressed plane, AnyPS5 would hand the title decompressed values, which is more permissive than the console.
   - Which tile mode, and whether HTILE is on for the real depth target, are worth logging next to the trace above.
3. **1920 × 2160 is the shape of a checkerboard (half-width 4K) target.** If the depth target is multisampled, the storage paths both options build on refuse it today: "storage image access to a multisampled depth surface is not implemented" (`DepthSurface.cpp:186`) and "sampling a multisampled depth surface" (`:127`). #5499's sample copy is the nearest existing piece.
4. **The depth image never starts from guest memory.** A new `DepthSurface` is cleared to `DB_DEPTH_CLEAR` (`DepthSurface.cpp:85-86`). If Village first writes the depth through the alias (CPU or compute) and then draws with depth tests, AnyPS5 ignores those writes too. This is the inverse direction, which #5446 starts on for storage writes.
5. **CPU write watching is off on aliased pages.** `WatchMapping` (`DirectMemory.cpp:489-505`) turns it off.
   - Reads stay safe: stamp queries there answer "changed" (`GuestMemory.cpp:1334-1343`).
   - Ordering does not: with A, a CPU store made through VA2 after the depth draw would be overwritten by a later flush of the plane at VA1. A would need to compare the bytes before storing over aliased pages, or accept that loss.
   - This does not affect Village as described: its CPU writes 0x20298b0000 once, at boot, before any depth is drawn.
