## Summary

**Atomics only.**
- `reason=7` (Unaligned) is recorded **only by atomics**: FLAT/GLOBAL atomics, flat atomics routed to LDS or scratch, 64-bit LDS atomics, and 64-bit buffer atomics.
- Unaligned plain loads and stores never fault: they go through a byte path.
- So the guest access at `0x3045601423` is a 4- or 8-byte atomic. The log line's `bytes=` field says which.
- The test is natural alignment (address & 3 or & 7). 16-byte alignment plays no part.

**What happens to it:**
- The faulting invocation's atomic is skipped, and it returns 0 as the "old" value.
- The rest of the dispatch's results are still written back.
- Then the completion logs `deferred write-back failed`. Nothing about the write-back itself failed: that is only where the fault record is read.

**Gap or guard.** It is a gap if FLAT/GLOBAL atomics follow the same DWORD alignment-mode rule as buffer accesses.
- That rule is RDNA2 ISA 8.1.7: the two low address bits are ignored for dword or wider accesses. It is the reading behind main's 7e4ce1ab3d for 32-bit buffer atomics.
- AnyPS5 now applies the rule to 32-bit buffer atomics, but still drops the same FLAT/GLOBAL atomic.

## 1. Where `reason=7` comes from (51c31ea17e)

### The reason and the record

- `core/shader/recompiler/BdaAbi.hpp:38`: `enum class FaultReason { Unmapped = 1, Permission, Overflow, InvalidTable, InvalidRectangle, LoopLimit, Unaligned, … }`, so **Unaligned = 7**.
- `BdaAbi.hpp:40-48`: the 32-byte `Fault` record holds `{state, reason, address, bytes, stage, instruction, otherFaults}`. It lives at the start of the per-use fault buffer (`FaultBufferBytes`, `BdaAbi.hpp:68`).
- `SpirvBackend/src/SpirvBdaFault.cpp:32-76` (`record_bda_fault`):
  - The first fault of a dispatch wins the `Empty → Writing` compare-exchange and fills the record. Later faults only set `otherFaults`, and Unaligned does not set it (`:55-58`).
  - So the logged address is the first misaligned lane's. Other lanes' misaligned atomics in the same dispatch are skipped without a record.
- **`stage=4`** is `static_cast<uint32_t>(program.Resources().stage)` (`SpirvBdaFault.cpp:69`). In `IrMetadata/ShaderStage.hpp:6-16`, `IrShaderStage{Unknown, Vertex, Pixel, Fetch, Compute, …}`, so 4 is **Compute**: a compute dispatch.

**32-bit buffer atomics do not fault.** They act on `address & ~3` (`SpirvRuntimeBuffer.cpp:1071`), from **7e4ce1ab3d** (Nahid Delic, merged in #6094): "The RDNA2 ISA (8.1.7) ignores the two low address bits of dword or wider non-formatted accesses in alignment mode DWORD. MXGP 26 (PPSA30839) sets bits with buffer_atomic_or at odd byte offsets, which recorded an unaligned BDA fault and dropped the atomic."

**What never records Unaligned** (the "which access sizes and alignments are refused" question):
- **Plain stores:**
  - `EmitBdaWrite` (`SpirvBdaRead.cpp:655-675`) and `EmitBdaStore` (`:729-748`) send an 8- or 16-bit store, or a dword store with `address & 3`, to `write_bda_bytes` (`:677-727`). That writes one byte at a time through `get_bda_write_pointer`.
  - `BdaAddressUnaligned` (`:119-121`) only chooses between that path and the dword path.
  - Multi-dword stores (`:750-820`) fall back to per-dword, then per-byte.
- **Plain loads:** misaligned spans also take a byte loop (`:205`, `:582`).
- **Granularity:**
  - The SPIR-V side issues byte stores through `PhysicalStorageBuffer` `uint8` pointers, with an alignment operand of 1.
  - The write-back marks written pages at 4 KiB (`WrittenPageShift` 12, chunks of 32 pages, `BdaAbi.hpp:56-70`).
  - Neither limits alignment.
- **What can't be expressed** is a single atomic at a misaligned address. SPIR-V `OpAtomic*` through a `PhysicalStorageBuffer` pointer has no alignment operand, so the pointer must be aligned to the atomic's size. No host atomic covers 4 bytes at an address ≡ 3 mod 4.

- **Byte and short stores exist** as their own opcodes: `GLOBAL_STORE_BYTE`, `GLOBAL_STORE_SHORT`, the `*_D16_HI` forms and the `FLAT_*` equivalents. 2. **The rule for misaligned atomics in each mode.** Ignored low bits, a memory violation, or undefined?
3. **Which `alignment_mode` the PS5 runs.** This is unmeasured; a hardware oracle run on gfx1013 would settle it.

## 3. Gap or guard

**If question 1 above says yes (DWORD mode, low bits ignored, FLAT like MUBUF): a gap.**
- AnyPS5 is then inconsistent: since 7e4ce1ab3d it serves a 32-bit `buffer_atomic` at an odd byte offset on the containing dword, but drops the same 32-bit `global_atomic`/`flat_atomic` (`EmitBdaAtomic`, `SpirvBdaRead.cpp:829-831`).
- **The exact handling is the same as 7e4ce1ab3d's:**
  - **4-byte atomics:** act on `address & ~3` with the unshifted data, the same scope and semantics, and note the write at the aligned address.
  - **8-byte atomics:** take `address & ~3`, and still fault when that is 4 mod 8. Here `0x…423 & ~3 = 0x…420`, which is 8-aligned, so it would be served.
- **Ordering:** this is one host atomic on one aligned word, so atomicity and ordering are unchanged. It needs no read-modify-write.
- A split into byte or short pieces, or a read-modify-write under the fault ABI, would **not** be exact. It would turn one atomic into several non-atomic steps that other lanes can interleave with. Neither the hardware nor this rule asks for it.
- The same question applies to `ApertureAtomic32/64` for flat atomics into scratch, and should be settled from the same ISA text.

**If the console runs STRICT, or misaligned atomics are violations: a guard,** and the address is probably wrong. What could produce `…423`:
- **A byte offset added to a dword pointer.** For example, base + index×stride + 3 where the guest meant a dword index, or a byte lane of a packed struct used as an atomic target. This is the MXGP pattern, which on hardware relies on the low bits being ignored. That points back to the gap reading.
- **A misread base.** A V# `BASE_ADDRESS` decoded with the wrong bit range, or a 64-bit pointer read from an SRT at the wrong offset, so its low bits come from a neighbouring field.
- **A lane value from a wrong VGPR or SGPR** feeding the address. For example, a `v_readlane` replacement or a pointer `phi` that picks the wrong source.

**My reading:** this is most likely the gap. It is the known MXGP pattern, AnyPS5 already treats the buffer form that way, and 16 or more pcs hit one odd address. That is what code with many atomic updates on one packed counter looks like, not one bad pointer. **Still to confirm:** §2 question 1, and the trace in §5 to name the opcode.
