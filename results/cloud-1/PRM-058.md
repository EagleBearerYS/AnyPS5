## Part 2: what our commits run in this test (for reference; the threshold is not met under interleaving)

The test sets `APS5_GPU_HEAP=1` and leaves `APS5_GPU_PATH` unset. On lavapipe `DescriptorHeapEnabled()` is false as well, so the descriptor heap is off. With that, per dispatch, draw, write or fill, our 8 commits run only the following (`git diff 5547aa11ef 9e843c1a9e`):

- **Device setup, once:**
  - `VulkanDevice.cpp:2091-2095` calls `GpuPathEnabled()`, which is false. So `deviceImagePath` stays false and no `DeviceImageTable` is created (`:2116`).
  - `VulkanDevice.cpp:3797` sets `target.deviceImageTables = state->deviceImagePath`, which is false.
- **Per dispatch:**
  - `Dispatch.cpp:173`, `if (request.target.deviceImageTables) …`, which is false.
  - `Dispatch.cpp:442-445`, `ExpectDeviceImages(...)`. That returns true at its first line, `HeapStages.cpp:605`: `if (!result.deviceImageTables || …) return true;`.
  - `VariantValidation.cpp:95-98`, `if (variant.compiled->deviceImageTables)`, which is false on a dispatch-cache lookup.
  - `DispatchLookup.cpp:116`, a new `EntryOutcome::DeviceImageFallback` case in the outcome switch. It is never produced here.
- **Per draw:**
  - `Draw.cpp:873-875`, a loop over the draw's programs calling `ExpectDeviceImages`. Each call returns at the same first line.
  - `DrawCapture.cpp:48` and `ShaderRegistry.cpp:1229`, `if (request.target.deviceImageTables)`, which is false.
- **Per guest store** (the test's fills and labels go through these):
  - `GuestMemory.cpp:1720`, `ownWriteSerial.fetch_add(1, std::memory_order_release)` in `storeOwn`'s `stampStored` step.
  - `GuestMemory.cpp:1768`, the same in `markWritten`.
  - Each sits directly before `++tracker.generation`, inside the tracker stamping. That is one atomic increment per stamped store.
  - Its only readers are `expectationState()` (`HeapStages.cpp:539-540`, reached only after `ExpectDeviceImages`' early return at `:605`) and `DeviceImageTable::refresh` (`DeviceImageTable.cpp:445`, only when a table exists). Neither runs here.
- **Shader compile** (the test runs with `ANYPS5_NO_SHADER_CACHE=1`, so it compiles per run):
  - The recompiler's device-column planning is gated on `request.target.deviceImageTables && gpuModeStage && …` (`Recompiler.cpp:337`), which is false.
  - Commit 1 does add four trailer words wherever an image-table map is built (`AppendTrailer`, `ImageTableAbi.hpp`). That cost is per map, at resolve time. I did not check whether this test's shaders use image tables.
- **Struct layout:** `DispatchEntry` gains one `std::uint64_t` counter, `deviceImageFallbacks` (`DispatchCache.hpp:70`), and `EntryOutcome` gains one value (`:94`).

**What the window depends on:** the test's window is `SatisfiedWaitDrainsOverlappingQueuedWork` (`PipelinedFill.cpp:189-221`). It submits a WAIT_REG_MEM whose address the blocked draw-pipeline item covers, then polls up to 3 s for `DrainRequestsByOpcode(0x3c)` to move. If the queue shows 2 outstanding items first, it reports "skipped an overlapping queued write". That race is decided by how soon the submit thread reaches the WAIT_REG_MEM drain, against how soon the label behind it gets queued. Neither path goes through any of the lines above except the store serial.

**Conclusion of the reading:** I find no work of ours on the submit or drain path beyond those guard checks and one atomic increment per store. I don't see how that could widen the window measurably. The interleaved counts agree with that, though they cannot rule out a small effect.
