## The three lines

All three print from the existing timeout report, under the same gate: after `APS5_GPU_WAIT_TIMEOUT_MS`, once per label address. They come right after v3's `wait submitted` line. No new switch was added, so there is no new `ENVIRONMENT.md` row.

### L1: the submission in two moments

```
[gpu]   label 0xA submitted by the title at stamp A value V0 (+T0 ms), checked at stamp N value V1 (+T1 ms), kind submit; now stamp S (+T ms)
[gpu]   label 0xA tail copied at stamp A value V0 (+T0 ms), checked at stamp N value V1 (+T1 ms), kind rewind-tail, valid bit seen +V ms; now stamp S (+T ms)
```

- **Copy moment:** taken in `copySegment`, which `Driver::Submit` reaches through `copyCommands` before `AwaitRegistrationPreparation()`. A REWIND tail is captured the same way in `executeRewindTail`.
  - It is recorded for every `WAIT_REG_MEM` (7 dwords) and `WAIT_REG_MEM_64` (9 dwords) packet on memory.
  - It records `eventSerial` and the raw label value: 32 or 64 bits, read only if the address is aligned and readable.
- **Check moment:** taken in `noteHeldAtSubmit`, with the same stamp and value.
- **REWIND tails:** `valid bit seen` is when `executeRewindTail` saw `RewindValid`. That is the moment it was entered if the bit was already set.
- **Times:** `+ms` uses `TraceMs()`, the origin of the `[gpu]` trace lines. Each moment reads the clock once per submission:
  - T0 is when the submission's first wait was copied;
  - T1 is when its first wait was checked;
  - the report prints 0.1 ms, so nothing is lost. Stamps and values are per wait.
- **Fallbacks:**
  - `submission moments not recorded`: the landing path (`landPendingWaits`) has no submission check.
  - `submission copy not recorded` or `tail copy not recorded`: a wait that `copySegment` inserted without a packet copy.

### L2: the CPU side

```
[gpu]   label 0xA block 0xB: watched; write generation at the check G0, tracker generation now G; stamp S cpu stamp C, after a collect stamp S2 cpu stamp C2; stamped after the check yes|no, a CPU store collected after the check yes|no
[gpu]   label 0xA block 0xB: not watched, no write stamps; write generation at the check G0, tracker generation now G
```

- **`stamp` and `cpu stamp`:** the tracker's `stampOf` and `cpuStampOf` for the label's 64 KiB block, read through a new `GuestMemory::StampsOf`.
- **Before and after:** values are printed as found at the timeout, then again after `CollectWritesUncached` over the label's page.
- **What the check records:** only the write generation (`WriteGeneration()`, lock-free).
  - **Deviation from the task:** the task asked for the block stamps and the watched state at the check too.
  - **Why:** reading them takes the tracker lock, and the check runs under the driver mutex for every wait packet.
- **The two yes/no flags** compare the stamps found after the collect with that generation.
- **Caveat:** "a CPU store collected after the check" means a collect after the check found a store. The store may itself predate the check if nothing collected the page in between.

### L3: producers on every queue

```
[gpu]   label 0xA writers pending or running: queue 0xQ serial S (running), queue 0xQ serial S (pending, K ahead of it) | none
[gpu]   label 0xA queue 0xQ: <state>; N pending        (one line per queue worker)
```

- **`<state>`** is one of:
  - `idle`, or `idle (dormant)` for queue 0;
  - `not executing, next pending serial S`;
  - `executing serial S before its first packet`;
  - `executing serial S at dword D opcode 0xOP`, then one of:
    - `, waiting on 0xX function F ref 0xR mask 0xM` while in `waitMemory`;
    - `, waiting on the REWIND control word at 0xX` while in `executeRewindTail`;
  - `executing serial S after its last packet`.
- **Writers** are matched against the dword through `labelWrites` of pending submissions and `runningWrites` of the running one.
  - A REWIND tail's writes are now added to `runningWrites`, so a producer inside a tail is listed too.
  - `runningWrites` is diagnostic only: v3's check and L3 are its only readers.
- **Locking:** the line takes the driver mutex once, at the timeout. No `waitMemory` caller holds it: workers execute outside it, and so does the landing path. The GPU mutex is not held at the report either.
- **Per-label prefix:** every state line carries its label, so two reports that interleave can still be told apart.
- **Worker state:** each worker gets `executingSerial`, set at dequeue and cleared under the mutex at completion. It also gets `executingPacket` on its own cache line, holding `(cursor + 1) << 8 | opcode`.

## The test

`LabelWaitHistory.cpp --timeout-reason` (100 ms timeout) keeps v3's case and adds three. Each case finds its lines by the label's prefix and asserts them.

1. **Cross-queue producer** (the case the task asked for):
   - **Setup:** queue 0x21 runs [wait gate == 1, RELEASE_MEM label = 1]. Queue 0x20 runs [wait label == 1, WRITE_DATA done].
   - **L1:** copy ≤ check ≤ now, in stamps and in ms, with the timeout at least 100 ms after the check.
   - **L2:** the block is the label's 64 KiB block.
   - **L3 writers:** `queue 0x21 serial S (running)`.
   - **L3 states:** queue 0x21 is executing that serial at dword 0, waiting on the gate. Queue 0x20 is waiting on the label.
   - **End:** the gate is then opened, and the wait must end.
2. **REWIND tail:** the submission is [REWIND, wait, WRITE_DATA], with the control word released 20 ms later.
   - It asserts `kind rewind-tail`, with valid bit ≤ copy ≤ check.
   - It asserts queue 0x20's waiting line.
3. **Watched label:** this case runs only when guest write watching is on; here it is, through userfaultfd.
   - The label sits in a 64 KiB block registered with `GuestWriteWatch` (the arena on Windows). The CPU stores 7 into it after the submission.
   - It asserts `watched`, both flags `yes`, and a CPU stamp after the collect greater than the generation at the check.

## Cost when no wait times out

**Per wait packet at submit:** this applies only to `WAIT_REG_MEM`/`_64` packets on memory.
- **At the copy:**
  - three atomic loads: the event stamp, `ForgetSerial()` and `AccessSerial()`;
  - one `DecodeWait`;
  - one `GuestMemory::Accessible` lookup, plus the label read;
  - one 64-byte entry in `waitCopies`.
- **At the check:**
  - two atomic loads: the stamp and `WriteGeneration()`;
  - a binary search in `waitCopies`;
  - the label read.
- **Accessibility:** the check reuses the copy's answer while `ForgetSerial()` (even) and `AccessSerial()` are unchanged. These are the two serials the page-state cache itself is invalidated by. So the copy's lookup replaces v3's lookup at the check, and the net count stays at one.
- **Clock:** two clock reads per submission that has waits.

**Elsewhere:**
- **Per packet in execution:** one relaxed store to the worker's `executingPacket`, on its own cache line. The TLS pointer is read once per submission.
- **Per submission:** three stores.
- **On the timeout path only:**
  - one driver-mutex hold to list the workers;
  - one uncached collect of the label's page.

**Measured with a scratch bench, not committed:**
- **Setup:** one ACB of 4096 already-satisfied `WAIT_REG_MEM` on queue 0x20, 40 rounds. The same binary ran against the base library (1999b77b13) and the head library, alternated five times.
- **Submit, minimum per run:**
  - base 3.38–3.51 ms;
  - head 3.72–3.89 ms;
  - **+86 ns per wait packet**, about 10% of the submit cost of a submission made of nothing but waits.
- **Submit to idle, median per wait:** base 2.11–2.88 µs and head 2.20–3.00 µs. The ranges overlap; nothing measurable.
- **What steady_clock costs here:** 31 ns per call (TSC).
- **An earlier version of the commit was not pushed:**
  - It did a second `Accessible` per wait and read the clock per wait.
  - It cost **+750 ns per wait**, because on Linux `Accessible` is a `process_vm_readv` syscall.
  - I reworked it as above before pushing. On Windows, `Accessible` reads cached page spans, so even that version would have cost much less there.
