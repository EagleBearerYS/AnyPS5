## Where each PR meets #4943, checked in code

None of the failures above involves #4943's code. I read #4943's change against each PR's diff for the semantic breaks a clean merge wouldn't show. None of the 12 PRs touches `DrawRelocate.cpp`, `DrawCapture.cpp`, `SrtEvaluator.cpp`, `DrawCache.hpp` or `DispatchCache.hpp`.

- **Field-by-field copies in the relocation** (`Execution/src/Driver/Draw/DrawRelocate.cpp:175-246`). `relocateDrawEntry` copies a `DispatchVariant` field by field (`copy->runs` … `copy->vertexInfo`, line 225), and builds a fresh `DrawEntry` with only `decode` and `stages` (line 198). A PR adding a field to either struct would merge cleanly but lose that field on every relocated hit. **No PR adds one:** no diff touches `DispatchCache.hpp` or `DrawCache.hpp`.
- **#6243 (T# record selection in the SRT walker).** The question is whether a user-data word could look relocatable while #6243's selection depends on its value. #4943 tracks user-data use only in the evaluator:
  - `SrtEvaluator.cpp:200-205`: a user-data word used as a raw read's base is marked `asBase`;
  - `SrtEvaluator.cpp:243`: the reads it bases are recorded;
  - `SrtEvaluator.cpp:422`: any other `GetUserData` is marked `asValue`, which makes the word not relocatable (`DrawRelocate.cpp:59`).
  - #6243's `Select` (`ResourceMaterializer.cpp`) evaluates the selection through `walker.EvaluateDescriptorSource`, so it goes through the same evaluator and is tracked. Its table record reads come from a V# loaded from memory (origin −1), so they don't move with a relocated word.
  - #6243 also changes `ShaderDiskCache.cpp` (`TableColumn` 80→88 bytes and 15→17 fields, `DescriptorSource` 160→168), which sits next to #4943's `RecompileResult` 472→496 and `BindingAllocationResult` 160→184 asserts. The merge compiles, so all the static_asserts hold together.
  - **Clean.**
- **#6636 (address-based draw build reuse).** Its only change in #4943's file `Execution/src/Driver/Draw/Draw.cpp` sorts `snapshots` by address and size after `snapshot()` builds them. #4943's run tagging sorts its own region copy before `tagVariantRuns` (`DrawCapture.cpp:161-164`), and `relocateDrawEntry` shifts runs by base, so it doesn't depend on snapshot order. Its other changes are in the graphics side (`ShaderResources`, `GuestBufferMemory`). **Clean**, and its new `agc_driver_address_draw_reuse` test passes on the merge.
- **#6683 (exact sample order).** It adds `pixel.sampleOrder` to the decode (`DrawDecode.cpp`, from `HostSampleOrder(state)` on the current device), to `sameDecode` (`DrawRegisterKey.cpp`) and to the stage lookup key (`DrawLookup.cpp`).
  - A relocated draw reuses the donor's whole decode (`DrawRelocate.cpp:198`, `decode = donor->decode`). That holds only if the donor saw the same state and device.
  - #4943's alias key mixes the full register shape (`DrawRegisterKey.cpp:148`, `mixOther(shapeKey)`, everything but the user words) and the device serial (`:154`), so a donor always has the same `sampleOrder`.
  - **Clean.**
- **The other eight** (#6730, #6457, #6479, #6678, #6646, #6475, #6455, #6682; #6451 only adds sample-location state) change host imports, write tracking, unit shadows or the recorder. None of those is something #4943's relocation reads. **Clean.**
