## Verdict

The exact path is possible on the host, and it is built: the PM candidate (stand-in + shader remap + swap at the pass bounds).

- **Where it's exact.** Every multisampled draw whose 2x2 pattern holds one set of positions in every pixel, in any order. This covers Village's and RE4's 2x checkerboard (x = +4/16 and -4/16, indices swapped on odd rows), on any device that has:
  - `shaderStorageImageMultisample` with a uint storage view of each colour format at the sample count;
  - `sampleRateShading`;
  - a depth format that FragDepth writes back exactly: D16, D32F, D16S8, D32FS8. Not D24.
- **How exact.** On lavapipe, every swap kind round-trips bit for bit and is permuted exactly. The shader's SampleID and coverage remaps are exact. Five sabotage runs each turned the test red: three on the exact path and two on the scene harness.
- **Still unproven: the end-to-end comparison on a real device.** `--grid-reference` compares Village's checkerboard bit for bit, through the exact path, against a reference:
  - the composite of four renders, each with one pixel's locations in every pixel, picked by pixel parity;
  - on a device with the 2x2 grid (AMD), also the native grid, which must equal the composite.

  It runs on any device with custom sample locations at 2 samples, so the 3070 can run it too. It has not run here: lavapipe has no `VK_EXT_sample_locations`. The commands are below.
- **Fallback.** GAC-030's fallback (#6451) stays behind the same decision, `HostSampleLocationsFor`, as its refusal branch. It applies when:
  - a requirement is missing;
  - or the pixels hold different positions.

  The log line names the reason.
- **What it costs.** Two passes over each multisampled attachment per render pass that draws with the stand-in.

  My bandwidth estimate for a 3070 at Village's size (1920x2160, 2x) is about 0.19 ms per colour swap and 0.28 ms per depth swap per direction. That makes about 1.5 ms per frame for one depth-only pass plus one colour pass. This is an estimate, not a measurement: the coordinator measures it with the benchmark mode (command below).
- **Still approximate after this branch.** One-sample targets under a varying pattern: #5907's sample-zero path, and the explorer's "rasterize with the targets' fewer samples" rule.
  - With one sample per pixel, Village's rows put sample 0 at different positions (+4/16 on even rows, -4/16 on odd rows).
  - No reordering can fix that, so on a device without a 2x2 grid at one sample (the 3070) it remains GAC-030's approximation.
  - The diagnostic's "stand-in draws 1x" counter tells whether Village has such passes. An exact path for them is sketched under item 1, option E.

## 1. Exact path: options weighed

Each option is weighed for Village's 2x checkerboard on a device without a 2x2 grid:

| Option | Exact? | Cost | Verdict |
|---|---|---|---|
| A. Stand-in + shader remap + pass-bound swap (PM candidate) | **Yes**, for same-set patterns: coverage, depth, stencil and interpolation run at the guest's positions, and only the index order differs, which the swap and remap undo. | 2 passes per MS attachment per pass. Colour: about 66 MB per direction at 1920x2160 2x RGBA16F (odd rows only). Depth: a 66 MB copy plus about 33 MB for the per-sample pass. Shader: about 10 ALU per SampleID or coverage access. | **Built.** |
| B. Row-parity split: draw twice, once per row parity, with that parity's locations, and kill the other rows | No, in general. The parity kill must happen before depth and stencil writes. A shader kill forces late Z, which changes early-Z shaders with side effects. A stencil row mask takes the guest's stencil. A scissor or discard rectangles cannot express 1080 interleaved rows. | 2x vertex and raster work for every draw in those passes. | Rejected as a path. The grid-reference test uses the idea as its oracle: it composes four whole renders by pixel parity after readback, where nothing has to be killed. |
| C. Reader-side remap: leave host order in memory, remap in every consumer | Only for consumers the driver can see and key. Every MS reader shader would be keyed by the producer's order per binding (`image_load` with a sample index, `image_msaa_load`/FMASK). Non-averaging resolves would be remapped. Swaps are still needed when the next pass draws with another pattern. | No swap bandwidth, but per-binding provenance and reader variants. | Rejected: wider and more fragile than A, and still needs A's swap. |
| D. Shader-side reconstruction and interpolation only (InterpolateAtOffset per pixel, as #6470 does for barycentrics) | No. It fixes interpolated attributes only. Coverage, depth and stencil stay at the stand-in positions, so each odd-row sample is covered and depth-tested at the other sample's position. | Cheap. | An approximation, not a fix. |
| E. (for one-sample targets, not built) Render a 2x temporary with the same-set stand-in, then keep each pixel's guest sample 0 | Yes for one-sample targets under a 2-sample same-set pattern. | A 2x temporary, a broadcast in and an extract out per pass. | Out of this task's scope. It is the follow-up if the diagnostic shows Village has 1x stand-in passes. |

### What A does

**Decision.** `Graphics/src/SampleOrder.cpp`: `HostSampleLocationsFor(context, state)`, called by the pipeline, the draw decode and the pass hooks.
- If the device has the grid: a 2x2 grid with no order. Devices with the grid are unchanged.
- Otherwise `SameSetSampleOrder(state)` (`State.cpp`) is computed: one nibble map per 2x2 pixel, host index to guest index. Village and RE4 both give `{0x76543210, 0x76543210, 0x76543201, 0x76543201}`.
- If `SampleOrderRefusal` returns empty, the result is a {1,1} grid plus that order.
- Otherwise it is GAC-030's stand-in alone, logged once per sample count with the reason:
  - "the device lacks sampleRateShading";
  - "color format F has no storage view at N samples";
  - "depth format F is not written back exactly through FragDepth";
  - "depth format F cannot be sampled at N samples";
  - "its pixels hold different locations".

**Shader** (`SpirvModuleEmitter.cpp`). A pixel shader compiled with an order:
- picks its pixel's word from `gl_FragCoord` parity in the prologue;
- reads SampleID as `(word >> 4*id) & 7`;
- writes its sample mask through the order (exported masks, alpha-to-coverage masks, the quad coverage mask);
- reads `gl_SampleMaskIn` back in guest order on the quad-mask path.

A uniform partial `PA_SC_AA_MASK` that the order does not preserve moves from the pipeline's `pSampleMask` to the shader's quad-mask path (`SampleMaskFollowsOrder`, `QuadSampleMasks(state, order)`).

**Swap** (`RecordSampleOrder`). It runs before `Begin` and after the pass ends. In the recorded path it runs in the recorder's `afterPass` closure, so a continued pass swaps once, at its real bounds. The pass key already holds every sample location, so draws sharing a pass share one order.
- **Colour:** an in-place compute pass through a uint storage view (`R8`/`R16`/`R32`/`RG32`/`RGBA32 UINT`) of the target. The target is created with `MUTABLE_FORMAT | EXTENDED_USAGE | STORAGE` only on devices without the grid. The attachment and sampled views restrict their usage to exclude STORAGE.
- **Depth:**
  1. `vkCmdCopyImage` of the render region into a cached temporary of the same format (at most 4 kept);
  2. a render pass on the attachment (LOAD/STORE, GENERAL) with the stand-in sample locations;
  3. per-sample shading, a fullscreen triangle with depth test ALWAYS and write, and `gl_FragDepth = texelFetch(copy, map[SampleID])`.

  Pixels whose map is the identity discard, so Village's even rows aren't touched.
- **Stencil:** with `VK_EXT_shader_stencil_export`, the same pass writes `gl_FragStencilRefARB` from the copy's stencil view (REPLACE, write mask 0xff). Without it:
  1. the depth pass first zeroes stencil (REPLACE, reference 0);
  2. then 8 passes, one per bit, discard where the source sample's bit is 0 and REPLACE with reference 0xff and write mask `1 << bit`.

  A depth format whose host format has stencil the guest does not use loads and stores the stencil untouched.
- **Load and store ops** (`PlanSampleOrder`):
  - LOAD: swap in; CLEAR: no swap in (a clear is the same in every sample); STORE: swap out; DONT_CARE: no swap out.
  - This driver's passes always LOAD and STORE (`Pipeline.cpp:381-401`), so every planned attachment swaps both ways.
  - `Draw.cpp` takes its attachment list and methods from `PlanSampleOrder`, which is what the mock test covers.

**Keys and versions.**
- Pipeline and library keys add the four context fields the decision reads.
- The pixel shader's order keys its variant and is serialized.
- **FormatVersion 40.** Open PRs take 37 (#6243, #6280, #6412, #6454) and 39 (#6470); 38 is unused. 40 is the next value above every in-flight one, so the version never moves backwards whichever lands first. Taking 38 would go backwards if this landed after #6470.
- **Request serialization version 32.** #6470 takes 31, and both add fields after `reversedBlend`. A tree with both reads #6470's fields at ≥ 31 and the order at ≥ 32.

**`agc_driver_sample_order` (default mode)**:
- **Swap round trips.** For each colour format (R8, R16F, RGBA8 sRGB, RGBA16F, RGBA32F, through every alias size) and each depth/stencil method (D32F, D16, D32FS8 depth only, with export, with bits), at every sample count the device renders:
  1. fill distinct per-sample values;
  2. swap to host order on a 16x10 region of a 20x12 image;
  3. check every sample equals `before[map[s]]` inside the region and is unchanged outside;
  4. swap back and check bit for bit.
- **Shader SampleID remap:** a store shader under a rectangle whose edges cut pixels at x + 0.5. Each pixel stores the guest indices of the host samples that the standard locations put on the covered side, checked for every pixel in both parities, plus the unmapped baseline.
- **Exported coverage remap:** reset depth, export a guest mask, then probe with early Z. The guest samples that took the depth equal the guest mask.
- **Scene checks:** the grid-reference scene (below), drawn through the driver with the standard locations at each sample count the device renders. Every colour sample must hold its own sample index in z and w, and depth must stay in [0, clear] with samples both at and below the clear value. This runs the AMD mode's draw and readback code everywhere, CI included.

**`agc_driver_sample_order_grid_reference`**:
1. **The scene.** Village's 2x pattern at 64x32:
   - a depth-only pass: a full-screen clear, then two slanted triangles with LESS;
   - a colour pass (RGBA16F + D32F): a full-screen triangle with ALWAYS, then a slanted triangle with LESS_OR_EQUAL. Both use a per-sample shader exporting (perspective I, J, SampleID, SampleID).
2. **The renders,** in one process:
   - the exact path: Village's pattern with the grid forced off (`sampleLocationGridSampleCounts = 0`);
   - the fallback: the same with `storageImageMultisample = false`;
   - the reference: four renders, each with one pixel's locations in every pixel. A uniform pattern needs no grid; the renders are composed by pixel parity. Every sample is rasterized, depth-tested and shaded independently at its own location, so this is what a 2x2 grid draws.
   - on a device with the 2x2 grid, also the native grid.
3. It reads back every sample of colour and depth, and runs the scene check on each render.
4. It requires:
   - the native grid to equal the composite (where there is a grid);
   - the exact path to equal the composite bit for bit;
   - the fallback to differ, so the scene tells the paths apart.
5. A device whose refusal rules exclude the exact path skips with the reason ("skipped, the device does not put the checkerboard's samples in the guest's order: ..."). On the 3070, that line would mean Village gets only the stand-in.

## 6. Adversarial review

- **Attachment kinds.**
  - Colour of 1/2/4/8/16-byte elements goes through the uint alias, bits preserved, so sRGB, float NaN payloads and denormals are untouched. 12-byte formats are refused (no alias) and fall back.
  - MRT swaps each target.
  - Depth: D16/D32F exact. D16S8 is exact where the host keeps D16S8. Where the host substitutes D24S8 it is refused: unorm24 doesn't round-trip through float.
  - D32FS8 with export or bits. Stencil-in-host-only formats keep their stencil.
  - Depth outside [0, 1] in D32F: FragDepth would be clamped unless depth clamp is off and `VK_EXT_depth_range_unrestricted` is enabled. The driver enables the extension where available (lavapipe has it). Guest Z clamps make such values rare; noted, not tested.
- **Blending, logic ops, dual source.** Within the pass, source and destination of host sample h both belong to guest sample `order[h]` (shaded at its position, stored at its swapped-in index), so per-sample blending is exact. Alpha-to-coverage masks are built in guest indices, including the dithered table, and stored through the order.
- **Load/store combos.** Always LOAD/STORE in this driver; the plan rule above covers CLEAR and DONT_CARE.
- **An interrupted pass.** When the recorder ends an open pass early (a dispatch, a copy, a sampled read, another pass key), its `afterPass` swaps out. The next draw's `Begin` swaps in again. That is correct, and costs a pair of swaps per interruption.
- **Feedback.** A draw sampling an MS colour target it renders to is refused already: "sampling a multisampled color target the draw renders to is not implemented". So is native MS depth feedback.
- **Continued passes across patterns.** The pass key holds every sample location, the target views and the sample count. Two draws in one pass therefore have one order: refusals depend on the formats, which the views fix.
- **A compatible depth image read between passes.**
  - Each pass swaps back at its end, so `DepthSurfaceTexture` reads guest order.
  - The depth swap pass uses the stand-in locations whenever the draw used them (`located`), so a sample-location-compatible image is never written or tested with other locations.
  - The copy and the swap pass stay in GENERAL, with no layout transitions.
- **Resolves and queries.** CB resolves run as separate passes on guest order, and averaging is order-free anyway. Occlusion counts are order-free.
- **Recipes.** Draw recipes are excluded for reordering pipelines: they would skip the swap.
- **Threading.** `RecordSampleOrder` runs only under the GPU mutex: `Recorder::Commands` and `CommandBatch` assert it.
- **Lifetimes.** Copy images and per-use framebuffers go to the recorder's keep list, or live in the synchronous path until `SubmitAndWait`.
- **Driver compression.** On devices without the grid, MS colour targets carry `MUTABLE_FORMAT | EXTENDED_USAGE | STORAGE`, which may disable colour compression. A `VkImageFormatListCreateInfo` would help but needs `VK_KHR_image_format_list` (the driver targets 1.1). Written in the debt entry.
- **Found and fixed while testing:**
  - Two pinned serializer layouts: ShaderMemory's derived v29–v20 streams, and `request_serializer`'s v30 upgrades.
  - EXTENDED_USAGE views: the attachment and sampled views now restrict usage.
  - The grid-reference harness's missing geometry stage and component mapping (see 3).
- **Pre-existing, not changed here: raw I/J evaluation location.**
  - All three perspective I/J pairs (sample, centre, centroid) map to one `BaryCoordSmooth` input (`InstructionTranslator.cpp:347-352`), as do the linear ones.
  - The emulated barycentric input gets a Location but never a `Sample` or `Centroid` decoration (`SpirvEmitterHelpers.cpp:283-288`).
  - So without `VK_KHR_fragment_shader_barycentric`, a shader that reads PERSP_SAMPLE I/J raw gets centre values. On lavapipe this showed in 1973 of 2048 pixels; the rest were edge pixels.
  - With the extension, native `BaryCoordKHR` is likewise one variable with no `Sample` or `Centroid` decoration. I have not checked where drivers evaluate it under sample shading.
  - `v_interp` reads go through host interpolation and are not affected. This is independent of the sample order: the exact path and the grid see the same values, so the comparison holds either way.
  - It would be a separate fix: split the barycentric kinds by location and decorate them.
