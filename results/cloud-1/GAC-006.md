## Why the non-imported paths do store the plane

- The expand leaves the plane pending in the write base's storage image (`RunDepthExpandPass`, Graphics/src/DepthSurface.cpp:1076, `MarkDirty`, `unstoredExpands` at 1137).
- `StoreDepthExpandWrites` (1148) stores it ahead of an address-based build only when an import covers the whole plane (1165). That is correct as long as every other reader flushes, and both non-imported readers do:
  - **Heap mirror.**
    1. `AcquireRegistered`, then `refreshHeapRuns` (Graphics/src/GuestBufferMemory.cpp:1621), then `prepareRange`, then `syncRange` (1407), then `FlushGpuWrites` over the whole run, then the recorder's hook `FlushForAccess` (Graphics/src/Recorder.cpp:1002), then `StorageTexture::FlushPending` (Graphics/src/Texture.cpp:3147).
    2. That writes the plane into guest memory and stamps its blocks.
    3. `UnchangedSince(run, verified)` then fails, and `appendChangedBlocks` recopies those blocks into the mirror before the build binds it.
    4. If an import does cover the write base, the store is only recorded. It is still followed by `MarkWritten` (Texture.cpp:4616/4730) and a `SyncThrough` in the hook (Recorder.cpp:1067), so the mirror again recopies the stored bytes.
  - **Copy.** `addCopiedRange` (2665) re-adds the range every build, and `copyRegion` reads it with `GuestMemory::Read` (3554), which calls the same hook first.
- The hook's one exception, the "CPU wrote every block since the image's generation" keep rule (Recorder.cpp:1047, `AccessKeptByCpu` Texture.cpp:3585, `blocksKept` 3547), applies only to accesses of up to 1 MiB (`ClassifyLimit`, Graphics/include/Texture.hpp:253). Village's 15.9 MiB plane and its heap runs are larger.

## What the evidence shows, and checks for one Village run each

- **"CPU view all zero at those dispatches" is expected even when everything works.** The store happens inside the dispatch's own build, during the mirror refresh or the copy, so a sample taken when the dispatch packet starts reads the zeros. The stronger evidence is that 0x2019730000 stays zero.
- Ranked by how well each check fits the symptoms (sampled reads right, buffer reads and the copy's output zero):

| # | Candidate | Village switch or log line | What it shows |
|---|---|---|---|
| 1 | The plane is never stored before the copies | `APS5_TRACE_FLUSH=1`: each store prints `[flush] image 0x20298b0000+… for <reason> 0x…` | No line between the expand and the two copies means no reader flushed it. Lines that name another reason place the store elsewhere. |
| 2 | Part of the write base is imported and read in place without a flush. `StoreDepthExpandWrites` needs one import covering the whole plane (`findImport`, GuestBufferMemory.cpp:1149-1157). Registered ranges over 64 MiB get window imports on access (`windowRun` 860, `rangeImportWindow` 855). A plane across a window edge, or only partly imported, is skipped there, yet the in-place part is read without the hook. | `APS5_BDA_FLUSH=1` flushes in-place regions of address-based builds | If the copies then hold depth, this is it. The fix would be to store when any import overlaps the plane, not only when one covers it. |
| 3 | The flush hook keeps the plane pending because the CPU (or a fill) wrote every block since the image's generation. Only possible if the game reads it in at most 1 MiB pieces. | `APS5_HOOK_FLUSH_CPU_BLOCKS=0` disables the keep rule | If the copies fill, the keep rule misjudges the expand's newer results. |
| 4 | The copies' own stores to 0x2019730000 are refused (a mirror or copy range is read-only in the BDA table) | the log would carry "BDA access failed … the store hit 0x… read-only in the BDA table" (Graphics/src/BdaResources.cpp:282-296, which throws) | Absent from the log means this is ruled out. |

- Also useful in that run: `APS5_PROFILE_DRAW=1` for the `[buffers] image mirrors … unwatched heaps U` and `[gpu] host import budget …` lines. They show whether the write base's range is mirrored, copied or unwatched.

## Separate finding: a window import inside a heap-mirrored range aborts the next build

- **Reproducer.**
  1. Register a write-watched range of 128 MiB and put the write base at its start.
  2. Set the budget to admit a 64 MiB window but not the range (`SetHostImportBudget(HostImportLiveBytes() + 96 MiB)`).
  3. Run an address-based copy (the space mirrors the whole range: its import with `end == 0` is refused).
  4. Run the expand, then the copy. `StoreDepthExpandWrites`' `HostImportFor` makes a 64 MiB window import, `importAccess` with eviction (GuestBufferMemory.cpp:2311).
- **At e1a94e7735 on Linux.**
  - The second build throws "compute shader …: AGC graphics: a heap mirror's range is no longer write-watched" (the `Require` in `refreshHeapRuns`, 1628), and the test process aborts.
  - With `APS5_WRITE_WATCH_IMPORTS=watch` all three rounds pass, with the window import live and the plane correct. With `=unwatch`, or the probe's default here ("imported ranges are compared"), it aborts.
- **Cause.** An import made with `watchedHostPointer == false` unwatches its window (`ImportWatched` with `staysWatched == false`, Execution/src/GuestMemory.cpp:1265, called at GuestBufferMemory.cpp:1036). The cached space's heap mirror of the containing range then finds part of its run unwatched.
- **On Windows** `decideImportWatch` sets `unwatchImports = true` for every device (GuestBufferMemory.cpp:637-640), so a direct (non-alias) window import there unwatches too.
- **Not committed:** the rules forbid a failing test. It belongs in its own task: drop or rebuild the mirror (or keep the window watched) when an import lands inside a mirrored range. The experiment's source is kept locally.
