## Design, and why

Two kinds of writable heap mirror, two mechanisms. Neither binds, copies or reads back the span.

**Resident mirrors (sparse buffers): store pages for unbound blocks, a GPU gather for bound ones.**
- The BDA table marks each unbound run of a writable resident span `Spill`. The shader sends a store into a `Spill` run to a *store page*: a 4 KiB page in a per-build pool (`APS5_BDA_STORE_PAGES`, default 1024 pages, about 4.6 MiB). It is claimed by key `((address - base) >> 12) + 1` in a 16-probe hash table.
- A read of a `Spill` run in the same dispatch looks up the same key and reads the store page on a hit, otherwise the unbound (zero) block. That is the "same-dispatch read" case.
- Bound pages that the written-page record lists are gathered on the GPU into pool slots after the work (`StorePageGather.comp`, recorded in `MarkGpuWrites` after `RecordCopyBacks`). They are compared on the CPU with the `ResidentBuffer` shadow, which equals the device bytes at upload, so the comparison is exact.
- Spilled pages are compared with zero, since the block was all zero in guest memory. Only the bytes that differ are written to guest memory, so a CPU byte written during the dispatch, in the same page or the same dword, survives.
- The block stays unbound; the next refresh binds it from guest memory if it then holds data. Nothing is bound to take a store, so `APS5_HEAP_MIRROR_MIB` is never charged for one.

**Copy-backed mirrors: per-byte store masks.**
- The table marks the span `Masked`. A store claims a page slot as above and ORs one bit per byte it wrote into a 512-byte mask (128 words) beside the slot.
- The write-back copies only the masked bytes from the mapped mirror to guest memory. No reference is needed, and CPU bytes survive at byte granularity.
- Residual, in the debt file: an atomic whose result leaves a byte unchanged still writes that byte back.

**Store pages compile only into dispatches that use them** (added after the cost runs below):
- The store-page code is one shader function, `bda_store_page_pointer`, called from each BDA lookup. In compute shaders the call is gated by a dispatch-time specialization constant, `PipelineSpecialization::StorePages` (8237, default 0). It is retained like the workgroup offsets.
- `VulkanDevice::recordDispatch` binds a variant with `StorePages = 1` only when the dispatch's `BdaResources` carries a store page pool and the module takes the constant. The variant is built once per pipeline and cached next to the split-dispatch variants.
- With 0, a `Spill`/`Masked` access faults `StorePages` (a loud refusal), never a lost store. Graphics shaders keep the call unconditionally.
- Why: Mesa inlines every function, so the probe loop was copied into every BDA access site. That made llvmpipe compile `flat_store` and `runtime_formatted_store*` 23–46 % slower cold and pushed four formatted-store tests over their own 30 s timeout. Numbers are below.

**The pending-write note: known before the dispatch, and the span is the narrowest correct note.**
- Ordering needs it before the dispatch. Host reads, copies, fills, labels and the next address-based refresh of that heap must wait for the storing use. Until the use completes, nothing says which pages it stored: a store can reach any address in the writable span, and the written-page record and masks are only readable afterwards.
- So the narrowest note known in advance is the set of writable spans the dispatch's BDA table exposes, which is the span. A post-dispatch page list can only refine it after completion.
- It is a range, not bytes: it costs no memory proportional to the heap. Its cost is one `Recorder::Sync` per later build over that heap while a storing use is in flight (BF-277's Q2).
- A red shows it is load-bearing: removing it fails the two-dispatch test ("the first of two storing dispatches lost the store of thread 0", below).

**Alternatives weighed:**
- **Bind the whole span** (781dc4525b, BF-278): scales with the committed heap. This is Ghost's stop at 688 of 2816 MiB.
- **Guest memory as the reference:**
  - Wrong on a page the CPU also wrote during the dispatch. The CPU's byte differs from the mirror's upload copy, so the diff treats it as a GPU store and writes the stale mirror byte over it.
  - It can't be made safe without knowing which bytes the GPU wrote, and that is exactly what masks give.
  - Two reds below (`guest-byte`, `guest-two`).
  - For resident mirrors the host shadow is an exact reference at no extra cost, so masks are only needed for copy-backed ones.
- **A synchronous readback after completion:** `CommandBatch` submits the open batch and reaps inside a completion, so it would wait for every in-flight batch.
- **Bitmap residency in the table:** splitting runs by a residency bitmap would lose anchors for the whole heap.
- **In-place import:**
  - Ghost's main heap is a mirror because an in-place import needs the whole heap committed and inside `APS5_HOST_IMPORT_MIB` (default max(6 GiB, RAM/2), capped by the host heap).
  - A storing build could import in place when that holds, and then needs no write-back at all. It is an option for hosts with room, not the answer for a 2.7 GiB heap under a small budget.
- **Loop-free store-page lookups** (to cut compile cost without variants): a direct-mapped or two-choice table refuses on collisions at a rate that grows with the stored page count. The probe loop stays, and specialization removes its cost where it is not used.

## PR body paragraph

Heap mirrors that a shader stores into through addresses no longer bind, copy or read back the whole heap span.

- **Resident mirrors:** a store into an unbound block is redirected to a 4 KiB store page from a small per-build pool (`APS5_BDA_STORE_PAGES`, default 1024 pages, about 4.6 MiB). Reads in the same dispatch find it there. After the use, the stored bytes are compared with zero and written to guest memory, and the block stays unbound. The stored pages of bound blocks are gathered on the GPU and compared with the resident shadow.
- **Copy-backed mirrors:** each store sets per-byte mask bits, and only those bytes are written back. CPU bytes written during the dispatch survive at byte granularity, in the same page or the same dword.
- **The pending-write note** still covers the span. It has to exist before the dispatch, and the span is the only set known then. It costs a range, not bytes.
- **Compile cost:** compute pipelines take the store-page code only through a dispatch-time specialization constant. The driver picks the specialized pipeline only when the BDA table carries store pages, so other compute shaders compile exactly as before.
- **Measured on lavapipe:** a storing dispatch over a 36–72 MiB heap mirror waits 0.1–1.4 ms instead of 15–50 ms. A 2 GiB heap runs inside `APS5_HEAP_MIRROR_MIB=64` with 1 MiB bound.
