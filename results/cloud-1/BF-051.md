# BF-051: does a CPU-side read wait for a BDA-table store recorded before it? Red/green on main (cloud-1)

**Inputs:**
- Upstream main **f8b22edfb** (still main at 07:30Z).
- The test: fork branch `test/bda-store-cpu-read` at **9a87fa97c**, one commit on f8b22edfb ("test(agc): read an indirect record a store through the BDA table wrote before a CPU-path draw"). It adds `core/libs/prx/libSceAgcDriver/tests/execution/BdaStoreCpuIndirectRead.cpp` and nothing else; ctest registers it from the `tests/execution` glob as `agc_driver_bda_store_cpu_indirect_read`.
- Upstream PR 6931 head **a00773731c** ("perf(agc): queue CPU-path indirect draws on the draw pipeline"), fetched with `git fetch upstream refs/pull/6931/head`. Its base is f474fb776 (main of 2026-10-16), 324 commits behind f8b22edfb. It was tested as is, with the same test file copied in.

**Machine:** cloud-1: Intel Xeon @ 2.80 GHz, 4 vCPUs, 15 GiB, Ubuntu 24.04, gcc 13.3.0, wild 0.10.0, lavapipe from Mesa 25.2.8 (LLVM 20.1.2), no /dev/udmabuf.

RESULT:
- **Red on main f8b22edfb: a CPU-side read does not wait for a BDA-table store recorded before it.** 20/20 in each of three cases, run on the test at fork `test/bda-store-cpu-read` 9a87fa97c.
  - The reader is a CPU-path `DRAW_INDIRECT` (`-> cpu (patched SGPR not folded)`). It reads its record as `instances 0` and draws nothing (covered 0 of 1024 bytes).
  - The cases: the writer's draw in the **open batch**, in a batch **submitted but not finished** (gdb: the committer's `Recorder::Submit` runs before the reader's `ReadDrawArguments`), or **held behind a blocking committer item**.
  - The store itself works: the record holds 1 after `WaitIdle` in every run. An `llvmpipe-1` thread writes it in place, after the worker read 0.
- **Memory:** imported in place. Private anonymous 64 KiB blocks, write-watch registered and added to `GuestAllocations`, host-imported through `VK_EXT_external_memory_host` (`host import of …+0x10000 ok`). Nothing is mirrored or copied back.
- **Why** (no single line "syncs" it, because nothing does):
  - The writer binds the BDA page table, so its build is address-based, holds the lease, and runs free. `lease = HoldsLease() && SyncLeaseWork()` is false (Graphics/src/Draw.cpp:2193), giving "recorded with completion".
  - `ShaderResources::MarkGpuWrites` notes only writable descriptor elements as pending writes (ShaderResources.cpp:4702). A table store is known only at completion, from the written-page record (`BdaResources::markWrittenPages`, BdaResources.cpp:307-323).
  - The read, `Pm4::ReadDrawArguments` (Pm4.cpp:869, from Execution/src/Driver/Draw/Draw.cpp:497), goes through `FlushForAccess` (Recorder.cpp:1004). That syncs only on `PendingWriteOverlaps` (Recorder.cpp:1025), which is false here.
  - Any of `APS5_SYNC_LEASE_DISPATCH=1`, `APS5_SYNC_COMPLETION_DRAWS=1` or `APS5_SYNC_DRAWS=1` turns it green.
  - The first test version was green only because a non-resident (linear) writer target makes the draw synchronous (`SubmitAndWait`, Graphics/src/Draw.cpp:2505), and the drain at Execution Draw.cpp:38 waits for that.
- **3b (writer held behind a committer item):**
  - **Main:** the reader **drained** (Draw.cpp:38; 2 items outstanding and the worker blocked for the 500 ms, 20/20), then **read the old record**.
  - **PR 6931 head a00773731c:** the reader **did not drain and did not wait** (3 outstanding, decided before the release, 20/20). It **read the old record** while the writer was still queued.
  - 6931 drains only on `Overlaps(records)`, and `DrawWriteRanges` (WrittenBuffers.cpp:96) has no range for table stores.
  - On 6931 the open and submitted cases read before the writer is even committed (20/20 each). Red 20/20 in all three cases.
- **Fix sketch** (local, not pushed; patches in the result file):
  - **A.** `FlushForAccess` at `ReadSite::IndirectArguments` first finishes the newest lease batch: `Submit` + `FinishUpTo(newestLeaseSerial)`, as the pin waiter does. That is 20 lines.
  - **B**, needed with 6931. A draw binding a BDA page table queues the unbounded range `[0, 2^64)` in `DrawWriteRanges`. That is 1 line.
  - Main+A: green 20/20 × 3 cases. 6931+A: `--open` green 19/20, `--submitted` 20/20, `--held` 0/20. 6931+A+B: green 20/20 × 3.
- **Cost:**
  - A makes each such read wait for the whole lease batch, whether or not the store hit the record: 0.007–0.015 ms on main becomes 12–21 ms (open), 227–276 ms (submitted, 50,000-instance writer) or 14–58 ms (held) on lavapipe. That is one synchronous draw's cost per CPU-path indirect draw, dispatch or index-attribute read that follows address-based work in flight.
  - B makes every `DrawPipeline::Overlaps` consumer (waits, predication, dispatch reads, captures, fills) drain behind an address-based draw.
  - AGC subset with main+A+B: the 51 AGC driver tests whose names match indirect, pipelin, dispatch, lease, address, bda, fill, capture, predicat, wait, label, recorded, copied or hook: main 50/51 (only the new test fails; 4 `agc_driver_pipeline_optimized_readback_*` skip), main+A+B **51/51** (the same 4 skip), 17 s and 18 s. The whole 480-test AGC set was started on main and stopped at 145/480 for time, so it is not a result.
  - Not PR-ready. The choice between making table stores visible before completion and paying a sync per CPU-path read is the driver owners'.
- **The test commit fails on main by design.** It is the red. Under CONVENTIONS it is not PR-ready alone: it needs its fix in the same commit or before it.

## The test

`BdaStoreCpuIndirectRead.cpp` runs PM4 through `sceAgcDriverSubmitDcb`, like `agc_driver_indirect_patched_stage`, whose vertex and pixel shaders it reuses.

**Memory: imported in place.**
- Three 64 KiB blocks: records, writer target, reader target. Each is a private anonymous `mmap`, aligned to 64 KiB, registered with `GuestWriteWatchRegister` and added to `GuestAllocations` as registered guest memory. On Windows it uses the `GuestArena` pattern.
- The writer's address-based build imports them through `VK_EXT_external_memory_host`. `APS5_TRACE_HOST_IMPORT=1` prints `host import of 0x…3d0000+0x10000 ok` for the records block before the read.
- A hardware watchpoint on the record word (gdb) shows the store landing in the guest page itself: an `llvmpipe-1` thread, running JIT code from an anonymous r-x mapping, writes 0 → 1 at the guest address. That happens after the queue worker (thread 26) has already read 0 there.
- Nothing is mirrored or copied back. The writer's outcome is "recorded with completion", not "copied writes".

**The writer** is a direct draw (`DRAW_INDEX_AUTO`). Its pixel shader stores 1 into the record's `instances` word: `v_mov_b32 v12, 1` then `global_store_dword v13, v12, s[2:3]`, with s[2:3] the address from user data. The recompiler turns that into a store through the BDA page table.
- Its color target is tiled (`CB_COLOR0_ATTRIB3 = 0x4dc6c000`) and made resident first by two plain draws, so the draw is recordable (`Graphics/src/Draw.cpp:2081`).
- Profile line: `64x4 1 targets recorded with completion`.

**The reader** is `DRAW_INDIRECT` (`0x24`) over a record `{3, 0, 0, 0}` that the writer turns into `{3, 1, 0, 0}`. The base-vertex location is a patched SGPR, so it takes the CPU path: `-> cpu (patched SGPR not folded)`. It draws into a linear target filled with 0x40.
- Covered bytes != 0 means it read the store.
- Every case also checks that the record holds 1 after `WaitIdle`, so the store itself works.

**Cases** (one argument each; no argument runs all three):
- `--open`: writer and reader in one DCB.
  - The reader drains the pipeline (`Execution/src/Driver/Draw/Draw.cpp:38`), so the writer is recorded into the open batch.
  - gdb on `Recorder::Submit` / `Pm4::ReadDrawArguments` shows the read before that batch's submit.
- `--submitted`: the writer (50,000 instances) plus a `WRITE_DATA` label in DCB 1, the reader in DCB 2.
  - gdb shows DCB 1's batch submitted by the committer (`DrawPipeline::run` → `completeSubmission` → `submitOpenWork` → `Recorder::Submit`) before the reader's `ReadDrawArguments`.
  - The read still sees 0, so the batch was submitted but not finished.
- `--held` (3b): a blocking committer item, as in PR 6931's `agc_driver_pipelined_indirect_draw`, is queued first. It spins on an atomic, without the GPU lock, released after 500 ms.
  - Then the writer and reader go in one DCB. The writer is queued behind the blocker.
  - After 500 ms the test prints `DrawPipeline::Queue0().Outstanding()`. 2 (blocker + writer) means the worker sits in the reader's drain. 3 means it went past the reader, because the DCB's completion is queued as a third item (`deferCompletion`).
  - It also prints a `[bda-store-cpu-read] releasing the blocker` line to stderr. With `APS5_TRACE_INDIRECT_DRAWS=1`, the order of that line and the reader's `[draw] indirect` line shows whether the reader was decided before or after the release.

**The first version of the test was green for the wrong reason.** The writer's target was linear, so it was not resident and not recordable. The committer ran it synchronously (`Graphics::Draw` → `CommandBatch::SubmitAndWait`, Graphics/src/Draw.cpp:2505), and the reader's drain at Execution Draw.cpp:38 waited for that. The red needs the writer actually recorded, hence the tiled resident target.

## Why the read doesn't wait (main f8b22edfb)

1. **The writer runs free.** It binds the BDA page table, so its build is address-based and holds the address-space lease.
   - In `Graphics::Draw`'s outcome block, `lease = resources->HoldsLease() && SyncLeaseWork()` (Graphics/src/Draw.cpp:2193) is false unless `APS5_SYNC_LEASE_DISPATCH` is set.
   - The only completion work is the BDA fault check (`NeedsCompletion`, ShaderResources.hpp:181). So the draw is recorded without a wait: "recorded with completion".
   - Its lease batch serial is noted for the pin waiter (`CountLeaseOutcome(false, Submissions() + 1)`, Draw.cpp:1533).
2. **Its store is not a pending write.**
   - `ShaderResources::MarkGpuWrites` (ShaderResources.cpp:4679) notes `recorder.NotePendingWrites(guestMemory.Writes())` (:4702). That list holds only the writable descriptor elements (`AddWritable`).
   - Where a store through the table lands is known only after the batch completes, from the fault buffer's written-page record: `BdaResources::CheckFault` → `markWrittenPages` (BdaResources.cpp:242, :307) → `GuestMemory::MarkWritten` (:322).
3. **The read only waits for listed writes.**
   - `Pm4::ReadDrawArguments` (Execution/src/Pm4.cpp:864-872) reads with `GuestMemory::Read` at `ReadSite::IndirectArguments`. It is called from `Driver::draw`'s CPU path (Execution/src/Driver/Draw/Draw.cpp:497, after `recordQueuedLabelsBeforeRead` at :493).
   - That goes through the flush hook `FlushForAccess` (Graphics/src/Recorder.cpp:1004). The hook syncs only if `Recorder::PendingWriteOverlaps` (Recorder.cpp:1025, :2831) finds the range in some batch's `writes`. Here it doesn't, so nothing waits.
   - It does not consult the lease serials, the BDA ranges, or the written-page record.
4. **So one comment doesn't hold here.** "The reads wait for the producing batch through the flush hook" (Graphics/src/Draw.cpp:2154) is true for descriptor-buffer writers, labels and copied writers. It is not true for a store through the BDA table.

**Switches that turn it green** (one run each, both cases):
- `APS5_SYNC_LEASE_DISPATCH=1` (the writer becomes "recorded then waited (lease)").
- `APS5_SYNC_COMPLETION_DRAWS=1` (the writer becomes synchronous).
- `APS5_SYNC_DRAWS=1` (every draw synchronous).

**Why 6931 doesn't drain.** 6931 drains at an indirect draw only if `pipeline.Overlaps(records)` or `Overlaps(count)` (its Execution/src/Driver/Draw/Draw.cpp:42-43).
- A queued draw's ranges come from `DrawWriteRanges` (Execution/src/Driver/Memory/WrittenBuffers.cpp:96): written descriptor buffers (`visitWrittenBuffers`, :17, `GuestBuffers` descriptors only), storage images, color, DCC, CMASK, depth and stencil.
- A store through the BDA table is in none of them, so the writer's item carries only its color target.
- **On 6931 the other two cases degrade the same way.** In `--open` and `--submitted` too, the reader reads before the writer is committed (20/20 each; the writer's commit line prints after the read).
- So on 6931, `--submitted` never reaches "submitted but incomplete". The reader runs ahead of the committer.

## Fix sketch and its cost (not PR-ready, not pushed)

Two parts, both local. The patches are kept on cloud-1 as `/home/user/bf051/fix-sketch.patch` (A) and `fix-sketch-drain.patch` (B); the text is in the appendix.

**A. An indirect-argument read finishes the lease batches first.** 13 lines in Graphics/src/GuestBufferMemory.cpp, 7 in Recorder.cpp.
- New `SyncLeaseBatches()`, next to `SyncLeaseWork`, under the GPU lock. If the newest batch recorded with a lease (`newestLeaseSerial`, noted by `CountLeaseOutcome`, GuestBufferMemory.cpp:2243) is newer than `finishedLeaseSerial`, it submits the open batch when that is the one and calls `Recorder::FinishUpTo(newestLeaseSerial)`.
- This is what the pin waiter already does for guest threads (GuestBufferMemory.cpp:2141-2147).
- `FlushForAccess` calls it first when `GuestMemory::CurrentReadSite() == ReadSite::IndirectArguments`, outside completion actions.
- That site covers every CPU read of GPU-produced arguments: draw records and counts (Pm4.cpp:864, :874), `ReadDispatchArguments` (:795) and `readIndexAttributes` (:962). Only the draw records are tested here.

**B (needed with 6931). A draw that binds a BDA page table queues an unbounded write range.** One line in `DrawWriteRanges` (WrittenBuffers.cpp:96): a stage with a `DescriptorRole::BdaPagetable` binding adds `[0, 2^64)`.
- The same rule the dispatch path states: "writes cannot be ranged", so it drains.
- With it, 6931's indirect draw drains behind the held writer. Then A waits for the recorded store.

- On 6931, A alone is green only when the committer happens to hold the GPU lock for the writer's commit as the reader's hook takes it. That's a race: 1 red in 20 on `--open`. With the writer held, it never helps.

**Cost of A: the read waits for the whole lease batch.** Measured as the driver's own record-read time: `readMs`, the argument `Driver::draw` passes to `Graphics::CountIndirectDraw` after the read loop. It was read with a gdb breakpoint, so gdb doesn't time it. 5 runs each:

| | `--open` (1-instance writer) | `--submitted` (50,000-instance writer) | `--held` |
|---|---|---|---|
| main | 0.008–0.014 ms | 0.007–0.015 ms | 0.009–0.015 ms |
| main + A | 11.9–20.7 ms | 227–276 ms | 14.2–57.5 ms |

- Each read that follows address-based work still in flight now costs one submit of the open batch (when it holds the lease) plus the GPU time left in it, under the GPU lock. That is a synchronous draw's cost, paid once per such CPU-path indirect draw, dispatch or index-attribute read.
- It fires whether or not the store hit the record. Nothing on the CPU knows where a store through the table lands until completion, so A can't be narrower without a GPU-side record of written pages that the CPU can read before completion.
- A title pays it at every CPU-path indirect draw (`-> cpu (...)`: `NotFolded` and the other non-GPU paths in `ClassifyIndirectDraw`) that follows an address-based draw or dispatch in the same frame. The PC can count that: `[address-sync] leases: N released at completion` and the CPU-path indirect counts in `[draws]`, both under `APS5_PROFILE_DRAW=1`.

**Cost of B: address-based draws stop being pipelined past most later packets.** The unbounded range makes every `DrawPipeline::Overlaps` consumer drain behind such a draw.
- The consumers are: the wait packet (PacketExecution.cpp:34), predication (:193), dispatch reads (Dispatch.cpp:286), variant validation (VariantValidation.cpp:85), capture of data a later draw reads (WriteEvidence.cpp:210) and buffer fills (BufferFill.cpp:198).
- A narrower B would mark the item address-based and drain only for indirect arguments and captures. That needs an `Item` flag in DrawPipeline.hpp, so it's a header change.
- The capture path (WriteEvidence.cpp:210) likely has the same hazard: a later draw's captured data that a queued BDA store writes. I did not test that.

**Neither part should go in as is.** A's wait is unconditional. The real fix is a decision only the driver owners can make:
- either make stores through the table visible before completion (note the writable lease ranges, which here is all registered memory, or a GPU-side written-page record the hook can read);
- or accept a sync per CPU-path indirect read after address-based work.
