## 1. Why #757 tables a CPU-evaluable buffer-heap T#

The #757 squash message (d9e47d1e9) gives no reason for putting evaluable T#s in tables. The reasons below are what main's code depends on. Line numbers are on main a077a88df5, which is unchanged from 8cd937e291 for these files.

1. **Throw versus poison.** A direct image is evaluated and validated at capture.
   - An invalid non-null T# throws "runtime image descriptor is invalid" (`ResourceMaterializer.cpp:822-823`).
   - A T# with no compatible prepared mode throws from `RuntimeImageMode` (`ResourceMaterializer.cpp:1438-1442`, called from `materializeTables` at :968).
   - A table entry instead goes through `TryRuntimeImageMode` (:1360-1436) inside `ResolveImageTables` (:1040-1193). There every failure becomes a poison code, which faults only when an active lane selects the entry (`SpirvImageEmitter.cpp` `EmitTableAccess` :1666-1734, `EmitTableFault` :1642-1647).
   - That is what makes "a bad T# in an untaken branch only poisons" hold. A direct T# in such a branch throws at capture, unless control-flow pruning proves the branch untaken (`SrtDescriptorEvaluation.cpp:68-105`, which needs a CPU-evaluable condition).
2. **One mode per entry, no pipeline variants.**
   - A direct image picks its runtime mode through a specialization constant (`SpirvImageEmitter.cpp:1831`, `PipelineSpecialization::ImageBase`). Another mode means another pipeline variant.
   - A table entry carries its mode in the map record's flags (`ResolveImageTables`, `decoded << ModeShift`; the shader reads it at :1689 and selects at :1803). A heap of differently formatted T#s therefore never specializes the pipeline.
3. **One planning path.** `TryMakeTableColumn` (`ResourceTracker.cpp:553-669`) plans every affine or masked heap load as a column without asking whether its offset is evaluable.
   - Only #758's pointer tables are direct-first: `if (address) { if (ValidateSource(direct)) return false; }` at :615-622.
   - The buffer-heap path never got that check.
4. **Not a reason: snapshot timing.** Tables and direct images are both read at capture time.
5. **Not a reason: draw-cache correctness.** Both paths capture the words they read (`ShaderMemory` read marks), so the cache is correct either way. Only the number of compared words differs, and for a table it is the whole heap.
6. **Not a reason: #5550 sharing.** One T# used by several operations has one handle and one source on both paths.
7. **Memory the shader writes.** A CPU-evaluated value reads memory at capture.
   - If the shader writes the key's buffer in the same dispatch, the captured key can differ from the one the shader reads at run time.
   - `IsRawRead` (`SrtInstructionPredicates.cpp:8-19`) does not exclude written memory, and `CheckTableStores` (`ResourceTracker.cpp:1339-1352`) only guards key-domain buffers.
   - A table sidesteps this for the key, because the shader reads the key itself.
8. **Store, packed and BY2/BY4 operations.** In a table these are `TableOperation::Unsupported`: they read zeros and fault when executed (`AssignTables` :1354-1371, `EmitTableAccess` :1682-1686). So on main a CPU-evaluable heap T# used by `image_store` already regressed against #5188's direct images. This branch leaves that as it is (see "Left as is").

How the fix handles each one:
- (1), (2) and (6) are kept, because a selected column is still a table.
- (3) gets the evaluability check.
- (7) gets an explicit guard (`SelectionWritten`, below).
- (4) and (5) need nothing.
- (8) is unchanged.

## 2. The fix (C1)

### Planning: `ResourceTracker.cpp`
- **`TryMakeTableColumn`, C1 :657-668.** For an image (not a sampler, not a pointer table) whose eight T# dwords and dword-0 offset pass `ValidateSource`, the column is marked `selected` and the offset is interned as a 1-dword descriptor source (`TableColumn::selection`).
  - Key domains are still computed as on main, so deselecting restores main's plan exactly.
  - Columns compare by `selected`/`selection` too, so two keys of one heap become two one-record tables.
- **`CheckTableStores`, :1402-1406, with `SelectionWritten` at :1368 and `SameBufferSource` at :1355.** These deselect a column whose offset chain reads memory the shader may write at run time:
  - a live `ReadConstBuffer` whose V# equals a written or atomic buffer's V#;
  - any live read while `bdaWrites` is set (stores through pointers or GPU-only descriptors);
  - a pointer read (`LoadAddressU32`) while any buffer is written.

  `ReadConst` SRT slots are not followed: the shader reads their captured value, not live memory.
- **`Run`, :150.** A selected handle's offset becomes the constant `column.addend`, so the shader reads entry 0. The selection chain is kept alive like the heap source.

### Snapshot: `ResourceMaterializer.cpp` `Select`, C1 :530; called from `Column` at :603
Select evaluates the offset with the SRT walker, then reads only that record, exactly as the scalar loads address it: `ScalarBufferDword(offset, column.offset + 4d, size)`.
- If evaluation fails, the column gets `fault = Unmapped` with keys 0. The table faults when a lane uses it, and nothing throws.
- Dwords past the heap read zeros, as hardware does; an all-zero T# maps to `NullCode`, like the full table's outside code.
- An unmapped record gets the `Unmapped` state, and an offset in the carry range (the same predicate as the full table) gets `Carried`, which is OffsetCarry poison.
- A record past the key cap or the record count is read rather than poisoned. That is an improvement over main, where it was OutsideSnapshot poison.
- The header base moves to `base + ((offset + c) & ~3) - ((addend + c) & ~3)`, with size `entry + 4 * dwords`:
  - the shader's fault address is the record's own (the GPU test checks it);
  - the written-heap check (`finishImageTables`) covers that record window, at most what main's whole-heap window covers;
  - `tables.ranges` gets the exact dwords read, which is what the BDA written-range check sees.
- The `[image-table]` profile line counts "selected records".

### Disk cache and docs
- `TableColumn` gains `selected` and `selection`. The encoder, decoder and layout asserts are updated, a decoded selection must name a known source, and `FormatVersion` becomes 36.
- `docs/dev/ARCHITECTURE.md` and the shader and libSceAgcDriver debt files describe selected columns.

### Why "direct-first" is a selected record, not an ordinary direct image
- **Same cost.** Both read one T# record per capture, plus the offset's reads.
- **Ordinary images break the fallback rule.** The task's fallback rule ("fall back to a table when CPU evaluation fails or the T# is invalid, instead of throwing") is a decision taken at run time, per capture. An ordinary direct image is decided at plan time. Falling back would need both paths in the shader, or a recompile, and a switch.
- **A selected record keeps the table semantics, so no switch is needed.** Poison instead of throw, per-entry modes and the written-heap fault all carry over, while the cost drops to that of a direct image.

### Left as is
- Shaders with any table column, selected or not, keep pure flat slots disabled (`SrtFlatSlotClasses.cpp:13-19`). Their draw-cache data-word hits (`DataWordPositions`) therefore stay off, as on main.
  - A follow-up could let a selected column report its reads to the read trace so pure slots stay on.
- `image_store`, atomics and packed operations through a selected column still fault, as through any table on main. Making them direct would bring back the throw (1).
- A write to the key's memory through a different V# over the same bytes is not detected. Main's buffer key domains have the same limit; it is documented in `docs/dev/debt/shader.md`.
- Value key domains no longer narrow image columns. Every key that has one is CPU-evaluable, so its column is selected. Key-buffer domains, for keys loaded per lane, still narrow.

## 5. The narrowing alternative (dropping `&& !ReadsThroughDescriptor(key)` at `ResourceTracker.cpp:516`)

**It replaces nothing and complements nothing, so I did not build it.**
- With C1, every key it would give a value domain is CPU-evaluable, so its column is already selected.
- The only columns left for it are the ones C1 deselects, and there it is unsound (below).
- Even where it applied, a narrowed table still costs O(keys) per capture:
  - the `states`, `words` and `codes` arrays over every key (`ResourceMaterializer.cpp:557-571`, `Snapshot` :711-747);
  - a map of `keys` entries in `ResolveImageTables`.
  
  The "SRT key" rows in section 4 measure exactly that case on main: 29 words, but 76-257 µs per capture.

**The `CheckTableStores` risk:**
- `CheckTableStores` (:1339-1352) clears a column's key domains only when a written buffer's source equals a domain's source. A value domain's source is the interned 1-dword key value, which never equals a buffer source, so a value domain is never cleared.
- That is safe today only because `ReadsThroughDescriptor` keeps live reads out of value domains: the key then comes from user data or captured SRT slots, which the shader cannot change.
- Dropping the check admits keys read live through a V# or a pointer that the same dispatch may write. The CPU would narrow to the pre-dispatch key, while the shader reads the new key at run time and lands outside the narrowed set. The result is OutsideDomain poison, a zero sample and a fault, on a record that is valid.
- `LoadAddressU32` keys with BDA writes would be unguarded the same way.
- C1's `SelectionWritten` is exactly the guard that fix would also need.

- **Textual overlap:** both change `Column()`, where C1 adds the early `if (column.selected) { Select(column, records); return records; }` after the heap evaluation, and the `[image-table]` printf. A port conflicts there; it resolves by keeping the early return ahead of the walk.
- **Semantics are disjoint:** a selected column never reaches the walk that the memo caches.

### The planned snapshot reuse (PM-028)
PM-028's plan is "keep a column while its words are unchanged; skip its read while `tables.ranges` has no write since the last snapshot".

What does not overlap:
- **Selected columns leave its scope.** That is every buffer-heap T# whose eight dwords and offset the walker evaluates. Their per-capture cost is the offset evaluation plus one record of 26 captured words, so there is nothing worth reusing. The reuse should serve only `!column.selected` columns: whole and narrowed tables keyed per lane (readfirstlane, loop phis, masks of lane values), where the 2.3-4.3 ms per capture remains.
- **It must not reuse a selected column on `tables.ranges` alone.** For a selected column, `tables.ranges` holds only the selected record's dwords. The key's own reads are captured by the walker's read marks, not in `tables.ranges`. So "no write over `tables.ranges`" does not prove the key unchanged. Excluding selected columns is the simple rule.
- **Other overlap:**
  - the shared `[image-table]` printf;
  - `Column()`'s early return.

### What
A T# that a shader loads from a buffer heap at a runtime offset has been an image table column since #757, so every capture snapshots the whole heap (up to 65,536 records) even when user data or an SRT read fixes the offset. That is #5188's case: a T# read from a constant buffer at a user-data offset.

When the T#'s eight dwords and its offset are values the SRT walker evaluates, the column is now **selected**:
- the shader indexes entry 0 of a one-record table;
- each capture evaluates the offset and reads only that record: 26 captured words instead of 262,161 for a 32,768-record heap;
- the column keeps every table semantic: an invalid T#, an unmapped record or an offset carry is poison that faults only when a lane selects it; a key the walker cannot read faults the table instead of throwing; modes are picked per entry, so there are no pipeline variants; a dispatch that writes the record faults.

A key chosen per lane stays a whole table, as does a key read from memory the shader may write at run time. No switch. The disk cache format goes to 36.
