# BF-128: what #9508's per-draw image-table map costs for Village-sized tables

**Verdict: not measured.** The heap is not live on lavapipe here.
- `writeHeapTableMap` never runs on lavapipe here, at any table size.
- As the task says, I stopped and did not measure the fallback as if it were the heap.
- There is no number against the ~100 µs per draw kill line. It needs a driver with `VK_EXT_descriptor_heap` (see "What would be needed").

## Is the heap live? No.

**The driver.**
- Mesa 25.2.8 (`mesa-vulkan-drivers 25.2.8-0ubuntu0.24.04.4`); the emulator reports `llvmpipe (LLVM 20.1.2, 256 bits) api=0x40413e`.
- `vulkaninfo` is not installed. Instead, `strings /usr/lib/x86_64-linux-gnu/libvulkan_lvp.so | grep -ic descriptor_heap` gives **0**. The library lists `VK_EXT_descriptor_buffer`, not `VK_EXT_descriptor_heap`.

**What #9508 requires.** It turns the heap on only when all of these hold (Execution/src/VulkanDevice.cpp:1772-1786 and :2073):
- the device lists `VK_EXT_descriptor_heap`, `VK_KHR_maintenance5`, dynamic rendering, depth-stencil resolve and create_renderpass2;
- it reports the `descriptorHeap` and `maintenance5` features;
- `BindlessHeap::Fits(properties)` holds;
- `maxPushDataSize` is at least 256.

**What happens when they don't.**
- Nothing is logged.
- `DescriptorHeapEnabled()`, and therefore `HeapComputeEnabled()`, stays false.
- `gpuResolvedImages` stays false (VulkanDevice.cpp:3692).
- So `writeHeapStage` (Graphics/src/ShaderResources.cpp:5835) and `writeHeapTableMap` (:6173) are never called.

**Runs (as the runner user, from the tree root).**

1. With the task's switches:
   - Command: `ANYPS5_NO_SHADER_CACHE=1 APS5_GPU_HEAP=1 APS5_VERIFY_GPU_HEAP=1 APS5_PIPELINE_STATS=1 APS5_DRAW_PIPELINE=1 VILLAGE_TABLE=4096 build/tests/agc_driver_village_draw_cost_tests --cost 80`
   - Result: exit 77, `skipped, no usable Vulkan device: AGC graphics: APS5_PIPELINE_STATS requires VK_KHR_pipeline_executable_properties`.
   - Lavapipe 25.2.8 lacks that extension, and the `[gpu-heap] cost (10 s):` line is printed only under `APS5_PIPELINE_STATS` (BindlessHeap.cpp:799, :825, :850). So that line cannot be produced on this machine even with a heap.
2. The same run without `APS5_PIPELINE_STATS`, `--cost 20`:
   - No `Vulkan descriptor heap: GPU-mode draws and dispatches bind from VK_EXT_descriptor_heap` line (VulkanDevice.cpp:2077).
   - 0 lines match `descriptor heap|gpu-heap|heap-slots`.
   - `village cost: 20 frames of 850 draws: wall median 476.37 us per draw (min 400.48, max 613.79), 404.92 ms per frame`
3. The same without `APS5_GPU_HEAP`:
   - `village cost: 20 frames of 850 draws: wall median 473.03 us per draw (min 373.46, max 563.65), 402.07 ms per frame`
   - This is the same path. **Both numbers are the per-draw fallback, not heap numbers.**
4. `agc_driver_bindless_images_tests`, under the env of its registered `_gpu_heap` variant (`APS5_GPU_HEAP=1 APS5_VERIFY_GPU_HEAP=1 APS5_DRAW_PIPELINE=1 APS5_PIPELINED_DRAWS=32 APS5_PIPELINE_DISPATCH=1`):
   - exit 0, `bindless image materialization tests passed`, with 0 heap lines.
   - So #9508's `_gpu_heap` ctest variants pass on lavapipe by taking the per-draw path. A green run there does not exercise the heap.

## What would be needed

1. **A driver with `VK_EXT_descriptor_heap`.** `APS5_PIPELINE_STATS` also needs `VK_KHR_pipeline_executable_properties`.
   - **RADV or ANV on Mesa 26.2 or later**, where the heap is on by default (Phoronix). On Mesa 26.1, RADV has it only behind `RADV_EXPERIMENTAL=heap`. A PC with one of these is the direct route.
   - **lavapipe:** I found no Mesa release that I could confirm has it.
     - A third-party PR (r-potter/clockwork#21, merged 2026-10-20) says lavapipe exposes the extension only on Mesa main, and builds it from a 2026-10-19 commit.
     - I could not verify this, because this container cannot reach gitlab.freedesktop.org or docs.mesa3d.org.
     - Building Mesa main here would need meson and LLVM development packages and several GB of disk; 6.4 GB is free.
   - **A software path:** #9508 has none. Without the extension, every stage takes the per-draw path.
2. **Bench sizes.** `MaxTableEntries = 4096` (VillageDrawCost.cpp:45), and `Setting()` clamps `VILLAGE_TABLE` to it. So 8,192 and 21,504 entries need `MaxTableEntries` raised. `TextureBytes` grows to 21,504 × 4 KiB ≈ 84 MiB.
3. **A dedicated timer for the map.**
   - #9508 times `writeHeapTableMap` only inside its "stage data" bucket (`HeapCostScope dataCost(HeapCost::StageData)`, ShaderResources.cpp:6169-6173), together with the shader-data and flattened-SRT writes.
   - Ring-span reuse is reported only in aggregate, for all spans: `ring spans W written / K kept / E expired`.
   - Per-refresh map time and map-only span reuse therefore need a temporary timer and counter around `writeHeapTableMap` and its `heapSpan` call (6035-6042).
