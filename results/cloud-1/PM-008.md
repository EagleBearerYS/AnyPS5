## Design

### Lines

The lines come after the first PR's lines, in this order:

| Line | Example | Source |
|---|---|---|
| `DRAWS` | `DRAWS: 1240  DISPATCH: 85` | Draw packets and dispatch packets per frame, averaged over the window of presents in the last second. |
| `SHADERS` | `SHADERS: 3  TOTAL: 1503` | Pipelines created in the last second (growth over the window), then the running total. |
| `VRAM` | `VRAM: 6.1/7.8 GB` | `heapUsage`/`heapBudget` of `Graphics::LargestDeviceLocalHeap` via `VkPhysicalDeviceMemoryBudgetPropertiesEXT`. |
| `RAM` | `RAM: 3.2 GB` | Process private memory. |
| `RES` | `RES: 1920X1080 / 2560X1440` | `present()`'s display size (none for clear-only presents) and the swapchain extent. |

**DRAWS** comes from per-worker counters (`PacketCounters`), incremented in `Driver::execute` (`PacketExecution.cpp`):

- in the draw-packet branch, for the same packets the `[draw] driver phases` line counts as "draw packets", without `APS5_PROFILE_DRAW`;
- in the `DISPATCH_DIRECT`/`DISPATCH_INDIRECT` (0x15/0x16) branch;
- packets skipped by predication are not counted.

How the counters work:

- Each worker thread leases a 64-byte-aligned counter pair from a registry once in its life. The lookup happens once per submission, and the reference is reused for every packet in it.
- An increment is a relaxed load, add and store by the worker's own thread, with no lock prefix and no shared cache line. The counters are `std::atomic` only so the presenting thread's read is not a data race.
- The overlay sums all workers' counters under the registry mutex once per shown frame. Workers take that mutex only when they first lease their counters, so the per-frame read does not contend with them.
- The counters of a finished worker go to the next worker unreset, so the sums never go back.
- The line is shown once anything was counted.

**SHADERS:** the driver has no single pipeline-creation choke point. It counts where a pipeline-cache miss leads to creation:

- at the end of the `Graphics::Pipeline` constructor (`Pipeline.cpp`): one per new draw state, built monolithically or linked from graphics pipeline libraries; library prebuilds return earlier and are not counted;
- after `CreateComputePipeline` in `VulkanDevice::dispatch`: one per new compute shader.

The driver's own pipelines (presentation, detiler, overlay and so on) and the `APS5_DUMP_COMPUTE_PIPELINES` capture/replay path are not counted. Each count is one relaxed `fetch_add` on a shared counter, which is cheap next to building a pipeline. The line is shown once a pipeline was created.

**VRAM:**

- `LargestDeviceLocalHeap` is the heap the texture-cache budget already reads; commit 1 makes it public instead of duplicating it.
- It is read only when `context.memoryProperties2` is set, which `VulkanDevice` does when the device has `VK_EXT_memory_budget`, and only with a non-zero budget.

**RAM:**

- Windows: `PrivateUsage` from `K32GetProcessMemoryInfo`, in kernel32, as the project's tests already call `K32GetPerformanceInfo`; no psapi library is linked.
- Linux: `RssAnon + VmSwap` from `/proc/self/status`, which reads kernel counters. `smaps_rollup` would walk every mapping on the presenting thread.
- The platform split is an `#ifdef _WIN32` inside `PerformanceOverlay.cpp`, as in `WorkerSampler.cpp`/`ThreadPriority.cpp`, with the `NOMINMAX` include pattern of `Jit.cpp`.
- The title's direct memory is shared memory on both systems (a memfd on Linux, a pagefile-backed section on Windows), so both figures leave it out.

**RES:** when the spaced form is wider than the 27 columns, the line is written without spaces around the `/`. If even that doesn't fit (two 5-digit sizes), it is dropped.

### Sampling

- `PerformanceOverlay::NotePresent(at, display)` is the only per-frame entry point. `VulkanDevice::present` calls it only when `PerformanceOverlay::Visible()`.
- It sums the packet counters, adds a sample with the GPU, driver, draw, dispatch and pipeline totals, and reads VRAM and RAM when `OverlaySampleDue` says so: on the first shown frame, then at least 1 s later.
- Showing the overlay again with F10 restarts the statistics and samples at once.

### Format

- Counts use `FormatOverlayCount`: whole numbers to 9999, then `12K`/`999K`, then `1M`/`999M`. Every count fits in 4 characters, so every line fits the 27-column panel; the widest, `DRAWS: 9999  DISPATCH: 9999`, is exactly 27.
- Memory is in GB of 2^30 bytes, through the first PR's `FormatOverlayValue`.

### Font and panel

- **New glyphs:** B, C, H, K, L, O, T and W, hand-drawn in the same 5x7 style. The test checks each against every other glyph, so O is not 0 and B is not 8.
- **Panel size:** with every line (GPU and DRIVER included) the panel is 116 units tall:
  - 232 px at 1080p (scale 2), **21.5% of the window**;
  - 32% at 720p (scale 2);
  - without the two profiling lines, 196 px at 1080p (18%).
- **No compact/full split:** the panel stays under a third of the window at 1080p, so I added none. `ANYPS5_OVERLAY` and F10 are unchanged.

### API changes to the first PR's code

- `OverlayStatistics` samples now hold `OverlayCounters` (GPU, driver, draws, dispatches, pipelines). A new `AddPresent` overload takes them; the old one stays and fills only the first two.
- There is a new `ComposeOverlay` overload with `OverlayDetails`; the old one forwards to it with no details.
- The two `NotePresent` overloads that nothing else called are replaced by `NotePresent(at, display)`.

## Cost

**Hidden** (no commands, no reads):

- Per draw or dispatch packet: one load/add/store on the worker's own counter, 0.32 ns in a tight loop on this Xeon.
- Per submission: one `thread_local` lookup.
- Per pipeline creation: one relaxed atomic add. Pipelines take milliseconds to build.

**Shown** (lavapipe, llvmpipe LLVM 20.1.2, 4 vCPUs):

| | 1920x1080 | 3840x2160 |
|---|---|---|
| Overlay pass GPU time, full panel: median of 10 (min–max) | 1.125 ms (0.947–1.312) | 2.095 ms (1.843–2.700) |
| Recording on the presenting thread | 0.045 ms | 0.044 ms |

- These are the same as cloud-2's numbers for the 5-line panel (1.08–1.30 ms and 1.82–2.20 ms). lavapipe's cost is mostly a fixed cost per render pass.
- Per frame: summing the packet counters takes 0.02 µs (one mutex lock).
- Once a second: VRAM read 7.0 µs, RAM read 12.2 µs.

## Not sure about

1. **"Plain per-worker counter":** I used `std::atomic` with relaxed load and store, not a bare `uint64_t`. The machine code is the same plain `mov/add/mov` on x86-64, and the other thread's read is not undefined behaviour.
2. **What DRAWS counts:** draw packets, including ones the driver then skips as having nothing to draw. This matches the profile line's "draw packets", not its "drawn".
3. **What SHADERS counts:** one per new draw state's `Pipeline`. Its alternate-alpha and per-face depth-bias variants are extra VkPipelines of the same state and are not counted separately. The label says SHADERS, as the task asked, but the count is pipelines.
4. **RAM definitions differ slightly:**
   - Windows `PrivateUsage` includes committed memory never touched; Linux `RssAnon + VmSwap` doesn't.
   - Neither includes the title's direct memory.
   - With one decimal in GB, a small process shows `0.0 GB`.
5. **The Windows `#ifdef` branch was not compiled here:** this VM has no MinGW. It uses `K32GetProcessMemoryInfo` with `PROCESS_MEMORY_COUNTERS_EX`.
6. **No hardware GPU and no HDR10 swapchain here.** The HDR10 overlay test from the first PR still passes.
7. **Overlap:** this branch touches one line of `present()` (the `NotePresent` call). It should rebase trivially over the FSR branch or over cloud-3's PM-007 combination. If the first PR changes in review, this branch rebases onto it: Depends on the first PR.

   - The "GPUs tested" line can only name lavapipe from here.
