## 3. The cause

**Two things meet:**
- `ReplayRacesDispatchTests` (`tests/execution/PipelineJournal.cpp:497`, added on main in 307f2202e7) records its 32 pipelines into the journal it shares with the earlier tests in the binary. That journal is capped at `APS5_PIPELINE_JOURNAL_MAX_MIB=1` (`main`, line 778), and the race assumes all 32 fit beside what is already there.
- #12840 makes every program that writes through an address carry the store-page path. That is `bda_store_page_pointer` (`DefineBdaStorePagePointer`, `SpirvBdaLookup.cpp:44`, emitted when `Info().bdaWrites`, lines 379–382), plus the store-page branch in each lookup (line 265).

**The effect:**
- The race fixture's SPIR-V grows 18.8%, and its journal module record 18.4%.
- Recording the batch hits the cap (`PipelineJournal.cpp:1199` `overCap`), and `evictUnderLock` (line 1068) rewrites the file to ¾ of the cap, keeping the newest 24.
- The replay can only race those 24. The dispatches build the 8 evicted pipelines, and the test reported that as a double build.

**Not affected:**
- the journal's identities, payloads, decoding and eviction order;
- the default cap (1024 MiB).

**What #12840 does change, and should be weighed separately:** every address-writing compute module costs 18.4% more journal (and SPIR-V) bytes, so a given cap holds about 16% fewer of them.

## 4. The fix (74070e473e)

**`tests/execution/PipelineJournal.cpp`, +20 −1, in `ReplayRacesDispatchTests` only:**
- Flush, then rename the journal file aside (`pipelines.journal.aside`), so the first device records the 32 race pipelines into an empty journal: 1,022,496 of 1,048,576 bytes.
- Keep each race shader's identity, and after the flush require that all 32 are in the journal (`ReadJournalComputeIdentities`): "the journal holds N of the 32 raced compute pipelines under its cap, so the replay cannot race the others".
- Run the race exactly as before; `created == replayed + present` is unchanged.
- Flush, remove the race journal, and rename the earlier journal back, so the tests after it see the journal they saw before.

**Why put the journal back, and not just empty it:**
- A first version only emptied it and left the race's 32 records behind (a full 1.0 MiB journal).
- That made `EvictionWatermarkTests`, which runs later in the same binary, fail 20/20: "three consecutive records after a rewrite triggered another rewrite". Its post-rewrite headroom depends on what the earlier tests left.
- With the race skipped, the unfixed merge passes every other test (3/3). Putting the journal back gives the later tests the same state.
- After the restore, the journal resyncs to the replaced file on its next append. It logs one "reached its size cap; 0 records (0.0 MiB) were dropped"; nothing is dropped.

**Why not a library change:** the journal records, identifies, replays and evicts correctly. The 8 are evicted because the test's cap cannot hold them, which is the journal's documented behaviour.

**Why not loosen the race check:**
- The check still requires exactly one build per pipeline.
- The new precondition is stricter: it fails if any race pipeline is missing from the journal, and it names that cause.
- With the set-aside removed (local check), the merge now fails with "the journal holds 24 of the 32 raced compute pipelines under its cap, so the replay cannot race the others", instead of "32 built for 24 replayed".

**Margin:** 32 race entries take 1,022,496 of 1,048,576 bytes (26,080 spare, 2.5%). About 800 more bytes of SPIR-V per address-writing shader would trip the new precondition, which then says so.
