## 1. The read: when are two 64 KiB units one tile of identical layout?

All references below are at #13251's head, 44b529e05d.

**Tile mode 7** is `TextureTileMode::kR64KBX`, the 8th enumerator (`Graphics/include/GuestTextureResource.hpp:20`, alias `RenderTarget64KB`, :44). That is the hardware's SW_64KB_R_X, swizzle mode 27 (`XorSwizzleMode`, :37-49).

**Format 36** is B10G11R11_UFLOAT, 4 bytes per element (`Graphics/src/TextureFormat.cpp:43`). A 64 KiB thin block of 4-byte elements is 128×128 elements (`kLog2BlockThin64KB[2] = {7,7}`, `Graphics/src/TextureTiling.cpp:41`, :61).

**How a texel is placed:**
- **Mips:** `ComputeTiledMipLayout` (`TextureTiling.cpp:201-276`) lays a mip that is not a tail out as whole blocks in rows.
  - `blocksPerRow` is the padded width over the block width (:228). The pitch is always padded to whole blocks (:226, :229), so the task's pitch condition always holds.
  - The tail levels share one block at offset 0 (:239, :245-251).
  - The levels follow from the smallest to level 0, each at a multiple of 64 KiB (:254-259).
  - `TextureTiling.hpp:36-38` states the same contract.
- **The detiler:** `Graphics/shaders/TextureDetile.comp:245-249` addresses a texel `p` at `(p.y/H · blocksPerRow + p.x/W) · BLOCK_BYTES + blockOffset(p)`.
  - For the equation family, `blockOffset` is `equationOffset(p) ^ pipeBankXor` (:134).
  - Each address bit is the parity of the x, y and slice bits its equation selects (`equationBit`, :74-77).
  - The slice input is the array layer (`TextureDetiler.cpp:264`/:455), and `pipeBankXor` is the descriptor's (:271/:462, from the address's low 16 bits: `GuestTextureResource.cpp:245`).
- **The equation:** for SW_64KB_R_X at 4 bytes (`TextureSwizzleEquations.hpp:38`), every equation bit selects only x bits 0-6 and y bits 0-6, which are inside the 128×128 block, plus slice bits. So inside one block, the byte holding element (x, y) depends only on (x mod 128, y mod 128), the slice and the pipe/bank XOR. It does not depend on the block's position, the mip, the pitch or the image.
- **The storage image:** `blockUnits` (`Graphics/src/Texture.cpp:1480`) requires a 64 KiB-aligned base, a thin surface, a tiled mode and no GCN split stride. Each tracked unit is then one 64 KiB guest block. `sliceWindows` (:3024-3103) moves a unit as whole tile blocks of its (layer, mip) slices: `ThinBlockLayout` at :3032, the block rows at :3056-3097.

**The condition, as implemented** (`unitTile` and the `tiles` check in `pendingAliases`, aade147005 `Texture.cpp:5918-5996`):

> A unit u of image A and the unit v of image B over the same 64 KiB guest block hold the same elements at the same bytes when all of the following hold:
> - both images are block-unit storage images (64 KiB-aligned base, thin, tiled);
> - both have the same tile mode, the same bytes per element, the same pipe/bank XOR, and no block compression;
> - the tile mode's swizzle equation uses only coordinate bits inside the block (checked per mode and element size: `swizzleWithinBlock`);
> - in each image the unit is exactly one tile block of a mip that is not a tail, with 64 KiB tile blocks: block offset `(unit·64K − sliceBegin)` at a block boundary, at tile (bx, by);
> - both lie in the same array slice;
> - the element rectangle each image holds in that tile, `min(128, mipWidth − 128·bx) × min(128, mipHeight − 128·by)`, is the same size in both. It always starts at the tile's origin.
>
> Then one `vkCmdCopyImage` region, from B's (mip, layer, 128·bx_B, 128·by_B) to A's (mip, layer, 128·bx_A, 128·by_A) with that extent, moves the block bit for bit.
>
> Equal extents, not only "a full tile", also cover the edge tiles of images whose edge falls at the same in-tile position. A full 128×128 tile in both is the common case.
>
> A smaller rectangle that merely fits inside the other's would let a borrow be correct. But the lender could then not be superseded when the borrower writes, because the lender holds elements the borrower lacks. Both images would stay pending over the block, and their stores would race. So the extents must be equal.

**What falls back to today's path, per unit:**
- mip-tail blocks, since several levels share the block at tail offsets;
- a short last unit;
- an edge tile of another extent;
- another array slice;
- another element size, pipe/bank XOR or tile mode;
- a swizzle that reaches outside the block (`kStandard*`, GCN and 4 KiB modes are refused this way, conservatively).

## 2. The change

### The refactor (1fc6a02b34): nothing changes on its own

**Per-unit lenders.** `borrowedFrom`/`borrowedVersion` become `BorrowedUnit{from, version, unit, held}` per unit (`Texture.hpp`).
- **Must `borrowedFrom` become per unit? Yes.** One image can now hold units from several lenders, and a lender's unit index differs from the borrower's.
- **`markLayersPending`** (aade147005 `Texture.cpp:3952-3964`) supersedes exactly the lender unit recorded for each unit it writes. It does so only while the lender is still at the version lent. That is sound because the borrower holds the same element set in that block.
- **`borrowersUnchanged`** (:5769) maps the lender's stored units to each borrower's own units.
- **`advanceBorrowers`** is unchanged, since it works on borrower units.
- **`forgetBorrowed`** resets units one by one.

**Alias plans.** `pendingAliases()` returns plans `{alias, sameShape, units[u] → lender unit, copyable[u]}`.
- In this commit it returns only the old same-surface image.
- `borrowUnits(plans, lenders)` copies from each lender.
- `refreshingAlias` becomes a set (`refreshingAliases`, :1786-1790). `FlushPending` leaves out every kept alias when the caller gives no `except` (:4272), as it did for the single alias.
- `WaitForFlushing` no longer receives the alias. It returns at once under the GPU mutex, which a refresh holds, so this is equivalent.

### The per-tile borrow (aade147005)

**Candidates.** `pendingAliases()` (:5951) also takes pending images that overlap the surface at another base or size and have at least one copyable unit. The same-surface image keeps priority through `stable_partition`.

**The refresh** (:2219-2262), per alias, per overlapping unit, with #13251's rules carried over unit by unit:
- an untracked stamp range, or a pending unit with generation 0, **refuses the alias**;
- a pending, unstamped unit where this image is also pending **refuses the alias**, the old order;
- a unit another kept alias also has pending refuses the later alias, so no block has two lenders;
- a **stamped** unit is dead: the alias stays pending there and its own write-back keeps the CPU's bytes;
- a pending, unstamped unit that the copy **cannot** take is **stored before the refresh's flush**, over that unit's range only (:2251).

**Is a partial flush of the alias possible? Yes.**
- `FlushPending(range)` reaches `writeBack(address, bytes)`. With `APS5_BLOCK_WRITEBACK_WIDEN` unset (the default), `writeBack` selects only the pending units overlapping the range (`Texture.cpp:5992`, `:6003`), so the store is scoped to those units.
- With the widen switch set, a store can take the alias's other units too. They are then stamped, and the borrow check after the flush treats them as dead: they are re-read from memory. That is correct, only slower.

**The rest of the refresh:**
- The kept aliases are exempt from the refresh's flush and from its hook (the set).
- After the keys are proved, the borrow selection (:2403-2430) re-checks stamps per alias and unit. It takes the unstamped pending ones not pending here, and keeps held entries only for the same lender, version and unit.
- After the upload, `borrowUnits` (:6004, called at :2541) copies one region per unit: `sliceWindows` regions for the same-surface alias, `unitTile` to `unitTile` for the others.

**Hook exemption with several aliases:** a set. Each kept alias's pending units over this surface are either taken, dead, or stored first. So leaving all of them out of the hook while the refresh reads the surface stores nothing that should have been stored.

### The Village trace (1a37781249, v4 only)

**Per-unit reasons.** The `[storage-alias]` reason for a store is now worked out per unit. "base differs" and "size differs" no longer refuse; the reasons are:
- `tiling differs`, `element size differs`, `pipe/bank XOR differs`, `block-compressed`, `swizzle not within a block`;
- `refreshed unit a mip tail or partial`, `flushed unit a mip tail or partial`, `array slice differs`, `tile extent differs`;
- as before: `untracked`, `flushed unit untracked`, `unit pending in both`, `scoped refresh` (now from the refresh itself);
- `another alias holds the units, or the keys turned`.

**Borrows are counted.** Each borrow adds an entry `refreshed … | flushed … | borrowed: N blocks, X MiB`, and the header gains "N 64 KiB blocks borrowed on the device (X MiB)". Entries are ranked by bytes. The `ENVIRONMENT.md` row is updated.

## 3. Tests

**New test: `agc_storage_alias_blocks`** (`tests/Recorder.cpp:12514`, registered with `APS5_PROFILE_DRAW=1`).
- **Setup:** R32 R 64 KiB X images, cached, over copied write-watched memory.
- **Each case:** X written, Y looked up, Y written, X looked up, two rounds.
- **Two runs per case:**
  - *stored*: `FlushPending` after every write, which is the old path;
  - *borrowed*: no stores.
- **Patterns:** they differ per texel, mip, image and round: `id<<28 | round<<24 | level<<20 | y<<10 | x`.

**Content checks:**
- after every lookup, Y or X must hold **the same texels in both runs**, every mip;
- after the final flush, guest memory must be byte-identical between the runs.

**Byte checks, borrowed run, per lookup:**
- every guest block taken on the device must be **unchanged in guest memory** by the lookup: 0 round-trip bytes;
- every fallback block must have received the other image's results first;
- the 'alias' device copies must be exactly the taken units × 64 KiB;
- with no fallback blocks: no 'storage refresh' write-back and no upload other than 'alias';
- with fallback blocks: exactly one 'storage refresh' write-back.

| Case (Village shape, scaled) | Y lookup | X lookup |
|---|---|---|
| 512x128 two units into 256x256 ("a 1920-wide image over part of a 960-wide one") | takes blocks 2-3 ('alias' 128 KiB), no store | takes blocks 2-3, no store |
| 128x128 at the base of 256x256 ("a smaller image at the same base") | takes block 0 (64 KiB) | takes block 0 |
| 128x64 at the base of 256x256 (a partial tile) | nothing taken; block 0 stored (old path) | nothing taken; block 0 stored |
| 512x128 over a 256x256 four-mip chain ("a mip-4 image whose tail block must fall back") | takes blocks 1-3 (192 KiB); tail block 0 stored, then uploaded ('flushed') | takes blocks 1-3; block 0 stored |

**Extended:** `agc_storage_alias_round_trip`'s R32 256x256/512x128 pair (same base and size, other width) now asserts the handoff for cached images over copied memory:
- no 'storage refresh' write-back;
- no 'flushed' upload;

## 5. How much of Village's overlap the condition covers

I modelled each pair from the task's lines with `ComputeTiledMipLayout`'s rules (4-byte elements, 128×128 tiles, tail at ≤64 wide). I then counted overlapping 64 KiB blocks whose tiles have equal extents in both images:

| Pair (refreshed / flushed) | Overlap per flush | Copyable | Why the rest fall back |
|---|---|---|---|
| 120x68 / 960x1080 mips 4, same base | 1 unit | 0 | 120×68 against 120×128 (level 3, tile 0): height differs |
| 960x1080 mips 4 / 120x2160 at +0x20000 | 17 units | 0 | 120-wide tiles against 128- and 112-wide tiles of levels 2 and 1 |
| 960x1080 mips 4 / 1920x1080 at +0x130000 | 81 units | **59 (73 %)** | 12 width and 10 height mismatches at level edges |
| 1920x1080 / 960x1080 mips 4 at +0x640000 | 54 units | **24 (44 %)** | 13 width, 17 height |
| **All four, ×7 flushes per 10 s** | 66.9 MiB | **36.3 MiB (54 %)** | |

So I expect a bit more than half of the traced overlap to move to the device. With the four lines' counts, that is 25.8 + 10.5 MiB per 10 s out of 66.9.

A "fits inside" rule would reach 81 % (54.2 MiB), but only with a different lender rule: store the lender's unit before the borrower's own store, because it cannot be superseded. That is not done here.

The script is `scratchpad/bf308/coverage.py` (not committed). The PC's F-trace with the v4 trace will show the real split: the `borrowed` blocks against the per-unit reasons.

## Notes

- **Write-back bytes on copied memory.** `countStorageWriteBack` counts a CPU write-back as the whole surface (`Texture.cpp`'s CPU path passes `guestBytes`), even when it stores one unit. The test therefore asserts stores by guest-memory blocks and write-back counts, not by write-back bytes.
- **The borrower's own pending units.** When a refresh takes units on the device but is not `unchanged`, its own pending units over copied memory are still stored ('refresh') before the CPU upload path, as on the base. Only the alias's round trip goes away. Cases 1 and 2 show that 'refresh' store; it is not a 'storage refresh'.
- **`RefreshLayers`.** It returns to a whole refresh whenever any plan exists (`!pendingAliases().empty()`), as it did for the one same-surface alias.
