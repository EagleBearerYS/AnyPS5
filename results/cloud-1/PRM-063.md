## What each commit does

1. **Metadata (point 4).** One check, `read_backup`, runs before anything in the live save changes, for both `sceSaveDataCheckBackupData` and `sceSaveDataRestoreBackupData`.
   - `_sd_backup/<dir>` missing: `NOT_FOUND`, as before.
   - `_sd_backup/<dir>` present but without `save/`, without `save.param`, with a `save.param` that is not exactly `sizeof(SaveDataParam)` (1,328 bytes), or with a `save.blocks` that is not a file: `INTERNAL`, with or without `param`.
   - The check no longer throws on a wrong-sized `.param`, and fills `param` only on success.
2. **Staged restore (point 1, decision 3).**
   - The backup, its `.param` and its blocks file are copied to `_sd_restore_tmp/<dir>/{save,save.param,save.blocks}`.
   - The copy is checked complete: every entry is present at its size, compared with `_sd_backup/<dir>`.
   - The copy is flushed. Then the live `_sd/<dir>`, `.param` and `.blocks` move to `_sd_restore_old/<dir>/…`, the staged copy moves into place, and the old one is removed.
   - A failed move puts back everything already moved, in reverse order (`FileSwap::undo`).
   - **The hook:** `void SaveDataSetFileStepHook_nid_no_patch(bool (*hook)(const char* step, const char* path))`. It is called before every copy and rename of the backup and the restore with a step name and the path written, and returning false fails that step as an I/O error. The step names are `backup.copy`, `backup.aside`, `backup.place`, `backup.rollback`, `restore.copy`, `restore.aside`, `restore.place` and `restore.rollback`.
   - The backup's copy became the same walk (`copy_tree`), so the hook sees each file. Commit 4 makes that walk refuse links.
3. **Backup swap (point 2, decision 1).**
   - If `rename(staged, entry)` fails, `old` is renamed back to `entry` and the staged copy is removed.
   - Every staged file is flushed before the swap: `FlushFileBuffers` on Windows, `fsync` on POSIX, as libc's `FlushPath` (General.cpp ~468/~492).
   - On POSIX the directories on both sides of each rename are fsynced after it. All of this happens before `RemoveTree(old)`.
4. **Roots (point 5, decision 2).**
   - Before any copy or delete, `require_plain_paths` checks each root the call uses:
     - backup: `_sd`, `_sd_backup`, `_sd_backup_tmp`, `_sd_backup_old`;
     - restore: `_sd`, `_sd_backup`, `_sd_restore_tmp`, `_sd_restore_old`;
     - check: `_sd_backup`.
   - It also checks every entry for the save and everything under them. A symlink (`symlink_status`), a Windows `FILE_ATTRIBUTE_REPARSE_POINT`, or anything not a plain file or directory gives `INTERNAL` with nothing changed.
   - Each entry's `weakly_canonical` must also lie under its root's.
   - `copy_tree` checks each entry itself and refuses a link instead of following it. There is no `std::filesystem::copy(..., recursive)` left.
5. **Tests only.** Behaviour 5fed277cf2 already has, plus `static_assert`s in `SceTypes.hpp`:
   - `SaveDataCheckBackupData` is 0x48, with `title_id` 0x08, `dir_name` 0x10, `param` 0x18, `icon` 0x20, `reserved` 0x28.
   - `SaveDataRestoreBackupData` is 0x48, with `title_id` 0x08, `dir_name` 0x10, `fingerprint` 0x18, `unused` 0x20, `reserved` 0x24, `pad2` 0x44.
   - The debt file's "not measured on a PS5 … follow shadPS4's PS4 binding" note is kept.
6. **Docs (point 3).** Three entries in the debt file, each under the 1,000-character limit:

## Decisions not in the task

- **The restore's staging is `_sd_restore_tmp/<dir>` and `_sd_restore_old/<dir>`, next to `_sd`, not inside it.** `sceSaveDataDirNameSearch` lists every directory in `_sd`, so a staged copy there would show up as a save, and stay after a crash. Same filesystem as `_sd`, so the renames stay renames. The layout is the backup's: `<entry>/save`, `save.param`, `save.blocks`.
- **The hook's signature is `bool (*)(const char* step, const char* path)`**, not a step name alone. Returning false fails that step. The path lets a test pick a file inside the tree, and the tests count calls of a step to fail the Nth. The hook is called for every directory and file the copies create, for the param write and blocks copy, and before every rename, rollbacks included.
- **"Complete" means the same entries at the same sizes,** compared between `_sd_backup/<dir>` and `_sd_restore_tmp/<dir>`, not a byte compare (saves go up to 1 GiB). `copy_file` either copies everything or throws.
- **Cleanup after a finished swap is best effort.** Removing `_sd_backup_old/<dir>` or `_sd_restore_old/<dir>` once the new copy is in place uses the `error_code` form, so a failure there doesn't report a backup or restore that succeeded as failed. The next backup or restore removes the leftover before it starts, and fails if it can't.
- **Each call checks only the roots it uses** (decision 2): backup `_sd`, `_sd_backup`, `_sd_backup_tmp`, `_sd_backup_old`; restore `_sd`, `_sd_backup`, `_sd_restore_tmp`, `_sd_restore_old`; check `_sd_backup`. A linked `_sd_backup_old` doesn't refuse a restore, and a linked `_sd_restore_old` doesn't refuse a backup.
- **A link anywhere in the live save is refused too,** for the restore (which removes the tree) and the backup (which copies it). `RemoveTree` would remove a link without following it, but decision 2 covers every entry touched.
- **`sceSaveDataCheckBackupData` applies the same check to `_sd_backup/<dir>`,** so a linked backup is `INTERNAL` there as well, not read through.
- **`..` and `a/b` with `sceSaveDataUmountWithBackup`:** this call takes a mount point, not a directory name, so it can't return `PARAMETER` for them. The tests check what can be checked:
  - such a save can't be mounted (`sceSaveDataMount3` gives `PARAMETER`);
  - `..` and `a/b` as mount points give `NOT_MOUNTED`, as every unknown mount point does (already documented in the debt file);
  - `PARAMETER` is checked for `sceSaveDataCheckBackupData` and `sceSaveDataRestoreBackupData`.
- **The failed-copy case for the backup (commit 5)** fails the first `backup.copy` step. The call returns 0, its event has `INTERNAL`, the save is unmounted (`sceSaveDataGetMountInfo` gives `NOT_MOUNTED`) and the previous backup is kept.
- **fsync is checked by reading the code only.** `strace` isn't installed on this VM. Flushing can't be observed from the tests; their failure paths go through the hook.
