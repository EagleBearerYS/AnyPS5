## 2. Conflict resolutions

Both conflicts come from BF-024's `a38c704ea` ("count GPU-side indirect draws that read their draw parameters"), which changed the lines BF-025 edits.

1. **`Graphics/include/Draw.hpp`.** BF-024 declares `CountIndirectDraw(IndirectDrawPath, double readMs, bool rewritten = false, bool drawParameters = false)`. BF-025 adds `struct IndirectPassStats`, `CountIndirectPass(bool continued, bool barrier)` and `IndirectPassCounters()` after the three-argument declaration. I kept BF-024's four-argument declaration and put BF-025's three additions after it.
2. **`Graphics/src/Draw.cpp`, two hunks:**
   - **Definitions.** BF-025's anonymous namespace (`IndirectPassCounts`, `PassCounts()`, `IndirectPassContinueOff()`), `CountIndirectPass` and `IndirectPassCounters` now sit before BF-024's four-argument `CountIndirectDraw`, which keeps its `indirectDrawParameters` count.
   - **End of `recordDraw`.** I kept BF-024's `CountIndirectDraw(..., rewritten, args->drawParameters)` and added BF-025's `if (gpuIndirect) CountIndirectPass(continued, argumentBarrier);` after it.
   - Checked against BF-025's diff, the ported `Draw.cpp` change is identical: the same 144-line diff with the same added and removed lines.

**Non-textual checks.**
- **#1896's pipelined record branch is unchanged.** `Execution/src/Driver/Draw/Draw.cpp`'s `indirectCpu && pipelineIndirect && no deferred labels && !rectList` branch, and the inline CPU branch, are as BF-024 left them. Both still clear the draw-parameter mode (`drawParameterSgprs = {}`, `indirect->drawParameters = false`) before their per-record rebuilds. Both draw each record directly, so the graphics side never sees them as GPU-side indirect draws.
- **No further pass state to clear on a CPU fallback.** BF-025 keeps no pass state in Execution. Its state lives in the recorder's open `Batch`:
  - `indirectArgumentsVisible`, `indirectUnknownWrites`, `indirectWrites`;
  - only a draw with `gpuIndirect` (path `Gpu`) reads it or sets it;
  - a CPU-path draw only adds its own `PassAccess` writes to `indirectWrites`. A CPU-path draw that uploads, copies or dispatches clears the state through `Recorder::Commands()`, as on main.
  - The in-place rule of `445cb2cc8` only changes `vertexRule` and `instanceRule`, which only `recordIndirectArguments` reads, on the GPU side.
- **Recorder unchanged in shape.** Between BF-025's base `e280ce9d5` and `a38c704ea`, the recorder differs only in:
  - fast5's `DrawUpload` chunk, which is host-written before submit and so needs no barrier;
  - snapshot offsets;
  - main's later `discard` and `removeLabels`, which the village tree doesn't have.
  - The raw command-buffer uses and the clear sites (`Commands()`, `flushPendingStore`, `closeStoreRun`, `dispatchDumps`) are the same 42 lines as main's. The four red mutations applied to the port's sources byte for byte.
- **With `APS5_PIPELINE_INDIRECT=1`**, a GPU-side draw is recorded on the pipeline's committer under the same device lock, through the same `recordDraw`, so the rule is unchanged. The write cases and the ×10 runs pass in that mode too (§3).

## 5. The `[draws]` line

The indirect part now reads:
```
; indirect: gpu-side N (M rewritten, K draw parameters), cpu-side C (...), argument reads R ms; gpu-side passes B begun, X continued; argument barriers P recorded, S skipped
```
- **B against X:** passes begun against continued for GPU-side indirect draws.
- **P against S:** argument barriers recorded against skipped.
- B + X = N for draws on the recorded path. The synchronous, non-lean path counts one pass and one barrier per draw.
