### The harness: `tests/execution/DescriptorHeapCeiling.cpp` (`agc_driver_descriptor_heap_ceiling`)

- **ctest mode:**
  - For table N = 8, table N = 128 and direct N = 8, the keyed image is sampled.
  - The same draw then sees that image's memory change (0 → 1 → 0 three times).
  - It passes with the heap off, with the heap on, and with the heap on plus the skip.
- **`--bench N M W [changed] [direct]`** prints one line per window and a median line.
- **The table draw is title-style.**
  - The pixel shader loads a draw constant (the material index).
  - It then reads `keys[material]` from a key buffer of N keys and loads the T# at `key × 16` from a table of N T#s, then `image_load`s it.
  - The textures are 64×4 R32F, linear, one per 64 KiB block, in a write-watched guest allocation.
  - The draw goes through `VulkanDevice::Draw` with a tiled, resident guest render target, so draws are recorded and use the draw resource cache (template hits).
- **"changed"** writes one texel of the last image before every draw: one image's memory changes.
- **"direct"** is the non-bindless path. A generated pixel shader `s_load_dwordx4`s N T#s at constant offsets from a user-data pointer and sums the loads, so the images become `GuestImages` bindings.
  - The recompiler emits 12 typed bindings of N each for the runtime modes.
  - Above 64 images the recompile fails with `image resource limit exceeded`. So the direct path is measured at N = 8 and 64; N = 128 is outside the direct path's limits.
- **Main narrows an image table to the key values found in the key buffer** (`ResourceMaterializer.cpp` `Narrow`, at most 256 scanned positions, `APS5_IMAGE_TABLE_KEY_SCAN`).
  - N = 8 and 128 narrow to exactly N elements.
  - N = 2,048 and 4,096 are over the scan limit, so the whole table is bound.
  - The harness checks that the `ImageTable` binding has N elements in each case.
  - A key in user data narrows to 2 elements (record 0 plus the key), which is why the harness reads it from memory.
- **Three harness traps, for anyone who reuses it.** Each one silently measures something else:
  - A linear color target is never resident. Every draw is then synchronous and a full build.
  - A vertex buffer outside guest memory makes every build non-reusable (`noteReusable`).
  - Textures inside the 64 MiB host import of the table buffer lose write-watch (`GuestMemory::Watched` is false). Revalidation then compares their bytes. So tables and textures live in separate guest allocations.

## 1. Today's per-draw descriptor cost (main path, heap off)

**What each column measures:**
- `lookup` is the `[draw]` phase of the cache find plus `Revalidate`: the validation that decides a cached table can be reused.
- `images`, `alloc` and `writes` are build phases (the `[resources]` names):
  - `images` is the stage-B `images` phase (`resolveImageTables`: per element decode, checks and `cachedTexture`);
  - `alloc` is the stage-A `descriptors` phase (layout lookup and set allocation);
  - `writes` is the stage-B `descriptors` phase (building the write arrays and one `vkUpdateDescriptorSets`).
- `prepare` is `PrepareDrawBindings`. On a template hit it allocates a fresh set (`AllocateRewritten`) for the draw's guest-buffer snapshots and re-issues every write of the set, table elements included.
- `bind` is the `vkCmdBindDescriptorSets` calls.
- `record` is the `[draw]` record phase. It includes lavapipe's per-draw processing of the bound sets at `vkCmdDraw*`.
- The table-reuse memo check (`FindReusedTable`/`TableCurrent`/`CachedTableTextures`) costs 0.3–0.5 µs per build and never hit here, so it is left out.

**What it says:**
- **Memory unchanged:**
  - Every draw is a template hit; nothing is built.
  - The cost is the validation: `Revalidate` re-proves every table texture, at 2.3–4.5 µs per element (18.3 ms at 4,096).
  - Then come the per-draw set rewrite (`prepare`, about 0.24 µs per element, because the snapshot set re-writes all N table descriptors every draw) and lavapipe's draw-time descriptor processing (`record`, about 0.3 µs per element).
- **One image changed:**
  - Every draw is a full build, because `Revalidate` fails on the changed texture and the whole `ShaderResources` is rebuilt.
  - `images` costs 4.8–5.5 µs per element and `writes` 0.37 µs per element.
- **lavapipe pays 11–15 ms per table set allocation, whatever N is.**
  - Binding 260 is declared with `imageTableCapacity` descriptors: 262,144 on lavapipe, which is 4 stages × 65,536.
  - lavapipe sizes a set's storage from the layout maximum, not from the variable count. gdb samples show `memset` inside `vkAllocateDescriptorSets` under `DescriptorCache::Allocate`, and `munmap` when the set is freed.
  - This is lavapipe-specific. The direct path's sets (no variable binding) allocate in 24–32 µs.

## 2. The heap prototype (image-table path, graphics stages)

**What it does (`APS5_DESCRIPTOR_HEAP=1`, default off):**
- **Device** (`Execution/src/VulkanDevice.cpp`):
  - Enables `descriptorBindingSampledImageUpdateAfterBind` and `descriptorBindingUpdateUnusedWhilePending`, and always queries the descriptor-indexing limits.
  - Creates one `DescriptorHeap` (`Graphics/src/DescriptorHeap.cpp`), a set with an `UPDATE_AFTER_BIND_POOL` layout:
    - binding 0: a sampled-image array sized from the device limit (`min(maxDescriptorSetUpdateAfterBindSampledImages, maxPerStageDescriptorUpdateAfterBindSampledImages, maxPerStageUpdateAfterBindResources − 1,024, 2^20)`), which is **998,976 slots** on lavapipe;
    - binding 1: 4,096 samplers;
    - both with `UPDATE_AFTER_BIND | PARTIALLY_BOUND | UPDATE_UNUSED_WHILE_PENDING`.
  - Slot 0 holds a placeholder 2D view.
- **Slots** (`Graphics/src/Texture.cpp`):
  - A `Texture` takes a slot for its view (and one for its first-layer view) on first table use, with one `vkUpdateDescriptorSets`. The slot is then cached on the texture.
  - `Texture::release` frees it. The slot is reused only once `Recorder::CompletedThrough()` passes the batch that was open at release.
  - Views are persistent, so a slot never changes while its texture lives.
- **Table** (`Graphics/src/ShaderResources.cpp`):
  - Graphics builds drop binding 260 from the per-draw sets (and from `DescribeSetLayouts`).
  - Each table map gets N more words, one slot per element, and `HeaderElementBase` points at them.
  - The map buffer is already per build and reused unchanged by template hits, so it plays the role of the index ring. A separate ring buffer would add an upload without saving one.
- **Shader** (`SpirvImageEmitter.cpp`, `SpirvEmitterHelpers.cpp`):
  - The table's image variables move to set 2, binding 0.
  - The element index becomes `checked ? map[map[HeaderElementBase] + element] : 0`: one extra SSBO load and a select, still decorated NonUniform.
  - `Recompiler.cpp` reports the heap variables as binding 260 to the binding plan, and `ShaderValidation.cpp` accepts them.
  - The switch is keyed in the shader disk cache: it is in `RecompilerSwitches`, and `ImageTableAbi::DescriptorHeapEnabled` is added to `shaderCacheReviewedNames`.
- **Pipelines and binds:**
  - Graphics pipeline layouts get set 2 (and an empty set 1 when the sets are not split); `PipelineLibrary` accepts the third set.
  - The heap set is bound per draw, after the draw's own sets.
- **Not covered:**
  - Table samplers stay in the per-draw set: the sampler array is declared but unused.
  - Compute dispatches keep binding 260.
  - Slot assignment takes a mutex.

**The skip (`APS5_DESCRIPTOR_HEAP_SKIP_IMAGES=1`, on top of the heap):** this is the addendum's minimal write-epoch check.
- Per table (keyed by its T# words, 4 per thread), each element remembers its texture (weakly) and the tracker generation (`GuestMemory::TrackerGeneration()`) stamped right after a `CollectWrites` of its range when it was last resolved.
- On the next build, an element whose texture is alive and whose range passes `CollectWrites` + `UnchangedSince(range, stamp)` is bound to its slot without decoding, without the per-element checks and without `cachedTexture`.
- The memo is dropped when a pending storage write overlaps one of its ranges.
- Main's whole-table memo needs every element unchanged, so it never helps when one image changed.

- **Slots:** with the heap a build reads N slots (`slotReads` = N). One new slot is assigned per draw in the changed cases: main replaces a changed texture with a new `Texture` object, so it gets a new view and a new slot. No slot is assigned on unchanged draws. Bind stays at 1–4 µs.
- **Skip hits:** it reused N − 1 elements per changed build (7/8, 127/128, 2,047/2,048, 4,095/4,096).

**What the heap removes (descriptors only):**
- On lavapipe the whole 11–15 ms set allocation goes. With no variable binding, set allocation drops to 23–42 µs.
- Writes drop from 0.37 µs per element to a constant 2–10 µs.
- The per-draw snapshot-set rewrite on template hits drops from about 0.24 µs per element to a constant 15–75 µs.
- lavapipe's draw-time processing of the table descriptors goes, about 0.23 µs per element.
- At N = 4,096: a template hit loses about 1.8 ms of descriptor work, a rebuild about 13.1 ms (11.5 ms of it lavapipe's allocation).

**What persistent views save on `images`:** nothing by themselves (N = 2,048: 9.9 → 10.1 ms; N = 4,096: 22.4 → 22.3 ms).
- `images` is the per-element resolution (decode, sampler-pairing checks, `cachedTexture`), not descriptor work, and the heap leaves it unchanged.
- With the write-generation skip it halves: 10.1 → 5.9 ms at 2,048, and 22.3 → 11.2 ms at 4,096.
- The remaining 2.7 µs per skipped element is roughly:
  - the `CollectWrites` page walk of the element's range;
  - `bind`'s per-element bookkeeping: the `Require*` sampler-pairing checks, and pushing into `textures`, `textureFirstLayer` and `describedRanges`.
- Moving the pairing checks to resolution time and keeping the previous build's per-element vectors would leave only the generation check, an estimated well under 1 µs.

**The ceiling is set by validation, not descriptors.**
- On unchanged draws, `lookup` (`Revalidate`) is 93 % of the draw at N = 4,096 (18.3 of 19.6 ms) in every mode. So the heap gains only 1–2 % there, although it removes about 1.8 ms of descriptor work.
- The real ceiling needs validation that is O(1) per table instead of O(N):
  - For example, #6454's vouch (one `SrtWriteStamp` per table span) for the T# words, plus one write stamp covering the table's texture ranges, instead of one `cachedTexture` proof per element.
  - With that, an unchanged draw at N = 4,096 would cost roughly the remaining prepare + record + bind: 0.3–0.4 ms instead of 19.6 ms.
  - A one-changed draw would cost one element's resolution plus a slot write, instead of a rebuild.
  - These are estimates from the per-phase numbers above, not measured.

## 3. Non-bindless titles (Lana, Animal Well): what the heap needs, and its per-draw cost

These titles bind a handful of T#s per draw through user data or the SRT. Those become `GuestImages` bindings: typed arrays per image kind, 12 bindings of N each for a T# whose mode is decided at run time. The heap needs four things there:
- **Per-draw slot lookups.** Each bound element's texture already gives its slot (`Texture::HeapSlot`, cached on the texture): N reads, a few ns each. This is the same code as the table path.
- **An index table.** The shader needs the N slots per draw.
  - With N ≤ 64 (the direct-path cap), the slots fit in push constants: 4 bytes each, under lavapipe's 256 bytes and the 128-byte minimum for N ≤ 32.
  - Larger N can use a word region in the existing ShaderData/FlattenedSrt buffer.
  - Either way the slots ride the per-draw push-constant or data path that is already there. No new set and no ring buffer.
- **A recompiler change.** `LoadSampledImageDescriptor`'s typed-heap branch (`SpirvDescriptors.cpp`, the `imageVariables` / `ResourceForDescriptor` path) must index the set-2 heap by `slots[resource]` instead of `image_<kind>[arrayIndex]`.
  - All 12 typed bindings alias the one heap binding, as the table path's `table_images_<kind>` variables already do.
  - The driver must pick the view per mode (2D or first-layer array, sRGB, base level). Each such view needs its own slot, because `Texture::SrgbView`/`BaseLevelView` are separate views.
  - The binding plan and validation must accept the heap set, as was done for tables.
- **Estimated per-draw cost.** Today's direct draws cost 49.5 µs (N = 8) and 125 µs (N = 64) unchanged, and 410 / 952 µs with one image changed. Of that, descriptor work is:
  - per template hit: `prepare` ~10 µs and `record` ~14–17 µs (part of the latter is the 12 × N descriptors lavapipe processes per draw);
  - per rebuild: `alloc` 24–32 µs and `writes` 5.5–6.7 µs.
  The heap would save about 5–15 µs per unchanged draw and about 30–40 µs per rebuild, roughly 10 %. `lookup` (23–94 µs unchanged, 233–546 µs changed) and `images` stay, as in item 2. Unlike tables, there is no lavapipe allocation cliff to remove here.

## 4. Risks

- **Device limits.** The prototype sizes the heap from the device at run time and refuses to start (`Require`) if the device allows no update-after-bind sampled images.
  - **lavapipe** (probe, measured): every `maxDescriptorSetUpdateAfterBind*` and `maxPerStage*UpdateAfterBind*` limit is 1,000,000, and `maxUpdateAfterBindDescriptorsInAllPools` is 4,294,967,295. sampledImageUpdateAfterBind, updateUnusedWhilePending, partiallyBound, runtimeDescriptorArray and native nonuniform sampled-image indexing are all supported. The heap gets 998,976 slots.
  - **NVIDIA:** not measured here. Public vulkaninfo dumps show 1,048,576 (2^20) for the regular per-set sampled-image limit ([TITAN RTX](https://openbenchmarking.org/system/2010279-FI-TESTWITHD90/NVIDIA%20TITAN%20RTX/vulkaninfo), [NVIDIA forum dump](https://forums.developer.nvidia.com/t/vulkaninfo-output/283155)). The update-after-bind values were not visible in what I could reach.
  - **AMD (RADV):** not measured here. RADV derives its per-set limits from a ~2 GiB descriptor budget and reports about 8.4 M (8,388,606 appears in [this dump](https://openbenchmarking.org/system/2010241-FI-DAV1DKERN58/v5.10%20Oct23/vulkaninfo), which does not name its driver). AMDVLK and Windows were not checked.
  - **Policy:** the prototype caps at 2^20, which fits all three. Run `vulkaninfo | grep UpdateAfterBindSampledImages` on each target before relying on it.
  - **macOS (MoltenVK)** is the riskiest. Update-after-bind sampled-image arrays need Metal argument buffers (tier 2) and are absent or small otherwise. The heap needs the current per-draw sets as a fallback there.
  - The 998,976-descriptor heap set cost nothing measurable to bind on lavapipe (1–4 µs per draw). I did not measure the driver memory it takes on NVIDIA or AMD.
- **Nonuniform indexing.**
  - The heap index comes from an SSBO load (`map[base + element]`), and its key can come from per-lane data. So it must stay decorated NonUniform, as the table index already is, and the device needs `shaderSampledImageArrayNonUniformIndexing`.
  - lavapipe, NVIDIA and AMD desktop drivers all expose it; main already requires it for graphics tables (`descriptorIndexing`).
  - Lanes that fail the table checks read slot 0, the placeholder, so they never touch a freed slot.
  - Non-bindless draws with uniform slots (push constants) would only need dynamic indexing.
- **#6454's epochs and slot reuse.** #6454 (`perf/shader-image-table-reuse-v3-pr`, head `1752c4a89`) vouches for an unwritten table column over its span with one `SrtWriteStamp`. The vouch lasts until a store crosses the span (the table's epoch). It also keeps a freed table's descriptor set and skips rewriting a table that set still holds (`1d66d852d`, `6fb584f01`). How that maps onto slots:
  - **A vouch covers the T# words, not the textures.** Within an epoch the words map to the same elements. Slots belong to texture views, though, and main replaces a texture whose memory changed with a new `Texture`. That is why the prototype assigns one new slot per changed draw.
  - So an epoch can keep a table's slot array only while every element's texture is the same object. The epoch must end on a texture replacement as well as on a store to the table. The skip's per-element `UnchangedSince` check is the second half of that.
  - With slots there is nothing left to "keep and skip rewriting": the map's slot words are the whole per-table state. #6454's kept sets would become kept slot arrays, a few KiB per table instead of a descriptor set.
  - **Slot reuse must outlive both the GPU and every holder.** The prototype frees a slot only when its view is destroyed. That happens only after every holder (`ShaderResources`, kept tables, the recorder's `Keep`) let go and the batches that used it completed. Reuse then waits for `CompletedThrough()` past the batch open at release.
  - #6454's kept table sets hold their textures, so a kept table keeps its slots alive. Its epoch therefore never sees a reused slot, as long as it holds its textures and not just their slot numbers.
  - A design that keeps only slot numbers (to save memory) would need a per-slot generation, checked against the epoch's stamp.
