## Design

**The stored generation.** `BdaResources` now keeps `tableGuardSerial` (BdaResources.hpp:92): the multisample-target guard generation its table was filtered at.
- **After a fresh filter** (BdaResources.cpp:343-344), it is the `guardSerial` that `ExcludeMultisampleTargetRanges(context.device, addressRanges, guardSerial)` wrote back under `guardedMutex`, not the value read before the call.
- **On a space-table cache hit** (:332), it is the key's `guardSerial`. The cache stores its entries' keys `(serial, guardSerial)` after that call (:382, :410), so a key match means the table was filtered at that generation.

**The recheck.** It is `BdaResources::TableGuardCurrent(device, ranges)` (BdaResources.cpp:435), reached through `ShaderResources::AddressTableGuardCurrent()` (ShaderResources.cpp:6090). It passes the build's cached space ranges, the ones its table was made from: `guestMemory.CachedAddressTable()->ranges`, or `AddressRanges()` when no space table is cached.
- **Unchanged generation:** the check returns at once. This is the common case. It costs `MultisampleTargetRangeGeneration()`: a shared lock on `guardedMutex` and one atomic load.
- **Moved generation:** it runs `ExcludeMultisampleTargetRanges` again over those ranges. This is the same function a fresh build calls; there is no second copy of the exclusion logic. It then compares the result, or the unfiltered ranges if nothing was excluded, with the table: the header's `count`, then the range bytes after the header.
  - **Equal:** the hit is kept, and the generation the call wrote back is stored.
  - **Different:** the hit is refused.

**Where it runs.** In `Draw.cpp`'s hit path (:1978), right after `RetakeSpace()` succeeds and before the snapshot service and `Revalidate`.
- A refusal takes the existing `AddressDrawReuse::SpaceChanged` ("space or epoch change") and releases the retaken space, like the snapshot refusals beside it.
- So the counters and the `[rescache]` line need no new reason.
- The draw then builds fresh, and the fresh build's table excludes the target's range.

**What it refuses and keeps:**

| change since the build | result |
|---|---|
| a resident multisample target created or recreated over a range in the space | refused (SpaceChanged), fresh build |
| a target retired or cleared that was inside the space, so the fresh filter now keeps a range the table excluded | refused (SpaceChanged), fresh build; this follows from the code, and no case covers it |
| a target created, recreated or retired outside the space | kept; the new generation is stored, so the next hit skips the recheck |
| an existing target re-acquired (no generation bump) | kept, no recheck |
| no target activity | kept, no recheck |

**Why not a blanket refusal.** The generation moves on every target create, recreate and retire. A blanket refusal would drop every space hit of a title that retires and recreates a multisample target each frame, even with the target outside the space. The outside case covers this: it keeps the hit on both heads.

**No production knob** was added.

## The test

**The helpers:**
- `MultisampleTargetsAvailable(scene)` (AddressDrawSpaceReuse.cpp:772) skips without write tracking or 4x colour sample counts, as `CachedImageMultisampleGuard`'s `main` does. Under `ANYPS5_REQUIRE_VULKAN=1` a skip fails.
- `PlaceMultisampleTarget(scene, address)` (:780) builds a 64x64 RGBA8 `ColorTarget` with `samples = 4` and calls `MultisampleTargetView` under `GuestMemory::GpuMutex()`. It then submits and waits.
- `RetireMultisampleTargets(scene)` (:798) calls `WaitIdle` and `ClearMultisampleTargets` under the lock, so later cases in the binary aren't affected.

**The cases:**
- **`multisample-target-inside`** (:805):
  1. Store 130 and draw twice, so the space-reuse build is cached and served.
  2. Place the target at `constants.Address(32768)`, inside the draw's registered constant allocation.
  3. Draw again and retire the target.
  4. Require exactly one `SpaceChanged` outcome, `Builds()` +1, and a drawn colour of 130.
- **`multisample-target-outside`** (:825):
  1. Store 160 and draw twice.
  2. Place the target in a separate, unregistered `Pages` block, outside the draw's space.
  3. Draw again and retire the target.
  4. Require one `Reused`, `Builds()` unchanged, and a colour of 160.
- Both cases are registered in `DefaultCases` (:884-885), so the existing ctest entries run them.

**One deviation from the task's test, and why.** The task put the target over the draw's guest constant and checked `FaultAt(address)`. That version crashes llvmpipe on the green head, so the test places the target 32 KiB away in the same allocation instead.
- The table recheck is the same either way: the target's range is inside the space's ranges, so the filtered table differs.
- With the target over the read word, the fresh build's `global_load_dword v1, v0, s[0:1]` (the test's `PixelCode`, which has an SGPR base) loads from an excluded BDA address.
- **llvmpipe SIGSEGVs** in its `llvmpipe-0` worker on that load, at si_addr 0x0, in JIT code with no symbols (`?? ()` frames).
- **This crash isn't caused by this commit:**
  - It reproduces with `APS5_NO_ADDRESS_DRAW_REUSE=1`, where there is no reuse at all.
  - It reproduces with no multisample target: a probe that draws `PixelCode` at an address in an unmapped `Unmapped` block segfaults the same way.
  - The existing fault cases use `IndirectPixelCode`, whose faulting load is the `off` form (`global_load_dword v1, v[2:3], off`). That form reports the fault through the fault buffer and doesn't crash.
- **A separate finding for the board:** a direct, SGPR-base global load from an address that isn't in the BDA table crashes lavapipe (LLVM 20.1.2, Mesa 25.2.8), where the `off` form reports a fault. I didn't chase it here, because it is outside this commit.
