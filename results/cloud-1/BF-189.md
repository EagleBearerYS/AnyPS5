**What the implemented writers share:**
- **Bytes:** each writer records with the same shared encoder as its sibling, so it writes the sibling's bytes.
- **Errors:** they return the sibling's `SCE_KERNEL_ERROR_EINVAL` for an invalid range, direct offset or protection, and write nothing.
- **GPU mask id:** ignored, as the siblings ignore it.
- **Protection or mask bits above 32:** rejected with `SCE_KERNEL_ERROR_EINVAL`. The sibling takes `int32` and can't receive them, so I followed the existing `sceKernelWriteModifyMtypeProtectCommand`, which rejects them (its test at `GuestAmpr.cpp:1351`).

**Why the 5 are dropped:**
- **No call site in the tree.**
- **Nothing in ampr_emu:** the names aren't among its hook targets, declarations or sources (grep over the clone at cfa85df379f6).
- **No public declaration** turned up in a web search for the names.
- **The sibling isn't enough:** the libSceAmpr siblings (`sceAmprCommandBufferWriteAddressOnCompletion`, `…WriteCounterOnCompletion`, `…WaitOnAddress`, `…WaitOnCounter`, `…WriteKernelEventQueueOnCompletion`) give the recorded arguments, but not the kernel form. Unknowns:
  - whether `dst`/`outSize` wrap them;
  - the argument widths;
  - whether the waits take `flush`;
  - the `ident` width of the event queue.

  The 13 confirmed rows all follow `(dst, sibling args, outSize)`, but applying that to these 5 would be a guess.
- **If the sibling pattern is accepted as confirmation,** they are a small follow-up: the same helper over the APR records (`WriteAddressCommand`, `WriteCounterCommand`, `WaitCommand`, `WriteKernelEventQueueCommand`).

**Open question (not changed here):**
- **Where the console exports these:** ampr_emu hooks these functions in libkernel (`kKnownLibkernelHandle = 0x2001`), and the two existing kernel writers live in libkernel (`Apr.cpp`). In this tree only libkernel_sys has export stubs for these 13 names, so the batch implements them there, as the task asks.
- **Why it might matter:** if titles import them from libkernel, then on Windows a libkernel import never reaches libkernel_sys (the reason #9273 moved pselect into libkernel). A follow-up would move them, the way pselect was moved.

## The encoder refactor (d689d1b59)

- **What moved:** `ValidMapRange`, `ValidAmmProtection`, `ValidMap`, `ValidRemap` and `ValidProtect`, plus new `EncodeAmmMap`, `EncodeAmmUnmap`, `EncodeAmmRemap` and `EncodeAmmProtect` (each returns the record, or `nullopt` if a check fails). They go into `core/libs/prx/libkernel/Apr/include/AprCommandBuffer.hpp` (namespace `Apr`), which already holds the record structs.
- **libSceAmpr after the move:**
  - it takes the validators with `using` declarations, so their existing call sites (the measures, map begin and PRT paths) are unchanged;
  - its `RecordAmmMap`, `RecordAmmRemap`, `RecordAmmProtect` and `sceAmprAmmCommandBufferUnmap` call the encoders, in the same check order (null buffer EINVAL, unbound EPERM, invalid EINVAL, then append).
- **No behaviour change:** the 9 AMPR tests pass at d689d1b59 (guest_ampr_markers, guest_amm_placement, guest_ampr_threads, guest_ampr_cpp_error and the five guest_apr_read_* tests).
- **No new link:** the kernel writers include the header only. A direct call into libSceAmpr would have needed new `_nid_no_patch` entry points, because exported names are NID-patched.

## The tests (guest_kernel_sys, `core/libs/tests/GuestKernelSys.cpp`)

**Registration:** `guest_kernel_sys_tests` now also links `libSceAmpr`. On WIN32 it gains the `PATH=path_list_prepend:$<TARGET_FILE_DIR:libSceAmpr>` entry that the libSceAmpr tests carry.

**`CheckAmmWriteCommands`** (92f7271cc):
- **How each writer is checked:** for every writer it calls the libSceAmpr sibling on a 64-byte bound buffer, then the kernel writer twice: once with `dst` null and an `outSize`, once with both.
- **What it requires:**
  - the same result in all three calls;
  - on success, the measured and reported size equal the sibling's appended bytes, the written bytes equal the sibling's record, nothing is written past it, and `outSize` null still writes the same bytes;
  - on failure, the sibling appended nothing, both sizes are untouched and the destination keeps its `0xCC` fill.
- **The inputs:**
  - valid arguments;
  - a misaligned address;
  - a misaligned direct offset (map direct);
  - a zero size (unmap);
  - a misaligned source (remap and multimap);
  - protection bit 0x04 in the protection or the mask.
- **Plus:** three writers given a protection or mask with bit 32 set return EINVAL and leave the size untouched.
- **Total:** 38 sibling comparisons and 3 wide-argument checks, 41 in all.

**`CheckAmmWaitCompletion`** (afd5c4a20):
- records a 16 KiB map with `sceKernelWriteMapCommand`;
- submits it with `sceAmprAmmSubmitCommandBuffer3` from a pool given with `sceAmprAmmGiveDirectMemory` (usage 1);
- requires `sceKernelWaitCommandBufferCompletion(id) == 0`, then writes and reads the mapped page;
- waits again, which returns 0;
- requires `ESRCH` for id 0, and for id + 1 (as the sibling does).

## Draft PR body

### What
Implements 13 of libkernel_sys's AMPR command exports on the libSceAmpr encoders:

- the twelve AMM writers: sceKernelWriteMapCommand, sceKernelWriteMapWithGpuMaskIdCommand, sceKernelWriteMapDirectCommand, sceKernelWriteMapDirectWithGpuMaskIdCommand, sceKernelWriteUnmapCommand, sceKernelWriteRemapCommand, sceKernelWriteRemapWithGpuMaskIdCommand, sceKernelWriteMultiMapCommand, sceKernelWriteMultiMapWithGpuMaskIdCommand, sceKernelWriteModifyProtectCommand, sceKernelWriteModifyProtectWithGpuMaskIdCommand, sceKernelWriteModifyMtypeProtectWithGpuMaskIdCommand;
- sceKernelWaitCommandBufferCompletion.

The AMM range and protection checks and the records they build move from libSceAmpr into the APR command buffer header that libSceAmpr and libkernel already share. Each kernel writer records exactly what its libSceAmpr command buffer sibling appends, with the same errors.
- Signatures follow ampr_emu's libkernel hook targets (cfa85df379f6, include/ampr_libkernel_hook_targets.h).
- A null `dst` only reports the size, as for sceKernelWriteModifyMtypeProtectCommand.
- The wait returns 0 once the AMM submission has run and SCE_KERNEL_ERROR_ESRCH for an id that was never submitted, as sceAmprAmmWaitCommandBufferCompletion does.

The five APR writers (WriteAddress, WriteCounter, WaitOnAddress, WaitOnCounter, EventQueueOnCompletion) stay NotImplemented: no source gives their kernel signatures.

- It also submits a map written by sceKernelWriteMapCommand, waits for it with sceKernelWaitCommandBufferCompletion, and uses the mapped page.
- The AMPR tests (guest_ampr_markers, guest_amm_placement, guest_ampr_threads, guest_ampr_cpp_error, guest_apr_read_*) pass unchanged.
