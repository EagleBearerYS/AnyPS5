## Verdict

1. **The fix works for every entry point.** `sceAgcDriverResolveShaderAbi`, its graphics path, `sceAgcDriverResolveGraphicsStagesAbi` and `sceAgcDriverResolveGraphicsAbi` no longer throw for a stage they cannot prepare:
   - they log it once, record the deferral and return;
   - the `ShaderPreparationScope` that libSceAgc opens around them still commits.

   Each entry point is red without the fix and green with it.
2. **The task's premise does not hold on main: no draw can prepare Village's stage either.**
   - The error comes from the recompiler's resource plan. That plan is keyed and built from the code and the stage interface only, never from user data or guest memory, so a draw whose interface matches the pipeline's builds the same plan and fails the same way.
   - Image tables don't change that. They serve a lane-keyed key at the ABI call too, but not a T# pointer that is itself a phi of user data and a ballot.
   - I rebuilt that chain. Through the ABI it fails with Village's exact message. A draw of it fails at use with the same message, and the new pixel test pins that.
   - **So for Village, this branch moves the stop from pipeline creation to the first draw of that pixel shader, if the title draws it.** Rendering it needs the recompiler change in §6, which I state as scope with a design.
3. **One real "fails at the ABI call, works at use" case exists:** a compute shader that calls user-data pointers.
   - On main, `ResolveShaderAbi` throws "s_swappc_b64 call target ... is not statically resolvable".
   - The dispatch links the callees.
   - With the fix, the dispatch prepares the shader at use and every lane computes 3 × (5 + 64).
4. **Stored failures are unchanged:** driver failures, `ProcessShutdown`, and a failure stored by the shader's own registration preparation still propagate.

## 1. Root cause and every eager-prepare path

**Root cause.** Village's throw goes through these steps:

1. libSceAgc's `sceAgcCreateInterpolantMapping` (InterpolantMapping.cpp:75, :83 / :115) or `sceAgcLinkShaders` (LinkShaders.cpp:25-34) opens a `ShaderPreparationScope`. That is a root transaction.
2. It calls `AgcDriverResolveShaderAbi_nid_postfix(ps, interpolant registers)`.
3. `Driver::ResolveShaderAbi` (main:1240) runs its prepare lambda (main:1272-1277): `PlanRegistered(..., false)` + `PrepareRegistered` → `PrepareShaderWithDiagnostics` (:42) → `ShaderRecompiler::PrepareShader` → `getSource` → the resource plan → `ResourceTracker::GetHandle`.
4. `GetHandle` throws `"GetImageResource dword 0 is not a valid runtime value"` (ResourceTracker.cpp:1382).
5. The entry point (EntryPoints.cpp:130-134) catches only `ProcessShutdown`, so the exception reaches the HLE function and the title.

**Why that T# chain fails:**
- The T# pointer is `Phi(GetUserData, CompositeExtractU32x4(Ballot(...)))`: a waterfall loop writes its ballot into the same SGPR pair.
- `RuntimeValidator` accepts a phi only when `ResolveInvariantPhi` reduces it to one value (IrProgram.cpp:801), and `Ballot` and `CompositeExtractU32x4` are not runtime-uniform ops (SrtInstructionPredicates.cpp:53).
- An image table can't take it over: `TryMakeTableColumn` (ResourceTracker.cpp:553) needs scalar reads of a heap as the pointer.
- The descriptor-phi split can't take it over either: `CollectDescriptorPhis` (:765) stops at the `LoadAddressU32`.

**The trap the task names.**
- A nested transaction destroyed uncommitted sets `root->failed` (main:272), and the root's `Commit` then throws "shader preparation transaction was aborted" (main:307).
- So the failure has to be caught inside each ABI call's own transaction, not at the entry point. §6 shows the entry-point variant failing.

## 2. The fix (17fd92440)

- **`DeferPipelineStage`** (head:890) logs once per shader:
  `Shader 0x… could not be prepared when the title created its pipeline (<what>); preparing it when it is used`.
  - It then sets `PreparedShaderState::deferred`, the flag registration already sets for a shader it prepares at use.
  - `ReportPreparedAtUse` keeps silencing the at-use line for such a shader (head:455).
- **`ShaderPreparationTransaction::Commit`** carries `deferred` into the shared state (head:330), so the once-per-shader check holds across calls. The global writers lock serializes it across threads.
- **`ResolveShaderAbi`:**
  - the prepare lambda catches `std::exception` and keeps the message (head:1286-1297);
  - after the existing entry merge, it defers the shader and pushes the ABI key into `registeredAbis` as before (head:1311);
  - a repeated call for the key returns at `CommittedAbi`, so nothing is prepared again.
- **`PrepareGraphicsStages(..., bool deferUnprepared = false)`:**
  - with `true` from `ResolveGraphicsStagesAbi`, a stage that throws is deferred inside the function's own transaction and returned with a null handle (head:1150-1158);
  - the other stages are still prepared;
  - `ResolveGraphicsStagesAbi` skips the null handle (head:1232) and records the `GraphicsAbi` key as before, so a repeat takes the reuse loop;
  - the default keeps every other caller, including `PreparedGraphics.cpp`, throwing.
- **`ResolvePreparedGraphics`** skips a fragment pair while either stage is deferred and has no artifact (head:1404). The draw's `DrawRectangle` calls it after both stages were prepared at use, so rect-list draws still get their rectangle.
- **What still propagates:**
  - driver failures, from `CheckFailure` at entry, before any catch;
  - `ProcessShutdown`: it is not a `std::exception` (Shutdown.hpp:6), so no catch here can take it;
  - a stored registration failure, rethrown by `AwaitRegisteredPreparation` outside the catches;
  - lookup errors.
- **docs/dev/ARCHITECTURE.md** gets one line next to the "prepared at use" line.

## 6. Adversarial review

### Could a better version prepare such stages at pipeline creation?

Scope, with a design. Making the resource plan accept Village's chain would fix both the ABI call and the draw. It takes three changes:

1. **Walk through the read.** `CollectDescriptorPhis` (ResourceTracker.cpp:765), `SubstituteEdge` and `Rematerialize` (:810) walk only runtime-uniform ops and `ReadFirstLane`. So they stop at the `LoadAddressU32` that reads the T# through the phi'd pointer. They need to look through a scalar-address read and its `GetAddressResource`, and re-emit that read once per arm.
2. **Poison the arm that cannot be rebuilt.**
   - `SplitDescriptorEdges` (:913) gives up when one arm cannot be rematerialized: Village's ballot arm.
   - With image-table poison semantics, that arm becomes a poisoned copy. It returns zero and, like a poisoned table entry, faults only when a lane takes it.
   - `EdgeSelector` picks that arm only when control arrives along its edge.
   - The entry arm then reads the real T#, `ValidateSource` sees only valid sources, and the stage prepares at pipeline creation and renders.
   - On hardware, the back-edge arm would read a T# at the address the ballot mask makes, so zero is a defined stand-in. If the edge is a structurizer artifact, it never runs.
3. **Costs and risks.**
   - The new reads appear after the SRT plan is built (Recompiler.cpp:293 before :298), so the materializer has to evaluate reads it has no slot for.
   - Every program with a non-invariant phi behind a scalar-address descriptor read changes its IR.
   - The disk cache format moves.
   - The fault needs a slot.
   - Tests: a recompiler case with a valid/valid phi (both arms read a real T#), one with a valid/poisoned phi (this chain), and a draw that renders the entry arm's texture.

It is a recompiler change of its own (one topic per PR), and it doesn't replace the deferral: the compute caller, and any other stage only its use can prepare, still need this branch. **It is what Village's pixel shader needs to render, so it should be the next task.**

### Other points

- **a. The premise.**
  - I sent three fragment programs through `ShaderRecompiler::PrepareShader` twice: once with the ABI call's interface, and once with input 0 defaulted, as `DefaultUnexportedInputs` does at a draw.
  - **Lane-keyed table offset:** it prepares in both. The table serves it at the ABI call too.
  - **Phi'd pointer:** it fails in both.
  - **Pointer keyed by `v_readfirstlane` of an interpolant:** it fails in both. `GetInterpolationParameter` stays an op, so the default is not folded.
  - The plan is cached per request key, and a plan failure is memoized (Recompiler.cpp:459), so a draw with the same interface fails at once. The pixel test's draw shows it.
- **b. A stage's stored registration failure still stops the title at its ABI call.**
  - It is kept, as the task says.
  - It applies to stages registration prepares in the background, when that preparation fails: compute shaders, pixel shaders without interpolants, and vertex shaders registration does not skip. The log then shows "could not be prepared after registration", and the ABI call rethrows the failure; the compute test pins this.
  - The same deferral there would have to treat a stored failure as deferred in `CommittedAbi`, in `PrepareGraphicsStages`' and `ResolvePreparedGraphics`' transaction reads, and in `ShaderPreparationScope`'s `Begin` (`SettleShaderPreparations`).
  - Village's stage is a pixel shader with interpolants, which registration does not prepare (main:798), so it is not this case.
- **c. Partial preparation.**
  - `PrepareRegistered` prepares two variants: partial threads for compute, no push data for pixel.
  - If the second throws, the whole stage is deferred and the first artifact is dropped. The source cache rebuilds it at use.
  - Not worth a partial record.
- **d. Push offsets.**
  - A deferred graphics stage adds no push bytes, so the stage after it is prepared at a lower offset than the draw will use.
  - Artifacts relocate, and `PreparedUnregisteredGraphics` checks that a relocated block reuses its artifact. At worst the draw prepares that stage again.
- **e. Concurrency.**
  - The first preparation runs outside the writers lock, but `Read` and `Edit` take it. A second thread that also failed sees the committed key and returns, so there is one line.
  - `deferred` is read and written only under the snapshot's mutex: `Commit` holds every destination's lock, and `ReportPreparedAtUse` runs under `SourceHandleFor`'s or `InvocationFor`'s lock.
- **f. What is caught.**
  - Only a `std::exception` from the preparation calls. Lookups, `CheckFailure` and the stored-failure rethrows are outside the catches.
  - A `std::bad_alloc` during preparation would be deferred too. The use would hit it again.
- **g. Rect-list draws of a deferred stage.**
  - `DrawRectangle` calls `ResolvePreparedGraphics` after the draw prepared both stages at use. So the skip never applies there, and the rectangle is built as on main.

## Draft PR text

Title: `fix(agc): leave a stage the title's pipeline ABI cannot prepare to its first use`

```markdown
### What
When a title creates a pipeline, `sceAgcDriverResolveShaderAbi`, `sceAgcDriverResolveGraphicsStagesAbi` and `sceAgcDriverResolveGraphicsAbi` prepare its stages. If the recompiler could not prepare a stage there, the call threw and the title stopped at pipeline creation. Two cases on main:
- Resident Evil Village stops this way on a pixel shader whose T# pointer is a phi of user data and a ballot (`GetImageResource dword 0 is not a valid runtime value`).
- A compute shader that calls user-data pointers stopped the same way, although its dispatch links the callees.

Such a stage is now left to its first use, like a stage registration cannot prepare:
- `ResolveShaderAbi` and `PrepareGraphicsStages` catch the failure inside their own preparation transaction. The `ShaderPreparationScope` that libSceAgc opens around the call (`sceAgcLinkShaders`, `sceAgcCreateInterpolantMapping`, `sceAgcCreatePrimState`) still commits. A catch at the entry point would leave that scope aborted.
- The shader is logged once ("could not be prepared when the title created its pipeline (…); preparing it when it is used") and marked deferred. The ABI key is recorded, so a repeated call prepares nothing.
- `ResolvePreparedGraphics` skips the rectangles of a deferred stage that has no artifact yet. This also lets `sceAgcDriverResolveGraphicsAbi` through for a stage deferred at registration, which threw "rectangle ABI has missing stage artifacts".

The draw or dispatch that uses the stage prepares it as before, and fails there if it cannot. Village's pixel shader still fails at its draw: the resource plan depends only on the code and the stage interface, so the draw builds the same plan.

Driver failures, `ProcessShutdown` and a failure stored by the shader's registration preparation still propagate. `docs/dev/ARCHITECTURE.md` gets a line.
```
