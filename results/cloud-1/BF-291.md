## Summary

- **What the complete stage is.** It is not a CPU-only phase. It:
  1. records into the device's single open batch (uploads, GPU copies, write-backs, staging copies, depth-plane copies, `Keep`);
  2. waits for and reaps batches, which runs other threads' completions;
  3. mutates per-object state that has no lock of its own (`StorageTexture` and `Texture` fields, the members of a cached `ShaderResources`, writable mirror contents);
  4. reconciles and retires host imports.

  The containers it looks things up in already lock themselves. What only the GPU mutex guards is the recorder, the per-object state, the mirror contents and cross-container consistency. Nothing asserts that: `buildComplete`, `Revalidate` and `UploadFinish` have no `AssertGpuLockHeld`; only comments state it (`SRh:171-175, 447-452, 570, 704-706`).
- **Per-family mutexes alone can't work.** They give memory safety at best (BF-293 reached the same conclusion and did not build C2). Today the cache mutexes are held across calls that take the GPU mutex, recursively (`SR:938-1056`, `SR:1240-1272` → `T:4288`, `T:4165`). Draws take them in the opposite order (GM first). Dropping the outer GM turns that into an AB/BA deadlock.
- **The design: plan unlocked, commit locked.** Each queue worker's complete stage becomes a **plan** run without GM, and a short **commit** under GM.
  - The plan only reads, through the containers' own mutexes, immutable snapshots, and existing atomic versions. It records nothing, waits for nothing and mutates nothing.
  - The commit checks the plan's ticket (the versions it read), applies the plan's side effects, and records.
  - If anything moved, the commit runs today's locked code. So a wrong plan costs time, never correctness.
  - GM stays the one lock for recording, submitting, waiting, reaping, per-object mutation, imports, mirrors, shadows and depth planes.
- **Six PR stages, each behind a switch where risky** (section 4). The first one, *wait before the hold*, needs no data-structure change at all.
  - **The gap it closes:** today's presync (`VD:5033-5048`) waits before the worker takes GM, but the worker then queues for the lock for 0.8 ms on average. Meanwhile the other queue records writes that this dispatch's stage B then waits for **under** the lock: "resources: hook waits", 0.43 ms per dispatch.
  - **What stage 1 does:** it re-checks those waits right after taking GM, before the hold has read or changed anything. If one is needed, it waits unlocked, relocks and loops (bounded).
- **Estimate for step 1 alone (section 6).**
  - **Hold:** up to 0.43 ms of the ~1.1 ms per dispatch.
  - **Throughput:** with BF-293's model, ~1.04–1.10× on queues 0x0 and 0x20, against BF-293's bound of 1.27–1.30× for the whole stage. The range depends on the share of hook waits that are for work recorded before the hold, which the PC's `[recorder]` line gives.

## 3. The design

### 3.1 Why not "one mutex per family"

**Option A: the complete stage takes family mutexes instead of GM, while other holders keep GM.**
- **Memory safety:** that would need every GM holder that touches the family to take the family mutex too (the recorder, per-image state, cached objects: dozens of sites).
- **Deadlock:** even then it deadlocks. The complete stage holds `cache.mutex` across `Refresh` → `FlushPending` → GM (`SR:1240-1272` → `T:4288`) and across `Texture` creation, which records (`SR:938-1056`). Draws take GM and then `cache.mutex`. That is AB/BA.
- **Correctness:** it also gives up the hold's atomicity, which the code relies on:
  - stage B's uploads and its dispatch in one hold (`SR:3777-3778`);
  - `RecordStagingCopies` and `RecordCopyBacks` in one hold (`GBM:5911, 5942, 6491`);
  - "the last note is mine" (`Rec:3186-3190`);
  - stamp-then-advance (`T:4952-4956`).

**Option B: per-image mutexes held while uploading (BF-293's item 2).** The upload records, and recording needs GM (one batch, one command pool, one queue). So the image mutex either orders before GM, which deadlocks against completions writing images back under GM, or the recording moves out from under it. That is deferred recording, which is what the commit below is.

### 3.2 Plan unlocked, commit locked

Each dispatch's complete stage splits in two.

**The plan** (no GM; any queue worker or the committer; concurrent):
- **What it is:** a pure function of:
  1. immutable inputs: the compiled shader, its descriptor words, stage A's records, and the fixed members of a completed cached object (`SR:5508-5509`: "Read without the device lock: these members are fixed once the build completed");
  2. reads of shared state through the containers' own mutexes, immutable snapshots, and atomic versions.
- **What it never does:** mutate a shared object, record, submit, wait, reap, call the flush hook on a pending range, take GM, or hold a container mutex across a call that may take GM.
- **When it needs one of those:** it stops and hands the commit "locked from here". The plan never decides on its own that something is unnecessary.
- **What it produces:**
  - a **decision**: the hit is current; or this record's texture is current; or this region needs an upload whose bytes are already in a private staging buffer;
  - the **deferred side effects** the locked code would have done: memo stamps, LRU touches, cache-entry generation advances, `Texture::keyProof` updates, `NoteProved`;
  - a **ticket**: every version it read.

**The commit** (under GM, in the dispatch's existing hold):
- Validates the ticket: pointer and serial compares, plus one tracker query over the plan's stamp ranges.
- On success: applies the side effects, records the planned uploads from their staging buffers, and continues into today's recording.
- On any mismatch, or "locked from here": runs today's code for that step.
- So the locked path is the fallback at every granularity (the whole hit, one record, one region), and a mistaken plan costs time, never correctness.

**What the ticket holds**, with the version that guards each read (most of these exist):

| The plan read | Validated at commit by | Exists? |
|---|---|---|
| guest bytes and stamps of a range | `GuestMemory::UnchangedSinceAll(ranges, g)`, with `g` = `TrackerGeneration()` at plan start: one tracker lock | yes (`GM.cpp:1946-1956, 2130-2136`) |
| CPU stores not yet collected | the existing epoch rule: a store unordered with the dispatch may be seen at the next ordering point (`GM.hpp:97-103`), as BF-284's race cases already accept | yes |
| no pending GPU write over a range | the lock-free snapshot at plan time (`Rec:657-668`); at commit, `publishGeneration` unchanged, or the exact `PendingWriteOverlaps` under GM | yes |
| no pending storage results over a range | `PendingSerial()` unchanged, or a range query under `Pending()`'s mutex | yes (`T:1612`) |
| a sampled-cache entry is still the cache's | `cache.erasures` unchanged plus the entry pointer | yes (`SR:383, 388`) |
| a storage-cache entry is still the cache's | an `erasures` counter on `StorageTextures()` | **new**, trivial |
| a `StorageTexture`'s proof fields (`version`, per-layer `generation`, `layerPending`, `uploadedKeys`/`filledKeys`, key proof) | a per-image immutable **ProofView** snapshot (`AtomicSharedPtr<const ProofView>`), republished under GM at the end of every mutating call; the ticket keeps the pointer | **new** (stage 2) |
| `Texture::keyProof`, `copiedVersion` | the same, on `Texture` | **new** |
| a cached object's `validatedTextures`, `proved*`, `pendingSerialSeen`, `importsProof` | the object's immutable `ProofMemo` / validated-textures snapshots, swapped under GM; the ticket keeps the pointers | **new** |
| an import pointer | `Imports().epoch`, plus the insert count #7514 adds | yes (`GBM:276-278`) |
| driver and label stores anywhere | `storeSerial` (split out of `ProofSerial`, below) | **new**, a split |

**Splitting `ProofSerial`.** Today it moves at every outermost GM acquisition by a non-committer thread (`GM.cpp:2409-2414`). With two queues, the other queue's every dispatch hold would invalidate every ticket.
- **The split:** `storeSerial`, bumped by the explicit `BreakProofs` calls (`GM.cpp:1998, 2045, 2855`; `Rec:3554, 3571, 3599`; `SR:5938`; `Draw.cpp:2167`; `DrawPipeline.cpp:396`), and `holdSerial`, the implicit bump.
- **No behaviour change:** `ProofSerial()` stays their combination for the existing memos.
- **What tickets use:** `storeSerial` plus the precise versions above. They don't need the implicit "something may have changed in another hold" belt, because every input they rely on has its own version.

**Where waits go: before the hold, never inside it.** Releasing GM in the middle of stage B (letting a nested `SyncThrough` wait unlocked) is not safe:
- the lookups hold `cache.mutex` around the hook (`SR:1026`, `SR:1240-1272`);
- the relock rule forbids that (`Rech:251-253`);
- it would break `SR:3777-3778`'s "nothing else touches them between here and the dispatch being recorded".

Instead, the worker computes the waits the hold would make and makes them **after taking GM but before the hold does anything**: unlock, wait, relock, re-check. That is stage 1. Later, the plan computes the serial to wait for and the worker waits before it takes GM, like the presync.

### 3.3 What still needs GM

- **Recording and submitting:** all `vkCmd*` into the open batch, `Submit`, `Keep`/`KeepBytes`/`OnComplete`/notes, `CommandBatch`, detiler rings, sparse binds on the main queue.
- **Waiting and reaping:** `Sync`, `SyncThrough`, `FinishUpTo`, `Reap`, and completions. These are moved *before* the hold by stage 1, not out of GM.
- **Per-object mutation and the snapshot republish:** `StorageTexture` and `Texture` state, cached `ShaderResources` members, view-map creation.
- **The rest of the device-state work:**
  - import reconcile, retire and creation; leases; address-space publish; address-based (BDA) builds, which stay fully locked as today;
  - writable-mirror refresh and contents; unit-shadow publish; depth-plane flushes and copies; multisample snapshots;
  - storage-image creation and eviction `Flush`, and resource-cache `Insert`/`Remove`, whose evictions go to `Keep`.

### 3.4 The lock order

From outermost to innermost:

0. `deviceReplacement` (`Presentation.cpp:62`)
1. `GuestMemory::GpuMutex` (recursive)
2. **container mutexes:** `Textures().mutex` (`SR:133`), `StorageTextures().mutex` (`SR:1086`), `surfacesMutex` (`DS:1674`), `targetsMutex` (`MS:863`), `ResourceCache::mutex` (`SRh:773`), `DescriptorCache::mutex` (`SRh:131`), `SamplerCache` (`Sampler.hpp:63`)
3. **registry mutexes:** `Pending()` (`T:1577`), `Imports().mutex` (`GBM:254`), `Mirrors().mutex` (`GBM:2442`), `Shadows` (`US:103`), `completedMutex`, `writtenBackMutex`, and the leaves `LiveImages` (`T:213`) and the label table (`Rec:549`)
4. the tracker mutex (`GM.cpp:944`); `BufferPool` (leaf)

**Rules:**
- **(a) Code holding GM** keeps today's order (1 → 2 → 3 → 4). Its re-acquisitions of 1 inside 2 or 3 (`FlushPending`, `Flush`, `FlushDepthPlanes`, the hook) stay legal only because they are recursive.
- **(b) The plan** may take one level-2 mutex at a time and levels 3 and 4 inside it. It never takes 1, and never calls anything that may take 1.
- **(c) No thread takes 1 at depth 0 while holding a level-2 or level-3 mutex.** This is the class behind BF-286's deadlock. Stage 0 turns rule (c) into an assertion: a TLS count of held level-2/3 mutexes, checked in `GpuMutexType::lock` when the thread does not already hold GM. #10026's imports-mutex assertion is one instance of it.
- **(d) The ProofView, ProofMemo and validated-texture snapshots** need no lock: they are published with an atomic pointer store under GM and loaded by the plan.

### 3.5 What this buys, and what it doesn't

- **In steady state:** a Village dispatch whose resources are a proven hit would hold GM for the ticket check, the deferred stamps and the recording. Today it holds it for the whole proof.
- **What stays locked:** misses, refreshes, CPU uploads that the plan can't prepare, mirror refreshes, import changes and every write-back.
- **When it pays:** in proportion to how often the plan's ticket survives. BF-292's ceiling switch (C1) and BF-290's real fix shrink the refresh and upload traffic that would otherwise force the locked path on Village's aliased storage images.

## 4. Staging into PRs

**The order** is by size and risk first, then by Village's spend: hook waits 0.43, Revalidate 0.41, B images 0.32, B upload 0.6 ms per dispatch. These rows overlap: "hook waits" is a locked wait inside the others (`VD:5596-5600`).
- **B upload comes last**, even though it is the largest row. Most of what `UploadFinish` does is commit-bound:
  - the mirror `Sync` and compares;
  - import reconcile and retire;
  - `FlushPending` over written ranges;
  - recording the GPU copies.
- **Only its CPU copies can move.** The PC's `[buffers]` line (import lookup, mirror refreshes, CPU copies) says how big that part is.
- **Stage 1 also shrinks the B upload row:** `UploadFinish`'s `CompletePendingCpuWrites` waits (`GBM:5444-5445`) are hook waits.

**Tests** follow BF-284's style. They are `tests/Recorder.cpp` modes that release the fixture's GM, run the steps meant to be unlocked, and take GM themselves where the worker would. Execution tests check pixels, and the existing pipelined-dispatch tests are re-registered with each switch on. No test asserts that a path throws.

- **Atomic or thread-local** counters that only GM serializes today:
  - `Texture.cpp` `Profile()` (`T:62-83`);

  - `DispatchCounters` (`VD:4577-4593`);

### Stage 1: wait before the hold (re-presync at the lock)

**Switch:** `APS5_RELOCK_PRESYNC=1` first. Default on after a Village B A A B, with `APS5_NO_RELOCK_PRESYNC=1` to turn it off.

- **Where:** right after the lock, before anything else in the hold:
  - `Dispatch.cpp:602`, before `recordLabelsForPacket` at `:605`, and so before `keysNoteBefore` at `:613` ("the last note is mine" stays true);
  - `Dispatch.cpp:509` (the committer's dispatch item);
  - the recipe path, whose presync is `VD:5091-5101`.
- **What it checks, under GM, exactly:**
  - **The ranges:** the ranges the hold will read on the CPU or wait on. That is `PresyncSurfaces()` (`SRh:352-359`) plus the cached object's or stage-A build's direct regions, described ranges and storage images. All are fixed after stage A or the build (`SR:5508-5509`).
  - **The predicates**, the same ones the in-hold waits use: `PendingWriteOverlaps`, the copied-writer lists, and completion labels. Use `CompletionLabelIn` if #9445 lands first.
  - A new `ShaderResources::LockWaitRanges()` returns the ranges, and the predicates run under GM, so they are exact.
- **If it would wait:**
  - It requires `DepthOnThisThread() == 1` and that no level-2/3 mutex is held (stage 0's count).
  - It takes the serial as presync does (`DescribePendingWrite`, then `SubmitAndEpoch` if the open batch is the target, `VD:4949-4961`).
  - It unlocks GM, runs `WaitRecorded(serial)`, relocks, `ReapRecorded(serial)` (the same reap the dispatch makes today, `VD:5593`) and re-checks. At most 2 rounds, then it proceeds as today, with waits locked.
- **Counters** (atomics, not profile-only): `relockPresyncs` (rounds), `relockWaitedUs`, and `lockedHookWaits` (a plain count of `SyncThrough`/`Sync` waits made at depth > 1). These go on a `[relock]` line.
- **What it moves:** the hook waits for work recorded before the hold began, from either queue: the `[recorder]` line's "pending write" source at the hook, `CompletePendingCpuWrites` and `syncRange`.
- **What it doesn't move:** waits for work the hold itself records. An example is a `Refresh` that writes another image's results back, records the copy into the host import, then re-uploads from host memory and waits for its own copy. That is the "recorded store" source, and Village's round trip (BF-290/BF-292).

### Stage 2: proof snapshots (data only, no lock change)

- **What it adds:**
  - per-image `ProofView` on `StorageTexture` and `Texture`;
  - `ProofMemo` and the validated-textures snapshot on `ShaderResources`;
  - the storage-cache `erasures` counter;
  - the `ProofSerial` split.
- **What republishes:** every mutating call republishes under GM: `upload`, `Refresh` (changed and unchanged), `writeBack*`, `markLayersPending`, `borrowUnits`, `supersedeHandedOver`/`advanceAdjacent` (on the *other* image), settle, `StampKeepingNewerResults`, `Flush`.
- **Behaviour** is identical. The cost is one allocation per mutating call, measured with BF-265's `agc_driver_village_draw_cost_tests` (`--cost 60`, 4,096 entries, the same cells as BF-284).
- **Tests:** a Recorder mode per mutation kind (seven cases) asserts that the snapshot pointer changed and its fields equal the live fields, read through a test accessor under GM.
- **Red:** drop one republish, and its case fails.
- **TSAN:** a reader thread loads the snapshots in a loop while the main thread mutates under GM. It must report no race; that run is the gate for stage 3.

### Stage 3: the fast proof off the lock (the Revalidate row, 0.41 ms)

- **Switch:** `APS5_PLANNED_REVALIDATE=1`.
- **The plan:** `ShaderResources::PlanRevalidate(shaders)` runs `fastRevalidate`'s predicate on the snapshots. It collects through the thread's memo, queries stamps through the tracker, and scans the registry under its mutex. Keys are read from guest bytes only when the lock-free snapshot and the registry say nothing is pending over them; otherwise the plan goes locked.
- **Where it runs:** in `PrepareDispatch` / `PrepareRecipe` for a cached object. The ticket travels in `PreparedDispatch` / `RecipeHit`.
- **Under GM:** `ticket.Valid()`, then apply the deferred side effects, else `Revalidate` as today. `Remove(key, object)` and `Keep` stay as today.
- **The case the epoch memo still handles:** if the same object was proved earlier in the epoch, the existing epoch memo answers it. That memo becomes a ProofMemo read.

**Race tests:**

| case (between the plan and the commit) | the commit must |
|---|---|
| nothing | use the ticket: `planned` +1, no locked proof |
| driver store + `MarkWritten` into a sampled surface | refuse (stamps); the locked proof rebuilds; pixels new |
| the other worker records a GPU write over a sampled surface | refuse (`publishGeneration`/`PendingSerial`); pixels after the sync |
| the other worker refreshes a bound storage image | refuse (ProofView) |
| `ClearCachedTextures` / storage eviction | refuse (`erasures`) |
| an import dropped | refuse (epoch) |
| a CPU store without a stamp, then `BumpCollectEpoch` | seen after the epoch (it may be missed before it, as today) |

**Reds:** for each row, remove that check and that row's test fails, on pixels or on the counts. As in BF-284, one of these reds may pass the pixel tests and need a targeted test; the R4 lesson there.

**Also:** `_planned` registrations of the dispatch-cache execution tests, and the TSAN run of the race modes with two planners and one committer.

### Stage 4: stage B's hits off the lock (the B images row, 0.32 ms)

- **Switch:** `APS5_PLANNED_LOOKUPS=1`.
- **The plan:** stage A's records (`SRh:465-506`) already carry what `fastTexture` needs. The plan evaluates the `fastTexture` predicate per record on the snapshots in `PrepareDispatch`.
- **The commit:** checks per record and falls back per record, so a miss in one element doesn't redo the others.
- **What stays locked:** misses, refreshes, creation and uploads.
- **Tests:** BF-284's `agc_deferred_draw_build` race cases (unchanged, driver store, eviction, GPU write, CPU store + epoch), run as two threads on a dispatch build, plus a two-elements-one-changed case for the per-record fallback.
- **Reds:** stamps not re-checked; `erasures` ignored; ProofView ignored; whole-build fallback instead of per record (counts).

### Stage 5: CPU upload data off the lock (the B upload row, and uploads inside B images)

One switch per kind:
- **5a:** guest-buffer snapshot copies in `UploadFinish` (`APS5_PLANNED_COPIES`);
- **5b:** sampled snapshot uploads in the `Texture` constructor (`T:440-445`);
- **5c:** the storage CPU upload path (`T:2926-2965`).

**How it works:**
- **The plan** copies guest bytes into a private `BufferPool` staging buffer when the plan says an upload is needed, and only if the source has no pending GPU write or result.
- **The commit** re-checks the stamps over the copied range, the pending snapshot and the import epoch. Then it records the copy from staging; otherwise it does the upload as today.

**What stays locked:** mirror refreshes (contents GM-only, completions write them), `FlushPending` of written ranges, and import creation. A per-mirror lock would be a later stage, once the PC's `[buffers]` line says mirrors matter.

**Tests:**
- **per kind:** store between the copy and the commit; GPU write noted; import created or dropped between (the region switches from copy to import); writable mirror present (the plan refuses). Each with pixels.
- **Reds:** one per check.

### Stage 6: not proposed now

Per-thread command recording (secondary command buffers executed into the open batch under GM). This is only worth it if, after stages 1 to 5, the recording itself is the hold. The "record:" rows of `[dispatch]` say whether it is.

**The model** (BF-293's own): the lock wait scales with the other queue's hold.

| f | hold per dispatch | lock wait per queue per 10 s | that queue's time for 10 s of work | throughput |
|---|---|---|---|---|
| today | 1.1 ms | 2.1–2.3 s | 10 s | 1.00× |

- **Interaction with BF-290 and BF-292:** they remove the "recorded store" waits, which step 1 cannot move. With BF-292's C1 switch on, nearly all remaining hook waits should be the "pending write" kind, so the two compose. A Village run with C1 on and off gives `f` directly.
