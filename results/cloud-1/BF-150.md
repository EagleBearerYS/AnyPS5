## What #8527 gives the change

- #8527 records the deferred 4-byte settle reads into one batch on the **main queue** (`submitSettleBatch`, GuestBufferMemory.cpp:1062-1113 on 60ab13644c). The batch has a barrier from all earlier commands' memory writes before the copies and one to all later commands after them. It runs only under `GpuMutex` from an import lookup (`settleUnwatchedImports`, :1170). `waitSettleBatch` now waits with `UINT64_MAX` and checks the result (:288-290).
- So a batch submitted under the GPU mutex is ordered after every main-queue submission before it. That is the ordering point the synchronous path uses: it calls the same `submitSettleBatch`, then waits on that batch's fence.

## The change (Windows)

- **`WatchedAfterSettle(context, address, bytes)`** (new, GuestBufferMemory.hpp/.cpp) is the one helper. On Windows, when the calling thread holds `GpuMutex` and the device has host imports and a settle queue, it:
  1. takes the imports lock and reconciles the imports if the registry changed (`refreshImports`, as `HostImportFor` does);
  2. finds every compared import over the range with a pending settle (`pendingSettles`, phase Wanted, Submitted or Settled), or one marked `settleOnDemand` (see "Partial blocks" below);
  3. moves the Wanted ones to the front of `settleWanted` and submits them with #8527's `submitSettleBatch`, after waiting for and reaping the batches first if all four are busy;
  4. waits for the fence of each needed batch, then `reapSettleBatches` and `rewatchSettledImports`;
  5. returns `GuestMemory::Watched(address, bytes)`.

  It returns `Watched` unchanged off Windows, without the GPU mutex, or when nothing is pending.
- **`initialDccClear`** (MultisampleTarget.cpp:418 on 60ab13644c, `:497` on main 8b3e39832a) calls `WatchedAfterSettle` instead of `GuestMemory::Watched`. The text "initial multisampled DCC contents require watched guest memory" stays. #7948's two FMASK checks can call the same helper; I did not touch them.
- **Conditions kept:**
  - every rule in `rewatchSettledImports` still applies, including a live storage image over the import (`StorageTexture::AnyLiveOverlaps`), which keeps it compared and counts it in `keptCompared`;
  - `APS5_NO_DEFERRED_SETTLES` / `SetHostImportDeferredSettles(false)` still keeps such imports compared;
  - a range that is unwatched without an import of its own (an explicit `Unwatch`) is still refused, because the helper only acts on imports with a pending or on-demand settle;
  - imports that are not Windows private writable `MEM_WRITE_WATCH` memory, aliases, and devices without a settle queue are untouched.
- **Cost:** one main-queue submission plus a CPU fence wait, only when an initial DCC import finds its range under a pending settle (target creation or re-creation, not per draw). The wait also covers all main-queue work submitted before it. No product path holds a main-queue submission on a host semaphore: `HoldNextSubmit` is only used by a test.

## Partial blocks: the finding

The deferred settle **never settles** an import that is not a whole number of 64 KiB blocks, such as Rush 2's `0x4006200000+0xc4000`. There are two reasons:

1. **It is never queued.** `importRunAt` queues a deferred read only when `base % settleBlockBytes == 0 && bytes % settleBlockBytes == 0` (GuestBufferMemory.cpp:1874 on 60ab13644c). A 0xc4000-byte import therefore stays compared for its whole life. No lookup ever returns it, which matches the held item that MGS4's 0x28000-byte DCC key imports stay compared.
2. **Even if queued, it could not return.** `GuestMemory::Rewatch` skips any range whose start or end is not on a tracker block (GuestMemory.cpp:1509). Exclusion is whole-block (`WriteWatchCoverage::Exclude`), so the import also excluded the 48 KiB of its last block that lie past it (0x40062c4000-0x40062d0000).

**The synchronous path handles it:**
- `importRunAt` now marks such an import `settleOnDemand`, under the same conditions a whole-block import gets a deferred read (deferred settles on, no alias, the probe keeps private imports watched, writable private memory). It is still not queued, so the deferred path is unchanged for it, and MGS4's imports stay as they are.
- When an initial DCC import needs its range, the import gets a settle read like any other. `rewatchSettledImports` then rewatches its range rounded out to whole 64 KiB blocks, so `Rewatch` accepts it, and every block, the shared ones included, is stamped as a CPU store.
- It keeps the import compared instead when any of these share that rounded span:
  - another compared (`unwatched`) import, whether live, trimmed or parked (by pinned range);
  - a live storage image.
  The refresh would re-exclude a block shared with a live compared import anyway (`refreshImports` re-`Unwatch`es compared imports).
- **Limit:** a retired compared import that a recorder still holds through `KeepThroughHold` is not visible there. If it shares the last block and the driver still marks its pages, those marks would read as CPU stores after the return. The only data at risk is a storage image created over those bytes before its marking ends. This is in the debt entry.
- Imports that are whole blocks take exactly the old path: the rounded span equals the import.

## Tests

- **Write-watch mode:** the test needs, and asserts, Windows private imports that stay watched after a settle read, using the probe through `settledImportsWatchPrivate`, as the other deferred-settle tests do. It prints `write watch: Windows private imports stay watched after a settle read; imports under 1 MiB wait for a deferred settle`.
  - If the device compares every import, or has no settle queue, no 4x color targets, no graphics or imports wider than 16 KiB, it skips with 77.
  - Off Windows it skips with 77 and prints `skipped, the device has no deferred settle of host imports: imports under 1 MiB wait for one only on Windows`. check_skips.py accepts that ("the device has no").
- **The cases.** Each target is a 4x R8G8B8A8 `SW_64KB_R_X` target with DCC keys 0xc0 (Clear1111). Each import is made off the GPU lock, so its settle is still pending (Wanted) when the DCC import runs. The DCC import is triggered by `MultisampleTargetView` under the GPU lock.
  1. **`a pending settle`:** 128x128, a 0x50000-byte import holding color (0x40000) and DCC keys.
     - It must be accepted, with more settle reads submitted and more imports back in the write watch than before, and the import no longer compared.
     - A Resolve into a single-sample target must read 0xffffffff everywhere (the clear).
     - After a CPU store into the import and one into the DCC keys, `UnchangedSince` must fail.
     - Re-acquiring the target must refuse with `writes to a resident multisampled DCC target or its metadata are not implemented`, so the write was tracked, not refused as unwatched.
  2. **`an import of whole and partial 64 KiB blocks`:** 128x384, a **0xc4000**-byte import (color 0xc0000 plus DCC keys at +0xc0000, Rush 2's shape).
     - First, 20 lookups under the GPU lock, 1 ms apart, must leave it compared. That is the finding above.
     - Then everything in case 1 must hold.
  3. **`a compared import in its last 64 KiB block`:** case 2, plus a compared 0x8000-byte import at +0xc8000. The DCC import must be refused (`initial multisampled DCC contents require watched guest memory`), and the import must stay compared.
  4. **`deferred settles off`:** case 1 with `SetHostImportDeferredSettles(false)`. It must be refused, and the import must stay compared.
  5. **`explicitly unwatched DCC keys`:** case 1, but the keys are in a separate, non-imported block explicitly `Unwatch`ed. It must be refused even though the color import settles.
- The test uses only existing APIs (`MultisampleTargetView`, `HostImportFor`, `HostImportSettles`, `RunColorMetadataPass`, ...), so it builds with the product hunks reverted.
- AlphaToCoverage.cpp's explicitly unwatched negative case (mode 4, `Unwatch(metadata, 4096)`) is unchanged and still refuses. It ran in the `alpha_to_coverage` set below.
