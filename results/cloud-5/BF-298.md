## What is the same as shadPS4

- **SetDecodeInput:**
  - writes `status` {1, 1} after the decoder and input checks and before the `auData`/`auSize` check;
  - maps a pts/dts of −1 to `AV_NOPTS_VALUE`;
  - copies the access unit into an `AVPacket` with the user data as `opaque`;
  - returns `FATAL` if packet allocation fails;
  - records the last pts/dts/user data and marks the decoder busy.
- **Worker:**
  - **Packet:** send, with the EOF→flush and EAGAIN→drain retries, then drain.
  - **Flush:** send null, drain, flush the context buffers, signal.
  - **Reset:** flush the context, free the decoded frames, reset the slot index, signal.
- **Sync:** waits for a frame or for an idle worker with an empty queue, then reports the queue size.
- **TrySync:** frames give OK and the count; busy or queued work gives `DECODE_RUNNING` and 0; otherwise OK and 0.
- **Flush:** queues the flush, waits for it, and reports the frames held after the worker's flush.
- **GetDecodeOutput:**
  - **Empty queue:** `NO_PICTURE` with shadPS4's fields: the maximum width, that width rounded to 64, the maximum height, count 0, null buffers and pictures[0/1] frame buffers, format 0. Every other field is left alone.
  - **A picture:**
    - It is converted to NV12 if needed and copied with `CopyNV12Data`'s layout: pitch is the width rounded to 64, height rounded to 16, and the last row is repeated into the alignment rows.
    - **Destination order:** the caller's frame buffer, then the next mapped slot (round robin), then the fallback buffer.
    - **HW picture info:** written at the end of the allocated frame buffer (the caller's `frameBufferSize`, else the decoder's), with:
      - codec type, user data, pts and dts (the last input's when the frame has none), valid 1;
      - the aligned width and height;
      - crop right/bottom as half the padding;
      - SAR 1:1 unless the frame has one;
      - flags 0x1, plus 0x2 when cropped.
    - **Output info:** every field shadPS4 fills, including pictures[0].flags = the codec type, aspect ratio 1, video format 5, colour primaries and transfer 1, and the full-range flag from the frame.
    - The sample aspect ratio and colour range are not carried through the NV12 conversion, as in shadPS4. So an FFmpeg yuv420p frame reports 1:1 and limited range.

## Differences from shadPS4

These are recorded in the debt entry, briefly, and here in full:

1. **Unknown handles:** a handle CreateDecoder didn't return throws, through #12838's `Find`. shadPS4 dereferences it.
2. **Oversized pictures:** if a decoded picture is larger than the caller's frame buffer or a mapped slot, it throws (`Export.cpp:391`) instead of overflowing. shadPS4's `CopyNV12Data` asserts only against the picture's own size.
3. **NV12 copy:** it always goes row by row. shadPS4 copies whole planes when the width is a multiple of 64, which assumes FFmpeg's line size equals the width. The bytes are the same whenever that assumption holds.
4. **Locking:**
   - **Delete:** the stop is requested under the decoder's lock, so the worker can't miss it between checking its condition and waiting. shadPS4 requests it without the lock.
   - **Slot selection:** the next slot is taken, and the last pts/dts read, under the decoder's lock.
   - **MapMemoryBlock:** it now also takes the decoder's lock, as shadPS4's does. #12838 took only the registry lock.
   - **The test hook `VdecCoreFrameBufferSlots`:** it reads the slots under the decoder's lock.
5. **Guard:** `CopyNv12` skips the row extension for a picture 0 or 1 rows high, where shadPS4's `height / 2 - 1` would underflow.

The six rows that are stubs in shadPS4 (`AnalyzeStream`, `Initialize`/`FinalizeComputeResource`, `Set`/`Sync`/`TrySyncDecodeOutputSw`) stay in "Unknown function info" as `NotImplemented`.

### How the NV12 contents are checked

The tree's references (`H264Fixture::PictureHashes`, checked by GuestVideodec2, GuestVdecsw and GuestVideodec) hash the uncropped 64x48 coded picture. shadPS4's path doesn't produce that:
- FFmpeg crops the frame to 64x40;
- `CopyNV12Data` then fills rows 40-47 (chroma 20-23) with copies of row 39 (chroma 19).

So `hashNv12(…, 48)` can't match by design. Instead, the test checks two things.

1. **The visible picture** (40 luma rows, then 20 chroma rows from the chroma plane at pitch × 48), with `hashNv12`'s FNV-1a, against `VisiblePictureHashes`.
   - **Where they come from:** libSceVideodec2's decode of the same fixture. Its own test checks that decode against `PictureHashes`.
   - **How:** I ran Videodec2's `testDecode` once with a print of the same visible-region hash (a local change that wasn't committed; the file was restored, and `git status` showed it clean).
   - **The values:** identical for the Annex B and length-prefixed runs:

     ```
     0x5871fdc85dfa274e 0x26ce4afb974cffc4 0xd2e739633733d5ba
     0x54feb3d290e028fd 0xfa1342a4ba1819c8 0x870125dd7f079a4c
     ```

   They come from an independent decoder, not from this code's conversion.
2. **The alignment rows:** every luma row 40-47 equals row 39, and every chroma row 20-23 equals row 19. That's `CopyNV12Data`'s rule.
