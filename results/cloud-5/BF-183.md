## The reading

### How `main` and #8429 serve CMASK-compressed 8s/8f FMASK

- **Decode.** `DecodeTextureResource` keeps an FMASK descriptor's CMASK address as `fmaskCmaskAddress` when dword 6 bit 21 (`COMPRESSION_EN`) is set. The metadata address comes from dword 6 bits 24-31 and dword 7.
  - Mesa builds GFX10 FMASK descriptors the same way: [`ac_descriptors.c` @761d5c8a L377-L383](https://gitlab.freedesktop.org/mesa/mesa/-/blob/761d5c8a/src/amd/common/ac_descriptors.c#L377). With `tc_compat_cmask` it sets `COMPRESSION_EN` and points `META_DATA_ADDRESS` at the CMASK.
- **Lookup.** The sampled lookup sends such a resource to `MultisampleTargetFmaskTexture_nid_no_patch`. That function finds the resident `MultisampleTarget` whose FMASK base matches and calls its `FmaskSampled`.
- **What `FmaskSampled` serves.** It never reads the guest's FMASK or CMASK bytes.
  - It requires an 8-sample DCC target whose FMASK was tracked at import. In `initialDccClear` that FMASK is watched, given a generation, kept disjoint from the color and metadata planes, guarded, and checked unchanged on every use.
  - It then answers with a snapshot texture that holds `0x76543210` in every texel.
- **So the multisample target supplies an identity FMASK.** The host image keeps every sample, so sample *s* → fragment *s* is the right map for the host's data, whatever the guest's CMASK tiles say.
- **The value is PAL's packed fully expanded FMASK for 8s/8f.** The source is `Gfx9Fmask::GetPackedExpandedValue`, [`gfx9MaskRam.cpp` @c5e80007 L5005-L5025](https://github.com/GPUOpen-Drivers/pal/blob/c5e800072a32f68b6ccc4422936d96167c6e0728/src/core/hw/gfxip/gfx9/gfx9MaskRam.cpp#L5005). #8429's debt line and tests cite the same table.
- **What #8429 adds.**
  - It reads the 8-bit, 16-bit and 32-bit uncompressed layouts from guest memory (`FmaskLayoutOf`, `FmaskExpansion`).
  - It refuses `COMPRESSION_EN` for every format but `Fmask32_S8_F8`, in both `ResourceMaterializer.cpp` and `GuestTextureResource.cpp`. The refusal reads "FMASK CMASK compression is implemented only for 8-sample, 8-fragment FMASK".
- **The color targets these titles can draw on this base.** `DecodeColorBuffer` refuses EQAA color targets with "color targets with fewer fragments than samples (EQAA) are unsupported" (`State.cpp:1748` at 4feda344e6). So on #8429, and on #9941 + #8429, every tracked target has as many fragments as samples.
- **What that implies for the titles' layout.** Rush 2 and Wave Race 64 draw their target before the FMASK read refuses. Their FMASK is therefore almost certainly `Fmask8_S2_F2` or `Fmask8_S4_F4`, since `Fmask32_S8_F8` was already served. This is inferred: their logs don't name the format.

#### Fragments equal samples (S2F2, S4F4)

As for 8s/8f, the right answer for a tracked native target is the identity map, sample *s* → fragment *s*:
- The host image stores every sample, so the guest's next color fetch by fragment index reads exactly that sample.
- A CMASK-compressed (fast-cleared) tile on the console holds one color in every fragment. The host image holds that color in every sample too, so identity reads it correctly as well.
- Identity is PAL's packed expanded value (`0x02`, `0xE4`). #8429's expansion turns it into `0x10` and `0x3210`.

#### One fragment (S2F1, S4F1, S8F1)

A compressed tile maps every sample to fragment 0, so the FMASK reads as packed 0. Expanded, that is `0x0…0` for the counted samples. The answer is known, but no tracked target can stand behind it:
- **On this base,** `DecodeColorBuffer` refuses one-fragment color targets, so no such target is ever tracked.
- **With fma-rc's #9450** (head 9a8fe7a396), the target is drawn on the host as one sample (`color.samples = 1`, `coverageSamples = N`). It is not a `MultisampleTarget`, so `MultisampleTargetFmaskTexture` finds no owner. #9450 also guards its FMASK plane as host memory ("guest access to it is not implemented").
- **Serving it would need** the FMASK zeros plus a multisampled color read that a single-sample host image answers. That is a separate change on top of #9450.

So these layouts keep a refusal, which now names the format.

#### EQAA (S4F2, S8F2, S8F4)

No target-backed read can answer these exactly:
- **On this base,** EQAA targets are refused when decoded.
- **With frankea's #9700** (head d9024161f0), the host keeps one color per *coverage* sample. The host data then needs sample *s* → host sample *s*, but an EQAA FMASK index can only address the first *F* fragments. An index of *F* or more means "unknown", which is PAL's expanded value for samples past *F*.
  - So no FMASK value addresses the host colors of samples at or past *F*.
  - A read that answered identity below *F* and "unknown" for the rest would make a resolve or a sample read drop those samples, where the console reads valid fragments.
- **Compression doesn't help.** The host never writes the guest CMASK, so it doesn't know which guest tiles are compressed. It can't use the console's "one fragment" answer for those tiles either.
- **#9700 also has no DCC on EQAA targets,** and it refuses texture access to the target and its FMASK plane. Tracked FMASK serving here requires a DCC target.

So EQAA keeps the refusal, which now names the format.

## What changed

All of this is in `MultisampleTarget.cpp` unless a file is named.

- **`nativeFmaskFormat(samples)`** maps 2 → `Fmask8_S2_F2`, 4 → `Fmask8_S4_F4` and 8 → `Fmask32_S8_F8`. `fmaskStorageFormat(layout)` gives the 8-, 16- or 32-bit `UINT` storage.
- **`tracksFmask(target)`** is true when the sample count has a layout and the target has both an FMASK and a CMASK. It replaces the `samples == 8u && …` tests in `initialDccClear` and `guard()`.
- **`fmaskResource(target)`** describes the target's own FMASK plane with its layout's storage format and `fmaskFormat`.
- **`fmaskSnapshotResource`** requires `resource.format` to be the layout's storage format.
  - It accepts identity selectors (X, Y, Z, W) for layouts other than S8F8, because #8429's expansion binding rewrites the selectors to identity.
  - The snapshot keeps the layout's own texel size instead of being forced to 32 bits.
- **`FmaskSampled`** requires as many fragments as samples, the target's sample count, DCC, and the tracked FMASK range. It fills every texel with the packed identity, `sample << (sample * bitsPerSample)` OR-ed over the samples.
- **`ResourceMaterializer.cpp` and `GuestTextureResource.cpp`** let `COMPRESSION_EN` through when fragments equal samples, and otherwise throw the named refusal. `FmaskLayoutName` builds the name from `FmaskLayoutOf`, so it is right for every layout, with no per-value text.

### Behaviour change to note

A 2- or 4-sample DCC color target with both an FMASK and a CMASK now has its FMASK plane tracked at import, as an 8-sample one already had: it is watched, given a generation, kept disjoint from the other planes, guarded, and checked unchanged.

The existing MSAA DCC clear tests program no FMASK (`cx[0x321] = 0`, `AlphaToCoverage.cpp:203`), so `agc_driver_msaa_dcc_clear_4` doesn't exercise this. `agc_driver_native_fmask_4` does.
