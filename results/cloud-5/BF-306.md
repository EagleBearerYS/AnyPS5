# BF-306 result (cloud-5)

## Summary

- **The change** is one line in the GPU-eligible indirect draw's memory-state decision (`Graphics/src/Draw.cpp:3104`): `PendingLabelIn` becomes `CompletionLabelIn`.
  - **Before:** any pending label over the records sent the draw to a CPU read, which waited in the flush hook for the label's batch under the GPU mutex.
  - **After:** a label the GPU stores no longer does. The draw takes the GPU indirect path, ordered after the store by the queued-store flush and the argument barrier that path already records.
  - **Still on the CPU:** labels that land only by a CPU store at their batch's reap, and labels another queue queued but hasn't recorded.
- **What it doesn't cover:** Village's 28 indirect-args pending-write syncs most likely aren't this case (§1.4).
  - **Where they come from:** the `[syncwait]` unlocked count (25-29) matches them. So they come from the driver's CPU-split path (`Driver/Draw/Draw.cpp:536`, `:1121`), which reads the records outside the GPU mutex.
  - **Why they stay:** BF-052 found every queue-0 draw there is CPU-split ("patched SGPR not folded" or "non-vertex path"). That path needs the record values to patch user SGPRs per record, so its wait stays (§1.3).
  - **What would remove them:** sourcing those SGPRs on the GPU, which is a recompiler change (#10359 starts it for the start instance).

### 1.1 When an indirect draw takes the CPU path, and when the GPU path

There are two decisions, in order.

**A. Shape (the driver, per draw):** `Execution/src/Driver/Draw/Draw.cpp:949-951` calls `ClassifyIndirectDraw` (`Execution/src/Driver/Draw/IndirectDraw.cpp:25-72`). A reason sends the draw to the driver's **CPU split**:

| Reason | Where |
| --- | --- |
| `IndexLimitUnknown` (no `INDEX_BUFFER_SIZE`) | `:32` |
| `IndexRange` (the index range isn't fully readable) | `:33` |
| `NonVertexPath` (mesh with offset locations, tessellation, rect list off the GPU) | `:35-39` |
| `DrawIndex` (multi-draw draw-index SGPR) | `:40` |
| `FeatureGap` (count or multi-draw without device support, a non-zero first instance without `drawIndirectFirstInstance`, constant rules over 256 records) | `:41-42`, `:56-57` |
| `FetchUnknown` / `NotFolded` / `IndxOffset` (the base-vertex or start-instance SGPR isn't the one the recompiler folds, is shared, or meets a non-zero `GE_INDX_OFFSET`) | `:43-55` |
| `VertexRange` (a V# extent over `APS5_INDIRECT_VERTEX_MIB`, 64 MiB) | `:59-64` |

Without a reason, each dimension gets `Rule::InPlace` (the record's value) or `Rule::Constant` (folded user word).

**The GPU path** (recorded draw `:2386`, synchronous draw `:3377`):
1. `:2413-2417` / `:3399-3400` flush queued label stores that touch the records.
2. `recordIndirectArguments` (`:2017-2047`) records the barrier `ALL_COMMANDS|HOST → DRAW_INDIRECT|TRANSFER`, `SHADER_WRITE|TRANSFER_WRITE|HOST_WRITE → INDIRECT_COMMAND_READ|TRANSFER_READ` (`:2020`). For constant rules it also copies into a scratch buffer and patches the constants (`:2029-2045`).
3. `recordDrawCommands` (`:1976-1991`) issues `vkCmdDraw*Indirect[Count]` from the import.
4. The mesh path's argument kernel (`:2073-2083`) has its own leading barrier (`Graphics/src/Recorder.cpp:2578`).

A synchronous draw's `CommandBatch` submits the recorder's open batch first (`Graphics/src/Resources.cpp:363`).

**The CPU reads** go through the flush hook (`ReadSite::IndirectArguments`, `Execution/src/Pm4.cpp:886`, `:895`):
- **Graphics:** `:3127-3131`, under the GPU mutex, so the hook's wait is locked.
- **The driver's CPU split:** `Driver/Draw/Draw.cpp:1119-1124`.
- **The driver's empty-draw pre-read** for programs last classified CPU (`EmptyIndirectSkip`, `CpuIndirectPrograms`): `:527-545`.

Both driver reads run before `lockForDraw` (`:1088-1105`), outside the GPU mutex, so their waits are the `[syncwait]` "unlocked hook waits".

- `Pm4.cpp:1001` is `INDEX_ATTRIBUTES_INDIRECT`'s record.

### 1.2 Which CPU-path decisions need the values

**The driver's CPU split** needs the values in every case. Per record it does all of these:
- patches the base-vertex, start-instance and draw-index user words (`Driver/Draw/Draw.cpp:1137-1146`);
- re-materialises the patched stages (`:1172-1179`);
- clamps or bounds the index range (`:1153-1164`);
- builds the mesh index-buffer descriptor (`:1168-1170`);
- rebuilds rect lists (`:1181`);
- skips empty records (`:1136`).

**The Graphics-level CPU path** uses the values only to:
- emit direct draws with the per-dimension rules (`:1993-2006`);
- skip an all-empty draw (`:3134-3138`);
- compact list-restart indices (`CompactIndirectListRestart`, `:1910`, the `FeatureGap` case);
- read the mesh path's first record (`:2085`).

**Decisions that don't need the values:**
- **Vertex range:** the resource build already bounds it without the values ("the descriptor's whole range is copied", `:1730-1731`; the index buffer is bound as declared).
- **The zero-count skip:** on the GPU a zero count or zero instances draws nothing, so the GPU path needs no skip.
- **The draw cache key:** it never holds record values; CPU-path indirect draws aren't cached (`Driver/Draw/DrawCapture.cpp:213`).

### 1.3 Which could go without the values, or be bounded conservatively

**On the GPU-eligible (B) side, by memory-state case:**

| Case | Verdict |
| --- | --- |
| Pending label stored on the GPU | **Needs no values.** The label is a `RecordStore` into the import in the open batch (`Execution/src/VulkanDevice.cpp:2576`, `:2621`, `:2628-2630`). The GPU path flushes queued stores over the records before its pass and orders the indirect read after them. **This is the change** |
| Pending label stored only by a completion | **Needs the CPU read.** `AfterCompletions(…, storedOnGpu=false)`, `VulkanDevice.cpp:2600-2602`, `Recorder.cpp:3520-3558`: the bytes reach guest memory only by a CPU store when the batch is reaped, after the GPU would have read them. Kept, and the test's case 3 proves it |
| Queued label of another queue | **Kept on the CPU.** It isn't recorded yet, so there's no GPU write to order behind. Main also sends it to the CPU, so this is no change |
| Copied writer | **Kept.** The write-back is a CPU store at the reap (`GuestBufferMemory.cpp:6181-6194`). The device-side source would be the copied region's own buffer, a larger change |
| Pending storage image | **Kept.** It is the recorded-store family (BF-292/303, the storage-alias fix), not a pending-write sync |
| `NotImported` | **Kept.** No device source |

**On the CPU-split (A) side:**

| Reason | Verdict |
| --- | --- |
| `NotFolded`, `FetchUnknown`, `IndxOffset`, `DrawIndex`, `NonVertexPath` | **Need the values.** The program reads the patched SGPR beyond the fetch add. A GPU source for it (`BaseVertex`/`BaseInstance`/`DrawIndex` builtins) is a recompiler change; #10359 starts it for the start instance |
| `IndexLimitUnknown` | **No conservative bound without the values.** The allocation's extent would be one, but it isn't the CP's limit (#7679 handles it per record) |
| `IndexRange` | **No conservative bound without the values** either |
| `VertexRange` | **Already conservative on the GPU path** (the whole extent). The 64 MiB cap is a cost policy, not a value dependence |
| `FeatureGap` | **A device limit** |

### 1.4 Village

**Village's syncs are on the driver's CPU split:**
- **The counts:** BF-295's profile has 28 pending-write syncs at `0x0 DRAW_INDEX_INDIRECT indirect-args` (760 ms) and 25-29 `[syncwait]` *unlocked* indirect-args waits (188-273 ms). Their counts match.
- **The locked/unlocked split:** the Graphics read (B) is locked, so its waits never appear in `[syncwait]`. The driver's reads (§1.1) are unlocked.
- **The 760 / 188-273 ms gap** fits the hook's relock after an unlocked wait, which `[hooksync]` times and `[syncwait]` doesn't.
- **The draws:** BF-052 found every queue-0 draw at the menu is CPU-split, "patched SGPR not folded" or "non-vertex path".

So these waits are on the CPU split, where the values are needed (§1.3); this change doesn't remove them.

**What would settle it on the PC:**
- **The `[draws]` line's `indirect:` field:** per-reason CPU-side counts.
- **The `[hooksync]` frames** for that row, against `nm -C`.

If the reasons are `not folded` / `non-vertex path`, the next step for this site is the recompiler-side SGPR source (#10359's approach widened to the base vertex), not this decision.

**What this change removes:** the locked wait of every GPU-eligible indirect draw whose records a label recorded on the GPU covers. For example, a `WRITE_DATA`, `COPY_DATA` or `DMA_DATA` payload into the records, recorded as a GPU store.

### 1.5 Bit-exactness

On the GPU path the draw reads the same record bytes the CPU path would have read after the wait, with the same per-dimension rules (the scratch rewrite for constants), so it draws the same draws and counts.

**One existing difference between the paths, unchanged here:** a record whose first index reaches past `INDEX_BUFFER_SIZE`.
- The CPU path clamps or skips it (`:1997-2002`).
- The GPU path relies on the bound index copy and robust buffer access, as it does on main for every GPU-path draw.
