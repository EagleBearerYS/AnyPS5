## Findings, ranked

### Blocking

None. I found no store pattern that the recompiler emits and the scan misses, and no case where continuing the pass drops an ordering that main keeps.

### Should fix

**S1. The store scan is a deny-list, and three write forms escape it.** Fixed in **4ff3b0545**. The scan is `ShaderAddressResources.cpp` `SpirvStoresThroughAddresses`, with `pointerOperandStored` at b3e94a514 lines 15–45. It knows `OpStore`, `OpCopyMemory(Sized)`, `OpAtomicStore`, `OpAtomicFlagClear` and the read-modify-write atomics, and it takes only `OpTypePointer` as a physical pointer type. These forms escape it:
- a store through an **untyped** PhysicalStorageBuffer pointer (`OpTypeUntypedPointerKHR`, SPV_KHR_untyped_pointers);
- an **`OpExtInst`** that writes through a pointer operand: GLSL.std.450 `Modf` and `Frexp` take an output pointer;
- **cooperative matrix stores** (`OpCooperativeMatrixStoreKHR`, `…StoreNV`, `…StoreTensorNV`).

A module using any of them would be taken as read-only, and its draws would continue a pass they must end.

**Today's recompiler emits none of them**, so this isn't a live bug:
- the backend's write opcodes are `OpStore`, `OpCopyMemory(Sized)`, `OpAtomicStore` and the read-modify-write atomics (counted by grep over `core/shader/recompiler/SpirvBackend`), all on the scan's list;
- its only GLSL.std.450 frexp is `FrexpStruct`, which returns a struct.

**Evidence:** each of the three cases fails on the old scan:
- "store scan: a store through an untyped physical pointer was missed";
- "store scan: an extended instruction writing through a physical pointer was missed";
- "store scan: a cooperative matrix store was missed".

All three pass with 4ff3b0545, which also stops the three pointer type declarations from adding their storage class (5349) to the set of pointer values. That was harmless, but could have produced a false "stores" verdict.

**S2. The test didn't cover ordering against buffer-descriptor writes.** Added in **f06328265**.
- **Why it matters:** a read-only BDA draw now relies on a single rule of the pass hazard tracker for ordering against guest memory written through a buffer descriptor: `PassHazards::Check`, b3e94a514 `PassHazards.cpp:42`, "unknown read after range write, or range write after unknown read".
- **What `agc_driver_address_passes` checked at b3e94a514:**
  - BDA reader then BDA reader;
  - BDA reader then BDA storer;
  - BDA storer then BDA reader.
- **Added cases:**
  - `--read-sees-descriptor-store`: a draw stores 1.0 through a V# from user data (`buffer_store_dword … s[4:7]`, not address-based), and the next draw reads it through the table. The reader begins its own pass and sees the store: stored 1, brightest color byte 255.
  - `--descriptor-store-after-read`: the reverse order; the storing draw begins its own pass.
- **Red:** with that tracker rule removed in a scratch build, both fail:
  - "a draw reading through the table continued the pass of a draw that stored through a buffer descriptor: 1 address-based draws, 0 began a pass, 1 continued one";
  - "a draw storing through a buffer descriptor continued the pass of a draw that read through the table: 1 other draws, 0 began a pass, 1 continued one".
- On lavapipe the read still returned 1.0 without the barrier; lavapipe serializes, so only the pass counts catch it there.

### Notes (no change made)

**N1. Feedback through the table: same bytes with or without the break.**
- Attachments and storage images are `VK_IMAGE_TILING_OPTIMAL` images with their own device memory (`Texture.cpp:1127–1145`). They never alias the guest memory that the BDA table maps.
- A BDA read of a render target's or storage image's guest range therefore sees guest memory as of the last write-back. Write-back is recorded outside render passes.
- The result is the same whether the pass breaks or not, so this is not changed by C-1. On hardware such a read would need a guest cache flush first, and that already ends the pass.

**N2. What main breaks the pass for, and C-1 keeps.** C-1 changes only `PassAccess::anyWrites`, for a build whose table programs all scan as read-only (`Draw.cpp:1793–1797`). Everything else is unchanged:
- **Forced:** a draw that samples its own attachment (`readsTarget`, `ShaderResources::ReadsImage`), capture, GPU-side indirect, mesh indirect (`Draw.cpp:1799`).
- **Image hazards:** by `VkImage` identity for storage images (with their written flag) and attachments (`PassHazards.cpp:47–56`).
- **Range hazards:** writes through descriptors (`GuestBufferMemory::AddWritable` → `Writes()`).
- **Unknown writes still set:** copied writes (`HasCopiedWrites`) and a lease without a table.
- **Pending stores:** queued DCC key stores and label stores are flushed before any lease draw (`Draw.cpp:1768–1776`). The flush ends the open pass.
- **Layout transitions and uploads:** recorded through `Recorder::Commands()` in `PrepareDrawBindings`, which ends the open pass. The next pass begins with the barrier from `SHADER_WRITE | TRANSFER_WRITE` to reads (`Draw.cpp`, `start.barrier`).
- **Image tables:** a storage, written or atomic image can't come from one. `ResourceTracker::AssignTables` marks it `TableOperation::Unsupported` and the materializer poisons it, so a draw can't write an image the pass doesn't list.

**N3. Interactions.**
- **Resources that change between draws:** each draw binds its own descriptor sets, and the table and uploads are recorded before the pass decision.
- **Indirect draws:** GPU-side and mesh-indirect draws are forced, as on main.
- **Address-space reuse:** that path is #6947's (`ShaderResources::SpaceReuse`); it isn't in main 661a1118cc.
- **`APS5_NO_ADDRESS_READ_PASSES=1`** restores the old flags. With it, `--readers` fails as expected: "2 address-based draws, 2 began a pass, 0 continued one".
- **`APS5_FULL_BARRIERS` / `APS5_NO_BARRIER_ELISION`** affect elision, not continuation, the same as for other draws.
- **`APS5_BARRIER_VALIDATE`:** the validator's `NoteAccess` still passes `conservative = HoldsLease()` for a lease draw that begins a pass (`Draw.cpp:1820`), and it isn't called for continued draws, which is true of every continued draw. So with C-1 the validator's "would emit" count overstates read-only BDA draws. Validator only.

**N4. Relation to #6947 (ddb3938e01).** It makes the same `recordDraw` change, but:
- keys it to #6946's recompiler field `bdaReadOnly`;
- gates it on `!ShaderResources::SpaceReuseDisabled()`, which is `!GpuHeapEnabled()` there, so it is on only under `APS5_GPU_HEAP`.

C-1 is on by default with an opt-out, and decides read-only by scanning the SPIR-V (no cache format change). The two textually conflict on the same lines in `Draw.cpp`. When #6946 lands, the recompiler's field is the better source: it is computed from IR stores rather than a deny-list of SPIR-V opcodes.

**N5. The counters (2d4512e5c8).**
- **Cost when unprofiled:** three bool stores per recorded draw. `reportDraw` runs only when `timer.profile` is set (`Draw.cpp:902`).
- **What they count:** draws are split by `HoldsLease()`, which is the same test recordDraw uses for `addressBased`. Begun, continued and flushed are counted for recorded draws only, and the totals are cumulative.

**N6. The test (b3e94a5148).** It fails without a939efe1a0, as BF-050 showed: `--readers` red at 0300bb0e79 and with the opt-out. It covered BDA-to-BDA ordering only; S2 adds the descriptor cases. It does not cover feedback, since by N1 that is the same with or without C-1.

**N7. Scan robustness.**
- Conservative on truncated or unreadable modules.
- One scan per module content hash: a 128-bit key and an unbounded `std::map` of bools, which is negligible.
- Correct for pointers loaded from guest memory, selected or phi'd pointers, called functions' pointer parameters, and copies out of guest memory into Function variables. The tests in 4ff3b0545 cover each of these, and they pass on both versions.
- Every graphics pipeline module is created from `program->spirv` (`Pipeline.cpp:339`), the same words the scan reads.

## Addendum: the Bug Finder's note (added to the task after I claimed it)

I first published this result without the note's two requests: review on current main, and break the write-back claim. Both are done below. The review branch gained one commit, **4796eac2d**.

**On current main.** I merged the review head f06328265 into upstream main **984e5d720** locally (merge dde304bc9, not pushed). That main contains f05fc7d953 and #6892 (88ee391839).
- The merge was clean: Draw.cpp auto-merged.
- #6892 makes a linear color target over an existing host import resident. `keepRecordedDraw` then calls `StorageTexture::FlushPending` on it right after the draw, which records the image's store-back into guest memory at once. Recording that copy ends the open pass, so the next draw can't continue it.
- The resident image is still an optimal-tiled image with its own memory, so N1 holds on main too: no image aliases the guest memory the table maps.

**The write-back claim, red/green: 4796eac2d** `test(agc): check that a read through the BDA table sees a target as with its pass broken`. The `agc_driver_address_passes --targets` mode works like this:
- **Draw A** (not address-based) renders a constant color into the target. Its RGBA8 bytes spell 1.0f (0, 0, 128/255, 63/255).
- **Read-only BDA draw B** then reads the target's first dword through the table into the same target.
- **Variants:** a tiled target and a linear one.
- **Registered twice:** inside `agc_driver_address_passes`, and as the new `agc_driver_address_passes_targets_split`, which runs the same cases with `APS5_NO_ADDRESS_READ_PASSES=1`. Both must read the same bytes.

Results (B's red byte: 0 = the bytes before A; 255 = A's color):

| tree | target | default (C-1) | `APS5_NO_ADDRESS_READ_PASSES=1` |
|---|---|---|---|
| 4796eac2d (main 661a1118cc) | tiled | 0; B **continued** A's pass | 0; B began a pass |
| 4796eac2d | linear (no #6892: drawn synchronously, not recorded) | 255 | 255 |
| merge with main 984e5d720 + the test (a10af0845) | tiled | 0; B **continued** A's pass | 0; B began a pass |
| same | linear over a host import (#6892: resident, recorded) | 255; B began a pass (the store-back ended A's) | 255; B began a pass |

**The bytes are the same with and without the break in every case, so C-1's claim holds on current main.**
- A tiled target reaches guest memory only through explicit write-backs, and none is recorded between two draws in a pass. That is why the continued read sees the bytes from before A, just as the broken one does.
- A linear target over an import is stored back right after its draw, which ends the pass in both modes.

**Red:** a scratch build (never committed) writes pending targets back whenever an address-based draw begins a pass. That is exactly the "a pass end records a write-back the read depends on" failure. Then:
- the default run still reads 0, because the pass continued and no write-back happened;
- the split run reads 255 and fails: "tiled target with APS5_NO_ADDRESS_READ_PASSES=1: a draw reading through the table the target the previous draw rendered read that draw's color …".

The pair catches a divergence in either direction.

**The scan against the note's oracle.** The note says the scan agreed with the recompiler's own `bdaWrites` on all 2,308 address-based programs of Resident Evil Village's shader cache. That matches my finding that no emitted pattern escapes. The recompiler's field (#6946) remains the better long-term source (N4).
