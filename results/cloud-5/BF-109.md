## Approach: (a), try first and fall back, gated by the existing proof

In `WindowsMappings::Collect`, the branch for private memory that is no view now works like this:

- **When the direct path is used:** `collectableRanges` (the memo `collectable()` writes) covers the whole `[address, end)`. That is always true after a clearing collect's own `collectable()` call; a non-clearing collect gets it only if an earlier collect left the memo covering.
- **The direct call:** `GetWriteWatch` runs from the cursor up to the next view or clean range, or the end, with no `VirtualQuery`. Success advances to that bound. The buffer cap and early return are as before.
- **Fallback:** if the direct call fails, as it does over more than one allocation, the collect drops the direct path for the rest of that collect. It continues exactly as today: `VirtualQuery`, the `MEM_COMMIT`/`MEM_PRIVATE` check (else `return false`), then `GetWriteWatch` bounded by the region.
- **Cost per collect:** at most one failed call, so a range over many small allocations costs today's queries plus one failed `GetWriteWatch`, not one per allocation.
- **The counter:** `WindowsMappings::RegionQueries()` counts `query()` calls, so a test can show the query is gone. It is one relaxed atomic increment.

**Why (a), correctness first:**
- **No new cache to invalidate.** The direct path trusts only the proof `Collect` already trusts for its early `return false`.
- **What clears that proof today:**
  - `Commit`, which also covers protection changes of committed memory;
  - `Map`;
  - `SetProtection`;
  - `reset()`, which `Reset` (release or decommit to a placeholder) and `Map` call.
- GuestArena.cpp changes commit state only through these: `WindowsMappings::Commit` at :456, `Reset` at :465, and `Map` at :470, :480 and :498 on main. `MapAlias`/`UnmapAlias` only add or remove alias views; an unmapped alias makes the direct call fail, and the query path then returns `false`, as today.
- **So a proven range is committed private** (or a view, which the walk handles separately), and its commit-state checks keep their meaning.
  - A range that is not committed private is never proven. Its collect takes the query path and returns `false` as before (the new case checks this).
  - Outside the arena, memory freed behind WindowsMappings' back makes the direct call fail, and the fallback's query returns `false`.
  - The one remaining gap: a page decommitted in place inside a still-proven write-watch allocation, by code that bypasses WindowsMappings. Nothing in the tree does that.
- **(b) rejected:** a separate extent cache would need its own invalidation on every commit, decommit, protect and placeholder split. That is more state to get wrong, for the same gain where it matters.
- **What (a) doesn't remove:** `collectable()`'s own walk, which queries each region on a memo miss. The memo is cleared by every `Commit`, `Map`, `Reset` and `SetProtection`.
  - In BF-106's bench the memo hits, since there is one query per span, the collect's.
  - How often it misses in Village is unknown. If it is often, (b)-style extents for `collectable()` would be the follow-up.

**Windows behaviour to confirm on the PC's run:**
1. `GetWriteWatch` over a range crossing two allocations fails without resetting anything. Under Wine 9.0 it fails with `ERROR_INVALID_PARAMETER` (87), and a call inside one allocation succeeds.
2. `GetWriteWatch` with a full output buffer resets only what it returns. The code already assumed this for a region-bounded call; the direct call makes the range longer.
