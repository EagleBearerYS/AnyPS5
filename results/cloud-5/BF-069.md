- **Thread:** one `std::jthread`, only when a switch is set (Windows only).
  - It starts beside the worker sampler, when queue worker 0 starts (`Driver::run`, `QueueWorker.cpp`: `StartWorkerSampler(); StartHeapWatch();`).
  - It is stopped and joined beside it at shutdown (`Lifecycle.cpp`: `StopWorkerSampler(); StopHeapWatch();`).
  - It sleeps on a `condition_variable_any` with the stop token, so shutdown never waits out a period. It is not on a hot path.
  - On Linux both functions are empty, so the switches do nothing.
- **`APS5_HEAP_REPORT=<seconds>`** prints one line per period, after `HeapLock`, a full `HeapWalk` of `GetProcessHeap()`, then `HeapUnlock`. For example:
  `[heap] busy 4.00 GiB in 9,812,334 blocks (zero pages ~0.25 GiB), free 1.50 GiB in 14,022 blocks (zero pages ~0.75 GiB), uncommitted 0.50 GiB, 402 regions; private 26.0 GiB; walk 210 ms; zero-page samples 1 in 1,024 busy pages (1,024), 1 in 768 free pages (512)`
  - **Zero pages are sampled with a fixed stride per kind** over the whole 4 KiB pages inside each block.
    - The stride is set so that about **2,048 pages of each kind** are read per walk.
    - It comes from the previous walk's page count for that kind. The first walk uses `PrivateUsage / 4 KiB`.
    - Each sampled page is read with `ReadProcessMemory` on the own process, so an unreadable page is skipped, not faulted on.
    - The estimate is `zero samples / samples × pages`. The line gives the stride and the sample counts.
  - **The lock is held for the whole walk, including the sampled reads.** The `walk` value in the line is that hold time.
- **`APS5_HEAP_TRIM=<seconds>`** calls `HeapSetInformation(GetProcessHeap(), HeapOptimizeResources, {HEAP_OPTIMIZE_RESOURCES_CURRENT_VERSION, 0})` and then `_heapmin()` each period. One line per call, with `PrivateUsage` before and after each call and each call's duration:
  `[heap-trim] HeapOptimizeResources ok, private 26.00 -> 24.50 GiB (-1.50 GiB) in 35 ms; _heapmin 0, private 24.50 -> 24.50 GiB (+0.00 GiB) in 1 ms`
  - Whether `_heapmin` adds anything after the first call shows as its own delta in each line.
- **Cost per walk:** not measured. Linux can't run it, and I have no Windows machine.
  - **What I expect on Windows:**
    - the walk grows with the number of heap entries;
    - the sampled reads add about 4,096 calls of a 4 KiB kernel copy, roughly 5–15 ms.
  - **For Village's ~9.8 million busy blocks I expect the lock to be held on the order of a second per walk.** That is an estimate, not a measurement.
  - During that time every heap allocation in the process waits, so **start with `APS5_HEAP_REPORT=60` or more** and read `walk … ms`.
  - **I did not slice the walk.** `HeapWalk` doesn't promise a consistent continuation once the lock is dropped. Its next entry is found from the last one, which may have been freed, coalesced or decommitted in the meantime, so a slice could fault inside `RtlWalkHeap`.
  - If the hold time is too long, the next step is a sliced walk with that risk in view, or a longer period.

## 1. Where the thread starts and stops

- **Start:** `Driver::run(id)` (`Execution/src/Driver/Queues/QueueWorker.cpp`). For `id == 0` it calls `StartWorkerSampler()` and then `StartHeapWatch()`.
  - `StartHeapWatch` reads `APS5_HEAP_REPORT` and `APS5_HEAP_TRIM` as whole seconds above zero. Any other value prints `[heap] <name>=<value> is not a whole number of seconds above zero; it is ignored`.
  - With neither switch set, no thread is made.
- **Stop:** `Lifecycle.cpp` shutdown calls `StopWorkerSampler()` and then `StopHeapWatch()`: `request_stop`, then `join`.
- **The thread's loop:**
  1. It waits until the next due time, or the stop.
  2. A report that is due runs first; a trim that is due runs after it, so a report shows the heap before that period's trim.
  3. An exception ends the watch with `[heap] the heap watch stopped: …`.
- **Lines** go through `ProfilePrint_nid_no_patch` (stderr), like the driver's other periodic lines.

## 2. The report

**Fields** (`HeapReport`):

| field | source |
|---|---|
| busy bytes and blocks | entries with `PROCESS_HEAP_ENTRY_BUSY`, `cbData` |
| free bytes and blocks | the other entries that are neither a region nor an uncommitted range (committed free blocks) |
| uncommitted bytes | `PROCESS_HEAP_UNCOMMITTED_RANGE`, `cbData` |
| regions | `PROCESS_HEAP_REGION` entries |
| busy/free pages | whole 4 KiB pages inside each block of that kind |
| busy/free zero pages | sampled as above; printed as `~` GiB |
| private | `GetProcessMemoryInfo(PROCESS_MEMORY_COUNTERS_EX).PrivateUsage`, read before the lock |
| walk | the time from `HeapLock` to `HeapUnlock` |

- **Nothing is allocated while the lock is held.** The sample buffer is on the stack, and the line is built after `HeapUnlock`.
- A walk that ends with any error other than `ERROR_NO_MORE_ITEMS` prints `[heap] the walk of the process heap stopped early (error N)`.

**Cost:** see the summary.
- Reading about 4,096 sampled pages is bounded by the stride.
- The walk itself is not bounded. It holds the lock in proportion to the heap's entry count.

## 3. The trim

`TrimProcessHeap()`:
1. `PrivateUsage`;
2. `HeapSetInformation(GetProcessHeap(), HeapOptimizeResources, &{HEAP_OPTIMIZE_RESOURCES_CURRENT_VERSION, 0}, sizeof)`, keeping its result and `GetLastError` on failure;
3. `PrivateUsage`;
4. `_heapmin()`, keeping its return value;
5. `PrivateUsage`.

Both calls are timed. `FormatHeapTrim` prints both deltas.

## 4. Tests (`agc_heap_watch`)

**On every platform: `CheckFormats`.**
- It requires the exact report line for a fixed report (above), and `[heap] the walk of the process heap stopped early (error 87)`.
- It requires the exact trim line for a fixed trim, and for a failed one: `[heap-trim] HeapOptimizeResources failed (error 87), private 26.00 -> 26.00 GiB (+0.00 GiB) in 0 ms; …`.
- On Linux: "the report and trim lines are formatted as expected", passed.

**On Windows: `CheckTrimAndReport`.**
- **The pattern:**
  - allocate ≥ 512 MiB with `malloc` in blocks of **64–480 KiB**, each filled with 0xA5;
  - allocate one 256 KiB block filled with zeros;
  - report;
  - free every block except the one crossing each **1 MiB** of the allocation order;
  - report;
  - trim.
- **The trim** must succeed, and `PrivateUsage` after it must be at least **half the freed amount** below `PrivateUsage` after the allocations.
- **The report:**
  - both walks finish;
  - busy bytes fall by the freed amount within 10%;
  - **free + uncommitted bytes rise by the freed amount within 10%**;
  - with exact sampling (stride 1), the busy zero-page count covers the 256 KiB zero block (≥ 63 pages), and both zero counts are within their kinds' page counts.
- It prints both report lines, the trim line, and a summary of what was allocated, kept and freed, with `PrivateUsage` at each step.

**Where it differs from the task's wording, and why:**
- **Blocks are 64–480 KiB, not up to 1 MiB.** The NT heap serves blocks above about 508 KiB with their own `VirtualAlloc`. Those leave the heap's segments at `free()`, so they would show up neither as free space nor in the trim.
- **One live block per 1 MiB,** which is smaller than any heap segment, so no segment can be released whole.
- **"Free bytes" is checked as free + uncommitted.** With the default decommit thresholds the NT heap decommits a large free block at `free()`, so freed bytes can show up as uncommitted ranges rather than free blocks. The two report lines show which happened.
- **The `PrivateUsage` drop is measured from after the allocations to after the trim,** for the same reason. The summary line gives the drop at the frees and the drop at the trim separately.
- **Linux runs the format checks instead of skipping** (see the summary).

**Name for the Windows run:** `agc_heap_watch`.
