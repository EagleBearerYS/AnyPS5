**Why only the queued path imports.**
- The queued >64 KiB store goes `storeBufferFill` → `VulkanDevice::FillBuffer`, and `FillBuffer` always works through `Graphics::HostImportFor`.
- With `APS5_TRACE_HOST_IMPORT=1` the queued run logs `[gpu] host import of 0x7f65311d0000+0x20000 ok … by access`. That is the 128 KiB metadata allocation (`DriverMetadataSpan`).
- Under Unwatch, `GuestBufferMemory.cpp` creates that import with `ImportWatched(base, bytes, …, watchedHostPointer)` and `watchedHostPointer = !state.unwatchImports`, so the range is unwatched after the store. A note made after the store then refuses.

**This matches the task's reading.** On Windows the same flag is `entry.alias != nullptr || !state.unwatchImports || settled`, with `settled` only for imports of 1 MiB or more (`settleFloorBytes = 0x100000`). A 128 KiB import over non-arena memory is therefore unwatched there too when the probe chose Unwatch.

## Part 2: the fix, and why it is not enough

**The change** (`Execution/src/Driver/Packets/PacketMemory.cpp`, `enqueueDmaPacket`, `source == 2 && DmaBytes > gpuStoreLimit` branch, inside the queued lambda):
- `Graphics::NoteDepthMetadataFill(fillAddress, fillBytes, pattern)` and `Graphics::NoteColorMetadataFill(fillAddress, fillBytes, pattern)` now run before `storeBufferFill`, inside `if (const auto localDevice = device.Load())`, so a fill that is never stored is never noted.
- `noteMetadata` is passed as `false`.
- This branch already excludes `DmaSelectGds` (1), the same test as the ≤64 KiB branch's `metadataFill`.
- The pattern is uniform, so `storeBufferFill`'s `uniform` guard on its own note was always true here.
- `NoteDepthMetadataFill` takes the GPU mutex itself, as on the ≤64 KiB branch.

**Why it still fails.**
- `DepthSurface::CheckCurrent` requires every `sampling.initial` range, the HTILE included, to be `GuestMemory::Watched`.
- The queued store's import has just unwatched the HTILE, and on Linux nothing rewatches a host-pointer import. Deferred settles exist only for dma-buf imports of 1 MiB or more.

**One step further** (local experiment, reverted). I allowed an unwatched HTILE in that `Require` when `queuedFill` holds. The run then fails at the next proof step: `AGC graphics: CPU writes raced native multisample depth clear`. That is `GuestMemory::UnchangedSinceCollected(metadata, clearGeneration)`, which cannot prove an unwatched range unchanged. So the whole clear proof assumes a write-watched HTILE. A queued fill whose import unwatches it needs a design decision, not a reorder. For example:
- keep the HTILE of a live native multisample depth surface watched across the import;
- or settle the import and rewatch before `CheckCurrent`, like BF-150's `WatchedAfterSettle` for initial DCC (Windows only, since Linux host-pointer imports have no settle);
- or prove the HTILE through a compared import, as BF-151 does for multisampled DCC.

**What this means for the 3070** (a reading, not measured). On Windows, `deferredSettles` is on by default (`APS5_NO_DEFERRED_SETTLES` turns it off). An unwatched 64 KiB-aligned import is queued for a settle (`pendingSettles`/`settleWanted`), and `rewatchSettledImports` rewatches it once the settle copy is done, unless a storage texture overlaps.
- **`CheckCurrent` itself does not settle first** at this base: there is no `WatchedAfterSettle` here.
- So with the fix, the 3070 most likely moves from the note's refusal to `CheckCurrent`'s `requires watched accessible guest memory`. It would pass only if a settle happened to complete between the fill and the sample.
- Only a Windows run can confirm this. The Linux test cannot model the settle.

## Part 4 (report only): the compute-kernel fill route

**Yes. A compute-kernel fill over a live native multisample depth target's HTILE with imports unwatched would hit the same refusal, on `main` as here.**

- **The route:** `Dispatch.cpp:137` calls `Driver::fillBuffer`, which ends with `storeBufferFill(queueId, base, bytes, pattern, localDevice, memoryFill.has_value(), true)` (`BufferFill.cpp:322`).
  - The fill is not cleared or absorbed for an HTILE range: `FillClear` is for storage textures, and `MultisampledColorFillAbsorbs` is for colour targets.
  - So `storeBufferFill` reaches `localDevice->FillBuffer`, which always goes through `HostImportFor`, the same import as the queued path.
- **Under Unwatch**, that import leaves the HTILE unwatched. The post-store `NoteDepthMetadataFill` (`if (noteMetadata && uniform)`, `BufferFill.cpp:422`) then refuses with `native multisample depth metadata fill over unwatched memory is not implemented`.
- **Moving that note before the store would not be enough either**, for the same reasons as part 2: `CheckCurrent` needs the HTILE watched, and the clear proof needs `UnchangedSinceCollected`.
- **On Linux at main's defaults** this is live. The lavapipe probe here reports `host imports resolve write protection: yes … imported ranges are compared`, so imports are unwatched unless a test forces Watch, which the driver-path tests do on non-Windows.
- I did not write a test. It would need a recognized fill kernel dispatched over a live target's HTILE, which is not cheap in this harness.
