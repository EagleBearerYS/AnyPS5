## How the two compose

**Why the branch is the natural core.** In FreeType 2.4.12 the legacy functions are thin wrappers over `ft_mem_*` with an item size of 1 (`ftutil.c` L436-L500 under `FT_CONFIG_OPTION_OLD_INTERNALS`, through `ftmemory.h` L144-L170 and L260-L277):

| legacy function | 2.4.12 expansion |
|---|---|
| `FT_Alloc` | `*P = ft_mem_alloc(memory, size, &error)` |
| `FT_QAlloc` | `*P = ft_mem_qalloc(memory, size, &error)` |
| `FT_Realloc` | `*P = ft_mem_realloc(memory, 1, current, size, *P, &error)` |
| `FT_QRealloc` | `*P = ft_mem_qrealloc(memory, 1, current, size, *P, &error)` |
| `FT_Free` | `ft_mem_free(memory, *P); *P = NULL` |

So the qalloc/qrealloc core is this branch's `ft_mem_qalloc` and `ft_mem_qrealloc`. #12373's `Reallocate` is `ft_mem_qrealloc` with an item size of 1 written out again.

**Within libSceFreeTypeOt.** Once both land, the three throwing Ot stubs #12373 names (`FT_QAlloc`, `FT_Realloc`, `FT_QRealloc`) can be one-line wrappers over this branch's `ft_mem_*`, which live in the same module.

**Across modules.** libSceFreeType's `FT_*` are in a different module (`libSceFreeType.prx`), so they cannot call our `ft_mem_*` across modules. A shared core would have to be header-only.
- **Where it could live:** inline `ft_mem_qalloc`/`ft_mem_qrealloc` bodies over `GuestMemoryRec` in a header under `libSceFreeType/include/`, which both modules already include. Either #12373's `libSceFreeType/include/MemoryAllocation.hpp` or a new header next to `GuestList.hpp`.
- **What it would replace:** `Reallocate` in #12373, and the bodies in this branch's `Memory.cpp`.

**Two policies must agree first:**
1. **Null record.** #12373 throws on a null record or output. This branch's `ft_mem_*` dereference the record, as FreeType does, and have no null check.
2. **Zeroing a new block.** See the version difference below: #12373 follows 2.4.12 and this branch follows 2.13.3.

## FreeType 2.4.12 against 2.13.3 for the eight functions

Compared: 2.4.12 [`cecf93ef90`](https://github.com/freetype/freetype/blob/cecf93ef90c660a8b0b45e5adbbfb5ea443fb6b9/src/base/ftutil.c#L49-L220) against 2.13.3 [`42608f77f2`](https://github.com/freetype/freetype/blob/42608f77f20749dd6ddc9e0536788eaad70ea4b5/src/base/ftutil.c#L48-L221).

**One behavioural difference:**
- **`ft_mem_qrealloc` with `cur_count == 0`:**
  - 2.4.12 calls `ft_mem_alloc(memory, new_count * item_size, &error)` (L146), which **zero-fills** the new block.
  - 2.13.3 calls `memory->alloc` directly and sets `Out_Of_Memory` itself, so the block is **not zeroed**.
  - The branch follows 2.13.3. #12373's `FT_QRealloc` zero-fills from 0, which matches 2.4.12.
  - `ft_mem_realloc` is unaffected, because it zeroes the grown region in both versions.

**Guards only, no observable effect:**
- `ft_mem_alloc` and `ft_mem_realloc` gain a `block &&` check in 2.13.3 before zeroing. When there is no error and size > 0, the block is never null; the only null case zeroes 0 bytes.
- `ft_mem_dup` gains `size > 0` and an explicit `(FT_Long)` cast in 2.13.3. With size 0 the copy is 0 bytes either way, and the implicit conversion is the same.

**Identical:** `ft_mem_qalloc` (`block == NULL` versus `!block`), `ft_mem_free`, `ft_mem_strdup` and `ft_mem_strcpyn`. The `FT_ASSERT` spelling also differs only cosmetically.

**Basis question for the reviewer.** The module exports `FT_QAlloc`, `FT_Realloc` and `FT_QRealloc` (the NIDs #12373 names). 2.13.3's `ftutil.c` has none of them; 2.4.12 has them only under `FT_CONFIG_OPTION_OLD_INTERNALS`. That points to a 2.4-era build of libSceFreeTypeOt. If so, `ft_mem_qrealloc` from a count of 0 should zero-fill, as 2.4.12 does. I did not change it: the branch follows the 2.13.3 basis that main's other libSceFreeTypeOt rows cite.
