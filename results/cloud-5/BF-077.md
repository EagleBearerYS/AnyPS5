## 2. Tests, red and green

**The seam.** Each test sets `Driver::SetCaptureCheckHook(&ChangeTableBeforeCheck)`. The hook runs on the queue worker, after the capture and right before the check. When armed, it disarms itself, rewrites the table and counts the change. No second thread is involved: the change happens at the same point on every run.

**`agc_driver_draw_recapture_on_change`** (pipelined; ctest `_inline` = synchronous, with `APS5_PIPELINED_DRAWS=0`)
- **Setup:**
  - A vertex program in the AddressPasses pattern reads three V#s from a table at block+0x300, which `s_load` reads.
  - The block is a registered 64 KiB `GuestBlock` (readable, writable, GPU). It is live: writable and host-backed.
  - V#1 points at data with x = +8 (block+0x900), V#2 at zeros (block+0xa00).
  - The pixel program does a global load, so the draw is an address-based (BDA) build and `AddSnapshot` compares it.
- **`ChangedTableIsBound`:**
  - V#0 starts as zeros. The hook rewrites it to a valid V# over block+0x800, whose x = −8, which moves the triangle onto the target.
  - The case requires: the table changed once, the brightest color byte is 255, and exactly 1 packet was prepared again.
- **`UnchangedTableIsNotRedone`:** the same draw again, hook not armed. It requires brightest 255 and 0 packets prepared again.

**`agc_driver_dispatch_recapture_on_change`** (locked; ctest `_items` with `APS5_PIPELINE_DISPATCH=1`)
- **Setup:**
  - A compute program `s_load`s a V# from a table in a registered block, `buffer_load`s lane i, adds 1 and stores through the V# in s[4:7].
  - Buffers: `first` (0x1000 + lane) and `moved` (0x2000 + lane).
- **Rounds:**
  1. Round 1 requires 0x1000 + lane + 1 (lane 0 = 0x1001).
  2. Round 2, hook armed, moves the table's V# from `first` to `moved` after the capture. It requires 0x2000 + lane + 1 (lane 0 = 0x2001) and 1 packet prepared again.
  3. Round 3, unchanged, requires 0x2001 and 0 packets prepared again.

## 5. Limits

**The pipelined path, Enqueue to commit.** The pipelined check runs on the worker, right before `Enqueue`. The committer records the draw later. A write that lands between `Enqueue` and `commitDraw` is not seen by this check.
- `AddSnapshot`'s compare stays the last check there, as the task asked. But it only warns, and only for address-based (BDA) builds (`ShaderAddressResources.cpp:144`).
- Closing that window would need the committer to compare and send the draw back to the worker. Once it is enqueued, the bindings are already baked, and the packets behind it are already being prepared.
- With `APS5_PIPELINED_DRAWS=0`, a draw is checked under the GPU lock right before recording, so the window after the check is the recording itself.

**The CPU-path indirect draw.** Its loop records several draws from one capture, and the check runs before the first record only. A write that lands between records of one packet is not seen.

**One retry per packet.** The second pass records whatever it captures, even if memory changes again before its own check. This is the "no loop" the task asked for. Its own capture is fresher, but nothing stops a title that keeps writing.

**Comparing twice:**
- **Synchronous draws:** `AddSnapshot` skips the regions the check just found equal, so there is no second memcmp.
- **Pipelined draws and dispatch items:** `AddSnapshot` runs later, on the committer, so the two compares are at different times. Marking a region compared would skip the only check of the Enqueue-to-commit window, so it is not marked: two compares per region for BDA builds.
- **Dispatches (locked and items):** `AddSnapshot` runs in `PrepareDispatch`, before the check, so the mark comes too late to skip anything. A dispatch whose build is address-based gets two compares per region: one at preparation, one under the lock.
- **The commit message is too broad here.** It says the regions the synchronous check found equal are skipped by `AddSnapshot`. That holds for draws, not dispatches.

**What the check reads.** It compares the bytes of the captured regions with guest memory, without a flush or a sync:
- A GPU write that the CPU-visible pages don't show yet is not seen, the same as with `AddSnapshot`.
- A write that leaves the captured bytes unchanged is not a change.
- For pages outside the guest arena and image spans, `CompareMapped` asks the kernel per region (see section 3).

**Not covered by a test:** the CPU-path indirect draw's check (line 565). It shares the code path of the synchronous check at line 622, but no test reaches it.

**Seen outside scope:** in the AddressPasses-style vertex program, a third vertex buffer's data does not seem to be added to the position. With x = −8 / +4 / +4 nothing rendered, so the test's layout uses −8 / +8 / 0. Not investigated.
