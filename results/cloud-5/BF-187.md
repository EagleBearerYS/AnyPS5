## Part B: the refusing check, the minimal cause and the fix

### Answer

- **The refusing check is (b), in a form BF-182 didn't hit.** It's `ChildKeyWord` (`ResourceTracker.cpp:694` on a765ccece), reached through `DescriptorWordReads` for the key's handle on V# A.
  - The key word is read through V# A.
  - The eight T# reads it indexes go through **V# B's** handle.
  - `ChildKeyWord` requires that handle to be `SameHandle` with V# A's.
- **The minimal cause:** V# B is a second load of the same pointer and address, but at another width. Each loaded word's `MemoryInfo` carries its instruction's `componentCount` and `componentIndex`, so `EquivalentValue` doesn't match V# A's words to V# B's. Two V#s are seen where the guest has one.
- **Why only the S# fails:**
  - The T# through V# B still plans. `MatchChildKey` sees the key read through a different handle and falls back to `MatchKeyDomain`, so the T#'s planning passes.
  - Only the S# through V# A is refused, with the title's text.
- **Why it must be the width:** for a scalar load, the translator records only `kind`, `offset`, `dataDwords`, `componentCount` and `componentIndex` (`ScalarBufferInstructions.cpp` `sLoad`). So two loads through one pointer value at one address can only differ in width, or in the pointer being a different IR value.
- **This is a reproduction, not a confirmation.** His run with the Part A trace will show the line `ChildKeyWord: a read at the key is through another handle than the V#`, with `buffer` set to V# B's handle:
  - if V# B is a wider (or split) load of the same address, the fix covers it;
  - if V# B is read from another address, it stays refused on purpose (see below), and the trace would show that.
- **It's within what #9969 means to allow.** Neither pinned refusal changes:
  - `agc_driver_pointer_vsharp_child_key_table` "a key word that also feeds the output";
  - `agc_driver_pointer_vsharp_shared_table` "a data read through a third handle on the V#'s words".

  Both are still refused, and green.

### The fix (f65f7d7ee)

- **`SameDescriptorWords(left, right)`:** two handles are the same V# when, word by word, each pair is either `EquivalentValue`, or both are `LoadAddressU32`/`ReadConstBuffer` reads with:
  - the same `MemoryInfo`, ignoring only `componentIndex` and `componentCount`;
  - pairwise equivalent operands: the same pointer, the same offset value, and so the same address.
- **Used in three places, and nowhere else:**
  - `ChildKeyWord`: the reads the key indexes;
  - `MatchChildKey`: the key's own handle, so the T# gets its child key domain instead of the fallback;
  - `WrittenThrough`: a store through any load of the address now counts, which can only refuse more.
- **`SameHandle` is unchanged** everywhere else.
- **Still refused:**
  - a copy of the V# at another address, even holding the same words (two addresses can differ at dispatch);
  - a key word that also feeds other instructions;
  - other key forms, and stores.
- **Debt entry:** "Nested image tables" now says "other-width loads of its address count as that V#". To stay at 994 characters (limit 1000), the non-gap clause "equal V#s in a column share a child snapshot" was dropped and "faults if it was not captured" became "faults if not captured".
- **`FormatVersion`:** unchanged at 50. No serialized structure changed, and the disk cache already rejects entries whose `SourceVersion()`, a hash of the recompiler sources, differs.

### The new test: `agc_driver_pointer_vsharp_copy_table`

The command is `agc_driver_image_table_tests --pointer-vsharp-copy-arm`. It is `RunPointerChildKeyTests` with `copy` set, using `PointerVsharpCopyCode` (103 words).

**What the program does:**
- **Per waterfall lane group:**
  1. Record read 1 into the pointer.
  2. A V# load before the inner loop, whose T# at 0x4c0 is sampled and is the arm's source.
- **Then a two-pass inner loop.**
  - **The pointer:** it goes through three constant arms, giving four nested Phis with the loop header, as in his `Phi(Phi(Phi(Phi(ReadConstBuffer@…, Phi)…`.
  - **V# A:** an `s_load_dwordx4` through the pointer. Its first handle reads the key at 0x0; a second handle reads the S# at 0x20.
  - **V# B:** an `s_load_dwordx8` through the same pointer and offset. Its eight T# reads are at `((key >> 16) << 5) + k`.
  - **The sample:** the T# at the key is sampled with the S#, and the T#'s dwords 1 and 2 are decoded into width and height.
  - **The back edge:** record read 2 reloads the pointer, which can take the T#'s dwords (the arm).

**What it checks, on every lane:** the sample through the T# at the key with its S#, width = 64 and height = 4, and the T# at 0x4c0. The runs are BF-182's:
- keys 2 and 5 (key at 0x0);
- the largest key (47) and 17;
- the S#s swapped with keys 30 and 47;
- record 1's pointer moved to the other V#;
- the arm taken: group 0's pointer takes the 0x4c0 T#'s dwords, and the run must fault outside the snapshot.
  - The key read and the width/height decode are replaced by constants there, so no real load goes through that pointer.
  - My first version took the arm from the T# read through V# B. That keeps V# B's loads real (aeb0b65e8), so its second pass loaded through the T#'s words and segfaulted in llvmpipe's JIT code. That is the program's own load, not a planner fault.
- **Refusals that must hold**, both with `GetSamplerResource dword 0 is not a valid runtime value`:
  - V# B loaded 16 bytes further on, where the records hold the same descriptor;
  - the key word also written to the output.
