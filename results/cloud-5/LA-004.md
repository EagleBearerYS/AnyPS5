## 6b(ii). GPU-written sampled textures

**What the CPU path's direct binding does for a GPU-written texture.**
- The texture cache serves a `Texture` that is a view of the resident storage image (`Texture::StorageSource()`), sampled in `VK_IMAGE_LAYOUT_GENERAL`. There is no copy and no shadow.
- `ShaderResources::StorageImages()` puts that image into the draw's `PassAccess`. `Recorder::StartDrawPass` then sees the hazard against the producer pass's attachment, ends the pass and records a barrier.
- On the copy path (`APS5_NO_HOST_IMPORT=1`) the cache serves a snapshot copy, refreshed once the target's write-back has landed.

**What the device path now does:**
- **The same texture.** `LookupDeviceTableTexture` goes through the texture cache's direct-binding path, so the heap slot holds the same storage-image view in `GENERAL`. That means the same texels and the same layout. Harness (h) and the bench's verify draw read the producer's texels both ways.
- **10e5f48f1, refresh:**
  - An entry whose texture views a storage image stays fresh while the storage cache still returns that image (`StorageTexture::Cached()`), and only CPU stores to its blocks count against it: `ChangedBlocks`' `cpu` flags, then `UnchangedSinceCollected` against the entry's generation.
  - A dropped image makes the entry stale.
  - The pending-store query excludes the entry's own image, so its own GPU writes don't re-prove the neighbours that share its blocks.
  - A re-check that finds the same texture keeps the entry, its slot and its bucket. No new texture or slot is made.
- **10e5f48f1, barriers:** `ShaderResources::StorageImages()` adds the table's storage views (`DeviceImageTable::StorageImages()`, cached and reset on hold/release) when the draw uses the table. The pass access that decides the pass barrier then sees them, as it does for a direct binding.
- **c530ad2c2, unwatched memory:**
  - A host import unregisters the whole guest allocation from the write watch, so its entries have generation 0. They were re-checked on every draw that moved the own-write serial: 4.35 M re-checks over 20 frames, about 5.6 ms per draw. That was my first bench run, at 2f4b827cd plus this work uncommitted.
  - Now they are re-checked only when the collect epoch moves or the driver stored over them. A block run with no newer stamp than the last scan is skipped.

**Honest limits of 10e5f48f1:**
- Neither memory mode on this machine reaches its own-generation branch.
  - With imports, a render target's entry has generation 0, so c530ad2c2's rule handles it: the entry is re-checked once per frame when the epoch moves, finds the same texture, and keeps its slot.

   - 4.3–4.5 ms of GPU time per device-path draw, against 0.17 ms per CPU-path draw, on a 64×4 target.

   - Each missing pixel lane appends a record: 128 per draw on the 64×4 target. The cold first frame drained 125,184 records and dropped 61,568 to find 256 distinct keys (host import, 3073e11d0).
   - a8b93dc86 keeps the program on the path.
   - A subgroup-level dedup in the lookup (one record per distinct key per wave) would cut the ring traffic and the drain cost by about 64×.
4. **Per-frame re-check of every unwatched entry** (host imports). Each live entry is re-checked once per collect-epoch move, about 150–170 µs per entry on this machine. That is 40–50 µs per draw at 256 entries, and it grows with live entries. A finer test is the next candidate: the driver's `NewestStamp` over the entry, plus the storage cache's own state, without the epoch.
5. **Part (f) without eager write-back.**
   - With a heap cap of 2, host import and the switch on, the warm draw reads zeros: "(f) the warm draw: pixel (0, 0) channel 0 is 0, expected 160". It happened in 3 of 3 runs.
