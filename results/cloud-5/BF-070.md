**The `insertDrawEntry` head needs more than a union of both sides:**
- **The PR's replacement path erases the shape's previous entry inline:** `accountDrawVariant(false)` for its variants, then `drawOrder.erase` and `drawCache.erase`.
- **The branch routes every erase through `dropDrawEntry`,** which also calls `unpinCpuIndirect` for a CPU-path indirect entry.
- **Such an entry can be the shape's previous entry:**
  - the branch inserts CPU-path indirect entries with the draw's shape when register keys and data hits are on;
  - `drawShapes[shape] = key` is set for any entry with a decode.
- **The leak:** the inline erase would leave that entry's bytes and pins in `cpuIndirectBytes`, `cpuIndirectPins` and `cpuIndirectEntries` for good. The cap would then refuse inserts earlier and earlier.
- **The resolution:**

```cpp
    const bool shapeUpdate = replaceShape && shape != 0;
    if (shapeUpdate) {
        ++counters.shapeUpdates;
        if (const auto shapeOf = drawShapes.find(shape); shapeOf != drawShapes.end() && shapeOf->second != key) {
            const auto previousKey = shapeOf->second;
            drawShapes.erase(shapeOf);
            if (const auto previous = drawCache.find(previousKey); previous != drawCache.end()) dropDrawEntry(previous);
        }
    }
    if (cpuIndirect) sweepCpuIndirect();
```

and `if (!shapeUpdate) ++counters.inserts;` where the branch counts an insert (after the cap's refusal).
- The shape is erased before `dropDrawEntry`, so `dropDrawEntry`'s own shape cleanup finds nothing and can't touch an invalidated iterator. Otherwise this is the PR's behaviour.
- `replaceShape` and `cpuIndirect` never hold together, because `shapeNeedsEntry` requires `!drawParameters.indirect`.

**How the two compose otherwise:**
- 6946's draw finisher hand-off requires `!drawParameters.indirect`. CPU-path indirect draws stay inline, so the branch's per-record patching runs where it did.
- 6946's lookup-side drain sits before `drawCacheMutex`, and the branch's `++drawLookupSerial` sits under it. They auto-merge side by side.
- The PR's data hits compare only the words in a stage's `userDataMask`. 6946 sets it in `DrawCapture.cpp` to `asValue | asBase | userDataRegisterReads`, or to every word when nothing is walked.
  - The branch's `walkedWords` is `asBase | asValue`, a subset, so every word the branch treats as walked is compared on a data hit.
  - The branch's `compiledValues` check therefore holds on that path too.
  - The trial below runs the PR's `draw_data_hit_user_words` tests with the branch.

**6931:**
- **What it does:** on the last drawable record of a CPU-path indirect draw, it enqueues the commit on the draw pipeline and returns from inside the record loop.
- **What that skips:** the branch adds the loop's `cpuIndirectPatched`, `cpuIndirectReused` and `cpuIndirectCaptured` after the loop. A pipelined last record would therefore not count that packet's stages. These are profile counters; no cache decision reads them.
- **The fix in the merge:** add them to `drawEntryCounters` before that return as well (a small lambda called at both returns).
- **Everything else composes:** the branch patches the record's result before the draw is built, and 6931 moves `results` into the commit after that.
- **Trial** (/home/user/ov-6931, both sides kept, without the counter fix):
  - **Pipelining on (the default):** 11 of 11 passed, including 6931's `agc_driver_pipelined_indirect_draw`.
  - **`APS5_NO_PIPELINED_INDIRECT=1`:** the 10 cache tests passed, and `agc_driver_pipelined_indirect_draw` failed: "the indirect draws drained the pipeline instead of queuing behind it".
  - **That failure is the test's own premise, not the branch.** On main + 6931 alone (9fb5f274d, /home/user/ov-6931-alone), the same test passes by default and fails with the same message under `APS5_NO_PIPELINED_INDIRECT=1`.

**6612 and 6679:**
- **What they change:** `locate(location)`, which gives one `(program, word)`, becomes `UserDataWords(programs, roles, location)`, which gives every word for that location across merged programs. `patch` then loops over them.
- **What the branch assumes:** one word per location (`compiledValues`, an array of 3; `writes`, an array of 3).
- **The resolution:**
  - make `writes` a `std::vector<UserWordWrite>`, or an array of `3 × programs.size()`;
  - take each word's compiled value from `programs[program].userData[word]` before the record loop, as the branch does for one word;
  - have `patch` record every word it writes.
  - `pushedOnly` and `compiledValuesOnly` are already evaluated per program over that program's writes.
- **Behaviour:** the branch's `keepCpuIndirect` excludes tessellation draws, so merged-hull draws stay uncached either way. Only the per-record loop's text is shared.
- Not built; the two PRs compete, and only one of them should need it.

**1896:**
- **What it adds:** with `APS5_PIPELINE_INDIRECT=1`, a CPU-path indirect draw takes a new block placed before the branch's.
