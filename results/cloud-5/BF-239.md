# BF-239 result (cloud-5)

## Verdict: not a bug on main, and not with our stack

- **On main, the GPU store of a cleared HTILE already stamps the generation.** It does so exactly as its sibling GPU fill does, and the generation recorded after the store is the post-store one.
- **The only reader of that recorded generation is `storeBackClearedHtile` itself.** It compares with `UnchangedSince`, which sees the stamp.
- **The native multisample depth owner's HTILE generation can never be stale from this store.** That is `sampling.initial[1].generation`, named `metadata` in `CheckCurrent`. `storeBackClearedHtile` never runs on a target whose HTILE a native owner guards.
- **Nothing was built or pushed.** The task asks for a fix branch only if the bug is real, so `fix/agc-htile-store-back-generation` does not exist.

**What the reporter's old tree likely lacked** (details at the end): the completion stamp for a GPU HTILE *clear* over a native owner's HTILE, and its re-armed baseline. These landed on main in #7233 and #7371 on 2026-10-23, well after their base. That is in a different function from the one they patched.

## Trace on main (d2b3ee3bcc)

### The store
All in `core/libs/prx/libSceAgcDriver/Graphics/src/DepthSurface.cpp`.

**`storeBackClearedHtile` (:1690–1733)** reads the target's whole HTILE. If its words are a fast-clear encoding, it rewrites them to the expanded encoding and returns the cleared aspects for the host surface to clear. It has two store paths:
- **GPU path (:1703–1718),** taken when a recorded fill is pending over the HTILE and `htileAfterPendingFills` knows the word it will leave. It calls `storeHtileOnGpu` (:1669–1688):
  - `vkCmdFillBuffer` into the HTILE's host import;
  - `recorder.NotePendingWordFill(address, bytes, word)` (:1685);
  - **`GuestMemory::MarkWritten(address, bytes)` (:1686).**

  Back in `storeBackClearedHtile`, `generation = GuestMemory::CollectWrites(...)` (:1713) is stored in `htileReads()[htileAddress]` (:1715).
- **CPU path (:1720–1731):** `GuestMemory::Write` of the expanded words, then `CollectWrites` (:1728), stored at :1731.

**What `MarkWritten` does:**
- `GuestMemory.hpp:85–89`: it "returns the generation the blocks were stamped with … `UnchangedSince(range, it)` holds until the next store over the range".
- `GuestMemory.hpp:98–99`: "The driver's own writes (Write, WriteChanged, MarkWritten) stamp their blocks, so they are never hidden" from the per-epoch collect memo.

So after either path, any `UnchangedSince` taken against a generation from before the store fails. A generation stamp is not left stale.

### Is it the odd one out? No
`VulkanDevice::FillBuffer` (`Execution/src/VulkanDevice.cpp:2587`) is the GPU fill behind the fill and DMA packets, which also store CMASK, DCC keys and HTILE. It does:
- the same `recorder.NotePendingWordFill(...)` (:2762) for a uniform fill;
- then `GuestMemory::MarkWritten(address, bytes)` (:2764).

The other GPU writes into guest memory in that file stamp the same way: `WriteLabelOnGpu` (:2545, :2551), `DumpSamplesOnGpu` (:2583) and `CopyBuffer` (:3031, :3037). `storeHtileOnGpu` is a copy of the pattern.

**No reader sees a stale view of the bytes after a GPU store.**
- Every CPU read of guest memory goes through `GuestMemory::Read`, which calls `FlushGpuWrites` before copying (`GuestMemory.cpp:2550–2553`).
- `CheckCurrent`'s raw `memcpy` of the HTILE (:359) runs only after :346 has refused any pending write over its ranges.

So the window between `MarkWritten` at record time and the fill landing on the GPU is not observable as "new generation, old bytes".

### Why the native owner's `metadata.generation` cannot meet this store
- **The call site skips native-owned targets.** `DepthSurfaceView` (:1958) runs `storeBackClearedHtile` only when `!RoutesToNativeDepthOwner(target)`.
- **`RoutesToNativeDepthOwner` (:1627–1633) covers every target that could touch an owner's HTILE.** It is true for:
  - every multisampled target;
  - every single-sample target whose HTILE range overlaps an active depth guard.
- **The guards cover the owner's HTILE.** A native owner registers guards over all of its `sampling.initial` ranges, which are depth and HTILE (plus the stencil plane on our stack), when sampling becomes active (:1990–1994).
- **Order doesn't matter.** A single-sample store-back that ran before the owner existed is synced and stamped before the owner's `prepareDepthSampling` takes its generations. It also leaves the expanded word (`expandedHtileWord`, :1604–1609: low nibble 0xf), which `htileProvesClear` rejects (`(word & 15) == 15`, :89–95), so the owner refuses the import instead of trusting it.

## Failure sequence

**None on main.** The candidate sequence would be:
1. A native owner imports an HTILE.
2. `storeBackClearedHtile` then stores the cleared HTILE on the GPU over it.
3. The owner keeps its old `metadata.generation` and serves its image against changed HTILE.

Step 2 cannot happen: the call is skipped by routing (:1958, :1627–1633). For a non-native target, the recorded generation is taken after `MarkWritten` (:1686 → :1713). A generation recorded before the store fails `UnchangedSince` after it.

**The reporter's suggested change would be harmful if applied to the native owner.** Bumping the owner's `metadata.generation` via `CollectWritesUncached` at a GPU HTILE store would make `CheckCurrent`'s `UnchangedSinceAll` (:369) accept a changed HTILE without re-proving its words. Main only refreshes `current[1].generation` after re-proving every word with `htileProvesClear` (:357–366).
