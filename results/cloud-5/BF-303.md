## The change

Lines are on `14873ade04`, `core/libs/prx/libSceAgcDriver/Graphics/src/Texture.cpp`:

```diff
-    const bool flushed = !handOverKeys.has_value() && FlushPending(scopeBegin, scopeBytes, alias.get(), "storage refresh", PublishScope::None);
+    bool flushed = !handOverKeys.has_value() && FlushPending(scopeBegin, scopeBytes, alias.get(), "storage refresh", PublishScope::None);

         keys = handOverKeys.has_value() ? *handOverKeys : ProvedKeys();
+        if (alias != nullptr && keys != DccKeys::Uncompressed) {
+            refreshingAlias = exemptAlias.previous;
+            alias = nullptr;
+            flushed = FlushPending(scopeBegin, scopeBytes, nullptr, "storage refresh", PublishScope::None) || flushed;
+            keys = ProvedKeys();
+        }
```

That's the intended shape from the task. At the borrow decision (right after the keys are proved after the flush), if the alias was kept but the keys aren't Uncompressed, the refresh:
1. **ends the alias's exemption:** `refreshingAlias` goes back to its value from before the refresh, so the hook's flushes for the rest of the refresh no longer leave the alias out, and the RAII guard still restores it at the end;
2. **drops the alias:** so the borrow block and `takeRefreshProof(alias != nullptr)` behave as on main's no-alias path;
3. **stores it over the surface:** as a refresh without an alias does (the same `FlushPending` with no exception, reason "storage refresh");
4. **proves the keys again**, since that store went to guest memory.

**Both paths:** it applies with and without a host import, because it doesn't depend on `direct`.

**Why this form and not "decide the keys once":** deciding the keys once isn't equivalent. The refresh's own flush can store keys, as the test shows: a linear image's write-back turns the keys single. So the keys proved before that flush can be stale by the upload.

### Why it keeps BF-290's proof (§2-3)

- **BF-290's exemption proof:** with the alias kept, each of its pending units is either (i) taken on the device by this refresh, or (ii) stamped since its generation.
  - The gap broke (i): the alias stayed exempt while the borrow block, which needs `keys == Uncompressed`, didn't run.
  - After the change, the alias stays kept, and so exempt, past the borrow decision only when the keys proved there are Uncompressed. So the borrow block runs whenever the exemption lasts, and (i)/(ii) hold again.
- **Row 11** (a bit copy needs uncompressed keys): it's now checked with the keys the borrow and upload actually use, not only with the keys proved before the flush.
- **(a)-(c)** (the copy's conditions and GPU order): they concern the device copy, which doesn't happen when the alias is dropped.
- **(d)** (the registry stays truthful): the dropped alias is stored, so it's no longer pending on what it stored, exactly as on main's no-alias path.
- **Ordering:**
  - **The store comes before every read of the surface for the upload.** Between the first flush and this point, the refresh reads only the DCC keys (`ProvedKeys`).
  - **`changed` covers what the store stamped, without an extra rescan.** The store happens before the change analysis (`UnchangedSince`, `scanBlocks`), so its stamps mark the units it wrote as changed. With the keys changed, every unit is changed anyway.
- **Store order:** the other images over the surface are stored by the first flush, and the alias by the second.
  - On a unit both images cover, the write-back that runs second drops the unit, because the first store stamped it. That's the same stamped-unit rule main applies between images inside one flush, and the rule the borrow applies on `a7e04ab973`, where the alias doesn't take units another store stamped.
- **Cost:** only when the gap occurs, that is, a DCC image whose keys a pending image's write-back changes during its own refresh. Then it's one more `FlushPending` and one more key proof.

- **Code:** `tests/Recorder.cpp`, `storageAliasKeysTests`, after BF-290's `storageAliasBorrowTests`.
- **Registration:** next to `agc_storage_alias_borrow` (`SKIP_RETURN_CODE 77`, `TIMEOUT 60`, the Windows PATH list).

**Setup:**
- **Memory:** a write-watched allocation of five 64 KiB blocks, host imports off (as BF-290's test).
  - The first block is DCC keys at 0xff (uncompressed); the surface is the next four units at 0x11.
  - The RGBA8 image's 1 KiB of keys sit right before the surface.
- **The three cached storage images:**
  - **X:** the RGBA8 (format 56) 256x256 kR64KBX image, with `dccAddress` = the keys;
  - **Y:** the R32 alias (format 20) over the same surface, no DCC;
  - **Z:** a linear R32 256x65 image over the keys and the surface's first unit. As a linear image it has a single tracked unit, so a flush stores it whole, keys included.
- **Guard:** the sample's texel (the centre) isn't in unit 0, which Z covers. The first layout, with the keys after the surface and Z over unit 3, failed this guard, because the centre is in unit 3.

**Steps:**
1. Y is cleared on the GPU to 0x80402030 (red 48) and marked dirty. Z is cleared to 0x10101010, the ClearSingle key byte, and marked dirty.
2. `X.Refresh()`:
   - **The alias is kept:** X's key proof from its upload still holds (nothing wrote the keys), so the keys are Uncompressed before the flush.
   - **The flush stores Z:** Z overlaps unit 0, so the flush (Y excepted) stores it. That turns X's keys to 0x10 (ClearSingle) and stamps unit 0.
3. The test checks that the keys now read all 0x10.
4. X must sample 48/255: Y's results in the units X reads, through the single-key expansion of guest memory.
5. Y must no longer be pending over the surface.
