## Summary

- **Re-pointing a page-table entry is the wrong mechanism for these rings.** It isn't needed, and it wouldn't be enough.
  - **Not needed:** a snapshot inside the build's address space adds nothing to the build (GBM:4952-4995 returns). The region that holds it is served live by its own table entry, and the table is the space's table, keyed by the space serial (GBM:6182, 6192).
  - Village's rings sit in 0x230200000+0x30100000. That is one registered 769 MiB range (GAC-040 §1.5), imported in 64 MiB cells or heap-mirrored. Both are live base regions.
  - **Not enough:** a moved snapshot's bytes reach the shader through **data words**, not the table:
    - folded scalar loads go into the per-draw `FlattenedSrt` buffer (binding 61);
    - the pointer to the block goes into push constants, or into the `ShaderData` buffer (binding 62).
- **The exact mechanism already exists for non-BDA draws.**
  - `MovedReadOnlyBuffers` notices changed `ShaderData`/`FlattenedSrt` words (SR:6018-6030).
  - `PrepareDrawBindings` uploads them into a `recorder.DrawUpload` slice, with the build's data patches applied (SR:6155-6163), and binds a per-use set from `AllocateRewritten` (SR:6241-6246).
  - BDA builds are kept out by two `usesBda` returns (SR:6014, SR:6136) and by #6636's refusal (p6636: SR:5391).
- **Answer: yes, exact, and well under 300 µs per use** for moved snapshots that are live in the same space.
  - The moved-snapshot check is a binary search plus a `memcmp` of 0x50-0x70 bytes, about 1 µs.
  - The data refresh is a word compare plus a slice copy, about 1-2 µs.
  - The per-use set is the dominant term: BF-041 measured 5-10 µs at 8-128 descriptors and 208-246 µs at 4,096 on lavapipe. S2 (BF-322) needs that same set for its per-use fault record, so this lane adds only about 3 µs on top of S2.
- **What it can't take exactly at that cost:** a moved snapshot served from a **copy**, i.e. outside the space. Its table range keys the table (GBM:3702, BR:159/179), so each use needs a new table and a set pointing at it. That stays refused in the first step.
- **The change** is one PR after BF-322's S1 (port #6636) and S2 (per-use fault record and set). Call it **S2m**: match snapshots by `(address, size)`, accept unmatched new snapshots that are live in the same space, and let BDA builds take moved data words.
  - With S2m, sibling draws of a key share one build. BF-322's S3 (several builds per key) becomes a fallback for whatever the first boot still shows.

## 1. How a BDA draw reads its snapshots

**From the driver to the build:**
- XD:1081-1084 makes one `GuestMemorySnapshot{address, bytes}` per region of `memory`:
  - program code (XD:592);
  - stage capture (`DrawCapture.cpp:121`);
  - draw-cache stage hits (XD:921, 929);
  - vertex decode reads (XD:1001).
- They pass through XD:1273 → `VulkanDevice` → GD:3738/3058 → GD:1893 `make_shared<ShaderResources>(…, snapshots)` → SR:1673-1675 → SAR:143-148: `AcquireRegistered()`, then `AddSnapshot` for each snapshot.
- **The list matters only to BDA builds.** Without a `BdaPagetable` binding it is ignored (SAR:143).

**Every place a snapshot's address or bytes enter the build:**

| destination | how | file:line |
| --- | --- | --- |
| **BDA table entry** | Only for a snapshot that lies in no region of the space or build. It becomes its own region, GBM:4996 `regions.push_back({snapshot.address, end, false, {bytes…}, nullptr})`. That region is merged (GBM:5333-5371), copied (`copyRegion` GBM:5737-5791, or the shared `snapshotCopy` cache keyed `{address, size, usage}` GBM:2513-2541), and mapped read-only, GBM:6051-6053 `address = … region.buffer->DeviceAddress(); permissions = Read | …`. **What this decides:**
- For a snapshot inside the space, re-pointing is **not a table operation**. The only state in the build that depends on the moved bytes is the two data buffers, plus bindings already pinned by the content key.
- Refreshing the data buffers per use is exact, because the shader reads only those buffers and push constants for these values. The push constants are already per draw.
- For a snapshot outside the space, the table **does** change with the address (GBM:3702), and the copy's buffer with the bytes (GBM:2513-2541).

## 2. What changes between uses of a ring draw, and what #6636 compares

**What the key forces equal between two draws that find each other's build:**
- the device;
- the stage count;
- each stage's variant id and binding layout;
- the image and sampler words;
- read-only buffers' stride, format and size;
- written or empty buffers' full words;
- the colour-attachment count (GD:1132-1162, SR:2754-2756).

**What may differ:**
- the snapshot list;
- `ShaderData` and `FlattenedSrt` words;
- read-only V# bases;
- target and index ranges (trimmed).

**What BF-105's PC counts add** (2,295 proofs; first failing check: address 2,185, count 108):
- **Address is the first check that fails in 95%.** The proof stops there, so for those draws neither the bytes nor the data words were ever compared. Whether the ring's contents also differ is **not known** from these lines.
- **55% come from 10 keys that each see 9 or more addresses** for the snapshot. That is one per-draw block per key, cycling through at least 9 slots (or 9+ sibling draws). Its size is fixed per key (0x50 or 0x70, from the PM's summary).
- **The 108 count refusals** are a separate issue: the capture shape differs between the hit and compile paths (BF-105 §6).
- **So between uses of a ring draw:**
  - always: the ring snapshot's address, and the user-data word that points at it (a push word, or `ShaderData`);
  - when the constants differ: the `FlattenedSrt` values. That is likely for sibling draws, and possibly not for one draw across frames.
- **Index shift:** the list is sorted by address (p6636 XD:503). A moving slot can also shift the index of every snapshot after it, so an index-by-index compare also fails on static snapshots.

**What #6636's proof compares** (b38ea43841), in `Revalidate` order (p6636 SR:3299-3315):
1. `reusable`;
2. not in use;
3. `CompleteSnapshotWrites(snapshots)`;
4. `SameSnapshots` (p6636 GBM:5639-5658):
   - the **count**;
   - per index, the **address and size**, GBM:5644 `if (snapshot.address != use.address || snapshot.bytes.size() != use.bytes) return false;`;
   - a **live use**: `memcmp` of live memory at the same address;
   - a **copied use**: the region lookup and shape, then `memcmp` against the copy's buffer;
5. `ResumeSpace`: the same space serial, device, registry generation, import epoch and mirrors (p6636 GBM:5666-5707);
6. `proveBuild`: import serials, images, buffers;
7. `SpaceImportsCurrent`.

Then `MovedReadOnlyBuffers` compares the data words and read-only bases, and **any** move refuses a BDA build (p6636 SR:5391 `if (usesBda && !moved.empty()) return std::nullopt;`).
- The build stores per snapshot only `SnapshotUse{address, bytes, live}` (p6636 `GuestBufferMemory.hpp:396-400`); copied bytes live in the copy's buffer.
- It re-copies nothing, never rebuilds the table, and binds its set as built.

## 3. The per-use re-point, designed exactly

**Which snapshots move:** only snapshots that are **live in the build's space** may move.
- That means inside a base region that is an import or a read-only mirror, the same kinds #6636's `SpaceRegions` admits.
- Not an overlay, a unit-shadowed range (GBM:4969), a copied range, or a region of the build's own.

**The proof replaces the index compare with a `(address, size)` match:**
1. Every new snapshot whose `(address, size)` equals a build use is checked as today (live `memcmp`, or copied region and bytes).
2. A new snapshot with no matching use must lie wholly inside a live base region of the resumed space.
   - The test is `baseOverlap` (GBM:4717), a binary search over the space's sorted base.
   - Its bytes are compared with live memory, as `AddSnapshot` does (GBM:4974-4975), with the same unit-shadow and `APS5_NO_SNAPSHOT_CHECK` rules.
   - A new snapshot outside the space, or one that partly overlaps a base region (`BaseOverlap::Partial`), refuses "snapshots".
3. Every **copied** use of the build must be matched. A copy left unmatched would keep a table entry with stale bytes that a run-time BDA read could still reach.
   - Unmatched **live** uses are harmless: their region stays mapped live and nothing in the build depends on them.
4. The count may then differ only in live snapshots. Some of BF-105's 108 count refusals may become reuses as a side effect.

**Where the moved bytes go (the per-use "copy"):**
- No table write and no slot are needed.
- `MovedReadOnlyBuffers` takes the data-role branch (SR:6018-6030) for BDA builds too: the `usesBda` early return at SR:6014 moves below the data-role loop. A read-only `GuestBuffers` element that moved still refuses for BDA in this step.
- `PrepareDrawBindings` (SR:6134-) builds the per-use set for BDA builds as well:
  - it uploads each changed data buffer into a `recorder.DrawUpload` slice and applies the build's `dataPatches` (SR:6155-6163);
  - it binds that slice and S2's per-use fault record in an `AllocateRewritten` set (SR:6241-6246), with `movedOnly` set so that no guest buffer is snapshotted;
  - the table, images and samplers are copied from the build's set unchanged.
- **A data change a patch depends on refuses,** as `MovedReadOnlyBuffers` already does: `if (item.dataWords.empty() && patched) return std::nullopt;` (SR:6027).
- **Push constants need nothing.** They are assembled from the current draw (GD:2269).

**Ordering:**
- **Against the previous use's GPU reads:** each use gets its own upload slice and fault record, and the build's table, images and samplers are read-only. Nothing the previous use reads is rewritten.
  - That is why `RefreshData`'s in-place `vkCmdUpdateBuffer` (SR:5089-5101) is **not** used. It writes the build's own buffer, would need the previous use complete, and isn't allowed inside a render pass.
  - The `InUse` refusal goes away only with S2 (one fault record per build today: p6636 `BdaResources.hpp:62`).
- **Against GPU stores into the ring through BDA:**
  - Not visible today. `PendingWriteOverlaps` reads only `batch.writes` (`Recorder.cpp:3142-3151`), and address-based work has no `Pending` source (BF-322 §3).
  - So a capture can read a ring slot before an in-flight BDA store lands. **A fresh build has the same order** (its capture runs first), so reuse adds no hazard.
  - The live `memcmp` doesn't catch it either: both sides read the same stale memory.
- **Against the recorder's pending writes:** #6636's `CompleteSnapshotWrites` (6e5b5bdf4b, p6636 SR:3301 and 2497-2505) syncs recorded GPU writes over the draw's snapshot ranges before the proof.
  - It takes the new list, so moved slots are covered.
  - Mirrors are refreshed per use in `ResumeSpace` (p6636 GBM:5691-5703).
- **The table: no fresh table and no slice.** With only live snapshots the build has no regions of its own, and the table is the space's (GBM:6182, 6192), which `ResumeSpace` proves is the same space.
  - A moved **copy** would need a new `AddressTableKey` (GBM:3702) → a `BdaResources` hash and `memcmp` of about 1,200 ranges, or a new table buffer on a miss (BR:159-200).
  - The per-use set would then point at that table. There is no per-use slice: the table is bound at offset 0 (BR:227), and a slice would need a dynamic binding, which is a recompiler change.

## 4. Per-use cost

| part | what it does | µs per use | source |
| --- | --- | --- | --- |
| moved-snapshot check | `baseOverlap` binary search over about 1,200 base regions (about 11 steps) + `memcmp` of 0x50-0x70 bytes | **about 1** (estimate) | GBM:4717, 4974; the space size from BF-322 §3 |
| matched snapshots | the existing `memcmp` | unchanged: BF-322's 170 µs per draw for all snapshots, which S4 (index) removes | BF-322 §2 |
| data-word compare | `MovedReadOnlyBuffers`' vector compare of `ShaderData`/`FlattenedSrt` words | **< 1** (estimate) | SR:6018-6026 |
| copy | `DrawUpload` slice + `memcpy` of each changed data buffer (the folded block: tens to hundreds of bytes) | **about 1** (estimate) | SR:6156-6160 |
| table | live moves: **0** (space-serial fast path). Copied moves: about 10 µs of hash and compare, plus a buffer on a miss (unmeasured); refused in S2m | 0 | GBM:6182; BR:122-200 |
| descriptor set | `AllocateRewritten` + rewrite: **5-10 at 8-128 descriptors, 107-131 at 2,048, 208-246 at 4,096** (BF-041 `prepare`, lavapipe). It scales with the image table | **shared with S2** | BF-041 §2; SR:6241-6246 |
| fault record | S2's per-use slot (#8963's 32-byte slot): reset and read at completion | about 1 (estimate), S2's | BF-322 S2 |

**Verdict: the re-point is as cheap as the `memcmp`.**
- It adds about 3 µs per use on top of the per-use set S2 already pays.
- The per-use set itself stays under 300 µs up to the largest table BF-041 measured (4,096 descriptors).
- **Unmeasured:** Village's descriptor count per BDA draw. BF-322's 600 µs of stage-B image lookups suggests hundreds to a few thousand.
- **Above about 4,096 descriptors** the set copy is the risk, not this lane. BF-322's S6 (a dynamic fault-record offset), extended to the two data bindings, would remove it.
