## 2. Where the decision is made

### Today

- `Graphics::Draw` decides `recordable` from the recorder, the dump limit and the targets' residency (Draw.cpp ~2153).
- After the resources are built, two more conditions can clear it:
  - stencil replay with fault checks (~2156);
  - `APS5_SYNC_COMPLETION_DRAWS` and `APS5_NO_RECORDER_SYNC_DRAWS` (~2268).
- The stages were compiled earlier, by the driver (`materializeDrawStage`, DrawCapture.cpp:40). With the switch on, that is with `deviceImageTables` set.
- The abort is at ~2414, after the pipeline is made.

### (a) Predict recordability before the stages are prepared (not built)

**What it needs:**
- **A residency predicate** the driver calls before materializing. It would cover `RecordDraws()`, the active recorder, the dump limit, and per colour target the resident rule:
  - samples;
  - tile mode;
  - detiler;
  - `APS5_NO_RESIDENT_TARGETS`;
  - and for a linear target, an existing host import.
- **The real lookup can't run then.** `CachedStorageSurface` and the `Require`s in `refreshResidentTarget` create or refresh images under the GPU mutex, and the draw finisher's capture does not hold it. So the predicate is a second copy of the rule.
- **Changes in the draw cache:**
  - A predicted-unrecorded draw that hits an entry holding device-table variants must skip that hit. This applies to matched, data-candidate and stage-data hits.
  - Its CPU variants must not become the draw key's entry. Otherwise the next recorded draw with that key gets the CPU variant: a permanent fallback for that key.
  - That touches `lookupDraw`, `cacheDrawStages` and the variant validation.

**Where it predicts wrong, so today's throw stays as the safety net:**
- a target lookup that throws ("stays non-resident");
- a linear target whose import comes or goes between capture and a pipelined commit;
- the reasons decided after the resources are built.

**Cost:**
- **Code:** about 20 lines in Graphics, 5 in the driver, and 20–30 in the cache files. That is about the same size as (b) or larger, in more files, and it is not exact.
- **Runtime:** a cheap check on every draw. An unrecorded draw compiles only its CPU variant, once, and later hits it in the draw cache.

### (b) Re-prepare at the throw (chosen)

**Graphics** (`Graphics/include/Draw.hpp`, `Graphics/src/Draw.cpp`):
- New type `UnrecordedDeviceImageDraw : std::runtime_error`.
- `Draw` throws it, with today's message, at the one point where `recorded` is final. That is after the resources are built and before anything is recorded or the resource cache is filled.
- The old `Require` (~2414) now only checks that the device has its table.

**Driver** (`Execution/src/Driver/Draw/Draw.cpp`, `DrawCapture.cpp`, `include/Driver/Driver.hpp`):
- **New member `Driver::drawStages`,** used by the three `Graphics::Draw` call sites. On the exception it:
  - re-materializes each stage whose result has `deviceImageTables`. A new `cpuImageTables` flag on `materializeDrawStage` makes it request the CPU target, and the recompiler's cache key already separates the two variants;
  - walks the push cursor as the first pass does. It re-prepares any later stage whose push offset moves, and checks the slot bound;
  - repoints the draw's stages to the new results. In the CPU-resolved indirect loop it writes them in place, and that loop's later records then keep the flag;
  - rebuilds the snapshots and draws again.
- **The push cursor walk is needed without graphics pipeline libraries.**
  - My first build checked only that the push blocks matched, and his `_nogpl` and `_nogpl_heap` failed it.
  - A probe (temporary, removed before the commit) showed why: the device-table variant's push block is **52 bytes** and the CPU variant's is **48**.
  - In VertexTable mode the vertex stage changes size, so the fragment stage's offset moves from 52 to 48 and it is re-prepared too.
  - With GPL the stages have fixed slots and nothing moves.
- **The pipelined commit** now holds the draw's tail (`DrawTail : enable_shared_from_this`) instead of 20 moved fields. That way it can prepare the stages again on its own thread.
  - The commit side writes only the tail's stages, captures, memory and compiled results.
  - The finisher reads only `programResults` after it hands the draw off, so they do not race.
- **No fallback.** Nothing calls the fallback path, and `DeviceImagesServe` is unchanged.
- **The draw cache keeps the device variants.** `cacheDrawStages` ran before the draw, so the next recorded draw of the program keeps the device table, as part (m) shows.

**Cost:**
- **Code:** 5 files, +89 −15.
- **Runtime, only on unrecorded draws with device-table stages:**
  - the device variant's resources are built and dropped;
  - one exception is thrown;
  - per device-table stage, one capture and one recompile-cache hit;
  - then the CPU variant's resources are built.
  - This is paid on every such draw, because the draw cache keeps the device variant for the recorded draws.
- **Measured with a scratch loop** (not committed): `--unrecorded-loop 200` in the harness. It draws 200 times into the non-resident linear target, with 3 rounds per run and 2 runs per switch state, on lavapipe, at 9673cb568 plus the loop. Submit to idle, per draw:

  | switch | rounds (µs per draw) | median |
  |---|---|---|
  | unset | 7,583, 7,267, 7,321, 7,748, 7,687, 8,809 | **7,635** |
  | on (b) | 7,807, 7,532, 7,866, 8,449, 7,842, 8,238 | **7,854** |

  - That is **+0.22 ms (about 3%)**, inside the round spread.
  - The counters show the reason: with the switch on, each round makes **200 CPU table snapshots**, one capture per draw. With it unset each round makes 0, because the draw cache hits.
  - Recorded draws pay nothing new.

### Why (b)

- **Both options can leave no permanent fallback,** but (a) only with the extra draw-cache guard.
- **(b) is the cheaper of the two:**
  - fewer lines and files;
  - no second copy of the residency rule;
  - no wrong-prediction path, so no throw left on a live path.
- **(a) would be cheaper only at run time, and only on unrecorded device-table draws** (about 3% here). Village shows none of those.
