## What was built (PM-094 §2)

### Discovery and logging
- **Where:** `app0-overlay` beside the resolved `app0` directory, which is `HostPath(state, {"app0"})` + `-overlay`, the same convention as `app0.zar`.
- **When it is read:** once, at the first archive-aware resolution of a path whose first component is `app0` (ASCII case ignored).
- **What it prints:**
  - `app0 overlay: <directory>` when the directory exists;
  - `app0 overlay: /app0/<guest path as asked> -> <host file>` the first time each replaced file resolves.
  - Both go through `WriteLogLine(stderr, ...)`.

### Precedence
1. A regular file in the overlay, looked up by its ASCII-folded relative path.
2. The `app0` directory on disk.
3. `app0.zar`.

- **Where it happens:** in `HostPath`, after `ResolveAlias` and before `ProvidedPath`.
- **Which calls use it:** the overlay is consulted when `Resolve` runs with `archived` set. That covers `ResolvePath`, `ResolvePathOrRelinkedModule`, `ResolveArchivedPath` and `chdir`, which are every guest path call.
- **Module flag:** it applies whether or not `module` is set. Read-only `sceKernelOpen` and `sceKernelStat` resolve with `module = true` (`Open.cpp:278-279`, `:425`), so excluding module resolutions would have missed the main read path.
- **Disk-only lookups:** `ResolveDiskPath` (`archived = false`) does not consult the overlay. Its only callers resolve the directory `/app0` itself (`AppArchive.cpp:40`, `Stdio.cpp:1147`).

### Directories
- **Never from the overlay:** a path with a trailing separator, or a directory, resolves to the base. So `opendir`/`getdirentries` listings, `chdir` and the working directory are unchanged.
- **Overlay-only directories:** an empty directory that exists only in the overlay is allowed, and resolves to the (missing) base path.

### Refusals
Each is a `std::runtime_error` thrown at the first `/app0` resolution, naming the host file, so the title stops. The scan is not marked done after a refusal, so later resolutions throw the same error again.

| condition | message |
|---|---|
| an overlay file with no regular-file counterpart in `app0/` (via the base's own `ResolveHostPath`) or `app0.zar` (`AppArchiveLookup`, not a directory) | `app0 overlay: <file> shadows no file in app0 or app0.zar` |
| a file whose first 4 bytes are `7f 45 4c 46` (ELF), `4f 15 3d 1d` (PS4 SELF) or `54 14 f5 ee` (PS5 SELF), the relinker's `ElfReader.cpp:85` magics in file byte order | `... is an ELF or SELF executable` |
| a symbolic link anywhere in the overlay, including the overlay directory itself | `... is a symbolic link` |
| any other file type | `... is neither a regular file nor a directory` |
| two overlay names that fold to the same path | `... and ... shadow the same file` |
| an unreadable entry | `app0 overlay: cannot read/list ...` |

**Why not `filesystem_error`:** `ResolvePathError_nid_no_patch` turns a `std::filesystem::filesystem_error` into an errno. So every refusal is a plain `runtime_error`, and filesystem calls in the scan use `error_code` overloads.

### Writes
- A write open, rename, unlink or chmod of a replaced path acts on the overlay copy, recorded in `docs/dev/debt/libc.md`.
- A new file under `/app0` that the overlay doesn't replace goes to `app0/` as before.

### Descriptor-relative opens: checked, and they did bypass `HostPath`
- **What I checked on `main` b7a451d62b:** every use of `GetDirectoryDescriptorPath_nid_no_patch`, the helper `*at` calls use to turn a directory descriptor into a host path.
- **What I found:** these sites build `<directory host path> / <guest relative path>` and call the host directly, never `HostPath`:
  - `libkernel/File/src/Open.cpp` `OpenInDirectory_nid_no_patch` (openat) and `StatInDirectory_nid_no_patch` (fstatat);
  - `libkernel_sys/Export.cpp`: `readlinkat`, `mkdirat`, `fchmodat`, `unlinkat` and `renameat` (both sides).
- **Uses that stay as they are:** directories only, so the overlay never applies:
  - `fchdir` (Export.cpp:410);
  - `fdopendir` (`libSceLibcInternal/Directory.cpp:15`).
- **Other path routes:** `realpath` (`libc/src/RealPath.cpp`) builds guest names lexically and resolves each through `ResolvePath`, so it never maps a host path back to a guest path and doesn't leak the overlay location. Everything else (`git grep 'Resolve.*Path.*_nid_no_patch'`) goes through `Resolve`/`HostPath`.
- **Fix:**
  - A new libc export, `AppOverlayPath_nid_no_patch(native)`, maps a host path inside the resolved `app0` (component-wise, ASCII case ignored, `..` refused) back to `app0/...` names and asks the same overlay table.
  - All 7 sites pass their combined path through it. This adds one line per site.
  - It returns at once when the overlay was read and is empty.
- **Proof it is needed:** red run 2 below.
