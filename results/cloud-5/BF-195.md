**Source of the answer:** the tree, in three places.
- **The library's debt file.** `docs/dev/debt/libSceNpCppWebApi.md`, entry `sce::Np::CppWebApi`, says: "every request entry point (API calls, transaction `start`/`getResponse`/`readData`, the `*Factory::create`s) returns `SCE_NP_WEBAPI_ERROR_NOT_SIGNED_IN` offline". The constant comes from shadPS4 `np_error.h` and fpPS4 `np_error.pas`, as that entry records.
- **The `InGameCatalog2V5` entry** in the same file says the same for that family: "transaction `start`/`getResponse*` fail `SCE_NP_WEBAPI_ERROR_NOT_SIGNED_IN`".
- **The neighbouring functions in `Export.cpp`, which already return it:**
  - all 18 other `TransactionBase<…>::start` overrides on main, for example the Leaderboards `GetRankingResponseBody` one;
  - all 9 other `Transaction<…>::getResponse` overrides and all 6 `getResponseHeaders`;
  - the same API's `DataApi::downloadData`;
  - InGameCatalog's `ContainerApi::getContainer`, which is the call that fills the `Vector<Container>` transaction.

**Kept as throws (8):** the destructors, which are dropped from the PR:
- InGameCatalog V5: `IntrusivePtr<Product>`, `IntrusivePtr<Container>`, `IntrusivePtr<Vector<IntrusivePtr<Sku>>>`, `IntrusivePtr<Vector<IntrusivePtr<Product>>>` and `IntrusivePtr<Vector<IntrusivePtr<Container>>>`;
- TitleCloudStorage V1: `IntrusivePtr<GetMultiDataStatusesResponseBody>`, `IntrusivePtr<Owner>` and `IntrusivePtr<Vector<IntrusivePtr<DataStatus>>>`.

Why they stay throws:
- **What already works:** all 8 bodies call the shared `ReleaseIntrusivePtr`. It already handles:
  - a null pointer;
  - a reference that is not the last;
  - the last reference of a pointer that has a deleter.
- **The one throwing branch:** the last reference of a pointer with **no deleter**.
- **No model in the tree:** that branch is the same for every instantiation. All 59 `IntrusivePtr` destructors on main call `ReleaseIntrusivePtr`, and all 59 are todo. None, merged #8264's included, gives the no-deleter case an answer to copy.
- **Where such objects come from:** nothing the library creates has a null deleter.
  - The constructors give a null object.
  - `Vector` bodies created by `pushBack` get `DestroyVectorBody`.
  - The pointer/deleter constructors store the title's deleter.
  - Every factory and API call fails offline, so no response object is ever created.

  So a pointer without a deleter can only hold an object the title built itself.
- **The debt file already records the gap.** The `IntrusivePtr` entry says: "destroying the object needs its destructor and the `LibContext` allocator, which are not implemented". PM-088 says the same: it needs "object layouts from a title's bundled module".

Any answer, whether freeing the object, leaking it or ignoring it, would be a guess. The rows keep throwing, and the existing entry still describes them.

**Neighbours still throwing (not in this batch):**
- the constructor, destructor and `finish` of both transactions;
- `ParameterToGetMultiDataStatusesByUser` (constructor, `initialize`, `setfields`, `terminate`, destructor);
- `ParameterToGetContainer` (constructor, `isInitialized`, `setserviceLabel`).

These are PM-088's silent-stub class, so CONTRIBUTING wants a title that needs them. A title that reaches these `start` calls has to construct the transaction first, and the constructor still throws.
