## Cause

- **`fastRevalidate` never asks the multisampled-target registry.** For each texture it checks:
  - release and depth planes;
  - write stamps (`CollectWrites` / `UnchangedSinceAll`);
  - DCC keys;
  - the pending storage-image registry;
  - eviction.
- **`MultisampleTargetView` writes no guest memory.** It adds guarded ranges to `MultisampleTarget.cpp`'s `guarded()` registry, so with watched imports every check above still passes and the reuse is accepted.
- **Only the full walk saw it.** Its lookups (`cachedTexture` → `RequireNoMultisampleTarget`, and `cachedStorageTexture`) throw, and Revalidate counts that as a refusal that threw, which is what the test expects.
- **Main's 67575aae8 closes the gap before either proof.** In `proveBuild`, every ordinary described range (sampled `texture` and `storage` entries, not image-table ones) goes through `RequireNoMultisampleColorTarget` before the fast proof or the full walk. Address-based and non-address builds share `proveBuild`, so it covers both.

## Fix and its per-proof cost

- **No new driver code.** The fix is main's guard, already in commit 1.
- **Cost of that guard per proof:** one `anyGuarded` atomic load per ordinary described range while no multisampled color target is guarded. While any is guarded, it is a shared lock plus a linear scan of the guarded ranges per described range, on every proof.
- **An optional optimization I prepared but did not apply.** A guard serial, bumped in `guard()`, with the proof rescanning only when the serial moved since its last proof (one atomic load per proof). It would only matter if MSAA titles show this scan in profiles, and as written it would also send image-table builds to the full walk. I left it out because 67c719022 deliberately exempts tables.
