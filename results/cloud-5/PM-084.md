## How a packet drain happens and is counted

- The packet loop drains at `Driver/Packets/PacketExecution.cpp:268` when the pipeline is busy and `keepsDrawPipeline` (`:37-73`) does not keep the packet. Before that, `:242` turns labels (and, with `APS5_PIPELINE_DMA`, DMA_DATA) into ordered items, and `:248-266` answers a WAIT from a pending label or a value already satisfied.
- `DrawPipeline::Drain` (`Driver/Draw/DrawPipeline.cpp:203-218`) counts only drains that found the pipeline busy. It records the opcode for every reason, not just `Packet` (`:215`). So the "packet drains by opcode" list also includes the `Capture`-reason drains that pass `0x15` (`Driver/Memory/BufferFill.cpp:245`).
- From the task's numbers, a packet drain waits 522/260 = 2.0 ms to 726/354 = 2.05 ms on average. An indirect drain waits 2390/119 = 20 ms to 2504/140 = 18 ms.

## Sizing

- **The bounds are upper bounds on worker wait removed, not on frame time.** Removing a drain does not remove the committer's work; it only lets the worker run ahead.
- **What the gain depends on.** If the committer is near saturation, the wait moves to "waiting for room" in `Enqueue` (`Driver/Draw/DrawPipeline.cpp:90-98`). If indirect drains remain, it moves into the next indirect drain, which then finds a fuller queue. The indirect drains run 119-140 per 10 s at 18-20 ms each, so until #1896 lands they will absorb part of what the packet changes free.
- **Committer busy % is needed to judge.** #1896 adds it to the `[draw] pipelined` line.
- **Overall:** 0x50 is about 80% of the packet-drain time; 0x15 is next at about 15%; 0x40 and 0x93 together are under 5%.

## Harness (`exp/packet-drain-study` = `d50a51eb01`)

**What it is:** `tests/execution/PacketDrainStudy.cpp`.
- **Probe method:** each probe enqueues a pipeline item that holds 32 bytes of guest memory until released. It then submits one packet on queue 0, followed by a RELEASE_MEM marker. A probe "passes" if the marker becomes a pending label with no drain request; it "drains" if a drain request appears first.
- **Idle-pipeline probes:** these count drain requests with nothing held. They show whether `Dispatch.cpp:138` is reached, since that drain call is unconditional.
- **ctests:** `agc_driver_packet_drain_study` (default), plus `_dma` and `_dispatch` for the two switches.

**Run:** cloud-5 (Ubuntu 24.04, GCC 13.3, lavapipe 25.2.8, 4 vCPU), build of `d50a51eb01`, `ANYPS5_NO_SHADER_CACHE=1`, pipeline depth 8. The three ctests passed 5 times out of 5 each (15/15 runs, about 0.11 s each).

## Recommendation: first piece

**0x50: make the ordered DMA items the default.** The code already exists, and on these counts it is about 80% of the packet-drain time.

1. **No-code A/B first.** A tester runs the RE Village menu scene on `main` with and without `APS5_PIPELINE_DMA=1`, with `APS5_PROFILE_DRAW=1`, on the same machine. Compare the `[draw] pipelined ... drains:` lines (packet count and ms, and 0x50 count), the indirect drains (to see how much wait just moves there), `tools/trace_digest.py` summaries, and the picture. If 0x50 drops and frame time does not improve, the committer is the bound, and #1896 or committer speed comes first.
2. **Close the inline path, then flip the default.** In `keepsDrawPipeline` case `0x50`, keep only prefetch and zero bytes, so that a DMA `enqueueDmaPacket` declines drains instead of running inline ahead of queued draws. Alternatively, use #8366's `Touches` (writes and reads). Then make `enqueueDmaPacket` default-on with an off switch, as `4a2b7d34f2` had it. Validate with `agc_driver_pipelined_dma`, `agc_driver_pipelined_dispatch*`, this harness's three ctests, and `^agc` with `ANYPS5_REQUIRE_VULKAN=1 ANYPS5_NO_SHADER_CACHE=1 VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` against `main`.
3. **Ask ivica00** (author of #6208 and `bf47f840ef`) why it was made opt-in before flipping it. I could not see the PR thread.

**After that**, by size and risk:
- the one-condition queue-0 gate fix for 0x15 (harness-confirmed);
- an A/B of `APS5_PIPELINE_DISPATCH=1`;
- COPY_DATA as ordered items;
- 0x93 last, since the worker blocks in those waits anyway.
