## The new line

```
[mem-census] pipelines (driver memory): graphics N live (store A of P pipeline objects, outside the store B; monolithic M, linked L; owners: pipeline objects …, library …, utility …), library parts C live (built …), compute D live (dispatch …, utility …), modules K live (library-retained R; created by pipeline objects …, library …, dispatch …, utility …); probe (rss|private delta of copies …): +X KiB per monolithic (…), +Y per linked, +Z per library part, +W per compute, +V per module; est T MiB
```

- **Live counts:** every `VkPipeline` and `VkShaderModule` handle created through the device's census-wrapped resolver, until destroyed. Each is tagged by the thread-local owner at creation: the `Pipeline` constructor, the pipeline library, compute dispatches, or anything else ("utility").
  - Graphics pipelines are split by their create-info. `LIBRARY_BIT` means a library part, a `VkPipelineLibraryCreateInfoKHR` with libraries means linked, and otherwise monolithic.
  - "store A of P pipeline objects" is `PipelineStore` entries out of live `Graphics::Pipeline` objects; "outside the store" is the rest (in-flight `Kept` draws, uncached collisions).
  - **Draw-cache variants own nothing:** `DrawRecipe` holds `std::weak_ptr<Graphics::Pipeline>` (`Recipe.hpp`), and the dispatch `Recipe` holds `std::weak_ptr<ComputePipelineObjects>`. So "variants B" in the task's template is always 0, and the line shows store versus outside the store instead.
- **Probes:** a census bumps an epoch.
  - The next `vkCreate*Pipelines` or `vkCreateShaderModule` call of each kind (monolithic, linked, library part, compute, module) first creates 4 copies (16 for modules) from the **same create-info**, with no pipeline cache and under the census mutex. It measures the process's private bytes on Windows (RSS on Linux) across the copies, then destroys them, then makes the real call.
  - This deliberately departs from the descriptor-pool probe, which probes at the census point. Rebuilding a graphics create-info later would mean deep-copying its whole `pNext` and state chain. Copying the call in flight measures a representative variant exactly, at no copy cost.
  - **Effect:** the numbers come from the first object of each kind created after the previous census, not from an object live at the census point. A kind created only before the first census and never again shows its last probe; a kind never created shows "not probed".
  - `est` = sum over kinds of (bytes per copy × live count).

## May they be destroyed right after `vkCreate*Pipelines`? (code reading; no fix in this task)

**What the spec says** (Vulkan-Docs `main`, 1.4.366 of 2026-10-23, fetched from GitHub; the Khronos registry is blocked from this session):
- `chapters/shaders.adoc` L1667, under `vkDestroyShaderModule`: "A shader module can be destroyed while pipelines created using its shaders are still in use."
- `chapters/pipelines.adoc` L728-L731: `VK_PIPELINE_CREATE_RETAIN_LINK_TIME_OPTIMIZATION_INFO_BIT_EXT` "specifies that pipeline libraries should retain any information necessary to later perform an optimal link with `VK_PIPELINE_CREATE_LINK_TIME_OPTIMIZATION_BIT_EXT`". VUIDs 06609 and 06610 require the libraries of an LTO link to have been created with it.
- I found no text that excepts pipeline libraries from the destroy rule.

**What that means for the code:**
- On that reading, the retained library modules could be destroyed right after the part is created. The part (created with `RETAIN_LINK_TIME_OPTIMIZATION_INFO`) is what the later optimal relink reads, not the module.
- The lines that would change are in `PipelineLibrary.cpp` (main numbering):
  - L245-L252 (the `if (optimize)` move into `device.modules`): destroy instead of keeping;
  - L44 and L362, which become unused.
  - In `Pipeline.cpp`, L751 would then free every `_modules` entry, as it already does when `optimize` is off.
- **Driver-behaviour caveat:** the retention may be a workaround for a driver that reads the module at relink. The shallow history can't confirm or rule that out. Any fix should be tested with the LTO relink on NVIDIA, the tester's driver.
- **Parts:** library parts are never evicted, so they grow with variants whether or not modules are kept. The census now shows both counts.
