## 2. The cause: (a)

**The failing interleaving,** with lines at 73f4f7e06e:
1. `StopsWithinAnImage` (`IdleStoreYields.cpp:148`) submits one packet with two dispatches over the same 8 MiB surface:
   - `StoreRowZeroCode` writes row 0, in the first 4 MiB piece (:156);
   - `StoreFarRowCode` writes row 1000, in the second piece (:157).
2. `SubmitAndWaitForPending` (:110-117) returns 5 ms after `StorageTexture::AnyPending()` turns true (:114, :116).
   - `AnyPending` turns true when the **first** dispatch is recorded: `markLayersPending` (`Texture.cpp:3921`) puts the image on the pending list at :3989.
3. The second dispatch runs a shader the queue hasn't seen ("preparing its artifact at dispatch").
   - `Driver::dispatch` prepares it (`Dispatch.cpp:586`, `PrepareDispatch`, which builds the pipeline) **before** it takes the GPU mutex (:608).
   - On llvmpipe, without a warm pipeline cache, that takes more than the 5 ms.
4. The test takes the GPU mutex (:163) while the far-row dispatch is still being prepared. Every check inside the lock passes:
   - the stopped `FlushAllPendingUntil` (:166) stores the first piece;
   - `FlushPending(split, …)` stores the rest of the image;
   - nothing is left pending.

   But the image holds only dispatch 1's results, so the second piece goes to guest memory with the far row still `0xdeadbeef`.
5. After the lock is released, the queue records the far-row dispatch, and the image is pending again.
   - `Contains(split, end)` (:172) reads guest memory. When that read comes before the dispatch is recorded, it finds no `Stored` word and the `Require` throws.
6. **The crash:** the throw unwinds `StopsWithinAnImage`, which frees `Surface::storage` (and skips `mutation.Remove`, :174).
   - `~ShutdownGuard` (:185-186) then joins the queue worker.
   - The worker records the far-row dispatch, `StorageTexture::refresh` compares the image with the freed guest range, and the process gets SIGSEGV.

**The evidence that it is (a) and not (b):**
- I built a temporary diagnostic of the test (not pushed). When the check fails, it calls `AgcDriverWaitIdle_nid_postfix()` and re-reads both halves.
- I ran it twice, 30 runs each. The first batch had 10 failures, but my script kept only each run's last line. The second batch kept the diagnostic line, and all 9 of its failures printed:

  ```
  DIAG within: before wait low=1 high=0, after WaitIdle low=1 high=1
  ```

- So the far row reaches guest memory once the queue has recorded and run its dispatch. Nothing is lost; the test only looked too early.
- None of the 60 diagnostic runs crashed, because the diagnostic waits before the surface is freed.

**Why it isn't (b):**
- `FlushAllPendingUntil` (`Texture.cpp:4680`) stops only between 4 MiB pieces (:4692), and what it doesn't store stays pending.
- In `Driver::run`, after `StoreIdleResults(true, stop)` (`QueueWorker.cpp:219`, `VulkanDevice.cpp:2487-2492`) returns because work is queued, the worker breaks out to run that work. The pending rest is picked up by the next idle period (`idleResultsPending`) or by any flush of that range.
- The in-lock checks show the stopped store and the store after it together leave nothing pending.

**Lavapipe:**
- The race needs the second dispatch's preparation to outlast the test's 5 ms. On llvmpipe that preparation includes compiling the compute pipeline on the CPU.
- The rate swings from 0/30 to 17/30 with llvmpipe's own shader cache alone, so the failure is timing, not lavapipe behaviour.
- **Any driver whose first pipeline build for that shader takes more than about 5 ms can hit it.** That includes a fresh runner, and ctest sets `ANYPS5_NO_SHADER_CACHE=1`. `vkQueueSubmit` timing plays no part: the window closes before anything is submitted.
- **`StopsBetweenImages` has the same window,** but both of its dispatches use `StoreRowZeroCode`. The second dispatch's preparation is then quick, and I saw no failure there.

## 3. The fix (test only)

**The change:** `SubmitAndWaitForPending` becomes `SubmitAndWaitIdle`.
- It submits, calls `AgcDriverWaitIdle_nid_postfix()`, which waits until every accepted submission is processed (`Lifecycle.cpp:237`), and then requires `AnyPending()`.
- The 1 ms poll and the 5 ms sleep go, and with them `<chrono>` and `<thread>`.
- Both sub-tests use it.

**What stays the same:**
- After the wait, the image is still pending: `VulkanDevice::WaitIdle` stores only drawn linear targets, as `StorageReadDuringIdleStore` already relies on.
- The test still takes the GPU mutex before the 50 ms quiet period ends, and still checks that a stopped store leaves the rest pending and that the next store brings both rows to guest memory. Its intent and its checks are unchanged.

**What remains:**
- The fixture's lock still has to win against the queue's own idle store, which starts after 50 ms of quiet once the queue is idle. The old fixture had the same margin, and the first sub-test's message names that case.
- I saw no such failure in 100 runs under 4-way load.
