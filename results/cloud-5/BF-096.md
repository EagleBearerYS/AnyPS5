## Structure

`ShaderResources::captureValidation` (`Graphics/src/ShaderResources.cpp`) now finds each object's newest record with one walk over the log, through a flat open-addressing table:

- **Table:** entries of (object, record index), sized to a power of two of at least twice the log, 16 minimum, so it is at most half full.
- **Hash:** Fibonacci hashing of the object pointer (`* 0x9e3779b97f4a7c15`, top bits), with linear probing.
- **Empty slots** are marked by the index (`Unrecorded`, the largest `size_t`), not by the pointer. So a null object is looked up like any other, exactly as main's search compares `it->object == object` for a null texture.
- **One pass, newest first:** the log is walked once from its newest record to its oldest. The first record seen for an object takes its slot, which makes it the newest, the same record main's backward search returns.
- **Fill:** `validatedTextures` is then filled with one probe per texture. An object with no record keeps the empty entry, as on main.
- **Cost:** O(records + textures) per capture, against main's O(textures × records).
- **No allocation per capture:** the table is a thread-owned `std::vector` (`ShaderRecompiler::ThreadOwned`, like `lookupLog()`), reassigned per capture without reallocating.
- **Retained memory:** it keeps at most 4 × `LookupLogBound` slots = 4,096 × 16 B = 64 KiB per thread. That covers a log of up to 2,048 records, Village's ~2,000-texture builds included, without reallocating. A larger capture drops its table afterwards, as the log itself does after a build past the bound.

**The seam for the test** (no behaviour change):
- The record struct moved from the file-local `LookupRecord` to `TextureLookupRecord` in `ShaderResources.hpp`, with the same fields.
- `captureValidation()` now calls a private static `captureValidation(log, sampled, validated)` and then clears the log, as before.
- `ShaderResources` names a `friend struct ShaderResourcesTestAccess`, the pattern of `VulkanDeviceTestAccess`, so the test can call the static with logs it builds itself.
- That is what makes the cases below reachable. Past the bound, the log only exists inside a build scope, so no other test can see it.

## Tests

**New ctest `agc_driver_validation_capture`**, from `tests/execution/ValidationCapture.cpp`:
- It is registered by the execution-test glob. The `${agcExecutionTests}` loop gives it the usual environment and the WIN32 `PATH` modification, so no separate PATH entry is needed.
- It needs no Vulkan device. It builds logs and texture lists from distinct addresses (non-owning `shared_ptr<Texture>`s, never dereferenced) and calls the static capture through `ShaderResourcesTestAccess`.
- Every texture's result is compared with a reference "last record of the object in the log", plus explicit checks.

The pinned cases:
- **Past the old 1,024 bound:** a build of 1,500 objects, each with its record.
- **Newest wins:**
  - an object logged before, inside and after the build takes the record after it, at both of its texture slots;
  - an object with an older record before its build record takes the build record;
  - the last object takes a record logged after the build.
- **Fields:** a record's depth flag, DCC keys and source pointer are carried over, and `collected` is 0.
- **Absent:** a texture absent from the log gets an empty entry (`valid == false`, every field zero).
- **Null:** a null texture takes the record of a null object, which is main's comparison.
- **Output reset:** the output vector is reset (it starts with a stale element).
- **Same thread:**
  - a three-record capture after the 1,500-record one keeps no stale record, so an object only in the earlier log stays empty;
  - an empty log gives no texture a record, and no textures give no records;
  - a 4,096-record capture with every seventh object logged twice, then a three-record capture again, exercises the table shrink.

- **Setup:** per size, a log of N records in texture order and N textures, as a build leaves them. 3 warm-up captures. Then 5 samples, each the mean of at least 3 captures and at least 50 ms. The median of the 5 is reported, in µs per capture.

- **2,000 textures:** ~0.70 ms → ~0.04 ms per build or full walk.
- **4,096 textures:** ~2.9 ms → ~0.085 ms.
- **16 textures:** about 10–20 ns slower per capture, most likely the table setup. At 16 the change is a wash, not a gain.
- **Branch cost:** linear in the count, about 20 ns per texture. That includes copying each record into `validatedTextures`, which main does too.
- **Against earlier numbers:** BF-039's in-harness figure for main at 2,000 was 1,100 µs. This loop measures the capture alone, on records laid out contiguously, so main's absolute numbers here are lower; the trend is the same.
