# BF-056: K4's GPU half with the GPU waited for (BF-046's arms A and B, `VILLAGE_GPU_SYNC=1`), cloud-5

RESULT:
- **K4's GPU half, with the GPU waited for** (`VILLAGE_GPU_SYNC=1`, lavapipe, 3 runs × 20 frames):
  - On the Village shape (table index), arm B's GPU per frame is **11,924.8 ms against arm A's 10,050.2 ms: +18.7%** (rasterizer CPU per draw 27,584 against 23,266: +18.6%).
  - That is under 30%, so K4's GPU half does not trip here. BF-046's "−50%" was saturation; the real figure is +19%.
- **It trips as soon as texture variety stops dominating** (step 3, same 4 textures in every draw): B is **51–73× A** (5,417 against 106 ms immediate, 7,499 against 103 ms constant). On lavapipe, today's path costs about 100× more GPU when every draw samples different textures; B's path costs a large fixed amount per draw.
- **The shader-side differences:**
  - B's run-time image path (run-time resolve and dynamically indexed heap sampling): about 12.3 ms of rasterizer CPU per draw even with immediate T#s (B 12,636 against A 334).
  - The run-time T# read from the table: +2.08 s of GPU per frame, about 1 ms of GPU per sample (constant − immediate on B). On A that difference is noise.
  - These are lavapipe numbers; the PC should repeat steps 2 and 3 on a real GPU.
- **Driver CPU per draw on the Village shape:**
  - A 544.5 = worker 417.4 + committer 138.6;
  - B 613.3, all on the worker.
  - Of this, **321.5 (A) and 438.0 (B) are worker CPU burned inside the GPU wait**. The driver's own CPU outside the wait is **A 223.0 and B 163.3**.
- **Branches:**
  - `exp/bf056-main` 4126b1fa2, on `exp/bf046-main` b7d6d98610;
  - `exp/bf056-fable` 7d6d5ee54, on `exp/bf046-fable` f46119d83c (his commits unchanged).
  - Each carries a41ab28ad (cherry-picked), 1a90ccb64's timing hunk and a new per-thread CPU split at the GPU wait. The harness file is identical on both.

## Setup

- **Machine:** cloud-5: Xeon @ 2.10 GHz, 4 vCPUs, 15 GiB. BF-046 ran on cloud-2 at 2.80 GHz, so absolute numbers differ from its tables. Compare arms within this file.
- **GPU:** lavapipe (llvmpipe, LLVM 20.1.2).
- **Build:** CI's Linux configure (Release, Ninja, gcc 13.3, ccache, SPIRV-Tools on, Wild 0.10.0). Only `libs` and `agc_driver_village_draw_cost_tests` were built per arm, as BF-046 did; fable-void's branch has one unrelated link failure.
- **Settings:** BF-046's own.
  - As the unprivileged `runner`, one run at a time on an otherwise idle machine, stdin /dev/null.
  - Environment: `ANYPS5_REQUIRE_VULKAN=1 GALLIUM_OVERRIDE_CPU_CAPS=avx ANYPS5_NO_SHADER_CACHE=1 LP_NUM_THREADS=2`, plus **`VILLAGE_GPU_SYNC=1`**.
  - `--cost 20`: 8 warm-up frames and 20 measured frames, 850 draws each.
  - Each arm's check passes first: "full-target draws sampled 1 to 4 textures through the T# table".
- **What the columns are:**
  - **GPU ms per frame:** the harness's GPU wait, from the frame's submission returning to `FlushGpuWrites` returning (median over 20 frames).
  - **Rasterizer CPU per draw:** lavapipe's two `llvmpipe-N` threads' CPU per frame ÷ 850.
  - **Driver CPU per draw:** the `qworker 0x0` and `draw-commit` threads' CPU per frame ÷ 850.
  - **"Inside the wait":** the part of driver CPU spent after the submission returned, while the GPU drained. The harness splits every thread's CPU at that point; see commit 3 below.

## Step 4: K4's GPU verdict

**On the Village shape (table index): B's GPU per draw is 18.7% above A's** (11,924.8 against 10,050.2 ms per frame; rasterizer CPU 27,583.8 against 23,266.0 µs per draw, +18.6%). That is under 30%, so **K4's GPU half does not trip on this harness**. BF-046 reached the same verdict, but the magnitude was wrong: +19%, not −50%.

**It does trip as soon as texture variety stops dominating.** With the same textures in every draw, B is 51–73× A (5.4–7.5 s against 0.1 s per frame). Village's real draws fall somewhere between these shapes.

**The shader-side differences** (rasterizer CPU per draw on lavapipe):
1. **B's run-time image path itself:** about **12.3 ms per draw** (immediate: B 12,636 against A 334), even with no table read and the same 4 textures every draw. On B the shader still resolves each sample at run time and samples through the descriptor heap with a dynamic index, where A binds CPU-resolved descriptors.
   - My reading, not verified on this machine: llvmpipe takes a generic, unspecialized sampling path for dynamically indexed image arrays.
   - My LA-004 harness saw the same kind of cost on the lane A device path: 4.3 ms of GPU per draw against 0.17 ms for CPU-resolved binding.
2. **The run-time T# read from the table** (`s_load_dwordx8` at the sample's index): about **4.9 ms per draw** (constant against immediate), about 2 ms per sample on lavapipe.

Both are lavapipe numbers. Lavapipe's relative cost of dynamic heap indexing need not carry over to a real GPU, so the PC should repeat steps 2 and 3 there before K4's GPU half is decided.

## Notes

- **Exit time:** with the GPU waited for, every run exited by itself. Whole runs, check and 28 frames included, took 10 s (A's variants), 170–240 s (B's variants) and 291–355 s (the table index). My script would have killed a process still exiting 20 s after printing its results, and none was. BF-046's unsynced runs had taken 4–10 minutes to exit.
- **Thread names:** on B, two threads are named `qworker 0x0`. Their CPU is summed as "worker", and the second one carries 33–43 µs per draw.
