## What lavapipe can and can't reach

- **Can't reach the reporter's path.** lavapipe has neither a 2x sample count (`framebufferColorSampleCounts`/`framebufferDepthSampleCounts` are 1 and 4) nor `VK_EXT_sample_locations`. So `agc_driver_sample_order_grid_reference` and `agc_driver_sample_order_recipe_depth_locations` skip (`skipped, the device has no 2x color and depth targets`).
  - The reporter's located 2x `D32_SFLOAT` draw can't run here, so validation couldn't look at the located parts: the located transitions, `VkRenderPassSampleLocationsBeginInfoEXT` and the pipeline's sample-locations state.
- **What does run:** `agc_driver_sample_order` takes `SampleOrders::Depth` and `SampleOrders::Storage` at 4x, unlocated (`SampleOrderPass{order, SwapRegion, {}, false}`). That covers D32_SFLOAT, D16_UNORM and D32_SFLOAT_S8_UINT, the last through all three methods.
  - D16_UNORM_S8_UINT can't be sampled at 4x here.
  - It also covers the copy, the transitions, the descriptor writes, the render pass and the draw itself, so the parts of the reporter's path that don't depend on locations are covered.

## 2. The draw's setup against the spec

1. **The copy image** (`CopyImage`, without `VK_IMAGE_CREATE_SAMPLE_LOCATIONS_COMPATIBLE_DEPTH_BIT_EXT`): **valid.**
   - The flag is required only for a depth/stencil image whose layout transitions carry sample locations, or that is a depth attachment while a pipeline with `sampleLocationsEnable` draws (`VUID-vkCmdDraw-sampleLocationsEnable-02689`). The copy is neither: it is only a copy destination and a sampled image.
   - The target, which has the flag, goes to `TRANSFER_SRC_OPTIMAL` with its `VkSampleLocationsInfoEXT` before the copy and back after, so the copy reads defined per-sample values.
   - `vkCmdCopyImage` has no sample-locations requirement, and sampling the copy as `texture2DMS` in `GENERAL` is allowed: it has `SAMPLED` usage.
   - **One real bug here:** the copy's own first transition (row 03320 above) left the stencil aspect of a combined format untransitioned. The fix is in section 4. The reporter's `D32_SFLOAT` has no stencil, so this isn't their fault.
2. **The descriptors:** **valid.**
   - For `SampleOrderMethod::Depth` only binding 0 is written; binding 1 is left unwritten.
   - `spirv-dis` of `SampleOrderDepth_spv.h` (SPIR-V 1.3): `stencilSource` is declared (`OpVariable` with Binding 1) but never loaded. `OpEntryPoint Fragment %main "main" %gl_FragCoord %gl_SampleID %gl_FragDepth` doesn't list it, and the only `OpImageFetch` reads `%depthSource`. So binding 1 is not statically used, and an unwritten descriptor that isn't statically used is valid.
   - `spirv-val --target-env vulkan1.1` accepts the module, and validation raised no undefined-descriptor error at the draw.
3. **The dynamic stencil state:** **valid.** `VK_DYNAMIC_STATE_STENCIL_WRITE_MASK` and `_REFERENCE` are in the pipeline's dynamic states and set before the draw. With a depth-only format and `stencilTestEnable = VK_FALSE` they have no effect. Nothing requires a stencil aspect to set them.
4. **The render pass and pipeline sample locations:** **valid by reading; not exercised here.**
   - `VkRenderPassSampleLocationsBeginInfoEXT` gives attachment 0's initial locations and subpass 0's post-subpass locations, the same `VkSampleLocationsInfoEXT` (grid {1,1}, `samples` locations) as the pipeline's `VkPipelineSampleLocationsStateCreateInfoEXT`.
   - A {1,1} grid divides every `maxSampleLocationGridSize`.
   - The attachment's image has the compatible-depth flag, as `02689` requires.
   - lavapipe has no `VK_EXT_sample_locations`, so the layer never saw this.
5. **Sample shading:** **valid.** `sampleShadingEnable` with `minSampleShading = 1.0` at 2x, a shader reading `gl_SampleID` (which makes it per-sample anyway), writing `gl_FragDepth` and using `discard` (`OpKill`): all allowed, and `gl_FragDepth` is clamped to the depth range.
6. **The extents:** **valid.**
   - `region = min(pass.extent, target.extent)`.
   - The copy is created at `target.extent` and copied over `region`.
   - The framebuffer and render area are `region`, and the viewport and scissor are `region`, so `gl_FragCoord` stays inside `region` and every `texelFetch` coordinate is inside the copy.
   - The framebuffer is no larger than the target view.

## 3. The index check

- **New mode:** `agc_driver_sample_order_map_indices` (`agc_driver_sample_order_tests --map-indices`, no device needed, in the WIN32 `PATH` list).
- **What it applies:** `mapFor`'s rule (a 0 word means `KeptSampleOrder`; the guest direction uses `InvertSampleOrder`) to:
  - the test's 2x, 4x and 8x orders (`OrderFor`; the 2x one is `{KeptSampleOrder, KeptSampleOrder, 0x76543201, 0x76543201}`, the grid reference's);
  - `SameSetSampleOrder`'s orders for 1,000 seeded random location sets each at 2, 4 and 8 samples. Each pixel holds the same multiset of positions in a random order, and every fourth set draws positions from 0..3, so positions repeat.
- **What it requires:** for every pixel's word, in both directions, the nibble the shader reads (`(map >> (gl_SampleID * 4)) & 7`) for each `sample < samples` is below `samples`, and the samples read every source sample exactly once.
- **Result:** 3,003 orders checked; it passes (5/5 here, and in the sweep). The out-of-range index is closed by a test.

## 4. The fix: fork `fix/agc-sample-order-depth-copy-aspects` = **5a9d89179c**

## For the reporter's 2x `D32_SFLOAT` device loss

Nothing validation saw on lavapipe explains it. The one violation is on combined depth/stencil formats only, and the located 2x path can't run here. In order of likelihood:

1. **Run validation on their own machine.** That machine has 2x and sample locations, so it can reach the located path:
   `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` with synchronization and GPU-assisted validation on (`vkconfig`, or the `vk_layer_settings.txt` above), then `ctest -R '^agc_driver_sample_order_grid_reference$' -V`.
   - A GPU-assisted run may need the 5 s `CommandBatch::Wait` timeout raised, as it did here.
2. **The copy's `DEPTH_STENCIL_ATTACHMENT` usage.**
   - The copy is never an attachment, but with that usage AMD's driver gives a 2x D32 image depth-compression metadata (HTILE).
   - A transfer write into it in `GENERAL`, then a `texture2DMS` fetch from it in `GENERAL`, is the AMD-specific step this draw adds over lavapipe and NVIDIA.
   - Try: create the copy with only `TRANSFER_DST | SAMPLED` usage; or keep the usage but give it the same `SAMPLE_LOCATIONS_COMPATIBLE_DEPTH_BIT` as the target; or move it to `DEPTH_STENCIL_READ_ONLY_OPTIMAL` (or `SHADER_READ_ONLY_OPTIMAL`) for the draw instead of sampling it in `GENERAL`.
3. **Binding 1 unwritten.** It is valid by spec, but writing it (the depth view) for the depth-only method too is a one-line way to rule out the driver touching an unwritten descriptor.
