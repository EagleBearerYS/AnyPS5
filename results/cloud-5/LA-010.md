### The same case with `APS5_GPU_HEAP=1`: lane A could push his GPU mode into its error, and now can't

**Red, as rebased** (the table asks `BindlessHeap::TextureSlot` like any user): the first compute program takes both slots, then a GPU-mode draw whose texture is in its user data (his `HeapDrawSample` pixel program) needs a slot of that kind and stops: `[gpu] driver failure: AGC graphics: the global image heap is full`. That is his D2R error, caused by lane A's entries.

**The fix**, in two commits:
- **05583a730** (in his `BindlessHeap`): `TextureSlot(kind, texture, view, layout, keepFree = 0)` takes a new slot only while more than `keepFree` slots of the kind are free (after a sweep). A texture that already holds a slot keeps it. His callers pass nothing and behave exactly as before. `TextureSlotCap()` exposes the slots per kind. Test: `agc_driver_heap_slots` (`keptSlots`).
- **71a0edd27** (lane A's seam): while `APS5_GPU_HEAP` is set, `DeviceImageHeap::Slot` passes `keepFree = cap − ⌊cap/2⌋`.

**How much of the heap lane A's budget can take:**
- **`APS5_GPU_HEAP` set:** at most ⌊cap/2⌋ slots of each kind, **2,048 of 4,096**, and only from slots GPU mode is not using: if GPU mode already holds more than half of a kind, lane A takes none. GPU mode always keeps at least half of each kind (2,048) to itself, whatever lane A holds. A key that finds no slot it may take falls back as before.
- **`APS5_GPU_HEAP` unset:** nothing else takes texture slots (`writeHeapStage` is GPU mode's only caller), so lane A may use all 4,096.
- The table's entry budget (16,384 entries, half the sampled-texture cache's bytes) is larger than either, so the slot limit is what binds. The Village bench peaks at 256 textures of one kind.
- **What this does not promise:** GPU mode can still hit its own heap-full error if its own stages need more than the half lane A may leave it. Lane A only guarantees it never takes that half.

**Green** (`APS5_GPU_PATH=1 APS5_GPU_HEAP=1`, ctest `agc_driver_device_image_path_heap_full_compute_gpu_heap`):
1. The first compute program asks for both slots and gets 1 (1 inserted, 1 without a slot); it falls back and its next batch reads the right texels through the CPU table.
2. The GPU-mode draw takes the other slot and draws its texel; `HeapStagesTaken` moves, no device prepare.
3. The second compute program meets the now full heap: 0 inserted, 3 without a slot, 1 fallback, right texels through the CPU table next batch.
4. The GPU-mode draw again: right texel. No "heap is full" anywhere.

Unit test `agc_driver_device_image_table_heap_cap_gpu_heap`: a heap of 2 slots per kind gives the table 1 of 5 textures (4 without a slot, 1 fallback), and GPU mode's own `TextureSlot` request for a refused key's texture still gets a slot. With the seam reverted it fails: "takes 1 … (2 inserted, 3 without a slot)". Without `APS5_GPU_HEAP` (`agc_driver_device_image_table_heap_cap`) the table still takes 2.
